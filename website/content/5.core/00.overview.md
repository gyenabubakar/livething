`@livething/core` is a small package that both the client and the server of LiveThing are built on. It is **runtime-agnostic**: it works the same way in a browser, in Node.js, or on Cloudflare, because it uses nothing that only one platform has. The [Client](/client/overview) and [Server](/server/overview) packages depend on it.

Some things live in this package because **both sides must agree on them**. These are your error definitions, the built-in errors, and the meaning of each WebSocket close code. This section is the reference for these shared parts.

## A shared peer dependency

`@livething/core` is a **peer dependency** of both `@livething/client` and `@livething/server`. A peer dependency is a package that another package needs, but that your own project must install. So you install `@livething/core` next to the client or the server. The [installation](/start/installation) commands already include it, for example `npm install @livething/client @livething/core`. After you install it, you import the shared parts from it:

```typescript [shared/errors.ts]
import { CloseCodes, error } from '@livething/core'
```

It has no client code and no server code. It does not use the DOM, WebSocket connections, or storage. This is why you can import it from anywhere, including code that runs on both sides.

## What lives here

| Area                | What it is                                                                                                                         |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **Errors**          | `LiveThingError`, the `error()` factory, and `.matches()`. The client and the server use this same error model                     |
| **Built-in errors** | The errors that LiveThing itself raises, such as `RateLimited` and `StreamAborted`                                                 |
| **Close codes**     | `CloseCodes`, a set of names for the numbers that say why a connection closed                                                      |
| **Wire types**      | `WireFrame`, `Message`, `encodeMessage()`, and `decodeMessage()` for the [wire protocol](/learn/wire-protocol), plus `WIRE_LIMITS` |

These parts are shared because of the **contract**: the one typed description of your API that the client and the server both use. An error that you `throw` on the server is the same error that you check with `.matches()` on the client. So its definition must be the same object on both sides. `CloseCodes` works the same way: both sides give a received code the same meaning.

Sending a close code has different rules on each side. The server follows the rules of the WebSocket protocol. A browser client can send fewer codes, because the browser's own `WebSocket.close()` API allows fewer. The client and the server each check the codes that they send. [Close Codes](/core/close-codes) lists the rules.

The client-side errors (`Timeout`, `Disconnected`, `Dropped`, `StreamCorrupted`, `StreamOverflow`) are defined here too, but client code imports them from `@livething/client/errors`. [Built-in Errors](/core/builtin-errors) lists every built-in error and where to import it from.
