`@livething/core` is the small, runtime-agnostic package both halves of LiveThing are built on. The [Client](/client/overview) and [Server](/server/overview) packages depend on it, and a few things live here precisely because **both sides need them to agree** — your error definitions, the built-in errors, and the meanings of WebSocket close codes. This section is the reference for that shared surface.

## A shared peer dependency

`@livething/core` is a **peer dependency** of both `@livething/client` and `@livething/server`, so you install it explicitly alongside them — the [installation](/start/installation) commands include it for you (`npm install @livething/client @livething/core`). Once it's in, you import the shared pieces from it:

```typescript [errors.ts]
import { CloseCodes, error } from '@livething/core'
```

It carries no client or server code — no DOM, no sockets, no storage — which is why it's safe to import from anywhere, including code that runs on both sides.

## What lives here

| Area                | What it is                                                                                        |
| ------------------- | ------------------------------------------------------------------------------------------------- |
| **Errors**          | `LiveThingError`, the `error()` factory, and `.matches()` — the one error model shared end to end |
| **Built-in errors** | the errors LiveThing ships (`RateLimited`, `StreamAborted`, …) plus the client-side ones          |
| **Close codes**     | `CloseCodes` — named reasons for closing a connection                                             |

The reason these are shared rather than living in one package is the contract idea: an error you `throw` on the server is an error you `.matches()` on the client, so its definition has to be the same object on both sides. `CloseCodes` works the same way: both sides attach the same meaning to a received code. Sending a code is different: the server uses the WebSocket protocol rule, while a browser client is limited by its native `WebSocket.close()` API. Each package validates its own close operation.
