When a WebSocket connection closes, the side that closes it sends a **close frame**. A close frame is a small message with a number (the close **code**) and an optional text (the close **reason**). The code says why the connection closed.

`CloseCodes` is the set of named codes that LiveThing uses, so you do not need to pass raw numbers around. The server sends a code when it closes a connection. On the client, `onClose` receives the code, and the reconnection primitive reads it to decide if it should try to connect again.

Inside a handler, call `ctx.close(code, reason)`. In this version of `send-message`, a banned user's connection is closed with `BANNED`:

```typescript [server/rooms.ts]
import { CloseCodes } from '@livething/core'
import * as v from 'valibot'
import { rooms } from './base'
import { isUserBanned } from './huddle-data'

export const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  async run(ctx, input) {
    if (await isUserBanned(ctx.user.id)) {
      ctx.close(CloseCodes.BANNED, 'You have been banned')
      return
    }

    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

## Which codes can be sent

The server and a browser client follow different rules when they send a close code.

- **Server:** a close frame may use `1000` to `1014`, except `1004`, `1005`, and `1006`. It may also use `3000` to `4999`.
- **Browser client:** `socket.disconnect(...)` may use only `1000`, or `3000` to `4999`. The browser's own `WebSocket.close()` API rejects the other standard values, including `1011`.

The standard values that are not in these ranges are reserved, or they only describe what happened. For example, `1006` means the connection ended in an abnormal way (it dropped without a close frame). You can see `1006` in a close event, but no side may send it in a close frame. A decimal such as `4000.5`, `NaN`, and `5000` are invalid everywhere.

The close reason also has a size limit: 123 bytes when encoded as UTF-8 (the usual text encoding on the web, where one character can take 1 to 4 bytes). A browser client must keep its reason within this limit. When the server closes a connection with a longer reason, LiveThing cuts the reason down to 123 bytes.

Use `CloseCodes` instead of raw numbers in application code. The server engine checks every close code the server sends, and the browser client checks every `socket.disconnect(...)` call.

The upgrade gate uses the same names. Huddle's `upgrade` hook refuses a bad session like this:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import { verifySession } from './auth'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    return { userId: user.id }
  },
})
```

## The codes

The range `1000` to `1014` holds the standard codes described above. The range `3000` to `3999` is for libraries and frameworks, and `4000` to `4999` is for your application. LiveThing gives names to a few `4xxx` codes for common situations:

| Code   | Name               | Meaning                                                                                                               |
| ------ | ------------------ | --------------------------------------------------------------------------------------------------------------------- |
| `1000` | `NORMAL`           | Normal close. The connection finished its work                                                                        |
| `1001` | `GOING_AWAY`       | The server is going away (restart, deploy, shutdown). Clients should reconnect                                        |
| `1002` | `PROTOCOL_ERROR`   | The other side sent data that breaks the protocol                                                                     |
| `1003` | `UNSUPPORTED_DATA` | The other side sent data that this server does not accept, such as a binary frame it cannot use                       |
| `1009` | `MESSAGE_TOO_BIG`  | The other side sent a message over the server's message limit (32 MiB by default)                                     |
| `1011` | `INTERNAL_ERROR`   | The server could not complete an operation                                                                            |
| `1013` | `TRY_AGAIN_LATER`  | The client read too slowly: the server's send buffer for it stayed too big for 10 seconds. Reconnect                  |
| `4001` | `AUTH_EXPIRED`     | The auth token expired. Get a new token and reconnect                                                                 |
| `4002` | `AUTH_INVALID`     | The auth token is not valid. Do not reconnect with the same token                                                     |
| `4003` | `DUPLICATE`        | A newer connection for the same user replaced this one                                                                |
| `4004` | `IDLE`             | No activity for too long. Keepalive closes with this code when pongs (the replies to its ping messages) do not arrive |
| `4005` | `RATE_LIMITED`     | The client sent messages too fast. Wait before reconnecting                                                           |
| `4009` | `BANNED`           | The user is blocked permanently. Do not reconnect                                                                     |
| `4010` | `CAPACITY`         | The server has too many connections. Retry later, and wait longer after each failed try                               |

LiveThing itself sends some of these codes:

- `NORMAL`: the default code for `ctx.close()` and `socket.disconnect()` when you pass no code.
- `GOING_AWAY`: the server is shutting down and closes every open connection.
- `UNSUPPORTED_DATA`: a client sends a binary frame to a server that does not list [`binary()`](/server/capabilities/binary), or a binary frame that does not start with LiveThing's magic bytes (see [Binary frames](/learn/wire-protocol#binary-frames)).
- `MESSAGE_TOO_BIG`: a client sent a message over the adapter's message limit. Cloudflare's limit is 32 MiB. On Node it is the endpoint's `maxMessageBytes`, which is also 32 MiB by default. The platform usually closes the socket first, and LiveThing checks each message again when it arrives, so the limit always holds.
- `TRY_AGAIN_LATER`: on a platform that reports its send buffer (Node), the data waiting to go to one connection stayed over twice the adapter's send limit (2 × 32 MiB = 64 MiB by default) for more than 10 seconds. LiveThing does not send that connection more frames, and closes it. During those 10 seconds LiveThing still sends, so the server's memory can grow by everything the app sends to that connection in that time. A client that is too slow to read even the close frame sees the connection drop with `1006` instead: one second after the close, LiveThing drops the socket. Other connections still get every broadcast. The client reconnects as after any close, and [replay](/server/replay/overview) or your own sync fills in what it missed. Cloudflare does not report its send buffer, so this close never happens there.
- `INTERNAL_ERROR`: server code tried to close with an invalid code (see [below](#what-livething-does-with-a-bad-code)), or the server failed while it set up a connection.
- `DUPLICATE` and `CAPACITY`: a user goes over the [per-user connection limit](/server/context-and-storage/users) (`users: { maxConnections }`). With `onExceed: 'replace'`, the oldest connection closes with `DUPLICATE`. With `onExceed: 'reject'`, the new connection closes with `CAPACITY`.
- `IDLE`: the server [keepalive](/server/capabilities/keepalive) capability sees no activity before its idle timeout, or the client [keepalive](/client/primitives/keepalive) primitive misses too many pongs.

LiveThing never sends `AUTH_EXPIRED`, `AUTH_INVALID`, `RATE_LIMITED`, or `BANNED` by itself. Your code sends them, with `ctx.close(...)`, `Disconnect(...)`, or `RejectUpgrade(...)`.

## How reconnection uses them

The [`reconnection()`](/client/primitives/reconnection) primitive reads the close code to decide if it should try again. By default, it does **not** reconnect after `AUTH_INVALID`, `DUPLICATE`, or `BANNED`, because a retry would only open a connection that the server closes again. After `DUPLICATE`, a newer connection for the same user replaced this one on purpose, so a retry would push that newer connection out in turn. After every other unexpected close, it retries with backoff (a wait that grows longer after each failed try). So a temporary code like `GOING_AWAY` or `CAPACITY` reconnects.

To stop on more codes, list them in `nonRetryableCodes`. That list adds to the three built-in codes. It does not replace them.

```typescript [client/ban-screen.ts]
import {
  binary,
  client,
  connect,
  reconnection,
} from '@livething/client'
import { CloseCodes } from '@livething/core'
import { showBannedScreen } from './huddle-ui'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  reconnection(),
)

socket.onClose(({ code, reason }) => {
  if (code === CloseCodes.BANNED) showBannedScreen(reason)
})
```

For a decision on each close, pass a `shouldReconnect(code, reason)` callback. It runs first, so returning `true` from it retries even a built-in no-retry code. The [reconnection page](/client/primitives/reconnection) explains both options.

## Reading them on the client

`onClose` gives you `{ code, reason, wasClean }`. You can compare `code` with a named code instead of a raw number. The same `CloseCodes` import works on the server and the client:

```typescript [client/refresh-on-expiry.ts]
import { CloseCodes } from '@livething/core'
import { socket } from './socket'

socket.onClose(({ code }) => {
  if (code === CloseCodes.AUTH_EXPIRED) refreshTokenAndReconnect()
})
```

On the server, you pass a code when you close a connection on purpose. Call `ctx.close(code, reason)`, or throw the server's `Disconnect(code, reason)` control-flow error.

## What LiveThing does with a bad code

Sometimes closing a connection is the safe action. For example, an authentication or privacy check may need to stop the connection, even when a bad code reached the close call. So LiveThing does not keep the socket open only because the code is invalid.

- **Server code:** `ctx.close(...)`, `Disconnect(...)`, connection references, user closes, and shutdown closes all go through the engine. If one of them gives an invalid code, LiveThing logs the mistake and sends `1011` with the general reason `Internal error`. It does not send the original reason, because that text may contain information that should not reach the other side.
- **Client code:** browsers allow only `1000`, or a custom code from `3000` to `4999`, when client code calls `socket.disconnect(...)`. With a bad code, or a reason longer than 123 UTF-8 bytes, the client closes with `CloseCodes.NORMAL` (`1000`) and reports a `RangeError` through `socket.onError(...)`. If no `onError` listener exists, the client throws that error again in a microtask (a small task that JavaScript runs right after the current code finishes). This is the usual client rule for local errors.
- **Rejected upgrades:** the upgrade is the HTTP request that opens a WebSocket connection. `RejectUpgrade(...)` accepts either a valid HTTP status (`400` to `599`) or a valid WebSocket close code. The server logs an invalid value and rejects the upgrade with a general HTTP `403` instead. The adapter does not try to fix a decimal or reserved close code itself.

Incoming close events are different. They describe what already happened on the connection, so `onDisconnect` can see a code such as `1006`. LiveThing does not try to send that code back or close the socket a second time.

The server-side forms are in [Control-flow errors](/server/capabilities/errors). The adapter side is in [Custom adapters](/server/adapters/custom-adapters).
