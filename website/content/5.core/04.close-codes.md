When a connection closes, the close **code** says why. `CloseCodes` is the named set LiveThing uses, so you normally do not pass raw numbers around. The server sends a code when it closes a connection; the client's `onClose` receives it, and the reconnection logic reads it to decide whether to retry.

```typescript [server.ts]
import { CloseCodes } from '@livething/core'

ctx.close(CloseCodes.BANNED, 'You have been banned')
```

## Which codes can be sent

The server and a browser client do not have the same rule when they send a close code.

- **Server:** a close frame may use `1000` through `1014`, except `1004`, `1005`, and `1006`, or `3000` through `4999`.
- **Browser client:** `socket.disconnect(...)` may use only `1000`, or `3000` through `4999`. The browser's own `WebSocket.close()` API rejects the other standard values, including `1011`.

The missing standard values are reserved or observational values. For example, `1006` means the peer observed an abnormal close; no endpoint is allowed to send it in a close frame. A decimal such as `4000.5`, `NaN`, and `5000` is invalid everywhere. Browser clients must also keep the UTF-8 close reason to 123 bytes or less.

Use `CloseCodes` instead of raw numbers in application code. The server engine validates every server close, and the browser client validates every `socket.disconnect(...)` call.

```typescript [close-code.ts]
import { CloseCodes } from '@livething/core'

ctx.close(CloseCodes.AUTH_INVALID, 'invalid token')
```

## The codes

`1000`–`1014` contains the usable standard codes above; `3000`–`3999` are available for libraries and frameworks, and `4000`–`4999` are application-defined. LiveThing claims a handful of `4xxx` codes for common situations:

| Code   | Name               | Meaning                                                                        |
| ------ | ------------------ | ------------------------------------------------------------------------------ |
| `1000` | `NORMAL`           | Normal closure — the connection finished its purpose                           |
| `1001` | `GOING_AWAY`       | Server going away — restart, deploy, shutdown. Clients should reconnect        |
| `1002` | `PROTOCOL_ERROR`   | The peer sent data that violates the WebSocket protocol                        |
| `1003` | `UNSUPPORTED_DATA` | The peer sent a frame type this server does not accept                         |
| `1011` | `INTERNAL_ERROR`   | The server could not complete an operation                                     |
| `4001` | `AUTH_EXPIRED`     | Auth token expired — refresh and reconnect                                     |
| `4002` | `AUTH_INVALID`     | Auth token invalid — don't reconnect with the same token                       |
| `4003` | `DUPLICATE`        | Another connection for the same user replaced this one                         |
| `4004` | `IDLE`             | Idle timeout — no activity for too long; keepalive's missed pongs trigger this |
| `4005` | `RATE_LIMITED`     | Sending too fast — back off before reconnecting                                |
| `4009` | `BANNED`           | User is permanently blocked — do not reconnect                                 |
| `4010` | `CAPACITY`         | Server at capacity — retry with backoff                                        |

## How reconnection uses them

The [`reconnection()`](/client/primitives/reconnection) primitive reads the close code to decide whether a drop is worth retrying. Codes that mean "this won't get better by retrying" — like `AUTH_INVALID` or `BANNED` — are treated as non-retryable, so the client stops instead of hammering a connection that will keep failing. A transient code like `GOING_AWAY` or `CAPACITY` reconnects with backoff.

```typescript [app.ts]
import { CloseCodes } from '@livething/core'

socket.onClose(({ code, reason }) => {
  if (code === CloseCodes.BANNED) showBannedScreen(reason)
})
```

## Reading them on the client

`onClose` gives you `{ code, reason, wasClean }`, so you can branch on the named code rather than a magic number — the same `CloseCodes` import works on both sides:

```typescript [app.ts]
socket.onClose(({ code }) => {
  if (code === CloseCodes.AUTH_EXPIRED) refreshTokenAndReconnect()
})
```

On the server, you pass a code when you deliberately close a connection — `ctx.close(code, reason)` or by throwing the server's `Disconnect(code, reason)` control-flow error.

## What LiveThing does with a bad code

Closing a connection is sometimes the safe action: for example, an authentication or privacy check may need to stop the connection even when a bad value reached the close call. LiveThing therefore does not leave the socket open just because the supplied code is invalid.

- **Server code:** `ctx.close(...)`, `Disconnect(...)`, connection references, user closes, and shutdown closes all go through the engine. If one supplies an invalid code, LiveThing logs the developer mistake and sends `1011` with the generic reason `Internal error`. It does not send the original reason, because that text may contain information that should not reach the peer.
- **Client code:** browsers only allow `1000` or a custom code from `3000`–`4999` when client code calls `socket.disconnect(...)`. A bad code, or a reason longer than 123 UTF-8 bytes, closes with `CloseCodes.NORMAL` (`1000`) and reports a `RangeError` through `socket.onError(...)`. With no `onError` listener, the usual client error-routing rule rethrows that local error on a microtask.
- **Rejected upgrades:** `RejectUpgrade(...)` accepts either a valid HTTP status (`400`–`599`) or a valid WebSocket close code. An invalid value is logged server-side and becomes a generic HTTP `403` rejection. The adapter does not try to coerce decimal or reserved close codes itself.

Incoming close events are different. They describe what already happened on the wire, so `onDisconnect` can observe a code such as `1006`. LiveThing does not try to send that code back or close the socket a second time.

The server-side forms are covered in [Control-flow errors](/server/capabilities/errors); the adapter boundary is covered in [Custom adapters](/server/adapters/custom-adapters).
