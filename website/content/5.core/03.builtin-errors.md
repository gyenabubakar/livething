LiveThing comes with a set of errors that you do not define yourself. They are in groups, based on where the error is created. The group also tells you where to import the error from:

- **Client-side errors** are created by the client itself. Import them from `@livething/client/errors`.
- **Framework errors** are created by LiveThing, mostly on the server, and are sent to the client. Import them from `@livething/core`.
- **Server-only errors** are created on the server and never leave it. Import them from `@livething/server/errors`.

All of them are `LiveThingError`s. You check them with `.matches()`, like any other error (see the [Error Model](/core/error-model)).

Every built-in error code on this page is **reserved**. `error()` throws if you give it one of these codes. Because of this, your own errors can never have the same code as a built-in error, and `Timeout.matches()` never matches an error of yours.

## Client-side errors

The client creates these errors itself. The server never sends them. Import them from `@livething/client/errors`:

::field-group
::field{name="Timeout" type="timeout"}
A `request()`, a `stream()` start, a stream `nudge()`, or an inbox query (`receiversOf()`, `readersOf()`) got no answer in time. It also ends a stream when no chunk arrives within the stream's timeout. This error carries no `detail`.
::
::field{name="Disconnected" type="disconnected"}
The socket closed, or you called `disconnect()`, while one of those calls, or a channel `subscribe()` or `unsubscribe()`, was still waiting. It also ends a running stream when the socket closes, unless the stream is durable and the client will reconnect. This error carries no `detail`.
::
::field{name="Dropped" type="dropped"}
A `request()` or `stream()` start was waiting in the offline buffer (the queue that holds messages until the socket is open again) and was removed before it was sent. This happens when the buffer is full, or when the message's TTL (time to live, the longest time it may wait) ran out while the client was offline. It also happens at once when the message alone is bigger than the buffer's `maxBytes`, so it could never go in. This error carries no `detail`.
::
::field{name="StreamCorrupted" type="stream-corrupted"}
A stream chunk is missing, so the stream failed instead of ending with a hole in it. The `for await` loop over a stream you started throws it, and a broadcast listener's `onError` gets it. Its `detail` is `{ expected: number, got: number }`: the `seq` the client was waiting for and the one that came. See [Client-side errors](/client/errors/client-side-errors).
::
::

This example loads a user's profile and reacts to each client-side error:

```typescript [client/load-profile.ts]
import {
  Disconnected,
  Dropped,
  Timeout,
} from '@livething/client/errors'
import {
  retryLoadingProfile,
  showOfflineNotice,
  waitForReconnection,
} from './huddle-ui'
import { socket } from './socket'

async function showProfile(userId: string) {
  try {
    return await socket.request('get-profile', { userId })
  } catch (err) {
    if (Timeout.matches(err)) retryLoadingProfile(userId)
    else if (Disconnected.matches(err)) waitForReconnection()
    else if (Dropped.matches(err)) showOfflineNotice()
  }
}
```

## Framework errors

LiveThing creates these errors. Most of them come from the server. A few are created by the client, and the list says when. Import them from `@livething/core`:

::field-group
::field{name="ValidationFailed" type="validation-failed"}
An incoming payload did not match its schema, or a stream received a nudge event it does not declare. The client also creates it, before sending, for an empty or too long event name, channel name or `streamId`. Its `detail` is `{ event: string, issues: Issue[] }`.
::
::field{name="RateLimited" type="rate-limited"}
A message was rejected because the connection sent faster than the rate limit allows. The handler did not run. Its `detail` is `{ retryAfterMs: number }` (milliseconds).
::
::field{name="ConnectionBusy" type="connection-busy"}
The connection already has 256 ordered handlers waiting or running, 256 messages waiting behind a channel subscribe, or twice the adapter's message limit (64 MiB by default) of messages whose handlers have not started, so a new one could not start. The connection stays open. `retryAfterMs` is 1000. Its `detail` is `{ retryAfterMs: number }` (milliseconds).
::
::field{name="ChannelNotFound" type="channel-not-found"}
A channel name matches no declared channel and no channel family, for example when a client subscribes to a misspelled name. This error carries no `detail`.
::
::field{name="ChannelNotSubscribed" type="channel-not-subscribed"}
You sent to, or unsubscribed from, a channel you are not a member of. The client also throws it before sending, when you use a channel handle that is not subscribed. This error carries no `detail`.
::
::field{name="CrossInstanceRef" type="cross-instance-ref"}
Thrown on the server when an operation gets a `ConnectionRef` or `UserRef` that belongs to another server instance. Nothing is sent. Its `detail` is `{ operation: string, targetInstance?: string, engineInstance?: string }`.
::
::field{name="RejoinRejected" type="rejoin-rejected"}
After a reconnect, the server refused to put the client back into a persistent channel, because the channel's `revalidate` hook threw. `message` is the message of that error. Its `detail` is `{ message: string }`.
::
::field{name="UnsupportedProtocol" type="unsupported-protocol"}
The client used a protocol feature that the server has not turned on (replay, or durable streams). Its `detail` is `{ event: '__replay__' | '__continueStream__' }`.
::
::field{name="InternalError" type="internal-error"}
A server error that LiveThing cannot classify. The server logs the real error. The client gets only this code, so internal details never reach it. This error carries no `detail`.
::
::field{name="RequestNoResponse" type="request-no-response"}
The client sends it back when a server-to-client request got no answer: the client has no handler for it, or the handler returned nothing. This error carries no `detail`.
::
::field{name="RequestNoCorrelation" type="request-no-correlation"}
A request message arrived without a correlation ID (the ID that matches a reply to its request). The LiveThing client always adds it, so this only happens with other clients. This error carries no `detail`.
::
::field{name="RequestInvalidResponse" type="request-invalid-response"}
A request handler's reply did not match the request's response schema. Its `detail` is `{ event: string, issues: Issue[] }`.
::
::field{name="StreamAborted" type="stream-aborted"}
A running stream was ended on the server. `reason` says why (see below). Its `detail` is `{ reason: StreamAbortedReason }`.
::
::field{name="NudgeOverflow" type="nudge-overflow"}
A `nudge()` could not be queued because the stream's nudge buffer is full. Only that nudge fails. The stream keeps running. Its `detail` is `{ cap: number }`.
::
::field{name="StreamIdCollision" type="stream-id-collision"}
You started a stream with your own `streamId`, and a stream with that ID is already running. This error carries no `detail`.
::
::field{name="StreamAlreadyActive" type="stream-already-active"}
You started a stream of an event while another stream of the same event is running on the connection. `allowConcurrent: true` on the stream definition allows this. Its `detail` is `{ event: string, streamId: string }`.
::
::field{name="DurableStreamRequiresUser" type="durable-stream-requires-user"}
An anonymous connection (one with no `userId`) tried to start a durable stream. This error carries no `detail`.
::
::

`Issue[]` is the Standard Schema issue array. Each issue is `{ message: string, path?: (string | number)[] }`.

### Examples

`RateLimited` and `ConnectionBusy` both tell you how long to wait before you try again, in milliseconds. When one of them rejects a `socket.request()`, handle it in the `catch` block of that request:

```typescript [client/load-profile-with-retry.ts]
import { ConnectionBusy, RateLimited } from '@livething/core'
import { socket } from './socket'

async function loadProfileWithRetry(userId: string) {
  for (;;) {
    try {
      return await socket.request('get-profile', { userId })
    } catch (err) {
      if (!RateLimited.matches(err) && !ConnectionBusy.matches(err)) {
        throw err
      }

      await new Promise((resolve) =>
        setTimeout(resolve, err.detail.retryAfterMs),
      )
    }
  }
}
```

The connection stays open after these errors. `socket.onServerError()` receives only errors that no call is waiting for, such as an error for a `socket.send()` (which does not wait for an answer). It does not receive an error that already rejected a `socket.request()` call.

`StreamAborted` tells you _why_ the stream ended, so you can react to each reason:

```typescript [client/ask-scout.ts]
import { StreamAborted } from '@livething/core'
import {
  askScoutAgain,
  render,
  showRetryButton,
  showSlowDownToast,
} from './huddle-ui'
import { socket } from './socket'

const general = socket.channel('rooms', 'room:general')

async function showScoutReply(prompt: string) {
  try {
    const reply = await general.stream('ask-scout', { prompt })
    for await (const chunk of reply) render(chunk.text)
  } catch (err) {
    if (StreamAborted.matches(err)) {
      if (err.detail.reason === 'expired') askScoutAgain()
      else if (err.detail.reason === 'buffer-full')
        showSlowDownToast()
      else if (err.detail.reason === 'interrupted') showRetryButton()
    }
  }
}
```

Its `reason` is one of these values:

::field-group
::field{name="cancelled"}
The stream was cancelled.
::
::field{name="buffer-full"}
A recorded stream's chunk buffer reached its limit.
::
::field{name="expired"}
A recorded stream whose generator stopped mid-stream waited longer than its `maxAgeMs` before the client came back.
::
::field{name="not-found"}
The client asked to continue a stream ID that the server does not know.
::
::field{name="hibernation-wake"}
The server lost a plain stream when it woke from hibernation. (For a durable stream, the LiveThing client continues on its own.)
::
::field{name="unsubscribed"}
This client left the channel the stream runs in (it unsubscribed, or it was kicked or removed), or it cancelled a broadcast stream. The server stops sending it chunks. Other clients of a broadcast stream still get them.
::
::field{name="interrupted"}
A recorded stream's generator stopped before it finished (it threw, or the server restarted, crashed, or was evicted while it ran). A continue sends the stored chunks the client missed, then ends the stream with this reason instead of a normal end.
::
::field{name="taken-over"}
Another connection of the same user continued this recorded stream while it was running, for example a second tab. The stream goes on for that connection and ends for this one.
::
::field{name="aborted"}
The server ended the stream for an internal reason that matches none of the reasons above.
::
::

**Hibernation** means the runtime removes an idle server from memory and starts it again when a message arrives. The stream's state in memory is lost at that moment, but the WebSocket connection stays open. Only runtimes that support hibernation send `hibernation-wake`: on the Cloudflare adapter, that is Durable Objects. On other runtimes you never see this reason.

::note
Some of these errors reject one specific call. Others go to `onServerError`. [Error Routing](/client/errors/onerror-routing) explains the rules.
::

## Server-only errors

These errors are created on the server and are never sent to the client. Import them from `@livething/server/errors`:

| Error        | Code           | When it happens                                                                                                                          | `detail` |
| ------------ | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| `NotAMember` | `not-a-member` | `ctx.channel.request(event, payload, { to })` was aimed at a connection that is not a member of that channel right now. Nothing is sent. | none     |

[Targeting channel members with `to`](/server/channels/scoped-streams-requests#targeting-channel-members-with-to) shows when `NotAMember` happens and how to handle it.
