LiveThing comes with a set of errors that you do not define yourself. They are in groups, based on where the error is created. The group also tells you where to import the error from:

- **Client-side errors** are created by the client itself. Import them from `@livething/client/errors`.
- **Framework errors** are created by LiveThing, mostly on the server, and are sent to the client. Import them from `@livething/core`.
- **Server-only errors** are created on the server and never leave it. Import them from `@livething/server/errors`.

All of them are `LiveThingError`s. You check them with `.matches()`, like any other error (see the [Error Model](/core/error-model)).

Every built-in error code on this page is **reserved**. `error()` throws if you give it one of these codes. Because of this, your own errors can never have the same code as a built-in error, and `Timeout.matches()` never matches an error of yours.

## Client-side errors

The client creates these errors itself. The server never sends them. Import them from `@livething/client/errors`:

| Error          | Code           | When it happens                                                                                                                                                                                                                                                                                                           | `detail` |
| -------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| `Timeout`      | `timeout`      | A `request()`, a `stream()` start, a stream `nudge()`, or an inbox query (`receiversOf()`, `readersOf()`) got no answer in time. It also ends a stream when no chunk arrives within the stream's timeout.                                                                                                                 | none     |
| `Disconnected` | `disconnected` | The socket closed, or you called `disconnect()`, while one of those calls, or a channel `subscribe()` or `unsubscribe()`, was still waiting. It also ends a running stream when the socket closes, unless the stream is resumable and the client will reconnect.                                                          | none     |
| `Dropped`      | `dropped`      | A `request()` or `stream()` start was waiting in the offline buffer (the queue that holds messages until the socket is open again) and was removed before it was sent. This happens when the buffer is full, or when the message's TTL (time to live, the longest time it may wait) ran out while the client was offline. | none     |

This example loads a room's chat history and reacts to each client-side error:

```typescript [client/room.ts]
import {
  Disconnected,
  Dropped,
  Timeout,
} from '@livething/client/errors'

try {
  const room = socket.channel('rooms', 'room:general')
  await room.request('load-history', {})
} catch (err) {
  if (Timeout.matches(err)) retry()
  else if (Disconnected.matches(err)) waitForReconnect()
  else if (Dropped.matches(err)) showOfflineNotice()
}
```

## Framework errors

LiveThing creates these errors. Most of them come from the server. A few are created by the client, and the table says when. Import them from `@livething/core`:

| Error                       | Code                           | When it happens                                                                                                                                                                                                    | `detail`                                                                  |
| --------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| `ValidationFailed`          | `validation-failed`            | An incoming payload did not match its schema, or a stream received a nudge event it does not declare. The client also creates it, before sending, for an empty or too long event name, channel name or `streamId`. | `{ event: string, issues: Issue[] }`                                      |
| `RateLimited`               | `rate-limited`                 | A message was rejected because the connection sent faster than the rate limit allows. The handler did not run.                                                                                                     | `{ retryAfterMs: number }` (milliseconds)                                 |
| `ConnectionBusy`            | `connection-busy`              | The connection already has 256 ordered handlers waiting or running, so a new one could not start. The connection stays open. `retryAfterMs` is 1000.                                                               | `{ retryAfterMs: number }` (milliseconds)                                 |
| `ChannelNotFound`           | `channel-not-found`            | A channel name matches no declared channel and no channel family, for example when a client subscribes to a misspelled name.                                                                                       | none                                                                      |
| `ChannelNotSubscribed`      | `channel-not-subscribed`       | You sent to, or unsubscribed from, a channel you are not a member of. The client also throws it before sending, when you use a channel handle that is not subscribed.                                              | none                                                                      |
| `CrossInstanceRef`          | `cross-instance-ref`           | Thrown on the server when an operation gets a `ConnectionRef` or `UserRef` that belongs to another server instance. Nothing is sent.                                                                               | `{ operation: string, targetInstance?: string, engineInstance?: string }` |
| `RejoinRejected`            | `rejoin-rejected`              | After a reconnect, the server refused to put the client back into a persistent channel, because the channel's `revalidate` hook threw. `message` is the message of that error.                                     | `{ message: string }`                                                     |
| `UnsupportedProtocol`       | `unsupported-protocol`         | The client used a protocol feature that the server has not turned on (replay, or resumable streams).                                                                                                               | `{ event: '__replay__' \| '__resumeStream__' }`                           |
| `InternalError`             | `internal-error`               | A server error that LiveThing cannot classify. The server logs the real error. The client gets only this code, so internal details never reach it.                                                                 | none                                                                      |
| `RequestNoResponse`         | `request-no-response`          | The client sends it back when a server-to-client request got no answer: the client has no handler for it, or the handler returned nothing.                                                                         | none                                                                      |
| `RequestNoCorrelation`      | `request-no-correlation`       | A request message arrived without a correlation ID (the ID that matches a reply to its request). The LiveThing client always adds it, so this only happens with other clients.                                     | none                                                                      |
| `RequestInvalidResponse`    | `request-invalid-response`     | A request handler's reply did not match the request's response schema.                                                                                                                                             | `{ event: string, issues: Issue[] }`                                      |
| `StreamAborted`             | `stream-aborted`               | A running stream was ended on the server. `reason` says why (see below).                                                                                                                                           | `{ reason: StreamAbortedReason }`                                         |
| `NudgeOverflow`             | `nudge-overflow`               | A `nudge()` could not be queued because the stream's nudge buffer is full. Only that nudge fails. The stream keeps running.                                                                                        | `{ cap: number }`                                                         |
| `StreamIdCollision`         | `stream-id-collision`          | You started a stream with your own `streamId`, and a stream with that ID is already running.                                                                                                                       | none                                                                      |
| `StreamAlreadyActive`       | `stream-already-active`        | You started a stream of an event while another stream of the same event is running on the connection. `allowConcurrent: true` on the stream definition allows this.                                                | `{ event: string, streamId: string }`                                     |
| `DurableStreamRequiresUser` | `durable-stream-requires-user` | An anonymous connection (one with no `userId`) tried to start a resumable or recorded stream.                                                                                                                      | none                                                                      |

`Issue[]` is the Standard Schema issue array. Each issue is `{ message: string, path?: (string | number)[] }`.

### Examples

`RateLimited` and `ConnectionBusy` both tell you how long to wait before you try again, in milliseconds. When one of them rejects a `socket.request()`, handle it in the `catch` block of that request:

```typescript [client/socket.ts]
import { ConnectionBusy, RateLimited } from '@livething/core'

async function deleteMessageWithRetry(messageId: string) {
  for (;;) {
    try {
      return await socket.request('delete-message', { messageId })
    } catch (err) {
      if (!RateLimited.matches(err) && !ConnectionBusy.matches(err)) {
        throw err
      }

      await new Promise((resolve) =>
        setTimeout(resolve, err.detail.retryAfterMs),
      )
    }
  }
}
```

The connection stays open after these errors. `socket.onServerError()` receives only errors that no call is waiting for, such as an error for a `socket.send()` (which does not wait for an answer). It does not receive an error that already rejected a `socket.request()` call.

`StreamAborted` tells you _why_ the stream ended, so you can react to each reason:

```typescript [client/room.ts]
import { StreamAborted } from '@livething/core'

try {
  const reply = await room.stream('ask-scout', { prompt })
  for await (const chunk of reply) render(chunk.text)
} catch (err) {
  if (StreamAborted.matches(err)) {
    if (err.detail.reason === 'hibernation-wake') restartStream()
    else if (err.detail.reason === 'buffer-full') showSlowDownToast()
  }
}
```

Its `reason` is one of these values:

| `reason`           | Meaning                                                                                                                                                                                                                     |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cancelled`        | The stream was cancelled.                                                                                                                                                                                                   |
| `buffer-full`      | A recorded stream's chunk buffer reached its limit.                                                                                                                                                                         |
| `expired`          | A paused resumable stream waited longer than its retention time before the client came back.                                                                                                                                |
| `not-found`        | The client asked to resume a stream ID that the server does not know.                                                                                                                                                       |
| `hibernation-wake` | The server lost a plain stream when it woke from hibernation. (For a durable stream, the LiveThing client resumes on its own.)                                                                                              |
| `unsubscribed`     | This client left the channel the stream runs in (it unsubscribed, or it was kicked or removed), or it cancelled a broadcast stream. The server stops sending it chunks. Other clients of a broadcast stream still get them. |
| `cursor-invalid`   | On resume, the saved cursor or payload could not be restored (for example, it did not pass the `resumableStream` cursor validator). The stored stream is deleted.                                                           |
| `aborted`          | The server ended the stream for an internal reason that matches none of the reasons above.                                                                                                                                  |

**Hibernation** means the runtime removes an idle server from memory and starts it again when a message arrives. The stream's state in memory is lost at that moment, but the WebSocket connection stays open. Only runtimes that support hibernation send `hibernation-wake`: on the Cloudflare adapter, that is Durable Objects. On other runtimes you never see this reason.

::note
Some of these errors reject one specific call. Others go to `onServerError`. [Error Routing](/client/errors/onerror-routing) explains the rules.
::

## Server-only errors

These errors are created on the server and are never sent to the client. Import them from `@livething/server/errors`:

| Error            | Code              | When it happens                                                                                                                                                                                                                             | `detail`                                               |
| ---------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| `DeferExhausted` | `defer-exhausted` | A handler deferred a message with `Defer(...)`, but the message cannot be retried again: it was already retried 3 times, or the connection has too many deferred messages waiting. The message is dropped and this error goes to `onError`. | `{ event: string, payload: unknown, retries: number }` |

[Server-side control-flow errors](/server/capabilities/errors#server-side-control-flow-errors) shows how to use `Defer` and `DeferExhausted`.
