Some of your code belongs to **both** sides. The error a server throws is the same error a client catches. The type a server declares is the type a client uses. _Isomorphic_ code is code that you write once and import on both sides. `@livething/core` is the package that makes this safe.

## Why it's safe to share

`@livething/core` is runtime-agnostic: it does not depend on one runtime, such as the browser or Node.js. It uses no browser globals, no WebSocket, and no storage. It is plain TypeScript. So a file that imports only from `@livething/core` and your schema library can be imported from client code, server code, or a file that both use. No platform-specific code comes in with it:

```typescript [shared/errors.ts]
// Safe on the server, in the browser, and in a shared file.
import { error } from '@livething/core'
import * as v from 'valibot'

export const Forbidden = error(
  'forbidden',
  v.object({ reason: v.string() }),
)
```

## Shared error definitions

Errors are the clearest example. You define an error **once**, in a file that both sides import. The server throws it. The client narrows it with `.matches()`. To _narrow_ means to check an unknown value and, when the check passes, let TypeScript treat it as a more exact type. Both sides use the same definition, so the `code` and the type of `detail` always match.

The server lists the error in the [`errors([...])`](/server/capabilities/errors) capability. This puts the error on the client contract. Then a handler can throw it:

::code-group

```typescript [shared/errors.ts]
import { error } from '@livething/core'
import * as v from 'valibot'

export const NotFound = error(
  'not-found',
  v.object({ id: v.string() }),
)
```

```typescript [server/huddle-definition.ts]
import { errors, server } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'
import { NotFound } from '../shared/errors'

const base = server({
  capabilities: [clientRequests(), errors([NotFound])],
})

export const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  async run(ctx, input) {
    const profile = await loadProfile(input.userId)
    if (!profile) throw NotFound({ id: input.userId }) // thrown on the server
    return profile
  },
})

export const huddle = base.assemble({
  handlers: [handleGetProfile],
})

export type HuddleSocket = InferClient<typeof huddle>
```

```typescript [client/show-profile.ts]
import { NotFound } from '../shared/errors'
import { socket } from './socket'

async function showProfile(userId: string) {
  try {
    return await socket.request('get-profile', { userId })
  } catch (err) {
    if (NotFound.matches(err)) showMissingProfile(err.detail.id) // matched on the client
  }
}
```

::

There is one definition with two uses, so the two sides cannot become different. The error model itself is explained in [Error Model](/core/error-model).

## Shared types

The other shared thing is the **contract**: the one typed description of your API. You do not write it twice. The server defines it, and the client imports the inferred type (the type that TypeScript works out from your code). [The Contract](/learn/the-contract) page in Learn explains this in detail. The idea is the same as for errors: declare it once and use it on both sides. The compiler then reports an error when the two sides do not match.

## Where to put shared files

A common layout is a shared folder (or a small package). It holds your error definitions and any plain types that both sides use. It imports only from `@livething/core` and your schema library:

```text
.
├── shared/
│   └── errors.ts   # error() definitions, imported by client and server
├── server/
│   └── huddle-definition.ts   # throws those errors, exports the contract type
└── client/
    └── socket.ts   # matches those errors, imports the contract type
```

Keep platform-specific code (DOM, storage, sockets) out of the shared files. Then you can import them from either side.
