Every LiveThing error — yours, the client's, or the framework's — is a **`LiveThingError`**: a regular `Error` subclass with a stable `code` and an optional typed `detail`. One shape end to end means one way to define, throw, and narrow errors, whichever side you're on.

```typescript [shape]
class LiveThingError extends Error {
  readonly code: string // a stable identifier, e.g. 'forbidden'
  readonly detail: unknown // extra data, narrowed to its real type by .matches()
}
```

## Defining an error

You define errors with the `error()` factory, from `@livething/core` (the [Client](/client/errors/overview) and Server packages also re-export it). There are two forms:

```typescript [errors.ts]
import { error } from '@livething/core'
import * as v from 'valibot'

// code-only — no detail payload
export const NotFound = error('not-found')

// with a detail schema — any Standard Schema (valibot, zod, arktype)
export const Forbidden = error(
  'forbidden',
  v.object({ reason: v.string() }),
)
```

Both forms return a **callable factory**. Calling it builds the error — `NotFound()` for a code-only one, `Forbidden({ reason: 'private post' })` for one with detail. Put these in a [shared file](/core/isomorphic-code) so the server can throw them and the client can match them.

## Narrowing with `.matches()`

Each definition carries a `.matches()` type guard. It returns `true` only when the value is a `LiveThingError`, its `code` matches, and — if the error was defined with a schema — its `detail` passes that schema. Inside a `true` branch, TypeScript knows the code **and** the `detail` type:

```typescript [app.ts]
import { Forbidden, NotFound } from './errors'

if (NotFound.matches(err)) {
  // err is LiveThingError<'not-found', void>
} else if (Forbidden.matches(err)) {
  console.log(err.detail.reason) // detail typed as { reason: string }
}
```

It's better than a string compare on two counts:

- **It narrows the type.** After `Forbidden.matches(err)`, `err.detail` is `{ reason: string }`, checked by the compiler.
- **It validates at runtime.** If the value carries the right code but a `detail` that doesn't fit the schema, `.matches()` returns `false` rather than handing back a malformed object — so a code match with the wrong shape is a non-match, not a crash.

## Code rules and reserved codes

A code identifies the error on the wire, so it has a couple of rules, enforced when you call `error()`:

- It must be a **non-empty string** that doesn't start or end with `__` — that prefix and suffix are reserved for LiveThing's own protocol frames (named `__x__`) and plugin-namespaced identifiers (`__pluginId:...`). The convention for your own codes is lowercase kebab-case (`'not-found'`, `'rate-exceeded'`).
- It can't be one of the **codes the framework already ships**. Those are reserved, because a frame carrying that code would be ambiguous between the framework's error and yours.

```typescript [errors.ts]
import { error } from '@livething/core'

error('__mine') // throws — the __ prefix is reserved
error('mine__') // throws — the __ suffix is reserved too
error('rate-limited') // throws — reserved by the framework
error('rate-exceeded') // fine — your own code
```

The full list of reserved framework codes is the [built-in errors](/core/builtin-errors).
