Every LiveThing error is a **`LiveThingError`**. This is true for the errors you define, the errors the client raises, and the errors the framework sends. `LiveThingError` is a normal `Error` subclass with two extra fields: a stable `code` and an optional typed `detail`. Because all errors have this one shape, you define, throw and check errors the same way on the client and on the server.

```typescript [shape]
class LiveThingError extends Error {
  readonly code: string // a stable identifier, e.g. 'forbidden'
  readonly detail: unknown // extra data, narrowed to its real type by .matches()
}
```

## Defining an error

You define errors with the `error()` factory from `@livething/core`. The client re-exports it from `@livething/client/errors` (see [Client errors](/client/errors/overview)), and the server re-exports it from `@livething/server`. There are two forms:

```typescript [shared/errors.ts]
import { error } from '@livething/core'
import * as v from 'valibot'

// code-only: no detail payload
export const NotFound = error('not-found')

// with a detail schema: any Standard Schema (valibot, zod, arktype)
export const Forbidden = error(
  'forbidden',
  v.object({ reason: v.string() }),
)
```

The second form takes a schema. It can be any **Standard Schema**, which is a shared interface that validation libraries such as valibot, zod and arktype all support. The type of `detail` comes from that schema.

Both forms return a **callable factory**, which is a function that builds the error when you call it:

- `NotFound()` builds a code-only error.
- `Forbidden({ reason: 'private post' })` builds an error with detail. The factory checks the detail against the schema and throws if it does not fit.

Put these definitions in a [shared file](/core/isomorphic-code). Then the server can throw them and the client can match them.

## Narrowing with `.matches()`

Each definition has a `.matches()` method. It is a **type guard**: a function that returns `true` or `false`, and when it returns `true`, TypeScript narrows the value to a more exact type. `.matches()` returns `true` only when all of these are true:

- the value is a `LiveThingError`
- its `code` is the same as the definition's code
- if the error was defined with a schema, its `detail` passes that schema

Inside a `true` branch, TypeScript knows the code **and** the `detail` type:

```typescript [client/socket.ts]
import { Forbidden, NotFound } from '../shared/errors'

if (NotFound.matches(err)) {
  // err is LiveThingError<'not-found', void>
} else if (Forbidden.matches(err)) {
  console.log(err.detail.reason) // detail typed as { reason: string }
}
```

This is better than comparing `err.code` to a string, for two reasons:

- **It narrows the type.** After `Forbidden.matches(err)`, `err.detail` has the type `{ reason: string }`, and the compiler checks how you use it.
- **It validates at runtime.** Suppose a value has the right code but its `detail` does not fit the schema. Then `.matches()` returns `false`. Your code does not receive a malformed object, so a wrong shape does not cause a crash later.

## Code rules and reserved codes

A code identifies the error on the wire, so `error()` checks it when you call it. The rules are:

- The code must be a **non-empty string**.
- The code must not start or end with `__`. LiveThing reserves this prefix and suffix for its own protocol frames (such as `__replay__`) and for plugin identifiers (`__pluginId:...`). For your own codes, use lowercase kebab-case, which means lowercase words joined by hyphens (`'not-found'`, `'rate-exceeded'`).
- The code must not be one of the **built-in error codes**. These codes are reserved. If your error used one, a frame with that code could mean either the built-in error or yours.

```typescript [shared/errors.ts]
import { error } from '@livething/core'

error('__mine') // throws: the __ prefix is reserved
error('mine__') // throws: the __ suffix is reserved too
error('rate-limited') // throws: a built-in error code
error('timeout') // throws: a built-in error code
error('rate-exceeded') // fine: your own code
```

The full list of reserved codes is in [Built-in Errors](/core/builtin-errors).
