`awareness()` is the client half of [awareness](/server/capabilities/awareness). Awareness is live state for each connection in a channel: the message a member is reading, where their cursor is, what they have selected. Your client sets its own state, and it sees the state of every other connection in the channel.

The channel must list the [`awareness()`](/server/capabilities/awareness) capability on the server. On such a channel, `awareness()` adds `channel.awareness` to the handle. The state type comes from the [client contract](/server/capabilities/awareness#the-client-contract), so `set()` and the states of the other members are typed.

```typescript [client/socket.ts]
import {
  awareness,
  binary,
  channels,
  client,
  connect,
  reconnection,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  channels(),
  awareness(),
  reconnection(),
)
```

`awareness()` needs [`channels()`](/client/primitives/channels). The order you list them in does not matter.

If the contract has a channel with awareness but you leave out `awareness()`, `channels()` writes a warning the first time you join that channel. The server still sends you the states of the other members, so leaving it out uses bandwidth for no benefit.

## Options

| Option       | Type     | Default | What it does                                                                      |
| ------------ | -------- | ------- | --------------------------------------------------------------------------------- |
| `throttleMs` | `number` | `50`    | The least time between two updates sent for one channel, in ms. `0` turns it off. |

The throttle sends the first update at once. Updates in the next `throttleMs` wait, and only the newest is sent when the time is up. The server also collects updates for its own `windowMs` (50 ms by default), so a lower `throttleMs` sends more messages without showing changes faster.

## The awareness surface

On a channel whose contract has `awareness`, the handle gets `channel.awareness`. The examples use `room`, a handle for Huddle's `room:general` channel. Its state is `{ viewingMessageId: string | null }`: the message at the top of the member's view.

| Member          | What it is                                                                                |
| --------------- | ----------------------------------------------------------------------------------------- |
| `set(state)`    | Replace this connection's state. Throttled.                                               |
| `clear()`       | Clear this connection's state. Sent at once.                                              |
| `mine`          | A store of the state this client last asked for, or `null`.                               |
| `self`          | A store of this connection's entry as the server holds it, or `null`.                     |
| `others`        | A store of a `ReadonlyMap` of every other connection's entry, by connection ID.           |
| `synced`        | A store that is `false` until the first full list of states after each join.              |
| `onRefused(cb)` | Runs `cb` when an update from this client is refused. Returns a function that removes it. |

The stores are [reactive stores](/client/overview#reactive-stores): read them with `get()`, watch them with `subscribe()`. `subscribe()` does not run the listener at once, so read the current value with `get()` first. Each change gives `others` a new `Map`, so a UI framework sees the change. To use the stores in React, Vue, Svelte or Solid, write the small [adapter for your framework](/recipes/framework-hooks/react) once.

### Setting your state

```typescript [client/room.ts]
room.awareness.set({ viewingMessageId: 'msg_481' })
```

`set()` replaces the whole state. It does not merge with the old one. The state must be a plain JSON object of the type the server's `state` schema checks.

`set()` does nothing, and writes an info log line, while the channel is not joined. During a rejoin after a reconnect, it keeps the state and sends it when the rejoin is done.

`clear()` removes your state from the channel. It is not throttled, and it drops a waiting `set()`.

### Your own state: `mine` and `self`

Your state has two stores, because what you asked for and what the server holds can be different:

- `mine` is what this client last asked for. It changes as soon as you call `set()` or `clear()`.
- `self` is the entry the server holds for this connection, from the server's own changes. It changes when the server takes your update, and when a server handler sets or clears your state.

A refused update changes `mine` but not `self`. To show your own state the way other members see it, read `self`.

### Other members: `others`

`others` holds every other connection in the channel that has a state. Each entry has:

| Field          | What it is                                                                         |
| -------------- | ---------------------------------------------------------------------------------- |
| `connectionId` | The connection the state belongs to.                                               |
| `memberId`     | The user ID on a persistent channel with a signed-in user, else the connection ID. |
| `meta`         | The connection's `meta` when its state first appeared.                             |
| `state`        | The state, typed by the server's `state` schema.                                   |
| `updatedAt`    | When the server took the state, in ms since 1970, on this client's clock.          |

Awareness is per connection. A person with two tabs open has two entries, and each tab can show a different message. Huddle's `rooms` channel is ephemeral, so `memberId` is the connection ID. To show each person once, Huddle groups the entries by the `userId` its `authenticate` puts in `meta`:

```typescript [client/viewers.ts]
import { onTopMessageChange, renderViewers } from './huddle-ui'
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')
await room.subscribe()

// Tell the room which message is at the top of this tab's view.
onTopMessageChange((messageId) =>
  room.awareness.set({ viewingMessageId: messageId }),
)

// Show each person once, with the message that each of their tabs shows.
function showViewers(
  others: ReturnType<typeof room.awareness.others.get>,
) {
  const people = new Map<
    unknown,
    { name: string; messageIds: (string | null)[] }
  >()
  for (const entry of others.values()) {
    const person = people.get(entry.meta.userId) ?? {
      name: String(entry.meta.name),
      messageIds: [],
    }

    person.messageIds.push(entry.state.viewingMessageId)
    people.set(entry.meta.userId, person)
  }

  renderViewers([...people.values()])
}

// `subscribe` only calls on a change, so show the list as it is now first.
showViewers(room.awareness.others.get())
room.awareness.others.subscribe(showViewers)
```

`meta` is typed as `Record<string, unknown>` on the client, because the contract does not know what `authenticate` returns.

## Joining, leaving and reconnecting

- **Joining.** Right after the member list, the server sends every state in the channel. `others` fills, and `synced` turns `true`. Before that, an empty `others` does not mean nobody has a state. Use `synced` to show a loading state, and show "nobody else is here" only when `synced` is `true`.
- **Leaving.** When you unsubscribe, are kicked, or a rejoin fails, `mine`, `self` and `others` are emptied, and `synced` turns `false`. The server clears your state for the other members. A later `subscribe()` starts with no state.
- **Reconnecting.** When the socket drops, `self` is emptied, as the server cleared your state, and `synced` turns `false`. `others` keeps its old entries until the rejoin brings a fresh list, so the list does not become empty for a moment. While `synced` is `false`, these entries can be out of date. After the rejoin, the client sends `mine` again, so you do not need to call `set()` again. Entries of your own old connection are left out of `others`.

## Refused updates

The server refuses an update when it is over the channel's `maxBytes`, fails the `state` schema, or fails the channel's `check`. Only you hear about it, through `onRefused`. The refusal does not go to `onServerError`.

```typescript [client/room.ts]
room.awareness.onRefused((refusal) => {
  console.warn('awareness update refused:', refusal.reason)
})
```

| Reason      | When                                                                                                                   |
| ----------- | ---------------------------------------------------------------------------------------------------------------------- |
| `too-large` | The state is over the channel's `maxBytes`, or this connection holds over 1 MiB of state and `meta` in all channels.   |
| `invalid`   | The state's JSON is not an object, or the server's schema refused it.                                                  |
| `check`     | The server's `check` returned `false`.                                                                                 |
| `error`     | The server's `check` or schema threw, or the server could not send your entry (for example, your `meta` is too large). |

The client checks `too-large` and `invalid` itself before it sends, using the `maxBytes` the server gave it on join. A state that fails these checks is not sent, and `mine` does not change.

A refused update leaves your old state in place on the server. A server `check` that refuses some states, such as Huddle's check that hides guests, refuses every update from that member, so `self` stays `null` for them.

## Bytes

Awareness state is JSON only. To share bytes, send them as normal channel messages with [`binary()`](/client/primitives/binary).
