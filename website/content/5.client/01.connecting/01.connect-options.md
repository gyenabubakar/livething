`connect(url, options?)` takes six options. All of them are optional, and the defaults work for most apps.

```typescript [client/socket.ts]
import { connect, websocket } from '@livething/client'
import { getSessionToken } from './huddle-data'

connect('wss://example.com/huddle', {
  lazy: false, // open only when something needs the socket (default: false)
  lazyIdleTimeoutMs: 10_000, // in lazy mode, close after this long with no use (default: 10s)
  token: () => getSessionToken(), // login token, read on every connect (default: none)
  protocols: ['huddle-v2'], // WebSocket subprotocols (default: none)
  transports: [websocket()], // how to connect (default: WebSocket only)
  connectTimeoutMs: 30_000, // how long the server may take to accept (default: 30s, 5s with several transports)
})
```

`token` has its own page: [Auth & Query](/client/connecting/auth-and-query#token-auth-with-token).

## `connect()` and `disconnect()`

Before the options, here are the two socket methods that open and close the connection:

- **`socket.connect()`** opens the connection. You can call it more than once. While the socket is already `open` or `connecting`, it does nothing.
- **`socket.disconnect(code?, reason?)`** closes the connection on purpose, and for good. It closes the connection, stops any reconnection, clears the send buffer, and rejects pending requests. `code` defaults to `1000` (normal closure) and `reason` defaults to `''`. Both go to the server (in the WebSocket close frame, or in a `__close__` frame on `http()`) and show up in `onClose`.

Your `on()` handlers stay registered after a `disconnect()`. So when you call `connect()` again later, all your listeners still work. A `disconnect()` ends the session, so the next `connect()` counts as a _first_ connect, not a reconnect. `onReconnect` does not run for it.

## `lazy`

By default (`lazy: false`), the socket opens when you call `connect()`, and not before. Adding a listener with `on()` or calling `send()` does **not** open a non-lazy socket. You decide when it connects.

With `lazy: true`, the socket stays closed until some code needs the connection. Then it opens by itself. These calls count as "needing the connection":

- `on(...)`: adding a listener.
- `send(...)`: sending a message.
- Primitive calls that need a connection, such as `request(...)`, `channel(...).subscribe()`, or `stream(...)`.

```typescript [client/socket.ts]
import { binary, client, connect } from '@livething/client'
import { showToast } from './huddle-ui'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle', { lazy: true }),
  binary(),
)

// No connection yet. Nothing uses the socket.

socket.on('notification', (data) => showToast(data.title))
// The socket connects now, because it has a listener.
```

A `send()` on a closed lazy socket starts the connection, but that first message is not delivered, because the socket is not open yet. `send()` returns `false`. Add [`buffering()`](/client/primitives/buffering) to hold the message and send it when the socket opens. Calls that wait for an answer, such as `request(...)` and `stream(...)`, don't have this problem: they wait for the socket to open and then send.

Each listener counts as a **consumer**: something that keeps the connection open. Calling the unsubscribe function that `on()` returns removes that consumer. When no consumers are left and no operations are pending, the socket closes after [`lazyIdleTimeoutMs`](#lazyidletimeoutms). The next `on()` or `send()` opens it again. This keeps the connection closed (and saves battery on mobile) on pages that use the socket only now and then.

```typescript [client/socket.ts]
// With the lazy socket from above:
const stop = socket.on('notification', (data) =>
  showToast(data.title),
) // 1 consumer: connects
// ...
stop() // 0 consumers: the idle timer starts, and the socket closes after lazyIdleTimeoutMs
```

A `send()` also counts as use. While the socket is open with no listeners, each `send()` starts the idle timer again from zero, so a socket that only sends stays open while it keeps sending.

The idle close is a normal `disconnect()`. `onClose` runs, and when the socket opens again later it is a first connect, so `onReconnect` does not run.

A `disconnect()` does **not** reset the consumer count. Your `on()` handlers stay registered after a disconnect, so they still count as consumers the next time you call `connect()`.

::note
**React strict mode.** In development, React 18 and later mount each component twice (mount, unmount, mount). A lazy socket handles this without closing. The unmount removes the listener, and the second mount adds it again right away, long before `lazyIdleTimeoutMs` ends. So the idle close never happens. Production builds mount only once.
::

## `lazyIdleTimeoutMs`

`lazyIdleTimeoutMs` is how long a **lazy** socket stays open with nothing using it before it closes, in milliseconds. The default is `10_000` (10 seconds). It applies only in lazy mode. A non-lazy socket stays open until you call `disconnect()`.

Set it to `0` to turn off the idle close:

```typescript [client/socket.ts]
connect('wss://example.com/huddle', {
  lazy: true,
  lazyIdleTimeoutMs: 0,
})
// Opens on first use, then stays open. It never closes by itself.
```

`lazy: true` with `lazyIdleTimeoutMs: 0` means "open when needed, then stay connected". Use it for a socket that your app needs only sometimes, when opening a new connection costs more than keeping one open.

## `protocols`

This option works on WebSocket only. `http()` ignores it.

A **subprotocol** is a name for a message format that the client and server agree on when the WebSocket opens. The client offers a list of names, and the server picks one.

`protocols` is the list of subprotocols the client offers. LiveThing passes it directly to the native `WebSocket` constructor. Most apps don't need it. Use it when a gateway in front of your server expects a subprotocol, for example `huddle-v2`.

LiveThing does not choose between subprotocols. The server accepts the first name you offer, on Node and on Cloudflare. When you also use [`token`](/client/connecting/auth-and-query#token-auth-with-token), your names come first and the token goes last, so the token is never the accepted name. Names that start with `livething-v1.token.` are kept for the token, so `connect()` throws a `LiveThingConfigError` when you list one.

```typescript [client/socket.ts]
import { binary, client, connect } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle', {
    protocols: ['huddle-v2'],
  }),
  binary(),
)

socket.connect()
// After the socket opens, read which one the server picked:
socket.protocol // 'huddle-v2', or null
```

`socket.protocol` is the subprotocol the server picked. It is `null` when you offered none, when the server picked none, or when the socket is not open. The names that LiveThing adds for `token` never show here.

## `transports`

`transports` lists how the client connects. Each entry is a function that you import, so a transport you don't list stays out of your bundle. The default is `[websocket()]`.

```typescript [client/socket.ts]
import { binary, client, connect, websocket } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle', { transports: [websocket()] }),
  binary(),
)

// While the socket is open, read the transport in use:
socket.transport.get() // 'websocket', or null when not connected
```

`socket.transport` is a store, like `socket.state`, so you can also watch it with its `subscribe` method. `socket.ws` is the native WebSocket while the socket is connecting or open over WebSocket, and `null` otherwise.

`http()` connects with server-sent events and POST requests. It can be your only transport, as below, or the one the client [moves to](#failover) when a network blocks WebSocket. The server must list [`http()`](/runtimes/transports/overview) too. Give the client one URL: each transport accepts `ws`, `wss`, `http` and `https`, and changes the scheme it needs.

```typescript [client/socket.ts]
import { binary, client, connect, http } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('https://example.com/huddle', { transports: [http()] }),
  binary(),
)
```

On `http()`, the [`token`](/client/connecting/auth-and-query#token-auth-with-token) goes in an `Authorization: Bearer` header when the stream opens, and messages go up in POST batches, one at a time, in order. Each POST goes to the exact URL of the stream, query included. If the browser can stream a request body (today Chromium browsers), and the stream's connection uses HTTP/2 or HTTP/3, the client also tries [stream mode](/runtimes/transports/http#stream-mode) in the background: one long POST that carries messages as you send them. If the server does not answer its first probe within 2 seconds, the client stays on POST batches. A message that, with its 5-byte frame header, is bigger than the server's `maxPostBytes` (512 KiB by default) throws a `RangeError` when you send it. Nothing is sent and the connection stays open, so send large files with [uploads](/client/primitives/uploads), which work on `http()` too. Binary messages from the server arrive as base64 text, about a third bigger than on WebSocket. Messages are delivered at most once, as on WebSocket: a message can be lost when the connection drops, and the client does not send it again.

Every stream request carries a `LiveThing-Protocol: livething-v1` header. A browser page on another origin must send a preflight request for it, so the server always sees the `Origin`. A stream request without this header gets `426`. The [Origin check](/runtimes/transports/http#origins-cors-and-proxies) needs `allowedOrigins` for a page on another origin.

On Cloudflare, an open `http()` stream keeps the Durable Object in memory, so it does not hibernate. You get no hibernation savings for these connections.

`http()` needs a `fetch` that streams the response body. Browsers have one. React Native's own `fetch` does not stream, so install Expo's `expo/fetch`, which also works in a bare React Native app, and set it as the global `fetch`. `http()` has no option for a custom `fetch`: it uses the global one.

Serve the site over HTTP/2 or HTTP/3. HTTP/1.1 allows six connections per site, shared by all tabs, and one `http()` connection can use up to three of them: the stream and two POSTs. With [debug logging](/client/connecting/debug-logging) on, the client logs a warning when it sees HTTP/1.1. Browsers use HTTP/2 only over TLS, so plain `http://localhost` is HTTP/1.1. For local development of an app that lists only `http()`, serve it with a local certificate. LiveThing does not share one connection between tabs, so each tab opens its own.

With `http()`, [`reconnection()`](/client/primitives/reconnection#when-the-count-resets) resets its backoff only after the connection has stayed open for 30 seconds and one POST has gone through, so a connection that opens and then fails every POST still backs off.

You can also list a transport you build yourself, such as long polling. It needs a matching server transport. [Custom Transports](/runtimes/transports/custom-transports) shows both sides.

### Failover

List more than one transport, and the client tries them in list order. The first one is the one you prefer, and the rest are fallbacks:

```typescript [client/socket.ts]
import {
  binary,
  client,
  connect,
  http,
  websocket,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle', {
    transports: [websocket(), http()],
  }),
  binary(),
)
```

A transport works when the server's first frame, `__connected__`, arrives. When a transport gets no answer while it connects, the client moves on to the next one, with no `onClose`, no `onError` and no backoff in between. These count as no answer:

- The wait runs out ([`connectTimeoutMs`](#connecttimeoutms), 5 seconds with several transports).
- The connection drops with close code `1006`. A browser reports a failed WebSocket handshake this way, whatever the reason.
- The `http()` stream request fails with a network error, a 5xx status, or a 404, 405 or 426 status (the server does not offer this transport).
- Any error status that LiveThing did not make, for example one from a proxy. LiveThing marks its own error responses with a `LiveThing-Error` header.

An answer from the server is final, and the client does not try the next transport. A close with any code other than `1006` is final, and so is an error status from LiveThing, such as a 401 from your [`authenticate`](/server/server/authenticate) function. A final answer goes to `onClose` with its [close code](/core/close-codes#codes-for-a-server-sent-events-stream), and then to `reconnection()`.

The client remembers a transport that failed, for 5 minutes. A transport is marked in two cases:

- It failed while connecting, and a later transport in the list then connected. If no transport connects, nothing is marked, so a short outage does not keep the socket on a later transport.
- An `http()` connection opened, but its first POST failed, so it cannot carry messages on this network.

Every open (a first connect, a reconnect, or a lazy socket that opens again) tries the list in order and skips the transports marked in the last 5 minutes. After 5 minutes, the client tries the first transport again. When every transport is marked, it tries them all, in list order. A connection that works stays on its transport: the client goes back to the first transport only at the next open. The memory is per socket and lives in memory only. A page reload starts with an empty memory.

`socket.transport` shows which transport is in use, so you can show a banner when the socket runs on a later transport.

## `connectTimeoutMs`

A connection counts as open only when the server accepts it: the server sends a first frame, `__connected__`, after the handshake and after your [`authenticate`](/server/server/authenticate) function. Until then, the socket stays `connecting`. `connectTimeoutMs` is how long the client waits for that frame. The wait covers the handshake, `authenticate`, and a slow server start, such as a Durable Object that wakes up from cold.

With several transports, a wait that runs out moves on to the next transport (see [Failover](#failover)). With one transport, or on the last one in the list, the client closes the connection and reports an error to `onError`. With [`reconnection()`](/client/primitives/reconnection), it then tries again after the normal backoff, so the socket never waits in `connecting` forever.

```typescript [client/socket.ts]
import {
  binary,
  client,
  connect,
  reconnection,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle', { connectTimeoutMs: 10_000 }),
  binary(),
  reconnection(),
)

socket.onError((error) =>
  console.warn('Huddle could not connect:', error),
)
```

The default is 30 seconds with one transport, because one transport has nothing to fail over to and a slow network can take a while. With several transports it is 5 seconds, so a transport that does not work gives way to the next one fast. The value must be a number of milliseconds from `1` to `2147483647`.
