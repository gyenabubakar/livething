An **environment** is the object that gives `platform()` its two signals: whether the app is visible, and whether the network is online. It is a plain object with up to two optional methods, one for each signal. You pass it as `platform({ environment })`.

## The shape

```typescript [environment.ts]
interface ClientEnvironment {
  // visibility: true when the app/tab is shown, false when hidden
  onVisibilityChange?(
    callback: (visible: boolean) => void,
  ): () => void

  // network: true when online, false when offline
  onNetworkChange?(callback: (online: boolean) => void): () => void
}
```

**An environment shows what it supports by the methods it has.** There is no separate list of features to keep up to date:

- Add `onVisibilityChange`, and the visibility behavior ([background disconnect](/client/platform/background-disconnect)) can turn on.
- Add `onNetworkChange`, and the network behavior ([network-aware reconnection](/client/platform/network-aware)) can turn on.
- Leave a method out when your platform cannot report that signal.

Each method takes a callback and returns an unsubscribe function. LiveThing calls the unsubscribe function to remove your listeners when it no longer needs the signal.

The `ClientEnvironment` type, the `environment()` helper and `WebEnvironment` come from the `@livething/client/environment` subpath. They are not exported from the package root `@livething/client`:

```typescript [client/socket.ts]
import {
  environment,
  WebEnvironment,
} from '@livething/client/environment'
import type { ClientEnvironment } from '@livething/client/environment'
```

## The built-in `WebEnvironment`

In a browser, you don't need to write an environment. Import the ready-made `WebEnvironment`:

```typescript [client/socket.ts]
import { binary, client, connect, platform } from '@livething/client'
import { WebEnvironment } from '@livething/client/environment'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  platform({ environment: WebEnvironment }),
)
```

For visibility, it listens to the `visibilitychange` event on `document`. For the network, it reads `navigator.onLine` and listens to the `online` and `offline` events on `window`. Two more details:

- **It reports the current state at once**, not only on the next change. A client that starts offline knows it is offline immediately. It does not assume it is online until the state changes.
- **It is SSR-safe.** SSR (server-side rendering) runs your page code on a server, where browser globals such as `document` and `window` do not exist. `WebEnvironment` reads these globals only inside its methods, never at import time, so importing it on the server does not throw. Where the globals don't exist (SSR, Node.js, any runtime without a DOM), it reports no signals.

## Authoring your own

Outside the browser (React Native, Electron, a custom runtime), write your own environment with the `environment(...)` helper. Implement only the signals your platform can report. This example is for Electron. It uses window focus as the visibility signal, and it has no network signal. The first file below defines the environment. The second passes it to `platform()` like any other environment:

::code-group

```typescript [electron-env.ts]
import { getCurrentWindow } from '@electron/remote'
import { environment } from '@livething/client/environment'

export const ElectronEnvironment = environment({
  onVisibilityChange(callback) {
    const win = getCurrentWindow()
    const handler = () => callback(win.isFocused())
    win.on('focus', handler)
    win.on('blur', handler)

    return () => {
      win.off('focus', handler)
      win.off('blur', handler)
    }
  },
})
```

```typescript [client/socket.ts]
import { binary, client, connect, platform } from '@livething/client'
import { ElectronEnvironment } from '../electron-env'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://huddle.example.com/huddle'),
  binary(),
  platform({
    environment: ElectronEnvironment,
    backgroundDisconnectMs: 30_000,
  }),
)
```

::

A [React Native](/recipes/framework-hooks/react-native) environment has the same shape. Connect `onVisibilityChange` to React Native's `AppState` API and `onNetworkChange` to the NetInfo library.

::note
The two methods of an environment are independent. An environment with only `onNetworkChange` supports network-aware reconnection, but not background disconnect.

If you set `backgroundDisconnectMs` and the environment has no `onVisibilityChange`, `platform()` throws a `LiveThingConfigError` when the client is created. This way you see the mistake at once, and the option does not fail without any error.
::

## `TextDecoder` on React Native

[`binary()`](/client/primitives/binary) reads the info of each binary message with `TextDecoder` and the `fatal: true` option, so a broken message is refused instead of read wrongly. Every browser, Node, Bun and Deno has it. On React Native, it depends on the version and the engine:

- **React Native 0.88 and later, with Hermes**: Hermes has its own `TextDecoder`, and it honours `fatal: true`. `binary()` works with no polyfill.
- **React Native 0.87 and earlier**, or an app that runs on JSC instead of Hermes: there is no `TextDecoder`. Add a polyfill, as shown below.

On a platform without `TextDecoder`, `client(...)` throws:

```text
[livething] binary() needs TextDecoder, which this platform does not have. On React Native, add a TextDecoder polyfill that supports fatal: true.
```

`binary()` also refuses a `TextDecoder` that ignores `fatal: true`: it decodes one broken byte when `client(...)` runs and expects an error. Then it throws a different message:

```text
[livething] binary() needs a TextDecoder that honours fatal: true, and this platform's TextDecoder does not honour fatal: true. Replace it with a TextDecoder polyfill that supports fatal: true.
```

`binary()` runs both checks on every platform, so a missing or loose decoder fails at once, with one of the messages above, and never reads a message wrongly.

When you need a polyfill, choose one that honours `fatal: true`:

- **`@exodus/bytes`** is maintained, and its README suggests it as a global `TextDecoder` for React Native apps. Its `TextDecoder` follows the Encoding standard. With `fatal: true` it decodes UTF-8 with a strict decoder that throws a `TypeError` on a broken byte.
- **`text-encoding`** and its fork **`@sinonjs/text-encoding`** also honour `fatal: true`. Both are deprecated on npm ("no longer maintained"), and both GitHub repositories are archived. They still follow the standard, which has not changed for UTF-8, but they get no fixes.
- **`fast-text-encoding`** ignores `fatal`, so `binary()` refuses it.

Install the polyfill, and set it as the global `TextDecoder` in your app's entry file, before the file that calls `client(...)` runs:

<!-- docs-check: skip: @exodus/bytes is not installed in the docs checker -->

```typescript [index.ts]
import { TextDecoder } from '@exodus/bytes/encoding-lite.js'

// Fills in a missing TextDecoder. If binary() says the platform's own TextDecoder
// does not honour fatal: true, assign the polyfill without this check.
if (typeof globalThis.TextDecoder === 'undefined') {
  globalThis.TextDecoder =
    TextDecoder as typeof globalThis.TextDecoder
}
```

`encoding-lite.js` has UTF-8 and the other common encodings, and is much smaller than `encoding.js`. A client that uses neither `binary()` nor `http()` never needs `TextDecoder`. [`http()`](/client/transports/http) needs both `TextEncoder` and `TextDecoder`.

The [`token`](/client/connecting/auth-and-query) option needs a global `TextEncoder`. The client encodes the token as base64url and sends it in the WebSocket subprotocol, and it does this with `TextEncoder`. Without a global `TextEncoder`, a connection that uses `token` cannot start, so add a polyfill for it too.

React Native's TypeScript types (`globals.d.ts`, React Native 0.88) do not declare `TextDecoder`. When your app's `tsconfig.json` has no `DOM` lib, `globalThis.TextDecoder` in the file above is a type error. Declare it yourself in a `.d.ts` file:

```typescript [text-decoder.d.ts]
declare var TextDecoder: typeof import('@exodus/bytes/encoding-lite.js').TextDecoder
```
