A WebSocket connection has a life: it's born during an HTTP handshake, it lives while messages flow, and it ends when one side closes. WSKit gives you a hook at each stage on the server, and the client tracks its own connection state in parallel. This page walks the whole arc, both sides.

## The server's view

A connection passes through a fixed sequence on the server. Each stage has a matching hook on `define(...)` or on `base`.

::steps{level="3"}

### Upgrade — the handshake gate

Before a socket even opens, the browser sends a normal HTTP request asking to "upgrade" to a WebSocket. The `upgrade` hook runs here, and it decides whether to let the connection through:

```typescript [chat.ts]
const base = define({
  env: t<Env>(),
  async upgrade(request) {
    const user = await validateToken(request.headers.get('authorization'))
    if (!user) throw RejectUpgrade(4002, 'Invalid token')
    return {
      userId: user.id, // stable key for this user
      meta: { userId: user.id }, // travels into ctx.meta everywhere
    }
  },
})
```

You return `{ userId, meta }` to accept, or throw `RejectUpgrade(code, reason)` to refuse the WSKit connection. A `4xx`/`5xx` code sends an HTTP rejection; a valid WebSocket close code completes the handshake and immediately closes it so the client can read the reason. `userId` is the durable key WSKit uses to recognize this user; `meta` is per-connection data that shows up as `ctx.meta` in every handler. This is the only place authentication happens — see [Authentication](/learn/identity-and-access) for the full story.

### Init — once, before any connection

The `onInit` hook runs once when the server instance first wakes up, before it handles any connection. It's where you'd set up storage tables or other one-time state. Its context gives you `sql`, `kv`, `env`, and `log` — no connection-specific data, because no connection exists yet.

```typescript [chat.ts]
base.onInit((ctx) => {
  ctx.sql.exec('CREATE TABLE IF NOT EXISTS log (seq INTEGER, event TEXT)')
})
```

### Connect — the socket is open

Once the upgrade succeeds and the socket opens, the `onConnect` hook fires for that connection. The context is a full handler context: you can `ctx.send(...)`, read `ctx.meta`, and so on. It's the right place to send a welcome event or announce a new arrival.

```typescript [chat.ts]
base.onConnect((ctx) => {
  ctx.send('connected', { username: ctx.meta.username })
})
```

### Messages — the pipeline

This is the long middle of the connection's life. Every message the client sends runs through the same pipeline: WSKit parses the frame, routes it to the handler you registered for that event, validates the payload against the handler's `input` schema, and only then calls your `run` function. Errors thrown inside `run` are routed too — covered in [Errors](/learn/messaging).

### Disconnect — the socket closes

When the connection ends — the client navigated away, the network dropped, or you closed it — the `onDisconnect` hook fires. Its context also carries `ctx.closeCode` and `ctx.closeReason`, so you can tell a graceful close (`1000`) from a kick or a ban.

```typescript [chat.ts]
base.onDisconnect((ctx) => {
  ctx.broadcast('disconnected', {
    username: ctx.meta.username,
    code: ctx.closeCode ?? -1,
  })
})
```

### Shutdown — the server is going away

Separate from a single disconnect, the `onShutdown` hook runs when the whole server instance is winding down. Its context can broadcast to everyone and close all connections at once.

::

There are two more hooks for handling failures during the message pipeline — `onError` (a handler threw) and `onValidationError` (a payload failed its schema). Both are covered where they belong, in [Errors](/learn/messaging) and [Validation](/learn/messaging).

## The client's view

The client doesn't see "upgrade" or "disconnect" as separate hooks — it tracks a single **connection state** that moves between four values:

| State          | Meaning                      |
| -------------- | ---------------------------- |
| `closed`       | Not connected and not trying |
| `connecting`   | Opening a connection         |
| `open`         | Connected and ready          |
| `reconnecting` | Dropped, waiting to retry    |

The state lives in `socket.state`, a reactive store: read it now with `socket.state.get()`, watch it with `socket.state.subscribe(...)`, and react to specific transitions with the lifecycle callbacks:

```typescript [app.ts]
socket.connect()

socket.state.subscribe((state) => {
  console.log('state is now', state)
})

socket.onOpen(() => {
  // fires on the first connect AND every reconnect
})

socket.onClose((event) => {
  console.log('closed:', event.code, event.reason)
})
```

The most useful callbacks:

- **`onOpen`** — runs on the first connect _and_ on every reconnect. The natural place to re-fetch state or re-subscribe to things.
- **`onReconnect`** — runs only on reconnects, not the first connect.
- **`onClose`** — runs on every close, with the close code and reason.
- **`onError`** — runs on a local or connection-level error, such as a thrown client callback.
- **`onServerError`** — runs on a typed server error that no request, stream, or channel claimed.

::note
The `reconnecting` state and automatic retries only happen if you add the `reconnection()` primitive. Without it, a dropped socket goes straight to `closed` and stays there. See [Reconnection](/learn/reliability).
::

## How the two views line up

The server's stages and the client's states describe the same events from opposite ends:

- The client's `connecting` → `open` transition is the server's `upgrade` then `onConnect`.
- A clean `socket.disconnect()` on the client triggers the server's `onDisconnect` hook with close code `1000`.
- A network drop moves the client to `reconnecting` (if reconnection is on) and fires the server's `onDisconnect` with whatever close code the drop produced.

Keeping both pictures in mind — the server's hooks and the client's states — is enough to reason about any connection, healthy or broken.
