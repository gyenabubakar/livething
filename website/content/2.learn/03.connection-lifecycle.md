A WebSocket connection goes through stages. It starts with an HTTP handshake, stays open while messages flow, and ends when one side closes it. On the server, LiveThing gives you a **hook** for each stage. A hook is a function you register, and LiveThing calls it when that stage happens. On the client, LiveThing tracks the connection state at the same time. This page follows a connection from start to end, on both sides.

## The server's view

On the server, a connection always passes through the same stages, in the same order. You set every hook as a key in the object you pass to `server(...)`: `upgrade` first, then `capabilities`, then the others (`onInit`, `onConnect` and so on). Keep `upgrade` above any hook that reads `ctx.meta`. TypeScript reads the object from top to bottom, so a hook above `upgrade` sees `ctx.meta` as `unknown`.

::steps{level="3"}

### Upgrade: the handshake check

Before the socket opens, the browser sends a normal HTTP request. This request asks the server to "upgrade" the connection to a WebSocket. The `upgrade` hook runs here and decides if the connection may continue:

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import { verifySession } from './auth'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')

    return {
      userId: user.id, // stable key for this user
      meta: { name: user.name, role: user.role }, // becomes ctx.meta in every handler
    }
  },
  capabilities: [
    emits({
      notification: t<{ title: string; body: string }>(),
    }),
  ],
})
```

`verifySession` is Huddle's own auth check: it reads the session token and returns the signed-in user's `id`, `name`, and `role`, or `null` if the token is bad. To accept the connection, return `{ userId, meta }`. To refuse it, throw `RejectUpgrade(code, reason)`. The code decides how the client is refused:

- An HTTP status code (`400` to `599`) sends a normal HTTP error response. No WebSocket opens.
- A WebSocket close code (such as `4002`) finishes the handshake and then closes the socket at once. The client can then read the close code and reason.

`userId` is the stable key LiveThing uses to recognize this user across connections. It is optional: if you leave it out, the connection is **anonymous** and has no user identity. [Identity & Access](/learn/identity-and-access#authentication-the-upgrade-gate) explains what changes for an anonymous connection. `meta` is data for this one connection. It appears as `ctx.meta` in every handler. The `upgrade` hook is the only place where authentication happens. See [Identity & Access](/learn/identity-and-access) for the details.

### Init: once, before any connection

The `onInit` hook runs once when the server instance starts, before it handles any connection. On Cloudflare, it runs each time the Durable Object starts again (for example, after it wakes up from sleep). Use it to create storage tables or other one-time state, and write it so it is safe to run more than once. Its context gives you `sql`, `kv`, `platform`, and `log`. It has no connection data, because no connection exists yet.

```typescript [server/base.ts]
import { server } from '@livething/server'

export const base = server({
  onInit(ctx) {
    ctx.sql.exec(
      'CREATE TABLE IF NOT EXISTS messages (id TEXT PRIMARY KEY, room TEXT, user_id TEXT, text TEXT, sent_at INTEGER)',
    )
  },
})
```

### Connect: the socket is open

After the upgrade succeeds and the socket opens, the `onConnect` hook runs for that connection. Its context is a full handler context: you can call `ctx.send(...)`, read `ctx.meta`, and so on. Use it to send a welcome event to the connection that just opened.

`onConnect` is a key in the same `server(...)` object, below `upgrade` and `capabilities`:

```typescript [server/base.ts]
import { emits, server, t } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import { verifySession } from './auth'

export const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')

    return { userId: user.id, meta: { name: user.name } }
  },
  capabilities: [
    emits({
      notification: t<{ title: string; body: string }>(),
    }),
  ],
  onConnect(ctx) {
    ctx.send('notification', {
      title: 'Welcome to Huddle',
      body: `Signed in as ${ctx.meta.name}`,
    })
  },
})
```

### Messages: the pipeline

This is the longest stage of a connection. Every message the client sends goes through the same steps, called the **pipeline**:

1. LiveThing parses the frame.
2. It finds the handler you registered for that event.
3. It checks the payload against the handler's `input` schema.
4. Only then does it call your `run` function.

LiveThing also catches errors thrown inside `run` and sends them to the right place. See [Errors](/learn/messaging).

### Disconnect: the socket closes

A connection can end because the user left the page, the network dropped, or your code closed it. In every case, the `onDisconnect` hook runs. Its context also has `ctx.closeCode` and `ctx.closeReason`. Use them to tell a normal close (`1000`) apart from a kick or a ban.

```typescript [server/base.ts]
import { server } from '@livething/server'

export const base = server({
  onDisconnect(ctx) {
    ctx.log.info('disconnected', {
      userId: ctx.user.id,
      code: ctx.closeCode ?? -1,
    })
  },
})
```

### Shutdown: the server stops

The `onShutdown` hook runs when the whole server instance stops. This is different from one connection closing. Its context is for the whole server, not for one connection. It can broadcast to every connection and close all connections at once.

::

One more hook handles failures in the message pipeline. `onError` runs when a handler throws an error, and when a payload does not match its schema (with a `ValidationFailed` error). Both cases are covered in [Messaging](/learn/messaging), under Errors and Validation.

## The client's view

The client has no separate "upgrade" or "disconnect" hooks. Instead, it tracks one **connection state**. The state is always one of four values:

| State          | Meaning                           |
| -------------- | --------------------------------- |
| `closed`       | Not connected and not trying      |
| `connecting`   | Opening a connection              |
| `open`         | Connected and ready               |
| `reconnecting` | Connection lost, waiting to retry |

The state is in `socket.state`, a reactive store. A reactive store is a value that tells listeners when it changes. Read the current state with `socket.state.get()`. Watch every change with `socket.state.subscribe(...)`. Use the lifecycle callbacks to react to specific changes:

```typescript [client: connection.ts]
import { socket } from './socket'

socket.connect()

socket.state.subscribe((state) => {
  console.log('state is now', state)
})

socket.onOpen(() => {
  // runs on the first connect AND on every reconnect
})

socket.onClose((event) => {
  console.log('closed:', event.code, event.reason)
})
```

The most useful callbacks:

- **`onOpen`** runs on the first connect _and_ on every reconnect. Use it to load fresh data or to subscribe again.
- **`onReconnect`** runs only on reconnects, not on the first connect.
- **`onClose`** runs on every close, with the close code and reason.
- **`onError`** runs on a local or connection error, for example when one of your client callbacks throws.
- **`onServerError`** runs on a typed server error that no request, stream, or channel handled.

::note
The `reconnecting` state and automatic retries happen only if you add the `reconnection()` primitive. Without it, a dropped socket goes straight to `closed` and stays there. See [Reconnection](/learn/reliability).
::

## How the two views match

The server's stages and the client's states describe the same events from the two ends of the connection:

- When the client moves from `connecting` to `open`, the server runs `upgrade` and then `onConnect`.
- When the client calls `socket.disconnect()`, the server runs `onDisconnect` with close code `1000`.
- When the network drops, the client moves to `reconnecting` (if reconnection is on). The server runs `onDisconnect` with the close code that the drop produced.

With the server's hooks and the client's states in mind, you can understand what happens to any connection, working or broken.
