A **channel** is a server-managed room: a named group of connections that share messages. When you broadcast to a channel, only its members hear it. Channels are how you build chat rooms, document sessions, game lobbies, live dashboards — anything where a subset of users belongs together.

You _could_ fake rooms with plain [events](/learn/messaging) — tag every message with a room ID and filter on the client. But then the server sends every message to everyone, the filtering sits on the wrong side of the wire, and there's no control over who can listen. Channels fix all three: membership lives on the server, broadcasts only reach members, and joining runs through an auth gate you write.

This page shows both halves together — declaring and gating a channel on the server, and joining and reading presence on the client.

## Declaring a channel and joining it

You declare a channel on the server with `base.channel(...)`, which needs the `channels()` capability. The smallest channel is a name plus the events it broadcasts. On the client, add the `channels()` primitive, grab a handle with `socket.channel(name)`, register listeners, then `subscribe()`.

::code-group

```typescript [server: chat.ts]
import { define, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import * as v from 'valibot'
import type { InferClient } from '@wskit/server'

const base = define({
  env: t<Env>(),
  capabilities: [channels()],
})

const room = base.channel('room', {
  outgoing: {
    emits: { message: t<{ from: string; text: string }>() },
  },
})

const handleSend = room.on('send', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    // ctx.channel is scoped to this room — reaches only its members.
    ctx.channel.broadcast('message', {
      from: ctx.meta.username,
      text: input.text,
    })
  },
})

export const handler = base.assemble(handleSend)
export type ChatSocket = InferClient<typeof handler>
```

```typescript [client: app.ts]
import { channels, client, connect } from '@wskit/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(connect('wss://example.com/ws'), channels())
socket.connect()

const room = socket.channel('room')

// Listeners can be registered before the subscribe is confirmed.
room.on('message', (data) => {
  console.log(`${data.from}: ${data.text}`)
})

await room.subscribe() // resolves once the server confirms the join

room.send('send', { text: 'hello room' })
```

::

`outgoing.emits` lists the events the channel pushes to its members — the channel's own little `emits`. These become the channel's `incoming` events on the client, which is why `room.on('message', …)` is typed from the room's events, not the socket's. The names flip by perspective the same way they do at the top level:

| Server                    | Client                   |
| ------------------------- | ------------------------ |
| `base.channel('room', …)` | `socket.channel('room')` |
| `outgoing.emits` events   | `room.on(event, …)`      |
| `room.on('send', …)`      | `room.send('send', …)`   |

::note
`base.assemble(handleSend)` already pulls in the `room` channel, because the handler carries its channel with it. You only pass a channel object to `assemble` directly when it has **no** message handlers — for example a channel that's purely a gate or presence.
::

A channel is a contract within the contract: in the client type, the `channels` key maps each room to its own `incoming` / `outgoing` (and, if you add them, `requests` and `streams`), mirrored exactly like the top level but scoped to that room. That's why the same event name can mean one thing at the socket level and another inside a channel.

## The auth gate: check and commit

Joining is never automatic — the client asks, and the server decides. If a channel needs information to make that call (a token, an invite code), declare a `subscribe` schema; the client must pass a matching payload, and it's validated before the gate runs. Then up to two gates decide go/no-go. **Throwing from either one rejects the subscribe.**

::code-group

```typescript [server: chat.ts]
const room = base.channel('room', {
  outgoing: { emits: { message: t<{ from: string; text: string }>() } },
  subscribe: v.object({ token: v.string() }),
  async check(ctx, input) {
    // input is typed { token: string } from the subscribe schema.
    const role = await lookupRole(input.token) // slow work goes here
    if (!role) throw new Error('unknown token')
    return { role } // handed to commit, fully typed
  },
  commit(ctx, { role }) {
    // Sync, runs in the same tick as the membership write.
    if (role === 'banned') throw new Error('banned')
    if (ctx.channel.members().length >= 50) throw new Error('room is full')
  },
})
```

```typescript [client: app.ts]
const room = socket.channel('room')

// The payload is required because the channel declared a subscribe schema.
await room.subscribe({ token: 'tok-member' })
```

::

`check(ctx, input)` runs first and can be `async`, so it's the place for lookups — verify the token, hit a database, call an auth service. Whatever it **returns** is handed to `commit`. `commit(ctx, checkResult)` runs second and must be **synchronous**: it's the last-moment check against live state, like room capacity, where the count must not change between the test and the write. Most channels need only `check`; `commit` is optional.

::tip
A plain `throw new Error(...)` rejects the join, but the client only sees a generic `internal-error` — WSKit never leaks raw error details. To send a reason the client can catch and narrow, throw a registered typed error instead. See [Messaging](/learn/messaging) for the error model.
::

The subscribe payload can be a **function** instead of a plain value. WSKit re-runs it on reconnect, so a rotating token stays fresh: `room.subscribe(() => ({ token: getFreshToken() }))`.

For the full gate behavior, the leave paths, and `revalidate` on reconnect, see [Server · Auth Gate](/server/channels/auth-gate) and [Client · channels](/client/primitives/channels).

## Static vs dynamic

There are two flavors of channel:

- **Static** channels have a fixed name you know at write time — `lobby`, `announcements`, `support`. You declare each one by name.
- **Dynamic** channels (also called _families_) follow a pattern, so one declaration covers many rooms. You pass a `[familyKey, template]` tuple with `{...}` placeholders, and rooms come and go as users subscribe.

::code-group

```typescript [server: chat.ts]
// One declaration covers room:alpha, room:42, and any other room:{id}.
const room = base.channel(['rooms', 'room:{id}'], {
  outgoing: { emits: { message: t<{ from: string; text: string }>() } },
})

const handleSend = room.on('send', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    // ctx.channel is bound to the exact room the message came in on.
    ctx.channel.name // 'room:alpha' — the matched name
    ctx.channel.family // 'rooms' — the family key
    ctx.channel.params.id // 'alpha' — typed from the {id} capture
    ctx.channel.broadcast('message', {
      from: ctx.meta.username,
      text: input.text,
    })
  },
})
```

```typescript [client: app.ts]
// For a family, pass the family key and the concrete room name.
const room = socket.channel('rooms', 'room:alpha')
await room.subscribe()
room.send('send', { text: 'hi' })
```

::

Use static when the set of rooms is known and small. Use dynamic when rooms are created on the fly — one per document, per game, per conversation. Each matched name is a fully separate instance: `room:alpha` never sees `room:42`'s members, and a broadcast to one never reaches the other. For the template grammar, captures, and isolation rules, see [Server · Dynamic Families](/server/channels/dynamic-families).

## Presence: members vs online

Once people are in a room you usually want to _show_ them — a roster, an avatar that dims when a connection drops, a "who's typing" line. That's **presence**, and it carries one important distinction:

- **Membership** is whether a connection belongs to the channel. You become a member when you subscribe and stay one until you unsubscribe or are removed. This is the "who's in this room" set.
- **Online** is whether a member's connection is live _right now_. A member can briefly go offline — laptop slept, network blipped — without leaving the room, then come back online, a member the whole time.

The split matters because a momentary drop shouldn't kick someone out. Presence is automatic once channels are on — you don't declare anything extra.

::code-group

```typescript [server: chat.ts]
// Read the roster inside any channel handler.
const handleWhoIsHere = room.on('who-is-here', {
  input: v.object({}),
  run(ctx) {
    const names = ctx.channel.members().map((m) => m.meta.username)
    ctx.send('roster', { names })
  },
})

// Lifecycle hooks fire as members truly join and leave.
room.subscribe((ctx) => {
  ctx.channel.broadcast('message', {
    from: 'system',
    text: `${ctx.meta.username} joined`,
  })
})

room.unsubscribe((ctx) => {
  ctx.channel.broadcast('message', {
    from: 'system',
    text: `${ctx.meta.username} left`,
  })
})
```

```typescript [client: app.ts]
const room = socket.channel('room')
await room.subscribe()

// A live snapshot, keyed by connection ID, each member carrying its meta.
for (const [connectionId, member] of room.members.get()) {
  console.log('here:', member.meta)
}

room.onMemberJoin((connectionId, member) =>
  addToRoster(connectionId, member.meta),
)
room.onMemberLeave((connectionId) => removeFromRoster(connectionId))
room.onMemberOffline((connectionId) => dimAvatar(connectionId)) // still a member, just away
room.onMemberOnline((connectionId, member) => brightenAvatar(connectionId))
```

::

The two pairs of callbacks answer different questions, and that's the whole point of presence:

| Callback          | Fires when                                                                    |
| ----------------- | ----------------------------------------------------------------------------- |
| `onMemberJoin`    | Someone subscribes — a real join, the member list grew                        |
| `onMemberLeave`   | Someone unsubscribes or is removed — a real leave, the list shrank            |
| `onMemberOnline`  | An existing member's connection comes back — the list is unchanged            |
| `onMemberOffline` | An existing member's connection drops but they stay a member — list unchanged |

Use **join/leave** to add and remove people from the visible roster, and **online/offline** to show a presence dot or grey out an avatar without removing anyone. When you subscribe, the server sends the full current roster, so `room.members.get()` starts populated — you don't wait for join events to trickle in. `room.members` is a reactive store, so you can also `room.members.subscribe(...)` to re-render the list on every change.

For the full member shape, server-side controls (kicking, server-driven subscribe), and how online/offline behaves on persistent channels, see [Server · channels](/server/channels/defining) and [Client · channels](/client/primitives/channels).
