A **channel** is a room that the server manages. It is a named group of connections that share messages. When you broadcast to a channel, only its members receive the message. You use channels for chat rooms, shared document sessions, game lobbies, live dashboards, and any other case where a group of users belongs together.

You _could_ build rooms with plain [events](/learn/messaging) instead: add a room ID to every message and filter on the client. But this has three problems. The server sends every message to every client. The filtering happens on the client, which is the wrong side. And nothing controls who can listen. Channels solve these problems. The server keeps the list of members, a broadcast reaches only members, and every join goes through an **auth gate**: a check that you write, which decides if a connection may join.

This page shows both sides together. On the server, you declare a channel and control who joins. On the client, you join the channel and read who is in it.

## Declaring a channel and joining it

You declare a channel on the server with `base.channel(...)`. This needs the `channels()` capability. The smallest channel is a name plus the events it broadcasts. On the client, add the `channels()` primitive and get a handle with `socket.channel(name)`. A **handle** is an object that you use to work with one channel. Register your listeners on it, then call `subscribe()` to join.

The server below also has an `upgrade` hook, as on the [Connection Lifecycle](/learn/connection-lifecycle) page. It puts the user's name into `meta`, so handlers can read it as `ctx.meta.username`. The later examples on this page use the same `base`.

::code-group

```typescript [server: chat.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { RejectUpgrade } from '@livething/server/errors'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await validateToken(token) // your own auth check
    if (!user) throw RejectUpgrade(4002, 'Invalid token')
    return { userId: user.id, meta: { username: user.name } }
  },
  capabilities: [channels()],
})

const room = base.channel('room', {
  capabilities: [
    emits({ message: t<{ from: string; text: string }>() }),
  ],
})

const handleSend = room.on('send', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    // ctx.channel sends only to the members of this room.
    // includeSelf also sends the message back to the sender.
    ctx.channel.broadcast(
      'message',
      { from: ctx.meta.username, text: input.text },
      { includeSelf: true },
    )
  },
})

export const definition = base.assemble({ handlers: [handleSend] })
export type ChatSocket = InferClient<typeof definition>
```

```typescript [client: app.ts]
import { channels, client, connect } from '@livething/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(
  connect('wss://example.com/ws'),
  channels(),
)
socket.connect()

const room = socket.channel('room')

// You can register listeners before the server confirms the subscribe.
room.on('message', (data) => {
  console.log(`${data.from}: ${data.text}`)
})

await room.subscribe() // resolves when the server confirms the join

room.send('send', { text: 'hello room' })
```

::

By default, `ctx.channel.broadcast(...)` skips the connection that sent the message. The `{ includeSelf: true }` option includes it, so the sender also sees its own message.

The channel's `emits(...)` capability lists the events that the channel sends to its members. It works like the top-level `emits`, but only for this channel. On the client, these become the channel's `incoming` events. This is why the type of `room.on('message', …)` comes from the room's events and not from the socket's events. The names swap sides in the same way as at the top level:

| Server                      | Client                   |
| --------------------------- | ------------------------ |
| `base.channel('room', …)`   | `socket.channel('room')` |
| Channel `emits(...)` events | `room.on(event, …)`      |
| `room.on('send', …)`        | `room.send('send', …)`   |

::note
`base.assemble({ handlers: [handleSend] })` adds the `room` channel and turns on `handleSend`. You must list every channel handler this way. If you pass the channel object itself, LiveThing adds the channel's settings and lifecycle hooks, but turns on none of its message handlers. This is useful for a channel that only has an auth gate or presence, or whose handlers you want to leave off on purpose.
::

A channel is a contract inside the contract. In the client type, the `channels` key maps each room to its own `incoming` and `outgoing` events (and `clientRequests`, `serverRequests` and `streams`, if you add them). They mirror the top level, but they belong only to that room. So the same event name can mean one thing at the socket level and a different thing inside a channel.

## The auth gate: check and commit

A client never joins a channel automatically. The client asks, and the server decides. The channel may need some data to decide, such as a token or an invite code. In that case, declare a `subscribe` schema. The client must then send a payload that matches it, and LiveThing validates the payload before the gate runs. After that, up to two gate functions decide yes or no. **If either one throws, the subscribe is rejected.**

::code-group

```typescript [server: chat.ts]
const room = base.channel('room', {
  capabilities: [
    emits({ message: t<{ from: string; text: string }>() }),
  ],
  subscribe: v.object({ token: v.string() }),
  async check(ctx, input) {
    // input is typed { token: string } from the subscribe schema.
    const role = await lookupRole(input.token) // slow work goes here
    if (!role) throw new Error('unknown token')
    return { role } // passed to commit, fully typed
  },
  commit(ctx, { role }) {
    // Synchronous: no other code runs between this check and the membership write.
    if (role === 'banned') throw new Error('banned')
    if (ctx.channel.members().length >= 50)
      throw new Error('room is full')
  },
})
```

```typescript [client: app.ts]
const room = socket.channel('room')

// The payload is required because the channel declares a subscribe schema.
await room.subscribe({ token: 'tok-member' })
```

::

`check(ctx, input)` runs first. It can be `async`, so this is the place for slow lookups: verify the token, read a database, or call an auth service. The value that `check` **returns** goes to `commit`. `commit(ctx, checkResult)` runs second and must be **synchronous**. It is the final check against the live state of the room, such as the room size. Because it is synchronous, the member count cannot change between the check and the moment the member is added. Most channels need only `check`. `commit` is optional.

::tip
A plain `throw new Error(...)` rejects the join, but the client only receives a generic `internal-error`. LiveThing never sends raw error details to the client. To send a reason that the client can catch and check, throw a registered typed error instead. See [Messaging](/learn/messaging) for how errors work.
::

The subscribe payload can also be a **function** instead of a plain value. On a channel with `membership: 'ephemeral'`, the client subscribes again after each reconnect, and LiveThing calls the function again each time. This keeps a token that changes over time up to date: `room.subscribe(() => ({ token: getFreshToken() }))`. Channels are `'persistent'` by default. On a persistent channel, the server puts the member back into the channel itself after a reconnect, and runs the channel's `revalidate` hook instead of `check`.

For the full gate behavior, the ways a member can leave, and `revalidate` on reconnect, see [Server · Auth Gate](/server/channels/auth-gate) and [Client · channels](/client/primitives/channels).

## Static vs dynamic

There are two kinds of channel:

- A **static** channel has a fixed name that you know when you write the code, such as `lobby`, `announcements`, or `support`. You declare each one by name.
- A **dynamic** channel (also called a _family_) follows a name pattern, so one declaration covers many rooms. You pass a `[familyKey, template]` tuple (an array with exactly two items). The template contains `{...}` placeholders. A new room exists as soon as a user subscribes to a name that matches the pattern.

::code-group

```typescript [server: chat.ts]
// One declaration covers room:alpha, room:42, and any other room:{id}.
const room = base.channel(['rooms', 'room:{id}'], {
  capabilities: [
    emits({ message: t<{ from: string; text: string }>() }),
  ],
})

const handleSend = room.on('send', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    // ctx.channel belongs to the exact room the message came from.
    ctx.channel.name // 'room:alpha': the matched name
    ctx.channel.family // 'rooms': the family key
    ctx.channel.params.id // 'alpha': typed from the {id} placeholder
    ctx.channel.broadcast('message', {
      from: ctx.meta.username,
      text: input.text,
    })
  },
})
```

```typescript [client: app.ts]
// For a family, pass the family key and the concrete room name.
const room = socket.channel('rooms', 'room:alpha')
await room.subscribe()
room.send('send', { text: 'hi' })
```

::

Use a static channel when the set of rooms is small and known in advance. Use a dynamic channel when your app creates rooms while it runs, for example one per document, per game, or per conversation. Each matched name is a fully separate room. `room:alpha` never sees the members of `room:42`, and a broadcast to one never reaches the other. For the template rules, placeholders, and how rooms stay separate, see [Server · Dynamic Families](/server/channels/dynamic-families).

## Presence: members vs online

When people are in a room, you usually want to _show_ them: a **roster** (the list of people in the room), an avatar that turns grey when a connection drops, or a "who is typing" line. This is called **presence**. Presence has two separate ideas:

- **Membership** says whether a connection belongs to the channel. A connection becomes a member when it subscribes. It stays a member until it unsubscribes or the server removes it. This is the "who is in this room" list.
- **Online** says whether a member's connection is live _right now_. Channels are persistent by default. On a persistent channel, a member can go offline for a short time (a laptop goes to sleep, or the network drops) without leaving the room. When the connection comes back, the member is online again, and was a member the whole time.

The split exists so that a short network drop does not remove someone from the room. On a channel with `membership: 'ephemeral'`, there is no such split: a disconnect counts as a real leave. Presence works as soon as channels are on. You don't declare anything extra.

In the example below, the room also declares a `roster` event, so a member can ask for the current list of names.

::code-group

```typescript [server: chat.ts]
const room = base.channel('room', {
  capabilities: [
    emits({
      message: t<{ from: string; text: string }>(),
      roster: t<{ names: string[] }>(),
    }),
  ],
})

// Read the roster inside any channel handler.
const handleWhoIsHere = room.on('who-is-here', {
  input: v.object({}),
  run(ctx) {
    const names = ctx.channel.members().map((m) => m.meta.username)
    // ctx.channel.send sends a channel event to this connection only.
    ctx.channel.send('roster', { names })
  },
})

// These hooks run only when a member really joins or leaves.
room.subscribe((ctx) => {
  ctx.channel.broadcast('message', {
    from: 'system',
    text: `${ctx.meta.username} joined`,
  })
})

room.unsubscribe((ctx) => {
  ctx.channel.broadcast('message', {
    from: 'system',
    text: `${ctx.meta.username} left`,
  })
})
```

```typescript [client: app.ts]
const room = socket.channel('room')
await room.subscribe()

// The current members, keyed by member ID.
// Each member carries its meta and whether it is online now.
for (const member of room.members.get().values()) {
  console.log('here:', member.meta, member.online)
}

room.onMemberJoin((memberId, member) =>
  addToRoster(memberId, member.meta),
)
room.onMemberLeave((memberId) => removeFromRoster(memberId))
room.onMemberOffline((memberId) => dimAvatar(memberId)) // still a member
room.onMemberOnline((memberId) => brightenAvatar(memberId))
```

::

On this persistent channel, a **member ID** is the user's ID (the `userId` from the upgrade step). So a user keeps the same member ID when they reconnect, and a user with two tabs open is one member. On an ephemeral channel, or for an anonymous connection, the member ID is the connection ID.

The two pairs of callbacks answer different questions:

| Callback          | Runs when                                                                               | Member list |
| ----------------- | --------------------------------------------------------------------------------------- | ----------- |
| `onMemberJoin`    | A new member subscribes                                                                 | grows       |
| `onMemberLeave`   | A member unsubscribes or is removed. On an ephemeral channel, a disconnect also counts. | shrinks     |
| `onMemberOnline`  | A member gets their first live connection in the channel: after a join or a reconnect   | unchanged   |
| `onMemberOffline` | A member's last live connection drops. It also runs right after `onMemberLeave`.        | unchanged   |

Use **join/leave** to add people to the visible roster and remove them from it. Use **online/offline** to show a presence dot or to grey out an avatar without removing anyone. A member who is offline stays in the list with `online: false`. When you subscribe, the server sends the full current roster, so `room.members.get()` has the list from the start. You don't need to wait for join events. `room.members` is a reactive store (a value you can watch for changes), so you can also call `room.members.subscribe(...)` to redraw the list on every change.

For the full member shape, the server-side controls (removing a member, subscribing a connection from the server), and how online/offline works on persistent channels, see [Server · channels](/server/channels/defining) and [Client · channels](/client/primitives/channels).
