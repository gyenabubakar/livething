LiveThing turns on almost nothing by default. You add features one at a time. Every feature has two matching parts: a **capability** on the server and a **primitive** on the client. This page explains how the two parts fit together, and why this design keeps your bundles small. (A bundle is the final JavaScript file that your build tool makes from your code and the libraries it imports.)

## A feature has two parts

Take channels as an example. A channel is a named group of connections, such as a chat room. To use channels, you turn them on in two places:

::code-group

```typescript [Server]
import { server } from '@livething/server'
import { channels } from '@livething/server/channels'

const base = server({
  capabilities: [channels()], // server part
})
```

```typescript [Client]
import { channels, client, connect } from '@livething/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(
  connect('wss://example.com/ws'),
  channels(), // client part
)
```

::

The server part is the **capability**. It adds the channel code to the server and gives your handlers `ctx.channel`, the object for working with the current channel. The client part is the **primitive**. It adds `socket.channel(...)` to the socket. Both parts have the same name, one on each side.

The whole framework uses this pairing. Client-to-server requests use a `clientRequests()` capability on the server and a `clientRequests()` primitive on the client. Streaming uses `stream()` on both sides. Keepalive (regular pings that check that the connection is still alive), replay (sending missed messages again after a reconnect) and dedup (dropping repeated copies of the same message) work the same way: a capability you list on the server and a primitive you pass on the client.

## Server: capabilities you list

On the server, you put capabilities in the `capabilities` array of `server(...)`:

```typescript [chat.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { clientRequests } from '@livething/server/client-requests'

const base = server({
  capabilities: [
    emits({ message: t<{ text: string }>() }),
    channels(),
    clientRequests(),
  ],
})
```

When you list a capability, two things happen:

1. The code for that feature goes into your build.
2. The matching entries go into your contract, so `InferClient` passes them to the client.

A capability that you do not list costs nothing. Its code is not in your build, and its keys are not in your contract.

Most capabilities have their own import path. For example, `channels()` comes from `@livething/server/channels` and `clientRequests()` comes from `@livething/server/client-requests`. A few common ones, like `emits()`, come directly from `@livething/server`. Each feature page shows the exact import.

::tip
Listing a capability also adds the matching builder methods to `base` (the methods you use to create handlers). Add `clientRequests()` and you can call `base.request(...)`. Add `channels()` and you can call `base.channel(...)`. Without the capability, these methods do not exist on `base`, so you cannot use a feature by mistake before you turn it on.
::

## Client: primitives you pass

On the client, primitives are arguments to the socket factory. `client<Contract>()` returns a function. You call that function with `connect(...)` and any primitives you want:

```typescript [app.ts]
import {
  channels,
  client,
  clientRequests,
  connect,
  reconnection,
} from '@livething/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(
  connect('wss://example.com/ws'),
  channels(),
  clientRequests(),
  reconnection(),
)
```

`connect(...)` is the only required primitive. It sets the server URL that the socket connects to. All the others are optional. A primitive you pass adds its methods to the socket. If you do not pass a primitive, its methods cannot be used. For example, if you call `socket.request(...)` without `clientRequests()`, TypeScript shows a compile error. You find the mistake while you write code, not when the app runs.

Some primitives match a server capability, for example `channels()`, `clientRequests()`, `serverRequests()` and `stream()`. Others exist only on the client, because they control how the client behaves and the server does not need them. `reconnection()`, `buffering()` and `quality()` are client-only.

## Your bundle contains only what you import

This design keeps LiveThing small. Each primitive and each capability is a separate module, so your bundler can remove every module you do not import. This removal is called **tree-shaking**.

On the client, a minimal typed socket is about **5.24 KB** (minified and gzipped). With every primitive, it is about **21.3 KB**. The difference comes only from the primitives you add.

The server works the same way. If you do not list `channels()`, the channel code is not in your server bundle. You never pay, in bytes or in extra concepts, for a feature you did not add.

For the full numbers per adapter and per capability, see [Bundle size](/start/why-livething#bundle-size).

## The mental model

When you want to add a feature, ask one question: _what is the capability, and what is the primitive?_

- The **capability** turns on the feature on the server and adds it to the contract.
- The **primitive** turns on the feature on the client and adds its methods to the socket.
- `InferClient` carries the types from one side to the other, so both parts always describe the same feature.

Every feature page in this section follows this pair.
