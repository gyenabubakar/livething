WSKit ships almost nothing turned on by default. You add features one at a time, and every feature comes in two matched halves: a **capability** on the server and a **primitive** on the client. This page explains that pairing and why it keeps your bundles small.

## A feature has two halves

Take channels. To use rooms, you turn them on in two places:

::code-group

```typescript [Server]
import { define, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'

const base = define({
  env: t<Env>(),
  capabilities: [channels()], // server half
})
```

```typescript [Client]
import { channels, client, connect } from '@wskit/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(
  connect('wss://example.com/ws'),
  channels(), // client half
)
```

::

The server half — the **capability** — turns on the room engine and the `ctx.channel` surface inside your handlers. The client half — the **primitive** — adds `socket.channel(...)` to the socket. Same feature, named the same thing, one on each side.

This pairing runs through the whole framework. Requests have a `requests()` capability and a `requestResponse()` primitive. Streaming has `stream()` on both sides. Keepalive, replay, dedup — each is a capability you list on the server and a primitive you pass on the client.

## Server: capabilities you list

On the server, capabilities go in the `capabilities` array of `define(...)`:

```typescript [chat.ts]
import { define, emits, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { requests } from '@wskit/server/requests'

const base = define({
  env: t<Env>(),
  capabilities: [
    emits({ message: t<{ text: string }>() }),
    channels(),
    requests(),
  ],
})
```

Listing a capability does two things. It pulls that feature's engine code into your build, and it adds the matching entries to your contract — so `InferClient` carries them to the client. A capability you leave out costs nothing: its code never ships, and its contract keys are simply absent.

Most capabilities live at their own import path — `channels()` from `@wskit/server/channels`, `requests()` from `@wskit/server/requests`, and so on. A few of the most common ones, like `emits()`, come straight from `@wskit/server`. Each feature page tells you the exact import.

::tip
Listing a capability is also what unlocks the matching builder methods on `base`. Add `requests()` and you can call `base.request(...)`. Add `channels()` and you can call `base.channel(...)`. Without the capability, those methods aren't there — so you can't accidentally use a feature you haven't turned on.
::

## Client: primitives you pass

On the client, primitives are arguments to the socket factory. `client<Contract>()` returns a function; you call it with `connect(...)` plus whatever primitives you want:

```typescript [app.ts]
import {
  channels,
  client,
  connect,
  reconnection,
  requestResponse,
} from '@wskit/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(
  connect('wss://example.com/ws'),
  channels(),
  requestResponse(),
  reconnection(),
)
```

`connect(...)` is the one required piece — it's where the socket dials. Everything after it is optional. A primitive you pass adds its methods to the socket; a primitive you don't pass simply doesn't exist on `socket`. Try to call `socket.request(...)` without `requestResponse()` and it's a compile error, not a runtime surprise.

Some primitives mirror a server capability (channels, requests, streams). Others are client-only, because they describe client behavior the server doesn't need to know about — reconnection, buffering, and quality tracking live entirely on the client.

## You pay for what you import

This two-halves design isn't just tidy — it's how WSKit stays small. Each primitive and capability is a separate module, so your bundler can drop everything you don't import. A minimal client comes to about **4.5 KB gzipped**; pull in every primitive and it's about **16 KB**. The difference is exactly the primitives you chose to leave out.

The same holds on the server: a handler with no channels never pulls the channel engine into its bundle. You're never paying — in bytes or in complexity — for a feature you didn't ask for.

## The mental model

When you want to add a feature, the question is always the same: _what's the capability, and what's the primitive?_

- The **capability** turns the feature on server-side and adds it to the contract.
- The **primitive** turns the feature on client-side and adds the methods.
- `InferClient` carries the typing between them, so the two halves are always describing the same thing.

Every feature page in this section is organized around that pair.
