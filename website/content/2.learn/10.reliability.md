Real networks are not stable. A laptop goes to sleep, a phone moves to another cell tower, a proxy closes a connection that has been quiet for too long, or you deploy a new version. Each of these drops the connection. An app that ignores this works well on your own machine but fails for real users. **Reliability** is a small set of primitives that keep a connection healthy and keep your data correct when the network fails.

The primitives work together. Each one handles a different failure, and together they cover a full drop and recovery:

- **Keepalive** finds a socket that stopped working without a close message, and closes it.
- **Reconnection** opens the socket again. It waits longer between each attempt, so many clients don't all hit the server at the same moment.
- **Buffering** keeps the messages you sent during the drop and sends them when the socket is back.
- **Replay** and **dedup** get the messages you missed while you were away, and make sure you don't process any message twice.

Most of this is client-side, because the client is where the network fails most often. A few also have a server part: replay, keepalive, and the `sequence` and `dedup` capabilities. You add only the ones you need. A primitive you leave out adds nothing to your bundle.

## Problem to primitive

| Problem                                               | Primitive                                            |
| ----------------------------------------------------- | ---------------------------------------------------- |
| A proxy closes a quiet socket without a close message | **Keepalive**: sends pings and notices missing pongs |
| The socket drops and stays closed                     | **Reconnection**: retries with backoff               |
| The user sends things while offline                   | **Buffering**: queues sends and flushes on reconnect |
| Messages were missed during the drop                  | **Replay**: catches up after reconnect               |
| The same message arrives twice                        | **Dedup**: drops the duplicate                       |

## The stacked client

A typical client that must survive drops adds several primitives in one `client<HuddleSocket>()(...)` call. They are plain functions. The order you list them in does not matter, because LiveThing sorts them by their dependencies:

```typescript [client: socket.ts]
import {
  binary,
  buffering,
  client,
  connect,
  keepalive,
  reconnection,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(), // Huddle's server sends binary messages
  reconnection(), // connect again after a drop
  keepalive(), // notice a dead socket fast
  buffering(), // keep sends made while offline
)
socket.connect()
```

Here is how they work together. **Keepalive** notices that the socket stopped answering and closes it. **Reconnection** opens it again. **Buffering** sends anything you tried to send while the socket was closed. **Replay** and **dedup** (add them when you need catch-up) deliver the messages the server sent while you were gone. The rest of this page covers each one: the idea, the smallest setup, and when to use it.

## Keepalive: notice a dead socket

A WebSocket can stop working without any close message. A proxy closes the connection, a phone loses signal, or a laptop goes to sleep, and both sides still think the socket is open. This is called a _half-open_ connection: it looks open, but no data gets through. Keepalive finds it. It sends small check messages called **pings** at a regular interval, and waits for the answers, called **pongs**. When too many pongs don't arrive, it treats the socket as dead and closes it. Reconnection can then start.

Keepalive has a real part on **both** sides. The client sends pings from its side. The server sends pings from its side and closes connections that go quiet.

::code-group

```typescript [client: socket.ts]
import { binary, client, connect, keepalive } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  keepalive({ maxMissedPongs: 2 }),
)
```

```typescript [server: keepalive.ts]
import { server } from '@livething/server'
import { keepalive } from '@livething/server/keepalive'

const base = server({
  capabilities: [
    keepalive({ pingIntervalMs: 30_000, idleTimeoutMs: 60_000 }),
  ],
})
```

::

On the client, `maxMissedPongs` is how many missed pongs the client allows (default `2`). The client pings as often as the server does: the server sends its `pingIntervalMs` in the first frame of each connection. When the server sends no pings, the client pings every 30 seconds. After `maxMissedPongs` missed pongs, the client closes the socket with the `IDLE` close code. If reconnection is installed, a new connection attempt starts.

On the server, `pingIntervalMs` is the time between pings (default `30_000`). `idleTimeoutMs` (default `60_000`) is how long a connection may send _nothing_ before the server closes it. Any message from the client resets this timer, including an app message or a pong. `pingIntervalMs` must be less than `idleTimeoutMs`, so that a healthy client's pong always arrives in time. If it is not less, `keepalive()` throws an error.

With [hibernation](/server/server/hibernation) on, the server runs no idle timer for a WebSocket that hibernates. On Cloudflare, the platform then answers a client's ping by itself, without waking the server. So such a connection has no server-side idle close. An [`http()`](/client/transports/http) connection keeps the object awake, so its timers still run.

Each ping and pong pair also measures latency. So `keepalive()` adds two reactive stores (see [Connection Lifecycle](/learn/connection-lifecycle)) to the client socket: `socket.quality` and `socket.latency`. Read the current value with `.get()`, or run code on every change with `.subscribe(...)`. You can use them to show a "your connection is poor" banner. To set your own latency limits for each quality level, pass `keepalive({ thresholds })`.

**When you need it:** for any socket that stays open for a long time, and especially for durable streams. Without keepalive, a half-open connection can stay unnoticed for minutes.

Full detail: [Client · keepalive](/client/primitives/keepalive) and [Server · keepalive](/server/capabilities/keepalive).

## Reconnection: bring the socket back

A plain WebSocket that drops stays closed. `onclose` runs, and nothing else happens. The `reconnection()` primitive makes the client connect again by itself after an unexpected drop. It is client-only. The server needs no setup for it.

```typescript [client: socket.ts]
import {
  binary,
  client,
  connect,
  reconnection,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  reconnection({ maxAttempts: Infinity }),
)
```

After a drop, the socket moves to the `reconnecting` state and tries again. It uses **exponential backoff**: the wait doubles after each attempt (1s, 2s, 4s, and so on) up to a limit, which is `maxDelay` (default 30 seconds). It also adds **jitter**, a small random change to each wait. Without jitter, a thousand clients that dropped at the same time would all retry at the same moment. By default the client stops after 10 attempts. Set `maxAttempts: Infinity` to retry with no limit.

Some closes should not be retried. For example, after a `BANNED` close, a new connection only gets banned again. So by default the client does not reconnect after `AUTH_INVALID`, `DUPLICATE`, or `BANNED`. To add more codes to that list, pass them in `nonRetryableCodes`. For a decision on each close, pass a `shouldReconnect(code, reason)` callback.

::tip
The named close codes, such as `CloseCodes.BANNED` and `CloseCodes.AUTH_INVALID`, come from `@livething/core`. So you can write them by name instead of remembering numbers.
::

Reconnection brings back the _socket_ only. It does not join channels again or deliver missed messages by itself. Other primitives do those jobs. Reconnection is the base they need: first the socket comes back, then the other primitives restore what was happening on it.

**When you need it:** almost always, for any app that should keep working after a short network drop.

Full detail: [Client · reconnection](/client/primitives/reconnection).

## Buffering: keep offline sends

What happens to a `send(...)` while the socket is closed? By default, the message is dropped, because there is no open connection to send it on. For actions the user starts, this is a real problem: the user types a message during a short drop, and the message is lost. The `buffering()` primitive **queues** the sends made while offline and **flushes** them when the socket reconnects. It is client-only, and it is on as soon as you add it to the socket.

```typescript [client: socket.ts]
import {
  binary,
  buffering,
  client,
  connect,
  reconnection,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  reconnection(),
  buffering({
    maxMessages: 50, // hold at most 50; the oldest is dropped when full
    ttl: 30_000, // drop a queued message after 30s because it is too old
  }),
)
```

`ttl` means "time to live": how long a queued message stays useful before it is dropped. Buffering works well with reconnection: reconnection brings the socket back, and buffering sends what you tried to send in the meantime. Buffering also checks what kind of close happened. After an **unexpected drop**, it keeps the queue for the reconnect. After you call `socket.disconnect()` yourself, it empties the queue, because you chose to leave. A message that gets old fast can set its own shorter TTL on each call:

```typescript [client: room.ts]
import { socket } from './socket'

const general = socket.channel('rooms', 'room:general')

// a typing indicator is useless if it waits in the queue for more than 2s
general.send('start-typing', {}, { ttl: 2000 })
```

::warning
Buffered messages are still fire-and-forget: the client sends them and does not wait for an answer. Buffering makes sure the client _tries_ to send a message when the socket returns. It does not confirm that the server handled it. If you need confirmation, use a [request](/learn/messaging). A request waits for the server's reply. If a buffered request is removed from the queue before it is sent (the queue was full, or its TTL passed), it rejects with the `Dropped` error.
::

**When you need it:** for user actions that must not be lost in a short drop, such as sending a chat message or posting a comment. It is less useful for frequent events where only the latest value matters, such as cursor positions. For those, use a short `ttl` or don't buffer them.

Full detail: [Client · buffering](/client/primitives/buffering).

## Replay & dedup: catch up without duplicates

Buffering handles messages _you_ tried to send while offline. But what about the messages the _server_ sent while you were away? Your client never got them, so they are lost unless the server kept a copy. **Replay** is the catch-up. The server gives each outgoing message a **sequence number**. The numbers only go up, but one client can see gaps between them, because other clients' messages use numbers too. The client remembers the highest number it has seen. On reconnect, it asks the server for every message after that number. **Dedup** protects against doubles. During a reconnect, the same message can arrive twice. So each message also carries a unique ID, and dedup drops any message whose ID it has already seen.

On the server, this pair uses three capabilities. `sequence()` gives each message its number. `dedup()` gives each outgoing message a unique ID. It also drops a duplicate message that comes _in_ with a delivery ID, but the LiveThing client does not set one. `replay` decides _which_ messages to store and send again.

::code-group

```typescript [client: socket.ts]
import {
  binary,
  client,
  connect,
  dedup,
  reconnection,
  replay,
} from '@livething/client'
import { showAnnouncement } from './huddle-ui'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  reconnection(),
  dedup(), // replay() needs dedup()
  replay(),
)

// Missed messages arrive through the same on() handlers as live ones.
socket.on('announcement', (data) => showAnnouncement(data))
```

```typescript [server: replay.ts]
import { emits, server, t } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [
    emits({
      announcement: t<{ text: string }>(),
    }),
    dedup(),
    sequence({ persist: true }), // persist so numbering survives a restart
    replay.history({ retention: { maxMessages: 100 } }),
  ],
})
```

::

On the client there is nothing to call. `replay()` remembers the highest sequence number for each scope: one for the top level, and one for each channel. On reconnect, it asks the server for the missed messages by itself. Those messages go to your normal `socket.on(...)` listeners. `replay()` needs `dedup()`, so that a message that arrives both as a replay and as a normal delivery is handled only once. If `dedup()` is missing, the `client()` call fails to compile. When TypeScript cannot be sure (see [Primitives](/client/primitives/overview) for the cases), and in plain JavaScript, `client()` throws an error when it builds the socket.

On the server, `replay` has two strategies:

- `replay.history(...)` keeps every message, up to a retention limit (how many messages, how many bytes, or how old). The byte limit is on by default: 64 MiB for each audience. Use it for a chat log.
- `replay.snapshot(...)` keeps only the latest message for each key you choose. Use it for live values such as a price or a status.

A client gets back only the messages that were addressed to it. A broadcast goes back to anyone who can read its scope, and `ctx.user.broadcast` goes back to that user. A message sent to chosen connections, such as `ctx.send` or a tag broadcast, goes back only to a client that comes back from one of those connections. The server gives each connection a secret resume token, and `replay()` shows the earlier tokens when it reconnects.

Both strategies need `dedup()` and `sequence({ persist: true })`. The server fails to start without them.

In history mode, [replay](/server/replay/overview#binary-events) stores [binary messages](/server/binary/overview) with their bytes. A client that was away gets the missed ones back with their bytes, in order with the JSON messages, and they go to your normal `binary.on(...)` listeners. A binary message too big for one row of the server's storage (8 MB on Cloudflare) is sent live only.

**When you need it:** when it matters that a user misses no messages during a drop, as in order feeds, chat, or live state. Skip it for data that the client loads again from the start after each reconnect.

Full detail: [Client · replay](/client/primitives/replay), [Client · dedup](/client/primitives/dedup), [Server · replay overview](/server/replay/overview), and the [sequence](/server/capabilities/sequence) and [dedup](/server/capabilities/dedup) capabilities.

## Inbox: guaranteed catch-up for each member

Replay is **best-effort**: it tries, but it does not promise. The server keeps a log for each channel, and a reconnecting client asks for the part it missed. If the client never asks, or if it is so far behind that the log already deleted those messages (the retention limit), it does not catch up. That is fine for a feed or live state. It is not fine for a direct message or an order that must not be lost.

**Inbox** is the guaranteed option. It stores catch-up for each **person**, not for each **place**. Every member of the channel gets a stored copy of every message. The server holds that copy until the member's client confirms that the message arrived (an **acknowledgement**, or "ack"). On reconnect, the server sends all held copies by itself, even to members who were offline when the message was sent. A member is not skipped because they were away, and the client does not need to ask. Members need a stable user ID for this. Anonymous connections get live messages only.

|                        | Replay                                    | Inbox                                     |
| ---------------------- | ----------------------------------------- | ----------------------------------------- |
| Catch-up is stored for | the channel (a place)                     | each member (a person)                    |
| Delivery               | best-effort: the client must ask          | guaranteed: held until acknowledged       |
| Offline member         | catches up only if they reconnect and ask | gets held messages on reconnect by itself |

Use **replay** when a missed message is acceptable. Use **inbox** when every member must see every message. You can use both on the same channel.

### Fan-out on read vs fan-out on write

**Fan-out** means making one message reach many members. The two options differ in **when** they make the catch-up copies for each member. This one choice explains both their cost and their guarantee.

- **Replay is fan-out on read.** The server stores a broadcast **once**: one shared log row for the whole channel, no matter how many members it has. (A message sent to chosen connections, such as `ctx.send` or a tag broadcast, is stored once for each user it reached.) The fan-out happens later, when a member **reads**: the member reconnects and asks, and the server reads that one shared log and sends back the missed part. Ten members that all fell behind read the same rows, and the server wrote only one row. This is cheap to store. But nothing is kept for a member who never asks, and retention can delete a row before a slow member comes back for it.
- **Inbox is fan-out on write.** When a message is sent, the server **writes** a stored copy into **each member's own queue**. So a broadcast to ten members makes ten queued rows. This costs more storage, but each copy is already waiting. An offline member gets their queue on reconnect, and there is no risk that the shared copy was already deleted. That is what makes delivery guaranteed.

So the choice is storage against certainty. Replay makes one write and depends on the reader coming back in time. Inbox makes one write per member, so each reader always finds their copy. Both send the caught-up messages over the same connection on reconnect. The only difference is where the copies are stored.

An inbox channel can limit how many held rows it keeps for each member, or how many bytes. If a member falls too far behind that limit, the oldest rows are deleted. On reconnect, the client then receives a **gap** signal, which tells it that some messages are missing. Replay uses the same gap signal.

An inbox stores [binary messages](/server/inbox/overview#binary-events), such as Huddle's voice notes, with their bytes. A member who was away gets each one back, in order with the JSON messages. Because an inbox promises delivery, a message too big to store (8 MB on Cloudflare) goes to nobody, and the server logs an error. Replay sends such a message live only.
