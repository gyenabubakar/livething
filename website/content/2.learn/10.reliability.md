Real networks are messy. A laptop sleeps, a phone changes towers, a proxy times out an idle socket, you ship a deploy — and the connection drops. A WebSocket app that ignores all this works perfectly on your machine and falls apart for users. **Reliability** is a small set of primitives that keep a connection healthy and your data consistent through that mess.

The key idea is that they **compose**. Each one handles a different failure, and together they cover a full drop-and-recover:

- **Keepalive** notices a socket that has silently died and closes it.
- **Reconnection** brings it back, with backoff so a crowd of clients doesn't stampede the server.
- **Buffering** holds the sends you made during the gap and flushes them on return.
- **Replay** and **dedup** catch up on the messages you missed while away — without processing anything twice.

Most of this is client-side, because the client is where the unreliable network bites hardest. A few have a server half too (replay, keepalive, and the sequence/dedup capabilities). You add only the ones you need — leave one out and you don't pay for it.

## Problem to primitive

| Problem | Primitive |
|---|---|
| An idle socket gets silently killed by a proxy | **Keepalive** — pings and missed-pong detection |
| The socket drops and stays dead | **Reconnection** — retry with backoff |
| The user sends things while offline | **Buffering** — queue and flush on reconnect |
| Messages were missed during the gap | **Replay** — catch up after reconnect |
| The same message arrives twice | **Dedup** — drop the duplicate |

## The stacked client

A typical resilient client stacks the primitives in one `client<AppSocket>()(...)` call. They're plain functions, applied in order:

```typescript [app.ts]
import { client, connect, reconnection, keepalive, buffering } from '@wskit/client'
import type { AppSocket } from '../server/app'

const socket = client<AppSocket>()(
  connect('wss://example.com/ws'),
  reconnection(), // get back after a drop
  keepalive(),    // notice a dead socket fast
  buffering({ enabled: true }), // don't lose sends while offline
)
socket.connect()
```

The story they tell together: **keepalive** notices the socket has stopped answering and force-closes it, **reconnection** brings it back, **buffering** replays anything you tried to send in the meantime, and **replay** plus **dedup** (added when you need catch-up) fill in the messages the server sent while you were gone. The rest of this page walks each one — the idea, the minimal usage, and when you reach for it.

## Keepalive — notice a dead socket

A WebSocket can die without telling anyone. A proxy times out the connection, a phone loses signal, a laptop sleeps — and both sides keep thinking the socket is fine. This is a *half-open* connection: it looks alive, but nothing gets through. Keepalive catches it by sending regular pings and watching for the pongs that should come back; after too many missed pongs it declares the socket dead and force-closes it, which lets reconnection take over.

This is the one reliability feature with a meaningful half on **both** ends. The client pings from its side; the server pings from its side and closes connections that go quiet.

::code-group
```typescript [client: app.ts]
import { client, connect, keepalive } from '@wskit/client'

const socket = client<AppSocket>()(
  connect('wss://example.com/ws'),
  keepalive({ interval: 30_000, maxMissedPongs: 2 }),
)
```

```typescript [server: socket.ts]
import { define, t } from '@wskit/server'
import { keepalive } from '@wskit/server/keepalive'

const base = define({
  env: t<Env>(),
  capabilities: [
    keepalive({ pingIntervalMs: 30_000, idleTimeoutMs: 60_000 }),
  ],
})
```
::

On the client, after `maxMissedPongs` pongs fail to arrive the socket is force-closed with the `IDLE` code — and if reconnection is installed, a fresh connect kicks off. On the server, `idleTimeoutMs` is how long a connection may send *nothing* (an app message or a pong both reset it) before the server closes it; `pingIntervalMs` must be comfortably less than the timeout so a healthy client's pong always lands in time.

Every ping/pong round-trip is also a latency measurement, so `keepalive()` adds quality methods on the client — `socket.getQuality()`, `socket.getLatency()`, and `socket.onQualityChange(...)` — handy for a "your connection is poor" banner. To set your own latency cut-offs, pair it with the `quality()` primitive.

**When you need it:** any long-lived socket, especially durable streams — without keepalive a half-open connection can sit unnoticed for minutes.

Full detail: [Client · keepalive](/client/primitives/keepalive), [Client · quality](/client/primitives/quality), and [Server · keepalive](/server/capabilities/keepalive).

## Reconnection — bring the socket back

A raw WebSocket that drops stays dropped — `onclose` fires and that's it. The `reconnection()` primitive makes the client reconnect on its own after an unexpected drop. It's client-only; the server doesn't need to know.

```typescript [app.ts]
import { client, connect, reconnection } from '@wskit/client'
import { CloseCodes } from '@wskit/core'

const socket = client<AppSocket>()(
  connect('wss://example.com/ws'),
  reconnection({
    maxAttempts: Infinity,
    nonRetryableCodes: [CloseCodes.BANNED, CloseCodes.AUTH_INVALID],
  }),
)
```

That's the whole setup. On a drop the socket moves to the `reconnecting` state and retries with **exponential backoff** (the wait doubles — 1s, 2s, 4s — up to a cap) plus **jitter** (a random nudge so a thousand clients that dropped together don't all retry on the same tick). Not every close should be retried, though — reconnecting after a `BANNED` close just gets the user banned again — so you can name `nonRetryableCodes`, or pass a `shouldReconnect(code, reason)` callback for case-by-case control.

::tip
The named close codes — `CloseCodes.BANNED`, `CloseCodes.AUTH_INVALID`, and so on — come from `@wskit/core`, so you can write them by name instead of memorizing numbers.
::

Reconnection brings the *socket* back. It does not, on its own, re-subscribe channels or replay missed messages — those are separate concerns the other primitives handle. It's the foundation they build on: first get the socket back, then restore what was happening on it.

**When you need it:** essentially always, for any app that should survive a network blip.

Full detail: [Client · reconnection](/client/primitives/reconnection).

## Buffering — don't lose offline sends

When the socket is down, what happens to a `send(...)`? By default it's dropped — there's no open pipe to put it on. For user-initiated actions that's a real problem: the user types a message during a blip and it vanishes. The `buffering()` primitive **queues** sends made while offline and **flushes** them in order when the socket reconnects. It's client-only, and off by default, so you turn it on explicitly.

```typescript [app.ts]
import { client, connect, reconnection, buffering } from '@wskit/client'

const socket = client<AppSocket>()(
  connect('wss://example.com/ws'),
  reconnection(),
  buffering({
    enabled: true,    // queue sends made while disconnected
    maxSize: 50,      // hold at most 50; oldest dropped when full
    ttl: 30_000,      // drop a queued message after 30s as stale
  }),
)
```

Buffering pairs naturally with reconnection — reconnection gets the socket back, buffering replays what you tried to send in the meantime. It's careful about which kind of close happened: an **accidental drop** keeps the queue for the reconnect, but a deliberate `socket.disconnect()` throws it away, since you meant to leave. A stale-prone message can carry its own shorter TTL per call:

```typescript [app.ts]
// this typing indicator is pointless if it sits queued for more than 2s
socket.send('typing', { userId }, { ttl: 2000 })
```

::warning
Buffered messages are still fire-and-forget — buffering guarantees a send is *attempted* when the socket returns, not that the server processed it. If you need confirmation, use a [request](/learn/messaging), which has its own in-flight handling and rejects with `Dropped` if a buffered request is evicted before it can go out.
::

**When you need it:** user actions that mustn't be lost to a momentary drop — sending a chat message, posting a comment. Less suited to high-frequency, only-the-latest-matters events like cursor positions, where a short `ttl` (or leaving them unbuffered) is better.

Full detail: [Client · buffering](/client/primitives/buffering).

## Replay & dedup — catch up without doubles

Buffering handles messages *you* tried to send while offline. But what about the messages the *server* sent while you were away? Those are gone from your point of view — unless the server kept them. **Replay** is the catch-up: the server stamps each outgoing message with a rising sequence number, the client remembers the highest it saw, and on reconnect it asks for everything after that. **Dedup** is the safety net: a reconnect can be messy and deliver a message twice, so each message also carries a unique ID, and dedup drops any ID already seen.

This pair has a server half made of three capabilities — `sequence()` numbers each message, `dedup()` stamps a unique ID (and drops duplicate *incoming* frames), and `replay` decides *what* to re-send.

::code-group
```typescript [client: app.ts]
import { client, connect, reconnection, dedup, replay } from '@wskit/client'

const socket = client<AppSocket>()(
  connect('wss://example.com/ws'),
  reconnection(),
  dedup(),  // list dedup before replay — replay depends on it
  replay(),
)

// Catch-up is invisible: missed messages arrive through the same on() handlers.
socket.on('order-update', (data) => updateOrder(data))
```

```typescript [server: socket.ts]
import { define, emits, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { sequence } from '@wskit/server/sequence'
import { replay } from '@wskit/server/replay'

const base = define({
  env: t<Env>(),
  capabilities: [
    emits({ 'order-update': t<{ id: string; status: string }>() }),
    dedup(),
    sequence({ persist: true }), // persist so numbering survives a restart
    replay.history({ retention: { maxMessages: 100 } }),
  ],
})
```
::

On the client there's nothing to call — `replay()` tracks the highest sequence number per scope and, on reconnect, automatically asks the server for the gap; the caught-up messages flow through your normal `socket.on(...)` listeners. `replay()` requires `dedup()` (so a message replayed-then-redelivered isn't processed twice), and `client()` throws at build if it's missing — which is why you list `dedup()` first.

On the server, `replay` comes in three strategies: `replay.history(...)` keeps every message up to a retention limit (good for a chat log), `replay.snapshot(...)` keeps only the latest value per logical key (good for live values like a price or status), and `replay.custom()` hands the storage and resend to you so you can back catch-up with your own database. Built-in replay needs both `dedup()` and `sequence({ persist: true })`.

**When you need it:** when missing messages during a gap actually matters — order feeds, chat, live state. Skip it for streams that re-derive themselves on reconnect.
