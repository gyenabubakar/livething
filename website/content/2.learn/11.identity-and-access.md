A socket that anyone can open is a risk. A real app needs to know _who_ is connecting, decide whether to let them in, and control what they can do after they connect. This last Learn page covers all three. Most of the work happens on the server, because the server decides who gets in. The client sends the credentials and then sees the result.

Think of access control as three layers, from the outside in:

1. **Authentication.** This is the entrance. The `upgrade` gate runs during the handshake and decides if a connection is allowed at all. If you reject here, the connection never reaches your handlers.
2. **Tags.** These organize the connections that got in. You label a connection by user, role, or team. Then you can address every connection with the same label as one group.
3. **Rate limiting.** This protects the server from too much traffic. Even a signed-in user can send too many events, so you cap how fast events can arrive.

## Authentication: the upgrade gate

Every WebSocket connection starts as a normal HTTP request that asks to "upgrade" to a WebSocket. This handshake is your one chance to check credentials. LiveThing gives you this chance in the **`upgrade`** hook on `server`. It is the only place where authentication happens. The hook gets the raw `Request`. It can be `async`, so you can call a database or an auth service before you decide.

To **accept** the connection, return `{ userId, meta }`. To **reject** it, throw `RejectUpgrade(code, reason)`. The code decides how the client is refused:

- An HTTP status code (`400` to `599`) sends a normal HTTP error response. No WebSocket opens.
- A WebSocket close code (such as `4002`) opens the socket only to send the close code and reason, then closes it at once.

In the example below, the client puts the token in the connection URL, and the server reads it back from the request.

::code-group

```typescript [server: upgrade.ts]
import { server } from '@livething/server'
import { RejectUpgrade } from '@livething/server/errors'
import { verifySession } from './auth'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user) throw RejectUpgrade(4002, 'invalid session')

    return {
      userId: user.id, // who this connection is
      meta: { name: user.name, role: user.role }, // travels into ctx.meta
    }
  },
})
```

```typescript [client: socket.ts]
import { binary, client, connect } from '@livething/client'
import { getSessionToken } from './huddle-data'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  // runs on every connect and reconnect, so it always sends the current token
  connect(
    () =>
      `wss://example.com/huddle?${new URLSearchParams({ token: getSessionToken() })}`,
  ),
  binary(),
)
```

::

The two return values are what the rest of your app uses:

- **`userId`** is a stable key for the person behind the connection. It is usually the user's ID from your database. LiveThing uses it as the key for stored per-user data, so it knows the same user again after a reconnect. A connection without a `userId` is **anonymous**: it has no user identity, and `ctx.user` on it points to no user. See [Server · Users](/server/context-and-storage/users).
- **`meta`** is any per-connection data that you want to read everywhere. It appears as `ctx.meta` in every handler, lifecycle hook, and channel gate. You set it at the gate from checked credentials, so every handler after the gate can trust `ctx.meta`.

The `code` you throw is a WebSocket close code, and the client can use it after the rejection too. `4002` is `CloseCodes.AUTH_INVALID`, one of the named close codes in `@livething/core`. On the client, the [reconnection](/learn/reliability) primitive passes each close code to your `shouldReconnect` callback and checks it against its no-retry list. That list holds `AUTH_INVALID`, `DUPLICATE`, and `BANNED` by default, plus any `nonRetryableCodes` you add. This is how the client decides if a retry makes sense. For example, it does not retry after a `BANNED` close. A `CAPACITY` close (the server has too many connections) may succeed if you retry later.

::note
A browser's WebSocket API cannot set custom headers on the handshake. So there are two practical ways to send a credential:

- The **URL query string**, built by the URL function shown above. It runs again on every reconnect, so the client picks up a new token when the old one is replaced.
- **Cookies**. The browser sends them automatically for a same-origin socket, so the client needs no setup.

Use the query string for a cross-origin socket, because browser rules for third-party cookies can drop the cookie.
::

Full detail: [Server · Upgrade](/server/server/upgrade) and [Client · Auth & Query](/client/connecting/auth-and-query).

## Tags: address a group as one

Sometimes you need to reach a _set_ of connections. For example: "send this to every admin" or "notify everyone on team 42". **Tags** do this. You label connections, then address every connection with the same label as one group. A tag has two parts: a **group** (the kind of label, such as `role`) and a **key** (the value, such as `admin`). One connection can have many tags.

You declare your groups up front with the `tags()` capability. This also makes the API type-safe: you can only use groups that you declared. A group is one of two kinds:

- **Ephemeral**: kept in memory for the connection, and removed when it disconnects.
- **Persistent**: stored for the user, and added back when the user reconnects.

If you declare a group with a schema, LiveThing validates the key on every `add()`. The `t<string>()` marker only sets the type and does no check at runtime.

Inside a handler, `ctx.tags` works on the current connection. Pick a group, then `add` or `remove` a key. To reach a whole group, `.ref(key)` gives you a handle to every connection that has that exact tag. With the handle you can `broadcast` to those connections, `count` them, or list them with `connections()`.

Huddle's definition declares only a `team` tag group. In the example below, `tags()` also declares `role` and `starred`, and `report-message` also tells every admin about the report.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import { tags } from '@livething/server/tags'
import * as v from 'valibot'
import { saveMessageReport } from './huddle-data'

const base = server({
  capabilities: [
    emits({ notification: t<{ title: string; body: string }>() }),
    clientRequests(),
    tags((ephemeral, persistent) => [
      ephemeral('role', v.picklist(['admin', 'member', 'guest'])), // validated on add
      ephemeral('team', t<string>()),
      persistent('starred', t<string>()), // room ids this user has starred
    ]),
  ],
})

const handleReportMessage = base.request('report-message', {
  input: v.object({ messageId: v.string(), reason: v.string() }),
  async run(ctx, input) {
    await saveMessageReport(
      input.messageId,
      input.reason,
      ctx.user.id,
    )

    // send an event to every connection tagged role:admin
    ctx.tags
      .ephemeral('role')
      .ref('admin')
      .broadcast('notification', {
        title: 'Message reported',
        body: input.reason,
      })

    const admins = ctx.tags.ephemeral('role').ref('admin').count()
    console.log(`${admins} admins online`)
  },
})
```

::note
Every routed handler returns a value. In a complete app, pass each value you want to run to `base.assemble({ handlers: [...] })`. A handler you leave out does not run and does not appear in the client contract.
::

`team` works the same way for a whole team: `ctx.tags.ephemeral('team').ref('acme-inc').broadcast(...)` reaches every connection on that team, on every device. You can also add an ephemeral tag at the moment a connection opens. Return a `tags` field from the upgrade gate next to `userId` and `meta`, for example `tags: { ephemeral: { role: user.role } }`. Persistent tags cannot be set there. Add them in a handler with `ctx.tags.persistent(group).add(key)`, for example when a member stars a room: `ctx.tags.persistent('starred').add(roomId)`. A persistent tag is stored for the user, so every open connection of that user gets it at once, and it comes back after a reconnect, on any device.

::note
Tags add nothing to the client contract. The client has no `tags()` primitive and nothing to configure. The client receives whatever the server sends to its group through a normal `socket.on('notification', …)` listener. For this to be typed, the event must be declared with `emits()`, as in the example above. All the grouping logic stays on the server.
::

Full detail: [Server · tags](/server/capabilities/tags).

## Rate limiting: cap the traffic

A signed-in user can still send too many events. It can happen by mistake (a loop in the client code that never stops) or on purpose. **Rate limiting** caps how fast events can arrive, so one connection cannot overload your server or send too many messages to a room. It runs on the server and uses a **token bucket**. A token bucket holds a fixed number of tokens and refills at a steady speed. Each incoming frame uses one token, and when the bucket is empty, the frame is rejected. The check runs _before_ validation and before your handler, so a rejected frame never reaches your code.

The limit has three levels, from the widest to the most specific. The most specific level wins:

::steps

### Global

The rule on the `rateLimit()` capability. It applies to every event by default.

### Channel

A channel can set its own `rateLimit`. This replaces the global rule for that channel's events. A channel can also turn the limit off with `rateLimit: false`.

### Handler

One handler can set its own `rateLimit`. This is the most specific level.
::

So you set a reasonable global default, raise it where traffic is normally high, and lower it on the few handlers that cost a lot to run. You must list the `rateLimit()` capability to use any rate limit, even a single per-handler limit. Without it, the `rateLimit` field on a handler is a type error.

A limit at one level only needs the fields it changes. Any field you leave out, such as `windowMs`, comes from the level above.

In this example, `delete-message` is a smaller version of Huddle's: it has no `confirm-delete` step.

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import { rateLimit } from '@livething/server/rate-limit'
import * as v from 'valibot'
import { deleteMessage } from './huddle-data'

const base = server({
  capabilities: [
    clientRequests(),
    rateLimit({ windowMs: 60_000, maxMessages: 60 }), // global: 60 events per minute, per connection
  ],
})

// deleting a message costs a real write, so it is limited to one call per minute
const handleDeleteMessage = base.request('delete-message', {
  input: v.object({ messageId: v.string() }),
  rateLimit: { maxMessages: 1 },
  async run(ctx, input) {
    await deleteMessage(input.messageId)
    return { deleted: true }
  },
})
```

By default, each connection gets its own budget. The `per` option changes what the budget is keyed on. Return `ctx.user.id`, or any field from `ctx.meta`, to share one budget across every socket that a user has open. Then a user who opens five tabs does not get five times the budget. An anonymous connection has an empty `ctx.user.id`. When `per` returns an empty string, LiveThing uses the connection's own budget, so anonymous connections never share one budget. Here is Huddle's `react` handler with a limit of 10 reactions per user:

```typescript [server/rooms.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { rateLimit } from '@livething/server/rate-limit'
import * as v from 'valibot'

const base = server({
  capabilities: [
    channels(),
    rateLimit({ windowMs: 60_000, maxMessages: 60 }),
  ],
})

const rooms = base.channel(['rooms', 'room:{roomId}'] as const, {
  capabilities: [
    emits({
      reaction: t<{
        messageId: string
        emoji: string
        from: string
      }>(),
    }),
  ],
})

const handleReact = rooms.on('react', {
  input: v.object({ messageId: v.string(), emoji: v.string() }),
  rateLimit: {
    maxMessages: 10,
    per: (ctx) => ctx.user.id,
  },
  run(ctx, input) {
    ctx.channel.broadcast('reaction', {
      messageId: input.messageId,
      emoji: input.emoji,
      from: ctx.user.id,
    })
  },
})
```

When a connection goes over the limit, the server rejects the frame and tells the client. The client gets the built-in `RateLimited` error. It carries `retryAfterMs`: the number of milliseconds to wait before the next try. You catch it like any other typed error. A rejected request rejects its promise. A rejected fire-and-forget event goes to `onServerError`.

```typescript [client: rate-limit.ts]
import { RateLimited } from '@livething/core'
import { socket } from './socket'

socket.onServerError((err) => {
  if (RateLimited.matches(err)) backOffFor(err.detail.retryAfterMs)
})
```

::tip
Wait `retryAfterMs` before you try again. Then the user sees a short, automatic pause instead of an error.
::
