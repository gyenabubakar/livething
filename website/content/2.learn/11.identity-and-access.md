A socket open to the world is a liability. Real apps need to know _who_ is connecting, decide whether to let them in, and control what they can do once they're through. This last Learn page covers all three — and it's mostly a server story, because the server is the gatekeeper. The client supplies credentials and sees the consequences.

Picture access control as three layers, working from the front door inward:

1. **Authentication** — the front door. The `upgrade` gate runs during the handshake and decides whether a connection is allowed at all. Reject here and no WSKit connection is created.
2. **Tags** — organizing who's inside. Label a connection by user, role, or team, then address every connection sharing a label as one group.
3. **Rate limiting** — protecting the inside. Even an authenticated user can flood you, so you cap how fast events come in.

## Authentication — the upgrade gate

Before a WebSocket becomes a live socket, it starts as an ordinary HTTP request asking to "upgrade." That handshake is your one chance to check credentials. WSKit hands you that chance in the **`upgrade`** hook on `define` — the single place authentication happens. It gets the raw `Request`, can be `async` (so you can hit a database or auth service), and you either accept or reject.

To **accept**, return `{ userId, meta }`. To **reject**, throw `RejectUpgrade(code, reason)`. An HTTP status sends an HTTP rejection; a valid WebSocket close code opens only long enough to deliver the close code and reason. The client supplies the token through the connection URL; the server reads it back off the request.

::code-group

```typescript [server: chat.ts]
import { define, t } from '@wskit/server'
import { RejectUpgrade } from '@wskit/server/errors'

const base = define({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await validateToken(token)
    if (!user) throw RejectUpgrade(4002, 'Invalid token')

    return {
      userId: user.id, // who this connection is
      meta: { userId: user.id, role: user.role }, // travels into ctx.meta
    }
  },
})
```

```typescript [client: app.ts]
import { client, connect, query } from '@wskit/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(
  connect('wss://example.com/ws'),
  query(() => ({ token: getAuthToken() })), // becomes ?token=… on the URL
)
```

::

The two return values are the payoff. **`userId`** is a stable key for _who_ is behind the connection — usually a user ID. WSKit uses it as the durable key, so it recognizes the same user across reconnects. A connection without a `userId` is **anonymous** — it has no user identity, and `ctx.user` on it addresses nobody. See [Server · Users](/server/context-and-storage/users). **`meta`** is any per-connection data you want everywhere: it surfaces as `ctx.meta` in every handler, lifecycle hook, and channel gate. From here on, every handler can trust `ctx.meta`, because it was set at the gate from validated credentials.

The `code` you throw is a WebSocket close code, and it matters beyond the rejection — on the client, [reconnection](/learn/reliability) reads it to decide whether retrying makes sense. A `BANNED` close shouldn't be retried; a transient `CAPACITY` close might be.

::note
A browser's WebSocket API can't set custom headers on the handshake, so the practical ways to pass a credential are the **URL query string** (the `query()` primitive above, which re-runs on every reconnect so a rotated token is picked up) and **cookies** (sent automatically for a same-origin socket — no client setup). Pick the query string for a cross-origin socket, where third-party cookie rules can drop the cookie.
::

Full detail: [Server · Upgrade](/server/define/upgrade) and [Client · Auth & Query](/client/connecting/auth-and-query).

## Tags — address a group as one

Sometimes you need to reach a _set_ of connections — "send this to every admin," "kick all of this user's open tabs," "notify everyone on team 42." **Tags** make that possible: you label connections, then address every connection sharing a label as a single group. A tag is a **group** (the kind of label, like `role`) and a **key** (the value, like `admin`); a connection can carry many.

You declare your groups up front with the `tags()` capability. That's also what makes the API type-safe — you can only reference groups you declared. A group can be **ephemeral** (lives in memory for the connection, gone on disconnect) or **persistent** (stored durably, survives reconnects). A group declared with a schema validates its key on every `add()`.

```typescript [chat.ts]
import { define, t } from '@wskit/server'
import { tags } from '@wskit/server/tags'
import * as v from 'valibot'

const base = define({
  capabilities: [
    tags((ephemeral, persistent) => [
      ephemeral('user', t<string>()),
      ephemeral('role', v.picklist(['admin', 'member', 'guest'])), // validated on add
      persistent('favorite', t<string>()),
    ]),
  ],
})
```

Inside a handler, `ctx.tags` is scoped to the current connection — pick a group, then `add` or `remove` a key. To reach a whole group, `.ref(key)` gives you a handle to every connection with that exact tag, which you can `broadcast` to, `count`, or list.

```typescript [chat.ts]
const handleNotifyAdmins = base.on('notify-admins', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    // send an event to every connection tagged role:admin
    ctx.tags
      .ephemeral('role')
      .ref('admin')
      .broadcast('admin-notice', { text: input.text })

    const admins = ctx.tags.ephemeral('role').ref('admin').count()
    console.log(`${admins} admins online`)
  },
})
```

::note
Every routed handler returns a value. In a complete app, pass each value you want to run to `base.assemble({ handlers: [...] })`; an omitted handler does not run or appear in the client contract.
::

A common real use is multi-tab: one user often has several sockets open. Tag each by `user`, and `ctx.tags.ephemeral('user').ref(userId)` addresses _all_ of that user's tabs at once — perfect for "log out everywhere." You can also seed an ephemeral tag the moment a connection opens, by returning a `tags` field from the upgrade gate alongside `userId` and `meta`.

::note
Tags add nothing to the client contract — there's no `tags()` primitive on the client and nothing to configure. The client just receives whatever the server sends to its group, through a normal `socket.on('admin-notice', …)` listener. The grouping logic stays on the server, where it belongs.
::

Full detail: [Server · tags](/server/capabilities/tags).

## Rate limiting — cap the flood

An authenticated user can still flood you — by accident with a runaway loop, or on purpose. **Rate limiting** caps how fast events arrive, so one connection can't drown your server or spam a room. It's server-side, it uses a token bucket (each frame spends one token; an empty bucket rejects the frame), and it runs _before_ validation and your handler — a throttled frame never reaches your code.

The limit cascades in three layers, broadest to most specific, with the most specific winning:

::steps

### Global

The rule on the `rateLimit()` capability. Applies to everything by default.

### Channel

A channel can set its own `rateLimit`, overriding the global rule for its events — or opting out with `{ enabled: false }`.

### Handler

An individual handler can set its own `rateLimit` — the tightest level of all.
::

So you set a sane global default, loosen it where traffic is naturally high, and tighten it on the handful of handlers that are expensive to run. Listing the capability is required to use any rate limit at all, even a single per-handler override.

```typescript [chat.ts]
import { define, t } from '@wskit/server'
import { rateLimit } from '@wskit/server/rate-limit'
import * as v from 'valibot'

const base = define({
  capabilities: [
    rateLimit({ windowMs: 60_000, max: 60 }), // baseline: 60 events/min, per connection
  ],
})

// an expensive handler tightens to one call per window
const handleReport = base.on('run-report', {
  input: v.object({}),
  rateLimit: { enabled: true, max: 1 },
  run(ctx) {
    /* ... */
  },
})
```

By default each connection gets its own budget. You change what the budget is keyed on with `per` — return `ctx.user.id` (or any field off `ctx.meta`) to share one budget across every socket a user has open, so opening five tabs doesn't give someone five times the allowance.

```typescript [chat.ts]
const handleShared = base.on('shared-action', {
  input: v.object({}),
  rateLimit: {
    enabled: true,
    max: 10,
    per: (ctx) => ctx.meta.userId,
  },
  run(ctx) {
    /* ... */
  },
})
```

When a connection trips the limit, the frame is rejected and the client is told — it surfaces as the built-in `RateLimited` error carrying a `retryAfterMs` (milliseconds to wait). You catch it the same way as any typed error: a rejected request rejects its promise, a rejected fire-and-forget event reaches `onServerError`.

```typescript [app.ts]
import { RateLimited } from '@wskit/core'

socket.onServerError((err) => {
  if (RateLimited.matches(err)) backOffFor(err.detail.retryAfterMs)
})
```

::tip
Reading `retryAfterMs` and waiting that long before retrying is the cooperative thing to do — it turns a hard rejection into a brief, automatic pause rather than a failure the user notices.
::

Full detail: [Server · rateLimit](/server/capabilities/rate-limit).
