Before a WebSocket connection becomes a live socket, it starts as an ordinary HTTP request asking to "upgrade." That handshake is your one chance to check credentials and decide whether to let the connection through. WSKit gives you that chance in the **`upgrade`** hook — the single place authentication happens. Reject there, and no socket ever opens.

You saw a glimpse of this in [Your First App](/start/your-first-app). Here's the full picture, both sides.

## The upgrade gate

The `upgrade` hook receives the raw HTTP `Request` for the handshake. You inspect it — read a header, a query parameter, a cookie — and either accept or reject:

```typescript [chat.ts]
import { define, t } from '@wskit/server'
import { RejectUpgrade } from '@wskit/server/errors'

const base = define({
  env: t<Env>(),
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await validateToken(token)
    if (!user) throw RejectUpgrade(4001, 'Invalid token')

    return {
      identity: user.id,                    // who this connection is
      meta: { userId: user.id, role: user.role }, // travels into ctx.meta
    }
  },
})
```

The hook can be `async`, so you can hit a database or an auth service. The `request` is a standard `Request`, so you read from it the usual ways — `request.headers.get(...)`, `new URL(request.url).searchParams`, and so on.

### Accepting: identity and meta

To accept, return an object with two parts:

- **`identity`** — a stable key for *who* is behind this connection, usually a user id. WSKit uses it as the durable key for the connection, so it's how the system recognizes the same user across reconnects.
- **`meta`** — any per-connection data you want available everywhere. It surfaces as `ctx.meta` in every handler, lifecycle hook, and channel gate. Put the user's id, role, display name — whatever your handlers need.

From here on, every handler can read `ctx.meta` and trust it, because it was set at the gate from validated credentials.

### Rejecting: RejectUpgrade and close codes

To reject, throw `RejectUpgrade(code, reason)`. The connection is refused before the socket opens, and the client sees the close code:

```typescript [chat.ts]
if (!token) throw RejectUpgrade(4001, 'Missing token')
if (banned(user)) throw RejectUpgrade(4009, 'Banned')
```

The `code` is a WebSocket close code, and `@wskit/core` exports named ones so you don't memorize numbers:

| Close code | Meaning |
|---|---|
| `CloseCodes.AUTH_EXPIRED` (4001) | Credentials expired |
| `CloseCodes.AUTH_INVALID` (4002) | Credentials invalid |
| `CloseCodes.BANNED` (4009) | This user is banned |
| `CloseCodes.RATE_LIMITED` (4005) | Too many requests |
| `CloseCodes.CAPACITY` (4010) | Server is full |

The close code matters beyond the rejection: on the client, [reconnection](/learn/reliability/reconnection) reads it to decide whether retrying makes sense. A `BANNED` close shouldn't be retried; a transient `CAPACITY` close might be.

## Passing credentials from the client

The client has to *get* the credential to the server during the handshake. A browser's WebSocket API doesn't let you set arbitrary headers on the handshake, so the two practical channels are the URL query string and cookies.

### Query parameters

The `query()` primitive adds parameters to the connection URL. It takes a function that runs on every connect *and reconnect*, so the value stays fresh:

```typescript [app.ts]
import { client, connect, query } from '@wskit/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(
  connect('wss://example.com/ws'),
  query(() => ({ token: getAuthToken() })),
)
```

On the server, you read it back from the request URL — `new URL(request.url).searchParams.get('token')`, exactly as in the gate above. Because the function re-runs on reconnect, a rotated token is picked up automatically when the socket comes back.

### Cookies

If your client runs in a browser on the same site as your server, the browser sends its cookies with the WebSocket handshake automatically. You read them from the request headers in `upgrade` — no client-side setup needed. This is the natural fit when you already have a session cookie from a normal login.

## How identity and meta flow downstream

Once the gate accepts, the values it returned are everywhere:

- `ctx.identity` is the stable key you set — used by durable features to recognize the user.
- `ctx.meta` is your per-connection data, readable in every handler, lifecycle hook, and channel `check`/`commit`.

That's the payoff of doing auth at the gate: every piece of code after it can trust `ctx.meta` without re-checking, because nothing got past the front door without being validated.

::tip
You can also attach initial [tags](/learn/identity-and-access/tags) from the upgrade gate by returning a `tags` field alongside `identity` and `meta` — handy for labelling a connection by user the moment it connects.
::
