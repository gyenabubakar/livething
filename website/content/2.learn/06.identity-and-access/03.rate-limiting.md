An authenticated user is still capable of flooding you — by accident with a runaway loop, or on purpose. **Rate limiting** caps how fast events can arrive, so one connection can't drown your server or spam a room. WSKit's rate limiter is server-side, and it cascades: you set a broad rule and tighten it where you need to.

## How the limit works

The limiter counts events in a sliding time window. You give it two numbers — a window length and a maximum count — and once a connection exceeds the max within the window, further events are rejected until the window rolls forward. By default, each connection has its own budget.

## A global limit

The simplest setup is one rule for everything, set on the `rateLimit()` capability:

```typescript [chat.ts]
import { define } from '@wskit/server'
import { rateLimit } from '@wskit/server/rate-limit'

const base = define({
  env: t<Env>(),
  capabilities: [
    rateLimit({ windowMs: 60_000, max: 60 }), // 60 events per minute, per connection
  ],
})
```

Now every incoming event counts against a per-connection budget of 60 per minute. That's the baseline; you can override it at finer levels.

## The cascade: global, channel, handler

The limit applies in layers, from broad to specific, with the most specific rule winning:

::note
The handler and channel snippets below are trimmed for focus. As always, a handler or channel only takes effect once you pass it to `base.assemble(...)` — see [The Contract](/learn/core-model/the-contract).
::

1. **Global** — the rule on `rateLimit()`. Applies to everything by default.
2. **Channel** — a channel can set its own `rateLimit`, overriding the global rule for events in that channel (or opting out entirely).
3. **Handler** — an individual handler can set its own `rateLimit`, the tightest level of all.

```typescript [chat.ts]
// an expensive handler gets a stricter cap than the global rule
const handleExpensive = base.on('run-report', {
  input: v.object({}),
  rateLimit: { enabled: true, max: 1 },
  run(ctx) { /* ... */ },
})

// a channel that opts out of limiting entirely
const firehose = base.channel('firehose', {
  outgoing: { emits: { tick: t<{ n: number }>() } },
  rateLimit: { enabled: false },
})

// a channel with no rateLimit simply inherits the global rule
const lobby = base.channel('lobby', {
  outgoing: { emits: { msg: t<{ text: string }>() } },
})
```

So you set a sane global default, loosen it where traffic is naturally high, and tighten it on the handful of handlers that are expensive to run.

## Sharing a budget

By default the budget is per *connection*, keyed automatically. But you can change what the budget is keyed on with `per` — for instance, to share one budget across every connection from the same user (so opening five tabs doesn't give someone five times the allowance):

```typescript [chat.ts]
const handleShared = base.on('shared-action', {
  input: v.object({}),
  // every connection with the same username draws from one bucket
  rateLimit: { enabled: true, max: 10, per: (ctx) => ctx.meta.username },
  run(ctx) { /* ... */ },
})
```

`per` returns the key the budget is grouped by. Return the user ID and all their tabs share a limit; return something coarser and a whole group shares one.

## What the client sees

When a connection trips the limit, the event is rejected and the client is told. It surfaces as a typed `rate-limited` error carrying a `retryAfter` — how long to wait before trying again. You catch and narrow it the same way as any typed error ([Errors](/learn/messaging/errors)):

```typescript [app.ts]
import { RateLimited } from '@wskit/core'

socket.onError((err) => {
  if (RateLimited.matches(err)) {
    backOffFor(err.detail.retryAfter)
  }
})

// for a rejected request, it rejects the Promise:
try {
  await socket.request('run-report', {})
} catch (err) {
  if (RateLimited.matches(err)) showSlowDownNotice()
}
```

For a rate-limited request, the request's Promise rejects with `RateLimited`; for a rate-limited fire-and-forget event, it surfaces on `onError`. Either way, `retryAfter` tells a well-behaved client exactly how long to hold off.

::tip
Reading `retryAfter` and waiting that long before retrying is the cooperative thing to do — it turns a hard rejection into a brief, automatic pause rather than a failure the user notices.
::

## The mental model

- Set a **global** rule for a sensible baseline.
- **Override per channel** to loosen or disable limiting where traffic is high.
- **Override per handler** for the expensive operations.
- Use **`per`** to decide what a budget is shared across — per connection, per user, or coarser.
- The client catches **`RateLimited`** and backs off for `retryAfter`.
