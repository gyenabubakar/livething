Subscribing is how a connection joins a channel. It's never automatic — a client asks to join, and the server decides whether to let it in. That decision is the channel's *auth gate*, and getting it right is most of what this page is about. We'll declare a channel on the server, gate the join, and subscribe from the client.

## Declaring a channel

You declare a channel with `base.channel(...)`, which needs the `channels()` capability turned on. The simplest channel is a name plus the events it can broadcast:

```typescript [chat.ts]
import { define, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [channels()],
})

const room = base.channel('room', {
  outgoing: {
    emits: { message: t<{ from: string; text: string }>() },
  },
})
```

`outgoing.emits` lists the events the channel can send to its members — the channel's own little `emits`. These become the channel's `incoming` events on the client.

### Dynamic channels

When you need many rooms following one shape, declare a *family* by passing `[familyKey, pattern]` instead of a plain name. The pattern uses `{...}` placeholders:

```typescript [chat.ts]
const room = base.channel(['room', 'room:{id}'], {
  outgoing: {
    emits: { message: t<{ from: string; text: string }>() },
  },
})
```

Now `room:alpha`, `room:42`, and any other `room:{id}` are all valid rooms covered by this one declaration. Inside a handler, `ctx.channel.name` is the matched name (`room:alpha`) and `ctx.channel.family` is the family key (`room`).

## The auth gate: check and commit

Joining runs through up to two gates. Both receive the connection context, and **throwing from either one rejects the subscription**.

### subscribe — the join payload

If a channel needs information to decide who can join — a token, an invite code — declare a `subscribe` schema. The client must pass a matching payload, and it's validated before the gate runs:

```typescript [chat.ts]
const room = base.channel('room', {
  outgoing: { emits: { message: t<{ from: string; text: string }>() } },
  subscribe: v.object({ token: v.string() }),
  // ...
})
```

### check — the async gate

`check(ctx, input)` runs first. It receives the validated subscribe payload and can be `async`, so it's the place for lookups — verify the token, check a database, hit an auth service. Whatever `check` **returns** is handed to `commit`:

```typescript [chat.ts]
async check(ctx, input) {
  // input is typed from the subscribe schema: { token: string }
  const role = await lookupRole(input.token)
  if (!role) throw new Error('unknown token')
  return { role } // passed to commit
}
```

### commit — the synchronous gate

`commit(ctx, checkResult)` runs second, and must be **synchronous**. It receives whatever `check` returned, with the type inferred — no annotation needed. Use it for last-moment checks against live state, like room capacity:

```typescript [chat.ts]
commit(ctx, { role }) {
  if (role === 'banned') throw new Error('banned')
  if (ctx.channel.members().length >= 50) throw new Error('room is full')
}
```

`commit` is optional — many channels only need `check`. The split exists because `check` does the slow async work, and `commit` makes the final go/no-go decision right before the member is added, when the live state (like the current member count) is accurate.

::tip
A plain `throw new Error(...)` still rejects the subscription, but the client only sees a generic `internal-error` — WSKit never leaks raw error details, so the client learns *that* it was refused, not *why*. To send a reason the client can catch and narrow, throw a registered typed error instead — see [Errors](/learn/messaging/errors).
::

## Channel handlers and broadcasting

Inside a channel handler — registered with `room.on(...)` — `ctx.channel` is scoped to that room. `ctx.channel.broadcast(...)` reaches only the channel's members:

```typescript [chat.ts]
const handleSend = room.on('send', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', { from: ctx.meta.username, text: input.text })
  },
})

export const handler = base.assemble(handleSend)
```

::note
`base.assemble(handleSend)` already pulls in the `room` channel, because the handler carries its channel with it. You only pass the channel object itself to `assemble` when the channel has **no** message handlers — for example a channel that's purely lifecycle hooks.
::

## Subscribing from the client

On the client, add the `channels()` primitive. Grab a handle with `socket.channel(name)`, register listeners, then `subscribe(...)` with the typed payload:

```typescript [app.ts]
import { client, connect, channels } from '@wskit/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(
  connect('wss://example.com/ws'),
  channels(),
)
socket.connect()

const room = socket.channel('room')

// Listeners can be registered before the subscribe is confirmed.
room.on('message', (data) => {
  console.log(`${data.from}: ${data.text}`)
})

// The payload is required because the channel declared a subscribe schema.
await room.subscribe({ token: 'tok-member' })

// Now you can send — typed against the channel's `send` handler.
room.send('send', { text: 'hello room' })
```

For a dynamic channel, you pass the family key and the room name: `socket.channel('room', 'room:alpha')`.

### Subscriptions are lazy and resilient

A few things worth knowing:

- `subscribe()` resolves once the server confirms the join. If the gate rejects, it rejects.
- You can register `on(...)` listeners *before* subscribing — they'll be ready when messages start.
- The subscribe payload can be a **function** instead of a plain value. WSKit re-runs it on reconnect, so a rotating token stays fresh: `room.subscribe(() => getFreshToken())`.

## What flows between them

| Server | Client |
|---|---|
| `base.channel('room', { subscribe, check })` | `socket.channel('room')` |
| the `subscribe` schema | the payload `room.subscribe(...)` requires |
| `outgoing.emits` events | `room.on(event, ...)` |
| `room.on('send', ...)` | `room.send('send', ...)` |

For the complete gate behavior, dynamic channel params, and server-side subscription control, see the [Server channels reference](/server/capabilities/channels) and the [Client channels reference](/client/primitives/channels).
