A **channel** is a server-managed room: a named group of connections that share messages. When you broadcast to a channel, only its members hear it. Channels are how you build chat rooms, document sessions, game lobbies, live dashboards — anything where a subset of users belongs together.

You met one channel already in [Your First App](/start/your-first-app). This chapter goes deeper: how subscription and auth really work, how to know who's in a room, and how requests and streams can be scoped to a single channel.

## Why channels, not just broadcasts

You *could* fake rooms with plain events — tag every message with a room id and filter on the client. But then the server is sending every message to everyone, the filtering is on the wrong side of the wire, and there's no auth on who can listen. Channels fix all of that: membership lives on the server, broadcasts only reach members, and joining runs through an auth gate you control.

## Static vs dynamic

There are two flavors:

- **Static channels** have a fixed name you know at write time — `lobby`, `announcements`, `support`. You declare each one by name.
- **Dynamic channels** (also called *families*) follow a pattern, so one declaration covers many rooms — `room:{id}` matches `room:alpha`, `room:42`, and any other id. You declare the pattern once; rooms come and go as users subscribe.

Use static when the set of rooms is known and small. Use dynamic when rooms are created on the fly — one per document, per game, per conversation.

## A contract inside the contract

Each channel carries its own mini-contract. In the client contract, the `channels` key maps each room to its own `incoming` and `outgoing` (and, if you add them, `requests`, `serverRequests`, and `streams`) — mirrored exactly like the top level, but scoped to that room:

```typescript [chat-socket.ts]
interface ChatSocket {
  channels: {
    rooms: {
      incoming: { message: { text: string; from: string } } // the server broadcasts to the room
      outgoing: { say: { text: string } }                   // you send into the room
    }
  }
}
```

That nesting is why `room.on('message', …)` and `room.send('say', …)` are typed from the room's own events — the same name can mean one thing at the top level and another inside a channel.

## The lifecycle in brief

Every channel follows the same arc:

1. **Declare** the channel on the server, with an optional `subscribe` schema and auth gate.
2. The client **subscribes**, passing a typed payload. The server's `check` (and optional `commit`) decide whether to let them in.
3. While subscribed, members **send and receive** the channel's events — scoped to the room.
4. **Presence** tracks who's in the room and who's currently online.
5. The client **unsubscribes**, or disconnects, and leaves.
