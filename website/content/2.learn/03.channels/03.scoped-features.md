A channel isn't only for broadcasting events. The other messaging features — requests, streams, and replay — can live *inside* a channel too. When they do, they're **scoped**: they belong to that room, addressed through the channel handle, and typed under the channel's own contract. This page shows how a feature you already know gets a channel-scoped version.

The pattern is consistent: whatever you'd declare on `base`, you declare on the channel instead; whatever you'd call on `socket`, you call on the channel handle instead.

::note
The server snippets below are trimmed to the scoped feature. As with any handler, the channel handlers here (`handleInfo`, `handleHistory`) only enter the contract once passed to `base.assemble(...)` — and passing a channel handler pulls its channel in too. See [The Contract](/learn/core-model/the-contract).
::

## Channel-scoped requests

A request scoped to a channel is declared with `channel.request(...)` and called on the client's channel handle. It works exactly like a top-level [request](/learn/messaging/requests), but it only makes sense in the context of that room — "get this channel's info", "claim a seat in this game":

::code-group
```typescript [Server]
import { requests } from '@wskit/server/requests'

const base = define({
  env: t<Env>(),
  capabilities: [channels(), requests()],
})

const room = base.channel('room', {
  outgoing: { emits: { message: t<{ text: string }>() } },
})

export const handleInfo = room.request('get-channel-info', {
  input: v.object({}),
  run(ctx) {
    // ctx.channel is scoped to this room
    return { name: ctx.channel.name, size: ctx.channel.members().length }
  },
})
```

```typescript [Client]
const room = socket.channel('room')
await room.subscribe()

const info = await room.request('get-channel-info', {})
// info: { name: string; size: number }
```
::

The request lives under the channel's contract, so `room.request(...)` only offers the requests that channel declared — and the top-level `socket.request(...)` doesn't see them.

## Channel-scoped streams

Streams scope to a channel the same way. Declare with `channel.stream(...)`; consume with `room.stream(...)`:

::code-group
```typescript [Server]
import { stream } from '@wskit/server/streams'

const base = define({
  env: t<Env>(),
  capabilities: [channels(), stream()],
})

const room = base.channel('room', {
  outgoing: { emits: { message: t<{ text: string }>() } },
})

export const handleHistory = room.stream('replay-history', {
  input: v.object({ limit: v.number() }),
  chunk: t<{ text: string; at: number }>(),
  async *run(ctx, input) {
    for (const msg of await loadHistory(ctx.channel.name, input.limit)) {
      yield msg
    }
  },
})
```

```typescript [Client]
const room = socket.channel('room')
await room.subscribe()

const history = await room.stream('replay-history', { limit: 50 })
for await (const msg of history) {
  render(msg)
}
```
::

The full streaming story — plain, durable, broadcast, nudges — all applies to channel-scoped streams. See the [Streaming](/learn/streaming/overview) chapter for the details; the only difference is where you declare and call them.

## Channel-scoped replay

[Replay](/learn/reliability/replay-and-dedup) — catching up on messages you missed while disconnected — can also be scoped per channel. Each channel tracks its own sequence of messages, so when a member reconnects, they catch up on that room's history independently of any other room. You turn replay on at the channel level, and the client's catch-up happens automatically per channel. The reliability chapter covers the mechanics; the takeaway here is that replay, like requests and streams, respects channel boundaries.

## The `ctx.channel` surface

On the server, everything channel-scoped is reached through `ctx.channel` inside a channel handler:

- `ctx.channel.name` — the channel's name (the matched name for a dynamic channel).
- `ctx.channel.family` — the family key, for dynamic channels.
- `ctx.channel.broadcast(event, payload, options?)` — broadcast to the channel's members.
- `ctx.channel.send(event, payload)` — send to the current connection, in the channel's scope.
- `ctx.channel.members()` — the channel's roster.

Because `ctx.channel` is scoped, the same handler logic naturally applies to whichever room it's handling — a dynamic `room:{id}` handler broadcasts to exactly the room the message came in on, with no extra bookkeeping.

## The mental model

A channel is a contract within the contract, and scoped features are why. Anything top-level — events, requests, streams, replay — has a channel-scoped twin, declared on the channel and addressed through the channel handle. Learn a feature once and you know its scoped version too; only the *where* changes.

You can see it directly in the client contract: the room's entry carries its own `requests` and `streams`, the same keys you'd find at the top level, just nested one room deep:

```typescript [chat-socket.ts]
interface ChatSocket {
  channels: {
    room: {
      incoming: { message: { text: string } }
      requests: {
        'get-channel-info': { payload: {}; response: { name: string; size: number } }
      }
      streams: {
        'replay-history': { payload: { limit: number }; chunk: { text: string; at: number } }
      }
    }
  }
}
```

So `room.request('get-channel-info', …)` reads from *this room's* `requests`, and the top-level `socket.request(...)` never sees it.
