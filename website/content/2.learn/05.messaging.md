Messaging is the heart of WSKit: the ways the server and client actually talk. Everything else — channels, streams, reliability — builds on these. It all comes down to one question: **do you expect an answer back?**

- **Events** never expect a reply. Send and move on — notifications, broadcasts, updates. The bulk of your traffic.
- **Requests** always expect a reply. You `await` a typed answer, in either direction.
- **Errors** are how a "no" comes back — typed, catchable by code.
- **Validation** sits under all of it: every incoming payload is checked against a schema before any handler runs.

Each piece below shows the server half and the client half together, because that's how the contract works — you declare a thing once and the matching method appears on the other side.

## Events — fire-and-forget, both ways

The simplest exchange: one side sends a named message, the other listens. Nobody waits. The server **declares** what it emits with the `emits()` capability and sends from a handler; the client **listens** with `on()` and **sends** with `send()`.

::code-group

```typescript [server: chat.ts]
import { define, emits, t } from '@wskit/server'
import * as v from 'valibot'
import type { InferClient } from '@wskit/server'

const base = define({
  env: t<Env>(),
  capabilities: [emits({ message: t<{ text: string; from: string }>() })],
})

export const handleSend = base.on('send-message', {
  input: v.object({ text: v.string(), from: v.string() }),
  run(ctx, input) {
    ctx.broadcast('message', input) // to everyone else on the socket
  },
})

export const handler = base.assemble({ handlers: [handleSend] })
export type ChatSocket = InferClient<typeof handler>
```

```typescript [client: app.ts]
import { client, connect } from '@wskit/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(connect('wss://example.com/ws'))
socket.connect()

socket.on('message', (data) => {
  // data: { text: string; from: string } — typed from the server
  console.log(`${data.from}: ${data.text}`)
})

socket.send('send-message', { text: 'hello', from: 'gyen' })
```

::

The two directions are the contract's `incoming` and `outgoing` keys, and the names flip by perspective: the server **emits** `message`, so the client **listens** for it; the server **handles** `send-message`, so the client **sends** it.

| Server                       | Client                           |
| ---------------------------- | -------------------------------- |
| `emits({ message })`         | `socket.on('message', …)`        |
| `base.on('send-message', …)` | `socket.send('send-message', …)` |

::note
`send()` returning `true` means _accepted_ — sent now, or queued if you turned on [buffering](/learn/reliability). It does not mean the server processed it. When you need that confirmation, use a request.
::

Full detail: [Server · emits](/server/capabilities/emits) and the [Client socket](/client/overview).

## Requests — ask and await

When you need a result — a lookup, a saved confirmation, a generated ID — use a request. The client asks, the server answers, the client `await`s a typed response. Turn on `requests()` on the server; whatever the handler **returns** becomes the response.

::code-group

```typescript [server: api.ts]
import { requests } from '@wskit/server/requests'

// base = define({ ..., capabilities: [requests()] })

export const handleGetPost = base.request('get-post', {
  input: v.object({ id: v.string() }),
  async run(ctx, input) {
    return await loadPost(input.id) // the return value is the response
  },
})
```

```typescript [client: app.ts]
import { client, clientRequests, connect } from '@wskit/client'

const socket = client<ApiSocket>()(connect(url), clientRequests())

const post = await socket.request('get-post', { id: '123' })
// post is typed from the handler's return value
```

::

The payload type comes from the handler's `input`, the result type from its return value — rename or reshape either on the server and the client call site updates with it. A request that gets no answer in time rejects with a `Timeout`; one interrupted by a drop rejects with `Disconnected`. The reverse direction — the **server** asking the **client** — is a _server request_: declare it with an `out` payload and an `in` reply schema, then `await ctx.request(...)` on the server and answer with `socket.onRequest(...)` on the client.

Full detail: [Server · requests](/server/capabilities/requests), [Client · client-requests](/client/primitives/client-requests), and [Client · server-requests](/client/primitives/server-requests).

## Errors — typed, end to end

An error shouldn't arrive as a string the client has to parse. You define an error once with a stable code and an optional typed detail, register it, and `throw` it; the client catches it by identity and reads `detail` with full type safety.

::code-group

```typescript [shared: errors.ts]
import { error } from '@wskit/server/errors'
import * as v from 'valibot'

export const NotFound = error('not-found', v.object({ id: v.string() }))
```

```typescript [server: api.ts]
import { errors } from '@wskit/server'
import { NotFound } from './errors'

// base = define({ ..., capabilities: [errors([NotFound])] })

export const handleGetPost = base.request('get-post', {
  input: v.object({ id: v.string() }),
  run(ctx, input) {
    const post = lookup(input.id)
    if (!post) throw NotFound({ id: input.id })
    return post
  },
})
```

```typescript [client: app.ts]
import { NotFound } from '../server/errors'

try {
  await socket.request('get-post', { id })
} catch (err) {
  if (NotFound.matches(err)) {
    console.log('no post with id', err.detail.id) // detail typed as { id: string }
  }
}
```

::

`.matches()` is a type guard, so the matched branch types `err.detail` for you — no string compares, no casts. A registered error thrown inside a request rejects that request's promise; thrown outside one, it surfaces on the client's `onServerError`.

Separately, a small family of **control-flow** errors steer the connection instead of reaching the client — `throw Block` to drop a message silently, `Disconnect(code, reason)` to close it, `Defer(ms)` to retry later. The client also has its own built-ins (`Timeout`, `Disconnected`, `Dropped`) you match the same way.

Full detail: [Server · errors](/server/capabilities/errors) and [Client · errors](/client/errors/overview).

## Validation — the gate before your handler

Anything a client sends is untrusted. The `input` schema on a handler is the gate: WSKit runs the payload through it and only a valid, typed payload reaches your `run`. You've seen it in every example above.

```typescript [api.ts]
export const handleSend = base.on('send-message', {
  input: v.object({
    text: v.pipe(v.string(), v.minLength(1), v.maxLength(500)),
    from: v.string(),
  }),
  run(ctx, input) {
    // input is already { text: string; from: string }, checked and typed
    ctx.broadcast('message', input)
  },
})
```

WSKit ships no schema library of its own — it accepts any [Standard Schema](https://standardschema.dev) validator, so valibot, Zod, and ArkType all work. These docs use valibot.

Validation runs on **incoming** data only — handler `input`, a channel's `subscribe` payload, the `in` reply of a server request. Outgoing payloads aren't re-checked at runtime: the server is trusted to produce the shapes it declared with `t<…>()`, and the contract still type-checks them at compile time. When a payload fails, the handler never runs — the failure rejects the request (or surfaces as a `validation-failed` error), and the server's `onValidationError` hook fires for logging.

Full detail: [Server · handlers](/server/handlers/overview).
