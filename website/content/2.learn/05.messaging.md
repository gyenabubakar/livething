Messaging is the base of LiveThing. It covers the ways the server and the client talk to each other. Channels, streams and reliability features all build on it. The main question for each message is: **do you expect an answer back?**

- **Events** never expect a reply. One side sends a message and continues with its work. Use them for notifications, broadcasts and updates. Most of your traffic is events.
- **Requests** always expect a reply. You `await` a typed answer. Requests work in both directions.
- **Binary messages** carry bytes, such as a picture or a file, with a small JSON **info** next to them. Events, requests and streams can all be binary.
- **Errors** are how a "no" comes back. They are typed, and your code can catch them.
- **Validation** applies to all incoming data. LiveThing checks every incoming payload against a schema before any handler runs.

Each section below shows the server half and the client half together. This is how the contract works: you declare a thing once on the server, and the matching method appears on the client.

## Events: fire-and-forget, both ways

An event is _fire-and-forget_: the sender sends it and does not wait for any answer. One side sends a named message, and the other side listens for it. The server **declares** the events it emits with the `emits()` capability, and sends them from a handler. The client **listens** with `on()` and **sends** with `send()`.

::code-group

```typescript [server: huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'

const base = server({
  capabilities: [
    emits({ 'user-renamed': t<{ userId: string; name: string }>() }),
  ],
})

export const handleRename = base.on('rename', {
  input: v.object({ name: v.string() }),
  run(ctx, input) {
    // to every other connection on this server
    ctx.broadcast('user-renamed', {
      userId: ctx.user.id,
      name: input.name,
    })
  },
})

export const huddle = base.assemble({ handlers: [handleRename] })
export type HuddleSocket = InferClient<typeof huddle>
```

```typescript [client: socket.ts]
import { client, connect } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
)
socket.connect()

socket.on('user-renamed', (data) => {
  // data: { userId: string; name: string }, typed from the server
  console.log(`${data.userId} is now ${data.name}`)
})

socket.send('rename', { name: 'Ama' })
```

::

`ctx.broadcast` does not send the event back to the connection that sent `rename`. Pass `{ includeSelf: true }` as a third argument to include it.

The two directions are the contract's `incoming` and `outgoing` keys. The names change with the point of view. The server **emits** `user-renamed`, so the client **listens** for it. The server **handles** `rename`, so the client **sends** it.

| Server                      | Client                         |
| --------------------------- | ------------------------------ |
| `emits({ 'user-renamed' })` | `socket.on('user-renamed', …)` |
| `base.on('rename', …)`      | `socket.send('rename', …)`     |

::note
When `send()` returns `true`, the socket _accepted_ the message: it sent it now, or it queued it because you turned on [buffering](/learn/reliability). It does not mean that the server processed it. When you need that confirmation, use a request. `send()` returns `false` when the message was dropped.
::

Full detail: [Server · emits](/server/capabilities/emits) and the [Client socket](/client/overview).

## Requests: ask and await

Use a request when you need a result, such as a lookup, a confirmation that data was saved, or a generated ID. The client asks, the server answers, and the client `await`s a typed response. Add the `clientRequests()` capability on the server and the `clientRequests()` primitive on the client. The value that the handler **returns** becomes the response.

::code-group

```typescript [server: huddle-definition.ts]
import { server } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'
import { loadProfile } from './huddle-data'

const base = server({
  capabilities: [clientRequests()],
})

export const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  async run(ctx, input) {
    return await loadProfile(input.userId) // the return value is the response
  },
})

export const huddle = base.assemble({
  handlers: [handleGetProfile],
})
export type HuddleSocket = InferClient<typeof huddle>
```

```typescript [client: socket.ts]
import { client, clientRequests, connect } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  clientRequests(),
)

const profile = await socket.request('get-profile', {
  userId: 'u_amara',
})
// profile is typed from the handler's return value
```

::

The payload type comes from the handler's `input`. The result type comes from its return value. When you rename or change either of them on the server, the types at the client call site change too. A request that gets no answer in time rejects with a `Timeout` error. A request that is still waiting when the connection drops rejects with a `Disconnected` error.

Requests also work in the other direction: the **server** can ask the **client**. This is a _server request_. On the server, declare it in the `serverRequests()` capability with an `out` type and an `in` schema. Then call `await ctx.request(...)` in a handler. On the client, add the `serverRequests()` primitive and answer with `socket.onRequest(...)`:

::code-group

```typescript [server: huddle-definition.ts]
import { server, t } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import { serverRequests } from '@livething/server/server-requests'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'
import { deleteMessage, loadMessagePreview } from './huddle-data'

const base = server({
  capabilities: [
    clientRequests(),
    serverRequests({
      'confirm-delete': {
        out: t<{ preview: string }>(),
        in: v.object({ confirmed: v.boolean() }),
      },
    }),
  ],
})

export const handleDeleteMessage = base.request('delete-message', {
  input: v.object({ messageId: v.string() }),
  async run(ctx, input) {
    const answer = await ctx.request('confirm-delete', {
      preview: await loadMessagePreview(input.messageId),
    })
    if (!answer.confirmed) return { deleted: false }

    await deleteMessage(input.messageId)
    return { deleted: true }
  },
})

export const huddle = base.assemble({
  handlers: [handleDeleteMessage],
})
export type HuddleSocket = InferClient<typeof huddle>
```

```typescript [client: socket.ts]
import {
  client,
  clientRequests,
  connect,
  serverRequests,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  clientRequests(),
  serverRequests(),
)

socket.onRequest('confirm-delete', (payload) => {
  return { confirmed: window.confirm(`Delete "${payload.preview}"?`) }
})
```

::

Full detail: [Server · clientRequests](/server/capabilities/client-requests), [Server · serverRequests](/server/capabilities/server-requests), [Client · client-requests](/client/primitives/client-requests), and [Client · server-requests](/client/primitives/server-requests).

## Binary messages: bytes with info

A payload is JSON. That is right for text and small data, but a picture, a file or a voice note is bytes, and bytes in JSON (as base64 text) are about a third bigger. A **binary message** carries the bytes as they are. It has two parts:

- the **info**: JSON that describes the bytes, such as the type of a file. It is typed and checked like a payload.
- the **bytes**: the data itself, as a `Uint8Array`. No schema checks them, but a handler can limit their size with `maxBytes`.

Add the `binary()` capability on the server and the `binary()` primitive on the client. On the server, `binary({ emits })` declares the binary events the server sends, and `base.binary.on(...)` handles one that the client sends. On the client, `socket.binary.send(...)` and `socket.binary.on(...)` work like `send` and `on`. `send` takes the event, then the bytes, then the info in `{ info }`: the bytes come second because a binary message is about the bytes. Huddle uses this for avatars: the client uploads a picture, and the server sends back a small preview of it:

::code-group

```typescript [server: huddle-definition.ts]
import { server, t } from '@livething/server'
import { binary } from '@livething/server/binary'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'
import { resizeAvatar, saveAvatar } from './huddle-data'

const base = server({
  capabilities: [binary({ emits: { 'avatar-preview': t<null>() } })],
})

export const handleUploadAvatar = base.binary.on('upload-avatar', {
  input: v.object({
    fileType: v.picklist(['image/png', 'image/jpeg']),
  }),
  maxBytes: 2 * 1024 * 1024,
  async run(ctx, input, bytes) {
    await saveAvatar(ctx.user.id, input.fileType, bytes.slice())
    ctx.binary.send('avatar-preview', await resizeAvatar(bytes), {
      info: null,
    })
  },
})

export const huddle = base.assemble({
  handlers: [handleUploadAvatar],
})
export type HuddleSocket = InferClient<typeof huddle>
```

```typescript [client: socket.ts]
import { binary, client, connect } from '@livething/client'
import { avatarBytes, showAvatar } from './huddle-ui'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
)
socket.connect()

socket.binary.on('avatar-preview', (_info, bytes) => {
  showAvatar(bytes)
})

socket.binary.send('upload-avatar', avatarBytes, {
  info: { fileType: 'image/png' },
})
```

::

`bytes` in the handler is a view of the message that arrived, so `bytes.slice()` makes a copy for code that keeps the bytes after `run` returns. The info proves nothing about the bytes, so `saveAvatar` still checks that they really are a picture.

Binary messages use the rest of LiveThing as JSON messages do. A channel declares its own binary events, such as [`screen-frame`](/server/binary/events#handling-binary-events) in Huddle's rooms. Requests, server requests and streams have binary versions: [`get-thumbnail`](/server/binary/requests#binary-requests) replies with a small picture of a file, and [`download-attachment`](/server/binary/streams#binary-streams) streams a file in pieces. History replay and inbox store binary messages with their bytes. A file too big for one message is an upload: [`upload-attachment`](/server/binary/uploads#an-upload-handler) sends a file in pieces, and resumes after a drop. Framework messages, such as errors and stream confirmations, stay JSON text.

Full detail: [Server · binary](/server/binary/overview) and [Client · binary](/client/primitives/binary). For uploads: [Server · uploads](/server/binary/uploads) and [Client · uploads](/client/primitives/uploads).

## Errors: typed, end to end

In LiveThing, an error does not arrive as a string that the client must parse. You define an error once, with a stable code and an optional typed detail. You register it on the server and `throw` it in a handler. The client catches it, checks it against the same definition, and reads `detail` with full types.

Put the definition in a file that both the server and the client import. Import `error` from `@livething/core`, because that package is safe to use on both sides (see [Isomorphic code](/core/isomorphic-code)).

::code-group

```typescript [shared: errors.ts]
import { error } from '@livething/core'
import * as v from 'valibot'

export const NotFound = error(
  'not-found',
  v.object({ id: v.string() }),
)
```

```typescript [server: huddle-definition.ts]
import { errors, server } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'
import { NotFound } from '../shared/errors'
import { loadProfile } from './huddle-data'

const base = server({
  capabilities: [clientRequests(), errors([NotFound])],
})

export const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  async run(ctx, input) {
    const profile = await loadProfile(input.userId)
    if (!profile) throw NotFound({ id: input.userId })

    return profile
  },
})

export const huddle = base.assemble({
  handlers: [handleGetProfile],
})
```

```typescript [client: profile.ts]
import { NotFound } from '../shared/errors'
import { socket } from './socket'

try {
  await socket.request('get-profile', { userId: 'u_amara' })
} catch (err) {
  if (NotFound.matches(err)) {
    console.log('no user with id', err.detail.id) // detail typed as { id: string }
  }
}
```

::

`.matches()` is a _type guard_: a function that tells TypeScript the exact type of a value when it returns `true`. So inside the matched branch, `err.detail` has its real type. You do not compare strings and you do not need casts. When a handler throws a registered error during a request, the promise of that request rejects with it. When the error is thrown outside a request (for example, in an `on()` handler), the client receives it through `socket.onServerError(...)`.

LiveThing also has a small group of **control-flow** errors. These errors change what happens to the message or the connection, and they do not reach the client:

- `throw Block` in an `intercept` drops the incoming message without any error.
- `throw Disconnect(code, reason)` closes the connection.

The client also has its own built-in errors (`Timeout`, `Disconnected`, `Dropped`, `StreamCorrupted`, `StreamOverflow`). You check them with `.matches()` in the same way.

Full detail: [Server · errors](/server/capabilities/errors) and [Client · errors](/client/errors/overview).

## Validation: the gate before your handler

Do not trust anything that a client sends. The `input` schema on a handler is the gate. LiveThing checks the payload against it, and only a valid, typed payload reaches your `run` function. Every example above uses it. Here is Huddle's `send-message` handler on `rooms`, with a stricter `input` that limits the text to 1 to 500 characters:

```typescript [server/rooms.ts]
import * as v from 'valibot'
import { rooms } from './base'

export const handleSendMessage = rooms.on('send-message', {
  input: v.object({
    text: v.pipe(v.string(), v.minLength(1), v.maxLength(500)),
  }),
  run(ctx, input) {
    // input is already { text: string }, checked and typed
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

LiveThing does not have its own schema library. It accepts any [Standard Schema](https://standardschema.dev) validator, so valibot, Zod and ArkType all work. These docs use valibot.

Validation runs on **incoming** data only:

- the `input` of a handler (for a binary message, the info; its bytes are limited only by `maxBytes`),
- the `subscribe` payload of a channel,
- the `in` reply of a server request.

At runtime, LiveThing checks only that an outgoing payload is an object or `null` in JSON. It does not check it against the shape declared with `t<…>()`: the server is trusted to send that shape, and TypeScript checks it at compile time.

When a payload fails validation, the handler does not run. If the message was a request, the request rejects with a `validation-failed` error. Otherwise the client receives the `validation-failed` error through `socket.onServerError(...)`. In both cases, the server's `onError` hook gets a `ValidationFailed` error, so you can log the failure.

Full detail: [Server · handlers](/server/handlers/overview).
