A plain stream is ephemeral: drop the connection mid-stream and it's gone. For a short stream you'd just re-request, that's fine. But for a long, expensive stream — a multi-minute AI generation, a large export — losing it on a network blip is painful. **Durable streams** solve this: the server keeps enough state that when the client reconnects, the stream picks up where it left off.

There are two flavors, and they differ in *what* gets saved.

## Two strategies

- **Recorded streams** save the **chunks** themselves in a buffer. On reconnect, the client gets replayed the chunks it missed. Best when each chunk matters and you want them all delivered — the server just keeps a rolling buffer and re-sends the gap.
- **Resumable streams** save a **cursor** — a small marker of how far the generator got. On reconnect, the generator restarts *from that cursor* and continues producing. Best when re-running from a position is cheaper or more correct than buffering every chunk — like paginating through rows where "I was at row 40" is all you need.

Both require the `persistence()` capability, which gives the server the storage to hold this state.

::note
The examples below leave off one line for focus: as with any handler, pass the durable-stream handler to `base.assemble(...)` for it to take effect and show up in the contract. See [The Contract](/learn/core-model/the-contract).
::

## Recorded streams

Declare with `base.recordedStream(...)`. It looks like a plain stream — you still write an `async *run` that yields chunks — but the framework buffers each chunk so it can replay them after a reconnect:

```typescript [export.ts]
import { define, t } from '@wskit/server'
import { persistence } from '@wskit/server/persistence'
import { recordedStream } from '@wskit/server/streams'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [persistence(), recordedStream()],
})

export const handleCountTokens = base.recordedStream('count-tokens', {
  input: v.object({}),
  chunk: t<{ idx: number }>(),
  maxChunks: 100,
  async *run() {
    for (let i = 1; i <= 50; i += 1) {
      yield { idx: i }
    }
  },
})
```

`maxChunks` caps how many chunks the buffer holds. You yield chunks exactly as in a plain stream — the durability is handled for you.

## Resumable streams

Declare with `base.resumableStream(...)`. Here you take part in the resume: you yield each chunk *together with a cursor* using `ctx.stream.withCursor(chunk, cursor)`, and when a resume happens, your generator reads `ctx.stream.cursor` to know where to restart:

```typescript [export.ts]
import { persistence } from '@wskit/server/persistence'
import { resumableStream } from '@wskit/server/streams'

const base = define({
  env: t<Env>(),
  capabilities: [persistence(), resumableStream()],
})

export const handlePaginate = base.resumableStream('paginate', {
  input: v.object({}),
  chunk: t<{ row: number }>(),
  async *run(ctx) {
    // on a fresh start cursor is null; on resume it's the last saved cursor
    const startAt = (ctx.stream.cursor as { idx: number } | null)?.idx ?? 0
    for (let i = startAt + 1; i <= 100; i += 1) {
      // yield the chunk AND the cursor to save alongside it
      yield ctx.stream.withCursor({ row: i }, { idx: i })
    }
  },
})
```

On the first run, `ctx.stream.cursor` is `null`, so you start from the beginning. After a reconnect, it holds the cursor you last saved, so you continue from there. The cursor is yours to define — whatever marker lets your generator resume correctly.

## Auto-resume on the client

The client side is the best part: **resume is automatic.** You start a durable stream exactly like a plain one — `socket.stream(...)`, `for await` — and if the socket drops and reconnects (with the [reconnection](/learn/reliability/reconnection) primitive on), the stream re-attaches itself and keeps delivering chunks into the same loop:

```typescript [app.ts]
const rows = await socket.stream('paginate', {})

for await (const chunk of rows) {
  // chunks keep arriving across a reconnect — the loop doesn't break
  render(chunk.row)
}
```

You don't write reconnect handling for the stream; the durability the server set up plus the client's auto-resume cover it.

## How the kinds are typed

The contract marks each stream's **kind** — `'ephemeral'` for plain streams, `'persistent'` for durable ones. This isn't just informational: the client uses it to gate the manual resume method, so you can only try to resume a stream that's actually persistent. A plain stream simply isn't a valid resume target, and the compiler enforces it.

## What flows between them

| Server | Client |
|---|---|
| `base.recordedStream(...)` | `socket.stream(...)`, auto-replays missed chunks on reconnect |
| `base.resumableStream(...)` + `withCursor` | `socket.stream(...)`, auto-resumes from cursor on reconnect |
| `persistence()` capability | `reconnection()` primitive (to trigger the reconnect) |

Pick **recorded** when every chunk must be delivered and buffering them is cheap; pick **resumable** when restarting the generator from a saved position is the cleaner way to continue.

For retention windows, disconnect behavior, and concurrent durable streams, see the [Server streams reference](/server/capabilities/streams) and the [Client stream reference](/client/primitives/stream).
