A plain stream is one-directional: the server pushes chunks, the client reads them. But sometimes the client needs to *talk back* to a stream while it's running — "pause", "speed up", "skip ahead" — without cancelling and restarting it. That's a **nudge**: a small typed message the client sends into a live stream, which the server's generator can read between chunks.

The classic case is an AI response: the user hits pause, or asks it to go faster. You don't want to tear down the stream and lose your place — you want to nudge it.

## Server: declare and read nudges

Nudges are declared in the stream config under `nudges`, as a map of nudge names to payload schemas. Each one is a message the client is allowed to send into this stream:

```typescript [ai.ts]
export const handleTokens = base.stream('start-tokens', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ token: string }>(),
  nudges: {
    pause: v.object({}),
    'speed-up': v.object({ factor: v.number() }),
  },
  async *run(ctx, input) {
    let delay = 50
    for (const word of input.prompt.split(' ')) {
      // yield the chunk, and read any nudges that arrived since the last yield
      const nudges = ctx.stream.nudges(yield { token: word + ' ' })

      if (nudges.some((n) => n.event === 'pause')) return

      const speedUp = nudges.find((n) => n.event === 'speed-up')
      if (speedUp) delay = Math.max(1, delay / speedUp.payload.factor)

      await new Promise((r) => setTimeout(r, delay))
    }
  },
})
```

The key line is `ctx.stream.nudges(yield chunk)`. Reading nudges is tied to yielding: you `yield` a chunk, and pass that yield expression to `ctx.stream.nudges(...)`, which hands back any nudges the client sent since your last yield. Each nudge in the array has an `event` (the nudge name) and a `payload` (typed from that nudge's schema).

This design means nudges are processed at natural points in your generator — right after each chunk — so you check for "pause" or "speed up" exactly when you're about to produce the next piece.

::note
This snippet shows just the stream handler. Like any handler, `handleTokens` has to be passed to `base.assemble(...)` to become part of your server and its contract — see [The Contract](/learn/core-model/the-contract).
::

## Client: nudge a running stream

On the client, the stream handle has a `nudge(name, payload)` method. You call it on a live stream while you're consuming it:

```typescript [app.ts]
const tokens = await socket.stream('start-tokens', { prompt: longPrompt })

// somewhere else — a button handler, say:
async function onSpeedUp() {
  await tokens.nudge('speed-up', { factor: 2 })
}

async function onPause() {
  await tokens.nudge('pause', {})
}

for await (const chunk of tokens) {
  render(chunk.token)
}
```

`nudge(...)` returns a Promise that resolves when the server confirms it received the nudge. If the nudge is refused or times out, the Promise rejects — but importantly, **a rejected nudge does not end the stream.** The stream keeps running; only the nudge call failed. After a stream has ended, a nudge resolves to a harmless no-op.

The nudge name and payload are typed from the server's `nudges` declaration, so you can only send nudges the stream actually accepts, with the right shape.

## What flows between them

| Server | Client |
|---|---|
| `nudges: { pause, 'speed-up' }` | `stream.nudge('speed-up', { factor })` |
| `ctx.stream.nudges(yield chunk)` | (the nudges arrive here) |
| each nudge: `{ event, payload }` | the `(name, payload)` you sent |

Nudges turn a stream from a one-way push into a steerable conversation, while keeping the chunk-flow itself untouched. They work on plain streams and durable streams alike — and on durable streams, buffered nudges even survive a resume.

For nudge timeouts, ordering guarantees, and the full handle API, see the [Server streams reference](/server/capabilities/streams) and the [Client stream reference](/client/primitives/stream).
