Some data doesn't arrive all at once — it comes in pieces, over time. The tokens of an AI response, the rows of a big query, the frames of a live feed. **Streaming** is WSKit's way of sending that kind of data: the server produces a sequence of chunks, and the client consumes them one by one as they arrive, instead of waiting for the whole thing.

## The streaming model

A WSKit stream is built on a familiar JavaScript idea: the **async generator**. On the server, you write an `async *` generator that `yield`s chunks; on the client, you `for await` over them as they arrive. The framework handles everything between — correlating the chunks, signalling the end, and cleaning up if either side bails out.

```typescript
// Server: yield chunks
async *run(ctx, input) {
  yield { token: 'Hello' }
  yield { token: ' world' }
}

// Client: consume them
for await (const chunk of stream) {
  process.stdout.write(chunk.token)
}
```

That's the shape of every stream. What differs is *how durable* the stream is and *who* receives it.

## Two kinds of stream

Every stream is one of **two kinds**, and the difference is whether its state outlives a disconnect:

- **Ephemeral** — *plain streams*. Chunks flow while the connection is up; if the socket drops mid-stream, the stream is gone. No stored state, nothing to resume — lighter, simpler, and the right default. Perfect for the common case where a lost stream just gets re-requested.
- **Durable** — *persistent streams*. The server keeps enough state that when the client reconnects, the stream picks up where it left off — either by replaying buffered chunks (*recorded*) or by resuming from a saved position (*resumable*). This needs the `persistence()` capability, in exchange for surviving network drops.

The contract marks each stream's kind — `ephemeral` or `persistent` — so the client only offers resume methods on streams that can actually resume. In the client contract, a stream lives under the `streams` key, pairing the `payload` that starts it with the `chunk` shape it yields:

```typescript [ai-socket.ts]
interface AiSocket {
  streams: {
    'ask-ai': {
      payload: { prompt: string }   // starts the stream
      chunk: { text: string }       // each piece you receive
      kind: 'ephemeral'             // or 'persistent' for a durable stream
    }
  }
}
```

## Behaviours on top

Two features apply to *either* kind. They aren't separate kinds — just options you switch on:

- **Broadcast** fans one stream out to many listeners at once, instead of one stream per client — a shared live feed everyone watches together. Any stream, ephemeral or durable, can be a broadcast.
- **Nudges** let the client send messages *into* a running stream — to pause it, speed it up, or steer it — without tearing it down.

## One client slot

By default, a connection runs **one stream per event name at a time**. Start a second `start-tokens` stream while the first is still going and you get an error, not two overlapping streams. This keeps things predictable — a stream maps to a clear, single activity. (You can opt into concurrent streams when you genuinely need them.)
