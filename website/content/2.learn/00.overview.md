In the [Start](/start/introduction) section, you built a small working app. **Learn** is a guided tour. It teaches LiveThing as one system, from the basics up, in the order in which the ideas depend on each other. Read the pages in order, and at the end you will know enough to build real apps.

LiveThing has two main packages: `@livething/server` and `@livething/client`. They are not two separate libraries that send messages to each other. They are the two halves of **one contract**. So every page in this section shows the server half and the client half together, because you build every feature on both sides.

This section is a **tutorial**, not a reference. Each page explains one idea and shows the smallest working version of both halves. For every option, every method, and every special case, each page links to the [Server](/server/overview) and [Client](/client/overview) sections. Learn the general idea here, and look up the details there.

## Foundations

Start with the four ideas that all other pages use. After you understand them, every feature has the same form: a capability on the server, a primitive on the client, and the messages that go between them.

::card-group
::card{title="The Contract" icon="i-ph-scroll-duotone" to="/learn/the-contract"}
The one inferred type that goes from the server to the client, and the "perspective flip": the client sees each event from the opposite side, as a mirror of the server's view.
::
::card{title="Capabilities & Primitives" icon="i-ph-puzzle-piece-duotone" to="/learn/capabilities-and-primitives"}
The matched opt-in pair, and why your bundle only contains the features you import.
::
::card{title="Connection Lifecycle" icon="i-ph-arrows-clockwise-duotone" to="/learn/connection-lifecycle"}
The stages of a connection (upgrade, connect, messages, disconnect) and the states the client goes through.
::
::card{title="Wire Protocol" icon="i-ph-brackets-curly-duotone" to="/learn/wire-protocol"}
The frames that both sides send: a three-item JSON array with the event name, the payload, and nested metadata for routing and for matching replies to requests, and the binary frame that puts the same array in front of raw bytes.
::
::

## The feature tour

After the foundations, each page below covers one group of features. It shows both halves, a real use case, and the messages that go between them.

::card-group
::card{title="Messaging" icon="i-ph-chat-circle-dots-duotone" to="/learn/messaging"}
The ways the two sides talk: events that need no reply, requests and responses in both directions, binary messages for bytes, typed errors, and payload validation.
::
::card{title="Channels" icon="i-ph-users-three-duotone" to="/learn/channels"}
Rooms that the server manages: joining through an access check that you write, and presence.
::
::card{title="Scoped Features" icon="i-ph-bounding-box-duotone" to="/learn/scoped-features"}
Requests, streams, and replay that belong to one channel, with their own typed contract.
::
::card{title="Streaming" icon="i-ph-waveform-duotone" to="/learn/streaming"}
Data that arrives in small parts over a stream: plain generator functions, stopping early, and nudges.
::
::card{title="Durable & Broadcast" icon="i-ph-broadcast-duotone" to="/learn/durable-and-broadcast"}
Streams that continue after the client reconnects, and streams that send one generator's output to many listeners.
::
::card{title="Reliability" icon="i-ph-pulse-duotone" to="/learn/reliability"}
How to keep a connection healthy on a bad network: reconnection, keepalive, buffering, replay, deduplication, and inbox.
::
::card{title="Identity & Access" icon="i-ph-key-duotone" to="/learn/identity-and-access"}
Who can connect and what they can use: authentication, tags, and rate limiting.
::
::

Start with **The Contract**. It is the one idea that the rest of the framework depends on.
::
