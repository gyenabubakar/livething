A channel is not only for broadcasting events. Other messaging features can also live _inside_ a channel: [client-to-server and server-to-client requests](/learn/messaging), streams, and replay. A feature that lives inside a channel is **scoped** to that channel. It belongs to that room, you call it through the channel handle, and its types come from the channel's own contract.

One rule covers all of them: **what you declare on `base`, you declare on the channel. What you call on `socket`, you call on the channel handle.** So when you know a feature, you also know its scoped version. Only the place where you declare and call it changes.

## Channel-scoped requests

You declare a channel-scoped request with `channel.request(...)`, and you call it on the client's channel handle. It works the same as a top-level request, but it is for things that only make sense inside that room, such as "get this channel's info" or "take a seat in this game".

::code-group

```typescript [server: chat.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'

const base = server({
  capabilities: [channels(), clientRequests()],
})

const room = base.channel('room', {
  capabilities: [emits({ message: t<{ text: string }>() })],
})

export const handleInfo = room.request('get-channel-info', {
  input: v.object({}),
  run(ctx) {
    // ctx.channel is scoped to this room.
    return {
      name: ctx.channel.name,
      size: ctx.channel.members().length,
    }
  },
})

export const definition = base.assemble({ handlers: [handleInfo] })
```

```typescript [client: app.ts]
const room = socket.channel('room')
await room.subscribe()

const info = await room.request('get-channel-info', {})
// info: { name: string; size: number }, typed from the handler's return value
```

::

The request belongs to the channel's contract. So `room.request(...)` offers only the requests that this channel declared, and the top-level `socket.request(...)` does not offer them at all. Scoped requests need the same setup as top-level ones: the `clientRequests()` capability on the server and the `clientRequests()` primitive on the client.

## Channel-scoped streams

A **stream** is a reply that the server sends in many small parts, called **chunks**, instead of one message. The [Streaming](/learn/streaming) page covers streams in full. Streams are scoped the same way as requests: declare them with `channel.stream(...)` and consume them with `room.stream(...)`.

::code-group

```typescript [server: chat.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'

const base = server({
  capabilities: [channels(), stream()],
})

const room = base.channel('room', {
  capabilities: [emits({ message: t<{ text: string }>() })],
})

export const handleHistory = room.stream('replay-history', {
  input: v.object({ limit: v.number() }),
  chunk: t<{ text: string; at: number }>(),
  async *run(ctx, input) {
    for (const msg of await loadHistory(
      ctx.channel.name,
      input.limit,
    )) {
      yield msg
    }
  },
})

export const definition = base.assemble({
  handlers: [handleHistory],
})
```

```typescript [client: app.ts]
const room = socket.channel('room')
await room.subscribe()

const history = await room.stream('replay-history', {
  limit: 50,
})
for await (const msg of history) {
  render(msg)
}
```

::

Everything in the streaming pages also applies to channel-scoped streams: plain, resumable, and recorded streams, and broadcast streams. A broadcast stream (one declared with `broadcast: true`) sends each chunk to many listeners at once. On a channel, it sends to that channel's members only. At the top level, it sends to every connection. The [Streaming](/learn/streaming) pages explain how streams work. The only difference here is where you declare and call them. The matching client primitive is [`stream()`](/client/primitives/stream).

## Channel-scoped replay

[Replay](/learn/reliability) lets a client get the messages it missed while it was disconnected. Replay can also be scoped to a channel. Each channel keeps its own message count (its **sequence**), so when a member reconnects, it gets the missed messages of _that room_ only, separate from every other room. You turn on replay in the channel's config. On the client, the `replay()` primitive then asks for missed messages once per channel, with no extra code. The [Reliability](/learn/reliability) page explains how replay works. The point here is that replay, like requests and streams, stays inside channel boundaries.

## The `ctx.channel` API

On the server, you reach everything channel-scoped through `ctx.channel` inside a channel handler. `ctx.channel` is bound to the exact room that the call came from. So one handler works for every room it handles. For example, a handler on a dynamic `room:{id}` channel broadcasts to the room that the message came from, with no extra code to track which room that is.

```typescript [chat.ts]
const handleSend = room.on('send', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.name // the matched name (the room name for a family)
    ctx.channel.family // the family key for a dynamic channel; absent for a static channel
    ctx.channel.members() // the connections in this channel
    ctx.channel.send('message', { text: 'just you' }) // the current connection only
    ctx.channel.broadcast('message', { text: input.text }) // only this channel's members
  },
})
```

This is the main difference from the top level: `ctx.channel.broadcast(...)` reaches only this channel's members, while the top-level `ctx.broadcast(...)` reaches every connection on the server. Both skip the sender unless you pass `{ includeSelf: true }`.

`ctx.channel` can also send server-to-client requests. For this, add the `serverRequests()` capability to the server, and declare the channel's requests with `serverRequests({...})` in the channel's `capabilities`. Then `ctx.channel` has two more methods:

- `request(...)` asks the current member and waits for its answer.
- `broadcastRequest(...)` sends the request to every member of the room and returns the first valid answer.

::note
The client contract shows the scoped features directly. A room's entry in the contract has its own `clientRequests`, `serverRequests` and `streams`. These are the same keys as at the top level, one level deeper, under the room. So `room.request('get-channel-info', …)` reads from _this room's_ requests, and `socket.request(...)` does not see it.
::

For the full scoped API (the server-to-client request methods, the stream kinds, and the per-channel replay config), see [Server · Scoped Streams & Requests](/server/channels/scoped-streams-requests) and [Client · channels](/client/primitives/channels).
