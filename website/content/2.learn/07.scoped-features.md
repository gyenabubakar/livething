A channel isn't only for broadcasting events. The other messaging features — [requests](/learn/messaging), streams, and replay — can live *inside* a channel too. When they do, they're **scoped**: they belong to that room, addressed through the channel handle, and typed under the channel's own contract.

The pattern is consistent and worth holding onto: **whatever you'd declare on `base`, you declare on the channel; whatever you'd call on `socket`, you call on the channel handle.** Learn a feature once and you know its scoped version — only the *where* changes.

## Channel-scoped requests

A request scoped to a channel is declared with `channel.request(...)` and called on the client's channel handle. It works exactly like a top-level request, but it only makes sense inside that room — "get this channel's info", "claim a seat in this game".

::code-group
```typescript [server: chat.ts]
import { define, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { requests } from '@wskit/server/requests'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [channels(), requests()],
})

const room = base.channel('room', {
  outgoing: { emits: { message: t<{ text: string }>() } },
})

export const handleInfo = room.request('get-channel-info', {
  input: v.object({}),
  run(ctx) {
    // ctx.channel is scoped to this room.
    return { name: ctx.channel.name, size: ctx.channel.members().length }
  },
})

export const handler = base.assemble(handleInfo)
```

```typescript [client: app.ts]
const room = socket.channel('room')
await room.subscribe()

const info = await room.request('get-channel-info', {})
// info: { name: string; size: number } — typed from the handler's return
```
::

The request lives under the channel's contract, so `room.request(...)` only offers the requests that channel declared — and the top-level `socket.request(...)` never sees them. Scoped requests need the `requests()` capability on the server and the `requestResponse()` primitive on the client, the same as top-level ones.

## Channel-scoped streams

Streams scope the same way. Declare with `channel.stream(...)`; consume with `room.stream(...)`.

::code-group
```typescript [server: chat.ts]
import { stream } from '@wskit/server/streams'

const base = define({
  env: t<Env>(),
  capabilities: [channels(), stream()],
})

const room = base.channel('room', {
  outgoing: { emits: { message: t<{ text: string }>() } },
})

export const handleHistory = room.stream('replay-history', {
  input: v.object({ limit: v.number() }),
  chunk: t<{ text: string; at: number }>(),
  async *run(ctx, input) {
    for (const msg of await loadHistory(ctx.channel.name, input.limit)) {
      yield msg
    }
  },
})
```

```typescript [client: app.ts]
const room = socket.channel('room')
await room.subscribe()

const history = await room.stream('replay-history', { limit: 50 })
for await (const msg of history) {
  render(msg)
}
```
::

The full streaming story — plain, durable, recorded, broadcast — all applies to channel-scoped streams. A channel-scoped `broadcast: true` stream fans out to that channel's members, where the top-level version fans out to the whole socket. The mechanics live in the [Streaming](/learn/streaming) pages; the only difference here is where you declare and call them. The matching client primitive is [`stream()`](/client/primitives/stream).

## Channel-scoped replay

[Replay](/learn/reliability) — catching up on messages you missed while disconnected — can also be scoped per channel. Each channel tracks its own sequence, so when a member reconnects they catch up on *that room's* history independently of any other room. You turn replay on at the channel level, and the client's catch-up happens automatically per channel. The [Reliability](/learn/reliability) page covers the mechanics; the takeaway here is that replay, like requests and streams, respects channel boundaries.

## The `ctx.channel` surface

On the server, everything channel-scoped is reached through `ctx.channel` inside a channel handler. Because the handle is bound to the exact room the call came in on, the same handler logic applies to whichever instance it's handling — a dynamic `room:{id}` handler broadcasts to exactly the room the message arrived on, with no extra bookkeeping.

```typescript [chat.ts]
const handleSend = room.on('send', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.name                    // the matched name (the instance for a family)
    ctx.channel.family                  // the family key, or null for a static channel
    ctx.channel.members()               // this channel's roster
    ctx.channel.send('message', { text: 'just you' })       // the current connection, in scope
    ctx.channel.broadcast('message', { text: input.text })  // only this channel's members
  },
})
```

`ctx.channel.broadcast(...)` reaches only this channel's members, while top-level `ctx.broadcast(...)` reaches the whole socket — that's the core difference. When `requests()` is on, `ctx.channel` also carries `request(...)` (ask the current member) and `broadcastRequest(...)` (fan out to the room, first answer wins).

::note
The scoped surface shows up directly in the client contract: a room's entry carries its own `requests` and `streams`, the same keys you'd find at the top level, just nested one room deep. So `room.request('get-channel-info', …)` reads from *this room's* requests, and `socket.request(...)` never sees it.
::
