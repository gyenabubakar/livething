A channel is not only for broadcasting events. Other messaging features can also live _inside_ a channel: [client-to-server and server-to-client requests](/learn/messaging), streams, and replay. A feature that lives inside a channel is **scoped** to that channel. It belongs to that room, you call it through the channel handle, and its types come from the channel's own contract.

One rule covers all of them: **what you declare on `base`, you declare on the channel. What you call on `socket`, you call on the channel handle.** So when you know a feature, you also know its scoped version. Only the place where you declare and call it changes.

## Channel-scoped requests

You declare a channel-scoped request with `channel.request(...)`, and you call it on the client's channel handle. It works the same as a top-level request, but it is for things that only make sense inside that room. Huddle's rooms have one: `load-history`, which pages through a room's older messages.

::code-group

```typescript [server: huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'
import { loadMessages } from './huddle-data'

const base = server({
  capabilities: [channels(), clientRequests()],
})

const rooms = base.channel(['rooms', 'room:{roomId}'] as const, {
  capabilities: [
    emits({
      message: t<{
        id: string
        text: string
        from: string
        sentAt: number
      }>(),
    }),
  ],
})

export const handleLoadHistory = rooms.request('load-history', {
  input: v.object({ before: v.optional(v.number()) }),
  async run(ctx, input) {
    // ctx.channel is scoped to this room.
    return {
      messages: await loadMessages(
        ctx.channel.params.roomId,
        input.before,
      ),
    }
  },
})

export const huddle = base.assemble({ handlers: [handleLoadHistory] })
```

```typescript [client: history.ts]
import { socket } from './socket'

const general = socket.channel('rooms', 'room:general')
await general.subscribe()

const page = await general.request('load-history', {
  before: Date.now(),
})
// page: { messages: Message[] }, typed from the handler's return value
```

::

The request belongs to the channel's contract. So `general.request(...)` offers only the requests that this channel declared, and the top-level `socket.request(...)` does not offer them at all. Scoped requests need the same setup as top-level ones: the `clientRequests()` capability on the server and the `clientRequests()` primitive on the client.

## Channel-scoped streams

A **stream** is a reply that the server sends in many small parts, called **chunks**, instead of one message. The [Streaming](/learn/streaming) page covers streams in full. Streams are scoped the same way as requests: declare them with `channel.stream(...)` (or, for a durable one, `channel.recordedStream(...)`) and consume them with the channel handle. Huddle's rooms use this for **Scout**, the AI assistant: anyone in a room can ask Scout, and its reply streams into the room. The `ask-scout` below is a smaller version than the one in Huddle's definition: it has no nudges yet.

::code-group

```typescript [server: huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { recordedStream } from '@livething/server/streams'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'
import { llm } from './llm'

const base = server({
  capabilities: [channels(), recordedStream()],
})

const rooms = base.channel(['rooms', 'room:{roomId}'] as const, {
  capabilities: [
    emits({
      message: t<{
        id: string
        text: string
        from: string
        sentAt: number
      }>(),
    }),
  ],
})

export const handleAskScout = rooms.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  broadcast: true, // every member of the room sees the reply, not only the one who asked
  async *run(ctx, input) {
    for await (const piece of llm.stream({
      messages: [{ role: 'user', text: input.prompt }],
      signal: ctx.stream.signal,
    })) {
      yield { text: piece }
    }
  },
})

export const huddle = base.assemble({
  handlers: [handleAskScout],
})

export type HuddleSocket = InferClient<typeof huddle>
```

```typescript [client: socket.ts]
import { channels, client, connect, stream } from '@livething/client'
import { render } from './huddle-ui'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://huddle.example.com/huddle'),
  channels(),
  stream(),
)

const general = socket.channel('rooms', 'room:general')
await general.subscribe()

const reply = await general.stream('ask-scout', {
  prompt: 'summarize the last hour of this room',
})
for await (const chunk of reply) {
  render(chunk.text)
}
```

::

Everything in the streaming pages also applies to channel-scoped streams: plain and recorded streams, and broadcast streams. A broadcast stream (one declared with `broadcast: true`) sends each chunk to many listeners at once. On a channel, it sends to that channel's members only. At the top level, it sends to every connection. This is why every member of a room sees Scout's reply, not only the one who asked. The [Streaming](/learn/streaming) and [Durable & Broadcast](/learn/durable-and-broadcast) pages explain how streams work, and come back to `ask-scout` for the parts left out here: stopping a reply, redirecting it, and continuing after a disconnect. The matching client primitive is [`stream()`](/client/primitives/stream).

## Channel-scoped replay

[Replay](/learn/reliability) lets a client get the messages it missed while it was disconnected. Replay can also be scoped to a channel. Each channel keeps its own message count (its **sequence**), so when a member reconnects, it gets the missed messages of _that room_ only, separate from every other room. You turn on replay in the channel's config. On the client, the `replay()` primitive then asks for missed messages once per channel, with no extra code. The [Reliability](/learn/reliability) page explains how replay works. The point here is that replay, like requests and streams, stays inside channel boundaries.

## The `ctx.channel` API

On the server, you reach everything channel-scoped through `ctx.channel` inside a channel handler. `ctx.channel` is bound to the exact room that the call came from. So one handler works for every room it handles. For example, a handler on the dynamic `room:{roomId}` channel broadcasts to the room that the message came from, with no extra code to track which room that is.

```typescript [server/rooms.ts]
import * as v from 'valibot'
import { rooms } from './base'

const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.name // the matched name (the room name for a family)
    ctx.channel.family // the family key for a dynamic channel; absent for a static channel
    ctx.channel.members() // the connections in this channel
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    }) // only this channel's members
  },
})
```

`ctx.channel.send(event, payload)` is the other way to send: it reaches only the connection that sent the message, not the whole room.

This is the main difference from the top level: `ctx.channel.broadcast(...)` reaches only this channel's members, while the top-level `ctx.broadcast(...)` reaches every connection on the server. Both skip the sender unless you pass `{ includeSelf: true }`.

`ctx.channel` can also send server-to-client requests. For this, add the `serverRequests()` capability to the server, and declare the channel's requests with `serverRequests({...})` in the channel's `capabilities`. Then `ctx.channel` has a `request(...)` method. It asks the current member and waits for its answer. Pass `{ to }` with a member's `ConnectionRef` to ask that member instead.

::note
The client contract shows the scoped features directly. A room's entry in the contract has its own `clientRequests`, `serverRequests` and `streams`. These are the same keys as at the top level, one level deeper, under the room. So `general.request('load-history', …)` reads from _this room's_ requests, and `socket.request(...)` does not see it.
::

For the full scoped API (the server-to-client request methods, the stream kinds, and the per-channel replay config), see [Server · Scoped Streams & Requests](/server/channels/scoped-streams-requests) and [Client · channels](/client/primitives/channels).
