A WebSocket can die without telling anyone. A proxy times out an idle connection, a phone loses signal mid-session, a laptop sleeps — and both sides keep thinking the socket is fine. This is a *half-open* connection: it looks alive but nothing gets through. **Keepalive** catches it, by sending regular pings and watching for the pongs that should come back. As a bonus, those round-trips measure latency, which gives you a **quality** signal.

Unlike most reliability features, keepalive has a meaningful half on both sides.

## The problem keepalive solves

Without keepalive, a half-open socket can sit there for minutes — the user thinks they're connected, but their messages vanish into a dead pipe. Keepalive turns that silent failure into a fast, detectable one: ping regularly, and if the pongs stop coming, declare the socket dead and close it. Once it's closed, [reconnection](/learn/reliability/reconnection) can bring it back.

## Server keepalive

On the server, the `keepalive()` capability sends pings and closes connections that go silent. It takes two required timings:

```typescript [app.ts]
import { define, t } from '@wskit/server'
import { keepalive } from '@wskit/server/keepalive'

const base = define({
  env: t<Env>(),
  capabilities: [
    keepalive({
      pingIntervalMs: 30_000, // ping every 30s
      idleTimeoutMs: 60_000,  // close after 60s of total silence
    }),
  ],
})
```

- **`pingIntervalMs`** — how often the server sends a keepalive ping.
- **`idleTimeoutMs`** — how long a connection may go without sending *any* frame before the server closes it. Every inbound frame — an app message or a pong — resets this window.

`pingIntervalMs` must be comfortably less than `idleTimeoutMs`, so a healthy client's pong always lands before the idle window runs out. The ping gives even a quiet client something to respond to, keeping it alive.

## Client keepalive

On the client, the `keepalive()` primitive does the same job from the other end — pinging and watching for missed pongs — and it closes the socket when too many pongs go missing:

```typescript [app.ts]
import { client, connect, keepalive } from '@wskit/client'

const socket = client<AppSocket>()(
  connect('wss://example.com/ws'),
  keepalive({
    interval: 30_000,    // ping every 30s (0 turns it off)
    maxMissedPongs: 2,   // force-close after 2 missed pongs
  }),
)
```

After `maxMissedPongs` pongs fail to arrive, the client gives up on the socket and force-closes it — which, if you have reconnection on, kicks off a fresh connect. The defaults (30s interval, 2 missed pongs) are reasonable for most apps.

## Connection quality

Every ping/pong round-trip is a latency measurement, and keepalive turns those measurements into a simple **quality** rating you can show users — the "your connection is poor" banner:

| Quality | Latency |
|---|---|
| `excellent` | under 50ms |
| `good` | 50–150ms |
| `degraded` | 150–500ms |
| `poor` | over 500ms, or after a missed pong |
| `disconnected` | the socket isn't open |

Read it on the client, and react to changes:

```typescript [app.ts]
const q = socket.getQuality()      // current rating
const ms = socket.getLatency()     // last round-trip in ms, or null

socket.onQualityChange((quality, latency) => {
  if (quality === 'poor' || quality === 'degraded') {
    showWeakConnectionBanner()
  } else {
    hideWeakConnectionBanner()
  }
})
```

These quality methods come from the `keepalive()` primitive — without it, there are no pongs to measure, so there's nothing to report.

### Tuning the thresholds

If the default latency bands don't suit your app, the `quality()` primitive lets you set your own cut-offs, which `keepalive()` then uses when rating:

```typescript [app.ts]
import { keepalive, quality } from '@wskit/client'

const socket = client<AppSocket>()(
  connect('wss://example.com/ws'),
  keepalive(),
  quality({ thresholds: { excellent: 30, good: 100, degraded: 300 } }),
)
```

The server can also observe per-connection latency and quality from its handler context, useful for routing or logging.

## What flows between them

| Server | Client |
|---|---|
| `keepalive({ pingIntervalMs, idleTimeoutMs })` | `keepalive({ interval, maxMissedPongs })` |
| pings; closes silent connections | pings; closes after missed pongs |
| reads per-connection latency/quality | `getQuality()`, `getLatency()`, `onQualityChange()` |

Both halves do the same fundamental thing — prove the pipe is alive — from their own end. Run both for the strongest detection.
