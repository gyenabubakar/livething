When the socket is down, what happens to a `send(...)`? By default, it's dropped — there's no open pipe to put it on. For a lot of apps that's fine, but for others it's a real problem: the user types a message during a network blip and it just vanishes. The `buffering()` primitive fixes that by **queueing** sends made while offline and **flushing** them when the socket reconnects. It's a client-only feature.

## Turning it on

Buffering is off by default, so you enable it explicitly:

```typescript [app.ts]
import { client, connect, reconnection, buffering } from '@wskit/client'
import type { AppSocket } from '../server/app'

const socket = client<AppSocket>()(
  connect('wss://example.com/ws'),
  reconnection(),
  buffering({ enabled: true }),
)
```

Now a `send(...)` made while the socket is closed goes into a queue instead of being dropped. When the connection returns, the queue flushes in order. Buffering pairs naturally with [reconnection](/learn/reliability/reconnection) — reconnection gets the socket back, and buffering replays what you tried to send in the meantime.

`socket.send(...)` returns `true` when a message is buffered (as well as when it's sent live), so a `true` result means "accepted," not necessarily "on the wire right now."

## The options

```typescript [app.ts]
buffering({
  enabled: true,
  maxSize: 50,        // hold at most 50 messages; oldest dropped when full
  ttl: 30_000,        // drop a queued message after 30s
  flushInterval: 0,   // 0 = flush all at once; >0 = stagger sends
})
```

- **`enabled`** — turn buffering on. Defaults to `false`.
- **`maxSize`** — the most messages the queue holds. When it's full, the oldest is dropped to make room. Defaults to 50.
- **`ttl`** — how long a queued message may wait before it's dropped as stale. Can be one number for everything, or a per-event map so different events expire at different rates.
- **`flushInterval`** — milliseconds between each message when flushing. `0` sends the whole queue at once; a positive value paces them out, which can be gentler on the server. Defaults to 0.

### Per-message TTL

For a one-off — a message that's only worth sending if it goes out soon — you can override the TTL on the individual `send`:

```typescript [app.ts]
// this typing indicator is pointless if it sits queued for more than 2s
socket.send('typing', { userId }, { ttl: 2000 })
```

The `ttl` in `SendOptions` overrides the buffering primitive's TTL for just that message.

## How a flush behaves

Buffering is careful about ordering and about which kind of close happened:

- **On reconnect**, the queue flushes in the order things were sent, so the server sees them in sequence.
- **On an intentional close** — you called `socket.disconnect()` — the buffer is cleared. You meant to leave; queued sends would be surprising.
- **On an accidental drop**, the buffer is kept for the reconnect, because you didn't mean to leave.

This distinction matters: buffering is meant to paper over *unexpected* gaps, not to hold messages across a deliberate logout.

## When to use it

Buffering shines for user-initiated actions that shouldn't be lost to a momentary drop — sending a chat message, posting a comment, toggling a setting. It's less suited to high-frequency, only-the-latest-matters events like cursor positions, where a stale queued value is worse than nothing (a short `ttl`, or just leaving buffering off for those, handles that).

::warning
Buffered messages are still fire-and-forget. Buffering guarantees a send is *attempted* when the socket returns — not that the server processed it. If you need confirmation, use a [request](/learn/messaging/requests), which has its own in-flight handling and a `Dropped` error if a buffered request is evicted before it can go out.
::
