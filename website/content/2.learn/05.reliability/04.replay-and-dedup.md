[Buffering](/learn/reliability/buffering) handles messages *you* tried to send while offline. But what about messages the *server* sent while you were away? Those are gone from your point of view — unless the server kept them. **Replay** is the catch-up mechanism: after a reconnect, the client asks for everything it missed, and the server re-sends it. **Deduplication** is its safety net: it makes sure a message that arrives twice is only processed once.

These two work as a pair, and they involve three server capabilities plus two client primitives. It sounds like a lot, but the pieces fit together cleanly.

## How catch-up works

The idea is simple. The server stamps every outgoing message with a **sequence number** — 1, 2, 3, and so on. The client remembers the highest number it has seen. When it reconnects, it tells the server "the last one I got was #42," and the server re-sends 43, 44, 45 — exactly the gap. That's replay.

Because a reconnect can be messy, a message might occasionally get delivered twice. So each message also carries a unique ID, and **dedup** drops any ID the client has already seen. Together: replay fills the gap, dedup makes sure nothing is double-counted.

## The server side

Catch-up needs three capabilities working together:

- **`sequence()`** stamps each outgoing message with its sequence number. Use `sequence({ persist: true })` so the numbering survives a server restart.
- **`dedup()`** stamps each outgoing message with a unique ID (and drops duplicate *incoming* messages from the client).
- **`replay`** is the strategy for *what* to re-send — it remembers past messages and resends the missed ones on request.

```typescript [app.ts]
import { define, emits, t } from '@wskit/server'
import { sequence } from '@wskit/server/sequence'
import { dedup } from '@wskit/server/dedup'
import { replay } from '@wskit/server/replay'

const base = define({
  env: t<Env>(),
  capabilities: [
    emits({ 'chat-msg': t<{ text: string; from: string }>() }),
    dedup(),
    sequence({ persist: true }),
    replay.history({ retention: { maxMessages: 100 } }),
  ],
})
```

### Three replay strategies

`replay` comes in three forms, depending on how much history you keep and how:

- **`replay.history(...)`** — keep every replayable message as its own entry, up to a retention limit. On reconnect, the client gets every message it missed, in order. Good for a chat log where each message matters.
- **`replay.snapshot(...)`** — keep only the *latest* value per logical key. On reconnect, the client gets the current state of each key, not its whole history. Good for live values — a price, a status — where only the newest matters.
- **`replay.custom()`** — you own the storage and the resend. You provide hooks to store each message and to replay them, so you can back catch-up with your own database.

Each is a swap in your `capabilities` — pick the one that fits your data:

::code-group
```typescript [history.ts]
// history: every message kept, up to a retention limit
replay.history({
  retention: { maxMessages: 100 },
})
```

```typescript [snapshot.ts]
// snapshot: only the latest per document id is kept
replay.snapshot({
  snapshotKey: (event, payload) => String(payload.docId),
  retention: { maxMessages: 50 },
})
```

```typescript [custom.ts]
// custom: you own the storage and the resend
replay.custom()

base.replay({
  beforeSend(ctx, msg) {
    ctx.sql.exec(
      'INSERT INTO log (seq, event, payload) VALUES (?, ?, ?)',
      msg.wire.seq, msg.event, JSON.stringify(msg.payload),
    )
  },
  replay(ctx, since) {
    for (const row of ctx.sql.exec('SELECT * FROM log WHERE seq > ?', since).toArray()) {
      ctx.sendReplay(row.event, JSON.parse(row.payload), { seq: row.seq, messageId: row.message_id })
    }
  },
})
```
::

## The client side

On the client, two primitives mirror the server. They depend on each other, so order matters — list `dedup()` before `replay()`:

```typescript [app.ts]
import { client, connect, reconnection, dedup, replay } from '@wskit/client'

const socket = client<AppSocket>()(
  connect('wss://example.com/ws'),
  reconnection(),
  dedup(),
  replay(),
)
```

- **`replay()`** tracks the highest sequence number seen and, on reconnect, automatically asks the server for everything after it. The caught-up messages arrive through your normal `socket.on(...)` listeners — no special handling.
- **`dedup()`** watches the unique ID on each message and drops any it has already delivered, so a message replayed-then-redelivered isn't processed twice.

You don't call anything to trigger catch-up; it happens on reconnect. Your listeners just receive the missed messages as if they'd been there all along.

## How it all fits

Here's the full picture of a drop-and-recover:

1. The socket drops. The user is offline; the server keeps emitting messages, each stamped with a sequence number and an ID.
2. [Reconnection](/learn/reliability/reconnection) brings the socket back.
3. `replay()` tells the server the last sequence number it saw; the server re-sends the gap.
4. `dedup()` drops any message that slipped through twice during the messy reconnect.
5. The client's listeners have now seen every message, exactly once, in order.

Replay also respects channel boundaries — each channel catches up on its own history independently, as noted in [Scoped Features](/learn/channels/scoped-features).

## What flows between them

| Server | Client |
|---|---|
| `sequence()` stamps a seq number | `replay()` tracks the highest seen |
| `dedup()` stamps a unique ID | `dedup()` drops repeats by ID |
| `replay.history/snapshot/custom` resends the gap | catch-up arrives via `socket.on(...)` |

For the full strategy options, retention tuning, and custom-replay hooks, see the server references for [replay](/server/capabilities/replay), [sequence](/server/capabilities/sequence), and [dedup](/server/capabilities/dedup), and the client references for [replay](/client/primitives/replay) and [dedup](/client/primitives/dedup).
