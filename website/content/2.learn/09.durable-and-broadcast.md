The [plain stream](/learn/streaming) from the last page is _ephemeral_ (short-lived): if the connection drops in the middle, the stream is gone. This is the right default. Most of the time, the client can simply start a lost stream again. But there are two cases where you need more:

- **Durable streams** continue after a disconnect. A long, expensive stream does not have to start over after a short network drop.
- **Broadcast streams** send the chunks of one generator to many listeners at the same time.

Both use the same core as a plain stream: a generator on the server and a loop or callbacks on the client. They add extra behavior on top.

## Durable streams: continuing after a disconnect

For an AI answer that takes several minutes, or a large export, losing the stream on a short network drop is a real problem. A durable stream keeps enough state on the server so that, when the client reconnects, the client gets the rest of the output without starting over. There are two kinds, and they save different things:

- **Recorded** saves the **chunks** themselves in a buffer (a stored list on the server). On reconnect, the server sends the client the chunks it missed. Use it when the source runs only once and cannot be run again (for example, the tokens from an LLM, a large language model, or a feed that another service pushes to you) and every chunk must arrive.
- **Cursor** saves a **cursor**: a small marker of how far the generator got. On reconnect, the generator starts again _from that cursor_ and keeps producing. Use it when starting again from a position is cheaper or more correct than storing every chunk. For example, when you page through rows, "I was at row 40" is all you need.

Every adapter gives the server durable storage to hold this state. Each kind only needs its own capability in `server({ capabilities })`.

### Recorded

Declare it with `base.recordedStream(...)` (or, scoped to a channel, `channel.recordedStream(...)`). It looks like a plain stream: you write an `async *run` that yields chunks. The difference is that LiveThing stores each chunk so it can send it again after a reconnect.

Huddle's `ask-scout` is a recorded stream, declared inside the `rooms` channel (channel-scoped streams work the same way, see [Scoped Features](/learn/scoped-features)): a member asks Scout something, the reply can run for a while, and a short drop must not lose any of it. This example also adds its `nudges`, `stop` and `redirect`, because a running AI reply is exactly the case where you cannot just start the stream again: `redirect` keeps the reply so far and continues it with a new instruction, and `stop` ends it early. Neither pauses or speeds up the model. That is not something you can do to a reply that is already streaming out of it.

::code-group

```typescript [server: scout.ts]
import { server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { recordedStream } from '@livething/server/streams'
import * as v from 'valibot'

const base = server({
  capabilities: [channels(), recordedStream()],
})

const rooms = base.channel(['rooms', 'room:{roomId}'] as const, {
  capabilities: [],
})

export const handleAskScout = rooms.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ text: string }>(),
  broadcast: true, // every member of the room sees the reply
  maxChunks: 500,
  nudges: {
    stop: null,
    redirect: v.object({ instruction: v.string() }),
  },
  async *run(ctx, input) {
    let messages: unknown[] = [
      { role: 'user', content: input.prompt },
    ]

    while (true) {
      const modelCall = new AbortController()
      let replySoFar = ''
      let redirectedTo: string | null = null

      for await (const piece of llm.stream({
        messages,
        signal: modelCall.signal,
      })) {
        replySoFar += piece
        const recent = ctx.stream.nudges(yield { text: piece })

        if (recent.some((n) => n.event === 'stop')) {
          modelCall.abort() // ends the model call; the stream ends right after
          return
        }
        const redirect = recent.find((n) => n.event === 'redirect')
        if (redirect) {
          modelCall.abort() // ends this model call; a new one starts below
          redirectedTo = redirect.payload.instruction
          break
        }
      }

      if (!redirectedTo) return // the model finished on its own

      messages = [
        ...messages,
        { role: 'assistant', content: replySoFar },
        { role: 'user', content: redirectedTo },
      ]
    }
  },
})
```

```typescript [client: scout.ts]
// Use it the same way as a plain stream. Continue happens automatically.
const general = socket.channel('rooms', 'room:general')
await general.subscribe()

const reply = await general.stream('ask-scout', {
  prompt: 'summarize the last hour of this room',
})

for await (const chunk of reply) {
  // chunks keep arriving after a reconnect, and the loop does not end
  render(chunk.text)
}

// while the reply is running, the asker can steer it:
await reply.nudge('redirect', {
  instruction: 'shorter, just the decisions',
})
await reply.nudge('stop')
```

::

`llm.stream({ messages, signal })` is Huddle's one call to the model: it sends the conversation so far and yields text pieces as they arrive, and stops early when `signal` aborts. Each turn through the `while` loop is one call to the model. A plain finish returns. A `redirect` nudge aborts the current call, adds what Scout said so far plus the new instruction to `messages`, and starts the next call at the top of the loop. `maxChunks` sets the largest number of chunks the buffer holds across every call in the loop. If the generator yields more than that, the stream stops with a `StreamAborted` error with reason `'buffer-full'` ([Server · Recorded](/server/streams/durable-recorded) shows how to catch it).

### Cursor

Declare it with `base.cursorStream(...)`. Here your code takes part in the reconnect. Yield each chunk _together with a cursor_ using `ctx.stream.withCursor(chunk, cursor)`. When a reconnect happens, read `ctx.stream.cursor` to know where to start again. On a fresh start, the cursor is `null`. After a reconnect, it holds the cursor of the last chunk the client confirmed it received.

Huddle uses this for `export-room`: an admin exports a room's full message history, which can be a lot of rows. Storing every page as a recorded chunk would be wasteful, since the rows themselves already live in the `messages` table. Instead, the cursor is simply "how far back have we paged", so a reconnect just pages again from there.

::code-group

```typescript [server: jobs.ts]
import { server, t } from '@livething/server'
import { cursorStream } from '@livething/server/streams'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'

const base = server({
  capabilities: [cursorStream()],
})

export const handleExportRoom = base.cursorStream('export-room', {
  input: v.object({ roomId: v.string() }),
  chunk: t<{ messages: Message[] }>(),
  cursor: t<{ before: number }>(),
  async *run(ctx, input) {
    // null on a fresh start; the last confirmed cursor on a reconnect
    let before = ctx.stream.cursor?.before ?? Date.now()
    while (true) {
      const page = await loadMessages(input.roomId, before)
      if (page.length === 0) return
      // yield the chunk and its cursor together
      yield ctx.stream.withCursor(
        { messages: page },
        { before: page.at(-1)!.sentAt },
      )
      before = page.at(-1)!.sentAt
    }
  },
})

export const huddle = base.assemble({
  handlers: [handleExportRoom],
})

export type HuddleSocket = InferClient<typeof huddle>
```

```typescript [client: socket.ts]
const pages = await socket.stream('export-room', {
  roomId: 'general',
})

for await (const chunk of pages) {
  render(chunk.messages)
}
```

::

### Auto-continue on the client

On the client, **continue is automatic.** You start a durable stream the same way as a plain one and read it with `for await`. If the socket drops and reconnects, the stream attaches again and keeps sending chunks into the _same loop_. You write no reconnect code. For this to work, the client needs the [`reconnection()`](/learn/reliability) primitive, so that a drop actually leads to a new connection. Also add the `keepalive()` primitive. Sometimes a connection stops working without a close message. Keepalive sends small check messages (pings), so the client can notice this and reconnect.

The contract marks the **kind** of each stream: `'ephemeral'` for plain streams, and `'persistent'` for both durable kinds. The client does not need to know if the server stored chunks or saved a cursor. The client types use `kind` for one thing: to allow the manual `continueStream(...)` method only on durable streams. You call this method for a _cold_ continue, for example after a page reload, when the old loop no longer exists. If you try to continue a plain stream, TypeScript shows a compile error.

| Server                                  | Client                                                           |
| --------------------------------------- | ---------------------------------------------------------------- |
| `base.recordedStream(...)`              | `socket.stream(...)`: sends the missed chunks again on reconnect |
| `base.cursorStream(...)` + `withCursor` | `socket.stream(...)`: continues from the cursor on reconnect     |
| (either durable builder)                | `reconnection()` primitive (makes the client reconnect)          |

Choose **recorded** when every chunk must arrive and storing the chunks is cheap. Choose **cursor** when starting the generator again from a saved position is the simpler way to continue. More detail: [Server · Cursor](/server/streams/durable-cursor), [Server · Recorded](/server/streams/durable-recorded), and [Client · durable continue](/client/streams/durable-and-continue).

## Broadcast streams: one feed, many listeners

Every stream so far has been one-to-one: one client starts it, and the same client reads it. A **broadcast stream** is one-to-many. The server runs a single generator and sends each chunk to _every_ listener at once. Use it for a shared live feed: a sports score ticker, a feed of cursors in a shared document, or a progress bar that a whole room watches together. Huddle uses it for `ask-scout`, from earlier on this page: when one member asks Scout something, every other member of the room sees the reply arrive too, not only the one who asked.

Declare it like any stream, with one extra option: `broadcast: true`. The client that starts the stream reads it with `socket.stream(...)` (or, scoped to a channel, `channel.stream(...)`) as usual. The other clients did not start it; they only listen to a shared feed. So they use a different method: `socket.onStream(name, handlers)` (or `channel.onStream(...)`). It is a listen-only subscription that calls your functions (callbacks) when something arrives.

`ask-scout`, declared earlier on this page, already has `broadcast: true`, so the server side needs no new code. Only the client side is new, for a member who wants to watch without asking:

```typescript [client: scout.ts]
// A teammate who did not ask still sees Scout's reply arrive, live.
const general = socket.channel('rooms', 'room:general')
await general.subscribe()

const stop = general.onStream('ask-scout', {
  onChunk(chunk, streamId) {
    renderScoutReply(streamId, chunk.text) // chunk: { text: string }
  },
  onEnd() {
    markScoutReplyComplete()
  },
  onError(error) {
    showError(error) // a stream error reaches every listener
  },
})

// later, to stop listening:
stop()
```

`onStream(...)` returns a function that stops the subscription. It runs for every stream with that event name, so if several members ask Scout at once, the `streamId` tells the replies apart. The differences from a regular stream:

|                        | Regular stream                     | Broadcast stream                               |
| ---------------------- | ---------------------------------- | ---------------------------------------------- |
| Client API             | `socket.stream(...)` + `for await` | `socket.onStream(...)` + callbacks             |
| Who reads it           | the client that started it         | the client that started it, and every listener |
| Generators running     | one per client                     | one, shared                                    |
| Continues after a drop | yes, if durable                    | listen-only; a listener does not continue it   |

You control a regular stream yourself. A broadcast is a shared feed that others can listen to. Broadcasts work well with [channels](/learn/channels): when you declare a broadcast stream inside a channel, it becomes a feed for that one room and reaches only its members. More detail: [Server · Broadcast](/server/streams/broadcast) and [Client · onStream](/client/streams/broadcast-onstream).
