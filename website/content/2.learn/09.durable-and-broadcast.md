The [plain stream](/learn/streaming) from the last page is _ephemeral_ (short-lived): if the connection drops in the middle, the stream is gone. This is the right default. Most of the time, the client can simply start a lost stream again. But there are two cases where you need more:

- **Durable streams** continue after a disconnect. A long, expensive stream continues from where it stopped after a short network drop.
- **Broadcast streams** send the chunks of one generator to many listeners at the same time.

Both use the same core as a plain stream: a generator on the server and a loop or callbacks on the client. They add extra behavior on top.

## Durable streams: continuing after a disconnect

For an AI answer that takes several minutes, or a large export, losing the stream on a short network drop is a real problem. A durable stream keeps enough state on the server so that, when the client reconnects, the stream continues from where it stopped. There are two kinds, and they save different things:

- **Recorded** saves the **chunks** themselves in a buffer (a stored list on the server). On reconnect, the server sends the client the chunks it missed. Use it when the source runs only once and cannot be run again (for example, the tokens from an LLM, a large language model, or a feed that another service pushes to you) and every chunk must arrive.
- **Resumable** saves a **cursor**: a small marker of how far the generator got. On reconnect, the generator starts again _from that cursor_ and keeps producing. Use it when starting again from a position is cheaper or more correct than storing every chunk. For example, when you page through rows, "I was at row 40" is all you need.

Every adapter gives the server durable storage to hold this state. Each kind only needs its own capability in `server({ capabilities })`.

### Recorded

Declare it with `base.recordedStream(...)`. It looks like a plain stream: you write an `async *run` that yields chunks. The difference is that LiveThing stores each chunk so it can send it again after a reconnect. `maxChunks` sets the largest number of chunks the buffer holds. If the generator yields more than that, the stream stops with a `StreamAborted` error with reason `'buffer-full'` ([Server · Recorded](/server/streams/durable-recorded) shows how to catch it).

::code-group

```typescript [server: ai.ts]
import { server, t } from '@livething/server'
import { recordedStream } from '@livething/server/streams'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'

const base = server({
  capabilities: [recordedStream()],
})

export const handleAiReply = base.recordedStream('ai-reply', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ token: string }>(),
  maxChunks: 1000,
  async *run(_ctx, input) {
    for (const word of input.prompt.split(' ')) {
      yield { token: word + ' ' } // LiveThing stores each chunk for you
    }
  },
})

export const definition = base.assemble({
  handlers: [handleAiReply],
})

export type AiSocket = InferClient<typeof definition>
```

```typescript [client: app.ts]
// Use it the same way as a plain stream. Resume happens automatically.
const reply = await socket.stream('ai-reply', {
  prompt: 'Explain WebSockets',
})

for await (const chunk of reply) {
  // chunks keep arriving after a reconnect, and the loop does not end
  render(chunk.token)
}
```

::

### Resumable

Declare it with `base.resumableStream(...)`. Here your code takes part in the resume. Yield each chunk _together with a cursor_ using `ctx.stream.withCursor(chunk, cursor)`. When a resume happens, read `ctx.stream.cursor` to know where to start again. On a fresh start, the cursor is `null`. After a reconnect, it holds the cursor of the last chunk the client confirmed it received.

::code-group

```typescript [server: export.ts]
import { server, t } from '@livething/server'
import { resumableStream } from '@livething/server/streams'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'

const base = server({
  capabilities: [resumableStream()],
})

export const handleExportRows = base.resumableStream('export-rows', {
  input: v.object({}),
  chunk: t<{ row: number }>(),
  cursor: t<{ idx: number }>(),
  async *run(ctx) {
    // null on a fresh start; the last confirmed cursor on a resume
    const startAt = ctx.stream.cursor?.idx ?? 0
    for (let i = startAt + 1; i <= 100; i += 1) {
      // yield the chunk and its cursor together
      yield ctx.stream.withCursor({ row: i }, { idx: i })
    }
  },
})

export const definition = base.assemble({
  handlers: [handleExportRows],
})

export type ExportSocket = InferClient<typeof definition>
```

```typescript [client: app.ts]
const rows = await socket.stream('export-rows', {})

for await (const chunk of rows) {
  render(chunk.row)
}
```

::

### Auto-resume on the client

On the client, **resume is automatic.** You start a durable stream the same way as a plain one and read it with `for await`. If the socket drops and reconnects, the stream attaches again and keeps sending chunks into the _same loop_. You write no reconnect code. For this to work, the client needs the [`reconnection()`](/learn/reliability) primitive, so that a drop actually leads to a new connection. Also add the `keepalive()` primitive. Sometimes a connection stops working without a close message. Keepalive sends small check messages (pings), so the client can notice this and reconnect.

The contract marks the **kind** of each stream: `'ephemeral'` for plain streams, and `'persistent'` for both durable kinds. The client does not need to know if the server stored chunks or saved a cursor. The client types use `kind` for one thing: to allow the manual `resumeStream(...)` method only on durable streams. You call this method for a _cold_ resume, for example after a page reload, when the old loop no longer exists. If you try to resume a plain stream, TypeScript shows a compile error.

| Server                                     | Client                                                           |
| ------------------------------------------ | ---------------------------------------------------------------- |
| `base.recordedStream(...)`                 | `socket.stream(...)`: sends the missed chunks again on reconnect |
| `base.resumableStream(...)` + `withCursor` | `socket.stream(...)`: continues from the cursor on reconnect     |
| (either durable builder)                   | `reconnection()` primitive (makes the client reconnect)          |

Choose **recorded** when every chunk must arrive and storing the chunks is cheap. Choose **resumable** when starting the generator again from a saved position is the simpler way to continue. More detail: [Server · Resumable](/server/streams/durable-resumable), [Server · Recorded](/server/streams/durable-recorded), and [Client · durable resume](/client/streams/durable-and-resume).

## Broadcast streams: one feed, many listeners

Every stream so far has been one-to-one: one client starts it, and the same client reads it. A **broadcast stream** is one-to-many. The server runs a single generator and sends each chunk to _every_ listener at once. Use it for a shared live feed: a sports score ticker, a feed of cursors in a shared document, or a progress bar that a whole room watches together.

Declare it like any stream, with one extra option: `broadcast: true`. The client that starts the stream reads it with `socket.stream(...)` as usual. The other clients did not start it; they only listen to a shared feed. So they use a different method: `socket.onStream(name, handlers)`. It is a listen-only subscription that calls your functions (callbacks) when something arrives.

::code-group

```typescript [server: feed.ts]
import { server, t } from '@livething/server'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'

const base = server({
  capabilities: [stream()],
})

export const handleTicker = base.stream('live-ticker', {
  input: v.object({ count: v.number() }),
  chunk: t<{ index: number }>(),
  broadcast: true, // one generator, sent to every listener
  async *run(_ctx, input) {
    for (let i = 0; i < input.count; i += 1) {
      yield { index: i }
      await new Promise((resolve) => setTimeout(resolve, 1000))
    }
  },
})

export const definition = base.assemble({ handlers: [handleTicker] })

export type FeedSocket = InferClient<typeof definition>
```

```typescript [client: app.ts]
import { client, connect, stream } from '@livething/client'
import type { FeedSocket } from '../server/feed'

const socket = client<FeedSocket>()(
  connect('wss://example.com/ws'),
  stream(),
)
socket.connect()

const stop = socket.onStream('live-ticker', {
  onChunk(chunk, streamId) {
    renderTick(streamId, chunk.index) // chunk: { index: number }
  },
  onEnd() {
    markComplete()
  },
  onError(error) {
    showError(error) // a stream error reaches every listener
  },
})

// later, to stop listening:
stop()
```

::

`onStream(...)` returns a function that stops the subscription. It runs for every stream with that event name, so if several broadcasts of the same event run at once, the `streamId` tells them apart. The differences from a regular stream:

|                    | Regular stream                     | Broadcast stream                               |
| ------------------ | ---------------------------------- | ---------------------------------------------- |
| Client API         | `socket.stream(...)` + `for await` | `socket.onStream(...)` + callbacks             |
| Who reads it       | the client that started it         | the client that started it, and every listener |
| Generators running | one per client                     | one, shared                                    |
| Resume             | yes, if durable                    | listen-only; a listener does not resume it     |

You control a regular stream yourself. A broadcast is a shared feed that others can listen to. Broadcasts work well with [channels](/learn/channels): when you declare a broadcast stream inside a channel, it becomes a feed for that one room and reaches only its members. More detail: [Server · Broadcast](/server/streams/broadcast) and [Client · onStream](/client/streams/broadcast-onstream).
