The [plain stream](/learn/streaming) from the last page is _ephemeral_: drop the connection mid-stream and it's gone. That's the right default — most of the time a lost stream just gets re-requested. But two things change that picture. **Durable streams** survive a disconnect, so a long, expensive stream picks up after a network blip. **Broadcast streams** send one generator's output to many listeners at once. Both keep the same generator-and-loop core; they're behaviours layered on top.

## Durable streams — surviving a disconnect

For a multi-minute AI generation or a large export, losing the stream on a network blip is painful. A durable stream keeps enough state on the server that when the client reconnects, the stream picks up where it left off. There are two flavours, and they differ in _what_ gets saved:

- **Recorded** saves the **chunks** themselves in a buffer. On reconnect the client is replayed the chunks it missed. Reach for it when the source is one-shot and can't be re-run — LLM tokens, a push feed — and every chunk must land.
- **Resumable** saves a **cursor**, a small marker of how far the generator got. On reconnect the generator restarts _from that cursor_ and keeps producing. Reach for it when re-running from a position is cheaper or more correct than buffering everything — like paginating rows, where "I was at row 40" is all you need.

Every adapter gives the server durable storage to hold this state, so neither flavour needs anything extra beyond its own builder capability.

### Recorded

Declare with `base.recordedStream(...)`. It looks just like a plain stream — you write an `async *run` that yields chunks — but the framework buffers each one to replay after a reconnect. `maxChunks` caps the buffer.

::code-group

```typescript [server: tokens.ts]
import { server, t } from '@wskit/server'
import { recordedStream } from '@wskit/server/streams'
import * as v from 'valibot'

const base = server({
  capabilities: [recordedStream()],
})

export const handleTokens = base.recordedStream('count-tokens', {
  input: v.object({}),
  chunk: t<{ idx: number }>(),
  maxChunks: 100,
  async *run() {
    for (let i = 1; i <= 50; i += 1) {
      yield { idx: i } // buffered for you — durability is automatic
    }
  },
})

export const definition = base.assemble({
  handlers: [handleTokens],
})
```

```typescript [client: app.ts]
// Consume it exactly like a plain stream — resume is automatic.
const tokens = await socket.stream('count-tokens', {})

for await (const chunk of tokens) {
  // chunks keep arriving across a reconnect — the loop doesn't break
  render(chunk.idx)
}
```

::

### Resumable

Declare with `base.resumableStream(...)`. Here you take part in the resume: yield each chunk _together with a cursor_ via `ctx.stream.withCursor(chunk, cursor)`, and when a resume happens, read `ctx.stream.cursor` to know where to restart. On a fresh start the cursor is `null`; after a reconnect it holds what you last saved.

::code-group

```typescript [server: paginate.ts]
import { server, t } from '@wskit/server'
import { resumableStream } from '@wskit/server/streams'
import * as v from 'valibot'

const base = server({
  capabilities: [resumableStream()],
})

export const handlePaginate = base.resumableStream('paginate', {
  input: v.object({}),
  chunk: t<{ row: number }>(),
  cursor: t<{ idx: number }>(),
  async *run(ctx) {
    // null on a fresh start; the last saved cursor on a resume
    const startAt = ctx.stream.cursor?.idx ?? 0
    for (let i = startAt + 1; i <= 100; i += 1) {
      // yield the chunk AND the cursor to save alongside it
      yield ctx.stream.withCursor({ row: i }, { idx: i })
    }
  },
})

export const definition = base.assemble({
  handlers: [handlePaginate],
})
```

```typescript [client: app.ts]
const rows = await socket.stream('paginate', {})

for await (const chunk of rows) {
  render(chunk.row)
}
```

::

### Auto-resume on the client

The client side is the best part: **resume is automatic.** You start a durable stream exactly like a plain one and iterate it with `for await`. If the socket drops and reconnects, the stream re-attaches itself and keeps delivering chunks into the _same loop_ — you write no reconnect handling. For this to work, the client needs the [`reconnection()`](/learn/reliability) primitive on, so a drop actually reconnects.

The contract marks each stream's **kind** — `'ephemeral'` for plain, `'persistent'` for both durable flavours. The client doesn't care whether the server recorded chunks or saved a cursor; it only reads `kind` to gate the manual `resumeStream(...)` method (for a _cold_ resume after a page reload). Try to resume a plain stream and the compiler stops you.

| Server                                     | Client                                                         |
| ------------------------------------------ | -------------------------------------------------------------- |
| `base.recordedStream(...)`                 | `socket.stream(...)` — auto-replays missed chunks on reconnect |
| `base.resumableStream(...)` + `withCursor` | `socket.stream(...)` — auto-resumes from cursor on reconnect   |
| (either durable builder)                   | `reconnection()` primitive (triggers the reconnect)            |

Pick **recorded** when every chunk must be delivered and buffering is cheap; pick **resumable** when restarting the generator from a saved position is the cleaner way to continue. Full detail: [Server · Resumable](/server/streams/durable-resumable), [Server · Recorded](/server/streams/durable-recorded), and [Client · durable resume](/client/streams/durable-and-resume).

## Broadcast streams — one feed, many listeners

Every stream so far has been one-to-one: a client starts it, that client consumes it. A **broadcast stream** is one-to-many — the server runs a single generator and fans its chunks out to _every_ listener at once. This is the shape for a shared live feed: a sports ticker, a collaborative cursor feed, a "server is processing" bar the whole room watches together.

Declare it like any stream with one extra flag, `broadcast: true`. Because the feed isn't _yours_ — you're tuning into something shared — the client consumes it differently: not `socket.stream(...)` and a loop, but `socket.onStream(name, handlers)`, a listen-only, callback-based subscription.

::code-group

```typescript [server: feed.ts]
import { server, t } from '@wskit/server'
import { stream } from '@wskit/server/streams'
import * as v from 'valibot'

const base = server({
  capabilities: [stream()],
})

export const handleFeed = base.stream('start-broadcast', {
  input: v.object({ count: v.number() }),
  chunk: t<{ index: number }>(),
  broadcast: true, // one generator, fanned out to every listener
  async *run(_ctx, input) {
    for (let i = 0; i < input.count; i += 1) {
      yield { index: i }
      await new Promise((r) => setTimeout(r, 1000))
    }
  },
})

export const definition = base.assemble({ handlers: [handleFeed] })
```

```typescript [client: app.ts]
import { client, connect, stream } from '@wskit/client'
import type { FeedSocket } from '../server/feed'

const socket = client<FeedSocket>()(
  connect('wss://example.com/ws'),
  stream(),
)
socket.connect()

const stop = socket.onStream('start-broadcast', {
  onChunk(chunk, streamId) {
    render(chunk.index) // chunk: { index: number }
  },
  onEnd(streamId, finalSeq) {
    markComplete()
  },
  onError(error, streamId) {
    showError(error) // a terminal error reaches every listener
  },
})

// later, to stop listening:
stop()
```

::

`onStream(...)` returns an unsubscribe function and fires for every stream matching the event name, so the `streamId` tells apart multiple broadcasts of the same event. The contrast with a regular stream is worth being precise about:

|                    | Regular stream                     | Broadcast stream                            |
| ------------------ | ---------------------------------- | ------------------------------------------- |
| Client API         | `socket.stream(...)` + `for await` | `socket.onStream(...)` + callbacks          |
| Who consumes       | the client that started it         | every listener                              |
| Generators running | one per client                     | one, shared                                 |
| Resume             | yes, if durable                    | listen-only; a subscriber doesn't resume it |

A regular stream is a private activity you drive; a broadcast is a public feed you tune into. Broadcasts pair naturally with [channels](/learn/channels) — declared inside a channel, a broadcast stream is a feed for one room, reaching exactly its members. Full detail: [Server · Broadcast](/server/streams/broadcast) and [Client · onStream](/client/streams/broadcast-onstream).
