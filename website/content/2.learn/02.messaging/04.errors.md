When something goes wrong, the client shouldn't have to parse error strings or guess at codes. WSKit gives errors the same treatment as everything else: you define them once, and they cross the wire **typed**, so the client can catch a specific error and read its details with full type safety. There's also a small family of *control-flow* errors that don't go to the client at all — they steer the connection itself.

## Typed errors, end to end

A typed error has a stable string **code** and an optional **detail** payload. You build one with the `error(...)` factory.

### Define an error

`error(code)` makes a code-only error; `error(code, schema)` adds a typed detail payload. These usually live in a shared file so both halves of your app can import them:

```typescript [errors.ts]
import { error } from '@wskit/server/errors'
import * as v from 'valibot'

export const NotFound = error('not-found', v.object({ id: v.string() }))
export const Forbidden = error('forbidden', v.object({ reason: v.string() }))
```

`error(...)` returns a callable factory. Call it to build the actual error: `NotFound({ id: '123' })`.

### Register and throw

To send a typed error to the client, list it in the `errors()` capability so it becomes part of the contract. Then `throw` it from any handler:

```typescript [api.ts]
import { define, errors, t } from '@wskit/server'
import type { InferClient } from '@wskit/server'
import { NotFound, Forbidden } from './errors'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [errors([NotFound, Forbidden])],
})

export const handleGetPost = base.request('get-post', {
  input: v.object({ id: v.string() }),
  run(ctx, input) {
    const post = lookup(input.id)
    if (!post) throw NotFound({ id: input.id })
    if (!post.public) throw Forbidden({ reason: 'private post' })
    return post
  },
})

export const handler = base.assemble(handleGetPost)
export type ApiSocket = InferClient<typeof handler>
```

When you throw a registered error during a request, the client's `request(...)` Promise rejects with that error — carried across the wire with its code and detail intact. As always, the handler only counts once it's passed to `base.assemble(...)`; that, plus the `errors()` capability, is what carries these error types into the client contract.

In the client contract, the registered errors land under the `errors` key — code mapped to its detail shape:

```typescript [api-socket.ts]
interface ApiSocket {
  errors: {
    'not-found': { id: string }
    forbidden: { reason: string }
  }
}
```

That's the slice `.matches()` reads from: because `forbidden` maps to `{ reason: string }`, `err.detail` is typed as `{ reason: string }` inside the `Forbidden.matches(err)` branch below.

### Catch and narrow on the client

On the client, you import the same error definitions and use `.matches(err)` to narrow. Inside the matched branch, `err.detail` is fully typed:

```typescript [app.ts]
import { NotFound, Forbidden } from '../server/errors'

try {
  const post = await socket.request('get-post', { id })
} catch (err) {
  if (NotFound.matches(err)) {
    console.log('no post with id', err.detail.id) // detail typed as { id: string }
  } else if (Forbidden.matches(err)) {
    console.log('blocked:', err.detail.reason)
  }
}
```

`.matches()` is a type guard, so TypeScript knows which error you're in and types `detail` accordingly. No string comparison, no casting.

## Built-in client errors

A few errors come from the client itself, not your server. They live in `@wskit/client/errors` and you match them exactly the same way:

| Error | When it happens |
|---|---|
| `Timeout` | A `request(...)` didn't get a reply in time |
| `Disconnected` | The socket dropped while a request was waiting |
| `Dropped` | A buffered request was evicted before it could be sent |

```typescript [app.ts]
import { Timeout, Disconnected } from '@wskit/client/errors'

try {
  await socket.request('slow-thing', {})
} catch (err) {
  if (Timeout.matches(err)) retry()
  else if (Disconnected.matches(err)) waitForReconnect()
}
```

## Control-flow errors

Some "errors" aren't about reporting a failure to the client — they're a way to tell the engine what to do with the connection. You throw them on the server, and they steer behavior instead of becoming a client-facing error. They come from `@wskit/server/errors`:

| Throw | Effect |
|---|---|
| `Block` | Silently drop the current message. Nothing goes to the client. |
| `Disconnect(code, reason)` | Close this connection now, with that WebSocket close code. |
| `Defer(delayMs)` | Re-queue this message to retry after a delay (a few attempts, then it gives up). |
| `RejectUpgrade(code, reason)` | Reject the connection during the upgrade handshake. Only valid in the `upgrade` hook. |

```typescript [api.ts]
import { Disconnect, Block } from '@wskit/server/errors'
import { CloseCodes } from '@wskit/core'

export const handleAction = base.on('action', {
  input: v.object({ kind: v.string() }),
  run(ctx, input) {
    if (isSpam(input)) throw Block                              // drop quietly
    if (tooManyViolations(ctx)) throw Disconnect(CloseCodes.BANNED, 'banned')
  },
})
```

`Block` is `throw Block` (no call — it's a constant). The others are functions you call with their arguments.

::note
`Disconnect` and `RejectUpgrade` take a WebSocket close code. `@wskit/core` exports named ones — `CloseCodes.BANNED`, `CloseCodes.AUTH_INVALID`, `CloseCodes.RATE_LIMITED`, and more — so you don't memorize numbers.
::

## Where each error goes

It helps to keep the routing straight:

- A **registered typed error** thrown during a request → rejects that request's Promise on the client.
- A **registered typed error** thrown outside a request → surfaces on the client's `onError` callback.
- A **control-flow error** (`Block`, `Disconnect`, `Defer`) → handled by the engine; never sent to the client.
- A **validation failure** → its own path, covered in [Validation](/learn/messaging/validation).

For the complete list of built-in errors and the routing rules in full, see the [Server errors reference](/server/capabilities/errors) and the [Client errors reference](/client/errors/overview).
