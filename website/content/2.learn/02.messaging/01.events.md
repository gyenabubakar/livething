Events are the simplest thing two sides can do over a socket: one side sends a named message with a payload, the other side listens for it. Nobody waits for a reply — you send and move on. This is *fire-and-forget*, and it's the right tool for most traffic: notifications, updates, broadcasts, anything where you don't need an answer back.

Events flow in both directions, and the two directions are set up a little differently. Let's take each.

## Server to client

For the server to send an event to clients, you first **declare** the event with the `emits()` capability, then **send** it from a handler.

### Declare what you emit

`emits({...})` lists the events the server can send, each with a type marker describing its payload. It comes straight from `@wskit/server`:

```typescript [chat.ts]
import { define, emits, t } from '@wskit/server'
import type { InferClient } from '@wskit/server'

const base = define({
  env: t<Env>(),
  capabilities: [
    emits({
      message: t<{ text: string; from: string }>(),
      'user-joined': t<{ username: string }>(),
    }),
  ],
})
```

The `t<Shape>()` marker is a type-only declaration — there's no runtime schema here, because the server is the one producing these payloads, so it's trusted to send the right shape. Declaring an event is what lets the contract carry it to the client as an `incoming` event.

### Send it

Inside any handler, two methods send a declared event:

- **`ctx.send(event, payload)`** — sends to the current connection only. Returns `true` if the message was accepted (sent or buffered), `false` if it was dropped.
- **`ctx.broadcast(event, payload, options?)`** — sends to every live connection. By default it excludes the connection that triggered the handler; pass `{ excludeSelf: false }` to include it.

```typescript [chat.ts]
export const handleSendMessage = base.on('send-message', {
  input: v.object({ text: v.string(), from: v.string() }),
  run(ctx, input) {
    // to everyone else
    ctx.broadcast('message', { text: input.text, from: input.from })
    // or just back to the sender
    ctx.send('message', { text: input.text, from: input.from })
  },
})

export const handler = base.assemble(handleSendMessage)
export type ChatSocket = InferClient<typeof handler>
```

Both methods are typed against your `emits()` declaration — a wrong event name or payload shape is a compile error.

Handlers are just exported values until you pass them to `base.assemble(...)`. Only assembled handlers become part of the server — and only they appear in the client type `InferClient` builds. Add a handler but forget to assemble it, and the client simply won't see it. (More on this in [The Contract](/learn/core-model/the-contract).)

## Client to server

The other direction works the same way in reverse. On the client, you **listen** for the events the server emits, and you **send** events the server handles.

### Listen

`socket.on(event, handler)` registers a listener. The `data` your handler receives is fully typed — straight from the server's `emits()`. It returns an unsubscribe function:

```typescript [app.ts]
const stop = socket.on('message', (data) => {
  // data: { text: string; from: string }
  console.log(`${data.from}: ${data.text}`)
})

// later, to stop listening:
stop()
```

### Send

`socket.send(event, payload)` sends an event the server has a handler for. It's typed against the server's handler `input`, and returns `true` if the message was sent or buffered, `false` if dropped:

```typescript [app.ts]
socket.send('send-message', { text: 'hello', from: 'gyen' })
```

::note
`send()` returning `true` means "accepted" — sent now, or queued if you've turned on [buffering](/learn/reliability/buffering). It does **not** mean the server received and processed it. If you need that confirmation, you want a [request](/learn/messaging/requests), not an event.
::

## What flows between them

Putting both halves together, the contract mirrors and the names flip:

| Server | Client |
|---|---|
| `emits({ message })` | `socket.on('message', ...)` |
| `base.on('send-message', ...)` | `socket.send('send-message', ...)` |

The server emits `message`, so the client listens for it. The server handles `send-message`, so the client sends it. You declared each event once; the compiler wired up the matching method on the other side.

In the client contract, those two directions are the `incoming` and `outgoing` keys — this is the slice of `ChatSocket` that events produce:

```typescript [chat-socket.ts]
interface ChatSocket {
  // what the server emits → you listen with on()
  incoming: {
    message: { text: string; from: string }
    'user-joined': { username: string }
  }
  // what the server handles → you send with send()
  outgoing: {
    'send-message': { text: string; from: string }
  }
}
```
