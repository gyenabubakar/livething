A regular [request](/learn/messaging/requests) goes client to server: the client asks, the server answers. A **server request** is the same idea pointed the other way — the *server* asks the *client* a question and waits for its reply. It's how a server gets a decision or a value that only the client has.

A good example: the server is about to do something sensitive and wants the user's confirmation. It asks the client "is this allowed?", the client answers `true` or `false`, and the server acts on the reply.

::note
From the **client's** point of view, this question arrives *inbound* — it's something the client receives and responds to, not something it initiates. Keep that direction in mind: on the client, a server request is a question you answer, not one you ask.
::

## Server: declare and ask

Server requests are declared inside the same `requests({...})` capability, but with a different slot shape that marks the direction.

### Declare the question

A server-to-client request slot has two parts: `out`, the payload the server sends (a type marker, since the server is trusted to produce it), and `in`, a schema validating the client's answer:

```typescript [api.ts]
import { define, t } from '@wskit/server'
import type { InferClient } from '@wskit/server'
import { requests } from '@wskit/server/requests'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [
    requests({
      'ask-permission': {
        out: t<{ action: string }>(),         // server → client payload
        in: v.object({ allowed: v.boolean() }), // validates the client's reply
      },
      'ping-ack': t<{ note: string }>(), // acknowledgement-only, no `in`
    }),
  ],
})
```

A slot with both `out` and `in` is a full question-and-answer. A slot that's just a type marker (`ping-ack` above) is acknowledgement-only — the server learns the client received it, with no data coming back.

### Ask the client

Inside a handler, `ctx.request(name, payload, options?)` sends the question to the current connection and returns a Promise of the client's validated answer:

```typescript [api.ts]
export const handleTrigger = base.on('trigger', {
  input: v.object({ action: v.string() }),
  async run(ctx, input) {
    try {
      const answer = await ctx.request('ask-permission', { action: input.action })
      // answer: { allowed: boolean } — validated against the `in` schema
      if (answer.allowed) doTheThing(input.action)
    } catch (error) {
      // the client never answered, or its reply failed validation, or it timed out
    }
  },
})

export const handler = base.assemble(handleTrigger)
export type ApiSocket = InferClient<typeof handler>
```

Pass `handleTrigger` to `base.assemble(...)` like any handler — that's what puts this exchange into the contract `ApiSocket` is inferred from.

Like a client request, it has a timeout (override it with `{ timeout: 500 }` as the third argument), and it rejects if the client doesn't answer in time.

## Client: receive and reply

On the client, add the `serverRequest()` primitive. It gives the socket an `onRequest(name, handler)` method. Your handler receives the server's payload, and **whatever it returns is sent back as the answer**:

```typescript [app.ts]
import { client, connect, serverRequest } from '@wskit/client'
import type { ApiSocket } from '../server/api'

const socket = client<ApiSocket>()(
  connect('wss://example.com/ws'),
  serverRequest(),
)
socket.connect()

socket.onRequest('ask-permission', (payload) => {
  // payload: { action: string } — what the server asked
  const allowed = window.confirm(`Allow ${payload.action}?`)
  return { allowed } // sent back to the server as the reply
})
```

The handler can be `async`, so you can `await` something — a dialog, a fetch — before replying. Both the incoming payload and the shape you must return are typed from the server's declaration. For an acknowledgement-only request, your handler just runs and returns nothing.

## What flows between them

| Server | Client |
|---|---|
| declare `{ out, in }` in `requests({...})` | — |
| `await ctx.request('ask-permission', payload)` | `socket.onRequest('ask-permission', handler)` |
| receives the validated `in` value | returns the answer the server awaits |

The direction is the mirror of a normal request: the server holds the asking side, the client holds the answering side. The `out` payload types the client handler's argument; the `in` schema types what the handler must return.

For the full behavior — broadcasting a question to many connections, channel-scoped server requests — see the [Server requests reference](/server/capabilities/requests) and the [Client server-request reference](/client/primitives/server-request).
