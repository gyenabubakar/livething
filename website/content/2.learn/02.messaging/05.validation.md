Anything a client sends is untrusted — it could be malformed, missing fields, or hand-crafted by someone poking at your socket. WSKit checks every incoming payload against a schema *before* your handler runs, so by the time your code sees the data, it's already the right shape. This page covers what gets validated, what happens when it fails, and how to react.

## Schemas on the input

You've already seen validation in every handler example: the `input` field. That schema is the gate. WSKit runs the payload through it, and only a payload that passes reaches your `run` function — typed exactly as the schema describes:

```typescript [api.ts]
import * as v from 'valibot'

export const handleSendMessage = base.on('send-message', {
  input: v.object({
    text: v.pipe(v.string(), v.minLength(1), v.maxLength(500)),
    from: v.string(),
  }),
  run(ctx, input) {
    // input is { text: string; from: string }, already checked.
    ctx.broadcast('message', input)
  },
})
```

The `input` schema appears on every incoming handler — `base.on(...)`, `base.request(...)`, channel handlers, stream starters. It's the single point where untrusted data becomes typed, validated data.

::note
The snippets on this page focus on the `input` schema, so they leave out the surrounding `define(...)` and `base.assemble(...)`. As always, a handler only becomes part of your server — and its contract — once you pass it to `base.assemble(...)`. See [The Contract](/learn/core-model/the-contract).
::

## Bring your own validator

WSKit doesn't ship its own schema library. Instead it accepts any validator that implements [Standard Schema](https://standardschema.dev) — a shared interface that valibot, Zod, ArkType, and others all support. These docs use [valibot](https://valibot.dev) because it's small and tree-shakeable, but you can use whatever you already have:

::code-group
```typescript [valibot]
import * as v from 'valibot'

input: v.object({ text: v.string(), count: v.number() })
```

```typescript [zod]
import { z } from 'zod'

input: z.object({ text: z.string(), count: z.number() })
```
::

Whichever you choose, WSKit reads both the runtime check and the inferred type from it — so `input` in your handler is typed from the same schema that validates it.

## What gets validated

Validation runs on **incoming** payloads — data the server receives:

- `input` on event handlers, request handlers, channel handlers, and stream starters.
- The `subscribe` schema on a channel — the join payload is checked before the auth gate runs.
- The `in` schema on a server-to-client request — the *client's reply* is validated before your `await ctx.request(...)` resolves.

Outgoing payloads — the things the server emits — aren't run through a schema, because the server is trusted to produce the shapes it declared with `t<...>()`. The contract still type-checks them at compile time; there's just no runtime schema, since there's no untrusted source.

## When validation fails

If an incoming payload doesn't match its schema, WSKit stops it before your handler runs and reports a validation failure. Two things let you observe it:

### The client side

A failed payload doesn't silently vanish. For a request, the Promise rejects. For an event, the failure surfaces as a typed error you can catch on the client's `onError` — it carries the code `'validation-failed'`.

### The `validationError` hook

On the server, the `validationError` hook fires whenever a payload is rejected, giving you the connection context and the event name that failed. It's the place for logging, metrics, or telling the offending client what happened:

```typescript [api.ts]
base.validationError((ctx, event) => {
  ctx.log.warn('rejected bad payload for', event)
  ctx.send('validation-error-fired', { event })
})
```

The hook runs *instead of* your handler — the handler never sees a payload that failed. This keeps the guarantee clean: inside `run`, the data is always valid.

::tip
Because the validated type flows into your handler, you get autocomplete and type-checking on `input` for free. Tighten the schema — add `minLength`, a `picklist`, an `email` check — and both the runtime guard and the handler's types follow along.
::
