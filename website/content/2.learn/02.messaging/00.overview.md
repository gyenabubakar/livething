Messaging is the heart of WSKit: the ways the server and client actually talk. Everything else — channels, streams, reliability — builds on top of these primitives. This section covers all of them, server half and client half together.

There are a few distinct ways to send something over a socket, and the difference between them comes down to one question: **do you expect an answer back?**

## The messaging primitives

::card-group
::card{title="Events" icon="i-ph-megaphone-duotone" to="/learn/messaging/events"}
Fire-and-forget, both ways. The server emits, the client listens; the client sends, the server handles. No reply expected.
::
::card{title="Requests" icon="i-ph-arrows-left-right-duotone" to="/learn/messaging/requests"}
The client asks the server a question and awaits a typed answer — request and response over the socket.
::
::card{title="Server Requests" icon="i-ph-question-duotone" to="/learn/messaging/server-requests"}
The reverse direction: the server asks the client a question, and the client replies.
::
::card{title="Errors" icon="i-ph-warning-duotone" to="/learn/messaging/errors"}
Typed errors that cross the wire, so the client can catch and narrow them by code — plus the control-flow errors that steer a connection.
::
::card{title="Validation" icon="i-ph-shield-check-duotone" to="/learn/messaging/validation"}
Every incoming payload is checked against a schema before your handler runs. Bring any Standard Schema validator.
::
::

## How they relate

Think of it as a spectrum of "do I need a reply":

- **Events** never expect a reply. You send and move on. Use them for the vast majority of traffic — notifications, broadcasts, updates.
- **Requests** always expect a reply. You `await` and get a typed answer (or a typed error). Use them when you need a result or confirmation.
- **Errors** are how a "no" comes back — a request can reject with a typed error you catch by code, and some errors steer the connection itself.
- **Validation** sits under all of it: whatever arrives, it's checked against your schema before any handler sees it.

Start with [Events](/learn/messaging/events) — they're the foundation the rest build on.
