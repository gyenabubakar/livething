Sometimes fire-and-forget isn't enough. You need an answer: the result of a lookup, confirmation that something saved, a generated id. A **request** is a message that expects a reply. The client asks, the server answers, and the client `await`s the typed response — all over the same socket.

Requests are the client-to-server direction. (The server can also ask the client — that's [Server Requests](/learn/messaging/server-requests).)

## Server: declare and handle

The server side has two parts: turn on the `requests()` capability, then register a request handler whose return value becomes the response.

### Turn on requests

`requests()` comes from `@wskit/server/requests`. Adding it to your capabilities unlocks the `base.request(...)` builder method:

```typescript [api.ts]
import { define, t } from '@wskit/server'
import { requests } from '@wskit/server/requests'
import type { InferClient } from '@wskit/server'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [requests()],
})
```

### Handle a request

`base.request(name, { input, run })` registers a handler. It looks almost exactly like an event handler — the difference is that whatever `run` **returns** is sent back to the client as the response:

```typescript [api.ts]
export const handleGetTime = base.request('get-time', {
  input: v.object({}),
  run() {
    return { now: new Date().toISOString() }
  },
})
```

The response is typed from the return value — no separate output schema needed. The client gets back exactly `{ now: string }`. Your `run` can be `async`; the client waits for the resolved value.

### When there's no useful answer

If a handler returns `undefined`, the client's request rejects rather than resolving with nothing — WSKit treats "no response" as a failure, so a request never hangs silently. If you want an acknowledgement-only request — "I got it" with no data — annotate the return type and the client will await a confirmation:

```typescript [api.ts]
export const handleMarkRead = base.request('mark-read', {
  input: v.object({ id: v.string() }),
  run(ctx, input): { ok: boolean } {
    markAsRead(input.id)
    return { ok: true }
  },
})

export const handler = base.assemble(handleGetTime, handleMarkRead)
export type ApiSocket = InferClient<typeof handler>
```

Both handlers have to be passed to `base.assemble(...)` — only assembled handlers land in the contract that `ApiSocket` is inferred from. Leave one out and the client won't have its `request` method.

## Client: ask and await

On the client, add the `requestResponse()` primitive. It gives the socket a `request(...)` method that returns a Promise of the typed response:

```typescript [app.ts]
import { client, connect, requestResponse } from '@wskit/client'
import type { ApiSocket } from '../server/api'

const socket = client<ApiSocket>()(
  connect('wss://example.com/ws'),
  requestResponse(),
)
socket.connect()

// payload is typed from the server's input; the result is typed from the return value
const { now } = await socket.request('get-time', {})
console.log('server time:', now)
```

### Timeouts

A request won't wait forever. If the server doesn't answer in time, the Promise rejects with a built-in `Timeout` error. The default wait is 10 seconds; you can set a different default when you create the primitive, or override it per call:

```typescript [app.ts]
const socket = client<ApiSocket>()(
  connect('wss://example.com/ws'),
  requestResponse({ timeout: 5000 }), // default for all requests
)

// override for one slow call
const result = await socket.request('generate-report', {}, { timeout: 30_000 })
```

If the socket drops while a request is in flight, it rejects with a `Disconnected` error instead. Both of these — and how to catch them — are covered in [Errors](/learn/messaging/errors).

## What flows between them

| Server | Client |
|---|---|
| `base.request('get-time', { run })` | `await socket.request('get-time', payload)` |
| the value `run` returns | the value the Promise resolves to |
| `run` throws / returns `undefined` | the Promise rejects |

The request name and payload type come straight from the server handler; the response type comes straight from its return value. Rename or reshape either on the server and the client call sites update with it.

For every option and the full behavior of in-flight requests, see the [Server requests reference](/server/capabilities/requests) and the [Client request-response reference](/client/primitives/request-response).
