LiveThing uses one small JSON frame for every application and framework message:

```json
["message", { "text": "hello", "from": "gyen" }, null]
```

Every frame has exactly three items:

1. the event name;
2. the payload, or `null` when the event has no payload;
3. metadata, either a nested object or `null`.

Metadata is never omitted. A client in another language can implement the protocol with a normal WebSocket and a JSON parser.

## Metadata

Metadata contains the framework details needed to route, match, deliver, or resume a frame. The details are arranged by feature:

```json
{
  "exchange": { "id": "request-42", "source": "server" },
  "channel": {
    "name": "room:42",
    "family": "rooms",
    "unsubscribeId": "leave-1",
    "membership": "persistent",
    "inbox": true,
    "readReceipts": true
  },
  "delivery": { "id": "message-7", "seq": 12 },
  "stream": {
    "id": "tokens-1",
    "event": "tokens",
    "durability": "persistent",
    "seq": 3,
    "nudgeId": "nudge-1",
    "terminated": false
  }
}
```

A frame includes only the groups and fields needed for that message:

| Group      | Fields                                                                   | Use                                      |
| ---------- | ------------------------------------------------------------------------ | ---------------------------------------- |
| `exchange` | `id`, `source`                                                           | Match a request and identify its side    |
| `channel`  | `name`, `family`, `unsubscribeId`, `membership`, `inbox`, `readReceipts` | Route channel traffic                    |
| `delivery` | `id`, `seq`                                                              | Deduplicate and order delivered messages |
| `stream`   | `id`, `event`, `durability`, `seq`, `nudgeId`, `terminated`              | Group and resume stream frames           |

`stream.seq` is the chunk number used to resume a stream. `delivery.seq` is the delivery number used to order or deduplicate channel and replay messages. `stream.durability` says whether the stream can continue across a disconnect.

## Reserved events

Framework events use names surrounded by double underscores:

| Event                                   | Meaning                                                        |
| --------------------------------------- | -------------------------------------------------------------- |
| `__error__`                             | A typed error, usually with `{ code, detail? }` as its payload |
| `__subscribe__` / `__subscribeOk__`     | Join a channel and confirm the join                            |
| `__unsubscribe__` / `__unsubscribeOk__` | Leave a channel and confirm the leave                          |
| `__streamOk__` / `__streamEnd__`        | Start and finish a stream                                      |
| `__nudgeOk__`                           | Confirm a stream nudge                                         |
| `__memberJoin__` / `__memberLeave__`    | Channel presence changes                                       |
| `__replay__`                            | Ask for messages missed during a reconnect                     |
| `__gap__`                               | Report a retention hole; the payload contains `missedThrough`  |

## Sending frames

A client sends the same three-item shape:

```json
["send-message", { "text": "hi" }, null]
```

A request adds its ID inside `metadata.exchange`:

```json
[
  "get-time",
  null,
  { "exchange": { "id": "request-42", "source": "client" } }
]
```

A channel subscription puts the channel name inside `metadata.channel.name`:

```json
["__subscribe__", null, { "channel": { "name": "room:42" } }]
```

That is the complete frame contract. The `@livething/client` package handles this framing for TypeScript applications; other clients only need to send and read the three-item JSON array.
