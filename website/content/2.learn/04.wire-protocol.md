Everything an untranslated WSKit endpoint sends over a socket — your events, requests, channel joins, stream chunks — travels as one simple JSON shape. You almost never touch it directly; the client and server build and parse it for you. But understanding the envelope makes the whole system legible, and it's exactly what you'd implement if you ever wanted to speak WSKit from another language. A server can instead expose an existing foreign wire format through [Translation](/server/define/translation).

## The envelope

Every frame is a JSON object with three top-level fields:

```json
{
  "event": "message",
  "payload": { "text": "hello", "from": "gyen" },
  "__wskit": {}
}
```

- **`event`** — a string naming what this frame is. For your own events, it's the name you declared (`"message"`, `"send-message"`). For framework operations it's a reserved name (more below).
- **`payload`** — the data. For your events, this is the typed object you sent. For framework frames, it's whatever that operation carries.
- **`__wskit`** — a metadata object that carries routing and correlation. On a plain fire-and-forget event it can be empty; on a request or a stream chunk it ties the frame back to the conversation it belongs to.

That's the entire protocol. Three keys, the same on both directions.

## The `__wskit` metadata

The `__wskit` object is how WSKit threads context through a single socket. Several different conversations — requests, streams, channel traffic — share one connection, so each frame needs enough metadata to know which conversation it belongs to. Most fields are optional and only appear when they're relevant. A few are required on the specific frame they belong to — `channelMembership`, for example, is always present on `__subscribeOk__`:

| Field               | Meaning                                                              |
| ------------------- | -------------------------------------------------------------------- |
| `correlationId`     | Ties a reply back to the request that asked for it                   |
| `source`            | Who started this exchange — `'server'` or `'client'`                 |
| `channel`           | The channel this frame is scoped to                                  |
| `channelFamily`     | The family key for a dynamic channel                                 |
| `channelMembership` | On `__subscribeOk__`, `'persistent'` or `'ephemeral'` — see below    |
| `inbox`             | On `__subscribeOk__`, marks a channel whose delivery is inbox-backed |
| `readReceipts`      | On `__subscribeOk__`, whether the channel expects read receipts      |
| `unsubscribeId`     | On `__unsubscribeOk__`, echoes the leave call it confirms            |
| `streamId`          | Groups all the chunks of one stream together                         |
| `streamKind`        | `'ephemeral'` or `'persistent'` — whether the stream can be resumed  |
| `seq`               | A sequence number, used to detect gaps after a reconnect             |
| `messageId`         | A unique ID used to drop duplicate messages                          |

For example, when you call `socket.request(...)`, the client stamps a `correlationId` on the outgoing frame; the server's reply carries the same `correlationId` back, so the client knows which pending promise to resolve. You never set these by hand — but seeing them explains how one socket juggles many overlapping conversations.

`channelMembership` is required on every `__subscribeOk__` frame — the server's confirmation that a subscribe succeeded. It tells the client who is responsible for re-subscribing this channel after the socket reconnects:

- **`'persistent'`** — the server rejoins this channel for the client automatically after a reconnect. The client must not re-subscribe it itself, or it would join twice.
- **`'ephemeral'`** — the server does not rejoin this channel. The client must call subscribe again itself after it reconnects.

## The TypeScript shape

If you write code that reads or changes raw frames — a plugin's `onIncoming` or `onOutgoing` hook, for example — you don't have to spell the envelope out yourself. `@wskit/core` exports two types for it: `WireMessage` for the whole frame (`event`, `payload`, `__wskit`), and `WSKitEnvelope` for the `__wskit` object described above. `@wskit/client` re-exports both, so a plugin author only ever needs to import from `@wskit/client`:

```typescript [my-plugin.ts]
import type { WireMessage } from '@wskit/client'

function logFrame(message: WireMessage) {
  console.log(message.event, message.payload)
}
```

## Reserved events

Most `event` names are yours. A set of names starting and ending with double underscores are reserved for the framework's own operations. You'll see these on the wire if you inspect traffic, but you never send them directly — the primitives and capabilities do. A sampling:

| Reserved event                          | What it does                                                      |
| --------------------------------------- | ----------------------------------------------------------------- |
| `__error__`                             | Carries a typed error, with `{ code, detail? }` as its payload    |
| `__subscribe__` / `__subscribeOk__`     | Join a channel, and the server's confirmation                     |
| `__unsubscribe__` / `__unsubscribeOk__` | Leave a channel, and its confirmation                             |
| `__streamOk__` / `__streamEnd__`        | A stream started, and a stream finished                           |
| `__nudgeOk__`                           | The server acknowledged a mid-stream nudge                        |
| `__memberJoin__` / `__memberLeave__`    | Channel presence changes                                          |
| `__replay__`                            | The client asking for messages it missed                          |
| `__gap__`                               | A retention hole; `payload.missedThrough` says how far it reaches |

Because these names are reserved, your own event and channel names can't start with `__` — WSKit rejects them, so framework traffic and app traffic can never collide.

For `__gap__`, the payload is `{ missedThrough: number }`. It means every sequence up to that value was evicted by retention; the frame itself is scoped by `__wskit.channel` / `channelFamily` when the hole belongs to a channel.

## Naming limits

To keep frames small and predictable, identifiers have length limits. The ones worth knowing:

| Identifier               | Max length     |
| ------------------------ | -------------- |
| Event name               | 128 characters |
| Channel name             | 256 characters |
| Channel family key       | 128 characters |
| Stream ID                | 128 characters |
| Correlation / message ID | 128 characters |

Channel names allow more room because a dynamic channel name can be a composite like `org:123:room:abc`. Names must be non-empty strings and may not begin with `__`.

## Speaking it from another language

Because the protocol is just JSON over a standard WebSocket, you aren't locked into `@wskit/client`. Anything that can open a WebSocket and read and write this envelope can talk to a WSKit server. To send a fire-and-forget event, you write:

```json
{ "event": "send-message", "payload": { "text": "hi" }, "__wskit": {} }
```

To make a request, you add a `correlationId` and wait for an `__error__` or a reply frame carrying the same ID back. That's the whole contract at the byte level — though for any TypeScript client, `@wskit/client` gives you the typing and the conversation-tracking for free.
