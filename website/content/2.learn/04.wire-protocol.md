A **frame** is one message as it travels over the connection. LiveThing has two kinds. A **text frame** is a small JSON array, and most messages use it, both your app's events and the framework's own events. A [**binary frame**](#binary-frames) puts the same JSON array in front of raw bytes, for data such as a picture or a file. This is a text frame:

```json
[
  "message",
  {
    "id": "m_8f2a",
    "text": "hello",
    "from": "maya",
    "sentAt": 1767225600000
  },
  null
]
```

Every frame is a JSON array with exactly three items. The only exception is the plain text frames `ping` and `pong`, which are not JSON. When the server lists `keepalive()`, it sends `ping` and the client answers `pong`. The client can also send `ping`, and the server answers `pong`. The other frames have three items:

1. the event name, a string;
2. the payload, or `null` when the event has no payload;
3. the metadata, a nested object or `null`.

The third item is never left out. When a frame has no metadata, the third item is `null`. An empty object `{}` is not allowed. Because a frame is plain JSON, a client in another language can use the protocol with a normal WebSocket and a JSON parser. The same frames also travel over [`http()`](#over-http).

## Metadata

Metadata holds the framework details that LiveThing needs to handle a frame. With these details, LiveThing can route the frame, match a reply to its request, deliver messages in order, and continue a stream after a disconnect. The details are in groups, one group per feature:

```json
{
  "exchange": { "id": "request-42", "source": "server" },
  "channel": {
    "name": "room:42",
    "family": "rooms",
    "unsubscribeId": "leave-1",
    "membership": "persistent",
    "inbox": true,
    "readReceipts": true
  },
  "delivery": { "id": "message-7", "seq": 12 },
  "stream": {
    "id": "ask-scout-1",
    "event": "ask-scout",
    "durability": "persistent",
    "seq": 3,
    "nudgeId": "nudge-1",
    "terminated": false
  },
  "upload": { "id": "upload-1", "seq": 2 }
}
```

This example shows almost every field at once. A real frame includes only the groups and fields that its message needs. In the `upload` group, a frame has `seq` (a piece) or `size` (the start), never both. Unknown groups and unknown fields are not allowed.

| Group      | Fields                                                                   | Use                                                            |
| ---------- | ------------------------------------------------------------------------ | -------------------------------------------------------------- |
| `exchange` | `id`, `source`                                                           | Match a reply to its request                                   |
| `channel`  | `name`, `family`, `unsubscribeId`, `membership`, `inbox`, `readReceipts` | Send a frame to a channel and describe that channel            |
| `delivery` | `id`, `seq`                                                              | Give a message an ID and a number, to order it and drop copies |
| `stream`   | `id`, `event`, `durability`, `seq`, `nudgeId`, `terminated`              | Group the frames of one stream and continue it                 |
| `upload`   | `id`, `seq`, `size`                                                      | Group the frames of one upload                                 |

Some fields need a short explanation:

- `exchange.source` is the side that started the request: `"client"` or `"server"`. The reply carries the same value.
- `channel.family` is the family key of a [dynamic channel](/learn/channels). A dynamic channel is one declaration that covers many rooms, such as `rooms` for `room:42`.
- `channel.unsubscribeId` is the ID of a leave request. The server's confirmation carries the same ID.
- `channel.membership` is `"persistent"` when the server stores the membership and puts the client back into the channel after a reconnect. It is `"ephemeral"` when the client must join again itself.
- `channel.inbox` and `channel.readReceipts` are `true` when the channel uses the inbox or read receipts feature. An inbox tracks which messages each user has received, and read receipts track which messages each user has read.
- `delivery.seq` is the delivery number. The client uses it to put channel and replay messages in order and to drop duplicate copies. A message sent to many connections carries the same `delivery.seq` and `delivery.id` for every recipient. Stream chunks carry `stream.seq` and no `delivery.seq`.
- `stream.seq` is the chunk number. A client uses it to continue a stream from the last chunk it received.
- `stream.durability` is `"persistent"` when the server stores the stream, so the stream can continue after a disconnect. It is `"ephemeral"` for a plain stream.
- `stream.nudgeId` is the ID of a nudge. A nudge is a small message that the client sends into a running [stream](/learn/streaming) to control it, for example to pause an AI reply.
- `stream.terminated` appears on a stream error. `false` means the error did not end the stream, for example when one nudge fails.
- `upload.id` is the client's ID of an [upload](#uploads), up to 128 characters. `upload.seq` numbers the pieces. `upload.size` is the size of the whole file, sent only on the start frame, when the client knows it. A frame never has both.

## Reserved events

Framework events have names that start and end with two underscores, such as `__error__`. For this reason, your own event names cannot start or end with `__`.

Most reserved events travel in one direction. Four go both ways, with a different payload in each direction: `__received__`, `__read__`, `__receivedQuery__` and `__readQuery__`. `__close__` goes both ways with the same payload. These five appear in both tables. `memberId` in a presence payload is the user ID when the channel is persistent and the connection has signed in, otherwise it is the connection ID.

### Client to server

| Event                | Payload                                              | Meaning                                                                                                                                                                                                                                    |
| -------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `__subscribe__`      | the subscribe payload the channel expects, or `null` | Join a channel                                                                                                                                                                                                                             |
| `__unsubscribe__`    | none                                                 | Leave a channel                                                                                                                                                                                                                            |
| `__replay__`         | `{ lastKnownSeq?, resume? }`                         | Ask for the messages missed since delivery number `lastKnownSeq` (or from the start). `resume` lists up to 8 resume tokens of earlier connections                                                                                          |
| `__streamCancel__`   | none                                                 | Stop a running stream                                                                                                                                                                                                                      |
| `__continueStream__` | `{ lastKnownSeq? }`                                  | Continue a stored stream after a reconnect, from chunk number `lastKnownSeq`                                                                                                                                                               |
| `__received__`       | `{ receivedThrough }`                                | Tell the server this user received the channel's messages up to that delivery number                                                                                                                                                       |
| `__read__`           | `{ readThrough }`                                    | Tell the server this user read the channel's messages up to that delivery number                                                                                                                                                           |
| `__receivedQuery__`  | `{ seq }`                                            | Ask which users received the message with that delivery number                                                                                                                                                                             |
| `__readQuery__`      | `{ seq }`                                            | Ask which users read the message with that delivery number                                                                                                                                                                                 |
| `__uploadEnd__`      | `{ totalBytes }`                                     | All pieces of an upload are sent, and the file has `totalBytes` bytes                                                                                                                                                                      |
| `__uploadCancel__`   | none                                                 | Cancel an upload                                                                                                                                                                                                                           |
| `__close__`          | `{ code, reason }`                                   | Close the connection. Only on [`http()`](#over-http), whose stream has no close frame of its own. The `code` must be `1000` or from `3000` to `4999`, or the server answers `400` and closes with `1002`. A `reason` over 123 bytes is cut |

## The first frame

When the server accepts the connection, it sends one `__connected__` frame first. (If `authenticate` rejects with a close code, the first frame is a `__close__` frame on `http()`, and on a WebSocket the connection closes with no frame.) The client counts the connection as open only when this frame arrives, so a connection that the server accepts and then closes at once never looks open. The frame holds the values the client must follow:

```json
[
  "__connected__",
  {
    "pingIntervalMs": 30000,
    "idleTimeoutMs": 60000,
    "maxResumeTokens": 8,
    "connectionId": "c_7f3a",
    "features": ["replay", "binary"],
    "resume": {
      "token": "0b6c1e4e-2f4a-4c55-9d1e-6a8f0e2b7c11",
      "seq": 12
    },
    "secret": null,
    "maxPostBytes": null
  },
  null
]
```

- `pingIntervalMs` and `idleTimeoutMs` are the server's [keepalive](/server/capabilities/keepalive) timings. The client pings at the same interval. Both are `null` when the server sends no pings.
- `maxResumeTokens` is the most resume tokens one `__replay__` may list.
- `connectionId` is the ID of this connection on the server. The client can use it to find itself in a member list.
- `features` lists the server features a client primitive needs: `replay`, `binary` and `uploads`. When the client has one of these primitives and the server does not list it, the client logs a warning.
- `resume` is this connection's secret resume token, and the delivery number where the connection started, or `null` when replay is off. A later `__replay__` shows the token to get back the messages sent to this connection.
- `secret` and `maxPostBytes` are for the [`http()`](/client/connecting/connect-options#transports) transport, where the client sends its messages as POST requests. Both are `null` on a WebSocket.

The client does not reply to this frame. When the server rejects a login with a close code, it closes the connection without sending this frame.

## Sending frames

A client sends the same three-item shape:

```json
["send-message", { "text": "hi" }, null]
```

A request adds its ID inside `metadata.exchange`:

```json
[
  "get-profile",
  { "userId": "u_amara" },
  { "exchange": { "id": "request-42", "source": "client" } }
]
```

To join a channel, a client puts the channel name inside `metadata.channel.name`. For a dynamic channel, it also adds the family key in `metadata.channel.family`. If the channel expects data when a client joins, that data goes in the payload.

```json
["__subscribe__", null, { "channel": { "name": "room:42" } }]
```

When a frame is not valid JSON or is not a three-item array, the server drops it. When the frame has the right shape but its metadata or payload is wrong, the server replies with an `__error__` frame whose code is `validation-failed`.

The `@livething/client` package builds and reads these frames for TypeScript apps. A client in another language only needs to send and read the three-item JSON array and the plain `ping` and `pong` text frames (with `keepalive()`, answer every `ping` with `pong`, or the server closes the connection as dead), plus the binary layout below when the server uses bytes.

## Binary frames

A **binary message** carries bytes, such as a picture or a file. The server takes and sends them when it lists [`binary()`](/server/binary/overview), and the client reads and writes them with the [`binary()`](/client/primitives/binary) primitive. Each binary message carries one LiveThing message in this layout:

```text
[ magic:          4 bytes = 0x6C 0x74 0x62 0x66 ("ltbf") ]
[ version:        1 byte  = 0x01                         ]
[ envelopeLength: 4 bytes, unsigned, big-endian          ]
[ envelope:       envelopeLength bytes, UTF-8 JSON       ]
[ bytes:          all the remaining bytes                ]
```

The **envelope** is the normal three-item frame: `[event, info, metadata]`. The **info** is JSON in the payload's place, such as the type of a file. The **bytes** are the data itself. The server routes a binary message by its envelope, in the same way as a text frame, so the channel membership check and every other check still run. A client in `room:general` sends one picture of its shared screen like this:

```text
ltbf | 1 | length | ["share-screen-frame",null,{"channel":{"name":"room:general","family":"rooms"}}] | picture bytes
```

The envelope is at most 64 KiB, so keep the info small and put the large data in the bytes. Framework events stay text: a binary frame named `__subscribe__`, `__error__` or any other `__x__` name gets an `__error__` frame with the code `wrong-frame-kind`.

Binary requests and streams use the metadata of their JSON versions. A [binary request](/server/binary/requests) and its reply carry the same `exchange`. Here a client asks for a small picture of a file. The request carries no bytes, and the reply carries the picture:

```text
→ ltbf | 1 | length | ["get-thumbnail",{"attachmentId":"att_1"},{"exchange":{"id":"request-7","source":"client"}}] | (no bytes)
← ltbf | 1 | length | ["get-thumbnail",{"fileType":"image/png"},{"exchange":{"id":"request-7","source":"client"}}] | picture bytes
```

A [binary stream](/server/binary/streams) starts with a binary message, and each chunk is a binary message with the normal `stream` group. Every other frame of the stream is text:

```text
→ ltbf | 1 | length | ["download-attachment",{"attachmentId":"att_1","fromByte":0},{"stream":{"id":"download-1"}}] | (no bytes)
← ["__streamOk__",null,{"stream":{"id":"download-1","durability":"ephemeral"}}]
← ltbf | 1 | length | ["download-attachment",{"fileName":"launch-plan.pdf","fileType":"application/pdf"},{"stream":{"id":"download-1","durability":"ephemeral","seq":1}}] | bytes
← ltbf | 1 | length | ["download-attachment",null,{"stream":{"id":"download-1","durability":"ephemeral","seq":2}}] | bytes
← ["__streamEnd__",null,{"stream":{"id":"download-1","seq":2}}]
```

A recorded binary stream has `"durability":"persistent"`. When a client continues it, the request is the normal text `__continueStream__`, and the stored chunks come back as binary messages with their `seq`:

```text
→ ["__continueStream__",{"lastKnownSeq":1},{"stream":{"id":"export-1"}}]
← ltbf | 1 | length | ["export-room-pdf",null,{"stream":{"id":"export-1","durability":"persistent","seq":2}}] | bytes
← ["__streamEnd__",null,{"stream":{"id":"export-1","seq":2,"event":"export-room-pdf"}}]
```

A binary message stored by an [inbox](/server/inbox/overview#binary-events) or by replay comes back the same way: one binary message with the channel and `delivery` metadata of the live one.

A [binary server request](/server/binary/requests#binary-server-requests) goes from the server to the client: the server sends a binary message with `"source":"server"`, and the client answers with a binary message with the same `exchange`. To decline, the client sends the normal text `__error__` frame.

### Uploads

An [upload](/server/binary/uploads) sends one large file in pieces. All its frames carry the `upload` group with the client's upload ID. The data frames are binary, with the upload's event name, and the framework frames are text. Here Huddle's client uploads a file of 600,000 bytes, in pieces of 256 KiB:

```text
→ ltbf | 1 | length | ["upload-attachment",{"fileName":"launch-plan.pdf","fileType":"application/pdf"},{"upload":{"id":"upload-1","size":600000}}] | (no bytes)
← ["__uploadAck__",{"receivedThrough":0,"savedThrough":0,"pieceBytes":262144,"windowBytes":2097152},{"upload":{"id":"upload-1"}}]
→ ltbf | 1 | length | ["upload-attachment",null,{"upload":{"id":"upload-1","seq":1}}] | 262,144 bytes
→ ltbf | 1 | length | ["upload-attachment",null,{"upload":{"id":"upload-1","seq":2}}] | 262,144 bytes
→ ltbf | 1 | length | ["upload-attachment",null,{"upload":{"id":"upload-1","seq":3}}] | 75,712 bytes
→ ["__uploadEnd__",{"totalBytes":600000},{"upload":{"id":"upload-1"}}]
← ["__uploadAck__",{"receivedThrough":262144,"savedThrough":0},{"upload":{"id":"upload-1"}}]
← ["__uploadAck__",{"receivedThrough":524288,"savedThrough":262144},{"upload":{"id":"upload-1"}}]
← ["__uploadAck__",{"receivedThrough":600000,"savedThrough":524288},{"upload":{"id":"upload-1"}}]
← ["__uploadDone__",{"info":{"attachmentId":"att_1"}},{"upload":{"id":"upload-1"}}]
```

- **The start** is a binary message with no bytes. Its payload is the upload's input, and `upload.size` is the size of the file when the client knows it.
- **The first `__uploadAck__`** answers the start. It gives the piece size and the window of the handler. `receivedThrough` and `savedThrough` are byte offsets in the whole file: how far `run` has read, and the last offset `run` gave to `ctx.upload.saved()`. The server sends one more ack each time `run` reads a piece, before `run` stores it, so `savedThrough` comes a little later.
- **The client sends a piece** only while it stays within `windowBytes` past the last `receivedThrough`.
- **Each piece** is a binary message with a `null` payload and an `upload.seq` that starts at `1` on every start. A piece starts where the earlier one ended: the first one at the `savedThrough` of the first ack.
- **`__uploadEnd__`** gives the size of the whole file. A text frame can arrive before the binary pieces that were sent before it, so the server ends the `for await` loop only when it has read exactly `totalBytes`.
- **`__uploadDone__`** is a text frame with the reply's info. It has no `exchange` group.

A resume is a new start with the same `upload.id`. Its first ack has the saved offset, and the pieces start again at `seq` 1, from that offset:

```text
← ["__uploadAck__",{"receivedThrough":262144,"savedThrough":262144,"pieceBytes":262144,"windowBytes":2097152},{"upload":{"id":"upload-1"}}]
```

A cancel is this text frame:

```text
→ ["__uploadCancel__",null,{"upload":{"id":"upload-1"}}]
```

An error for an upload is a text `__error__` frame with the same `upload` group:

```text
← ["__error__",{"code":"upload-aborted","detail":{"reason":"taken-over"}},{"upload":{"id":"upload-1"}}]
```

The server answers a binary message it cannot use like this:

| Binary message                                                            | What the server does                                            |
| ------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Any binary message, when the server does not list `binary()`              | Closes the connection with `1003` (`UNSUPPORTED_DATA`)          |
| No magic bytes at the start                                               | Closes the connection with `1003` (`UNSUPPORTED_DATA`)          |
| Bigger than the adapter's message limit                                   | Closes the connection with `1009` (`MESSAGE_TOO_BIG`)           |
| A broken header, an envelope over 64 KiB, or an envelope that is not JSON | Drops it and writes a warning to the log, like broken JSON text |
| An envelope that is not a three-item array with a string event            | Drops it, like a text frame of that shape                       |
| Bad metadata                                                              | `__error__` with `validation-failed`                            |
| A framework event name, or a nudge                                        | `__error__` with `wrong-frame-kind`                             |
| An event whose handler takes text (and text for a binary handler)         | `__error__` with `wrong-frame-kind`                             |
| An answer to a server request of the other kind                           | The request fails as for an answer that is not valid            |
| A channel event from a connection that is not a member                    | `__error__` with `channel-not-subscribed`                       |
| Info that fails the handler's `input`, or bytes over its `maxBytes`       | `__error__` with `validation-failed`                            |

[Close codes](/core/close-codes) and [Built-in errors](/core/builtin-errors) list them.

On the client, [`binary()`](/client/primitives/binary) reads and writes binary messages, on the socket and on channel handles: events, requests and their replies, stream chunks, and the server's requests with their answers. It reads the envelope with the same parser as a text frame. It sets the WebSocket's `binaryType` to `'arraybuffer'`, so it reads every message with no `await`, and text and binary messages keep their order. The client answers a binary message like this:

| Binary message                                                             | What the client does                                                     |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Any binary message, without `binary()`                                     | Reports an `Error` to `onError` and drops it                             |
| A LiveThing event                                                          | Gives it to the event's `binary.on(...)` listeners                       |
| The reply to a `binary.request`                                            | Resolves that request with `{ info, bytes }`                             |
| The reply to a JSON `request`                                              | Drops it: a JSON request waits for its text reply                        |
| A chunk of a `binary.stream`, `binary.onStream` or `binary.continueStream` | Gives `{ info, bytes }` to the loop or to `onChunk`                      |
| A server request, with `serverRequests()`                                  | Runs its `binary.onRequest` handler, or declines with a text `__error__` |
| A reply or a chunk that nothing waits for                                  | Drops it, and logs it when debug logging is on                           |
| A broken header or envelope                                                | Drops it, and logs it when debug logging is on, like broken JSON text    |
| No magic bytes at the start                                                | Reports an `Error` to `onError` and drops it                             |

A text reply to a `binary.request` rejects it with `request-invalid-response` too, and a text chunk in a binary stream is dropped, so the stream's `seq` check fails it with `stream-corrupted`.

## Over `http()`

The [`http()`](/client/connecting/connect-options#transports) transport carries the same frames over plain HTTP. The server sends on one long server-sent events (SSE) response, and the client sends with POST requests.

**The stream.** The client opens it with a `GET` to the endpoint URL, with an `Accept: text/event-stream` header, a `LiveThing-Protocol: livething-v1` header and, when the app uses [`token`](/client/connecting/auth-and-query#token-auth-with-token), an `Authorization: Bearer` header. The `LiveThing-Protocol` header makes a cross-origin browser send a CORS preflight first, and a preflight carries the `Origin` header, so the server can always check the origin of a page on another site. A `GET` without this header, or without `Accept: text/event-stream`, gets a `426` answer with `LiveThing-Error: not-offered`. The response has `Content-Type: text/event-stream`, `Cache-Control: no-store, no-transform` and `X-Accel-Buffering: no`, so a proxy does not compress or hold the stream. Each frame is one `data:` line:

```text
data: ["__connected__",{"pingIntervalMs":30000,"idleTimeoutMs":60000,"maxResumeTokens":8,"connectionId":"c_7f3a","features":["binary"],"resume":null,"secret":"4mT0…","maxPostBytes":524288},null]

data: ["message",{"id":"m_8f2a","text":"hello","from":"maya","sentAt":1767225600000},null]

data: ping

data: bbHRiZgEAAAA…
```

A text frame is the same JSON array as on a WebSocket. A binary frame is the letter `b` and then the whole [binary frame](#binary-frames) in base64, so it is about a third bigger than on a WebSocket. `ping` and `pong` are the plain words, as on a WebSocket. The first frame is `__connected__` (or `__close__` when `authenticate` rejects with a close code), and here `secret` and `maxPostBytes` have values. SSE has no close frame, so before the server ends a stream, it sends a last `__close__` frame with the close code and the reason. A stream that ends without it counts as close code `1006`.

**The POSTs.** The client sends to the exact URL of the stream, query included, with a `LiveThing-Secret` header that holds the `secret`, a `LiveThing-Lane` header, and `Content-Type: application/octet-stream`. The body is a batch of frames. Each frame is 1 byte for its kind (`0` for text, `1` for binary), 4 bytes for its length (big-endian), and then its data. Bytes go up raw, with no base64. The client has one POST in flight on each of two lanes:

- **`data`** carries every other frame, in order, at most 255 frames and `maxPostBytes` bytes in one batch.
- **`control`** carries only `ping`, `pong` and `__close__`, so a slow upload never holds back a `pong`.

Each data frame of a connection has a sequence number, from 1. A `data` POST has a `LiveThing-Seq` header with the number of its first frame. The server drops the frames it already has, so a frame that comes twice runs its handler once. A number past the next one the server expects means frames are missing: the server answers `400` and closes the connection with `1002`.

**Stream mode.** The client can also send its data frames in one long POST, with a `LiveThing-Upload: stream` header and a body that stays open (`fetch` with `duplex: 'half'`). It holds the `data` lane, and uses the same frames plus three more kinds:

- **`2`, a probe**, with no data. The server answers at once on the stream with `["__ack__",{"seq":N,"probe":true},null]`, where `N` is the number of the last data frame it has.
- **`3`, a start frame**, with 4 bytes of data: the sequence number of the next data frame. Data frames follow it.
- **`4`, a close frame**, with the same `__close__` text as on the `control` lane. The server runs the data frames before it, answers the long POST `204`, and ends the stream. So a client in stream mode sends no `control` POST to close. When the stream does not end within a second, the client sends `__close__` on the `control` lane.

The server answers the data frames on the stream with `["__ack__",{"seq":N},null]`, at most one for each 20 ms, and at once when the body ends. A frame over `maxPostBytes` gets `413`. A long POST that sends nothing for 45 seconds gets `408`. A `data` POST takes the lane from a long POST: the long POST gets `409`, and nothing closes. While the connection is busy, the server stops reading the body, so the client's writes slow down. The client writes a probe after 15 seconds with no writes, and when the probe's answer does not come within 2 seconds, or the long POST fails or ends before the client closes it, it sends every frame without an `__ack__` again in `data` POSTs. After 8 MiB of frames, the client closes the long POST itself and opens a fresh one, with no probe. The fresh one starts with a start frame and sends every frame without an `__ack__` again, and the client stays in stream mode. See [Stream mode](/runtimes/transports/http#stream-mode).

The server answers a POST like this:

| Status | When                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `204`  | The server took every frame of the batch. It answers before the handlers finish                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `400`  | A missing or unknown lane, a missing or wrong `LiveThing-Seq` on a `data` POST, a control frame that is not allowed, a batch that does not parse, or a long POST that breaks the frame rules (a data frame before its start frame, a start frame that is not 4 bytes or has a wrong sequence number, a frame that does not parse, a close frame with a code a client may not send, or a start frame while a `data` POST holds the lane): the server also closes the connection with `1002`. A body that did not arrive whole gets `400` too, and nothing closes |
| `403`  | The `Origin` is not [allowed](/runtimes/transports/http#origins-cors-and-proxies)                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `404`  | The server does not know this secret, for example after a restart                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `408`  | A long POST that sent nothing for 45 seconds. Nothing closes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `409`  | A second POST in the same lane: the server also closes the connection with `1002`. A long POST whose lane a `data` POST took gets `409` too, and nothing closes                                                                                                                                                                                                                                                                                                                                                                                                 |
| `410`  | A long POST that is still open when the connection closes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `413`  | The body, or one frame of a long POST, is over `maxPostBytes`. Nothing closes on the server                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `503`  | The connection is [busy](/server/handlers/per-connection-queue#busy-on-http). The JSON body is `{ room, retryAfterMs }`                                                                                                                                                                                                                                                                                                                                                                                                                                         |

Every error that LiveThing makes carries a `LiveThing-Error` header, so the client can tell it apart from an error that a proxy makes. The client handles an answer like this:

- A `503` busy answer is not a failure. The client sends only `room` frames after `retryAfterMs` (at least 250 ms, then doubling up to 1 second) and keeps the rest in its queue. Busy answers for 30 seconds with no frame taken count as a failure.
- A `403` with the `LiveThing-Error` header is final. The connection closes with `4002` (`AUTH_INVALID`).
- A `404` drops the connection, and the client reconnects with a new stream and resumes.
- Any other failure, or a `data` or `control` POST with no answer in 30 seconds, also drops the connection, and the client reconnects. When this happens before the first POST of the connection worked, the client also skips `http()` for [5 minutes](/client/connecting/connect-options#failover).
