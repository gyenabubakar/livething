WSKit has one big idea, and everything else hangs off it: **you describe your app once, on the server, and the client picks up the exact same description automatically.** That shared description is the *contract*. This page explains what's in it, how it gets to the client, and the one mental trick — the perspective flip — that makes it all line up.

## One source of truth

A normal WebSocket app has two copies of the truth. The server knows it sends a `message` event with `{ text, from }`. The client also has to know that — usually in a hand-written type, or in nobody's head at all. The two copies drift, and you find out in production.

WSKit keeps a single source of truth: the server definition. When you call `base.assemble(...)`, WSKit gathers every event, request, stream, channel, and error your server declared into one type — the **server contract**. You never write that type by hand; it's inferred from the handlers and capabilities you already wrote.

`InferClient` then takes that server contract and turns it into the **client contract**:

```typescript [chat.ts]
import type { InferClient } from '@wskit/server'

export const handler = base.assemble(handleSendMessage)

// The whole client API, derived from the server. One line.
export type ChatSocket = InferClient<typeof handler>
```

The client imports that one type and nothing else about the shape of your API:

```typescript [app.ts]
import { client, connect } from '@wskit/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(connect('wss://example.com/ws'))
```

There's no code generation step, no build script, no schema file to keep in sync. The types flow through a normal TypeScript import. Change the server, and the client's types change the next time the compiler runs.

## What the contract holds

The contract is a single object type with a fixed set of keys. Each key is one kind of thing your app can do:

| Key | What it is |
|---|---|
| `incoming` | Events the client receives from the server |
| `outgoing` | Events the client sends to the server |
| `requests` | Client-to-server question/answer pairs |
| `serverRequests` | Server-to-client questions the client answers |
| `streams` | Progressive, chunked data the server pushes |
| `channels` | Server-managed rooms, each with its own nested contract |
| `errors` | Typed error codes the server can send |

Every key is optional. A tiny app might only have `incoming` and `outgoing`. As you add capabilities on the server, more keys fill in — and the client gains the matching methods automatically.

## What the contract looks like

The table above is the map; here's the territory. This is a complete client contract — the type `InferClient` produces for a chat app that has grown every feature. You never write this by hand, but it's worth seeing once in full, because every other page in these docs shows you one slice of it:

```typescript [chat-socket.ts]
// The single type the client imports. Each key is one kind of traffic.
interface ChatSocket {
  // Events the server pushes to you (fire-and-forget).
  incoming: {
    message: { text: string; from: string }
    'user-joined': { username: string }
  }
  // Events you push to the server.
  outgoing: {
    'send-message': { text: string; from: string }
  }
  // You ask, the server answers (payload out, response back).
  requests: {
    'get-history': {
      payload: { limit: number }
      response: { messages: string[] }
    }
  }
  // The server asks, you answer.
  serverRequests: {
    'confirm-action': {
      payload: { action: string }
      response: { allowed: boolean }
    }
  }
  // Progressive, chunked data the server pushes.
  streams: {
    'ask-ai': {
      payload: { prompt: string }
      chunk: { text: string }
      kind: 'ephemeral'
    }
  }
  // Rooms — each carries its own mirrored mini-contract.
  channels: {
    rooms: {
      incoming: {
        message: { text: string; from: string }
      }
      outgoing: {
        say: { text: string }
      }
    }
  }
  // Typed errors the server can send.
  errors: {
    'not-found': { id: string }
    forbidden: { reason: string }
  }
}
```

A `request` or `serverRequest` entry pairs a `payload` (what's sent) with a `response` (what comes back). A `stream` entry pairs the `payload` that starts it with the `chunk` shape it yields, plus a `kind` (`'ephemeral'` or `'persistent'`). A `channel` entry is a contract inside the contract — the same keys again, scoped to that room. When you reach a feature's own page, you'll see that one key isolated.

## The perspective flip

Here's the part worth slowing down for. The server and the client describe the *same* traffic, but from opposite ends. So the contract **mirrors** as it crosses the wire.

Think of one event. On the server you say "I **emit** `message`." From where the client stands, that same event is something it **receives**. So:

- The server's **emitted** events become the client's **`incoming`**.
- The server's **handlers** (the events it listens for) become the client's **`outgoing`** — because to trigger a handler, the client has to send.

The same flip applies everywhere. A client-to-server request is a `request` you make on the client and a handler you write on the server. A server-to-client request is the reverse: the server asks, the client answers.

::note
The words `incoming` and `outgoing` are always read **from the point of view of whoever holds the type**. On the client, `incoming` is what arrives at the client. The server's own contract uses the same words from its own side. Whenever a name seems backwards, ask "incoming to whom?" — that resolves it every time.
::

A quick way to see the flip in action, straight from the Quickstart:

::code-group
```typescript [Server]
// Server emits `message`, handles `send-message`.
const base = define({
  env: t<Env>(),
  capabilities: [
    emits({ message: t<{ text: string; from: string }>() }),
  ],
})

export const handleSendMessage = base.on('send-message', {
  input: v.object({ text: v.string(), from: v.string() }),
  run(ctx, input) {
    ctx.broadcast('message', input)
  },
})
```

```typescript [Client]
// Client receives `message`, sends `send-message` — flipped.
socket.on('message', (data) => {
  // data: { text: string; from: string }
})

socket.send('send-message', { text: 'hi', from: 'gyen' })
```
::

The server `emits` `message`, so the client `on`s it. The server handles `send-message`, so the client `send`s it. You wrote the contract once; the compiler handed the mirror image to the other side.

## Channels mirror too

A channel is a contract inside the contract. Each channel you declare on the server becomes an entry under the client's `channels` key, with its own `incoming`, `outgoing`, `requests`, and `streams` — flipped the same way. That's why, in [Your First App](/start/your-first-app), `lobby.on('lobby-message', ...)` and `lobby.send('say', ...)` were already typed: the channel carried its own little mirrored contract along with the rest.

## Why this matters

Because the contract is inferred rather than copied, the two sides physically cannot drift:

- Listening for an event the server doesn't emit is a compile error.
- Sending the wrong payload shape is a compile error.
- Renaming an event on the server lights up every stale call site on the client.
- Autocomplete works for every event name and field, on both ends.

You declare your app once and let the compiler keep both halves honest.
