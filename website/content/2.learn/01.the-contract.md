LiveThing is built on one main idea: **you describe your app once, on the server, and the client gets the exact same description automatically.** This shared description is the _contract_. This page explains what the contract holds, how it gets to the client, and the "perspective flip": the rule that the client sees every event from the opposite side.

## One source of truth

A normal WebSocket app has two copies of the same facts. The server knows that it sends a `message` event with `{ text, from }`. The client also has to know this. Usually a developer writes a separate type for it on the client, or does not write it down at all. Over time, the two copies stop matching, and you only find the problem when users hit it.

The examples in these docs all come from the same small app, **Huddle**, a team chat app with rooms and an AI assistant. LiveThing keeps one source of truth: the server definition. A **routed handler** is a handler for one named event or request, such as the value that `base.on('send-message', ...)` returns. When you call `base.assemble(...)`, LiveThing collects the routed handlers you list, plus the capabilities, channel settings, and lifecycle hooks you declared, into one server definition. The type of this definition carries the **server contract**. You never write that type yourself. TypeScript infers it (works it out) from the handlers and capabilities you already wrote.

`InferClient` then takes that server contract and turns it into the **client contract**:

```typescript [server/huddle.ts]
import type { InferClient } from '@livething/server'

export const huddle = base.assemble({
  handlers: [handleSendMessage],
})

// The whole client API, derived from the server. One line.
export type HuddleSocket = InferClient<typeof huddle>
```

The client imports that one type and nothing else about the shape of your API:

```typescript [client/socket.ts]
import { client, connect } from '@livething/client'
import type { HuddleSocket } from '@monorepo/server/huddle'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
)
```

You do not need a code generation step, a build script, or a schema file to keep in sync. The types move through a normal TypeScript import. When you change the server, the client's types change the next time the compiler runs.

Defining a routed handler is not enough to make it active. You must also pass the value it returns to `base.assemble({ handlers: [...] })`. If you do not, the handler does not run, and it is not part of `InferClient`.

::note
`InferClient` describes a LiveThing client that uses the normal LiveThing wire protocol (the message format on the connection). Some clients use another library's protocol and connect through [server translation](/server/server/translation). Those clients keep using their own SDK and types. The translator converts their protocol on the server, before the messages reach your handlers.
::

## What the contract holds

The contract is a single object type with a fixed set of keys. Each key is one kind of thing your app can do:

| Key              | What it is                                              |
| ---------------- | ------------------------------------------------------- |
| `incoming`       | Events the client receives from the server              |
| `outgoing`       | Events the client sends to the server                   |
| `clientRequests` | Requests the client sends and the server answers        |
| `serverRequests` | Requests the server sends and the client answers        |
| `streams`        | Data the server sends in many small parts (chunks)      |
| `channels`       | Server-managed rooms, each with its own nested contract |
| `errors`         | Typed error codes the server can send                   |

Every key is optional. A small app might only use `incoming` and `outgoing`. When you add capabilities on the server, more keys get entries. To use a key's methods on the client, such as `request(...)` for `clientRequests`, you add the matching client primitive. The next page, [Capabilities & Primitives](/learn/capabilities-and-primitives), explains these pairs.

The `errors` key always has entries in a contract from `InferClient`. It holds the errors you define, plus the built-in errors that LiveThing itself can send, such as `validation-failed`.

## What the contract looks like

Below is a client contract for Huddle that uses every kind of traffic. It is a simplified version of the type that `InferClient` produces. The real type also lists the built-in errors and a few extra fields that the client uses internally. You never write this type yourself. It is shown here in full because every other page in these docs shows one part of it.

```typescript [server/huddle-definition.ts]
// The single type the client imports. Each key is one kind of traffic.
interface HuddleSocket {
  // Events the server sends to you. No reply is expected.
  incoming: {
    notification: { title: string; body: string }
    'user-renamed': { userId: string; name: string }
  }
  // Events you send to the server.
  outgoing: {
    'set-status': { status: 'active' | 'away' | 'busy' }
  }
  // You ask, the server answers (payload out, response back).
  clientRequests: {
    'get-profile': {
      payload: { userId: string }
      response: {
        id: string
        name: string
        status: 'active' | 'away' | 'busy'
      }
    }
  }
  // The server asks, you answer.
  serverRequests: {
    'confirm-delete': {
      payload: { preview: string }
      response: { confirmed: boolean }
    }
  }
  // Data the server sends in chunks.
  streams: {
    'search-messages': {
      payload: { query: string }
      chunk: {
        hit: {
          id: string
          text: string
          from: string
          sentAt: number
        }
      }
      kind: 'ephemeral'
    }
  }
  // Rooms. Each one has its own smaller contract.
  channels: {
    rooms: {
      incoming: {
        message: {
          id: string
          text: string
          from: string
          sentAt: number
        }
      }
      outgoing: {
        'send-message': { text: string }
      }
    }
  }
  // Typed errors the server can send.
  errors: {
    'not-found': { id: string }
    forbidden: { reason: string }
  }
}
```

A `clientRequests` or `serverRequests` entry pairs a `payload` (what is sent) with a `response` (what comes back). A `streams` entry pairs the `payload` that starts the stream with the shape of each `chunk`, plus a `kind`. The kind is `'ephemeral'` for a plain stream, which ends when the connection drops. It is `'persistent'` for a durable stream, which the client can continue after it reconnects. A `channels` entry is a contract inside the contract: the same keys again, but only for that room. Each feature's own page shows its key on its own.

## The perspective flip

The server and the client describe the _same_ traffic, but from opposite ends. So when the contract goes from the server to the client, it is **mirrored** (turned the other way around).

Think of one event. On the server you say "I **emit** (send) `message`." For the client, that same event is something it **receives**. So:

- The events the server **emits** become the client's **`incoming`**.
- The server's **handlers** (the events it listens for) become the client's **`outgoing`**, because the client must send an event to run a handler.

The same flip applies to everything. A client-to-server request is a `request` call on the client and a handler on the server. A server-to-client request is the reverse: the server asks, and the client answers.

::note
The words `incoming` and `outgoing` always describe the traffic **from the side that holds the type**. On the client, `incoming` is what arrives at the client. The server's own contract uses the same words from the server's side. When a name seems backwards, ask "incoming to which side?" The answer tells you what the name means.
::

Here is the flip in the app from the Quickstart:

::code-group

```typescript [Server]
// Server emits `message`, handles `send-message`.
const base = server({
  capabilities: [
    emits({ message: t<{ text: string; from: string }>() }),
  ],
})

export const handleSendMessage = base.on('send-message', {
  input: v.object({ text: v.string(), from: v.string() }),
  run(ctx, input) {
    ctx.broadcast('message', input)
  },
})
```

```typescript [Client]
// Client receives `message`, sends `send-message`. This is the flip.
socket.on('message', (data) => {
  // data: { text: string; from: string }
})

socket.send('send-message', { text: 'hi there', from: 'amara' })
```

::

The server emits `message`, so the client listens for it with `on`. The server handles `send-message`, so the client sends it with `send`. You wrote the contract once, and the compiler gave the mirrored version to the client.

## Channels mirror too

A channel is a contract inside the contract. Each channel you declare on the server becomes an entry under the client's `channels` key. The entry has its own `incoming`, `outgoing`, `clientRequests`, `serverRequests`, and `streams`, flipped in the same way.

## Why this matters

The client contract is inferred from the server code. It is not a copy. So the two sides cannot stop matching:

- Listening for an event the server doesn't emit is a compile error.
- Sending the wrong payload shape is a compile error.
- If you rename an event on the server, every client call that still uses the old name becomes a compile error.
- Autocomplete works for every event name and field, on both ends.

You declare your app once, and the compiler checks that both halves agree.
