Some data does not arrive all at once. It comes in pieces, over time: the tokens of an AI reply, the rows of a big database query, the frames of a live video feed. **Streaming** is how LiveThing sends this kind of data. The server produces a sequence of pieces, called **chunks**. The client reads them one by one as they arrive, and does not wait for the whole result.

Streaming in LiveThing uses one JavaScript feature: the **async generator**. An async generator is a function written as `async function*` (or `async *name()` inside an object). It can `await` like any async function, and it can hand out many values over time with `yield`. The server writes an `async *run` generator that `yield`s chunks. The client reads them with a `for await ... of` loop, a loop that waits for each next value. LiveThing handles everything between the two sides: it tags each chunk with its stream, tells the client when the stream ends, and cleans up if either side stops early. Each example below shows the server and the client together, because you declare a stream once on the server and the matching typed methods appear on the client.

## A stream, end to end

On the server, turn on the `stream()` capability and declare a stream with `base.stream(...)`. Three parts define it:

- `input`: a schema for the payload that starts the stream.
- `chunk`: a `t<Shape>()` type marker for each chunk you send.
- `async *run`: the generator. Each value it `yield`s becomes one chunk.

On the client, add the `stream()` primitive, call `socket.stream(name, payload)`, and loop over the handle it returns. A **handle** is the object that represents one running stream.

::code-group

```typescript [server: ai.ts]
import { server, t } from '@livething/server'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'

const base = server({
  capabilities: [stream()],
})

export const handleTokens = base.stream('start-tokens', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ token: string }>(),
  async *run(ctx, input) {
    for (const word of input.prompt.split(' ')) {
      yield { token: word + ' ' } // each yield is one chunk on the wire
    }
  },
})

export const definition = base.assemble({
  handlers: [handleTokens],
})

export type AiSocket = InferClient<typeof definition>
```

```typescript [client: app.ts]
import { client, connect, stream } from '@livething/client'
import type { AiSocket } from '../server/ai'

const socket = client<AiSocket>()(
  connect('wss://example.com/ws'),
  stream(),
)
socket.connect()

const tokens = await socket.stream('start-tokens', {
  prompt: 'hello there friend',
})

for await (const chunk of tokens) {
  // chunk: { token: string }, typed from the server's declaration
  process.stdout.write(chunk.token)
}
// the loop ends when the server's generator finishes
```

::

Because `run` is `async`, you can `await` between yields. For example, you can call an AI model, read the next page of a database query, or wait on a timer. The client gets each chunk as soon as you yield it. The payload you pass and the chunk type you receive are both typed from the server's declaration.

| Server                                 | Client                                         |
| -------------------------------------- | ---------------------------------------------- |
| `base.stream('start-tokens', { run })` | `await socket.stream('start-tokens', payload)` |
| each `yield`                           | one turn of the `for await` loop               |
| generator finishes                     | loop ends                                      |
| generator throws                       | loop throws (catch with `try/catch`)           |

## Stopping early

You do not have to read a stream to the end. When you `break` (or `return`) out of the `for await` loop, the client tells the server to stop. You can also call `tokens.cancel()` from outside the loop. In both cases the server stops the generator. On the server side, `ctx.stream.signal` fires. This is an `AbortSignal`, the standard JavaScript object that tells async work to stop. Pass it to slow work, such as `fetch(url, { signal: ctx.stream.signal })`. For cleanup code, wrap the generator body in `try/finally`: the `finally` block runs when the stream stops.

```typescript [client: app.ts]
for await (const chunk of tokens) {
  render(chunk.token)
  if (userClickedStop) break // cancels the stream
}
```

::note
A stream is a separate feature from [messaging](/learn/messaging) and [channels](/learn/channels). If the generator throws a registered error, the `for await` loop throws that error. You check it with `.matches()`, the same as any other registered error.
::

## One stream per event name

By default, a connection runs **one stream per event name at a time**. If you start a second `start-tokens` stream while the first one is still running, you get a `stream-already-active` error. The two streams do not run side by side. Sometimes you need several runs of the same stream at once, for example to run several searches in parallel. For that case, set `allowConcurrent: true` in the server declaration.

## Nudges: steer a running stream

A plain stream goes one way: the server sends, and the client reads. Sometimes the client needs to _steer_ a running stream ("pause", "go faster", "skip ahead") without stopping it and losing its place. A **nudge** does this. A nudge is a small typed message that the client sends _into_ a running stream. The generator reads it between chunks. A common example is an AI reply where the user clicks pause or asks the reply to go faster.

On the server, declare a `nudges` map. Each key is a nudge name, and each value is a payload schema, or `null` for a nudge with no payload. Then read the nudges that arrived with `ctx.stream.nudges(yield chunk)`. Reading nudges is tied to yielding: you check for nudges at the moment you send the next chunk. On the client, the handle gets a typed `nudge(name, payload)` method.

::code-group

```typescript [server: ai.ts]
export const handleTokens = base.stream('start-tokens', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ token: string }>(),
  nudges: {
    pause: null,
    'speed-up': v.object({ factor: v.number() }),
  },
  async *run(ctx, input) {
    let delay = 50
    for (const word of input.prompt.split(' ')) {
      // yield a chunk, and read any nudges that arrived since the last yield
      const recent = ctx.stream.nudges(yield { token: word + ' ' })

      if (recent.some((n) => n.event === 'pause')) return

      const speedUp = recent.find((n) => n.event === 'speed-up')
      if (speedUp) delay = Math.max(1, delay / speedUp.payload.factor)

      await new Promise((r) => setTimeout(r, delay))
    }
  },
})
```

```typescript [client: app.ts]
const tokens = await socket.stream('start-tokens', {
  prompt: longPrompt,
})

// for example, in button click handlers:
async function onSpeedUp() {
  await tokens.nudge('speed-up', { factor: 2 })
}
async function onPause() {
  await tokens.nudge('pause')
}

for await (const chunk of tokens) {
  render(chunk.token)
}
```

::

Each nudge the server reads is an `{ event, payload }` object. Both fields are typed from the `nudges` map. The client can only send the names that the map declares, with the right payload shape. A nudge declared as `null` has no payload, so the client sends it with just its name: `nudge('pause')`.

`nudge(...)` returns a promise. The promise resolves when the server confirms the nudge. It rejects if the server refuses the nudge or if no confirmation arrives in time (10 seconds by default). A rejected nudge does **not** end the stream. If you call `nudge(...)` after the stream has finished, nothing is sent and the promise resolves.

::tip
Only the client that started a stream can nudge it. Nudges do not change how chunks flow. They add a second path, from the client into the running generator.
::
