Some data doesn't arrive all at once — it comes in pieces, over time. The tokens of an AI reply, the rows of a big query, the frames of a live feed. **Streaming** is how WSKit sends that kind of data: the server produces a sequence of chunks, and the client reads them one by one as they arrive, instead of waiting for the whole thing.

The whole idea rests on one JavaScript pattern you already know — the **async generator**. The server writes an `async *run` that `yield`s chunks; the client `for await`s over them. WSKit wires up everything between: correlating the chunks, signalling the end, and cleaning up if either side bails. Each piece below shows both halves together, because that's how the contract works — you declare a stream once and the matching methods appear on the other side.

## A stream, end to end

On the server, turn on the `stream()` capability and declare a stream with `base.stream(...)`. Three pieces define it: an `input` schema for the payload that starts it, a `chunk` type marker for each piece you send, and the `async *run` generator whose every `yield` becomes one chunk. On the client, add the `stream()` primitive, call `socket.stream(name, payload)`, and iterate the handle it returns.

::code-group

```typescript [server: ai.ts]
import { define, t } from '@wskit/server'
import { stream } from '@wskit/server/streams'
import * as v from 'valibot'

const base = define({
  capabilities: [stream()],
})

export const handleTokens = base.stream('start-tokens', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ token: string }>(),
  async *run(ctx, input) {
    for (const word of input.prompt.split(' ')) {
      yield { token: word + ' ' } // each yield is one chunk on the wire
    }
  },
})

export const handler = base.assemble({ handlers: [handleTokens] })
```

```typescript [client: app.ts]
import { client, connect, stream } from '@wskit/client'
import type { AiSocket } from '../server/ai'

const socket = client<AiSocket>()(connect('wss://example.com/ws'), stream())
socket.connect()

const tokens = await socket.stream('start-tokens', {
  prompt: 'hello there friend',
})

for await (const chunk of tokens) {
  // chunk: { token: string } — typed from the server's declaration
  process.stdout.write(chunk.token)
}
// loop ends when the server's generator finishes
```

::

Because `run` is `async`, you can `await` between yields — call an LLM, read a database page, wait on a timer — and the client gets each chunk the moment you yield it. The payload you pass and the chunk type you receive are both typed from the server's declaration.

| Server                                 | Client                                         |
| -------------------------------------- | ---------------------------------------------- |
| `base.stream('start-tokens', { run })` | `await socket.stream('start-tokens', payload)` |
| each `yield`                           | one turn of the `for await` loop               |
| generator finishes                     | loop ends                                      |
| generator throws                       | loop throws (catch with `try/catch`)           |

## Stopping early

You don't have to drain a whole stream. `break` (or `return`) out of the `for await` loop and the client tells the server to stop; you can also call `tokens.cancel()` from outside the loop. Either way the server's generator is torn down — on its side that surfaces as `ctx.stream.signal`, an `AbortSignal` you can wire into slow work or wrap with `try/finally` for cleanup.

```typescript [client: app.ts]
for await (const chunk of tokens) {
  render(chunk.token)
  if (userClickedStop) break // cancels the stream
}
```

::note
A stream is its own thing, separate from [messaging](/learn/messaging) and [channels](/learn/channels). If the generator throws a registered error, it surfaces out of the `for await` loop, so you `.matches()` it just like any other error.
::

## One stream per event name

By default a connection runs **one stream per event name at a time**. Start a second `start-tokens` while the first is still going and you get a `stream-already-active` error, not two overlapping streams — a stream maps to one clear activity. When you genuinely need parallel runs of the same event (fan-out searches, say), set `allowConcurrent: true` on the server declaration.

## Nudges — talk back to a running stream

A plain stream is one-way: the server pushes, the client reads. But sometimes the client needs to _steer_ a live stream — "pause", "go faster", "skip ahead" — without tearing it down and losing its place. That's a **nudge**: a small typed message the client sends _into_ a running stream, which the generator reads between chunks. The classic case is an AI reply where the user hits pause or asks it to speed up.

On the server, declare a `nudges` map (each name mapped to a payload schema, or `null` for none), then read what arrived with `ctx.stream.nudges(yield chunk)` — reading is tied to yielding, so you check for nudges right when you're about to produce the next piece. On the client, the handle gains a typed `nudge(name, payload)` method.

::code-group

```typescript [server: ai.ts]
export const handleTokens = base.stream('start-tokens', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ token: string }>(),
  nudges: {
    pause: null,
    'speed-up': v.object({ factor: v.number() }),
  },
  async *run(ctx, input) {
    let delay = 50
    for (const word of input.prompt.split(' ')) {
      // yield a chunk, and read any nudges that arrived since the last yield
      const recent = ctx.stream.nudges(yield { token: word + ' ' })

      if (recent.some((n) => n.event === 'pause')) return

      const speedUp = recent.find((n) => n.event === 'speed-up')
      if (speedUp) delay = Math.max(1, delay / speedUp.payload.factor)

      await new Promise((r) => setTimeout(r, delay))
    }
  },
})
```

```typescript [client: app.ts]
const tokens = await socket.stream('start-tokens', { prompt: longPrompt })

// elsewhere — button handlers, say:
async function onSpeedUp() {
  await tokens.nudge('speed-up', { factor: 2 })
}
async function onPause() {
  await tokens.nudge('pause', {})
}

for await (const chunk of tokens) {
  render(chunk.token)
}
```

::

Each nudge the server reads is a `{ event, payload }` pair, both typed from the `nudges` map — and the client can only send names that map declares, with the right shape. `nudge(...)` returns a promise that resolves when the server confirms it; if it's refused or times out the promise rejects, but a rejected nudge does **not** end the stream. After a stream has finished, a nudge is a harmless no-op.

::tip
Only the client that started a stream can nudge it. Nudges keep the chunk-flow itself untouched — they turn a one-way push into a steerable conversation.
::
