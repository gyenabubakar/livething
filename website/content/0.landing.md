::landing-hero
#title

the framework for building realtime apps in typescript

#description
LiveThing is a typed, WebSocket-first realtime framework for TypeScript. Write your server, and your client gets its types from it, with no shared schema file and no code generation. A message carries typed JSON, or raw bytes such as a picture or a file. Rooms, requests, durable streams, presence and reconnection come built in.

#headline
The Contract

#title
Client types come from your server

#description
Describe your app once on the server, and the client gets its types from it. If the two sides stop matching, your editor shows a type error before the code runs.
:::

#headline
Channels

#title
Rooms with their own rules, API and presence

#description
Each channel is a room with its own join rule, its own typed events, requests and streams, and a live list of who is in it. Declare a family like `room:{roomId}` and every chat gets its own room. The rules run on your server, and a persistent channel puts members back in their rooms when they reconnect.
:::

#headline
Requests

#title
Requests over one socket

#description
Send a request and `await` a typed reply, with no request IDs to track. Send many at once, and each reply finds its own call even when replies arrive out of order. The server can send requests to the client too.
:::

#headline
Streaming

#title
Streaming responses, chunk by chunk

#description
Send each typed chunk as soon as it exists, which suits LLM output and live feeds. The client can nudge a stream while it runs, and a durable stream carries on after a disconnect.
:::

#headline
Reliability

#title
Reconnection and replay

#description
Laptops sleep, phones lose signal, and you deploy. LiveThing reconnects with backoff, holds what you send while offline, and replays what you missed without duplicates.
:::

#headline
Runs anywhere

#title
Runtime- and transport-agnostic

#description
The engine runs your contract, channels, requests and streams, but it never opens a socket. A small adapter feeds it messages, so the same app code runs over WebSocket or `http()`, on Node, Bun or Cloudflare.
:::

#headline
Split Streams

#title
Live where WebSocket can't go

#description
Company proxies, antivirus tools and school networks block WebSocket, and your users get a frozen app. A Split Stream gets through anyway: a live, two-way connection made of plain HTTP, with server-sent events coming down and POSTs going up. Add `http()` after `websocket()`, and the client switches on its own the moment WebSocket fails. Same app, same code, still live.
:::
