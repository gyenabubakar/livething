This page builds on the [Node.js adapter](/runtimes/adapters/node). It shows only what is different with SvelteKit. The options, limits, origins, compression, client IP, storage, admin API and shutdown work as that page explains.

A SvelteKit `+server` file answers with a `Response`, which cannot switch the connection to WebSocket: only the code that holds the Node socket can do that. So LiveThing must be attached to the Node HTTP server itself. This page does that in two places:

- In development, you attach LiveThing to the Node server that Vite creates.
- In production, you write a small custom Node server around the request handler that `adapter-node` builds.

```bash [pnpm]
pnpm add @livething/core @livething/server @livething/server-node
pnpm add -D @sveltejs/adapter-node
```

`adapter-node` builds your SvelteKit app as a Node request handler. This handler serves the built browser files, the prerendered pages and your SvelteKit routes.

Configure the adapter:

```js [svelte.config.js]
import adapter from '@sveltejs/adapter-node'

export default {
  kit: {
    adapter: adapter(),
  },
}
```

The build creates `build/handler.js`. The production server below imports it.

The finished server setup uses these files:

```text
huddle-endpoint.js
huddle-server.js
src/lib/server/huddle-definition.ts
svelte.config.js
vite.config.ts
```

`huddle-endpoint.js` and `huddle-server.js` are server-only. The runtime values in `huddle-definition.ts` are also server-only. Client code may import the inferred client contract from `huddle-definition.ts` with `import type`. TypeScript removes type-only imports, so that import is not in the browser build.

## Share the SvelteKit endpoint

```js [huddle-endpoint.js]
import { setup } from '@livething/server-node'
import { huddle } from './src/lib/server/huddle-definition.ts'

const shared = (globalThis[Symbol.for('huddle.endpoint')] ??=
  createHuddleEndpoint())

function createHuddleEndpoint() {
  const huddleNode = setup()
  const huddleEndpoint = huddleNode.bind(huddle, {
    sql: './data/huddle.sqlite',
  })
  return { huddleNode, huddleEndpoint }
}

export const { huddleNode, huddleEndpoint } = shared

export function handleHuddleUpgrade(request, socket, head) {
  const url = new URL(
    request.url ?? '/',
    `http://${request.headers.host}`,
  )
  if (url.pathname !== '/huddle') return false

  huddleEndpoint.upgrade(request, socket, head)
  return true
}
```

`huddle` is the [server definition](/server/server/overview) that contains your event handlers. Keep that file in TypeScript so it can export `InferClient<typeof huddle>` for your client. Node.js 24 runs the `.ts` file directly.

`handleHuddleUpgrade` sends upgrade requests for `/huddle` to LiveThing and returns `true`. For any other path, it does nothing and returns `false`.

The development config and the production server both import this module, so both use the same endpoint and the same `/huddle` path. Each process still creates its own LiveThing runtime. When your SvelteKit route code imports this module too, the `globalThis` check keeps one endpoint, as [React Router](/runtimes/node-frameworks/react-router#share-one-endpoint-with-route-code) explains.

## SvelteKit development server

During development, SvelteKit runs on Vite's Node HTTP server. A small Vite plugin connects LiveThing to that server. In the plugin's `configureServer` hook, it waits for LiveThing to be ready and adds the upgrade listener. Vite runs this hook before the server starts listening. Add the plugin before `sveltekit()`:

```ts [vite.config.ts]
import { sveltekit } from '@sveltejs/kit/vite'
import { defineConfig } from 'vite'
import { handleHuddleUpgrade, huddleNode } from './huddle-endpoint.js'

export default defineConfig({
  plugins: [
    {
      name: 'livething-huddle',
      async configureServer(vite) {
        if (!vite.httpServer) {
          throw new Error('Vite did not create an HTTP server')
        }

        await huddleNode.ready()
        vite.httpServer.on('upgrade', handleHuddleUpgrade)
        vite.httpServer.once(
          'close',
          () => void huddleNode.shutdown(),
        )
      },
    },
    sveltekit(),
  ],
})
```

Vite has its own WebSocket for hot updates. The upgrade function returns `false` for every path except `/huddle`, so Vite can still handle that WebSocket. When the development server stops, the `close` listener calls `huddleNode.shutdown()`, which closes LiveThing's connections, timers and storage.

## SvelteKit production server

Build SvelteKit with `adapter-node`. Then import the generated request handler into a Node server that your app owns:

```js [huddle-server.js]
import { createServer } from 'node:http'
import { handler } from './build/handler.js'
import { handleHuddleUpgrade, huddleNode } from './huddle-endpoint.js'

const server = createServer(handler)

server.on('upgrade', (request, socket, head) => {
  if (!handleHuddleUpgrade(request, socket, head)) socket.destroy()
})

await huddleNode.ready()
server.listen(
  Number(process.env.PORT ?? 3000),
  process.env.HOST ?? '0.0.0.0',
)

process.once('SIGTERM', async () => {
  await huddleNode.shutdown()
  server.close()
})
```

`handler` answers normal HTTP requests. The `upgrade` listener sends `/huddle` to LiveThing. This production process has no Vite hot-update WebSocket, so the server closes every other upgrade request. `huddleNode.ready()` waits for LiveThing's storage to start before the server accepts requests. On `SIGTERM`, `shutdown()` closes LiveThing first, and then `server.close()` stops the HTTP server.

Point your `start` script at the custom server:

```json [package.json]
{
  "scripts": {
    "start": "node huddle-server.js"
  }
}
```

Run `pnpm dev` during development. Run `pnpm build` and then `pnpm start` in production. The client connects to `/huddle` in both modes.

The endpoint can also offer `http()`, on its own or next to WebSocket. Its requests are plain HTTP requests, so both servers send them to LiveThing before SvelteKit: [Serve `http()`](#serve-http) shows the change.

## Serve `http()`

First add `transports` and the `handleHuddleRequest` function to `huddle-endpoint.js`, as [Serve `http()` on Node frameworks](/runtimes/node-frameworks/overview#express-koa-react-router-sveltekit-and-astro) shows. Keep the module's `globalThis` guard and its `handleHuddleUpgrade` function.

In development, add `vite.middlewares.use(handleHuddleRequest)` to the plugin's `configureServer` hook in [SvelteKit development server](#sveltekit-development-server), next to the `upgrade` listener. Vite runs that middleware before its own. In production, send each request to LiveThing first, and then to SvelteKit's handler:

```js [huddle-server.js]
import { createServer } from 'node:http'
import { handler } from './build/handler.js'
import { handleHuddleRequest } from './huddle-endpoint.js'

const server = createServer((request, response) => {
  handleHuddleRequest(request, response, () =>
    handler(request, response),
  )
})
```

The `upgrade` listener, `ready()` and the shutdown code of the production server stay the same.

## Call the admin API from a SvelteKit route

A server route can use the admin API:

```ts [src/routes/admin/announcements/+server.ts]
import { verifySession } from '../../../../auth.js'
import { huddleEndpoint } from '../../../../huddle-endpoint.js'

export async function POST({ request }: { request: Request }) {
  const token = request.headers
    .get('authorization')
    ?.replace(/^Bearer /i, '')
  const user = await verifySession(token) // your auth
  if (user?.role !== 'admin') {
    return new Response(null, { status: 401 })
  }

  const { text } = (await request.json()) as { text: string }

  const admin = await huddleEndpoint.admin()
  await admin.announce(text)

  return new Response(null, { status: 204 })
}
```

The route imports the same `huddle-endpoint.js` module as the Vite plugin and `huddle-server.js`, and the `globalThis` check in that module makes sure all of them get the one running endpoint. So the admin call reaches the users connected to `/huddle`, in development and in production.
