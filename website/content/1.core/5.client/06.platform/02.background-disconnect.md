An open socket in a tab that the user is not looking at still uses battery on the device and resources on the server. **Background disconnect** closes the socket after the app has been hidden for some time. When the user comes back, it opens the socket again right away. You don't write any of this code yourself.

You turn it on with the `backgroundDisconnectMs` option of `platform()`:

```typescript [client/socket.ts]
import {
  binary,
  client,
  connect,
  platform,
  reconnection,
} from '@livething/client'
import { WebEnvironment } from '@livething/client/environment'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  reconnection(),
  platform({
    environment: WebEnvironment,
    backgroundDisconnectMs: 30_000, // disconnect 30s after the tab is hidden
  }),
)
```

## How it behaves

The number is a **grace period**. The socket does not close the moment the tab is hidden:

- When the app becomes hidden, a timer starts. It runs for `backgroundDisconnectMs` milliseconds.
- If the app becomes visible **before** the timer ends, the timer is cancelled and nothing else happens. A quick switch to another tab never closes the socket.
- If the timer **does** end while the socket is still open, the socket is **suspended**. This means it is closed on purpose, and the close does not count as a connection drop that `reconnection()` should retry.
- When the app becomes visible again after that, the socket opens again automatically.

```text
// platform() does this for you:
// hidden ──30s──▶ suspend the socket
// visible ─────▶ open it again
```

So a short hide and return does not close the socket. Only a tab that stays hidden for the full grace period gets disconnected, and going back to it opens the socket again at once.

## What you can observe

Background disconnect uses the same public events as any other close and reopen. Any handlers you already have for these events also run for it:

| Moment               | Fires                                                | What you get                                                              |
| -------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------- |
| Suspend on hide      | `socket.onClose(...)`                                | `{ code: 1000, reason: 'background', wasClean: true }`                    |
| Open again on return | `socket.onOpen(...)`, then `socket.onReconnect(...)` | Channels have already rejoined and durable streams have already continued |

The return is handled as a **reconnect**, not as a new first connect. Each primitive does its usual reconnect work first: channels rejoin and durable streams continue, the same as after a network drop. Then your `socket.onOpen(...)` and `socket.onReconnect(...)` handlers run. So code attached to `socket.onReconnect(...)` also runs when the user comes back to a hidden tab.

## Edge cases it handles for you

- **The socket already closed for another reason.** Suppose a short network problem closes the socket while the tab is hidden. `platform()` then cancels its timer and does not mark the socket as closed by background disconnect. So coming back to the tab does not open it again. If you added `reconnection()`, that primitive handles the drop instead.
- **Starting hidden.** `platform()` starts to watch visibility at the start of each connection attempt, before the socket opens, and the environment reports the current visibility at that moment. That first report does not start the timer. Only a change from visible to hidden starts it. So if a socket connects in a tab that is already hidden, it is not disconnected until the user shows the tab and hides it again.
- **A manual `disconnect()` stops the watching.** If you call `socket.disconnect()` yourself, `platform()` removes its visibility and network listeners. Background disconnect (and network-aware reconnection) watch again only after you call `connect()` and the next connection attempt starts.

## It needs visibility

Background disconnect depends on the visibility signal, so the environment must have an `onVisibilityChange` method. If you set `backgroundDisconnectMs` with an environment that cannot report visibility, `client()` throws a `LiveThingConfigError` when it creates the socket. You see the mistake at once, instead of a feature that does nothing:

```typescript [client/socket.ts]
import { binary, client, connect, platform } from '@livething/client'
import { environment } from '@livething/client/environment'
import type { HuddleSocket } from '../server/huddle-definition'

const networkOnlyEnvironment = environment({
  onNetworkChange(callback) {
    const goOnline = () => callback(true)
    const goOffline = () => callback(false)
    window.addEventListener('online', goOnline)
    window.addEventListener('offline', goOffline)

    return () => {
      window.removeEventListener('online', goOnline)
      window.removeEventListener('offline', goOffline)
    }
  },
})

// networkOnlyEnvironment has onNetworkChange but no onVisibilityChange,
// so client() throws LiveThingConfigError
const socket = client<HuddleSocket>()(
  connect('wss://huddle.example.com/huddle'),
  binary(),
  platform({
    environment: networkOnlyEnvironment,
    backgroundDisconnectMs: 30_000,
  }),
)
```

If you leave `backgroundDisconnectMs` out (or set it to `0`), `platform()` only passes the signals on. It never closes the socket because the tab is hidden.

::note
The return to the tab opens the socket again without `reconnection()`. Add [`reconnection()`](/core/client/primitives/reconnection) as well, so that if this new connection fails (for example, because the network is still down), the socket keeps trying. The suspend itself is on purpose, so `reconnection()` does not retry it. The socket opens again only when the tab becomes visible.
::
