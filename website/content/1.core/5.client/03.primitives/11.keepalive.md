A **ping** is a small frame one side sends to ask "are you still there?". A **pong** is the reply. The time between sending a ping and getting its pong is the **round-trip latency**.

`keepalive()` makes the client send its own pings, measure round-trip latency, and close a connection that stops answering. It is opt-in. Without it, the client still **replies** to the server's pings. That reply is built into the socket, so the server does not drop you for being idle. But the client sends no pings of its own and measures no latency.

```typescript [client/socket.ts]
import { binary, client, connect, keepalive } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  keepalive({ maxMissedPongs: 2 }),
)
```

## The ping interval

The client pings as often as the server does. The server sends its ping interval in the first frame of every connection, and the client uses it. You set the interval once, on the server, with the server's [`keepalive({ pingIntervalMs })`](/core/server/capabilities/keepalive). So the two sides cannot disagree, for example a client that pings more slowly than the server's idle timeout. When the server sends no pings, because it does not list `keepalive()` or because the connection is a WebSocket that [hibernates](/core/server/server/hibernation), the client pings every 30 seconds.

On [`http()`](/core/client/transports/http), each ping and each pong goes up in a small POST, and the server's `pong` comes back on the stream. A POST is a billed request on Cloudflare, so client pings there add to the cost.

## The quality API

Connection quality only has a value when something measures pongs. So the quality [stores](/core/client/overview#reactive-stores) belong to this primitive. They are added to the socket only when you install `keepalive()`:

```typescript [client/socket.ts]
socket.quality // ReadableStore<'excellent' | 'good' | 'degraded' | 'poor' | 'disconnected'>
socket.latency // ReadableStore<number | null>: last round-trip in ms, null when not measured

const stop = socket.quality.subscribe((quality) => {
  updateConnectionIndicator(quality, socket.latency.get())
})
```

`socket.quality.get()` returns `'disconnected'` whenever the socket is not open. After the socket opens, it stays `'disconnected'` until the first pong arrives. There is no guessed value at open. The store publishes only when the tier changes.

`socket.latency` is set on every pong to that pong's round-trip time. A pong carries no id, so the client keeps only one ping in flight at a time, and each pong answers that ping. A pong slower than the ping interval therefore still reports its real round trip. `socket.latency` is `null` before the first pong, after a missed pong, and after the socket closes.

## The quality tiers

The tier comes from the average latency of the last 5 pongs, so one slow pong does not change it much. A missed pong is different: the tier changes to `'poor'` right away, without averaging. The `thresholds` option splits the average into tiers. The defaults are the same table the server uses for [`ctx.quality`](/core/server/capabilities/keepalive#what-it-adds-to-the-context), so both sides give the same tier for the same latency:

| Tier           | Default average latency           | Meaning      |
| -------------- | --------------------------------- | ------------ |
| `excellent`    | under 100 ms                      | fast         |
| `good`         | 100 to 299 ms                     | fine         |
| `degraded`     | 300 to 999 ms                     | slow         |
| `poor`         | 1000 ms or more, or a missed pong | bad          |
| `disconnected` | none                              | not measured |

Each side still measures its own pings, so at a given moment the client and the server can report different tiers. The client tier is only for your UI. It is not sent over the wire.

To use your own cut-offs, pass `thresholds`. `poor` is everything at or above `degraded`:

```typescript [client/socket.ts]
import { keepalive } from '@livething/client'

keepalive({
  thresholds: { excellent: 30, good: 100, degraded: 300 },
})
```

All three thresholds are required. Each must be a number, `0` or more, and they must not go down: `excellent` <= `good` <= `degraded`. Otherwise `keepalive()` throws a `LiveThingConfigError`. The same happens for a `maxMissedPongs` that is not a whole number of `1` or more.

## Reading it in your UI

A common use is a colored dot that shows the connection status:

```typescript [client/connection-dot.ts]
import type { ConnectionQuality } from '@livething/client'
import { setDotColor, setTooltip } from './huddle-ui'
import { socket } from './socket'

const dotColor: Record<ConnectionQuality, string> = {
  excellent: 'green',
  good: 'green',
  degraded: 'amber',
  poor: 'red',
  disconnected: 'grey',
}

socket.quality.subscribe((quality) => {
  setDotColor(dotColor[quality])
})

// null before the first pong, and again after a missed pong
socket.latency.subscribe((latency) => {
  setTooltip(latency === null ? 'measuring…' : `${latency} ms`)
})
```

`socket.quality` changes only when the tier changes. `socket.latency` changes on every pong and shows the latest single measurement, not the average. That is why the example listens to each store on its own.

Both are reactive stores, so you connect them to a UI framework with the same small [adapter](/core/recipes/framework-hooks/react) you use for the connection state.

## Missed-pong detection

Each ping expects a pong. When the next ping is due and the last one has no pong yet, the client counts one miss and sends no new ping. So a lost ping is never answered, and it ends in a missed-pong close. The client counts misses in a row:

- **1 missed pong** sets the quality to `'poor'` as an early warning, and sets `socket.latency` to `null`.
- **`maxMissedPongs` misses** (default `2`) mean the connection is dead, even though the connection has not closed. This is called a **half-open** connection: the socket still looks open in code, but no data gets through. The client closes it with close code `IDLE` (`4004`). Because the other side no longer answers, the browser may not get a reply to that close, and then `onClose` receives `1006` instead of `4004`. On `http()` there is no close handshake, so `onClose` always receives `4004`, with `wasClean` set to `true`. If [`reconnection()`](/core/client/primitives/reconnection) is installed, the client then reconnects.

This is why durable streams and long-lived sockets should use `keepalive()`. Without it, nothing checks that the other side still answers, so a half-open connection can stay open and nobody notices.

You can react to the early `'poor'` warning, to the close, or to both:

```typescript [client/weak-connection.ts]
import { CloseCodes } from '@livething/core'
import { showWeakConnectionBanner } from './huddle-ui'
import { socket } from './socket'

// Warn the user when quality drops, before the client closes the connection.
socket.quality.subscribe((quality) => {
  if (quality === 'poor') showWeakConnectionBanner()
})

// The close reaches onClose with code 4004 (IDLE), or 1006 when the
// other side never answered the close.
socket.onClose((event) => {
  if (event.code === CloseCodes.IDLE || event.code === 1006) {
    // The socket looked open but stopped answering. reconnection() opens a new one.
    console.warn('connection stopped answering, reconnecting')
  }
})
```

## Options

```typescript [client/socket.ts]
import { keepalive } from '@livething/client'

keepalive({
  maxMissedPongs: 2, // misses before the client closes the socket (default: 2)
  thresholds: { excellent: 100, good: 300, degraded: 1000 }, // tier cut-offs in ms (these are the defaults)
})
```

There is no option for the ping interval: it comes from the server (see [The ping interval](#the-ping-interval)). To turn client pings off, leave `keepalive()` out of `client(...)`.

Together, the ping interval and `maxMissedPongs` set the slowest round trip the client accepts. With the defaults, a pong must come back within about 60 seconds (30 seconds × `maxMissedPongs`). A slower pong arrives too late, because the client has already closed the socket.

## The other direction

Pings go both ways. The server can send its own pings, and the client answers them automatically. If the server lists the [`keepalive()`](/core/server/capabilities/keepalive) capability, it closes any connection that sends nothing for longer than its idle timeout, with close code `IDLE`. Any frame from the client resets that timer: a normal message or the automatic pong. LiveThing's client sends the pong for you. A client you write yourself in another language must also answer pings, or the server closes it as dead. The frames are plain text, not JSON arrays: the server sends the text `ping` and the client answers with the text `pong`. The client can also send `ping`, and the server answers `pong`.

The server does not always run that idle check. [Hibernation](/core/server/server/hibernation) is a Cloudflare Durable Objects mode where the server object is removed from memory while it has no work, and the socket stays open. For a WebSocket that hibernates, the server runs no idle timer, so it never closes a quiet client. The server keepalive page explains this in its hibernation section. If you need to detect a dead connection, keep `keepalive()` installed on the client. Then the client finds its own half-open connection and does not depend on the server.
