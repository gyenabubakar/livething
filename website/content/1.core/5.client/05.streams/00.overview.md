A **stream** is data that the server sends in many small pieces (called **chunks**) instead of all at once. Examples are the tokens of an LLM answer, the rows of a database query, or a live news feed. The [`stream()`](/core/client/primitives/stream) primitive page is the short reference. This chapter goes into full detail. It covers the handle and its iterator, nudges, automatic reconnect, reattaching of durable streams, and listen-only broadcast streams.

For the server side (writing the generator that produces the chunks, and the difference between plain and recorded streams), see [Streams](/core/server/streams/overview) in the Server section. Everything on this page is about the client.

## Two ways to consume a stream

A stream can start from the client or from the server, and each case uses a different method:

- **You start it.** You call `stream(...)`. The server runs a generator only for you. You read the chunks with a `for await` loop over the **handle**.
- **The server broadcasts it.** The server sends one stream to many clients. You did not start it, so there is no handle. Instead, you pass callback functions to `onStream(...)`, and they run as chunks arrive.

A third method, `continueStream(...)`, connects you again to a **durable** stream that you started earlier. A durable stream is one the server keeps, so it can continue after a disconnect. You use `continueStream(...)` after a page reload, or from another tab.

| Method                                      | What it does                       | You get back            |
| ------------------------------------------- | ---------------------------------- | ----------------------- |
| `stream(event, payload, options?)`          | Start a stream and read it         | `Promise<StreamHandle>` |
| `onStream(event, handlers)`                 | Listen to a broadcast stream       | an unsubscribe function |
| `continueStream(event, streamId, options?)` | Reattach to a durable stream by ID | `StreamHandle`          |

## The contract side

All three methods get their types from the `streams` key of your contract. Each entry has these parts:

- `payload`: the data that starts the stream.
- `chunk`: the shape of each piece the stream sends.
- `kind`: `'ephemeral'` or `'persistent'`.
- `nudges` (optional): a map of messages you can send into a running stream.

```typescript [shape]
interface HuddleSocket {
  streams: {
    'run-task': {
      payload: { goal: string; roomId: string }
      chunk: { step: string; detail: string }
      kind: 'ephemeral' // or 'persistent' for a durable stream
      nudges: { 'add-context': { text: string } } // optional mid-stream messages
    }
  }
}
```

`kind: 'persistent'` is what allows [`continueStream(...)`](/core/client/streams/durable-and-continue) for that stream. Passing an `'ephemeral'` stream to `continueStream(...)` is a type error. [`nudges`](/core/client/streams/nudges) gives the types for the `nudge(...)` method on the handle.

## Streams of bytes

A stream can send bytes, such as Huddle's [`download-attachment`](/core/server/binary/streams#binary-streams), which sends a file in pieces. With [`binary()`](/core/client/primitives/binary) installed next to `stream()`, read it with `socket.binary.stream(...)`, listen to a broadcast one with `socket.binary.onStream(...)`, or continue a recorded one, such as Huddle's [`export-room-pdf`](/core/server/binary/streams#recorded-binary-streams), with `socket.binary.continueStream(...)`. Everything in this chapter works the same, except that each chunk is `{ info, bytes }`. The [binary streams](/core/client/primitives/binary#streams) section has the details.

## Pair durable streams with keepalive

A durable stream waits for its next chunk. Sometimes a connection becomes **half-open**: it stops working, but no close frame arrives, so the client does not know it is dead. The stream cannot detect this by itself. Without help, the loop waits until the per-chunk timeout fails it, or forever if you turned that timeout off. The stream does not continue.

[`keepalive()`](/core/client/primitives/keepalive) sends regular pings, so it notices the dead connection. [`reconnection()`](/core/client/primitives/reconnection) then opens a new connection, and the stream continues on it. Add both next to `stream()` whenever you use persistent streams.

In debug mode, a durable stream started with `stream()` logs a warning when `keepalive()` is missing. A `continueStream()` reattach does not log this warning, so don't depend on the warning to find the problem.
