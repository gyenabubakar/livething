When you test UI that reacts to a socket, the main question is: "When this event arrives, does my code do the right thing?" A unit test should not need a real WebSocket server to answer that. LiveThing has four helpers for this: `inject` and `injectChannel` for JSON messages, and `injectBinary` and `injectChannelBinary` for binary messages. They push a fake message through the **real** incoming pipeline. The incoming pipeline is the list of steps that every message from the server goes through before it reaches your code. So your `.on()` handlers, intercepts, and primitives all run the same way they do in production. The socket never has to connect.

All four come from the `@livething/client/testing` subpath. The binary ones are covered in [Injecting a binary message](#injecting-a-binary-message):

```ts [client/socket.test.ts]
import {
  inject,
  injectBinary,
  injectChannel,
  injectChannelBinary,
} from '@livething/client/testing'
```

## Injecting an event

`inject(socket, event, payload)` delivers a message as if the server sent it. The message goes through the full incoming pipeline in this order:

1. The `onIncoming` hook of `dedup()`.
2. Your intercepts.
3. The `onIncoming` hook of every other primitive (channels, streams, and the others).
4. Your `.on()` handlers.

It works even while the socket is `'closed'`. It does not open the socket. It puts the message directly into the same pipeline that a real frame goes through:

```ts [client/socket.test.ts]
import { binary, client, connect } from '@livething/client'
import { inject } from '@livething/client/testing'
import { expect, test, vi } from 'vitest'
import type { HuddleSocket } from '../server/huddle-definition'

test('shows an incoming notification', () => {
  const socket = client<HuddleSocket>()(
    connect('wss://example.com/huddle'),
    binary(),
  )

  const handler = vi.fn()
  socket.on('notification', handler)

  inject(socket, 'notification', {
    title: 'Reminder',
    body: 'Standup in 5 minutes',
  })

  expect(handler).toHaveBeenCalledWith({
    title: 'Reminder',
    body: 'Standup in 5 minutes',
  })
  expect(socket.state.get()).toBe('closed') // never connected
})
```

The test never calls `socket.connect()`, so it tests the handler logic alone. There is no network and there are no timers, so the test gives the same result every time.

## Injecting a channel message

The client finds the right channel for a message by reading a channel tag on the frame. A plain `inject` adds no tag, so its message does not reach a channel handler. Use `injectChannel` instead. It takes the socket, the event name, and `{ channel, payload }`, and adds the channel tag to the frame, so the `channels()` primitive delivers the message to that channel's handlers:

```ts [client/room.test.ts]
import { binary, channels, client, connect } from '@livething/client'
import { injectChannel } from '@livething/client/testing'
import { expect, test, vi } from 'vitest'
import type { HuddleSocket } from '../server/huddle-definition'

test('routes a message to the announcements channel', () => {
  const socket = client<HuddleSocket>()(
    connect('wss://example.com/huddle'),
    binary(),
    channels(),
  )

  const handler = vi.fn()
  socket.channel('announcements').on('announcement', handler)

  injectChannel(socket, 'announcement', {
    channel: 'announcements',
    payload: { text: 'Office closed Friday for the holiday' },
  })

  expect(handler).toHaveBeenCalledWith({
    text: 'Office closed Friday for the holiday',
  })
})
```

The channel tag decides which handlers run:

- An `injectChannel` call for `announcements` runs only the handlers of `announcements`. It never runs the handlers of another channel.
- A plain `inject(socket, 'announcement', …)` is _not_ a channel message. It does not reach any channel handler.
- `injectChannel` needs the `channels()` primitive on the socket to route the message, the same as in a real app.

A fixed channel, such as `announcements`, is named by its name. One channel of a dynamic family, such as one of Huddle's rooms, is named with `{ family, name }`. The family name alone would reach no handle, so TypeScript does not accept it:

```ts [client/room.test.ts]
import { injectChannel } from '@livething/client/testing'
import { socket } from './socket'

const general = { family: 'rooms', name: 'room:general' } as const
injectChannel(socket, 'message', {
  channel: general,
  payload: {
    id: 'm-7',
    text: 'hi',
    from: 'u_amara',
    sentAt: 1717000000000,
  },
})
```

## Injecting a binary message

`injectBinary` and `injectChannelBinary` do the same for [binary messages](/core/client/primitives/binary). The info and the bytes take the place of the payload:

<!-- docs-check: skip -->

```ts
injectBinary(socket, event, { info, bytes? })
injectChannelBinary(socket, event, { channel, info, bytes? })
```

They reach `binary.on(...)` listeners, and a normal `on(...)` listener never sees them. The bytes default to an empty `Uint8Array`. The socket needs `binary()`, as in the app. For a channel of a dynamic family, such as one of Huddle's rooms, pass `{ family, name }`:

```ts [client/screen-share.test.ts]
import { binary, channels, client, connect } from '@livething/client'
import {
  injectBinary,
  injectChannelBinary,
} from '@livething/client/testing'
import { expect, test, vi } from 'vitest'
import type { HuddleSocket } from '../server/huddle-definition'

test('paints a shared screen and shows the avatar preview', () => {
  const socket = client<HuddleSocket>()(
    connect('wss://example.com/huddle'),
    binary(),
    channels(),
  )
  const picture = new Uint8Array([137, 80, 78, 71])

  const onPreview = vi.fn()
  socket.binary.on('avatar-preview', onPreview)
  injectBinary(socket, 'avatar-preview', {
    info: null,
    bytes: picture,
  })
  expect(onPreview).toHaveBeenCalledWith(null, picture)

  const onFrame = vi.fn()
  socket
    .channel('rooms', 'room:general')
    .binary.on('screen-frame', onFrame)
  injectChannelBinary(socket, 'screen-frame', {
    channel: { family: 'rooms', name: 'room:general' },
    info: { from: 'u_amara' },
    bytes: picture,
  })
  expect(onFrame).toHaveBeenCalledWith({ from: 'u_amara' }, picture)
})
```

An injected message skips the frame parser, so the listener gets the array you passed, not a view of a frame.

## Intercepts and primitives still run

Injection uses the real pipeline, so every step before your handlers runs too. For example, an [`intercept`](/core/client/primitives/intercept) that throws `Block` drops the injected message before it reaches `.on()`. It does the same with a real message:

```ts [client/socket.test.ts]
import { binary, client, connect, intercept } from '@livething/client'
import { Block } from '@livething/client/errors'
import { inject } from '@livething/client/testing'
import { expect, test, vi } from 'vitest'
import type { HuddleSocket } from '../server/huddle-definition'

test('an intercept can block an injected notification', () => {
  const doNotDisturb = true

  const socket = client<HuddleSocket>()(
    connect('wss://example.com/huddle'),
    binary(),
    intercept((m) => {
      if (m.event === 'notification' && doNotDisturb) throw Block
    }),
  )

  const handler = vi.fn()
  socket.on('notification', handler)

  inject(socket, 'notification', {
    title: 'Reminder',
    body: 'Standup in 5 minutes',
  })

  expect(handler).not.toHaveBeenCalled() // the intercept dropped it
})
```

So you can test more than "did my handler run". You can also check that your filters, deduplication, and other primitives do the right thing with a known input.

## The injectors are typed from your contract

`inject` and `injectChannel` use the same contract type as `client<HuddleSocket>()`. TypeScript checks the event name, the channel name and the payload shape when it compiles the test. A typo or a wrong payload is a type error, so the test cannot pass by mistake. The `socket` below is a `client<HuddleSocket>()` socket like the ones above:

```ts [client/socket.test.ts]
import { inject, injectChannel } from '@livething/client/testing'
import { socket } from './socket'

inject(socket, 'notification', {
  title: 'Reminder',
  body: 'Standup in 5 minutes',
})

// @ts-expect-error 'nope' isn't an incoming event
inject(socket, 'nope', {
  title: 'Reminder',
  body: 'Standup in 5 minutes',
})

inject(socket, 'notification', {
  // @ts-expect-error title must be a string
  title: 42,
  body: 'Standup in 5 minutes',
})

// @ts-expect-error 'lobby' isn't a channel on this contract
injectChannel(socket, 'announcement', {
  channel: 'lobby',
  payload: { text: 'hi' },
})
```

The test and your `.on()` handlers use the same `HuddleSocket` type. When the contract changes, the test stops compiling and shows you what to update.

## Beyond unit tests

`inject` and `injectChannel` cover events that the server pushes and channel messages. This is most of what a client does. Some flows need a real server:

- a `request()` that must get its matching response
- a request from the server that your code answers with `onRequest()`
- the chunks of a stream
- reconnection
- the wire protocol itself

For these, write an end-to-end test. `inject()` and `injectChannel()` send frames without the routing data that LiveThing uses to match a response to its request, or a chunk to its stream. So they cannot test request matching or stream grouping. Use a real server, or a small echo server, for those flows.
