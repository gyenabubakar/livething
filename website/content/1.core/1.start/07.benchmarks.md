LiveThing does more work for each message than a raw WebSocket server: it checks the message, finds the handler, builds the `ctx`, and tracks channel members. This page shows what that work costs on Node.js. It compares LiveThing with the same app written on [`ws`](https://github.com/websockets/ws), the WebSocket library that `@livething/server-node` uses, and on [Socket.IO](https://socket.io), a popular realtime library.

## What was measured

The benchmark runs one small chat app on three servers:

- **LiveThing**: the app on `@livething/server-node`, with channels. The channels are [ephemeral](/core/server/channels/defining#membership-keep-membership-after-a-reconnect), the default: a member leaves when its connection closes, and LiveThing keeps the members only in memory. This works like the rooms of the other two servers.
- **Plain `ws`**: the same app written directly on `ws`, with no framework. It reads each message, parses the JSON, and keeps a list of members for each room. It sends every message the simple way: one `ws.send()` call for each recipient.
- **Socket.IO**: the same app on Socket.IO, with its rooms. Compression is off, as it is on the other two servers.

All three servers send the same events with the same payloads. Each step uses JSON messages, except the binary steps, which send raw bytes.

The app runs over WebSocket on all three servers. It also runs over the fallback transport of each framework: [`http()`](/core/runtimes/transports/http) on LiveThing, and HTTP long-polling on Socket.IO. See [Over the fallback transports](#over-the-fallback-transports).

LiveThing runs with [presence off](/core/server/channels/membership-and-presence#turning-presence-off), because the other two servers do not tell members who joined or left. [Joining a channel](#joining-a-channel) also shows LiveThing with presence on.

The server runs alone on one machine. 2,000 real clients run on a second machine in the same data center and connect over its private network. They use the `ws` client for LiveThing and plain `ws` over WebSocket, the Socket.IO client for Socket.IO, and a small HTTP client that follows the LiveThing protocol for `http()`. For each step, the benchmark reads how much CPU time the **server** process used and divides it by the units of work in that step: one connection, one message, one join or one delivery. CPU time for each unit changes little with the speed of the clients.

The tables below turn that CPU time into **how many units one CPU core can handle per second**. Higher is better. Memory is the one exception: there, lower is better. In each row, the best result is in **bold** on a green background. The second best is in _italics_ on a yellow background. Under each of them, small text says how many times better it is than the next result: the best against the second, and the second against the third. Node.js runs your JavaScript on one thread, so one core is the limit for one server process.

### Warmed up and cold start

Every table has two tabs. Pick one, and every table on the page shows it.

- **Warmed up**: the server runs every step once, then the benchmark runs every step again with new clients and shows the second time. This is how a server costs after it has been running for a while.
- **Cold start**: each step runs once, in a server that has just started. This is how a server costs in its first seconds, after a deploy or a restart.

The two differ because Node.js compiles your code while it runs. V8, the JavaScript engine of Node.js, first runs a function slowly, then makes a faster version of the functions that run often. It builds those faster versions on other threads, and the benchmark counts the CPU time of every thread of the server. So the first time a step runs, its numbers include some of that compiling. A short step, like a join step, shows it the most. The server's code is the same in both tabs.

In a channel of 2,000 members, LiveThing handles **5.8 times** as many deliveries as plain `ws`, and **5.1 times** as many as Socket.IO.

A broadcast sends the same message to many members. Most of its cost is not JavaScript. It is the **system call**: the request that hands bytes to the operating system to send. Plain `ws` makes one system call for each message to each member. LiveThing does two things to cut this cost:

- **It builds a broadcast message once.** The bytes of the WebSocket message are made one time and written to every member, instead of once for each member. This saves JavaScript work.
- **It sends a connection's messages together.** Node.js reads the messages that arrive together, from all clients, and runs their handlers one after another. LiveThing holds what those handlers send until Node.js has run them all. Then it copies each connection's small messages into one buffer and sends it in one system call. So when several handlers broadcast, each member gets all of their messages in one write. This saves system calls. The order of the messages does not change, and a message never waits for new data from the network. A connection that has 64 KiB waiting sends it at once.

In this benchmark, each sender sends several messages in a row (10 in the big channel, 5 in the channels of 10), so the server often handles several broadcasts at once, and their messages to each member go out together. An app that sends one broadcast at a time gets less from the second change. Both changes work only when compression is off, which is the default: with `compression` on, each member's message is compressed and sent on its own.

You can write both changes yourself in a `ws` server. LiveThing does them for every app that runs on the Node.js adapter's own server or on Fastify. The Hono and h3 adapters do not use them yet.

Here LiveThing does extra work that plain `ws` does not do. For each message, LiveThing checks that the message follows the LiveThing [wire protocol](/core/learn/wire-protocol), routes it to its handler, and gives the handler a typed `ctx`. For each request, it also matches the reply to the request. For each connection, it runs the sign-in hook and sets up the connection's state. The app in this benchmark has no payload schemas. A schema on a handler adds the cost of your validator.

That work shows here. Warmed up, plain `ws` handles **1.6 times** as many echoes as LiveThing and **1.9 times** as many requests. It is also faster for connections and disconnects, and it uses the least memory.

Socket.IO also does work for each message, and LiveThing is close to it. Warmed up, the two handle about the same number of echoes and disconnects, Socket.IO handles 9 percent more requests, and LiveThing handles 4 percent more new connections and uses less memory. At a cold start, LiveThing handles 10 percent more echoes than Socket.IO, and Socket.IO 18 percent more requests.

## Over the fallback transports

When a client cannot use WebSocket, LiveThing can use [`http()`](/core/runtimes/transports/http): the server sends with server-sent events on one long HTTP response, and the client sends with POST requests. Socket.IO has no server-sent events. Its fallback is **HTTP long-polling**: the client keeps a GET request open until the server has data for it, and sends with POST requests.

The same 2,000 clients and the same steps run over both fallbacks. LiveThing runs in its two modes:

- **Batch mode** on HTTP/1.1: the client sends with short POSTs. Every browser supports it. A proxy must pass the stream on without holding it, as in [Origins, CORS and proxies](/core/runtimes/transports/http#origins-cors-and-proxies).
- **[Stream mode](/core/runtimes/transports/http#stream-mode)** on HTTP/2: the client sends all its messages in one long POST. The server serves the HTTP/2 streams with [`handleStream`](/core/runtimes/adapters/node#less-memory-on-http2). The benchmark uses HTTP/2 without TLS, as no column here uses TLS.

Socket.IO long-polling runs on HTTP/1.1. The WebSocket column of LiveThing is there to show what a fallback costs, so the marks only compare the three fallbacks.

- **A JSON broadcast in a big channel can cost less than on WebSocket.** Both modes send the messages that wait for one member as one buffer, in one write. In the channel of 2,000 members, both modes handle more deliveries than WebSocket. In the channels of 10 and for binary broadcasts, WebSocket costs less. In the channel of 2,000 members, batch mode handles **2.9 times** as many deliveries as Socket.IO, and stream mode **3.0 times**.
- **A message from a client costs more than on WebSocket.** In batch mode, messages come in short POSTs, and each POST is a new HTTP request that carries the messages waiting at that moment. So an echo costs about twice as much CPU as on WebSocket, or more at a cold start. In stream mode, all messages come in one open request, so an echo costs 35 to 50 percent more.
- **Socket.IO is faster than batch mode for echo and requests, and uses the least memory.** Stream mode is the fastest of the three for echo and requests, but uses the most memory: it holds two open HTTP/2 streams for each client.
- **Big binary messages cost more than on WebSocket, and the most in stream mode.** Server-sent events carry only text, so both modes send bytes as base64, which is a third bigger. It builds the base64 of a broadcast once for all members. With 64 KiB messages, batch mode handles **7.2 times** as many deliveries as Socket.IO, and stream mode **4.1 times**. For a 64 KiB echo, Socket.IO is the fastest of the three.
- **Batch mode is the fastest for new connections**, and a little faster than stream mode for disconnects. A stream-mode client also opens its long POST and checks that it works.

The fallback is for the clients that cannot use WebSocket. Most clients still connect over WebSocket, so most of your server's work has the costs in the WebSocket tables.

In Node.js, the Socket.IO long-polling client opens a new TCP connection for every request unless it gets an HTTP agent that keeps connections open. Browsers keep connections open, so the benchmark gives the client such an agent, and the server keeps idle connections for 65 seconds. The operating system queues only so many new connections that the server has not accepted yet (on macOS, only 128), so both HTTP clients open at most 100 new connections at a time (16 in all when the clients run in several processes), and every client opens its connections the same way. In stream mode, each client opens one HTTP/2 connection.

## What the numbers mean for your app

- **One server process can do a lot.** Even the slowest number over WebSocket, about 1,500 joins per second into one big channel with presence on, is far more than most apps see.
- **Busy broadcast apps gain the most.** Chat rooms, live dashboards and multiplayer state send one message to many people, often several at once. That is where LiveThing uses the least CPU.
- **Your handlers cost more than LiveThing does.** A handler that reads a database or calls another service takes milliseconds. Here, one core handles about 55,000 echoes a second on LiveThing and 87,000 on plain `ws`. So one echo costs less than a fiftieth of a millisecond on either.
- **A server costs more in its first seconds.** Right after a start, V8 is still compiling the server's code, so the same work costs more CPU. The cold start tab shows how much.
- **TLS adds CPU.** The clients here are in the same data center as the server and do not use TLS. Over the internet, each message takes longer to arrive, and TLS (`wss://` and `https://`) adds CPU that these numbers do not include. Every server pays that cost the same way.

The results depend on the machine, the Node.js version and the size of the messages. Run the benchmark on your own machine to see your numbers.

## Run it yourself

The benchmark is in the LiveThing repository. Clone it, install the dependencies, and build the packages:

```bash
pnpm install
pnpm build
```

Then run each server with 2,000 clients from the Node.js adapter's folder. `LOAD_PRESENCE=off` turns presence off on LiveThing, as the tables do, and the other servers ignore it:

```bash
cd server-adapters/node
LOAD_PRESENCE=off node bench/load.mjs livething 2000
node bench/load.mjs ws 2000
node bench/load.mjs socket.io 2000
```

Run the fallback transports with `livething-http` (batch mode), `livething-http-stream` (stream mode) and `socket.io-polling`. `LOAD_H2_ENTRY=stream` serves the HTTP/2 streams with `handleStream`, as the table does:

```bash
LOAD_PRESENCE=off node bench/load.mjs livething-http 2000
LOAD_PRESENCE=off LOAD_H2_ENTRY=stream node bench/load.mjs livething-http-stream 2000
node bench/load.mjs socket.io-polling 2000
```

These commands give the cold start numbers. Add `LOAD_WARM=on` to any of them for the warmed-up numbers: the benchmark then runs every step twice in the same server and prints only the second time.

```bash
LOAD_WARM=on LOAD_PRESENCE=off node bench/load.mjs livething 2000
```

Leave out `LOAD_PRESENCE=off` to run LiveThing with presence on. `LOAD_BINARY_SIZES` sets the sizes of the binary steps, in bytes (default: `1024,65536`), and an empty value skips them. The top of `bench/load.mjs` lists every environment variable it reads.

Each run prints one line for each step. `cpuUsPerUnit` is the server's CPU time for one unit, in microseconds. One second divided by that number gives the units per second that the tables show.

### Run every table at once

One command runs every server in both tabs, 5 rounds in a new order each round, as the tables do:

```bash
cd server-adapters/node
pnpm bench:load core
```

That is 14 runs in each round, so it takes a while. Try `BENCH_ROUNDS=1` first to see how long one round takes on your machine.

The results go to a new folder in `bench-results`, named after the date and time. `summary.json` has the median of each step: units per second on one core, memory and time. `runs.jsonl` has every run. Leave out `core` to also run the chat app, which stores its messages in SQLite.

### Run the server on another machine

On one machine, the clients and the server share the CPU. To measure the server alone, run it on a second machine in the same network. On each machine, clone the repository with `git` and run the setup script. It works on Linux (Ubuntu or Amazon Linux 2023) and needs `sudo`. It installs build tools, Node.js and pnpm, then installs and builds the packages:

```bash
sh server-adapters/node/bench/setup-machine.sh
```

The client machine must reach the server machine on ports 9100 and 9101. On the server machine, start the benchmark's server with the machine's private IP address, the address inside the network:

```bash
cd server-adapters/node
node bench/load-remote.mjs 10.0.1.20
```

On the client machine, run the benchmark with the same IP address in `LOAD_SERVER`:

```bash
cd server-adapters/node
LOAD_SERVER=10.0.1.20 pnpm bench:load core
```
