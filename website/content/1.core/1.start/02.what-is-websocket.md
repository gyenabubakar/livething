LiveThing is WebSocket-first, so it helps to know what a WebSocket is. This page is a short introduction to the protocol that LiveThing uses. It covers how a WebSocket differs from HTTP, how it compares with other realtime options, and why a raw WebSocket is not enough on its own. If you already know WebSockets well, go to [Why LiveThing](/core/start/why-livething).

## HTTP asks, WebSocket talks both ways

The web runs on HTTP. In HTTP, each exchange happens once: the client sends a request, the server sends a response, and the exchange ends. The server can only send data as an answer to a request. To show "live" updates over HTTP, the client has to _poll_. Polling means the client asks again and again: "Is there anything new?" This wastes requests, and the updates always arrive a little late.

A **WebSocket** works in a different way. It is a single connection that stays open. While it is open, **either side can send a message at any time**, as many times as it wants. Each message adds only a few bytes of extra data. This two-way connection that stays open makes realtime features easy to build: chat, live cursors, AI answers that arrive word by word, and presence.

|                  | HTTP request                 | WebSocket                           |
| ---------------- | ---------------------------- | ----------------------------------- |
| Shape            | One request, one response    | One long-lived connection           |
| Who can send     | Client asks, server answers  | Both sides, any time                |
| Lifetime         | Closes after the response    | Stays open until either side closes |
| Per-message cost | Full headers every time      | A few bytes of framing              |
| Good for         | Fetching and submitting data | Live updates, push, back-and-forth  |

_Framing_ is the small header the protocol adds to each message to mark where the message starts and ends.

## How a connection opens

A WebSocket starts as an ordinary HTTP request that asks to **upgrade**. This first exchange is called the _handshake_. The browser sends a normal `GET` request with a few special headers. If the server agrees, it replies with `101 Switching Protocols`. From then on, the same TCP connection is used as a two-way WebSocket.

```text [client request]
GET /huddle HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
```

```text [server response]
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
```

The handshake is the only moment when the connection looks like a normal HTTP request, with a URL, headers, and cookies. This makes it the right place to **authenticate** the user. LiveThing gives you a function that runs at this moment, called the [`authenticate` hook](/core/server/server/authenticate).

::note
WebSocket URLs have their own schemes. `ws://` is the plain version and **`wss://`** is the version encrypted with TLS. They match `http://` and `https://`. Use `wss://` in production, the same way you use `https://` for a website.
::

## Messages, not a byte stream

After the connection opens, the two sides exchange **messages**, not a continuous stream of bytes. Each send is one separate message. It is a **text** message, usually a string of JSON, or a **binary** message: raw bytes. LiveThing uses both. Most messages are JSON text, and [binary messages](/core/learn/wire-protocol#binary-frames) carry bytes such as pictures and files. The protocol also has a few **control messages** that the browser handles for you:

- `ping` and `pong`: a heartbeat. One side sends `ping`, and the other side answers `pong` to show it is still there.
- `close`: the last message. It carries a number called a **close code** that says why the connection ended.

So the model is simple: one open connection, separate messages in both directions, and a clean close at the end.

## The raw browser API

Every browser has a built-in `WebSocket` object. This is the whole API:

```typescript [client/raw-huddle-socket.ts]
const ws = new WebSocket('wss://example.com/huddle')

ws.addEventListener('open', () => {
  ws.send(JSON.stringify({ type: 'hello', name: 'Ada' }))
})

ws.addEventListener('message', (event) => {
  const data = JSON.parse(event.data) // event.data is a string. You parse it yourself.
  console.log('got', data)
})

ws.addEventListener('close', (event) => {
  console.log('closed', event.code, event.reason)
})

ws.addEventListener('error', () => {
  console.log('something went wrong')
})

// later
ws.close(1000, 'done')
```

You open a socket, listen for four events, `send()` strings, and call `close()`. It is a useful building block, but a low-level one.

## How WebSocket compares to the alternatives

WebSocket is not the only way to build realtime features on the web. The right choice depends on which direction the data needs to travel. _Latency_ below means the delay between an event and the moment the other side sees it.

- **Split Streams.** Two one-way streams that make one two-way connection out of plain HTTP: a GET whose response stays open carries events down (Server-Sent Events, below), and a POST whose body stays open carries messages up. Where a browser or network can't keep the POST open, short POSTs carry the messages instead. It works where WebSocket is blocked, with one request each way instead of one per message. LiveThing builds it for you. [Introduction to Split Streams](/core/start/split-streams) explains how it works.
- **Short polling.** The client asks "Is there anything new?" on a timer. It is very simple and works everywhere. But it wastes requests, because most answers are empty. It is also slow: the delay can be as long as the timer interval.
- **Long polling.** The client sends a request, and the server _holds it open_ until it has something to send. Then the server answers, and the client sends a new request right away. Latency is lower than short polling. But every message still needs a new request, so connections open and close all the time. Socket.IO starts with long polling by default, and then upgrades to WebSocket when it can.
- **Server-Sent Events (SSE).** A browser standard (the `EventSource` API) for a one-way stream from the server to the client, sent over one long-lived HTTP response. It is simple, it reconnects on its own, and it uses plain HTTP. But data only flows **one way**: the client cannot send data back over it. It also carries **text only**. It fits notifications, feeds, and progress updates, where the client only listens.
- **WebSocket.** One connection, **both directions**, text or binary, with very little extra data per message. It is the general choice for two-way realtime, and every modern browser and server runtime supports it.
- **WebTransport.** A newer API built on HTTP/3 and QUIC. Like WebSocket, it sends data both ways. It also adds **unreliable datagrams**: small messages that can be lost and are not sent again. Games and media use them, because for them a lost packet is better than a late one. All major browsers support it only since 2026, and many servers, hosting platforms, and older browsers do not support it yet.
- **WebRTC data channels.** These connect two browsers directly (**peer-to-peer**, or P2P), not a browser and a server. They run on UDP, so latency is very low. Messages can be unreliable and arrive out of order if you choose. They are made for video, voice, and P2P games. To connect two peers, you need a signalling step and STUN/TURN servers. This is a different problem from "talk to my server."

| Approach            | Direction                | Best for                                         |
| ------------------- | ------------------------ | ------------------------------------------------ |
| Split Streams       | Both ways, over HTTP     | Two-way realtime where WebSocket is blocked      |
| Short polling       | Client asks, repeatedly  | The simplest "is it done yet?" check             |
| Long polling        | One way per held request | Near-realtime updates without WebSocket support  |
| Server-Sent Events  | Server → client only     | Notifications, feeds, and progress (listen-only) |
| **WebSocket**       | **Both ways**            | **General-purpose two-way realtime**             |
| WebTransport        | Both ways (+ datagrams)  | Games and media on newer browsers and servers    |
| WebRTC data channel | Peer-to-peer             | Video, voice, and P2P games                      |

::note
You may also hear two other names. They work at a layer _above_ this list and do not replace it. **MQTT** is a publish/subscribe messaging protocol. It is common in IoT, and in the browser it often runs _over_ a WebSocket. **gRPC** also supports streaming. But its browser version (gRPC-Web) cannot stream in both directions at once, so gRPC is mostly used between servers, not for browser realtime.
::

For a typical app that needs two-way communication with its server, WebSocket is the default choice. It has broad support, a simple model, and traffic in both directions. Use SSE when you only send data _to_ the client. Use a [Split Stream](/core/start/split-streams) where a network blocks WebSocket. Consider WebTransport when you need datagrams and your platforms support it. Use WebRTC when the connection is truly peer-to-peer.

## What a raw WebSocket doesn't give you

Look at what the example above does _not_ do:

- **No types.** `event.data` is only a string. You call `JSON.parse` and hope the data has the shape you expect.
- **No reconnection.** If the connection drops (a laptop goes to sleep, the network fails, or the server restarts during a deploy), it stays closed.
- **No request and reply.** You cannot send a message and `await` an answer.
- **No rooms.** There is no built-in way to send a message to a group of users.
- **No catch-up.** Messages sent while a client was offline are lost to that client.
- **No dead-connection check.** Nothing notices a connection that stopped working without closing.

A raw WebSocket only carries messages. You must build everything else that a real app needs yourself. You also build it without types, on both the client and the server, so the two sides can stop matching without any error.

LiveThing provides these missing parts.
