A raw WebSocket is a good low-level building block, but it is not enough to build a real app on. When real users start to use it, you have to write the same extra code again and again. And none of that code is typed.

## The problem with writing it yourself

The browser gives you `new WebSocket(url)`, `send()`, and four events. You must build everything else yourself:

- **Reconnection.** Connections drop because of deploys, short network problems, or a laptop that goes to sleep. You need **backoff** and **jitter**. Without them, 10,000 clients can all reconnect at the same moment and overload the server.
- **Keepalive.** Proxies close connections that have been idle for some time. You need to send small **ping** messages and check that a **pong** reply comes back. You also need a way to find a **half-open** connection: one that looks open on your side, but the other side is gone.
- **Request and response.** A WebSocket message gets no reply by default. If a message needs an answer, you must invent **correlation IDs** and keep a list of requests that are still waiting.
- **Rooms.** To send messages to a group, you must track who is in which group, check access when someone joins, and send each message only to the right group.
- **Catching up after a drop.** A client can miss messages while it is offline. To send them again, you need sequence numbers and **replay** (sending the missed messages again).
- **Blocked networks.** Some company proxies, antivirus tools and school networks block WebSocket. Your app needs a second way to talk over plain HTTP, and it must keep every message in order and send none twice.
- **Bytes.** To send a picture or a file, you either put it in JSON as base64 text, which makes it about a third bigger, or you design your own binary format and parse it on both sides.
- **Types.** None of this code is typed. Event names are plain strings. Payloads are `any`. The server and the client slowly stop matching, and you find the mismatch only when the app breaks for users.

In the end, you write a small framework inside your app, without type safety.

## What LiveThing gives you

LiveThing is that framework, written once and typed from the server to the client. Every feature is **opt-in**: you add only the features you need.

- **A typed contract.** TypeScript infers it from your server code, and the client uses the same types. The two sides always match, and your editor can autocomplete every event and payload.
- **Reconnection** with exponential backoff and jitter (`reconnection()`).
- **Keepalive** with pings and detection of missed pongs (`keepalive()`).
- **Request and response** over the socket, in both directions: client to server and server to client (`clientRequests()` and `serverRequests()`).
- **Channels.** These are rooms that the server manages. You can add an access check that runs before a client joins. The server tracks who is a member, and you can send messages to one channel only (`channels()`).
- **Streaming** for data that arrives in parts, such as tokens from an AI model. This includes durable streams, which continue after a client disconnects and reconnects (`stream()`).
- **Replay** to get the messages a client missed while it was disconnected (`replay()`).
- **Binary messages** for pictures, files and audio: the bytes travel as they are, with a small typed JSON info next to them, in events, requests and streams (`binary()`). Large files go in pieces, and resume after a drop (`uploads()`).
- **A fallback over plain HTTP.** Where a network blocks WebSocket, the client moves to a [Split Stream](/core/start/split-streams): server-sent events down, and POSTs up (where the browser and the network allow it, one POST whose body stays open). Your app code does not change (`http()`).
- **Deduplication**, **message buffering**, and more. Each one is a separate primitive.

Because every feature is opt-in, your bundle contains only the code for the features you import. This is true on the client and on the server.

## Bundle size

LiveThing ships one module per feature. Every package is marked as **side-effect free**, which tells your bundler that a module does nothing when it is imported. So the bundler can remove every module you don't use. This is called **tree-shaking**.

The sizes below count only LiveThing's own code. Two kinds of third-party code are left out:

- The libraries that `@livething/server-node` depends on: `ws` (the WebSocket server) and `better-sqlite3` (the SQLite driver). They are installed with the adapter, but they are not part of the numbers. `better-sqlite3` is a native module, so a bundler cannot include it anyway.
- Web frameworks such as Hono, Fastify, and H3. You install the one you use yourself.

### Server

On the server, bundle size barely matters. Users never download server code, and a Node.js server loads it once at startup. Cloudflare is the one place where it counts: a Worker's uncompressed size is [limited to 64 MiB](https://developers.cloudflare.com/workers/platform/limits/), and a larger Worker can start more slowly.

Server sizes are minified, not gzipped, because server code is not downloaded over the network. A minimal server app includes the **engine**: the code that handles connections, sends each message to the right handler, and manages storage. Every adapter includes it.

Each capability that you list adds its own code to the minimal app. A capability that you leave out adds nothing.

The server includes [valibot](https://valibot.dev), a schema validation library. The server uses it to check every message of the LiveThing wire protocol, so valibot is already inside the numbers above. If you also write your handler schemas with valibot, they add little extra code, because they use the same valibot code. LiveThing accepts any [Standard Schema](https://standardschema.dev) validator. But if you use a different validator library, your bundle contains that library's code as well as valibot's.

## How it compares

LiveThing does not try to solve every problem, and it is not always the right choice.

### Versus a raw WebSocket

Some apps send only a few messages, never need a reply, and never reconnect. For those apps, a raw WebSocket is enough, and LiveThing adds more than you need. LiveThing becomes useful when you need reconnection, types, requests, rooms, or catching up after a drop. LiveThing stays small when your needs are small. But for the simplest apps, a raw WebSocket is still the simpler choice.

LiveThing is also faster than a hand-written `ws` server where realtime apps work the hardest: broadcasts. In a channel of 2,000 members, one CPU core of a warmed-up server delivers **5.8 times** as many messages with LiveThing as with plain `ws`, and **5.1 times** as many as with Socket.IO. The [Server Benchmarks](/core/start/benchmarks) page has every number, including what the checks, routing and typed `ctx` cost for each message.

### Versus Socket.IO

[Socket.IO](https://socket.io) is a popular realtime library for JavaScript. LiveThing differs from it in four ways:

- **Types come from your server code.** In Socket.IO, you can type your events, but you write the event interfaces yourself and keep the client and server copies in sync. LiveThing infers one contract from the server code. So if you change an event on the server, TypeScript shows an error at every place on the client that no longer matches.
- **Channels do more than rooms.** Compared with Socket.IO rooms, LiveThing channels also give you an access check that runs before a client joins, member tracking, and requests and streams that belong to one channel. All of this is typed.
- **A different fallback.** When WebSocket is blocked, Socket.IO uses long polling: the server ends a request each time it sends events, so the client opens a new one after every answer. LiveThing uses a [Split Stream](/core/start/split-streams), which keeps one request open each way where the browser allows it.
- **Any language can talk to it.** The [wire protocol](/core/learn/wire-protocol) is plain JSON over a normal WebSocket (or over plain HTTP with LiveThing's [`http()` transport](/core/runtimes/transports/overview)), and a binary message is the same JSON in front of the bytes, with a 9-byte header. A client written in another language can connect to a LiveThing server without a special library.
