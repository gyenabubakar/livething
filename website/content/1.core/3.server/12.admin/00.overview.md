Every handler you write runs **because a socket did something**. A client connected, or it sent a message. So the handler's `ctx` belongs to that one socket: `ctx.connection.id` is that client's ID, and `ctx.send(...)` replies to that client.

But many things happen **outside** the socket layer and still need to change the live state. Your auth provider sends a `user.deleted` webhook. A cron job archives old rooms at midnight. An admin clicks "remove member" in a separate dashboard. None of these is a WebSocket client. The trigger arrives over HTTP, from a queue, or from a timer. That code needs a typed, safe way to reach the running server.

That way is the **admin surface**: a set of operations you call from your own server code. You get it from the object your adapter gives you. On Node, `bind(...)` returns an endpoint (called `huddleEndpoint` on this page), and you call `await huddleEndpoint.admin()`. On Cloudflare, you call `await stub.admin()` on the Durable Object stub.

## It has no current connection

An admin operation runs when no socket is involved. So its context is **connectionless**: there is no "current connection" to act on. It has no `ctx.connection.id`, `ctx.send`, `ctx.meta`, or `ctx.close`. If you use one of them, TypeScript reports a compile error.

Instead, it has operations for the whole server: broadcast to everyone, find a channel by name, remove a user everywhere, and read storage. The `onShutdown` hook and scheduled tasks work the same way. They are connectionless too.

Both parts below use Huddle's `base`. The `api` in the second part is an example. It replaces the `api` of Huddle's `assemble(...)` call.

```typescript [server/admin-api.ts]
import * as v from 'valibot'
import { base } from './base'
import { handleSendDigest } from './huddle-definition'

// Inside a handler: a socket is the subject.
const handleRename = base.on('rename', {
  input: v.object({ name: v.string() }),
  run(ctx, input) {
    ctx.connection.id // ✓ this client
    ctx.send('user-renamed', {
      userId: ctx.user.id,
      name: input.name,
    }) // ✓ reply to this client
  },
})

// An admin operation: no socket is the subject.
base.assemble({
  handlers: [handleRename, handleSendDigest],
  api: (ctx) => ({
    evict(userId: string) {
      // @ts-expect-error: there is no "this client"
      ctx.connection.id
      ctx.purgeUser(userId) // ✓ act on the whole server
    },
  }),
})
```

## Two kinds of operation

The admin surface has two layers.

**[Built-in operations](/core/server/admin/context)** come with LiveThing. You do not write them. `broadcast`, `purgeUser`, `closeConnections`, `connections`, `users`, and the others are always there. A few more come with their capability: `channels` comes with [`channels()`](/core/server/capabilities/channels), and `schedule` and `cancelScheduled` come with [`scheduled()`](/core/server/capabilities/scheduled). If the capability is not in your server, these members do not exist on `ctx`, and using them is a compile error. On Cloudflare, [the stub](/core/server/admin/reaching-it) has the same built-ins in the same shape, for example `admin.users.get(id).broadcast(…)`.

**Your own operations** are the [`api`](/core/server/admin/authoring) you write on `assemble`. It is a factory. The object holds the methods you want the outside caller to have.

Huddle's own `announce` sends to the `announcements` channel. This smaller version sends to every connection:

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'

const base = server({
  capabilities: [emits({ announcement: t<{ text: string }>() })],
})

export const huddle = base.assemble({
  handlers: [],
  api: (ctx) => ({
    announce(text: string) {
      ctx.broadcast('announcement', { text })
    },
  }),
})
```

Later, from a Node webhook or cron job:

```typescript [server/jobs.ts]
import { huddleEndpoint } from './huddle-endpoint'

const admin = await huddleEndpoint.admin()
await admin.announce('Maintenance in 5 minutes') // your own operation
await admin.purgeUser('user_9') // a built-in
```

On Cloudflare, the same two calls go through the Durable Object stub:

```typescript [worker.ts]
import type { Env } from './helpers'

export default {
  async fetch(request: Request, env: Env) {
    const id = env.HUDDLE_SERVER.idFromName('global')
    const admin = await env.HUDDLE_SERVER.get(id).admin()
    await admin.announce('Maintenance in 5 minutes')
    await admin.purgeUser('user_9')

    return new Response('ok')
  },
}
```

::warning
**Built-in names win.** Your `api` might return a method with the same name as a built-in, for example your own `broadcast`. In that case LiveThing keeps the built-in and drops your method. Your method cannot replace a LiveThing operation. Give your own operations different names.
::

Some names already have a meaning in JavaScript, and they follow a different rule. These names are `then`, `constructor`, `__proto__`, `toString`, `valueOf`, and every other name on `Object.prototype`. An `api` method with one of these names would break the admin surface. For example, a `then` method makes `await chat.admin()` wait forever. So LiveThing **throws a `LiveThingConfigError`** when the server starts, because it builds the admin surface once at startup to check the names. It does not drop these methods without telling you. Rename the method.

There is one exception. If your `api` factory returns a class instance, JavaScript adds a `constructor` property to the class prototype automatically. LiveThing ignores that property. A `constructor` member that your own code defines is still rejected.
