You add your own admin operations with the `api` field of `assemble`. The `api` field is a factory, which means a function that builds and returns an object. It receives the connectionless [admin context](/core/server/admin/context) and returns an object of methods. Code outside the socket layer can then call those methods through the adapter's admin surface.

Huddle's own `api` has one method, `announce`. In the examples on this page, the `api` is shown alone on a smaller Huddle server. In your app, you write it in the `assemble(...)` call of `server/huddle-definition.ts`, and it replaces the `api` that is there.

::code-group

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'

const base = server({
  capabilities: [emits({ announcement: t<{ text: string }>() })],
})

export const huddle = base.assemble({
  handlers: [],
  api: (ctx) => ({
    announce(text: string) {
      ctx.broadcast('announcement', { text })
    },
    onlineCount() {
      return ctx.connectionCount
    },
  }),
})
```

```typescript [huddle-server.ts]
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const huddleEndpoint = setup().bind(huddle, {
  sql: './data/huddle.sqlite',
})

const admin = await huddleEndpoint.admin()
admin.announce('Huddle restarts in 5 minutes')
const live = admin.onlineCount()
```

```typescript [worker.ts]
import { bind } from '@livething/server-cloudflare'
import { huddle } from './server/huddle-definition'

export class HuddleServer extends bind(huddle) {}

export default {
  async fetch(request: Request, env: Env) {
    const id = env.HUDDLE_SERVER.idFromName('global')
    const admin = await env.HUDDLE_SERVER.get(id).admin()
    await admin.announce('Huddle restarts in 5 minutes')
    const live = await admin.onlineCount()

    return Response.json({ live })
  },
}

interface Env {
  HUDDLE_SERVER: {
    idFromName(name: string): unknown
    get(id: unknown): InstanceType<typeof HuddleServer>
  }
}
```

::

LiveThing runs the `api` factory once when the server starts, and again each time you get the admin surface. Every method you return becomes a call on the admin surface, next to the built-in operations such as `purgeUser`.

How you get the admin surface depends on the runtime, as the `huddle-server.ts` and `worker.ts` tabs above show. On Node, it comes from the endpoint that `bind(...)` returns (called `huddleEndpoint` above). On Cloudflare, it comes through the Durable Object stub, which is the object your Worker uses to call one Durable Object.

On Cloudflare, every call goes from the Worker to the Durable Object, which is a remote call. So every call returns a promise, even when your method returns nothing. Only some values can [cross that boundary](/core/server/admin/reaching-it).

::note
A built-in operation always wins over your own method with the same name. For example, if you return a method called `purgeUser` or `plugin`, callers still get the built-in one, and your method is ignored. The admin type shows only the built-in. Give your methods their own names. A few names, such as `then` and `constructor`, are not allowed at all, because JavaScript already gives them a meaning. If you use one, the server fails at startup with a `LiveThingConfigError`.
::

## The `ctx` is connectionless

The `ctx` your factory receives is the admin context. It is a view of the whole server, with no current socket. `ctx.send`, `ctx.connection.id`, and `ctx.meta` are **not** on it, so using one of them is a compile error. Instead you get `ctx.broadcast`, `ctx.connections`, `ctx.users`, `ctx.purgeUser`, `ctx.closeConnections`, `ctx.sql`, and the rest of the members listed in [Admin Context](/core/server/admin/context).

Members that belong to a capability follow the same rules here as in your handlers. `ctx.channels` needs [`channels()`](/core/server/capabilities/channels) in the capabilities list. `ctx.schedule` and `ctx.cancelScheduled` need [`scheduled()`](/core/server/capabilities/scheduled). Without the capability, the member is not on the type, so reading it is a compile error. This is better than a call that does nothing and gives no error.

```typescript [server/admin-api.ts]
import { base } from './base'
import { handleSendDigest } from './huddle-definition'

export const huddleWithAnnounce = base.assemble({
  handlers: [handleSendDigest],
  api: (ctx) => ({
    announce(text: string) {
      ctx.broadcast('announcement', { text }) // ✓ whole-server
      // @ts-expect-error: no current connection here
      ctx.send('announcement', { text })
    },
  }),
})
```

## Return types reach the caller

Whatever a method returns becomes the caller's result. TypeScript infers its type, so you do not declare a response schema. A method that returns a value is a read. A method that returns nothing is an action.

```typescript [server/admin-api.ts]
import { base } from './base'
import { handleSendDigest } from './huddle-definition'

export const huddleWithBans = base.assemble({
  handlers: [handleSendDigest],
  api: (ctx) => ({
    // read: the return type reaches the caller
    bans() {
      return ctx.sql
        .exec<{ id: string }>('SELECT id FROM bans')
        .toArray()
    },
    // action: returns nothing
    async deleteAccount(id: string) {
      await ctx.purgeUser(id)
    },
  }),
})
```

::note
This is the `api` of the **top-level** server. A plugin's `assemble` also takes an `api`. It gets the same kind of `ctx`, with the plugin's own names. Admin code reaches it with [`admin.plugin(id)`](/core/server/plugins/scoped-ctx#calling-the-api-from-admin-code), and a host handler with `ctx.plugin(id)`.
::

## `purgeUser` cleans up all durable data

`ctx.purgeUser(id)` removes a user everywhere: channel membership, persistent tags, inbox rows and read receipts, their last-seen mark, their durable streams, and their [uploads](/core/server/binary/resuming#the-upload-record). It marks each upload that is not done for cleanup and starts a sweep. The sweep runs that upload's `onDiscard` later, and `ctx.purgeUser` does not wait for it. If an `onDiscard` throws, the next sweep runs it again. Then it closes their live sockets. From the moment it starts, their sockets take no more messages, a subscribe waiting in `check` ends with no membership, and nothing saves a new row for them, so the cleanup cannot miss one. It does not need a capability of its own. It cleans up only the durable data that exists for that user. For a capability you did not list, there is nothing to clean up, so that step does nothing.

Every cleanup step runs, even if an earlier step throws. The live sockets are always closed. If any step failed, `ctx.purgeUser` rejects after all steps have run. The error is an `AggregateError` that holds all the failures, not only the first one.

It also stops every recorded stream the user started: `ctx.stream.signal` fires, the generator ends, and the subscribers of a broadcast stream get its end. The purge does not wait for a generator that is still in an `await`, so pass the signal to slow work.

By default, it also deletes the content of any [broadcast stream the user created](/core/server/admin/context#broadcast-streams-the-user-created). This is the safe choice for a "delete this user's data" call. Pass `{ keepBroadcastContent: true }` to keep that content instead.
