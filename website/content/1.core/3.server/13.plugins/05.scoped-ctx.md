A plugin uses `ctx` in three places:

- **Inside** the plugin, its handlers receive a **scoped** `ctx`. "Scoped" means the `ctx` works only inside the plugin's own part of the server. Short names point to the plugin's own capabilities and emits.
- **In its `authenticate`**, the plugin receives a scoped `ctx` too, with its `ctx.kv` keys namespaced to the plugin. [Authoring](/core/server/plugins/authoring#the-scoped-authenticate) covers it.
- **Outside** the plugin, the host calls the plugin's `api` through `ctx.plugin(id)`, and admin code through `admin.plugin(id)`.

This page covers the first and the last.

## The scoped `ctx` inside a plugin

A plugin's handlers get the same `ctx` that a top-level server's handlers get: `ctx.send`, `ctx.kv`, `ctx.tags`, `ctx.channels`, `ctx.schedule`, and the rest. The difference is that every name points to the **plugin's own** part of the server. You write short names, and LiveThing adds the plugin's namespace for you (see [Namespacing](/core/server/plugins/namespacing)).

```typescript [polls/polls-definition.ts]
import { emits, server, t } from '@livething/server'
import * as v from 'valibot'

const h = server({
  scope: 'plugin',
  capabilities: [
    emits({
      'poll-updated': t<{
        pollId: string
        votes: Record<string, number>
      }>(),
    }),
  ],
})

const vote = h.on('vote', {
  input: v.object({ pollId: v.string(), option: v.string() }),
  async run(ctx, input) {
    const votes =
      ((await ctx.kv.get(`poll:${input.pollId}`)) as
        | Record<string, number>
        | undefined) ?? {}

    votes[input.option] = (votes[input.option] ?? 0) + 1

    // The ctx.kv key is namespaced too, so it never collides with the host's keys
    await ctx.kv.set(`poll:${input.pollId}`, votes)

    // 'poll-updated' is the plugin's own emit. It goes out as
    // __acme:polls::poll-updated, which matches the plugin's emits(...)
    ctx.send('poll-updated', { pollId: input.pollId, votes })
  },
})
```

The plugin `ctx` has no field for your own settings, such as API keys. If a plugin needs such values, it should accept them in its [factory function](/core/server/plugins/authoring) and use them when it builds its scoped handlers (the handlers can read them because they are defined inside that function).

The scoped `ctx` only has the fields for the capabilities the plugin listed. For example, a plugin that lists `emits(...)` but not `channels()` has `ctx.send` but no `ctx.channels`. Reading a field the plugin did not declare is a compile error, the same as on a top-level server.

## The `api` a plugin exposes

A plugin can expose an **API** with the `api` field of its scoped `assemble(...)`. The `api` field is a factory function that returns an object with the methods the host can call. You write it next to the handlers it uses. Then `plugin(...)` wraps the assembled result.

The factory receives the plugin's scoped **connectionless** `ctx`: the same `ctx` that a [scheduled task](/core/server/handlers/scheduled) and the [admin `api`](/core/server/admin/context) get, with the plugin's short names. It has `broadcast`, `connections`, `users`, `channels` (with `channels()`), `kv`, `sql`, `schedule` (with `scheduled()`), `log` and `platform`. It has no `ctx.connection` or `ctx.send`, because the same API serves every caller, and admin code has no connection at all. A method that needs the caller takes it as an argument, such as `polls.vote(pollId, ctx.user.id)`.

```typescript [polls/polls-definition.ts]
import { emits, server, t } from '@livething/server'
import { plugin } from '@livething/server/plugins'
import * as v from 'valibot'

const h = server({
  scope: 'plugin',
  capabilities: [
    emits({
      'poll-updated': t<{
        pollId: string
        votes: Record<string, number>
      }>(),
    }),
  ],
})

const vote = h.on('vote', {
  input: v.object({ pollId: v.string(), option: v.string() }),
  async run(ctx, input) {
    const votes =
      ((await ctx.kv.get(`poll:${input.pollId}`)) as
        | Record<string, number>
        | undefined) ?? {}

    votes[input.option] = (votes[input.option] ?? 0) + 1
    await ctx.kv.set(`poll:${input.pollId}`, votes)
    ctx.send('poll-updated', { pollId: input.pollId, votes })
  },
})

const polls = h.assemble({
  handlers: [vote],
  api(ctx) {
    return {
      async createPoll(question: string, options: string[]) {
        const pollId = crypto.randomUUID()
        // Uses the plugin's scoped ctx, so the key is namespaced
        await ctx.kv.set(
          `poll:${pollId}`,
          Object.fromEntries(options.map((option) => [option, 0])),
        )
        await ctx.kv.set(`poll-question:${pollId}`, question)
        return pollId
      },
      async results(pollId: string) {
        return (
          ((await ctx.kv.get(`poll:${pollId}`)) as
            | Record<string, number>
            | undefined) ?? {}
        )
      },
    }
  },
})

export const Polls = plugin('acme:polls', {
  definition: polls,
})
```

## Calling the API with `ctx.plugin(id)`

Any host handler can get a registered plugin's API with `ctx.plugin(id)`. So can the host's code that has no connection: a scheduled task, the `onShutdown` hook and the host's own admin `api`. TypeScript suggests only the IDs of the plugins that the host listed. The return type is that plugin's `api` type, so the call is fully typed and needs no casts. In this smaller Huddle server, `Polls()` is listed in `capabilities` next to two poll events:

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import * as v from 'valibot'
import { Polls } from './polls'

export const base = server({
  capabilities: [
    Polls(),
    emits({
      'poll-created': t<{ pollId: string }>(),
      'poll-results': t<{ votes: Record<string, number> }>(),
    }),
  ],
})

const handleGetResults = base.on('get-poll-results', {
  input: v.object({ pollId: v.string() }),
  async run(ctx, input) {
    const polls = ctx.plugin('acme:polls') // typed to the plugin's api
    const votes = await polls.results(input.pollId)
    ctx.log.info('poll results', { pollId: input.pollId, votes })
  },
})
```

LiveThing builds the API object the first time any code calls `ctx.plugin(id)`, and keeps it. Every later call, from any handler or connection, returns the same object, so the plugin's `api` factory runs once for each running server (on Cloudflare, once for each Durable Object instance). State the factory keeps in a variable is shared by every caller, and it is lost when the server restarts or the Durable Object sleeps. Keep anything that must last in `ctx.kv` or `ctx.sql`.

::note
[Errors](/core/core/error-model) from a plugin are [namespaced](/core/server/plugins/namespacing) too. When a plugin handler throws an error that the plugin declared, such as `denied()`, the client receives the code `__acme:polls::denied`, not just `denied`. So a plugin's error codes never collide with the host's.
::

::warning
`ctx.plugin(id)` only takes the ID of a plugin the host listed. Any other ID is a type error, and a type argument can't widen it. On a server with no plugins, `ctx.plugin` itself is a type error. In plain JavaScript, where nothing checks the ID, an unknown ID throws when the code runs:

```text
[livething] plugin('acme:polls') — no plugin with id 'acme:polls' is registered. List the plugin in server({ capabilities: [...] }).
```

A listed plugin whose `assemble` has no `api` throws a `LiveThingConfigError` that says `plugin('acme:polls') has no api`.
::

## Calling the API from admin code

Admin code, such as a cron job or a webhook, reaches the same API with `admin.plugin(id)`. It is typed the same way as `ctx.plugin(id)`. On Node, it is the plugin's API object itself. Here a small Huddle server lists `Polls()`, and a nightly job reads one poll's results:

::code-group

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { Polls } from './polls'

const base = server({ capabilities: [Polls()] })

export const huddle = base.assemble({ handlers: [] })
```

```typescript [server/huddle-endpoint.ts]
import { setup } from '@livething/server-node'
import { huddle } from './huddle-definition'

export const huddleNode = setup()
export const huddleEndpoint = huddleNode.bind(huddle, {
  sql: './data/huddle.sqlite',
})
```

```typescript [server/poll-report.ts]
import { huddleEndpoint } from './huddle-endpoint'

export async function logPollResults(pollId: string) {
  const admin = await huddleEndpoint.admin()
  const votes = await admin.plugin('acme:polls').results(pollId)
  console.info('poll results', { pollId, votes })
}
```

::

On Cloudflare, the stub's admin surface has the same `plugin(id)`. Each call goes over Workers RPC to the Durable Object, so every method returns a promise, and only the API's methods reach the Worker. A plain value on the API object does not, so read such a value through a method.

::code-group

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { Polls } from './polls'

const base = server({ capabilities: [Polls()] })

export const huddle = base.assemble({ handlers: [] })
```

```typescript [worker.ts]
import { bind } from '@livething/server-cloudflare'
import { huddle } from './server/huddle-definition'

export class HuddleServer extends bind(huddle) {}

interface Env {
  HUDDLE_SERVER: DurableObjectNamespace<HuddleServer>
}

export default {
  async fetch(request: Request, env: Env) {
    const pollId =
      new URL(request.url).searchParams.get('pollId') ?? ''
    const id = env.HUDDLE_SERVER.idFromName('global')
    const admin = await env.HUDDLE_SERVER.get(id).admin()
    const votes = await admin.plugin('acme:polls').results(pollId)

    return Response.json(votes)
  },
}
```

::

`admin.plugin(id)` takes only the ID of a plugin the server lists. Any other ID is a type error, and on a server with no plugins, `admin.plugin` itself is a type error. In plain JavaScript, an unknown ID throws the same error as `ctx.plugin(id)`. On Cloudflare, an API method named `then`, `dup` or `constructor` throws too, because a Workers RPC stub can't call a method by any of those names. A getter on the API object never reaches the stub, and it is not run.

### A larger example

Here the `acme:polls` plugin's api exposes `createPoll` and `results` methods. In a version of Huddle with the polls plugin added, `base` lists `Polls()` and emits `poll-created` and `poll-results`. That version calls the plugin from two handlers:

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import * as v from 'valibot'
import { Polls } from './polls'

const base = server({
  capabilities: [
    Polls(),
    emits({
      'poll-created': t<{ pollId: string }>(),
      'poll-results': t<{ votes: Record<string, number> }>(),
    }),
  ],
})

const handleCreatePoll = base.on('create-poll', {
  input: v.object({
    question: v.string(),
    options: v.array(v.string()),
  }),
  async run(ctx, input) {
    const polls = ctx.plugin('acme:polls')
    const pollId = await polls.createPoll(
      input.question,
      input.options,
    )
    ctx.send('poll-created', { pollId })
  },
})

const handleGetResults = base.on('get-poll-results', {
  input: v.object({ pollId: v.string() }),
  async run(ctx, input) {
    const polls = ctx.plugin('acme:polls')
    ctx.send('poll-results', {
      votes: await polls.results(input.pollId),
    })
  },
})

export const huddle = base.assemble({
  handlers: [handleCreatePoll, handleGetResults],
})
```

## One plugin per ID

A server can list each plugin **only once**. `plugin('acme:polls', ...)` returns a factory, and you list its result (`Polls()`) once. The host stores its plugins by ID, so the same plugin can't be registered twice. Listing an ID twice throws at `assemble()`:

```text
[livething] plugin('acme:polls') is listed more than once. Each plugin id owns a namespace and must be unique — list it once, or give the second one a different id.
```

If you need two of something, write two plugins with different IDs (`acme:cache-east`, `acme:cache-west`), or keep several copies inside one plugin's own state.

[Client plugins](/core/client/plugins/overview) follow the same rule: each client plugin ID can be registered only once on a socket.
