Inbox keeps a stored row for each member until that member acknowledges it. If a member never comes back, their rows would keep growing forever. The `retention` option puts a limit on that queue. When a member is behind and the limit is reached, the server **evicts** the member's oldest rows to make room. This page covers that eviction, the **overflow watermark** it records, and the `__gap__` frame. The `__gap__` frame tells a reconnecting client: "you missed some messages, and the earliest ones are gone."

## Limiting stored rows with `retention`

`retention` limits how many rows inbox keeps **per member**. It takes three optional limits. Each one must be a positive whole number:

| Field         | What it does                                                                                                                                                                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `maxMessages` | Keep at most this many rows per member. An acknowledged row is already deleted, so all of these rows are undelivered.                                                                                                                                  |
| `maxAgeMs`    | Remove rows by age, in milliseconds. A row older than this is removed. Every removed row is undelivered, so each removal raises an overflow watermark.                                                                                                 |
| `maxBytes`    | Keep at most this many bytes per member: each row's payload as JSON (or a binary event's info), plus a binary event's bytes. The oldest rows go first. A message that alone is bigger is [not sent at all](/core/server/inbox/overview#binary-events). |

```typescript [server/dms.ts]
import { emits, t } from '@livething/server'
import { inbox } from '@livething/server/inbox'
import { base, Message } from './base'

const dms = base.channel(['dms', 'dm:{pair}'], {
  membership: 'persistent',
  capabilities: [
    inbox({
      retention: { maxMessages: 500, maxAgeMs: 86_400_000 },
    }),
    emits({ message: t<Message>() }),
  ],
})
```

Here `dms` is a smaller version of Huddle's, with a `retention` limit that Huddle's `dms` does not have. Each member keeps at most 500 rows, and any row older than one day is removed. The server deletes a row as soon as it is acknowledged, so the limit applies to the undelivered queue. Without `retention`, a member's queue has no limit. That is fine for channels where members reconnect quickly. It is risky for channels where a member might stay away for a long time.

::note
A live broadcast and [`ctx.channel.inbox.backfill(...)`](/core/server/inbox/delivery) both check `retention` right after they insert rows. `maxMessages` and `maxBytes` remove rows when a new row could go over the count or the bytes. The server also checks them again when it starts, so a changed limit applies to rows that are already stored. `maxAgeMs` also sets a stored alarm for the time the earliest row expires, so old rows are removed even when the channel is quiet. The server has one stored alarm, and scheduled tasks use it too. Because the alarm is saved, it still fires after the server hibernates or restarts. Cleanup can happen after the age limit only when the platform fires the alarm late.

A row is removed when it is strictly older than `maxAgeMs`. So cleanup never happens before the configured age, and it normally happens at the first alarm after that point. Each time the server starts, it also removes rows that have already expired, before its normal startup work. Every removed row is undelivered, so removing one raises a watermark, and the member's next reconnect reports the lost range with `__gap__`. If you must delete data by a fixed legal deadline, do not depend on the platform alarm firing on time. Add your own external check.
::

## What overflow means

A member can be behind because they are offline or because their client has not acknowledged yet. When a new broadcast pushes such a member's queue past `maxMessages`, the server evicts the **oldest stored rows** to make room. Each eviction raises the member's **overflow watermark**. The watermark is a stored sequence number: the highest sequence among the lost rows.

Here is a small example. This `dms` uses `maxMessages: 1`, so each member keeps at most one undelivered row.

```typescript [server/dms.ts]
import { emits, t } from '@livething/server'
import { inbox } from '@livething/server/inbox'
import * as v from 'valibot'
import { base, Message } from './base'

const dms = base.channel(['dms', 'dm:{pair}'], {
  membership: 'persistent',
  capabilities: [
    inbox({ retention: { maxMessages: 1 } }),
    emits({ message: t<Message>() }),
  ],
})

export const handleSendMessage = dms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: payload.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

Now follow an overflow step by step:

::steps{level="3"}

### Both members subscribe

Alice and Bob both subscribe to `dm:alice+bob`, so both are stored members.

### Alice goes offline

Alice's connection closes. Her one-row queue is empty, and she stays a member of `dm:alice+bob`.

### First broadcast fills the queue

Bob broadcasts `m1`. Alice's queue holds one row: `m1`.

### Second broadcast overflows

Bob broadcasts `m2`. Alice is already at her one-row limit, so the server **evicts** `m1` and sets her overflow watermark to the sequence of `m1`. Her queue now holds `m2`.

::

Alice has lost `m1` permanently. The next sections show how her client learns about it.

## The `__gap__` frame in the drain

When Alice reconnects, the [reconnect drain](/core/server/inbox/delivery#the-reconnect-drain) runs. Her overflow watermark is set, so the server sends a `__gap__` frame for the channel **before** the rows that are still stored:

```json
// server -> client, before the stored rows
["__gap__", { "missedThrough": 1 }, { "channel": { "name": "dm:alice+bob", "family": "dms" } }]

// then the stored row
["message", { "id": "m2", "text": "second", "from": "bob", "sentAt": 1767225600000 }, { "channel": { "name": "dm:alice+bob", "family": "dms" }, "delivery": { "id": "msg_k7q2_2", "seq": 2 } }]
```

The gap comes first, so a client can react to the missing messages before it shows the messages that are still there. Inbox still delivers every row it kept, and the `__gap__` frame reports the rows it had to delete.

## `gaps()` reports the gap

The [`gaps()` client primitive](/core/client/primitives/gaps) reports `__gap__` to your code through the `onGap` callback. On an inbox channel, the [`inbox()` primitive](/core/client/primitives/inbox) also reads the frame. It moves its acknowledgement forward to `missedThrough`, so the server stops reporting the same gap. An **inbox-only client** is a client with `inbox()` in its stack but not `gaps()`. It has no `onGap` callback. LiveThing never passes reserved frames such as `__gap__` to your message handlers. So on an inbox-only client, delivery continues, but your code is never told about the hole.

To react to overflow gaps, add `gaps()` to the client stack. It works next to `inbox()` and does not need `replay()`. This is a smaller version of Huddle's `client/socket.ts`:

```typescript [client/socket.ts]
import {
  binary,
  channels,
  client,
  connect,
  dedup,
  gaps,
  inbox,
  reconnection,
} from '@livething/client'
import { reloadChannelHistory } from './huddle-ui'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://huddle.example.com/huddle'),
  binary(),
  channels(),
  gaps(),
  inbox(),
  dedup(),
  reconnection(),
)

const dm = socket.channel('dms', 'dm:alice+bob')

dm.onGap((info) => {
  // Every message at or below info.missedThrough on this channel is gone.
  // Reload the full history, or fetch it from your own server.
  reloadChannelHistory('dm:alice+bob', info.missedThrough)
})
```

`reloadChannelHistory` stands for Huddle's own client code. It would call the [`load-history`](/core/server/handlers/request#channel-scoped-request-handlers) request or fetch the messages from your own server, then replace the list on screen.

An inbox overflow is a **channel-scoped** gap. It arrives on `socket.channel(...).onGap(...)`, not on the top-level `socket.onGap(...)`. The callback receives a `GapInfo` object:

- `missedThrough`: the highest sequence number that is gone. Every message at or below it is lost. For inbox overflow, this is the highest sequence among the evicted undelivered rows.
- `channel` / `channelFamily`: set on a channel gap, missing on a top-level gap. For a dynamic channel family, use both values together. The family key plus the concrete channel name identify one channel. The concrete name alone is not enough.

`channel.onGap` exists only when `gaps()` is in the client stack. Without it, TypeScript reports that `onGap` does not exist on the channel handle.

::note
This is the same `onGap` you use for [replay's catch-up gaps](/core/server/replay/overview). Replay sends a gap when it cannot fully catch a channel up, because its retention already deleted messages the client had not seen. Inbox overflow and replay eviction are two sources of the same signal, and one `gaps()` handler covers both.
::

## Choosing your limits

`retention` is a trade-off between storage and how far a member can fall behind without losing messages:

- **No `retention`**: no member ever loses a message, but the queue of a member who never returns grows without limit. Use this when members reconnect quickly and you expect them to come back.
- **`maxMessages`, `maxAgeMs` or `maxBytes` set**: storage has a limit, but a member who falls far enough behind loses the oldest messages and gets a `__gap__` frame when they return. Use this for busy channels, where it would cost too much to store days of messages for an absent member who would not read them anyway. A channel with [binary events](/core/server/inbox/overview#binary-events) gets `maxBytes` of 64 MiB per member when it sets none: a few voice notes take more room than thousands of text messages, so a limit on the number of rows alone does not limit the storage. A channel with no binary events has no default limit.

If you set limits, add `gaps()` to the client. Then a member who overflows is told about it, instead of never learning about the messages they will not receive.
