## Binary streams

`base.binary.stream(name, config)` is [`base.stream`](/core/server/streams/plain) for bytes. Each value the generator yields is `{ info, bytes }`, and goes out as one binary message. It needs [`stream()`](/core/server/capabilities/streams) too. Without it, `base.binary.stream` does not exist on the type, and calling it throws.

Huddle sends a stored file in pieces, to a user who may read it:

```typescript [server/attachments.ts]
import * as v from 'valibot'
import { NotFound } from '../shared/errors'
import { canReadAttachment } from './attachment-files'
import { base } from './base'
import { openAttachment } from './helpers'

type FileInfo = { fileName: string; fileType: string }

export const handleDownloadAttachment = base.binary.stream(
  'download-attachment',
  {
    input: v.object({
      attachmentId: v.string(),
      fromByte: v.number(),
    }),
    async *run(ctx, input) {
      if (
        !(await canReadAttachment(ctx.user.id, input.attachmentId))
      ) {
        throw NotFound({ id: input.attachmentId })
      }

      const file = await openAttachment(
        input.attachmentId,
        input.fromByte,
      )
      // The first chunk says what the file is. The others need no info.
      let info: FileInfo | null = {
        fileName: file.name,
        fileType: file.type,
      }

      for await (const piece of file.pieces(ctx.stream.signal)) {
        yield { info, bytes: piece }

        info = null
        await ctx.stream.drain()
      }
    },
  },
)
```

- **`input`** checks the info of the binary message that starts the stream, and `run` gets that message's bytes as its third argument. `download-attachment` sends none, so its `run` leaves that parameter out.
- **The info type** comes from what `run` yields. Here `info` is declared as `FileInfo | null`, so that is the type. To fix it yourself, write the return type on `run`. Like every outgoing payload, the info is not checked when the server runs.

  <!-- docs-check: skip -->

  ```ts
  // server/attachments.ts: `run` from above, with its return type
  async *run(ctx, input): AsyncGenerator<{ info: FileInfo | null; bytes: Uint8Array }> {
    // the same body as above
  },
  ```

- **`ctx.stream`** is the same as in a JSON stream: `signal` fires when the client cancels or leaves, `drain()` waits until the socket's buffer is small again, and `nudges()` reads the [nudges](/core/server/streams/config-and-lifecycle) that arrived. Call `drain()` after each piece, as here: binary chunks are large, and the generator can make them faster than the client reads them. On a Cloudflare WebSocket, `drain()` does nothing, because the platform does not report how full the socket is. A server-sent events stream on Cloudflare is paced, so `drain()` waits there.
- `nudges`, `broadcast`, `allowConcurrent` and `maxBytes` work as they do on `base.stream` and `base.binary.on`. A channel has the same method: `rooms.binary.stream(...)`.

Only the chunks are binary. `__streamOk__`, `__streamEnd__`, an `__error__` that ends the stream, the client's `__streamCancel__`, and every nudge stay **text** frames. A nudge sent as a binary message gets `wrong-frame-kind`. Each chunk carries the same stream metadata as a JSON chunk: the stream ID, `durability: 'ephemeral'`, and a `seq` that starts at `1`. `__streamEnd__` carries the last `seq`.

When the connection drops, the client starts `download-attachment` again from the last byte it got, with `fromByte`. A [hibernation](/core/server/server/hibernation) wake ends a running binary stream with `stream-aborted` and the reason `'hibernation-wake'`, the same as a JSON stream, and the client can start it again from its position.

### Recorded binary streams

`base.binary.recordedStream()` is [`base.recordedStream`](/core/server/streams/durable-recorded) for bytes. It needs [`recordedStream()`](/core/server/capabilities/streams) too. Without it, `base.binary.recordedStream` does not exist on the type, and calling it throws.

Each chunk is stored with its bytes, and the generator keeps running when the client's connection drops. When the client continues the stream, the server sends the stored chunks it missed again, as binary frames with the same `seq`, then the live ones. This suits data that takes long to make and is made once, such as Huddle's PDF export of a room:

```typescript [server/exports.ts]
import * as v from 'valibot'
import { base } from './base'
import { renderRoomPdf } from './helpers'

export const handleExportRoomPdf = base.binary.recordedStream(
  'export-room-pdf',
  {
    input: v.object({ roomId: v.string() }),
    maxBufferBytes: 128 * 1024 * 1024,
    async *run(ctx, input) {
      let info: { fileName: string } | null = {
        fileName: `${input.roomId}.pdf`,
      }

      for await (const piece of renderRoomPdf(input.roomId)) {
        yield { info, bytes: piece }

        info = null
        await ctx.stream.drain()
      }
    },
  },
)
```

- The config is a `binary.stream` config with the options of a recorded stream: `maxChunks`, `maxBufferBytes`, `maxAgeMs` and `retentionAfterEndMs`. `maxBytes` still limits the bytes of the frame that starts the stream.
- **`maxBufferBytes`** limits the bytes stored for one stream: each chunk's info as JSON, plus its bytes. It is 64 MiB by default. `maxChunks` (500 by default) still applies too.
- Each chunk carries `durability: 'persistent'`, and `__streamOk__` says the same.
- A channel has the same method: `rooms.binary.recordedStream(...)`.

A chunk the stream cannot store is not stored or sent: one that would go over `maxChunks` or `maxBufferBytes`, and one that alone is bigger than one row of the adapter's SQL storage, or bigger than the adapter's send limit. The generator gets `StreamAborted` with the reason `'buffer-full'` at its `yield`, and the server logs a warning, once for each event and limit, for a chunk that is too big. So the client never sees a missing `seq`: it gets the chunks before, and then the error, or the end if the generator catches the error and returns. On Cloudflare one row is at most 8 MB, so keep each chunk well under that. A binary recorded stream does everything else a [recorded stream](/core/server/streams/durable-recorded) does.
