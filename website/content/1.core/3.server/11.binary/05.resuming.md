This page builds on [Uploads](/core/server/binary/uploads), which shows how to write an upload handler.

## `ctx.upload`

`run` gets the normal handler `ctx`, plus `ctx.upload`:

::field-group
::field{name="ctx.upload.savedThrough" type="number"}
Where this run starts. It is `0` for a new upload. For a resumed one, it is the last offset given to `saved()`, and the first piece starts there. Unlike `state`, it follows each `saved()` in this run.
::
::field{name="ctx.upload.state"}
The state saved with the last saved offset, checked with the handler's [`state` schema](#the-state), or `undefined` when none was saved. Its type is the schema's output. It is read once, when `run` starts, so a `saved()` in this run does not change it. It exists only when the handler has a `state` schema.
::
::field{name="ctx.upload.saved(offset, { state }?)" type="void"}
Says that the bytes up to `offset` are really stored, so a resume starts there. With a `state` schema, give `state` to keep a small JSON value with it, such as a file ID or the parts of a multipart upload. A `state` of `undefined` clears the state, so it reads back as `undefined`. `saved()` checks the state with the schema in its JSON form, and throws a `TypeError` when it fails, or when the state has no JSON form. Without a schema, `saved()` takes only the offset, and a `state` throws a `TypeError`. The offset and the state are written in **one SQL write**, so they always match. It throws a `RangeError` when the offset goes back, when it is more than the bytes `run` has read, or when the state is more than 64 KiB of JSON.
::
::field{name="ctx.upload.signal" type="AbortSignal"}
Fires when the client cancels, when the connection closes, or when another connection [takes over](#taking-over) the upload. The `for await` loop throws at the next piece anyway. Pass the signal to every slow call, such as a write to S3, so `run` stops soon, and check it before any side effect, such as posting a message.
::
::

::warning
Stop `run` on `ctx.upload.signal`. When `run` has not settled 10 seconds after it was stopped (a cancel, a takeover, a closed connection, a purge or a failed upload), LiveThing stops waiting for it. The upload continues without it, so a new start can run, and what the old `run` does later is ignored and logged. A `ctx.upload.saved()` from that old `run` throws, so it cannot write over the record of the run that took its place. But a `run` that ignores its signal can still write bytes or post a message after the upload moved on.
::

### The state

The handler's `state` schema types the state, and LiveThing checks a stored state with it each time it reads the state back: when a resumed `run` starts, and before `onDiscard`. A stored state can be older than your code. An older deploy may have saved it with another schema. `saved()` checks the state too, in its JSON form, the way a resume reads it back. TypeScript cannot see that a `Date`, a `Map` or `NaN` changes in JSON, so a state that would fail the schema after JSON makes `saved()` throw a `TypeError`, and nothing is stored.

The `state` schema must be **synchronous**. LiveThing runs it while it holds the upload, and also when the server starts, when it cleans up old uploads, so the check must not wait. An async schema, such as one built with `v.pipeAsync`, is a configuration error: LiveThing throws a `LiveThingConfigError` when it first runs it. A `saved()` with a state throws it in `run`, so nothing is stored. When LiveThing reads a stored state:

- **On a resume**, the start stops. The record stays as it is, and the client gets a plain `internal-error`.
- **In the cleanup** (an expiry, a cancel, a failure or a purge), the record is already marked `discarding`, so it waits. LiveThing logs an error and tries again about every minute, until you deploy a synchronous schema.

When a stored state fails the schema, or the schema throws, LiveThing logs a warning with the event, the upload ID and the schema's issues (or the thrown error's message), and:

- **on a resume**, `run` does not run. The client gets `upload-aborted` with the reason `'bad-state'`, and the upload is discarded: `onDiscard` runs with `ctx.upload.state` set to `undefined`. So it can still clean up with the input.
- **before `onDiscard`** (a cancel, an expiry, a failure or a purge), `onDiscard` runs with `ctx.upload.state` set to `undefined`.

So when you change the `state` schema, make `onDiscard` able to clean up without the state, or keep the schema able to read the old shape.

Call `saved()` only after the bytes are really stored. If the connection drops after a `saved()`, the client sends the bytes after that offset again, and the bytes before it are never sent again. So a `saved()` too early loses bytes, and a `saved()` that comes late only sends some bytes twice. Write the bytes so that the same bytes written twice give the same file, as `writeAttachmentBytes` does with its offset.

## Resuming

A drop does not end an upload. The record stays, and the client starts the upload again with the same upload ID, usually as soon as the socket is open again. On every start, `run` runs **again**, from `ctx.upload.savedThrough`:

1. The first run of `upload-attachment` reads 3 MiB, and calls `saved()` after each piece.
2. The connection drops. The `for await` loop throws `Disconnected`, so `run` stops.
3. The client reconnects and starts the upload again. LiveThing reads the record: the input, the saved offset (3 MiB) and the state (the attachment ID), which it checks with the `state` schema.
4. `run` runs again. `ctx.upload.savedThrough` is 3 MiB, and the first piece has the offset 3 MiB.

The client can [resume from another tab, or after a page reload](/core/client/primitives/uploads#resuming-after-a-reload), if it kept the upload ID. A resume must send the same input as the first start, and the same size (or no size, if the first start had none), or it gets `upload-aborted` with the reason `'input-mismatch'`. This holds for a done upload too: a start with another input or size gets `'input-mismatch'`, not the stored reply.

When `run` returns, the upload is done. There is one exception: when a drop or a takeover stopped `run` before it read every byte, and `run` catches the error and returns anyway, LiveThing ignores the reply and logs a warning. Otherwise a part of the file would be marked done. The upload resumes from its saved offset on the next start. So let the error from the pieces reach the end of `run`.

If the reply is lost in a drop, the client starts the upload again, and the server sends it the stored reply. `run` does not run a second time. The reply is kept for `retentionAfterDoneMs`.

### Taking over

An upload belongs to its user, and one connection runs it at a time. When another connection of the same user starts the same upload ID, for example a second tab, it **takes over**: the first connection gets `upload-aborted` with the reason `'taken-over'`, its `run` stops, and the new connection resumes the upload once that `run` has settled.

## onDiscard

`onDiscard(ctx, input)` runs when an upload ends without finishing:

- the client cancels it,
- it expires (see [The upload record](#the-upload-record)),
- `run` throws,
- the client breaks the protocol, for example with a piece that is too big,
- a resume finds a stored state that fails the `state` schema,
- or the user is purged with [`purgeUser`](/core/server/admin/authoring#purgeuser-cleans-up-all-durable-data).

Delete what the upload stored there, or abort a multipart upload. `onDiscard` runs with no connection, like a [scheduled task](/core/server/handlers/scheduled): its `ctx` has no `ctx.send`, but it has the senders that need no connection. `ctx.upload` holds what the record kept: `savedThrough` and, with a `state` schema, `state`, checked with that schema. A stored state that fails the check reads as `undefined` (see [The state](#the-state)). The `input` is the one the record kept too: what the client sent, after the `input` schema, as JSON. So a schema that makes a `Date` or a `Map` gives `onDiscard` its JSON form, not the object `run` got.

`onDiscard` runs **at least once**. When it throws, LiveThing logs the error, keeps the record, and runs it again about a minute later. So it can run twice for one upload, and it must be safe to run twice: deleting a file that is already deleted must not throw. A drop does not run `onDiscard`, because the upload can still resume.

## The upload record

LiveThing keeps one row per upload in its reserved table `__livething_uploads`, in the server's own SQL storage. Do not write to it yourself.

| Column          | Holds                                                                                                             |
| --------------- | ----------------------------------------------------------------------------------------------------------------- |
| `user_id`       | The user the upload belongs to                                                                                    |
| `upload_id`     | The client's upload ID. The primary key is `user_id` and `upload_id`.                                             |
| `event`         | The upload's event name                                                                                           |
| `input`         | The checked input, as JSON                                                                                        |
| `size`          | The size the client sent at the start, or `NULL`                                                                  |
| `saved_through` | The last offset given to `saved()`                                                                                |
| `state`         | The last state given to `saved()`, as JSON, or `NULL`. Checked with the `state` schema when it is read back       |
| `status`        | `'active'`, `'done'` or `'discarding'`                                                                            |
| `reply`         | The reply's info, as JSON, once the upload is done                                                                |
| `updated_at`    | The last time the upload moved: a `saved()`, a piece (at most once a minute), or the end of a run that can resume |
| `metadata`      | Reserved JSON, `'{}'`. LiveThing does not use it yet                                                              |

An `active` upload can start or resume. When it gets no piece and no `saved()` for `expireAfterMs`, it **expires**: `onDiscard` runs, then the row is deleted. An upload that a connection is running never expires, even when `run` is slow. A `done` row keeps the reply for `retentionAfterDoneMs`, then it is deleted. A `discarding` row waits for its `onDiscard` to succeed.

LiveThing checks these times with the server's durable alarm, and again each time the server starts. So an upload expires after the server was down too.

`purgeUser` stops the user's running uploads: the client gets `upload-aborted` with the reason `'gone'`. Then `onDiscard` runs for each of the user's uploads that is not done.
