## Handling binary events

`base.binary.on(name, config)` creates the handler for one binary event that a client sends. A channel has the same method: `rooms.binary.on(...)`. Pass the handler to `base.assemble()`, as you do for every handler:

```typescript [server/avatars.ts]
import * as v from 'valibot'
import { base } from './base'
import { resizeAvatar, saveAvatar } from './helpers'

export const handleUploadAvatar = base.binary.on('upload-avatar', {
  input: v.object({
    fileType: v.picklist(['image/png', 'image/jpeg']),
  }),
  maxBytes: 2 * 1024 * 1024,
  async run(ctx, input, bytes) {
    await saveAvatar(ctx.user.id, input.fileType, bytes.slice())
    ctx.binary.send('avatar-preview', await resizeAvatar(bytes), {
      info: null,
    })
  },
})
```

- **`input`** is the schema for the info. It works like `input` on `base.on`: it is optional, and the handler gets the checked info as its second argument.
- **`maxBytes`** limits the bytes of each message. It is optional. Without it, the limit is what always fits in the adapter's message limit, with the header and up to 64 KiB of info. A value that cannot fit makes the server fail when it starts (see [Size limits](/core/server/capabilities/binary#size-limits)). For a file that is bigger than one message, or that takes long to send, use an [upload](/core/server/binary/uploads) instead.
- **`run(ctx, input, bytes)`** gets the bytes as a plain `Uint8Array`. The array is a view of the message that arrived, not a copy. Call `bytes.slice()` for a copy when your code keeps the bytes after `run` returns.
- `rateLimit` and `allowInterleaving` work as they do on `base.on`.

A channel handler gets `ctx.channel`, as any channel handler does. Huddle's room handler sends each picture of a shared screen on to the other members:

```typescript [server/screen-share.ts]
import * as v from 'valibot'
import { rooms } from './base'

export const handleShareScreenFrame = rooms.binary.on(
  'share-screen-frame',
  {
    input: v.null(),
    maxBytes: 1024 * 1024,
    run(ctx, _input, bytes) {
      ctx.channel.binary.broadcast('screen-frame', bytes, {
        info: { from: ctx.user.id },
      })
    },
  },
)
```

::warning
The info describes the bytes, but it proves nothing about them: **a client can send any info and any bytes**. So `saveAvatar` must still check that the bytes really are a picture of that type. Set facts such as `from` on the server, as `handleShareScreenFrame` does. If the client set `from`, it could say it is someone else.
::

A binary event goes through the same steps as a JSON event, in the same order: the channel membership check, the rate limit, the [intercepts](/core/server/lifecycle-and-intercept/intercept), then the checks on the info and the bytes. A rate-limited message never reaches your intercepts. A non-member gets `channel-not-subscribed`, and info that fails `input`, or bytes over `maxBytes`, gets `validation-failed`. Other messages the server refuses are in the [binary frames](/core/learn/wire-protocol#binary-frames) of the wire protocol.

## Sending binary events

Every object that can send a JSON event has a `.binary` key with the same methods. Each one reaches the same connections, takes the same options, and returns the same value as its JSON version:

| JSON sender                                    | Binary sender                                                      | Returns                                            |
| ---------------------------------------------- | ------------------------------------------------------------------ | -------------------------------------------------- |
| `ctx.send(event, payload)`                     | `ctx.binary.send(event, bytes, { info })`                          | `false` when the adapter refused the frame         |
| `ctx.broadcast(event, payload, options)`       | `ctx.binary.broadcast(event, bytes, { info, ...options })`         | nothing                                            |
| `ctx.channel.send(event, payload)`             | `ctx.channel.binary.send(event, bytes, { info })`                  | `1` when delivered, else `0`                       |
| `ctx.channel.broadcastTo(to, event, payload)`  | `ctx.channel.binary.broadcastTo(event, bytes, { to, info })`       | the number of sockets reached                      |
| `ctx.channel.broadcast(event, payload)`        | `ctx.channel.binary.broadcast(event, bytes, { info, ...options })` | nothing                                            |
| `ctx.channels.get(...).broadcast(...)`         | `ctx.channels.get(...).binary.broadcast(...)`                      | nothing                                            |
| `ctx.user.broadcast(event, payload)`           | `ctx.user.binary.broadcast(event, bytes, { info })`                | the number of sockets reached                      |
| `ctx.connections.get(ref).send(...)`           | `ctx.connections.get(ref).binary.send(...)`                        | `false` when it is not live                        |
| `ctx.tags.ephemeral(group).broadcast(...)`     | `ctx.tags.ephemeral(group).binary.broadcast(...)`                  | nothing                                            |
| `ctx.channel.inbox.backfill(userId, messages)` | `ctx.channel.inbox.binary.backfill(userId, messages)`              | nothing; throws when a message is too big to store |

The same goes for `ctx.users.get(id)`, a tag's `.ref(key)`, and connectionless code: [scheduled tasks](/core/server/capabilities/scheduled), `onShutdown` and the in-process [admin API](/core/server/admin/overview) on Node have `ctx.binary.broadcast` and `ctx.channels.binary.broadcast`, plus `.binary` on a channel handle from `ctx.channels.get(...)`, on `ctx.users.get(id)` and on `ctx.connections.get(ref)`. [The Cloudflare admin stub](/core/server/admin/reaching-it) has the same, except on `admin.channels.get(...)`, which has no `broadcast` at all: use `admin.channels.binary.broadcast()`. It takes the event, the bytes, and `{ channel, info }`.

The arguments come in this order: the event, the bytes, then an object with the info and the options. The bytes come second because a binary method is about the bytes, and the info goes in `{ info }` with the other options. The event and the info are typed from the `binary({ emits })` that declares the event, so a JSON event name, a typo or the wrong info is a compile error. The bytes are a `Uint8Array` or an `ArrayBuffer`. Pass `undefined` to send no bytes.

The `handleUploadAvatar` handler from the top of this page sends the preview only to the tab that uploaded the avatar. To show it in every tab of that user, change `ctx.binary.send` to `ctx.user.binary.broadcast`. The rest of the handler stays the same:

```typescript [server/avatars.ts]
import * as v from 'valibot'
import { base } from './base'
import { resizeAvatar, saveAvatar } from './helpers'

export const handleUploadAvatar = base.binary.on('upload-avatar', {
  input: v.object({
    fileType: v.picklist(['image/png', 'image/jpeg']),
  }),
  maxBytes: 2 * 1024 * 1024,
  async run(ctx, input, bytes) {
    await saveAvatar(ctx.user.id, input.fileType, bytes.slice())
    const preview = await resizeAvatar(bytes)
    const tabs = ctx.user.binary.broadcast(
      'avatar-preview',
      preview,
      {
        info: null,
      },
    )
    ctx.log.info('avatar preview sent', { tabs })
  },
})
```

To pass an `ArrayBuffer`, pass one the bytes own entirely, such as `bytes.slice().buffer`. A `Uint8Array` can be a view into a bigger buffer (a Node `Buffer` often is), so its `.buffer` can hold other data too.

For each send, LiveThing:

- Adds the same metadata as for a JSON event: the channel, and the message ID and sequence number when [`dedup()`](/core/server/capabilities/dedup) and [`sequence()`](/core/server/capabilities/sequence) are listed. JSON and binary events in a scope share one sequence counter, so they keep one order.
- Copies the bytes into the message once. Your code can change its own bytes after the send returns.
- Builds the message **once** for a broadcast, and writes that same message to each socket.
- Runs the [`onOutgoing`](/core/server/lifecycle-and-intercept/outgoing) hook once. Its `frame.payload` is the info, and `frame.bytes` is the bytes.

Only data is binary: events, request replies, stream chunks and server requests with their answers. Every framework message stays text, such as `__error__`, `__subscribeOk__`, `__streamOk__`, `__streamEnd__` and `__nudgeOk__`.
