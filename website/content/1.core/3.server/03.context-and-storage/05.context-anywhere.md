A handler receives `ctx` as its first argument. When a helper function needs `ctx`, you normally pass it down as an argument. In a deep call chain, this is repetitive. The `context` object lets a helper read the `ctx` of the handler that is running now, so you do not pass it down.

::code-group

```typescript [server/permissions.ts]
import { context } from '@livething/server'
import { Forbidden } from '../shared/errors'
import { base } from './base'

export function requireAdmin() {
  const ctx = context.connection(base)
  if (ctx.meta.role !== 'admin') {
    throw Forbidden({ reason: 'only an admin may do this' })
  }
}
```

```typescript [server/archive-room.ts]
import * as v from 'valibot'
import { base } from './base'
import { requireAdmin } from './permissions'

export const handleArchiveRoom = base.on('archive-room', {
  input: v.object({ roomId: v.string() }),
  async run(ctx, input) {
    requireAdmin() // no ctx argument
    ctx.sql.exec(
      'UPDATE rooms SET archived = 1 WHERE id = ?',
      input.roomId,
    )
  },
})
```

::

`Forbidden` is a typed error that the server lists in its [`errors([...])`](/core/server/capabilities/errors) capability.

`context.connection(base)` returns the same object that `run(ctx, ...)` received. It works after an `await` too. Two handlers that run at the same time each see their own `ctx`.

## The accessors

Each kind of code that LiveThing runs has its own accessor, because each kind has a different `ctx`. Pass the value that `server(...)` returned (`base`), or the channel that `base.channel(...)` returned.

| Accessor                            | Returns the `ctx` of                                                                                                                                                                                                                                          |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `context.connection(base)`          | An event, request or stream handler of the server, a top-level [intercept](/core/server/lifecycle-and-intercept/intercept), and the `onConnect`, `onDisconnect`, `onPing`, `onPong` and `onError` hooks. The `onError` hook works for events in a channel too |
| `context.channel(channel)`          | An event, request or stream handler of one channel, and an intercept of that channel. It has `ctx.channel`, and its params and events are typed from that channel                                                                                             |
| `context.channelLifecycle(channel)` | The `onSubscribe`, `onUnsubscribe` and `onSessionEnd` hooks of one channel. It has the channel's own handles, such as `ctx.channel.inbox` and `ctx.channel.request`, when the channel has them                                                                |
| `context.channelGate(channel)`      | The `check`, `commit` and `revalidate` hooks of one channel. These hooks do not have `ctx.channel.inbox`, `readReceipts` or `request`, so the type leaves them out                                                                                            |
| `context.task(base)`                | A [scheduled task](/core/server/handlers/scheduled) handler                                                                                                                                                                                                   |
| `context.init(base)`                | An `onInit` hook                                                                                                                                                                                                                                              |
| `context.shutdown(base)`            | An `onShutdown` hook                                                                                                                                                                                                                                          |
| `context.authenticate(base)`        | An [`authenticate` function](/core/server/server/authenticate#the-authenticate-ctx). In the app's `authenticate`, pass the app's `base`. In a plugin's `authenticate`, pass that plugin's own `base` to get the plugin's scoped `ctx`                         |

There is no accessor that works in every kind of code. A helper that needs only storage can take `ctx.sql` (the `SQLProvider` type) as an argument.

::note
The type that `context.connection(base)` and `context.channel(channel)` return does not have `ctx.stream`. Only the `ctx` of a stream handler has it, so read `ctx.stream.signal` from the `ctx` argument of the handler.
::

## The types

Each accessor returns the type of the `ctx` that its kind of code receives. For `context.connection(base)` and the channel accessors, that is the type a handler of that `base` or channel receives. It has the same events, the same `ctx.meta` and the same fields that capabilities add. `context.task`, `context.init`, `context.shutdown` and `context.authenticate` return the smaller `ctx` of a task, an `onInit` hook, an `onShutdown` hook and an `authenticate` function, which have no connection fields such as `ctx.user` or `ctx.send`:

```typescript [server/welcome.ts]
import { context } from '@livething/server'
import { base } from './base'

export function welcomeCurrentUser() {
  const ctx = context.connection(base)
  ctx.send('notification', { title: 'Hi', body: 'Welcome' }) // checked against emits(...)
  return ctx.meta.role // typed from your `authenticate` function
}
```

A channel accessor also has `ctx.channel`, typed from the channel. Here `rooms` is the `rooms` channel family, with names that match `room:{roomId}`. It is exported from `server/base.ts`:

```typescript [server/room-context.ts]
import { context } from '@livething/server'
import { rooms } from './base'

export function currentRoomId() {
  return context.channel(rooms).channel.params.roomId // string
}
```

::note
The hooks of a channel have two accessors, because they have two different `ctx` types. In the `check`, `commit` and `revalidate` hooks, `ctx.channel.inbox`, `ctx.channel.readReceipts` and `ctx.channel.request` do not exist, so `context.channelGate(channel)` does not list them. Use `context.channelLifecycle(channel)` in the `onSubscribe`, `onUnsubscribe` and `onSessionEnd` hooks, where they do exist. Calling the wrong one throws an error that names the accessor to use.
::

## A hook in its own file

A hook is a key in `server({ ... })`, so a hook in another file is a function that you pass as the value. Give it a block body, and read `ctx` with an accessor on the first line. The hook file imports `base`, and `base` imports the hook. This is fine, because the types do not depend on each other.

::code-group

```typescript [server/base.ts]
import { emits, server, t } from '@livething/server'
import { verifySession } from './auth'
import { greet } from './greet'

export const base = server({
  async authenticate(request) {
    const token = request.headers
      .get('Authorization')
      ?.replace('Bearer ', '')
    const user = await verifySession(token)
    return { userId: user?.id, meta: { name: user?.name ?? 'guest' } }
  },
  capabilities: [
    emits({ notification: t<{ title: string; body: string }>() }),
  ],
  onConnect: greet,
})
```

```typescript [server/greet.ts]
import { context } from '@livething/server'
import { base } from './base'

export function greet() {
  const ctx = context.connection(base)
  ctx.send('notification', {
    title: 'Welcome',
    body: `hi, ${ctx.meta.name}`,
  })
}
```

::

::warning
Do not write the hook as an arrow function that returns a method call on the accessor's result:

<!-- docs-check: skip -->

```ts
// Circular type error
const greet = () =>
  context
    .connection(base)
    .send('notification', { title: 'Hi', body: 'Welcome' })
```

The type of `base` then depends on the hook, and the hook's type depends on `base`. TypeScript reports a circular type error. A function with a block body, like `greet` above, has no such problem.
::

## When an accessor throws

Every accessor is a runtime check. It throws an error that starts with `[livething]` in these cases:

- **Outside an invocation.** No handler or hook is running, for example in a callback that was created before any handler ran.
- **The wrong kind.** For example, `context.task(base)` inside an event handler. The message names the accessor to use instead.
- **The wrong server or channel.** The `base` or channel that you passed is not the one that is running.

Some code is not covered:

- **Outgoing hooks** (`onOutgoing`) always throw, because the hook watches a finished send, not one handler call, and the connections that received the frame are often not the one that sent it. Use the hook's own `ctx` argument instead.
- **A plugin's `api` methods** run as the app handler that calls them, so an accessor there needs the app's `base`. The plugin's own `base` throws. Use the scoped `ctx` that the `api` factory receives instead.

Inside a plugin's own code, pass the plugin's own `base` and channels. Every accessor then returns the plugin's scoped `ctx`, the same one that the plugin's handlers and hooks receive. The app's `base` throws there, so an app helper that calls `context.connection(base)` can't be called from plugin code. Pass `ctx` to that helper instead.

## Stale context

The context follows the async call chain, not the handler that is "current". A timer that a handler starts still sees that handler's `ctx` when it fires, after the handler has returned. The connection may be closed by then. LiveThing does not check this for you. `ctx.send` still hands the frame to the closed socket, and what happens next depends on the runtime. Code that runs later should not assume that its connection is still open.

```typescript [server/reminders.ts]
import { context } from '@livething/server'
import * as v from 'valibot'
import { base } from './base'

export const handleRemindMe = base.on('remind-me', {
  input: v.object({ text: v.string(), delayMs: v.number() }),
  run(ctx, input) {
    setTimeout(() => {
      // Still the same connection's ctx, even if the socket has closed.
      const later = context.connection(base)
      later.send('notification', {
        title: 'Reminder',
        body: input.text,
      })
    }, input.delayMs)
  },
})
```

For work that must last longer than the connection, use a [scheduled task](/core/server/handlers/scheduled) and `context.task(base)`.

## Trade-offs

When you pass `ctx` as an argument, the compiler checks that every caller has one. With `context`, the type is the same, but the compiler cannot check that a `ctx` exists at the moment you call. That check moves to the runtime, and it fails with the errors above. Use an argument when a function is called from many places or from code that runs outside handlers.

## In `authenticate`

The `authenticate` function receives its `ctx` as the second argument. Use it there. Do not call `context.authenticate(base)` inside `server({ authenticate })` to build the return value. The type of `base` depends on what `authenticate` returns. If a value from `context.authenticate(base)` reaches the returned value, TypeScript reports a circular reference (`'base' implicitly has type 'any'`).

`context.authenticate(base)` is for helpers in other files. If `authenticate` calls such a helper, write an explicit return type on it, or TypeScript reports a similar circular-type error:

```typescript [server/sessions.ts]
import { context } from '@livething/server'
import { base } from './base'

export function findSession(token: string | null): {
  userId: string
  role: 'admin' | 'member'
} | null {
  return context
    .authenticate(base)
    .sql.exec<{
      userId: string
      role: 'admin' | 'member'
    }>(
      'SELECT user_id AS userId, role FROM sessions WHERE token = ?',
      token,
    )
    .one()
}
```

## Adapters

`context` needs an async-context store, which the adapter already provides through [`asyncContextFactory`](/core/runtimes/adapters/custom-adapters). On Cloudflare, the `nodejs_compat` flag that the adapter already needs is enough.
