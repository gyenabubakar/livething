`onOutgoing` watches the app frames your server sends to clients. It runs **once per send**, **after** the frame was written to the sockets. It tells you which event went out, with which payload, who the send was addressed to, and how many sockets got it. Use it for work that looks at every outgoing message: metrics, tracing and audit logs.

The hook only watches. It cannot change a frame, and it cannot stop one: by the time it runs, the frame is already on the wire. A value it returns is ignored. To change or drop a message, do it in the code that sends it, or in the inbound [`intercept`](/core/server/lifecycle-and-intercept/intercept) before your handler runs.

`onOutgoing` is a key of `server({ ... })`, like `intercept`. It needs **no** capability.

```typescript [server/base.ts]
import { server } from '@livething/server'

const base = server({
  onOutgoing(ctx, frame) {
    if (ctx) {
      ctx.log.info('sent', {
        event: frame.event,
        target: frame.target.kind,
        recipients: frame.recipients,
      })
    }
  },
})
```

A server has one `onOutgoing` hook. Each [plugin](/core/server/plugins/authoring) can have its own.

## What it sees

The hook sees every **app frame** the server sends:

- events: `ctx.send`, `ctx.broadcast`, `ctx.channel.send`, `ctx.channel.broadcastTo`, `ctx.channel.broadcast`, `ctx.user.broadcast`, `ctx.connections.get(ref).send`, a tag broadcast, and a send from a scheduled task, `onShutdown` or the admin API, and the `.binary` version of each one,
- stream chunks,
- server-to-client requests, including a request to one user,
- the replies to client requests.

It does **not** see:

- LiveThing's own protocol frames, the ones with a `__name__` event, such as member updates, read receipts, the frame that ends a stream, and error frames,
- frames that [replay](/core/server/replay/overview) sends again: the answer to a client's catch-up request and `ctx.sendReplay(...)`,
- the stored [inbox](/core/server/inbox/overview) messages that LiveThing delivers when a member reconnects,
- the stored chunks of a [durable stream](/core/server/streams/overview) that LiveThing sends again when a client reconnects.

### One send, one call

A send to many connections is **one frame** and **one hook call**. LiveThing checks the payload, turns it into JSON and adds the delivery metadata (`metadata.delivery.seq`, `metadata.delivery.id`) once, so every recipient gets the same bytes. This holds for every send with more than one recipient: `ctx.broadcast`, a channel broadcast, a user broadcast, `broadcastTo` with any recipient, a tag broadcast, the chunks of a broadcast stream (the creator and every peer get the same frame), and a request to one user (each of the user's sockets gets a copy that adds only its own exchange ID).

The hook also runs when nobody got the frame, for example a broadcast to an empty room. Then `frame.recipients` is `0`.

### A send inside the hook

A send made inside `onOutgoing` goes out, but no `onOutgoing` hook sees it, even after an `await` in the hook. Without this rule, a hook that sends would run itself again without end. So one frame from a handler gives one hook call, however many frames the hook sends.

## The frame

The handler receives `(ctx, frame)`. `frame` is an `OutgoingFrame`:

::field-group
::field{name="event" type="string"}
The event name as it was sent to the client.
::
::field{name="payload" type="unknown"}
The payload as it was sent: the JSON copy, after any `toJSON()` ran. It is `null` for an event sent with no payload, and for the reply to a request whose handler returned nothing. For a [binary send](/core/server/binary/overview), such as a binary event, a chunk of a binary stream or the reply to a binary request, it is the info. Check `frame.event` first, then read the payload with a cast (see [Reading the payload](#reading-the-payload)).
::
::field{name="bytes" type="Uint8Array | undefined"}
The bytes of a binary send (a binary event, a chunk of a binary stream or the reply to a binary request), as your code passed them to the send, or `undefined` for a text frame. A binary broadcast is one call too, with one `bytes` for every recipient.
::
::field{name="owner" type="FrameOwner"}
Whether the event belongs to your app (`{ kind: 'app' }`) or to a plugin (`{ kind: 'plugin', id }`).
::
::field{name="channel" type="{ name: string; family: string | null } | null"}
The channel the frame was sent in, or `null` for a top-level frame. `family` is the family key of a [dynamic family](/core/server/channels/dynamic-families), or `null` for a static channel.
::
::field{name="target" type="OutgoingTarget"}
Who the send was [addressed to](#targets).
::
::field{name="recipients" type="number"}
How many sockets the frame was written to. It can be `0`.
::
::

### Targets

`frame.target` is an `OutgoingTarget`. Import the type from `@livething/server`. Its `kind` field tells you which form it has:

| `target`                                | Sent by                                                                                                                                                                               |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{ kind: 'all' }`                       | `ctx.broadcast`, a broadcast from a scheduled task, `onShutdown` or the admin API, and a top-level broadcast stream                                                                   |
| `{ kind: 'channel' }`                   | a channel broadcast and a channel broadcast stream. `frame.channel` says which channel.                                                                                               |
| `{ kind: 'connection', id }`            | `ctx.send`, `ctx.channel.send`, `ctx.connections.get(ref).send`, a server request to one connection, a request reply, a plain stream chunk, and `broadcastTo` a `ConnectionRef`       |
| `{ kind: 'user', id }`                  | `ctx.user.broadcast`, `ctx.users.get(id).broadcast`, `broadcastTo` a `UserRef`, and a request to one user                                                                             |
| `{ kind: 'tag', tagKind, group, key? }` | a tag ref or tag group broadcast, and `broadcastTo` a `TagRef` or `TagGroupHandle`. `tagKind` is `'ephemeral'` or `'persistent'`. `key` is not set when a whole group was the target. |

## `ctx`

`ctx` is the connection whose `on`, `request`, or `stream` handler, `intercept`, or `onConnect`, `onError`, `onPing`, or `onPong` hook is running when the frame is sent. For a plain `ctx.send(...)` inside a handler, this is the same socket that receives the frame, so `ctx` is the receiver. On a broadcast from that code, `ctx` is the sender, not each receiver. In every other case there is no such connection, and **`ctx` is `undefined`**: a channel `onSubscribe` hook, `onDisconnect`, a `schedule(...)` task, `onInit`, `onShutdown`, or the admin API. The type is `AppCtx | undefined`.

`ctx` is also created new for each call. Values that an `intercept` stored with `ctx.provide(...)` for the current message are not on it.

::caution
Check `ctx` before you read any connection field. A hook that reads `ctx.log` without the check throws on a frame that is sent with no connection in scope. `frame` is always present, so build your logic on `frame`, and use `ctx` only when it is there.
::

## Examples

### Count what goes out

Count how many sockets each event reached, split by target kind. Read the counts from wherever you export your metrics.

```typescript [server/base.ts]
import { server } from '@livething/server'

const socketsReached = new Map<string, number>()

const base = server({
  onOutgoing(ctx, frame) {
    const key = `${frame.event}:${frame.target.kind}`
    socketsReached.set(
      key,
      (socketsReached.get(key) ?? 0) + frame.recipients,
    )
  },
})
```

A `ctx.channel.broadcast(...)` from a member's handler, in a room of 40 members, reaches the other 39. It adds `39` to `message:channel` in one call, not 39 calls of `1`.

### Log room messages

Write one log line for each chat message sent in a room:

```typescript [server/base.ts]
import { server } from '@livething/server'

const base = server({
  onOutgoing(ctx, frame) {
    if (frame.event !== 'message' || frame.channel === null) return

    const message = frame.payload as { id: string; from: string }

    ctx?.log.info('message delivered', {
      room: frame.channel.name,
      messageId: message.id,
      from: message.from,
      recipients: frame.recipients,
    })
  },
})
```

## Reading the payload

`frame.payload` has the type `unknown`. Check `frame.event`, then read the payload with a cast, as in the example above. An event declared with `t<null>()` has a `null` payload. This is the same pattern as on the inbound `intercept`.

The `ctx.matches` and `ctx.unsafeCast` helpers work **only on inbound frames**. They take an `InterceptFrame`, not an `OutgoingFrame`, so you can't use them here.

## A different payload for each recipient

Because a send to many connections is one shared frame, every recipient gets the same payload. When each member needs their own payload, send to each member yourself. Loop over the connections and send to each one:

- in a channel: loop over `ctx.channel.members()` and call `ctx.channel.broadcastTo()` with each `member.ref()`, as in the channel example below,
- on the whole server: loop over `ctx.connections.all()`,
- for a tag: loop over the `connections()` of a tag ref or tag group handle,
- for one user: loop over `ctx.user.connections()` or `ctx.users.get(id).connections()`.

Outside a channel, send to each connection with `ctx.connections.get(info.ref())`. Here every connection of the `eng` team gets its own notification:

```ts
// Inside any Huddle handler
const team = ctx.tags.ephemeral('team').ref('eng')
for (const info of team.connections()) {
  ctx.connections.get(info.ref()).send('notification', {
    title: 'Standup',
    body: `Hi ${info.userId}, the eng standup starts in 5 minutes.`,
  })
}
```

In the channel example, `rooms` also emits a `message-with-mention` event, which Huddle's own `rooms` does not have. It takes the place of Huddle's `rooms` here:

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import * as v from 'valibot'

const base = server({ capabilities: [channels()] })

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    emits({
      'message-with-mention': t<{
        id: string
        text: string
        from: string
        mentionsYou: boolean
      }>(),
    }),
  ],
})

export const handleSendMention = rooms.on('send-mention', {
  input: v.object({
    text: v.string(),
    mentionedUserIds: v.array(v.string()),
  }),
  run(ctx, input) {
    const id = crypto.randomUUID()
    for (const member of ctx.channel.members()) {
      ctx.channel.broadcastTo(member.ref(), 'message-with-mention', {
        id,
        text: input.text,
        from: ctx.user.id,
        mentionsYou: input.mentionedUserIds.includes(member.userId),
      })
    }
  },
})

export const huddle = base.assemble({ handlers: [handleSendMention] })
```

Each of these sends is its own frame, with its own delivery sequence number, and the hook runs once for each. [Replay](/core/server/replay/overview) records each one for its own connection only, so a member who was not connected when it was sent never catches up on it. Use one broadcast when every member can get the same payload.

## Errors in the hook

A hook that throws, or that returns a promise that rejects, is logged as `[livething] onOutgoing hook failed`. The send is not affected: the frame already went out, and the code that sent it never sees the error. LiveThing does not wait for a returned promise before it goes on.

There is one exception. A LiveThing configuration error that the hook throws is thrown again to the code that sent the frame, so you see it while you develop.

## Plugin ownership

As in an intercept, `frame.owner` tells you whether the frame belongs to your app or to a plugin. The app's `onOutgoing` hook sees every outbound app frame, including the frames that plugins send. When your server lists plugins, the type of `frame.owner.id` is the union of the installed plugin IDs.

```typescript [server/base.ts]
import { server } from '@livething/server'

const base = server({
  onOutgoing(ctx, frame) {
    if (ctx && frame.owner.kind === 'plugin') {
      ctx.log.info('plugin send', {
        id: frame.owner.id,
        event: frame.event,
      })
    }
  },
})
```

A plugin's own `onOutgoing` hook also sees every app frame. For the plugin's own events, `frame.event` is the short name the plugin declared, without the `__<id>::` part. For how to write a plugin, see [Plugins](/core/server/plugins/overview).

## `onOutgoing` vs `intercept`

::note
`intercept` and `onOutgoing` both get a `frame` with `event`, `payload` and `owner`, but they do different jobs. `intercept` runs **before** the handler and can rewrite the payload or drop the frame with `Block`. `onOutgoing` runs **after** the send and only watches. `Block` has no meaning here. The inbound side is described in [Intercept](/core/server/lifecycle-and-intercept/intercept). For where both hooks run in the message pipeline, see [Pipeline execution order](/core/server/under-the-hood/pipeline-execution-order).
::
