A **recorded stream** keeps working after a client disconnects because it **stores every chunk** it sends. This store is the stream's **buffer**. The generator keeps running while the client is away. When the client reconnects, it gets the chunks it missed from the buffer, then the live chunks. The generator never runs a second time. Use this kind when your source is one-shot, which means you can't ask it for the same data again "from position N". Examples: tokens from an AI model (LLM), events from a third-party API that pushes data to you, or the [bytes of a PDF](#chunks-of-bytes) that takes long to make.

To enable the builder, list [`recordedStream()`](/core/server/capabilities/streams) in your capabilities. The buffer is saved in the server's own SQL storage, and every LiveThing adapter provides this storage automatically. The plain-stream basics (generator, `signal`, `drain()`, ending) are on [Plain Streams](/core/server/streams/plain). This page covers only what recording adds.

## What "recorded" means

Every chunk you yield is written to storage _before_ it is sent. When the client drops, the generator does not stop: it runs to the end and adds each new chunk to the buffer. If the client drops after chunk 3 and reconnects, LiveThing sends chunks 4, 5, and so on from the buffer, then the chunks the generator makes after that. Your code can't tell that a replay happened.

Because a drop does not stop the generator, `ctx.stream.signal` does not fire [when the client disconnects](/core/server/streams/config-and-lifecycle#disconnect-behavior). It fires when the stream is cancelled, when the client leaves the stream's channel, and when the server shuts down.

On this page, `ask-scout` sits on `base` and each example gives it only the options it is about. In Huddle, `ask-scout` is on `rooms` with `broadcast: true`, `stop` and `redirect` nudges, and no other options. The retention options below are the defaults, written out to show them:

```ts [server/scout.ts]
import { server } from '@livething/server'
import { recordedStream } from '@livething/server/streams'
import * as v from 'valibot'
import { llm } from './llm'

const base = server({
  capabilities: [recordedStream()],
})

export const handleAskScout = base.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  maxAgeMs: 300_000,
  retentionAfterEndMs: 30_000,
  async *run(ctx, input) {
    const messages = [{ role: 'user', text: input.prompt }]
    for await (const piece of llm.stream({
      messages,
      signal: ctx.stream.signal,
    })) {
      yield { text: piece }
    }
  },
})
```

You only yield chunks, and LiveThing keeps the buffer, so recording needs no extra code in your generator.

How a chunk looks on the wire depends on its type:

- A **plain-object** chunk is sent as it is. Its keys become the frame payload. An object whose `toJSON()` returns an object is sent as that object.
- Any other chunk with JSON is wrapped as `{ value: <chunk> }`: a number, a string, `null`, an array, or an object whose `toJSON()` gives something else, such as a `Date`. The client reads it at `.value`, and the client's types say so: when `run` yields numbers, each chunk is typed `{ value: number | null }`, because JSON sends `NaN` and `Infinity` as `null`.
- A chunk with no JSON is refused with an error: `undefined`, a function without `toJSON()`, a `symbol`, a `bigint`, and an iterable without `toJSON()` such as a `Map` (JSON would send `{}`).

Yield objects when you want the client to get the same shape you yielded.

## When to use a plain stream instead

If your source _can_ start again from a position (database pages, a file offset, a row ID), a [plain stream](/core/server/streams/plain#starting-again-from-a-position) with the position in its input stores nothing and is usually the simpler choice. Use recorded when the source really can't send the same data again.

## The buffer limit and StreamAborted

The buffer holds at most `maxChunks` chunks (default **500**) and `maxBufferBytes` bytes (default **64 MiB**: each chunk as JSON, plus the bytes of a binary chunk). When a yield would go over either limit, LiveThing throws `StreamAborted` with `reason: 'buffer-full'` **at the generator's `yield`**. Your code can catch it and stop cleanly.

The same happens for one chunk that is too big to keep: bigger than one row of the adapter's SQL storage (8 MB on Cloudflare), or bigger than the adapter's send limit. The server then also logs a warning, once for each event and limit.

```ts [server/scout.ts]
import { StreamAborted } from '@livething/server/errors'
import * as v from 'valibot'
import { base } from './base'
import { llm } from './llm'

export const handleAskScoutShort = base.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  maxChunks: 2, // a very small limit, to show the behavior
  async *run(ctx, input) {
    const messages = [{ role: 'user', text: input.prompt }]
    for await (const piece of llm.stream({
      messages,
      signal: ctx.stream.signal,
    })) {
      try {
        yield { text: piece }
      } catch (err) {
        if (
          StreamAborted.matches(err) &&
          err.detail.reason === 'buffer-full'
        ) {
          return // stop cleanly: the buffer is full
        }

        throw err
      }
    }
  },
})
```

The stream ends in both cases. The difference is what the client gets:

- If you catch the error and `return`, the stream ends normally.
- If you don't catch it, the `StreamAborted` error leaves the generator and the client gets it as the stream's error. Client code can use it, for example, to show a "slow down" message.

`StreamAborted` is a built-in error from `@livething/core`. See the [built-in errors catalog](/core/core/builtin-errors) and the full list of [abort reasons](/core/server/streams/config-and-lifecycle#abort-reasons).

::caution
`maxChunks` and `maxBufferBytes` are hard limits on what the buffer holds **at the same time**. Chunks are not removed from the buffer when the client reads them, so the buffer grows with every `yield`. When a `yield` would go over a limit, or its chunk is too big to keep, LiveThing does three things. It drops the chunk from that `yield`: it is neither stored nor sent. It throws `StreamAborted` with the reason `'buffer-full'` at that `yield`. And it ends the stream. The end message carries the `seq` of the last chunk that was sent, so the client never sees a missing chunk, and ends cleanly. So a recorded stream can't produce more than its limits. Catch the error to stop cleanly, or set limits large enough for the whole run.
::

## Chunks of bytes

`base.binary.recordedStream` is a recorded stream whose generator yields `{ info, bytes }`. Each chunk is stored with its bytes, and goes out as one binary message, live and when a client continues the stream. Everything on this page works the same way for it. Huddle's [`export-room-pdf`](/core/server/binary/streams#recorded-binary-streams) sends a PDF of a room this way, because making the PDF takes long and runs once.

When a client continues a recorded stream, JSON or binary, the server reads the stored chunks a page at a time, and waits while the socket's buffer is full, the same way a [replay catch-up](/core/server/replay/overview) does. Until the last stored chunk is sent, that client gets no live chunk, end or error of the stream. Each live chunk is stored first, so the client gets it from storage, in order and once. A client that reads nothing for about 50 seconds is closed with `1013`, and can continue again from its last chunk.

Binary chunks are large, so the byte limit matters more than the chunk limit. Set `maxBufferBytes` above the biggest file the stream sends, and keep each chunk well under one storage row.

## The contract slice

Every server-pushed stream reaches the client through the one `streams` map that `InferClient` produces (see the [overview](/core/server/streams/overview)). A recorded stream's entry uses the stream name as its key and has `kind: 'persistent'`. Apart from `kind`, it has the same fields as a plain stream's entry.

```ts [shape]
type ClientStreams = {
  'ask-scout': {
    payload: { prompt: string }
    chunk: { text: string }
    kind: 'persistent'
  }
}
```

Recording happens only on the server. On the client, a `'persistent'` stream continues by itself after a reconnect, and [`continueStream(...)`](/core/client/streams/durable-and-continue) picks one up by its ID.

## Nudges and reconnect

Nudges work the same as on a plain stream. A nudge reaches only a **running** generator, because nudges are kept in memory, not in storage.

If a nudge stopped the stream before the client dropped, the stream stays stopped after the reconnect. The generator has returned, so the stream is marked as ended. A reconnect sends the recorded chunks up to that point and then the end of the stream.

A client drop does not stop the generator, so a nudge that arrived but was not read yet stays in its buffer, and the generator reads it at its next `yield`.

```ts [server/scout.ts]
import * as v from 'valibot'
import { base } from './base'
import { llm } from './llm'

export const handleAskScoutStoppable = base.recordedStream(
  'ask-scout',
  {
    input: v.object({ prompt: v.string() }),
    nudges: { stop: null },
    async *run(ctx, input) {
      const messages = [{ role: 'user', text: input.prompt }]
      for await (const piece of llm.stream({
        messages,
        signal: ctx.stream.signal,
      })) {
        const recent = ctx.stream.nudges(yield { text: piece })
        if (recent.some((n) => n.event === 'stop')) return
      }
    },
  },
)
```

## When the generator stops before it finishes

The generator can stop before it reaches its end: it throws, or the server process stops while it runs (a deploy, a crash, a restart, or a Cloudflare Durable Object that is evicted). The stored chunks stay. A client that continues the stream gets the chunks it missed, and then the stream ends with a `StreamAborted` error whose reason is `'interrupted'`, not with a normal end. So the app can tell a cut-off reply from a finished one:

```ts [client/scout.ts]
import { StreamAborted } from '@livething/core'
import { render, showRetryButton } from './huddle-ui'
import { socket } from './socket'

const general = socket.channel('rooms', 'room:general')
await general.subscribe()
const reply = await general.stream('ask-scout', {
  prompt: 'Summarize today in #general',
})

try {
  for await (const chunk of reply) render(chunk.text)
} catch (err) {
  if (
    StreamAborted.matches(err) &&
    err.detail.reason === 'interrupted'
  ) {
    showRetryButton() // the reply was cut off; ask Scout again
  } else {
    throw err
  }
}
```

A generator that throws while a client is attached still sends its real error to that client. `'interrupted'` is what a later continue reports. A stream that really finished always ends normally.

## Retention

A recorded stream's buffer is kept in storage so a client that comes back can get the missed chunks. Two options control how long:

| Option                | Default    | What it controls                                                                                                       |
| --------------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------- |
| `maxAgeMs`            | 5 minutes  | How long a stream whose generator stopped mid-stream (for example after a restart) is kept before LiveThing deletes it |
| `retentionAfterEndMs` | 30 seconds | How long the buffer is kept after the stream ends                                                                      |

Full details are on [Configuration & Lifecycle](/core/server/streams/config-and-lifecycle).
