This page is the reference for stream options and runtime behavior for both stream kinds (plain and recorded). The earlier pages show each kind in use. This page lists every option and its default. It also covers the lifecycle details: how nudges are buffered, how long stored streams are kept, what happens when a client disconnects, and the reasons a stream can be stopped.

## Nudges

A **nudge** is a typed message that the client sends _into_ a stream that is already running. Declare nudges as a map from event name to schema. Use `null` for a nudge with no payload. Inside the generator, `ctx.stream.nudges(yield ...)` returns the nudges that arrived since the last `yield`. Each one has the shape `{ event, payload }`.

This version of Huddle's `tail-audit-log` also lets only an admin start it. `Forbidden` is in Huddle's [`errors([...])`](/core/server/capabilities/errors#declaring-typed-errors), and `ctx.meta.role` comes from Huddle's [`authenticate` hook](/core/server/server/authenticate#the-authenticate-ctx):

```ts [server/admin.ts]
import * as v from 'valibot'
import { Forbidden } from '../shared/errors'
import { auditLogEntries } from './audit-log'
import { base } from './base'

const levels = ['info', 'warn', 'error'] as const

export const handleTailAuditLog = base.stream('tail-audit-log', {
  input: v.object({}),
  nudges: {
    stop: null, // no payload
    'set-level': v.object({ level: v.picklist(levels) }), // typed payload
  },
  async *run(ctx) {
    if (ctx.meta.role !== 'admin') {
      throw Forbidden({
        reason: 'only an admin may tail the audit log',
      })
    }

    let minLevel = 0 // index into `levels`: 0 shows every line
    for await (const entry of auditLogEntries(ctx.stream.signal)) {
      if (levels.indexOf(entry.level) < minLevel) continue

      const recent = ctx.stream.nudges(yield { line: entry.line })
      for (const n of recent) {
        if (n.event === 'stop') return

        if (n.event === 'set-level') {
          minLevel = levels.indexOf(n.payload.level)
        }
      }
    }
  },
})
```

`ctx.stream.nudges()` exists only when the stream declares at least one nudge. TypeScript narrows each message by its `event`, so `n.payload` has the right type for that event.

### Nudge buffering and overflow

Nudges that arrive between two `yield`s wait in a buffer. Your generator gets them at the next `yield`. The buffer has a limit. If the client sends nudges faster than the generator reads them and the buffer is full, LiveThing rejects the extra nudge with `NudgeOverflow`. This error is **non-terminal**: only that one nudge fails, and the stream keeps running.

```ts [client/admin.ts]
import { NudgeOverflow } from '@livething/core'
import { socket } from './socket'

const auditLog = await socket.stream('tail-audit-log', {})

// A rejected nudge throws NudgeOverflow. The stream keeps running.
try {
  await auditLog.nudge('set-level', { level: 'error' })
} catch (err) {
  if (NudgeOverflow.matches(err)) {
    // Sending too fast. Wait a little, then try again.
    // err.detail.cap is the buffer limit.
  }
}
```

`NudgeOverflow` carries `detail.cap`, the buffer limit, so the client knows how many nudges can wait at once. The limit is **256** waiting nudges. It is the same for plain and recorded streams, and no option changes it.

Waiting nudges survive a disconnect only on a recorded stream, because its generator keeps running (see [Disconnect behavior](#disconnect-behavior)). A plain stream stops when the client drops, and its nudge buffer is lost with it.

`NudgeOverflow` is a built-in error. See the [built-in errors catalog](/core/core/builtin-errors).

## Retention windows (recorded only)

Recorded streams are kept in storage, so a client that comes back can continue them. Two options control how long LiveThing keeps them.

| Option                | Default    | What it controls                                                                                                                                                                                                                                                                                      |
| --------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maxAgeMs`            | 5 minutes  | How long a stream whose generator stopped mid-stream (for example after a server restart, crash, deploy, or Cloudflare eviction) is kept, so a reconnecting client can still replay its chunks and learn it was interrupted. A reconnect after this time gets `StreamAborted({ reason: 'expired' })`. |
| `retentionAfterEndMs` | 30 seconds | How long an **ended** stream is kept after it finishes, so a client that reconnects quickly can still continue it. A reconnect after this time gets `StreamAborted({ reason: 'not-found' })`.                                                                                                         |

Here `ask-scout` sits on `base` with only the retention options. In Huddle, it is on `rooms` with `broadcast: true`, `stop` and `redirect` nudges, and no retention options (the defaults apply).

```ts [server/scout.ts]
import * as v from 'valibot'
import { base } from './base'
import { llm } from './llm'

export const handleAskScout = base.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  maxAgeMs: 10_000, // a cut-off stream is deleted after 10s
  retentionAfterEndMs: 30_000, // an ended stream is kept for 30s
  async *run(ctx, input) {
    const messages = [{ role: 'user', text: input.prompt }]
    for await (const piece of llm.stream({
      messages,
      signal: ctx.stream.signal,
    })) {
      yield { text: piece }
    }
  },
})
```

A background job runs about every 60 seconds. It deletes stored streams whose time is over, so old streams do not fill up storage.

## Disconnect behavior

What happens to the running generator when the connection that started the stream (its owner) drops depends on the kind:

| Kind     | When the owner drops                                                                                                                                                                                |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Plain    | LiveThing fires the abort signal and calls the generator's `return()`. The stream is gone.                                                                                                          |
| Recorded | The generator keeps running and stores each chunk. Broadcast subscribers keep getting chunks and the end. When the owner reconnects, LiveThing sends it the chunks it missed, then the live chunks. |

This also covers a **half-open** socket, one that died without a close frame: when the client reconnects and continues while the server still thinks the old socket is open, the running generator moves to the new connection. The server cannot tell this from a second tab that is healthy, so the old socket gets a terminal `taken-over` error either way. A dead socket has nobody to read it.

If a recorded generator stops before it finishes (it throws, or the server process stops while it runs), a later continue sends the stored chunks the client missed and then ends the stream with `StreamAborted` and the reason `'interrupted'`, not a normal end. On the wire, the last frame is:

```json
[
  "__error__",
  { "code": "stream-aborted", "detail": { "reason": "interrupted" } },
  {
    "stream": {
      "id": "s1",
      "event": "ask-scout",
      "terminated": true
    }
  }
]
```

A stream in a channel, like Huddle's `ask-scout`, also carries its `channel` metadata. This example leaves it out. LiveThing stores the stream as ended and interrupted, so every later continue gets the same signal until `retentionAfterEndMs` passes. A stream that really finished ends with a plain stream-end frame.

## The abort signal

Every stream generator gets [`ctx.stream.signal`](/core/server/streams/plain#the-abort-signal), an `AbortSignal`. It fires when the stream is cancelled, when the client leaves the stream's channel, when the user who started it is purged, or when the server shuts down. On a plain stream it also fires when the client disconnects. A recorded stream is not stopped when the client disconnects, so its signal does not fire then. Pass the signal into awaited work, such as `fetch`, so that work stops as soon as the stream stops.

## Abort reasons

When LiveThing has to stop a stream, or refuse a reconnect, it sends `StreamAborted` to the client with a `reason`. Client code reads the reason to decide what to do: continue, start again, or show an error. `StreamAborted` is a built-in error from `@livething/core`.

::field-group
::field{name="'cancelled'"}
The stream was cancelled, by the client or by the server.
::
::field{name="'buffer-full'"}
A recorded stream's buffer went over `maxChunks` or `maxBufferBytes`, or one chunk was too big to store or send. LiveThing throws it **into** the generator at the `yield`, so you can catch it.
::
::field{name="'expired'"}
A recorded stream whose generator stopped mid-stream was kept longer than `maxAgeMs` before the client came back.
::
::field{name="'not-found'"}
A reconnect named a stream ID the server does not know, or an ended stream older than `retentionAfterEndMs`.
::
::field{name="'hibernation-wake'"}
A running stream was lost because the server lost its in-memory state (for example, a Durable Object waking from hibernation). The connection is still open. Only the running stream is gone. For a durable stream, the LiveThing client continues on its own, so only a plain stream shows this reason to your code.
::
::field{name="'unsubscribed'"}
Two cases. The client cancelled this broadcast stream earlier, so the server stopped sending it chunks, and the stream keeps running for everyone else. Or the connection left the stream's channel (it unsubscribed, was kicked, or was removed), which stops every stream it ran there. The owning client gets this reason as the terminal error.
::
::field{name="'interrupted'"}
A recorded stream's generator stopped before it finished: it threw, or the server restarted, crashed, or was evicted while it ran. A continue sends the stored chunks the client missed, then this terminal error. Broadcast subscribers that continue get it too.
::
::field{name="'taken-over'"}
Another connection of the same user continued this recorded stream while it was still running, for example a second tab calling `continueStream`. The generator keeps running and its chunks go to the new connection. The old connection gets this reason as the terminal error, so its `for await` loop throws and does not continue on its own.
::
::field{name="'aborted'"}
Any other internal reason that matches none of the above.
::
::

```ts [client/scout.ts]
import { StreamAborted } from '@livething/core'
import {
  askScoutAgain,
  render,
  showRetryButton,
  showSlowDownToast,
} from './huddle-ui'
import { socket } from './socket'

const general = socket.channel('rooms', 'room:general')
await general.subscribe()
const handle = await general.stream('ask-scout', {
  prompt: 'Summarize today in #general',
})

try {
  for await (const chunk of handle) {
    render(chunk.text)
  }
} catch (err) {
  if (!StreamAborted.matches(err)) throw err

  if (err.detail.reason === 'buffer-full') showSlowDownToast()
  else if (err.detail.reason === 'interrupted') showRetryButton()
  else if (err.detail.reason === 'expired') askScoutAgain()
}
```

[`buffer-full`](/core/server/streams/durable-recorded#the-buffer-limit-and-streamaborted) is the only reason that server code can handle directly. LiveThing throws it into the generator, so your handler can catch it and stop cleanly. The shared error model (matching, codes, `detail`) is on the [Error model](/core/core/error-model) page.

## Stream ID and collisions

A client can start a stream with its own stream ID, using the `streamId` option of `socket.stream(...)`. The ID must be a non-empty string of up to 128 characters. This lets the client use an ID from its own app, such as a conversation ID or a job ID, to continue the stream later. If another running stream already uses that ID, LiveThing rejects the start with `StreamIdCollision`. When the client does not send an ID, LiveThing creates one.

A start is also rejected, with `StreamAlreadyActive`, when another stream of the same event is already running on the same connection. Set `allowConcurrent: true` on the stream to allow this.

Both are built-in errors. See the [built-in errors catalog](/core/core/builtin-errors).

## Storage layout (recorded streams)

When you list `recordedStream()`, LiveThing stores recorded streams in three SQL tables. They are in the server's own SQLite storage, the same database you use through `ctx.sql`. LiveThing creates the tables with `CREATE TABLE IF NOT EXISTS` [when the server starts](/core/server/under-the-hood/compile-and-boot#initialize-storage-schema), not when the first stream starts. Every other capability with stored tables does the same.

<!-- prettier-ignore-start -->
::field-group
::field{name="__livething_streams"}
One row per recorded stream. Who owns it and what started it (`user_id`, `stream_id`, `creator_user_id`, `event`, `payload`); lifecycle (`status`: active, suspended, or ended; `interrupted`, set when the generator stopped before it finished; `last_activity_at`, `ended_at`); the sequence number of the last chunk sent (`last_seq`); scope (`channel_key`, `channel_family`, `broadcast`); the retention options (`max_chunks`, `max_age_ms`, `retention_after_end_ms`).
::
::field{name="__livething_stream_chunks"}
One row per stored chunk of a recorded stream. Which stream it belongs to (`user_id`, `stream_id`), its order (`seq`), the chunk itself as JSON (`payload`, or the info of a binary chunk), the bytes of a binary chunk (`binary_payload`, `NULL` for a JSON chunk), and the bytes that `maxBufferBytes` counts (`row_bytes`).
::
::field{name="__livething_stream_subscribers"}
One row per subscriber of a broadcast stream. Which stream and who (`user_id`, `stream_id`, `subscriber_user_id`), the last chunk a reconnect has sent them (`caught_up_seq`), and when they cancelled (`unsubscribed_at`, `null` while still subscribed).
::
::
<!-- prettier-ignore-end -->

`user_id` is not always the user ID of a connection. For a broadcast stream, it is a key that LiveThing builds from the stream's scope (the whole server, or one channel). So every subscriber finds the same row when it continues, whatever its own user ID is. Deleting a stream's `__livething_streams` row also deletes its chunks and subscriber rows (a cascade delete).

::warning
Every table LiveThing owns uses the reserved `__livething_` prefix, including the three above. Never create your own table with that prefix, because `ctx.sql` is the same SQLite database that LiveThing writes to. A name collision gives no error at startup. For example, say you created a table named `__livething_streams` before you listed `recordedStream()`. LiveThing's `CREATE TABLE IF NOT EXISTS` then keeps your table and its different columns, with no error. Recorded streams later fail at runtime with unclear SQL errors, instead of a clear "table already exists" error at startup.
::

## Full option reference

Every option of the two builders (`base.stream`, `base.recordedStream`), with its default.

::field-group
::field{name="input" required}
Schema for the start payload the client sends. The second argument of `run` is the validated value. Applies to both stream kinds.
::
::field{name="nudges"}
Default: `{}`. Map from nudge event name to schema (or `null` for no payload). Read with `ctx.stream.nudges(yield ...)`. Applies to both stream kinds.
::
::field{name="broadcast" type="boolean"}
Default: `false`. Send chunks to every connection in scope, not only the connection that started the stream. Applies to both stream kinds.
::
::field{name="allowConcurrent" type="boolean"}
Default: `false`. Allow more than one stream of the same event at once on a connection. Without it, a second start is rejected with `stream-already-active`. Applies to both stream kinds.
::
::field{name="maxChunks" type="number"}
Default: 500. Maximum number of stored chunks. Going over it throws `StreamAborted` with the reason `'buffer-full'` into the generator. Applies to recorded streams only.
::
::field{name="maxBufferBytes" type="number"}
Default: 64 MiB. Maximum number of stored bytes: each chunk as JSON, plus the bytes of a binary chunk. Going over it throws `StreamAborted` with the reason `'buffer-full'` into the generator, as `maxChunks` does. Applies to recorded streams only.
::
::field{name="maxAgeMs" type="number"}
Default: 5 minutes. How long a stream whose generator stopped mid-stream (for example after a server restart) is kept before LiveThing deletes it. Applies to recorded streams only.
::
::field{name="retentionAfterEndMs" type="number"}
Default: 30 seconds. How long an ended stream is kept, so a client that reconnects quickly can still continue it. Applies to recorded streams only.
::
::field{name="run" required}
The async generator. Each yielded value is sent as one chunk. Applies to both stream kinds.
::
::
