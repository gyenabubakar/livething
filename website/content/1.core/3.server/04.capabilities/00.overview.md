A **capability** is an opt-in feature. You turn it on for a server by listing it in `server({ capabilities: [...] })`. Emitting events, typed errors, client-to-server requests, server-to-client requests, streams, channels, dedup and rate limiting are all capabilities. You add the ones your app needs and leave the rest out.

## What a capability is

When you call `server`, you give it an array of capabilities. You can also give it an `authenticate` function, which this example leaves out:

```typescript [server/not-found.ts]
import { emits, error, errors, server, t } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'
import type { Message } from './base'

const NotFound = error('not-found', v.object({ id: v.string() }))

const base = server({
  capabilities: [
    emits({ message: t<Message>() }),
    clientRequests(),
    errors([NotFound]),
  ],
})
```

Here `NotFound` is defined inline to keep the example in one file. Huddle imports it from [`../shared/errors`](/core/core/isomorphic-code#shared-error-definitions).

Listing a capability adds its engine code to your bundle. A capability you leave out adds no code. So **you pay only for what you use.** A small app that only pushes events lists `emits` and nothing else. Its bundle has no request, stream or channel code.

List each capability once per `capabilities` array. Put all of that capability's declarations in that one call. For example, use one `emits({ ... })` for every event at that scope, and one `serverRequests({ ... })` for every server-to-client request. A channel has its own array, so it may use the same capability name as the server without sharing declarations.

::note
The capability array is the only way to turn a feature on. There is no global config flag and no "enable everything" mode. If a feature is not in the array, its methods are not on `ctx` and its keys are not on the client contract.
::

## How capabilities shape your app

A capability adds to one or both of these places:

- The **[client contract](/core/learn/the-contract)**. This is the type that `InferClient<typeof huddle>` produces. It tells the client which events, requests and errors the server has. The events you declare with `emits` fill the client's `incoming` key. The errors you register with `errors` fill its `errors` key. The channels you define with `channels` fill its `channels` key. The client gets the matching typed methods with no extra code.
- The handler **`ctx`**. This is the context object your handlers receive. Adding `tags` puts `ctx.tags` on it. Adding `channels` puts `ctx.channels` on it. A method from a capability you did not list is not on `ctx`.

## The catalog

This table lists each capability, where to import it from, and what it gives you. Each row links to its own page.

| Capability                                                  | Import                              | What it enables                                                                                                              |
| ----------------------------------------------------------- | ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| [emits](/core/server/capabilities/emits)                    | `@livething/server`                 | Declare server→client events; enables `ctx.send` and `ctx.broadcast`                                                         |
| [errors](/core/server/capabilities/errors)                  | `@livething/server`                 | Register typed errors so they reach the client contract                                                                      |
| [clientRequests](/core/server/capabilities/client-requests) | `@livething/server/client-requests` | Client→server question/answer pairs your handlers respond to                                                                 |
| [serverRequests](/core/server/capabilities/server-requests) | `@livething/server/server-requests` | Server→client question/answer pairs the server sends                                                                         |
| [scheduled](/core/server/capabilities/scheduled)            | `@livething/server/scheduled`       | Run work later with timers and alarms (server-only)                                                                          |
| [streams](/core/server/capabilities/streams)                | `@livething/server/streams`         | Data the server pushes in chunks: `stream`, `recordedStream`                                                                 |
| [binary](/core/server/capabilities/binary)                  | `@livething/server/binary`          | Messages that carry raw bytes with JSON info: `binary.on`, `binary.request`, `binary.stream` and `.binary` senders           |
| [uploads](/core/server/capabilities/uploads)                | `@livething/server/uploads`         | Large files sent in pieces, with resume and cancel: `binary.upload` (needs `binary`)                                         |
| [channels](/core/server/capabilities/channels)              | `@livething/server/channels`        | Server-managed rooms, each with its own nested contract                                                                      |
| [tags](/core/server/capabilities/tags)                      | `@livething/server/tags`            | Group connections and address them by label                                                                                  |
| [keepalive](/core/server/capabilities/keepalive)            | `@livething/server/keepalive`       | Find and close dead connections with protocol-level pings. The [`http()`](/core/runtimes/transports/http) transport needs it |
| [dedup](/core/server/capabilities/dedup)                    | `@livething/server/dedup`           | Drop duplicate incoming messages                                                                                             |
| [sequence](/core/server/capabilities/sequence)              | `@livething/server/sequence`        | Number outgoing messages so the client can find gaps                                                                         |
| [replay](/core/server/capabilities/replay)                  | `@livething/server/replay`          | Send missed messages again on reconnect: `replay.history`, `replay.snapshot`                                                 |
| [rateLimit](/core/server/capabilities/rate-limit)           | `@livething/server/rate-limit`      | Limit how fast a connection can send                                                                                         |
| [lastSeen](/core/server/capabilities/last-seen)             | `@livething/server/last-seen`       | Track when each user was last seen: `ctx.lastSeen.at` / `.atMany`                                                            |

`emits` and `errors` come from the main `@livething/server` entry. Every other capability has its own subpath. Your bundler can then remove the code of every capability you do not import. This is called tree-shaking.

[Plugins](/core/server/plugins/overview) also go in the `capabilities` array. You build one with `plugin()` from `@livething/server/plugins`.

Three capabilities are not in this table: [inbox](/core/server/capabilities/inbox), [readReceipts](/core/server/capabilities/read-receipts) and [awareness](/core/server/capabilities/awareness). They never go in `server({ capabilities: [...] })`. They go in [a channel's own `capabilities` list](/core/server/capabilities/channels#capabilities-a-channel-may-need) instead. You import `inbox` and `readReceipts` from `@livething/server/inbox`, and `awareness` from `@livething/server/awareness`.

## Capabilities that plugins cannot list :badge[host-only]

A **plugin** is a reusable add-on that brings its own events, requests and channels to a server. The server that uses the plugin is called the **host**.

Some capabilities keep state for the whole connection, not for one feature. These capabilities are **host-only**: `keepalive`, `dedup`, `sequence`, `rateLimit`, `lastSeen`, and the `replay.*` family. You cannot list them in a plugin's scoped server definition (`server({ scope: 'plugin' })`), because a plugin is a self-contained add-on and these capabilities affect the whole connection. Listing one there is a type error.

If a plugin needs one of these, it [declares a dependency on the host](/core/server/plugins/depends-on). It does not list the capability itself.

## Requirements checked at assemble

A few capabilities need other capabilities to be listed too. `assemble()` checks this. If a needed capability is missing, `assemble()` throws an error that names the missing capability and where to add it:

- **Replay** (`replay.history()` and `replay.snapshot()`) needs `dedup()` and `sequence()`. Replay finds missed messages by their message ID and sequence number, so both capabilities must be on.
- **A channel's `inbox()`** ([listed in the channel's own `capabilities`](/core/server/capabilities/channels#capabilities-a-channel-may-need)) needs `channels()`, `sequence()` and `dedup()` on the host. **`readReceipts()`** needs `inbox()` on the same channel.

Some rules need the settings of other capabilities, so `assemble()` cannot check them. The engine checks them when the server starts, before any connection. Replay and inbox both need the sequence numbers to be saved to storage (`sequence({ persist: true })`), so they stay correct after a restart. A channel with `inbox()` must also set `membership: 'persistent'`. [Compile and boot](/core/server/under-the-hood/compile-and-boot) lists these checks.

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [
    dedup(),
    sequence({ persist: true }),
    replay.history(),
  ],
})
```

A plugin's scoped server definition works differently. If the plugin uses a feature that needs a host-only capability, LiveThing records that capability as a dependency on the host. You do not list it inside the plugin, and `assemble()` does not throw for it.
