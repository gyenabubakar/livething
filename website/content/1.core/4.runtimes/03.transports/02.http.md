`http()` runs LiveThing over plain HTTP requests: the server sends on a server-sent events stream, and the client sends with POST requests to the same URL. [Transports](/core/runtimes/transports/overview#turn-on-http) shows how to turn it on, and how the client picks between it and WebSocket. This page covers what is the same on every runtime: how the client sends, origins and proxies, and the costs. For the setup of your runtime, see [Node.js](/core/runtimes/adapters/node), your [Node framework's page](/core/runtimes/node-frameworks/overview), [Cloudflare](/core/runtimes/adapters/cloudflare#the-http-transport), [Bun](/core/runtimes/adapters/bun#the-http-transport) or [Deno](/core/runtimes/adapters/deno#the-http-transport).

## Stream mode

`http()` sends in one of two ways. Both use the same server and need no setup:

- **Batch mode**, where every client starts: short POSTs. One POST is in flight at a time. The messages you send while it is in flight go together in the next POST, up to 255 messages and `maxPostBytes`. When the connection is [busy](/core/server/handlers/per-connection-queue#busy-on-http), the next POST carries only as many messages as the server has room for, and the rest wait. `ping`, `pong` and the close go in a second POST, so they never wait behind your messages.
- **Stream mode**: one long POST whose body stays open, and each message goes in it as you send it. No new request per message, so it costs the server less and adds less delay, most of all behind a proxy.

The client moves to stream mode by itself, when it can:

1. After its first POST, the client checks that fetch can stream a request body and that the site is not on HTTP/1.1. Today this means Chromium browsers (Chrome, Edge, Brave, Opera and others) over HTTP/2 or HTTP/3. The stable releases of Firefox and Safari do not stream a request body yet, nor does any browser on iOS, and a browser refuses it on HTTP/1.1, so these clients stay in batch mode. The check runs on every connection, so a browser moves to stream mode once it supports it.
2. It opens the long POST and writes a small probe first. The server answers the probe on the stream at once.
3. When the answer comes, the client sends its next messages in the long POST. If it does not come within 2 seconds, or the request fails before the answer comes, the client stays in batch mode. It remembers this for the origin for 10 minutes, so the next connections do not try again. A long POST that fails later moves only this connection back to batch mode.

The probe is needed because some proxies read the whole body of a request before they pass it on. Such a proxy holds the long POST and never fails it. nginx does this by default. To let stream mode through nginx, add `proxy_request_buffering off;` and `client_max_body_size 0;` to the location of your endpoint. nginx limits a request body to 1 MB by default, also when it streams the body, and a long POST carries up to 8 MiB of messages before the client opens a fresh one. LiveThing still checks every message against its own limits. Without these lines, everything still works, in batch mode.

The server answers the long POST's messages on the stream, with one short answer for a burst of them. If the long POST dies later, the client sends every message that was not answered again, in batch mode. Each message has a number, so the server drops a message it already has, and no handler runs twice for one message. A long POST that sends nothing for 15 seconds sends a probe, so a dead path shows up there too. To close, the client writes the close in the long POST, after its last messages, and the server ends the stream when it reads it. So the messages run before the close, and a close costs no extra POST.

After 8 MiB of messages, the client ends the long POST and opens a fresh one, with no probe, because proxies and hosts limit the size of one request body, and on Cloudflare one request also has a limit on CPU time. The fresh one starts again at the first message with no answer yet, and the server drops the ones it already has. So one long POST carries about 8 MiB of new messages, plus the ones it sends again, which are at most four times `maxPostBytes`. With the default `maxPostBytes` of 512 KiB, one long POST stays under about 12 MiB.

## Origins, CORS and proxies

The Origin check covers both transports. A request with an `Origin` header must have the same host and port as its `Host` header, or its origin must be in `allowedOrigins`. Otherwise it gets `403`, and `authenticate` does not run. A request with no `Origin` header, such as one from a Node or mobile client, passes, unless its `Sec-Fetch-Site` header says it came from another site. The [Node.js](/core/runtimes/adapters/node#allowed-origins) and [Cloudflare](/core/runtimes/adapters/cloudflare#allowed-origins) pages show the option.

The check compares the host and port of the `Origin` with `Host`. So it does not stop DNS rebinding against a server that has no authentication, for example a local dev server. Add `authenticate` to such a server.

A browser can send a cross-site request with no `Origin` header, for example a `no-cors` `fetch`. To stop this on the stream, the client sends a `LiveThing-Protocol: livething-v1` header with every stream request. A plain cross-site request cannot carry this header, so the browser must send a preflight first, and the preflight carries `Origin`. The server answers a stream request without this header, or with another value, with `426` and `LiveThing-Error: not-offered`. This is the same answer as for a request without `Accept: text/event-stream`. So a page on another origin cannot open a stream without an `Origin` header.

A client on another origin needs CORS for `http()`, because the stream and the POSTs are `fetch` requests. LiveThing does the CORS part for every origin in `allowedOrigins`:

- It answers the preflight `OPTIONS` request. It allows the `Authorization`, `LiveThing-Secret`, `LiveThing-Lane`, `LiveThing-Seq`, `LiveThing-Upload`, `LiveThing-Protocol` and `Content-Type` headers, and sets `Access-Control-Max-Age` to 600 seconds, so a browser does not repeat the preflight before each POST.
- It adds `Access-Control-Allow-Origin` and `Vary: Origin` to the stream, the POSTs and every error response, and exposes the `LiveThing-Error` header, so the client can read an error status.

A request from an origin that is not allowed gets no CORS headers, so the browser reports a network error. Set `allowedOrigins` for every origin that serves your pages. The stream and the POSTs send cookies to the same origin only. A client on another origin logs in with the [`token`](/core/client/connecting/auth-and-query#token-auth-with-token) option, which goes in an `Authorization` header when the stream opens. Keep tokens small: a request whose headers are too large fails with `431`.

A preflight has no `Authorization` header, no cookies and no LiveThing headers. So a proxy, a Worker or a middleware in front of LiveThing must let `OPTIONS` requests through to the endpoint, or answer them itself. A reverse proxy that changes the `Host` header needs `allowedOrigins`, because the same-origin check reads `Host`. nginx changes it by default. Add `proxy_set_header Host $http_host;` to keep the browser's `Host`, or set `allowedOrigins`. A plain nginx `proxy_pass` with no `Upgrade` headers blocks WebSocket, and the client moves on to `http()`. nginx also reads a whole request body before it passes it on, which keeps clients in batch mode; see [Stream mode](#stream-mode).

The stream response has `Cache-Control: no-store, no-transform` and `X-Accel-Buffering: no`. `no-transform` tells a proxy not to compress the stream, because a proxy that compresses holds data until a block fills. `X-Accel-Buffering: no` tells nginx not to buffer it.

## Costs and limits

`http()` costs more than WebSocket for each message a client sends, and for each open connection's memory. (A broadcast can cost less: see the [benchmarks](/core/start/benchmarks#over-the-fallback-transports).) When you list both, keep WebSocket first in the client's list, so a client uses `http()` only when WebSocket fails.

- **Binary is bigger going down.** The server sends a binary message as base64 text on the stream, which is about a third bigger than on WebSocket (for example, 40,121 characters for 30,088 bytes). The client sends binary up as raw bytes.
- **One POST at a time.** In batch mode, the client sends its messages in POST batches, one batch at a time, in order. A batch holds at most 255 messages and `maxPostBytes` of data. A second lane carries only `ping`, `pong` and the close, so a slow upload cannot delay a `pong`. Each POST goes to the exact URL of its stream, query included. [Stream mode](#stream-mode) sends the messages in one long POST instead.
- **Serve over HTTP/2 or HTTP/3.** HTTP/1.1 allows six connections per site, shared by all tabs, and one client on `http()` can use three: the stream and the two POST lanes. On HTTP/2 and HTTP/3 they all share one connection, and only there can the client use stream mode. Browsers use HTTP/2 only over TLS, so plain `http://localhost` is HTTP/1.1. For local development of an app that lists only `http()`, use a local certificate. LiveThing does not share one connection between tabs.
- **Delivery is at most once**, as on WebSocket. A message can be lost when the connection drops, and the client does not send it again. If your app needs a retry, the app sends the message again. Within one connection, each message has a number, so the server drops a copy: a message that the client sends again after stream mode fails, or a POST that a browser or a proxy repeats on a network connection that was reset. A new connection starts new numbers, so make actions that change data idempotent.
- **A logout does not close an open stream.** The login check runs once, when the stream opens. Each POST carries only the connection's secret, not the login token. So your logout code must close the user's connections, for example with [`ctx.closeConnections({ userId })`](/core/server/admin/context#close-connections). This is the same as on WebSocket.
- **Several Node instances need sticky routing.** The stream and its POSTs must reach the same Node process. Run one instance, or use a load balancer that sends the stream and its POSTs to the same instance. LiveThing does not forward requests between instances. A POST that reaches another instance gets `404`, and the client opens a new stream and resumes.
- **On Cloudflare, an open stream keeps the Durable Object awake.** See [Cloudflare](/core/runtimes/adapters/cloudflare#the-http-transport).

### A tab that goes to sleep

A browser can freeze a background tab to save power. Chrome does it with Energy Saver on, for example. A frozen tab runs no code, so it cannot answer the server's [`keepalive()`](/core/server/capabilities/keepalive) pings, and the server closes the connection with `4004` (`IDLE`) after `idleTimeoutMs`. When the tab wakes, the client gets that close at once, and [`reconnection()`](/core/client/primitives/reconnection) connects again. Use [`replay()`](/core/server/capabilities/replay) for the messages sent while the tab was asleep. We tested this with `http()` in Chrome.
