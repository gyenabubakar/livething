`@livething/server-node` runs a LiveThing server definition on Node.js. Your application owns the HTTP server, its routes, and its signal handling (for example, what happens when the process gets `SIGTERM`). LiveThing owns one **endpoint** for each definition you bind. An endpoint is one running copy of a definition. It has its own engine, storage, timers, connections, and shutdown work.

This page sets up an endpoint with `node:http`. The options, limits, storage and shutdown steps on this page apply to every framework. The [Node frameworks](/core/runtimes/node-frameworks/overview) pages have one page for each framework, with only what is different there.

## Install

```bash [pnpm]
pnpm add @livething/server @livething/server-node @livething/core
```

The adapter uses two libraries: [`ws`](https://github.com/websockets/ws) to handle raw Node upgrades, and [`better-sqlite3`](https://github.com/WiseLibs/better-sqlite3) for its default SQL storage. Both are normal dependencies of the adapter, so the command above installs them for you. The adapter supports Node.js 22 and newer.

`better-sqlite3` contains native code, so it runs a build script when you install it. The build tools of many frameworks, such as Vite and Nuxt, use `esbuild`, which also has an install script. pnpm can block install scripts. If it does, allow these two packages in `package.json`:

```json [package.json]
{
  "pnpm": {
    "onlyBuiltDependencies": ["better-sqlite3", "esbuild"]
  }
}
```

## node:http

Call `setup()` once for the group of endpoints that should shut down together. Its `bind()` method creates one endpoint from one definition. `bind()` always takes an options object as its second argument.

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind, ready, shutdown } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})

const app = createServer((request, response) => {
  response.statusCode = 404
  response.end()
})

app.on('upgrade', (request, socket, head) => {
  const url = new URL(
    request.url ?? '/',
    `http://${request.headers.host}`,
  )

  if (url.pathname === '/huddle') {
    huddleEndpoint.upgrade(request, socket, head)
    return
  }

  socket.destroy()
})

await ready()
app.listen(3000)

process.once('SIGTERM', async () => {
  await shutdown()
  app.close()
})
```

`huddleEndpoint.upgrade` does not check the request path. Your application does that. It does check the request type: when the `Upgrade` header is not `websocket`, it answers `400` and your `authenticate` hook does not run. This keeps the basic Node API small, and you can use any routing library or your own matching code. For framework routes and route parameters, use the entry point for your framework: `@livething/server-node/hono`, `@livething/server-node/fastify`, or `@livething/server-node/h3`. [Node frameworks](/core/runtimes/node-frameworks/overview) lists them all.

The endpoint can also offer `http()`, on its own or next to WebSocket. Its requests are plain HTTP requests, not upgrades, so they go to `huddleEndpoint.handle` from your request listener. [Serve `http()`](#serve-http) shows the setup.

You can bind several endpoints to the same server. Each one gets its own path. Here Huddle also runs a second definition, `presence`, next to `huddle`:

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'
import { presence } from './server/presence-definition'

const { bind, ready } = setup()
const huddleEndpoint = bind(huddle, { sql: './data/huddle.sqlite' })
const presenceEndpoint = bind(presence, {
  sql: './data/presence.sqlite',
})

const app = createServer((request, response) => {
  response.statusCode = 404
  response.end()
})

app.on('upgrade', (request, socket, head) => {
  const pathname = new URL(
    request.url ?? '/',
    `http://${request.headers.host}`,
  ).pathname

  if (pathname === '/huddle') {
    huddleEndpoint.upgrade(request, socket, head)
    return
  }

  if (pathname === '/presence') {
    presenceEndpoint.upgrade(request, socket, head)
    return
  }

  socket.destroy()
})

await ready()
app.listen(3000)
```

Wait for `ready()` before you call `listen()`. `ready()` waits for every endpoint that the setup has created at the time of the call. If you create an endpoint later, wait for that endpoint's own `ready()` method before you send traffic to it.

## Serve `http()`

On Node, `http()` uses plain HTTP requests, not upgrades, so they do not reach `huddleEndpoint.upgrade`. Pass every request to the endpoint's path to `huddleEndpoint.handle`. It serves the stream, the POSTs and the CORS preflight:

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { http, setup, websocket } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind, ready } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocket(), http()],
})

function isHuddlePath(url = '/'): boolean {
  return new URL(url, 'http://localhost').pathname === '/huddle'
}

const app = createServer((request, response) => {
  if (isHuddlePath(request.url)) {
    huddleEndpoint.handle(request, response)
    return
  }

  response.statusCode = 404
  response.end()
})

app.on('upgrade', (request, socket, head) => {
  if (isHuddlePath(request.url)) {
    huddleEndpoint.upgrade(request, socket, head)
    return
  }

  socket.destroy()
})

await ready()
app.listen(3000)
```

`handle`, like `upgrade`, does not check the path. Your app does. `handle` also takes a request and a response from a `node:http2` compatibility server, which is how you serve `http()` over HTTP/2 on Node, and how browser clients get [stream mode](/core/runtimes/transports/http#stream-mode). Browsers use HTTP/2 only over TLS, so use `createSecureServer` from `node:http2` with `allowHTTP1: true`, which keeps WebSocket working on HTTP/1.1.

`shutdown()` closes the open streams with the other connections, and drops a stream request that is still in `authenticate`. Node's server timeouts do not cut an open stream, so you do not need to change them. A POST body follows Node's `requestTimeout`, which is 300 seconds by default. On `node:http`, that timeout also ends the long POST of stream mode after 300 seconds, and the client moves back to batch mode. A `node:http2` server has no such timeout.

### Less memory on HTTP/2

For each HTTP/2 stream, a `node:http2` server with a `request` listener makes a request and a response object, and keeps them while the stream is open. An open stream costs about 2 KB more with them. A client holds its SSE stream open, and in stream mode its long POST too. `huddleEndpoint.handleStream(stream, headers)` serves the raw stream of a `stream` listener instead, with no such objects. It is the same as `handle` in every other way.

Node makes those objects for every stream of a server that has a `request` listener, also for the streams you pass to `handleStream`. HTTP/1.1 needs that listener, and so do WebSocket (its upgrade starts on HTTP/1.1) and proxies that speak only HTTP/1.1 to your server. So give each protocol its own server, and let one TLS port pick between them:

```ts [huddle-server.ts]
import { readFileSync } from 'node:fs'
import { createServer as createHttp1Server } from 'node:http'
import { createServer as createHttp2Server } from 'node:http2'
import { createServer as createTlsServer } from 'node:tls'
import { http, setup, websocket } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind, ready } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocket(), http()],
})

function isHuddlePath(url = '/'): boolean {
  return new URL(url, 'https://localhost').pathname === '/huddle'
}

// HTTP/2 with only a `stream` listener.
const http2App = createHttp2Server()
http2App.on('stream', (stream, headers) => {
  if (isHuddlePath(headers[':path'])) {
    huddleEndpoint.handleStream(stream, headers)
    return
  }

  stream.respond({ ':status': 404 })
  stream.end()
})

// HTTP/1.1, for WebSocket and for proxies that speak only HTTP/1.1.
const http1App = createHttp1Server((request, response) => {
  if (isHuddlePath(request.url)) {
    huddleEndpoint.handle(request, response)
    return
  }

  response.statusCode = 404
  response.end()
})
http1App.on('upgrade', (request, socket, head) => {
  if (isHuddlePath(request.url)) {
    huddleEndpoint.upgrade(request, socket, head)
    return
  }

  socket.destroy()
})

// Each TLS connection goes to the server of the protocol the client picked.
const tlsOptions = {
  key: readFileSync('./certs/huddle.key'),
  cert: readFileSync('./certs/huddle.crt'),
  ALPNProtocols: ['h2', 'http/1.1'],
}

const huddleServer = createTlsServer(tlsOptions, (socket) => {
  const app = socket.alpnProtocol === 'h2' ? http2App : http1App
  app.emit('connection', socket)
})

await ready()
huddleServer.listen(443)
```

In our [load test](/core/start/benchmarks) with 2,000 clients, on a server that had just started, this cut the server's memory for each connection from 22.0 KB to 18.2 KB in stream mode, and from 17.0 KB to 15.0 KB in batch mode over HTTP/2. Connects and disconnects also cost less CPU. A server with `allowHTTP1: true` and `handle` works the same, with that extra cost.

## Runtime configuration and the upgrade request

The Node adapter does not copy environment variables into the LiveThing context. Read Node configuration from `process.env` in your Node entry point. You can also pass the values directly into the server definition or plugin factory that needs them.

Your `authenticate(request)` function receives a standard Web API `Request`. The adapter builds it from Node's `IncomingMessage`. It contains the full request URL, method, headers, cookies, and an abort signal, so read the path, the query string or a header from it when the definition needs them. The signal aborts if the client leaves before the handshake finishes, or when `shutdown()` starts:

```ts [server/huddle-definition.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectAuth } from '@livething/server/errors'
import { verifySession } from './auth'

const base = server({
  async authenticate(request) {
    const token = request.headers
      .get('Authorization')
      ?.replace('Bearer ', '')
    const user = await verifySession(token) // your auth: returns { id, name, role } or null
    if (!user) {
      throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { userId: user.id, name: user.name, role: user.role },
    }
  },
  capabilities: [],
})
```

The request has no body, because it is an upgrade request. The [Authenticate](/core/server/server/authenticate) page shows what `authenticate` can return and how to reject a connection.

## Message size limit

Each endpoint has a largest message size, `maxMessageBytes`. The default is 32 MiB, the same as Cloudflare, so the same app behaves the same on both. It must be a whole number from 1 to `2147483647`, because `ws` keeps its `maxPayload` as a 32-bit number. A client message over the limit closes the socket with `1009` ([`MESSAGE_TOO_BIG`](/core/core/close-codes)), and a server send over the limit throws an error instead of sending. Raise it on purpose when an endpoint needs bigger messages:

```ts [huddle-server.ts]
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
// Huddle's file uploads need room for messages up to 64 MiB.
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  maxMessageBytes: 64 * 1024 * 1024,
})
```

`bind()` creates a `ws` server for each endpoint and sets its `maxPayload` to `maxMessageBytes`, so `ws` refuses a bigger message before LiveThing reads it. You set the limit in one place. When you pass your own `webSocketServer`, LiveThing does not change it. Set its `maxPayload` to the same value as `maxMessageBytes`. LiveThing also checks the length of every message when it arrives, so the limit holds even when only one of the two is set.

[Fastify](/core/runtimes/node-frameworks/fastify), [H3](/core/runtimes/node-frameworks/h3) and the [Nitro apps](/core/runtimes/node-frameworks/overview#nitro-apps-nuxt-solidstart-and-tanstack-start) create the WebSocket server themselves, so LiveThing does not set its limit there either. Set it in both places: give that server a message limit, and pass the same value to `bind()` as `maxMessageBytes`. If you set only the server's limit, LiveThing still closes a connection with `1009` at its own limit, which is 32 MiB by default. [Hono](/core/runtimes/node-frameworks/hono#message-size-and-compression-on-hono) sets the limit in `setup()`.

One connection can also hold up to twice `maxMessageBytes` of [messages whose handlers have not started yet](/core/server/handlers/per-connection-queue).

## Allowed origins

A browser sends an `Origin` header with every WebSocket handshake: the scheme, host and port of the page that opens the socket. The endpoint compares the host and port of that `Origin` with the request's `Host` header. If they differ, it answers `403` and does not run `authenticate`. This stops another website from opening a socket with your users' cookies. A request with no `Origin` header, such as one from a Node or mobile client, passes, unless its `Sec-Fetch-Site` header says it came from another site. The endpoint does not read `X-Forwarded-Host`, because any client can send it.

The check compares the host and port of the `Origin` with `Host`, so it does not stop DNS rebinding against a server that has no authentication, such as a local dev server. Add `authenticate` to such a server.

When your pages are served from another origin, list that origin in `allowedOrigins`. You also need it behind a reverse proxy that changes the `Host` header:

```ts [huddle-server.ts]
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
// Huddle's web app runs on the Vite dev server during development.
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  allowedOrigins: ['http://localhost:5173'],
})
```

Write each entry as an origin: the scheme, host and port, with no path. `bind()` throws for any other value.

The same check covers [`http()`](/core/runtimes/transports/http#origins-cors-and-proxies), where `allowedOrigins` also decides which origins get CORS headers. The client sends a `LiveThing-Protocol: livething-v1` header with every stream request, so a browser always sends a preflight with `Origin` first. A stream request without it gets `426`.

## Compression

`compression: true` turns on the WebSocket compression extension, `permessage-deflate`. Browsers and the `ws` client ask for it on their own, so the client needs no change. With it on, each message of at least 1024 bytes goes compressed, in both directions.

```ts [huddle-server.ts]
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
// Huddle's `load-history` pages are big JSON lists of messages, which compress well.
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  compression: true,
})
```

To change the smallest size that gets compressed, pass `compression: { threshold }`, in bytes. For example, `compression: { threshold: 4096 }`. A small message gains little and still costs CPU, so it goes as it is.

Compression helps JSON and text a lot, because they repeat the same keys and words. It does not help bytes that are already compressed, such as images, audio and video. Huddle's voice notes and screen frames, for example, stay about the same size. [Binary messages](/core/client/primitives/binary) still work with compression on.

Compression costs CPU for every message, and memory for every connection. For this reason it is off by default. Each message is compressed on its own, so a connection keeps no data from earlier messages. This uses less memory, but repeated small messages compress less well.

When you pass your own `webSocketServer`, set `perMessageDeflate` on it instead. `bind()` throws an error if it gets both `webSocketServer` and `compression`. When a framework creates the WebSocket server, you turn on compression there too. The [framework pages](/core/runtimes/node-frameworks/overview) show how.

## Client IP

Read the client address in [`authenticate(request)`](/core/server/server/authenticate#client-ip). The adapter puts it in the `LiveThing-Client-IP` request header. On Node, there is no single correct way to find the end user's IP address. By default the adapter does not add the header. Set the `clientIp` option only when you know how requests reach your Node process:

```ts
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  clientIp: { mode: 'direct' },
})
```

`direct` uses the TCP peer address. This is the address of the computer that opened the connection to Node. If Node runs behind a proxy, that address may be the proxy's address. When requests pass through proxies that you trust, list the proxy networks:

```ts
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  clientIp: {
    mode: 'proxy',
    trustedProxies: ['127.0.0.1/32', '10.0.0.0/8'],
  },
})
```

Each entry is an IP address or an address range in CIDR form. The list must not be empty.

In `proxy` mode, the TCP peer must be one of the trusted proxies. The adapter then reads the addresses in the `X-Forwarded-For` header, starting from the one nearest to Node. It uses the first address that is not a trusted proxy. If an address in that chain is not a valid IP address, or if every address is a trusted proxy, the adapter does not add `LiveThing-Client-IP`. The adapter never trusts forwarding headers unless you set `proxy` mode.

`clientIp` needs the original Node request, because it reads the socket address from it. Hono, Fastify and H3 v2 can give the binding that request. H3 v1, and so Nuxt, cannot. Each framework page says what it supports.

## Storage, timers, and WebSockets

By default, the `sql` storage is an in-memory `better-sqlite3` database, so its data is lost when the process stops. Give a file path when SQL data, KV data, or scheduled work must survive a restart:

```ts
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})
```

`better-sqlite3` and `node:sqlite` create the file but not its folder. Create the `data` folder before you start the server. When the folder does not exist, `bind()` throws an error.

When you give a file path, Node opens the database in WAL mode with `synchronous = NORMAL`. In this mode, SQLite does not wait for the disk on each commit, so writes are many times faster. If the app crashes, no data is lost. If the computer loses power, the last few commits can be lost. Clients may already have those messages, and replay will not send them again. With `sequence({ persist: true })`, the server can also give a delivery number a second time. SQLite also keeps two more files next to the database, ending in `-wal` and `-shm`. Keep them with the database. WAL mode stays on the file, so other programs that open it later use it too. WAL does not work on a network drive, such as NFS. Keep the file on a local disk. If you need every commit on disk, open the database yourself and pass it in. LiveThing does not change the settings of a database you pass in.

The `sql` option also accepts a `better-sqlite3` database that you opened yourself, a `node:sqlite` database, or your own SQL provider. When you do not give a `kv` provider, Node stores `ctx.kv` in the same SQLite database as `ctx.sql`. If you give your own SQL provider, you must also give a `kv` provider. LiveThing closes the resources it creates. It never closes a SQL database or KV provider that you passed in.

### SQLite without a native module

Node.js has its own SQLite in the `node:sqlite` module. Pass a `DatabaseSync` as `sql`, and the adapter uses it in place of `better-sqlite3`, for `ctx.sql` and `ctx.kv`:

```ts [huddle-endpoint.ts]
import { DatabaseSync } from 'node:sqlite'
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const huddleDatabase = new DatabaseSync('./data/huddle.sqlite')
const { bind } = setup()
export const huddleEndpoint = bind(huddle, { sql: huddleDatabase })
```

On Node 22, this needs 22.16 or newer. Node 22, Node 24 before 24.15, and Node 25 before 25.7 print an `ExperimentalWarning` when `node:sqlite` loads. `better-sqlite3` is still installed, and its build script still runs, but its native code never loads while every endpoint gets a `node:sqlite` database. The [Deno](/core/runtimes/adapters/deno) setup uses the same option.

`ctx.sql` works the same on both, with two differences. When a query has fewer values than `?` placeholders, `better-sqlite3` throws, but `node:sqlite` stores `NULL` for the missing ones. And when a stored integer is bigger than `Number.MAX_SAFE_INTEGER`, `better-sqlite3` rounds it, but `node:sqlite` throws a `RangeError`.

The endpoint forwards messages, close events, and errors to the engine. It forwards a binary message as a plain `Uint8Array`. A server that lists [`binary()`](/core/server/binary/overview) routes it; without `binary()`, a binary frame closes the socket with code `1003` (unsupported data). Raw Node endpoints report the socket's real `ws.bufferedAmount`. So `ctx.stream.drain()` waits on the real socket buffer when a stream sends faster than the client can read.

Node does not support hibernation. If a definition enables hibernation, the endpoint fails when it starts, and `ready()` rejects with an error.

## Call the admin API from your app

Each endpoint has its own admin object. It runs in the same process as your HTTP server, so any code in that process can use it: an HTTP route, a webhook handler, or a background job. `huddleEndpoint.admin()` returns the built-in [admin context](/core/server/admin/context) plus the methods from [`assemble({ api })`](/core/server/admin/authoring). TypeScript infers its type from the server definition.

For example, Huddle's moderators post an announcement from an internal dashboard. The dashboard sends a `POST` request, and the route calls `announce` from Huddle's admin `api`, which sends the announcement on the `announcements` channel, so every member of that channel gets it:

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { verifySession } from './auth'
import { huddleEndpoint } from './huddle-endpoint'

const app = createServer(async (request, response) => {
  const url = new URL(
    request.url ?? '/',
    `http://${request.headers.host}`,
  )

  if (
    request.method === 'POST' &&
    url.pathname === '/admin/announcements'
  ) {
    const token = request.headers.authorization?.replace(
      'Bearer ',
      '',
    )
    const user = await verifySession(token) // your auth
    if (user?.role !== 'admin') {
      response.writeHead(401).end()
      return
    }

    let body = ''
    for await (const chunk of request) body += chunk
    const { text } = JSON.parse(body) as { text: string }

    const admin = await huddleEndpoint.admin()
    await admin.announce(text)
    response.writeHead(204).end()
    return
  }

  response.writeHead(404).end()
})
```

Here `huddleEndpoint` is the endpoint from `bind(huddle, ...)`, exported from its own module (`huddle-endpoint.ts`) so that the upgrade listener and the routes share it. The same object has the built-in operations. For example, a webhook from your auth provider can call `admin.purgeUser(userId)` when a user deletes their account, and a health route can read `admin.connectionCount`.

::warning
An admin call skips every check that protects the socket side: `authenticate`, channel `check` and `commit`, and rate limits. Protect every route that calls `admin()` with [your own auth](/core/server/admin/reaching-it#auth-is-your-boundary), as the `verifySession` check does above.
::

## Shutdown

Your application decides when to stop. `shutdown()` does these steps:

1. It destroys the sockets and responses of upgrades and requests that are still in progress, and waits for their work to end.
2. It stops the timers and waits for the scheduled tasks that are running.
3. It runs your `onShutdown` hooks.
4. It closes the open connections: the WebSockets and the server-sent events streams.
5. It closes the storage that LiveThing created.

`shutdown()` does not close your HTTP server, and it does not add signal handlers. Call `shutdown()` first, then close your server. If an upgrade or a request to `handle` arrives after shutdown starts but before your HTTP server closes, LiveThing destroys that socket or response, without a WebSocket handshake, and does not run the definition for it, so `authenticate` does not run either. H3 is different: see [H3 v2](/core/runtimes/node-frameworks/h3#h3-v2) and [H3 v1](/core/runtimes/node-frameworks/h3#h3-v1).
