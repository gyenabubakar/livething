Each framework page shows only what is different from the `node:http` setup of the [Node.js adapter](/core/runtimes/adapters/node). Everything else works as that page explains: the options, limits, origins, compression, client IP, storage, admin API and shutdown.

| Framework                                    | Import                           | Where LiveThing gets the upgrade                        |
| -------------------------------------------- | -------------------------------- | ------------------------------------------------------- |
| Express, Koa, React Router, SvelteKit, Astro | `@livething/server-node`         | The `upgrade` event of a Node HTTP server your app owns |
| Hono                                         | `@livething/server-node/hono`    | A Hono route                                            |
| Fastify                                      | `@livething/server-node/fastify` | A Fastify route, with `@fastify/websocket`              |
| H3 v2, SolidStart, TanStack Start            | `@livething/server-node/h3`      | An H3 route, with CrossWS 0.4                           |
| H3 v1, Nuxt 4                                | `@livething/server-node/h3/v1`   | An H3 route, with CrossWS 0.3                           |

With `@livething/server-node`, `bind()` creates the `ws` server, so `maxMessageBytes` and `compression` work as [Message size limit](/core/runtimes/adapters/node#message-size-limit) and [Compression](/core/runtimes/adapters/node#compression) explain. The framework's routes, route parameters and middleware do not run for an upgrade request. Match the WebSocket path yourself in the `upgrade` listener. If you want to declare WebSocket routes with the framework's own router, with route parameters and middleware, use Hono, Fastify or H3.

Each framework page ends with an admin route for that framework. In it, `huddleEndpoint` is the endpoint from `bind(huddle, ...)`, exported from its own module so the WebSocket side and the admin route share it. `announce` comes from Huddle's [admin `api`](/core/server/admin/authoring), and the same object has the built-in operations, such as `purgeUser` and `connectionCount`. An admin call skips every check that protects the socket side, so protect each admin route with your own auth, as [Call the admin API from your app](/core/runtimes/adapters/node#call-the-admin-api-from-your-app) explains.

If your framework is not listed, [Build your own](/core/runtimes/node-frameworks/build-your-own) shows how to write an integration for it.

## Nitro apps: Nuxt, SolidStart and TanStack Start

[Nitro](https://nitro.build) is the server layer under Nuxt, SolidStart and TanStack Start. It runs both the development server and the production Node server, and it provides the route files and the lifecycle hooks. Nitro uses H3 to send each HTTP request and WebSocket request to the right route, and CrossWS to run the WebSocket connection. Nuxt 4 runs on Nitro 2, which uses H3 v1. SolidStart v2 and TanStack Start run on Nitro 3, which uses H3 v2. So LiveThing connects to them through its H3 bindings, and one WebSocket route file works both in development and in the built Node server.

A Nitro app uses three LiveThing files:

- `server/utils/huddle-endpoint.ts` creates the endpoint. The WebSocket route, the startup plugin, and any server route that calls the admin API all import it from here, so they all use the same running endpoint.
- `server/routes/huddle.ts` is the WebSocket route. Nitro turns this file path into the URL `/huddle`, and the client connects to `/huddle`. The endpoint can also offer `http()`, on its own or next to WebSocket, and this route serves it too: see the change for [Nuxt](/core/runtimes/node-frameworks/nuxt#serve-http), [SolidStart](/core/runtimes/node-frameworks/solidstart#serve-http) and [TanStack Start](/core/runtimes/node-frameworks/tanstack-start#serve-http).
- `server/plugins/huddle.ts` starts and stops LiveThing together with Nitro. A Nitro plugin is a file in `server/plugins/` that runs once when the Nitro server starts. It is not an HTTP route. Name the file after the server it starts.

::warning
Call `setup()` and `bind()` only in the endpoint file. Each `bind()` call starts a separate LiveThing endpoint with its own connections. An endpoint created in another file sees no connected users.
::

The plugin does two things:

- It adds `shutdown` to Nitro's `close` hook. When Nitro closes, LiveThing closes its connections, stops its timers, and closes the SQLite file.
- It calls `ready()`, which resolves when LiveThing's storage and timers have started. When startup fails (for example, the SQLite file cannot open), the plugin logs the error and stops the process, so you see the failure at startup and not on the first connection.

Nitro does not wait for a plugin's promise, so the plugin does not `await` `ready()`. This is not a problem for early traffic: a WebSocket upgrade that arrives before startup finishes waits until LiveThing is ready.

Nitro creates the WebSocket server, so set its message limit and `maxMessageBytes` both, as [Message size limit](/core/runtimes/adapters/node#message-size-limit) explains. Nitro also runs that server, so LiveThing cannot turn on WebSocket compression (`permessage-deflate`) there. Each framework page says what you can do.

Run `pnpm dev` during development. Build and run the production Node server with:

```bash
pnpm build
HOST=0.0.0.0 PORT=3000 node .output/server/index.mjs
```

`HOST=0.0.0.0` makes the server accept connections from other machines, not only from `localhost`.

Some Nitro development servers give the route only a Web API `Request`. The built Node server also gives it the raw Node request. The route accepts WebSocket connections in both cases. On SolidStart and TanStack Start, set LiveThing's [`clientIp`](/core/runtimes/node-frameworks/h3#client-ip-on-h3-v2) option only when your Nitro host gives the route the raw Node request. If you set `clientIp` and the host gives only a Web API `Request`, every upgrade to this route throws an error. Nuxt does not support `clientIp` at all.

## Serve `http()`

Each Node framework binding has a matching route for [`http()`](/core/runtimes/transports/overview). Hono, Fastify and H3 have their own `handle` route. The other frameworks run on a Node HTTP server that your app owns, so they use `huddleEndpoint.handle` from `@livething/server-node`. Each framework page shows its route.

### Express, Koa, React Router, SvelteKit and Astro

The [Express](/core/runtimes/node-frameworks/express), [Koa](/core/runtimes/node-frameworks/koa), [React Router](/core/runtimes/node-frameworks/react-router), [SvelteKit](/core/runtimes/node-frameworks/sveltekit) and [Astro](/core/runtimes/node-frameworks/astro) pages bind Huddle with `@livething/server-node`. Add `transports` to that `bind()` call, and add a function that sends the `http()` requests for `/huddle` to LiveThing and passes every other request on:

```js [huddle-endpoint.js]
import { http, setup, websocket } from '@livething/server-node'
import { huddle } from './server/huddle-definition.ts'

export const huddleNode = setup()
export const huddleEndpoint = huddleNode.bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocket(), http()],
})

export function handleHuddleRequest(request, response, next) {
  const url = new URL(
    request.url ?? '/',
    `http://${request.headers.host}`,
  )
  if (url.pathname !== '/huddle') return next()

  huddleEndpoint.handle(request, response)
}
```

`handleHuddleRequest` has the shape of a Connect or Express middleware: `(request, response, next)`. For React Router, SvelteKit and Astro, the module also keeps its `globalThis` guard, and for SvelteKit and Astro its `handleHuddleUpgrade` function. The `upgrade` listener of each framework stays as it is. Each framework page shows where the function goes.
