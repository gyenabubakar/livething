This page builds on the [Node.js adapter](/core/runtimes/adapters/node). It shows only what is different with SolidStart. The options, limits, origins, compression, client IP, storage, admin API and shutdown work as that page explains.

SolidStart v2 can run on Nitro 3, so LiveThing connects to it through its [H3 v2 binding](/core/runtimes/node-frameworks/h3#h3-v2). Read [Nitro apps](/core/runtimes/node-frameworks/overview#nitro-apps-nuxt-solidstart-and-tanstack-start) first for what each file does.

```bash [pnpm]
pnpm add @livething/core @livething/server @livething/server-node h3@^2.0.1-rc.31 crossws@^0.4.12 nitro
```

In `vite.config.ts`, add the Nitro Vite plugin after the SolidStart Vite plugin. Then turn on WebSockets and choose the Node server preset:

```ts [vite.config.ts]
import { solidStart } from '@solidjs/start/config'
import { nitro } from 'nitro/vite'
import { defineConfig } from 'vite'

export default defineConfig({
  plugins: [solidStart(), nitro()],
  nitro: {
    serverDir: './server',
    preset: 'node_server',
    features: {
      websocket: true,
    },
  },
})
```

Merge these values into your existing config. Keep your other Vite plugins and SolidStart options.

- `serverDir` is the folder that holds Nitro's route files and plugin files.
- A preset is a Nitro build target. `node_server` builds a Node process.
- `features.websocket` turns on Nitro's WebSocket upgrade path. It is off by default.

Create the endpoint. The example expects `server/huddle-definition.ts` to export `huddle`, the [server definition](/core/server/server/overview) that contains your event handlers. `setup()` creates the shared adapter. `bind()` connects the server definition to the adapter and returns the endpoint:

```ts [server/utils/huddle-endpoint.ts]
import { setup } from '@livething/server-node/h3'
import { huddle } from '../huddle-definition'

export const huddleNode = setup()
export const huddleEndpoint = huddleNode.bind(huddle, {
  sql: './data/huddle.sqlite',
})
```

Export `huddleEndpoint.connect` as the WebSocket route. It is the H3 WebSocket handler for this route, and it runs the WebSocket handshake:

```ts [server/routes/huddle.ts]
import { huddleEndpoint } from '../utils/huddle-endpoint'

export default huddleEndpoint.connect
```

Add the Nitro plugin:

```ts [server/plugins/huddle.ts]
import { definePlugin } from 'nitro'
import { huddleNode } from '../utils/huddle-endpoint'

export default definePlugin((nitroApp) => {
  nitroApp.hooks.hook('close', huddleNode.shutdown)

  huddleNode.ready().catch((error) => {
    console.error('LiveThing huddle server failed to start', error)
    process.exit(1)
  })
})
```

Whether you can turn on compression depends on the WebSocket server options that SolidStart and Nitro give you. When that server has compression on, LiveThing asks for each message to be compressed. `ws` compresses a message only when the client agreed to compression and the message is not under the server's size threshold. [Message size and compression on H3](/core/runtimes/node-frameworks/h3#message-size-and-compression-on-h3) explains when that threshold works.

## Serve `http()`

SolidStart runs on Nitro with H3 v2. Add `transports` to the endpoint file from the setup above:

```ts [server/utils/huddle-endpoint.ts]
import { http, websocket } from '@livething/server-node'
import { setup } from '@livething/server-node/h3'
import { huddle } from '../huddle-definition'

export const huddleNode = setup()
export const huddleEndpoint = huddleNode.bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocket(), http()],
})
```

The route file `server/routes/huddle.ts` stays as it is. Nitro sends every method to `huddleEndpoint.connect`, and `connect` passes a request that is not a WebSocket upgrade to `handle`. As on [H3 v2](/core/runtimes/node-frameworks/h3#serve-http-on-h3-v2), `handle` needs the original Node request. The `node_server` preset runs on a Node server. A development server that gives the route only a Web API `Request` gets `500` from `handle`.

## Call the admin API from a SolidStart route

A normal Nitro route can use the admin API:

```ts [server/routes/admin/announcements.post.ts]
import { defineEventHandler } from 'h3'
import { verifySession } from '../../utils/auth'
import { huddleEndpoint } from '../../utils/huddle-endpoint'

export default defineEventHandler(async (event) => {
  const token = event.req.headers
    .get('authorization')
    ?.replace(/^Bearer /i, '')
  const user = await verifySession(token) // your auth
  if (user?.role !== 'admin') {
    event.res.status = 401
    return null
  }

  const { text } = (await event.req.json()) as { text: string }

  const admin = await huddleEndpoint.admin()
  await admin.announce(text)
  event.res.status = 204

  return null
})
```

The route imports `huddleEndpoint` from the same shared file as the WebSocket route, so the admin call reaches the users connected to `/huddle`.
