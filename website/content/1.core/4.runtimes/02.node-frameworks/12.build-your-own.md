`@livething/server-node/binding` is the public API for people who build a Node WebSocket integration for a framework. Application code should use `setup()` from `@livething/server-node`, or a ready-made integration such as `@livething/server-node/hono`. The [Node frameworks](/core/runtimes/node-frameworks/overview) overview lists the ready-made ones.

The following example builds a Hono integration in small steps. It needs `hono` and `@hono/node-server`.

Start with the host's existing WebSocket setup and the outer shape of its binding:

```ts [hono-binding.ts]
import { upgradeWebSocket } from '@hono/node-server'
import { WebSocketServer } from 'ws'
import type { ServerDefinition } from '@livething/server'
import type { NodeEndpointOptions } from '@livething/server-node'
import type { Context, Next } from 'hono'
import type { WebSocket } from 'ws'

export function setup() {
  const server = new WebSocketServer({ noServer: true })
  const upgradeRoute = upgradeWebSocket(() => ({}))

  function bind(
    huddle: ServerDefinition,
    options: NodeEndpointOptions,
  ) {
    const upgrade = async (context: Context, next: Next) => {
      return upgradeRoute(context, next)
    }

    return { upgrade }
  }

  return {
    websocket: { server },
    bind,
  }
}
```

## 3. Prepare before Hono completes the handshake

Call `prepare()` or `prepareNode()` only for a WebSocket upgrade request. They run your `authenticate` hook, and the binding does not check the request type for you. The route below checks the `Upgrade` header first and calls `next()` for any other request.

`lifecycle.prepare()` gives your callback an abort signal, and the callback passes that signal to `huddleEndpoint.prepareNode()`. Hono's Node server keeps the original `IncomingMessage` at `context.env.incoming`. `prepareNode()` reads it, so LiveThing can apply the endpoint's `clientIp` option.

`lifecycle.prepare()` returns `undefined` in three cases: the client left, shutdown started while preparation was running, or shutdown had already started. In these cases, destroy the Node socket and do not start a WebSocket handshake. Otherwise the result has one of three types:

- `http`: LiveThing rejected the upgrade with an HTTP response. Return `result.response` from the Hono route.
- `socket`: LiveThing rejected the upgrade with a WebSocket close code. Hono must complete the handshake first, then close the socket.
- `accept`: LiveThing accepted the upgrade. Hono must complete the handshake.

## 4. Reject or accept the socket

When Hono opens the socket, a `socket` result closes it at once with its code and reason. An `accept` result has an `accept()` method. Pass it a small transport object: the socket functions that LiveThing needs (`send`, `close`, `bufferedAmount`, and `backpressureSupported`). `send` gets a frame that is either `{ kind: 'text', text }` or `{ kind: 'bytes', bytes }`. It sends text as a text message and bytes as a binary message. `send` must return `false`, and must not throw, when the socket is no longer open, so LiveThing does not count the message as delivered. `accept()` returns the LiveThing connection. Save it for the later socket events. `accept()` can be called only once for each result.

```diff [hono-binding.ts]
diff --git a/hono-binding.ts b/hono-binding.ts
--- a/hono-binding.ts
+++ b/hono-binding.ts
@@ -32,2 +32,23 @@ export function setup() {

+          if (result.type === 'socket') {
+            closeWebSocket(socket, result.code, result.reason)
+            return
+          }
+
+          const rawSocket = socket.raw as WebSocket
+          try {
+            const connection = result.accept({
+              send: (frame) => {
+                if (rawSocket.readyState !== rawSocket.OPEN) return false
+                socket.send(frame.kind === 'text' ? frame.text : frame.bytes)
+                return true
+              },
+              close: (code, reason) => socket.close(code, reason),
+              bufferedAmount: () => rawSocket.bufferedAmount,
+              backpressureSupported: true,
+            })
+            connections.set(socket, connection)
+          } catch {
+            closeWebSocket(socket, 1011, '[livething] connection setup failed')
+          }
```

## 5. Forward the socket events

Forward a text message to `message()` and a binary message to `binaryMessage()` as a `Uint8Array`. Hono's Node server gives each binary message as its own `ArrayBuffer`, so a plain `Uint8Array` over it holds exactly the message's bytes. LiveThing decides what to do with a binary message, so do not close the socket for one yourself. `closeWebSocket()` shortens the close reason when needed, because a WebSocket close reason can be at most 123 bytes. Report errors, but remove the saved connection only in `onClose`. Some hosts send an `error` event before their final `close` event.

## 6. Return ready, admin, and shutdown

Return `ready` and `admin` from each endpoint. Return `ready` and `shutdown` from `setup()`. `lifecycle.shutdown()` cancels upgrades that are still in progress, waits for them to finish, and then runs `node.shutdown`, which closes the endpoints.

The integration now handles HTTP rejection, rejection with a WebSocket close code, accepted connections, and text messages.

The application only binds the endpoint to its Hono route:

```ts [huddle-server.ts]
import { Hono } from 'hono'
import { setup } from './hono-binding'
import { huddle } from './server/huddle-definition'

const app = new Hono()
const { bind, ready, websocket } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})

app.get('/huddle', huddleEndpoint.upgrade)

await ready()
```

Keep the Hono Node startup code that your application already has. Where that code configures Hono's WebSocket host, give it `app.fetch` and `websocket`. LiveThing does not create the server, start listening, or close the server.

## Serve `http()` and custom transports

`prepare()` and `prepareNode()` are only for WebSocket upgrades. A plain HTTP request goes to `huddleEndpoint.handleNode(request, response)`. It takes Node's `IncomingMessage` and `ServerResponse` (or their `node:http2` versions) and writes the whole answer. It serves the stream, the POSTs and the CORS preflight of [`http()`](/core/runtimes/transports/http), and the requests of a [custom transport](/core/runtimes/transports/custom-transports). When no transport takes the request, it answers `426`, so call it only for the endpoint's path. It rejects only when the endpoint itself fails, for example when it shuts down while it opens a stream. It has already destroyed the response then, so the route does not need to.

Add a second route next to `upgrade` that skips WebSocket upgrades and passes the rest on. In Hono, `context.env.incoming` and `context.env.outgoing` are the Node request and response, and the route returns `RESPONSE_ALREADY_SENT` from `@hono/node-server/utils/response`, because `handleNode` already wrote the response:

```diff [hono-binding.ts]
diff --git a/hono-binding.ts b/hono-binding.ts
--- a/hono-binding.ts
+++ b/hono-binding.ts
@@ -1,2 +1,3 @@
 import { upgradeWebSocket } from '@hono/node-server'
+import { RESPONSE_ALREADY_SENT } from '@hono/node-server/utils/response'
 import {
@@ -66,1 +67,24 @@ export function setup() {
+    const handle = async (context: Context, next: Next) => {
+      if (context.req.header('upgrade')?.toLowerCase() === 'websocket') {
+        return next()
+      }
+
+      const incoming = context.env.incoming
+      const outgoing = context.env.outgoing
+      const served = await lifecycle.prepare(incoming, async (signal) => {
+        // A shutdown ends a request that a custom transport still holds.
+        signal.addEventListener('abort', () => outgoing.destroy())
+        await huddleEndpoint.handleNode(incoming, outgoing)
+        return true
+      })
+      if (!served) outgoing.destroy()
+
+      return RESPONSE_ALREADY_SENT
+    }
+
-    return { upgrade, ready: huddleEndpoint.ready, admin: huddleEndpoint.admin }
+    return {
+      upgrade,
+      handle,
+      ready: huddleEndpoint.ready,
+      admin: huddleEndpoint.admin,
+    }
```

The route runs the call through `lifecycle.prepare()`, as the `upgrade` route does. When the signal aborts, it destroys `context.env.outgoing`, so `shutdown()` can end a request that a custom transport still holds. If `prepare()` does not serve the request (for example, the server is already shutting down), the route destroys the response too. Return `handle` from `bind()` next to `upgrade`, and mount it on the same path as `upgrade`, for every method, for example with `app.all('/huddle', huddleEndpoint.handle)`.

## Give the application the admin API

An application reaches its endpoint's [admin API](/core/server/admin/overview) only through what your integration's `bind()` returns. So return `admin: endpoint.admin`, as step 6 does. If you leave it out, the application has no way to call `purgeUser`, `broadcast`, or its own `api` methods. You can pass the function on as it is: `endpoint.admin` does not depend on `this`.

The application then calls it from any route, in the same way as with a ready-made integration. The [Hono admin route](/core/runtimes/node-frameworks/hono#call-the-admin-api-from-a-hono-route) works as it is, with `setup` imported from `./hono-binding` instead of `@livething/server-node/hono`. The admin route and the WebSocket route use the same `huddleEndpoint`, so the admin call reaches the users connected to `/huddle`.

## Client IP in an integration

Both `prepare()` and `prepareNode()` remove any `LiveThing-Client-IP` header that the client sent. `prepareNode()` is for a host that has Node's `IncomingMessage`. It applies the endpoint's `clientIp` option itself. A Fetch-based host calls `prepare(request, options)` instead, with the address in `options.clientIp`. Pass `clientIp` only when the host got that address from trusted connection or proxy data.
