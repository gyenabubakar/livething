These are the fixed limits and the default limits that LiveThing applies on every connection. Sizes in KiB and MiB are powers of 1024.

## Messages

| Limit                                | Value  | Where it is set                                                                   |
| ------------------------------------ | ------ | --------------------------------------------------------------------------------- |
| Largest message, in either direction | 32 MiB | `maxMessageBytes` on Node. Fixed on Cloudflare                                    |
| Envelope of a binary frame           | 64 KiB | Fixed. See [binary frames](/core/learn/wire-protocol#binary-frames)               |
| Frames waiting per connection        | 256    | Fixed. See [the per-connection queue](/core/server/handlers/per-connection-queue) |
| Resume tokens in one `__replay__`    | 8      | Fixed. The server sends it as `maxResumeTokens` in `__connected__`                |

A message over the largest size closes the connection with `1009` (`MESSAGE_TOO_BIG`). A frame that does not fit in the queue gets a [`connection-busy`](/core/core/builtin-errors) error.

## HTTP transport

The [`http()`](/core/runtimes/transports/http) transport adds limits for the POST requests that carry the client's messages.

| Limit                                             | Value                   | Where it is set                                              |
| ------------------------------------------------- | ----------------------- | ------------------------------------------------------------ |
| Largest POST body                                 | 512 KiB                 | `http({ maxPostBytes })` on the server                       |
| Frames in one POST                                | 255                     | Fixed                                                        |
| POSTs in flight                                   | One per lane, two lanes | Fixed                                                        |
| Wait for a `data` or `control` POST answer        | 30 seconds              | Fixed. Then the client reconnects                            |
| Busy answers with no progress                     | 30 seconds              | Fixed. Then the client reconnects                            |
| Unread bytes of one stream, Cloudflare            | 48 MiB                  | Fixed. Then the stream is dropped                            |
| Unread bytes of all streams of one Durable Object | 64 MiB                  | Fixed. Then the stream with the most unread bytes is dropped |

`maxPostBytes` must be at most half of `maxMessageBytes`, and an [upload](/core/server/binary/uploads)'s `pieceBytes`, plus room for the frame's header, must fit in `maxPostBytes`. The server checks both at startup. The default 512 KiB is under nginx's default body limit of 1 MB and above the default upload piece of 256 KiB.

A single message that, with its 5-byte frame header, is bigger than `maxPostBytes` cannot go up over `http()`. The client throws a `RangeError` before it sends anything, and the connection stays open. Send large data with [uploads](/core/client/primitives/uploads), which split it into pieces.

A dropped stream closes with `1013` on the server. The client sees the stream fail, reconnects, and [replay](/core/server/replay/overview) sends what it missed. Streams and stream catch-up wait for the client at 256 KiB of unread data, so only a burst of plain sends reaches these caps.

All headers of a request together have a size limit (16 KiB on Node by default), so a large [`token`](/core/client/connecting/auth-and-query#token-auth-with-token) or cookie can fail the request with `431`. Keep tokens small.
