`collaboration()` from `@livething/plugin-collaboration/client` returns a client [plugin](/core/client/plugins/overview) factory. Give it the same doc list the server gets:

```typescript [client/huddle-collab.ts]
import {
  collaboration,
  indexedDbStorage,
} from '@livething/plugin-collaboration/client'
import { huddleDocs } from '../shared/huddle-docs'

export const HuddleCollaboration = collaboration({
  docs: huddleDocs,
  storage: indexedDbStorage(),
})
```

List it in `client()` after the primitives it uses: `channels()`, `binary()`, `awareness()` and `clientRequests()`.

```typescript [client/socket.ts]
import {
  awareness,
  binary,
  channels,
  client,
  clientRequests,
  connect,
} from '@livething/client'
import { HuddleCollaboration } from './huddle-collab'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://huddle.example.com/huddle'),
  channels(),
  binary(),
  awareness(),
  clientRequests(),
  HuddleCollaboration(),
)
```

| Option         | What it does                                                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `docs`         | every doc type the app has, the same list the server gets                                                                       |
| `storage`      | keeps docs on the device, so an edit made offline survives a reload. `indexedDbStorage()` covers browsers. Default: memory only |
| `closeDelayMs` | how long a doc stays joined after its last `close()`, in ms. Default 1000                                                       |
| `onError`      | gets errors no call can throw (see [Errors](#errors)). Default: they are reported like an uncaught error                        |

## Opening a doc

`HuddleCollaboration.use(socket)` gives the plugin's API, and `doc(type, id)` gives one doc's handle. It's the same object every time for the same doc, like `socket.channel()`, and a type the app does not list is a type error.

```typescript [client/task-board.ts]
import { HuddleCollaboration } from './huddle-collab'
import { socket } from './socket'

export const collab = HuddleCollaboration.use(socket)
export const board = collab.doc('task-board', 'general')
```

Then open it while you use it, and close it when you are done, such as when a view mounts and unmounts:

```ts
await board.open()
// ... the board is synced: read it and change it
board.close()
```

`open()` loads what the device keeps, joins the doc's room, and syncs: the client says what it has, the server sends what it's missing, and the client sends what the server is missing. It resolves once the doc is synced. It rejects with `access-denied` when the server's `access` says no, and when the doc is closed before it synced.

`open()` is counted, so each `open()` needs a `close()`. After the last `close()`, the doc stays joined for `closeDelayMs`, so React StrictMode's quick unmount and remount does not leave and join again. A closed doc keeps its content in memory, and the next `open()` only syncs what changed.

Two stores show where the doc is:

| Store    | Values                                                                                                                                            |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `status` | `'closed'`, `'opening'` (joining for the first time), `'synced'`, `'saving'` (the server has not confirmed some of your changes yet), `'offline'` |
| `access` | `'edit'` or `'view'` once open, else `null`                                                                                                       |

## Reading: `state` and `select()`

`board.state` is a store of the doc as a read-only, plain JSON copy (a **snapshot**). `select()` makes a store of one part of it:

```ts
const task = board.select((s) =>
  s.tasks.find((t) => t.id === 't_1042'),
)
task.subscribe((value) => render(value?.title ?? 'Deleted'))
```

When something changes, the plugin builds a new snapshot but reuses every part that did not change. If one task changes, every other task in the new snapshot is the same object as before. That keeps every framework fast:

- `select()` notifies only when its result changed (by `===`), so a component that shows one task does not re-render when another task changes.
- React's `memo`, Vue's `computed`, Svelte stores and Solid memos all skip work when they see the same object again.

`board.keyOf(task)` gives a list item's internal ID from a snapshot item. It stays the same when the item moves, so it makes a good key when you render a list.

## Writing: `change()`

`change()` is how you edit the doc. You pass it a function, and the plugin calls it once, right away, with a **draft**: an object shaped like the doc that you can write to.

```typescript [client/task-actions.ts]
import { board } from './task-board'

export function finishTask(taskId: string) {
  board.change((d) => {
    const task = d.tasks.find((t) => t.id === taskId)
    if (task) task.done = true
  })
}

export function renameBoard(title: string) {
  board.change((d) => {
    d.title = title
  })
}
```

- **Text and values are assigned.** Lists and records change through their methods ([Lists and moves](/plugins/collaboration/lists-and-moves)). Assigning a list, or text to a number, is a type error.
- **Assigning text merges.** `d.title = title` does not replace the whole text. The plugin works out which letters changed and edits only those, so if someone adds a word at the end while you fix one at the start, both edits stay. Anchors on the words that did not change stay too.
- **One `change()` is one step**: one undo step, one update to the server, and one store update. Listeners never see a half-done change.
- **All or nothing.** If your function throws, or a value fails its schema, nothing changes, and `change()` throws (`invalid-change` for a schema failure).
- `change()` returns what your function returns. It runs at once, so an `async` function is refused. Calling `change()` inside another `change()` throws.

In a doc this client may only view, `change()` throws a `read-only` error before anything changes. Its `detail` says which doc: `{ type, id }`.

## Undo and redo

```ts
board.history.undo()
board.history.redo()
board.history.canUndo // a store of boolean
board.history.canRedo
board.history.pause() // changes until resume() become one undo step
board.history.resume()
```

Undo takes back only **your** changes. If you tick a task and someone else renames another one, your undo un-ticks yours and leaves their rename. An undo is a new change, so every member gets it. It also puts a moved task back, and brings back a task you deleted, with the same ID. Use `pause()` and `resume()` around something like a drag, so many small changes undo as one.

## When the server undoes a change

The server checks every change. When it refuses one, it undoes it for everyone, and the doc already shows the undone state. `onRefused` tells you it happened, with a reason for your logs:

```ts
board.onRefused((refusal) => {
  showToast('A change could not be saved.')
  console.warn('refused', refusal.reason)
})
```

This mostly happens with an older app version whose schema does not match the server's.

## Offline

While the socket is down, `status` is `'offline'` and `change()` keeps working. When the socket is back, the plugin joins again and sends what the server is missing, and the edits merge with what others did meanwhile.

The server runs `access` again on that join. If it now gives `'view'`, the edits made offline are not sent, and `onRefused` gets the reason `'this client may only view the doc'`. It runs whenever a `'view'` client joins with content the server does not have, on that join and every later one, while this client's copy (and its device storage) still holds it. Most often that is the user's own offline edits, including ones device storage kept from an earlier load, so tell the user their changes were not saved. It can also be content the server lost, such as after its database was reset, which a viewer's device still holds.

Edits made offline live in memory. To keep them across a reload, give the plugin a `storage`. `indexedDbStorage()` keeps docs in the browser's IndexedDB. Other platforms, such as React Native, pass their own [`CollaborationStorage`](/plugins/collaboration/reference#collaborationstorage): three methods, `load`, `append` and `compact`.

## Errors

| Error            | Where                            | When                                                       |
| ---------------- | -------------------------------- | ---------------------------------------------------------- |
| `access-denied`  | `open()`, `versions.save()`      | the server's `access` refused, or the client may only view |
| `doc-not-found`  | `open()`                         | the server does not serve this doc type                    |
| `read-only`      | `change()`, `versions.restore()` | this client may only view the doc                          |
| `invalid-change` | `change()`                       | a value fails its schema                                   |

Some errors have no call to throw from: content from the server that does not match this client's schema (from another app version), a store listener that threw, or a failed device write. They go to the `onError` option. Without it, they are reported like an uncaught error. When content does not match the schema, `state` keeps its last good copy.
