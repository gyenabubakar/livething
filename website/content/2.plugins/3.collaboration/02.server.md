`collaboration()` from `@livething/plugin-collaboration/server` returns a [plugin](/core/server/plugins/overview) factory. Give it the same doc list the client gets, and an `access` function:

```typescript [server/huddle-collaboration.ts]
import { collaboration } from '@livething/plugin-collaboration/server'
import { huddleDocs } from '../shared/huddle-docs'
import { isRoomMember } from './helpers'

export const HuddleCollaboration = collaboration({
  docs: huddleDocs,
  async access(ctx, doc) {
    if (!ctx.user.id || !(await isRoomMember(ctx.user.id, doc.id))) {
      return false
    }

    return ctx.meta.role === 'guest' ? 'view' : 'edit'
  },
})
```

The host lists it next to [`channels()`](/core/server/channels/overview), which it needs, in the builder that `server/huddle-definition.ts` assembles:

```typescript [server/base.ts]
import { server } from '@livething/server'
import { channels } from '@livething/server/channels'
import { HuddleCollaboration } from './huddle-collaboration'

export const base = server({
  // ...and Huddle's other capabilities
  capabilities: [channels(), HuddleCollaboration()],
})
```

That's all the setup. The plugin has one channel family, `docs`, and each doc is one room in it, named `<type>:<id>`, so a doc works on every runtime and transport LiveThing has, including a Cloudflare Durable Object that hibernates.

## Who may open a doc: `access`

`access(ctx, doc)` runs when a client opens a doc, and again each time it rejoins after a reconnect, so a change of role takes effect on the next rejoin. `doc` is typed from your doc list: `{ type: 'task-board', id: string }`. It returns:

| Return   | What the client can do                                                              |
| -------- | ----------------------------------------------------------------------------------- |
| `'edit'` | read the doc and change it                                                          |
| `'view'` | read the doc. Its `change()` throws `read-only`, and the server refuses its updates |
| `false`  | nothing: its `open()` rejects with `access-denied`                                  |

`ctx` has the connection's `user` (`{ id }`, or `id: null`), its `meta` from `authenticate`, and its `connection` (`{ id }`). A client that asks for a doc type the server does not list, or sends a doc ID that is empty, too long or holds half of an emoji alone, gets `doc-not-found`. The plugin's client refuses such an ID before it sends anything, so only a hand-made client gets this far.

The plugin keeps each connection's access in its own ephemeral [tags](/core/server/capabilities/tags), so it survives a Cloudflare hibernation wake, and ends when the connection closes.

## The server checks every change

Every update a client sends is checked against the doc's schema before anyone else gets it. The check looks only at what the update changed, so it stays fast on a big doc. It refuses, for example:

- a value its schema refuses, such as `done: 'yes'`;
- a write to a part of the Yjs doc the schema does not describe;
- the wrong kind of content, such as a list where text goes;
- an update that is broken, or needs earlier updates the server does not have.

It lets through a key that an object, a list item or a record value holds but the schema does not, such as a field you removed from the doc type. The doc keeps that content and never reads it, so an undo or a restore of an old item still works. A top-level field you removed from the doc type is content of the same kind: a write to it is refused, but a delete of what it holds goes through, because the doc never reads it. The update size limit still applies to it, and so does the nesting limit: Yjs types nest at most 200 deep in a doc, because Yjs deletes and copies them by recursion.

A refused update is undone for everyone: the server applies it, then applies a second update that takes it back, and sends the members only the net result. So every copy stays the same, and the bad value never sticks. The client that sent it hears about it through [`onRefused`](/plugins/collaboration/client#when-the-server-undoes-a-change). An update that needs earlier updates (because one was lost on the way) is not undone: the client syncs again and sends everything the server lacks.

## Storage

Docs are kept in the server's own SQL, the same `ctx.sql` your handlers use, so it works on Node and on Cloudflare with no setup. The plugin makes its tables on first use: `livething_collaboration_updates` for the doc content, and `livething_collaboration_versions` and `livething_collaboration_version_parts` for [versions](/plugins/collaboration/versions). Its due saves go in the server's [scheduled task tables](/core/server/capabilities/scheduled), as the app's own tasks do. With `onSave` set, each doc's editors since its last save go in the plugin's own [`ctx.kv`](/core/server/context-and-storage/sql-and-kv) until that save ends. A custom `storage` changes neither.

- Each accepted update is appended. After 200 updates, or 4 MiB of them, the plugin compacts the doc's log into one update, so loading stays fast.
- An update bigger than a row may hold is split across rows.
- A stored update that is broken, such as one a crash cut off, is skipped whole and logged, and the doc opens with the rest. No half of an edit goes in.
- A doc loads when someone first uses it, and unloads after its last member leaves, once its changes are stored and any `onSave` for it has finished. With `onSave` set, a doc that server code changed while it had no members stays loaded until `onSave` runs.
- Edits are live before they are stored. If a write fails, the error is logged, the doc stays loaded, and the plugin stores the whole doc on the next write, or tries again every 5 seconds once nobody is using the doc.

To keep docs somewhere else, pass `storage`. It is a `ServerStorage`: three methods for updates (`load`, `append`, `compact`) and four for versions (`saveVersion`, `listVersions`, `readVersion`, `deleteVersion`). The [Reference](/plugins/collaboration/reference#serverstorage) lists what each one must do. Any method can be async.

## Before anyone reads: `onLoad`

`onLoad` runs each time a doc loads on the server, before a client or your server code reads it. A doc loads when someone first uses it, and again after it unloaded or the server restarted. Use it when your app keeps the content in its own database too, and a doc should start from there. Huddle had task boards before they were shared docs, so a room's first board starts from its old `tasks` table:

```typescript
import { collaboration } from '@livething/plugin-collaboration/server'
import { huddleDocs } from '../shared/huddle-docs'
import { isRoomMember, readOldBoard } from './helpers'

export const HuddleCollaboration = collaboration({
  docs: huddleDocs,
  async access(ctx, doc) {
    if (!ctx.user.id || !(await isRoomMember(ctx.user.id, doc.id))) {
      return false
    }

    return ctx.meta.role === 'guest' ? 'view' : 'edit'
  },
  async onLoad(_ctx, board) {
    // A board that was stored once is the one to keep: its edits are newer.
    if (!board.empty) return

    const old = await readOldBoard(board.id)
    if (!old) return

    board.change((d) => {
      d.title = old.title
      for (const column of old.columns) {
        d.columns.push(column)
      }

      for (const task of old.tasks) {
        d.tasks.push({ ...task, notes: '' })
      }
    })
  },
})
```

- `board.empty` is `true` when nothing was ever stored for the doc. Fill only an empty doc. A stored doc can hold edits that `onSave` has not saved yet, as when the server restarted before its save, so your database can be older than the doc. Overwriting the doc from it would lose those edits. When your database changes outside the doc, put the change in with a server [`change()`](#editing-from-server-code) at that time.
- `board.state` is the doc as stored, such as to check a field before you fill it. Like a server `read()`, `state` throws `invalid-change` when the stored doc no longer matches its schema. When `onLoad` lets that error through, the doc does not load.
- `board.change()` takes the same draft as a server [`change()`](#editing-from-server-code), and runs at once: there is nothing to `await`, and `state` shows it. Its changes are held until `onLoad` ends. Then a member already in the doc's room gets them, as after a [hibernation wake](/core/server/server/hibernation), and they are stored. They do not run `onSave`, because they copy in what your app already has. `change()` works only while `onLoad` runs.
- In `onLoad`, read and edit the doc only through `board.state` and `board.change()`. A server `read()` or `change()` of the same doc waits for the load, and the load waits for `onLoad`, so neither would ever end.
- When `onLoad` throws, the doc does not load, and none of its changes is kept, so nobody reads a half-filled doc. A client's `open()` rejects, and the next use of the doc runs `onLoad` again, with the doc as it was stored before.
- `ctx` has `log` and `platform`, as in `onSave`.

## After edits: `onSave`

`onSave` runs once a doc's changes settle: `saveDelayMs` (2000 by default) after the last change, or at once when the last member leaves. Use it for work that should follow edits, but not run on every keystroke: a search index, a webhook, a summary.

```typescript
import { collaboration } from '@livething/plugin-collaboration/server'
import { huddleDocs } from '../shared/huddle-docs'
import { indexTaskTitles, isRoomMember } from './helpers'

export const HuddleCollaboration = collaboration({
  docs: huddleDocs,
  async access(ctx, doc) {
    if (!ctx.user.id) return false

    return (await isRoomMember(ctx.user.id, doc.id)) ? 'edit' : false
  },
  async onSave(ctx, event) {
    const titles = event.state.tasks.map((task) => task.title)
    await indexTaskTitles(event.id, titles)
    ctx.log.info('indexed task board', {
      roomId: event.id,
      editedBy: event.editors,
    })
  },
})
```

`event` has the doc's `type`, `id` and `state`, the typed snapshot, and `editors`, who changed it. With several doc types, check `event.type` first, and `state` narrows to that type. `ctx` has `log` and `platform`. An error that `onSave` throws is logged. For one doc, `onSave` runs one call at a time, in order: a call that starts while another runs waits for it, then gets the doc as it is then.

`event.editors` lists the user IDs of the clients whose changes came since the last `onSave` that ended, in the order each first changed the doc. Use it to name who edited, or to reset an approval when someone changes an approved doc. A change from your server code or from `onLoad` adds nobody, and neither does a client with no user ID, so `editors` is empty when only those changed the doc. A refused update adds nobody either. The list is kept in the plugin's own [`ctx.kv`](/core/server/context-and-storage/sql-and-kv), so a save that runs after a restart still names them. When `onSave` throws, its editors stay for the next save. When the server stops while `onSave` runs, the next start runs that save again, with the same editors. A user that [`purgeUser`](/core/server/admin/context#remove-a-user-everywhere) removed can still be in the list until the next save ends. Like due saves, the list needs file storage on Node.

- When the server shuts down, it stores every doc and runs every save that is due (or waits for one that is running) before the shutdown ends. It waits at most 10 seconds, so a stuck database can't hold the shutdown; then it logs what it could not finish.
- When a doc's stored content no longer matches its schema (a field was changed in a way [Changing a doc type later](/plugins/collaboration/describing-a-doc#changing-a-doc-type-later) warns about), `onSave` does not run for it, and the server logs why. Its `read()` throws `invalid-change` too.
- A save that is due is kept in the server's storage, as a [scheduled task](/core/server/capabilities/scheduled) of the plugin's own. So it still runs when the server restarts before it, as when Cloudflare removes a Durable Object from memory or a deploy restarts it: the next start runs it, with the doc as it was stored. The plugin stores the task once on the first change, not on every change, so a doc that changes many times a second costs one storage write per save. On Node, this needs storage in a file: the default storage is in memory, so a stopped process loses its due saves.
- Keep `onSave` short. A due save runs as a scheduled task, with the other tasks that are due at the same time. The server records them all as done only once every one has ended, so a slow `onSave` also holds back the next due tasks, and a crash before then runs them all again. For slow work, such as a long export, record that it is needed in `onSave`, and do the work elsewhere.
- Make `onSave` safe to run twice for the same content. When the server stops while `onSave` runs, the task is still stored, so the next start runs it again. The doc itself is already stored, so `onSave` is never the only record of a change.

## Editing from server code

A handler reaches the docs with `ctx.plugin('livething:collaboration')`. `doc(type, id)` gives a typed doc with `read()`, `change()` and [`versions`](/plugins/collaboration/versions). `change()` takes the same draft as the client's, and every member who has the doc open gets the change:

```typescript [server/archive-board.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleArchiveBoard = base.on('archive-board', {
  input: v.object({ roomId: v.string() }),
  async run(ctx, input) {
    await ctx
      .plugin('livething:collaboration')
      .doc('task-board', input.roomId)
      .change((d) => {
        d.archived = true
      })
  },
})
```

`change()` resolves with what your function returns. It rejects with `invalid-change` when a value fails the schema, and then the doc stays as it was. A change that writes nothing sends and stores nothing.

Admin code, such as a cron job, reaches the same API with [`admin.plugin('livething:collaboration')`](/core/server/plugins/scoped-ctx#calling-the-api-from-admin-code). On Node it is the same object, so `read()` and `change()` work as above:

```typescript [server/close-sprint.ts]
import { huddleEndpoint } from './huddle-endpoint'

export async function closeSprint(roomId: string) {
  const admin = await huddleEndpoint.admin()
  const board = admin
    .plugin('livething:collaboration')
    .doc('task-board', roomId)

  // Keep the board as it was, then clear the done tasks.
  await board.versions.save('End of sprint')
  await board.change((d) => {
    for (let index = d.tasks.length - 1; index >= 0; index -= 1) {
      if (d.tasks.at(index)?.done) d.tasks.delete(index)
    }
  })
}
```

On Cloudflare, a Worker reaches the Durable Object over RPC. Your `change()` function would run in the Worker, while the draft lives in the Durable Object, so call `change()` inside the Durable Object instead: in a handler, or in an operation of your server's own [`api`](/core/server/admin/authoring) that the Worker calls.
