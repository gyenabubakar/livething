`collaboration()` from `@livething/plugin-collaboration/server` returns a [plugin](/core/server/plugins/overview) factory. Give it the same doc list the client gets, and an `access` function:

```typescript [server/huddle-collaboration.ts]
import { collaboration } from '@livething/plugin-collaboration/server'
import { huddleDocs } from '../shared/huddle-docs'
import { isRoomMember } from './helpers'

export const HuddleCollaboration = collaboration({
  docs: huddleDocs,
  async access(ctx, doc) {
    if (!ctx.user.id || !(await isRoomMember(ctx.user.id, doc.id))) {
      return false
    }

    return ctx.meta.role === 'guest' ? 'view' : 'edit'
  },
})
```

The host lists it next to [`channels()`](/core/server/channels/overview), which it needs, in the builder that `server/huddle-definition.ts` assembles:

```typescript [server/base.ts]
import { server } from '@livething/server'
import { channels } from '@livething/server/channels'
import { HuddleCollaboration } from './huddle-collaboration'

export const base = server({
  // ...and Huddle's other capabilities
  capabilities: [channels(), HuddleCollaboration()],
})
```

That's all the setup. The plugin has one channel family, `docs`, and each doc is one room in it, named `<type>:<id>`, so a doc works on every runtime and transport LiveThing has, including a Cloudflare Durable Object that hibernates.

## Who may open a doc: `access`

`access(ctx, doc)` runs when a client opens a doc, and again each time it rejoins after a reconnect, so a change of role takes effect on the next rejoin. `doc` is typed from your doc list: `{ type: 'task-board', id: string }`. It returns:

| Return   | What the client can do                                                              |
| -------- | ----------------------------------------------------------------------------------- |
| `'edit'` | read the doc and change it                                                          |
| `'view'` | read the doc. Its `change()` throws `read-only`, and the server refuses its updates |
| `false`  | nothing: its `open()` rejects with `access-denied`                                  |

`ctx` has the connection's `user` (`{ id }`, or `id: null`), its `meta` from `authenticate`, and its `connection` (`{ id }`). A client that asks for a doc type the server does not list gets `doc-not-found`.

The plugin keeps each connection's access in its own ephemeral [tags](/core/server/capabilities/tags), so it survives a Cloudflare hibernation wake, and ends when the connection closes.

## The server checks every change

Every update a client sends is checked against the doc's schema before anyone else gets it. The check looks only at what the update changed, so it stays fast on a big doc. It refuses, for example:

- a value its schema refuses, such as `done: 'yes'`;
- a write to a part of the Yjs doc the schema does not describe;
- the wrong kind of content, such as a list where text goes;
- an update that is broken, or needs earlier updates the server does not have.

It lets through a key that an object, a list item or a record value holds but the schema does not, such as a field you removed from the doc type. The doc keeps that content and never reads it, so an undo or a restore of an old item still works. The update size limit still applies to it, and so does the nesting limit: Yjs types nest at most 200 deep in a doc, because Yjs deletes and copies them by recursion.

A refused update is undone for everyone: the server applies it, then applies a second update that takes it back, and sends the members only the net result. So every copy stays the same, and the bad value never sticks. The client that sent it hears about it through [`onRefused`](/plugins/collaboration/client#when-the-server-undoes-a-change). An update that needs earlier updates (because one was lost on the way) is not undone: the client syncs again and sends everything the server lacks.

## Storage

Docs are kept in the server's own SQL, the same `ctx.sql` your handlers use, so it works on Node and on Cloudflare with no setup. The plugin makes its tables on first use: `livething_collaboration_updates` for the doc content, and `livething_collaboration_versions` and `livething_collaboration_version_parts` for [versions](/plugins/collaboration/versions).

- Each accepted update is appended. After 200 updates, or 4 MiB of them, the plugin compacts the doc's log into one update, so loading stays fast.
- An update bigger than a row may hold is split across rows.
- A doc loads when someone first uses it, and unloads after its last member leaves, once its changes are stored and any `onSave` for it has finished. With `onSave` set, a doc that server code changed while it had no members stays loaded until `onSave` runs.
- Edits are live before they are stored. If a write fails, the error is logged, the doc stays loaded, and the plugin stores the whole doc on the next write, or tries again every 5 seconds once nobody is using the doc.

To keep docs somewhere else, pass `storage`. It is a `ServerStorage`: three methods for updates (`load`, `append`, `compact`) and four for versions (`saveVersion`, `listVersions`, `readVersion`, `deleteVersion`). The [Reference](/plugins/collaboration/reference#serverstorage) lists what each one must do. Any method can be async.

## After edits: `onSave`

`onSave` runs once a doc's changes settle: `saveDelayMs` (2000 by default) after the last change, or at once when the last member leaves. Use it for work that should follow edits, but not run on every keystroke: a search index, a webhook, a summary.

```typescript
import { collaboration } from '@livething/plugin-collaboration/server'
import { huddleDocs } from '../shared/huddle-docs'
import { indexTaskTitles, isRoomMember } from './helpers'

export const HuddleCollaboration = collaboration({
  docs: huddleDocs,
  async access(ctx, doc) {
    if (!ctx.user.id) return false

    return (await isRoomMember(ctx.user.id, doc.id)) ? 'edit' : false
  },
  async onSave(ctx, event) {
    const titles = event.state.tasks.map((task) => task.title)
    await indexTaskTitles(event.id, titles)
    ctx.log.info('indexed task board', { roomId: event.id })
  },
})
```

`event` has the doc's `type`, `id` and `state`, the typed snapshot. With several doc types, check `event.type` first, and `state` narrows to that type. `ctx` has `log` and `platform`. An error that `onSave` throws is logged. For one doc, `onSave` runs one call at a time, in order: a call that starts while another runs waits for it, then gets the doc as it is then.

- When the server shuts down, it stores every doc and runs every save that is due (or waits for one that is running) before the shutdown ends. It waits at most 10 seconds, so a stuck database can't hold the shutdown; then it logs what it could not finish.
- When a doc's stored content no longer matches its schema (a field was changed in a way [Changing a doc type later](/plugins/collaboration/describing-a-doc#changing-a-doc-type-later) warns about), `onSave` does not run for it, and the server logs why. Its `read()` throws `invalid-change` too.
- The wait before `onSave` is a timer. On Cloudflare, a Durable Object does not hibernate while a timer is pending, so it stays awake for `saveDelayMs` after each change. And when Cloudflare removes the object from memory, a pending `onSave` is lost. Keep `saveDelayMs` short, and treat `onSave` as a helper for work you can redo, not as the only record of a change: the doc itself is already stored.

## Editing from server code

A handler reaches the docs with `ctx.plugin('livething:collaboration')`. `doc(type, id)` gives a typed doc with `read()`, `change()` and [`versions`](/plugins/collaboration/versions). `change()` takes the same draft as the client's, and every member who has the doc open gets the change:

```typescript [server/archive-board.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleArchiveBoard = base.on('archive-board', {
  input: v.object({ roomId: v.string() }),
  async run(ctx, input) {
    await ctx
      .plugin('livething:collaboration')
      .doc('task-board', input.roomId)
      .change((d) => {
        d.archived = true
      })
  },
})
```

`change()` resolves with what your function returns. It rejects with `invalid-change` when a value fails the schema, and then the doc stays as it was. A change that writes nothing sends and stores nothing.

Admin code, such as a cron job, reaches the same API with [`admin.plugin('livething:collaboration')`](/core/server/plugins/scoped-ctx#calling-the-api-from-admin-code). On Node it is the same object, so `read()` and `change()` work as above:

```typescript [server/close-sprint.ts]
import { huddleEndpoint } from './huddle-endpoint'

export async function closeSprint(roomId: string) {
  const admin = await huddleEndpoint.admin()
  const board = admin
    .plugin('livething:collaboration')
    .doc('task-board', roomId)

  // Keep the board as it was, then clear the done tasks.
  await board.versions.save('End of sprint')
  await board.change((d) => {
    for (let index = d.tasks.length - 1; index >= 0; index -= 1) {
      if (d.tasks.at(index)?.done) d.tasks.delete(index)
    }
  })
}
```

On Cloudflare, a Worker reaches the Durable Object over RPC. Your `change()` function would run in the Worker, while the draft lives in the Durable Object, so call `change()` inside the Durable Object instead: in a handler, or in an operation of your server's own [`api`](/core/server/admin/authoring) that the Worker calls.
