`define({ scoped: true })` returns a **scoped builder**. It looks and feels like a top-level `define` — same `base.on`, `base.request`, `base.channel`, same `ctx` — but it is meant for a **plugin**: a self-contained feature that runs inside a host server rather than being the host. The scoped builder is how you author a plugin's behavior before wrapping it with `plugin(...)`.

::note
This page is about the scoped builder itself. For packaging and using plugins — `plugin(...)`, `dependsOn`, `ctx.plugin(id)`, and the client side — see [Plugins](/server/plugins/overview).
::

## What a scoped define is for

A normal `define` produces the whole server. A scoped `define` produces one **slice** of a server, packaged so it can be dropped into any host. The plugin gets its own events, handlers, channels, and storage, all kept under its own namespace so it never collides with the host or with another plugin.

You author the slice with the scoped builder, assemble it, and hand the result to `plugin(...)`:

```typescript [presence.ts]
import { define, emits, t } from '@wskit/server'
import { plugin } from '@wskit/server/plugin'
import * as v from 'valibot'

// 1. a scoped builder — no env, just this plugin's own capabilities
const h = define({
  scoped: true,
  capabilities: [emits({ 'user-online': t<{ id: string }>() })],
})

// 2. handlers, exactly like a top-level server
const heartbeat = h.on('heartbeat', {
  input: v.object({}),
  run(ctx) {
    ctx.send('user-online', { id: ctx.id })
  },
})

// 3. assemble, then wrap with plugin(...)
export const Presence = plugin('acme:presence', {
  handler: h.assemble(heartbeat),
  api: (ctx) => ({ ping() { ctx.send('user-online', { id: ctx.id }) } }),
})
```

The host then lists `Presence()` like any other capability:

```typescript [host.ts]
import { define, t } from '@wskit/server'
import { Presence } from './presence'

const base = define({
  env: t<Env>(),
  capabilities: [Presence()],   // the plugin plugs in here
})
```

## How it differs from a top-level define

A scoped builder is the same builder type, but its config is smaller and a few rules are tighter.

| | Top-level `define` | Scoped `define({ scoped: true })` |
| --- | --- | --- |
| `scoped` field | absent (or `false`) | **`true`** — required |
| `env` field | required | **not allowed** — the plugin inherits the host's env |
| `capabilities` | any capability | only **plugin-safe** capabilities (no host-owned engines) |
| `upgrade` | the app's auth gate | a scoped gate that runs before the app's (see below) |
| transport, env, global engines | owned by this server | inherited from the host |

The key idea: a plugin does not own the platform. It has no `env` of its own, it does not own the transport, and it cannot own the global engines. It declares only its own namespaced slice and borrows the rest from the host.

### No `env`

A scoped config has no `env` field. The plugin's handlers still see `ctx.env` — it is the **host's** env, passed through. So a plugin reads the same bindings the host has, without re-declaring them.

```typescript [no-env.ts]
const h = define({
  scoped: true,
  // no env: t<...>() here — the plugin uses the host's env
  capabilities: [emits({ tick: t<{ n: number }>() })],
})
```

### Host-owned capabilities are off-limits

These engines are **host-owned**: `dedup`, `sequence`, `keepalive`, `persistence`, `rateLimit`, and the whole `replay` family — built-in `replay.history()` / `replay.snapshot()` **and** `replay.custom()`. They are global to the whole server, so a plugin can never list one — doing so is a compile error. A plugin that *needs* one declares a prerequisite instead, and the host must satisfy it.

```typescript [host-only.ts]
const h = define({
  scoped: true,
  capabilities: [
    resumableStream(),   // OK — a plugin can own its own durable streams
    // persistence(),    // compile error: host-owned, a plugin can't list it
  ],
})
```

The durable streams above *need* persistence to work, but the plugin does not — and cannot — list it. That requirement is **auto-derived**: WSKit reads it off the plugin's own streams and passes it up to the host as a dependency. The host must list `persistence()`, or its `assemble` fails with a clear error. (This is the requirement mechanism from [Capabilities](/server/define/capabilities), applied across the plugin boundary.) You can also state a prerequisite explicitly with `dependsOn` — see [Plugins](/server/plugins/overview).

::note
"Plugin-safe" is exactly "every capability except the host-owned engines listed above." Behavior capabilities a plugin *can* own itself — `requests`, `channels`, the stream kinds, `emits`, `errors`, `tags`, `intercepts` — are all fine in a scoped list. Note `base.replay` is not among them: even `replay.custom()` is host-owned, so a plugin cannot register its own custom replay strategy.
::

## Everything is namespaced

A plugin's surface is kept separate from the host's. Its events, channels, storage keys, tags, errors, and intercept keys all travel under the plugin's id, so two plugins (or a plugin and the host) never step on each other.

You write your plugin's code as if it were the only thing running — short event names, short channel names, short storage keys. WSKit adds the namespace on the wire and in storage for you. From inside a handler you keep using the short names; the framework resolves them against the plugin's own slice.

```typescript [namespaced.ts]
const h = define({
  scoped: true,
  capabilities: [channels(), emits({ joined: t<{ who: string }>() })],
})

// 'room' and 'joined' are the plugin's own short names — namespaced on the wire
const room = h.channel('room', {
  outgoing: { emits: { joined: t<{ who: string }>() } },
})

room.subscribe((ctx) => {
  ctx.channel.broadcast('joined', { who: ctx.id }, { excludeSelf: false })
})
```

## The scoped `upgrade`

A plugin may supply its own `upgrade` in the scoped config. It is the plugin's chance to inspect the handshake and contribute to the connection — for example to read a header the plugin cares about.

```typescript [scoped-upgrade.ts]
const h = define({
  scoped: true,
  upgrade(request) {
    const region = request.headers.get('cf-ipcountry') ?? 'unknown'
    return { meta: { region } }   // merged into the connection's meta
  },
  capabilities: [emits({ located: t<{ region: string }>() })],
})
```

A scoped `upgrade` differs from the app's in a few specific ways:

- **It runs first.** In the inbound order, every plugin's `upgrade` runs before the app's `upgrade`.
- **It sees only the raw request.** It does not see the app's `identity` or `meta` — it runs before those are decided.
- **Its `meta` is merged.** The plugin's returned `meta` is shallow-merged into the connection's metadata. On a key conflict, the **app wins**.
- **Its `tags` are concatenated.** Tags from the plugin and the app stack rather than overwrite.
- **Only one upgrade may own `identity`.** A plugin *may* return `identity` — but only one upgrade hook across the whole server (the app's, or one plugin's) is allowed to. Two that return it is an error.
- **It can veto.** Throwing `RejectUpgrade(code, reason)` from a scoped `upgrade` rejects the whole handshake, exactly as the app's gate does. (See [Environment and upgrade](/server/define/env-and-upgrade) for how the reject code is answered.)

## Assembling a scoped builder

A scoped builder's `assemble` works the same way — collect the handler values — and the result is a scoped handler ready for `plugin(...)`. You never run a scoped definition directly through an adapter; it goes through `plugin(...)` and into a host.

```typescript [assemble.ts]
const heartbeat = h.on('heartbeat', {
  input: v.object({}),
  run(ctx) { ctx.send('user-online', { id: ctx.id }) },
})

export const Presence = plugin('acme:presence', {
  handler: h.assemble(heartbeat),   // a scoped handler, not a runnable server
})
```
