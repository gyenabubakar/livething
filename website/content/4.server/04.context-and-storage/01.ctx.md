These are the fields on **every** `ctx` inside a connection handler — they are there no matter which capabilities you listed. Capability-specific fields (`ctx.tags`, `ctx.channels`, `ctx.schedule`, latency/quality, and more) are covered on the [next page](/server/context-and-storage/capability-gated-ctx).

The fields group by purpose: identity, messaging, connection inspection, storage, platform, and per-dispatch locals.

## Identity

Who this connection is.

| Field | Type | What it is |
|---|---|---|
| `ctx.id` | `string` | Unique ID for this socket. Stable for the life of the connection. |
| `ctx.identity` | `string` | The identity string your upgrade step returned. The same person on two devices has two `id`s but one `identity`. |
| `ctx.self` | `ConnectionRef` | A reference handle to this connection. Pass it to anything that takes a `ConnectionRef`. |
| `ctx.meta` | your `upgrade` return | The metadata you attached during upgrade, fully typed from its return value. |

`id` is per-socket; `identity` is per-user. Use `identity` when you key durable state, `id` when you address one live socket.

```typescript [identity.ts]
base.on('who-am-i', {
  input: v.object({}),
  run(ctx) {
    // meta is typed from the upgrade step — here it returned { username }.
    ctx.send('who-am-i-result', { username: ctx.meta.username })
  },
})
```

`ctx.meta` is typed, not `any`. If your upgrade step returns `{ username: string }`, then `ctx.meta.username` is a `string` and `ctx.meta.role` is a compile error. See [Defining a server](/server/define/overview) for the upgrade step.

## Messaging

Send events out.

| Method | Returns | What it does |
|---|---|---|
| `ctx.send(event, payload)` | `boolean` | Send to **this** connection only. Returns `false` if the socket's buffer is full. |
| `ctx.broadcast(event, payload, options?)` | `void` | Send to every other connection on this instance. Pass `{ excludeSelf: false }` to include the sender. |

Both are typed against your `emits(...)` events — a wrong event name or payload shape is a compile error.

```typescript [messaging.ts]
const handleDoBroadcast = base.on('do-broadcast', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    // Goes to everyone EXCEPT the sender — excludeSelf defaults to true.
    ctx.broadcast('message', { text: input.text, from: ctx.meta.username })
  },
})

const handleDoBroadcastExcludeSelf = base.on('do-broadcast-exclude-self', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    // excludeSelf: false sends to the sender too.
    ctx.broadcast(
      'message',
      { text: input.text, from: ctx.meta.username },
      { excludeSelf: false },
    )
  },
})
```

`ctx.send` returns whether the message was accepted into the socket buffer. A `false` means the buffer is full — a sign the client is slow. Check it when delivery matters:

```typescript [send-result.ts]
base.on('ping-self', {
  input: v.object({}),
  run(ctx) {
    const delivered = ctx.send('message', { text: 'pong', from: 'server' })
    if (!delivered) ctx.log.warn('send buffer full', { id: ctx.id })
  },
})
```

::note
`ctx.broadcast` always fans out to every connection on the instance. To send only to members of a channel, use a channel handle's `broadcast` — see [Channels](/server/channels/overview). To send to connections holding a tag, use the tag handle's `send` — see [Tags](/server/capabilities/tags).
::

## Closing the connection

| Method | What it does |
|---|---|
| `ctx.close(code?, reason?)` | Close **this** connection with an optional WebSocket close code and reason. |

```typescript [close.ts]
base.on('do-server-close', {
  input: v.object({}),
  run(ctx) {
    ctx.close(4010, 'server-close')
  },
})
```

Codes in the `4000`–`4999` range are yours to define. See [Close codes](/core/close-codes) for the shared catalog and what is reserved.

## Inspecting connections

Read who is connected and how full this socket's buffer is.

| Field / method | Type | What it is |
|---|---|---|
| `ctx.connectionCount` | `number` | How many connections are open on this instance right now. |
| `ctx.getConnections()` | `ConnectionInfo[]` | A snapshot of every live connection. |
| `ctx.bufferedAmount` | `number` | Bytes still queued to send to **this** socket. A rising value means the client is slow. |

```typescript [members.ts]
base.on('list-members', {
  input: v.object({}),
  run(ctx) {
    const peers = ctx.getConnections()
    // peers[].meta is typed from your upgrade step — no cast needed.
    const usernames = peers.map((p) => p.meta.username)
    ctx.send('members-list-result', { members: usernames })
  },
})
```

`getConnections()` returns a read-only snapshot — it does not update after you read it. Each entry is a `ConnectionInfo`, and you can build a `ConnectionRef` from one with `.ref()` to address that socket. The [Connections page](/server/context-and-storage/connections) covers `ConnectionInfo` and addressing in full.

::note
`getConnections()` returns `ConnectionInfo<Meta>[]`, where `Meta` is your upgrade type — so `peers[].meta.username` is typed just like your own `ctx.meta`, no cast needed. The same holds for the snapshots from channel `members()` and tag `connections()`.
::

## Storage

Durable state.

| Field | Type | What it is |
|---|---|---|
| `ctx.sql` | `SQLProvider` | SQLite access — queries and transactions. |
| `ctx.kv` | `KVProvider` | A simple durable key-value store. |

```typescript [storage.ts]
base.on('save-note', {
  input: v.object({ title: v.string(), body: v.string() }),
  run(ctx, input) {
    ctx.sql.exec('INSERT INTO notes (title, body) VALUES (?, ?)', input.title, input.body)
  },
})
```

Both surfaces have their own page — see [SQL & KV](/server/context-and-storage/sql-and-kv) for the full API, when to use which, and transactions.

## Platform & logging

The runtime around your handler.

| Field / method | Type | What it is |
|---|---|---|
| `ctx.env` | your env type | Platform bindings and secrets, typed from `env: t<Env>()` in `define`. |
| `ctx.log` | `Logger` | Structured logger — `info`, `warn`, `error`, each taking a message and optional data object. |
| `ctx.platform` | `unknown` | The raw platform object from the adapter (for example a Durable Object state). Untyped by default. |
| `ctx.waitUntil(promise)` | `void` | Keep the runtime alive until the promise settles, even after the handler returns. |
| `ctx.setAlarm(time)` | `void` | Set a low-level platform alarm at an absolute time (ms since epoch). Prefer `ctx.schedule(...)` from the `scheduled()` capability for most cases. |

```typescript [logging.ts]
base.on('process-order', {
  input: v.object({ orderId: v.string() }),
  async run(ctx, input) {
    ctx.log.info('order received', { orderId: input.orderId, by: ctx.meta.username })

    // Let a slow side-effect finish after the handler returns.
    ctx.waitUntil(recordToAnalytics(input.orderId))
  },
})
```

Always prefer `ctx.log` over `console.log` — the adapter routes it to your platform's log system with the data fields indexed.

`ctx.env` is typed from the `env: t<Env>()` you pass to `define`, so reading a binding that does not exist is a compile error:

```typescript [env.ts]
base.on('read-env-probe', {
  input: v.object({}),
  run(ctx) {
    ctx.send('env-result', { keyCount: Object.keys(ctx.env as object).length })
  },
})
```

## Per-dispatch locals

Pass a typed value from an intercept down to the handler that runs in the **same** message dispatch.

| Method | What it does |
|---|---|
| `ctx.provide(key, value)` | Store a typed value under a `localKey` for this dispatch. |
| `ctx.inject(key)` | Read a value an upstream `provide` stored. Returns `undefined` if nothing was stored for the key. |

```typescript [locals.ts]
import { localKey } from '@wskit/server'

const TopKey = localKey<{ tag: string }>('top')

base.intercept((ctx) => {
  ctx.provide(TopKey, { tag: 'top' })
})

base.on('echo', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    const top = ctx.inject(TopKey)
    ctx.send('echoed', { text: `${input.text}:${top?.tag ?? 'none'}` })
  },
})
```

Locals are isolated per dispatch — what you `provide` for one message is **not** visible to the next. They never touch durable storage; for that, use `ctx.sql` or `ctx.kv`. The full story — typed keys, intercept-to-handler flow, channel scoping — is on the [Provide & inject](/server/lifecycle-and-intercept/provide-inject) page.

## Validating a frame (inside intercepts)

When you write an intercept, the message `frame` arrives with an `unknown` payload — the intercept runs before validation. Two `ctx` helpers — present on every connection `ctx`, no capability needed — check a frame against a declared event:

| Method | Returns | What it does |
|---|---|---|
| `ctx.matches(key, frame)` | `boolean` | `true` when the frame's event and scope match the key **and** its payload passes the declared validator. A bad payload returns `false`. |
| `ctx.unsafeCast(key, frame)` | — | Checks only that `key` is a declared event; skips the payload validator. Use when your own logic already proved the shape. |

Both throw if the key names no declared event. Channel-scoped keys use the `@family::event` form. `matches` is a type guard and `unsafeCast` returns a narrowed frame, so after either one the `frame` is typed for that key. In practice the narrowed payload often stays `unknown`, so you still read it with a cast. See [Intercept](/server/lifecycle-and-intercept/intercept) for the full pattern.
