The [core fields](/server/context-and-storage/ctx) are on every `ctx`. On top of those, some capabilities add their own field. These appear on `ctx` **only** when the capability is listed in `define({ capabilities: [...] })`. List the capability and the field is there, fully typed. Leave it out and the field is **not on the type** — reading it is a compile error.

## The gate is the type, not a runtime check

There is no `if (ctx.tags)` to write. The field either exists on the type or it does not, decided at compile time from your capability list. This means you cannot accidentally call into a capability you forgot to enable — the compiler stops you first.

```typescript [gate.ts]
// With tags() listed:
const base = define({
  env: t<Env>(),
  upgrade: (request) => requireUsernameWithUserTag(request),
  capabilities: [
    tags((ephemeral) => [ephemeral('user', t<string>())]),
    emits({ 'tag-result': t<{ tags: string }>() }),
  ],
})

base.on('tag-self', {
  input: v.object({ tag: v.string() }),
  run(ctx, input) {
    ctx.tags.ephemeral('user').add(input.tag) // OK — tags() is listed
  },
})

// Without tags() in the list, `ctx.tags` would be a compile error here —
// the field is simply absent from the type.
```

## The map

| Capability | Adds to `ctx` |
|---|---|
| `keepalive(...)` | `ctx.latency`, `ctx.quality` |
| `requests()` | `ctx.request(...)`, `ctx.broadcastRequest(...)`, and `request(...)` on `ctx.connection(ref)` |
| `scheduled(...)` | `ctx.schedule(...)`, `ctx.cancelScheduled(...)` |
| `channels()` | `ctx.channels` |
| `tags(...)` | `ctx.tags` |
| `replay.history()` / `replay.snapshot()` / `replay.custom()` | `ctx.sendReplay(...)` |
| `plugin(...)` | `ctx.plugin(id, registrationId?)` |

The rest of this page shows each one. The deep behavior of each capability lives in its own page — here we show the `ctx` surface and link out.

## `ctx.latency` and `ctx.quality` — keepalive

The `keepalive()` capability runs a server-side ping/pong loop and surfaces what it measures on `ctx`.

| Field | Type | What it is |
|---|---|---|
| `ctx.latency` | `number \| null` | Last measured round-trip in milliseconds, or `null` before the first measurement. |
| `ctx.quality` | `'excellent' \| 'good' \| 'degraded' \| 'poor' \| null` | A coarse health label from the rolling latency average, or `null` before the first round-trip. |

```typescript [quality.ts]
const base = define({
  env: t<Env>(),
  upgrade: (request) => requireUsername(request),
  capabilities: [
    keepalive({ pingIntervalMs: 1_000, idleTimeoutMs: 10_000 }),
    emits({
      'quality-result': t<{
        quality: string | null
        latency: number | null
        bufferedAmount: number
      }>(),
    }),
  ],
})

base.on('get-quality', {
  input: v.object({}),
  run(ctx) {
    ctx.send('quality-result', {
      quality: ctx.quality,
      latency: ctx.latency,
      bufferedAmount: ctx.bufferedAmount ?? 0,
    })
  },
})
```

The quality bands: `'excellent'` is under 100 ms, `'good'` is 100–299 ms, `'degraded'` is 300–999 ms, `'poor'` is 1000 ms and up. Both fields stay `null` until the first ping/pong completes. When you run with hibernation enabled, no server-side ping is sent, so `quality` is always `null`. Full config — intervals, timeouts, hibernation — is on the [Keepalive](/server/capabilities/keepalive) page.

## `ctx.tags` — tags

The `tags(...)` capability adds `ctx.tags`, the handle for grouping connections by label. You declare groups in the capability; `ctx.tags.ephemeral(group)` and `ctx.tags.persistent(group)` only accept declared group names.

```typescript [tags.ts]
const base = define({
  env: t<Env>(),
  upgrade: (request) => requireUsernameWithUserTag(request),
  capabilities: [
    tags((ephemeral) => [ephemeral('user', t<string>()), ephemeral('label', t<string>())]),
    emits({ 'tag-result': t<{ tags: string }>() }),
  ],
})

const handleTagSelf = base.on('tag-self', {
  input: v.object({ tag: v.string() }),
  run(ctx, input) {
    ctx.tags.ephemeral('label').add(input.tag) // tag this connection
    ctx.send('tag-result', { tags: serializeTags(ctx.tags.list()) })
  },
})

const handleUntagSelf = base.on('untag-self', {
  input: v.object({ tag: v.string() }),
  run(ctx, input) {
    ctx.tags.ephemeral('label').remove(input.tag) // untag this connection
    ctx.send('tag-result', { tags: serializeTags(ctx.tags.list()) })
  },
})
```

A group handle (`ctx.tags.ephemeral('label')`) carries `add`, `remove`, `has`, and group-wide reads. A ref handle (`.ref(key)`) addresses every connection holding one exact key — you can `send` to them or read them with `connections()`:

```typescript [tag-fanout.ts]
base.on('get-by-tag', {
  input: v.object({ tag: v.string() }),
  run(ctx, input) {
    const matches = ctx.tags.ephemeral('user').ref(input.tag).connections()
    ctx.send('connections-by-tag-result', { tag: input.tag, count: matches.length })
  },
})
```

`ctx.tags.list()` returns every tag ref on the current connection. The full surface — persistent vs ephemeral groups, group-wide `send`/`count`/`keys`, kicking by tag — is on the [Tags](/server/capabilities/tags) page.

## `ctx.channels` — channels

The `channels()` capability adds `ctx.channels`, which resolves a channel handle from any handler. Use it to send into a channel, read its members, or kick connections out of it.

```typescript [channels.ts]
const base = define({
  env: t<Env>(),
  upgrade: (request) => requireUsernameWithUserTag(request),
  capabilities: [
    emits({ 'members-result': t<{ channel: string; count: number }>() }),
    tags((ephemeral) => [ephemeral('user', t<string>())]),
    channels(),
  ],
})

base.on('get-members', {
  input: v.object({ channel: v.string() }),
  run(ctx) {
    ctx.send('members-result', {
      channel: 'room',
      count: ctx.channels.get('room').members().length,
    })
  },
})
```

`ctx.channels.get(name)` resolves a static channel; `ctx.channels.get(family, name)` resolves one inside a dynamic family. The handle carries `send`, `broadcast`, `members()`, `subscribe(ref)`, `kick(target, reason)`, and `removeMember(identity)`. The deep behavior — broadcast scoping, family vs static, kicking — lives in the [Channels](/server/channels/overview) chapter.

::note
Inside a **channel handler** you get `ctx.channel` (singular) — send and broadcast already scoped to the current channel. `ctx.channels` (plural) is the from-anywhere lookup. See [Channels](/server/channels/overview).
::

## `ctx.schedule` and `ctx.cancelScheduled` — scheduled

The `scheduled(...)` capability adds queue control for durable tasks.

| Method | What it does |
|---|---|
| `ctx.schedule(taskId, { time, data? })` | Queue a declared task to run once at `time` (ms since epoch). `data` is typed to that task's payload. |
| `ctx.cancelScheduled(taskId, filter?)` | Cancel pending runs of a task. With no filter, cancels all; with a filter, cancels runs whose `data` matches. |

```typescript [schedule.ts]
base.on('remind-me', {
  input: v.object({ text: v.string(), atMs: v.number() }),
  run(ctx, input) {
    ctx.schedule('send-reminder', { time: input.atMs, data: { text: input.text } })
  },
})
```

Only task ids you declared with `scheduled(...)` are accepted, and `data` is typed to that task's declared payload — a wrong id or payload is a compile error. The task body, declared with `base.scheduled(...)`, runs in a [task context](/server/context-and-storage/overview#context-shapes-by-handler-type) with no per-connection `send`. Full details are on the [Scheduled](/server/capabilities/scheduled) page.

## `ctx.request` and `ctx.broadcastRequest` — requests

The `requests()` capability lets the server ask the client a question and await a typed answer. It adds the request arm in three places.

| Surface | What it does |
|---|---|
| `ctx.request(event, payload, options?)` | Ask the **current** connection a declared server→client request; resolves its typed answer. |
| `ctx.broadcastRequest(event, payload, options?)` | Ask everyone; resolves the first valid answer plus the `from` ref. |
| `ctx.connection(ref).request(...)` | Ask **one specific** connection by ref. |

```typescript [server-request.ts]
base.on('confirm-action', {
  input: v.object({}),
  async run(ctx) {
    const answer = await ctx.request('confirm', { question: 'Proceed?' }, { timeout: 5_000 })
    ctx.send('confirm-result', { ok: answer.ok })
  },
})
```

Without `requests()` listed, `ctx.connection(ref)` returns a handle with **only** `send` — the `request` arm is absent from the type. With it listed, the same handle gains `request(...)`. The full request/response model lives on the [Requests](/server/capabilities/requests) page.

## `ctx.sendReplay` — replay

A replay capability (`replay.history()`, `replay.snapshot()`, or `replay.custom()`) adds `ctx.sendReplay`, used to inject a synthetic replay frame for one outgoing event with the wire metadata a reconnecting client needs to dedup it.

```typescript [send-replay.ts]
base.on('seed-history', {
  input: v.object({}),
  run(ctx) {
    ctx.sendReplay('message', { text: 'welcome back', from: 'server' }, {
      seq: 1,
      messageId: 'm-1',
    })
  },
})
```

You mostly reach for this inside a custom replay handler. The full replay model is on the [Replay](/server/capabilities/replay) page.

## `ctx.plugin` — plugins

When you register a server plugin, `ctx.plugin(id)` reaches that plugin's per-connection API. The id is typed to the plugins you listed, and the result is that plugin's API type. Pass `registrationId` to pick an instance when the same plugin is registered more than once. See the [Plugins](/server/plugins/overview) chapter.
