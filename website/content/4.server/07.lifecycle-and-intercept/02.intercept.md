`intercept` is one hook that runs for **every incoming frame**, before schema validation and before the handler. It is the single place to do cross-cutting inbound work: audit logging, rate metrics, payload sanitizing, auth checks, or dropping unwanted traffic. It can look at a frame, replace its payload, or stop it.

It needs the `intercepts()` capability. Listing that capability grants `base.intercept(...)` and the channel `intercept(...)`. The `ctx.matches(...)` / `ctx.unsafeCast(...)` helpers are on every connection `ctx` regardless — they're just most useful here, inside an intercept.

```typescript [enable.ts]
import { define, t } from '@wskit/server'
import { intercepts } from '@wskit/server/intercepts'

const base = define({
  env: t<Env>(),
  capabilities: [intercepts()],
})

base.intercept((ctx, frame) => {
  ctx.log.info('incoming', { event: frame.event, kind: frame.kind })
})
```

Without `intercepts()`, `base.intercept` is not on the builder type — calling it is a compile error, not a runtime surprise.

## The frame

The handler receives `(ctx, frame)`. `frame` is a read-only view of the message as it arrives:

::field-group
  ::field{name="event" type="string"}
  The event name exactly as it came from the client.
  ::
  ::field{name="payload" type="unknown"}
  The raw, unvalidated payload. Gate on `frame.event` / `frame.kind`, then read it (see [Reading the payload](#reading-the-payload)).
  ::
  ::field{name="kind" type="'incoming' | 'request' | 'stream' | 'nudge' | 'unknown'"}
  Which handler family this event routes to, or `'unknown'` if none matches.
  ::
  ::field{name="routing" type="InterceptRouting"}
  Curated routing markers: `messageId`, `correlationId`, `streamId`, `channel`, `channelFamily`, `seq`. Read-only.
  ::
  ::field{name="owner" type="FrameOwner"}
  Whether the event is app-owned (`{ kind: 'app' }`) or owned by a plugin (`{ kind: 'plugin', id }`). See [Plugins](#plugins-and-frame-ownership) below.
  ::
::

The event name and routing are **locked** from the moment the message hits the dispatcher — an intercept cannot reroute a frame. Only the payload can change.

```typescript [branch-by-kind.ts]
base.intercept((ctx, frame) => {
  if (frame.kind === 'request') ctx.log.info('request in', { event: frame.event })
  if (frame.kind === 'stream') ctx.log.info('stream start', { event: frame.event })
  if (frame.kind === 'unknown') ctx.log.warn('no handler for', { event: frame.event })
})
```

## Inspect, rewrite, or pass through

The return value decides what happens to the payload:

- **Return nothing** (`void` / `undefined`) — the frame passes through unchanged.
- **Return a value** — that value **replaces** `frame.payload` for the next intercept and for the handler.

The returned value becomes the payload verbatim, even if it happens to be an object with its own `event` or `routing` fields — those do not reroute anything.

```typescript [rewrite.ts]
base.intercept((ctx, frame) => {
  if (frame.kind === 'incoming' && frame.event === 'send-message') {
    const p = frame.payload as { text: string }
    // Strip whitespace before the handler — and before validation — sees it.
    return { ...p, text: p.text.trim() }
  }
  // every other frame passes through untouched
})
```

Because the rewrite happens **before** validation, the handler's schema validates the value you returned, not the original.

## Reading the payload

`frame.payload` is typed `unknown` — an intercept runs before validation, so the framework has not checked the shape yet. The pattern is: gate on `frame.event` and `frame.kind` first, then read the payload.

```typescript [read.ts]
base.intercept((ctx, frame) => {
  if (frame.kind === 'incoming' && frame.event === 'send-message') {
    const p = frame.payload as { text: string }
    if (containsProfanity(p.text)) return { ...p, text: mask(p.text) }
  }
})
```

The cast is the deliberate boundary: an intercept sits **before** the schema, so the wire payload is genuinely `unknown` here and you assert the shape you expect.

### `ctx.matches` — the validating guard

To run the event's declared validator inside the intercept, use `ctx.matches(key, frame)`. It returns `true` only when the frame's event, scope, and **validated** payload all line up — so a frame that fails the schema returns `false` instead of slipping through.

```typescript [matches.ts]
base.intercept((ctx, frame) => {
  // Runs the validator declared for 'send-message'. False if the payload is bad.
  if (ctx.matches('send-message', frame)) {
    const p = frame.payload as { text: string }
    if (containsProfanity(p.text)) return { ...p, text: mask(p.text) }
  }
})
```

`ctx.matches` throws if the key names an event the server does not declare — a typo is caught loudly. Use the `@family::event` key form for a channel-scoped event:

```typescript [matches-channel.ts]
base.intercept((ctx, frame) => {
  if (ctx.matches('@lobby::say', frame)) {
    const p = frame.payload as { text: string }
    auditChannelMessage(p.text)
  }
})
```

`ctx.unsafeCast(key, frame)` is the no-runtime-check sibling: it validates the **key** against the catalog (an unknown event throws) but does not run the payload validator. Use it when your own logic already established the shape.

::note
`ctx.matches` and `ctx.unsafeCast` are on every connection `ctx` — they don't need the `intercepts()` capability (only `base.intercept(...)` itself does). They check the event key against the server's declared catalog at runtime; read the payload with a cast after the guard, as the examples above do.
::

## Blocking and disconnecting

An intercept can stop a frame by throwing a control-flow error from `@wskit/server/errors`:

- **`Block`** — silently drop the frame. The handler never runs and no response is sent. The socket stays open.
- **`Disconnect(code, reason)`** — close the connection.

```typescript [block-and-disconnect.ts]
import { Block, Disconnect, CloseCodes } from '@wskit/server/errors'

base.intercept((ctx, frame) => {
  // Drop frames from a muted user without telling them
  if (isMuted(ctx.meta.userId)) throw Block

  // Hard-stop an abusive connection
  if (tooManyFrames(ctx)) throw Disconnect(CloseCodes.BANNED, 'Rate abuse')
})
```

You can also throw any **registered typed error** to surface it to the client — the same way a handler does. That path, and the difference between `Block`, `Disconnect`, and a typed error, is the shared error model in [Core](/core/error-model); the server control-flow errors live in [Control-flow errors](/server/capabilities/errors).

## Channel intercepts

A channel gets its own `intercept`, registered on the channel object (also gated by `intercepts()`). It sees frames addressed to that channel. The pipeline runs the **top-level** intercept first, then the **channel** one.

```typescript [channel-intercept.ts]
const room = base.channel('room', {
  outgoing: { emits: { said: t<{ text: string }>() } },
})

room.intercept((ctx, frame) => {
  if (frame.kind === 'incoming' && frame.event === 'say') {
    const p = frame.payload as { text: string }
    if (p.text === '') throw Block // drop empty messages in this channel
  }
})

const handleSay = room.on('say', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('said', { text: input.text })
  },
})
```

Both intercepts share the same per-frame locals store — a value an upstream top-level intercept provides is readable in the channel one. See [provide / inject](/server/lifecycle-and-intercept/provide-inject).

## What kinds an intercept sees

An intercept runs for normal events (`incoming`), `request` frames, `stream` start frames, and `nudge` frames sent into a running stream. For a nudge, the intercept runs **before** the hint is buffered for the generator, so a rewrite changes what the generator reads and a `Block` drops the nudge.

```typescript [nudge.ts]
base.intercept((ctx, frame) => {
  if (frame.kind === 'nudge' && frame.event === 'hint') {
    const p = frame.payload as { text: string }
    if (p.text === 'stop') throw Block            // drop this nudge
    return { ...p, text: p.text.toLowerCase() }   // or rewrite it
  }
})
```

## Plugins and frame ownership

`frame.owner` tells you whether a frame belongs to your app or to an installed plugin. An app intercept sees **every** frame — its own and plugins'. A plugin's intercept sees only its own frames, unless it was granted host observation.

```typescript [owner.ts]
base.intercept((ctx, frame) => {
  if (frame.owner.kind === 'plugin') {
    ctx.log.info('plugin frame', { id: frame.owner.id, event: frame.event })
  }
})
```

When you list plugins, `frame.owner.id` is typed to the union of installed plugin ids, so you get autocomplete on the id. Authoring plugins and the host-observation grant are covered in [Plugins](/server/plugins/overview).

::note
One `intercept` per server, plus one per channel. To run several pieces of inbound logic, put them in the one intercept.
::
