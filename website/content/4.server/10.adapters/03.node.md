::warning
The Node.js adapter (`@wskit/server-node`) is **planned** and does not exist yet. [Cloudflare Durable Objects](/server/adapters/cloudflare) is the adapter available today. This page is a placeholder so you know what to expect.
::

## What stays the same

WSKit splits a server into two halves: a platform-agnostic **definition** and a platform-specific **adapter**. The definition — `define`, capabilities, handlers, `assemble` — does not change between platforms. So this much will be identical on Node.js and on Cloudflare:

```ts [handler.ts]
import { define, emits, t } from '@wskit/server'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [emits({ pong: t<{ text: string }>() })],
})

const handlePing = base.on('ping', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.send('pong', { text: input.text })
  },
})

export const chat = base.assemble(handlePing)
```

## What will change

Only the adapter entry — the line that turns the definition into a running service. On Cloudflare that is `server(chat)`, which yields a Durable Object class. The Node.js adapter will expose its own `server(...)` entry that runs the same `chat` definition, likely attached to an HTTP server. The exact API is not settled, so this page will not invent one.

::note
Node.js exposes real outbound buffer pressure, so `ctx.stream.drain()` will pace a stream generator against the live socket buffer once the adapter lands. On Cloudflare, which does not expose buffer fullness, `drain()` is a no-op. Same definition, different runtime behavior — driven by the adapter, not your code.
::

Until the Node.js adapter ships, build on [Cloudflare](/server/adapters/cloudflare) — your handler code carries over unchanged when the Node entry arrives. See [Installation](/start/installation) for the current package list.
