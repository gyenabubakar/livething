::warning
The Bun adapter (`@wskit/server-bun`) is **planned** and does not exist yet. [Cloudflare Durable Objects](/server/adapters/cloudflare) is the adapter available today. This page is a placeholder so you know what to expect.
::

## What stays the same

The point of the adapter split is that your **server code does not change** between platforms. The definition you write with `define`, capabilities, handlers, and `assemble` is platform-agnostic. Only the adapter entry — the one line that turns the definition into a runtime service — changes when you switch.

So this much is identical on Bun and on Cloudflare:

```ts [handler.ts]
import { define, emits, t } from '@wskit/server'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [emits({ pong: t<{ text: string }>() })],
})

const handlePing = base.on('ping', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.send('pong', { text: input.text })
  },
})

export const chat = base.assemble(handlePing)
```

## What will change

Only the last step — the adapter call. On Cloudflare you write `server(chat)` and export a Durable Object class. The Bun adapter will expose its own `server(...)` entry that starts a Bun service from the same `chat` definition. The exact shape is not settled yet, so this page will not show a fake API.

::note
One real difference once it lands: Bun exposes live outbound buffer pressure, so `ctx.stream.drain()` will pace a stream generator against the real socket buffer. On Cloudflare, which does not expose that, `drain()` resolves immediately as a no-op. The definition is the same; the runtime fills in the rest.
::

Until the Bun adapter ships, build on [Cloudflare](/server/adapters/cloudflare) — the handler code carries straight over when the Bun entry arrives. See [Installation](/start/installation) for the current package list.
