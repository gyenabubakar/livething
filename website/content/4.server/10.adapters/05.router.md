A real app rarely has one server. You might have a chat room, a presence tracker, and a live document — three separate handlers, each with its own contract. WSKit has **no `router()` API**. You run multiple handlers the same way Cloudflare already routes traffic: one Worker `fetch`, several Durable Object classes, and a small switch on the request path.

::note
This page is about the Cloudflare adapter, where routing is the Worker's job. The mechanism is plain Cloudflare — bindings and `idFromName` — not a WSKit construct.
::

## One class per handler

Each handler becomes its own Durable Object class through `server(...)`. Keep them in their own files and export each class.

```ts [servers.ts]
import { server } from '@wskit/server-cloudflare'
import { chatHandler } from './chat-handler'
import { presenceHandler } from './presence-handler'
import { docHandler } from './doc-handler'

export const ChatRoom = server(chatHandler)
export const Presence = server(presenceHandler)
export const Document = server(docHandler)
```

## Route in the Worker `fetch`

The Worker's default export sees every request. Match the path, pick the matching binding, derive a Durable Object ID, and forward the request to that stub. The adapter handles the upgrade inside the chosen Durable Object.

```ts [worker.ts]
export { ChatRoom, Presence, Document } from './servers'

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url)
    const room = url.searchParams.get('room') ?? 'default'

    if (url.pathname === '/ws/chat') {
      const id = env.CHAT_ROOM.idFromName(room)
      return env.CHAT_ROOM.get(id).fetch(request)
    }

    if (url.pathname === '/ws/presence') {
      const id = env.PRESENCE.idFromName(room)
      return env.PRESENCE.get(id).fetch(request)
    }

    if (url.pathname === '/ws/document') {
      const id = env.DOCUMENT.idFromName(room)
      return env.DOCUMENT.get(id).fetch(request)
    }

    return new Response('not found', { status: 404 })
  },
} satisfies ExportedHandler<Env>
```

Each `idFromName(room)` keeps separate rooms isolated: `/ws/chat?room=lobby` and `/ws/chat?room=staff` are two different Durable Object instances of the same `ChatRoom` class, with separate connections and storage.

## A table-driven router for many handlers

Once you have more than a handful of routes, a lookup table reads better than a stack of `if`s. Map each path to its binding name, then resolve the binding off `env`.

```ts [worker.ts]
const ROUTES: Record<string, keyof Env> = {
  '/ws/chat': 'CHAT_ROOM',
  '/ws/presence': 'PRESENCE',
  '/ws/document': 'DOCUMENT',
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url)
    const room = url.searchParams.get('room') ?? 'default'

    const bindingName = ROUTES[url.pathname]
    if (bindingName) {
      const namespace = env[bindingName] as DurableObjectNamespace
      const id = namespace.idFromName(room)
      return namespace.get(id).fetch(request)
    }

    return new Response('not found', { status: 404 })
  },
} satisfies ExportedHandler<Env>
```

## Bind every class in `wrangler.jsonc`

Each class needs a binding and a `migrations` entry. Add new classes as `new_sqlite_classes` under a fresh migration `tag` so they get SQLite storage.

```jsonc [wrangler.jsonc]
{
  "name": "app",
  "main": "src/worker.ts",
  "compatibility_date": "2026-04-07",
  "durable_objects": {
    "bindings": [
      { "name": "CHAT_ROOM", "class_name": "ChatRoom" },
      { "name": "PRESENCE", "class_name": "Presence" },
      { "name": "DOCUMENT", "class_name": "Document" }
    ]
  },
  "migrations": [
    {
      "tag": "v1",
      "new_sqlite_classes": ["ChatRoom", "Presence", "Document"]
    }
  ]
}
```

::tip
The `room` here can be anything that names an instance — a user ID, a document ID, a tenant ID. `idFromName` always returns the same Durable Object for the same name, so the same name always reaches the same connections and storage.
::

## Non-WebSocket routes too

The Worker `fetch` is plain Cloudflare, so the same switch can answer admin or health routes that are not WebSocket upgrades. The graceful [`shutdown()`](/server/adapters/cloudflare#graceful-shutdown) RPC is a good example — call it from an admin path before a deploy:

```ts [worker.ts]
if (url.pathname === '/admin/drain-chat') {
  const id = env.CHAT_ROOM.idFromName(room)
  await env.CHAT_ROOM.get(id).shutdown()
  return new Response(null, { status: 204 })
}
```
