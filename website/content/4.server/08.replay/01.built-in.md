Built-in replay means WSKit owns the storage. You list one capability, and the engine records every outgoing message and resends the missing tail when a client reconnects. No handler code, no table to manage.

There are two modes: **history** keeps every message, **snapshot** keeps only the latest value per key.

## What both modes need

Built-in replay is not standalone. It depends on two other capabilities, and the build fails fast without them:

- [`dedup()`](/server/capabilities/dedup) — stamps each message with the id replay keys off and the client de-duplicates against.
- [`sequence({ persist: true })`](/server/capabilities/sequence) — gives each message a stable sequence number that survives a restart, so stored rows order correctly. The `persist: true` part is required; an in-memory sequence is not enough, and the build says so.

It also needs the platform `storage` capability (the SQL store), which the Cloudflare adapter provides.

::code-group
```typescript [history-server.ts]
import { define, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { sequence } from '@wskit/server/sequence'
import { replay } from '@wskit/server/replay'

const base = define({
  env: t<Env>(),
  capabilities: [
    dedup(),
    sequence({ persist: true }),
    replay.history(),
  ],
})
```

```typescript [snapshot-server.ts]
import { define, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { sequence } from '@wskit/server/sequence'
import { replay } from '@wskit/server/replay'

const base = define({
  env: t<Env>(),
  capabilities: [
    dedup(),
    sequence({ persist: true }),
    replay.snapshot(),
  ],
})
```
::

## History mode

`replay.history(...)` keeps **every** message as its own row. On reconnect, the client says "I last saw sequence N" and gets every recorded message after N, in order. This is what you want for a chat room, an activity feed, or a log — anything where the full sequence of events matters and you cannot skip the middle.

```typescript [chat-server.ts]
import { define, emits, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { sequence } from '@wskit/server/sequence'
import { replay } from '@wskit/server/replay'
import * as v from 'valibot'

const ChatMsg = v.object({ text: v.string(), from: v.string() })
const SendMsg = v.object({ text: v.string() })

const base = define({
  env: t<Env>(),
  capabilities: [
    emits({ 'chat-msg': t<v.InferOutput<typeof ChatMsg>>() }),
    dedup(),
    sequence({ persist: true }),
    replay.history({
      retention: { maxMessages: 1000, maxAgeMs: 3_600_000 },
      durability: 'strict',
      exclude: ['cursor'],
    }),
  ],
})

export const handleSendMsg = base.on('send-msg', {
  input: SendMsg,
  run(ctx, payload) {
    const msg = { text: payload.text, from: ctx.meta.username }
    ctx.send('chat-msg', msg)
    ctx.broadcast('chat-msg', msg)
  },
})
```

Nothing in the handler mentions replay. Every `chat-msg` is recorded as it goes out. When the socket comes back, the client gets the ones it missed, and `cursor` events are skipped because they are in the `exclude` list.

### History config

| Field | Type | Default | What it does |
|---|---|---|---|
| `durability` | `'strict' \| 'best-effort'` | `'strict'` | `strict` writes the row before the send completes. `best-effort` sends first, then stores asynchronously — lower latency, small risk of losing the very last row on a crash. |
| `retention.maxMessages` | `number` | none | Keep at most this many rows per store. When the store grows past it, the oldest rows are deleted. |
| `retention.maxAgeMs` | `number` | none | Delete rows older than this many milliseconds. Pruned on boot and whenever a new message is stored. |
| `exclude` | `string[]` | `[]` | Event names to never record. They still send live; they just never appear in replay. |

::note
`maxMessages` is **per store**. There are only two kinds of store: one top-level store, and one per channel. So `maxMessages: 1000` means up to 1000 top-level rows, plus up to 1000 rows for each channel that has its own replay.
::

## Snapshot mode

`replay.snapshot(...)` keeps only the **latest** row per logical key. A reconnecting client gets the current state of each key, not the full history of how it got there. This is what you want for a document, a counter, or a presence map — the journey does not matter, only where things landed.

You give it two functions:

- `snapshotKey(event, payload)` — builds the key that decides which rows replace each other. Rows with the same key collapse into one. If you omit it, the event name is the key.
- `reduce(previous, next)` — optional. Combines the stored value with the new one instead of always taking the newest. Return an `{ event, payload }` to store, or `null` to delete that key's snapshot.

```typescript [docs-server.ts]
import { define, emits, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { sequence } from '@wskit/server/sequence'
import { replay } from '@wskit/server/replay'
import * as v from 'valibot'
import type { ReplaySnapshotValue } from '@wskit/server/replay'

const DocSnapshot = v.object({ docId: v.string(), title: v.string() })
const DocDeleted = v.object({ docId: v.string() })
const CounterSnapshot = v.object({ key: v.string(), total: v.number() })

function reduceSnapshot(
  previous: ReplaySnapshotValue | null,
  next: ReplaySnapshotValue,
): ReplaySnapshotValue | null {
  if (next.event === 'doc-deleted') return null            // forget this key
  if (next.event !== 'counter-snapshot') return next       // latest wins

  // For counters, add the running total instead of replacing it.
  const previousTotal =
    previous?.event === 'counter-snapshot' ? Number(previous.payload.total) : 0
  return {
    event: next.event,
    payload: { ...next.payload, total: previousTotal + Number(next.payload.total) },
  }
}

const base = define({
  env: t<Env>(),
  capabilities: [
    emits({
      'doc-snapshot': t<v.InferOutput<typeof DocSnapshot>>(),
      'doc-deleted': t<v.InferOutput<typeof DocDeleted>>(),
      'counter-snapshot': t<v.InferOutput<typeof CounterSnapshot>>(),
    }),
    dedup(),
    sequence({ persist: true }),
    replay.snapshot({
      snapshotKey: (_event, payload) => String(payload.docId ?? payload.key),
      reduce: reduceSnapshot,
      retention: { maxMessages: 5, maxAgeMs: 1_000 },
      durability: 'best-effort',
    }),
  ],
})
```

Here every `doc-snapshot` for the same `docId` replaces the last one — a reconnecting client gets only the newest title per document. A `doc-deleted` returns `null`, so that key drops out of the store entirely. A `counter-snapshot` adds to the running total instead of replacing it.

You can type `snapshotKey` and `reduce` as standalone functions with the exported [`SnapshotKeyFn`](/server/capabilities/replay) and `SnapshotReducer` types, or write them inline as arrows.

### Snapshot config

Snapshot mode takes everything history mode takes (`durability`, `retention`, `exclude`) plus two of its own:

| Field | Type | Default | What it does |
|---|---|---|---|
| `snapshotKey` | `(event, payload) => string` | event name | Logical key. Rows sharing a key replace each other. |
| `reduce` | `(previous, next) => value \| null` | latest wins | Combine the stored snapshot with the new event. `previous` is the current value or `null`. Return a value to store, or `null` to delete that key's snapshot. |

::tip
Snapshot mode also coalesces in memory. If a handler sends many messages for the same key in one go — say a burst of counter increments — they fold together inside the open handler scope and only the final value is written once when the handler finishes, instead of one SQL write per send.
::

## Durability: strict vs best-effort

`durability` decides the order of storing and sending:

- **`strict`** (default) — store the row first, then send. The message is recorded before the client could have seen it, so a crash never loses a sent-but-unstored message. Slightly higher send latency.
- **`best-effort`** — send first, then store asynchronously. Lower latency, but if the process dies in the gap, the last message may not make it into the store.

Use `strict` when missing a message would be a real problem (orders, payments, audit logs). Use `best-effort` when a touch of latency matters more than the last message in a crash (cursors, presence, high-frequency snapshots).

## Per-channel replay

Server-level replay **cascades** — it records channel traffic too. To override that for one channel, set `replay` in the channel config:

```typescript [rooms-server.ts]
// Inherit + enable the server-level strategy for this channel:
const busy = base.channel('busy-room', { replay: true })

// Opt this channel out entirely — its messages are not stored or replayed:
const quiet = base.channel('quiet-room', { replay: false })
```

`replay: true` gives the channel its own store using the server-level config. `replay: false` opts the channel out — messages on it are not recorded by either the server-level or a channel-level instance. See [Channels](/server/channels/overview) for the subscribe-time side of channel replay.

## Manual replay from a handler

Built-in replay is automatic, but you can also resend a stored message by hand — useful for a "load older history" button. With replay registered, the connection context gains `ctx.sendReplay(event, payload, wire)`:

```typescript [history-button.ts]
export const handleRequestHistory = base.on('request-history', {
  input: v.object({}),
  run(ctx) {
    ctx.sendReplay(
      'chat-msg',
      { text: 'injected-history', from: 'system' },
      { seq: 0, messageId: 'manual-001' },
    )
  },
})
```

The `wire` object names the `seq` and `messageId` the client uses to order and de-duplicate the frame.

**Inside a channel handler**, use `ctx.channel.sendReplay(...)`. The channel name is implicit, so you pass only `seq` and `messageId`:

```typescript [room-history.ts]
// chatRoom is a channel: const chatRoom = base.channel('room', { ... })
export const handleRoomHistory = chatRoom.on('request-room-history', {
  input: v.object({}),
  run(ctx) {
    ctx.channel.sendReplay(
      'room-msg',
      { text: 'injected-room-history', from: 'system' },
      { seq: 0, messageId: 'room-manual-001' },
    )
  },
})
```

**From a top-level handler**, to target a channel — or one instance of a dynamic family — stay on `ctx.sendReplay` and name the `channel` (and `channelFamily` for a family) in the wire, so client-side routing stays correct:

```typescript [family-history.ts]
ctx.sendReplay(
  'room-msg',
  { text: 'family-injected', from: 'system' },
  { seq: 0, messageId: 'fam-manual-001', channel: 'fam-1', channelFamily: 'fams' },
)
```

::warning
`sendReplay` is contract-checked at runtime. The event must be a declared outgoing event for that scope — sending an undeclared event throws `[wskit] Outgoing event "..." was not declared in the active scope.`. The type surface only offers declared events, so you hit this only if you cast past it.
::
