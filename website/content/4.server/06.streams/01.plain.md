A **plain stream** is an async generator that pushes chunks to one client. It is *ephemeral*: it lives only as long as the connection. The moment the client disconnects or cancels, the generator's `return()` runs, your `finally` blocks fire, and the stream is gone. Nothing is stored — if the client wants the data again it must ask for a fresh stream.

This page is the deep dive on plain-stream behavior. For the first-look "how do I write a stream method" intro, start at [`base.stream`](/server/handlers/stream). To enable the builder, list `stream()` in your capabilities — see [Stream capabilities](/server/capabilities/streams).

## The generator

`base.stream(event, config)` registers a stream. The `run` function is an async generator: each value it yields is sent to the client as one chunk, typed by the `chunk` marker.

```ts [plain-stream.ts]
import { define, t } from '@wskit/server'
import { stream } from '@wskit/server/streams'
import * as v from 'valibot'

const Token = t<{ index: number }>()

const base = define({
  env: t<Env>(),
  capabilities: [stream()],
})

export const handleStartTokens = base.stream('start-tokens', {
  input: v.object({ count: v.number() }),
  chunk: Token,
  async *run(_ctx, input) {
    for (let i = 0; i < input.count; i += 1) {
      yield { index: i }
      await new Promise((r) => setTimeout(r, 200))
    }
  },
})
```

- `input` validates the start payload the client sends. Inside `run`, the second argument is the validated, typed value.
- `chunk` is a [type marker](/server/define/overview) — it types each yielded chunk but is never validated (chunks go *out*, so there is nothing to check). Omit it and the chunk type is inferred from what `run` yields.
- Each `yield` is one wire frame. The generator owns the pacing.

::note
The `chunk` marker is optional. `base.stream('feed', { input, async *run() { yield { index: 0 } } })` infers the chunk type from the yielded value. Pass `chunk` when you want a named, reused type or an explicit shape.
::

## How a stream ends

A plain stream finishes in one of a few ways. The framework sends a terminal frame for each.

| How it ends | What the framework does |
|---|---|
| **Normal completion** | The generator returns (falls off the end or `return`s). The framework sends a stream-end frame. |
| **Empty stream** | A generator that yields nothing still completes — the client gets an immediate stream-end with no chunks. |
| **Defined error** | The generator throws a registered error (one declared with [`error()`](/core/error-model)). The client gets that error, terminal. |
| **Unknown error** | The generator throws anything else. The client gets an `internal-error`, terminal — the real error is not leaked. |
| **Client disconnect** | The socket drops. The framework calls `generator.return()`, so your `finally` blocks run. |
| **Client cancel** | The client cancels the stream. Treated like a disconnect — `return()` is called and `finally` runs. |

A defined error reaches the client with its code and detail; an unknown error is replaced with `internal-error` so you never leak internals.

```ts [stream-errors.ts]
import { error } from '@wskit/server/errors'

const ModelMissing = error('model-missing', v.object({ id: v.string() }))

export const handleAsk = base.stream('ask', {
  input: v.object({}),
  chunk: Token,
  async *run() {
    yield { index: 0 }
    // Reaches the client as { code: 'model-missing', detail: { id } }.
    throw ModelMissing({ id: 'gpt-x' })
  },
})

export const handleBoom = base.stream('boom', {
  input: v.object({}),
  chunk: Token,
  async *run() {
    yield { index: 0 }
    // Reaches the client as { code: 'internal-error' } — the real error is hidden.
    throw new Error('boom')
  },
})
```

For the full error model — defining errors, `.matches()`, the built-in catalog — see [Error model](/core/error-model).

## Cleaning up on disconnect

Because a client disconnect calls `generator.return()`, a `try/finally` is the right place to release resources or fire a final side effect. The connection is still open on a *cancel* (the client is alive, it just stopped this stream), so a `ctx.send(...)` from `finally` lands; on a full disconnect there is nothing to send to.

```ts [cleanup.ts]
export const handleWithCleanup = base.stream('with-cleanup', {
  input: v.object({}),
  chunk: Token,
  async *run(ctx) {
    let completed = false
    try {
      for (let i = 0; i < 20; i += 1) {
        yield { index: i }
        await new Promise((r) => setTimeout(r, 50))
      }
      completed = true
    } finally {
      // Runs on normal completion AND on cancel/disconnect.
      if (!completed) ctx.send('cancel-observed', { cancelled: true })
    }
  },
})
```

## The abort signal

`ctx.stream.signal` is an `AbortSignal` that fires when the stream is cancelled, the client disconnects, or the server shuts down. Pass it into slow awaited work so the work stops the instant the stream is torn down instead of running to completion in the background.

```ts [signal.ts]
export const handleSlow = base.stream('slow', {
  input: v.object({}),
  chunk: Token,
  async *run(ctx) {
    const { signal } = ctx.stream

    yield { index: 0 }

    // Forward the signal into the awaited work. If the client cancels, the
    // fetch aborts immediately instead of holding the stream open.
    const res = await fetch('https://example.com/slow', { signal })
    const data = (await res.json()) as { index: number }
    yield data
  },
})
```

`signal.aborted` is `true` once it has fired, and `signal.reason` carries why. Wiring a timer or any awaited promise to it lets the generator wake up the moment the stream is cancelled rather than blocking on a long timeout.

```ts [signal-timer.ts]
export const handleAwaitOrAbort = base.stream('await-or-abort', {
  input: v.object({}),
  chunk: Token,
  async *run(ctx) {
    const { signal } = ctx.stream
    yield { index: 0 }

    await new Promise<void>((resolve, reject) => {
      const timer = setTimeout(resolve, 60_000)
      signal.addEventListener(
        'abort',
        () => {
          clearTimeout(timer)
          reject(new Error('aborted'))
        },
        { once: true },
      )
    }).catch(() => {
      // Swallowed: the abort path ends the stream cleanly.
    })
  },
})
```

## Backpressure with drain()

If your generator produces chunks faster than the client can read them, the outbound buffer grows. `ctx.stream.drain()` pauses the generator until the buffered amount is back under the stream's `highWaterMark`, then resolves. Call it between yields to pace a fast producer against a slow consumer.

```ts [drain.ts]
export const handleDrainFeed = base.stream('drain-feed', {
  input: v.object({ count: v.number() }),
  chunk: Token,
  highWaterMark: 64 * 1024, // override the 256 KB default
  async *run(ctx, input) {
    for (let i = 0; i < input.count; i += 1) {
      yield { index: i }
      await ctx.stream.drain()
    }
  },
})
```

- `highWaterMark` is the buffer limit in bytes. Default is **256 KB**. `drain()` resolves once the buffer is under this mark.
- On a healthy client `drain()` resolves the moment the buffer is below the mark, so the stream runs at full speed.

::caution
On Cloudflare, the platform does not expose how full the outbound buffer is, so `drain()` is a no-op that resolves immediately. Your generator must still complete and deliver every chunk — `drain()` is a hint, not a correctness requirement. Treat it as "pace here if the adapter can," not "this will block."
::

## One stream per event, by default

By default a connection can run only one stream of a given event at a time. Starting a second `start-tokens` while one is already running rejects the second start with `stream-already-active` (the existing stream's ID is in `detail.streamId`). Set `allowConcurrent: true` when the use case genuinely needs parallel runs of the same event — for example fan-out searches.

```ts [concurrent.ts]
export const handleSearch = base.stream('search', {
  input: v.object({ query: v.string() }),
  chunk: Token,
  allowConcurrent: true, // the same client may run several 'search' streams at once
  async *run(_ctx, input) {
    // ...
  },
})
```

The `stream-already-active` rejection is a built-in error — see the [built-in errors catalog](/core/builtin-errors).

## Nudges: steering a running stream

A **nudge** is a typed client→server message sent *into* a stream that is already running. Declare nudges in a `nudges` map (event name → schema, or `null` for no payload). After each `yield`, read the nudges that arrived with `ctx.stream.nudges(yield ...)`.

```ts [nudges.ts]
export const handleNudged = base.stream('nudged', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ token: string }>(),
  nudges: {
    pause: null,
    'speed-up': v.object({ factor: v.number() }),
  },
  async *run(ctx, input) {
    let delay = 50
    for (const word of input.prompt.split(' ')) {
      const recent = ctx.stream.nudges(yield { token: word + ' ' })
      if (recent.some((n) => n.event === 'pause')) return
      const speed = recent.find((n) => n.event === 'speed-up')
      if (speed) delay = Math.max(1, delay / speed.payload.factor)
      await new Promise((r) => setTimeout(r, delay))
    }
  },
})
```

`ctx.stream.nudges(...)` returns the typed nudge messages that arrived since the last yield, each `{ event, payload }`. The `nudges()` reader only exists on `ctx.stream` when the stream declares at least one nudge. Nudges, their buffer cap, and overflow are covered in full on [Configuration & Lifecycle](/server/streams/config-and-lifecycle#nudges).
