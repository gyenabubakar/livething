A **family** is one channel declaration that matches many names. Instead of declaring a static channel per room, you declare one template — `room:{id}` — and every matching name becomes its own isolated channel instance, all sharing the same events, gate, and handlers.

```typescript [rooms.ts]
const rooms = base.channel(['rooms', 'room:{id}'], {
  outgoing: {
    emits: { 'room-message': t<{ channel: string; text: string; from: string }>() },
  },
})
```

`rooms` is the **family key** — the identifier you use in `ctx.channels.get('rooms', name)`. `room:{id}` is the **template** matched against the name a client subscribes to. A client subscribing to `room:general` lands in the `general` instance; `room:design` is a separate instance with separate members.

The `[familyKey, template]` tuple is the only way to declare a family with `base.channel(...)`. It builds the same family key and matcher the lower-level `scope(key, template)` helper produces.

## The template grammar

A template is plain literal text plus `{name}` captures. WSKit compiles it to a linear-time matcher itself, so unlike a raw regex it can never trigger catastrophic backtracking.

| Template | Matches | `params` |
|---|---|---|
| `room:{id}` | `room:general` | `{ id: 'general' }` |
| `org:{org}/thread:{tid}` | `org:acme/thread:42` | `{ org: 'acme', tid: '42' }` |
| `cfg{{x}}` | `cfg{x}` | `{}` (literal braces) |

The rules:

- `{name}` captures one or more characters. The name must be a plain identifier — letters, digits, underscore, not starting with a digit.
- A literal must separate two captures, so `{a}{b}` is rejected but `{a}:{b}` is fine. This keeps a multi-capture template unambiguous.
- Write `{{` and `}}` for literal `{` and `}`.
- Each capture name must be unique within a template.

A malformed template — an unclosed brace, an empty `{}`, a bad name, a duplicate name, or two captures with no literal between them — throws a clear error at startup.

## Captures in the handler

Inside a family handler, `ctx.channel` tells you which instance the call came in on. `ctx.channel.name` is the full matched name, `ctx.channel.family` is the key, and `ctx.channel.params` holds the captures, typed from the template.

```typescript [rooms.ts]
const handleEchoName = rooms.on('echo-name', {
  input: v.object({}),
  run(ctx) {
    ctx.channel.name        // 'room:general'
    ctx.channel.family      // 'rooms'
    ctx.channel.params.id   // 'general' — typed string from {id}
    ctx.channel.broadcast('room-message', {
      channel: ctx.channel.name,
      text: 'hello',
      from: ctx.meta.username,
    })
  },
})
```

## Reaching one instance from outside

From any handler, `ctx.channels.get(family, name)` resolves a concrete instance. Pass the family key and the full matched name:

```typescript [rooms.ts]
const handleMembers = base.on('room-members', {
  input: v.object({ name: v.string() }),
  run(ctx, payload) {
    const handle = ctx.channels.get('rooms', payload.name) // e.g. 'room:general'
    const count = handle.members().length
    ctx.send('members-result', { name: payload.name, count })
  },
})
```

For a fully typed handle, pass the family declaration's `.at(params)` result instead of a raw string. `.at(...)` fills the template from the captures and types the handle to that channel's events and requests:

```typescript [rooms.ts]
const handleBroadcast = base.on('announce', {
  input: v.object({ id: v.string(), text: v.string() }),
  run(ctx, payload) {
    const ref = rooms.at({ id: payload.id }) // → 'room:<id>', typed
    ctx.channels.get(ref).broadcast('room-message', {
      channel: `room:${payload.id}`,
      text: payload.text,
      from: 'system',
    })
  },
})
```

`.at(...)` exists only on family declarations — calling it on a static channel throws, because a static channel is already a single instance you pass to `get(name)` directly. Calling `.at({})` without the template's required captures is a compile error.

## Per-instance isolation

Each matched name is a fully separate channel. Members, broadcasts, and the gate are scoped to the exact instance — `room:general` never sees `room:design`'s members, and a broadcast to one never reaches the other. The same is true between a static channel and a family.

```typescript [isolation.ts]
const general = base.channel('general', {
  outgoing: { emits: { msg: t<{ from: string; text: string }>() } },
})

const rooms = base.channel(['rooms', 'room:{id}'], {
  outgoing: { emits: { msg: t<{ from: string; text: string }>() } },
})

// A broadcast in 'general' reaches only its members.
const handleGeneral = general.on('send-in-general', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('msg', { from: 'static', text: payload.text })
  },
})

// A broadcast in a 'rooms' instance reaches only that instance's members.
const handleRoom = rooms.on('send-in-room', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('msg', { from: 'family', text: payload.text })
  },
})
```

## Key collision rules

Routing is by the `(family-key, name)` pair, never by gluing the two together. That keeps two families isolated even when their qualified names could be confused if you concatenated them.

```typescript [collision.ts]
// 'rooms' matches names like 'private-lobby'.
const rooms = base.channel(['rooms', 'private-{id}'], {
  outgoing: { emits: { hello: t<{ family: string; text: string }>() } },
})

// 'rooms-private' matches names like 'lobby'.
const roomsPrivate = base.channel(['rooms-private', '{id}'], {
  outgoing: { emits: { hello: t<{ family: string; text: string }>() } },
})
```

A naive `key + '/' + name` scheme would read both `rooms` + `private-lobby` and `rooms-private` + `lobby` as the same string. WSKit routes by the tuple, so they stay separate.

There is one rule the framework enforces at startup: **a family pattern must not match a static channel name.** If it did, the same wire name could route to two different definitions depending on lookup order. This boots-checks and throws with a message telling you to narrow the family pattern or rename the static channel.

```typescript [conflict.ts]
// This pair fails at startup: the family 'room:{id}' matches the static
// name 'room:vip', so the same subscribe could resolve two ways.
base.channel('room:vip', { /* ... */ })
base.channel(['rooms', 'room:{id}'], { /* ... */ })
```

Two different families *may* share the same template (e.g. both use `room:{id}`) — they are still isolated by their distinct family keys.

A second startup rule rounds this out: **a static channel name must not equal a family key.** Declaring `base.channel('rooms', ...)` alongside a family whose key is `'rooms'` throws at startup telling you to rename one — the name and the key share the same lookup space.

## Presence — who is in, and who is online

A channel keeps every member's roster in sync by broadcasting presence frames. There are two pairs, and the difference matters.

- **`__memberJoin__` / `__memberLeave__`** — the **member list changed**. Someone was added to or removed from the channel.
- **`__memberOnline__` / `__memberOffline__`** — a **socket for an existing member** connected or dropped. The member list did not change.

Why two pairs? On a persistent channel a member can be "in" the channel while temporarily disconnected. Their socket dropping does not remove them from the roster — they will be auto-rejoined on reconnect — so it fires `__memberOffline__`, not `__memberLeave__`. When they reconnect, the roster is unchanged, so it fires `__memberOnline__`, not `__memberJoin__`.

Put plainly:

| Event | Means | Member list |
|---|---|---|
| `__memberJoin__` | A new member joined for the first time | grew |
| `__memberLeave__` | A member truly left (unsubscribe, kick, `removeMember`) | shrank |
| `__memberOnline__` | An existing member's socket connected (or rejoined) | unchanged |
| `__memberOffline__` | An existing member's socket dropped | unchanged |

A concrete walk-through on a persistent channel:

::steps{level="3"}

### First subscribe

Alice joins `room:general`. Peers get `__memberJoin__` then `__memberOnline__` — she is both a new member and now online.

### Network blip

Alice's connection drops. She keeps her seat (persistent), so peers get only `__memberOffline__`. The roster still lists Alice.

### Reconnect

Alice's socket comes back and is auto-rejoined. The roster did not change, so peers get only `__memberOnline__` — no second `__memberJoin__`.

### True leave

Alice sends `__unsubscribe__` (or is kicked). Now she really leaves, so peers get `__memberLeave__` then `__memberOffline__`.

::

On an **ephemeral** channel (no persistence, or `persistent: false`) there is no "online but not joined" state — a disconnect is a true leave, so it fires `__memberLeave__`. The `__memberOnline__`/`__memberOffline__` distinction only earns its keep on persistent channels.

### Presence payloads

`__memberJoin__`, `__memberLeave__`, and `__memberOnline__` each carry `{ connectionId, meta }` — the connection's id and the metadata your upgrade hook set. `__memberOffline__` carries `{ connectionId }` only. Every presence frame is tagged with the channel it belongs to (and the family key for a family channel), so a client subscribed to several channels can tell them apart.

::note
A new member also receives a one-time member sync right after its subscribe is confirmed — the current roster, so it starts with the full list instead of rebuilding it from join frames. The join/online frames keep that list current from then on.
::
