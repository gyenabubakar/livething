A WebSocket can die without either side noticing — a phone goes through a tunnel, a laptop sleeps, a router drops the link. The socket stays "open" in code while no bytes flow. **keepalive** catches this. The server sends a `ping` on a timer, a live client answers `pong`, and any connection that stops answering is closed.

## How it works

Two timers run per connection:

1. **The ping timer.** Every `pingIntervalMs`, the server sends a `ping` frame. A live client answers `pong` automatically — you write no code for this.
2. **The idle timer.** Every inbound frame resets it. That includes app messages *and* the automatic `pong`. If `idleTimeoutMs` passes with nothing inbound, the engine closes the socket with the `IDLE` close code (`4004`).

The ping exists so a quiet-but-alive client still produces a frame in time. A client that has truly gone away sends nothing — not even a pong — so its idle window elapses and it gets closed.

keepalive adds nothing to the client contract. It runs at the transport layer; `InferClient` is unchanged.

## Enable it

Import `keepalive` from `@wskit/server/keepalive` and list it in `capabilities`. Both options are required — there are no defaults.

```typescript [server/socket.ts]
import { define, t } from '@wskit/server'
import { keepalive } from '@wskit/server/keepalive'

const base = define({
  env: t<Env>(),
  capabilities: [
    keepalive({ pingIntervalMs: 30_000, idleTimeoutMs: 60_000 }),
  ],
})
```

This pings every 30 seconds and closes any connection that sends nothing for 60 seconds.

## Configuration

| Option | Type | Required | Default | What it is |
|---|---|---|---|---|
| `pingIntervalMs` | `number` | yes | none | How often the server sends a `ping`, in milliseconds |
| `idleTimeoutMs` | `number` | yes | none | How long a connection may go with no inbound frame before it is closed, in milliseconds |

Both must be positive integers. And `pingIntervalMs` must be **strictly less than** `idleTimeoutMs`.

::warning
**`pingIntervalMs` must be less than `idleTimeoutMs`.** The ping has to land — and the pong come back — before the idle window closes. If the interval is greater than or equal to the timeout, the build throws a clear error, because a quiet-but-alive client would be dropped before it ever got a ping to answer. Leave headroom: a 1-second ping against a 2-second timeout gives the pong a full second of margin.
::

```typescript [server/socket.ts]
// Throws at build: 60_000 is not less than 60_000.
keepalive({ pingIntervalMs: 60_000, idleTimeoutMs: 60_000 })
```

## What it adds to the context

With keepalive listed, the round-trip time of each ping/pong is measured and surfaced on the handler context:

- `ctx.latency` — the most recent measured round-trip, in milliseconds.
- `ctx.quality` — a coarse rating derived from latency.

```typescript [server/handlers.ts]
const handlePing = base.on('check-health', {
  run(ctx) {
    ctx.send('health', {
      latencyMs: ctx.latency,
      quality: ctx.quality,
    })
  },
})
```

::note
`ctx.quality` is `null` when hibernation is enabled, or before any latency has been measured. Both `ctx.latency` and `ctx.quality` are capability-gated — they only exist on the context when `keepalive()` is listed. See [capability-gated context fields](/server/context-and-storage/capability-gated-ctx).
::
