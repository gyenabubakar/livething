You author a plugin with a **scoped builder**: `define({ scoped: true })`. It looks and feels like a top-level `define` — same `base.on`, `base.request`, `base.channel`, same `ctx` — but it builds one **slice** of a server rather than the whole thing. You assemble that slice and wrap it with `plugin(...)`, and the result drops into any host.

## What a scoped define is for

A normal `define` produces the whole server. A scoped `define` produces one **slice** of a server, packaged so it can be dropped into any host. The plugin gets its own events, handlers, channels, and storage, all kept under its own namespace so it never collides with the host or with another plugin.

You author the slice with the scoped builder, assemble it, and hand the result to `plugin(...)`:

```typescript [presence.ts]
import { define, emits, t } from '@wskit/server'
import { plugin } from '@wskit/server/plugin'
import * as v from 'valibot'

// 1. a scoped builder — no env, just this plugin's own capabilities
const h = define({
  scoped: true,
  capabilities: [emits({ 'user-online': t<{ id: string }>() })],
})

// 2. handlers, exactly like a top-level server
const heartbeat = h.on('heartbeat', {
  input: v.object({}),
  run(ctx) {
    ctx.send('user-online', { id: ctx.id })
  },
})

// 3. assemble the handlers plus the api, then wrap with plugin(...)
const handler = h.assemble({
  handlers: [heartbeat],
  api(ctx) {
    return {
      ping() {
        ctx.send('user-online', { id: ctx.id })
      },
    }
  },
})

export const Presence = plugin('acme:presence', { handler })
```

The host then lists `Presence()` like any other capability:

```typescript [host.ts]
import { define, t } from '@wskit/server'
import { Presence } from './presence'

const base = define({
  env: t<Env>(),
  capabilities: [Presence()], // the plugin plugs in here
})
```

## How it differs from a top-level define

A scoped builder is the same builder type, but its config is smaller and a few rules are tighter.

|                                | Top-level `define`   | Scoped `define({ scoped: true })`                                                                       |
| ------------------------------ | -------------------- | ------------------------------------------------------------------------------------------------------- |
| `scoped` field                 | absent (or `false`)  | **`true`** — required                                                                                   |
| `env` field                    | required             | **not allowed** — the plugin inherits the host's env                                                    |
| `capabilities`                 | any capability       | only **plugin-safe** capabilities (no host-owned engines — see [dependsOn](/server/plugins/depends-on)) |
| `upgrade`                      | the app's auth gate  | a scoped gate that runs before the app's (see below)                                                    |
| transport, env, global engines | owned by this server | inherited from the host                                                                                 |

The key idea: a plugin does not own the platform. It has no `env` of its own, it does not own the transport, and it cannot own the global engines. It declares only its own namespaced slice and borrows the rest from the host.

### No `env`

A scoped config has no `env` field. The plugin's handlers still see `ctx.env` — it is the **host's** env, passed through. So a plugin reads the same bindings the host has, without re-declaring them.

```typescript [no-env.ts]
const h = define({
  scoped: true,
  // no env: t<...>() here — the plugin uses the host's env
  capabilities: [emits({ tick: t<{ n: number }>() })],
})
```

A plugin can list its own behavior capabilities — `requests`, `channels`, the stream kinds, `emits`, `errors`, `tags`, `intercepts`. What it **can't** list are the host-owned engines (`dedup`, `sequence`, `persistence`, and friends); those it depends on instead. See [dependsOn](/server/plugins/depends-on).

## Hooks a plugin can register

The scoped builder exposes the same lifecycle hooks and shared hooks (the ones that run around every handler) a top-level server has, scoped to the plugin. A plugin can register `onInit` (server startup), `onConnect` / `onDisconnect` (per connection), `onPing` / `onPong` (heartbeat frames), `onShutdown` (server stop), `onError` and `onValidationError` (its own failures), and — with the `intercepts()` capability — `intercept` (inbound) and `onOutgoing` (outbound). Use them to set up the plugin's own storage, track its own state, or filter its own frames.

```typescript [hooks.ts]
const h = define({
  scoped: true,
  capabilities: [intercepts(), emits({ tick: t<{ n: number }>() })],
})

h.onInit((ctx) => {
  ctx.sql.exec('CREATE TABLE IF NOT EXISTS ticks (n INTEGER)') // plugin's own table
})

h.onConnect((ctx) => {
  ctx.log.info('plugin saw a connection', { id: ctx.id })
})

h.intercept((ctx, frame) => {
  // by default this sees only the plugin's own frames — see Observing host traffic
})

h.onError((ctx, error, event) => {
  ctx.log.error('plugin handler failed', { event }) // only the plugin's own failures
})
```

A plugin's hooks are nested around the app's, in this order: plugin `onInit`/`onConnect` run before the app's, plugin `onDisconnect`/`onShutdown` after (shutdown is LIFO — the app runs first, then plugins in reverse registration order). A plugin's `onError`/`onValidationError` run before the app's. By default a plugin's `intercept`/`onOutgoing` see only the plugin's own frames — widening that needs an explicit grant. See [Observing host traffic](/server/plugins/observe-host) and the [pipeline execution order](/server/under-the-hood/pipeline-execution-order).

## The scoped `upgrade`

A plugin may supply its own `upgrade` in the scoped config. It is the plugin's chance to inspect the handshake and contribute to the connection — for example to read a header the plugin cares about.

```typescript [scoped-upgrade.ts]
const h = define({
  scoped: true,
  upgrade(request) {
    const region = request.headers.get('cf-ipcountry') ?? 'unknown'
    return { meta: { region } } // merged into the connection's meta
  },
  capabilities: [emits({ located: t<{ region: string }>() })],
})
```

A scoped `upgrade` differs from the app's in a few specific ways:

- **It runs first.** In the inbound order, every plugin's `upgrade` runs before the app's `upgrade`.
- **It sees only the raw request.** It does not see the app's `identity` or `meta` — it runs before those are decided.
- **Its `meta` is merged.** The plugin's returned `meta` is shallow-merged into the connection's metadata. On a key conflict, the **app wins**.
- **Its `tags` are concatenated.** Tags from the plugin and the app stack rather than overwrite.
- **Only one upgrade may own `identity`.** A plugin _may_ return `identity` — but only one upgrade hook across the whole server (the app's, or one plugin's) is allowed to. Two that return it is an error.
- **It can veto.** Throwing `RejectUpgrade(code, reason)` from a scoped `upgrade` rejects the whole handshake, exactly as the app's gate does. (See [Environment and upgrade](/server/define/env-and-upgrade) for how the reject code is answered.)

## Assembling a scoped builder

A scoped builder's `assemble` works the same way — collect the handler values — and the result is a scoped handler ready for `plugin(...)`. You never run a scoped definition directly through an adapter; it goes through `plugin(...)` and into a host.

```typescript [assemble.ts]
const heartbeat = h.on('heartbeat', {
  input: v.object({}),
  run(ctx) {
    ctx.send('user-online', { id: ctx.id })
  },
})

export const Presence = plugin('acme:presence', {
  handler: h.assemble({ handlers: [heartbeat] }), // a scoped handler, not a runnable server
})
```

The id must match `/^[a-z0-9-]+:[a-z0-9-]+$/` — lowercase letters, digits, and hyphens on each side of a single colon. A malformed id (uppercase, missing colon, empty half) throws the moment `plugin(...)` is called, not later at assemble.

## The plugin manifest

`plugin(id, manifest)` takes the assembled scoped handler plus a small manifest object. This is the whole shape:

::field-group
::field{name="handler" type="ScopedHandler"}
Required. The result of `h.assemble(...)` on a scoped builder. `plugin(...)` throws if it was not built with `define({ scoped: true })`. Any `api` the host reaches with `ctx.plugin(id)` is authored on that `assemble`, not here — see [Scoped context and API](/server/plugins/scoped-ctx).
::
::field{name="dependsOn" type="HostCapabilityFactory[]"}
Optional. Host-owned capability factories (`persistence`, `dedup`, `sequence`, `keepalive`, `rateLimit`, the `replay` family) the host must list. See [dependsOn](/server/plugins/depends-on).
::
::field{name="observesHostTraffic" type="boolean"}
Optional, defaults to `false`. Opts the plugin's `intercept` / `onOutgoing` hooks into seeing the host app's frames too. When `true`, the host must list the plugin wrapped in `observeHost(...)`. See [Observing host traffic](/server/plugins/observe-host).
::
::
