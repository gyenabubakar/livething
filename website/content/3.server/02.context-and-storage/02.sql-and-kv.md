Your server gets two durable stores on `ctx`, both backed by the adapter's storage and both surviving restarts and hibernation:

- **`ctx.sql`** — a SQLite database for relational data: tables, queries, transactions.
- **`ctx.kv`** — a simple key-value store for lightweight state: flags, counters, small caches.

Both are available on the connection context and on the init, scheduled, and shutdown contexts. Both are bound lazily — reading `ctx.sql` or `ctx.kv` never throws by itself; the check happens the moment you call a method on them, and it throws there if the adapter provides no storage.

## When to use which

| Use `ctx.sql` when…                                  | Use `ctx.kv` when…                              |
| ---------------------------------------------------- | ----------------------------------------------- |
| You have rows with fields and you query across them. | You have one value behind one key.              |
| You need ordering, filtering, joins, or counts.      | You want a quick flag, counter, or cache entry. |
| You need a multi-step write to be atomic.            | You want a value to expire on its own (TTL).    |

A rough rule: if you would write a `WHERE` or `ORDER BY`, reach for `ctx.sql`. If you would write `get(key)` / `set(key, value)`, reach for `ctx.kv`.

## `ctx.sql`

### Running a query

`ctx.sql.exec(query, ...params)` runs one statement. Bind values with positional `?` placeholders — pass them as extra arguments, never by string-building the SQL. This keeps queries injection-safe.

```typescript [insert.ts]
base.on('save-note', {
  input: v.object({ title: v.string(), body: v.string() }),
  run(ctx, input) {
    ctx.sql.exec(
      'INSERT INTO notes (title, body) VALUES (?, ?)',
      input.title,
      input.body,
    )
  },
})
```

### Reading rows

`exec(...)` returns a result cursor. Call exactly **one** reader on it:

| Reader       | Returns                            | Use when                             |
| ------------ | ---------------------------------- | ------------------------------------ |
| `.toArray()` | every matching row as objects      | you expect zero or more rows         |
| `.one()`     | the single matching row, or `null` | you expect at most one row           |
| `.raw()`     | every row as a plain column array  | you want column arrays, no key names |

Pass a generic row type so the rows are typed. The generic is a TypeScript hint only — WSKit does not validate rows at runtime.

```typescript [read.ts]
base.on('get-notes', {
  input: v.object({}),
  run(ctx) {
    const notes = ctx.sql
      .exec<{
        id: number
        title: string
        body: string
      }>('SELECT id, title, body FROM notes ORDER BY id DESC')
      .toArray()
    // notes is typed Array<{ id: number; title: string; body: string }>
    ctx.send('notes-list', { notes })
  },
})
```

`.one()` returns `null` when nothing matched, and **throws** when more than one row matched — it is for single-row reads. If a query can match many rows and you want the first, add `LIMIT 1` or use `.toArray()[0]` instead.

```typescript [one.ts]
base.on('count-notes', {
  input: v.object({}),
  run(ctx) {
    const row = ctx.sql
      .exec<{ c: number }>('SELECT COUNT(*) AS c FROM notes')
      .one()
    ctx.send('count-result', { count: row ? Number(row.c) : 0 })
  },
})
```

`.raw()` skips key names and hands back column arrays — useful when you only care about positions or are shipping rows straight over the wire:

```typescript [raw.ts]
base.on('dump-notes', {
  input: v.object({}),
  run(ctx) {
    const rows = ctx.sql
      .exec('SELECT id, title FROM notes ORDER BY id DESC')
      .raw()
    ctx.send('dump-result', { rows: rows as unknown[][] })
  },
})
```

::warning
A result cursor is **one-shot** — you may call exactly one reader on it. Calling a second reader on the same result throws. If you need the rows twice, store the first reader's output in a variable.

```typescript [reuse.ts]
const result = ctx.sql.exec<{ c: number }>('SELECT COUNT(*) AS c FROM notes')
result.one()
result.toArray() // throws — the cursor was already read
```

::

### Transactions

`ctx.sql.transaction(fn)` runs several queries as one atomic unit. It **commits** when the callback returns and **rolls back** if the callback throws — and rethrows that error to you. Use it whenever a multi-step write must be all-or-nothing.

```typescript [transfer.ts]
base.on('transfer', {
  input: v.object({ from: v.string(), to: v.string(), amount: v.number() }),
  run(ctx, input) {
    ctx.sql.transaction((tx) => {
      tx.exec(
        'UPDATE wallets SET balance = balance - ? WHERE id = ?',
        input.amount,
        input.from,
      )
      tx.exec(
        'UPDATE wallets SET balance = balance + ? WHERE id = ?',
        input.amount,
        input.to,
      )
    })
  },
})
```

The `tx` passed to your callback has the same `exec(...)` as `ctx.sql`. If anything inside throws, neither write lands:

```typescript [rollback.ts]
base.on('try-transfer', {
  input: v.object({}),
  run(ctx) {
    try {
      ctx.sql.transaction((tx) => {
        tx.exec('INSERT INTO notes (title, body) VALUES (?, ?)', 'pending', 'x')
        throw new Error('changed my mind') // rolls back the INSERT above
      })
    } catch {
      // The transaction rethrows after rolling back — the row is gone.
    }
  },
})
```

### Creating tables once

Run table creation in the init hook so it happens once at startup, before any connection. The init context has `ctx.sql` too.

```typescript [init.ts]
base.init((ctx) => {
  ctx.sql.exec(`
    CREATE TABLE IF NOT EXISTS notes (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      title TEXT NOT NULL,
      body TEXT NOT NULL
    )
  `)
})
```

See [Lifecycle hooks](/server/lifecycle-and-intercept/hooks) for the init hook.

## Reserved WSKit tables

Every table WSKit itself creates is named with the reserved `__wskit_` prefix — `__wskit_replay`, `__wskit_scheduled`, and so on. **Never create your own table (or index) under that prefix**, whether or not you are using the capability behind it yet.

::caution
`CREATE TABLE IF NOT EXISTS` only complains when a real conflict occurs — it never checks that an existing table's columns match what it's about to declare. So if you hand-create a table named, say, `__wskit_replay` before you add `replay()` to your capabilities, nothing fails at that point. Add `replay()` later, and its own `CREATE TABLE IF NOT EXISTS __wskit_replay ...` finds a table with that name already there and does nothing — you get **no** "table already exists" error to point at the mistake. Replay then reads and writes through your table's columns instead of its own, and the failures show up later as confusing SQL errors (or silently wrong reads, if a column name happens to match by accident) instead of at boot, where you could actually see the cause.
::

Unlike `ctx.kv` (below), `ctx.sql` has **no runtime guard** against a reserved table name — nothing stops the collision at the call site. Keeping clear of `__wskit_` is a convention you have to hold yourself; WSKit does not enforce it for you.

The full reserved set today:

| Table                         | Purpose                                                                                         | Owned by                                                                         |
| ----------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `__wskit_meta`                | Schema-version marker the engine reads on boot to skip re-running schema-init that already ran. | Engine internal — see [Compile & boot](/server/under-the-hood/compile-and-boot). |
| `__wskit_connections`         | One row per live connection, restored on a hibernation wake.                                    | [Hibernation](/server/define/hibernation)                                        |
| `__wskit_channel_memberships` | Durable record of which channels each identity belongs to.                                      | [persistence](/server/capabilities/persistence)                                  |
| `__wskit_tags`                | Durable (persistent) tag rows per identity.                                                     | [tags](/server/capabilities/tags)                                                |
| `__wskit_sequence`            | Next sequence number to hand out, per scope.                                                    | [sequence](/server/capabilities/sequence)                                        |
| `__wskit_scheduled`           | Queued scheduled-task runs waiting to fire.                                                     | [scheduled](/server/capabilities/scheduled)                                      |
| `__wskit_scheduled_dlq`       | Failed scheduled-task runs that exhausted their retries.                                        | [scheduled](/server/capabilities/scheduled)                                      |
| `__wskit_replay`              | Recorded outgoing messages kept for reconnect catch-up.                                         | [replay](/server/capabilities/replay)                                            |
| `__wskit_replay_watermark`    | Per-scope cursor marking how far replay history has been evicted.                               | [replay](/server/capabilities/replay)                                            |
| `__wskit_inbox`               | Held per-member rows waiting to be delivered and acknowledged.                                  | [inbox](/server/capabilities/inbox)                                              |
| `__wskit_inbox_watermark`     | Per-member cursor marking how far inbox history has been evicted.                               | [inbox](/server/capabilities/inbox)                                              |
| `__wskit_inbox_receipts`      | Per-member received/read cursors for a channel.                                                 | [inbox](/server/capabilities/inbox)                                              |
| `__wskit_last_seen`           | One row per identity: its last-seen timestamp.                                                  | [lastSeen](/server/capabilities/last-seen)                                       |
| `__wskit_streams`             | One row per durable stream (resumable or recorded).                                             | [streams](/server/capabilities/streams)                                          |
| `__wskit_stream_chunks`       | Recorded chunks for a recorded stream.                                                          | [streams](/server/capabilities/streams)                                          |
| `__wskit_stream_subscribers`  | Per-subscriber resume cursor for a broadcast stream.                                            | [streams](/server/capabilities/streams)                                          |

This list is names and purpose only — the owning capability's own page is where full column schema lives, if it publishes one. WSKit also creates a handful of `__wskit_idx_*` indexes alongside these tables; the same rule applies to index names.

## `ctx.kv`

A small async key-value store. Every method returns a `Promise`, so `await` them.

| Method                             | Returns             | What it does                                                        |
| ---------------------------------- | ------------------- | ------------------------------------------------------------------- |
| `ctx.kv.get(key)`                  | `Promise<unknown>`  | Read one value. Resolves `undefined` when the key is absent.        |
| `ctx.kv.set(key, value, options?)` | `Promise<void>`     | Write one value. Optional `{ ttl }` in milliseconds sets an expiry. |
| `ctx.kv.delete(key)`               | `Promise<void>`     | Remove one key.                                                     |
| `ctx.kv.list(prefix?)`             | `Promise<string[]>` | List keys, optionally only those starting with `prefix`.            |

```typescript [kv-basic.ts]
const handleKvSetGet = base.on('kv-set-get', {
  input: v.object({ key: v.string(), value: v.string() }),
  async run(ctx, input) {
    await ctx.kv.set(input.key, input.value)
    const value = (await ctx.kv.get(input.key)) as string | null
    ctx.send('kv-result', { key: input.key, value })
  },
})
```

::note
`ctx.kv.get(...)` resolves `unknown` — the store does not know your value's type. Narrow or cast it when you read it back, as the `as string | null` above does. This is the one genuine `unknown` boundary in the KV API.
::

::warning
KV keys starting with `__` or containing `::` are **reserved** for the plugin namespace. Passing one to any `ctx.kv` method (`get`, `set`, `delete`, `list`) throws at runtime, so keep your own keys clear of both forms.
::

### TTL — expiring values

Pass `{ ttl }` (milliseconds) to `set` to make a value expire on its own. Good for typing indicators, short locks, or rate-limit windows.

```typescript [ttl.ts]
base.on('start-typing', {
  input: v.object({}),
  async run(ctx) {
    // Auto-clears after 5 seconds even if "stop typing" never arrives.
    await ctx.kv.set(`typing:${ctx.identity}`, true, { ttl: 5_000 })
  },
})
```

A `ttl` of `0` means **no expiry**, not "expire now" — the value stays readable. But the Cloudflare adapter logs a warning when you pass `{ ttl: 0 }`, because `0` is a common mistake for "expire immediately". Omit `ttl` when you want no expiry instead of passing `0`:

```typescript [ttl-zero.ts]
await ctx.kv.set('flag', 'on') // no expiry — preferred, no warning
await ctx.kv.set('flag', 'on', { ttl: 0 }) // also no expiry, but logs a warning
const value = (await ctx.kv.get('flag')) as string | null
```

::note
The warning never includes the key — keys often carry user or session IDs, so the adapter keeps them out of log output.
::

### Listing by prefix

`list(prefix)` returns only keys that start with the prefix — namespace your keys and you can scan one group:

```typescript [list.ts]
base.on('typing-list', {
  input: v.object({ room: v.string() }),
  async run(ctx, input) {
    const keys = await ctx.kv.list(`typing:${input.room}:`)
    ctx.send('typing-list-result', { keys })
  },
})
```

Calling `list()` with no prefix returns all keys in your own namespace — framework-internal keys (the plugin-namespaced ones) are filtered out, so you never see another plugin's storage.

## Storage and retention

`ctx.sql` and `ctx.kv` are always durable — restarts and hibernation do not wipe them. What capabilities like persistence add on top is automatic durability for **framework-managed** state (channel membership, replay history — kept in the [reserved `__wskit_` tables](#reserved-wskit-tables) above) and retention policies for it. That is a separate concern from your own rows and keys here; see the [Persistence](/server/capabilities/persistence) page for how the framework persists its own state and how retention is configured.
