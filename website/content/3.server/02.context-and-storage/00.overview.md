Every handler you register gets one argument first: `ctx`. It is the **connection context** — the surface you use to send to the client, read who is connected, log, reach storage, and address other sockets. This chapter walks the whole surface, then storage and connection addressing in depth.

```typescript [chat.ts]
base.on('send', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.send('message', { text: input.text, from: ctx.meta.username })
    ctx.broadcast('message', { text: input.text, from: ctx.meta.username })
  },
})
```

`ctx` is the first parameter; the validated `input` is the second.

## `ctx` is scoped to one connection

Inside a connection handler, `ctx` is bound to the socket that sent the message. `ctx.id` is that socket's ID, `ctx.send(...)` goes back to that socket, and `ctx.meta` is the metadata you returned for it during the upgrade step. The same handler runs for every connection, but each run gets its own `ctx`.

```typescript [whoami.ts]
base.on('who-am-i', {
  input: v.object({}),
  run(ctx) {
    ctx.send('who-am-i-result', { connectionId: ctx.id })
  },
})
```

## The shape changes two ways

`ctx` is not one fixed type. What it carries depends on **two** things:

1. **Which capabilities you listed** in `define({ capabilities: [...] })`. Each capability that needs a connection-level surface adds its own field — `tags()` adds `ctx.tags`, `channels()` adds `ctx.channels`, `keepalive()` adds `ctx.latency` and `ctx.quality`, `scheduled({...})` adds `ctx.schedule` and `ctx.cancelScheduled`, `requests()` adds `ctx.request` and `ctx.broadcastRequest`, a replay capability adds `ctx.sendReplay`, and so on. Without the capability, the field is **not on the type at all** — reading it is a compile error, not a runtime `undefined`.

2. **Which handler type you are in.** A connection handler gets the full connection surface. A channel handler adds `ctx.channel`. Lifecycle hooks that run with no live socket (init, scheduled tasks, shutdown) get a trimmed surface with no per-connection `send`.

## Context shapes by handler type

This is the map of which `ctx` you get where. The pages above cover the connection handler in full; this table is the quick reference for the other handler types.

| Handler | What `ctx` carries |
|---|---|
| Connection handler (`on`, `request`, `stream`) | The full connection surface — core fields plus every listed capability's fields. |
| Channel handler | The same, plus `ctx.channel` — `send`, `broadcast`, `members`, `subscribe`, `kick`, and `removeMember` scoped to the current channel. |
| Init hook (`base.init`) | Storage (`sql`, `kv`), `env`, `log`, `platform`. No connections exist yet, so no `send`, `broadcast`, or `id`. |
| Scheduled task | `broadcast`, `connection(ref)`, `getConnections()`, storage, `schedule`/`cancelScheduled`, `env`, `log`, `waitUntil`. No per-connection `send`, `id`, `meta`, or `ctx.tags` — a task is not tied to one socket. |
| Shutdown hook (`base.shutdown`) | `broadcast`, `closeAll()`, `getConnections()`, storage, `schedule`/`cancelScheduled`, `env`, `log`, `waitUntil`. No per-connection `send`. |
| Disconnect hook | The connection surface plus `ctx.closeCode` and `ctx.closeReason`. |

::note
`ctx.closeCode` and `ctx.closeReason` are typed as optional everywhere but are only filled in inside the disconnect hook. In every other handler they are `undefined`. See [Lifecycle hooks](/server/lifecycle-and-intercept/hooks) for init, shutdown, connect, and disconnect.
::

## Where state lives

`ctx` itself holds no app state between messages — each message dispatch gets a fresh `ctx`. Durable state lives in storage:

- **`ctx.sql`** — a SQLite database for relational data: rows, queries, transactions. Survives restarts and hibernation.
- **`ctx.kv`** — a simple key-value store for lightweight state: flags, counters, small caches. Also durable, with optional TTL.

For passing a value **within a single message dispatch** (from an intercept down to the handler) there is `ctx.provide` / `ctx.inject` — that is per-dispatch only and never touches durable storage. See [Provide & inject](/server/lifecycle-and-intercept/provide-inject).
