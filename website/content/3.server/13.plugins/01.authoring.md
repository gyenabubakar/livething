You write a plugin with a **scoped builder**: `server({ scope: 'plugin' })`. It works like a top-level `server`. It has the same `base.on`, `base.request` and `base.channel` methods, and its handlers get the same `ctx`. The difference is that it builds one **slice** of a server, not the whole server. You assemble that slice, wrap it with `plugin(...)`, and then any host can use it. The **host** is the app server that lists the plugin.

## What a scoped server definition is for

A normal `server` produces the whole server. A scoped `server` produces one slice of a server, packaged so that any host can add it. The plugin has its own events, handlers, channels and storage. LiveThing keeps all of them under the plugin's own namespace, so they never collide with the host or with another plugin.

You write the slice with the scoped builder, assemble it, and pass the result to `plugin(...)`:

```typescript [polls/polls-definition.ts]
import { emits, server, t } from '@livething/server'
import { plugin } from '@livething/server/plugins'
import * as v from 'valibot'

// 1. a scoped builder with this plugin's own capabilities
const h = server({
  scope: 'plugin',
  capabilities: [
    emits({
      'poll-updated': t<{
        pollId: string
        votes: Record<string, number>
      }>(),
    }),
  ],
})

// 2. handlers, written the same way as on a top-level server
const vote = h.on('vote', {
  input: v.object({ pollId: v.string(), option: v.string() }),
  async run(ctx, input) {
    const votes =
      ((await ctx.kv.get(`poll:${input.pollId}`)) as
        | Record<string, number>
        | undefined) ?? {}

    votes[input.option] = (votes[input.option] ?? 0) + 1
    await ctx.kv.set(`poll:${input.pollId}`, votes)
    ctx.send('poll-updated', { pollId: input.pollId, votes })
  },
})

// 3. assemble the handlers and the api, then wrap the result with plugin(...)
const pollsDefinition = h.assemble({
  handlers: [vote],
  api(ctx) {
    return {
      async results(pollId: string) {
        return (
          ((await ctx.kv.get(`poll:${pollId}`)) as
            | Record<string, number>
            | undefined) ?? {}
        )
      },
    }
  },
})

export const Polls = plugin('acme:polls', {
  definition: pollsDefinition,
})
```

The host then lists `Polls()` like any other capability. Here is a version of Huddle with the polls plugin added. Its `base` lists it, and its other capabilities are left out:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { Polls } from './polls'

const base = server({
  capabilities: [Polls()], // the plugin is added here
})
```

## How it differs from a top-level server

A scoped builder has the same builder type. Its config accepts fewer options, and a few rules are stricter.

|                           | Top-level `server`   | Scoped `server({ scope: 'plugin' })`                                                                      |
| ------------------------- | -------------------- | --------------------------------------------------------------------------------------------------------- |
| `scope` field             | absent               | **`'plugin'`**, required                                                                                  |
| `capabilities`            | any capability       | only **plugin-safe** capabilities, so no host-owned engines (see [dependsOn](/server/plugins/depends-on)) |
| `authenticate`            | the app's auth hook  | a scoped hook that runs before the app's hook (see below)                                                 |
| transport, global engines | owned by this server | come from the host                                                                                        |

A plugin does not own the platform, the transport or the global engines. It only declares its own namespaced slice. If the plugin needs a secret, a URL or a service, accept that value as an argument of a plugin factory function, and use it inside the scoped handlers.

::warning
**The host must keep the plugin's capability type.** Put `Polls()` directly in `server({ capabilities: [...] })`. If you share the list as a variable, make it an `as const` tuple:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { Polls } from './polls'

const capabilities = [Polls()] as const

const base = server({
  capabilities,
})
```

Do not widen the list to `AnyCapability[]`. With that type, TypeScript forgets which plugin is in the list, and the plugin's contract types can be lost.
::

A plugin can keep its configuration typed by taking it as an argument of a factory function:

::code-group

```typescript [polls/polls-definition.ts]
import { emits, server, t } from '@livething/server'
import { plugin } from '@livething/server/plugins'
import * as v from 'valibot'

export function pollsPlugin(config: { maxOptions: number }) {
  const h = server({
    scope: 'plugin',
    capabilities: [
      emits({ 'poll-rejected': t<{ maxOptions: number }>() }),
    ],
  })
  const createPoll = h.on('create-poll', {
    input: v.object({
      question: v.string(),
      options: v.array(v.string()),
    }),
    async run(ctx, input) {
      if (input.options.length > config.maxOptions) {
        ctx.send('poll-rejected', { maxOptions: config.maxOptions })
        return
      }

      await ctx.kv.set(
        `poll:${crypto.randomUUID()}`,
        Object.fromEntries(
          input.options.map((option) => [option, 0]),
        ),
      )
    },
  })
  return plugin('acme:polls', {
    definition: h.assemble({ handlers: [createPoll] }),
  })
}
```

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { pollsPlugin } from '../polls/polls-definition'

const base = server({
  capabilities: [
    pollsPlugin({
      maxOptions: Number(process.env.POLL_MAX_OPTIONS ?? 6),
    })(),
  ],
})
```

::

`pollsPlugin(...)` returns the plugin factory, so the host calls it twice: once with the config, and once more to create the capability. The host reads its own runtime configuration and passes the value in, as the `server/huddle-definition.ts` tab shows.

A scoped builder lists its capabilities the same way as a top-level server:

```typescript [polls/polls-slice.ts]
import { emits, server, t } from '@livething/server'

const h = server({
  scope: 'plugin',
  capabilities: [
    emits({
      'poll-updated': t<{
        pollId: string
        votes: Record<string, number>
      }>(),
    }),
  ],
})
```

A plugin can list its own behavior capabilities: `clientRequests`, `serverRequests`, `scheduled`, `channels`, the stream kinds, `emits`, `errors` and `tags`. It **can't** list the host-owned engines: `dedup`, `sequence`, `keepalive`, `lastSeen`, `rateLimit` and the `replay` family. Listing one of them is a compile error. The plugin [depends on them](/server/plugins/depends-on) instead.

## Hooks a plugin can register

A scoped builder takes the same hooks as a top-level server. They are keys in the `server({ scope: 'plugin', ... })` object, after `authenticate` and `capabilities`, and each hook runs with the plugin's scoped `ctx`. Keep `authenticate` above any hook that reads `ctx.meta`: TypeScript reads the object from top to bottom, so a hook above `authenticate` sees `ctx.meta` as `unknown`. A plugin can set:

- `onInit`: runs when the server starts.
- `onConnect` and `onDisconnect`: run for each connection.
- `onPing` and `onPong`: run for heartbeat frames.
- `onShutdown`: runs when the server stops.
- `onError`: runs for the plugin's own failures, including payloads that fail their schema. Inside it, `event` is the short name the plugin declared, not the namespaced wire name. A LiveThing protocol frame (such as `__subscribe__`) keeps its own name, because it has no plugin-owned short name to give back.
- `intercept` (inbound frames): needs no capability.
- `onOutgoing` (watches outbound sends): needs no capability, the same as on a top-level server.

Use them to set up the plugin's own storage, to track its own state, to change or drop incoming frames (`intercept`), or to watch what the server sends (`onOutgoing`).

```typescript [polls/polls-definition.ts]
import { emits, server, t } from '@livething/server'
import { Block } from '@livething/server/errors'

const h = server({
  scope: 'plugin',
  capabilities: [
    emits({
      'poll-updated': t<{
        pollId: string
        votes: Record<string, number>
      }>(),
    }),
  ],
  onInit(ctx) {
    // SQL table names are not namespaced, so use a name unique to the plugin
    ctx.sql.exec(
      'CREATE TABLE IF NOT EXISTS acme_poll_votes (poll_id TEXT, user_id TEXT, option TEXT)',
    )
  },
  intercept(ctx, frame) {
    // Anyone can see polls, but only a signed-in user can vote.
    // An anonymous connection has an empty user id.
    if (frame.event === 'vote' && ctx.user.id === '') throw Block
  },
  onError(ctx, error, event) {
    ctx.log.error('poll handler failed', { event }) // only the plugin's own failures
  },
})
```

A plugin's hooks wrap around the app's hooks, like layers:

- Plugin `onInit`, `onConnect`, `onPing` and `onPong` run before the app's hooks, in the order the host lists the plugins.
- Plugin `onDisconnect` and `onShutdown` run after the app's hooks, in reverse order. The app runs first, then the last-listed plugin, and the first-listed plugin runs last.
- A plugin's `onError` runs before the app's.
- A plugin `intercept` runs for every incoming frame. A plugin `onOutgoing` hook sees every app frame the server sends, once per send and after it went out, the same as the app's. For the plugin's own events, `frame.event` is the short name the plugin declared. See the [pipeline execution order](/server/under-the-hood/pipeline-execution-order) and the [outgoing hook](/server/lifecycle-and-intercept/outgoing).

## The scoped `authenticate`

A plugin can give its own `authenticate` function in the scoped config. The plugin uses it to inspect the connection request and to add data to the connection. For example, it can read a header that the plugin needs:

```typescript [polls/polls-slice.ts]
import { emits, server, t } from '@livething/server'

const h = server({
  scope: 'plugin',
  authenticate(request) {
    const region = request.headers.get('cf-ipcountry') ?? 'unknown'
    return { meta: { region } } // merged into the connection's meta
  },
  capabilities: [emits({ located: t<{ region: string }>() })],
})
```

A scoped `authenticate` is different from the app's `authenticate` in these ways:

- **It runs first.** Every plugin's `authenticate` runs before the app's `authenticate`, in the order the host lists the plugins.
- **It does not see the app's identity.** It does not see the app's `userId` or `meta`, because it runs before the app decides them.
- **It receives a scoped `ctx`.** Its second argument is a [`ctx`](/server/server/authenticate#the-authenticate-ctx), like the app's `authenticate` gets. Its `ctx.kv` keys are namespaced to the plugin, the same as in the plugin's handlers. Use that `ctx` argument inside `authenticate` itself. A helper in another file that `authenticate` calls can reach the same `ctx` with [`context.authenticate(h)`](/server/context-and-storage/context-anywhere), where `h` is the plugin's own `server(...)` result from the example above. Give that helper an explicit return type, or TypeScript reports a circular type.
- **Its `meta` is merged.** LiveThing shallow-merges the plugin's returned `meta` into the connection's metadata. When the plugin and the app return the same key, the **app's value wins**.
- **Its `tags` are added together.** The tags from the plugin and the tags from the app are joined into one list. Neither list replaces the other.
- **Only one `authenticate` may return `userId`.** A plugin _may_ return `userId`. But across the whole server, only one `authenticate` function (the app's, or one plugin's) may return it. If two of them return a `userId`, the connection fails with an error and the server rejects the connection with HTTP status 500.
- **It can reject the connection.** Throwing `RejectAuth(code, reason)` from a scoped `authenticate` [rejects the whole connection](/server/server/authenticate), the same way as in the app's hook.

## Assembling a scoped builder

A scoped builder's `assemble` works the same way as on a top-level server. You pass it the routed handler values: the ones from `h.on`, `h.request`, `h.scheduled`, `h.binary.upload` (with `binary()` and [`uploads()`](/server/binary/uploads#uploads-in-a-plugin) listed) and the like, and the plugin's channels. Hooks are not passed here. They are keys in `server({ scope: 'plugin', ... })`, and in a channel's config. A scheduled task the plugin declares must have its handler in the list, or `assemble()` reports an error. The result is a scoped server definition, ready for `plugin(...)`. You never run a scoped server definition with an adapter. It always goes through `plugin(...)` and into a host.

```typescript [polls/index.ts]
import { plugin } from '@livething/server/plugins'
import { h, vote } from './polls-slice'

export const Polls = plugin('acme:polls', {
  definition: h.assemble({ handlers: [vote] }), // a scoped server definition, not a runnable server
})
```

A plugin with a scheduled task and a channel passes both. The scheduled handler is a value from `h.scheduled`. The channel's hooks sit in its config, and passing the channel itself turns them on:

```typescript [polls/closing-polls.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { plugin } from '@livething/server/plugins'
import { scheduled } from '@livething/server/scheduled'

const h = server({
  scope: 'plugin',
  capabilities: [
    channels(),
    scheduled({ 'close-poll': { data: t<{ pollId: string }>() } }),
  ],
})

const poll = h.channel(['polls', 'poll:{pollId}'], {
  capabilities: [emits({ 'poll-finished': t<{ pollId: string }>() })],
  onSubscribe(ctx) {
    ctx.log.info('joined poll', { pollId: ctx.channel.params.pollId })
  },
})

const handleClosePoll = h.scheduled('close-poll', {
  async run(ctx, data) {
    await ctx.kv.set(`poll-finished:${data.pollId}`, true)
  },
})

export const ClosingPolls = plugin('acme:closing-polls', {
  definition: h.assemble({ handlers: [handleClosePoll, poll] }),
})
```

The plugin ID must match `/^[a-z0-9-]+:[a-z0-9-]+$/`. That means lowercase letters, digits and hyphens on each side of a single colon. A wrong ID (with uppercase letters, with no colon, or with an empty side) throws an error as soon as you call `plugin(...)`. It does not wait until `assemble`.

## The plugin manifest

`plugin(id, manifest)` takes the plugin ID and a small manifest object. The manifest holds the assembled scoped server definition and, if needed, the plugin's dependencies. This is the whole shape:

::field-group
::field{name="definition" type="ServerDefinition"}
Required. The result of `h.assemble(...)` on a scoped builder. `plugin(...)` throws an error if the definition was not built with `server({ scope: 'plugin' })`. You write the [`api`](/server/plugins/scoped-ctx) that the host reaches with `ctx.plugin(id)` in that `assemble` call, not in the manifest.
::
::field{name="dependsOn" type="HostCapabilityFactory[]"}
Optional. Factories of [host-owned capabilities](/server/plugins/depends-on) (`dedup`, `sequence`, `keepalive`, `lastSeen`, `rateLimit`, the `replay` family) that the host must list.
::
::
