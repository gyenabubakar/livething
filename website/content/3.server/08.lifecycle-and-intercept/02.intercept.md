`intercept` is one hook that runs for **every incoming frame**. It runs before schema validation and before the handler. Use it for inbound work that applies to all traffic: audit logging, message counts, cleaning up payloads, auth checks, or dropping unwanted messages. An intercept can read a frame, replace its payload, or stop it.

`intercept` is a key of `server({ ... })`, and a key of a channel's config. It needs no capability. Intercepts run only on the server, so they add nothing to the client contract, and `InferClient` stays the same. Write it after `upgrade` and `capabilities`, so that `ctx.meta` has its type.

```typescript [server/base.ts]
import { server } from '@livething/server'

const base = server({
  intercept(ctx, frame) {
    ctx.log.info('incoming', {
      event: frame.event,
      kind: frame.kind,
    })
  },
})
```

## Use it

Imagine a moderator can mute a user for a while. A muted user can still read, but the server drops the messages they send. Huddle's definition has no `mutes` table, so this example adds one. In Huddle, `send-message` is an event of the `rooms` and `dms` channels. A top-level intercept also sees channel frames, with the same event name. The intercept checks the `mutes` table before the `send-message` handler runs:

```typescript [server/base.ts]
import { server } from '@livething/server'
import { Block } from '@livething/server/errors'

const base = server({
  onInit(ctx) {
    ctx.sql.exec(
      'CREATE TABLE IF NOT EXISTS mutes (user_id TEXT NOT NULL, until INTEGER NOT NULL)',
    )
  },
  intercept(ctx, frame) {
    if (frame.event !== 'send-message') return

    const mute = ctx.sql
      .exec<{
        until: number
      }>(
        'SELECT until FROM mutes WHERE user_id = ? AND until > ? LIMIT 1',
        ctx.user.id,
        Date.now(),
      )
      .one()
    if (mute) throw Block
  },
})
```

`throw Block` drops the frame, so the handler never runs and the client gets no reply. Every other frame passes through unchanged, because the intercept returns nothing. The query ends with `LIMIT 1` because `.one()` throws when more than one row matches.

The examples below show only the `intercept` key of `server({ ... })`. If an intercept gets long, move it to [its own file](/server/lifecycle-and-intercept/hooks#hooks-in-another-file) and read the `ctx` with `context.connection(base)`.

## The frame

The hook receives `(ctx, frame)`. `frame` is a read-only view of the message as it arrives:

::field-group
::field{name="event" type="string"}
The event name exactly as the client sent it.
::
::field{name="payload" type="unknown"}
The raw payload. It is not validated yet. Check `frame.event` and `frame.kind` first, then read it (see [Reading the payload](#reading-the-payload)).
::
::field{name="kind" type="'incoming' | 'request' | 'stream' | 'upload' | 'nudge' | 'unknown'"}
The type of handler this event goes to: `'incoming'` for an `on` handler, `'request'` for a request handler, `'stream'` for the start of any stream, `'upload'` for the start of an [upload](/server/binary/uploads), and `'nudge'` for a nudge sent into a running stream. The pieces of an upload never reach an intercept: the upload's window limits how fast they come. It is `'unknown'` when no handler matches the event.
::
::field{name="routing" type="InterceptRouting"}
The routing fields the client sent with this frame: `messageId`, `correlationId`, `streamId`, `channel`, `channelFamily`, `deliverySeq`, `streamSeq`. Each field is present only when the frame carries it. `channelFamily` is `null` for a static channel. All fields are read-only.
::
::field{name="owner" type="FrameOwner"}
[Who owns the event](#plugins-and-frame-ownership): your app (`{ kind: 'app' }`) or a plugin (`{ kind: 'plugin', id }`).
::
::field{name="size" type="number"}
The size of the whole frame as it arrived, in bytes. For a text frame, this is its UTF-8 length. For a binary frame, it is the length of the whole message: the header, the info and the bytes. It stays the same when an intercept changes the payload.
::
::field{name="bytes" type="Uint8Array | undefined"}
The bytes of a [binary message](/server/binary/overview), or `undefined` for a text frame. For a binary message, `frame.payload` is its info. `frame.kind` still names the type of handler, not the kind of frame.
::
::

The event name and the routing are **locked**. An intercept cannot send a frame to a different handler. It can change only the payload. For a binary message, a returned value replaces the info, and the bytes stay as they arrived: an intercept can read them, but it cannot replace them.

An intercept sees a binary message only after the server checked that the frame kind matches the handler. So a binary frame for a JSON handler, a text frame for a binary handler, and a binary nudge never reach it: they get `wrong-frame-kind`. `ctx.matches` checks the frame kind too, so a binary handler's key matches only a binary frame.

```typescript [server/base.ts]
import { server } from '@livething/server'

const base = server({
  intercept(ctx, frame) {
    if (frame.kind === 'request') {
      ctx.log.info('request in', { event: frame.event })
    }

    if (frame.kind === 'stream') {
      ctx.log.info('stream start', { event: frame.event })
    }

    if (frame.kind === 'unknown') {
      ctx.log.warn('no handler for', { event: frame.event })
    }
  },
})
```

## Inspect, rewrite, or pass through

The return value decides what happens to the payload:

- **Return nothing** (`void` or `undefined`): the frame passes through unchanged.
- **Return a value**: that value **replaces** `frame.payload` for any intercept that runs after this one (such as a channel intercept) and for the handler.

The returned value becomes the payload exactly as it is. If it is an object with its own `event` or `routing` fields, those fields are only payload data. They do not change where the frame goes.

```typescript [server/base.ts]
import { server } from '@livething/server'

const base = server({
  intercept(ctx, frame) {
    if (frame.kind === 'incoming' && frame.event === 'send-message') {
      const p = frame.payload as { text: string }

      // Remove extra spaces before validation and before the handler.
      return { ...p, text: p.text.trim() }
    }
    // Every other frame passes through unchanged.
  },
})
```

The rewrite happens **before** validation. So the handler's schema checks the value you returned, not the original payload.

## Reading the payload

`frame.payload` has the type `unknown`. An intercept runs before validation, so LiveThing has not checked the shape yet. First check `frame.event` and `frame.kind`, then read the payload.

```typescript [server/base.ts]
import { server } from '@livething/server'
import { containsProfanity, maskProfanity } from './helpers'

const base = server({
  intercept(ctx, frame) {
    if (frame.kind === 'incoming' && frame.event === 'send-message') {
      const p = frame.payload as { text: string }

      if (containsProfanity(p.text)) {
        return { ...p, text: maskProfanity(p.text) }
      }
    }
  },
})
```

The cast (`as { text: string }`) is on purpose. The intercept runs before the schema, so the payload really is `unknown` at this point. The cast states the shape you expect.

::note
An intercept can be `async`. LiveThing waits for it to finish before the frame goes on, so an async auth check or database lookup inside an intercept works. Keep it fast: every incoming frame waits for it.
::

### `ctx.matches`: check with the validator

To run the event's declared validator inside the intercept, use `ctx.matches(key, frame)`. It returns `true` only when the frame's event, its scope (top level or a channel), and its **validated** payload all match the key. A frame whose payload fails the schema returns `false`, so it does not get through the check.

```typescript [server/base.ts]
import { server } from '@livething/server'
import { containsProfanity, maskProfanity } from './helpers'

const base = server({
  intercept(ctx, frame) {
    // Runs the validator declared for 'rename'. False if the payload is bad.
    if (ctx.matches('rename', frame)) {
      const p = frame.payload as { name: string }

      if (containsProfanity(p.name)) {
        return { ...p, name: maskProfanity(p.name) }
      }
    }
  },
})
```

`ctx.matches` throws if the key names an event that the server does not declare. So a typo in the key fails right away and is not ignored. For an event on a channel, use the key form `@<channel>::<event>`. For a channel family, use the family key in place of the channel name.

```typescript [server/base.ts]
import { server } from '@livething/server'

const base = server({
  intercept(ctx, frame) {
    // 'rooms' is the family key for the rooms channel family.
    if (ctx.matches('@rooms::send-message', frame)) {
      const p = frame.payload as { text: string }

      ctx.log.info('room message', { length: p.text.length })
    }
  },
})
```

### `ctx.unsafeCast`: no payload check

`ctx.unsafeCast(key, frame)` is the version with no runtime payload check. It checks the **key** against the events your server declares (an unknown event throws), but it does not run the payload validator. It also does not compare the key with `frame.event`. It returns the same frame, typed for that key. So check `frame.event` yourself first. Use it when your own code already knows the shape.

```typescript [server/base.ts]
import { server } from '@livething/server'

const base = server({
  intercept(ctx, frame) {
    if (frame.kind === 'incoming' && frame.event === 'rename') {
      // The log line only reads the name, so skip the validator.
      const renamed = ctx.unsafeCast('rename', frame)
      const p = renamed.payload as { name: string }

      ctx.log.info('rename requested', { name: p.name })
    }
  },
})
```

::note
`ctx.matches` and `ctx.unsafeCast` are on every connection `ctx`, not only in an intercept. At runtime they check the key against the events your server declares. After the check, read the payload with a cast, as the examples above do.
::

## Blocking and disconnecting

An intercept can stop a frame by throwing a control-flow error. A control-flow error is a special value from `@livething/server/errors` that tells LiveThing what to do with the frame:

- **`Block`**: drop the frame without a message to the client. The handler does not run and no response is sent, so a blocked request waits on the client until it times out. The socket stays open.
- **`Disconnect(code, reason)`**: close the connection with that close code and reason.

```typescript [server/base.ts]
import { server } from '@livething/server'
import {
  Block,
  CloseCodes,
  Disconnect,
} from '@livething/server/errors'
import { isMuted, isSendingTooManyFrames } from './helpers'

const base = server({
  intercept(ctx, frame) {
    // Drop frames from a muted user without telling them.
    if (isMuted(ctx.user.id)) throw Block

    // Close the connection of a client sending too many frames.
    if (isSendingTooManyFrames(ctx.user.id)) {
      throw Disconnect(CloseCodes.BANNED, 'Rate abuse')
    }
  },
})
```

You can also throw any **registered typed error** to send it to the client, the same way a handler does. The shared error model in [Core](/core/error-model) covers that path and the difference between `Block`, `Disconnect`, and a typed error. The server control-flow errors are listed in [Control-flow errors](/server/capabilities/errors).

## Channel intercepts

A channel can have its own `intercept`, a key in the channel's config. The server must list `channels()` to declare channels. A channel intercept sees only the frames sent to that channel. For those frames, LiveThing runs the **top-level** intercept first, then the **channel** one. A channel intercept only runs if you pass the channel to `assemble()`.

```typescript [server/base.ts]
import { server } from '@livething/server'
import { channels } from '@livething/server/channels'
import { Block } from '@livething/server/errors'

const base = server({ capabilities: [channels()] })

export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  intercept(ctx, frame) {
    if (frame.kind === 'incoming' && frame.event === 'send-message') {
      const p = frame.payload as { text: string }

      if (p.text === '') throw Block // drop empty messages in this room
    }
  },
})
```

Both intercepts use the same [per-frame store](/server/lifecycle-and-intercept/provide-inject). A value that the top-level intercept stores with `ctx.provide` can be read in the channel intercept.

## Which kinds an intercept sees

An intercept runs for normal events (`incoming`), `request` frames, `stream` start frames, and `nudge` frames sent into a running stream. For a nudge, the intercept runs **before** LiveThing adds the nudge to the stream's buffer. So a rewrite changes what the stream handler reads, and a `Block` drops the nudge.

```typescript [server/base.ts]
import { server } from '@livething/server'
import { Block } from '@livething/server/errors'

const base = server({
  intercept(ctx, frame) {
    // 'redirect' is a nudge on Scout's ask-scout stream: it carries a new instruction.
    if (frame.kind === 'nudge' && frame.event === 'redirect') {
      const p = frame.payload as { instruction: string }

      if (p.instruction.length > 500) throw Block

      // drop an overly long redirect
      return { ...p, instruction: p.instruction.trim() }
    }
  },
})
```

A **registered typed error** thrown from an intercept for a nudge does not end the stream. It rejects the client's `nudge()` promise, and the stream keeps running. A `Block` also drops only that one nudge. The stream ends only when the stream _handler_ itself throws.

## Plugins and frame ownership

`frame.owner` tells you if a frame belongs to your app or to an installed plugin. Both app intercepts and plugin intercepts see **every** frame.

```typescript [server/base.ts]
import { server } from '@livething/server'

const base = server({
  intercept(ctx, frame) {
    if (frame.owner.kind === 'plugin') {
      ctx.log.info('plugin frame', {
        id: frame.owner.id,
        event: frame.event,
      })
    }
  },
})
```

When your server lists plugins, the type of `frame.owner.id` is the union of the installed plugin IDs, so your editor can autocomplete the ID. [Plugins](/server/plugins/overview) explains how to write a plugin.

::note
A server has one `intercept`, and each channel can have one more. To run several pieces of inbound logic, put them all in the one intercept.
::
