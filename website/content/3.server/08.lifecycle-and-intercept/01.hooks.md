A lifecycle hook is a function that runs at a fixed moment in the life of the server or of a connection. It does not run for a named event. There are eight lifecycle hooks, and each one is a method on the `base` builder. Each hook is a singleton: a server can have only one of each. Registering the same hook twice throws an error (`Duplicate onConnect hook on this server`).

| Hook                | Runs                                                        | `ctx` shape                                               | Extra arguments                    |
| ------------------- | ----------------------------------------------------------- | --------------------------------------------------------- | ---------------------------------- |
| `onInit`            | once at server startup, before any connection               | `InitContext`: storage, log, platform, no connection      | none                               |
| `onConnect`         | each time a connection opens, after `upgrade(...)` succeeds | connection `ctx`                                          | none                               |
| `onDisconnect`      | each time a connection closes, for any reason               | connection `ctx`, with `closeCode` and `closeReason` set  | none                               |
| `onPing`            | each time a client sends a `ping`                           | connection `ctx`                                          | none                               |
| `onPong`            | each time a client sends a `pong`                           | connection `ctx`                                          | none                               |
| `onError`           | on any unhandled error from a handler                       | connection `ctx`                                          | `error: unknown`, `event?: string` |
| `onValidationError` | when an incoming payload fails its schema                   | connection `ctx`                                          | `event: string`, `error: unknown`  |
| `onShutdown`        | once when the server stops                                  | `ShutdownContext`: the whole server, no single connection | none                               |

Each hook accepts a sync or an async function. You do not pass any of them to `assemble(...)`. Calling the method on `base` is enough.

## `onInit`

Runs once while the server starts, before any client connects. Use it for one-time setup, such as creating tables, running migrations (changes to the database schema), or filling a cache.

```typescript [init.ts]
base.onInit((ctx) => {
  ctx.sql.exec(`
    CREATE TABLE IF NOT EXISTS messages (
      id    TEXT PRIMARY KEY,
      room  TEXT NOT NULL,
      text  TEXT NOT NULL,
      at    INTEGER NOT NULL
    )
  `)
})
```

Here `ctx` is an `InitContext`, not a connection context. No client is connected yet, so it has **no** `send`, `broadcast`, `meta`, or `connection`. It has these fields:

::field-group
::field{name="sql" type="SQLProvider"}
SQL access for creating tables, running migrations, and adding starting data.
::
::field{name="kv" type="KVProvider"}
Key-value storage with simple get, set, and delete.
::
::field{name="log" type="Logger"}
Structured logger.
::
::field{name="platform" type="Platform"}
The raw platform object from the adapter (the Durable Object state on Cloudflare).
::
::

```typescript [init-async.ts]
base.onInit(async (ctx) => {
  const seeded = await ctx.kv.get('seeded')
  if (!seeded) {
    ctx.sql.exec("INSERT INTO rooms (name) VALUES ('lobby')")
    await ctx.kv.set('seeded', true)
  }
})
```

::caution
LiveThing does **not** contain an error thrown from `onInit` the way it contains errors from `onDisconnect` and `onShutdown`. There is no connection yet, so the `onError` hook has nothing to run against. The error makes server startup fail, and no socket opens until `onInit` succeeds. If a failure in some setup step should not block every connection, wrap that step in its own `try`/`catch`.
::

## `onConnect`

Runs every time a connection opens. It runs after `upgrade(...)` returns the connection's `userId` and `meta`, and after LiveThing has rejoined the connection to its persistent channels. Here `ctx` is the full connection context for the socket that just opened.

```typescript [connect.ts]
base.onConnect((ctx) => {
  ctx.send('welcome', { username: ctx.meta.username })
  ctx.broadcast('user-joined', { username: ctx.meta.username })
  ctx.log.info('connected', {
    id: ctx.connection.id,
    userId: ctx.user.id,
  })
})
```

`ctx.meta` is the metadata that your `upgrade(...)` hook returned for this connection. Its type comes from that hook. `ctx.send` sends to this socket. `ctx.broadcast` sends to every other connection. The page [Upgrade](/server/server/upgrade) shows how to write the upgrade hook.

## `onDisconnect`

Runs every time a connection closes. The close can be a normal close from the client, a network drop, a kick from the server, or a server shutdown. This is the only hook where `ctx.closeCode` and `ctx.closeReason` are set.

```typescript [disconnect.ts]
base.onDisconnect((ctx) => {
  ctx.broadcast('user-left', {
    username: ctx.meta.username,
    code: ctx.closeCode ?? -1,
    reason: ctx.closeReason ?? '',
  })
})
```

`closeCode` and `closeReason` are optional in the `ctx` type, so give them a fallback value. These are common codes:

| Code   | Meaning                                                                                                 |
| ------ | ------------------------------------------------------------------------------------------------------- |
| `1000` | Normal close.                                                                                           |
| `1001` | Going away. The server sends it during shutdown.                                                        |
| `1006` | Abnormal close (a network failure, with no close frame).                                                |
| `4xxx` | Defined by the application, for example a code you passed to `Disconnect(code, reason)` to kick a user. |

The page [Close Codes](/core/close-codes) lists every close code that LiveThing uses.

::caution
In `onDisconnect`, `ctx.send(...)` does not reach the closing socket, because that socket is already closed. Use `ctx.broadcast(...)` to tell the **other** connections, or write to storage. The example above uses `ctx.broadcast(...)`.
::

## `onPing`

Runs every time a client sends a bare `ping` frame. A `ping` is a heartbeat: a small message that a client sends to check that the server is still there. It is plain text, not JSON, so it never reaches an `on(...)` handler.

**The server has already replied with `pong` before this hook runs.** LiveThing sends the reply even when you register no `onPing` hook. Use `onPing` to observe pings, not to answer them.

```typescript [on-ping.ts]
base.onPing((ctx) => {
  ctx.log.info('client sent a ping', {
    connectionId: ctx.connection.id,
  })
})
```

::warning
With Cloudflare [hibernation](/server/server/hibernation) and no [translation](/server/server/translation), `onPing` does not run. The Workers runtime answers the client's `ping` with `pong` itself and does not wake the Durable Object. With translation, LiveThing turns off this automatic reply. The frame then wakes the object so that it can go through the translator, and the translated result can reach `onPing`. The Workers runtime never answers a `pong` automatically, so `onPong` is not affected.
::

## `onPong`

Runs every time a client sends a bare `pong` frame. A client normally sends a `pong` to answer a `ping` from the **server**. On the server, only the [`keepalive()`](/server/capabilities/keepalive) capability sends pings, on a timer.

```typescript [on-pong.ts]
base.onPong((ctx) => {
  ctx.log.info('client is alive', {
    connectionId: ctx.connection.id,
  })
})
```

When `keepalive()` is in the capabilities list, it measures the round-trip time before your hook runs. So `ctx.latency` already holds the new value in your hook:

```typescript [on-pong-latency.ts]
import { server } from '@livething/server'
import { keepalive } from '@livething/server/keepalive'

const base = server({
  capabilities: [
    keepalive({ pingIntervalMs: 30_000, idleTimeoutMs: 60_000 }),
  ],
})

base.onPong((ctx) => {
  // Already updated from the pong that triggered this hook.
  ctx.log.info('round-trip', {
    ms: ctx.latency,
    quality: ctx.quality,
  })
})
```

Without `keepalive()`, `ctx.latency` does not exist on the context, and reading it is a compile error. The hook still runs if a `pong` arrives, but nothing has measured a round-trip.

::note
The order is fixed. For each `ping` and `pong`, LiveThing runs the capability hooks first (including the `keepalive()` measurement), then plugin hooks, and your `base.onPong(...)` hook last. This is why `ctx.latency` is already up to date in your hook.
::

Your own code cannot send a `ping`. A `pong` frame has no ID, so `keepalive()` can only match a `pong` to its `ping` because it is the only sender of pings. A second sender would make it time the wrong ping and report a wrong `ctx.latency`. If you want a heartbeat, add [`keepalive()`](/server/capabilities/keepalive) to the capabilities list and let it send the pings.

## `onError`

Runs on any unhandled error thrown by a handler: the body of an `on`, `request`, or `stream` handler, or an intercept. It is an observer. Use it to log errors, count them, or save the failed message for later (a dead-letter store). It does **not** change what the client receives.

```typescript [error.ts]
base.onError((ctx, error, event) => {
  ctx.log.error('handler threw', {
    event,
    message: error instanceof Error ? error.message : String(error),
  })
})
```

`event` is the name of the incoming event that caused the error, when LiveThing knows it. Otherwise it is `undefined`. `error` has the type `unknown`, so check its type before you read its fields.

`DeferExhausted` also arrives in this hook. LiveThing raises it when a message that a handler delayed with `Defer(...)` has used all its retries. See [Control-flow errors](/server/capabilities/errors) for `Defer` and `DeferExhausted`.

## `onValidationError`

Runs when an incoming payload does not match the schema declared on its handler. In that case the handler does not run. LiveThing calls this hook so that you can observe the failure, and then sends a `validation-failed` error to the client.

```typescript [validation-error.ts]
base.onValidationError((ctx, event, error) => {
  ctx.log.warn('payload rejected', {
    event,
    id: ctx.connection.id,
    error,
  })
})
```

The arguments are the connection `ctx`, the `event` name (a `string`, always known here), and the validation `error` (type `unknown`).

If you register both `onValidationError` and `onError`, a schema failure runs **both** hooks. `onValidationError` runs first, because it is the specific signal. Then `onError` runs as part of the normal error path. If both hooks write to the same log, check that you do not log the same failure twice.

## `onShutdown`

Runs once when the server is stopping. The connections that were open before shutdown can still be reached at this point, so you can send a last message or close them early. After `onShutdown` finishes, LiveThing closes every remaining connection with close code `1001` (going away) and runs `onDisconnect` for each one.

```typescript [shutdown.ts]
base.onShutdown((ctx) => {
  ctx.broadcast('server-stopping', { reason: 'maintenance' })
})
```

Here `ctx` is a `ShutdownContext`, which is a view of the whole server. It does not belong to a single connection, so it has no `send` or `meta`. It has these fields:

::field-group
::field{name="closeAll" type="(code?, reason?) => void"}
Close every open connection at once. Calling it is optional: LiveThing closes the rest after the hook.
::
::field{name="broadcast" type="(event, payload) => void"}
Send to every open connection. It is typed from your `emits(...)` events, so a wrong event name or payload is a compile error.
::
::field{name="connections / connectionCount / users" type="managers / number"}
See who is still connected. `connections.all()` returns a list of every open connection, `connectionCount` is how many there are, and `users.get(id)` reaches every socket of one user.
::
::field{name="sql / kv" type="storage"}
Last writes, for example to save buffered data or a counter.
::
::field{name="schedule / cancelScheduled" type="task control"}
Add or cancel durable scheduled work.
::
::field{name="log / platform" type="platform"}
The logger and the raw platform object. Bindings that belong to one runtime are on the platform object.
::
::

## Error isolation

After a connection exists, an error thrown from a lifecycle hook never crashes the server. What else happens depends on which hook threw:

- `onDisconnect` and `onShutdown`: LiveThing logs the error and continues. The rest of the cleanup still runs.
- `onPing`, `onPong`, and `onValidationError`: LiveThing logs the error and continues.
- `onConnect`: the error goes through the normal error path. It runs the `onError` hook and sends the client an `__error__` frame.
- `onError`: LiveThing logs the error and still finishes handling the original failure. For example, if your `onError` hook throws because your logging service is down, the client still receives its `__error__` frame, so a pending request rejects and does not wait forever.

`onInit` is the one hook that can stop the server. See the caution in the [`onInit`](#oninit) section.

```typescript [error-isolation.ts]
// Even if this observer throws, the original handler error is still
// turned into an error frame, and the client still receives it.
base.onError(() => {
  throw new Error('logging service is down')
})

// base.request(...) needs the clientRequests() capability.
const handleSendMessage = base.request('send-message', {
  input: v.object({ text: v.string() }),
  run() {
    throw new Error('database write failed') // → the client gets an internal-error reply
  },
})
```

The shared error model in [Core](/core/error-model) explains how a thrown error becomes an error frame for the client. It also explains how `Block`, `Disconnect`, and `Defer` differ from a plain throw. The server control-flow errors are in [Control-flow errors](/server/capabilities/errors).
