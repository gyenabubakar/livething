A lifecycle hook is a function that runs at a fixed moment in the life of the server or of a connection. It does not run for a named event. There are seven lifecycle hooks. Each one is a key in the object that you pass to `server({ ... })`, so a server has at most one of each.

::field-group
::field{name="onInit" type="(ctx: InitContext)"}
Runs once at server startup, before any connection. `ctx` has storage, the logger and the platform, but no connection.
::
::field{name="onConnect" type="(ctx)"}
Runs each time a connection opens, after `upgrade(...)` succeeds. `ctx` is the connection's context.
::
::field{name="onDisconnect" type="(ctx)"}
Runs each time a connection closes, for any reason. `ctx` is the connection's context, with `closeCode` and `closeReason` set.
::
::field{name="onPing" type="(ctx)"}
Runs each time a client sends a `ping`. `ctx` is the connection's context.
::
::field{name="onPong" type="(ctx)"}
Runs each time a client sends a `pong`. `ctx` is the connection's context.
::
::field{name="onError" type="(ctx, error: unknown, event?: string)"}
Runs on any unhandled error from a handler, and on every payload that fails its schema. `event` is the name of the event whose handler threw, when there is one.
::
::field{name="onShutdown" type="(ctx: ConnectionlessContext)"}
Runs once when the server stops. `ctx` is the whole server, not a single connection.
::
::

Each hook accepts a sync or an async function. You do not pass any of them to `assemble(...)`. A hook is part of the server, so LiveThing runs it as soon as the server exists.

::warning
Write `upgrade` and `capabilities` **before** the hooks. TypeScript reads the object from top to bottom. If `upgrade` takes a parameter, such as `upgrade(request)`, a hook written above it sees `ctx.meta` as `unknown`.
::

All of a server's hooks go in its one `server({ ... })` object. Each example below shows one hook inside a small `server({ ... })` of its own. A hook that is long can live in [another file](#hooks-in-another-file).

## `onInit`

Runs once while the server starts, before any client connects. Use it for one-time setup, such as creating tables, running migrations, or filling a cache.

```typescript [server/base.ts]
import { server } from '@livething/server'

const base = server({
  onInit(ctx) {
    ctx.sql.exec(`
      CREATE TABLE IF NOT EXISTS messages (
        id      TEXT PRIMARY KEY,
        room    TEXT NOT NULL,
        user_id TEXT NOT NULL,
        text    TEXT NOT NULL,
        sent_at INTEGER NOT NULL
      )
    `)
  },
})
```

Here `ctx` is an `InitContext`, not a connection context. No client is connected yet, so it has **no** `send`, `broadcast`, `meta`, or `connection`. It has these fields:

::field-group
::field{name="sql" type="SQLProvider"}
SQL access for creating tables, running migrations, and adding starting data.
::
::field{name="kv" type="KVProvider"}
Key-value storage with simple get, set, and delete.
::
::field{name="log" type="Logger"}
Structured logger.
::
::field{name="platform" type="Platform"}
The raw platform object from the adapter (on Cloudflare, `Platform<Env>`).
::
::

```typescript [server/base.ts]
import { server } from '@livething/server'

const base = server({
  async onInit(ctx) {
    ctx.sql.exec(
      'CREATE TABLE IF NOT EXISTS rooms (id TEXT PRIMARY KEY, name TEXT NOT NULL)',
    )
    const seeded = await ctx.kv.get('seeded')
    if (!seeded) {
      ctx.sql.exec(
        "INSERT INTO rooms (id, name) VALUES ('general', '#general')",
      )
      await ctx.kv.set('seeded', true)
    }
  },
})
```

::caution
LiveThing does **not** contain an error thrown from `onInit` the way it contains errors from `onDisconnect` and `onShutdown`. There is no connection yet, so the `onError` hook has nothing to run against. The error makes server startup fail, and no socket opens until `onInit` succeeds. If a failure in some setup step should not block every connection, wrap that step in its own `try`/`catch`.
::

## `onConnect`

Runs every time a connection opens. It runs after `upgrade(...)` returns the connection's `userId` and `meta`, and after LiveThing has rejoined the connection to its persistent channels. Here `ctx` is the full connection context for the socket that just opened.

```typescript [server/base.ts]
import { emits, server, t } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import { verifySession } from './auth'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user) {
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    emits({
      notification: t<{ title: string; body: string }>(),
      'status-changed': t<{
        userId: string
        status: 'active' | 'away' | 'busy'
      }>(),
    }),
  ],
  onConnect(ctx) {
    ctx.send('notification', {
      title: 'Welcome back',
      body: `Signed in as ${ctx.meta.name}`,
    })
    ctx.broadcast('status-changed', {
      userId: ctx.user.id,
      status: 'active',
    })
    ctx.log.info('connected', {
      id: ctx.connection.id,
      userId: ctx.user.id,
    })
  },
})
```

`ctx.meta` is the metadata that your `upgrade(...)` function returned for this connection. Its type comes from that function, and `onConnect` is written after `upgrade`, so the type is known. `ctx.send` sends to this socket. `ctx.broadcast` sends to every other connection. The page [Upgrade](/server/server/upgrade) shows how to write the upgrade function.

## `onDisconnect`

Runs every time a connection closes. The close can be a normal close from the client, a network drop, a kick from the server, or a server shutdown. This is the only hook where `ctx.closeCode` and `ctx.closeReason` are set.

```typescript [server/base.ts]
import { emits, server, t } from '@livething/server'

const base = server({
  capabilities: [
    emits({
      'status-changed': t<{
        userId: string
        status: 'active' | 'away' | 'busy'
      }>(),
    }),
  ],
  onDisconnect(ctx) {
    ctx.broadcast('status-changed', {
      userId: ctx.user.id,
      status: 'away',
    })
    ctx.log.info('disconnected', {
      userId: ctx.user.id,
      code: ctx.closeCode ?? -1,
      reason: ctx.closeReason ?? '',
    })
  },
})
```

`closeCode` and `closeReason` are optional in the `ctx` type, so give them a fallback value. These are common codes:

| Code   | Meaning                                                                                                 |
| ------ | ------------------------------------------------------------------------------------------------------- |
| `1000` | Normal close.                                                                                           |
| `1001` | Going away. The server sends it during shutdown.                                                        |
| `1006` | Abnormal close (a network failure, with no close frame).                                                |
| `4xxx` | Defined by the application, for example a code you passed to `Disconnect(code, reason)` to kick a user. |

The page [Close Codes](/core/close-codes) lists every close code that LiveThing uses.

::caution
In `onDisconnect`, `ctx.send(...)` does not reach the closing socket, because that socket is already closed. Use `ctx.broadcast(...)` to tell the **other** connections, or write to storage. The example above uses `ctx.broadcast(...)`.
::

## `onPing`

Runs every time a client sends a bare `ping` frame. A `ping` is a heartbeat: a small message that a client sends to check that the server is still there. It is plain text, not JSON, so it never reaches an `on(...)` handler.

**The server has already replied with `pong` before this hook runs.** LiveThing sends the reply even when you write no `onPing` hook. Use `onPing` to observe pings, not to answer them.

```typescript [server/base.ts]
import { server } from '@livething/server'

const base = server({
  onPing(ctx) {
    ctx.log.info('client sent a ping', {
      connectionId: ctx.connection.id,
    })
  },
})
```

::warning
With Cloudflare [hibernation](/server/server/hibernation), `onPing` does not run. The Workers runtime answers the client's `ping` with `pong` itself and does not wake the Durable Object. The Workers runtime never answers a `pong` automatically, so `onPong` is not affected.
::

## `onPong`

Runs every time a client sends a bare `pong` frame. A client normally sends a `pong` to answer a `ping` from the **server**. On the server, only the [`keepalive()`](/server/capabilities/keepalive) capability sends pings, on a timer.

When `keepalive()` is in the capabilities list, it measures the round-trip time before your hook runs. So `ctx.latency` already holds the new value in your hook. This smaller server lists `keepalive()`, as Huddle does:

```typescript [server/base.ts]
import { server } from '@livething/server'
import { keepalive } from '@livething/server/keepalive'

const base = server({
  capabilities: [keepalive()],
  onPong(ctx) {
    // Already updated from the pong that triggered this hook.
    ctx.log.info('round-trip', {
      ms: ctx.latency,
      quality: ctx.quality,
    })
  },
})
```

Without `keepalive()`, `ctx.latency` does not exist on the context, and reading it is a compile error. The hook still runs if a `pong` arrives, but nothing has measured a round-trip.

::note
The order is fixed. For each `ping` and `pong`, LiveThing runs the capability hooks first (including the `keepalive()` measurement), then plugin hooks, and your `onPong` hook last. This is why `ctx.latency` is already up to date in your hook.
::

Your own code cannot send a `ping`. A `pong` frame has no ID, so `keepalive()` can only match a `pong` to its `ping` because it is the only sender of pings. A second sender would make it time the wrong ping and report a wrong `ctx.latency`. If you want a heartbeat, add [`keepalive()`](/server/capabilities/keepalive) to the capabilities list and let it send the pings.

## `onError`

Runs on any unhandled error thrown by a handler: the body of an `on`, `request`, or `stream` handler, or an intercept. It is an observer. Use it to log errors, count them, or save the failed message for later (a dead-letter store). It does **not** change what the client receives.

```typescript [server/base.ts]
import { server } from '@livething/server'

const base = server({
  onError(ctx, error, event) {
    ctx.log.error('handler threw', {
      event,
      message: error instanceof Error ? error.message : String(error),
    })
  },
})
```

`event` is the name of the incoming event that caused the error, when LiveThing knows it. Otherwise it is `undefined`. `error` has the type `unknown`, so check its type before you read its fields.

`onError` also runs for errors that you declared in [`errors([...])`](/server/capabilities/errors), not only for unexpected ones. To treat them differently, check the error with `.matches(error)` first.

If you write no `onError` hook, LiveThing logs each unexpected error itself with `logger.error`, together with the event name, so the error that the client only sees as `internal-error` is not lost. A hook replaces that log, because the hook now owns the error. An error that you built with `error()` and declared in [`errors([...])`](/server/capabilities/errors) is not logged, because it is part of your contract. One built with `error()` but not declared gets a `logger.warn` instead, and the client gets `internal-error`.

### Validation failures

When an incoming payload does not match the schema declared on its handler, the handler does not run. `onError` gets a `ValidationFailed` error for every such schema failure, and then LiveThing sends a `validation-failed` error to the client. Check for it with `ValidationFailed.matches(error)`:

```typescript [server/base.ts]
import { server } from '@livething/server'
import { ValidationFailed } from '@livething/server/errors'

const base = server({
  onError(ctx, error, event) {
    if (ValidationFailed.matches(error)) {
      ctx.log.warn('payload rejected', {
        event,
        id: ctx.connection.id,
        issues: error.detail.issues,
      })
    }
  },
})
```

## `onShutdown`

Runs once when the server is stopping. The connections that were open before shutdown can still be reached at this point, so you can send a last message or close them early. After `onShutdown` finishes, LiveThing closes every remaining connection with close code `1001` (going away) and runs `onDisconnect` for each one.

```typescript [server/base.ts]
import { emits, server, t } from '@livething/server'

const base = server({
  capabilities: [
    emits({
      notification: t<{ title: string; body: string }>(),
    }),
  ],
  onShutdown(ctx) {
    ctx.broadcast('notification', {
      title: 'Huddle is restarting',
      body: 'You will reconnect in a moment.',
    })
  },
})
```

Here `ctx` is a `ConnectionlessContext`, which is a view of the whole server. Scheduled task bodies and the [admin `api`](/server/admin/context) get the same context. It does not belong to a single connection, so it has no `send` or `meta`. It has these fields:

::field-group
::field{name="closeConnections" type="(filter?, code?, reason?) => void"}
Close every open connection, or only one user's with `{ userId }`. Calling it is optional: LiveThing closes the rest after the hook.
::
::field{name="broadcast" type="(event, payload) => void"}
Send to every open connection. It is typed from your `emits(...)` events, so a wrong event name or payload is a compile error.
::
::field{name="connections / connectionCount / users" type="managers / number"}
See who is still connected. `connections.all()` returns a list of every open connection, `connectionCount` is how many there are, and `users.get(id)` reaches every socket of one user.
::
::field{name="channels" type="manager"}
`channels.get(...)` reaches one channel to broadcast to its members, list them, or kick someone. Only with [`channels()`](/server/capabilities/channels).
::
::field{name="purgeUser" type="(userId, options?) => Promise<void>"}
[Remove a user everywhere](/server/admin/context#remove-a-user-everywhere).
::
::field{name="sql / kv" type="storage"}
Last writes, for example to save buffered data or a counter.
::
::field{name="schedule / cancelScheduled" type="task control"}
Add or cancel durable scheduled work.
::
::field{name="log / platform" type="platform"}
The logger and the raw platform object. Bindings that belong to one runtime are on the platform object.
::
::

## Hooks in another file

A hook can be a function in its own file. A function that is written outside `server({ ... })` has no `base` to take its `ctx` type from, so read the context with the [`context` accessors](/server/context-and-storage/context-anywhere). Write the function with a block body, and pass it as the hook:

::code-group

```typescript [server/greet.ts]
import { context } from '@livething/server'
import { base } from './base'

export function greet() {
  const ctx = context.connection(base)
  ctx.send('notification', {
    title: 'Welcome back',
    body: `Signed in as ${ctx.meta.name}`,
  })
}
```

```typescript [server/base.ts]
import { emits, server, t } from '@livething/server'
import { verifySession } from './auth'
import { greet } from './greet'

export const base = server({
  async upgrade(request) {
    const user = await verifySession(
      new URL(request.url).searchParams.get('token'),
    )
    return { userId: user?.id, meta: { name: user?.name ?? 'guest' } }
  },
  capabilities: [
    emits({
      notification: t<{ title: string; body: string }>(),
    }),
  ],
  onConnect: greet,
})
```

::

`greet` imports `base`, and `base` imports `greet`. This is fine because `greet` only reads `base` when a connection opens, long after both files have loaded.

::caution
Use a block body (`{ ... }`) with a `const ctx = ...` line. An arrow function that returns a method call on `base` or on its channels, such as `const greet = () => context.connection(base).send('notification', { title: 'Hi', body: 'Welcome' })`, gives a circular type error: the type of `base` depends on the hook, and the type of the hook depends on `base`. The same applies to a hook written inside `server({ ... })`, such as `onConnect: (ctx) => ctx.channels.get(lobby.at({})).subscribe(ctx.connection)`. Add the braces and the error goes away.
::

## Error isolation

After a connection exists, an error thrown from a lifecycle hook never crashes the server. What else happens depends on which hook threw:

- `onDisconnect` and `onShutdown`: LiveThing logs the error and continues. The rest of the cleanup still runs.
- `onPing` and `onPong`: LiveThing logs the error and continues.
- `onConnect`: the error goes through the normal error path. It runs the `onError` hook and sends the client an `__error__` frame. The connection stays open. To refuse the connection, reject it in `upgrade` or close it yourself.
- `onError`: LiveThing logs the error and still finishes handling the original failure. For example, if your `onError` hook throws because your logging service is down, the client still receives its `__error__` frame, so a pending request rejects and does not wait forever.

`onInit` is the one hook that can stop the server. See the caution in the [`onInit`](#oninit) section.

In this example, `get-profile` always fails, to show the error path:

```typescript [server/base.ts]
import { server } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'

const base = server({
  capabilities: [clientRequests()],
  // Even if this observer throws, the original handler error is still
  // turned into an error frame, and the client still receives it.
  onError() {
    throw new Error('logging service is down')
  },
})

const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  run() {
    throw new Error('database read failed') // → the client gets an internal-error reply
  },
})

export const huddle = base.assemble({ handlers: [handleGetProfile] })
```

The shared error model in [Core](/core/error-model) explains how a thrown error becomes an error frame for the client. It also explains how `Block` and `Disconnect` differ from a plain throw. The server control-flow errors are in [Control-flow errors](/server/capabilities/errors).
