`onOutgoing` is the outbound version of [`intercept`](/server/lifecycle-and-intercept/intercept). `intercept` sees messages that come in from clients. `onOutgoing` sees the event frames your server sends to clients: `ctx.send`, `ctx.broadcast`, `ctx.channel.send`, `ctx.channel.broadcastTo`, stream chunks and server requests. It runs right before the frame is serialized (turned into JSON text). Use it for outbound work that applies to every message, such as adding a field to every message, removing private data before it is sent, or dropping a frame when a condition is true.

Some of LiveThing's own protocol frames, such as `__error__` and the frame that ends a stream, are sent directly and do not pass through this hook.

On a [translated endpoint](/server/server/translation), `translator.outbound` runs after serialization. So this hook always sees the LiveThing frame, not the other wire format.

`onOutgoing` is a plain method on `base`. It needs **no** capability. (`intercept` needs the `intercepts()` capability.)

```typescript [server/huddle.ts]
base.onOutgoing((ctx, frame) => {
  if (ctx) ctx.log.info('outgoing', { event: frame.event })
})
```

A server has one `onOutgoing` hook. If you register a second one, LiveThing throws an error.

## The frame

The handler receives `(ctx, frame)`. `frame` is an `OutgoingFrame`. It is the outbound version of an `InterceptFrame`, with fewer fields. An outgoing frame already knows where it goes, so it has no `kind` and no `routing`:

::field-group
::field{name="event" type="string"}
The event name as it will be sent to the client. It is locked: you cannot change it.
::
::field{name="payload" type="unknown"}
The payload value. Check `frame.event` first, then read the payload with a cast (see [Reading the payload](#reading-the-payload)).
::
::field{name="owner" type="FrameOwner"}
Whether the event belongs to your app (`{ kind: 'app' }`) or to a plugin (`{ kind: 'plugin', id }`).
::
::

`ctx` is the connection whose `on`, `request`, or `stream` handler, `intercept`, or `onConnect` hook is running when the frame is sent. For a plain `ctx.send(...)` inside a handler, this is the same socket that receives the frame, so `ctx` is the receiver. On a `ctx.broadcast(...)` from that code, `ctx` is the sender, not each receiver. In every other case there is no such connection, and **`ctx` is `undefined`**: a channel subscribe hook, `onDisconnect`, `onError`, a `schedule(...)` task, `onInit`, `onShutdown`, or the admin API. The type is `AppCtx | undefined`.

`ctx` is also created new for each send. Values that an `intercept` stored with `ctx.provide(...)` for the current message are not on it.

::caution
`ctx` can be `undefined`, so check it before you read any connection field. The type does not make you do this check, because `ctx` is typed as the connection context. A hook that reads `ctx.log` without the check throws on a frame that is sent with no connection in scope. `frame` is always present, so put per-message logic on `frame`, and check `ctx` before you use it.

```typescript [server/huddle.ts]
base.onOutgoing((ctx, frame) => {
  // frame is always present. ctx is undefined in a scheduled task or onShutdown.
  if (!ctx) return

  if (frame.owner.kind === 'plugin') {
    ctx.log.info('plugin event sent', { event: frame.event })
  }
})
```

::

## Inspect, rewrite, or block

The rules are the same as for `intercept`:

- **Return nothing**: the frame goes out unchanged.
- **Return a value**: the value **replaces** `frame.payload`. The event stays the same.
- **Throw `Block`**: the frame is dropped, and nothing is sent.

```typescript [server/huddle.ts]
base.onOutgoing((ctx, frame) => {
  // Add a server timestamp to every outbound payload
  const p = frame.payload as Record<string, unknown>
  return { ...p, sentAt: Date.now() }
})
```

The next example reads `process.env`, which is Node.js-specific. On another runtime, read the setting from that runtime's configuration instead.

```typescript [server/huddle.ts]
import { Block } from '@livething/server/errors'

base.onOutgoing((ctx, frame) => {
  if (frame.event === 'profile') {
    const p = frame.payload as { email?: string }
    const { email, ...safe } = p
    return safe // email never leaves the server
  }

  if (
    frame.event === 'debug-trace' &&
    process.env.NODE_ENV === 'production'
  ) {
    throw Block // drop debug frames in production
  }
})
```

After the hook returns, LiveThing checks the frame again. The payload must still be a plain object, and the event must be one your server declared with `emits(...)`. If the hook returns something that is not an object, LiveThing rejects the frame. A rewrite can change what is inside the payload, but the payload must stay an object.

::caution
`Block` does not have the same effect on every kind of send.

- **One recipient** (`ctx.send(...)`, `ctx.channel.send(...)`, `ctx.channel.broadcastTo(...)`): the `Block` is thrown out of that call, like an error thrown in a handler. Code that you wrote **after** the call in the same `run(...)` does not run.
- **Broadcast** (`ctx.broadcast(...)`, `ctx.channel.broadcast(...)`): LiveThing catches the `Block` and logs it. No member gets the message, and the rest of your handler keeps running.
- **Reply to a client request**: the reply is sent after your request handler has finished, so none of your code is skipped. The client gets no reply, and its request fails with a timeout.

So don't depend on code after a blocked `ctx.send(...)`. Put cleanup before the send, or check the condition before you call `send`.
::

::note
For `ctx.broadcast(...)` and `ctx.channel.broadcast(...)`, the hook runs **once** for the whole broadcast, not once per recipient. Every member gets the same payload. `ctx.channel.broadcastTo(...)` and a stream's broadcast chunks are different: each recipient's copy is sent separately, so the hook runs once per copy. A hook that reads a changing value (like `Date.now()`) can then give each recipient a different value.
::

## Reading the payload

`frame.payload` has the type `unknown`. Check `frame.event`, then read the payload with a cast. This is the same pattern as on the inbound `intercept`:

```typescript [server/huddle.ts]
base.onOutgoing((ctx, frame) => {
  if (frame.event === 'message') {
    const p = frame.payload as { text: string }
    return { ...p, text: p.text.trimEnd() }
  }
})
```

The `ctx.matches` and `ctx.unsafeCast` helpers work **only on inbound frames**. They take an `InterceptFrame`, not an `OutgoingFrame`, so you can't use them here. In `onOutgoing`, check `frame.event` and use a cast.

## Plugin ownership

As in an intercept, `frame.owner` tells you whether the frame belongs to your app or to a plugin. Every `onOutgoing` hook sees every outbound frame, including frames that plugins send. When your server lists plugins, the type of `frame.owner.id` is the union of the installed plugin IDs. For how to write a plugin, see [Plugins](/server/plugins/overview).

```typescript [server/huddle.ts]
base.onOutgoing((ctx, frame) => {
  if (ctx && frame.owner.kind === 'plugin') {
    ctx.log.info('plugin send', {
      id: frame.owner.id,
      event: frame.event,
    })
  }
})
```

## `base.onOutgoing` vs `emits()`

These two are easy to mix up:

- `base.onOutgoing((ctx, frame) => ...)` is the hook on this page. It runs on each outbound frame, so you can inspect or rewrite it.
- `emits({...})` is how you **declare** which server-to-client events exist (see [emits](/server/capabilities/emits)).

To declare which events the server can send, use `emits(...)`. Use this hook to process those frames as they leave the server.

::note
`onOutgoing` works like `intercept`, in the other direction. Both have the same locked event, the same "return a value to rewrite the payload" rule, the same `Block` to drop a frame, and the same `frame.owner`. The inbound side also has `kind` and `routing`. It is described in [Intercept](/server/lifecycle-and-intercept/intercept). For where both hooks run in the message pipeline, see [Pipeline execution order](/server/under-the-hood/pipeline-execution-order).
::
