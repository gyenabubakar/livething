An intercept often does work that the handler needs later. For example, it checks a token, loads a user, or works out a permission. `ctx.provide` and `ctx.inject` pass that result on to the handler. You don't need a global variable, you don't fetch the data a second time, and you don't need a type cast (`as`).

The values live in a small store that belongs to one incoming frame (one message from a client). Each time LiveThing processes an incoming frame (this is called a **dispatch**), it creates a new, empty store. When the dispatch ends, the store is gone. This page uses "message" and "frame" for the same thing.

There are three steps:

::steps

### Make a key

`localKey<T>(name?)` returns a typed key. `T` is the type of the value the key carries. The name is optional and is only used for debugging. Export the key, so the intercept and the handler import the same key.

```typescript [keys.ts]
import { localKey } from '@livething/server'

export const AuthKey = localKey<{
  userId: string
  role: string
}>('auth')
```

### Provide in an intercept

`ctx.provide(key, value)` stores a value for the current message. The `value` must match the key's type. A value of the wrong type is a compile error.

```typescript [intercept.ts]
// Unauthorized is your own typed error: error('unauthorized'). See Core.
// ctx.meta.token is set by your upgrade function.
base.intercept(async (ctx) => {
  const auth = await verifyToken(ctx.meta.token)
  if (!auth) throw Unauthorized()
  ctx.provide(AuthKey, auth) // typed as { userId, role }
})
```

### Inject in a handler

`ctx.inject(key)` reads the value back. The result type is `T | undefined`. It is `undefined` when nothing was provided for that key during this message.

```typescript [definition.ts]
base.on('admin-action', {
  input: v.object({ target: v.string() }),
  run(ctx, input) {
    const auth = ctx.inject(AuthKey) // { userId, role } | undefined
    // Forbidden is your own typed error: error('forbidden', ...). See Core.
    if (auth?.role !== 'admin')
      throw Forbidden({ reason: 'Not admin' })
    // ... do the admin work
  },
})
```

::

## The typing

The key's type parameter is used by both calls. `provide` only accepts a value of the key's type. `inject` returns that type or `undefined`.

```typescript [typing.ts]
const CountKey = localKey<number>('count')

ctx.provide(CountKey, 42) // ok
ctx.provide(CountKey, 'oops') // compile error: string is not number

const n = ctx.inject(CountKey) // number | undefined
const strict: number = ctx.inject(CountKey) // compile error: the type is number | undefined
```

LiveThing tells keys apart by the **key object itself**, not by its name. Two `localKey` calls with the same name create two different keys, and their values never mix. This is why you export one key and import it everywhere, instead of creating it again in each file.

```typescript [identity.ts]
const a = localKey<string>('user')
const b = localKey<string>('user') // a different key with the same name

ctx.provide(a, 'alice')
ctx.inject(a) // 'alice'
ctx.inject(b) // undefined, because b is a different key
```

## Per-frame isolation

Each dispatch starts with an empty store. A value you provide can be read by every intercept that runs after it and by the handler, for that same message only. The next message cannot see it. A message from another connection cannot see it either.

```typescript [isolation.ts]
const StepKey = localKey<number>('step')

base.intercept((ctx) => {
  ctx.provide(StepKey, 1) // only this message's handler can read this
})

base.on('next-step', {
  input: v.object({}),
  run(ctx) {
    ctx.inject(StepKey) // 1, for this message only
  },
})
```

If you call `provide` again with the same key during the same dispatch, the new value replaces the old one.

## Full example: from intercept to handler

Here is a full server. The top-level intercept provides one key. An `on` handler and a `request` handler both read it.

::code-group

```typescript [keys.ts]
import { localKey } from '@livething/server'

export const TraceKey = localKey<{ traceId: string }>('trace')
```

```typescript [server.ts]
import { emits, server, t } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import { intercepts } from '@livething/server/intercepts'
import * as v from 'valibot'
import { TraceKey } from './keys.ts'

const base = server({
  upgrade: (request) => requireAuth(request),
  capabilities: [
    emits({ echoed: t<{ text: string; traceId: string }>() }),
    clientRequests(),
    intercepts(),
  ],
})

base.intercept((ctx) => {
  ctx.provide(TraceKey, { traceId: crypto.randomUUID() })
})

const handleEcho = base.on('echo', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    const trace = ctx.inject(TraceKey)
    ctx.send('echoed', {
      text: input.text,
      traceId: trace?.traceId ?? 'none',
    })
  },
})

const handleLookup = base.request('lookup', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    const trace = ctx.inject(TraceKey)
    return { text: input.text, traceId: trace?.traceId ?? 'none' }
  },
})

export const definition = base.assemble({
  handlers: [handleEcho, handleLookup],
})
```

## Sharing between the top-level and channel intercepts

When a message is for a channel, the top-level intercept and the channel intercept for that message use **one** shared store. A value that the top-level intercept provides can be read in the channel intercept and in the channel handler.

```typescript [channel-share.ts]
import { emits, localKey, t } from '@livething/server'
import * as v from 'valibot'

// base lists channels() and intercepts() in its capabilities.
export const TraceKey = localKey<{ traceId: string }>('trace')
export const RoomKey = localKey<{ muted: boolean }>('room')

base.intercept((ctx) => {
  ctx.provide(TraceKey, { traceId: crypto.randomUUID() })
})

const room = base.channel('room', {
  capabilities: [
    emits({
      message: t<{ text: string; traceId: string; muted: boolean }>(),
    }),
  ],
})

room.intercept((ctx) => {
  ctx.provide(RoomKey, { muted: false })
})

const handleRoomMessage = room.on('message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    const trace = ctx.inject(TraceKey) // from the top-level intercept
    const roomState = ctx.inject(RoomKey) // from the channel intercept
    ctx.channel.send('message', {
      text: input.text,
      traceId: trace?.traceId ?? 'none',
      muted: roomState?.muted ?? false,
    })
  },
})
```

::note
`provide` and `inject` exist on every connection `ctx`, but they only carry data **within one message's dispatch**. For state that must last longer than one message (per connection or per user), use `ctx.meta`, `ctx.sql` or `ctx.kv` instead. [Context & Storage](/server/context-and-storage/ctx) covers the `ctx` object and storage.
::
