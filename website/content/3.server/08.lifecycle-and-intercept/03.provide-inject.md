An intercept often does work that the handler needs later. For example, it checks a token, loads a user, or works out a permission. `ctx.provide` and `ctx.inject` pass that result on to the handler. You don't need a global variable, you don't fetch the data a second time, and you don't need a type cast (`as`).

The values live in a small store that belongs to one incoming frame. Each time LiveThing processes an incoming frame (this is called a **dispatch**), it creates a new, empty store. When the dispatch ends, the store is gone. This page uses "message" and "frame" for the same thing.

There are three steps:

::steps

### Make a key

`localKey<T>(name?)` returns a typed key. `T` is the type of the value the key carries. The name is optional and is only used for debugging. Export the key, so the intercept and the handler import the same key.

```typescript [server/moderation.ts]
import { localKey } from '@livething/server'

export const ModerationKey = localKey<{
  role: 'admin' | 'member' | 'guest'
  muted: boolean
}>('moderation')
```

### Provide in an intercept

`ctx.provide(key, value)` stores a value for the current message. The `value` must match the key's type. A value of the wrong type is a compile error.

```typescript [server/base.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import { verifySession } from './auth'
import { isMuted } from './helpers'
import { ModerationKey } from './moderation'

export const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user) {
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  intercept(ctx) {
    ctx.provide(ModerationKey, {
      role: ctx.meta.role,
      muted: isMuted(ctx.user.id),
    })
  },
})
```

`intercept` comes after `upgrade`, so `ctx.meta.role` has its type.

### Inject in a handler

`ctx.inject(key)` reads the value back. The result type is `T | undefined`. It is `undefined` when nothing was provided for that key during this message.

```typescript [server/huddle-handlers.ts]
import * as v from 'valibot'
import { base } from './base'
import { ModerationKey } from './moderation'

export const handleArchiveRoom = base.on('archive-room', {
  input: v.object({ roomId: v.string() }),
  run(ctx, input) {
    const moderation = ctx.inject(ModerationKey) // { role, muted } | undefined
    if (moderation?.role !== 'admin') {
      throw new Error('only an admin may archive a room')
    }
    // ... archive the room
  },
})
```

## The typing

The key's type parameter is used by both calls. `provide` only accepts a value of the key's type. `inject` returns that type or `undefined`.

```typescript [server/base.ts]
import { localKey, server } from '@livething/server'

const CountKey = localKey<number>('count')

const base = server({
  intercept(ctx) {
    ctx.provide(CountKey, 42) // ok
    // @ts-expect-error: a string is not a number
    ctx.provide(CountKey, 'oops')

    const n = ctx.inject(CountKey) // number | undefined
    // @ts-expect-error: the type is number | undefined
    const strict: number = ctx.inject(CountKey)
  },
})
```

LiveThing tells keys apart by the **key object itself**, not by its name. Two `localKey` calls with the same name create two different keys, and their values never mix. This is why you export one key and import it everywhere, instead of creating it again in each file.

```typescript [server/base.ts]
import { localKey, server } from '@livething/server'

const a = localKey<string>('user')
const b = localKey<string>('user') // a different key with the same name

const base = server({
  intercept(ctx) {
    ctx.provide(a, 'alice')
    ctx.inject(a) // 'alice'
    ctx.inject(b) // undefined, because b is a different key
  },
})
```

## Per-frame isolation

Each dispatch starts with an empty store. A value you provide can be read by every intercept that runs after it and by the handler, for that same message only. The next message cannot see it. A message from another connection cannot see it either.

```typescript [server/base.ts]
import { localKey, server } from '@livething/server'
import * as v from 'valibot'

const RequestIdKey = localKey<string>('request-id')

const base = server({
  intercept(ctx) {
    ctx.provide(RequestIdKey, crypto.randomUUID()) // only this message's handler can read this
  },
})

const handleSetStatus = base.on('set-status', {
  input: v.object({ status: v.picklist(['active', 'away', 'busy']) }),
  run(ctx) {
    ctx.inject(RequestIdKey) // the ID of this message only
  },
})
```

If you call `provide` again with the same key during the same dispatch, the new value replaces the old one.

## Full example: from intercept to handler

Here is a full server. The top-level intercept provides one key. An `on` handler and a `request` handler both read it.

::code-group

```typescript [server/trace.ts]
import { localKey } from '@livething/server'

export const TraceKey = localKey<{ traceId: string }>('trace')
```

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import * as v from 'valibot'
import { verifySession } from './auth'
import { loadProfile } from './helpers'
import { TraceKey } from './trace'

type Status = 'active' | 'away' | 'busy'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user) {
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    emits({
      'status-changed': t<{ userId: string; status: Status }>(),
    }),
    clientRequests(),
  ],
  intercept(ctx) {
    ctx.provide(TraceKey, { traceId: crypto.randomUUID() })
  },
})

const handleSetStatus = base.on('set-status', {
  input: v.object({ status: v.picklist(['active', 'away', 'busy']) }),
  run(ctx, input) {
    const trace = ctx.inject(TraceKey)
    ctx.log.info('status set', { traceId: trace?.traceId ?? 'none' })
    ctx.broadcast('status-changed', {
      userId: ctx.user.id,
      status: input.status,
    })
  },
})

const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  run(ctx, input) {
    const trace = ctx.inject(TraceKey)
    ctx.log.info('get-profile', { traceId: trace?.traceId ?? 'none' })
    return loadProfile(input.userId)
  },
})

export const huddle = base.assemble({
  handlers: [handleSetStatus, handleGetProfile],
})
```

## Sharing between the top-level and channel intercepts

When a message is for a channel, the top-level intercept and the channel intercept for that message use **one** shared store. A value that the top-level intercept provides can be read in the channel intercept and in the channel handler. In this example, the `send-message` handler of `rooms` also drops a muted user's message. Huddle's own handler does not do this.

```typescript [server/huddle-definition.ts]
import { emits, localKey, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import * as v from 'valibot'
import { isMuted } from './helpers'

export const TraceKey = localKey<{ traceId: string }>('trace') // as in trace.ts above
export const RoomKey = localKey<{ muted: boolean }>('room')

const base = server({
  capabilities: [channels()],
  intercept(ctx) {
    ctx.provide(TraceKey, { traceId: crypto.randomUUID() })
  },
})

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    emits({
      message: t<{
        id: string
        text: string
        from: string
        sentAt: number
      }>(),
    }),
  ],
  intercept(ctx) {
    ctx.provide(RoomKey, { muted: isMuted(ctx.user.id) })
  },
})

const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    const trace = ctx.inject(TraceKey) // from the top-level intercept
    const roomState = ctx.inject(RoomKey) // from the channel intercept
    if (roomState?.muted) {
      ctx.log.info('dropped a muted message', {
        traceId: trace?.traceId ?? 'none',
      })
      return
    }

    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})

export const huddle = base.assemble({
  handlers: [handleSendMessage],
})
```

::note
`provide` and `inject` exist on every connection `ctx`, but they only carry data **within one message's dispatch**. For state that must last longer than one message (per connection or per user), use `ctx.meta`, `ctx.sql` or `ctx.kv` instead. [Context & Storage](/server/context-and-storage/ctx) covers the `ctx` object and storage.
::
