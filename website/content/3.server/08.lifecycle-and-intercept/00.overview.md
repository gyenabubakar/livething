Most of a LiveThing server is made of per-event handlers: `base.on(...)`, `base.request(...)`, `base.stream(...)`. This chapter is about **hooks**. A hook is a function that runs **around** those handlers. It runs for every connection or for every frame (one message on the wire), not for one named event.

There are four kinds. Each one sits at a different point in the message pipeline (the fixed list of steps a message goes through on the server):

::field-group
::field{name="Lifecycle hooks" type="init / connect / disconnect / ping / pong / error / validationError / shutdown"}
Run at connection and server milestones: startup, a socket opening, a socket closing, a `ping` or `pong` from a client, an unhandled error, a validation failure, and shutdown. They observe. They do not change a frame. See [Lifecycle Hooks](/server/lifecycle-and-intercept/hooks).
::
::field{name="intercept" type="(ctx, frame) => unknown | void"}
Runs for every **incoming** frame, before schema validation and before the handler. It can read the frame, rewrite its payload, or block it. It needs the `intercepts()` capability. See [Intercept](/server/lifecycle-and-intercept/intercept).
::
::field{name="provide / inject" type="ctx.provide(key, value) → ctx.inject(key)"}
Typed per-frame values. Each frame gets its own small store, and the store is removed when that frame is done. An intercept saves a value with `ctx.provide`. The handler for the same frame reads it with `ctx.inject`. See [provide / inject](/server/lifecycle-and-intercept/provide-inject).
::
::field{name="outgoing" type="(ctx, frame) => unknown | void"}
The outgoing version of `intercept`. It runs for every **server-to-client** frame, before the frame is serialized (turned into JSON text). It can read the frame, rewrite its payload, or drop it with `Block`. `Block` works a little differently here than on the incoming side. See [Outgoing Hook](/server/lifecycle-and-intercept/outgoing).
::
::

## Where each one sits

A message comes in, a handler handles it, and a reply goes out. Each hook sits at a fixed point on that path:

```text
incoming frame
  → intercept            (inspect / rewrite / block)   ← needs intercepts()
  → schema validation    (onValidationError hook on failure)
  → on / request / stream handler
  → ctx.send / ctx.broadcast / ctx.channel.send ...
  → onOutgoing           (inspect / rewrite / block)
  → serialize → translator.outbound? → wire
```

The lifecycle hooks run at points in the life of the server and of each connection:

```text
server boots          → onInit
connection opens      → onConnect
client sends ping     → onPing
client answers ping   → onPong
connection closes     → onDisconnect
unhandled error       → onError
validation fails      → onValidationError
server stops          → onShutdown
```

These diagrams show the general shape, not every step. Plugins, dedup, nudge buffering and the exact order of steps are in [Pipeline execution order](/server/under-the-hood/pipeline-execution-order).

## One per server

`intercept`, `onOutgoing` and each lifecycle hook are **singletons**: a server has only one of each. A channel can also have its own `intercept`, which only sees that channel's frames. You cannot register two `onConnect` hooks. Put all your connect logic in one hook. If you register the same hook twice, LiveThing throws an error.

## A first look

Every hook here is a method on the `base` builder that `server(...)` returns. You do not pass any of them to `assemble(...)`. LiveThing includes them automatically.

```typescript [server.ts]
import { emits, server, t } from '@livething/server'
import { intercepts } from '@livething/server/intercepts'
import * as v from 'valibot'

const base = server({
  upgrade: (request) => requireAuth(request),
  capabilities: [
    emits({ message: t<{ text: string }>() }),
    intercepts(),
  ],
})

base.onInit((ctx) => {
  ctx.sql.exec(
    'CREATE TABLE IF NOT EXISTS audit (event TEXT, at INTEGER)',
  )
})

base.onConnect((ctx) => {
  ctx.log.info('connected', { id: ctx.connection.id })
})

base.intercept((ctx, frame) => {
  ctx.log.info('incoming', {
    event: frame.event,
    kind: frame.kind,
  })
})

base.onOutgoing((ctx, frame) => {
  // ctx is undefined when no connection is active, for example in a scheduled task
  if (ctx) ctx.log.info('outgoing', { event: frame.event })
})

const handleSend = base.on('send', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.send('message', { text: input.text })
  },
})

export const definition = base.assemble({ handlers: [handleSend] })
```

::note
The client and the server share one error model: `LiveThingError`, the `error()` factory, `.matches()`, and the list of built-in errors. It is described once in [Core](/core/error-model). This chapter covers the **server-only** errors that you throw from these hooks to control what happens next (`Block` and `Disconnect`). For everything else, it links to Core.
::
