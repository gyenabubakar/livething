Most of a LiveThing server is made of per-event handlers: `base.on(...)`, `base.request(...)`, `base.stream(...)`. This chapter is about **hooks**. A hook is a function that runs **around** those handlers. It runs for every connection or for every frame (one message on the wire), not for one named event.

There are four kinds. Each one sits at a different point in the message pipeline (the fixed list of steps a message goes through on the server):

::field-group
::field{name="Lifecycle hooks" type="init / connect / disconnect / ping / pong / error / shutdown"}
Run at connection and server milestones: startup, a socket opening, a socket closing, a `ping` or `pong` from a client, an unhandled error or a validation failure, and shutdown. They observe. They do not change a frame. See [Lifecycle Hooks](/server/lifecycle-and-intercept/hooks).
::
::field{name="intercept" type="(ctx, frame) => unknown | void"}
Runs for every **incoming** frame, before schema validation and before the handler. It can read the frame, rewrite its payload, or block it. See [Intercept](/server/lifecycle-and-intercept/intercept).
::
::field{name="provide / inject" type="ctx.provide(key, value) → ctx.inject(key)"}
Typed per-frame values. Each frame gets its own small store, and the store is removed when that frame is done. An intercept saves a value with `ctx.provide`. The handler for the same frame reads it with `ctx.inject`. See [provide / inject](/server/lifecycle-and-intercept/provide-inject).
::
::field{name="onOutgoing" type="(ctx, frame) => void | Promise<void>"}
Watches every **server-to-client** app frame, once per send, after the frame was written to the sockets. It sees the event, the payload, who the send was addressed to, and how many sockets got it. It cannot change or stop a frame. Use it for metrics, tracing and audit logs. See [Outgoing Hook](/server/lifecycle-and-intercept/outgoing).
::
::

## Where each one sits

A message comes in, a handler handles it, and a reply goes out. Each hook sits at a fixed point on that path:

```text
incoming frame
  → intercept            (inspect / rewrite / block)
  → schema validation    (onError hook gets ValidationFailed on failure)
  → on / request / stream handler
  → ctx.send / ctx.broadcast / ctx.channel.send ...
  → serialize → wire
  → onOutgoing           (watch only, once per send)
```

The lifecycle hooks run at points in the life of the server and of each connection:

```text
server boots          → onInit
connection opens      → onConnect
client sends ping     → onPing
client answers ping   → onPong
connection closes     → onDisconnect
unhandled error       → onError
validation fails      → onError (with ValidationFailed)
server stops          → onShutdown
```

These diagrams show the general shape, not every step. Plugins, dedup, nudge buffering and the exact order of steps are in [Pipeline execution order](/server/under-the-hood/pipeline-execution-order).

## One per server

`intercept`, `onOutgoing` and each lifecycle hook are keys of one object, so a server has only one of each. A channel can also have its own `intercept`, which only sees that channel's frames. Put all your connect logic in one `onConnect` function.

## A first look

Every hook here is a key in the object that you pass to `server({ ... })`. You do not pass any of them to `assemble(...)`. Write them after `upgrade` and `capabilities`: TypeScript reads the object from top to bottom, so a hook above `upgrade` sees `ctx.meta` as `unknown`.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import * as v from 'valibot'
import { verifySession } from './auth'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    emits({ 'user-renamed': t<{ userId: string; name: string }>() }),
  ],
  onInit(ctx) {
    ctx.sql.exec(
      'CREATE TABLE IF NOT EXISTS messages (id TEXT PRIMARY KEY, room TEXT, user_id TEXT, text TEXT, sent_at INTEGER)',
    )
  },
  onConnect(ctx) {
    ctx.log.info('connected', { id: ctx.connection.id })
  },
  intercept(ctx, frame) {
    ctx.log.info('incoming', {
      event: frame.event,
      kind: frame.kind,
    })
  },
  onOutgoing(ctx, frame) {
    // ctx is undefined when no connection is active, for example in a scheduled task
    if (ctx) {
      ctx.log.info('outgoing', {
        event: frame.event,
        target: frame.target.kind,
        recipients: frame.recipients,
      })
    }
  },
})

// A member picks a new display name. ctx.user.setMeta updates every one of
// their live connections, and the broadcast tells everyone else.
// Huddle's own rename only broadcasts; this version also saves the name.
const handleRename = base.on('rename', {
  input: v.object({ name: v.string() }),
  run(ctx, input) {
    ctx.user.setMeta({ name: input.name })
    ctx.broadcast('user-renamed', {
      userId: ctx.user.id,
      name: input.name,
    })
  },
})

export const huddle = base.assemble({ handlers: [handleRename] })
```

::note
The client and the server share one error model: `LiveThingError`, the `error()` factory, `.matches()`, and the list of built-in errors. It is described once in [Core](/core/error-model). This chapter covers the **server-only** errors that you throw from these hooks to control what happens next (`Block` and `Disconnect`). For everything else, it links to Core.
::
