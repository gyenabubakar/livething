After a reconnect, a client needs to know whether it missed anything while the socket was down. **sequence** answers that. It stamps a monotonically increasing number on every outgoing message, so the client can watch the numbers climb — and a jump from `41` to `45` tells it three messages went missing.

## How it works

Every server-to-client application message gets a `seq` value stamped into its `__wskit` envelope: `1`, `2`, `3`, and so on. Protocol frames are skipped and carry no `seq`. The client reads these in order. If the next number is not one more than the last, there is a gap, and the client knows to ask the server for what it missed.

The counter is a single Durable-Object-level value, shared across every connection on that instance — so `seq` climbs monotonically across all concurrent sockets, not per connection. Durable and resumable stream chunks are the one exception: they carry their own per-stream `seq`, which the global stamper does not overwrite.

sequence adds nothing to the client contract. The `seq` value rides in the transport envelope, not in your typed payloads; `InferClient` is unchanged.

## Enable it

Import `sequence` from `@wskit/server/sequence` and list it in `capabilities`. The options object is optional.

```typescript [server/socket.ts]
import { define, t } from '@wskit/server'
import { sequence } from '@wskit/server/sequence'

const base = define({
  env: t<Env>(),
  capabilities: [sequence()],
})
```

That gives you an in-memory counter, which is enough for gap detection.

## Configuration

| Option | Type | Required | Default | What it is |
|---|---|---|---|---|
| `persist` | `boolean` | no | `false` | Keep the counter across server restarts (needs storage) |
| `batchSize` | `number` | no | `100` | How many `seq` values to reserve per storage write — only used when `persist: true` |

`batchSize` must be a positive integer if given.

### In-memory (the default)

With `persist: false`, the counter lives in memory and resets to zero each time the server starts. That is fine for gap detection: the client uses `seq` to spot a missing message, not as a globally unique ID. This mode does no storage writes.

```typescript [server/socket.ts]
const base = define({
  env: t<Env>(),
  capabilities: [sequence()], // same as sequence({ persist: false })
})
```

### Persistent

With `persist: true`, the counter is stored durably and survives a server restart, so sequence numbers never repeat across reconnections. It writes to the Durable Object's own SQL storage — you do **not** need to list `persistence()` for this. (The `persistence()` capability is a separate switch for durable channel membership and identity-keyed tags, not for the sequence counter.)

```typescript [server/socket.ts]
import { define, t } from '@wskit/server'
import { sequence } from '@wskit/server/sequence'

const base = define({
  env: t<Env>(),
  capabilities: [sequence({ persist: true })],
})
```

### Tuning `batchSize`

When persistent, the counter does not hit storage on every send. It reserves a range of `batchSize` numbers in one write, hands them out from memory, then reserves the next range when the batch runs dry. The default of `100` means about one storage write per hundred messages.

```typescript [server/socket.ts]
const base = define({
  env: t<Env>(),
  capabilities: [sequence({ persist: true, batchSize: 100 })],
})
```

A larger `batchSize` means fewer storage writes but a bigger possible gap: if the server crashes mid-batch, the unused numbers in that range are never sent, leaving a jump in the `seq` values on the wire. That gap is harmless — the client treats any jump as "ask the server what's missing" — but a very large jump can look surprising in logs. `batchSize` is **ignored** when `persist` is `false`, since the in-memory counter does no writes to batch.

## Host-only :badge[host-only]

sequence is a **host-only** capability. It cannot be listed inside a plugin's scoped handler — only the top-level `define(...)` may enable it.

## Pairs with dedup and replay

sequence is the natural partner of [dedup](/server/capabilities/dedup): sequence reveals what never arrived, dedup drops what arrived twice. Built-in [replay](/server/capabilities/replay) builds on both — it needs `dedup()` and `sequence({ persist: true })` together so it can re-send exactly the messages a reconnecting client missed.
