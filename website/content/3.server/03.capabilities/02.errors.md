This page covers the two server-side error concerns: **declaring typed errors** so they reach the client contract, and **server-side control-flow errors** you throw to close a socket, reject an upgrade, or retry a message.

The shared error _model_ — what a `WSKitError` is, how `.matches()` works, the built-in errors, and the close codes — lives in the Core section. This page links out to it rather than repeating it.

## Declaring typed errors

You build an error with `error('code', schema?)`, then register the ones you want the client to know about with `errors([...])`. Both come from `@wskit/server` (and `error` is also re-exported from `@wskit/core`).

```typescript [errors.ts]
import { error } from '@wskit/server'
import * as v from 'valibot'

export const NotFound = error('not-found', v.object({ id: v.string() }))
export const Forbidden = error('forbidden', v.object({ reason: v.string() }))
```

`error(...)` returns a **factory**. Call the factory to build the error value you throw. Registering with `errors([...])` is what puts these on the client contract so the client can match them by code:

```typescript [server.ts]
import { define, errors, t } from '@wskit/server'
import { Forbidden, NotFound } from './errors'

const base = define({
  env: t<Env>(),
  capabilities: [errors([NotFound, Forbidden])],
})
```

### The contract slice

`errors([...])` fills the client's `errors` key — the typed error codes the client can receive and narrow on. The two errors above produce this slice:

```typescript [chat-socket.ts]
interface ChatSocket {
  errors: {
    'not-found': { id: string }
    forbidden: { reason: string }
  }
}
```

See [The Error Model](/core/error-model) for the shared `WSKitError` shape and `.matches()`.

::note
`error('code', schema?)` throws at declare time if the code is reused, starts or ends with `__`, or matches a code WSKit already uses for a built-in error (see [Built-in Errors](/core/builtin-errors)). `errors([...])` needs at least one error — an empty list is a type error — and throws if you list the same code twice.
::

### Throwing from a handler

Throw the result of calling a registered factory. WSKit catches it and sends a typed error frame to the client:

```typescript [handlers.ts]
const handleLookup = base.on('trigger-not-found', {
  input: v.object({}),
  run() {
    throw NotFound({ id: 'missing' })
  },
})
```

### Code-only errors

An error with no schema carries no detail. Declare it with just a code, and **call the factory** to throw it — throwing the bare factory function would not be recognized as an error and normalizes to an internal error:

```typescript [code-only.ts]
import { error } from '@wskit/server'

const SimpleError = error('simple-error')

const handleSimple = base.on('trigger-simple', {
  input: v.object({}),
  run() {
    throw SimpleError() // call it — do not throw the bare factory
  },
})
```

::caution
Throwing a `WSKitError` whose code is **not** in your `errors([...])` list does not send that code to the client. WSKit collapses it to the built-in `internal-error` code (and logs a server-side warning that the code was never declared), because a code the contract never declared is one the client cannot narrow on. Register an error to send its real code and detail — that is what puts the typed entry on the client contract.
::

## Server-side control-flow errors

These are a different thing from the typed errors above. They are not part of the shared model and they are not all sent to the client — they steer the server's own flow. They come from `@wskit/server/errors`:

```typescript [imports.ts]
import {
  Block,
  CloseCodes,
  Defer,
  DeferExhausted,
  Disconnect,
  RejectUpgrade,
} from '@wskit/server/errors'
```

| Error                         | Valid in                                          | Sent to client?                        |
| ----------------------------- | ------------------------------------------------- | -------------------------------------- |
| `Disconnect(code, reason)`    | any handler                                       | closes the socket with that code       |
| `Block`                       | inbound `intercept` only                          | no — frame is dropped silently         |
| `RejectUpgrade(code, reason)` | `upgrade` hook only                               | refuses the connection before it opens |
| `Defer(delayMs)`              | `incoming` handlers, request handlers, intercepts | no — retries the message instead       |
| `DeferExhausted`              | fired on `onError` after retries run out          | no — server-only signal                |

### Disconnect — close the socket

Throw `Disconnect(code, reason)` to bail out of a handler and close the connection. When you need to close but keep running (to log or clean up), call `ctx.close(code, reason)` instead — that closes without throwing.

```typescript [disconnect.ts]
const handleForceDisconnect = base.on('force-disconnect', {
  input: v.object({}),
  run() {
    throw Disconnect(CloseCodes.BANNED, 'too many violations')
  },
})
```

`CloseCodes` is the named set of WebSocket close codes — see [Close Codes](/core/close-codes) for the full list.

### Block — silently drop an inbound frame

Throw `Block` — the bare marker, not a call — from an inbound `intercept` to drop the current frame. The handler never runs and **no error is sent to the client**. It is caught only on the inbound dispatch path, so it belongs in an intercept; throwing it from an `onOutgoing` hook is not recognized and propagates as an unhandled error.

```typescript [block.ts]
import { Block } from '@wskit/server/errors'

base.intercept((ctx, frame) => {
  if (frame.event === 'spam') throw Block // drop it — the client hears nothing
})
```

### RejectUpgrade — refuse the connection

Throw `RejectUpgrade(code, reason)` to refuse a WebSocket upgrade before the connection opens. It is **only valid inside the `upgrade` hook** — throwing it anywhere else is treated as an unrecognized error.

```typescript [upgrade.ts]
const base = define({
  env: t<Env>(),
  async upgrade(request) {
    const user = await validateToken(request.headers.get('authorization'))
    if (!user) throw RejectUpgrade(4002, 'invalid token')
    return { identity: user.id, meta: { userId: user.id } }
  },
})
```

### Defer — retry a message later

Throw `Defer(delayMs)` to re-enqueue the current message and run the handler again after a delay. This is useful when the handler cannot make progress yet — a lock is held, a resource is not ready.

`Defer` retries up to **3 times**, so the handler runs **at most 4 times** total (the first attempt plus 3 retries). It is valid in `incoming` handlers, **request handlers**, and intercepts. In a **stream handler** it normalizes to an `internal-error` — a generator that has already yielded chunks cannot be retried from the top.

```typescript [defer.ts]
const handleDeferTest = base.on('defer-test', {
  input: v.object({}),
  async run(ctx) {
    const key = `defer:${ctx.id}`
    const attempts = ((await ctx.kv.get(key)) as number | undefined) ?? 0
    await ctx.kv.set(key, attempts + 1)
    if (attempts < 1) throw Defer(50) // not ready — try again in 50ms
    await ctx.kv.delete(key)
    ctx.send('defer-result', { received: true })
  },
})
```

::caution
In a **request handler**, throw `Defer` _before_ you return a response, never after. Each retry runs the handler again from the top, and the client's request timeout keeps counting down across retries — three defers of 500 ms each burn 1.5 s before the handler can succeed.
::

### DeferExhausted — Defer ran out of retries

When a message keeps throwing `Defer` and the retries run out, WSKit fires a `DeferExhausted` error on your `onError` handler. It is **never sent to the client** — it is a server-only signal so you can dead-letter the message. Its `detail` carries `event`, `payload`, and `retries`:

```typescript [error-hook.ts]
base.onError((ctx, error, event) => {
  if (DeferExhausted.matches(error)) {
    ctx.send('defer-exhausted-result', {
      event: event ?? 'unknown',
      retries: error.detail.retries,
    })
  }
})
```
