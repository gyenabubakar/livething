`persistence()` turns on durable storage for a server. With it on, three things survive a restart: durable channel memberships, user-keyed (persistent) tag rows, and durable streams. Without it, those features cannot exist — so `persistence()` is the prerequisite a few other capabilities check for.

## What it does

Listing `persistence()` gives the server a place to write state that outlives a single connection or a restart. It is the backing storage for:

- **Durable streams** — `resumableStream()` and `recordedStream()`.
- **Persistent tag groups** — tag rows keyed by a connection's `userId`, declared with the `persistent` builder in `tags(...)`.
- **Persistent channel membership** — a member stays in the channel across reconnects and restarts.

You do not call any method on `persistence()` itself. You list it, and the features above start using durable storage.

## How to enable

Import it from its own subpath and add it to your capability array. It takes no config:

```typescript [server.ts]
import { define, t } from '@wskit/server'
import { persistence } from '@wskit/server/persistence'

const base = define({
  env: t<Env>(),
  capabilities: [persistence()],
})
```

::note
`persistence()` has no config object. It is a plain on/off switch — list it to turn durable storage on, leave it out to keep everything in memory.
::

## It is a prerequisite

Two features check for `persistence()` when you call `assemble()`. If it is missing, `assemble()` throws with a message that names `persistence()` as the fix. So you never ship a server that quietly drops durable state — the build fails fast instead.

| Feature                                  | Without `persistence()`                     |
| ---------------------------------------- | ------------------------------------------- |
| `resumableStream()` / `recordedStream()` | `assemble()` throws                         |
| `persistent` tag group in `tags(...)`    | `assemble()` throws                         |
| Persistent channel membership            | No throw — the channel just stays ephemeral |

Persistent channel membership behaves differently from the other two. Without `persistence()`, every channel simply stays ephemeral, even a channel you did not mark `persistent: false`. `persistence()` is what switches durable membership on; it is not a hard requirement a channel fails to build without.

### With a recorded stream

A recorded stream stores its chunks so a client can replay it later. That storage needs `persistence()`:

```typescript [stream-server.ts]
import { define, t } from '@wskit/server'
import { persistence } from '@wskit/server/persistence'
import { recordedStream } from '@wskit/server/streams'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [persistence(), recordedStream()],
})

export const liveFeed = base.recordedStream('live-feed', {
  input: v.object({ topic: v.string() }),
  chunk: t<{ value: number }>(),
  async *run(ctx, input) {
    yield { value: 1 }
    yield { value: 2 }
  },
})
```

Drop `persistence()` from that array and `assemble()` fails, telling you to add it back.

### With a persistent tag group

Tag groups come in two flavors. An `ephemeral` group lives only as long as the connection. A `persistent` group is keyed by `userId` and survives reconnects — and that durable half needs `persistence()`:

```typescript [tags-server.ts]
import { define, t } from '@wskit/server'
import { persistence } from '@wskit/server/persistence'
import { tags } from '@wskit/server/tags'

const base = define({
  env: t<Env>(),
  capabilities: [
    persistence(),
    tags((ephemeral, persistent) => [
      ephemeral('role', t<string>()), // gone when the socket closes
      persistent('favorite', t<string>()), // survives reconnects — needs persistence()
    ]),
  ],
})
```

The `ephemeral('role', ...)` group works without `persistence()`. The `persistent('favorite', ...)` group does not — listing it without `persistence()` fails the build.

### Persistent channel membership

When `persistence()` is on, a channel keeps its members across reconnects by default. A member who drops and comes back is auto-rejoined to the rooms they were in. To opt one channel out of that, set `persistent: false` on its config:

```typescript [channels-server.ts]
import { define, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { persistence } from '@wskit/server/persistence'

const base = define({
  env: t<Env>(),
  capabilities: [persistence(), channels()],
})

// Durable membership — a returning member is auto-rejoined.
const archiveRoom = base.channel('archive-room', {
  outgoing: { emits: { 'room-message': t<{ text: string; from: string }>() } },
})

// Opted out — membership lasts only for the live connection.
const typingIndicator = base.channel('typing-indicator', {
  persistent: false,
  outgoing: { emits: { 'room-message': t<{ text: string; from: string }>() } },
})
```

With durable membership, a member who simply drops the socket is **not** treated as having left. Remaining members receive `__memberOffline__` instead of `__memberLeave__`, and when the same user reconnects they receive `__memberOnline__`. A real leave — an explicit unsubscribe, or a `kick` — is what broadcasts `__memberLeave__`. See [Membership & Presence](/server/channels/membership-and-presence) for the presence frames.

If you rename or remove a channel between deploys, its stored membership rows would otherwise linger. WSKit purges these orphaned rows on the next engine boot: a channel that no current definition claims has its durable memberships swept, and the cleanup is noted in the log.

See [channels](/server/capabilities/channels) for the full membership and auth-gate model.

## SQLite table

Persistent channel membership is backed by one table in the server's own SQL storage: `__wskit_channel_memberships`. It is created the first time `persistence()` runs. The name starts with the reserved `__wskit_` prefix — do not create a table with this name yourself, even before you add `persistence()`, since there is no "table already exists" error to catch the collision. See the [full reserved-table list](/server/context-and-storage/sql-and-kv#reserved-wskit-tables) for every table WSKit owns.

| Column           | Type      | Notes                                                                    |
| ---------------- | --------- | ------------------------------------------------------------------------ |
| `user_id`        | `TEXT`    | The member's user id — part of the primary key.                          |
| `channel_name`   | `TEXT`    | The channel (or the resolved family instance) — part of the primary key. |
| `channel_family` | `TEXT`    | The family key, or `''` for a static channel — part of the primary key.  |
| `joined_at`      | `INTEGER` | Unix ms the membership row was written.                                  |
| `metadata`       | `TEXT`    | Reserved JSON blob for future fields; not read or written yet.           |

The primary key is `(user_id, channel_name, channel_family)`, so re-subscribing an already-durable member updates the row instead of duplicating it. Persistent tag rows (`persistent(...)` in `tags()`) live in a separate table, `__wskit_tags` — see [tags](/server/capabilities/tags) for its schema.

## Host-only capability

`persistence()` is **host-only**. It reaches across the whole connection, so you cannot list it inside a plugin's scoped handler. If a plugin needs durable storage, it declares a dependency on the host instead of listing `persistence()` itself — see [Depending on host capabilities](/server/plugins/depends-on).

## What it adds to the client contract

Nothing. `persistence()` is pure server-side storage — it adds no keys to the client contract and no methods to the client socket. What the client sees comes from the features that sit on top of it (durable streams, channels, tags), not from `persistence()` itself.
