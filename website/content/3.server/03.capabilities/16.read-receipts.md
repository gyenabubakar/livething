Inbox already tracks who _received_ each message, so the received cursor and its `receiversOf` query come with an inbox channel and need no opt-in — pushing the double-grey tick live to other members is a separate `broadcastReceipts` flag on `inbox()`. **readReceipts** adds the blue check on top: who has _read_ a message, not just received it. A member advances a read cursor, and the channel learns who has read up to which message.

`readReceipts()` is a **channel-only** capability, like `inbox()`: it is listed inside a channel's own `capabilities`, next to `inbox()`, never in the top-level `define({ capabilities: [...] })` array.

This page is the enable-and-configure reference. For how receipts behave on the wire — the `__received__` / `__read__` fan-out, `receiversOf` / `readersOf`, and the member cap — see [Receipts](/server/inbox/receipts).

## Requirements :badge[needs inbox()]

Read receipts build on inbox: they reuse the same per-member cursors, sequence numbers, and storage. So a channel that lists `readReceipts()` must also list `inbox()` in that same channel's `capabilities` — this is a compile-time check, not just a runtime one: `readReceipts()` alone in a channel's `capabilities` array does not type-check. `inbox()` brings its own host requirements — `channels()`, `sequence({ persist: true })`, and `dedup()`. See [`inbox`](/server/capabilities/inbox) for that list.

::note
A read acknowledgement implies received: a `__read__` also settles that member's inbox rows up to the read mark. Marking a message read without having acked its delivery first is fine — inbox catches up.
::

## How to enable

Import both `inbox` and `readReceipts` from `@wskit/server/inbox`, then list them together in the channel's own `capabilities`:

```typescript [receipts-server.ts]
import { define, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { dedup } from '@wskit/server/dedup'
import { inbox, readReceipts } from '@wskit/server/inbox'
import { sequence } from '@wskit/server/sequence'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  upgrade: (request) => requireUsername(request),
  capabilities: [channels(), sequence({ persist: true }), dedup()],
})

const chat = base.channel('chat', {
  capabilities: [inbox(), readReceipts()],
  outgoing: { emits: { 'room-msg': t<{ text: string; from: string }>() } },
})

export const handleSend = chat.on('send-room-msg', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('room-msg', {
      text: payload.text,
      from: ctx.meta.username,
    })
  },
})
```

To tune the member cap, pass an options object to `readReceipts(...)`:

```typescript [read-receipts-options-server.ts]
const chat = base.channel('chat', {
  capabilities: [inbox(), readReceipts({ maxReceiptAudience: 512 })],
  outgoing: { emits: { 'room-msg': t<{ text: string; from: string }>() } },
})
```

## Configuration

The only field on `ReadReceiptsOptions` is optional.

| Option               | Type     | Default | What it does                                                                                                                                                                                         |
| -------------------- | -------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maxReceiptAudience` | `number` | `256`   | Only live-broadcast the read `__read__` frame while the channel has at most this many members. Above it the read cursor is still tracked and stays readable via `readersOf`, but no live tick fires. |

## Querying who has read

A channel handle's `readReceipts()` method returns the channel's `ChannelReadReceipts` surface, or `null` when the channel has no `readReceipts()` enabled. Inside a handler scoped to `chat`, `ctx.channel` is that channel's own handle, so `ctx.channel.readReceipts()` is never `null` there — the type still carries the possibility, so check it once:

```typescript [readers-of-server.ts]
export const handleAskRead = chat.on('ask-read', {
  input: v.object({ seq: v.number() }),
  run(ctx, input) {
    const receipts = ctx.channel.readReceipts()
    if (!receipts) return

    const userIds = receipts.readersOf(input.seq)
    ctx.send('cursor-answer', { seq: input.seq, userIds })
  },
})
```

From anywhere else — another handler, a hook, a scheduled task — reach the same surface through `ctx.channels.get('chat').readReceipts()`.

## What it adds to the client contract

A channel whose contract has `readReceipts: true` gains `readers`, `onRead`, `markAsRead`, and `readersOf` on its client handle — `markAsRead(seq?)` advances the read cursor (omit `seq` to mark everything received so far), and `readersOf(seq)` queries who has read up to a message. As with inbox, the channel object must be passed to `base.assemble(...)` for `InferClient` to carry the flag. See [Receipts](/server/inbox/receipts) for the deep behaviour.
