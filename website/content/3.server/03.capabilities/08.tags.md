A **tag** is a label you attach to a connection. Once a connection carries a tag, you can find every connection with that same tag, count them, or send an event to all of them at once. Tags are how you address connections by who they are (`role:admin`) or what they care about (`topic:billing`) instead of holding a list of socket IDs yourself.

You declare named **groups** up front — `role`, `color`, `favorite` — and each group holds a set of string **keys** per connection. WSKit groups connections by the triple `(kind, group, key)`: every connection that added the key `admin` under the `role` group is one addressable set.

## What you get

- A typed `ctx.tags` surface inside handlers to add, remove, count, and fan out to tags.
- Optional initial tags set at connect time, returned from `upgrade(...)`.
- Two storage policies — **ephemeral** (in memory) and **persistent** (durable) — so you pick how long a tag lives.

Tags add nothing to the client contract. They are server-side infrastructure for grouping connections, not wire messages — the client never sees them and `InferClient` is unchanged.

## Enable it

Import `tags` from `@wskit/server/tags` and list it in `capabilities`. The factory takes one callback. The callback receives two builders, `ephemeral` and `persistent`; each call declares one group and you return the array of every group.

```typescript [server/chat.ts]
import { define, t } from '@wskit/server'
import { tags } from '@wskit/server/tags'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [
    tags((ephemeral, persistent) => [
      ephemeral('role', t<string>()),
      ephemeral('color', v.picklist(['red', 'blue', 'green'])),
      persistent('favorite', t<string>()),
    ]),
  ],
})
```

Each builder call is `ephemeral(name, type?)` or `persistent(name, type?)`. The optional second argument types the keys in that group:

- A `t<T>()` marker types the value at compile time and costs nothing at runtime — no validation runs.
- A Standard Schema (for example `v.picklist([...])`) types the value **and** validates it on every `add()`.

So in the example above, `role` and `favorite` accept any string, while `color` rejects anything outside `'red' | 'blue' | 'green'` when you add it.

## Configuration

The callback returns an array of group declarations. Each declaration is one of the two builders:

| Builder                   | What it declares   | Storage                                                               | Needs         |
| ------------------------- | ------------------ | --------------------------------------------------------------------- | ------------- |
| `ephemeral(name, type?)`  | An in-memory group | Survives a hibernation wake on the same socket; gone on disconnect    | nothing extra |
| `persistent(name, type?)` | A durable group    | Keyed by user; survives disconnect and reconnect, and server restarts | nothing extra |

The `type?` argument on either builder:

| `type?` argument                             | Effect                                                      |
| -------------------------------------------- | ----------------------------------------------------------- |
| omitted                                      | Keys are typed as `string`, no runtime validation           |
| `t<T extends string>()`                      | Keys are typed as `T`, no runtime validation                |
| a Standard Schema (e.g. `v.picklist([...])`) | Keys are typed from the schema **and** validated on `add()` |

### Ephemeral vs persistent

The two kinds differ only in how long a tag lives:

- **Ephemeral** tags live in memory for the connection. They survive a hibernation wake on the same socket, but the moment that connection disconnects, its ephemeral tags are gone. Use them for the live, in-session label: who is in this call, who picked the color red.
- **Persistent** tags are stored durably against the connection's `userId`. They survive a disconnect-and-reconnect cycle and server restarts. Use them for a label that should follow a user back: a saved preference like `favorite`.

A group name can be declared in both kinds — `ephemeral('role')` and `persistent('role')` are two independent groups. Declaring the same name twice in the _same_ kind throws at build.

### Removing a persistent group

A user's `persistent(...)` rows stay in `__wskit_tags` even after you remove that group from the `tags(...)` declaration — the durable table does not know your contract changed. WSKit cleans this up itself: on the connection's next connect (or hibernation wake), it checks every stored row's group against the groups still declared. A row whose group is no longer declared is dropped from that connection's live tags **and** deleted from `__wskit_tags`, so it does not keep coming back. A row whose group is still declared is restored as usual, whether or not that group has a schema.

This is self-healing rather than something you have to run yourself: each affected user's stale rows disappear the next time that user connects, one connect at a time. You do not need a migration step to remove a persistent group from a live server.

## The `ctx.tags` surface

Listing `tags(...)` adds `ctx.tags` to every handler. Two methods return a group handle:

```typescript [server/handlers.ts]
const handlePromote = base.on('promote', {
  run(ctx) {
    const role = ctx.tags.ephemeral('role') // a TagGroupHandle
    role.add('admin')
  },
})
```

Passing a group name you did not declare is a **type error** — only declared ephemeral names go to `ephemeral(...)`, and only declared persistent names go to `persistent(...)`.

### Group handle methods

`ctx.tags.ephemeral(group)` and `ctx.tags.persistent(group)` return a `TagGroupHandle`. The current-connection methods act on the connection running the handler; the group-wide methods act on every connection on this instance.

| Method                  | Returns             | What it does                                                          |
| ----------------------- | ------------------- | --------------------------------------------------------------------- |
| `.add(key)`             | `void`              | Adds `key` to the current connection under this group                 |
| `.remove(key)`          | `void`              | Removes `key` from the current connection                             |
| `.has(key)`             | `boolean`           | Whether the current connection holds `key`                            |
| `.list()`               | `readonly TagRef[]` | The current connection's keys under this group                        |
| `.keys()`               | `readonly string[]` | Every active key under this group across connections on this instance |
| `.connections()`        | `ConnectionInfo[]`  | Snapshot of every connection holding any key in this group            |
| `.count()`              | `number`            | Number of distinct connections holding any key in this group          |
| `.send(event, payload)` | `void`              | Sends an event to every connection holding any key in this group      |
| `.ref(key)`             | `TagRefHandle`      | A handle scoped to one exact `(kind, group, key)`                     |

An empty-string key is a no-op: `.add('')` and `ref('').send(...)` do nothing, so a `t<string>()` group can never create a fake `""` tag.

### Ref handle methods

`.ref(key)` narrows from the whole group to one exact key. The returned `TagRefHandle` carries the data fields (`kind`, `group`, `key`) plus the methods that act on that one set of connections:

| Method                  | Returns            | What it does                                                   |
| ----------------------- | ------------------ | -------------------------------------------------------------- |
| `.send(event, payload)` | `void`             | Sends to every connection on this instance with this exact tag |
| `.connections()`        | `ConnectionInfo[]` | Snapshot of those connections                                  |
| `.count()`              | `number`           | How many connections hold this exact tag                       |
| `.has(ref)`             | `boolean`          | Whether a given connection holds this tag                      |

A `TagRefHandle` is accepted anywhere a plain `TagRef` is — the `upgrade(...)` return, `ConnectionInfo.tags`, and a channel handle's `kick(...)`. The methods are stripped when it crosses the wire.

### Listing every tag on the connection

`ctx.tags.list()` returns every tag ref attached to the current connection, across all groups and kinds. Each ref carries `kind`, `group`, and `key`:

```typescript [server/handlers.ts]
const handleListMyTags = base.on('list-my-tags', {
  run(ctx) {
    const mine = ctx.tags.list().map((ref) => ({
      kind: ref.kind,
      group: ref.group,
      key: ref.key,
    }))
    ctx.send('tags-list', { tags: mine })
  },
})
```

## A handler doing add, ref, send, and count

A handler can tag the current connection, then address everyone with a tag and report the size of that set:

```typescript [server/handlers.ts]
import { define, emits, t } from '@wskit/server'
import { tags } from '@wskit/server/tags'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [
    tags((ephemeral) => [
      ephemeral('user', t<string>()),
      ephemeral('role', t<string>()),
    ]),
    emits({
      'fan-out-echo': t<{ text: string; from: string }>(),
      'count-result': t<{ count: number }>(),
    }),
  ],
})

// Send one event to everyone holding role:<key>.
const handleFanOut = base.on('fan-out-to-role', {
  input: v.object({ key: v.string(), text: v.string() }),
  run(ctx, input) {
    ctx.tags
      .ephemeral('role')
      .ref(input.key)
      .send('fan-out-echo', { text: input.text, from: ctx.meta.username })
  },
})

// Count how many connections currently hold role:<key>.
const handleCount = base.on('count-by-role', {
  input: v.object({ key: v.string() }),
  run(ctx, input) {
    const count = ctx.tags.ephemeral('role').ref(input.key).count()
    ctx.send('count-result', { count })
  },
})
```

## Initial tags from `upgrade`

You can attach **ephemeral** tags the moment a connection opens by returning them from `upgrade(...)`. The shape is an object per group, `{ group: key }`, under `tags.ephemeral`:

```typescript [server/upgrade.ts]
import { define, t } from '@wskit/server'
import { tags } from '@wskit/server/tags'

const base = define({
  env: t<Env>(),
  upgrade: (request) => {
    const role = new URL(request.url).searchParams.get('role') ?? 'viewer'
    return {
      userId: crypto.randomUUID(),
      tags: { ephemeral: { role } },
    }
  },
  capabilities: [tags((ephemeral) => [ephemeral('role', t<string>())])],
})
```

Only declared ephemeral group names are accepted here, and only one key per group. Persistent tags are not set from `upgrade(...)` — add those inside a handler with `ctx.tags.persistent(group).add(key)`.

## With `requests()`: broadcast requests to a tag

If you also list `requests()`, both the group handle and the ref handle gain `.broadcastRequest(event, payload)`. It sends a request to every connection in that set and resolves with the first answer that comes back:

```typescript [server/poll.ts]
const handlePoll = base.on('poll-admins', {
  run(ctx) {
    // Every admin gets asked; the first reply wins.
    return ctx.tags.ephemeral('role').ref('admin').broadcastRequest('vote', {
      question: 'ship it?',
    })
  },
})
```

Without `requests()` listed, `.broadcastRequest` is not on the handles — it is a type error to call it. See [requests](/server/capabilities/requests) for the full request model.

## SQLite table

A `persistent(...)` group's rows live in `__wskit_tags`, a table created in the server's own SQL storage. Ephemeral groups never touch it — they exist only in memory. The name starts with the reserved `__wskit_` prefix — never create a table with this name yourself, even before you add `tags(...)`, since there is no "table already exists" error to catch the collision. See the [full reserved-table list](/server/context-and-storage/sql-and-kv#reserved-wskit-tables) for every table WSKit owns.

| Column       | Type      | Notes                                                          |
| ------------ | --------- | -------------------------------------------------------------- |
| `user_id`    | `TEXT`    | The connection's user id — part of the primary key.            |
| `group_name` | `TEXT`    | The `persistent(...)` group name — part of the primary key.    |
| `key`        | `TEXT`    | The tag key added under that group — part of the primary key.  |
| `added_at`   | `INTEGER` | Unix ms the tag was added.                                     |
| `metadata`   | `TEXT`    | Reserved JSON blob for future fields; not read or written yet. |

The primary key is `(user_id, group_name, key)`, so adding the same key twice for the same user and group is a no-op, not a duplicate row.
