Replay is best-effort catch-up on a channel: it keeps one shared log and a reconnecting client asks for the tail it missed. **Inbox** is guaranteed delivery to a person: on every broadcast the engine writes one durable row per member and holds it until that member confirms it arrived — so a member who was offline when the message was sent still gets it, drained automatically on their next reconnect.

This page is the enable-and-configure reference. For how inbox behaves on the wire — the held-until-acknowledged flow, the reconnect drain, receipts, and the overflow gap — see [Inbox](/server/inbox/overview), split into [Delivery and acknowledgements](/server/inbox/delivery), [Receipts](/server/inbox/receipts), and [Overflow and the gap signal](/server/inbox/overflow-and-gap).

## Requirements

Inbox is durable per-member delivery, so it builds on four other capabilities. Leave any out and `assemble()` fails at boot with a message naming the fix:

| Capability | Why it's required |
|---|---|
| [`channels()`](/server/capabilities/channels) | Inbox is channel-scoped — it delivers to a channel's members. |
| [`persistence()`](/server/capabilities/persistence) | The held rows and per-member cursors live in the Durable Object's SQL storage. |
| [`sequence({ persist: true })`](/server/capabilities/sequence) | Held rows order and settle by sequence number, which must survive a restart. A plain `sequence()` is rejected. |
| [`dedup()`](/server/capabilities/dedup) | The reconnect drain re-delivers held rows; dedup drops any the client already saw live. |

::note
Inbox delivers to a **member identity**, so members need a stable identity — set one on upgrade (here `requireUsername`). An anonymous connection still gets messages live while it is connected, but has no durable queue, so it gets no offline drain and no guarantee.
::

## How to enable

List the `inbox()` capability once — it takes no config — then switch it on per channel with `inbox: true`. Every broadcast to that channel writes one held row per member:

```typescript [inbox-server.ts]
import { define, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { dedup } from '@wskit/server/dedup'
import { inbox } from '@wskit/server/inbox'
import { persistence } from '@wskit/server/persistence'
import { sequence } from '@wskit/server/sequence'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  upgrade: (request) => requireUsername(request),
  capabilities: [persistence(), channels(), sequence({ persist: true }), dedup(), inbox()],
})

const chat = base.channel('chat', {
  persistent: true,
  inbox: true,
  outgoing: { emits: { 'room-msg': t<{ text: string; from: string }>() } },
})

export const handleSend = chat.on('send-room-msg', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('room-msg', { text: payload.text, from: ctx.meta.username })
  },
})
```

Nothing in the handler mentions inbox. You broadcast as usual; the engine turns each broadcast into a durable per-member delivery.

To tune one channel, pass an options object instead of `true`:

```typescript [inbox-options-server.ts]
const chat = base.channel('chat', {
  persistent: true,
  inbox: { retention: { maxMessages: 1 } },
  outgoing: { emits: { 'room-msg': t<{ text: string; from: string }>() } },
})
```

## Configuration

Every field on `InboxOptions` is optional.

| Option | Type | Default | What it does |
|---|---|---|---|
| `afterDelivered` | `'delete' \| 'keep'` | `'delete'` | After a member acks a row, `delete` drops it; `keep` retains it. `keep` **requires** `retention` — the build throws without it. |
| `retention` | `{ maxMessages?: number; maxAgeMs?: number }` | none | Bounds held rows **per member**. `maxMessages`: keep at most N undelivered rows; while a member is behind, an (N+1)th broadcast evicts the oldest and raises that member's overflow watermark. `maxAgeMs`: age rows out by time. |
| `broadcastUpTo` | `number` | `256` | Only live-broadcast the received `__received__` tick while the channel has at most this many members. Above it the received cursor is still tracked and stays queryable via `receiversOf`, but no live tick fires — its fan-out is O(members²). |

::note
`afterDelivered: 'keep'` without `retention` fails the build: with delivered rows never dropped, an unbounded queue would grow forever, so a bound is mandatory.
::

## What it adds to the client contract

An inbox channel gains a received surface on its client handle — `receivers`, `onReceived`, and `receiversOf` — because inbox already tracks each member's acknowledgement. These appear only on channels whose contract has `inbox: true`.

For that flag to reach the client type, the channel object must be passed to `base.assemble(...)` alongside the handlers, so `InferClient` carries it:

```typescript [inbox-assemble.ts]
export const inboxHandler = base.assemble(handleSend, chat)

export type InboxClient = InferClient<typeof inboxHandler>
```

On the client, the [`inbox()`](/client/primitives/inbox) primitive reads that flag and exposes the surface — a live `receivers` store, an `onReceived` listener, and the authoritative `receiversOf` query. Read receipts — the blue check, who has *read* a message — are a separate opt-in; see [`readReceipts`](/server/capabilities/read-receipts).
