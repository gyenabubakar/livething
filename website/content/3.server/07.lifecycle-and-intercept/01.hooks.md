Lifecycle hooks run on connection and server milestones, not on a named event. There are six, all methods on the `base` builder. Each is a singleton — one per server.

| Hook | Fires | `ctx` shape | Extra arguments |
|---|---|---|---|
| `init` | once at server startup, before any connection | `InitContext` — storage, env, log, no connection | — |
| `connect` | each time a connection opens, after `upgrade(...)` succeeds | connection `ctx` | — |
| `disconnect` | each time a connection closes, for any reason | connection `ctx`, with `closeCode` / `closeReason` set | — |
| `error` | on any unhandled error from a handler | connection `ctx` | `error: unknown`, `event?: string` |
| `validationError` | when an incoming payload fails its schema | connection `ctx` | `event: string`, `error: unknown` |
| `shutdown` | once when the server stops | `ShutdownContext` — whole-server, no single connection | — |

All six accept a sync or async function. None of them are passed to `assemble(...)`.

## `init`

Runs once during server startup, before any client connects. Use it for one-time setup: creating tables, running migrations, warming a cache.

```typescript [init.ts]
base.init((ctx) => {
  ctx.sql.exec(`
    CREATE TABLE IF NOT EXISTS messages (
      id    TEXT PRIMARY KEY,
      room  TEXT NOT NULL,
      text  TEXT NOT NULL,
      at    INTEGER NOT NULL
    )
  `)
})
```

`ctx` here is an `InitContext`, not a connection context. It has **no** `send`, `broadcast`, `meta`, or `id` — no client is connected yet. What it does carry:

::field-group
  ::field{name="sql" type="SQLProvider"}
  SQL access for table creation, migrations, and seeding.
  ::
  ::field{name="kv" type="KVProvider"}
  Key-value storage for simple get/set/delete.
  ::
  ::field{name="env" type="Env"}
  Platform env bindings (secrets, feature flags) — typed from the `t<Env>()` you passed to `define`.
  ::
  ::field{name="log" type="Logger"}
  Structured logger.
  ::
  ::field{name="platform" type="Platform"}
  The raw platform object from the adapter (a Durable Object state on Cloudflare).
  ::
::

```typescript [init-async.ts]
base.init(async (ctx) => {
  const seeded = await ctx.kv.get('seeded')
  if (!seeded) {
    ctx.sql.exec("INSERT INTO rooms (name) VALUES ('lobby')")
    await ctx.kv.set('seeded', true)
  }
})
```

::caution
A throw from `init` is **not** contained the way `disconnect` and `shutdown` throws are. There is no connection yet, so there is nothing for the `error` hook to attach to — the throw fails server startup itself. No socket opens until `init` succeeds. Wrap risky setup in its own `try`/`catch` if a failure there should not block every connection.
::

## `connect`

Runs every time a connection opens — after `upgrade(...)` returns its `identity` and `meta`, and after any persistent channels are auto-rejoined. Here `ctx` is the full connection context, scoped to the socket that just opened.

```typescript [connect.ts]
base.connect((ctx) => {
  ctx.send('welcome', { username: ctx.meta.username })
  ctx.broadcast('user-joined', { username: ctx.meta.username })
  ctx.log.info('connected', { id: ctx.id, identity: ctx.identity })
})
```

`ctx.meta` is the metadata your `upgrade(...)` hook returned for this connection, and it is typed from that hook. `ctx.send` goes to this socket; `ctx.broadcast` fans out to the others. Defining the upgrade gate itself is covered in [Env & Upgrade](/server/define/env-and-upgrade).

## `disconnect`

Runs every time a connection closes — a clean client close, a network drop, a server-side kick, or a shutdown. This is the only place `ctx.closeCode` and `ctx.closeReason` are set.

```typescript [disconnect.ts]
base.disconnect((ctx) => {
  ctx.broadcast('user-left', {
    username: ctx.meta.username,
    code: ctx.closeCode ?? -1,
    reason: ctx.closeReason ?? '',
  })
})
```

`closeCode` and `closeReason` are optional, so guard them. Common codes you will see:

| Code | Meaning |
|---|---|
| `1000` | Graceful close. |
| `1001` | Going away — sent during server shutdown. |
| `1006` | Abnormal close (network failure, no close frame). |
| `4xxx` | Application-defined — e.g. a code you passed to `Disconnect(code, reason)` or a moderator kick. |

The full list of framework close codes is in [Close Codes](/core/close-codes).

::caution
`ctx.send(...)` in a `disconnect` hook will not reach the closing socket — it is gone. Use `ctx.broadcast(...)` to tell the **other** connections, or write to storage. The example above broadcasts.
::

## `error`

Runs on any unhandled error thrown by a handler — an `on`, `request`, or `stream` body, or an intercept. It is an observer: a place to log, count, or dead-letter. It does **not** change what the client sees.

```typescript [error.ts]
base.error((ctx, error, event) => {
  ctx.log.error('handler threw', {
    event,
    message: error instanceof Error ? error.message : String(error),
  })
})
```

`event` is the incoming event name that caused the error, when the engine knows it; it is `undefined` otherwise. `error` is typed `unknown` — narrow it before reading.

This hook is also where `DeferExhausted` surfaces when a message deferred with `Defer(...)` runs out of retries. See [Control-flow errors](/server/capabilities/errors) for `Defer` and `DeferExhausted`.

## `validationError`

Runs when an incoming payload fails the schema declared on its handler. The handler never runs in that case; the engine sends a `validation-failed` error to the client and calls this hook so you can observe the failure.

```typescript [validation-error.ts]
base.validationError((ctx, event, error) => {
  ctx.log.warn('payload rejected', { event, id: ctx.id })
})
```

The arguments are the connection `ctx`, the `event` name (a `string`, always known here), and the validation `error` (typed `unknown`).

If you register both `validationError` and `error`, a schema failure fires **both** — `validationError` first (the specific signal), then `error` (as part of the standard error path). Guard against double-logging the same failure if both hooks write to the same place.

## `shutdown`

Runs once when the server is stopping. Connections that were live before shutdown are still reachable at this point — you can send a final message or close them early. After every `shutdown` hook finishes, the engine closes any remaining connections with a going-away code and runs the `disconnect` path for each.

```typescript [shutdown.ts]
base.shutdown((ctx) => {
  ctx.broadcast('server-stopping', { reason: 'maintenance' })
})
```

`ctx` here is a `ShutdownContext` — the whole-server view. There is no single connection, so there is no `send` or `meta`. What it carries:

::field-group
  ::field{name="closeAll" type="(code?, reason?) => void"}
  Close every live connection at once. Optional — the engine closes the rest for you after the hook.
  ::
  ::field{name="broadcast" type="(event, payload) => void"}
  Send to every live connection. Typed against your `emits(...)` events, so a wrong event or payload is a compile error.
  ::
  ::field{name="getConnections / connectionCount" type="snapshot / number"}
  Inspect who is still connected.
  ::
  ::field{name="sql / kv" type="storage"}
  Final writes — flush a buffer, persist a counter.
  ::
  ::field{name="schedule / cancelScheduled" type="task control"}
  Queue or cancel durable scheduled work.
  ::
  ::field{name="env / log / waitUntil / platform" type="platform"}
  Env bindings, logging, runtime keep-alive, and the raw platform object.
  ::
::

## Error isolation

Once a connection exists, a throw from a lifecycle hook never crashes the server — but what *else* happens depends on which hook threw. A throw from `disconnect` or `shutdown` is fully **contained** — the engine just logs it and moves on. A throw from `connect`, though, routes through the normal error path: it fires the `error` hook and sends the client an `__error__` frame. And `error` itself is protected against its own failures: if your `error` hook throws (say your logging sink is down), the engine still does the right thing for the original failure — it sends the client its `__error__` so a pending request rejects instead of hanging. `init` is the exception to "never crashes the server" — see the caution above.

```typescript [error-isolation.ts]
// Even if this observer throws, the original handler error is still
// normalized and the client still receives its error frame.
base.error(() => {
  throw new Error('logging sink is down')
})

const handleDoRequest = base.request('do-request', {
  input: v.object({ text: v.string() }),
  run() {
    throw new Error('boom') // → client gets an internal-error reply
  },
})
```

The isolation rules — how a thrown error becomes a client error frame, and how `Block` / `Disconnect` / `Defer` differ from a plain throw — are the shared error model in [Core](/core/error-model), with the server control-flow errors in [Control-flow errors](/server/capabilities/errors).
