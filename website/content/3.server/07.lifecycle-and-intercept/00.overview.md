Most of a WSKit server is per-event handlers: `base.on(...)`, `base.request(...)`, `base.stream(...)`. This chapter is about the hooks that sit **around** those handlers — code that runs for every connection or every frame, not for one named event.

There are four kinds, and they live at different points in the message pipeline:

::field-group
  ::field{name="Lifecycle hooks" type="init / connect / disconnect / error / validationError / shutdown"}
  Run on connection and server milestones — startup, a socket opening, a socket closing, an unhandled error, a validation failure, and shutdown. They observe; they do not change a frame. See [Lifecycle Hooks](/server/lifecycle-and-intercept/hooks).
  ::
  ::field{name="intercept" type="(ctx, frame) => unknown | void"}
  Runs for every **incoming** frame, before schema validation and before the handler. It can inspect, rewrite, or block the frame. Needs the `intercepts()` capability. See [Intercept](/server/lifecycle-and-intercept/intercept).
  ::
  ::field{name="provide / inject" type="ctx.provide(key, value) → ctx.inject(key)"}
  Typed per-frame locals. An intercept stores a value with `ctx.provide`; the handler for that same frame reads it with `ctx.inject`. See [provide / inject](/server/lifecycle-and-intercept/provide-inject).
  ::
  ::field{name="outgoing" type="(ctx, frame) => unknown | void"}
  The outbound mirror of `intercept`. Runs for every **server-to-client** frame, before it is serialized. It can inspect, rewrite, or drop the frame with `Block` — though `Block` behaves differently here than on the inbound side (see [Outgoing Hook](/server/lifecycle-and-intercept/outgoing)).
  ::
::

## Where each one sits

A message flows in, gets handled, and a reply flows out. Each hook taps a fixed point on that path:

```text
incoming frame
  → intercept            (inspect / rewrite / block)   ← needs intercepts()
  → schema validation    (validationError hook on failure)
  → on / request / stream handler
  → ctx.send / ctx.broadcast / ctx.channel.send ...
  → outgoing             (inspect / rewrite / block)
  → serialize → wire
```

And around the connection itself:

```text
server boots        → init
connection opens    → connect
connection closes   → disconnect
unhandled error     → error
validation fails    → validationError
server stops        → shutdown
```

This is the shape, not the full order. Plugins, dedup, nudge buffering, and the exact step sequence live in [Pipeline execution order](/server/under-the-hood/pipeline-execution-order) — link there when you need the precise list.

## One per server

`intercept`, `outgoing`, and each lifecycle hook are **singletons** — one per server (a channel gets its own scoped `intercept`). You do not register two `connect` hooks; you put all your connect logic in one.

## A first look

Every hook here is a method on the `base` builder returned by `define(...)`. None of them are passed to `assemble(...)` — they fold in automatically.

```typescript [server.ts]
import { define, emits, t } from '@wskit/server'
import { intercepts } from '@wskit/server/intercepts'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  upgrade: (request) => requireAuth(request),
  capabilities: [
    emits({ message: t<{ text: string }>() }),
    intercepts(),
  ],
})

base.init((ctx) => {
  ctx.sql.exec('CREATE TABLE IF NOT EXISTS audit (event TEXT, at INTEGER)')
})

base.connect((ctx) => {
  ctx.log.info('connected', { id: ctx.id })
})

base.intercept((ctx, frame) => {
  ctx.log.info('incoming', { event: frame.event, kind: frame.kind })
})

base.outgoing((ctx, frame) => {
  // ctx is undefined for frames from a broadcast or a scheduled task — guard it
  if (ctx) ctx.log.info('outgoing', { event: frame.event })
})

const handleSend = base.on('send', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.send('message', { text: input.text })
  },
})

export const handler = base.assemble(handleSend)
```

::note
The shared error model — `WSKitError`, the `error()` factory, `.matches()`, and the built-in error catalog — is the same on the client and the server, so it lives once in [Core](/core/error-model). This chapter covers the **server-specific** control-flow errors you throw from these hooks (`Block`, `Disconnect`) and links to Core for the rest.
::
