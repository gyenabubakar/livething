In LiveThing, you pay only for the capabilities you list. A capability you leave out adds no code to your server bundle. This page explains how that works. The engine's frame dispatcher (the code that routes each incoming frame) does not import any feature directly. It reaches each feature through an optional **slot**, and a slot is filled only when you list its capability.

## The dispatcher does not import features

When a frame arrives, one dispatcher routes it. The dispatcher does not import the stream runtime or the request runtime. The engine does use a few small channel helpers, such as the check that matches a channel name to its channel family. But the channel **runtime** itself (the subscribe, kick and leave protocol, and broadcast routing) is loaded through a slot, like the other features. The engine carries a set of optional slots, one per feature. For each frame, the dispatcher reads the matching slot and calls it if it is filled.

So the stream path works like this: "Is there a stream trigger in the slot? If yes, call it." If you did not list `stream()`, the slot is empty and the dispatcher skips it. Nothing in the engine imports the stream runtime, so no code path reaches it, and the bundler removes it.

Each slot belongs to one capability:

| Capability                               | Fills the slot for                                                                                |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `stream()`                               | starting plain streams, and nudging and cancelling live streams                                   |
| `resumableStream()` / `recordedStream()` | the durable-stream service                                                                        |
| `clientRequests()`                       | running `request` handlers                                                                        |
| `channels()`                             | the subscribe / leave / kick runtime and the `ctx.channel` surface                                |
| `intercepts()`                           | the intercept pipeline that runs your `intercept(...)` handlers                                   |
| `scheduled()`                            | the task scheduler behind `ctx.schedule`                                                          |
| `tags()`                                 | the `ctx.tags` group handles                                                                      |
| `inbox()`                                | the per-member delivery fan-out, the delivery after a reconnect, and cleanup when a member leaves |
| `lastSeen()`                             | the storage behind `ctx.lastSeen`                                                                 |

A few slots can be filled by more than one capability. `rateLimit()` also fills the intercept slot, because it runs as an intercept. A resumable or recorded stream also fills the scheduler slot, because it removes old stream data with a scheduled task.

`inbox()` and `readReceipts()` also add a method to every channel handle that `ctx.channel` and `ctx.channels.get(...)` return: `handle.inbox()` and `handle.readReceipts()`. So any handle can reach them, not only the scope that declared them. On a channel that did not enable the capability, the method returns `null`. The same rule applies here: list the capability and the method exists and ships. Leave it out and it does not.

## Listing a capability loads its code

The slots are filled during the **install** step of boot. Each capability you listed registers its runtime and fills its own slot. A capability you did not list never runs that step, so nothing imports its runtime.

This is why listing a capability adds its code to your bundle. There is no build flag and no extra import to manage. Putting `channels()` in your `capabilities` list is the one reference that makes the channel runtime reachable. Remove it, and the same code becomes unreachable and tree-shaking (the bundler step that removes unused code) removes it.

```typescript [server/huddle.ts]
import { emits, server, t } from '@livething/server'
import * as v from 'valibot'

// No channels(), no clientRequests(), no stream(). None of those runtimes
// are reachable from this engine, so none of them ship.
const base = server({
  capabilities: [
    emits({ 'user-renamed': t<{ userId: string; name: string }>() }),
  ],
})

const handleRename = base.on('rename', {
  input: v.object({ name: v.string() }),
  run(ctx, input) {
    ctx.send('user-renamed', {
      userId: ctx.user.id,
      name: input.name,
    })
  },
})

export const definition = base.assemble({ handlers: [handleRename] })
```

Add `channels()` to that list, and the channel runtime, its frame handlers and the `ctx.channel` surface become reachable and ship. You change nothing else in your code. The list controls what ships.

## The same idea on both sides of the connection

This is the server half of LiveThing's opt-in design. The client works the same way. A primitive you do not pass to `client()` does not exist on the socket, and its code never loads. This is why the minimal client is only a few kilobytes.

On the server, this matters most for edge runtimes like Cloudflare Workers, where a smaller bundle means a faster cold start (the time a new server instance takes to start and handle its first request).
