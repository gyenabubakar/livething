This page shows **when** each part of a LiveThing server runs. The other chapters explain each feature on its own. This page puts them in order, so you can see exactly where your intercept, validation, handler, `onOutgoing` hook, plugins and channels sit on the path of a single frame. A frame is one message on the WebSocket.

This page is a reference, not a tutorial. Each step links to the chapter that explains it.

## The two paths

A frame is either coming **in** (the client sent it) or going **out** (the server is sending it). These are two separate pipelines, and each has its own hooks. A pipeline is a fixed list of steps that every frame passes through, in order.

- **Inbound:** a frame arrives. It can first pass through a [translator](/server/server/translation) (a function that converts another protocol's messages into LiveThing frames). Then LiveThing routes it, validates it and handles it. The steps here are the channel membership check, `intercept`, the schema validator and the handler.
- **Outbound:** the server sends a frame. It passes the `onOutgoing` hook, can be recorded for replay, is serialized (turned into JSON text), can pass through a translator, and is written to the socket.

The **connection lifecycle** hooks run around both paths: `onInit`, `onConnect`, `onDisconnect`, `onPing`, `onPong`, `onError`, `onValidationError` and `onShutdown`.

## Before any frame: the connection opens

LiveThing must accept a socket before the socket can send an app frame. The steps below run once for each connection.

::steps

### Upgrade

The HTTP upgrade request reaches the server. Every `upgrade` hook runs, in a fixed order. Each hook can return `userId`, `meta` and ephemeral `tags`. LiveThing merges the results:

- `meta` objects are shallow-merged (their top-level keys are combined).
- `tags` lists are joined into one list.
- **At most one** hook may return `userId`. If two hooks return it, the upgrade fails.

The order is nested: **plugin `upgrade` hooks run first** (in the order the plugins are listed), then LiveThing's internal hooks, then **the app's `upgrade` runs last**. Because the app's result is applied last, the app's `meta` value wins when two hooks set the same key.

```text
plugin upgrade (plugin order) → internal hooks → app upgrade
```

If any hook throws, LiveThing refuses the socket and creates no connection. Throw `RejectUpgrade(code, reason)` to choose the code and reason. Any other error refuses the socket with HTTP 500. [Plugins · Authoring](/server/plugins/authoring) explains how to write a plugin's own `upgrade`. [Upgrade](/server/server/upgrade) explains the app's `upgrade`.

### Auto-rejoin persistent channels

Before your code sees the connection, LiveThing subscribes it again to every persistent channel that its `userId` was a member of. This is called auto-rejoin. It also restores the user's persistent tags. Auto-rejoin does not run the channel's `check` or `commit` functions again, because the user already passed them once. If the channel has a `revalidate` function, it runs instead. When `revalidate` throws, LiveThing deletes that membership and sends the client a `rejoin-rejected` error for that channel. See [Channels · Authorization gate](/server/channels/auth-gate).

### `onConnect`

The socket is now live. The `onConnect` hooks run in the same nested order: **plugin `onConnect` hooks first** (in the order the plugins are listed), then **the app's `onConnect` last**. Here `ctx` is the full connection context. LiveThing waits for `onConnect` to finish before it handles the first frame from this socket.
::

::note
`onInit` is **not** part of opening a connection. It runs once when the server starts, before any connection opens. Plugin `onInit` hooks run first, then the app's `onInit`. See [the lifecycle table](#where-the-lifecycle-fires) below.
::

## Inbound: a frame arriving

After the connection opens, every text frame the client sends follows this path. The steps below are the order for a normal **app event**. That is a frame whose `event` is one of your own `on`, `request`, `stream` or channel events.

::steps

### Translate, parse, and pre-checks

When the server has a `translate` option, `translator.inbound(raw)` runs first, on every frame. This includes the bare `ping` and `pong` strings, because translation runs before LiveThing checks for them. After translation, LiveThing checks these cases in order. Each one stops the frame early, before routing:

- A bare `ping` or `pong` string is a keepalive frame (a small message that checks the connection is still alive). It is not JSON. LiveThing answers it or records it, runs its hooks, and stops. See [the lifecycle table](#where-the-lifecycle-fires).
- Every other frame is parsed as JSON and its shape is checked. A frame that is not valid JSON, or does not have the frame shape, is dropped.
- A frame that answers a server-initiated request carries `metadata.exchange.id`. LiveThing passes it to the request code, which settles the server's waiting promise. The frame stops here.
- If `dedup()` is on, a frame whose `metadata.delivery.id` this connection has already sent is dropped as a duplicate.

### Channel membership gate

If the frame is addressed to a channel, the connection must already be a member of that channel. A frame for a channel the connection has not subscribed to gets a `channel-not-subscribed` error. It never reaches an intercept or a handler. Joining a channel (the `check` / `commit` gate) is a separate flow. See [Channels · Authorization gate](/server/channels/auth-gate).

### `intercept`: top-level, then channel

The [`intercept`](/server/lifecycle-and-intercept/intercept) hook runs. An intercept is a function that sees each incoming frame before its handler. If the frame belongs to a channel, the **top-level** intercept runs first, then the **channel** intercept. Each intercept can:

- read the frame,
- rewrite its payload (the value it returns replaces `frame.payload` for the next step),
- stop the frame by throwing `Block` (the frame is dropped with no error) or `Disconnect` (the socket is closed).

```text
top-level intercept → channel intercept (if the frame belongs to a channel)
```

Intercepts run **before** validation, so a rewrite changes what the validator and the handler see. Intercepts need the `intercepts()` capability.

::note
**Nudge frames take a separate path.** A nudge is a message the client sends into a stream that is already running (`frame.kind === 'nudge'`). A nudge also passes through the top-level and channel intercepts. After that, LiveThing checks its payload against that nudge's own schema and gives it to the running stream. It does not use the stream handler's input schema, and it does not start a handler. A `Block` drops only that nudge, with no error. Any other error rejects the promise that the client's `nudge()` call returned. The stream keeps running.
::

### Schema validation

The handler's input schema runs against the payload (the rewritten payload, if an intercept changed it). If validation fails, the handler does not run. LiveThing runs the [`onValidationError`](/server/lifecycle-and-intercept/hooks) hook, then the `onError` hook, and sends a `validation-failed` error to the client.

### Handler

The matching handler runs. It is exactly one of `on`, `request` or `stream`, or the channel version of one of them. [Per-connection event queue](/server/handlers/per-connection-queue) explains when handlers for the same connection run one after another and when they can overlap. A frame that answers a server-to-client request was already handled in the pre-checks above, so it never enters this queue. Anything a handler sends (`ctx.send`, `ctx.broadcast`, `ctx.channel.send`, `ctx.channel.broadcastTo`, a stream chunk, a request) starts the [outbound path](#outbound-a-frame-leaving).
::

### Where `provide` / `inject` values flow

LiveThing handles each incoming frame in one **dispatch** (one run of the inbound path for that frame). Each dispatch has its own small store of values. The store is created the first time it is used and is removed when the dispatch ends. A value that an intercept stores with `ctx.provide(key, value)` can be read by every later step for the same frame: a later intercept and the handler. Nothing else can read it. The top-level intercept, the channel intercept and the handler all share the same store for that frame.

```text
intercept: ctx.provide(AuthKey, auth)
   → channel intercept: ctx.inject(AuthKey)  ✓
   → handler: ctx.inject(AuthKey)            ✓
next frame: ctx.inject(AuthKey)              undefined (new, empty store)
```

The full API is in [provide / inject](/server/lifecycle-and-intercept/provide-inject).

### Example: a `send-message` event

A client sends `send-message` to Huddle. The server lists `intercepts()` and has an `on('send-message')` handler. The intercept removes extra spaces around the text:

```typescript [rooms.ts]
import { emits, server, t } from '@livething/server'
import { intercepts } from '@livething/server/intercepts'
import * as v from 'valibot'

const base = server({
  capabilities: [
    emits({ message: t<{ text: string }>() }),
    intercepts(),
  ],
})

base.intercept((ctx, frame) => {
  // ctx.matches runs the 'send-message' validator, so the cast below is safe.
  if (ctx.matches('send-message', frame)) {
    const payload = frame.payload as { text: string }
    return { ...payload, text: payload.text.trim() }
  }
})

const handleSendMessage = base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.send('message', { text: input.text }) // starts the outbound path
  },
})

export const definition = base.assemble({
  handlers: [handleSendMessage],
})
```

The frame goes through these steps:

```text
send-message arrives
  → membership gate   (not a channel frame, so skipped)
  → intercept         text trimmed
  → validate          v.object({ text }) runs on the trimmed value
  → handler           ctx.send('message', ...)
        → onOutgoing  (outbound path, below)
        → wire
```

If the intercept had thrown `Block`, the path would stop at the intercept. There would be no validation, no handler and no reply.

## Outbound: a frame leaving

Every server-to-client frame follows this path before it is written to the socket. This includes a handler's `ctx.send`, a `ctx.broadcast`, a stream chunk, a server request, a greeting sent from `onConnect`, and a frame sent from a scheduled task.

::steps

### `onOutgoing` hook

The [`onOutgoing`](/server/lifecycle-and-intercept/outgoing) hook runs first. It can read the frame, rewrite its payload by returning a value, or drop the frame by throwing `Block`. It cannot change the event name. For `ctx.broadcast` and `ctx.channel.broadcast`, the hook runs **once** for the whole broadcast, before LiveThing sends to each member. See [onOutgoing](/server/lifecycle-and-intercept/outgoing) for how `Block` behaves on each kind of send.

### Declaration check

The event must be an outgoing event that the active scope declares: an `emits(...)` event, a stream event, or one of LiveThing's own protocol events. For an event that is not declared, LiveThing throws `[livething] Outgoing event "..." was not declared in the active scope.`. On a broadcast, LiveThing logs this error and sends the frame to no one. Frames that carry `metadata.exchange.id`, such as request replies, skip this check.

### Framework metadata

LiveThing adds the metadata fields that the enabled capabilities need. `sequence()` writes `metadata.delivery.seq` (a number that grows by one for each frame). `dedup()` writes `metadata.delivery.id` (a unique ID for the frame). A frame sent in a channel carries `metadata.channel`. On a broadcast, these fields are written once, and every member gets the same values.

### Inbox fan-out: channel broadcasts only

This step runs when [`inbox()`](/server/capabilities/inbox) is listed, the frame is a channel broadcast, and that channel has an inbox. LiveThing writes one stored inbox row for each member of the channel. This is the fan-out. It runs **once for the whole broadcast**, before LiveThing sends to each member. Each row uses the delivery sequence number and ID that the previous step added. A member who is offline still gets a row, and LiveThing delivers it when that member reconnects.

### Replay record: strict mode

If [built-in replay](/server/replay/built-in) is on with **`durability: 'strict'`** (the default), LiveThing writes the frame to the replay store **here, before the send**. So a recorded frame is saved before the client can receive it.

### Serialize and send

LiveThing turns the frame into JSON text. If the server has a translator with an `outbound` function, that function converts the text. Then LiveThing writes the text to the socket.

### Replay record: best-effort mode

If replay is on with **`durability: 'best-effort'`**, LiveThing records the frame **after** the send, without waiting for the write to finish. The send is faster, but if the server crashes between the send and the record, the last frame can be lost.
::

So replay durability changes only one thing: **whether the record happens before or after the send**.

| `durability`       | Order                 | Trade-off                                                 |
| ------------------ | --------------------- | --------------------------------------------------------- |
| `strict` (default) | record → send         | No frame is sent without being recorded. Slightly slower. |
| `best-effort`      | send → record (async) | Faster. The last frame can be lost if the server crashes. |

The full explanation is in [Built-in replay · Durability](/server/replay/built-in#durability-strict-vs-best-effort). Replay never records these frames:

- frames with `metadata.exchange.id` (replies to one request, meant for one client),
- frames with `metadata.stream.id` (stream chunks),
- LiveThing's own protocol frames,
- events listed in the replay `exclude` option.

Replay is for history that any member can catch up on, not for private exchanges.

### Outbound order, short version

```text
ctx.send / broadcast / chunk
  → onOutgoing hook      (rewrite / Block)
  → declaration check
  → metadata             (delivery sequence and ID, channel)
  → [inbox fan-out, once, channel broadcasts only]
  → [strict replay record]
  → serialize → translator.outbound? → wire
  → [best-effort replay record (async)]
```

## Where the lifecycle fires

The eight lifecycle hooks run at fixed points on the inbound and outbound paths above. They observe. They cannot rewrite a frame.

| Hook                | Runs when                            | Where it runs on the paths                                                                                                                                                                   |
| ------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `onInit`            | once when the server starts          | Before everything else. Plugin `onInit` first, then the app's.                                                                                                                               |
| `onConnect`         | each connection opens                | After upgrade and auto-rejoin, before the socket's first inbound frame. Plugin `onConnect` first, then the app's.                                                                            |
| `onDisconnect`      | each connection closes               | After the socket's last frame. The app's `onDisconnect` first, then plugins in reverse order.                                                                                                |
| `onPing`            | a client sends a bare `ping`         | Outside the inbound path. A `ping` is not JSON and is never routed. LiveThing's own hook sends `pong` first, then plugin `onPing` hooks run, then the app's.                                 |
| `onPong`            | a client sends a bare `pong`         | Outside the inbound path, like `ping`. `keepalive()` records the round-trip time first, then plugin `onPong` hooks run, then the app's.                                                      |
| `onError`           | a step fails with an error           | During the inbound path: when an intercept or handler throws, after `onValidationError` when validation fails, and when a membership check fails. Also where `DeferExhausted` appears.       |
| `onValidationError` | an incoming payload fails its schema | During the inbound path, at the validation step. The handler does not run.                                                                                                                   |
| `onShutdown`        | once when the server stops           | Running streams are told to stop first. Then the app's `onShutdown` runs, then plugins in reverse order. After that, LiveThing closes every open socket, which runs `onDisconnect` for each. |

A bare `ping` or `pong` never reaches JSON parsing, routing, intercepts or a handler. It goes only to its own list of hooks. It also counts as activity on the connection. So when [`keepalive()`](/server/capabilities/keepalive) is listed and [hibernation](/server/server/hibernation) is off, a `ping` or `pong` resets that connection's idle timer. Without `keepalive()` there is no idle timer to reset.

Hibernation is a Cloudflare adapter feature. With hibernation on, `keepalive()` does not start an idle timer, so these frames reset nothing. Also, the Workers runtime answers a client's `ping` itself, so the `ping` never reaches the server instance and runs no hook. The one exception is a server with a `translate` option: then LiveThing turns off the automatic answer, and `ping` goes through the translator and the hooks as usual.

The full hook reference (`ctx` shapes, arguments, and what happens when a hook throws) is in [Lifecycle hooks](/server/lifecycle-and-intercept/hooks).

::note
The lifecycle hooks use the same nested order as the per-frame hooks. The hooks at the **start** of a connection or the server (`onInit`, `onConnect`) run plugins **before** the app, so a plugin sees the connection first. The hooks at the **end** (`onDisconnect`, `onShutdown`) run the app **first**, then plugins in **reverse** order. So a plugin cleans up after the app code that depends on it.
::

## Plugins and channels in the order

Two rules decide where plugin and channel code fits into the paths above.

### Plugins: nested order

A plugin's hooks run around the app's hooks. They never replace them:

- **Start hooks** (`upgrade`, `onInit`, `onConnect`): plugin hooks run **first**, in the order the plugins are listed, then the app's. `onPing`, `onPong`, `onError` and `onValidationError` also run plugin hooks first.
- **End hooks** (`onDisconnect`, `onShutdown`): the app runs **first**, then plugins in **reverse** order.
- **Per-frame hooks** (`intercept`, `onOutgoing`): every hook runs for every frame. LiveThing reads which plugin (or the app) owns the frame from the event name, and gives it to the hook as `frame.owner`. See [Plugin namespacing](/server/plugins/namespacing).

### Channels: nested scope

For a frame that belongs to a channel, the channel's per-frame hooks run **inside** the top-level ones:

- **Inbound:** the top-level `intercept` runs, then the channel `intercept`. Both use the same `provide` / `inject` store for that frame.
- **The channel's handler** is the one [handler step](#handler). There is no separate "channel handler" step. The channel's `on`, `request` or `stream` is the handler that step runs when the frame belongs to the channel.

### Built-in capabilities and plugin order

Inside one scope (the app, one plugin, or one channel), LiveThing's built-in capabilities run at the **fixed** points named above:

- `dedup()` at the inbound pre-checks,
- `sequence()` and `dedup()` at the outbound metadata step,
- replay at the record step.

The order in which you list them does not change when they run. Each one has its own fixed point in the pipeline. **Plugin order** (the nested order above) only affects hooks that both the app and its plugins can register: `upgrade`, the eight lifecycle hooks, `intercept` and `onOutgoing`.

## Full picture

One `send-message` frame in a room, on a server with one plugin, `intercepts()` and strict replay:

```text
── connection opens ──────────────────────────────
upgrade:   plugin → app          (userId, meta, tags merged)
auto-rejoin persistent channels
onConnect: plugin → app

── send-message arrives (in a room) ──────────────
parse + pre-checks (dedup)
channel membership gate
intercept:  top-level → channel   (rewrite / Block)
validate:   channel handler's schema
handler:    rooms.on('send-message') runs
   └─ ctx.channel.broadcast('message', ...)
        ── outbound, once for the broadcast ─────
        onOutgoing hook          (rewrite / Block)
        declaration check
        metadata                 (delivery sequence and ID, channel)
        ── outbound, for each member ────────────
        replay record (strict)   ← before send, stored once
        serialize
        translator.outbound?     ← last change to the wire format
        wire

── connection closes ─────────────────────────────
onDisconnect: app → plugin (reverse)
```
