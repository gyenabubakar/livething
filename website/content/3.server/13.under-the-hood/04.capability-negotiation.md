The server definition names no platform. So it cannot know if the platform can hibernate idle sockets, or if it can report how full a socket's send buffer is. The adapter declares these things. When the server starts, the engine reads what the adapter supports and adjusts its behavior. This is why one definition can run on two platforms and behave differently, with no change to your handler code. This matching between what the definition asks for and what the adapter supports is called **capability negotiation**.

## What the adapter declares

An adapter declares two platform features. The engine reacts to both.

- **Hibernation.** Hibernation means the platform removes an idle server instance from memory (this is called an **eviction**) but keeps its sockets open. The adapter either gives the engine a way to save and restore each socket's state across an eviction, or it does not. Giving that save/restore pair _is_ the signal. There is no separate `true`/`false` flag.
- **Outbound backpressure.** **Backpressure** is what happens when the server sends data faster than the client can read it, so unsent data builds up in the socket's send buffer. Each accepted connection says whether the platform reports how full this buffer really is (`backpressureSupported`). When it does, the engine slows streams down based on the real buffer. When it does not, the engine treats the buffer as always ready.

## Hibernation: provided or refused

When your definition sets `hibernation: { enabled: true }` in `server()`, the adapter must support hibernation. If the adapter gives the save/restore pair (the Cloudflare adapter does), the engine uses the hibernation path. It accepts sockets through the platform's hibernation API. It also writes each socket's state into the platform's attachment (a small piece of data the platform stores with each socket), so the state survives an eviction.

If the adapter does **not** support hibernation, the engine does not ignore the setting. It throws an error at startup, before it accepts any connection:

```text
[livething] Server definition requires hibernation, but adapter "my-adapter" does not support it.
```

So `hibernation: { enabled: true }` is a strict requirement. The server either runs on a platform that can hibernate, or it fails at startup with a clear error. The Cloudflare hibernation details, including what state survives a hibernation cycle, are in [Hibernation](/server/server/hibernation). How ping and pong frames behave with a translator under hibernation is in [Translation](/server/server/translation).

Storage and timers are different. Every adapter must give the engine storage and timers. The engine's runtime options type requires both, so an adapter that leaves them out does not type-check. Because of this, hibernation is the only platform feature the engine checks at startup. It is the only one a platform can be missing.

## Backpressure: real pacing or a no-op

`ctx.stream.drain()` waits until the outbound buffer is below the stream's limit (`highWaterMark`, 256 KB by default) before the generator produces more. What it does depends on the adapter.

- A connection that reports backpressure support (the Node.js and Bun adapters, when the socket reports its buffer size) gives `drain()` a real buffer to check. So a fast generator cannot send faster than a slow client can read.
- A connection that does not report it makes `drain()` resolve at once. Cloudflare is an example: it does not report how full the buffer is. On Cloudflare, `drain()` is a no-op (a call that does nothing).
- For a **broadcast** stream (one stream sent to many connections), `drain()` waits for the subscriber with the _least_ buffered data, not for the slowest one. So one slow client cannot hold back the stream for every other client.

```typescript [drain.ts]
base.stream('export-rows', {
  input: v.object({}),
  async *run(ctx) {
    for (const row of await loadRows()) {
      yield row
      await ctx.stream.drain() // wait while the client's outbound buffer is full
    }
  },
})
```

Your stream handler calls `drain()` the same way on every platform. Where the platform reports the buffer, the pacing is real. Where it does not, the call does nothing and causes no harm. So the same code is correct on every platform. [Streams](/server/streams/overview) covers streams in detail.

## Why it works this way

The three layers exist so that the definition works on any platform. If the definition had to name hibernation storage or buffer APIs, it would work on only one platform. Instead, the definition says what you want, such as "hibernate idle sockets" or "pace this stream". The engine compares that with what the adapter can do. Then it does one of three things: it does what you asked, it turns the request into a safe no-op, or it refuses to start. [Custom adapters](/server/adapters/custom-adapters) shows how to write an adapter that declares these features.
