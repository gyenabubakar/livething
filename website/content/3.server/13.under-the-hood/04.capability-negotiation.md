The definition layer names no platform, so it can't know whether the runtime hibernates idle sockets or exposes outbound buffer pressure. Those are the adapter's to declare. At boot the engine reads what the adapter supports and adapts — which is why one definition can run on two platforms and behave differently without a line of handler code changing.

## What the adapter declares

An adapter advertises its platform's capabilities in two places, and the engine reacts to both.

- **Hibernation** — the adapter either provides a way to persist and restore per-socket state across an eviction, or it doesn't. Providing it _is_ the capability signal; there is no separate flag.
- **Outbound backpressure** — each accepted connection says whether the platform exposes real send-buffer fullness. When it does, the engine paces against the live buffer; when it doesn't, it treats the buffer as always-ready.

## Hibernation: provided or refused

When your definition sets `hibernation: { enabled: true }`, the engine needs the adapter to back it. If the adapter provides the persist/restore mechanism — as the Cloudflare adapter does — the engine takes the hibernatable path: it accepts sockets through the platform's hibernation API and writes each socket's state into the platform's attachment so it survives an eviction.

If the adapter does **not** support hibernation, the engine refuses to boot rather than silently ignoring the request:

```text
[wskit] Handler requires hibernation, but adapter "my-adapter" does not support it.
```

So `hibernation: { enabled: true }` is a real contract: it either runs on a hibernating platform or fails loudly at startup. The Cloudflare specifics — what survives a cycle and its untranslated-only edge ping/pong auto-response — are in [Hibernation](/server/define/hibernation).

Hibernation also depends on durable **storage** — it persists each socket's state so it survives an eviction. Storage is not something an adapter can opt out of: every adapter's options type requires it, along with timers, so an adapter written without storage does not even type-check. Hibernation is the one platform requirement the engine checks at boot, because it is the one capability a platform can genuinely lack.

## Backpressure: real pacing or a no-op

`ctx.stream.drain()` waits for the outbound buffer to drain before the generator produces more. Whether it does anything depends entirely on the adapter.

- A connection that reports backpressure support (a Node or Bun adapter) gives `drain()` a live buffer to pace against, so a fast generator can't outrun a slow client.
- A connection that doesn't (Cloudflare, which does not expose buffer fullness) makes `drain()` resolve immediately — a documented no-op, not a hidden difference.
- For a **broadcast** stream, `drain()` paces against the _healthiest_ subscriber — the one with the least buffered data — never the slowest, so a single slow client can't stall the whole fan-out.

```typescript [drain.ts]
base.stream('feed', {
  input: v.object({}),
  async *run(ctx) {
    for (const row of await loadRows()) {
      yield row
      await ctx.stream.drain() // pace against the client's outbound buffer
    }
  },
})
```

Your stream handler calls `drain()` the same way on both. The pacing is real where the platform allows it and harmless where it doesn't, so the same code is correct everywhere. The streaming side is covered in [Streams](/server/streams/overview).

## Why it works this way

The point of the three-layer split is that the definition stays portable. If the definition had to name hibernation persistence or buffer APIs, it would be locked to one platform. Instead it states _intent_ — "hibernate idle sockets," "pace this stream" — and the engine matches that intent against what the adapter can actually do: honor it, downgrade it to a safe no-op, or refuse to boot. Writing an adapter that declares these capabilities is covered in [Custom adapters](/server/adapters/custom-adapters).
