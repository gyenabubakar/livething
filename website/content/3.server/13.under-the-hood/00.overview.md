You do not need this chapter to use LiveThing. The earlier chapters show you what to write. This chapter explains what happens **after** you write it. It answers three questions: why the pipeline (the fixed list of steps every message goes through) runs in its order, why a feature you do not list adds no code to your app, and why the same server can behave differently on two platforms. There is no new API to learn here. It explains the reasons behind the rules you already know.

## Three layers

A running LiveThing server has three layers, one on top of the other. You write the first layer, you choose the second, and you never touch the third.

::steps

### The definition

You call `server`, add capabilities, add handlers, and call `assemble`. The result is a **server definition**. It is a frozen object (it cannot be changed after it is made) and it does not know which platform it will run on. It is not a running server and it holds no connection state. It holds two things: the list of primitives (capabilities and handlers) you selected, and the contract type that `InferClient` reads. The chapters from [server()](/server/server/overview) to [Plugins](/server/plugins/overview) are all about building this one object.

### The adapter

An **adapter** takes a definition and returns a service for one platform. For example, `bind(huddle)` from `@livething/server-cloudflare` returns a Durable Object class. The adapter controls the platform's WebSocket lifecycle (accepting, reading and closing sockets). It gives the engine four things: storage, timers, a platform object and a logger. [Adapters](/server/adapters/overview) covers this layer, and [Custom adapters](/server/adapters/custom-adapters) shows how to write your own.

### The engine

The **engine** lives inside the adapter. It is the part that runs your definition. It compiles the definition into fast lookup tables, installs the runtime code of each capability, accepts sockets, and passes every frame (one WebSocket message) through the pipeline. You never create the engine yourself. The adapter creates it through a factory function.
::

This split is why one definition can run on any platform. The definition does not name a runtime. The engine does not name a platform. The adapter is the only layer that knows both.

## How the engine is built

The engine keeps **state** apart from **behavior**. This explains a phrase you see often in these docs: "a capability fills a slot."

- **State** is kept in one container. It holds the open connections, the member indexes for channels and tags, the compiled lookup tables, the registered hooks, and a set of empty **feature slots**. A feature slot is a place for one capability's runtime code.
- **Behavior** is in the runtime modules that read and write that state: the boot routine, the message dispatcher and the connection lifecycle.

When the engine boots, each capability you listed registers its hooks and fills the slots it owns. A capability you did not list leaves its slot empty, and the engine skips that slot when it routes a frame. The next three pages explain what follows from this design:

## One definition, different runtimes

The adapter is the only layer that knows the platform. So the same definition can behave differently, depending on which adapter runs it. The adapter declares what its platform supports. For example, it declares whether the platform can hibernate idle sockets (keep them open while the server sleeps) and whether it reports backpressure (how full the outgoing send buffer is). The engine then adjusts its behavior to match.

Cloudflare can hibernate, but it does not report how full the send buffer is. So on Cloudflare, `ctx.stream.drain()` does nothing and returns at once. The Node and Bun adapters report the real buffer size, so the same `drain()` call makes a stream generator wait until the buffer has room. Your handler code stays the same on both. [Capability negotiation](/server/under-the-hood/capability-negotiation), the last page of this chapter, explains this in detail.
