A server definition is a frozen list of primitives. Before the engine can route a frame against it, it has to turn that list into something fast to look up, install each capability's runtime, and check the whole thing holds together. That all happens once, at boot — the moment the adapter creates an engine.

## Compile: from list to lookup tables

`assemble` hands the engine an immutable `ServerDefinition` — the primitives you registered, in the order you registered them. Walking that list on every frame would be slow, so the first thing the engine does is **compile** it into a compact set of lookup tables: one map of outgoing events, one of incoming handlers, one each for requests, streams, channels, and scheduled tasks.

After that, routing a frame is a single map lookup by event name, not a scan. The engine resolves `say` to its handler in one step regardless of how many handlers you declared.

Compile is also where the **wire-facing rules** are enforced, because a name that can't travel over the wire is better caught at startup than on the frame that needs it. The same walk that builds the tables rejects:

| Rule                        | What it catches                                                                                                                                                                                            |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reserved names              | An event called `ping` or `pong` (the keepalive frames), or any name starting **or ending** with `__` (reserved for protocol and plugin events).                                                           |
| Reserved syntax             | A channel or event name containing `::`, or a channel name starting with `@` or `#`, which collide with the path-key grammar `intercept`'s `ctx.matches(...)` uses.                                        |
| Names too long for the wire | An event or channel name past the protocol's length limit, which no client could ever address.                                                                                                             |
| Duplicate registration      | The same event registered as more than one of incoming / request / stream / resumableStream / recordedStream within a scope — the engine would pick one and silently shadow the rest.                      |
| Missing prerequisite        | A capability used without one it depends on — built-in `replay` without `dedup` (replay keys off the `messageId` dedup stamps). This dependency is caught here at compile, not at the later validate step. |

## The boot sequence

Once compiled, the engine runs a fixed startup routine. The adapter triggers it once — on Cloudflare, inside `blockConcurrencyWhile`, so no frame is handled until it finishes.

::steps

### Check adapter requirements

Every adapter is required to provide storage and timers — they are non-optional fields on the adapter's options type, so an adapter missing either one does not type-check and never reaches this step. Hibernation is different: a platform can genuinely lack it, so this is the one requirement the engine checks at boot. If your definition sets `hibernation: { enabled: true }` and the adapter does not provide the persist/restore mechanism, boot fails here, naming the adapter:

```text
[wskit] Handler requires hibernation, but adapter "my-adapter" does not support it.
```

### Install each capability's runtime

The engine walks the primitive tree and lets every primitive register its runtime hooks and **fill the feature slots it owns** — the stream trigger, the request dispatcher, the channel runtime, and so on. A capability you didn't list never runs here, so its slot stays empty and its code never loads. This is the mechanism the [Feature slots](/server/under-the-hood/feature-slots) page covers in full.

### Validate against settled state

Some rules can only be checked once every capability is installed, because one capability depends on another's runtime configuration. Each capability owns its own check; the engine just runs them. Built-in **replay** and **inbox** both need `sequence: { persist: true }` for a stable row order across restarts — each checks it here, once `sequence()` has been installed and its persistence setting is known:

```text
[wskit] replay requires `sequence: { persist: true }` for durable replay.
```

A channel's `.revalidate()` hook needs a **persistent** channel to ever fire (it only runs on auto-rejoin, which only happens for persistent channels) — that check runs here too, per channel.

The built-in **replay** dependency on `dedup` — it needs the `messageId` dedup stamps — is checked one step earlier, during compile/construction, with this message:

```text
[wskit] contract uses replay but did not enable dedup. Replay persists every
outgoing message keyed by messageId, which dedup stamps. Add `dedup: true` to the contract config.
```

### Initialize storage schema

Every adapter provides durable SQL storage, so capabilities that keep tables (replay, channels, inbox, tags, sequence, last-seen, the durable scheduler, durable streams, and hibernation's connection snapshot) run their idempotent schema hooks now. Those hooks run on every boot, so a capability added after storage was initialized creates its tables on the next wake. A marker row records whether the storage has ever been initialized; it does not skip schema hooks. The marker is documented below.

### Run `onInit`

Finally the lifecycle `onInit` hooks run: **plugin `onInit` hooks first, in registration order, then the app's**. Hooks are nested in this order, so a plugin sees startup before the app that depends on it. `onInit` runs once, before the first connection ever opens.
::

After `onInit` returns, the engine is live and the adapter starts accepting sockets.

## The schema marker table

The engine uses one reserved table, `__wskit_meta`, to tell a truly fresh store from storage that has already been initialized:

| Column  | Type               | Meaning                                                 |
| ------- | ------------------ | ------------------------------------------------------- |
| `key`   | `TEXT PRIMARY KEY` | The marker name. Today the only row is `'initialized'`. |
| `value` | `TEXT NOT NULL`    | The marker value, currently `'1'`.                      |

On boot the engine checks for the `initialized` row before running any schema-init hooks:

- **Row present** — the store has been initialized before. The engine still runs every schema-init hook; each hook must be idempotent.
- **Row missing** — a fresh store. The engine runs every schema-init hook, then creates `__wskit_meta` and writes the marker.

The marker is not a schema-version gate. WSKit does not compare versions or skip hooks on warm boots; schema changes are handled by the idempotent hooks themselves.

`__wskit_meta` is created by the engine itself, not by any one capability, because it has to exist before any capability's own schema check can run.

::warning
`__wskit_meta` is reserved, along with every other WSKit table — they all use the `__wskit_` prefix (`__wskit_replay`, `__wskit_channel_memberships`, `__wskit_inbox`, and so on). Never create your own table under that prefix; a name collision corrupts WSKit's own bookkeeping.
::

## Two passes, both before the first frame

A misconfigured server never reaches a client. Two separate passes guard it:

- **`assemble`**, when you build the definition, catches the structural mistakes — two handlers on the same event, a scheduled task with no registered body, a per-handler `rateLimit` override whose capability was never listed.
- **The engine**, when it boots, catches everything above — the wire-name rules and the built-in replay-needs-dedup dependency at compile, an adapter that doesn't support hibernation at the adapter-requirements step, and the remaining cross-capability rules (replay/inbox needing a persistent `sequence`, a channel's `.revalidate()` needing a persistent channel) at the validate step.

A boot example: replay listed without its dependencies fails at compile, so the server throws on startup rather than dropping a frame later.

```typescript [broken.ts]
import { define, t } from '@wskit/server'
import { replay } from '@wskit/server/replay'

// Throws at boot: replay needs dedup() and sequence({ persist: true }).
const base = define({
  env: t<Env>(),
  capabilities: [replay.history()],
})
```

Adding `dedup()` and `sequence({ persist: true })` clears it — the full rule is in [Built-in replay](/server/replay/built-in).
