A server definition is a frozen list of primitives. Before the engine can route a frame with it, the engine must do three things. It turns the list into tables that are fast to search. It installs the runtime code of each capability. It checks that the parts of the definition work together. All of this happens once, at **boot** (the startup of the engine, when the adapter creates it).

## Compile: from list to lookup tables

`assemble` gives the engine an immutable `ServerDefinition` (it cannot be changed). It holds the primitives you selected, in the order you assembled them. Searching that list on every frame would be slow. So the first thing the engine does is **compile** it: it builds a small set of lookup tables (maps from a name to its handler). There is one map for outgoing events and one for incoming handlers. There is also one each for requests, streams, channels and scheduled tasks.

After compile, the engine routes a frame with one map lookup by event name. It does not scan a list. The engine finds the handler for `say` in one step, no matter how many handlers you assembled.

Compile also checks the **wire rules**: the rules for names that travel over the WebSocket connection. A name that cannot travel over the wire should fail at startup, not later on the frame that needs it. While it builds the tables, compile rejects these problems:

| Rule                        | What it catches                                                                                                                                                                                                                                      |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reserved names              | An event called `ping` or `pong` (the keepalive frames). A channel name that starts or ends with `__`. LiveThing keeps `__` for protocol and plugin events. (An event name that starts or ends with `__` fails earlier, when you declare the event.) |
| Reserved syntax             | A channel or event name that contains `::`, or a channel name that starts with `@` or `#`. These characters are part of the key format that `ctx.matches(...)` uses in an `intercept`, such as `'@rooms::send-message'`.                             |
| Names too long for the wire | An event name longer than 128 characters, a channel name longer than 256, or a channel family key longer than 128. No client could send a name that long.                                                                                            |
| Duplicate registration      | The same event name registered as more than one of incoming / request / stream / resumableStream / recordedStream in one scope (the top level, or one channel). Only one of them could ever run.                                                     |
| Missing prerequisite        | Built-in `replay` without `dedup()`, or with a `sequence()` that does not use `persist: true`. `assemble` already rejects a missing `dedup()` or `sequence()`, so in practice compile catches a sequence that does not persist.                      |

## The boot sequence

After compile, the engine runs a fixed startup routine. The adapter starts it once. On Cloudflare, it runs inside `blockConcurrencyWhile` (a Durable Object method that holds all incoming events until a function finishes), so no frame is handled until the routine ends.

::steps

### Check adapter requirements

Every adapter must provide storage and timers. They are required fields on the adapter's options type, so an adapter without them does not type-check and never gets to this step. Hibernation is different. Hibernation lets the platform keep idle sockets open while the server sleeps, and some platforms do not have it. So this is the one requirement the engine checks at boot. If your definition sets `hibernation: { enabled: true }` and the adapter cannot save and restore connections, boot fails here. The error names the adapter:

```text
[livething] Server definition requires hibernation, but adapter "my-adapter" does not support it.
```

### Install each capability's runtime

The engine walks through the list of primitives, including the primitives inside each channel. Every primitive registers its runtime hooks and **fills the feature slots it owns**, such as the stream trigger, the request dispatcher and the channel runtime. A capability you did not list does not run here. Its slot stays empty and its code is not loaded. The [Feature slots](/server/under-the-hood/feature-slots) page explains this in full.

### Validate against settled state

Some rules can be checked only after every capability is installed, because one capability depends on the runtime settings of another. Each capability owns its own check, and the engine runs them all. For example, built-in **inbox** needs `sequence({ persist: true })`, so the order of stored rows stays the same after a restart. Inbox checks this here, after `sequence()` is installed and its `persist` setting is known:

```text
[livething] inbox needs a persistent sequence for durable delivery. List sequence({ persist: true }) in server({ capabilities: [...] }) instead of sequence().
```

Two other checks run at this step, once for each channel:

- A channel with `inbox()` must be persistent. Inbox delivers to the saved member list, and a channel with `membership: 'ephemeral'` saves no members.
- A channel with a `.revalidate()` hook must be persistent. The hook runs only when a member rejoins the channel automatically after a reconnect, and only persistent channels do that. On any other channel, the hook would never run.

Built-in **replay** has the same `persist: true` rule, but it fails earlier, at compile (see the table above).

### Initialize storage schema

Every adapter provides durable SQL storage (a database that keeps data after a restart). So each capability that keeps tables creates them now with its schema hook (the setup code that runs `CREATE TABLE IF NOT EXISTS`). These capabilities are replay, channels, inbox, tags, sequence, last-seen, the durable scheduler, durable streams and hibernation (for its saved connection list). The hooks are idempotent: running them again changes nothing. They run on every boot, so if you add a capability after the storage was first set up, it creates its tables on the next boot. A marker records whether the storage was ever set up, but it never skips a schema hook. The [marker table](#the-schema-marker-table) section below explains it.

### Run `onInit`

Last, the lifecycle `onInit` hooks run. **Plugin `onInit` hooks run first, in the order you registered the plugins. The app's hooks run after them.** So a plugin is ready before the app code that depends on it. `onInit` runs once each time the engine starts, before the engine accepts any connection.
::

After the `onInit` hooks finish, the engine is ready and the adapter starts to accept sockets.

## The schema marker table

The engine uses one reserved table, `__livething_meta`, to tell new storage apart from storage that was already set up:

| Column  | Type               | Meaning                                           |
| ------- | ------------------ | ------------------------------------------------- |
| `key`   | `TEXT PRIMARY KEY` | The marker name. The only row is `'initialized'`. |
| `value` | `TEXT NOT NULL`    | The marker value, `'1'`.                          |

At boot, before any schema hook runs, the engine checks whether this table exists:

- **Table exists.** The storage was set up before. The engine still runs every schema hook, so each hook must be idempotent. Stored rows from an earlier run, such as channel memberships, may still be there.
- **Table missing.** The storage is new. The engine runs every schema hook, then creates `__livething_meta` and writes the marker row.

The marker is not a schema version check. LiveThing does not compare versions, and it does not skip hooks when the storage was set up before. The idempotent hooks handle schema changes themselves.

The engine creates `__livething_meta` itself. No capability owns it. The engine writes it after the schema hooks finish, and only when the storage is new.

::warning
`__livething_meta` is reserved. So is every other LiveThing table. They all start with `__livething_` (`__livething_replay`, `__livething_channel_memberships`, `__livething_inbox` and others). Never create your own table with that prefix. If your table has the same name as a LiveThing table, it breaks the data LiveThing stores there.
::

## Two checks, both before the first frame

A server with a wrong configuration never serves a client. Two separate checks stop it:

- **`assemble`**, when you build the definition, catches mistakes in the structure. Examples: two handlers on the same event, a scheduled task with no registered body, a capability that another capability needs but you did not list (such as `replay` without `dedup()`), and a per-handler `rateLimit` override when you did not list the `rateLimit()` capability.
- **The engine**, when it boots, catches everything described above. Compile catches the wire-name rules and replay with a sequence that does not persist. The adapter-requirements step catches an adapter without hibernation. The validate step catches the other rules between capabilities: inbox with a sequence that does not persist, and inbox or `.revalidate()` on a channel that is not persistent.

For example, this definition lists replay with a `sequence()` that does not persist. `assemble` accepts it, but the engine throws at startup, before any frame is handled:

```typescript [server/huddle.ts]
import { server } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [dedup(), sequence(), replay.history()],
})

// `assemble` accepts this definition. The engine rejects it when it starts,
// because replay needs `sequence({ persist: true })`.
export const huddle = base.assemble({ handlers: [] })
```

Change `sequence()` to `sequence({ persist: true })` to fix it. [Built-in replay](/server/replay/built-in) lists everything replay needs.
