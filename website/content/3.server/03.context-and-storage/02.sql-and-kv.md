Your server gets two durable stores on `ctx`. "Durable" means the data stays when the server restarts or hibernates (sleeps while idle and wakes up later). The adapter (the package that runs LiveThing on a platform, such as Node or Cloudflare) provides the storage behind both:

- **`ctx.sql`**: a SQLite database for relational data (data in tables with rows and columns). Use it for tables, queries, and transactions.
- **`ctx.kv`**: a simple key-value store. Each value is saved under a text key. Use it for small pieces of state: flags, counters, small caches.

Every adapter provides both stores. You can use them in connection handlers, in the `onInit` and `onShutdown` lifecycle hooks, in scheduled tasks, and in the [admin context](/server/admin/context) (the `ctx` of code that runs outside any connection, such as a webhook handler).

::note
On Node, the default `sql` storage is an in-memory database, so its data is lost when the process stops. `ctx.kv` uses the same database by default. Give the adapter a file path to keep the data. See [Storage, timers, and WebSockets](/server/adapters/node/node-http#storage-timers-and-websockets).
::

## When to use which

| Use `ctx.sql` when…                                  | Use `ctx.kv` when…                              |
| ---------------------------------------------------- | ----------------------------------------------- |
| You have rows with fields and you query across them. | You have one value behind one key.              |
| You need ordering, filtering, joins, or counts.      | You want a quick flag, counter, or cache entry. |
| You need a multi-step write to be atomic.            | You want a value to expire on its own (TTL).    |

"Atomic" means all the steps happen, or none of them do. "TTL" (time to live) is how long a value stays before it is deleted.

A simple rule: if you would write a `WHERE` or `ORDER BY`, use `ctx.sql`. If you would write `get(key)` / `set(key, value)`, use `ctx.kv`.

## `ctx.sql`

### Running a query

`ctx.sql.exec(query, ...params)` runs one statement. Put a `?` placeholder in the SQL for each value, and pass the values as extra arguments in the same order. This is called binding the values. Never build the SQL string by joining values into it. Bound values keep your queries safe from SQL injection (an attack where a value changes the meaning of the query).

```typescript [server/rooms.ts]
base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.sql.exec(
      'INSERT INTO messages (id, room, user_id, text, sent_at) VALUES (?, ?, ?, ?, ?)',
      crypto.randomUUID(),
      'general',
      ctx.user.id,
      input.text,
      Date.now(),
    )
  },
})
```

### Reading rows

`exec(...)` returns a result cursor (an object that holds the query's rows). Call exactly **one** reader method on it:

| Reader       | Returns                            | Use when                             |
| ------------ | ---------------------------------- | ------------------------------------ |
| `.toArray()` | every matching row as objects      | you expect zero or more rows         |
| `.one()`     | the single matching row, or `null` | you expect at most one row           |
| `.raw()`     | every row as a plain column array  | you want column arrays, no key names |

Pass a row type as a generic (the type in `<...>` after `exec`) so the rows are typed. The generic is only a TypeScript hint. LiveThing does not check the rows at runtime.

```typescript [server/rooms.ts]
base.request('load-history', {
  input: v.object({ before: v.optional(v.number()) }),
  run(ctx, input) {
    const messages = ctx.sql
      .exec<{
        id: string
        text: string
        from: string
        sentAt: number
      }>(
        'SELECT id, text, user_id AS "from", sent_at AS sentAt FROM messages ' +
          'WHERE room = ? AND sent_at < ? ORDER BY sent_at DESC LIMIT 50',
        'general',
        input.before ?? Date.now(),
      )
      .toArray()
    // messages is typed Array<{ id: string; text: string; from: string; sentAt: number }>
    return { messages }
  },
})
```

`.one()` returns `null` when nothing matched. It **throws** when more than one row matched, because it is for single-row reads. If a query can match many rows and you want the first, add `LIMIT 1` or use `.toArray()[0]` instead.

```typescript [server/rooms.ts]
base.request('room-member-count', {
  input: v.object({ room: v.string() }),
  run(ctx, input) {
    const row = ctx.sql
      .exec<{
        c: number
      }>(
        'SELECT COUNT(*) AS c FROM room_members WHERE room = ?',
        input.room,
      )
      .one()
    return { count: row ? Number(row.c) : 0 }
  },
})
```

`.raw()` leaves out the key names and returns each row as an array of column values (`unknown[][]`). This is useful when you only need the column positions, or when you send the rows to the client as they are:

```typescript [server/huddle.ts]
base.request('list-bans', {
  input: v.object({}),
  run(ctx) {
    const rows = ctx.sql
      .exec('SELECT user_id, reason FROM bans ORDER BY user_id')
      .raw()
    return { rows }
  },
})
```

::warning
You can read a result cursor only **once**. Call exactly one reader on it. Calling a second reader on the same result throws. If you need the rows twice, store the first reader's output in a variable.

```typescript [server/rooms.ts]
const result = ctx.sql.exec<{ c: number }>(
  'SELECT COUNT(*) AS c FROM messages',
)
result.one()
result.toArray() // throws: the cursor was already read
```

::

### Transactions

`ctx.sql.transaction(fn)` runs several queries as one atomic unit. It **commits** (saves all the changes) when the callback returns. It **rolls back** (undoes all the changes) if the callback throws, and then throws the same error to your code. The callback must be synchronous, so do async work before or after it. Use a transaction whenever a multi-step write must happen completely or not at all.

```typescript [server/rooms.ts]
base.on('archive-room', {
  input: v.object({ roomId: v.string() }),
  run(ctx, input) {
    ctx.sql.transaction((tx) => {
      tx.exec(
        'UPDATE rooms SET archived = 1 WHERE id = ?',
        input.roomId,
      )
      tx.exec('DELETE FROM room_members WHERE room = ?', input.roomId)
    })
  },
})
```

The `tx` passed to your callback has the same `exec(...)` as `ctx.sql`. If anything inside the callback throws, no write inside it is saved:

```typescript [server/rooms.ts]
base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    try {
      ctx.sql.transaction((tx) => {
        tx.exec(
          'INSERT INTO messages (id, room, user_id, text, sent_at) VALUES (?, ?, ?, ?, ?)',
          crypto.randomUUID(),
          'general',
          ctx.user.id,
          input.text,
          Date.now(),
        )
        throw new Error('changed my mind') // rolls back the INSERT above
      })
    } catch {
      // The transaction throws the error again after rolling back.
      // The row is not saved.
    }
  },
})
```

### Statement limits

`ctx.sql` runs on a real SQLite database, and every SQLite database limits how much one statement can carry. LiveThing does **not** set these limits. They come from the SQL engine your adapter runs on, and they are very different between adapters:

| Adapter                                           | Bound parameters per statement | Length of the SQL text | Size of one stored string, one stored BLOB, or one whole table row |
| ------------------------------------------------- | ------------------------------ | ---------------------- | ------------------------------------------------------------------ |
| Cloudflare (Durable Objects SQLite)               | 100                            | 100 KB                 | 2 MB                                                               |
| Node, Deno, Bun (`better-sqlite3` / stock SQLite) | 32,766                         | ~1 GB                  | ~1 GB                                                              |

A BLOB is binary data (raw bytes) stored in a column. Cloudflare's numbers are documented at [developers.cloudflare.com/durable-objects/platform/limits](https://developers.cloudflare.com/durable-objects/platform/limits/). The stock SQLite numbers are at [sqlite.org/limits.html](https://sqlite.org/limits.html).

The Cloudflare limits are much lower. Some queries use one `?` per item, such as a batched `INSERT` or `WHERE id IN (?, ?, ?, ...)`. Such a query can work on Node and then fail on Cloudflare as soon as it binds more than 100 values.

### Why a 2 MB value fits in a 100 KB statement

These two numbers seem to disagree. They do not, because they measure two different things, and the database receives the two things separately.

The **SQL text** is the query string itself. The **bound values** are the data you pass with it, one for each `?`. The database receives them as two separate pieces and never joins them into one string.

So this stores a 2 MB document through a statement whose text is about 35 bytes:

```typescript [server/rooms.ts]
const longMessage = 'a'.repeat(2_000_000) // 2 MB

// The SQL text is only this short string: about 60 bytes.
// The 2 MB travels separately as a bound value.
ctx.sql.exec(
  'INSERT INTO messages (id, text) VALUES (?, ?)',
  crypto.randomUUID(),
  longMessage,
)
```

If you build the same statement by joining the value into the text, it fails, because now the 2 MB **is** the SQL text:

```typescript [server/rooms.ts]
// Do not do this. The statement text is now 2 MB, far past Cloudflare's 100 KB.
ctx.sql.exec(
  `INSERT INTO messages (id, text) VALUES ('${crypto.randomUUID()}', '${longMessage}')`,
)
```

Always pass values as `?` parameters. This keeps the SQL text under the length limit. It also stops a value that contains a quote character from changing the meaning of your query.

If you build SQL with a changing number of bound values, do not assume a limit. Read the limit of the adapter you are running on. Each adapter gives it as `ctx.sql.limits`, an object with three fields:

```typescript [server/rooms.ts]
const limits = ctx.sql.limits
// limits.maxBoundParams:    most `?` placeholders one statement may bind
// limits.maxStatementBytes: most bytes the SQL text may be
// limits.maxValueBytes:     most bytes one stored string, one stored BLOB,
//                           or one whole table row may be
```

This handler splits a long list into batches, so no `INSERT` binds more values than the adapter allows:

```typescript [server/rooms.ts]
base.on('create-invites', {
  input: v.object({ room: v.string(), tokens: v.array(v.string()) }),
  run(ctx, input) {
    const { maxBoundParams } = ctx.sql.limits
    const paramsPerItem = 3 // one `?` each for token, room, expires_at
    const batchSize = Math.floor(maxBoundParams / paramsPerItem)
    const expiresAt = Date.now() + 86_400_000

    for (let i = 0; i < input.tokens.length; i += batchSize) {
      const batch = input.tokens.slice(i, i + batchSize)
      const placeholders = batch.map(() => '(?, ?, ?)').join(', ')
      const values = batch.flatMap((token) => [
        token,
        input.room,
        expiresAt,
      ])
      ctx.sql.exec(
        `INSERT INTO invites (token, room, expires_at) VALUES ${placeholders}`,
        ...values,
      )
    }
  },
})
```

### Creating tables once

Create your tables in the onInit hook (a function that runs when the server starts, before any connection). The onInit context has `ctx.sql` too. `CREATE TABLE IF NOT EXISTS` creates the table only the first time, so it is safe to run on every start.

```typescript [server/huddle.ts]
base.onInit((ctx) => {
  ctx.sql.exec(`
    CREATE TABLE IF NOT EXISTS messages (
      id TEXT PRIMARY KEY,
      room TEXT NOT NULL,
      user_id TEXT NOT NULL,
      text TEXT NOT NULL,
      sent_at INTEGER NOT NULL
    )
  `)
})
```

See [Lifecycle hooks](/server/lifecycle-and-intercept/hooks) for the onInit hook.

## Reserved LiveThing tables

Every table that LiveThing creates starts with the reserved prefix `__livething_`, for example `__livething_replay` and `__livething_scheduled`. **Never create your own table (or index) with that prefix**, even if you do not use the capability behind it yet.

::caution
`CREATE TABLE IF NOT EXISTS` does nothing when a table with that name already exists. It does not check that the existing table has the same columns. Here is what can go wrong:

1. You create your own table named `__livething_replay` before you add `replay.history()` to your capabilities. Nothing fails.
2. Later you add `replay.history()`. Its `CREATE TABLE IF NOT EXISTS __livething_replay ...` finds your table and does nothing. You get **no** "table already exists" error.
3. Replay then reads and writes your table instead of its own. You see confusing SQL errors later, or wrong data with no error if a column name matches by chance. Nothing fails at startup, where the cause would be easy to find.
   ::

`ctx.kv` (below) rejects reserved keys, but `ctx.sql` has **no runtime check** for reserved table names. LiveThing does not stop you from using the `__livething_` prefix. You must avoid it yourself.

The full list of reserved tables:

| Table                             | Purpose                                                                                                            | Owned by                                                                           |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `__livething_meta`                | A marker LiveThing reads to tell whether the storage is new. Table setup still runs on every start.                | LiveThing internal. See [Compile & boot](/server/under-the-hood/compile-and-boot). |
| `__livething_alarm_state`         | One retry time, kept while LiveThing retries a failed write to the durable alarm (a timer that survives restarts). | LiveThing internal.                                                                |
| `__livething_node_alarm`          | The Node adapter's one saved alarm time and a counter that goes up each time the alarm changes.                    | Node adapter only.                                                                 |
| `__livething_kv`                  | The Node adapter's default `ctx.kv` store: keys, values, and optional expiry times.                                | Node adapter only.                                                                 |
| `__livething_connections`         | One row per live connection, restored when the server wakes from hibernation.                                      | [Hibernation](/server/server/hibernation)                                          |
| `__livething_channel_memberships` | Durable record of which channels each user belongs to.                                                             | [Membership & Presence](/server/channels/membership-and-presence)                  |
| `__livething_tags`                | Durable (persistent) tag rows per user.                                                                            | [tags](/server/capabilities/tags)                                                  |
| `__livething_sequence`            | Next sequence number to give out, per scope.                                                                       | [sequence](/server/capabilities/sequence)                                          |
| `__livething_scheduled`           | Queued scheduled-task runs waiting to run.                                                                         | [scheduled](/server/capabilities/scheduled)                                        |
| `__livething_scheduled_dlq`       | Failed scheduled-task runs that used up all their retries.                                                         | [scheduled](/server/capabilities/scheduled)                                        |
| `__livething_replay`              | Recorded outgoing messages kept so clients can catch up after a reconnect.                                         | [replay](/server/capabilities/replay)                                              |
| `__livething_replay_watermark`    | Per-scope and per-user cursor that marks how much old replay history was removed.                                  | [replay](/server/capabilities/replay)                                              |
| `__livething_inbox`               | Held per-member rows waiting to be delivered and acknowledged.                                                     | [inbox](/server/capabilities/inbox)                                                |
| `__livething_inbox_watermark`     | Per-member cursor that marks how much old inbox history was removed.                                               | [inbox](/server/capabilities/inbox)                                                |
| `__livething_inbox_receipts`      | Per-member received/read cursors for a channel.                                                                    | [inbox](/server/capabilities/inbox)                                                |
| `__livething_last_seen`           | One row per user: its last-seen timestamp.                                                                         | [lastSeen](/server/capabilities/last-seen)                                         |
| `__livething_streams`             | One row per durable stream (cursor or recorded).                                                                   | [streams](/server/capabilities/streams)                                            |
| `__livething_stream_chunks`       | Recorded chunks for a recorded stream.                                                                             | [streams](/server/capabilities/streams)                                            |
| `__livething_stream_checkpoints`  | Saved cursor checkpoints for a cursor stream.                                                                      | [streams](/server/capabilities/streams)                                            |
| `__livething_stream_subscribers`  | Per-subscriber reconnect cursor for a broadcast stream.                                                            | [streams](/server/capabilities/streams)                                            |

This list gives only names and purposes. If a table's columns are documented, they are on the page of the capability that owns it. LiveThing also creates some `__livething_idx_*` indexes for these tables. The same rule applies to index names.

## `ctx.kv`

`ctx.kv` is a small async key-value store. Every method returns a `Promise`, so `await` each call.

| Method                             | Returns             | What it does                                                         |
| ---------------------------------- | ------------------- | -------------------------------------------------------------------- |
| `ctx.kv.get(key)`                  | `Promise<unknown>`  | Read one value. Resolves to `undefined` when the key does not exist. |
| `ctx.kv.set(key, value, options?)` | `Promise<void>`     | Write one value. Optional `{ ttl }` in milliseconds sets an expiry.  |
| `ctx.kv.delete(key)`               | `Promise<void>`     | Remove one key.                                                      |
| `ctx.kv.list(prefix?)`             | `Promise<string[]>` | List keys, optionally only those that start with `prefix`.           |

```typescript [server/rooms.ts]
base.request('save-draft', {
  input: v.object({ room: v.string(), text: v.string() }),
  async run(ctx, input) {
    const key = `draft:${ctx.user.id}:${input.room}`
    await ctx.kv.set(key, input.text)
    const saved = (await ctx.kv.get(key)) as string | undefined
    return { saved }
  },
})
```

::note
`ctx.kv.get(...)` resolves to `unknown`, because the store does not know your value's type. When you read a value back, check its type, or cast it (tell TypeScript which type it is), as the `as string | undefined` above does. `get` is the only KV method that returns `unknown`.
::

::warning
KV keys that start with `__` or contain `::` are **reserved** for [plugins](/server/plugins/overview) (reusable packages of server features). Each plugin stores its keys as `__<plugin id>::<key>`. If you pass such a key to any `ctx.kv` method (`get`, `set`, `delete`, `list`), the call fails with an error at runtime. Do not use either form in your own keys.
::

### TTL: expiring values

Pass `{ ttl }` (in milliseconds) to `set` to make a value expire on its own. This is useful for typing indicators, short locks, or rate-limit windows.

```typescript [server/rooms.ts]
base.on('start-typing', {
  input: v.object({ room: v.string() }),
  async run(ctx, input) {
    // Clears itself after 5 seconds, even if "stop typing" never arrives.
    await ctx.kv.set(`typing:${input.room}:${ctx.user.id}`, true, {
      ttl: 5_000,
    })
  },
})
```

A `ttl` of `0` means **no expiry**. It does not mean "expire now", so the value stays readable. The Node and Cloudflare adapters log a warning when you pass `{ ttl: 0 }`, because people often pass `0` by mistake when they mean "expire now". When you want no expiry, leave out `ttl` instead of passing `0`:

```typescript [server/admin.ts]
await ctx.kv.set('maintenance-mode', 'on') // no expiry, no warning (preferred)
await ctx.kv.set('maintenance-mode', 'on', { ttl: 0 }) // also no expiry, but logs a warning
const value = (await ctx.kv.get('maintenance-mode')) as
  | string
  | undefined
```

::note
The warning never includes the key. Keys often contain user or session IDs, so the adapter keeps them out of the logs.
::

### Listing by prefix

`list(prefix)` returns only the keys that start with the prefix. If you give related keys the same prefix (for example `typing:<room>:`), you can list one group:

```typescript [server/rooms.ts]
base.request('who-is-typing', {
  input: v.object({ room: v.string() }),
  async run(ctx, input) {
    const keys = await ctx.kv.list(`typing:${input.room}:`)
    return { keys }
  },
})
```

Calling `list()` with no prefix returns all your own keys. Plugin keys (the reserved forms above) are left out, so you never see a plugin's storage.

## Storage and retention

`ctx.sql` and `ctx.kv` are durable: restarts and hibernation do not delete them. (On Node, give the adapter a file path, as the note at the top of this page explains.) You do not need to turn this on for your own rows and keys. The state that LiveThing manages, such as channel membership and replay history, is kept in the [reserved `__livething_` tables](#reserved-livething-tables) above and is durable in the same way. The options of the capability that owns a table set how long its data is kept (its retention). They do not turn durability on or off.
