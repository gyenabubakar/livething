Your server gets two durable stores on `ctx`, both backed by the adapter's storage and both surviving restarts and hibernation:

- **`ctx.sql`** — a SQLite database for relational data: tables, queries, transactions.
- **`ctx.kv`** — a simple key-value store for lightweight state: flags, counters, small caches.

Both are available on the connection context and on the init, scheduled, and shutdown contexts. Both are bound lazily — reading `ctx.sql` or `ctx.kv` never throws by itself; the check happens the moment you call a method on them, and it throws there if the adapter provides no storage.

## When to use which

| Use `ctx.sql` when…                                  | Use `ctx.kv` when…                              |
| ---------------------------------------------------- | ----------------------------------------------- |
| You have rows with fields and you query across them. | You have one value behind one key.              |
| You need ordering, filtering, joins, or counts.      | You want a quick flag, counter, or cache entry. |
| You need a multi-step write to be atomic.            | You want a value to expire on its own (TTL).    |

A rough rule: if you would write a `WHERE` or `ORDER BY`, reach for `ctx.sql`. If you would write `get(key)` / `set(key, value)`, reach for `ctx.kv`.

## `ctx.sql`

### Running a query

`ctx.sql.exec(query, ...params)` runs one statement. Bind values with positional `?` placeholders — pass them as extra arguments, never by string-building the SQL. This keeps queries injection-safe.

```typescript [insert.ts]
base.on('save-note', {
  input: v.object({ title: v.string(), body: v.string() }),
  run(ctx, input) {
    ctx.sql.exec(
      'INSERT INTO notes (title, body) VALUES (?, ?)',
      input.title,
      input.body,
    )
  },
})
```

### Reading rows

`exec(...)` returns a result cursor. Call exactly **one** reader on it:

| Reader       | Returns                            | Use when                             |
| ------------ | ---------------------------------- | ------------------------------------ |
| `.toArray()` | every matching row as objects      | you expect zero or more rows         |
| `.one()`     | the single matching row, or `null` | you expect at most one row           |
| `.raw()`     | every row as a plain column array  | you want column arrays, no key names |

Pass a generic row type so the rows are typed. The generic is a TypeScript hint only — LiveThing does not validate rows at runtime.

```typescript [read.ts]
base.on('get-notes', {
  input: v.object({}),
  run(ctx) {
    const notes = ctx.sql
      .exec<{
        id: number
        title: string
        body: string
      }>('SELECT id, title, body FROM notes ORDER BY id DESC')
      .toArray()
    // notes is typed Array<{ id: number; title: string; body: string }>
    ctx.send('notes-list', { notes })
  },
})
```

`.one()` returns `null` when nothing matched, and **throws** when more than one row matched — it is for single-row reads. If a query can match many rows and you want the first, add `LIMIT 1` or use `.toArray()[0]` instead.

```typescript [one.ts]
base.on('count-notes', {
  input: v.object({}),
  run(ctx) {
    const row = ctx.sql
      .exec<{ c: number }>('SELECT COUNT(*) AS c FROM notes')
      .one()
    ctx.send('count-result', { count: row ? Number(row.c) : 0 })
  },
})
```

`.raw()` skips key names and hands back column arrays — useful when you only care about positions or are shipping rows straight over the wire:

```typescript [raw.ts]
base.on('dump-notes', {
  input: v.object({}),
  run(ctx) {
    const rows = ctx.sql
      .exec('SELECT id, title FROM notes ORDER BY id DESC')
      .raw()
    ctx.send('dump-result', { rows: rows as unknown[][] })
  },
})
```

::warning
A result cursor is **one-shot** — you may call exactly one reader on it. Calling a second reader on the same result throws. If you need the rows twice, store the first reader's output in a variable.

```typescript [reuse.ts]
const result = ctx.sql.exec<{ c: number }>(
  'SELECT COUNT(*) AS c FROM notes',
)
result.one()
result.toArray() // throws — the cursor was already read
```

::

### Transactions

`ctx.sql.transaction(fn)` runs several queries as one atomic unit. It **commits** when the callback returns and **rolls back** if the callback throws — and rethrows that error to you. The callback must be synchronous: do async work before or after it. Use it whenever a multi-step write must be all-or-nothing.

```typescript [transfer.ts]
base.on('transfer', {
  input: v.object({
    from: v.string(),
    to: v.string(),
    amount: v.number(),
  }),
  run(ctx, input) {
    ctx.sql.transaction((tx) => {
      tx.exec(
        'UPDATE wallets SET balance = balance - ? WHERE id = ?',
        input.amount,
        input.from,
      )
      tx.exec(
        'UPDATE wallets SET balance = balance + ? WHERE id = ?',
        input.amount,
        input.to,
      )
    })
  },
})
```

The `tx` passed to your callback has the same `exec(...)` as `ctx.sql`. If anything inside throws, neither write lands:

```typescript [rollback.ts]
base.on('try-transfer', {
  input: v.object({}),
  run(ctx) {
    try {
      ctx.sql.transaction((tx) => {
        tx.exec(
          'INSERT INTO notes (title, body) VALUES (?, ?)',
          'pending',
          'x',
        )
        throw new Error('changed my mind') // rolls back the INSERT above
      })
    } catch {
      // The transaction rethrows after rolling back — the row is gone.
    }
  },
})
```

### Statement limits

`ctx.sql` runs on top of a real SQLite database, and every SQLite database caps how much one statement can carry. These are **not** limits LiveThing invents — they belong to the SQL engine your adapter runs on, and they differ a lot by adapter:

| Adapter                                                      | Bound parameters per statement                       | Length of the SQL text | Size of one stored string, one stored BLOB, or one whole table row |
| ------------------------------------------------------------ | ---------------------------------------------------- | ---------------------- | ------------------------------------------------------------------ |
| Cloudflare (Durable Objects SQLite)                          | 100                                                  | 100 KB                 | 2 MB                                                               |
| Node, Deno, Bun (`node:sqlite` / `bun:sqlite`, stock SQLite) | tens of thousands (32,766 or more, engine-dependent) | ~1 GB                  | ~1 GB                                                              |

Cloudflare's numbers are documented at [developers.cloudflare.com/durable-objects/platform/limits](https://developers.cloudflare.com/durable-objects/platform/limits/); the stock SQLite numbers at [sqlite.org/limits.html](https://sqlite.org/limits.html). The Cloudflare limits are much tighter — a query built with one `?` per item (a batched `INSERT`, or `WHERE id IN (?, ?, ?, ...)`) that works fine against `node:sqlite` in a test can fail against Cloudflare at a surprisingly small item count.

### Why a 2 MB value fits in a 100 KB statement

Those two numbers look like they contradict each other. They do not, because they measure two different things that travel separately.

The **SQL text** is the query string itself. The **bound values** are the data you pass alongside it for each `?`. The database receives them as two separate pieces and never joins them into one string.

So this stores a 2 MB document through a statement whose text is about 40 bytes:

```typescript [bound.ts]
const document = 'a'.repeat(2_000_000) // 2 MB

// The SQL text is just this short string — about 40 bytes.
// The 2 MB travels separately as a bound value.
ctx.sql.exec('INSERT INTO docs (body) VALUES (?)', document)
```

Build the same statement by joining the value into the text and it breaks, because now the 2 MB **is** the SQL text:

```typescript [inlined.ts]
// Do not do this. The statement text is now 2 MB, far past Cloudflare's 100 KB.
ctx.sql.exec(`INSERT INTO docs (body) VALUES ('${document}')`)
```

Always pass values as `?` parameters. Besides keeping you under the statement-length limit, it is what stops a value containing a quote character from changing the meaning of your query.

If you build SQL with a variable number of bound values, read the ceiling for the adapter you are actually running on instead of assuming a number. Each adapter exposes it as `ctx.sql.limits`, an object with three fields:

```typescript [limits.ts]
const limits = ctx.sql.limits
// limits.maxBoundParams    — most `?` placeholders one statement may bind
// limits.maxStatementBytes — most bytes the SQL text may be
// limits.maxValueBytes     — most bytes one stored string, one stored BLOB,
//                            or one whole table row may be
```

```typescript [batch-check.ts]
base.on('bulk-insert', {
  input: v.object({ items: v.array(v.string()) }),
  run(ctx, input) {
    const { maxBoundParams } = ctx.sql.limits
    const paramsPerItem = 1 // one `?` per item
    const batchSize = Math.floor(maxBoundParams / paramsPerItem)

    for (let i = 0; i < input.items.length; i += batchSize) {
      const batch = input.items.slice(i, i + batchSize)
      const placeholders = batch.map(() => '?').join(', ')
      ctx.sql.exec(
        `INSERT INTO items (name) VALUES ${placeholders}`,
        ...batch,
      )
    }
  },
})
```

### Creating tables once

Run table creation in the onInit hook so it happens once at startup, before any connection. The onInit context has `ctx.sql` too.

```typescript [init.ts]
base.onInit((ctx) => {
  ctx.sql.exec(`
    CREATE TABLE IF NOT EXISTS notes (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      title TEXT NOT NULL,
      body TEXT NOT NULL
    )
  `)
})
```

See [Lifecycle hooks](/server/lifecycle-and-intercept/hooks) for the onInit hook.

## Reserved LiveThing tables

Every table LiveThing itself creates is named with the reserved `__livething_` prefix — `__livething_replay`, `__livething_scheduled`, and so on. **Never create your own table (or index) under that prefix**, whether or not you are using the capability behind it yet.

::caution
`CREATE TABLE IF NOT EXISTS` only complains when a real conflict occurs — it never checks that an existing table's columns match what it's about to declare. So if you hand-create a table named, say, `__livething_replay` before you add `replay()` to your capabilities, nothing fails at that point. Add `replay()` later, and its own `CREATE TABLE IF NOT EXISTS __livething_replay ...` finds a table with that name already there and does nothing — you get **no** "table already exists" error to point at the mistake. Replay then reads and writes through your table's columns instead of its own, and the failures show up later as confusing SQL errors (or silently wrong reads, if a column name happens to match by accident) instead of at boot, where you could actually see the cause.
::

Unlike `ctx.kv` (below), `ctx.sql` has **no runtime guard** against a reserved table name — nothing stops the collision at the call site. Keeping clear of `__livething_` is a convention you have to hold yourself; LiveThing does not enforce it for you.

The full reserved set today:

| Table                             | Purpose                                                                                                         | Owned by                                                                         |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `__livething_meta`                | Initialization marker the engine reads to distinguish fresh storage; schema-init hooks still run on every boot. | Engine internal — see [Compile & boot](/server/under-the-hood/compile-and-boot). |
| `__livething_alarm_state`         | One retry deadline kept while the engine retries a failed durable-alarm provider write.                         | Engine internal.                                                                 |
| `__livething_node_alarm`          | Node adapter's one persisted alarm deadline and generation counter.                                             | Node adapter only.                                                               |
| `__livething_kv`                  | Node adapter's durable `ctx.kv` keys, values, and optional expiry times.                                        | Node adapter only.                                                               |
| `__livething_connections`         | One row per live connection, restored on a hibernation wake.                                                    | [Hibernation](/server/server/hibernation)                                        |
| `__livething_channel_memberships` | Durable record of which channels each user belongs to.                                                          | [Membership & Presence](/server/channels/membership-and-presence)                |
| `__livething_tags`                | Durable (persistent) tag rows per user.                                                                         | [tags](/server/capabilities/tags)                                                |
| `__livething_sequence`            | Next sequence number to hand out, per scope.                                                                    | [sequence](/server/capabilities/sequence)                                        |
| `__livething_scheduled`           | Queued scheduled-task runs waiting to fire.                                                                     | [scheduled](/server/capabilities/scheduled)                                      |
| `__livething_scheduled_dlq`       | Failed scheduled-task runs that exhausted their retries.                                                        | [scheduled](/server/capabilities/scheduled)                                      |
| `__livething_replay`              | Recorded outgoing messages kept for reconnect catch-up.                                                         | [replay](/server/capabilities/replay)                                            |
| `__livething_replay_watermark`    | Per-scope cursor marking how far replay history has been evicted.                                               | [replay](/server/capabilities/replay)                                            |
| `__livething_inbox`               | Held per-member rows waiting to be delivered and acknowledged.                                                  | [inbox](/server/capabilities/inbox)                                              |
| `__livething_inbox_watermark`     | Per-member cursor marking how far inbox history has been evicted.                                               | [inbox](/server/capabilities/inbox)                                              |
| `__livething_inbox_receipts`      | Per-member received/read cursors for a channel.                                                                 | [inbox](/server/capabilities/inbox)                                              |
| `__livething_last_seen`           | One row per user: its last-seen timestamp.                                                                      | [lastSeen](/server/capabilities/last-seen)                                       |
| `__livething_streams`             | One row per durable stream (resumable or recorded).                                                             | [streams](/server/capabilities/streams)                                          |
| `__livething_stream_chunks`       | Recorded chunks for a recorded stream.                                                                          | [streams](/server/capabilities/streams)                                          |
| `__livething_stream_subscribers`  | Per-subscriber resume cursor for a broadcast stream.                                                            | [streams](/server/capabilities/streams)                                          |

This list is names and purpose only — the owning capability's own page is where full column schema lives, if it publishes one. LiveThing also creates a handful of `__livething_idx_*` indexes alongside these tables; the same rule applies to index names.

## `ctx.kv`

A small async key-value store. Every method returns a `Promise`, so `await` them.

| Method                             | Returns             | What it does                                                        |
| ---------------------------------- | ------------------- | ------------------------------------------------------------------- |
| `ctx.kv.get(key)`                  | `Promise<unknown>`  | Read one value. Resolves `undefined` when the key is absent.        |
| `ctx.kv.set(key, value, options?)` | `Promise<void>`     | Write one value. Optional `{ ttl }` in milliseconds sets an expiry. |
| `ctx.kv.delete(key)`               | `Promise<void>`     | Remove one key.                                                     |
| `ctx.kv.list(prefix?)`             | `Promise<string[]>` | List keys, optionally only those starting with `prefix`.            |

```typescript [kv-basic.ts]
const handleKvSetGet = base.on('kv-set-get', {
  input: v.object({ key: v.string(), value: v.string() }),
  async run(ctx, input) {
    await ctx.kv.set(input.key, input.value)
    const value = (await ctx.kv.get(input.key)) as string | null
    ctx.send('kv-result', { key: input.key, value })
  },
})
```

::note
`ctx.kv.get(...)` resolves `unknown` — the store does not know your value's type. Narrow or cast it when you read it back, as the `as string | null` above does. This is the one genuine `unknown` boundary in the KV API.
::

::warning
KV keys starting with `__` or containing `::` are **reserved** for the plugin namespace. Passing one to any `ctx.kv` method (`get`, `set`, `delete`, `list`) throws at runtime, so keep your own keys clear of both forms.
::

### TTL — expiring values

Pass `{ ttl }` (milliseconds) to `set` to make a value expire on its own. Good for typing indicators, short locks, or rate-limit windows.

```typescript [ttl.ts]
base.on('start-typing', {
  input: v.object({}),
  async run(ctx) {
    // Auto-clears after 5 seconds even if "stop typing" never arrives.
    await ctx.kv.set(`typing:${ctx.user.id}`, true, {
      ttl: 5_000,
    })
  },
})
```

A `ttl` of `0` means **no expiry**, not "expire now" — the value stays readable. But the Cloudflare adapter logs a warning when you pass `{ ttl: 0 }`, because `0` is a common mistake for "expire immediately". Omit `ttl` when you want no expiry instead of passing `0`:

```typescript [ttl-zero.ts]
await ctx.kv.set('flag', 'on') // no expiry — preferred, no warning
await ctx.kv.set('flag', 'on', { ttl: 0 }) // also no expiry, but logs a warning
const value = (await ctx.kv.get('flag')) as string | null
```

::note
The warning never includes the key — keys often carry user or session IDs, so the adapter keeps them out of log output.
::

### Listing by prefix

`list(prefix)` returns only keys that start with the prefix — namespace your keys and you can scan one group:

```typescript [list.ts]
base.on('typing-list', {
  input: v.object({ room: v.string() }),
  async run(ctx, input) {
    const keys = await ctx.kv.list(`typing:${input.room}:`)
    ctx.send('typing-list-result', { keys })
  },
})
```

Calling `list()` with no prefix returns all keys in your own namespace — framework-internal keys (the plugin-namespaced ones) are filtered out, so you never see another plugin's storage.

## Storage and retention

`ctx.sql` and `ctx.kv` are always durable — restarts and hibernation do not wipe them. Every adapter guarantees this storage, so your own rows and keys here are already safe without listing anything. Framework-managed state (channel membership, replay history — kept in the [reserved `__livething_` tables](#reserved-livething-tables) above) is durable the same way; the capability that owns each table is what configures its retention, not what turns its durability on.
