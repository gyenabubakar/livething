A handler receives `ctx` as its first argument. When a helper function needs `ctx`, you normally pass it down as an argument. In a deep call chain, this is repetitive. The `context` object lets a helper read the `ctx` of the handler that is running now, so you do not pass it down.

```typescript [server/permissions.ts]
import { context } from '@livething/server'
import { Forbidden } from '../shared/errors'
import { base } from './huddle'

export function requireAdmin() {
  const ctx = context.connection(base)
  if (ctx.meta.role !== 'admin') {
    throw Forbidden({ reason: 'only an admin may do this' })
  }
}
```

`Forbidden` is a typed error that the server lists in its [`errors([...])`](/server/capabilities/errors) capability.

```typescript [server/rooms.ts]
import * as v from 'valibot'
import { base } from './huddle'
import { requireAdmin } from './permissions'

base.on('archive-room', {
  input: v.object({ roomId: v.string() }),
  async run(ctx, input) {
    requireAdmin() // no ctx argument
    ctx.sql.exec(
      'UPDATE rooms SET archived = 1 WHERE id = ?',
      input.roomId,
    )
  },
})
```

`context.connection(base)` returns the same object that `run(ctx, ...)` received. It works after an `await` too. Two handlers that run at the same time each see their own `ctx`.

## The accessors

Each kind of code that LiveThing runs has its own accessor, because each kind has a different `ctx`. Pass the value that `server(...)` returned (`base`), or the channel that `base.channel(...)` returned.

| Accessor                            | Returns the `ctx` of                                                                                                                                                                                                                                                                                  |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `context.connection(base)`          | An event, request or stream handler of the server, a top-level [intercept](/server/lifecycle-and-intercept/intercept), and the `onConnect`, `onDisconnect`, `onPing`, `onPong`, `onError` and `onValidationError` hooks. The `onError` and `onValidationError` hooks work for events in a channel too |
| `context.channel(channel)`          | An event, request or stream handler of one channel, and an intercept of that channel. It has `ctx.channel`, and its params and events are typed from that channel                                                                                                                                     |
| `context.channelLifecycle(channel)` | The `subscribe`, `unsubscribe` and `sessionEnd` hooks of one channel. It has the channel's own handles, such as `ctx.channel.inbox` and `ctx.channel.request`, when the channel has them                                                                                                              |
| `context.channelGate(channel)`      | The `check`, `commit` and `revalidate` hooks of one channel. These hooks do not have `ctx.channel.inbox`, `readReceipts`, `request` or `broadcastRequest`, so the type leaves them out                                                                                                                |
| `context.task(base)`                | A [scheduled task](/server/handlers/scheduled) handler                                                                                                                                                                                                                                                |
| `context.init(base)`                | An `onInit` hook                                                                                                                                                                                                                                                                                      |
| `context.shutdown(base)`            | An `onShutdown` hook                                                                                                                                                                                                                                                                                  |
| `context.upgrade(base)`             | An [`upgrade` function](/server/server/upgrade#the-upgrade-ctx): the app's with the app's `base`, or a plugin's own with that plugin's own `base`, where it is the plugin's scoped `ctx`                                                                                                              |

There is no accessor that works in every kind of code. A helper that needs only storage can take `ctx.sql` (the `SQLProvider` type) as an argument.

::note
The type that `context.connection(base)` and `context.channel(channel)` return does not have `ctx.stream`. Only the `ctx` of a stream handler has it, so read `ctx.stream.signal` from the `ctx` argument of the handler.
::

## The types

The return type is the type that a handler of that `base` or channel receives. It has the same events, the same `ctx.meta` and the same fields that capabilities add:

```typescript [server/permissions.ts]
const ctx = context.connection(base)
ctx.send('notification', { title: 'Hi', body: 'Welcome' }) // checked against emits(...)
ctx.meta.role // typed from your upgrade function
```

A channel accessor also has `ctx.channel`, typed from the channel. Here `rooms` is the channel from `base.channel(['rooms', 'room:{roomId}'], ...)`, exported from `server/rooms.ts`:

```typescript [server/room-context.ts]
import { context } from '@livething/server'
import { rooms } from './rooms'

export function currentRoomId() {
  return context.channel(rooms).channel.params.roomId // string
}
```

::note
The hooks of a channel have two accessors, because they have two different `ctx` types. In the `check`, `commit` and `revalidate` hooks, `ctx.channel.inbox`, `ctx.channel.readReceipts`, `ctx.channel.request` and `ctx.channel.broadcastRequest` do not exist, so `context.channelGate(channel)` does not list them. Use `context.channelLifecycle(channel)` in the `subscribe`, `unsubscribe` and `sessionEnd` hooks, where they do exist. Calling the wrong one throws an error that names the accessor to use.
::

## When an accessor throws

Every accessor is a runtime check. It throws an error that starts with `[livething]` in these cases:

- **Outside an invocation.** No handler or hook is running, for example in a callback that was created before any handler ran.
- **The wrong kind.** For example, `context.task(base)` inside an event handler. The message names the accessor to use instead.
- **The wrong server or channel.** The `base` or channel that you passed is not the one that is running.

Some code is not covered:

- **Outgoing hooks** (`onOutgoing`) always throw, because the connection that receives a frame is often not the one that sent it.
- **Custom replay hooks and translators** open no context. An accessor there can throw, or return the `ctx` of the unrelated handler that caused the call.
- **A plugin's own `onInit`, `onShutdown`, `onPing` and `onPong` hooks** open no context either.

A plugin does not know the app's `base`. The channels that a plugin declares have no accessor either: passing one to `context.channel`, `context.channelGate` or `context.channelLifecycle` throws at runtime, even when TypeScript accepts it. A plugin's own `base` is accepted only by `context.upgrade`, inside the plugin's own `upgrade`, where it returns the plugin's scoped `ctx`. Inside a plugin's event handler, an accessor returns the app's own `ctx`, not the plugin's scoped `ctx`.

## Stale context

The context follows the async call chain, not the handler that is "current". A timer that a handler starts still sees that handler's `ctx` when it fires, after the handler has returned. The connection may be closed by then. LiveThing does not check this for you. `ctx.send` still hands the frame to the closed socket, and what happens next depends on the runtime. Code that runs later should not assume that its connection is still open.

```typescript [server/huddle.ts]
base.on('remind-me', {
  run() {
    setTimeout(() => {
      // Still the same connection's ctx, even if the socket has closed.
      const later = context.connection(base)
      later.send('notification', {
        title: 'Reminder',
        body: 'Time is up',
      })
    }, 60_000)
  },
})
```

For work that must last longer than the connection, use a [scheduled task](/server/handlers/scheduled) and `context.task(base)`.

## Trade-offs

When you pass `ctx` as an argument, the compiler checks that every caller has one. With `context`, the type is the same, but the compiler cannot check that a `ctx` exists at the moment you call. That check moves to the runtime, and it fails with the errors above. Use an argument when a function is called from many places or from code that runs outside handlers.

## In `upgrade`

The `upgrade` function receives its `ctx` as the second argument. Use it there. Do not call `context.upgrade(base)` inside `server({ upgrade })` to build the return value. The type of `base` depends on what `upgrade` returns. If a value from `context.upgrade(base)` reaches the returned value, TypeScript reports a circular reference (`'base' implicitly has type 'any'`).

`context.upgrade(base)` is for helpers in other files. If `upgrade` calls such a helper, write an explicit return type on it, or TypeScript reports a similar circular-type error:

```typescript [server/sessions.ts]
import { context } from '@livething/server'
import { base } from './huddle'

export function findSession(token: string | null): {
  userId: string
  role: 'admin' | 'member'
} | null {
  return context
    .upgrade(base)
    .sql.exec<{
      userId: string
      role: 'admin' | 'member'
    }>(
      'SELECT user_id AS userId, role FROM sessions WHERE token = ?',
      token,
    )
    .one()
}
```

## Adapters

`context` needs an async-context store, which the adapter already provides through `asyncContextFactory`. LiveThing keeps one shared store for the whole process. The first engine that is created makes it, and every later engine in the process reuses it. On Cloudflare, the `nodejs_compat` flag that the adapter already needs is enough. See [Custom adapters](/server/adapters/custom-adapters).
