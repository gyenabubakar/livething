These are the fields on **every** `ctx` inside a connection handler — they are there no matter which capabilities you listed. Capability-specific fields (`ctx.tags`, `ctx.channels`, `ctx.schedule`, latency/quality, and more) are added by the capability that owns them, and documented on that capability's own page — see the [table at the end](#fields-added-by-capabilities).

The fields group by purpose: identity, messaging, connection inspection, storage, platform, and per-dispatch locals.

The same connection scope also determines handler scheduling. See [Per-Connection Event Queue](/server/handlers/per-connection-queue) for the queue and the exceptions for requests and streams.

## Identity

Who this connection is, and who owns it.

Every connection belongs to exactly one **user** — the account your `upgrade` step returned a `userId` for. A connection whose `upgrade` returned no `userId` is **anonymous**: it has no user identity at all. `ctx.user` is still present on every connection, but on an anonymous one its `id` is an empty string and it reaches nobody — see [Users](/server/context-and-storage/users) for the full model.

| Field               | Type                  | What it is                                                                                                                                |
| ------------------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `ctx.connection`    | `ConnectionRef`       | A reference to this socket. Pass it to anything that takes a `ConnectionRef` (`ctx.connections.get(...)`, channel `subscribe`, and more). |
| `ctx.connection.id` | `string`              | Unique ID for this socket. Stable for the life of the connection.                                                                         |
| `ctx.user`          | `UserHandle`          | A handle to this connection's user — `.id`, `.send(...)`, `.setMeta(...)`, and more. See [Users](/server/context-and-storage/users).      |
| `ctx.user.id`       | `string`              | The user id your upgrade step returned. The same person on two devices has two connection ids but one `ctx.user.id`.                      |
| `ctx.meta`          | your `upgrade` return | The metadata you attached during upgrade, fully typed from its return value.                                                              |

`ctx.connection.id` is per-socket; `ctx.user.id` is per-user. Use `ctx.user.id` when you key durable state, `ctx.connection.id` when you address one live socket.

```typescript [identity.ts]
base.on('who-am-i', {
  input: v.object({}),
  run(ctx) {
    // meta is typed from the upgrade step — here it returned { username }.
    ctx.send('who-am-i-result', {
      userId: ctx.user.id,
      username: ctx.meta.username,
    })
  },
})
```

`ctx.meta` is typed, not `any`. If your upgrade step returns `{ username: string }`, then `ctx.meta.username` is a `string` and `ctx.meta.role` is a compile error. See [Defining a server](/server/define/overview) for the upgrade step.

## Messaging

Send events out.

| Method                                    | Returns            | What it does                                                                                                                                                                       |
| ----------------------------------------- | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ctx.send(event, payload)`                | `void`             | Send to **this** connection only. Dispatches the frame or throws — an undeclared event, or a non-object payload.                                                                   |
| `ctx.broadcast(event, payload, options?)` | `void`             | Send to every other connection on this instance. Pass `{ includeSelf: true }` to also deliver to the sender.                                                                       |
| `ctx.connections.get(ref)`                | `ConnectionHandle` | A handle to one specific socket by its `ConnectionRef`. Its `.send(event, payload)` returns `false` when that socket is gone; with `serverRequests()` it also has `.request(...)`. |

`ctx.connections.get(ref).close(code?, reason?)` closes that exact referenced socket. It does not close the user's other connections; use `ctx.users.get(id).close(...)` or `ctx.closeConnections({ userId: id }, ...)` when you want user-wide or filtered closure.

Both are typed against your `emits(...)` events — a wrong event name or payload shape is a compile error.

::note
**Rule of thumb — `.send` vs `.broadcast`, everywhere.** Wherever you see **`.send(...)`** — top-level `ctx.send` or a channel's `ctx.channel.send` — it targets exactly one socket: the connection whose event you are handling. Wherever you see **`.broadcast(...)`**, it targets many: every connection on the instance (`ctx.broadcast`), or every member of the channel (`ctx.channel.broadcast`). The channel forms differ from the top-level ones only in reach — a channel-stamped frame arrives on the client's handle for _that channel_, not the global socket.
::

```typescript [messaging.ts]
const handleDoBroadcast = base.on('do-broadcast', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    // Goes to everyone EXCEPT the sender — includeSelf defaults to false.
    ctx.broadcast('message', { text: input.text, from: ctx.meta.username })
  },
})

const handleDoBroadcastIncludeSelf = base.on('do-broadcast-include-self', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    // includeSelf: true sends to the sender too.
    ctx.broadcast(
      'message',
      { text: input.text, from: ctx.meta.username },
      { includeSelf: true },
    )
  },
})
```

`ctx.send` returns nothing — it dispatches the frame or throws. It does not report a full buffer, so to spot a slow client read `ctx.bufferedAmount` (bytes still queued to this socket) instead; a rising value means the client is falling behind:

```typescript [send-result.ts]
base.on('ping-self', {
  input: v.object({}),
  run(ctx) {
    ctx.send('message', { text: 'pong', from: 'server' })
    if (ctx.bufferedAmount > 1_000_000)
      ctx.log.warn('client is slow', { id: ctx.connection.id })
  },
})
```

::note
`ctx.broadcast` always fans out to every connection on the instance. To send only to members of a channel, use a channel handle's `broadcast` — see [Channels](/server/channels/overview). To send to connections holding a tag, use the tag handle's `send` — see [Tags](/server/capabilities/tags).
::

## Closing the connection

| Method                      | What it does                                                                |
| --------------------------- | --------------------------------------------------------------------------- |
| `ctx.close(code?, reason?)` | Close **this** connection with an optional WebSocket close code and reason. |

```typescript [close.ts]
import { CloseCodes } from '@wskit/core'

base.on('do-server-close', {
  input: v.object({}),
  run(ctx) {
    ctx.close(CloseCodes.CAPACITY, 'server-close')
  },
})
```

Use `CloseCodes` rather than raw numbers. `4000`–`4999` are available for application codes; `3000`–`3999` are also valid but conventionally belong to libraries and frameworks. If server code supplies an invalid value, the engine logs it and closes with `1011` / `Internal error` instead of leaving the connection open. See [Close codes](/core/close-codes) for the shared catalog, the valid ranges, and what is reserved.

Inside the `onDisconnect` hook, two read-only fields carry _how_ the socket closed:

| Field             | Type                  | What it is                                                                                                                       |
| ----------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `ctx.closeCode`   | `number \| undefined` | The WebSocket close code for this disconnect. Filled in only inside the `onDisconnect` hook; `undefined` in every other handler. |
| `ctx.closeReason` | `string \| undefined` | The close reason string, same timing.                                                                                            |

```typescript [on-close.ts]
base.onDisconnect((ctx) => {
  ctx.log.info('socket closed', {
    code: ctx.closeCode,
    reason: ctx.closeReason,
  })
})
```

## Inspecting connections

Read who is connected and how full this socket's buffer is.

| Field / method          | Type               | What it is                                                                              |
| ----------------------- | ------------------ | --------------------------------------------------------------------------------------- |
| `ctx.connectionCount`   | `number`           | How many connections are open on this instance right now.                               |
| `ctx.connections.all()` | `ConnectionInfo[]` | A snapshot of every live connection.                                                    |
| `ctx.bufferedAmount`    | `number`           | Bytes still queued to send to **this** socket. A rising value means the client is slow. |

```typescript [members.ts]
base.on('list-members', {
  input: v.object({}),
  run(ctx) {
    const peers = ctx.connections.all()
    // peers[].meta is typed from your upgrade step — no cast needed.
    const usernames = peers.map((p) => p.meta.username)
    ctx.send('members-list-result', { members: usernames })
  },
})
```

`ctx.connections.all()` returns a read-only snapshot — it does not update after you read it. Each entry is a `ConnectionInfo`, and you can build a `ConnectionRef` from one with `.ref()` to address that socket. The [Connections page](/server/context-and-storage/connections) covers `ConnectionInfo` and addressing in full.

::note
`ctx.connections.all()` returns `ConnectionInfo<Meta>[]`, where `Meta` is your upgrade type — so `peers[].meta.username` is typed just like your own `ctx.meta`, no cast needed. The same holds for the snapshots from channel `members()` and tag `connections()`.
::

## Storage

Durable state.

| Field     | Type          | What it is                                |
| --------- | ------------- | ----------------------------------------- |
| `ctx.sql` | `SQLProvider` | SQLite access — queries and transactions. |
| `ctx.kv`  | `KVProvider`  | A simple durable key-value store.         |

```typescript [storage.ts]
base.on('save-note', {
  input: v.object({ title: v.string(), body: v.string() }),
  run(ctx, input) {
    ctx.sql.exec(
      'INSERT INTO notes (title, body) VALUES (?, ?)',
      input.title,
      input.body,
    )
  },
})
```

Both surfaces have their own page — see [SQL & KV](/server/context-and-storage/sql-and-kv) for the full API, when to use which, and transactions.

## Platform & logging

The runtime around your handler.

| Field / method | Type          | What it is                                                                                         |
| -------------- | ------------- | -------------------------------------------------------------------------------------------------- |
| `ctx.env`      | your env type | Platform bindings and secrets, typed from `env: t<Env>()` in `define`.                             |
| `ctx.log`      | `Logger`      | Structured logger — `info`, `warn`, `error`, each taking a message and optional data object.       |
| `ctx.platform` | `unknown`     | The raw platform object from the adapter (for example a Durable Object state). Untyped by default. |

```typescript [logging.ts]
base.on('process-order', {
  input: v.object({ orderId: v.string() }),
  async run(ctx, input) {
    ctx.log.info('order received', {
      orderId: input.orderId,
      by: ctx.meta.username,
    })

    await recordToAnalytics(input.orderId)
  },
})
```

Always prefer `ctx.log` over `console.log` — the adapter routes it to your platform's log system with the data fields indexed.

`ctx.env` is typed from the `env: t<Env>()` you pass to `define`, so reading a binding that does not exist is a compile error:

```typescript [env.ts]
base.on('read-env-probe', {
  input: v.object({}),
  run(ctx) {
    ctx.send('env-result', { keyCount: Object.keys(ctx.env as object).length })
  },
})
```

## Per-dispatch locals

Pass a typed value from an intercept down to the handler that runs in the **same** message dispatch.

| Method                    | What it does                                                                                      |
| ------------------------- | ------------------------------------------------------------------------------------------------- |
| `ctx.provide(key, value)` | Store a typed value under a `localKey` for this dispatch.                                         |
| `ctx.inject(key)`         | Read a value an upstream `provide` stored. Returns `undefined` if nothing was stored for the key. |

```typescript [locals.ts]
import { localKey } from '@wskit/server'

const TopKey = localKey<{ tag: string }>('top')

base.intercept((ctx) => {
  ctx.provide(TopKey, { tag: 'top' })
})

base.on('echo', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    const top = ctx.inject(TopKey)
    ctx.send('echoed', { text: `${input.text}:${top?.tag ?? 'none'}` })
  },
})
```

Locals are isolated per dispatch — what you `provide` for one message is **not** visible to the next. They never touch durable storage; for that, use `ctx.sql` or `ctx.kv`. The full story — typed keys, intercept-to-handler flow, channel scoping — is on the [Provide & inject](/server/lifecycle-and-intercept/provide-inject) page.

## Frame guards

`ctx.matches` and `ctx.unsafeCast` narrow a **frame** — the `(ctx, frame)` value an [`intercept`](/server/capabilities/intercepts) or [`onOutgoing`](/server/lifecycle-and-intercept/outgoing) hook hands you — against one of your declared events, turning its `unknown` payload into a known shape. They are **core**: on every `ctx`, no capability to list.

| Method                       | Returns    | What it does                                                                                                                            |
| ---------------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `ctx.matches(key, frame)`    | `boolean`  | `true` when the frame's event and scope match the key **and** its payload passes the declared validator. A bad payload returns `false`. |
| `ctx.unsafeCast(key, frame)` | type guard | Checks only that `key` is a declared event; skips the payload validator. Use when your own logic already proved the shape.              |

```typescript [frame-guards.ts]
base.onOutgoing((ctx, frame) => {
  // Runs the validator declared for 'message'. False if the payload is bad.
  if (ctx.matches('message', frame)) {
    const p = frame.payload as { text: string }
    return { ...p, text: p.text.trimEnd() }
  }
})
```

Both throw if the key names no declared event, so a typo is caught immediately rather than passing silently. Channel-scoped keys use the `@family::event` form. `matches` validates the payload; `unsafeCast` is a type-only assertion that skips validation — reach for it only when your own logic already proved the shape.

An `intercept` is the most common place to use them, because its `frame.payload` arrives typed `unknown` before validation runs. See [intercepts](/server/capabilities/intercepts) for that hook.

## Fields added by capabilities

Beyond the core fields above, listing a capability can add its own field to `ctx`. Each is documented on the capability's own page. The gate is the **type**, not a runtime check: if you didn't list the capability the field isn't on `ctx` and the compiler stops you — there's no `if (ctx.tags)` to write.

| Capability         | Adds to `ctx`                                                                  | Page                                                   |
| ------------------ | ------------------------------------------------------------------------------ | ------------------------------------------------------ |
| `keepalive(...)`   | `ctx.latency`, `ctx.quality`                                                   | [keepalive](/server/capabilities/keepalive)            |
| `serverRequests()` | `ctx.request`, `ctx.broadcastRequest`, `request` on `ctx.connections.get(ref)` | [serverRequests](/server/capabilities/server-requests) |
| `scheduled(...)`   | `ctx.schedule`, `ctx.cancelScheduled`                                          | [scheduled](/server/capabilities/scheduled)            |
| `channels()`       | `ctx.channels`                                                                 | [channels](/server/capabilities/channels)              |
| `tags(...)`        | `ctx.tags`                                                                     | [tags](/server/capabilities/tags)                      |
| `replay.*`         | `ctx.sendReplay`                                                               | [replay](/server/capabilities/replay)                  |
| a server plugin    | `ctx.plugin(id)`                                                               | [Plugins · Scoped ctx](/server/plugins/scoped-ctx)     |
