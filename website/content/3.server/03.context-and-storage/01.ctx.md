This page lists the fields on **every** `ctx` inside a connection handler. They are there no matter which capabilities you listed. Other fields (`ctx.tags`, `ctx.channels`, `ctx.schedule`, `ctx.latency`, and more) come from a capability. Each one is documented on its capability's own page. The [table at the end](#fields-added-by-capabilities) lists them.

The fields are grouped by purpose: identity, messaging, closing, connection inspection, storage, platform, per-dispatch locals, and frame guards.

Each `ctx` belongs to one connection, and LiveThing runs the events of one connection through a [queue](/server/handlers/per-connection-queue), with exceptions for requests and streams.

## Identity

These fields tell you which connection this is, and which user owns it.

Every connection belongs to at most one **[user](/server/context-and-storage/users)**: the account that your `authenticate` step returned a `userId` for. A connection whose `authenticate` returned no `userId` is **anonymous**. It has no user identity. `ctx.user` is still present on an anonymous connection, but its `id` is an empty string and it reaches no socket.

::field-group
::field{name="ctx.connection" type="ConnectionRef"}
A reference to this socket. Pass it to anything that takes a `ConnectionRef` (`ctx.connections.get(...)`, channel `subscribe`, and more).
::
::field{name="ctx.connection.id" type="string"}
The unique ID of this socket. It stays the same while the socket is open. A new socket (for example, after a reconnect) gets a new ID.
::
::field{name="ctx.user" type="UserHandle"}
A handle to this connection's [user](/server/context-and-storage/users), with `.id`, `.broadcast(...)`, `.setMeta(...)`, `.close(...)`, and more.
::
::field{name="ctx.user.id" type="string"}
The user ID that your `authenticate` step returned. The same person on two devices has two connection IDs but one `ctx.user.id`.
::
::field{name="ctx.users.get(id)" type="UserHandle"}
A handle to any [user](/server/context-and-storage/users), by user ID.
::
::field{name="ctx.meta" type="Record<string, unknown>"}
The metadata you attached in `authenticate`. Its exact type is the `meta` object that your `authenticate` returns.
::
::field{name="ctx.setMeta(patch)" type="void"}
Merge `patch` into this connection's `meta`. The change is saved once, at the end of the handler.
::
::

`ctx.connection.id` is per socket. `ctx.user.id` is per user. Use `ctx.user.id` as the key for state that must last (durable state). Use `ctx.connection.id` when you want to address one live socket.

```typescript [server/whoami.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleWhoami = base.on('whoami', {
  input: v.object({}),
  run(ctx) {
    // meta is typed from the `authenticate` step. Here it returned { name, role }.
    ctx.send('notification', {
      title: 'You',
      body: `${ctx.meta.name} (${ctx.user.id})`,
    })
  },
})
```

`ctx.meta` is typed, not `any`. If your [`authenticate` step](/server/server/overview) returns `{ name: string; role: Role }`, then `ctx.meta.name` is a `string`, and `ctx.meta.email` is a compile error.

## Messaging

These methods send events out.

::field-group
::field{name="ctx.send(event, payload)" type="boolean"}
Send to **this** connection only. Returns `true` when the frame was handed to the socket, `false` when the platform adapter refused the frame. Throws when the event is not declared or the payload is not an object.
::
::field{name="ctx.broadcast(event, payload, options?)" type="void"}
Send to every other connection on this instance. Pass `{ includeSelf: true }` to also send to the sender.
::
::field{name="ctx.connections.get(ref)" type="ConnectionHandle"}
A handle to one specific socket, by its `ConnectionRef`. Its `.send(event, payload)` returns `false` when that socket is gone. With the `serverRequests()` capability it also has `.request(...)`.
::
::

`ctx.send` and `ctx.broadcast` are typed against your `emits(...)` events. A wrong event name or a wrong payload shape is a compile error.

`ctx.connections.get(ref).close()` closes only that one socket. It takes an optional close code and reason. It does not close the user's other connections. To close every socket of one user, use `ctx.users.get(id).close(...)` (or `ctx.user.close(...)` for the current user).

::note
**`.send` compared with `.broadcast`.** This rule is the same everywhere. **`.send(...)`** (the top-level `ctx.send` or a channel's `ctx.channel.send`) sends to exactly one socket: the connection whose event you are handling. **`.broadcast(...)`** sends to many sockets:

- `ctx.broadcast`: every connection on the instance (except the sender, unless you pass `includeSelf: true`).
- `ctx.user.broadcast`: every live socket of one user.
- `ctx.tags.ephemeral(group)`, then `.ref(key).broadcast`: every connection that holds that tag.
- `ctx.channel.broadcast`: every member of the channel.

The channel forms reach fewer sockets than the top-level forms. Also, a frame sent through a channel arrives on the client's handle for _that channel_, not on the main socket.
::

In Huddle, `send-message` and `react` are handlers on the `rooms` channel. Here they are on `base`, so the examples show `ctx.broadcast`:

```typescript [server/messages.ts]
import * as v from 'valibot'
import { base } from './base'

const handleSendMessage = base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    const message = {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    }

    // Goes to everyone EXCEPT the sender. includeSelf is false by default.
    ctx.broadcast('message', message)
  },
})

const handleReact = base.on('react', {
  input: v.object({ messageId: v.string(), emoji: v.string() }),
  run(ctx, input) {
    // includeSelf: true sends to the sender too, so their own reaction shows at once.
    ctx.broadcast(
      'reaction',
      {
        messageId: input.messageId,
        emoji: input.emoji,
        from: ctx.user.id,
      },
      { includeSelf: true },
    )
  },
})
```

`ctx.send` does not tell you when the socket's send buffer is full. To find a slow client, read `ctx.bufferedAmount`. It is the number of bytes still waiting to be sent to this socket. A value that keeps growing means the client cannot keep up:

```typescript [server/messages.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleSendMessage = base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.send('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
    if (ctx.bufferedAmount > 1_000_000) {
      ctx.log.warn('client is slow', { id: ctx.connection.id })
    }
  },
})
```

::note
`ctx.broadcast` always sends to every other connection on the instance. It cannot be limited to a channel or a tag. To send only to the members of a channel, use [a channel handle's `broadcast`](/server/channels/overview). To send to the connections that hold a tag, use [the tag handle's `broadcast`](/server/capabilities/tags).
::

## Closing the connection

| Method                      | What it does                                                                   |
| --------------------------- | ------------------------------------------------------------------------------ |
| `ctx.close(code?, reason?)` | Close **this** connection, with an optional WebSocket close code and a reason. |

```typescript [server/sign-out.ts]
import { CloseCodes } from '@livething/core'
import * as v from 'valibot'
import { base } from './base'

export const handleSignOut = base.on('sign-out', {
  input: v.object({}),
  run(ctx) {
    ctx.close(CloseCodes.NORMAL, 'signed out')
  },
})
```

Use [`CloseCodes`](/core/close-codes) instead of raw numbers. Codes `4000` to `4999` are for your application. Codes `3000` to `3999` are also valid, but by convention they are for libraries and frameworks. If server code passes a code that is not valid, LiveThing logs it and closes the socket with `1011` / `Internal error`, so the connection does not stay open.

Inside the `onDisconnect` hook, two read-only fields tell you _how_ the socket closed:

| Field             | Type                  | What it is                                                                                                                            |
| ----------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `ctx.closeCode`   | `number \| undefined` | The WebSocket close code of this disconnect. It is set only inside the `onDisconnect` hook. In every other handler it is `undefined`. |
| `ctx.closeReason` | `string \| undefined` | The close reason text. It is set only in the same hook as `ctx.closeCode`.                                                            |

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'

export const base = server({
  onDisconnect(ctx) {
    ctx.log.info('socket closed', {
      code: ctx.closeCode,
      reason: ctx.closeReason,
    })
  },
})
```

## Inspecting connections

These fields tell you who is connected and how full this socket's send buffer is.

| Field / method          | Type               | What it is                                                                                         |
| ----------------------- | ------------------ | -------------------------------------------------------------------------------------------------- |
| `ctx.connectionCount`   | `number`           | How many connections are open on this instance right now.                                          |
| `ctx.connections.all()` | `ConnectionInfo[]` | A snapshot of every live connection.                                                               |
| `ctx.bufferedAmount`    | `number`           | Bytes still waiting to be sent to **this** socket. A value that keeps growing means a slow client. |

```typescript [server/who-is-here.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleWhoIsHere = base.on('who-is-here', {
  input: v.object({}),
  run(ctx) {
    const peers = ctx.connections.all()
    // peers[].meta is typed from your `authenticate` step. No cast is needed.
    const names = peers.map((p) => p.meta.name)
    ctx.send('notification', {
      title: 'Online now',
      body: names.join(', '),
    })
  },
})
```

`ctx.connections.all()` returns a read-only snapshot. A snapshot is a copy of the data at one moment, so it does not change after you read it. Each entry is a `ConnectionInfo`. Call `.ref()` on an entry to get a `ConnectionRef` for that socket. The [Connections page](/server/context-and-storage/connections) covers `ConnectionInfo` and addressing in full.

::note
`ctx.connections.all()` returns `ConnectionInfo<Meta>[]`, where `Meta` is the type your `authenticate` step returns. So `peers[].meta.name` is typed in the same way as your own `ctx.meta`, and you need no cast. The same is true for the snapshots from channel `members()` and tag `connections()`.
::

## Storage

These fields give you durable state: data that stays after the connection closes.

| Field     | Type          | What it is                                                  |
| --------- | ------------- | ----------------------------------------------------------- |
| `ctx.sql` | `SQLProvider` | Access to a SQLite database, with queries and transactions. |
| `ctx.kv`  | `KVProvider`  | A simple durable key-value store.                           |

```typescript [server/messages.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleSendMessage = base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.sql.exec(
      'INSERT INTO messages (id, room, user_id, text, sent_at) VALUES (?, ?, ?, ?, ?)',
      crypto.randomUUID(),
      'general',
      ctx.user.id,
      input.text,
      Date.now(),
    )
  },
})
```

Each of the two has [its own page](/server/context-and-storage/sql-and-kv), with the full API, when to use which one, and transactions.

## Platform & logging

These fields give you access to the runtime that runs your handler.

| Field / method | Type      | What it is                                                                                              |
| -------------- | --------- | ------------------------------------------------------------------------------------------------------- |
| `ctx.log`      | `Logger`  | A structured logger with `info`, `warn`, and `error`. Each takes a message and an optional data object. |
| `ctx.platform` | `unknown` | The raw platform object from the adapter (on Cloudflare, `Platform<Env>`). It is untyped by default.    |

This `set-status` handler is smaller than Huddle's. It logs the change and saves the status in `ctx.kv`, and it does not broadcast:

```typescript [server/status.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleSetStatus = base.on('set-status', {
  input: v.object({ status: v.picklist(['active', 'away', 'busy']) }),
  async run(ctx, input) {
    ctx.log.info('status changed', {
      by: ctx.user.id,
      status: input.status,
    })

    await ctx.kv.set(`status:${ctx.user.id}`, input.status)
  },
})
```

Use `ctx.log` instead of `console.log`. The adapter decides where log entries go, so your handler code stays the same on every platform. The Node.js and Cloudflare adapters write each entry to the console, with the data object as a separate value next to the message.

`ctx.platform` gives you bindings that exist only on one runtime. Its type is `unknown` in the core API. When you need those bindings, cast it to the platform adapter's type. For example, Cloudflare handlers can cast it to the adapter's `Platform<Env>` type and read `platform.env`. See the [Cloudflare adapter](/server/adapters/cloudflare) page.

## Per-dispatch locals

A **dispatch** is one run of LiveThing's pipeline for one incoming message: the intercepts first, then the handler. Per-dispatch locals pass a typed value from an intercept to the handler that runs in the **same** dispatch. An [intercept](/server/lifecycle-and-intercept/intercept) is a hook that runs before the handler for every incoming frame.

| Method                    | What it does                                                                                          |
| ------------------------- | ----------------------------------------------------------------------------------------------------- |
| `ctx.provide(key, value)` | Store a typed value under a `localKey` for this dispatch.                                             |
| `ctx.inject(key)`         | Read a value that an earlier `provide` stored. Returns `undefined` if nothing was stored for the key. |

```typescript [server/huddle-definition.ts]
import { emits, localKey, server, t } from '@livething/server'
import * as v from 'valibot'
import type { Message } from './base'

const ReceivedAtKey = localKey<number>('received-at')

export const base = server({
  capabilities: [emits({ message: t<Message>() })],
  intercept(ctx) {
    ctx.provide(ReceivedAtKey, Date.now())
  },
})

export const handleSendMessage = base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })

    const receivedAt = ctx.inject(ReceivedAtKey)
    if (receivedAt !== undefined) {
      ctx.log.info('message handled', { ms: Date.now() - receivedAt })
    }
  },
})
```

Locals belong to one dispatch. A value you `provide` for one message is **not** visible to the next message. Locals are never saved to durable storage. For that, use `ctx.sql` or `ctx.kv`. The [provide / inject](/server/lifecycle-and-intercept/provide-inject) page covers typed keys, the flow from intercept to handler, and channel scoping.

## Frame guards

A **frame** is one message on the wire. An [`intercept`](/server/lifecycle-and-intercept/intercept) hook receives each incoming frame as its `(ctx, frame)` argument, before validation. The frame's `payload` has the type `unknown`. `ctx.matches` and `ctx.unsafeCast` check a frame against one of your declared incoming events. They are **core**: they are on every `ctx`, and you do not need to list a capability for them.

They work only on incoming frames. The outgoing hook [`onOutgoing`](/server/lifecycle-and-intercept/outgoing) receives a different frame type, so you cannot use them there.

| Method                       | Returns            | What it does                                                                                                                            |
| ---------------------------- | ------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| `ctx.matches(key, frame)`    | `boolean`          | `true` when the frame's event and scope match the key **and** its payload passes the declared validator. A bad payload returns `false`. |
| `ctx.unsafeCast(key, frame)` | the frame, retyped | Checks only that `key` is a declared event. It does not run the payload validator and does not compare the key with `frame.event`.      |

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'

export const base = server({
  intercept(ctx, frame) {
    // Runs the validator declared for 'send-message'. False if the payload is bad.
    if (ctx.matches('send-message', frame)) {
      const p = frame.payload as { text: string }

      return { ...p, text: p.text.trimEnd() }
    }
  },
})
```

Both methods throw if the key does not name a declared event, so a typo in the key fails right away. For an event on a channel, use the key form `@family::event`. `matches` validates the payload. `unsafeCast` skips validation, so use it only when your own code already knows the shape of the payload.

An [intercept](/server/lifecycle-and-intercept/intercept) is where you use them most often, because the payload has not been validated yet.

## Fields added by capabilities

When you list a capability, it can add its own field to `ctx`. Each field is documented on its capability's page. The check happens in the **type**, not at runtime: if you did not list the capability, the field is not on the `ctx` type and you get a compile error. You never need to write a check such as `if (ctx.tags)`.

| Capability         | Adds to `ctx`                                                                                                                                    | Page                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| `keepalive(...)`   | `ctx.latency`, `ctx.quality`                                                                                                                     | [keepalive](/server/capabilities/keepalive)            |
| `serverRequests()` | `ctx.request`, `request` on `ctx.connections.get(ref)`, `ctx.user` and `ctx.users.get(id)`                                                       | [serverRequests](/server/capabilities/server-requests) |
| `scheduled(...)`   | `ctx.schedule`, `ctx.cancelScheduled`                                                                                                            | [scheduled](/server/capabilities/scheduled)            |
| `channels()`       | `ctx.channels`                                                                                                                                   | [channels](/server/capabilities/channels)              |
| `tags(...)`        | `ctx.tags`                                                                                                                                       | [tags](/server/capabilities/tags)                      |
| `replay.*`         | `ctx.sendReplay`                                                                                                                                 | [replay](/server/capabilities/replay)                  |
| `lastSeen()`       | `ctx.lastSeen`                                                                                                                                   | [lastSeen](/server/capabilities/last-seen)             |
| `binary(...)`      | `ctx.binary`, and `.binary` on every sender (`ctx.channel`, `ctx.user`, tag handles, …), with `.binary.request` for `binary({ serverRequests })` | [binary](/server/binary/overview)                      |
| a server plugin    | `ctx.plugin(id)`                                                                                                                                 | [Plugins · Scoped ctx](/server/plugins/scoped-ctx)     |

`ctx.binary` is a little different: the key is always on the type, but without `binary()` its type is `never`, so any use of it is still a compile error.
