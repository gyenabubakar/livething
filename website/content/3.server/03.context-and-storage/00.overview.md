Every handler you register gets `ctx` as its first argument. `ctx` is the **connection context**: the object you use to send to the client, see who is connected, write logs, use storage, and send to other sockets. This chapter covers all of `ctx` first. Then it covers storage and connection addressing in more detail.

Because `ctx` belongs to one live connection, LiveThing also keeps a work queue for each connection. Read [Per-Connection Event Queue](/server/handlers/per-connection-queue) before the handler pages. It explains which work waits for earlier work to finish and which work can run at the same time.

```typescript [server/rooms.ts]
base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    const message = {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    }
    ctx.send('message', message)
    ctx.broadcast('message', message)
  },
})
```

`ctx` is the first parameter. The validated `input` is the second. `ctx.broadcast` skips the connection that sent the message, so this handler also calls `ctx.send` to show the message to its sender.

## `ctx` is scoped to one connection

Inside a connection handler, `ctx` belongs to the socket that sent the message:

- `ctx.connection.id` is that socket's ID.
- `ctx.send(...)` sends back to that socket.
- `ctx.meta` is the metadata (extra data about the connection, such as a display name) that you returned for it during the upgrade step. The upgrade step is the function that accepts or rejects a new connection.

The same handler runs for every connection, but each run gets its own `ctx`.

```typescript [server/huddle.ts]
base.on('whoami', {
  input: v.object({}),
  run(ctx) {
    ctx.send('notification', {
      title: 'You',
      body: ctx.connection.id,
    })
  },
})
```

## The shape changes two ways

`ctx` is not one fixed type. The fields it has depend on **two** things:

1. **Which capabilities you listed** in `server({ capabilities: [...] })`. A capability is a feature you turn on for your server. Some capabilities add their own field to `ctx`:
   - `tags(...)` adds `ctx.tags`.
   - `channels()` adds `ctx.channels`.
   - `keepalive(...)` adds `ctx.latency` and `ctx.quality`.
   - `scheduled(...)` adds `ctx.schedule` and `ctx.cancelScheduled`.
   - `serverRequests()` adds `ctx.request` and `ctx.broadcastRequest`.
   - A replay capability adds `ctx.sendReplay`.

   Other capabilities add fields too. If you did not list the capability, the field is **not on the type at all**, so reading it is a compile error. You never get a field that exists but is `undefined` at runtime.

2. **Which handler type you are in.** A connection handler gets all the connection fields. A channel handler also gets `ctx.channel`. Some code runs with no live socket: the init hook, scheduled tasks, and the shutdown hook. (A hook is a function that LiveThing calls at a fixed moment, such as server startup.) This code gets a smaller `ctx` with no per-connection `send`.

## Context shapes by handler type

This table shows which `ctx` you get in each kind of handler. The pages above cover the connection handler in full. Use this table as a quick reference for the other handler types.

| Handler                                        | What `ctx` has                                                                                                                                                                                                                                                         |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Connection handler (`on`, `request`, `stream`) | All connection fields: the core fields plus the fields of every capability you listed.                                                                                                                                                                                 |
| Channel handler                                | The same, plus `ctx.channel`. It has `send`, `broadcastTo`, `broadcast`, `members`, `subscribe`, and `kick`, and they all work on the current channel only. With a replay capability, use `ctx.channel.sendReplay`. There is no `ctx.sendReplay` in a channel handler. |
| Init hook (`base.onInit`)                      | Storage (`sql`, `kv`), `log`, `platform`. No connections exist yet, so there is no `send`, `broadcast`, or `connection.id`.                                                                                                                                            |
| The app's `upgrade` function                   | The same as the init hook: storage (`sql`, `kv`), `log`, `platform`. No connection exists yet during the handshake. See [Upgrade](/server/server/upgrade#the-upgrade-ctx).                                                                                             |
| Scheduled task                                 | `broadcast`, `connections.get(ref)`, `connections.all()`, `users`, storage, `schedule`/`cancelScheduled`, `log`, `platform`. No per-connection `send`, `connection.id`, `meta`, or `ctx.tags`, because a task does not belong to one socket.                           |
| Shutdown hook (`base.onShutdown`)              | `broadcast`, `closeAll()`, `connections.get(ref)`, `connections.all()`, `users`, storage, `schedule`/`cancelScheduled`, `log`, `platform`. No per-connection `send`.                                                                                                   |
| onDisconnect hook                              | All connection fields, with `ctx.closeCode` and `ctx.closeReason` filled in.                                                                                                                                                                                           |

::note
`ctx.closeCode` and `ctx.closeReason` are optional in the type of every connection `ctx`, but they have a value only inside the onDisconnect hook. In every other handler they are `undefined`. See [Lifecycle hooks](/server/lifecycle-and-intercept/hooks) for onInit, onShutdown, onConnect, and onDisconnect.
::

## Where state lives

`ctx` does not keep app state between messages. Each message dispatch (one run of the handlers for one incoming message) gets a new `ctx`. Durable state lives in storage:

- **`ctx.sql`**: a SQLite database for relational data (rows, queries, transactions). The data stays after restarts and hibernation.
- **`ctx.kv`**: a simple key-value store for small state, such as flags, counters, and small caches. It is also durable. You can give a key a TTL (time to live), after which the key expires.

To pass a value **within one message dispatch** (for example, from an intercept, which is code that runs before the handler, to the handler itself), use `ctx.provide` and `ctx.inject`. These values last for one dispatch only and are never written to durable storage. See [Provide & inject](/server/lifecycle-and-intercept/provide-inject).
