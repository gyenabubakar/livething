A **user** is one account in your app. A connection belongs to a user when your `authenticate` step gives it a `userId`. A connection without a `userId` is **anonymous** and belongs to no user.

This page explains:

- what a user is,
- the difference between a `ConnectionRef` and a `UserRef`,
- `UserHandle`, the object you use to act on all of a user's live connections at the same time.

## Every connection has a user

To accept a connection, your `authenticate` step returns `{ userId, meta }`. The `userId` is the account that this connection belongs to:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { verifySession } from './auth'

const base = server({
  authenticate: async (request) => {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    // No session: accept the connection as anonymous (no userId).
    if (!user) {
      return { meta: { name: 'guest', role: 'guest' as const } }
    }

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
})
```

If `authenticate` returns no `userId`, or if you do not define `authenticate` at all, the connection is **anonymous**. It has no user identity.

`ctx.user` still exists on an anonymous connection, so your handler code does not need to check for it first. But on an anonymous connection, `ctx.user` points to no user, so it reaches no socket:

| Case                                | `ctx.user.id`          | `ctx.user.broadcast(...)` reaches              |
| ----------------------------------- | ---------------------- | ---------------------------------------------- |
| `authenticate` returned a `userId`  | that `userId`          | every live connection that has that `userId`   |
| `authenticate` returned no `userId` | `''` (an empty string) | no connection, not even the calling connection |

To reach an anonymous connection, address it as one socket. Use `ctx.send(...)` for the calling connection, or `ctx.connections.get(ref).send(...)` for another connection. This addresses the connection, not the user.

Some features must keep working after a reconnect, for example durable channel membership and [durable streams](#anonymous-connections-and-durable-streams). These features need a real `userId`.

## One socket vs one user

There are two kinds of address. Each one reaches a different set of sockets:

| Address         | Reaches                                                                      | How to get one                                                    |
| --------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `ConnectionRef` | Exactly one socket.                                                          | `ctx.connection`, or `ref()` on any `ConnectionInfo`.             |
| `UserRef`       | Every **live** connection the user has right now (all tabs and all devices). | `ctx.user.ref()`, `UserInfo.ref()`, or `ctx.users.get(id).ref()`. |

If one person opens your app in two browser tabs, that is two `ConnectionRef`s but one `UserRef`. An event sent to the `UserRef` goes to both tabs. An event sent to a `ConnectionRef` goes only to that one tab.

```typescript [server/whoami.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleWhoami = base.on('whoami', {
  input: v.object({}),
  run(ctx) {
    ctx.send('notification', {
      title: 'You',
      body: `connection ${ctx.connection.id}, user ${ctx.user.id}`,
    })
  },
})
```

## `ctx.user`: the user of the calling connection

`ctx.user` is a `UserHandle`. A handle is an object you use to act on something. This one acts on the account behind the connection that is running the handler. It has the `.id` field, and methods that act on every live tab this user has open:

::field-group
::field{name="id" type="string"}
The user ID. It has the same value as `ctx.connection.userId`. It is `''` (an empty string) for an anonymous connection.
::
::field{name="ref()" type="() => UserRef"}
Returns a `UserRef` for this user. Pass it to any API that addresses the whole user, such as `kick`.
::
::field{name="broadcast(event, payload)" type="(event, payload) => number"}
Sends an event to every live connection this user has. Returns the number of sockets that received it.
::
::field{name="request(event, payload, opts?)" type="(event, payload, opts?) => Promise<{ response, from }>"}
Sends a question to the user and waits for the first valid answer from any of the user's live connections. `from` is the `ConnectionRef` of the connection that answered. This method exists only when the server lists the `serverRequests({...})` capability.
::
::field{name="binary" type="object"}
`binary.broadcast(event, info, bytes)` and `binary.request(event, info, bytes)`: the same as `broadcast` and `request`, for messages that carry bytes, such as Huddle's [`avatar-preview`](/server/binary/events#handling-binary-events) to every tab of the user. `binary.broadcast` exists when the server lists [`binary()`](/server/binary/events#sending-binary-events), and `binary.request` when `binary({ serverRequests })` declares a request. That also needs the [`serverRequests()`](/server/capabilities/server-requests) capability: without it, `assemble()` throws.
::
::field{name="setMeta(patch)" type="(patch: Partial<Meta>) => void"}
Merges `patch` into the `meta` of **every** live connection of this user. All of the user's tabs and devices get the same patch.
::
::field{name="connections()" type="() => ConnectionInfo<Meta>[]"}
Returns a snapshot of this user's live connections. A snapshot is a copy of the data at one moment. It does not update.
::
::field{name="close(code?, reason?)" type="(code?, reason?) => void"}
Closes every live connection this user has.
::
::field{name="info()" type="() => UserInfo<Meta> | null"}
Returns a snapshot of this user, or `null` when the user has no live connections right now.
::
::field{name="isOnline()" type="() => boolean"}
Returns `true` when this user has [at least one live connection](#checking-if-a-user-is-online) on this server instance. It reads memory only and builds no snapshot.
::
::

Huddle's `rename` handler uses `ctx.broadcast`. This version uses the user handle, so only this user's own tabs get the event:

```typescript [server/rename.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleRename = base.on('rename', {
  input: v.object({ name: v.string() }),
  run(ctx, input) {
    // Every tab this user has open gets the new name and the 'user-renamed' event.
    ctx.user.setMeta({ name: input.name })
    const delivered = ctx.user.broadcast('user-renamed', {
      userId: ctx.user.id,
      name: input.name,
    })
    ctx.send('notification', {
      title: 'Renamed',
      body: `${delivered} tabs notified`,
    })
  },
})
```

## `ctx.users`: reaching any user by ID

`ctx.users` is a `UsersManager`. Its `.get(id)` method returns a `UserHandle` for any user ID. You can use this handle even when the user has no live connections right now. In that case, its `broadcast` reaches no socket and returns `0`.

`ctx.users.get('')` also reaches no socket. `''` is never a real user ID, so it never matches a live connection.

`ctx.users` sends only to sockets that are live now. A user who is offline gets nothing, and nothing is stored for them. This is different from a DM channel's inbox, which holds the channel's broadcasts for offline members. This handler (it is not part of Huddle's definition) sends a note straight to one user:

```typescript [server/private-note.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleSendPrivateNote = base.on('send-private-note', {
  input: v.object({ toUserId: v.string(), text: v.string() }),
  run(ctx, input) {
    // Reaches every live tab of that user, even if they never subscribed to
    // a channel with this connection. Delivered is 0 if they are offline,
    // and then nobody receives the note.
    const delivered = ctx.users
      .get(input.toUserId)
      .broadcast('message', {
        id: crypto.randomUUID(),
        text: input.text,
        from: ctx.user.id,
        sentAt: Date.now(),
      })
    ctx.log.info('private note delivered', { delivered })
  },
})
```

## `UserInfo`: a read-only snapshot

`ctx.user.info()` and `ctx.users.get(id).info()` return a `UserInfo`, or `null` if the user has no live connections.

`ConnectionInfo` has a `.meta` field, but `UserInfo` does not. Metadata belongs to each connection, because one user can have different `meta` on different sockets (for example, a different device or a different session). To read it, call `connections()` and read `meta` on each connection.

::field-group
::field{name="id" type="string"}
The user ID.
::
::field{name="connections()" type="() => ConnectionInfo<Meta>[]"}
A snapshot of this user's live connections.
::
::field{name="channels" type="readonly string[]"}
The names of all channels that any of this user's live connections is subscribed to. Each name appears once.
::
::field{name="tags" type="readonly TagRef[]"}
All tag refs on any of this user's live connections. Each tag appears once.
::
::field{name="lastSeen()" type="(() => number | null) | undefined"}
Reads this user's last-seen time, as a timestamp in milliseconds. This method exists only when the [`lastSeen()`](/server/capabilities/last-seen) capability is listed. It returns `null` when no last-seen time has been saved for this user yet. Each call reads storage.
::
::field{name="ref()" type="() => UserRef"}
Returns a `UserRef` for this user.
::
::

```typescript [server/get-presence.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleGetPresence = base.request('get-presence', {
  input: v.object({ userId: v.string() }),
  run(ctx, input) {
    const info = ctx.users.get(input.userId).info()
    return {
      tabCount: info?.connections().length ?? 0,
      channels: info?.channels ?? [],
    }
  },
})
```

## Checking if a user is online

`ctx.users.get(id).isOnline()` returns `true` when the user has at least one live connection. Use it when you only need a yes or no. It is cheaper than `info() !== null`, because it does not build a `UserInfo` snapshot.

```typescript [server/is-teammate-online.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleIsTeammateOnline = base.request(
  'is-teammate-online',
  {
    input: v.object({ userId: v.string() }),
    run(ctx, input) {
      return { online: ctx.users.get(input.userId).isOnline() }
    },
  },
)
```

`isOnline()` only knows about connections on **this server instance**: one Durable Object on Cloudflare, one process on Node. A user connected only to a different Durable Object or a different Node process is `false` here.

## Limiting connections per user

`server({ users: { maxConnections, onExceed } })` sets the largest number of live connections one user can have at the same time:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { verifySession } from './auth'

const base = server({
  authenticate: async (request) => {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user) {
      return { meta: { name: 'guest', role: 'guest' as const } }
    }

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  users: { maxConnections: 3, onExceed: 'replace' },
})
```

`onExceed` is required when you pass `users`. It decides what happens when a new connection would go over the limit:

| `onExceed`  | What happens                                                                                                                           |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `'replace'` | LiveThing closes the user's **oldest** connection(s) with `CloseCodes.DUPLICATE` (`4003`), so the new connection fits under the limit. |
| `'reject'`  | LiveThing refuses the **new** connection. It closes it with `CloseCodes.CAPACITY` (`4010`) before `onConnect` runs.                    |

Any other value makes `assemble()` throw a `LiveThingConfigError`.

If you leave out `users.maxConnections`, one user can have any number of connections. This is the default.

Anonymous connections have no `userId`, so this limit **never** applies to them. The limit only counts connections that have the same real `userId`.

`maxConnections` must be a positive whole number. `0`, a negative number, and a fraction such as `1.5` all make `server(...)` throw. So you see the error when the server starts, not when the first connection arrives.

## Anonymous connections and durable streams

Durable streams save their state under the connection's real user ID. A reconnect then uses that user ID to find the stream and continue it. An anonymous connection has no user ID for this.

If an anonymous connection starts one of these streams, the server rejects it with the `DurableStreamRequiresUser` error. This error is exported from `@livething/core`. The client code below catches it:

```typescript [client/scout.ts]
import { DurableStreamRequiresUser } from '@livething/core'
import { socket } from './socket'

const general = socket.channel('rooms', 'room:general')

try {
  await general.stream('ask-scout', { prompt: 'summarize this room' })
} catch (err) {
  if (DurableStreamRequiresUser.matches(err)) {
    // Sign the connection in (return a userId from authenticate) before you try
    // a durable stream again, or use a plain stream instead.
  }
}
```

To fix this, give the connection a `userId` in `authenticate`, or use a plain (non-durable) [stream](/server/streams/overview). LiveThing reserves other [built-in errors](/core/builtin-errors) like this one.
