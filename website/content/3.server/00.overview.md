A WSKit server is built in three moves. You **define** the server, you write **handlers**, and you **assemble** them into one finished thing the runtime can run. Everything else in this section fills in those three moves.

```typescript [shape.ts]
const base = define({ env, upgrade, capabilities }) // 1. define the server

export const handleSend = base.on('send', {
  /* ... */
}) // 2. write handlers

export const handler = base.assemble({ handlers: [handleSend] }) // 3. assemble them
```

That `handler` is what you hand to a platform adapter. On Cloudflare it becomes a Durable Object class; on Bun, Node, or Deno it becomes a running server.

## A minimal server, end to end

Here is the whole loop — server, adapter, and client — for a tiny echo server.

::code-group

```typescript [chat.ts]
import { define, emits, t } from '@wskit/server'
import { RejectUpgrade } from '@wskit/server/errors'
import * as v from 'valibot'
import type { InferClient } from '@wskit/server'

const base = define({
  env: t<Env>(),
  upgrade(request) {
    const username = new URL(request.url).searchParams.get('username')
    if (!username) throw RejectUpgrade(4001, 'Missing username')
    return { userId: username, meta: { username } }
  },
  capabilities: [emits({ pong: t<{ text: string }>() })],
})

export const handlePing = base.on('ping', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.send('pong', { text: input.text })
  },
})

export const handler = base.assemble({ handlers: [handlePing] })
export type ChatSocket = InferClient<typeof handler>
```

```typescript [worker.ts]
import { server } from '@wskit/server-cloudflare'
import { handler } from './chat'

export const ChatRoom = server(handler)
```

```typescript [app.ts]
import { client, connect } from '@wskit/client'
import type { ChatSocket } from './chat'

const socket = client<ChatSocket>()(connect('wss://example.com/ws'))
socket.connect()

socket.send('ping', { text: 'hello' })
socket.on('pong', (data) => {
  // data: { text: string } — typed from the server
  console.log(data.text)
})
```

::

The server file never imports the client, and the client file imports only the `ChatSocket` **type**. That one type is the whole contract — every event, payload, request, and stream the two sides agree on — and it is generated from the server by `InferClient`. Change a payload on the server and the client stops compiling until you fix it.

## The mental model

### `define(config)` returns a builder

`define(...)` does not run a server. It reads a small config — the platform env type, an optional auth gate, and a list of capabilities — and returns a **builder** (this page calls it `base`). The builder is typed against everything you gave it. The methods it carries, and the payloads those methods accept, are shaped by your config.

```typescript [define.ts]
const base = define({
  env: t<Env>(), // ctx.env is typed to this everywhere
  upgrade(request) {
    /* ... */
  }, // the auth gate
  capabilities: [
    /* ... */
  ], // each one adds engine code and builder methods
})
```

`base.on(...)` is always there. The rest — `base.request`, `base.stream`, `base.channel`, `base.scheduled`, `base.intercept` — appear only when you list the capability that grants them. Calling a method whose capability you did not list is a compile error, not a runtime surprise.

### Handlers are plain values

Each builder method returns an ordinary value you export.

```typescript [handlers.ts]
export const handleSend = base.on('send', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    /* ... */
  },
})

export const handleLookup = base.request('lookup', {
  input: v.object({ id: v.string() }),
  run(ctx, input) {
    return { found: true }
  },
})
```

Because they are just values, you can spread handlers across files, group them however you like, and import them wherever you need them. Nothing is registered globally — a handler does nothing until you pass it to `assemble`.

### `base.assemble({ handlers })` finalizes the server

`assemble` collects your handler values into the finished `ServerDefinition`. The upgrade gate, the lifecycle hooks, the intercept, and every listed capability are folded in for you — you pass only handlers.

```typescript [assemble.ts]
export const handler = base.assemble({
  handlers: [
    handleSend,
    handleLookup,
    lobby, // a channel object, or any of its handler values
  ],
})
```

`assemble` is also where many mistakes are caught early. Two handlers bound to the same event name, a scheduled task declared but never given a body, a per-handler `rateLimit` override without the `rateLimit()` capability — each throws a clear build error here instead of failing in production.

::note
Capabilities go in `define({ capabilities: [...] })`, never in `assemble(...)`. Passing a capability to `assemble` is a type error — and a runtime throw as a second check, in case the type error is missed.
::

## How a server is shaped

```
define({ env, upgrade, capabilities })   →  base (the builder)

base.on / request / stream / scheduled    →  handler values (one per event)
base.resumableStream / recordedStream / channel
base.onInit / onConnect / ...             →  lifecycle hooks (registered on base)
base.intercept                            →  inbound hook (needs the intercepts capability)

base.assemble({ handlers })               →  ServerDefinition

InferClient<typeof handler>               →  the client-side type

server(handler)                           →  the running platform
  @wskit/server-cloudflare               →  a Durable Object class
  @wskit/server-bun / -node / -deno      →  a standalone server
```

Lifecycle hooks (`onInit`, `onConnect`, `onDisconnect`, and friends) are registered straight onto `base` and return nothing — you do not pass them to `assemble`. Handlers are values you export and then collect. Capabilities are listed once, up front.
