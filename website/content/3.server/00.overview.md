You build a LiveThing server in three steps:

1. Call **`server()`** to create a server builder.
2. Write **event handlers**. An event handler is the code that runs when a client sends a message with a given event name.
3. **Assemble** the handlers into one finished **server definition**. This is the object a runtime runs.

The rest of this section explains each of these steps in detail.

```typescript [server/huddle-definition.ts]
const base = server({ upgrade, capabilities }) // 1. create the server builder

export const handleRename = base.on('rename', {
  /* ... */
}) // 2. write an event handler

export const definition = base.assemble({ handlers: [handleRename] }) // 3. assemble them
```

You pass the server definition to a **platform adapter**. An adapter is the package that connects LiveThing to one runtime:

- On Cloudflare, `bind(definition)` turns it into a Durable Object class. A Durable Object is a Cloudflare object that keeps its own state and runs your server code in one place.
- On Node.js, `setup().bind(definition, options)` turns it into a WebSocket endpoint for your application's HTTP server.
- On Bun and Deno, the adapter turns it into a service for that runtime.

## A minimal server, end to end

This example shows the whole loop (server, adapter and client) for a small slice of Huddle, the team chat app these docs use for every example. The client sends `rename` with a new display name, and the server saves it and tells everyone.

::code-group

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token) // your auth: returns { id, name, role } or null
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    emits({ 'user-renamed': t<{ userId: string; name: string }>() }),
  ],
})

export const handleRename = base.on('rename', {
  input: v.object({ name: v.string() }),
  run(ctx, input) {
    ctx.user.setMeta({ name: input.name })
    ctx.user.broadcast('user-renamed', {
      userId: ctx.user.id,
      name: input.name,
    })
  },
})

export const huddle = base.assemble({ handlers: [handleRename] })
export type HuddleSocket = InferClient<typeof huddle>
```

```typescript [worker.ts]
import { bind } from '@livething/server-cloudflare'
import { huddle } from './server/huddle-definition'

export class HuddleServer extends bind(huddle) {}
```

```typescript [client/socket.ts]
import { client, connect, query } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  query(() => ({ token: getSessionToken() })),
)
socket.connect()

socket.send('rename', { name: 'Priya' })
socket.on('user-renamed', (data) => {
  // data: { userId: string; name: string } — typed from the server
  console.log(data.name)
})
```

::

The server file never imports the client. The client file imports only the `HuddleSocket` **type**. That one type is the whole contract: every event, payload, request and stream that the two sides agree on. `InferClient` creates it from the server definition. If you change a payload on the server, the client code shows type errors until you update it.

## The mental model

### `server(config)` returns a builder

`server(...)` does not start a server. It reads a small config object and returns a **builder**. A builder is an object whose methods you call to create the parts of your server. This section calls it `base`.

The config holds the setup the server needs before any connection. The two main parts are:

- `upgrade`: an optional auth gate. It runs when a client tries to connect, and it accepts or rejects the connection.
- `capabilities`: a list of the features this server uses. A capability is an opt-in feature, such as client requests or channels. You list it once, and LiveThing adds its code and its builder methods.

The builder's types come from this config. The config decides which methods the builder has and which payloads those methods accept.

```typescript [server/huddle.ts]
const base = server({
  upgrade(request) {
    /* ... */
  }, // the auth gate
  capabilities: [
    /* ... */
  ], // each one adds engine code and builder methods
})
```

`base.on(...)` is always there. Other methods, such as `base.request`, `base.stream`, `base.channel`, `base.scheduled` and `base.intercept`, exist only when you list the capability that adds them. If you call a method whose capability you did not list, you get a compile error. You do not have to wait for the code to run to find the mistake.

### Routed handlers are plain values

A **routed handler** is a handler that LiveThing calls by event name when a client message arrives. The client-facing builder methods (`on`, `request`, `stream` and the channel methods) return routed handlers as ordinary values that you export.

```typescript [server/huddle.ts]
export const handleSendMessage = base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    /* ... */
  },
})

export const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  run(ctx, input) {
    return loadProfile(input.userId) // your storage lookup
  },
})
```

These are plain values, so you can put routed handlers in different files, group them as you like, and import them where you need them. LiveThing does not register them anywhere when you create them. A routed handler does nothing until you pass it to `assemble`.

### `base.assemble({ handlers })` finishes the server

`assemble` collects your routed handler values into the finished `ServerDefinition`. It also adds, without extra code from you, the upgrade gate, the lifecycle hooks, the scheduled task bodies, the intercept and every capability you listed.

```typescript [assemble.ts]
export const huddle = base.assemble({
  handlers: [
    handleSendMessage,
    handleGetProfile,
    rooms, // a channel object, or any of its handler values
  ],
})
```

`assemble` also checks for common mistakes early. For example:

- Two handlers use the same event name.
- A scheduled task is declared but has no body.
- A handler has its own `rateLimit` setting, but the `rateLimit()` capability is not listed.

Each of these throws a clear error when `assemble` runs, so you find the mistake at build time and not in production.

::note
Capabilities go in `server({ capabilities: [...] })`, never in `assemble(...)`. If you pass a capability to `assemble`, you get a type error. `assemble` also throws at runtime, in case the type error is missed.
::

## How a server is shaped

```
server({ upgrade, capabilities })         →  base (the builder)

base.on / request / stream                 →  handler values (one per event)
base.resumableStream / recordedStream / channel
base.scheduled / onInit / onConnect / ... →  server work (registered on base)
base.intercept                            →  inbound hook (needs the intercepts capability)

base.assemble({ handlers })               →  ServerDefinition

InferClient<typeof definition>            →  the client-side type

bind(definition)                          →  a Durable Object class
  @livething/server-cloudflare
setup().bind(definition, options)         →  a Node.js WebSocket endpoint
  @livething/server-node                     (your HTTP server owns the route and listener)
bind(definition, options)                 →  a Bun or Deno runtime service
```

Some `base` methods register server work directly on `base` and return nothing:

- scheduled task bodies (`base.scheduled`)
- lifecycle hooks, which run at fixed points in a connection's life (`onInit`, `onConnect`, `onDisconnect` and others)

You do not pass these to `assemble`. Routed handlers are different: they are values that you export and then collect in `assemble`. Capabilities are listed once, at the start, in `server()`.
