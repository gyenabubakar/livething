`define(config)` is the entry point for every WSKit server. It takes a small config and returns a **builder** — the object this section calls `base`. The builder carries the methods you use to register handlers and lifecycle hooks, and those methods are typed against the config you gave it. The path is always the same: `define` → handlers on `base` → `base.assemble(...)`.

## What `define` returns

The return value is a builder. It is **not** a running server and it holds no state about a connection. It is a typed factory: call its methods to produce handler values, then collect them with `assemble`.

```typescript [base.ts]
import { define, emits, t } from '@wskit/server'

const base = define({
  env: t<Env>(),
  capabilities: [emits({ tick: t<{ n: number }>() })],
})

// base.on is always present
const handleStart = base.on('start', {
  run(ctx) {
    ctx.send('tick', { n: 1 })
  },
})

// base.request only exists because requests() was listed — it isn't here,
// so calling base.request(...) would be a compile error.

export const handler = base.assemble({ handlers: [handleStart] })
```

The builder always carries `base.on`, the lifecycle hooks (`onInit`, `onConnect`, `onDisconnect`, `onError`, `onValidationError`, `onShutdown`), the outbound `onOutgoing` hook, and `assemble`. Every other method — `request`, `stream`, `resumableStream`, `recordedStream`, `channel`, `scheduled`, the inbound `intercept`, and the custom `replay` — is added only when the matching capability is in your list. (The inbound `intercept` hook needs the `intercepts()` capability, so it is gated like the rest.) Those methods are covered in [Handlers](/server/handlers/overview); the hooks in [Lifecycle and intercept](/server/lifecycle-and-intercept/overview).

## The config shape

```typescript [config.ts]
const base = define({
  env: t<Env>(), // required — the platform bindings type
  upgrade(request) {
    /* ... */
  }, // optional — the auth gate
  users: { maxConnections: 3, onExceed: 'replace' }, // optional — per-user connection cap
  capabilities: [
    /* ... */
  ], // optional — opt-in features
  hibernation: { enabled: true }, // optional — Cloudflare hibernation hint
  translate: legacy, // optional — one foreign wire-format translator
})
```

| Field          | Required | What it does                                                                                                                                                                                                                                                                  |
| -------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `env`          | yes      | A `t<Env>()` marker for your platform bindings. It carries no runtime value — it only types `ctx.env` everywhere. See [Environment and upgrade](/server/define/env-and-upgrade).                                                                                              |
| `upgrade`      | no       | The handshake gate. It reads the raw `Request` and returns `{ userId, meta?, tags? }` to accept, or throws `RejectUpgrade(code, reason)` to reject. Omit it and every connection is accepted as anonymous. See [Environment and upgrade](/server/define/env-and-upgrade).     |
| `users`        | no       | `{ maxConnections?, onExceed }` — caps how many live connections one user may hold at once. `onExceed: 'reject'` refuses the newcomer; `'replace'` drops the user's oldest connection(s) to make room. Omit it for unlimited. See [Users](/server/context-and-storage/users). |
| `capabilities` | no       | The list of opt-in features. Each one adds engine code to the bundle and may grant a builder method. Omit it for a bare `base.on`-only server. See [Capabilities](/server/define/capabilities).                                                                               |
| `hibernation`  | no       | `{ enabled: boolean }` — a hint to a Cloudflare adapter to hibernate idle connections. See [Hibernation](/server/define/hibernation).                                                                                                                                         |
| `translate`    | no       | One server-only wire-format translator factory. It adapts an existing client protocol at the connection edge; it is not a capability or plugin. See [Translation](/server/define/translation).                                                                                |

That is the whole config. `define` holds **bootstrap** — the things the runtime needs to exist and accept a connection. Optional behavior is either a config field, such as `hibernation` or `translate`, or an opt-in capability listed in `capabilities`.

::note
There is one more form: `define({ scope: 'plugin', ... })`. It has no `env` field and is used only by plugins — see [Plugins › Authoring](/server/plugins/authoring).
::

## The typing flows from the config

What you put in the config shapes the builder's types:

- **`env`** sets the type of `ctx.env` in every handler.
- **`upgrade`**'s return type sets `ctx.meta`. Return `{ meta: { userId: string } }` and `ctx.meta.userId` is a typed `string` everywhere.
- **`capabilities`** decide which builder methods exist and which `ctx` surfaces are present. List `requests()` and `base.request` plus `ctx.request` appear; leave it out and reading either is a compile error.

```typescript [typed.ts]
import { define, emits, t } from '@wskit/server'
import { requests } from '@wskit/server/requests'

const base = define({
  env: t<{ DB: D1Database }>(),
  upgrade(request) {
    return { userId: 'u1', meta: { role: 'admin' as const } }
  },
  capabilities: [requests(), emits({ welcome: t<{ role: string }>() })],
})

const handleHello = base.request('hello', {
  run(ctx) {
    // ctx.env.DB     → D1Database     (from env)
    // ctx.meta.role  → 'admin'        (from upgrade)
    // base.request   → exists         (from requests())
    return { role: ctx.meta.role }
  },
})

export const handler = base.assemble({ handlers: [handleHello] })
```

## From `define` to `assemble`

The journey has three stops, every time:

::steps{level="3"}

### Call `define`

Pass the config. Hold the returned builder in a `const` — usually named `base`.

```typescript [step-1.ts]
const base = define({
  env: t<Env>(),
  upgrade: (request) => requireUser(request),
  capabilities: [emits({ message: t<{ text: string }>() })],
})
```

### Register handlers and hooks

Call builder methods to produce handler values, and register lifecycle hooks inline. Handlers are exportable values; hooks return nothing.

```typescript [step-2.ts]
base.onConnect((ctx) => {
  ctx.send('message', { text: `welcome, ${ctx.user.id}` })
})

export const handleSay = base.on('say', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.broadcast('message', { text: input.text })
  },
})
```

### Assemble

Pass every handler value to `assemble`. The upgrade gate, the hooks, the intercept, and the listed capabilities are folded in automatically — you pass only handlers. The result is a `ServerDefinition` for an adapter to run.

```typescript [step-3.ts]
export const handler = base.assemble({ handlers: [handleSay] })
export type ChatSocket = InferClient<typeof handler>
```

::

`assemble` is where the server is finalized and validated. It rejects, at build time, things like two handlers on the same event — even if they are different kinds of handler, e.g. an `on` and a `request` that share a name — a scheduled task declared with no body (or the reverse, a `base.scheduled` body for a task never declared in `scheduled({...})`), or a per-handler `rateLimit` override whose `rateLimit()` capability was never listed. Pass a capability to `assemble` by mistake and it throws too — capabilities belong in `define`.

::warning
The lifecycle hooks (`onInit`, `onConnect`, `onDisconnect`, `onError`, `onValidationError`, `onShutdown`, `intercept`, `onOutgoing`) are checked earlier and separately: each one throws the moment you register it a second time, not at `assemble`. Calling `base.onConnect(...)` twice throws immediately on the second call — one hook per lifecycle event, per server.
::

## Splitting across files

Because the builder and its handlers are plain values, you can export `base` from one file and attach handlers in others. This keeps a large server readable.

::code-group

```typescript [setup.ts]
import { define, emits, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { requireUser } from './upgrade'

export const base = define({
  env: t<Env>(),
  upgrade: (request) => requireUser(request),
  capabilities: [emits({ notification: t<{ text: string }>() }), channels()],
})
```

```typescript [rooms.ts]
import { base } from './setup'

export const lobby = base.channel('lobby', {
  outgoing: { emits: { joined: t<{ who: string }>() } },
})

lobby.subscribe((ctx) => {
  ctx.channel.broadcast('joined', { who: ctx.connection.id })
})
```

```typescript [index.ts]
import type { InferClient } from '@wskit/server'
import { lobby } from './rooms'
import { base } from './setup'

export const handler = base.assemble({ handlers: [lobby] })
export type AppSocket = InferClient<typeof handler>
```
