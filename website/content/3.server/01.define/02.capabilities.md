A **capability** is an opt-in feature you list in `define({ capabilities: [...] })`. This page is about the _mechanism_: how listing a capability changes the bundle and the builder, how capabilities compose, and how missing prerequisites are caught. For what each capability _does_, see the [Capabilities chapter](/server/capabilities/overview).

## The `capabilities` array

You build a capability by calling its factory — `emits(...)`, `clientRequests()`, `channels()`, and so on — and placing the result in the array.

```typescript [list.ts]
import { define, emits, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { clientRequests } from '@wskit/server/client-requests'

const base = define({
  capabilities: [
    emits({ message: t<{ text: string }>() }),
    clientRequests(),
    channels(),
  ],
})
```

You never build a capability by hand — always call the factory. Each factory decides three things: the runtime code it adds, the contract slots it declares, and the builder method (if any) it grants.

::warning
**Keep the capability list precisely typed.** Write it inline in `define(...)`. If you need to reuse it, keep its tuple type with `as const`:

```typescript [typed-list.ts]
const capabilities = [
  clientRequests(),
  channels(),
  AuthPlugin(),
] as const

const base = define({
  capabilities,
})
```

Do not annotate the list as `AnyCapability[]`, and do not spread a list that has already been widened to that type. Doing so erases the specific capability and plugin types before WSKit receives them.
::

::note
Most capabilities live on their own import subpath — `@wskit/server/client-requests`, `@wskit/server/channels`, `@wskit/server/streams`, and the rest. A few (`emits`, `errors`, `t`) come straight from `@wskit/server`. The [Capabilities chapter](/server/capabilities/overview) lists the import for each.
::

## Listing one is what ships it

This is the core idea: **a feature's engine code is pulled into your bundle only when you list its capability.** Leave `channels()` out and not one byte of channel-routing code ships. This keeps a small server small — you pay for the features you use and nothing else.

That is also why capabilities are values you import, not flags you toggle. The import is the signal to your bundler that the code is needed.

## A capability does two jobs

Listing a capability can do two separate things.

### 1. Grant a builder method

Some capabilities add a method to `base`. The method exists only when its capability is listed — calling it otherwise is a compile error (and a runtime throw as a backstop).

```typescript [grants.ts]
import { define, t } from '@wskit/server'
import { clientRequests } from '@wskit/server/client-requests'

const withRequests = define({
  capabilities: [clientRequests()],
})
withRequests.request('lookup', { run: () => ({ ok: true }) }) // OK — clientRequests() listed

const without = define({
  capabilities: [],
})
// without.request(...)   ← compile error: base.request does not exist
```

Which capability grants which method:

| Capability          | Builder method it grants |
| ------------------- | ------------------------ |
| `clientRequests()`  | `base.request`           |
| `scheduled({...})`  | `base.scheduled`         |
| `stream()`          | `base.stream`            |
| `resumableStream()` | `base.resumableStream`   |
| `recordedStream()`  | `base.recordedStream`    |
| `channels()`        | `base.channel`           |
| `intercepts()`      | `base.intercept`         |
| `replay.custom()`   | `base.replay`            |

Capabilities like `emits(...)`, `errors([...])`, `tags(...)`, `keepalive(...)`, `dedup()`, `sequence()`, and `rateLimit()` grant **no** method — they declare a contract slot, add a `ctx` surface, or turn on an engine.

### 2. Add a `ctx` surface

Some capabilities add a field to the `ctx` every handler receives. Like the methods, the field exists only when the capability is listed — reading it otherwise is a compile error, not a present-but-null field.

```typescript [ctx-surface.ts]
import { define, t } from '@wskit/server'
import { scheduled } from '@wskit/server/scheduled'

const base = define({
  capabilities: [scheduled({ cleanup: null })],
})

const handleStart = base.on('start', {
  run(ctx) {
    // ctx.schedule exists because scheduled(...) is listed
    ctx.schedule('cleanup', { time: Date.now() + 60_000 })
  },
})
```

`clientRequests()` adds `ctx.request` / `ctx.broadcastRequest` / `ctx.connections.get(ref).request`; `channels()` adds `ctx.channels`; `tags(...)` adds `ctx.tags`; `keepalive(...)` adds `ctx.latency` / `ctx.quality`; `intercepts()` adds `ctx.matches` / `ctx.unsafeCast`; a replay capability adds `ctx.sendReplay`. The `ctx` shape and these surfaces are covered in [Context and storage](/server/context-and-storage/overview).

::note
`ctx.matches` and `ctx.unsafeCast` are the one exception to the compile-time gate: they sit on `ctx` in the types even without `intercepts()`, but calling either one throws at runtime unless `intercepts()` is listed. List it whenever you narrow frame payloads.
::

## How capabilities compose

The list is merged. Each capability contributes its slice of the client contract and its runtime primitives, and `define` folds them all into one builder typed against the union.

```typescript [compose.ts]
import { define, emits, error, errors, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { clientRequests } from '@wskit/server/client-requests'
import * as v from 'valibot'

const QuotaExceeded = error(
  'quota-exceeded',
  v.object({ retryAfterMs: v.number() }),
)

const base = define({
  capabilities: [
    emits({
      // server→client events
      message: t<{ text: string }>(),
    }),
    errors([QuotaExceeded]), // typed server errors
    clientRequests(), // grants base.request + ctx.request
    channels(), // grants base.channel + ctx.channels
  ],
})
```

The contract slices stack: `emits` fills the events slot, `errors` the errors slot, and `clientRequests` / `channels` enable their builder methods and contract slots. `serverRequests` adds the server-to-client request surface. `InferClient<typeof handler>` reads the merged result, so the client sees the full surface of every capability you listed.

Listing the same singleton capability twice is rejected at `assemble` time for a **few** capabilities — two `rateLimit()` entries throw `rateLimit() is listed more than once`, and two built-in replay strategies throw a similar error.

::warning
That check is not universal. Host engines like `dedup()`, `sequence(...)`, and `keepalive(...)` install once and silently ignore every later listing — there is no error. So `capabilities: [sequence({ persist: true }), sequence({ persist: false })]` quietly keeps the **first** config and drops the second, with nothing telling you the second one was ignored. Only list each of these once.
::

## Requirements and auto-derivation

Some features depend on others. Built-in replay needs message dedup and ordering; a channel's `inbox()` needs the channel machinery, dedup, and a durable sequence. WSKit checks these for you.

When a handler or feature needs a capability you did not list, `assemble` throws a clear error naming what is missing:

```typescript [missing.ts]
import { define, t } from '@wskit/server'
import { replay } from '@wskit/server/replay'

const base = define({
  capabilities: [replay.history()], // built-in replay needs dedup + a durable sequence...
})

// base.assemble({ handlers: [] })
//   → throws: the dedup() capability is required by replay but is not listed. Add dedup().
```

The fix is to list the prerequisite:

```typescript [fixed.ts]
import { define, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { replay } from '@wskit/server/replay'
import { sequence } from '@wskit/server/sequence'

const base = define({
  capabilities: [
    dedup(),
    sequence({ persist: true }),
    replay.history(),
  ], // now it assembles
})
```

The common requirements:

| Feature                                                                   | Requires                                                               |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Built-in replay (`replay.history()` / `replay.snapshot()`)                | `dedup()` and `sequence({ persist: true })`                            |
| A channel's `inbox()` (listed in the channel's own `capabilities`)        | `channels()`, `sequence({ persist: true })`, and `dedup()` on the host |
| A channel's `readReceipts()` (listed in the channel's own `capabilities`) | `inbox()` on the same channel                                          |

The check walks both top-level handlers and channel-nested ones, so a durable stream declared inside a channel triggers the same requirement machinery.

::note
For built-in replay the presence check at `assemble` only asks that `dedup()` and `sequence(...)` are listed. The `persist: true` part is checked one step later, at server startup: a bare `sequence()` assembles fine but then throws at startup, asking for `sequence: { persist: true }` for durable replay. List `sequence({ persist: true })` from the start.
::

::note
This is what "auto-derivation" means for **plugins**: a plugin that owns a channel with `inbox()` does not have to list `dedup()` or `sequence()` itself (it can't — those engines are host-owned). The requirement is derived from the channel and passed up to the host to satisfy. See [Plugins › dependsOn](/server/plugins/depends-on).
::

## Ordering

The order of the array does **not** change behavior. Capabilities are collected into sets, so listing `channels()` before or after `emits(...)` makes no difference to the result. Order them however reads best — the recommended style is to put engine capabilities (`dedup`, `sequence`) first, then behavior capabilities, then the `emits` block last.

```typescript [ordering.ts]
const base = define({
  capabilities: [
    // engines
    dedup(),
    sequence({ persist: true }),
    // behaviors
    clientRequests(),
    channels(),
    resumableStream(),
    // the event catalog, read at a glance
    emits({
      welcome: t<{ username: string }>(),
      goodbye: t<{ username: string }>(),
    }),
  ],
})
```

The one rule the checker enforces is _presence_, not position: every required capability must be somewhere in the list.
