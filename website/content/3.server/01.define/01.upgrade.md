The `upgrade` field runs during the HTTP-to-WebSocket handshake. It is where you authenticate the request and decide whether to let the socket in.

WSKit does not provide a cross-platform environment object. Runtime configuration belongs to the runtime: Node code can read `process.env`, while a Cloudflare Durable Object can read bindings from its adapter platform value (`ctx.platform.env`) or from a Worker entry point's `env` argument. Keep runtime-specific configuration at that edge, and pass explicit values into shared handlers or plugins when they need them.

For Cloudflare bindings, use the `Platform` type exported by `@wskit/server-cloudflare` (or the `cloudflare:workers` types generated for your Worker) when you need to type the platform escape hatch:

```typescript [cloudflare-config.ts]
import type { Platform } from '@wskit/server-cloudflare'

interface Env {
  API_URL: string
}

base.on('lookup', {
  run(ctx) {
    const platform = ctx.platform as Platform<Env>
    const apiUrl = platform.env.API_URL
    ctx.send('lookup-result', { apiUrl })
  },
})
```

A plugin that needs configuration should accept it as an explicit factory value. The host chooses the value when it registers the plugin, so the plugin does not depend on a hidden framework environment:

```typescript [plugin-config.ts]
import { define, emits, t } from '@wskit/server'
import { plugin } from '@wskit/server/plugins'

export function auditPlugin(config: { topic: string }) {
  const pluginBase = define({
    scope: 'plugin',
    capabilities: [emits({ recorded: t<{ topic: string }>() })],
  })
  const record = pluginBase.on('record', {
    run(ctx) {
      ctx.send('recorded', { topic: config.topic })
    },
  })
  return plugin('acme:audit', {
    handler: pluginBase.assemble({ handlers: [record] }),
  })
}

const base = define({
  capabilities: [auditPlugin({ topic: 'audit-events' })()],
})
```

## `upgrade` — the auth gate

`upgrade` runs once, during the HTTP-to-WebSocket handshake, before any handler. It receives the raw `Request` — headers, URL, cookies, everything an HTTP request carries — and decides whether the connection is accepted or rejected.

```typescript [upgrade.ts]
import { define, t } from '@wskit/server'
import { RejectUpgrade } from '@wskit/server/errors'

const base = define({
  async upgrade(request) {
    const token = request.headers.get('authorization')
    const user = await validateToken(token)
    if (!user) throw RejectUpgrade(4002, 'Invalid token')
    return {
      userId: user.id,
      meta: { userId: user.id, role: user.role },
    }
  },
  capabilities: [],
})
```

`upgrade` may be `async`. Return a value to **accept** the connection, or throw `RejectUpgrade(code, reason)` to **reject** it.

### Reading the request

The argument is a standard `Request`. Common things to pull from it:

```typescript [reading.ts]
async upgrade(request) {
  const url = new URL(request.url)
  const room = url.searchParams.get('room')          // query string
  const token = request.headers.get('authorization')  // header
  const cookie = request.headers.get('cookie')         // cookies

  // ... validate and return
}
```

A small, common pattern is to pull a username straight from the query string:

```typescript [username.ts]
import { RejectUpgrade } from '@wskit/server/errors'

async upgrade(request) {
  const username = new URL(request.url).searchParams.get('username')
  if (!username) throw RejectUpgrade(4001, 'Missing username')
  return { userId: username, meta: { username } }
}
```

::warning
Runtime configuration is **not** an argument to either the top-level or plugin `upgrade` — both receive only the `Request`. If authentication needs configuration or a service, make it available through a closure or module scope; there is no `ctx` yet during the handshake.
::

## What `upgrade` returns

The accept value is `UpgradeReturn` — one required field and two optional ones.

::field-group
::field{name="userId" type="string"}
Required. The stable id for the user behind this socket. It is the row key for durable state, and the key channels use to re-attach the same user on reconnect. Maximum 256 characters — returning a longer one throws when the connection is accepted (it is a durable storage key, so it is capped rather than truncated). Use a stable ID (a user ID or ULID), not a token. This is the one field you almost always set.
::

::field{name="meta" type="TMeta"}
Optional. Per-connection metadata, surfaced as `ctx.meta` in every handler. Its type flows straight into `ctx.meta`, so return `{ userId: 'u1' }` and `ctx.meta.userId` is a typed `string`. Defaults to `{}`.
::

::field{name="tags" type="{ ephemeral?: { group: key } }"}
Optional. Initial ephemeral tags to attach before any handler runs. The keys are the ephemeral group names declared by the `tags(...)` capability, so this field is only useful with `tags()` listed. Persistent tags cannot be seeded here — add them at runtime with `ctx.tags.persistent(group).add(key)`.
::
::

```typescript [return.ts]
async upgrade(request) {
  const user = await authenticate(request)
  if (!user) throw RejectUpgrade(4003, 'Unauthorized')
  return {
    userId: user.id,
    meta: { userId: user.id, plan: user.plan },
    tags: { ephemeral: { role: user.role } },   // needs tags() with a 'role' group
  }
}
```

::caution
The group name in `tags.ephemeral` is not checked at compile time against what `tags(...)` declares — it is a plain string key. Return a group that `tags(...)` never declared (a typo, or `tags()` not listed at all) and the connection fails at runtime with `onUpgrade returned an ephemeral tag for group '<name>', which is not declared under tags (ephemeral)`. Double-check the group name matches the `tags(...)` capability exactly.
::

### `userId` is the durable key

`userId` is more than a label. It is the key WSKit uses to store per-user durable state, and to rejoin a returning user to the channels they belong to. Give the same person the same `userId` across reconnects and their durable memberships and stored state follow them. The reference for tags and channel rejoin lives in [Channels](/server/channels/overview) and the [tags capability](/server/capabilities/tags).

Inside any handler or hook the value is readable as `ctx.user.id` — a `string`, empty for an anonymous socket:

```typescript [read-user-id.ts]
base.on('whoami', {
  run(ctx) {
    ctx.send('you', { userId: ctx.user.id }) // the value from upgrade()
  },
})
```

### `UpgradeFn` and `UpgradeReturn`, named

If you write the gate as a standalone function (handy for reuse across handlers), these are the shapes to match:

```typescript [shapes.ts]
import type { UpgradeFn, UpgradeReturn } from '@wskit/server'

// UpgradeReturn<TMeta> = { userId: string; meta?: TMeta; tags?: {...} }
// UpgradeFn<TMeta>     = (request: Request) => UpgradeReturn<TMeta> | Promise<...>

interface Upgrade extends UpgradeReturn<{ username: string }> {}

const requireUsername: UpgradeFn<{ username: string }> = (request) => {
  const username = new URL(request.url).searchParams.get('username')
  if (!username) throw RejectUpgrade(4001, 'Missing username')
  return { userId: username, meta: { username } }
}

const base = define({
  upgrade: requireUsername,
  capabilities: [],
})
```

## Anonymous connections

`upgrade` is optional. Omit it — and the connection is still **accepted**, just anonymous:

- `userId` defaults to `''`
- `meta` defaults to `{}`
- `tags` defaults to none

```typescript [anonymous.ts]
const base = define({
  capabilities: [],
  // no upgrade — every connection is accepted as anonymous
})
```

`userId` is a required field, so you cannot "return no user" — keeping an `upgrade` that accepts everyone means returning an empty string explicitly:

```typescript [anonymous-explicit.ts]
const base = define({
  upgrade() {
    return { userId: '', meta: {} } // accepted, anonymous
  },
  capabilities: [],
})
```

Anonymous connections do not collapse onto one shared user, and they do not become users either. Each has no user identity at all: `ctx.user` exists but reaches nobody. Internally, storage that must not be shared between two anonymous sockets — a durable stream's row, for example — falls back to the connection's own id as its key. That is a storage detail, not a user identity. See [Users](/server/context-and-storage/users) for the full model. Storage that exists only to re-attach a returning user — durable channel memberships and persistent tags — has no stable key to match an anonymous reconnect against, so the durable write is **skipped** for an empty `userId` rather than keyed on the connection ID. If you want every socket authenticated, supply an `upgrade` that throws `RejectUpgrade(...)` when credentials are missing.

## Rejecting the upgrade

Throw `RejectUpgrade(code, reason)` to refuse a connection during the handshake. The `code` you pass decides whether the client sees an HTTP rejection or an immediate WebSocket close.

```typescript [reject.ts]
import { RejectUpgrade } from '@wskit/server/errors'

async upgrade(request) {
  const token = request.headers.get('authorization')
  if (!token) throw RejectUpgrade(401, 'Missing credentials')         // HTTP 401
  const user = await validateToken(token)
  if (!user) throw RejectUpgrade(4002, 'Invalid token')               // WS close 4002
  if (user.banned) throw RejectUpgrade(403, 'Account suspended')      // HTTP 403
  return { userId: user.id, meta: { userId: user.id } }
}
```

### How the reject code is answered

The number you pass to `RejectUpgrade` is interpreted by its range:

| `code` you pass                             | What the client gets                                                                                                                                                                  | When to use it                                                         |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| A valid WebSocket close code                | The handshake completes, then the socket is immediately closed with that code and reason. This is the **only** way a browser `WebSocket` can read the reason — via its `close` event. | When the client is a browser `WebSocket` and you want it to see _why_. |
| `400`–`599` (an HTTP status)                | That HTTP status, with `reason` as the response body.                                                                                                                                 | For a plain HTTP rejection a `fetch`/proxy can read.                   |
| A decimal, reserved, or out-of-range number | Falls back to HTTP `403 Forbidden` and is logged server-side.                                                                                                                         | A safe fallback; use a valid code instead.                             |

So `RejectUpgrade(4002, 'Invalid token')` lets a browser client read `'Invalid token'` off the close event, while `RejectUpgrade(401, 'Missing credentials')` returns a real HTTP 401. A value such as `4000.5` or `1006` is not turned into a close frame; it becomes the safe `403` response. Pick the range that matches how your client connects.

::tip
WebSocket close codes in the **4000–4999** range are reserved for application use. Reach for those when you want a browser client to distinguish your reasons. See [Close codes](/core/close-codes) for the full map.
::

### The non-WebSocket case

A plain `GET` with no `Upgrade: websocket` header never reaches your `upgrade`. The adapter answers it with HTTP `426 Upgrade Required` first. So `upgrade` only ever runs for a genuine WebSocket handshake — you do not have to guard against ordinary HTTP traffic inside it.

## A scoped `upgrade`

A plugin can supply its own `upgrade` through the scoped builder. It runs before the app's upgrade, sees only the raw request (not the app's userId), and merges its `meta` into the connection. That variant is covered in [Plugins › Authoring](/server/plugins/authoring).
