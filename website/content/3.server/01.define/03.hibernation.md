A Cloudflare Durable Object that holds open WebSocket connections normally has to stay in memory for as long as those connections live — even when nobody is sending anything. **Hibernation** lets the runtime evict that Durable Object from memory between messages and bring it back only when a frame actually arrives. You stop paying for idle wall-clock time, and a mostly-quiet room costs almost nothing to keep open.

::warning
Hibernation is a **Cloudflare Durable Objects** feature, so only the Cloudflare adapter — `@wskit/server-cloudflare` — supports it. On Bun, Node, or Deno the `hibernation` flag is ignored and the instance stays in memory the whole time. See [Installation](/start/installation) for the adapter packages.
::

WSKit turns this on with one config flag.

## Turning it on

Set `hibernation: { enabled: true }` in `define`.

```typescript [define.ts]
import { define, emits, t } from '@wskit/server'

const base = define({
  env: t<Env>(),
  hibernation: { enabled: true },
  capabilities: [
    emits({ message: t<{ text: string }>() }),
  ],
})
```

That is the whole config.

## What it is

Without hibernation, a Durable Object instance lives in memory the whole time a socket is open, holding every connection in a normal in-memory map. With hibernation, Cloudflare may **evict the instance between frames**. The sockets stay open at the edge, but the JavaScript object that owns them is gone until the next message wakes it up.

That wake gives you a fresh instance with an empty connection map. So for hibernation to be safe, WSKit has to be able to rebuild each connection from durable storage instead of memory — which is the part the framework handles for you.

## What survives

The thing to understand is that **in-memory variables do not survive a hibernation eviction, but durable storage does.**

| Survives hibernation | Does not survive |
| --- | --- |
| The open WebSocket connections (kept at the edge) | Module-level or instance-level variables you set in memory |
| `ctx.sql` and `ctx.kv` storage | A `Map` or counter you keep on the side |
| Each connection's `identity`, `meta`, and tags | Anything you cached in a closure |
| Durable channel memberships, resumable/recorded streams | The in-memory connection map |
| Durable alarms behind `ctx.schedule` | `setTimeout` / `setInterval` timers held in memory |
| (durable streams reattach on wake) | Plain in-flight `base.stream` generators — see below |

WSKit restores a connection's `identity`, `meta`, and tags from its own per-connection snapshot when the socket wakes, so your handlers see the same `ctx.identity` and `ctx.meta` they always did. The framework also persists durable channel memberships and durable streams to storage, so they come back too.

Plain (non-durable) streams are the exception. An in-flight `base.stream` generator lives only in memory, so it cannot be rebuilt after an eviction: a wake aborts it and the client receives `StreamAborted` with `detail.reason === 'hibernation-wake'`, then can restart it. Resumable and recorded streams do not have this problem — they replay from their durable buffer. The same goes for in-memory `setTimeout` / `setInterval` timers: they are lost on a wake, so use durable alarms (`ctx.schedule`) for anything that must fire after an idle stretch.

The rule for your own code: if you want state to outlive an idle period, **write it to `ctx.sql` or `ctx.kv`**, not to a plain variable.

```typescript [state.ts]
// WRONG under hibernation — this counter resets when the DO is evicted.
let messageCount = 0
base.on('say', { run() { messageCount += 1 } })

// RIGHT — durable storage survives the wake.
base.on('say', {
  run(ctx) {
    ctx.sql.exec(
      'INSERT INTO counters (id, n) VALUES (1, 1) ' +
        'ON CONFLICT(id) DO UPDATE SET n = n + 1',
    )
  },
})
```

::tip
The same advice applies even without hibernation — a Durable Object can be evicted for other reasons. Treating durable storage as the source of truth and memory as a cache is the safe default. See [Context and storage](/server/context-and-storage/overview) for `ctx.sql` and `ctx.kv`.
::

## How WSKit handles it

You do not write any wake-up code. When hibernation is on, the framework:

- Stores each connection's `identity`, `meta`, and tags in a per-socket snapshot, so a woken instance can rebuild that connection's `ctx` without memory.
- Restores the connection on the first message after a wake, then runs your handler as normal.
- Persists durable channel memberships and durable streams to storage so they reattach after a wake.
- Keeps the right connections and drops orphaned ones when a fresh instance boots, by reconciling the sockets the edge handed back against what storage knows.

From a handler's point of view nothing changes — `ctx.identity`, `ctx.meta`, `ctx.send`, `ctx.broadcast`, and storage all behave the same whether or not the instance was just woken.

## The trade-offs

Turning hibernation on changes two things about server-side liveness checks.

### Server pings are disabled

WSKit's server-side keepalive pings stop. Under hibernation, the runtime answers the client's keepalive "ping" with "pong" **at the edge**, so a hibernated Durable Object is not woken just to reply to a heartbeat. That is the whole point — but it means the server is not actively probing each client on a timer.

### Latency and quality go null

Because the server is not running its own ping/pong round-trips, it has no fresh round-trip time to report. `ctx.latency` and `ctx.quality` only exist when `keepalive()` is listed — without it, reading them is a compile error, not a `null`. So the rule is: when `keepalive()` *is* listed alongside hibernation, both fields are always `null`.

```typescript [latency.ts]
import { define, t } from '@wskit/server'
import { keepalive } from '@wskit/server/keepalive'

const base = define({
  env: t<Env>(),
  hibernation: { enabled: true },
  capabilities: [keepalive({ pingIntervalMs: 30_000, idleTimeoutMs: 60_000 })],
})

base.on('check', {
  run(ctx) {
    // Under hibernation these are always null — the server runs no pings.
    console.log(ctx.latency)  // null
    console.log(ctx.quality)  // null
  },
})
```

If you need live server-measured latency, leave hibernation off. If you mostly care about cost for idle rooms and the client-side connection health is enough, turn it on. (The `keepalive` capability and `ctx.latency` / `ctx.quality` are covered in the [keepalive capability](/server/capabilities/keepalive).)

## When to use it

Reach for hibernation when connections are open far longer than they are busy — chat rooms, presence channels, collaborative documents, anything where a socket sits idle for long stretches. Leave it off when you need the server to actively measure each client's latency, or when the workload is busy enough that the instance would rarely be evicted anyway.
