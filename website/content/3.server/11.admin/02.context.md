The `ctx` your `api` factory receives — and the `ctx` the built-in operations run against — is the **admin context**. It is the whole-server view: no `id`, no `send`, no `meta`, because no socket is the subject. This page lists what it does have.

## Broadcast to everyone

`ctx.broadcast(event, payload)` sends an event to every live connection. It is typed against your server's `emits(...)`, so a wrong event name or payload is a compile error.

```typescript
api: (ctx) => ({
  announce(text: string) {
    ctx.broadcast('announcement', { text })
  },
})
```

## Reach a channel by name

`ctx.channels.get(name)` returns a handle to one channel, addressed by name — you are not a member, you are acting on it from outside. For a dynamic family, pass the family key and the instance name: `ctx.channels.get('rooms', 'rooms:42')`.

`ctx.channels` belongs to the [`channels()`](/server/capabilities/channels) capability. List it in `define({ capabilities: [...] })` or `ctx.channels` is not on the type at all, and reading it is a compile error — the same gating your handlers get.

The handle gives you the channel operations that do not need a connection:

```typescript
api: (ctx) => ({
  async closeRoom(room: string) {
    const channel = ctx.channels.get(room)
    channel.broadcast('room-closing', {}) // to the channel's members
    for (const member of channel.members()) {
      await channel.kick(member.ref(), { reason: 'room-closed', revoke: true })
    }
  },
})
```

`channel.kick(target, opts)` removes a `UserRef` (or a `TagRef` for everyone holding a tag) from the channel. Pass `{ revoke: true }` to also drop the durable membership row, so the user does not auto-rejoin on their next reconnect.

## Drop a user everywhere

`ctx.purgeUser(userId)` is the one call the auth-webhook case needs. It leaves every channel the user belongs to — live and durable — removes their persistent tags, wipes their inbox rows and read receipts, their last-seen mark, their durable streams, and closes every live socket they hold. It needs no capability of its own — it cleans up whichever durable state a user actually has.

Every cleanup step runs even if an earlier one throws, and the sockets are always closed — a purge never stops halfway through and leaves live connections open because one step failed. If any step failed, `ctx.purgeUser` throws after everything else has run, with all the failures collected together, so you learn about a partial cleanup instead of it failing silently.

```typescript
api: (ctx) => ({
  userDeleted(id: string) {
    return ctx.purgeUser(id)
  },
})
```

### Broadcast streams the user created

A [broadcast](/server/streams/broadcast) stream — one created with `broadcast: true` on a [resumable](/server/streams/durable-resumable) or [recorded](/server/streams/durable-recorded) stream — belongs to the whole channel, not just to the connection that started it. So `ctx.purgeUser` has to decide what happens to a stream a purged user created but other people are still reading.

**By default it deletes that content too**, same as everything else the user owns: the stream and its recorded chunks are gone. This is the safe default for a "delete this user's data" call — a caller who does not read the options should not silently leave data behind.

```typescript
// Default: any broadcast stream alice created (the stream row and its
// recorded chunks) is deleted, the same as everything else she owns.
await ctx.purgeUser('alice')
```

Pass `{ keepBroadcastContent: true }` when the broadcast content belongs to the channel in your app's model, and other members should still be able to read it after alice is gone:

```typescript
// Keep the channel-owned stream and its chunks. alice is still removed
// as its creator — the row no longer credits a deleted user.
await ctx.purgeUser('alice', { keepBroadcastContent: true })
```

Either way, the user is cleared as the stream's creator — a purge never leaves a record crediting a deleted user.

## Close connections

`ctx.closeConnections()` closes every live socket. Pass `{ userId }` to close only one user's sockets, and an optional close code and reason.

```typescript
ctx.closeConnections() // everyone
ctx.closeConnections({ userId: 'user_9' }, 4001, 'session revoked') // one user
```

## Inspect connections

`ctx.connections.all()` returns a snapshot of every live connection, and `ctx.connectionCount` is how many there are right now. To reach one connection or one user, use `ctx.connections.get(ref)` and `ctx.users.get(id)`.

```typescript
api: (ctx) => ({
  onlineUsers() {
    return ctx.connections.all().map((c) => c.userId)
  },
})
```

## Storage, scheduling, and platform

The admin context also carries the storage and platform surface, the same shapes your handlers use:

::field-group
::field{name="sql" type="SQLProvider"}
Run SQL against the server's durable store — `ctx.sql.exec('UPDATE ...', ...)`.
::
::field{name="kv" type="KVProvider"}
Simple key-value get / set / delete.
::
::field{name="schedule / cancelScheduled" type="(taskId, ...) => void"}
Queue or cancel a scheduled task, exactly as in a handler. Owned by the [`scheduled()`](/server/capabilities/scheduled) capability — without it listed, neither member is on the type.
::
::field{name="env" type="Env"}
Your platform bindings.
::
::field{name="log" type="Logger"}
The server's structured logger.
::
::field{name="platform" type="Platform"}
The raw platform object from the adapter.
::
::

::note
`tags` admin operations are not on this context yet — reach tag groups from a connection handler for now.
::
