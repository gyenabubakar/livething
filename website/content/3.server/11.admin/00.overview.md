Every handler you write runs **because a socket did something**. A client connected, or it sent a message. So the handler's `ctx` belongs to that one socket: `ctx.connection.id` is that client's ID, and `ctx.send(...)` replies to that client.

But many things happen **outside** the socket layer and still need to change the live state. Your auth provider sends a `user.deleted` webhook (an HTTP request that another service sends to your server when something happens). A cron job (a task that runs on a timer) archives old rooms at midnight. An admin clicks "remove member" in a separate dashboard. None of these is a WebSocket client. The trigger arrives over HTTP, from a queue, or from a timer. That code needs a typed, safe way to reach the running server.

That way is the **admin surface**: a set of operations you call from your own server code. You get it from the object your adapter gives you. On Node, `bind(...)` returns an endpoint (called `chat` on this page), and you call `await chat.admin()`. On Cloudflare, you call `await stub.admin()` on the Durable Object stub.

## It has no current connection

An admin operation runs when no socket is involved. So its context is **connectionless**: there is no "current connection" to act on. It has no `ctx.connection.id`, `ctx.send`, `ctx.meta`, or `ctx.close`. If you use one of them, TypeScript reports a compile error.

Instead, it has operations for the whole server: broadcast to everyone, find a channel by name, remove a user everywhere, and read storage. The `onShutdown` hook and scheduled tasks work the same way. They are connectionless too.

```typescript
// Inside a handler: a socket is the subject.
base.on('ping', {
  run(ctx) {
    ctx.connection.id // ✓ this client
    ctx.send('pong', {}) // ✓ reply to this client
  },
})

// An admin operation: no socket is the subject.
base.assemble({
  handlers: [
    /* ... */
  ],
  api: (ctx) => ({
    evict(userId: string) {
      ctx.connection.id // ✗ compile error: there is no "this client"
      ctx.purgeUser(userId) // ✓ act on the whole server
    },
  }),
})
```

## Two kinds of operation

The admin surface has two layers.

**Built-in operations** come with LiveThing. You do not write them. `broadcast`, `purgeUser`, `closeConnections`, `connections`, `users`, and the others are always there. A few more come with their capability: `channels` comes with [`channels()`](/server/capabilities/channels), and `schedule` and `cancelScheduled` come with [`scheduled()`](/server/capabilities/scheduled). If the capability is not in your server, these members do not exist on `ctx`, and using them is a compile error. See [Admin Context](/server/admin/context) for the full list. On Cloudflare, the stub gives you the built-ins as flat methods with different names (for example `listConnections()` and `sendToUser()`). See [Reaching it](/server/admin/reaching-it).

**Your own operations** are the `api` you write on `assemble`. It is a factory (a function that builds and returns an object). The object holds the methods you want the outside caller to have. See [Authoring an API](/server/admin/authoring).

```typescript
const definition = base.assemble({
  handlers: [
    /* ... */
  ],
  api: (ctx) => ({
    announce(text: string) {
      ctx.broadcast('announcement', { text })
    },
  }),
})

// Later, from a Node webhook or cron job:
const admin = await chat.admin()
await admin.announce('Maintenance in 5 minutes') // your own operation
await admin.purgeUser('user_9') // a built-in
```

On Cloudflare, the same two calls go through the Durable Object stub (the handle a Worker uses to call methods on a Durable Object):

```typescript [worker.ts]
const admin = await env.CHAT_DO.get(id).admin()
await admin.announce('Maintenance in 5 minutes')
await admin.purgeUser('user_9')
```

::warning
**Built-in names win.** Your `api` might return a method with the same name as a built-in, for example your own `broadcast`. In that case LiveThing keeps the built-in and drops your method. Your method cannot replace a LiveThing operation. Give your own operations different names.
::

Some names already have a meaning in JavaScript, and they follow a different rule. These names are `then`, `constructor`, `__proto__`, `toString`, `valueOf`, and every other name on `Object.prototype` (the object that every plain JavaScript object gets its built-in methods from). An `api` method with one of these names would break the admin surface. For example, a `then` method makes `await chat.admin()` wait forever. So LiveThing **throws a `LiveThingConfigError`** when the server starts, because it builds the admin surface once at startup to check the names. It does not drop these methods without telling you. Rename the method.

There is one exception. If your `api` factory returns a class instance, JavaScript adds a `constructor` property to the class prototype automatically. LiveThing ignores that property. A `constructor` member that your own code defines is still rejected.
