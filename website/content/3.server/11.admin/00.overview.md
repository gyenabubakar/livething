Every handler you write runs **because a socket did something** — a client connected, or sent a message. So its `ctx` is tied to that one socket: `ctx.connection.id` is who they are, `ctx.send(...)` replies to them.

But plenty happens **outside** the socket layer that still needs to change the live state. Your auth provider fires a `user.deleted` webhook. A cron job archives old rooms at midnight. An admin clicks "remove member" in a separate dashboard. None of these is a WebSocket client — the trigger arrives over HTTP, a queue, or a timer — and that code needs a typed, safe way to reach the running server.

That is the **admin surface**: a set of operations you call from your own server code. The adapter's live object reaches it — on Node, `await chat.admin()`; on Cloudflare, `await stub.admin()`.

## It has no current connection

Because an admin operation runs when no socket is in the picture, its context is **connectionless** — there is no "current connection" to act on. So it has no `ctx.connection.id`, `ctx.send`, `ctx.meta`, or `ctx.close`. Reaching for one is a compile error.

What it has instead are whole-server operations: broadcast to everyone, reach a channel by name, drop a user everywhere, read storage. This is the same split you already saw with `onShutdown` and scheduled tasks — they are connectionless too.

```typescript
// Inside a handler: a socket is the subject.
base.on('ping', {
  run(ctx) {
    ctx.connection.id // ✓ this client
    ctx.send('pong', {}) // ✓ reply to this client
  },
})

// An admin operation: no socket is the subject.
base.assemble({
  handlers: [
    /* ... */
  ],
  api: (ctx) => ({
    evict(userId: string) {
      ctx.connection.id // ✗ compile error — there is no "this client"
      ctx.purgeUser(userId) // ✓ act on the whole server
    },
  }),
})
```

## Two kinds of operation

The admin surface is built from two layers.

**Built-in operations** ship with the framework. You do not write them — `broadcast`, `purgeUser`, `closeConnections`, `connections`, `users`, and the rest are always there. A few more come with their capability: `channels` with [`channels()`](/server/capabilities/channels), `schedule` with [`scheduled()`](/server/capabilities/scheduled). See [Admin Context](/server/admin/context) for the full set.

**Your own operations** are the `api` you author on `assemble` — a factory that returns whatever methods you want the outside caller to have. See [Authoring an api](/server/admin/authoring).

```typescript
const definition = base.assemble({
  handlers: [
    /* ... */
  ],
  api: (ctx) => ({
    announce(text: string) {
      ctx.broadcast('announcement', { text })
    },
  }),
})

// Later, from a Node webhook or cron:
const admin = await chat.admin()
await admin.announce('Maintenance in 5 minutes') // your own operation
await admin.purgeUser('user_9') // a built-in
```

On Cloudflare the same two calls go through the Durable Object stub:

```typescript [worker.ts]
const admin = await env.CHAT_ROOM.get(id).admin()
await admin.announce('Maintenance in 5 minutes')
await admin.purgeUser('user_9')
```

::warning
**Built-in names win.** If your `api` returns a method with the same name as a built-in (say you also name one `broadcast`), the built-in is kept and yours is dropped — it cannot shadow a framework operation. Give your own operations distinct names.
::

JavaScript's own reserved object names are different: an `api` method named `then`, `constructor`, `__proto__`, `toString`, `valueOf`, or another inherited `Object.prototype` name makes the admin surface unsafe or ambiguous, so the engine **throws a `WSKitConfigError`** while building it. It does not silently drop those methods. Rename the method. The `constructor` marker that JavaScript places on a class prototype is ignored; an app-defined `constructor` member is rejected.
