You add your own admin operations with the `api` field of `assemble`. The `api` field is a factory, which means a function that builds and returns an object. It receives the connectionless [admin context](/server/admin/context) and returns an object of methods. Code outside the socket layer can then call those methods through the adapter's admin surface.

```typescript [server.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'

const base = server({
  capabilities: [
    channels(),
    emits({ 'room-archived': t<{ room: string }>() }),
  ],
})

export const definition = base.assemble({
  handlers: [
    /* your on / channel / request handlers */
  ],
  api: (ctx) => ({
    archiveRoom(room: string) {
      ctx.sql.exec('UPDATE rooms SET archived = 1 WHERE id = ?', room)
      ctx.broadcast('room-archived', { room })
    },
    liveCount() {
      return ctx.connectionCount
    },
  }),
})
```

LiveThing runs the `api` factory once when the server starts, and again each time you get the admin surface. Every method you return becomes a call on the admin surface, next to the built-in operations such as `purgeUser`.

How you get the admin surface depends on the runtime. On Node, it comes from the endpoint that `bind(...)` returns (called `chat` below). On Cloudflare, it comes through the Durable Object stub, which is the object your Worker uses to call one Durable Object:

```typescript [node.ts]
const admin = await chat.admin()
await admin.archiveRoom('room:42')
const live = admin.liveCount()
```

```typescript [worker.ts]
const id = env.CHAT_ROOM.idFromName('lobby')
const admin = await env.CHAT_ROOM.get(id).admin()
await admin.archiveRoom('room:42')
const live = await admin.liveCount()
```

On Cloudflare, every call goes from the Worker to the Durable Object, which is a remote call. So every call returns a promise, even when your method returns nothing. See [Reaching it](/server/admin/reaching-it) for what can and cannot cross that boundary.

::note
A built-in operation always wins over your own method with the same name. For example, if you return a method called `purgeUser`, callers still get the built-in `purgeUser`, and your method is ignored. Give your methods their own names. A few names, such as `then` and `constructor`, are not allowed at all, because JavaScript already gives them a meaning. If you use one, the server fails at startup with a `LiveThingConfigError`.
::

## The `ctx` is connectionless

The `ctx` your factory receives is the admin context. It is a view of the whole server, with no current socket. `ctx.send`, `ctx.connection.id`, and `ctx.meta` are **not** on it, so using one of them is a compile error. Instead you get `ctx.broadcast`, `ctx.connections`, `ctx.users`, `ctx.purgeUser`, `ctx.closeConnections`, `ctx.sql`, and the rest of the members listed in [Admin Context](/server/admin/context).

Members that belong to a capability follow the same rules here as in your handlers. `ctx.channels` needs [`channels()`](/server/capabilities/channels) in the capabilities list. `ctx.schedule` and `ctx.cancelScheduled` need [`scheduled()`](/server/capabilities/scheduled). Without the capability, the member is not on the type, so reading it is a compile error. This is better than a call that does nothing and gives no error.

```typescript
api: (ctx) => ({
  announce(text: string) {
    ctx.broadcast('announcement', { text }) // ✓ whole-server
    // @ts-expect-error: no current connection here
    ctx.send('announcement', { text })
  },
})
```

## Return types reach the caller

Whatever a method returns becomes the caller's result. TypeScript infers its type, so you do not declare a response schema. A method that returns a value is a read. A method that returns nothing is an action.

```typescript
api: (ctx) => ({
  // read: the return type reaches the caller
  bans() {
    return ctx.sql
      .exec<{ id: string }>('SELECT id FROM bans')
      .toArray()
  },
  // action: returns nothing
  async deleteAccount(id: string) {
    await ctx.purgeUser(id)
  },
})
```

::note
This is the `api` of the **top-level** server. A plugin's `assemble` also takes an `api`, but a plugin's `api` is per connection. A host handler reaches it with `ctx.plugin(id)`, not through the admin surface. See [Scoped context and API](/server/plugins/scoped-ctx).
::

## `purgeUser` cleans up all durable data

`ctx.purgeUser(id)` removes a user everywhere: channel membership, persistent tags, inbox rows and read receipts, their last-seen mark, and their durable streams. Then it closes their live sockets. It does not need a capability of its own. It cleans up only the durable data that exists for that user. For a capability you did not list, there is nothing to clean up, so that step does nothing.

Every cleanup step runs, even if an earlier step throws. The live sockets are always closed. If any step failed, `ctx.purgeUser` rejects after all steps have run. The error is an `AggregateError` that holds all the failures, not only the first one.

By default, it also deletes the content of any broadcast stream the user created. This is the safe choice for a "delete this user's data" call. Pass `{ keepBroadcastContent: true }` to keep that content instead. See [Admin Context](/server/admin/context#broadcast-streams-the-user-created) for the details.
