A queue is a list of work that runs in order: first in, first out. LiveThing gives every live connection its own work queue in memory. By default, your `on` handlers wait in this queue, so the handlers for one connection run in the same order the client sent the messages. The whole server does not run one task at a time. Only the work of one connection is ordered.

The queue is internal to LiveThing and has no API. You do not read it, add work to it, or manage it yourself. You only choose, for each handler, whether it waits in the queue.

The queue of one connection holds up to **256 unfinished ordered handlers**. This number includes the handler that is running now. When the queue is full, LiveThing rejects the next ordered handler with the built-in `ConnectionBusy` error (code `connection-busy`). The connection stays open. The error's `detail.retryAfterMs` value tells the client how many milliseconds to wait before it tries again. LiveThing sets it to `1000`.

`ConnectionBusy` is separate from the optional [`rateLimit()`](/server/capabilities/rate-limit) capability. A rate limit controls how often the server accepts messages from a client. `ConnectionBusy` means the server has too much unfinished work for this connection right now.

Messages for a channel also wait while a subscribe to that channel runs, because the client sends the subscribe first. They wait until `check`, `commit` and `onSubscribe` have finished, before they reach the queue. Up to **256 messages** of one connection can wait like this. The next message gets `ConnectionBusy`. The rate limit counts a waiting message when it arrives, not when it runs.

There is also a limit on **bytes**. One connection can hold up to **twice the adapter's message limit** (64 MiB with the default 32 MiB limit) of messages that have arrived but whose handler has not started yet, whatever they wait for: their turn in the queue, a subscribe, or an async intercept. A message counts from the moment it arrives until its handler starts. After that, its memory belongs to the handler, so a long request or stream does not keep counting. A message that would take the connection over this limit gets `ConnectionBusy`, the same as a full queue. Without this limit, one connection could hold hundreds of large messages at the same time.

The limit counts the messages that can wait: your app's events, and a channel subscribe, which counts until `check`, `commit` and `onSubscribe` have finished. LiveThing's other protocol messages (leaving a channel, cancelling a stream, read receipts), `ping`, `pong` and a client's answer to a [server request](/server/capabilities/server-requests) do not count. A full budget never stops a client from leaving a channel, cancelling a stream or answering the server.

The byte budget is not the only wait. An answer to a server request is handled at once. A protocol message for one channel, such as cancelling a stream of that channel or a read receipt in it, waits while a subscribe to that channel runs, like every other message for that channel. It is one of the 256 messages that can wait there, so it can get `ConnectionBusy` too. Leaving a channel never waits: it cancels the pending subscribe to that channel first.

The pieces of an [upload](/server/binary/uploads) count too, from the moment they arrive until the upload's `run` reads them. The upload's window keeps them small: `windowBytes + pieceBytes` must fit in the adapter's message limit, which is half of this budget.

## Busy on `http()`

On a WebSocket, each message that does not fit gets its own `ConnectionBusy` error. On [`http()`](/server/adapters/transports), the client sends its messages in POST batches of up to 255 frames, one below the queue's 256, and the server checks a whole batch before it hands any of it to your handlers. It counts the same messages as the queue: app events and channel subscribes. `ping`, `pong` and `__close__` go in a second POST lane, so a busy batch never holds them back, as on a WebSocket. The server also never counts the other protocol messages or an answer to a server request, so these never use up room. But they travel in the batch, so when the server refuses a batch, it refuses them too. They go out with the rest of the batch when the client sends it again.

When the frames in flight plus the batch would go over 255 frames, or over the adapter's message limit in bytes, the server takes none of the batch. It answers `503` with a `LiveThing-Error: busy` header and a JSON body:

```json
{ "room": 40, "retryAfterMs": 250 }
```

`room` is how many frames from the start of the batch fit now. The client waits `retryAfterMs` (250 ms at first, then doubling up to 1 second), sends only `room` frames, and keeps the rest in order in its queue. When `room` is `0`, it sends one frame, so it learns when the server has room again. A busy answer drops nothing and does not end the connection. When the server stays busy for 30 seconds and takes no frame, the client counts it as a failed POST and reconnects. The frames still in its queue are lost then, as they are when a WebSocket drops. Your code sees none of this: there is no `ConnectionBusy` error for a frame that waits in the client's queue.

Some work can skip the queue. Such work interleaves with the queued work: it starts at once and runs at the same time as the work in the queue. The table shows the default for each kind of work:

| Work                                                                     | Default                     | How to change it                                                                                                       |
| ------------------------------------------------------------------------ | --------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `on` and channel `on` handlers                                           | Wait in the queue           | Set `allowInterleaving: true` when the handler does not depend on the order of earlier messages.                       |
| `request` and channel `request` handlers                                 | Interleave with queued work | Set `allowInterleaving: false` when the request must see the changes that earlier handlers made.                       |
| Stream starts                                                            | Skip the queue              | Set `allowConcurrent: true` to let one connection run the same stream event more than once at the same time.           |
| Answers to server→client requests, and LiveThing's own protocol messages | Handled at once             | None. They are not your handlers. A protocol message for a channel still waits while a subscribe to that channel runs. |

By default, a connection can run only one stream of the same event at a time. A second start is rejected with the `StreamAlreadyActive` error while the first stream is still running.

Only work for the same connection is ordered. Work for different connections runs at the same time. The queue lives only in memory while the connection is open. It does not save messages for later delivery, and it is not related to the [Inbox](/server/inbox/overview) capability.

Only work that waits in the queue can fail with `ConnectionBusy`. A request interleaves by default, so it never waits in the queue and cannot fail this way. A request fails with `ConnectionBusy` only when you set `allowInterleaving: false` on it, or when it is a channel request sent while a subscribe to that channel is still pending, because every frame for the channel waits behind the subscribe. In this version of `get-profile`, the request waits for earlier ordered work:

```typescript [server/profile-handlers.ts]
import * as v from 'valibot'
import { base } from './base'
import { loadProfile } from './helpers'

export const handleGetProfile = base.request('get-profile', {
  allowInterleaving: false,
  input: v.object({ userId: v.string() }),
  run(ctx, input) {
    return loadProfile(input.userId)
  },
})
```

On the client, a request that fails with `ConnectionBusy` can wait and try again. This function sends the `get-profile` request until it gets an answer. When the error is `ConnectionBusy`, it waits `retryAfterMs` milliseconds before the next try. It throws any other error again:

```typescript [client/profile.ts]
import { ConnectionBusy } from '@livething/core'
import { socket } from './socket'

async function getProfileWithRetry(input: { userId: string }) {
  for (;;) {
    try {
      return await socket.request('get-profile', input)
    } catch (error) {
      if (!ConnectionBusy.matches(error)) throw error

      await new Promise((resolve) =>
        setTimeout(resolve, error.detail.retryAfterMs),
      )
    }
  }
}

// This listener receives only unclaimed errors from fire-and-forget work.
socket.onServerError((error) => {
  console.error('unclaimed server error', error)
})
```

A failed `socket.request(...)` rejects the Promise of that request, so handle the error in `catch`. LiveThing does not also pass it to `socket.onServerError(...)`. A message sent with `socket.send(...)` is fire-and-forget: it has no Promise. So a `ConnectionBusy` error for an `on` handler goes to `socket.onServerError(...)`.

## A familiar pattern

Actor systems use a similar model. In an actor system, each actor has a mailbox, which is a queue of messages. Erlang and Elixir processes, and Akka and Pekko actors, handle one mailbox message at a time, while different processes or actors run at the same time. LiveThing uses different names and has its own rules for requests and streams. The idea is the same: the state of one connection is easier to understand when its work runs in order.
