WSKit gives every live connection its own ordered, in-memory work queue for ordinary application handlers. This keeps stateful work on one connection in the order the client sent it, without making the whole server run one task at a time.

The queue is an engine rule, not an API. You do not read it, add work to it, or manage it directly.

The queue admits up to **256 unfinished ordered operations** for one connection, including the operation currently running. When it is full, the next ordered operation is rejected with the built-in `ConnectionBusy` error and the connection stays open. Its `detail.retryAfterMs` value tells the client how long to wait before trying again. This is separate from the optional [`rateLimit()`](/server/capabilities/rate-limit) capability: rate limiting controls how often frames are accepted, while `ConnectionBusy` reports temporary processing pressure.

| Work                                              | Default                     | Opt out or opt in                                                                   |
| ------------------------------------------------- | --------------------------- | ----------------------------------------------------------------------------------- |
| `on` and channel `on` handlers                    | Wait in the queue           | Set `allowInterleaving: true` when the handler does not need ordered state.         |
| `request` and channel `request` handlers          | Interleave with queued work | Set `allowInterleaving: false` when the request must observe earlier state changes. |
| Stream starts                                     | Skip the ordinary queue     | Use `allowConcurrent` to control overlapping runs of the same stream event.         |
| Server→client request answers and protocol frames | Handled immediately         | They are not application handlers.                                                  |

Only work for the same connection is ordered. Different connections continue to run concurrently. The queue is an in-memory scheduling rule for a live connection; it is not durable delivery and is unrelated to the [Inbox](/server/inbox/overview) capability.

```typescript [client.ts]
import { ConnectionBusy } from '@wskit/core'

socket.onServerError((error) => {
  if (ConnectionBusy.matches(error)) {
    setTimeout(retry, error.detail.retryAfterMs)
  }
})
```

## A familiar pattern

This is similar to the message queues used by actor systems. Erlang and Elixir processes, and Akka and Pekko actors, process one mailbox item at a time while different processes or actors can run concurrently. WSKit uses different names and has different rules for requests and streams, but the same idea makes per-connection state easier to reason about.
