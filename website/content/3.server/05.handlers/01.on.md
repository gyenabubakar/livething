`base.on(event, config)` handles one **client→server event** — the client sends a message, your `run` reacts, and that's it. There is no reply back to the sender for this event; the client's `send()` does not wait for anything. `base.on` is always on `base`, no capability needed.

```typescript [chat.ts]
import { emits, server, t } from '@wskit/server'
import * as v from 'valibot'

const base = server({
  capabilities: [
    emits({ message: t<{ text: string; from: string }>() }),
  ],
})

export const handleSend = base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.broadcast('message', {
      text: input.text,
      from: ctx.user.id,
    })
  },
})

export const definition = base.assemble({ handlers: [handleSend] })
```

On the client this is a plain send — no awaiting:

```typescript [app.ts]
socket.send('send-message', { text: 'hello' })
```

## The config

| Field               | Required | What it does                                                                                                                                                                          |
| ------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `input`             | no       | A Validator for the payload. The engine validates the wire payload before `run`; a bad payload never reaches your code. Omit it and `input` is typed `unknown`.                       |
| `run`               | yes      | `run(ctx, input)`. Your code. Returns `void` or `Promise<void>` — see [return value](#the-return-value).                                                                              |
| `allowInterleaving` | no       | Run this handler without waiting for earlier ordinary work on the same connection. Defaults to `false`, so `on` handlers run in order per connection.                                 |
| `rateLimit`         | no       | A per-handler rate-limit override. Only present when the [`rateLimit()`](/server/capabilities/rate-limit) capability is listed; passing it without the capability is a compile error. |

## Validating the payload

Pass a schema to `input` and WSKit validates each incoming payload against it. If it fails, `run` does **not** run; the framework surfaces a validation error instead, and your [`base.onValidationError`](/server/lifecycle-and-intercept/hooks) hook (if any) fires. Inside `run`, `input` is typed from the schema — no cast, no re-check.

```typescript [handlers.ts]
const handleEchoPing = base.on('echo-ping', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    // input: { text: string } — already validated
    ctx.send('echo-pong', { text: input.text })
  },
})
```

Omit `input` to accept any payload. It arrives typed `unknown`, so you narrow it yourself:

```typescript [handlers.ts]
const handleEchoAnything = base.on('echo-anything', {
  run(ctx, input) {
    // input: unknown — no schema, so you decide what to trust
    ctx.send('anything-echo', { got: input })
  },
})
```

::tip
`input` validation is for the **payload only**. The event name itself is already routed — a client that sends an event you never bound is **silently dropped** (the engine ignores the frame and the connection stays alive), not rejected with an error. You only validate the contents.
::

A validation failure on an `on` event still reaches the client, just not through a promise or a loop — there's neither here. The engine sends a `validation-failed` error frame, and because nothing is waiting on a correlation id for a fire-and-forget event, it lands on the client's server-error listener: [`socket.onServerError(...)`](/client/errors/onerror-routing).

```typescript [app.ts]
socket.onServerError((error) => {
  // a bad payload on any `on` event you didn't otherwise catch surfaces here
  console.warn('unclaimed error', error)
})
```

## The return value

`run` is fire-and-forget. Whatever you return is **ignored** — there is no response channel for an `on` handler. Return `void`, or make `run` `async` and return a `Promise<void>`; the framework awaits it so a thrown rejection is caught.

```typescript [handlers.ts]
const handleAsyncPing = base.on('async-ping', {
  input: v.object({ delay: v.number() }),
  async run(ctx, input) {
    await new Promise((resolve) => setTimeout(resolve, input.delay))
    ctx.send('async-done', { message: 'async-done' })
  },
})
```

To send something _back_ to the client and have the client await it, use [`base.request`](/server/handlers/request) instead — that's the request/response kind.

## Work order on one connection

`on` handlers are ordered per connection by default. See [Per-Connection Event Queue](/server/handlers/per-connection-queue) for the queue, the `allowInterleaving` escape hatch, and the rules for requests and streams.

## Sending and broadcasting

`run` reaches the connection through `ctx`. Two methods push events out, both typed against your [`emits({...})`](/server/capabilities/emits) declarations — you can only send an event you declared, with the payload shape it declared:

- **`ctx.send(event, payload)`** — to the calling connection. Returns nothing — it dispatches the frame or throws (an undeclared event, or a non-object payload). The `false`-when-gone return belongs to `ctx.connections.get(ref).send()`.
- **`ctx.broadcast(event, payload, options?)`** — to every _other_ connection on this server instance. The caller is excluded by default; pass `{ includeSelf: true }` to include them.

```typescript [handlers.ts]
const handleSay = base.on('say', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.send('echo', { text: input.text }) // back to me
    ctx.broadcast('message', { text: input.text }) // everyone else
    ctx.broadcast(
      'message',
      { text: input.text },
      { includeSelf: true },
    ) // everyone, me too
  },
})
```

Sending an event you never declared, or a payload of the wrong shape, is a compile error. The full set of things on `ctx` — storage, connections, tags, channels — is covered in [Context and storage](/server/context-and-storage/overview).

## Throwing a typed error

An `on` handler has no reply, but a throw still matters: it stops the handler and is reported to your [`base.onError`](/server/lifecycle-and-intercept/hooks) hook. For a clean, typed failure, throw an error built with `error()` rather than a bare `Error`. The shared error model — defining errors, `error()`, `.matches()`, the built-in catalog — lives in [Core](/core/error-model); declare your errors with the [`errors([...])`](/server/capabilities/errors) capability.

```typescript [handlers.ts]
import { error, errors, server, t } from '@wskit/server'
import * as v from 'valibot'

const Forbidden = error('forbidden', v.object({ reason: v.string() }))

const base = server({
  capabilities: [errors([Forbidden])],
})

const handleDelete = base.on('delete-room', {
  input: v.object({ roomId: v.string() }),
  run(ctx, input) {
    if (!isOwner(ctx.user.id, input.roomId)) {
      throw Forbidden({ reason: 'not the room owner' })
    }
    deleteRoom(input.roomId)
  },
})
```

::note
Because `on` is fire-and-forget, a throw does not reject anything on the client — there is no pending promise to reject. It ends this handler run and fires your error hook. Like a validation failure, the resulting error frame is unclaimed and lands on [`socket.onServerError(...)`](/client/errors/onerror-routing) rather than on any specific call. To reject something the client is awaiting, use [`base.request`](/server/handlers/request), where a throw rejects the client's pending request.
::

## Per-handler rate limit

With the [`rateLimit()`](/server/capabilities/rate-limit) capability listed, you can tighten, loosen, or disable the limit for one event by passing `rateLimit` in the config. It overrides the global rule for this handler only.

```typescript [handlers.ts]
const handleSend = base.on('send-message', {
  input: v.object({ text: v.string() }),
  rateLimit: { enabled: true, max: 10, windowMs: 60_000 }, // at most 10/min on this event
  run(ctx, input) {
    ctx.broadcast('message', {
      text: input.text,
      from: ctx.user.id,
    })
  },
})
```

Without the `rateLimit()` capability the field isn't on the config type, so adding it is a compile error — you can't silently configure a limit the engine isn't there to enforce.
