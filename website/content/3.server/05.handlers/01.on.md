`base.on(event, config)` handles one **client→server event**. The client sends a message and your `run` function reacts to it. The server sends no reply for this event, so the client's `send()` does not wait for anything. This style is called **fire-and-forget**: the sender sends the message and does not wait for a result. `base.on` is always on `base`. It does not need a capability.

```typescript [server/huddle.ts]
import { emits, server, t } from '@livething/server'
import * as v from 'valibot'

const base = server({
  capabilities: [
    emits({ 'user-renamed': t<{ userId: string; name: string }>() }),
  ],
})

export const handleRename = base.on('rename', {
  input: v.object({ name: v.string() }),
  run(ctx, input) {
    ctx.user.setMeta({ name: input.name })
    ctx.user.broadcast('user-renamed', {
      userId: ctx.user.id,
      name: input.name,
    })
  },
})

export const huddle = base.assemble({ handlers: [handleRename] })
```

On the client, this is a plain send. There is nothing to `await`:

```typescript [client/socket.ts]
socket.send('rename', { name: 'Jordan' })
```

## The config

| Field               | Required | What it does                                                                                                                                                                                                                                                       |
| ------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `input`             | no       | A validator for the payload: a schema from any [Standard Schema](https://standardschema.dev) library, such as Valibot or Zod. LiveThing checks the payload before `run`, so a bad payload never reaches your code. If you omit it, `input` has the type `unknown`. |
| `run`               | yes      | `run(ctx, input)`. Your code. It returns `void` or `Promise<void>`. See [The return value](#the-return-value).                                                                                                                                                     |
| `allowInterleaving` | no       | Run this handler without waiting for earlier ordered work on the same connection. The default is `false`, so `on` handlers run one after another, in order, for each connection.                                                                                   |
| `rateLimit`         | no       | A rate limit for this handler only. This field exists only when the [`rateLimit()`](/server/capabilities/rate-limit) capability is listed. If you pass it without the capability, you get a compile error.                                                         |

## Validating the payload

Pass a schema to `input`, and LiveThing checks each incoming payload against it. If the check fails, `run` does **not** run. LiveThing reports a `validation-failed` error instead, and your [`base.onValidationError`](/server/lifecycle-and-intercept/hooks) hook runs, if you have one. Your `base.onError` hook also receives the error. Inside `run`, the type of `input` comes from the schema. You don't need a cast or a second check.

The examples below use a `base` whose `emits({...})` declares every event that they send.

```typescript [server/huddle.ts]
const handleSetStatus = base.on('set-status', {
  input: v.object({ status: v.picklist(['active', 'away', 'busy']) }),
  run(ctx, input) {
    // input: { status: 'active' | 'away' | 'busy' }. It is already valid.
    ctx.broadcast('status-changed', {
      userId: ctx.user.id,
      status: input.status,
    })
  },
})
```

Omit `input` to accept any payload. The payload then has the type `unknown`, so you must check it yourself before you use it:

```typescript [server/huddle.ts]
const handleClientLog = base.on('client-log', {
  run(ctx, input) {
    // input: unknown. There is no schema, so check the value yourself.
    if (typeof input !== 'string') return
    logClientEvent(ctx.user.id, input)
  },
})
```

::tip
`input` validation checks **only the payload**. The event name is handled before validation. If a client sends an event name that has no handler, LiveThing **ignores the message**. It sends no error, and the connection stays open. So you only need to validate the contents.
::

A validation failure on an `on` event still reaches the client. But the client has no pending promise for this event, so the error cannot go there. LiveThing sends a `validation-failed` error frame (a message with the event name `__error__`). No call on the client is waiting for it, so it is an **unclaimed** error, and it goes to the client's [`socket.onServerError(...)`](/client/errors/onerror-routing) listener:

```typescript [client/socket.ts]
socket.onServerError((error) => {
  // A bad payload on any `on` event arrives here.
  console.warn('unclaimed server error', error)
})
```

## The return value

`run` is fire-and-forget. LiveThing **ignores** the value that `run` returns, because an `on` handler has no way to reply. Return `void`, or make `run` `async` and return a `Promise<void>`. LiveThing waits for the promise, so it also catches an error thrown inside an `async` `run`.

```typescript [server/huddle.ts]
const handleSaveDraft = base.on('save-draft', {
  input: v.object({ roomId: v.string(), text: v.string() }),
  async run(ctx, input) {
    await ctx.kv.set(
      `draft:${ctx.user.id}:${input.roomId}`,
      input.text,
    )
    ctx.send('draft-saved', {
      roomId: input.roomId,
      savedAt: Date.now(),
    })
  },
})
```

If the client must wait for an answer from the server, use [`base.request`](/server/handlers/request) instead. A request handler returns a response, and the client can `await` it.

## Work order on one connection

By default, `on` handlers run in order for each connection. See [Per-Connection Event Queue](/server/handlers/per-connection-queue) for how the queue works, how `allowInterleaving` lets a handler skip it, and the rules for requests and streams.

## Sending and broadcasting

`run` uses `ctx` (the connection context) to send events. Two methods send events out. Both are typed from your [`emits({...})`](/server/capabilities/emits) declarations: you can only send an event that you declared, and only with the payload shape that you declared for it.

- **`ctx.send(event, payload)`** sends to the calling connection. It returns `true` when the frame was handed to the socket, and `false` when it was not: on a server with a translator, the connection is closing or the outbound translation failed (LiveThing then closes the connection), or the platform adapter refused the frame. It throws if the event is not declared or the payload is not an object. `ctx.connections.get(ref).send()` works the same way, for a connection other than the caller.
- **`ctx.broadcast(event, payload, options?)`** sends to every _other_ connection on this server instance. By default, the calling connection does not get the event. Pass `{ includeSelf: true }` to send it to the caller too.

```typescript [server/huddle.ts]
const handleSetStatus = base.on('set-status', {
  input: v.object({ status: v.picklist(['active', 'away', 'busy']) }),
  run(ctx, input) {
    const payload = { userId: ctx.user.id, status: input.status }
    ctx.send('status-changed', payload) // only the caller
    ctx.broadcast('status-changed', payload) // everyone except the caller
    ctx.broadcast('status-changed', payload, { includeSelf: true }) // everyone, including the caller
  },
})
```

If you send an event that you never declared, or a payload with the wrong shape, you get a compile error. For everything else on `ctx` (storage, connections, tags and channels), see [Context and storage](/server/context-and-storage/overview).

## Throwing a typed error

An `on` handler has no reply, but a thrown error still matters. It stops the handler, and LiveThing reports it to your [`base.onError`](/server/lifecycle-and-intercept/hooks) hook. For a clear, typed failure, throw an error made with `error()` instead of a plain `Error`. The shared error model (how to define errors, `error()`, `.matches()`, and the built-in errors) is described in [Core](/core/error-model). Declare your errors with the [`errors([...])`](/server/capabilities/errors) capability.

```typescript [server/rooms.ts]
import { error, errors, server } from '@livething/server'
import * as v from 'valibot'

const Forbidden = error('forbidden', v.object({ reason: v.string() }))

const base = server({
  capabilities: [errors([Forbidden])],
})

const handleArchiveRoom = base.on('archive-room', {
  input: v.object({ roomId: v.string() }),
  run(ctx, input) {
    if (ctx.meta.role !== 'admin') {
      throw Forbidden({ reason: 'only an admin may archive a room' })
    }
    archiveRoom(input.roomId)
  },
})
```

::note
An `on` event is fire-and-forget, so a thrown error does not reject anything on the client. There is no pending promise to reject. The error ends this run of the handler and runs your error hook. LiveThing then sends an error frame to the client. As with a validation failure, no call is waiting for it, so it goes to [`socket.onServerError(...)`](/client/errors/onerror-routing). If you want the error to reject a call that the client is waiting on, use [`base.request`](/server/handlers/request). There, a thrown error rejects the client's pending request.
::

## Per-handler rate limit

A **rate limit** sets how many messages a client may send in a period of time. When the [`rateLimit()`](/server/capabilities/rate-limit) capability is listed, you can make the limit stricter, make it looser, or turn it off for one event. Pass `rateLimit` in the config. It sets a separate limit for this handler only. Any field you leave out (`max`, `windowMs` or `per`) comes from the global rule. Pass `{ enabled: false }` to turn the limit off for this event.

```typescript [server/rooms.ts]
const handleReact = base.on('react', {
  input: v.object({ messageId: v.string(), emoji: v.string() }),
  rateLimit: { enabled: true, max: 10, windowMs: 60_000 }, // at most 10 per minute for this event
  run(ctx, input) {
    ctx.broadcast('reaction', {
      messageId: input.messageId,
      emoji: input.emoji,
      from: ctx.user.id,
    })
  },
})
```

Without the `rateLimit()` capability, the `rateLimit` field is not part of the config type, so adding it is a compile error. This stops you from setting a limit that nothing on the server would enforce.
