A **routed handler** binds your code to a client event, request, or stream. You build it with a method on `base` (the builder `define()` returns), export the value it gives back, and pass it to `base.assemble(...)`. That last call collects routed handlers into the final server an [adapter](/server/adapters/overview) runs. Scheduled task bodies register directly on `base`; see [base.scheduled](/server/handlers/scheduled).

```typescript [chat.ts]
import { define, emits, t } from '@wskit/server'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [emits({ message: t<{ text: string; from: string }>() })],
})

// 1. build a handler — it's an exportable value
const handleSend = base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.broadcast('message', { text: input.text, from: ctx.user.id })
  },
})

// 2. collect routed handlers into the server
export const handler = base.assemble({ handlers: [handleSend] })
```

## The handler methods on `base`

`base.on(...)` is always there. The rest appear on `base` only when you list their [capability](/server/capabilities/overview) in `define(...)` — for example `base.request(...)` shows up once `clientRequests()` is in `capabilities`. Listing a capability is what turns its `base` method on and pulls its engine code into your bundle.

| Method                                | Reacts to                                       | Needs the capability | Page                                                  |
| ------------------------------------- | ----------------------------------------------- | -------------------- | ----------------------------------------------------- |
| `base.on(event, config)`              | A client→server event, fire-and-forget          | — (always present)   | [base.on](/server/handlers/on)                        |
| `base.request(event, config)`         | A client→server request that awaits a reply     | `clientRequests()`   | [base.request](/server/handlers/request)              |
| `base.stream(event, config)`          | A start message, then pushes a stream of chunks | `stream()`           | [base.stream](/server/handlers/stream)                |
| `base.resumableStream(event, config)` | Same, but the stream survives a reconnect       | `resumableStream()`  | [Durable streams](/server/streams/durable-resumable)  |
| `base.recordedStream(event, config)`  | Same, but late joiners get the chunks so far    | `recordedStream()`   | [Durable streams](/server/streams/durable-recorded)   |
| `base.channel(pattern, config)`       | A room — its own `on`/`request`/`stream` block  | `channels()`         | [Channel handlers](/server/handlers/channel-handlers) |

::note
Lifecycle hooks (`base.onInit`, `base.onConnect`, `base.onDisconnect`, ...), `base.scheduled`, and the `base.intercept` / `base.onOutgoing` hooks are not routed handlers — you do not pass them to `assemble()`. They register themselves on `base` and are folded in for you. See [Lifecycle and intercept](/server/lifecycle-and-intercept/overview).
::

## The common shape

Every routed handler — `on`, `request`, `stream`, and their channel forms — takes an **event name** and a **config object**. Two fields show up across all of them:

- **`input`** — an optional schema that validates the client payload before your code runs. Pass a Validator (Valibot, Zod, and the like) to validate the wire payload and reject bad ones. Omit it and the payload is typed `unknown`.
- **`run`** — your code. For `on` and `request` it's a normal function; for the stream methods it's an async generator. It always receives `ctx` first (the [connection context](/server/context-and-storage/overview)) and the validated `input` second.

```typescript [shapes.ts]
// fire-and-forget: run returns nothing
base.on('typing', {
  input: v.object({ roomId: v.string() }),
  run(ctx, input) {
    /* ... */
  },
})

// request: run's return value is the reply
base.request('get-user', {
  input: v.object({ id: v.string() }),
  run(ctx, input) {
    return { id: input.id }
  },
})

// stream: run is an async generator, each yield is a chunk
base.stream('feed', {
  input: v.object({ count: v.number() }),
  async *run(ctx, input) {
    for (let i = 0; i < input.count; i += 1) yield { index: i }
  },
})
```

`base.scheduled(taskId, config)` is a direct registration method: it takes a **task ID** (matched to a task you declared in the `scheduled({...})` capability), and its config has only `run` — there is no `input`, because a task has a server-supplied payload, not a client one. It returns nothing and does not belong in `handlers`. See [base.scheduled](/server/handlers/scheduled).

Before choosing a handler, read [Per-Connection Event Queue](/server/handlers/per-connection-queue). It explains the per-connection work queue and why `on`, `request`, and streams have different scheduling rules.

## Routed handlers are plain values

A `base.on(...)` call does not register anything by itself. It returns a value, and nothing happens until that value reaches `assemble()`. This is why you **export** handlers and split them across files freely — they are inert until collected.

```typescript [send.ts]
export const handleSend = base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.broadcast('message', { text: input.text, from: ctx.user.id })
  },
})
```

```typescript [server.ts]
import { handleSend } from './send.ts'
import { handleGetUser } from './users.ts'

export const handler = base.assemble({ handlers: [handleSend, handleGetUser] })
```

## `base.assemble(...)`

`assemble(...)` takes your routed handlers as `{ handlers: [...] }` and produces the `ServerDefinition` your adapter mounts. The upgrade gate, lifecycle hooks, scheduled task bodies, intercept, and your listed capabilities are folded in automatically — you only pass routed **handlers**.

```typescript [server.ts]
export const handler = base.assemble({
  handlers: [
    handleSend,
    handleGetUser,
    handleLobbyMessage, // a handler value returned by lobby.on(...)
    lobby, // optional: channel configuration and lifecycle behavior only
  ],
})
```

A channel handler value activates that handler only. List every routed channel handler you want to run. Passing the channel object directly includes its configuration and lifecycle behavior, but activates no routed handlers.

A scoped plugin handler can also pass an `api` alongside `handlers` — the per-connection surface the host reaches with `ctx.plugin(id)`. See [Scoped context and API](/server/plugins/scoped-ctx).

### What `assemble()` rejects

`assemble(...)` checks your handler set and throws a build error — at boot, not on the wire — when something is wrong. Each message tells you exactly what to fix.

| Mistake                                                                          | What you get                                                                               |
| -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Two handlers of the same kind bound to one event                                 | `Duplicate <kind> handler for '<event>' passed to assemble().`                             |
| One event name claimed by two kinds, e.g. `base.on('x')` and `base.request('x')` | `Event name 'x' is bound by both a <kind> handler and a <kind> handler ...`                |
| A scheduled task declared with no `base.scheduled(...)` body                     | `No body for scheduled task '<taskId>'. Register it with base.scheduled('<taskId>', ...).` |
| A capability passed to `assemble()` instead of `define({ capabilities })`        | `A capability was passed to assemble(). ...`                                               |

::note
There is no "stream declared with no body" error. A `base.stream(...)` (or `resumableStream` / `recordedStream`) call always carries its generator, so a stream can never exist without a body.
::

An **event name is unique within one assembled server definition, across kinds.** You cannot pass both `base.on('ping')` and `base.request('ping')` to the same `assemble()` call — pick one kind per name. Inert values that are not assembled do not collide. The same name can also live independently inside a channel; channel events are scoped to that channel. See [Channel handlers](/server/handlers/channel-handlers).

## Inferring the client type

The value `assemble()` returns also carries the full typed contract. Feed it to `InferClient` and the client side gets every event, request, stream, and channel you bound — fully typed, with no second declaration to keep in sync.

```typescript [server.ts]
import type { InferClient } from '@wskit/server'

export const handler = base.assemble({ handlers: [handleSend, handleGetUser] })

export type AppClient = InferClient<typeof handler>
```
