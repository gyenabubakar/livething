A **routed handler** connects your code to one named message from the client: an event, a request or a stream. You build it with a method on `base`. The method gives back a value. You export that value and pass it to `base.assemble(...)`. `assemble` collects the routed handlers into the final **server definition**, the object that an [adapter](/server/adapters/overview) runs.

A scheduled task body is a routed handler too: [`base.scheduled(...)`](/server/handlers/scheduled) returns a value that you pass to `assemble()`.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import * as v from 'valibot'

const base = server({
  capabilities: [
    emits({
      'status-changed': t<{
        userId: string
        status: 'active' | 'away' | 'busy'
      }>(),
    }),
  ],
})

// 1. build a handler value (you can export it)
const handleSetStatus = base.on('set-status', {
  input: v.object({ status: v.picklist(['active', 'away', 'busy']) }),
  run(ctx, input) {
    ctx.broadcast('status-changed', {
      userId: ctx.user.id,
      status: input.status,
    })
  },
})

// 2. collect routed handlers into the server
export const huddle = base.assemble({ handlers: [handleSetStatus] })
```

## The handler methods on `base`

`base.on(...)` is always there. The other methods exist on `base` only when you list their [capability](/server/capabilities/overview) in `server(...)`. For example, `base.request(...)` exists only when `clientRequests()` is in `capabilities`. Listing a capability adds its method to `base` and adds the capability's code to your bundle.

| Method                               | Reacts to                                                              | Needs the capability | Page                                                   |
| ------------------------------------ | ---------------------------------------------------------------------- | -------------------- | ------------------------------------------------------ |
| `base.on(event, config)`             | A client→server event with no reply                                    | None (always there)  | [base.on](/server/handlers/on)                         |
| `base.request(event, config)`        | A client→server request that waits for a reply                         | `clientRequests()`   | [base.request](/server/handlers/request)               |
| `base.stream(event, config)`         | A start message, then sends a series of chunks                         | `stream()`           | [base.stream](/server/handlers/stream)                 |
| `base.recordedStream(event, config)` | Same, and after a reconnect the client gets the saved chunks it missed | `recordedStream()`   | [Recorded streams](/server/streams/durable-recorded)   |
| `base.binary.on(event, config)`      | A client→server binary message: JSON info and bytes, with no reply     | `binary()`           | [binary](/server/binary/events#handling-binary-events) |
| `base.channel(pattern, config)`      | A room with its own `on`, `request` and `stream`                       | `channels()`         | [Channel handlers](/server/handlers/channel-handlers)  |

With [`binary()`](/server/binary/overview) listed, `base.binary.request`, `base.binary.stream` and `base.binary.recordedStream` are the versions of `request`, `stream` and `recordedStream` that carry bytes. Each needs the capability of its JSON version too.

::note
[Lifecycle hooks](/server/lifecycle-and-intercept/overview) (`onInit`, `onConnect`, `onDisconnect`, ...) and the `intercept` and `onOutgoing` hooks are not routed handlers. They are keys of the object that you pass to `server({ ... })`, so you do not pass them to `assemble()`. `base.scheduled(...)` is different: it returns a handler, and you pass it to `assemble()` like the others.
::

## The common shape

Every routed handler (`on`, `request`, the stream methods, and their channel forms) takes an **event name** and a **config object**. Two fields appear in all of them:

- **`input`**: an optional schema. It checks the payload the client sends before your code runs, and LiveThing rejects a payload that does not match. You can use any [Standard Schema](https://standardschema.dev) library, such as Valibot or Zod. If you leave `input` out, the payload has the type `unknown`.
- **`run`**: your code. For `on` and `request` it is a normal function. For the stream methods it is an async generator. It always receives `ctx` first (the [connection context](/server/context-and-storage/overview)) and the validated `input` second.

```typescript [server/huddle-handlers.ts]
import * as v from 'valibot'
import { base } from './base'
import { loadProfile, searchMessages } from './helpers'

// event with no reply: run returns nothing
export const handleRename = base.on('rename', {
  input: v.object({ name: v.string() }),
  run(ctx, input) {
    // this version also saves the name; Huddle's own rename only broadcasts
    ctx.user.setMeta({ name: input.name })
    ctx.broadcast('user-renamed', {
      userId: ctx.user.id,
      name: input.name,
    })
  },
})

// request: run's return value is the reply
export const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  run(ctx, input) {
    return loadProfile(input.userId) // your own lookup, returns the user's profile
  },
})

// stream: run is an async generator, each yield is a chunk
export const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  async *run(ctx, input) {
    for await (const hit of searchMessages(input.query)) {
      yield { hit }
    }
  },
})
```

[`base.scheduled(taskId, config)`](/server/handlers/scheduled) takes a **task ID**, which must match a task you declared in the `scheduled({...})` capability. Its config has only `run`. There is no `input`, because the server supplies a task's payload, not a client. It returns a handler value, and you pass it in `handlers`.

Before you choose a handler kind, read [Per-Connection Event Queue](/server/handlers/per-connection-queue). It explains the work queue that each connection has, and why `on`, `request` and streams follow different rules for when they run.

## Routed handlers are plain values

A `base.on(...)` call does not register anything by itself. It returns a value, and that value does nothing until you pass it to `assemble()`. This is why you can **export** handlers and split them across many files. A handler value has no effect until `assemble()` collects it.

Here is Huddle split over three files:

::code-group

```typescript [server/profile-handlers.ts]
import * as v from 'valibot'
import { base } from './base'
import { loadProfile } from './helpers'

export const handleSetStatus = base.on('set-status', {
  input: v.object({ status: v.picklist(['active', 'away', 'busy']) }),
  run(ctx, input) {
    ctx.broadcast('status-changed', {
      userId: ctx.user.id,
      status: input.status,
    })
  },
})

// get-profile is a plain top-level request, kept here next to set-status.
export const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  run(ctx, input) {
    return loadProfile(input.userId)
  },
})
```

```typescript [server/base.ts]
import { emits, server, t } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'

export const base = server({
  capabilities: [
    emits({
      'status-changed': t<{
        userId: string
        status: 'active' | 'away' | 'busy'
      }>(),
    }),
    clientRequests(),
  ],
})
```

```typescript [server/huddle-definition.ts]
import { base } from './base'
import { handleGetProfile, handleSetStatus } from './profile-handlers'

export const huddle = base.assemble({
  handlers: [handleSetStatus, handleGetProfile],
})
```

::

## `base.assemble(...)`

`assemble(...)` takes your routed handlers as `{ handlers: [...] }` and returns the `ServerDefinition` that your adapter runs. It adds the `authenticate` function, the hooks and your listed capabilities automatically. You pass only **handlers** (and channels).

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'
import { loadProfile } from './helpers'

const base = server({
  capabilities: [channels(), clientRequests()],
})

const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  run: (ctx, input) => loadProfile(input.userId),
})

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ typing: t<{ from: string }>() })],
})

const handleStartTyping = rooms.on('start-typing', {
  input: v.object({}),
  run(ctx) {
    ctx.channel.broadcast('typing', { from: ctx.user.id })
  },
})

export const huddle = base.assemble({
  handlers: [
    handleGetProfile,
    handleStartTyping, // a handler value returned by rooms.on(...)
    rooms, // optional: channel configuration and lifecycle behavior only
  ],
})
```

A channel handler value turns on that one handler only. List every routed channel handler you want to run. If you pass the channel object itself, `assemble()` turns on the channel's configuration and hooks, but none of its routed handlers. That is what Huddle does with `announcements`: only the server sends to it, so it has no handlers.

### Grouping handlers

A larger app can keep the handlers of one feature in a file, export them as a list, and spread the lists in `assemble()`. Write the list with `as const`:

::code-group

```typescript [server/room-handlers.ts]
import * as v from 'valibot'
import { rooms } from './base'

export const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})

export const handleReact = rooms.on('react', {
  input: v.object({ messageId: v.string(), emoji: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('reaction', {
      messageId: input.messageId,
      emoji: input.emoji,
      from: ctx.user.id,
    })
  },
})

export const roomHandlers = [handleSendMessage, handleReact] as const
```

```typescript [server/dm-handlers.ts]
import * as v from 'valibot'
import { dms } from './base'

export const handleSendDm = dms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})

export const dmHandlers = [handleSendDm] as const
```

```typescript [server/huddle-definition.ts]
import { base } from './base'
import { dmHandlers } from './dm-handlers'
import { buildDigest } from './helpers'
import { roomHandlers } from './room-handlers'

const handleSendDigest = base.scheduled('send-digest', {
  run(ctx, data) {
    buildDigest(data.userId)
  },
})

export const huddle = base.assemble({
  handlers: [handleSendDigest, ...roomHandlers, ...dmHandlers],
})
```

::

`as const` is what lets TypeScript know how many handlers the list has and which ones. With it, a duplicate event is a compile error. A plain array still works, but then LiveThing checks it only when `assemble()` runs.

::note
Very large lists slow down the compile check. In one test, a list of 500 handlers took about 15 seconds to typecheck, and a list of 600 failed with TS2589 ("Type instantiation is excessively deep"). If you reach that size, pass a plain array. It compiled 600 handlers without the error, and `assemble()` still checks it for duplicates when it runs.
::

A scoped plugin (a server built with `server({ scope: 'plugin' })`) can also pass `api` next to `handlers`. `api` is a function that builds the plugin's [per-connection API](/server/plugins/scoped-ctx). The host server reads it with `ctx.plugin(id)`.

### What `assemble()` rejects

`assemble(...)` checks your handlers. When the list has a known length (an array literal, or a list written with `as const`), TypeScript reports a duplicate event or a missing scheduled task as a compile error. Otherwise, `assemble()` throws when it runs, as your server code loads, not later when a client sends a message. Each error message tells you what to fix. Every thrown message starts with `[livething]`.

| Mistake                                                                          | What you get                                                                                    |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Two handlers of the same kind bound to one event                                 | `Duplicate <kind> handler for '<event>' passed to assemble().`                                  |
| One event name claimed by two kinds, e.g. `base.on('x')` and `base.request('x')` | `Event name 'x' is bound by both a <kind> handler and a <kind> handler ...`                     |
| Two handlers on one channel using the same event name, of any kind               | `Duplicate event '<event>' on channel '<channel>' passed to assemble(). ...`                    |
| A scheduled task declared, with no `base.scheduled(...)` handler passed          | `Scheduled task '<taskId>' has no handler. Pass base.scheduled('<taskId>', ...) to assemble().` |
| A `base.scheduled(...)` handler for a task that is not declared                  | `base.scheduled('<taskId>') has no matching declaration. ...`                                   |
| A capability passed to `assemble()` instead of `server({ capabilities })`        | `A capability was passed to assemble(). ...`                                                    |

::note
There is no "stream declared with no body" error. A `base.stream(...)` or `base.recordedStream(...)` call always includes its generator, so a stream always has a body.
::

**An event name must be unique within one scope, across all handler kinds.** The top level is one scope, and each [channel](/server/handlers/channel-handlers) is another. You cannot pass both `base.on('ping')` and `base.request('ping')` to the same `assemble()` call. Choose one kind for each name. Handler values that you do not pass to `assemble()` do not cause a conflict. A channel can use the same name as a top-level handler, and two channels can use the same name, because channel events belong to that channel only.

## Inferring the client type

The value that `assemble()` returns also carries the full typed **contract**. Pass its type to `InferClient`, and the client gets a type for every event, request, stream and channel in the definition. You do not write a second copy of these types for the client.

```typescript [server/huddle-definition.ts]
import type { InferClient } from '@livething/server'

// huddle is the value that base.assemble(...) returned
export type HuddleSocket = InferClient<typeof huddle>
```
