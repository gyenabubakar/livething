`base.stream(event, config)` defines a stream handler. The client sends a start message. Your `run` function then produces the data. `run` is an **async generator**. Each value it yields is one **chunk**, and LiveThing sends each chunk to the client as soon as it is yielded. When the generator returns, the stream ends.

`base.stream` exists on `base` only when the [`stream()`](/server/capabilities/streams) capability is listed. If you call it without that capability, `base.stream(...)` throws this error when it runs: `[livething] base.stream() needs the stream() capability. Add stream() to capabilities.`

```typescript [server/search-definition.ts]
import { server } from '@livething/server'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'
import { searchMessages } from './helpers'

const base = server({
  capabilities: [stream()],
})

export const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  async *run(_ctx, input) {
    for await (const hit of searchMessages(input.query)) {
      yield { hit } // each yield is a chunk on the client
    }
  },
})

export const huddle = base.assemble({
  handlers: [handleSearchMessages],
})
```

On the client, the stream is an async iterable:

```typescript [client/search.ts]
const hits = await socket.stream('search-messages', {
  query: 'launch plan',
})
for await (const chunk of hits) appendSearchHit(chunk.hit)
// the loop exits when the generator returns
```

This page covers how to write the generator for `base.stream`. There are other [kinds of streams](/server/streams/overview): durable streams ([`recordedStream`](/server/streams/durable-recorded)), which can continue after the client disconnects, and [broadcast streams](/server/streams/broadcast), which send the same chunks to many connections. You write their generators the same way.

## The config

::field-group
::field{name="input"}
A schema (for example a Valibot schema) for the start payload. LiveThing validates the payload before `run` starts. If the payload is not valid, the start is rejected.
::
::field{name="nudges"}
[Messages the client can send](#nudges) into the running generator to change what it does.
::
::field{name="broadcast"}
[Send the stream](/server/streams/broadcast) to every connection (or every channel member) instead of only the one that started it. Default `false`.
::
::field{name="allowConcurrent"}
Allow more than one stream of the same event at the same time on one connection. Default `false`: a second start while one is running is refused.
::
::field{name="run" required}
The async generator. Each `yield` sends a chunk. `return` ends the stream.
::
::

## Writing the generator

`run` is an `async *` generator. Each value you `yield` is sent as a chunk, and the client's loop receives the chunks in order. The stream ends cleanly when the generator finishes. This happens when it calls `return`, reaches the end of its body, or yields nothing at all. The client's `for await` loop then exits.

```typescript [server/search.ts]
import * as v from 'valibot'
import { base } from './base'
import { searchMessages } from './huddle-data'

// yields one chunk per hit, then ends
const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  async *run(_ctx, input) {
    for await (const hit of searchMessages(input.query)) {
      yield { hit }
    }
  },
})

// yields nothing, so the stream ends at once
const handleEmptySearch = base.stream('search-messages-empty', {
  input: v.object({}),
  async *run() {},
})
```

### Typing the chunk

The chunk type comes from what `run` yields. The client contract lists it as `chunk`. To fix the type yourself, write the generator's return type as `AsyncGenerator<T>`. Then a `yield` of any other shape is a type error. This is useful when the inferred type is too narrow. Here `step` comes from an `as const` list, so without the return type the client would see `'search' | 'read' | 'write'`, not `string`:

```typescript [server/scout.ts]
import * as v from 'valibot'
import { base } from './base'
import { runScoutStep } from './huddle-data'

const handleRunTask = base.stream('run-task', {
  input: v.object({ roomId: v.string(), goal: v.string() }),
  async *run(
    _ctx,
    input,
  ): AsyncGenerator<{ step: string; detail: string }> {
    for (const step of ['search', 'read', 'write'] as const) {
      yield { step, detail: await runScoutStep(step, input.goal) }
    }
  },
})
```

A chunk is JSON. For chunks of bytes, such as the pieces of a file, use [`base.binary.stream`](/server/binary/streams): its generator yields `{ info, bytes }`, and the info type comes from what it yields.

## The stream handle

Inside the generator, `ctx.stream` holds the controls for this run of the stream.

### The abort signal

`ctx.stream.signal` is an `AbortSignal`. It fires when the stream is **cancelled, the client disconnects, or the server shuts down**. Pass it into any slow awaited work, such as a `fetch`. That work then stops as soon as the stream is no longer needed.

```typescript [server/scout.ts]
import * as v from 'valibot'
import { base } from './base'
import { runScoutStep } from './huddle-data'

const handleRunTask = base.stream('run-task', {
  input: v.object({ roomId: v.string(), goal: v.string() }),
  async *run(
    ctx,
    input,
  ): AsyncGenerator<{ step: string; detail: string }> {
    for (const step of ['search', 'read', 'write'] as const) {
      const detail = await runScoutStep(step, input.goal, {
        signal: ctx.stream.signal,
      })
      yield { step, detail }
    }
  },
})
```

When a stream is cancelled, LiveThing calls the generator's `return()` method. This runs any `finally` block in the generator, so `try/finally` is the place for cleanup code. The example below uses a flag to find out if the stream was cancelled before it finished:

```typescript [server/admin.ts]
import * as v from 'valibot'
import { auditLogEntries } from './audit-log'
import { base } from './base'

const handleTailAuditLog = base.stream('tail-audit-log', {
  input: v.object({}),
  async *run(ctx) {
    let completed = false
    try {
      for await (const entry of auditLogEntries(ctx.stream.signal)) {
        yield { line: entry.line }
      }

      completed = true
    } finally {
      if (!completed) {
        console.log('tail-audit-log stopped before it finished')
      } // the stream was cancelled
    }
  },
})
```

### Backpressure with `drain()`

**Backpressure** means slowing down the sender when the receiver cannot keep up. Data that is waiting to be sent to a connection sits in its outbound buffer. `ctx.stream.drain()` pauses the generator until that buffer holds less than 256 KB, then lets it continue. This stops a fast generator from filling server memory with chunks faster than the client reads them. Call it after each `yield` in a fast loop.

```typescript [server/search.ts]
import * as v from 'valibot'
import { base } from './base'
import { searchMessages } from './huddle-data'

const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  async *run(ctx, input) {
    for await (const hit of searchMessages(input.query)) {
      yield { hit }

      await ctx.stream.drain() // wait until the buffer is below 256 KB
    }
  },
})
```

::note
Cloudflare does not report how full the socket buffer is. On Cloudflare, `drain()` resolves at once and does nothing. You can still call `drain()` in your loop. It pauses where the runtime reports the buffer size and has no effect on Cloudflare.
::

## Nudges

A **nudge** is a message the client sends into a stream that is already running, for example "cancel", "add context" or "speed up". The `nudges` map declares them. Each entry is a schema for the nudge payload, or `null` for a nudge with no payload. After a `yield`, call `ctx.stream.nudges(yieldedValue)` to read the nudges that arrived since the last yield.

```typescript [server/scout.ts]
import * as v from 'valibot'
import { base } from './base'
import { runScoutStep } from './huddle-data'

const handleRunTask = base.stream('run-task', {
  input: v.object({ roomId: v.string(), goal: v.string() }),
  nudges: {
    'add-context': v.object({ text: v.string() }), // nudge with a payload
  },
  async *run(
    ctx,
    input,
  ): AsyncGenerator<{ step: string; detail: string }> {
    let context = ''
    for (const step of ['search', 'read', 'write'] as const) {
      const detail = await runScoutStep(step, input.goal, { context })
      const recent = ctx.stream.nudges(yield { step, detail })
      const added = recent.find((n) => n.event === 'add-context')
      if (added) context = added.payload.text // read between steps, used in the next one
    }
  },
})
```

`ctx.stream.nudges(...)` exists only when the stream declares `nudges`. Each message it returns has the type `{ event, payload }`, and checking `event` narrows `payload` to that nudge's type. For the client side of nudges, see [Streams](/server/streams/overview).

Nudges that are not read yet wait in a buffer. The buffer holds up to **256** nudges per stream. If the client sends nudges faster than the generator reads them and the buffer is full, the server rejects each new nudge with a `nudge-overflow` error. This error is **non-terminal**: only that nudge fails, the stream keeps running, and you read the nudges already in the buffer as normal. Read nudges after each `yield` so the buffer does not fill.

Stream starts do not wait in the normal [per-connection queue](/server/handlers/per-connection-queue), which is different from `on` and `request`. `allowConcurrent` controls overlapping runs of the same stream event.

## Throwing from a stream

If the generator throws, the stream ends with an **error**, and the client's `for await` loop throws. Throw a typed [`error()`](/core/error-model) that you listed in `errors([...])`, so the client can check which error it got. Any other error reaches the client as `internal-error`.

Huddle's [`errors([NotFound, Forbidden, RoomFull])`](/server/capabilities/errors#declaring-typed-errors) already lists [`NotFound`](/core/isomorphic-code#shared-error-definitions). This version of `run-task` throws it when the room does not exist:

```typescript [server/scout.ts]
import * as v from 'valibot'
import { NotFound } from '../shared/errors'
import { base } from './base'
import { roomExists, runScoutStep } from './helpers'

const handleRunTask = base.stream('run-task', {
  input: v.object({ roomId: v.string(), goal: v.string() }),
  async *run(
    _ctx,
    input,
  ): AsyncGenerator<{ step: string; detail: string }> {
    if (!roomExists(input.roomId)) {
      throw NotFound({ id: input.roomId })
    }

    // the client's loop throws
    for (const step of ['search', 'read', 'write'] as const) {
      yield { step, detail: await runScoutStep(step, input.goal) }
    }
  },
})
```

## One stream per event at a time

By default a connection runs **one** stream per event name. If a start message arrives for an event that is already streaming on that connection, it is refused with a `stream-already-active` error. Set `allowConcurrent: true` to allow more than one run of the same event at the same time.

```typescript [server/search.ts]
import * as v from 'valibot'
import { base } from './base'
import { searchMessages } from './huddle-data'

const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  allowConcurrent: true, // a new search can start before the old one finishes
  async *run(_ctx, input) {
    for await (const hit of searchMessages(input.query)) yield { hit }
  },
})
```
