`base.stream(event, config)` handles a stream: the client sends a start message, your `run` — an **async generator** — yields chunks, and each yield is sent to the client one at a time. When the generator returns, the stream ends.

`base.stream` appears on `base` only when the [`stream()`](/server/capabilities/streams) capability is listed. Calling it without that capability throws at boot: `[wskit] base.stream() needs the stream() capability. Add stream() to capabilities.`

```typescript [feed.ts]
import { define, t } from '@wskit/server'
import { stream } from '@wskit/server/streams'
import * as v from 'valibot'

const base = define({
  capabilities: [stream()],
})

export const handleTokens = base.stream('start-tokens', {
  input: v.object({ count: v.number() }),
  chunk: t<{ index: number }>(),
  async *run(ctx, input) {
    for (let i = 0; i < input.count; i += 1) {
      yield { index: i } // each yield is a chunk on the client
    }
  },
})

export const handler = base.assemble({
  handlers: [handleTokens],
})
```

On the client this is an async iterable:

```typescript [app.ts]
const tokens = await socket.stream('start-tokens', { count: 5 })
for await (const chunk of tokens) render(chunk.index)
// loop exits when the generator returns
```

This page covers `base.stream` as a **handler method** — writing the generator. Durable kinds ([`resumableStream`](/server/streams/durable-resumable), [`recordedStream`](/server/streams/durable-recorded)) and [broadcast streams](/server/streams/broadcast) are built the same way but configured for survival and fan-out; see [Streams](/server/streams/overview) for those.

## The config

| Field             | Required | What it does                                                                                                                                    |
| ----------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `input`           | no       | A Validator for the start payload. Validated before `run`; a bad payload rejects the start.                                                     |
| `chunk`           | no       | An explicit chunk type marker, `t<T>()`. Otherwise the chunk type is inferred from what `run` yields.                                           |
| `nudges`          | no       | Client→server steering messages delivered into the running generator — see [Nudges](#nudges).                                                   |
| `broadcast`       | no       | Fan the stream out to every connection (or channel member) instead of one. Default `false`. See [Broadcast streams](/server/streams/broadcast). |
| `allowConcurrent` | no       | Permit overlapping streams of the same event on one connection. Default `false` — a second start while one runs is refused.                     |
| `highWaterMark`   | no       | Outbound backpressure limit in bytes for `ctx.stream.drain()`. Default `256 * 1024` (256 KB).                                                   |
| `run`             | yes      | The async generator. Each `yield` is a chunk; `return` ends the stream.                                                                         |

## Writing the generator

`run` is an `async *` generator. The value you `yield` is sent as a chunk; the loop on the client receives them in order. When the generator finishes — `return`, falling off the end, or yielding nothing at all — the stream ends cleanly and the client's `for await` loop exits.

```typescript [handlers.ts]
// yields five chunks, then ends
const handleTokens = base.stream('start-tokens', {
  input: v.object({ count: v.number() }),
  chunk: t<{ index: number }>(),
  async *run(_ctx, input) {
    for (let i = 0; i < input.count; i += 1) {
      yield { index: i }
      await new Promise((r) => setTimeout(r, 200)) // pace the chunks
    }
  },
})

// yields nothing — the stream ends immediately
const handleEmpty = base.stream('start-empty', {
  input: v.object({}),
  async *run() {},
})
```

### Typing the chunk

By default the chunk type is **inferred** from what you yield. Pass `chunk: t<T>()` to fix it explicitly — handy when the body yields several shapes and you want one declared type, or when you want the contract type to read clearly:

```typescript [handlers.ts]
const Token = t<{ index: number }>()

const handleTokens = base.stream('start-tokens', {
  input: v.object({ count: v.number() }),
  chunk: Token, // every yield must be { index: number }
  async *run(_ctx, input) {
    for (let i = 0; i < input.count; i += 1) yield { index: i }
  },
})
```

## The stream handle

Inside the generator, `ctx.stream` carries the controls for this run.

### The abort signal

`ctx.stream.signal` is an `AbortSignal` that fires when the stream is **cancelled, the client disconnects, or the server shuts down**. Pass it into any slow awaited work so that work stops the instant the stream is no longer wanted.

```typescript [handlers.ts]
const handleProxy = base.stream('proxy', {
  input: v.object({ url: v.string() }),
  async *run(ctx, input) {
    const res = await fetch(input.url, {
      signal: ctx.stream.signal,
    })
    const reader = res.body!.getReader()
    while (true) {
      const { done, value } = await reader.read()
      if (done) return
      yield { bytes: value.length }
    }
  },
})
```

When a stream is cancelled, the generator's `return()` runs — so a `try/finally` is your cleanup hook. This is how you observe a cancel and react:

```typescript [handlers.ts]
const handleObserve = base.stream('watch', {
  input: v.object({}),
  async *run(ctx) {
    let completed = false
    try {
      for (let i = 0; i < 20; i += 1) {
        yield { index: i }
        await new Promise((r) => setTimeout(r, 50))
      }
      completed = true
    } finally {
      if (!completed) ctx.send('cancel-observed', { cancelled: true }) // we were cancelled
    }
  },
})
```

### Backpressure with `drain()`

`ctx.stream.drain()` pauses the generator until the outbound buffer is below `highWaterMark`, then resumes — so a fast producer doesn't pile chunks up in memory faster than the client reads them. Call it between yields on a hot loop.

```typescript [handlers.ts]
const handleFirehose = base.stream('firehose', {
  input: v.object({}),
  highWaterMark: 128 * 1024, // pause when more than 128 KB is buffered
  async *run(ctx) {
    for (const row of rows()) {
      yield row
      await ctx.stream.drain() // wait until the client has caught up
    }
  },
})
```

::note
On Cloudflare, which does not expose how full the socket buffer is, `drain()` resolves immediately — it's a safe no-op there. Write your loop with `drain()` anyway and it does the right thing on every runtime.
::

## Nudges

A `nudges` map declares client→server steering messages that arrive _into_ the running generator — a "cancel", an "add context", a "speed up". Each entry is a schema (or `null` for a no-payload nudge). After a `yield`, read what arrived since the last yield with `ctx.stream.nudges(yieldedValue)`.

```typescript [handlers.ts]
const handleFeed = base.stream('feed', {
  input: v.object({ count: v.number() }),
  chunk: t<{ index: number }>(),
  nudges: {
    cancel: null, // no-payload nudge
    'add-context': v.object({ text: v.string() }), // nudge with a payload
  },
  async *run(ctx, input) {
    for (let i = 0; i < input.count; i += 1) {
      const recent = ctx.stream.nudges(yield { index: i })
      if (recent.some((n) => n.event === 'cancel')) return // client asked to stop
      const context = recent.find((n) => n.event === 'add-context')
      if (context) applyContext(context.payload.text) // payload is typed { text: string }
    }
  },
})
```

`ctx.stream.nudges(...)` is present only when the stream declares `nudges`. The messages it returns are typed `{ event, payload }`, narrowed by the event name. For the full nudge round-trip and the client side, see [Streams](/server/streams/overview).

The inbound nudge buffer holds up to **256** unread nudges per stream. If a client sends nudges faster than the generator drains them and the buffer fills, the server sends a **non-terminal** `nudge-overflow` error to that client — the stream keeps running and you keep reading nudges as normal. Reading after each `yield` keeps the buffer from filling.

Stream starts skip the ordinary per-connection work queue. See [Per-Connection Event Queue](/server/handlers/per-connection-queue) for how this differs from `on` and `request`, and how `allowConcurrent` controls overlapping runs of the same stream event.

## Throwing from a stream

A throw inside the generator ends the stream as an **error**: the client's `for await` loop throws. Throw a typed [`error()`](/core/error-model) so the client can narrow it; a bare `throw` surfaces as a generic stream error.

```typescript [handlers.ts]
import { define, error, errors, t } from '@wskit/server'
import { stream } from '@wskit/server/streams'
import * as v from 'valibot'

const NotFound = error('not-found', v.object({ id: v.string() }))

const base = define({
  capabilities: [stream(), errors([NotFound])],
})

const handleStream = base.stream('start-model', {
  input: v.object({ id: v.string() }),
  chunk: t<{ token: string }>(),
  async *run(_ctx, input) {
    if (!modelExists(input.id)) throw NotFound({ id: input.id }) // loop throws on the client
    for (const token of run(input.id)) yield { token }
  },
})
```

## One stream per event at a time

By default a connection runs **one** stream per event name. A start message for an event that's already streaming on that connection is refused with a `stream-already-active` error. Set `allowConcurrent: true` to let overlapping runs of the same event coexist.

```typescript [handlers.ts]
const handleSearch = base.stream('search', {
  input: v.object({ query: v.string() }),
  allowConcurrent: true, // a new search can start before the old one finishes
  async *run(_ctx, input) {
    for await (const hit of search(input.query)) yield hit
  },
})
```
