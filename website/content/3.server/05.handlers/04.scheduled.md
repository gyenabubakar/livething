`base.scheduled(taskId, config)` registers the **body** of a scheduled task. The body is the code that runs later, on a timer, with no client connected. It is keyed by a **task ID**, not by an event name. That ID must match a task you declared in the [`scheduled({ ... })`](/server/capabilities/scheduled) capability.

`base.scheduled` exists on `base` only when `scheduled({...})` is listed in `capabilities`.

```typescript [cleanup.ts]
import { server } from '@livething/server'
import { scheduled } from '@livething/server/scheduled'

const base = server({
  capabilities: [
    scheduled({ cleanup: null }), // declare the task
  ],
})

base.scheduled('cleanup', {
  run(ctx) {
    ctx.sql.exec(
      'DELETE FROM sessions WHERE expires_at < ?',
      Date.now(),
    )
  },
})

export const definition = base.assemble({ handlers: [] })
```

A task has two parts:

- the **declaration** in the capability: its ID, payload type, interval and retry policy,
- the **body** you register here.

`base.scheduled(...)` returns nothing. LiveThing adds the body to the server when you call `assemble()`. A declared task with no body is a build error, and so is a body with no declaration. See [Declaration and body must match](#declaration-and-body-must-match).

## The config

The config has one field: `run`. There is no `input` field. A task is started by the server (with `ctx.schedule(...)`), not by a client, so no payload arrives over the network that needs checking.

| Field | Required | What it does                                                                                                                   |
| ----- | -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `run` | yes      | `run(ctx)` for a task with no payload, or `run(ctx, data)` for a task declared with `data`. Returns `void` or `Promise<void>`. |

## Firing a task

To queue a run, call `ctx.schedule(taskId, { time, data? })` from a handler that runs for a connection, such as a `base.on` handler. `time` is a Unix timestamp in milliseconds: the number of milliseconds since 1 January 1970 (UTC), the same kind of number `Date.now()` returns. The body runs at that time. No caller waits for it.

```typescript [handlers.ts]
import * as v from 'valibot'

const handleScheduleCleanup = base.on('schedule-cleanup', {
  input: v.object({ delayMs: v.number() }),
  run(ctx, input) {
    ctx.schedule('cleanup', { time: Date.now() + input.delayMs })
  },
})
```

`ctx.schedule(...)` checks its arguments **synchronously** (right away, before it returns). On a mistake it throws inside the handler that called it. These calls throw:

- a task ID that is not declared,
- a `time` that is not a positive whole number (`NaN`, `Infinity`, `0`, negative numbers and fractions all throw),
- `data` passed to a task that declares no payload,
- `data` that fails the task's declared schema.

Wrap the call in `try`/`catch` if you want to handle the error yourself. If you don't catch it, the error passes up to the handler.

To cancel runs that are still waiting, call `ctx.cancelScheduled(taskId)`. You can pass a data filter as the second argument, for example `ctx.cancelScheduled('report', { userId })`. With a filter, LiveThing cancels only the runs whose payload has the same value for every key in the filter. A filtered cancel never stops a recurring task, because a recurring task has no payload. Call `ctx.cancelScheduled(taskId)` with no filter to stop it. A recurring task stopped this way stays stopped, even after a restart. Call `ctx.schedule(taskId, { time })` to start it again: the first run happens at `time`, then it goes back to running every `every` milliseconds. The `scheduled({...})` capability adds both `schedule` and `cancelScheduled` to `ctx`. See [Context and storage](/server/context-and-storage/overview).

## The task context

A scheduled `run` gets a **task context**, not a connection context. A timer has no socket behind it, so the task context has server-wide tools and no per-connection ones:

| On `ctx`                                         | What it does                                                                                                                                                                                    |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ctx.sql` / `ctx.kv`                             | Storage: query, migrate, read and write.                                                                                                                                                        |
| `ctx.broadcast(event, payload)`                  | Sends an event to **every** live connection. It has no `includeSelf` option, because there is no caller to leave out.                                                                           |
| `ctx.connections.get(ref)`                       | A handle for one connection, found by its `ConnectionRef`. Its `send(event, payload)` sends to only that socket. It returns `true` when the event was sent and `false` when the socket is gone. |
| `ctx.connections.all()`                          | A snapshot (a copy taken at one moment) of every live connection.                                                                                                                               |
| `ctx.users.get(id)`                              | A handle for one user, by user ID. It reaches every socket that user has open. See [Users](/server/context-and-storage/users).                                                                  |
| `ctx.connectionCount`                            | How many connections are open right now.                                                                                                                                                        |
| `ctx.schedule(...)` / `ctx.cancelScheduled(...)` | Queue or cancel another task run.                                                                                                                                                               |
| `ctx.log`                                        | The structured logger.                                                                                                                                                                          |
| `ctx.platform`                                   | The raw platform object (for example the Durable Object state on Cloudflare).                                                                                                                   |

::note
There is no `ctx.send` here. `ctx.send` sends to the calling connection, and a task has no calling connection. To reach connections from a task, broadcast to all of them, or send to one with `ctx.connections.get(ref).send(...)`.
::

A task that broadcasts to everyone:

```typescript [handlers.ts]
base.scheduled('cleanup', {
  run(ctx) {
    ctx.broadcast('cleanup-done', { at: Date.now() })
  },
})
```

A task that sends to one connection. The handler that queues the task puts its own `ctx.connection` (a `ConnectionRef`, the address of that socket) into the task's typed `data`. The body uses that ref later:

```typescript [reminders.ts]
import { server, t } from '@livething/server'
import { scheduled } from '@livething/server/scheduled'
import * as v from 'valibot'
import type { ConnectionRef } from '@livething/server'

const base = server({
  capabilities: [
    scheduled({
      'notify-user': {
        data: t<{ connection: ConnectionRef; text: string }>(),
      },
    }),
  ],
})

base.scheduled('notify-user', {
  run(ctx, data) {
    ctx.connections
      .get(data.connection)
      .send('you-have-mail', { text: data.text })
  },
})

const handleRemindMe = base.on('remind-me', {
  input: v.object({ text: v.string(), delayMs: v.number() }),
  run(ctx, input) {
    ctx.schedule('notify-user', {
      time: Date.now() + input.delayMs,
      data: { connection: ctx.connection, text: input.text },
    })
  },
})
```

If that socket closed before the task runs, `send` returns `false` and nothing is sent. A new socket gets a new connection ID, so the old ref does not reach a reconnected client. To reach the person on any socket they have open, store their user ID instead and use `ctx.users.get(id)`.

## Tasks with a payload

Declare `data` on the task, and your `run` gets a typed second argument. The payload comes from the `ctx.schedule(taskId, { time, data })` call that queued the run, so your own server code supplies it. How you declare `data` decides whether LiveThing checks it at runtime:

- A `t<T>()` marker gives the type only. There is no runtime check.
- A Standard Schema validator (for example a valibot schema) is **checked when you call `ctx.schedule()`**. A payload that fails the check throws there, and the run is not queued.

```typescript [report.ts]
const base = server({
  capabilities: [
    scheduled({
      report: { data: t<{ userId: string }>() },
    }),
  ],
})

base.scheduled('report', {
  run(ctx, data) {
    buildReport(data.userId) // data: { userId: string }
  },
})
```

Queue it with the matching `data`:

```typescript [handlers.ts]
ctx.schedule('report', {
  time: Date.now() + 60_000,
  data: { userId: ctx.user.id },
})
```

## Recurring and retrying tasks

You set how a task behaves on its **declaration** in the [`scheduled({...})`](/server/capabilities/scheduled) capability, not here. That includes `every` (the interval for a recurring task), `retry` (the retry policy) and whether it carries `data`. The body looks the same in every case. A recurring task runs its body again and again. A task with retries runs its body again after it fails.

```typescript [tasks.ts]
const base = server({
  capabilities: [
    scheduled({
      heartbeat: { every: 30_000 }, // recurs every 30s
      sync: { retry: [1000, 5000, 15000] }, // retries with this backoff
    }),
  ],
})

base.scheduled('heartbeat', {
  run(ctx) {
    ctx.broadcast('tick', { at: Date.now() })
  },
})

base.scheduled('sync', {
  run() {
    if (!doSync()) throw new Error('sync failed') // a throw triggers the declared retry
  },
})
```

A recurring task cannot also carry a `data` payload, because no caller exists to supply one.

A task that leaves out `retry` uses the default policy, the same as `retry: true`. The default is 3 retries with a backoff (the wait before each retry) of `[1000, 5000, 25000]` ms. When a run has no retries left, it moves to the **dead-letter queue**. This is a durable SQL table named `__livething_scheduled_dlq` that keeps a record of runs that failed for good. You can read it with `ctx.sql`. [The `scheduled()` capability](/server/capabilities/scheduled) page lists every declaration option and explains the dead-letter queue in full.

A run can happen more than once: after a retry, or again after the server crashed while the body was running. So **task bodies must be idempotent**. An idempotent body gives the same result when it runs twice as when it runs once. See [At-least-once delivery](/server/capabilities/scheduled#at-least-once-delivery) for what to guard against.

## Declaration and body must match

Every declared task needs exactly one body, and every body needs a matching declaration. `assemble()` checks all of them:

| Mistake                                                                  | Error                                                                                                      |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| A task declared in `scheduled({...})` with no `base.scheduled(...)` body | `No body for scheduled task '<taskId>'. Register it with base.scheduled('<taskId>', ...).`                 |
| A `base.scheduled(...)` body whose ID isn't declared                     | `base.scheduled('<taskId>') has no matching declaration. Declare it in the scheduled({ ... }) capability.` |

Registering a second body for the same task ID throws right away, the same as registering a lifecycle hook twice.

A task ID that is not declared is also a compile error. The `taskId` parameter only accepts the IDs you declared, so TypeScript catches a typo before your code reaches `assemble()`.
