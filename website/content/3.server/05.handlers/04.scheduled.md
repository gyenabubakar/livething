`base.scheduled(taskId, config)` creates the **handler** of a scheduled task. The handler holds the code that runs later, on a timer, with no client connected. It is keyed by a **task ID**, not by an event name. That ID must match a task you declared in the [`scheduled({ ... })`](/server/capabilities/scheduled) capability.

`base.scheduled` exists on `base` only when `scheduled({...})` is listed in `capabilities`.

```typescript [server/jobs.ts]
import { server } from '@livething/server'
import { scheduled } from '@livething/server/scheduled'

const base = server({
  capabilities: [
    scheduled({ 'expire-invites': { every: 3_600_000 } }), // declare the task
  ],
})

const handleExpireInvites = base.scheduled('expire-invites', {
  run(ctx) {
    ctx.sql.exec(
      'DELETE FROM invites WHERE expires_at < ?',
      Date.now(),
    )
  },
})

export const huddle = base.assemble({
  handlers: [handleExpireInvites],
})
```

A task has two parts:

- the **declaration** in the capability: its ID, payload type, interval and retry policy,
- the **handler** you create here.

`base.scheduled(...)` returns a handler value, the same as `base.on(...)`. It does nothing until you pass it to `assemble()`. A declared task with no handler passed [is an error](#declaration-and-handler-must-match), and so is a handler with no declaration.

## The config

The config has one field: `run`. There is no `input` field. A task is started by the server (with `ctx.schedule(...)`), not by a client, so no payload arrives over the network that needs checking.

| Field | Required | What it does                                                                                                                   |
| ----- | -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `run` | yes      | `run(ctx)` for a task with no payload, or `run(ctx, data)` for a task declared with `data`. Returns `void` or `Promise<void>`. |

## Firing a task

To queue a run, call `ctx.schedule(taskId, { time, data? })` from a handler that runs for a connection, such as a `base.on` handler. `time` is a Unix timestamp in milliseconds: the number of milliseconds since 1 January 1970 (UTC), the same kind of number `Date.now()` returns. The body runs at that time. No caller waits for it.

```typescript [server/huddle-definition.ts]
import { server, t } from '@livething/server'
import { scheduled } from '@livething/server/scheduled'
import * as v from 'valibot'

const base = server({
  capabilities: [
    scheduled({ 'send-digest': { data: t<{ userId: string }>() } }),
  ],
})

// The 'send-digest' task, queued when a client sends 'subscribe-digest'.
const handleSubscribeDigest = base.on('subscribe-digest', {
  input: v.object({ delayMs: v.number() }),
  run(ctx, input) {
    ctx.schedule('send-digest', {
      time: Date.now() + input.delayMs,
      data: { userId: ctx.user.id },
    })
  },
})
```

`ctx.schedule(...)` checks its arguments **synchronously**. On a mistake it throws inside the handler that called it. These calls throw:

- a task ID that is not declared,
- a `time` that is not a positive whole number (`NaN`, `Infinity`, `0`, negative numbers and fractions all throw),
- `data` passed to a task that declares no payload,
- `data` that fails the task's declared schema.

Wrap the call in `try`/`catch` if you want to handle the error yourself. If you don't catch it, the error passes up to the handler.

To cancel runs that are still waiting, call `ctx.cancelScheduled(taskId)`. You can pass a data filter as the second argument, for example `ctx.cancelScheduled('send-digest', { userId })`. With a filter, LiveThing cancels only the runs whose payload has the same value for every key in the filter. A filtered cancel never stops a recurring task, because a recurring task has no payload. Call `ctx.cancelScheduled(taskId)` with no filter to stop it. A recurring task stopped this way stays stopped, even after a restart. Call `ctx.schedule(taskId, { time })` to start it again: the first run happens at `time`, then it goes back to running every `every` milliseconds. The `scheduled({...})` capability adds both `schedule` and `cancelScheduled` to [`ctx`](/server/context-and-storage/overview).

## The task's ctx

A scheduled `run` gets a **connectionless context** (the `ConnectionlessContext` type), not a connection context. A timer has no socket behind it, so this `ctx` has server-wide tools and no per-connection ones. It is the same `ctx` that the [`onShutdown`](/server/lifecycle-and-intercept/hooks) hook and your [admin `api`](/server/admin/context) get. Every event name and payload is checked against your server's `emits(...)`, so a typo is a compile error.

| On `ctx`                                          | What it does                                                                                                                                                                                    |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ctx.sql` / `ctx.kv`                              | Storage: query, migrate, read and write.                                                                                                                                                        |
| `ctx.broadcast(event, payload)`                   | Sends an event to **every** live connection. It has no `includeSelf` option, because there is no caller to leave out.                                                                           |
| `ctx.connections.get(ref)`                        | A handle for one connection, found by its `ConnectionRef`. Its `send(event, payload)` sends to only that socket. It returns `true` when the event was sent and `false` when the socket is gone. |
| `ctx.connections.all()`                           | A snapshot of every live connection.                                                                                                                                                            |
| `ctx.users.get(id)`                               | A [handle for one user](/server/context-and-storage/users), by user ID. It reaches every socket that user has open.                                                                             |
| `ctx.channels.get(...)`                           | A handle for one channel: `broadcast`, `members` and `kick`. Only with [`channels()`](/server/capabilities/channels).                                                                           |
| `ctx.channels.broadcast(channel, event, payload)` | Sends an event to one channel's members. The event and payload are checked against the channel you name. Only with [`channels()`](/server/capabilities/channels).                               |
| `ctx.connectionCount`                             | How many connections are open right now.                                                                                                                                                        |
| `ctx.closeConnections(filter?, code?, reason?)`   | Closes every live connection, or only one user's with `{ userId }`.                                                                                                                             |
| `ctx.purgeUser(userId)`                           | [Removes a user everywhere](/server/admin/context#remove-a-user-everywhere).                                                                                                                    |
| `ctx.schedule(...)` / `ctx.cancelScheduled(...)`  | Queue or cancel another task run.                                                                                                                                                               |
| `ctx.log`                                         | The structured logger.                                                                                                                                                                          |
| `ctx.platform`                                    | The raw platform object (on Cloudflare, `Platform<Env>`).                                                                                                                                       |

::note
There is no `ctx.send` here. `ctx.send` sends to the calling connection, and a task has no calling connection. To reach connections from a task, broadcast to all of them, send to one with `ctx.connections.get(ref).send(...)`, or broadcast to a channel's members with `ctx.channels.get(...).broadcast(...)`.
::

A task that broadcasts to everyone:

```typescript [server/jobs.ts]
import { emits, server, t } from '@livething/server'
import { scheduled } from '@livething/server/scheduled'

const base = server({
  capabilities: [
    emits({ 'invites-expired': t<{ at: number }>() }),
    scheduled({ 'expire-invites': { every: 3_600_000 } }),
  ],
})

const handleExpireInvites = base.scheduled('expire-invites', {
  run(ctx) {
    ctx.sql.exec(
      'DELETE FROM invites WHERE expires_at < ?',
      Date.now(),
    )
    ctx.broadcast('invites-expired', { at: Date.now() })
  },
})

export const huddle = base.assemble({
  handlers: [handleExpireInvites],
})
```

A task that sends to one connection. The handler that queues the task puts its own `ctx.connection` into the task's typed `data`. The body uses that ref later:

```typescript [server/jobs.ts]
import { emits, server, t } from '@livething/server'
import { scheduled } from '@livething/server/scheduled'
import * as v from 'valibot'
import type { ConnectionRef } from '@livething/server'

const base = server({
  capabilities: [
    emits({ reminder: t<{ text: string }>() }),
    scheduled({
      remind: {
        data: t<{ connection: ConnectionRef; text: string }>(),
      },
    }),
  ],
})

const handleRemind = base.scheduled('remind', {
  run(ctx, data) {
    ctx.connections
      .get(data.connection)
      .send('reminder', { text: data.text })
  },
})

const handleRemindMe = base.on('remind-me', {
  input: v.object({ text: v.string(), delayMs: v.number() }),
  run(ctx, input) {
    ctx.schedule('remind', {
      time: Date.now() + input.delayMs,
      data: { connection: ctx.connection, text: input.text },
    })
  },
})

export const huddle = base.assemble({
  handlers: [handleRemind, handleRemindMe],
})
```

If that socket closed before the task runs, `send` returns `false` and nothing is sent. A new socket gets a new connection ID, so the old ref does not reach a reconnected client. To reach the person on any socket they have open, store their user ID instead and use `ctx.users.get(id)`.

A task that broadcasts to the members of one room. Pass the channel's `.at(params)` ref to `ctx.channels.get`, and `broadcast` is checked against that channel's own `emits(...)`:

```typescript [server/jobs.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { scheduled } from '@livething/server/scheduled'

const base = server({
  capabilities: [
    channels(),
    scheduled({ 'archive-room': { data: t<{ roomId: string }>() } }),
  ],
})

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ 'room-archived': t<{ roomId: string }>() })],
})

const handleArchiveRoom = base.scheduled('archive-room', {
  run(ctx, data) {
    ctx.channels
      .get(rooms.at({ roomId: data.roomId }))
      .broadcast('room-archived', { roomId: data.roomId })
  },
})

export const huddle = base.assemble({
  handlers: [handleArchiveRoom, rooms],
})
```

## Tasks with a payload

Declare `data` on the task, and your `run` gets a typed second argument. The payload comes from the `ctx.schedule(taskId, { time, data })` call that queued the run, so your own server code supplies it. How you declare `data` decides whether LiveThing checks it at runtime:

- A `t<T>()` marker gives the type only. There is no runtime check.
- A Standard Schema validator (for example a valibot schema) is **checked when you call `ctx.schedule()`**. A payload that fails the check throws there, and the run is not queued.

```typescript [server/jobs.ts]
import { server, t } from '@livething/server'
import { scheduled } from '@livething/server/scheduled'
import { buildDigest } from './huddle-data'

const base = server({
  capabilities: [
    scheduled({
      'send-digest': { data: t<{ userId: string }>() },
    }),
  ],
})

const handleSendDigest = base.scheduled('send-digest', {
  run(ctx, data) {
    buildDigest(data.userId) // data: { userId: string }
  },
})

export const huddle = base.assemble({ handlers: [handleSendDigest] })
```

Queue it with the matching `data`:

```typescript [server/huddle-handlers.ts]
// Inside a base.on handler, such as 'subscribe-digest' above:
ctx.schedule('send-digest', {
  time: Date.now() + 60_000,
  data: { userId: ctx.user.id },
})
```

## Recurring and retrying tasks

You set how a task behaves on its **declaration** in the [`scheduled({...})`](/server/capabilities/scheduled) capability, not here. That includes `every`, `retry` and whether it carries `data`. The body looks the same in every case. A recurring task runs its body again and again. A task with retries runs its body again after it fails.

```typescript [server/jobs.ts]
import { server, t } from '@livething/server'
import { scheduled } from '@livething/server/scheduled'
import { sendDigestEmail } from './huddle-data'

const base = server({
  capabilities: [
    scheduled({
      'expire-invites': { every: 3_600_000 }, // recurs every hour
      'send-digest': {
        data: t<{ userId: string }>(),
        retry: [1000, 5000, 15000],
      }, // retries with this backoff
    }),
  ],
})

const handleExpireInvites = base.scheduled('expire-invites', {
  run(ctx) {
    ctx.sql.exec(
      'DELETE FROM invites WHERE expires_at < ?',
      Date.now(),
    )
  },
})

const handleSendDigest = base.scheduled('send-digest', {
  run(ctx, data) {
    if (!sendDigestEmail(data.userId)) {
      throw new Error('digest send failed')
    } // a throw triggers the declared retry
  },
})

export const huddle = base.assemble({
  handlers: [handleExpireInvites, handleSendDigest],
})
```

A recurring task cannot also carry a `data` payload, because no caller exists to supply one.

A task that leaves out `retry` uses the default policy, the same as `retry: true`. The default is 3 retries with a backoff of `[1000, 5000, 25000]` ms. When a run has no retries left, it moves to the [**dead-letter queue**](/server/capabilities/scheduled). This is a durable SQL table named `__livething_scheduled_dlq` that keeps a record of runs that failed for good. You can read it with `ctx.sql`. Every declaration option is set on the `scheduled()` capability.

A run can happen more than once: after a retry, or again after the server crashed while the body was running. So **task bodies must be idempotent**. An idempotent body gives the same result when it runs twice as when it runs once. [At-least-once delivery](/server/capabilities/scheduled#at-least-once-delivery) covers what to guard against.

## Declaration and handler must match

Every declared task needs exactly one handler passed to `assemble()`, and every handler needs a matching declaration.

| Mistake                                                                      | Error                                                                                                      |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| A task declared in `scheduled({...})` with no handler passed to `assemble()` | `Scheduled task '<taskId>' has no handler. Pass base.scheduled('<taskId>', ...) to assemble().`            |
| A `base.scheduled(...)` handler whose ID isn't declared                      | `base.scheduled('<taskId>') has no matching declaration. Declare it in the scheduled({ ... }) capability.` |
| Two handlers for the same task ID                                            | `Duplicate scheduled task '<taskId>' passed to assemble(). Two handlers run this task. Remove one.`        |

When the [`handlers`](/server/handlers/overview#grouping-handlers) list has a known length (an array literal, or a list written with `as const`), the missing handler and the duplicate are compile errors. Otherwise `assemble()` throws when it runs.

A task ID that is not declared is also a compile error at the `base.scheduled(...)` call. The `taskId` parameter only accepts the IDs you declared, so TypeScript catches a typo.
