A **channel** is a room: a named group of connections that share events. `base.channel(pattern, config)` declares a channel and returns a channel object. That object has the same handler methods as `base`: `on`, `request`, and the stream methods. Each of these methods is **scoped to the channel**. This means the handler runs only for connections that are subscribed to that channel (its **members**), and its `ctx` has an extra typed field, `ctx.channel`.

`base.channel` exists on `base` only when you list the [`channels()`](/server/capabilities/channels) capability.

```typescript [server/rooms.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import * as v from 'valibot'
import { Message } from './base'

const base = server({
  capabilities: [channels()],
})

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
})

// a definition scoped to `rooms`
export const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})

export const huddle = base.assemble({ handlers: [handleSendMessage] })
```

This page shows how to **attach handlers** to a channel. The other channel topics (the auth gate, dynamic families, presence, and membership) are explained in [Channels](/server/channels/overview). This page links to those pages and does not repeat them.

::note
Pass every channel handler that you want to run to `assemble()`. A handler value brings its channel's configuration with it, and turns on only that one handler. You can also pass the channel object itself. That adds the channel's configuration and its lifecycle callbacks, but it turns on none of the channel's handlers.
::

## The handler methods on a channel

The channel object has the same builder methods as `base`. Each one is scoped to the channel, and each one needs the same capability as its top-level form:

| Method                                  | What it handles                       | Needs                                                      |
| --------------------------------------- | ------------------------------------- | ---------------------------------------------------------- |
| `channel.on(event, config)`             | A client→server event from a member   | nothing extra                                              |
| `channel.request(event, config)`        | A client→server request from a member | [`clientRequests()`](/server/capabilities/client-requests) |
| `channel.stream(event, config)`         | A stream scoped to the channel        | [`stream()`](/server/capabilities/streams)                 |
| `channel.recordedStream(event, config)` | A recorded stream in the channel      | [`recordedStream()`](/server/capabilities/streams)         |

The config for each method is the same as for its top-level form. See [base.on](/server/handlers/on), [base.request](/server/handlers/request), and [base.stream](/server/handlers/stream). The only difference is `ctx`: inside a channel handler, `ctx` also has `ctx.channel`.

Channel handlers use the same per-connection scheduling rules as top-level handlers (the rules that decide whether a handler waits for earlier work on the same connection). See [Per-Connection Event Queue](/server/handlers/per-connection-queue).

```typescript [server/rooms.ts]
import { t } from '@livething/server'
import * as v from 'valibot'
import { Message, rooms } from './base'
import { searchRoomMessages } from './helpers'

// a channel event handler
const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})

// a channel request handler: the return value is the reply
const handleLoadHistory = rooms.request('load-history', {
  input: v.object({ before: v.optional(v.number()) }),
  async run(ctx, input) {
    const messages = await loadMessages(
      ctx.channel.params.roomId,
      input.before,
    )
    return { messages }
  },
})

// a channel stream: the generator is the same as a top-level one.
// This one searches only the room it was started in. Huddle's own
// 'search-messages' is a top-level stream that searches all messages.
const handleRoomSearch = rooms.stream('search-messages', {
  input: v.object({ query: v.string() }),
  chunk: t<{ hit: Message }>(),
  async *run(ctx, input) {
    for await (const hit of searchRoomMessages(
      ctx.channel.params.roomId,
      input.query,
    )) {
      yield { hit }
    }
  },
})
```

## `ctx.channel`

Inside a channel handler, `ctx` has `ctx.channel`. It is the handle for the channel that matched. Its send methods are typed from the `emits(...)` capability that you listed in that channel's config:

::field-group
::field{name="name" type="string"}
The name of the matched channel. For a static channel this is its name (for example `'announcements'`). For a dynamic family it is the template with the values filled in (for example `'room:general'`).
::
::field{name="family" type="string | null"}
The family key for a [dynamic family](/server/channels/dynamic-families). `null` for a static channel.
::
::field{name="params" type="Record<string, string>"}
The values captured by the `{name}` parts of a dynamic pattern, for example `{ roomId: 'general' }`. An empty object `{}` for a static channel.
::
::field{name="send" type="(event, payload) => number"}
Sends a channel event to the calling connection. Returns `1` when it was delivered and `0` when it was not.
::
::field{name="broadcastTo" type="(to, event, payload) => number"}
Sends a channel event to some of the channel's members. `to` is a `ConnectionRef`, `UserRef`, `TagRef`, or `TagGroupHandle`. Every selected member gets the same frame. Returns the number of sockets that received it.
::
::field{name="broadcast" type="(event, payload, options?) => void"}
Sends a channel event to the channel's members. It skips the calling connection by default. Pass `{ includeSelf: true }` to include it.
::
::field{name="members" type="() => ConnectionInfo[]"}
A list of the connections that are subscribed to the channel at this moment.
::
::field{name="subscribe" type="(ref, payload?) => Promise<void>"}
Subscribes a connection from server code. It runs the same steps as a subscribe from the client: `check`, then `commit`, then the channel's `onSubscribe` hook. Returns a promise.
::
::field{name="kick" type="(target, opts) => Promise<void>"}
Removes a user's subscribed connections. `target` is a `UserRef`, a `TagRef`, or a tag group handle. `opts.reason` (a string) is required. Sends `__kicked__`, then `__memberLeave__` / `__memberOffline__` to the other members. A kick is permanent: it deletes the saved membership, so the user does not join again automatically on reconnect. Returns a promise.
::
::

When the channel's own `capabilities` list includes `serverRequests(...)`, `inbox()`, or `readReceipts()`, `ctx.channel` also has `request`, `inbox`, or `readReceipts`. See [Channel-scoped requests](/server/channels/scoped-streams-requests#channel-scoped-requests) and [Inbox](/server/capabilities/inbox).

```typescript [server/rooms.ts]
import * as v from 'valibot'
import { rooms } from './base'

const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
    // ctx.channel.name   → 'room:general'
    // ctx.channel.family → 'rooms'
    // ctx.channel.params → { roomId: 'general' }
  },
})
```

`ctx.channel.send`, `ctx.channel.broadcastTo`, and `ctx.channel.broadcast` are typed to the channel's **own** emits, the ones declared in the channel config. If you send a channel event that you did not declare on that channel, TypeScript reports a compile error. The rest of `ctx` is still there: storage, the top-level `ctx.send` and `ctx.broadcast`, tags, and so on. `ctx.channel` is an extra field. See [Context and storage](/server/context-and-storage/overview).

The three send methods follow the same pattern as at the top level. `.send` reaches only the calling connection. `.broadcastTo` reaches the members that you select. `.broadcast` reaches all the channel's members. The difference is that the channel forms send the event on this channel, so on the client it arrives on the channel handle, not on the socket. See [Core Context](/server/context-and-storage/ctx#messaging).

### On a dynamic family

A [dynamic family](/server/channels/dynamic-families) is declared with a `[familyKey, template]` pair. In its handlers, `ctx.channel.params` has the captured values and `ctx.channel.family` is the family key:

```typescript [server/rooms.ts]
import * as v from 'valibot'
import { rooms } from './base'

const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    // ctx.channel.params → { roomId: string }, typed from the template
    // ctx.channel.family → 'rooms'
    // ctx.channel.name   → the matched name, e.g. 'room:general' (the template filled in)
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

## The gate and lifecycle callbacks

A channel often controls who may join, and runs code when members join and leave. These are **not** message handlers. They belong to the whole channel, not to one event:

- `check` and `commit` are keys of the config object in `base.channel(pattern, config)`. `check` is an async test that runs before the new subscriber is counted. `commit` is a synchronous test that runs after. Throw from either one to reject the subscribe.
- `onSubscribe`, `onUnsubscribe`, and `onSessionEnd` are keys of the same object. They are lifecycle callbacks (functions that run when a member joins, leaves, or its session ends).

In this example, `rooms` also has a `check` and two callbacks that Huddle's own `rooms` does not have:

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { base, Message } from './base'
import { isBanned } from './helpers'

export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  check(ctx) {
    if (isBanned(ctx.user.id)) {
      throw new Error('banned users may not join a room') // rejects the subscribe
    }
  },
  onSubscribe(ctx) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: `${ctx.meta.name} joined`,
      from: 'system',
      sentAt: Date.now(),
    })
  },
  onUnsubscribe(ctx) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: `${ctx.meta.name} left`,
      from: 'system',
      sentAt: Date.now(),
    })
  },
})
```

The config and these callbacks turn on when you pass the channel to `assemble()`. That is all a channel with no handlers needs: Huddle passes `announcements` by itself.

[Channels](/server/channels/overview) explains the auth gate, families, presence, and membership in full. This section only shows where the gate and the lifecycle callbacks sit next to the handlers.

## Errors in channel handlers

A throw from `channel.request` or from a channel stream method reaches the client in the same way as for the top-level forms. See [base.request](/server/handlers/request#throwing-to-reject) and [base.stream](/server/handlers/stream#throwing-from-a-stream). The client matches those errors to the request or stream by its correlation ID (the ID that links a reply to the call that started it), not by the channel. So the pending `request()` promise rejects, or the stream's `for await` loop throws.

`channel.on` works differently. Like `base.on`, it is fire-and-forget: the client sends the event and does not wait for an answer. So when validation fails or the handler throws, there is no promise to reject. The error arrives on the client as an error for that channel. When no subscribe is in progress, the channel stays subscribed and the error goes to the socket's [`socket.onServerError(...)`](/client/errors/onerror-routing) listener:

```typescript [client/socket.ts]
socket.onServerError((error) => {
  // also receives a bad payload or a throw from `rooms.on(...)` on the server
  console.warn('server error', error.code)
})
```

The channel's `onSubscriptionFailed(...)` hook runs only for a failed subscribe or a failed rejoin after a reconnect. See [Lifecycle hooks](/client/channels/lifecycle-hooks).

## Channel-scoped intercept

A channel can also have its own intercept, which applies only to that channel. `intercept` is a key of the channel's config: a function that sees every incoming frame for the channel before LiveThing routes it to a handler. Throw to block the frame. A channel can have one. See [Intercept](/server/lifecycle-and-intercept/intercept).

In this example, the intercept blocks a guest from sending the `redirect` nudge (a message the client sends into a running stream) that arrives for `rooms`:

```typescript [server/rooms.ts]
import { Block } from '@livething/server/errors'
import { base } from './base'

export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  intercept(ctx, frame) {
    if (
      frame.kind === 'nudge' &&
      frame.event === 'redirect' &&
      ctx.meta.role === 'guest'
    )
      throw Block
  },
})
```

## Event names are scoped to the channel

Each channel has its own namespace (its own set of event names). `rooms.on('send-message', ...)` and a top-level `base.on('send-message', ...)` are two different handlers. The channel one runs only for `rooms` members. So you can use the same name at the top level and inside a channel, and the two do not conflict. Inside one channel, an event name can still belong to only one kind of handler. For example, you can't have both `rooms.on('typing')` and `rooms.request('typing')`. That is a compile error in `assemble()` when the `handlers` list has a known length, and an error when `assemble()` runs otherwise. Two channels can also use the same name.
