`base.request(event, config)` handles a **client→server request**. The client sends a request and waits for a reply. The value that your `run` function returns becomes the response. TypeScript infers the response type from that return value, and the client gets the same type: its request promise resolves with the response.

`base.request` is available on `base` only when you list the [`clientRequests()`](/server/capabilities/client-requests) capability. If you call it without that capability, the call throws this error:

```text
[livething] base.request() needs clientRequests(). Add clientRequests() to capabilities.
```

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'
import { loadProfile } from './helpers'

const base = server({
  capabilities: [clientRequests()],
})

export const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  run(ctx, input) {
    return loadProfile(input.userId) // the return value is the response
  },
})

export const huddle = base.assemble({
  handlers: [handleGetProfile],
})
```

On the client, this is one awaited round trip:

```typescript [client/socket.ts]
const profile = await socket.request('get-profile', {
  userId: 'u_42',
})
// profile: { id: string; name: string; status: 'active' | 'away' | 'busy' }, inferred from the handler's return
```

## The contract slice

The client contract is the type that tells the client what the server accepts and sends. A request adds one entry under `clientRequests` in that type. The entry's key is the event name. It holds the payload the request takes and the response it returns:

```typescript [shape]
// the slice `base.request('get-profile', ...)` contributes
type GetProfileSlice = {
  clientRequests: {
    'get-profile': {
      payload: { userId: string }
      response: {
        id: string
        name: string
        status: 'active' | 'away' | 'busy'
      }
    }
  }
}
```

## The config

::field-group
::field{name="input"}
A validator for the request payload. LiveThing checks the payload before `run`. A bad payload rejects the client's request, and your code does not run. If you leave it out, `input` has the type `unknown`.
::
::field{name="run" required}
`run(ctx, input)`. Returns the response, either directly or as a `Promise`. The response type is inferred from the return value.
::
::field{name="allowInterleaving"}
Run this request without waiting for earlier ordinary work on the same connection. The default is `true`, so a request gets a fast reply. Set it to `false` when the request must see state changes in order.
::
::field{name="rateLimit"}
A rate-limit rule for this handler only. It exists only when you list the [`rateLimit()`](/server/capabilities/rate-limit) capability.
::
::

By default, client→server requests interleave with other ordinary work on the same connection, following the full scheduling model of the [per-connection event queue](/server/handlers/per-connection-queue). This means a request can run while earlier work on that connection is still running. Set `allowInterleaving: false` when the request must wait for earlier work that changes state:

```typescript [server/huddle-handlers.ts]
const handleUnreadCount = base.request('unread-count', {
  allowInterleaving: false,
  input: v.object({}),
  run(ctx) {
    return { count: unreadCount(ctx.user.id) } // must see the read receipts earlier handlers just wrote
  },
})
```

The other direction works differently. When a client answers a server→client request, that answer is not an app handler. LiveThing settles it at once and does not put it in the per-connection work queue.

## The response value

The value that `run` returns **is** the reply. The client's `request(...)` promise resolves with it, and its type comes from the return value:

```typescript [server/huddle-handlers.ts]
const handleOnlineCount = base.request('online-count', {
  input: v.object({}),
  run(ctx) {
    return { count: ctx.connectionCount } // client resolves with { count: number }
  },
})
```

`run` can be async. Return a `Promise`, and the client gets the resolved value:

```typescript [server/huddle-handlers.ts]
const handleGetRoom = base.request('get-room', {
  input: v.object({ roomId: v.string() }),
  async run(ctx, input) {
    const room = await loadRoom(input.roomId) // some async work
    return { name: room.name }
  },
})
```

::caution
LiveThing does **not** validate the response before it sends it. It skips this check on purpose, to avoid the extra work. So the return type is your contract. Return the shape you typed. A wrong shape compiles only if you cast it.
::

A reply must be an object in JSON. A `null` reply is not a value: it is the same as returning nothing (see below). Returning a number, a string, a boolean or an array is a compile error, and a cast past it makes the client's request fail with `internal-error`. To reply with one value, put it inside an object, as `{ count }` does above.

### Returning nothing is a void acknowledgement

A handler can finish without an answer: it has no `return`, or it returns `null` or `undefined`. In that case the client's request settles as a **void acknowledgement**. The server sends an empty reply frame that matches the request, and the client's `request()` resolves with no value. The response type is inferred as `void`. Use this when the client only needs to know that the server finished the work.

```typescript [server/huddle-handlers.ts]
const handleMuteUser = base.request('mute-user', {
  input: v.object({ userId: v.string(), untilMs: v.number() }),
  run(ctx, input) {
    muteUser(input.userId, input.untilMs)
    // no return → the client's request() resolves with no value
  },
})
```

LiveThing treats both `null` and `undefined` as this void acknowledgement. To send a value that is `null`, `0`, `false` or `''` as real data, put it inside an object:

```typescript [server/huddle-handlers.ts]
const handleUnreadCount = base.request('unread-count', {
  input: v.object({}),
  run(ctx) {
    return { count: 0 } // resolves with { count: 0 }: a real response, not an acknowledgement
  },
})
```

To **fail** a request instead of acknowledging it, throw an error. The next section shows how.

## Throwing to reject

A request handler can fail the request by throwing. The client's promise then **rejects** instead of resolving. Throw an error built with [`error()`](/core/error-model). The client then gets a typed failure that it can narrow. Declare your errors with the [`errors([...])`](/server/capabilities/errors) capability. The shared error model is described in [Core](/core/error-model).

On the client, the rejection is a `LiveThingError`. Narrow it with `.matches()`. Put the error in a file that the server and the client both import. Huddle's `shared/errors.ts` exports `NotFound`, `Forbidden` and `RoomFull`, and its `errors([...])` capability already lists them. This version of `get-profile` throws `NotFound` when there is no such user:

::code-group

```typescript [server/profile-handlers.ts]
import * as v from 'valibot'
import { NotFound } from '../shared/errors'
import { base } from './base'
import { loadProfile } from './helpers'

const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  async run(ctx, input) {
    const profile = await loadProfile(input.userId)
    if (!profile) throw NotFound({ id: input.userId })

    // rejects the client's request
    return profile
  },
})
```

```typescript [shared/errors.ts]
import { error } from '@livething/core'
import * as v from 'valibot'

export const NotFound = error(
  'not-found',
  v.object({ id: v.string() }),
)
```

```typescript [client/profile-card.ts]
import { NotFound } from '../shared/errors'
import { showMissingProfile } from './huddle-ui'
import { socket } from './socket'

const userId = 'u_42'

try {
  const profile = await socket.request('get-profile', { userId })
} catch (err) {
  if (NotFound.matches(err)) showMissingProfile(userId)
  else throw err
}
```

::

A plain `throw new Error(...)` also works, but the client only sees a general `internal-error`. Use `error()` to give the client a code that it can check.

## Server→client requests

In the other direction, the **server** asks a **connection** a question and waits for its answer. This is not a handler. You start it from `ctx`. Inside any handler, `ctx.request(event, payload)` sends a server→client request to the calling connection and resolves with its typed answer. An optional third argument holds the `options`. You declare these requests in `serverRequests({ ... })`.

The default for `options.timeout` is **10 000 ms**. The promise can reject for these reasons:

| Rejection                  | When                                                                                                                                                                                                                                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `timeout`                  | The client does not answer in time.                                                                                                                                                                                                                                                                                            |
| `disconnected`             | The target connection closes before it answers.                                                                                                                                                                                                                                                                                |
| `request-invalid-response` | The answer does not match the declared `in` schema, or it is the wrong kind of frame: a binary answer to `ctx.request`, or a text answer to `ctx.binary.request`.                                                                                                                                                              |
| `request-not-declared`     | The event is not in the `serverRequests({...})` map. The promise rejects at once, before any message is sent. If the event is in `binary({ serverRequests })` instead, the error message says so, and tells you to use `ctx.binary.request`. The same is true for `ctx.binary.request` on a name from `serverRequests({...})`. |
| `request-no-response`      | The client has no `onRequest` handler for this request, or its handler threw an error.                                                                                                                                                                                                                                         |

For how to declare and use these requests, see [Context and storage](/server/context-and-storage/overview) and the [`serverRequests()`](/server/capabilities/server-requests) capability.

```typescript [server/huddle-handlers.ts]
import * as v from 'valibot'
import { base } from './base'
import { deleteMessage, loadMessagePreview } from './huddle-data'

const handleDeleteMessage = base.request('delete-message', {
  input: v.object({ messageId: v.string() }),
  async run(ctx, input) {
    const preview = await loadMessagePreview(input.messageId)
    const answer = await ctx.request('confirm-delete', { preview })
    if (!answer.confirmed) return { deleted: false }

    await deleteMessage(input.messageId)

    return { deleted: true }
  },
})
```

Two other forms send the request to connections other than the calling one:

- **`request(...)` on `ctx.connections.get(ref)`** asks one _other_ connection. You address it by its `ConnectionRef`.
- **`request(...)` on `ctx.users.get(id)`** asks one user. The question goes to every tab that user has open on this server instance. It resolves with the **first valid answer**, as `{ response, from }`, where `from` is the `ConnectionRef` of the tab that answered.

Both take the same arguments as `ctx.request`:

```ts
import type { ConnectionRef } from '@livething/server'

declare const ref: ConnectionRef

// In a handler: ask one other connection
const preview = 'Lunch moved to 13:00'
await ctx.connections.get(ref).request('confirm-delete', { preview })
```

```ts
// In a handler: ask every tab of one user
const preview = 'Lunch moved to 13:00'
const user = ctx.users.get('user_9')
const { response, from } = await user.request('confirm-delete', {
  preview,
})
```

In this version of `report-message`, the handler also asks the on-call moderator to take the report. Huddle's own `report-message` only saves it:

```typescript [server/huddle-definition.ts]
import { server, t } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import { serverRequests } from '@livething/server/server-requests'
import * as v from 'valibot'
import { loadOnCallModeratorId, saveMessageReport } from './helpers'

const base = server({
  capabilities: [
    clientRequests(),
    serverRequests({
      'take-report': {
        out: t<{ messageId: string; reason: string }>(),
        in: v.object({ accepted: v.boolean() }),
      },
    }),
  ],
})

const handleReportMessage = base.request('report-message', {
  input: v.object({ messageId: v.string(), reason: v.string() }),
  async run(ctx, input) {
    await saveMessageReport(
      input.messageId,
      input.reason,
      ctx.user.id,
    )
    const moderatorId = await loadOnCallModeratorId()
    const { response } = await ctx.users
      .get(moderatorId)
      .request('take-report', {
        messageId: input.messageId,
        reason: input.reason,
      })
    return { accepted: response.accepted }
  },
})
```

## Channel-scoped request handlers

A channel is a named group of connections, like a chat room. A channel can register its own request handlers with `channel.request(event, config)`. This handler works like `base.request`, but `ctx.channel` is available, and the request belongs to that channel only. So two channels can both declare a `load-history` request, and the two do not conflict. `base.channel(...)` needs the [`channels()`](/server/capabilities/channels) capability:

```typescript [server/rooms.ts]
import * as v from 'valibot'
import { rooms } from './base'
import { loadMessages } from './helpers'

export const handleLoadHistory = rooms.request('load-history', {
  input: v.object({ before: v.optional(v.number()) }),
  async run(ctx, input) {
    // ctx.channel is the room this request arrived on
    const messages = await loadMessages(
      ctx.channel.params.roomId,
      input.before,
    )
    return { messages }
  },
})
```
