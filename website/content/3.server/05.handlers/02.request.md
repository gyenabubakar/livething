`base.request(event, config)` handles a **client→server request** — the client sends a request and awaits a reply. Whatever your `run` returns becomes the response; its type is inferred from the return and flows to the client, where the request promise resolves with it.

`base.request` appears on `base` only when the [`clientRequests()`](/server/capabilities/client-requests) capability is listed. Calling it without that capability throws at boot: `[wskit] base.request() needs the clientRequests() capability. Add clientRequests() to capabilities.`

```typescript [users.ts]
import { server, t } from '@wskit/server'
import { clientRequests } from '@wskit/server/client-requests'
import * as v from 'valibot'

const base = server({
  capabilities: [clientRequests()],
})

export const handleGetUser = base.request('get-user', {
  input: v.object({ id: v.string() }),
  run(ctx, input) {
    return { id: input.id, name: lookupName(input.id) } // the return value is the response
  },
})

export const definition = base.assemble({
  handlers: [handleGetUser],
})
```

On the client this is an awaited round-trip:

```typescript [app.ts]
const user = await socket.request('get-user', { id: 'u_42' })
// user: { id: string; name: string } — inferred from the handler's return
```

## The contract slice

A request adds a `clientRequests` entry to the materialized client type — keyed by event, with the payload it takes and the response it returns:

```typescript [contract.ts]
// the slice `base.request('get-user', ...)` contributes
{
  clientRequests: {
    'get-user': {
      payload: { id: string }
      response: { id: string; name: string }
    }
  }
}
```

## The config

| Field               | Required | What it does                                                                                                                                                                                        |
| ------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `input`             | no       | A Validator for the request payload. Validated before `run`; a bad payload rejects the client without running your code. Omit it and `input` is typed `unknown`.                                    |
| `run`               | yes      | `run(ctx, input)`. Returns the response (sync or `Promise`). The response type is inferred from the return.                                                                                         |
| `allowInterleaving` | no       | Run this request without waiting for earlier ordinary work on the same connection. Defaults to `true`, so a request can get a timely reply. Set `false` when it must observe ordered state changes. |
| `rateLimit`         | no       | A per-handler rate-limit override. Present only when the [`rateLimit()`](/server/capabilities/rate-limit) capability is listed.                                                                     |

Client→server requests interleave with other ordinary work on the same connection by default. Set `allowInterleaving: false` when the request must wait for earlier state-changing work. See [Per-Connection Event Queue](/server/handlers/per-connection-queue) for the full scheduling model:

```typescript [handlers.ts]
const handleReadBalance = base.request('read-balance', {
  allowInterleaving: false,
  input: v.object({}),
  run(ctx) {
    return readBalance(ctx.user.id)
  },
})
```

The response to a server→client request is not an app handler, so WSKit settles it immediately rather than putting it in the per-connection work queue.

## The response value

The value `run` returns **is** the reply. The client's `request(...)` promise resolves with it, typed from the return:

```typescript [handlers.ts]
const handleGetTime = base.request('get-time', {
  input: v.object({}),
  run() {
    return { now: Date.now() } // client resolves with { now: number }
  },
})
```

`run` can be async — return a `Promise` and the client awaits the resolved value:

```typescript [handlers.ts]
const handleLookup = base.request('lookup', {
  input: v.object({ id: v.string() }),
  async run(ctx, input) {
    const profile = await fetchProfile(input.id) // some async work
    return { name: profile.name }
  },
})
```

::caution
The response is **not** validated on its way out. WSKit skips outgoing validation on purpose — it's overhead it avoids — so the return type is your contract. Return the shape you typed; a wrong shape compiles only if you cast it.
::

### Returning nothing is a void acknowledgement

A handler that produces no answer — no `return`, or a `return` of `null` or `undefined` — settles the client's request as a **void acknowledgement**: the server sends an empty correlated frame and the client's `request()` resolves with no value. Its response type is inferred as `void`. Use this for a "fire and confirm" request, where the client only needs to know the server finished.

```typescript [handlers.ts]
const handleSave = base.request('save', {
  input: v.object({ id: v.string() }),
  run(ctx, input) {
    saveRow(input.id)
    // no return → the client's request() resolves with no value
  },
})
```

`null` and `undefined` are both treated as this void ack. If you need to send `null` as real data, model it as an object — e.g. `return { value: null }`. Every other falsy value (`0`, `false`, `''`) is a real response that resolves the client with that value:

```typescript [falsy.ts]
const handleCount = base.request('unread-count', {
  input: v.object({}),
  run(ctx) {
    return 0 // resolves with 0 — a real response, not an ack
  },
})
```

To **fail** a request rather than acknowledge it, throw — see below.

## Throwing to reject

A request handler can fail the request by throwing. The client's promise then **rejects** instead of resolving. Throw an error built with [`error()`](/core/error-model) so the client gets a typed, narrowable failure rather than a generic one. Declare your errors with the [`errors([...])`](/server/capabilities/errors) capability; the shared model lives in [Core](/core/error-model).

```typescript [handlers.ts]
import { error, errors, server, t } from '@wskit/server'
import { clientRequests } from '@wskit/server/client-requests'
import * as v from 'valibot'

const NotFound = error('not-found', v.object({ id: v.string() }))

const base = server({
  capabilities: [clientRequests(), errors([NotFound])],
})

const handleGetUser = base.request('get-user', {
  input: v.object({ id: v.string() }),
  run(ctx, input) {
    const user = lookup(input.id)
    if (!user) throw NotFound({ id: input.id }) // rejects the client's request
    return user
  },
})
```

On the client, that rejection is a `WSKitError` you narrow with `.matches()`:

```typescript [app.ts]
import { NotFound } from '../server/errors'

try {
  const user = await socket.request('get-user', { id: 'u_42' })
} catch (err) {
  if (NotFound.matches(err)) showMissing(err.detail.id)
  else throw err
}
```

A plain `throw new Error(...)` works too, but the client only sees a generic internal error — use `error()` to give it a code it can branch on.

## Server→client requests

The other direction — the **server** asking a **connection** and awaiting its answer — is not a handler. It starts from `ctx`: inside any handler, `ctx.request(event, payload, options?)` asks the calling connection a server→client request you declared in `serverRequests({ ... })` and resolves its typed answer.

The `options.timeout` defaults to **10 000 ms**. The promise can reject for these reasons:

| Rejection                  | When                                                                                                       |
| -------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `timeout`                  | The client does not answer in time.                                                                        |
| `disconnected`             | The target connection drops before answering.                                                              |
| `request-invalid-response` | The answer fails the declared `in` schema.                                                                 |
| `request-not-declared`     | The event is not in the `serverRequests({...})` map. Rejects immediately, before any wire message is sent. |

See [Context and storage](/server/context-and-storage/overview) and the [`serverRequests()`](/server/capabilities/server-requests) capability for declaring and using it.

```typescript [handlers.ts]
const handleTrigger = base.on('trigger', {
  input: v.object({ action: v.string() }),
  async run(ctx, input) {
    const answer = await ctx.request('ask-permission', {
      action: input.action,
    })
    if (answer.allowed) doAction(input.action)
  },
})
```

Two variants reach beyond the calling connection:

- **`ctx.connections.get(ref).request(event, payload, options?)`** — ask one _other_ connection, addressed by its `ConnectionRef`.
- **`ctx.broadcastRequest(event, payload, options?)`** — send the question to every connection and resolve with the **first valid answer**, as `{ response, from }`. The caller is excluded by default; pass `{ includeSelf: true }` to include it.

```typescript [fan-out.ts]
const handleElect = base.on('elect', {
  input: v.object({ turn: v.number() }),
  async run(ctx, input) {
    const { response, from } = await ctx.broadcastRequest(
      'volunteer',
      {
        turn: input.turn,
      },
    )
    ctx.send('elected', {
      who: from.userId,
      ready: response.ready,
    })
  },
})
```

## Channel-scoped request handlers

A channel can register its own request handlers with `channel.request(event, config)`. The handler works like `base.request`, but `ctx.channel` is available and the request is scoped to that room (so two channels can both declare a `lookup` request without clashing):

```typescript [channel-request.ts]
const room = base.channel('room', {
  capabilities: [emits({})],
})

export const handleRoomLookup = room.request('lookup', {
  input: v.object({ id: v.string() }),
  run(ctx, input) {
    // ctx.channel is the room this request arrived on
    return { id: input.id, room: ctx.channel.name }
  },
})
```
