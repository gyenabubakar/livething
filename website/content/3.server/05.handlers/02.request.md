`base.request(event, config)` handles a **client→server request**. The client sends a request and waits for a reply. The value that your `run` function returns becomes the response. TypeScript infers the response type from that return value, and the client gets the same type: its request promise resolves with the response.

`base.request` is available on `base` only when you list the [`clientRequests()`](/server/capabilities/client-requests) capability. If you call it without that capability, the call throws this error: `[livething] base.request() needs clientRequests(). Add clientRequests() to capabilities.`

```typescript [users.ts]
import { server } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'

const base = server({
  capabilities: [clientRequests()],
})

export const handleGetUser = base.request('get-user', {
  input: v.object({ id: v.string() }),
  run(ctx, input) {
    return { id: input.id, name: lookupName(input.id) } // the return value is the response
  },
})

export const definition = base.assemble({
  handlers: [handleGetUser],
})
```

On the client, this is one awaited round trip (a message out and its reply back):

```typescript [app.ts]
const user = await socket.request('get-user', { id: 'u_42' })
// user: { id: string; name: string }, inferred from the handler's return
```

## The contract slice

The client contract is the type that tells the client what the server accepts and sends. A request adds one entry under `clientRequests` in that type. The entry's key is the event name. It holds the payload the request takes and the response it returns:

```typescript [contract.ts]
// the slice `base.request('get-user', ...)` contributes
{
  clientRequests: {
    'get-user': {
      payload: { id: string }
      response: { id: string; name: string }
    }
  }
}
```

## The config

| Field               | Required | What it does                                                                                                                                                                                                                                    |
| ------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `input`             | no       | A validator (a schema that checks the payload) for the request payload. LiveThing checks the payload before `run`. A bad payload rejects the client's request, and your code does not run. If you leave it out, `input` has the type `unknown`. |
| `run`               | yes      | `run(ctx, input)`. Returns the response, either directly or as a `Promise`. The response type is inferred from the return value.                                                                                                                |
| `allowInterleaving` | no       | Run this request without waiting for earlier ordinary work on the same connection. The default is `true`, so a request gets a fast reply. Set it to `false` when the request must see state changes in order.                                   |
| `rateLimit`         | no       | A rate-limit rule for this handler only. It exists only when you list the [`rateLimit()`](/server/capabilities/rate-limit) capability.                                                                                                          |

By default, client→server requests interleave with other ordinary work on the same connection. This means a request can run while earlier work on that connection is still running. Set `allowInterleaving: false` when the request must wait for earlier work that changes state. See [Per-Connection Event Queue](/server/handlers/per-connection-queue) for the full scheduling model:

```typescript [handlers.ts]
const handleReadBalance = base.request('read-balance', {
  allowInterleaving: false,
  input: v.object({}),
  run(ctx) {
    return readBalance(ctx.user.id)
  },
})
```

The other direction works differently. When a client answers a server→client request, that answer is not an app handler. LiveThing settles it at once and does not put it in the per-connection work queue.

## The response value

The value that `run` returns **is** the reply. The client's `request(...)` promise resolves with it, and its type comes from the return value:

```typescript [handlers.ts]
const handleGetTime = base.request('get-time', {
  input: v.object({}),
  run() {
    return { now: Date.now() } // client resolves with { now: number }
  },
})
```

`run` can be async. Return a `Promise`, and the client gets the resolved value:

```typescript [handlers.ts]
const handleLookup = base.request('lookup', {
  input: v.object({ id: v.string() }),
  async run(ctx, input) {
    const profile = await fetchProfile(input.id) // some async work
    return { name: profile.name }
  },
})
```

::caution
LiveThing does **not** validate the response before it sends it. It skips this check on purpose, to avoid the extra work. So the return type is your contract. Return the shape you typed. A wrong shape compiles only if you cast it.
::

### Returning nothing is a void acknowledgement

A handler can finish without an answer: it has no `return`, or it returns `null` or `undefined`. In that case the client's request settles as a **void acknowledgement**. The server sends an empty reply frame that matches the request, and the client's `request()` resolves with no value. The response type is inferred as `void`. Use this when the client only needs to know that the server finished the work.

```typescript [handlers.ts]
const handleSave = base.request('save', {
  input: v.object({ id: v.string() }),
  run(ctx, input) {
    saveRow(input.id)
    // no return → the client's request() resolves with no value
  },
})
```

LiveThing treats both `null` and `undefined` as this void acknowledgement. If you need to send `null` as real data, put it inside an object, for example `return { value: null }`. Every other falsy value (`0`, `false`, `''`) is a real response, and the client resolves with that value:

```typescript [falsy.ts]
const handleCount = base.request('unread-count', {
  input: v.object({}),
  run(ctx) {
    return 0 // resolves with 0: a real response, not an acknowledgement
  },
})
```

To **fail** a request instead of acknowledging it, throw an error. The next section shows how.

## Throwing to reject

A request handler can fail the request by throwing. The client's promise then **rejects** instead of resolving. Throw an error built with [`error()`](/core/error-model). The client then gets a typed failure that it can narrow (check for one specific error and get its typed detail). Declare your errors with the [`errors([...])`](/server/capabilities/errors) capability. The shared error model is described in [Core](/core/error-model).

```typescript [handlers.ts]
import { error, errors, server } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'

const NotFound = error('not-found', v.object({ id: v.string() }))

const base = server({
  capabilities: [clientRequests(), errors([NotFound])],
})

const handleGetUser = base.request('get-user', {
  input: v.object({ id: v.string() }),
  run(ctx, input) {
    const user = lookup(input.id)
    if (!user) throw NotFound({ id: input.id }) // rejects the client's request
    return user
  },
})
```

On the client, the rejection is a `LiveThingError`. Narrow it with `.matches()`:

```typescript [app.ts]
import { NotFound } from '../server/errors'

try {
  const user = await socket.request('get-user', { id: 'u_42' })
} catch (err) {
  if (NotFound.matches(err)) showMissing(err.detail.id)
  else throw err
}
```

A plain `throw new Error(...)` also works, but the client only sees a general `internal-error`. Use `error()` to give the client a code that it can check.

## Server→client requests

In the other direction, the **server** asks a **connection** a question and waits for its answer. This is not a handler. You start it from `ctx`. Inside any handler, `ctx.request(event, payload, options?)` sends a server→client request to the calling connection and resolves with its typed answer. You declare these requests in `serverRequests({ ... })`.

The default for `options.timeout` is **10 000 ms**. The promise can reject for these reasons:

| Rejection                  | When                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `timeout`                  | The client does not answer in time.                                                                           |
| `disconnected`             | The target connection closes before it answers.                                                               |
| `request-invalid-response` | The answer does not match the declared `in` schema.                                                           |
| `request-not-declared`     | The event is not in the `serverRequests({...})` map. The promise rejects at once, before any message is sent. |
| `request-no-response`      | The client has no `onRequest` handler for this request, or its handler threw an error.                        |

For how to declare and use these requests, see [Context and storage](/server/context-and-storage/overview) and the [`serverRequests()`](/server/capabilities/server-requests) capability.

```typescript [handlers.ts]
const handleTrigger = base.on('trigger', {
  input: v.object({ action: v.string() }),
  async run(ctx, input) {
    const answer = await ctx.request('ask-permission', {
      action: input.action,
    })
    if (answer.allowed) doAction(input.action)
  },
})
```

Two other forms send the request to connections other than the calling one:

- **`ctx.connections.get(ref).request(event, payload, options?)`** asks one _other_ connection. You address it by its `ConnectionRef` (a reference to one connection).
- **`ctx.broadcastRequest(event, payload, options?)`** sends the question to every connection on this server instance (one running copy of your server). It resolves with the **first valid answer**, as `{ response, from }`. By default, the calling connection is not asked. Pass `{ includeSelf: true }` to ask it too.

```typescript [fan-out.ts]
const handlePickHost = base.on('pick-host', {
  input: v.object({ round: v.number() }),
  async run(ctx, input) {
    const { response, from } = await ctx.broadcastRequest(
      'volunteer',
      {
        round: input.round,
      },
    )
    ctx.send('host-picked', {
      userId: from.userId,
      ready: response.ready,
    })
  },
})
```

## Channel-scoped request handlers

A channel is a named group of connections, like a chat room. A channel can register its own request handlers with `channel.request(event, config)`. This handler works like `base.request`, but `ctx.channel` is available, and the request belongs to that channel only. So two channels can both declare a `lookup` request, and the two do not conflict. `base.channel(...)` needs the [`channels()`](/server/capabilities/channels) capability:

```typescript [channel-request.ts]
const room = base.channel('room', {
  capabilities: [emits({})],
})

export const handleRoomLookup = room.request('lookup', {
  input: v.object({ id: v.string() }),
  run(ctx, input) {
    // ctx.channel is the room this request arrived on
    return { id: input.id, room: ctx.channel.name }
  },
})
```
