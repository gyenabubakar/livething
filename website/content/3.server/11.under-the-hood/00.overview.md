You never need this chapter to use WSKit. The earlier chapters show you what to write; this one explains what happens **after** you write it — why the pipeline runs in the order it does, why a feature you don't list costs nothing, and why the same server behaves differently on two platforms. It is the *why* behind the rules, not a new API to learn.

## Three layers

A running WSKit server is three layers stacked on top of each other. You author the first, pick the second, and never touch the third.

::steps
### The definition

`define` → capabilities → handlers → `assemble` produces a **server definition**: a frozen, platform-blind blueprint. It is not a running server and holds no connection state — it is just the list of primitives you registered, plus the contract type `InferClient` reads. The whole of chapters [define()](/server/define/overview) through [Plugins](/server/plugins/overview) is about building this one object.

### The adapter

An **adapter** wraps a definition and hands back a service for one platform — `server(chat)` from `@wskit/server-cloudflare` returns a Durable Object class. The adapter owns the platform's WebSocket lifecycle and supplies the engine with storage, timers, env, and a logger. [Adapters](/server/adapters/overview) covers this layer, and [Custom adapters](/server/adapters/custom-adapters) covers writing your own.

### The engine

Inside the adapter sits the **engine** — the part that actually runs your definition. It compiles the definition into fast lookup tables, installs each capability's runtime, accepts sockets, and walks every frame through the pipeline. You never construct it directly; the adapter does, through a factory.
::

The split is what lets one definition run anywhere: the definition names no runtime, the engine names no platform, and the adapter is the only piece that knows both.

## How the engine is built

The engine itself separates **state** from **behavior**, which is worth knowing because it explains a recurring phrase in these docs — "a capability fills a slot."

- **State** lives in one container: the open connections, the channel and tag member indexes, the compiled lookup tables, the registered hooks, and a set of empty **feature slots**.
- **Behavior** lives in the runtime modules that read and write that state — the boot routine, the message dispatcher, the connection lifecycle.

When the engine boots, each capability you listed registers its hooks and fills the slots it owns. A capability you didn't list leaves its slot empty, and the engine simply skips it when routing a frame. That single mechanism is behind three things this chapter unpacks:

- **[Compile and boot](/server/under-the-hood/compile-and-boot)** — how `assemble`'s frozen list becomes lookup tables, the order the boot routine runs in, and the checks that turn a misconfigured server into a clear startup error instead of a broken first frame.
- **[Feature slots](/server/under-the-hood/feature-slots)** — why listing a capability is the exact thing that pulls its code into your bundle, and leaving it out tree-shakes it away.
- **[Pipeline execution order](/server/under-the-hood/pipeline-execution-order)** — the precise order every inbound and outbound frame walks, with plugins, channels, and capabilities slotted in.

## One definition, different runtimes

Because the adapter is the only layer that knows the platform, the same definition can behave differently depending on which adapter runs it. The adapter declares what its platform supports — whether it can hibernate idle sockets, whether it exposes outbound buffer pressure — and the engine adapts to that.

Cloudflare hibernates but does not expose buffer fullness, so `ctx.stream.drain()` is a no-op there; a Node or Bun adapter would expose real pressure, so the same `drain()` paces a generator against the live buffer. Your handler code does not change. [Capability negotiation](/server/under-the-hood/capability-negotiation) is the last page of this chapter.
