This page is the precise reference for **when** each piece of a WSKit server runs. The other chapters teach each feature on its own; this one lays them out in order so you can reason about exactly where your intercept, validation, handler, outgoing hook, plugins, and channels sit on the path of a single frame.

It is a reference, not a tutorial. Each step links to the chapter that owns it.

## The two paths

A frame is either coming **in** (the client sent it) or going **out** (the server is sending it). They are separate pipelines with separate hooks:

- **Inbound** — a frame arrives, gets routed, validated, and handled. The hooks here are the channel membership gate, `intercept`, the schema validator, and the handler.
- **Outbound** — the server emits a frame; it passes the `outgoing` hook, gets recorded for replay, and goes on the wire.

Around both sits the **connection lifecycle**: `init`, `connect`, `disconnect`, `error`, `validationError`, `shutdown`.

## Before any frame: the connection opens

A socket has to be accepted before it can send a single app frame. This runs once per connection.

::steps
### Upgrade

The HTTP upgrade request hits the server. Every `upgrade` hook runs, in a fixed order, and each may return `identity`, `meta`, and ephemeral `tags`. The results are merged — `meta` is shallow-merged, `tags` are concatenated, and **at most one** hook may own `identity`.

The order is nested: **plugin `upgrade` hooks first** (in the order the plugins were listed), then any internal hooks, then **the app's `upgrade` last**. Because the app applies last, its `meta` wins on a key conflict.

```text
plugin upgrade (plugin order) → internal hooks → app upgrade
```

If any hook rejects (it throws the upgrade-reject signal, or any other error), the socket is refused and no connection is created. Authoring a plugin's scoped `upgrade` is covered in [Plugins · Authoring](/server/plugins/authoring); the app-side gate is in [Environment & Upgrade](/server/define/env-and-upgrade).

### Auto-rejoin persistent channels

Before the connection is handed to your code, the engine re-subscribes it to every persistent channel its `identity` was a member of. This skips the channel `check` / `commit` gate — the membership already passed it once.

### `connect`

The socket is now live. `connect` hooks run in the same nested order: **plugin `connect` hooks first** (registration order), then **the app's `connect` last**. Here `ctx` is the full connection context.
::

::note
`init` is **not** part of opening a connection. It runs once at server startup, before the first connection ever opens — plugin `init` hooks first, then the app's `init`. See [the lifecycle table](#where-the-lifecycle-fires) below.
::

## Inbound: a frame arriving

Once the connection is open, every text frame the client sends walks this path. The steps below are the order for a normal **app event** — a frame whose `event` is one of your declared `on` / `request` / `stream` / channel events.

::steps
### Parse and pre-checks

The raw text is parsed as JSON and shape-checked. A few fast paths short-circuit here before routing:

- `ping` / `pong` keepalive frames are answered and dropped.
- A frame that answers a server-initiated request (it echoes a `correlationId`) is handed to the request machinery and stops here.
- If `dedup()` is on, a frame whose `messageId` was already seen on this connection is dropped.

### Channel membership gate

If the frame is addressed to a channel, the connection must already be a member. A frame for a channel the connection has not subscribed to is rejected with a `channel-not-subscribed` error and never reaches an intercept or handler. (Joining a channel — the `check` / `commit` gate — is its own flow; see [Channels · Authorization gate](/server/channels/auth-gate).)

### `intercept` — top-level, then channel

The [`intercept`](/server/lifecycle-and-intercept/overview) hook runs. If the frame is channel-scoped, the **top-level** intercept runs first, then the **channel** intercept. Each can read the frame, rewrite its payload (the return value replaces `frame.payload` for the next step), or stop it by throwing `Block` (drop silently) or `Disconnect` (close the socket).

```text
top-level intercept → channel intercept (if channel-scoped)
```

This runs **before** validation, so a rewrite changes what the validator and handler see. Intercepts need the `intercepts()` capability.

::note
**Nudge frames take a parallel branch.** A nudge sent into a running stream (`frame.kind === 'nudge'`) also passes through the top-level and channel intercepts — but not schema validation or a handler. A `Block` drops just that nudge silently; any other throw (a typed error) is **non-terminal**, rejecting the client's `nudge()` promise while the stream keeps running.
::

### Schema validation

The handler's declared input schema runs against the (possibly rewritten) payload. On failure the handler never runs: the engine fires the [`validationError`](/server/lifecycle-and-intercept/hooks) hook and sends a `validation-failed` error to the client.

### Handler

The matched handler runs — exactly one of `on`, `request`, `stream`, or the channel-scoped version. Anything it sends out (`ctx.send`, `ctx.broadcast`, `ctx.channel.send`, a stream chunk, a request) starts the [outbound path](#outbound-a-frame-leaving).
::

### Where `provide` / `inject` locals flow

The per-frame locals store is created on first use and lives for **this one dispatch**. A value an intercept stores with `ctx.provide(key, value)` is readable by every downstream step of the same frame — a later intercept and the handler — and by nothing else. The top-level and channel intercepts and the handler all share the one store for that frame.

```text
intercept: ctx.provide(AuthKey, auth)
   → channel intercept: ctx.inject(AuthKey)  ✓
   → handler: ctx.inject(AuthKey)            ✓
next frame: ctx.inject(AuthKey)              undefined (fresh store)
```

The full API is in [provide / inject](/server/lifecycle-and-intercept/provide-inject).

### Worked example: a `say` event

A client sends `say` to a server with `intercepts()` listed and an `on('say')` handler:

```typescript [say-server.ts]
import { define, emits, t } from '@wskit/server'
import { intercepts } from '@wskit/server/intercepts'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [
    emits({ said: t<{ text: string }>() }),
    intercepts(),
  ],
})

base.intercept((ctx, frame) => {
  if (frame.kind === 'incoming' && frame.event === 'say') {
    const p = frame.payload as { text: string }
    return { ...p, text: p.text.trim() } // rewrite before validation
  }
})

const handleSay = base.on('say', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.send('said', { text: input.text }) // → starts the outbound path
  },
})

export const handler = base.assemble(handleSay)
```

The frame walks:

```text
say arrives
  → membership gate   (not channel-scoped → skip)
  → intercept         text trimmed
  → validate          v.object({ text }) runs on the trimmed value
  → handler           ctx.send('said', ...)
        → outgoing    (outbound path, below)
        → wire
```

If the intercept had thrown `Block`, the path stops at the intercept — no validation, no handler, no reply.

## Outbound: a frame leaving

Every server→client frame — from a handler's `ctx.send`, a `ctx.broadcast`, a stream chunk, a server request, a `connect` greeting, a `schedule` task — walks this path before it hits the wire.

::steps
### `outgoing` hook

The [`outgoing`](/server/lifecycle-and-intercept/overview) hook runs first. It can read the frame or rewrite its payload by returning a value — it cannot `Block` (that signal is inbound-only). The event name is locked. On a broadcast the hook runs **once** against the prepared frame, before the per-recipient loop; only the per-socket `__wskit` stamping and the before/after-send hooks run once per recipient.

### Declaration check

The (possibly rewritten) event must be a declared outgoing event for the active scope — an `emits(...)` / `outgoing(...)` event, or a real protocol event. An undeclared event throws `[wskit] Outgoing event "..." was not declared in the active scope.`. (Request replies, which carry a `correlationId`, skip this check.)

### `__wskit` metadata

The framework stamps routing onto the frame's `__wskit` envelope — the `seq` sequence number (from `sequence()`), the `messageId` dedup ID (from `dedup()`), channel markers, and any plugin-contributed keys.

### Replay record — strict mode

If [built-in replay](/server/replay/built-in) is on with **`durability: 'strict'`** (the default), the frame is written to the replay store **here, before the send**. So a recorded frame is on disk before the client could ever have seen it.

### Serialize and send

The frame is serialized to JSON and written to the socket.

### Replay record — best-effort mode

If replay is on with **`durability: 'best-effort'`**, the record runs **after** the send, asynchronously. The send latency is lower, but a crash in the gap can lose the last frame.
::

So the only difference replay durability makes is **which side of the send the record sits on**:

| `durability` | Order | Trade-off |
|---|---|---|
| `strict` (default) | record → send | No sent-but-unrecorded frame, slightly higher latency. |
| `best-effort` | send → record (async) | Lower latency, the last frame can be lost on a crash. |

The full durability discussion is in [Built-in replay · Durability](/server/replay/built-in#durability-strict-vs-best-effort). Frames that carry a `correlationId` (1:1 request replies) or a `streamId` (stream chunks) are never recorded — replay is for broadcastable history, not private exchanges.

### Outbound order, condensed

```text
ctx.send / broadcast / chunk
  → outgoing hook        (rewrite / Block)
  → declaration check
  → __wskit stamps       (seq, messageId, channel)
  → [strict replay record]
  → serialize → wire
  → [best-effort replay record (async)]
```

## Where the lifecycle fires

The six lifecycle hooks fire at fixed points relative to the inbound and outbound paths above. They observe — they do not rewrite a frame.

| Hook | Fires | Relative to the paths |
|---|---|---|
| `init` | once at startup, before any connection | Before everything. Plugin `init` first, then the app's. |
| `connect` | each connection opens | After upgrade + auto-rejoin, before that socket's first inbound frame. Plugin `connect` first, then the app's. |
| `disconnect` | each connection closes | After the socket's last frame. App `disconnect` first, then plugins in reverse. |
| `error` | a handler / intercept throws an unhandled error | During the inbound path, when the handler or an intercept throws. Also where `DeferExhausted` surfaces. |
| `validationError` | an incoming payload fails its schema | During the inbound path, at the validation step, instead of the handler. |
| `shutdown` | once when the server stops | After all connections' last frames. App `shutdown` first, then plugins in reverse. |

The full hook reference — `ctx` shapes, arguments, error isolation — is in [Lifecycle Hooks](/server/lifecycle-and-intercept/hooks).

::note
The lifecycle hooks follow the same nested order as the per-frame hooks. **Inbound** milestones (`init`, `connect`) run plugins **before** the app, so a plugin sees the connection first. **Outbound** milestones (`disconnect`, `shutdown`) run the app **first**, then plugins in **reverse** registration order, so a plugin tears down after the app that depended on it.
::

## Plugins and channels in the order

Two scoping rules govern where plugin and channel work slots into the paths above.

### Plugins — nested order

A plugin's hooks run around the app's, never replacing them:

- **Inbound milestones** (`upgrade`, `init`, `connect`) — plugin hooks run **first**, in registration order, then the app's.
- **Outbound milestones** (`disconnect`, `shutdown`) — the app runs **first**, then plugins in **reverse** registration order.
- **Per-frame hooks** (`intercept`, `outgoing`) — a plugin's hook runs only for **its own** frames, unless it was granted host observation. An app hook always runs for every frame. Frame ownership is read from the event name and exposed as `frame.owner`. See [Plugins · Observe host](/server/plugins/observe-host).

### Channels — scope nesting

A channel's per-frame hooks nest **inside** the top-level ones for a channel-scoped frame:

- **Inbound** — the top-level `intercept` runs, then the channel `intercept`. Both share the one per-frame locals store.
- **A channel's own handler** is the single handler step — there is no separate "channel handler" phase; the channel's `on` / `request` / `stream` is what the [handler step](#handler) routes to when the frame is channel-scoped.

### Primitives and capabilities vs plugin ordering

Within one scope (the app, or one plugin, or one channel), the framework's built-in capabilities slot into the **fixed** points named above — `dedup()` at the inbound pre-check, `sequence()` and `dedup()` at the outbound `__wskit` stamp, `replay` at the record step. They are not ordered relative to each other by registration; each owns a fixed seam in the pipeline. **Plugin ordering** (the nested order above) only governs hooks that share a seam across the app and its plugins — `upgrade`, `init`, `connect`, `disconnect`, `shutdown`, `intercept`, and `outgoing`.

## Full picture

One channel-scoped `say` frame, on a server with one plugin, `intercepts()`, and strict replay:

```text
── connection opens ──────────────────────────────
upgrade:   plugin → app          (identity, meta, tags merged)
auto-rejoin persistent channels
connect:   plugin → app

── say arrives (channel-scoped) ──────────────────
parse + pre-checks (dedup)
channel membership gate
intercept:  top-level → channel   (rewrite / Block)
validate:   channel handler's schema
handler:    room.on('say') runs
   └─ ctx.channel.broadcast('said', ...)
        ── outbound, per recipient ──────────────
        outgoing hook            (rewrite / Block)
        declaration check
        __wskit stamps           (seq, messageId, channel)
        replay record (strict)   ← before send
        serialize → wire

── connection closes ─────────────────────────────
disconnect: app → plugin (reverse)
```
