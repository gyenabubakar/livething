Receipts answer two questions about a message: **who received it** and **who read it**. Many chat apps show these as ticks: a grey double tick for "received" and a blue tick for "read". In LiveThing, each question belongs to its own capability. `inbox()` handles "received". `readReceipts()` handles "read".

Inbox already tracks each member's delivery acknowledgement. So the received data needs no extra setup. Sending it live to other members is an opt-in flag. Read receipts are a small, separate capability that you add on top of inbox. This page covers both, the live `__received__` and `__read__` updates they send, the member limit on those updates, and how a client can ask the server for receipts at any time.

## Received receipts: always tracked, live updates are opt-in

Every inbox channel keeps a **received cursor** for each member. A cursor is one sequence number: the highest message sequence that the member has acknowledged. Everything at or below that number has arrived. See [Delivery and acknowledgements](/server/inbox/delivery) for how the client sends these acknowledgements. The cursor needs no extra setup. You get it as soon as the channel has inbox.

You can read that cursor in two ways:

- **On the server**, `ctx.channel.inbox.receiversOf(seq)` returns the user IDs whose received cursor has reached `seq`. This works on any inbox channel, with no opt-in.
- **On the clients**, when a member's cursor moves forward, the server can send a `__received__` frame with `{ userId, receivedThrough }` to the channel's connected members. This is a live update. A client can use it to show "Bob has received everything up to here." It is **off by default**. Turn it on with `broadcastReceipts: true` in the channel's `inbox(...)` options.

::note
**An anonymous connection never appears in `receiversOf` or `readersOf`.** Both cursors are stored by the member's `userId` (see [Requirements](/server/inbox/overview#requirements)). A connection with no `userId` has no cursor to move. This happens when the server has no `upgrade` hook, or when the hook returns no `userId`. The server ignores this connection's acknowledgements without an error, and the connection still gets messages live. But it never gets a stored receipt, so it does not appear in either query or in either live update.
::

Here `dms` also sets `broadcastReceipts: true`, which Huddle's `dms` does not.

```typescript [server/dms.ts]
import { emits, t } from '@livething/server'
import { inbox } from '@livething/server/inbox'
import { base, Message } from './base'

const dms = base.channel(['dms', 'dm:{pair}'], {
  membership: 'persistent',
  capabilities: [
    inbox({ broadcastReceipts: true }), // send the grey double tick live to members
    emits({ message: t<Message>() }),
  ],
})
```

With `broadcastReceipts` on, the server sends this frame to the channel when Bob's received cursor moves to 7:

```json
[
  "__received__",
  { "userId": "bob", "receivedThrough": 7 },
  { "channel": { "name": "dm:alice+bob", "family": "dms" } }
]
```

This is the same `__received__` event name that a client uses to acknowledge delivery. The two directions carry different payloads. From client to server, it carries only the sender's own cursor (`receivedThrough`). From server to clients, it also names the member whose cursor moved (`userId`). Inbox handles both directions.

## Read receipts: the opt-in `readReceipts()` capability

A member _receiving_ a message is not the same as _reading_ it. Read receipts track the blue tick: who has actually seen the message. This is a separate `readReceipts()` capability. Like `inbox()`, it works only on channels. List it next to `inbox()` in the channel's own `capabilities`. You can pass `{ maxReceiptAudience }` to it (see [the member limit](#the-live-updates-and-their-member-limit) below).

This is the `dms` channel of Huddle, written out in full:

```typescript [server/dms.ts]
import { emits, t } from '@livething/server'
import { inbox, readReceipts } from '@livething/server/inbox'
import { base, Message } from './base'

const dms = base.channel(['dms', 'dm:{pair}'], {
  membership: 'persistent',
  capabilities: [
    inbox(),
    readReceipts(),
    emits({ message: t<Message>() }),
  ],
})
```

::note
`readReceipts()` requires `inbox()` in the same channel's `capabilities`. It also requires what inbox requires on the server, such as `sequence({ persist: true })`. Without them there is nowhere to store the read cursor, so LiveThing throws an error before the server starts if `readReceipts()` is used alone. See [Requirements](/server/capabilities/read-receipts#requirements-needs-inbox) on the capability page.
::

The client moves its read cursor forward with `markAsRead()`. This sends a `__read__` frame:

```json
[
  "__read__",
  { "readThrough": 7 },
  { "channel": { "name": "dm:alice+bob", "family": "dms" } }
]
```

The server stores the new read cursor. Then it sends a `__read__` frame to the channel. This frame carries `readThrough` and the member's `userId`:

```json
[
  "__read__",
  { "userId": "bob", "readThrough": 7 },
  { "channel": { "name": "dm:alice+bob", "family": "dms" } }
]
```

On the server, `ctx.channel.readReceipts.readersOf(seq)` returns the user IDs whose read cursor has reached `seq`.

::tip
**Read means received too.** A member cannot read a message they never received. So a `__read__` frame also moves that member's received cursor up to the read mark, if it is lower, and settles their held inbox rows up to that mark, the same way a `__received__` does. This is rare, because the client acknowledges "received" first. When it does happen and the channel has `broadcastReceipts` on, the server also sends a `__received__` update, so the received data stays correct.
::

## Asking for a cursor from a handler

Inside a `dms` handler, you query both cursors through `ctx.channel`, with its `inbox` and `readReceipts` properties. They are typed and always present here, because `dms` lists both `inbox()` and `readReceipts()` in its own `capabilities`. In this example, one handler answers a question about either cursor. It sends the server's stored answer back as its own event. This does not depend on the live updates:

```typescript [server/dms.ts]
import * as v from 'valibot'
import { dms } from './base'

const AskCursor = v.object({
  kind: v.picklist(['received', 'read']),
  seq: v.number(),
})

export const handleAskCursor = dms.on('ask-cursor', {
  input: AskCursor,
  run(ctx, input) {
    const userIds =
      input.kind === 'read'
        ? ctx.channel.readReceipts.readersOf(input.seq)
        : ctx.channel.inbox.receiversOf(input.seq)
    ctx.send('cursor-answer', {
      kind: input.kind,
      seq: input.seq,
      userIds,
    })
  },
})
```

Use this "ask, then answer" pattern when you need a correct answer. A client can miss a live update (for example, while it is offline), and big channels send no live updates at all. `receiversOf` and `readersOf` read the stored cursors directly, so their answer is always up to date.

::note
`ctx.channel.readReceipts` (like `ctx.channel.inbox`) exists in `dms.on(...)` handlers and in the `onSubscribe`, `onUnsubscribe`, and `onSessionEnd` hooks. Write each of those below `capabilities` in the channel's config object. It does **not** exist in `check`, `commit`, or `revalidate`. At runtime, handles returned by `ctx.channels.get(...)` also have no `readReceipts()` method during those three hooks. See [Auth Gate](/server/channels/auth-gate).
::

## The client side

On the client, the [`inbox()`](/client/primitives/inbox) and [`readReceipts()`](/client/primitives/read-receipts) primitives each add **their own** methods to a channel handle, when the channel's contract has the matching flag. There is no shared receipts store. A `dms` channel with `inbox: true` gets `receivers`, `onReceived` and `receiversOf`. Adding `readReceipts: true` also gives it `readers`, `onRead`, `markAsRead` and `readersOf`. This is a smaller version of Huddle's `client/socket.ts`, with only the primitives that receipts need.

```typescript [client/socket.ts]
import {
  binary,
  channels,
  client,
  connect,
  dedup,
  inbox,
  readReceipts,
  reconnection,
} from '@livething/client'
import { renderReceipt } from './huddle-ui'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://huddle.example.com/huddle'),
  binary(),
  channels(),
  inbox(),
  readReceipts(),
  dedup(),
  reconnection(),
)

const dm = socket.channel('dms', 'dm:alice+bob')
await dm.subscribe()

// Two live stores, one for each capability. Each holds a Map<userId, cursor>.
dm.receivers.subscribe(() => {
  for (const [userId, receivedThrough] of dm.receivers.get()) {
    renderReceipt(userId, { received: receivedThrough })
  }
})
dm.readers.subscribe(() => {
  for (const [userId, readThrough] of dm.readers.get()) {
    renderReceipt(userId, { read: readThrough })
  }
})

// Move the read cursor forward to cover everything received so far.
dm.markAsRead()

// Ask the server who has reached seq 1 on each cursor.
const receivedBy = await dm.receiversOf(1)
const readBy = await dm.readersOf(1)
```

`renderReceipt` stands for Huddle's own UI code. `dm.receivers` and `dm.readers` are readable stores. Each holds a `Map<userId, number>`, with one entry per member. A member whose cursor is still `0` is not in the map. `receivers` updates from `__received__` frames, which the server sends only when the channel has `broadcastReceipts` on. `readers` updates from `__read__` frames. `markAsRead()` with no argument marks everything received so far as read. `receiversOf(seq)` and `readersOf(seq)` send a query to the server (see the last section of this page) and resolve to a list of user IDs. The [client inbox primitive](/client/primitives/inbox#the-received-surface) and [read receipts primitive](/client/primitives/read-receipts) pages cover them in full.

## The live updates and their member limit

The received and read updates are live. Every time a member's cursor moves, the server sends an update to the channel's connected members. (The received update is sent only when the channel turns on `broadcastReceipts`. The read update always comes with `readReceipts()`.) This works well for small channels. But the cost grows with the square of the member count, written **O(members²)**. With N members, one message can cause N acknowledgements, and each one is sent to N members. On a large channel, that is a lot of frames.

So `maxReceiptAudience` limits the live updates. The default is 256. Both `inbox()` and `readReceipts()` accept it for each channel:

A large room (rather than a two-person `dms` channel) is where this limit matters most. Here `rooms` is a different version from Huddle's: it is persistent, and it uses inbox and read receipts.

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { inbox, readReceipts } from '@livething/server/inbox'
import { base, Message } from './base'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  membership: 'persistent',
  capabilities: [
    inbox({ broadcastReceipts: true, maxReceiptAudience: 100 }),
    readReceipts({ maxReceiptAudience: 100 }),
    emits({ message: t<Message>() }),
  ],
})
```

While the channel has **at most** `maxReceiptAudience` connected members, the server sends `__received__` and `__read__` updates live. Each open connection counts as one member here. Above the limit, the server stops sending live updates, but it **still stores** the cursors. You lose only the live updates. You can still ask who received or read a message with `receiversOf` and `readersOf` on the server, or `dm.receiversOf(seq)` and `dm.readersOf(seq)` on a client channel handle. For a big room, use these queries.

## The query frames: `__receivedQuery__` and `__readQuery__`

`receiversOf` sends a `__receivedQuery__` frame, and `readersOf` sends a `__readQuery__` frame. The request and its reply use the same event name. An `exchange.id` connects them, the same way a normal request and its reply are connected. The request names a `seq`. The reply repeats the `exchange.id` and lists the user IDs. Each query belongs to its own capability. So `receiversOf` works with `inbox()` alone. It does not need `readReceipts()`.

```json
// client -> server
["__receivedQuery__", { "seq": 7 }, { "channel": { "name": "room:general", "family": "rooms" }, "exchange": { "id": "q-1" } }]

// server -> client
["__receivedQuery__", { "userIds": ["bob"] }, { "channel": { "name": "room:general", "family": "rooms" }, "exchange": { "id": "q-1" } }]
```

::warning
**Only a member may ask.** If a connection is not a current member of the channel, the server **drops** its `__receivedQuery__` or `__readQuery__` without any reply. The server also ignores a `__read__` or `__received__` from a non-member, so it moves no cursor and sends no update. Because every receipt frame requires membership, a connection outside the channel cannot find out who read what.
::
