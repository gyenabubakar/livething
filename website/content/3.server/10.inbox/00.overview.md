[Replay](/server/replay/overview) is best-effort catch-up for a **place**. A channel keeps one shared log, and a reconnecting client asks for the part it missed. **Inbox** is guaranteed delivery to each **recipient**. Every member who receives a broadcast gets their own stored copy. The server keeps that copy until the member's client confirms that the message arrived. This works even if the member was offline when the message was sent. Like a normal channel broadcast, inbox skips the sender by default. Pass `{ includeSelf: true }` to include the sender.

The difference is who owns the message. Replay stores one shared history per channel and sends whatever part a client asks for. If a client never asks, it never catches up. Inbox writes one row **per member** on every broadcast. It keeps each member's row until that member **acknowledges** it. No message is lost because a member was away. (The only exception is a channel with a `retention` limit, described [below](#the-storage-model).)

## Inbox vs replay

Both help a client that lost its connection, but they make different promises. You can use either one, or both on the same channel.

|                               | Replay                           | Inbox                                 |
| ----------------------------- | -------------------------------- | ------------------------------------- |
| Belongs to                    | the channel (a place)            | each member (a person)                |
| Stores                        | one shared log                   | one copy per member                   |
| Catch-up                      | best-effort: the client must ask | guaranteed: kept until acknowledged   |
| Delivery to an offline member | only if they reconnect and ask   | sent again automatically on reconnect |
| Cost                          | one row per message              | one row per message **per member**    |

Use **replay** when your app still works if a message is missed: a feed, presence, the latest state of a document. Use **inbox** when every recipient must see every message: direct messages, a task assigned to one person, an order that must not be lost.

## How it works

Inbox is [**fan-out on write**](/learn/reliability#fan-out-on-read-vs-fan-out-on-write). This means the server makes the copies when the message is sent, not later when a member asks. When a handler broadcasts to an inbox channel, the server writes a stored row into the **queue** of every current member who should receive it. This includes members who are offline. Members who are connected also get the message live.

The sender does not get a row by default, because a channel broadcast skips the sending connection. If the sender has another connection in the same channel (for example, a second device), that user still gets a row. Pass `{ includeSelf: true }` to include the sending connection too.

Each row stays in the queue until its member sends a `__received__` acknowledgement. The client's [`inbox()` primitive](/client/primitives/inbox) sends it for you. The row is then **settled**. The server then deletes it.

A member who was offline when the message was sent still has their rows waiting. When that member reconnects, the server adds them back to the channel and **drains** their queue: it sends the waiting rows again, in order. A row can reach the client twice: once live, and again in the drain. The `dedup()` primitive on the client drops the second copy, so your code handles each message only once.

A broadcast gets **one** delivery sequence number and **one** delivery ID. Every recipient gets the same pair. Each member's stored row carries that same pair, so the row matches the live message the member may also have received. On the client, the inbox primitive uses `metadata.delivery.seq` to know what to acknowledge, and `dedup()` uses `metadata.delivery.id` to find duplicates. A drained copy of a message the client already saw live is dropped.

Here is the `dms` channel of Huddle in a smaller form, with only `inbox()` and `message`. Huddle's `dms` also lists `readReceipts()`.

```typescript [server/dms.ts]
import { emits, t } from '@livething/server'
import { inbox } from '@livething/server/inbox'
import * as v from 'valibot'
import { base, Message } from './base'

// A channel with inbox listed in its own capabilities: every broadcast writes
// one stored row per member.
const dms = base.channel(['dms', 'dm:{pair}'], {
  membership: 'persistent',
  capabilities: [inbox(), emits({ message: t<Message>() })],
})

export const handleSendMessage = dms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: payload.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

`base` is the Huddle server with its [`upgrade` hook](/server/server/upgrade), `channels()`, `sequence({ persist: true })` and `dedup()`.

The handler does not mention inbox. You broadcast as usual, and the server turns each broadcast into a stored delivery for each member.

## The storage model

Inbox keeps three kinds of stored data. All of it is in the server's own SQL storage, which every adapter provides, so you do not need to turn anything on for it.

Inbox stores this data by **user ID**, not by connection. An **anonymous** connection is one with no `userId`. It has no stored data, as the [Requirements](#requirements) section explains.

::field-group
::field{name="One queue per member, per channel"}
Because inbox is fan-out on write, each member has their own stored copy. Every broadcast adds one row to each current member's queue for that channel. A row holds the delivery sequence number, the delivery ID, the event name, and the payload. For a [binary event](#binary-events), the payload is the info, and the row holds the bytes too. The drain on reconnect reads from this queue.
::

::field{name="A received cursor and a read cursor, per member"}
A **cursor** is a stored sequence number that marks how far a member has got. Each member has two cursors per channel: how far they have acknowledged **receiving**, and how far they have marked as **read**. Each cursor is a **high-water mark**: it records the highest sequence number reached and covers everything below it. A `__received__` or `__read__` acknowledgement moves the cursor forward and settles every queued row at or below that number in one step. The read cursor can never be ahead of the received cursor: marking a message as read also marks it as received. [`receiversOf` / `readersOf`](/server/inbox/receipts) read these cursors. An anonymous connection has no cursors.
::

::field{name="An overflow watermark, per member"}
A channel can set a `retention` limit on each member's queue: a maximum number of rows, a maximum age, a maximum number of bytes, or any of them together. When the limit is reached, the server deletes the member's oldest rows. These rows were not delivered yet, so the server stores the highest sequence number among them as the member's **overflow watermark**. On the member's next drain, the watermark becomes a [`__gap__` signal](/server/inbox/overflow-and-gap). A member with no deleted rows has no watermark and gets no gap signal.
::
::

An anonymous connection gets messages live while it is connected. It has no queue, so it gets no drain after a reconnect and no delivery guarantee.

## The cost on wake

On Cloudflare, a Durable Object can use [hibernation](/server/server/hibernation). The object is removed from memory while its WebSockets stay open, and the stored data stays too. What was only in memory is built again. The next message or event starts it again (this is a **wake**). Inbox can only make its guarantee if the server always knows who is a member of each channel. This includes members whose socket has sent nothing since the last wake. So on the **first** start after the object was removed from memory, LiveThing restores the channel membership of **every** open socket at once. It does not wait for each socket's next message.

::warning
This is the cost of the guarantee. The restore does work in proportion to the **number of open sockets**, once per wake. Without it, a broadcast or inbox fan-out sent right after a wake would miss members that had not sent anything since the wake. A missed member breaks the guarantee. Runtimes without hibernation never remove the object from memory this way, so they do not pay this cost.
::

You do not call anything for this. It happens automatically on an adapter that uses [hibernation](/server/server/hibernation). Keep it in mind when you think about the wake cost of a busy channel.

## What you turn on, and what you get

Inbox is a **channel** feature. You list `inbox()` inside a channel's own `capabilities`, with an optional config object. One part is always on, and two parts are optional:

- **[Guaranteed delivery](/server/inbox/delivery)**: rows are kept until acknowledged, as described above. This is always on for an inbox channel.
- **[Delivered receipts](/server/inbox/receipts)**: inbox always stores each member's acknowledgement, so `receiversOf` can always tell you who has received messages up to which sequence number. Sending that information live to the other members is optional. Turn it on with `inbox({ broadcastReceipts: true })`.
- **[Read receipts](/server/inbox/receipts)**: who has _seen_ a message, not only received it. This is a separate `readReceipts()` capability that you add to the channel.

A channel can set a `retention` limit on the rows it keeps per member. If a member falls behind that limit, their oldest rows are deleted. When the member reconnects, the server tells them that [some messages are missing](/server/inbox/overflow-and-gap).

### Binary events

A channel with `inbox()` can list [binary events](/server/binary/overview) in its `capabilities`. Each member's row then holds the info and the bytes, and the drain sends it as one binary frame, with the same channel and delivery metadata as the live frame. Binary and JSON rows share one sequence order, so the drain sends them mixed, in that order. Huddle's `dms` channel sends voice notes this way:

```typescript [server/voice-notes.ts]
import * as v from 'valibot'
import { dms } from './base'

export const handleSendVoiceNote = dms.binary.on('send-voice-note', {
  input: v.object({ durationMs: v.number() }),
  maxBytes: 1024 * 1024,
  run(ctx, input, bytes) {
    ctx.channel.binary.broadcast(
      'voice-note',
      { from: ctx.user.id, durationMs: input.durationMs },
      bytes,
    )
  },
})
```

A member who is away when Amara sends a voice note gets it when they come back, with every byte. The acknowledgement, the receipts and `retention` work the same as for JSON rows. To seed a member's inbox with binary messages, use [`ctx.channel.inbox.binary.backfill(...)`](/server/inbox/delivery#backfilling-binary-messages).

A few binary messages can take more room than thousands of JSON ones. So a channel that lists binary events gets `retention.maxBytes` of **64 MiB** for each member when it sets none, the same default as replay. Over it, the member's oldest rows are deleted, and the member gets a [`__gap__`](/server/inbox/overflow-and-gap). Set your own `maxBytes` to change it. A channel with no binary events keeps no default limit: an inbox promises delivery, and a limit drops owed messages.

One rule is different from replay. Replay is best-effort, so it sends a message live even when it cannot store it. An inbox promises every member every message, so a message it **cannot store goes to nobody**, also not to the members who are online. Sending it live only would break the promise with no sign. A message cannot be stored when:

- it is bigger than one row of the adapter's SQL storage (8 MB on Cloudflare),
- it is bigger than the adapter's send limit, so it could never be sent again, or
- it alone is bigger than the channel's `retention.maxBytes`.

The server logs an error that names the event and the limit, once for each event and limit. This applies to JSON messages too, but a JSON message is rarely that big. Keep each binary message well under the row limit. To send a file that is bigger, store it yourself (for example in object storage), and send an inbox message with a link to it.

## Requirements

Inbox stores a copy for each member, so the channel needs **persistent membership** and the server needs three other capabilities. Persistent membership (the Channels pages also call it **durable membership**) means the server stores who is in the channel, and adds a returning user back after a reconnect. Channels are ephemeral by default, so set `membership: 'persistent'` on an inbox channel. An inbox channel without it fails when the server starts, because it has no stored member list to write rows for or to add members back from.

If you leave out one of the required capabilities, `assemble()` throws an error. `sequence()` is different: any `sequence()` passes the `assemble()` check, but inbox also needs `persist: true` on it. The server checks that later, when it starts. The [`inbox` capability page](/server/capabilities/inbox) has the full requirements and configuration reference.

| Requirement                                                    | Why it's required                                                                                                                                                |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`channels()`](/server/capabilities/channels)                  | Inbox works inside a channel. It delivers to the channel's members.                                                                                              |
| `membership: 'persistent'`                                     | Inbox needs a stored member list to write rows for offline members and to drain after a reconnect. An ephemeral channel (the default) fails at startup.          |
| [`sequence({ persist: true })`](/server/capabilities/sequence) | Rows are ordered and settled by sequence number, which must stay the same after a server restart. A plain `sequence()` passes `assemble()` but fails at startup. |
| [`dedup()`](/server/capabilities/dedup)                        | The drain after a reconnect sends stored rows again. `dedup()` drops the ones the client already got live.                                                       |

::note
Inbox delivers to a **member's user ID**, so members need a stable `userId`. Set it in `upgrade` (here `verifySession` does this). An anonymous connection with no `userId` still gets messages live while it is connected. It has no stored queue, so it gets no drain after a reconnect and no delivery guarantee.
::

The `inbox()` and `readReceipts()` option reference is on the [`inbox` capability page](/server/capabilities/inbox) and the [`readReceipts` capability page](/server/capabilities/read-receipts).
