Replay is best-effort catch-up on a **place**: a channel keeps a shared log, and a reconnecting client asks for the tail it missed. **Inbox** is guaranteed delivery to each eligible **recipient**: every member who receives a broadcast gets a durable copy, held until that member confirms it arrived — even if they were offline when it was sent. The sender is excluded by default, like a normal channel broadcast; pass `{ includeSelf: true }` to include the sender.

The difference is who the message belongs to. Replay stores one shared history per channel and hands out whatever slice a client asks for; if a client never asks, it never catches up. Inbox writes one row **per member** on every broadcast and keeps each member's row until that member acknowledges it. Nothing is dropped because someone happened to be away.

## Inbox vs replay

Both fill the gap a dropped socket leaves, but they make different promises. You can run either, or both on the same channel.

|                               | Replay                            | Inbox                                |
| ----------------------------- | --------------------------------- | ------------------------------------ |
| Belongs to                    | the channel (a place)             | each member (a person)               |
| Stores                        | one shared log                    | one copy per member                  |
| Catch-up                      | best-effort — the client must ask | guaranteed — held until acknowledged |
| Delivery to an offline member | only if they reconnect and ask    | drained automatically on reconnect   |
| Cost                          | one row per message               | one row per message **per member**   |

Reach for **replay** when missing a message is survivable — a feed, presence, a document's latest state. Reach for **inbox** when every eligible recipient must see every message — direct messages, a task assigned to one person, an order that must not be lost.

## How it works

Inbox is [**fan-out on write**](/learn/reliability#fan-out-on-read-vs-fan-out-on-write). When a handler broadcasts to an inbox channel, the engine writes a durable row to every eligible current member's queue as the message goes out. Each eligible member also gets the message live if connected. The sender is not eligible by default because channel broadcasts exclude the sending connection; `{ includeSelf: true }` includes that sender too. Each held row stays until its member sends a `__received__` acknowledgement, at which point it is settled and dropped. A member who was offline at broadcast time still has their rows waiting: on reconnect the client auto-rejoins the channel and the server **drains** the held rows, re-delivering them in order. `dedup` on the client suppresses any that also arrived live, so nothing is processed twice.

A broadcast gets **one** delivery sequence and **one** delivery ID shared by every recipient. Each member's queued row carries that same pair, so a member's inbox row matches the live frame it also received: the client orders by `metadata.delivery.seq` and de-duplicates by `metadata.delivery.id`, and a drained copy of something already seen live is discarded rather than processed twice.

```typescript [inbox-server.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { dedup } from '@livething/server/dedup'
import { inbox } from '@livething/server/inbox'
import { sequence } from '@livething/server/sequence'
import * as v from 'valibot'

const base = server({
  upgrade: (request) => requireUsername(request),
  capabilities: [channels(), sequence({ persist: true }), dedup()],
})

// A channel with inbox listed in its own capabilities: every broadcast writes
// one held row per member.
const chat = base.channel('chat', {
  capabilities: [
    inbox(),
    emits({ 'room-msg': t<{ text: string; from: string }>() }),
  ],
})

export const handleSend = chat.on('send-room-msg', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('room-msg', {
      text: payload.text,
      from: ctx.meta.username,
    })
  },
})
```

Nothing in the handler mentions inbox. You broadcast as usual; the engine turns each broadcast into a durable per-member delivery.

## The storage model

Inbox keeps three durable structures, all in the server's own SQL storage — storage every adapter guarantees, so nothing needs to be turned on for it.

::field-group
::field{name="One queue per member, per channel"}
Fan-out on write means the durable copy is per member: every broadcast appends one row to each current member's queue for that channel. A row carries the delivery sequence, delivery ID, event, and payload. This is the store the reconnect drain reads back.
::

::field{name="A received cursor and a read cursor, per member"}
Each member has one cursor pair per channel: how far they have acknowledged **receiving**, and how far they have marked **read**. Both are cumulative high-water marks — a `__received__` or `__read__` ack advances them and settles every queued row at or below the mark in one shot. Read can never run ahead of received. These cursors are what [`receiversOf` / `readersOf`](/server/inbox/receipts) read. An anonymous connection gets no cursor row either, for the same reason it gets no queue: both are keyed on a stable `userId`.
::

::field{name="An overflow watermark, per member"}
When a bounded queue evicts a member's oldest undelivered row, the engine records the sequence it dropped as that member's overflow watermark. On the member's next drain it becomes a [`__gap__` signal](/server/inbox/overflow-and-gap); a member with no eviction has no watermark and gets no gap.
::
::

An anonymous connection — one with no stable `userId` — has no place in this model: it gets messages live while connected but no queue, so no offline drain and no guarantee. See [Requirements](#requirements).

## The cost on wake

Under Cloudflare's Durable Object [hibernation](/server/server/hibernation), the object is evicted from memory while its WebSockets stay open at the edge. The guarantee depends on the server knowing, at all times, who is a member of each channel — even for a member whose own socket has been silent since the last wake. So on the **first** boot after an eviction, LiveThing restores **every** surviving socket's channel membership up front, rather than lazily on each socket's next message.

::warning
This is the price of the guarantee, and it is real: the restore does work proportional to the **number of surviving sockets**, once per wake. Without it, a broadcast or inbox fan-out fired right after a wake would miss members that had not sent anything since the wake — and a missed member breaks the promise. Non-hibernation runtimes never evict this way and pay nothing here.
::

You do not call anything to get this — it is automatic on a hibernating adapter. It is worth knowing about when you reason about a busy channel's wake cost. See [Hibernation](/server/server/hibernation) for what survives an eviction and what is rebuilt.

## What you turn on, and what you get

Inbox is a **channel** feature — `inbox()` is listed inside a channel's own `capabilities`, optionally with a config object. One thing is always on, and two are opt-in:

- **Guaranteed delivery** — the held-until-acknowledged behaviour above. Always on for an inbox channel. See [Delivery and acknowledgements](/server/inbox/delivery).
- **Delivered receipts** (the double-grey check) — inbox always tracks each member's acknowledgement, so `receiversOf` can tell you who has received up to which message with no opt-in. Pushing that live to the other members as a tick is opt-in, with `broadcastReceipts: true`. See [Receipts](/server/inbox/receipts).
- **Read receipts** (the blue check) — who has _seen_ a message, not just received it. This is a separate `readReceipts()` capability a channel opts into. See [Receipts](/server/inbox/receipts).

If a channel bounds how many held rows it keeps per member and a member falls behind, the oldest rows are evicted — and the member is told, on reconnect, that there is a hole. See [Overflow and the gap signal](/server/inbox/overflow-and-gap).

## Requirements

Inbox is durable per-member delivery, so the channel must use `membership: 'persistent'` and the host needs three other capabilities. An inbox channel with ephemeral membership fails validation at server startup because it has no durable member roster to fan out to or auto-rejoin. Leaving a host capability out entirely fails at `assemble()`; `sequence()` is a special case — listing it at all satisfies `assemble()`, but inbox also needs `persist: true` on it, which is checked one step later, at server startup. The full requirements and configuration reference lives on the [`inbox` capability page](/server/capabilities/inbox):

| Capability                                                     | Why it's required                                                                                                                                 |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`channels()`](/server/capabilities/channels)                  | Inbox is channel-scoped — it delivers to a channel's members.                                                                                     |
| `membership: 'persistent'`                                     | Inbox needs a durable member roster for offline fan-out and reconnect drain; an ephemeral inbox channel is rejected at startup.                   |
| [`sequence({ persist: true })`](/server/capabilities/sequence) | Held rows order and settle by sequence number, which must survive a restart. A plain `sequence()` passes `assemble()` but is rejected at startup. |
| [`dedup()`](/server/capabilities/dedup)                        | The reconnect drain re-delivers held rows; dedup drops any the client already saw live.                                                           |

::note
Inbox delivers to a **member's user id**, so members need a stable `userId` — set one on upgrade (here `requireUsername`). An anonymous connection with no `userId` still gets messages live while it is connected, but has no durable queue, so it gets no offline drain and no guaranteed delivery.
::
