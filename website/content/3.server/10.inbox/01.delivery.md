Inbox makes one promise: every eligible member gets every message, including the messages sent while they were offline. Three parts keep this promise, and this page explains each one:

1. A **row** (one saved copy of a message in the database) is written for each member on every broadcast.
2. The client sends a `__received__` **acknowledgement** (a short message that says "I got it"), and this settles the row.
3. When a member reconnects, the server **drains** their queue: it sends again every row that the member did not acknowledge.

The [Overview](/server/inbox/overview) compares inbox with replay and explains the storage model. This page covers how delivery works.

## One row per member, kept until acknowledged

When a handler broadcasts to an inbox channel, LiveThing writes a durable row (a row stored in the database, so it survives a disconnect or a restart) into the queue of **every eligible current member** while the message goes out. This is called [**fan-out on write**](/learn/reliability#fan-out-on-read-vs-fan-out-on-write). Members who are connected also get the message live, at the same time. Each row stays in that member's queue until the member sends a `__received__` acknowledgement for it. At that point the row is _settled_, and the server deletes it.

`ctx.channel.broadcast(...)` skips the sending connection by default, the same as a plain channel broadcast. The sender's user gets no row for their own message when the sending connection is that user's only connection in the channel. If the same user is also in the channel from another connection (for example, a second browser tab), that user still gets a row, because the other connection receives the message live. Pass `{ includeSelf: true }` to treat the sender like any other member.

Your handler code does not change. You broadcast as usual, and LiveThing turns each broadcast into a durable delivery for each member. Here is a smaller `dms` than Huddle's, with only `inbox()` and `message`:

```typescript [server/dms.ts]
import { emits, t } from '@livething/server'
import { inbox } from '@livething/server/inbox'
import * as v from 'valibot'
import { base, Message } from './base'

// inbox() is in this channel's own capabilities, so every broadcast writes
// one row for each member.
const dms = base.channel(['dms', 'dm:{pair}'], {
  membership: 'persistent',
  capabilities: [inbox(), emits({ message: t<Message>() })],
})

export const handleSendMessage = dms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: payload.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

Add `handleSendMessage` to `base.assemble({ handlers: [...] })` to turn on this route. If you pass only `dms`, the app gets the channel's inbox settings and lifecycle hooks, but not the `send-message` handler.

::note
Inbox delivers to a **member's user ID**, so each member needs a stable `userId`. Set one in the upgrade step (Huddle's `upgrade` hook returns `user.id`). An anonymous connection (one with no `userId`) still gets messages live while it is connected. It has no durable queue, so it gets no drain after a reconnect and no delivery guarantee. See the [Overview requirements](/server/inbox/overview#requirements) for the full list.
::

## The client acknowledges for you

You do not write the `__received__` acknowledgement yourself. The [client `inbox()` primitive](/client/primitives/inbox) tracks the highest sequence number it has seen on each inbox channel and sends `__received__` automatically. The client knows which channels use inbox from the `__subscribeOk__` confirmation: for an inbox channel, that frame carries `metadata.channel.inbox: true`.

The acknowledgement is a channel-scoped frame (one WebSocket message that belongs to one channel):

```json
[
  "__received__",
  { "receivedThrough": 7 },
  { "channel": { "name": "dm:alice+bob", "family": "dms" } }
]
```

`receivedThrough` is a sequence number. It means "I have every message on this channel up to and including number 7." This one value is a **cursor** (a saved position in the message list). It settles every row at or below that number in one step.

For a dynamic channel family, "this channel" means the family key plus the concrete channel name. For example, `rooms` at `room:general` is a different inbox scope from `rooms` at `room:design`, even though both come from the same family declaration. A static channel has no family key. The client sends both values in the channel routing metadata, so an acknowledgement for one room never settles rows in another room. [`gaps()`](/client/primitives/gaps) uses the same identity rule for gap frames.

The client also **sends its acknowledgement again on reconnect**. When the socket reconnects and the client joins the channel again, it sends its highest cursor again. So if a member acknowledged messages just before the connection dropped, the server does not send those rows again.

## The reconnect drain

A member who was offline during a broadcast still has their rows waiting. On reconnect, [durable membership](/server/channels/membership-and-presence) joins the member to the channel again automatically. Then LiveThing **drains** the queue: it sends the waiting rows again, in order, and each row keeps its original sequence number.

The drain reads the rows a page at a time, so a member with many rows (or large binary ones) does not fill the server's memory. When the socket's buffer is full, the drain waits for it to empty, the same way a [replay catch-up](/server/replay/overview) does. While it waits, the live messages of that member's inbox channels wait too, and go out after the last stored row, so the order stays the same. A member whose client reads nothing for about 50 seconds is closed with `1013`, and the next drain starts again from the first row they have not acknowledged. The drain does not hold up the connection's other work: its messages, heartbeats and `onConnect` go on while it waits.

A drained row can repeat a message that the member already saw live before the socket dropped. The client [`dedup()`](/client/primitives/dedup) primitive removes these repeats by message ID, so your `on()` handlers run once for each message. The server needs [`dedup()`](/server/capabilities/dedup) too, because it gives each message the ID that the client checks. This is why inbox requires `dedup()`.

Here is the offline path from start to end:

::steps{level="3"}

### Both members subscribe

Alice and Bob both subscribe to their `dm:alice+bob` channel. Both now have durable memberships, which stay after a socket drops.

### Alice's socket drops

Alice goes offline. Her membership stays. Only her connection is gone.

### Bob broadcasts

Bob broadcasts `message`. LiveThing writes a row into Alice's queue, because she is still a durable member. Connected members get the message live.

### Alice reconnects and drains

Alice reconnects. Durable membership joins her to `dm:alice+bob` again, and then the drain sends her waiting `message`. The message still has its original sequence number.

### The client acknowledges

Alice's client sends `__received__ { receivedThrough: <seq> }` automatically. The row is settled and deleted.

### A later reconnect does not repeat it

Alice's socket drops and reconnects again. The row is gone, so the server does **not** send it again.

::

The last step is the main goal: after a member acknowledges a message, the server does not send it again, even after many reconnects.

Inbox is a delivery queue, not a message history. Because an acknowledged row is deleted, the queue holds only messages not yet delivered. Keep your message history in your own database.

## Adding rows to a member's queue: `ctx.channel.inbox.backfill`

Inside a channel handler, you can add rows to one member's queue yourself. Use this to give a late joiner some history, or to move an existing message log into inbox. In `dms`'s own handlers, `ctx.channel.inbox` is the channel's `ChannelInbox` object. It is typed as always present (never `null`) because `dms` lists `inbox()` in its own `capabilities`:

```typescript [server/dms.ts]
import * as v from 'valibot'
import { dms } from './base'
import { loadMessages } from './helpers'

export const handleShareHistory = dms.on('share-history', {
  input: v.object({ userId: v.string() }),
  async run(ctx, payload) {
    const history = await loadMessages(ctx.channel.params.pair)
    ctx.channel.inbox.backfill(
      payload.userId,
      history.map((message) => ({
        event: 'message' as const,
        payload: message,
        __livething: { messageId: message.id },
      })),
    )
  },
})
```

Each frame's `__livething.messageId` is its message ID. You do not choose the sequence number: the server takes it from the same counter that live messages use, one number per frame, in the order you pass them. So a backfilled row never takes a sequence number that a later live message needs.

When the member is online and in the channel, `backfill` sends the new messages to each of the member's connections in that channel straight away, in sequence order, with the same sequence number and message ID as the stored row. The client acknowledges them like any other inbox message. When the member is offline, or online but not in the channel, the messages wait in the queue and arrive with the drain on the member's next connect. A frame that `backfill` skips because its message ID is already stored is not sent again.

This means backfilled messages arrive as the **newest** messages, after everything the member already has waiting. Delivery order and display order are different things. If your message payload carries its own timestamp (for example a `sentAt` field), sort by that timestamp to show the messages in time order. Do not sort by sequence number.

The channel handle knows the channel's declared events, so `backfill` checks both the event name and its payload at compile time. A wrong event or a wrong payload is a TypeScript error. A handle that you get from a plain string (with `ctx.channels.get(name)`) has looser types, because TypeScript does not know which channel it is. Use the channel's own handle when you want the strictest typing.

Each frame's `payload` must be a plain object with string keys, or `null`. This is the same rule as for `ctx.channel.broadcast(...)`, which sends a `Message`. Any other value (a string, a number, an array) throws an error, so a bad row is never stored. A message that the inbox [cannot store](/server/inbox/overview#binary-events), because it is too big, throws a `RangeError` too, and then no message of that call is stored.

### Backfilling binary messages

On a channel with [binary events](/server/inbox/overview#binary-events), `ctx.channel.inbox.binary.backfill(userId, messages)` does the same for them. Each message has the event, its `info`, its `bytes` (a `Uint8Array` or an `ArrayBuffer`, which you can leave out), and its message ID. The member gets each one as one binary frame, straight away or with the next drain, as above. Huddle could seed a direct message with voice notes from an older app:

```typescript [server/voice-notes.ts]
import { dms } from './base'
import { loadOldVoiceNotes } from './helpers'

export const seedVoiceNotes = dms.on('import-voice-notes', {
  async run(ctx) {
    const notes = await loadOldVoiceNotes(ctx.channel.name)
    ctx.channel.inbox.binary.backfill(
      ctx.user.id,
      notes.map((note) => ({
        event: 'voice-note',
        info: { from: note.from, durationMs: note.durationMs },
        bytes: note.bytes,
        __livething: { messageId: note.id },
      })),
    )
  },
})
```

The event and the info are typed from the channel's `binary({ emits })`, so a JSON event, or the wrong info, is a compile error. On a channel without binary events, `inbox.binary` has the type `never`.

`backfill` applies the channel's `retention` limit the same way a live broadcast does. If the new rows push the member's queue past the limit, the rows with the lowest sequence numbers are removed. Backfilled rows are the newest, so the rows that were already waiting go first. When a removed row was not yet delivered, LiveThing raises the member's **overflow watermark** (the saved highest sequence number the member lost). Because of this, the member's next reconnect drain sends a `__gap__` frame for the rows that `backfill` pushed out. If you add more history than `retention` allows, this is expected: a live broadcast would hit the same limit. See [Overflow and the gap signal](/server/inbox/overflow-and-gap) for what that removal does.

### Running the same backfill twice

A member holds at most one row per message ID on each channel. So while the rows are still waiting, running the same `backfill` again is safe: a frame whose `messageId` is already stored for that member is skipped, and the stored row is not replaced.

After the member acknowledges a message, its row is deleted. LiveThing then has nothing left to compare against, so a later `backfill` that includes the same message stores it again, and the member gets it twice. The client's [`dedup()`](/client/primitives/dedup) does not stop this: it only remembers message IDs for a short time, in memory.

Backfill each member once. A good place is the channel's `onSubscribe` hook, with your own table that records who you already seeded. Here is Huddle's `dms` channel with that hook:

```typescript [server/huddle-dms.ts]
import { emits, t } from '@livething/server'
import { inbox } from '@livething/server/inbox'
import { base, Message } from './base'
import { loadMessages } from './helpers'

export const dms = base.channel(['dms', 'dm:{pair}'], {
  membership: 'persistent',
  capabilities: [inbox(), emits({ message: t<Message>() })],
  async onSubscribe(ctx) {
    const seeded = ctx.sql
      .exec(
        'SELECT 1 FROM dm_seeded WHERE user_id = ? AND channel = ?',
        ctx.user.id,
        ctx.channel.name,
      )
      .one()
    if (seeded) return

    const history = await loadMessages(ctx.channel.params.pair)
    ctx.channel.inbox.backfill(
      ctx.user.id,
      history.map((message) => ({
        event: 'message' as const,
        payload: message,
        __livething: { messageId: message.id },
      })),
    )
    ctx.sql.exec(
      'INSERT INTO dm_seeded (user_id, channel) VALUES (?, ?)',
      ctx.user.id,
      ctx.channel.name,
    )
  },
})
```

The `onSubscribe` hook runs every time the member joins, including after a reconnect, so the `dm_seeded` check is what makes the history arrive only once. `dm_seeded` is your own table. Create it once in an `onInit` hook, with `CREATE TABLE IF NOT EXISTS dm_seeded (user_id TEXT NOT NULL, channel TEXT NOT NULL, PRIMARY KEY (user_id, channel))`. See [SQL and KV](/server/context-and-storage/sql-and-kv#creating-tables-once).

## Who received a message: `ctx.channel.inbox.receiversOf`

Inbox already tracks each member's acknowledgement, so it can tell you which members have received messages up to a given sequence number. `receiversOf(seq)` on the same object returns the user IDs whose received cursor has reached `seq`:

```typescript [server/dms.ts]
import * as v from 'valibot'
import { dms } from './base'

export const handleAskReceivedBy = dms.on('ask-received-by', {
  input: v.object({ seq: v.number() }),
  run(ctx, payload) {
    const userIds = ctx.channel.inbox.receiversOf(payload.seq)
    ctx.send('cursor-answer', {
      kind: 'received',
      seq: payload.seq,
      userIds,
    })
  },
})
```

Received receipts are built on this. The [Receipts](/server/inbox/receipts) page shows how the server also sends this cursor live to the channel as a `__received__` frame, and how read receipts use the same shape.

::note
`ctx.channel.inbox` exists in `dms.on(...)` handlers and in the `onSubscribe`, `onUnsubscribe`, and `onSessionEnd` hooks. Write each of those below `capabilities` in the channel's config object. It does **not** exist in `check`, `commit`, or `revalidate`. At runtime, handles from `ctx.channels.get(...)` also have no `inbox()` method during those three steps. See [Auth Gate](/server/channels/auth-gate) for what `check`, `commit`, and `revalidate` do.
::

## Using inbox from any handle: `handle.inbox()` / `handle.readReceipts()`

`ctx.channel.inbox` and `ctx.channel.readReceipts` are available only in a handler that belongs to that exact channel. There, they are typed as always present (never `null`), because the channel's own `capabilities` list includes `inbox()` / `readReceipts()`. From another channel's handler, a top-level handler or a connection hook, get a handle for the channel and call its `inbox()` and `readReceipts()` methods. Both can return `null`: they return the object when that channel has the feature turned on, and `null` when it does not. Check for `null` before you use the result.

```typescript [server/forward.ts]
import * as v from 'valibot'
import { base, dms } from './base'

export const handleForwardToDm = base.on('forward-to-dm', {
  input: v.object({ pair: v.string(), text: v.string() }),
  run(ctx, input) {
    const dmInbox = ctx.channels
      .get(dms.at({ pair: input.pair }))
      .inbox()
    if (!dmInbox) return

    const id = crypto.randomUUID()
    dmInbox.backfill(ctx.user.id, [
      {
        event: 'message',
        payload: {
          id,
          text: input.text,
          from: ctx.user.id,
          sentAt: Date.now(),
        },
        __livething: { messageId: id },
      },
    ])
  },
})
```

This top-level handler lets a member save a message into one of their own direct message channels. `dms.at({ pair })` names one channel of the `dms` family, so `ctx.channels.get(...)` can find it. A plain string works only for a channel with a fixed name. `ctx.channels.get(...)` works in any handler, so you can use it to reach an inbox or read-receipts channel that the current handler does not belong to. For a channel with neither feature turned on, both methods return `null`. The `null` check is the only check you need, and no type cast is needed.

## Who is behind: `ctx.channel.inbox.backlog()`

`backlog()` is a monitoring query. It does not warn or throw. It lists every member that still has rows for this channel that they have not acknowledged, so you can see who is behind and by how many rows. It reads the same rows and cursors that the reconnect drain uses. It is not a separate log or an estimate.

```typescript [server/dms.ts]
import * as v from 'valibot'
import { dms } from './base'

export const handleInspectBacklog = dms.on('inspect-backlog', {
  input: v.object({}),
  run(ctx) {
    const entries = ctx.channel.inbox.backlog()
    for (const entry of entries) {
      ctx.log.info('inbox backlog', {
        userId: entry.userId,
        online: entry.online,
        heldRows: entry.heldRows,
        receivedThrough: entry.receivedThrough,
        oldestHeldAt: entry.oldestHeldAt,
      })
    }
  },
})
```

Each entry is an `InboxBacklogEntry`:

::field-group
::field{name="userId" type="string"}
The member's user ID.
::
::field{name="online" type="boolean"}
Whether this user has a live connection on this server instance right now. If a member is `online` and `heldRows` keeps growing, the member's client is not acknowledging messages. This is a different problem from an offline member with the same number of waiting rows.
::
::field{name="heldRows" type="number"}
The number of rows for this member on this channel that are not yet acknowledged.
::
::field{name="receivedThrough" type="number"}
The member's received cursor for this channel. It is `0` if the member has never sent an acknowledgement.
::
::field{name="oldestHeldAt" type="number"}
The time (in milliseconds) when the member's oldest unacknowledged row was created. It shows how long the member has been behind.
::
::field{name="lastSeenAt" type="number | null | undefined"}
The member's last-seen timestamp. It is present only when the [`lastSeen()`](/server/capabilities/last-seen) capability is also installed. Otherwise the field is absent (`undefined`).
::
::

Only members with at least one waiting row appear in the list. A member who has acknowledged everything is not in the list. Without `lastSeen()`, entries have no `lastSeenAt` key. `heldRows` and `oldestHeldAt` show how far behind a member is.

`backlog()` is available in the same places as `backfill` and `receiversOf`: on `ctx.channel.inbox` inside this channel's own handlers, or from anywhere with `ctx.channels.get(name).inbox()?.backlog()`.
