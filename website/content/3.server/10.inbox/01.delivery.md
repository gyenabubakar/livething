Inbox makes one promise: every eligible member gets every message, including the messages sent while they were offline. Three parts keep this promise, and this page explains each one:

1. A **row** (one saved copy of a message in the database) is written for each member on every broadcast.
2. The client sends a `__received__` **acknowledgement** (a short message that says "I got it"), and this settles the row.
3. When a member reconnects, the server **drains** their queue: it sends again every row that the member did not acknowledge.

The [Overview](/server/inbox/overview) compares inbox with replay and explains the storage model. This page covers how delivery works.

## One row per member, kept until acknowledged

When a handler broadcasts to an inbox channel, LiveThing writes a durable row (a row stored in the database, so it survives a disconnect or a restart) into the queue of **every eligible current member** while the message goes out. This is called [**fan-out on write**](/learn/reliability#fan-out-on-read-vs-fan-out-on-write). Members who are connected also get the message live, at the same time. Each row stays in that member's queue until the member sends a `__received__` acknowledgement for it. At that point the row is _settled_. By default, a settled row is deleted.

`ctx.channel.broadcast(...)` skips the sending connection by default, the same as a plain channel broadcast. The sender's user gets no row for their own message when the sending connection is that user's only connection in the channel. If the same user is also in the channel from another connection (for example, a second browser tab), that user still gets a row, because the other connection receives the message live. Pass `{ includeSelf: true }` to treat the sender like any other member.

Your handler code does not change. You broadcast as usual, and LiveThing turns each broadcast into a durable delivery for each member.

```typescript [inbox-server.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { dedup } from '@livething/server/dedup'
import { inbox } from '@livething/server/inbox'
import { sequence } from '@livething/server/sequence'
import * as v from 'valibot'
import { requireUsername } from './upgrade'

const RoomMsg = v.object({ text: v.string(), from: v.string() })
const SendRoomMsg = v.object({ text: v.string() })

const base = server({
  upgrade: (request) => requireUsername(request),
  capabilities: [channels(), sequence({ persist: true }), dedup()],
})

// inbox() is in this channel's own capabilities, so every broadcast writes
// one row for each member.
const chat = base.channel('chat', {
  capabilities: [
    inbox(),
    emits({
      'room-msg': t<v.InferOutput<typeof RoomMsg>>(),
      'got-it': t<{ seq: number; userIds: string[] }>(),
    }),
  ],
})

export const handleSendRoomMsg = chat.on('send-room-msg', {
  input: SendRoomMsg,
  run(ctx, payload) {
    ctx.channel.broadcast('room-msg', {
      text: payload.text,
      from: ctx.meta.username,
    })
  },
})
```

Add `handleSendRoomMsg` to `base.assemble({ handlers: [...] })` to turn on this route. If you pass only `chat`, the app gets the channel's inbox settings and lifecycle hooks, but not the `send-room-msg` handler.

::note
Inbox delivers to a **member's user ID**, so each member needs a stable `userId`. Set one in the upgrade step (here, `requireUsername` does it). An anonymous connection (one with no `userId`) still gets messages live while it is connected. It has no durable queue, so it gets no drain after a reconnect and no delivery guarantee. See the [Overview requirements](/server/inbox/overview#requirements) for the full list.
::

## The client acknowledges for you

You do not write the `__received__` acknowledgement yourself. The [client `inbox()` primitive](/client/primitives/inbox) tracks the highest sequence number it has seen on each inbox channel and sends `__received__` automatically. The client knows which channels use inbox from the `__subscribeOk__` confirmation: for an inbox channel, that frame carries `metadata.channel.inbox: true`.

The acknowledgement is a channel-scoped frame (one WebSocket message that belongs to one channel):

```json
[
  "__received__",
  { "receivedThrough": 7 },
  { "channel": { "name": "chat" } }
]
```

`receivedThrough` is a sequence number. It means "I have every message on this channel up to and including number 7." This one value is a **cursor** (a saved position in the message list). It settles every row at or below that number in one step.

For a dynamic channel family, "this channel" means the family key plus the concrete channel name. For example, `rooms` at `room-42` is a different inbox scope from `rooms` at `room-43`, even though both come from the same family declaration. A static channel has no family key. The client sends both values in the channel routing metadata, so an acknowledgement for one room never settles rows in another room. [`gaps()`](/client/primitives/gaps) uses the same identity rule for gap frames.

The client also **sends its acknowledgement again on reconnect**. When the socket reconnects and the client joins the channel again, it sends its highest cursor again. So if a member acknowledged messages just before the connection dropped, the server does not send those rows again.

## The reconnect drain

A member who was offline during a broadcast still has their rows waiting. On reconnect, [durable membership](/server/channels/membership-and-presence) joins the member to the channel again automatically. Then LiveThing **drains** the queue: it sends the waiting rows again, in order, and each row keeps its original sequence number.

A drained row can repeat a message that the member already saw live before the socket dropped. The client [`dedup()`](/client/primitives/dedup) primitive removes these repeats by message ID, so your `on()` handlers run once for each message. The server needs [`dedup()`](/server/capabilities/dedup) too, because it gives each message the ID that the client checks. This is why inbox requires `dedup()`.

Here is the offline path from start to end:

::steps{level="3"}

### Both members subscribe

Alice and Bob both subscribe to `chat`. Both now have durable memberships, which stay after a socket drops.

### Alice's socket drops

Alice goes offline. Her membership stays. Only her connection is gone.

### Bob broadcasts

Bob broadcasts `room-msg`. LiveThing writes a row into Alice's queue, because she is still a durable member. Connected members get the message live.

### Alice reconnects and drains

Alice reconnects. Durable membership joins her to `chat` again, and then the drain sends her waiting `room-msg`. The message still has its original sequence number.

### The client acknowledges

Alice's client sends `__received__ { receivedThrough: <seq> }` automatically. The row is settled and, by default, deleted.

### A later reconnect does not repeat it

Alice's socket drops and reconnects again. The row is gone, so the server does **not** send it again.

::

The last step is the main goal: after a member acknowledges a message, the server does not send it again, even after many reconnects.

## `onDelivered`: delete or retain

After a member acknowledges a row, the `onDelivered` option decides what happens to that row:

| Value                | Behavior                                                                                             |
| -------------------- | ---------------------------------------------------------------------------------------------------- |
| `'delete'` (default) | The row is deleted as soon as it is settled. The queue holds only messages not yet delivered.        |
| `'retain'`           | The row is kept after it is settled. Use this when you want to keep a history of delivered messages. |

```typescript [on-delivered.ts]
// Default: acknowledged rows are deleted.
const chat = base.channel('chat', {
  capabilities: [
    inbox(),
    emits({ 'room-msg': t<v.InferOutput<typeof RoomMsg>>() }),
  ],
})

// Keep acknowledged rows. This needs retention to limit them.
const audited = base.channel('audited', {
  capabilities: [
    inbox({
      onDelivered: 'retain',
      retention: { maxMessages: 500 },
    }),
    emits({ 'room-msg': t<v.InferOutput<typeof RoomMsg>>() }),
  ],
})
```

::warning
`onDelivered: 'retain'` **requires** a `retention` option. Without it, TypeScript reports an error, and the build throws:

```text
[livething] inbox `onDelivered: 'retain'` requires `retention` so kept rows can age out.
```

Without a limit, kept rows would grow forever. See [Overflow and the gap signal](/server/inbox/overflow-and-gap) for what `retention` does.
::

## Adding rows to a member's queue: `ctx.channel.inbox.backfill`

Inside a channel handler, you can add rows to one member's queue yourself. Use this to give a late joiner some history, or to move an existing message log into inbox. In `chat`'s own handlers, `ctx.channel.inbox` is the channel's `ChannelInbox` object. It is typed as always present (never `null`) because `chat` lists `inbox()` in its own `capabilities`:

```typescript [backfill.ts]
export const handleSeedHistory = chat.on('seed-history', {
  input: v.object({ userId: v.string() }),
  run(ctx, payload) {
    ctx.channel.inbox.backfill(payload.userId, [
      {
        event: 'room-msg',
        payload: { text: 'welcome', from: 'system' },
        __livething: { deliverySeq: 1, messageId: 'seed-1' },
      },
      {
        event: 'room-msg',
        payload: { text: 'house rules', from: 'system' },
        __livething: { deliverySeq: 2, messageId: 'seed-2' },
      },
    ])
  },
})
```

Each frame's `__livething.deliverySeq` is its sequence number, and `__livething.messageId` is its message ID. The client uses these two values to order the added rows and to remove repeats, the same as for a normal drained row. Choose them so they fit correctly into that member's cursor.

The channel handle knows the channel's declared events, so `backfill` checks both the event name and its payload at compile time. A wrong event or a wrong payload is a TypeScript error. A handle that you get from a plain string (with `ctx.channels.get(name)`) has looser types, because TypeScript does not know which channel it is. Use the channel's own handle when you want the strictest typing.

Each frame's `payload` must be a plain object with string keys. This is the same shape that `ctx.channel.broadcast(...)` sends, like `{ text: 'welcome', from: 'system' }`. Any other value (a string, a number, an array) throws an error, so a bad row is never stored.

`backfill` applies the channel's `retention` limit the same way a live broadcast does. If the new rows push the member's queue past the limit, the oldest rows are removed. When a removed row was not yet delivered, LiveThing raises the member's **overflow watermark** (the saved highest sequence number the member lost). Because of this, the member's next reconnect drain sends a `__gap__` frame for the history that `backfill` pushed out. Removing an acknowledged row that `'retain'` kept does not raise the watermark. If you add more history than `retention` allows, this is expected: a live broadcast would hit the same limit. See [Overflow and the gap signal](/server/inbox/overflow-and-gap) for what that removal does.

If you call `backfill` again with a frame that is already stored, nothing happens. The row for that user, channel and sequence number already exists, so the new copy is ignored and the stored row is not replaced. This matters most for a row the member already acknowledged: running a backfill again does not turn a message that was already read back into an unread one.

## Who received a message: `ctx.channel.inbox.receiversOf`

Inbox already tracks each member's acknowledgement, so it can tell you which members have received messages up to a given sequence number. `receiversOf(seq)` on the same object returns the user IDs whose received cursor has reached `seq`:

```typescript [received-by.ts]
export const handleWhoGotIt = chat.on('who-got-it', {
  input: v.object({ seq: v.number() }),
  run(ctx, payload) {
    const userIds = ctx.channel.inbox.receiversOf(payload.seq)
    ctx.channel.send('got-it', { seq: payload.seq, userIds })
  },
})
```

Received receipts are built on this. The [Receipts](/server/inbox/receipts) page shows how the server also sends this cursor live to the channel as a `__received__` frame, and how read receipts use the same shape.

::note
`ctx.channel.inbox` exists in `chat.on(...)` handlers and in the `subscribe`, `unsubscribe`, and `sessionEnd` lifecycle hooks. You write each of those after the `base.channel(...)` object is complete. It does **not** exist in `check`, `commit`, or `revalidate`. You write those three inside that same object, next to the `capabilities` list (the array that turns on `inbox()`), so TypeScript cannot yet know what `capabilities` adds to `ctx.channel`. At runtime, handles from `ctx.channels.get(...)` also have no `inbox()` method during those three steps. See [Auth Gate](/server/channels/auth-gate) for what `check`, `commit`, and `revalidate` do.
::

## Using inbox from any handle: `handle.inbox()` / `handle.readReceipts()`

`ctx.channel.inbox` and `ctx.channel.readReceipts` are available only in a handler that belongs to that exact channel. There, they are typed as always present (never `null`), because the channel's own `capabilities` list includes `inbox()` / `readReceipts()`. From anywhere else (another channel's handler, a top-level handler, a hook, a scheduled task), get a handle for the channel and call its `inbox()` and `readReceipts()` methods. Both can return `null`: they return the object when that channel has the feature turned on, and `null` when it does not. Check for `null` before you use the result.

```typescript [handle-inbox.ts]
export const handleBackfillOther = base.on('backfill-other-room', {
  input: v.object({ room: v.string(), userId: v.string() }),
  run(ctx, input) {
    const other = ctx.channels.get(input.room)
    const otherInbox = other.inbox()
    if (!otherInbox) return

    otherInbox.backfill(input.userId, [
      {
        event: 'room-msg',
        payload: { text: 'catch up on this', from: 'system' },
        __livething: { deliverySeq: 1, messageId: 'seed-1' },
      },
    ])
  },
})
```

`ctx.channels.get(...)` works in any handler, so you can use it to reach an inbox or read-receipts channel that the current handler does not belong to. For a channel with neither feature turned on, both methods return `null`. The `null` check is the only check you need, and no type cast is needed.

## Who is behind: `ctx.channel.inbox.backlog()`

`backlog()` is a monitoring query. It does not warn or throw. It lists every member that still has rows for this channel that they have not acknowledged, so you can see who is behind and by how many rows. It reads the same rows and cursors that the reconnect drain uses. It is not a separate log or an estimate.

```typescript [inbox-backlog.ts]
export const handleInspectBacklog = chat.on('inspect-backlog', {
  input: v.object({}),
  run(ctx) {
    const entries = ctx.channel.inbox.backlog()
    for (const entry of entries) {
      ctx.log.info('inbox backlog', {
        userId: entry.userId,
        online: entry.online,
        heldRows: entry.heldRows,
        receivedThrough: entry.receivedThrough,
        oldestHeldAt: entry.oldestHeldAt,
      })
    }
  },
})
```

Each entry is an `InboxBacklogEntry`:

::field-group
::field{name="userId" type="string"}
The member's user ID.
::
::field{name="online" type="boolean"}
Whether this user has a live connection on this server instance right now. If a member is `online` and `heldRows` keeps growing, the member's client is not acknowledging messages. This is a different problem from an offline member with the same number of waiting rows.
::
::field{name="heldRows" type="number"}
The number of rows for this member on this channel that are not yet acknowledged.
::
::field{name="receivedThrough" type="number"}
The member's received cursor for this channel. It is `0` if the member has never sent an acknowledgement.
::
::field{name="oldestHeldAt" type="number"}
The time (in milliseconds) when the member's oldest unacknowledged row was created. It shows how long the member has been behind.
::
::field{name="lastSeenAt" type="number | null | undefined"}
The member's last-seen timestamp. It is present only when the [`lastSeen()`](/server/capabilities/last-seen) capability is also installed. Otherwise the field is absent (`undefined`).
::
::

Only members with at least one waiting row appear in the list. A member who has acknowledged everything is not in the list. Without `lastSeen()`, entries have no `lastSeenAt` key. There is no `lag` field: `heldRows` and `oldestHeldAt` already show how far behind a member is.

`backlog()` is available in the same places as `backfill` and `receiversOf`: on `ctx.channel.inbox` inside this channel's own handlers, or from anywhere with `ctx.channels.get(name).inbox()?.backlog()`.
