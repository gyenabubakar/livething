Inbox holds a durable row per member until that member acknowledges it. A member who never comes back would otherwise pile up rows forever. `retention` bounds that queue — and when a bound is hit while a member is behind, the oldest held row is evicted. This page is about that eviction, the **overflow watermark** it raises, and the `__gap__` frame that tells a reconnecting client "you missed some, and the earliest are gone."

## Bounding held rows with `retention`

`retention` caps how many rows inbox keeps **per member**. It takes two optional bounds:

| Field         | What it does                                                                                                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maxMessages` | Keep at most this many rows per member. In `delete` mode those are all undelivered until acknowledgement; in `retain` mode acknowledged rows count too and may be pruned. |
| `maxAgeMs`    | Age rows out by time — a row older than this is dropped regardless of acknowledgement. Only an evicted undelivered row raises an overflow watermark.                      |

```typescript [retention.ts]
const chat = base.channel('chat', {
  capabilities: [
    inbox({
      retention: { maxMessages: 500, maxAgeMs: 86_400_000 },
    }),
    emits({ 'room-msg': t<v.InferOutput<typeof RoomMsg>>() }),
  ],
})
```

Here each member keeps at most 500 rows, and any row older than a day is aged out. In the default `delete` mode, that is the undelivered queue because acknowledged rows are removed immediately. With `retain`, acknowledged rows also use the bound. Without `retention`, a member's queue is unbounded — fine for channels where members reconnect promptly, dangerous for ones where a member might vanish for a long time.

::note
Both a live broadcast and [`ctx.channel.inbox.backfill(...)`](/server/inbox/delivery) check `retention` right after they insert. `maxMessages` prunes when a new row could exceed the count and is reconciled again at boot, so a changed cap applies to rows already stored. `maxAgeMs` also registers a durable alarm for the earliest row expiry, so a channel that goes quiet still gets swept. The alarm is shared with scheduled work and survives hibernation; only the platform's alarm delay can make cleanup later than the age window.

Rows are removed when they are strictly older than `maxAgeMs`, so cleanup happens no earlier than the configured age and normally on the first alarm after that point. An evicted acknowledged row does not mean the member missed anything and does not raise a watermark; an evicted undelivered row does, and the next reconnect reports the lost range with `__gap__`. A cold boot also sweeps already-expired rows before normal work starts. If a fixed legal deletion deadline is required, treat platform alarm delivery as eventual and add an external control.
::

## What overflow means

When a member is behind — offline, or just not acknowledging — and a new broadcast pushes their queue past `maxMessages`, the **oldest held rows are evicted** to make room. In `retain` mode, an acknowledged row can be one of those evictions; it is already known to have arrived and does not create a hole. Only an evicted undelivered row raises that member's **overflow watermark**, to the highest sequence among the lost undelivered rows.

The smallest example makes it concrete: `maxMessages: 1` keeps exactly one undelivered row per member.

```typescript [inbox-gap-server.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { dedup } from '@livething/server/dedup'
import { inbox } from '@livething/server/inbox'
import { sequence } from '@livething/server/sequence'
import * as v from 'valibot'
import { requireUsername } from './upgrade'

const RoomMsg = v.object({ text: v.string(), from: v.string() })
const SendRoomMsg = v.object({ text: v.string() })

const base = server({
  upgrade: (request) => requireUsername(request),
  capabilities: [channels(), sequence({ persist: true }), dedup()],
})

const chat = base.channel('chat', {
  capabilities: [
    inbox({ retention: { maxMessages: 1 } }),
    emits({ 'room-msg': t<v.InferOutput<typeof RoomMsg>>() }),
  ],
})

export const handleSendRoomMsg = chat.on('send-room-msg', {
  input: SendRoomMsg,
  run(ctx, payload) {
    ctx.channel.broadcast('room-msg', {
      text: payload.text,
      from: ctx.meta.username,
    })
  },
})
```

Now walk the overflow:

::steps{level="3"}

### Both members subscribe

Alice and Bob both subscribe to `chat`, so both are durable members.

### Alice's socket drops

Alice goes offline. Her one-row queue is empty and her membership stays.

### First broadcast fills the queue

Bob broadcasts `m1`. Alice's queue holds one row: `m1`.

### Second broadcast overflows

Bob broadcasts `m2`. Alice is already at her one-row cap, so `m1` is **evicted** and her overflow watermark is raised to `m1`'s sequence. Her queue now holds `m2`.

::

Alice has permanently missed `m1`. The remaining question is how she finds out.

## The `__gap__` frame on the drain

When Alice reconnects, the [reconnect drain](/server/inbox/delivery#the-reconnect-drain) runs. Because her overflow watermark is set, the engine emits a `__gap__` frame for the channel **before** the surviving rows:

```json
// server -> client, before the surviving rows
["__gap__", { "missedThrough": 1 }, { "channel": { "name": "chat" } }]

// then the surviving row
["room-msg", { "text": "m2", "from": "bob" }, { "channel": { "name": "chat" }, "delivery": { "seq": 2 } }]
```

The order matters: the gap comes first so a client can react to the hole before rendering the messages that survived it. This is the honest version of guaranteed delivery — inbox still guarantees you get everything it _held_, and tells you plainly about anything it had to drop.

## `gaps()` surfaces the gap

Here is the important detail. The [`gaps()` client primitive](/client/primitives/gaps) surfaces `__gap__` through the `onGap` callback. The [`inbox()` primitive](/client/primitives/inbox) still reads the frame on an inbox channel and advances its acknowledgement through `missedThrough`, so the server does not keep reporting the same gap. An **inbox-only client** — one whose stack has `inbox()` but not `gaps()` — has no `onGap` callback; the reserved frame is kept out of application message handlers, so delivery continues but the member does not learn about the hole.

So to react to overflow gaps, add `gaps()` to the client stack. It slots in alongside inbox and does not require replay:

```typescript [gap-client.ts]
import {
  channels,
  client,
  connect,
  dedup,
  gaps,
  inbox,
  reconnection,
} from '@livething/client'
import type { InboxGapClient } from './socket-types'

const socket = client<InboxGapClient>()(
  connect('wss://example.com/inbox-gap'),
  channels(),
  gaps(),
  inbox(),
  dedup(),
  reconnection({ maxDelay: 400 }),
)

const chat = socket.channel('chat')

chat.onGap((info) => {
  // Everything at or below info.missedThrough on this channel is gone —
  // fall back to a full reload or a server-side history fetch.
  reloadChannelHistory(chat, info.missedThrough)
})
```

An inbox overflow is a **channel-scoped** gap, so it lands on `socket.channel(...).onGap(...)`, not the top-level `socket.onGap(...)`. The callback receives a `GapInfo`:

- `missedThrough` — the highest sequence such that everything at or below it is gone. That is the evicted row's sequence.
- `channel` / `channelFamily` — set on a channel gap, absent on a top-level one. For a dynamic family, use the pair together: the family key plus the concrete channel name identify one scope; the concrete name alone is not enough.

`channel.onGap` exists only when `gaps()` is in the client stack. Without it, TypeScript reports that `onGap` does not exist on the channel handle.

::note
This is the same `onGap` you use for [replay's own catch-up gaps](/server/replay/overview) — when replay could not fully catch a channel up because retention had already evicted messages the client had not seen. Inbox overflow and replay eviction are two sources of the same signal, and a single `gaps()` handler covers both.
::

## Choosing your bounds

`retention` trades memory for how far a member can fall behind without losing anything:

- **No `retention`** — no member ever loses a message, but a vanished member's queue grows without limit. Good when members reconnect promptly and you trust them to return.
- **`maxMessages` / `maxAgeMs` set** — bounded memory, but a member far enough behind loses the oldest messages and gets a `__gap__` on return. Good for busy channels where an absent member catching up on days of backlog is neither useful nor affordable.

If you set bounds, pair the client with `gaps()` so a member who overflows is told, rather than silently missing messages they will never see delivered.
