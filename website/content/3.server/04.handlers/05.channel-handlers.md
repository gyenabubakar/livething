A **channel** is a room — a named group of connections that share events. `base.channel(pattern, config)` declares one and returns a channel object. That object has the same handler methods as `base` — `on`, `request`, and the stream methods — but each one is **scoped to the channel**: it only fires for connections subscribed to that channel, and its `ctx` gains a typed `ctx.channel`.

`base.channel` appears on `base` only when the [`channels()`](/server/capabilities/channels) capability is listed.

```typescript [lobby.ts]
import { define, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [channels()],
})

const lobby = base.channel('lobby', {
  outgoing: {
    emits: { message: t<{ text: string; from: string }>() },
  },
})

// a handler scoped to `lobby`
export const handleSay = lobby.on('say', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', { text: input.text, from: ctx.identity })
  },
})

export const handler = base.assemble(handleSay)
```

This page is about **attaching handlers** inside a channel. The channel *concepts* — the auth gate, dynamic families, presence, membership — live in [Channels](/server/channels/overview); this page links there rather than repeating them.

::note
Pass any one channel handler — or the channel object itself — to `assemble()` and the **whole channel** is pulled in once. You don't list every handler in a channel separately.
::

## The handler methods on a channel

The channel object carries the same builders as `base`, each scoped to the channel and each gated by the same capability:

| Method | What it handles | Needs |
|---|---|---|
| `channel.on(event, config)` | A client→server event from a member | — |
| `channel.request(event, config)` | A client→server request from a member | [`requests()`](/server/capabilities/requests) |
| `channel.stream(event, config)` | A stream scoped to the channel | [`stream()`](/server/capabilities/streams) |
| `channel.resumableStream(event, config)` | A resumable stream in the channel | [`resumableStream()`](/server/capabilities/streams) |
| `channel.recordedStream(event, config)` | A recorded stream in the channel | [`recordedStream()`](/server/capabilities/streams) |

The config for each is the same as its top-level form — covered on [base.on](/server/handlers/on), [base.request](/server/handlers/request), and [base.stream](/server/handlers/stream). The one difference is `ctx`: inside a channel handler, `ctx` carries `ctx.channel`.

```typescript [handlers.ts]
// a channel event handler
const handleSay = lobby.on('say', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', { text: input.text, from: ctx.identity })
  },
})

// a channel request handler — return value is the reply
const handleGetInfo = lobby.request('get-info', {
  input: v.object({}),
  run(ctx) {
    return { memberCount: ctx.channel.members().length }
  },
})

// a channel stream — the generator is identical to a top-level one
const handleFeed = lobby.stream('feed', {
  input: v.object({ count: v.number() }),
  chunk: t<{ index: number }>(),
  async *run(_ctx, input) {
    for (let i = 0; i < input.count; i += 1) yield { index: i }
  },
})
```

## `ctx.channel`

Inside a channel handler, `ctx` gains `ctx.channel` — the handle for the matched channel, typed against that channel's `outgoing.emits` declarations:

| On `ctx.channel` | What it is |
|---|---|
| `.name` | The matched channel name — the static name (e.g. `'lobby'`) or the filled-in template path for a dynamic family (e.g. `'room:42'`). |
| `.family` | The family key for a [dynamic family](/server/channels/dynamic-families), or `null` for a static channel. |
| `.params` | The `{name}` captures from a dynamic pattern, e.g. `{ id: 'abc' }`. |
| `.send(event, payload)` | Send a channel event to the calling connection. |
| `.broadcast(event, payload, options?)` | Send a channel event to the channel's members. `{ excludeSelf: false }` includes the caller. |
| `.members()` | A snapshot of the channel's members. |
| `.subscribe(ref, payload?)` | Subscribe a connection from server code — runs the channel's `check` → `commit` → `onSubscribe` flow. |
| `.kick(target, reason)` | Force-remove sockets — a `ConnectionRef`, a `TagRef`, or a tag group handle. Sends `__kicked__`, then `__memberLeave__` / `__memberOffline__` to the rest. |
| `.removeMember(identity)` | A true leave for a whole identity — drops every live socket of that user *and* its durable membership row. |

```typescript [handlers.ts]
const handleSay = lobby.on('say', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', {
      text: input.text,
      from: ctx.identity,
    })
    // ctx.channel.name   → 'lobby'
    // ctx.channel.family → null (static)
    // ctx.channel.params → {} (static)
  },
})
```

`ctx.channel.send` and `ctx.channel.broadcast` are typed to the channel's **own** emits, declared in the channel config. Sending a channel event you didn't declare on that channel is a compile error. The rest of `ctx` — storage, the top-level `ctx.send`/`ctx.broadcast`, tags — is still there; `ctx.channel` is added on top. See [Context and storage](/server/context-and-storage/overview).

### On a dynamic family

For a [dynamic family](/server/channels/dynamic-families) — declared with a `[familyKey, template]` pair — `ctx.channel.params` carries the captures and `ctx.channel.family` is the family key:

```typescript [rooms.ts]
const rooms = base.channel(['rooms', 'room:{id}'], {
  outgoing: { emits: { message: t<{ text: string }>() } },
})

const handleRoomSay = rooms.on('say', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    // ctx.channel.params → { id: string } — typed from the template
    // ctx.channel.family → 'rooms'
    // ctx.channel.name   → the matched path, e.g. 'room:42' (the template filled in)
    ctx.channel.broadcast('message', { text: `[${ctx.channel.params.id}] ${input.text}` })
  },
})
```

## The gate and lifecycle, in brief

A channel often guards who may join and reacts to joins and leaves. Those are **not** message handlers — they belong to the channel, not to one event:

- `check` and `commit` are fields on the `base.channel(pattern, config)` config object — `check` is the async gate before a subscriber is counted, `commit` the sync gate after. Throw from either to reject the subscribe.
- `channel.subscribe(...)`, `channel.unsubscribe(...)`, and `channel.sessionEnd(...)` are methods that register lifecycle callbacks.

```typescript [room.ts]
const room = base.channel('room', {
  outgoing: { emits: { 'room-message': t<{ text: string; from: string }>() } },
  check(ctx) {
    if (ctx.meta.username === 'blocked-user') {
      throw new Error('blocked-user may not subscribe') // rejects the subscribe
    }
  },
})

room.subscribe((ctx) => {
  ctx.channel.broadcast('room-message', { text: `${ctx.meta.username} joined`, from: 'system' })
})

room.unsubscribe((ctx) => {
  ctx.channel.broadcast('room-message', { text: `${ctx.meta.username} left`, from: 'system' })
})
```

The auth gate, families, presence, membership, and scope declaration are covered in full in [Channels](/server/channels/overview) — this section only shows where the gate and lifecycle sit relative to the handlers.

## Channel-scoped intercept and replay

A channel can also own an intercept and a custom replay strategy, scoped to that channel:

- `channel.intercept(...)` inspects every incoming frame in the channel before routing — needs the `intercepts()` capability. See [Intercept](/server/lifecycle-and-intercept/intercept).
- `channel.replay(...)` registers a custom replay strategy for the channel. See [Replay](/server/replay/overview).

```typescript [room.ts]
import { Block } from '@wskit/server/errors'

lobby.intercept((ctx, frame) => {
  if (frame.kind === 'nudge' && frame.event === 'cancel') throw Block
})
```

## Event names are scoped to the channel

A channel event name lives in its own namespace. `lobby.on('say', ...)` and a top-level `base.on('say', ...)` are two different handlers — the channel one only fires for `lobby` members. So the same name can appear at the top level and inside a channel without colliding. Within a single channel, an event name is still one kind: you can't have both `lobby.on('x')` and `lobby.request('x')`.
