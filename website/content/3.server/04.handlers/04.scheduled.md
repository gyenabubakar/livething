`base.scheduled(taskId, config)` binds the **body** of a scheduled task — code that runs later, on a timer, with no client connected. It is the one handler keyed by a **task ID** rather than an event name, and that ID must match a task you declared in the [`scheduled({ ... })`](/server/capabilities/scheduled) capability.

`base.scheduled` appears on `base` only when `scheduled({...})` is listed.

```typescript [cleanup.ts]
import { define, t } from '@wskit/server'
import { scheduled } from '@wskit/server/scheduled'

const base = define({
  env: t<Env>(),
  capabilities: [
    scheduled({ cleanup: null }), // declare the task
  ],
})

export const handleCleanup = base.scheduled('cleanup', {
  run(ctx) {
    ctx.sql.exec('DELETE FROM sessions WHERE expires_at < ?', Date.now())
  },
})

export const handler = base.assemble({ handlers: [handleCleanup] })
```

Two halves make a task: the **declaration** in the capability (its ID, payload type, interval, retry policy) and the **body** here. They are paired at `assemble()`. A declared task with no body, or a body with no declaration, is a build error — see [the rules](#declaration-and-body-must-match).

## The config

The config has just one field — `run`. There is no `input`, because a task is fired by the server (with `ctx.schedule(...)`), not by a client, so there is no wire payload to validate.

| Field | Required | What it does                                                                                                              |
| ----- | -------- | ------------------------------------------------------------------------------------------------------------------------- |
| `run` | yes      | `run(ctx)` for a no-payload task, or `run(ctx, data)` for a task declared with `data`. Returns `void` or `Promise<void>`. |

## Firing a task

You queue a run from any connection-scoped handler with `ctx.schedule(taskId, { time, data? })`, where `time` is a Unix timestamp in milliseconds. The body runs at that time, later, with no caller attached.

```typescript [handlers.ts]
const handleScheduleCleanup = base.on('schedule-cleanup', {
  input: v.object({ delayMs: v.number() }),
  run(ctx, input) {
    ctx.schedule('cleanup', { time: Date.now() + input.delayMs })
  },
})
```

`ctx.schedule(...)` validates its arguments **synchronously** and throws inside the calling handler on a mistake — an unregistered task ID, a `time` that is not a positive integer (`NaN`, `Infinity`, `0`, negative, and fractional values all throw), `data` passed to a task with no declared payload, or `data` that fails the task's declared schema. Catch it if you want to handle the failure rather than let it bubble.

Cancel pending runs with `ctx.cancelScheduled(taskId)`. Pass a data filter as a second argument — `ctx.cancelScheduled('report', { userId })` — to cancel only the runs whose payload matches every key in the filter; a recurring task's baseline runs are never removed by a filtered cancel. Both `schedule` and `cancelScheduled` are added to `ctx` by the `scheduled({...})` capability — see [Context and storage](/server/context-and-storage/overview).

## The task context

A scheduled `run` gets a **task context**, not a connection context — there is no single socket behind a timer. It has server-wide tools, not per-connection ones:

| On `ctx`                                         | What it does                                                                                                                                                               |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ctx.sql` / `ctx.kv`                             | Storage — query, migrate, read and write.                                                                                                                                  |
| `ctx.broadcast(event, payload)`                  | Send an event to **every** live connection. No `excludeSelf` option — there's no caller to exclude.                                                                        |
| `ctx.connection(ref)`                            | A handle for one connection by ref; its `send(event, payload)` delivers to just that socket and returns `true` if delivered or `false` if the connection is stale or gone. |
| `ctx.getConnections()`                           | A snapshot of every live connection.                                                                                                                                       |
| `ctx.connectionCount`                            | How many connections are open right now.                                                                                                                                   |
| `ctx.schedule(...)` / `ctx.cancelScheduled(...)` | Queue or cancel another task run.                                                                                                                                          |
| `ctx.env`                                        | The platform env bindings.                                                                                                                                                 |
| `ctx.log`                                        | The structured logger.                                                                                                                                                     |
| `ctx.waitUntil(promise)`                         | Keep the runtime alive until the promise settles.                                                                                                                          |
| `ctx.platform`                                   | The raw platform object (for example the Durable Object state on Cloudflare).                                                                                              |

::note
There is no `ctx.send` here — that targets "the calling connection", and a task has none. To reach a connection, broadcast to all, or address one with `ctx.connection(ref).send(...)`.
::

A task that broadcasts to everyone:

```typescript [handlers.ts]
const handleCleanup = base.scheduled('cleanup', {
  run(ctx) {
    ctx.broadcast('cleanup-done', { at: Date.now() })
  },
})
```

A task that addresses one connection by ref — the ref came in through the task's typed `data`:

```typescript [handlers.ts]
const base = define({
  env: t<Env>(),
  capabilities: [
    scheduled({
      'notify-user': { data: t<{ connectionId: string; text: string }>() },
    }),
  ],
})

const handleNotify = base.scheduled('notify-user', {
  run(ctx, data) {
    const ref = {
      __wskit: 'connection-ref' as const,
      id: data.connectionId,
      instance: undefined,
      identity: data.connectionId,
    }
    ctx.connection(ref).send('you-have-mail', { text: data.text })
  },
})
```

## Tasks with a payload

Declare `data` on the task and your `run` gets a typed second argument. The payload comes from the `ctx.schedule(taskId, { time, data })` call that queued the run — it's server-supplied. Whether it is validated depends on how you declared `data`: a `t<T>()` marker types it only, with no runtime check, while a Standard Schema validator (e.g. a valibot schema) is **validated at `ctx.schedule()` time**, and a payload that fails it throws there, before the run is even queued.

```typescript [report.ts]
const base = define({
  env: t<Env>(),
  capabilities: [
    scheduled({
      report: { data: t<{ userId: string }>() },
    }),
  ],
})

const handleReport = base.scheduled('report', {
  run(ctx, data) {
    buildReport(data.userId) // data: { userId: string }
  },
})
```

Queue it with the matching `data`:

```typescript [handlers.ts]
ctx.schedule('report', {
  time: Date.now() + 60_000,
  data: { userId: ctx.identity },
})
```

## Recurring and retrying tasks

A task's behavior — `every` (recurring interval), `retry` (backoff policy), and whether it carries `data` — is set on the **declaration**, in the [`scheduled({...})`](/server/capabilities/scheduled) capability, not here. The body is the same either way: a recurring task just fires repeatedly, and a retried task re-runs its body on failure.

```typescript [tasks.ts]
const base = define({
  env: t<Env>(),
  capabilities: [
    scheduled({
      heartbeat: { every: 30_000 }, // recurs every 30s
      sync: { retry: [1000, 5000, 15000] }, // retries with this backoff
    }),
  ],
})

const handleHeartbeat = base.scheduled('heartbeat', {
  run(ctx) {
    ctx.broadcast('tick', { at: Date.now() })
  },
})

const handleSync = base.scheduled('sync', {
  run() {
    if (!doSync()) throw new Error('sync failed') // a throw triggers the declared retry
  },
})
```

A recurring task cannot also carry a `data` payload — it has no caller to supply one. The default `retry: true` policy is 3 retries with a `[1000, 5000, 25000]` ms backoff. A task that exhausts its retries lands in the **dead-letter queue** — a durable, queryable SQL table named `__wskit_scheduled_dlq` you can read with `ctx.sql`. The full set of declaration options and the dead-letter behavior live in [the `scheduled()` capability](/server/capabilities/scheduled).

Because a run can fire more than once — a retry, or a re-fire after the server crashed mid-run — **task bodies must be idempotent**. See [At-least-once delivery](/server/capabilities/scheduled#at-least-once-delivery) for what to guard.

## Declaration and body must match

Every declared task needs exactly one body, and every body needs a matching declaration. `assemble()` enforces both:

| Mistake                                                                  | Error                                                                                                      |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| A task declared in `scheduled({...})` with no `base.scheduled(...)` body | `No handler for scheduled task '<taskId>'. Add base.scheduled('<taskId>', ...) and pass it to assemble().` |
| A `base.scheduled(...)` body whose ID isn't declared                     | `base.scheduled('<taskId>') has no matching declaration. Declare it in the scheduled({ ... }) capability.` |

Binding an undeclared task ID is also a compile error — `taskId` is typed to the IDs you declared, so a typo fails before it ever reaches `assemble()`.
