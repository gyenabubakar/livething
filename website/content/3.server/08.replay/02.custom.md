Built-in replay stores messages for you in WSKit's own table. Custom replay puts you in control: **you** decide where messages go and how they come back. Use it when you want a schema of your own, a database you already run, an external store, or filtering the built-in modes do not cover.

You enable it with the `replay.custom()` capability, then register a `base.replay({ ... })` hook with up to three functions.

```typescript [custom-server.ts]
import { define, emits, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { replay } from '@wskit/server/replay'
import { sequence } from '@wskit/server/sequence'
import * as v from 'valibot'

const Note = v.object({ text: v.string(), author: v.string() })
const AddNote = v.object({ text: v.string() })

const base = define({
  env: t<Env>(),
  capabilities: [
    emits({ note: t<v.InferOutput<typeof Note>>() }),
    dedup(),
    sequence({ persist: true }),
    replay.custom(),
  ],
})
```

::note
`replay.custom()` does **not** require `dedup()` or `sequence({ persist: true })` the way built-in replay does — you own the storage and the sequencing. Most real handlers list them anyway because they want stable sequence numbers to use as a replay cursor, as the example above does.
::

## The three hooks

`base.replay({ ... })` takes three functions. Only `replay` (the resend) is required.

| Hook                   | When it runs                                        | What you do                                                                                               |
| ---------------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `beforeSend(ctx, msg)` | synchronously, before each outgoing message is sent | Write the message into your store. This is "store before send" — strict durability.                       |
| `afterSend(ctx, msg)`  | after each message is sent (may be async)           | Write the message into your store. This is "store after send" — best-effort durability, lower latency.    |
| `replay(ctx, since)`   | when a client reconnects and asks for replay        | Read your store for everything newer than `since`, and call `ctx.sendReplay(...)` for each. **Required.** |

You usually pick **one** of `beforeSend` / `afterSend` to write, and use `replay` to read back. The fixture below uses both: `beforeSend` inserts the row, and `afterSend` marks it confirmed once the send actually happened.

```typescript [custom-hooks.ts]
base.replay({
  beforeSend(ctx, msg) {
    ctx.sql.exec(
      'INSERT INTO _custom_replay (event, payload, seq, message_id) VALUES (?, ?, ?, ?)',
      msg.event,
      JSON.stringify(msg.payload),
      msg.wire.seq,
      msg.wire.messageId,
    )
  },
  afterSend(ctx, msg) {
    ctx.sql.exec(
      'UPDATE _custom_replay SET confirmed = 1 WHERE seq = ?',
      msg.wire.seq,
    )
  },
  replay(ctx, since) {
    const rows = ctx.sql
      .exec<{
        event: string
        payload: string
        seq: number
        message_id: string
      }>(
        'SELECT event, payload, seq, message_id FROM _custom_replay WHERE seq > ? ORDER BY seq ASC',
        since,
      )
      .toArray()

    for (const row of rows) {
      ctx.sendReplay(row.event, JSON.parse(row.payload), {
        seq: row.seq,
        messageId: row.message_id,
      })
    }
  },
})
```

Create the table once in `base.onInit(...)`:

```typescript [custom-init.ts]
base.onInit((ctx) => {
  ctx.sql.exec(`
    CREATE TABLE IF NOT EXISTS _custom_replay (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      event TEXT NOT NULL,
      payload TEXT NOT NULL,
      seq INTEGER NOT NULL,
      message_id TEXT NOT NULL,
      confirmed INTEGER NOT NULL DEFAULT 0
    )
  `)
})
```

## What the hooks receive

### The message in `beforeSend` / `afterSend`

Each write hook gets `(ctx, msg)`. The `msg` has the clean event and payload plus a `wire` object you use as a storage key and cursor:

| `msg` field              | Type                      | Notes                                                                        |
| ------------------------ | ------------------------- | ---------------------------------------------------------------------------- |
| `msg.event`              | `string`                  | the event name                                                               |
| `msg.payload`            | `Record<string, unknown>` | the application payload, already clean                                       |
| `msg.wire.seq`           | `number`                  | per-connection sequence number — your replay cursor                          |
| `msg.wire.messageId`     | `string`                  | unique message ID — a good storage key, and what the client de-duplicates on |
| `msg.wire.channel`       | `string \| null`          | concrete channel name when the message came from a channel, else `null`      |
| `msg.wire.channelFamily` | `string \| null`          | family key for a dynamic channel, else `null`                                |

The `ctx` here gives you `sql`, `kv`, `env`, `log`, `platform`, and `meta` (the per-connection metadata from `upgrade`).

### The context in `replay`

The `replay` hook gets `(ctx, since)`. `since` is the last sequence number the client received — resend everything after it. The `ctx` adds:

- `ctx.sendReplay(event, payload, wire)` — resend one stored message.
- `ctx.request.channel` / `ctx.request.channelFamily` — the routing markers from the client's replay request (`null` for an unscoped top-level request). Use them to filter which rows to send back. In a channel-scoped hook you get `ctx.channel.name` instead.
- `ctx.id`, `ctx.meta`, `ctx.sql`, `ctx.kv`, `ctx.env`, `ctx.log`, `ctx.platform`, `ctx.waitUntil(...)`.

## The contract gate on sendReplay

`ctx.sendReplay(...)` is checked at runtime, exactly like the built-in one. The event must be declared as an outgoing event for the active scope, and the payload must be a plain record. Send an undeclared event and it throws — your `replay` hook can catch that and report it instead of crashing the resend:

```typescript [guarded-replay.ts]
replay(ctx, since) {
  // The type surface only offers declared events; you only hit this by casting past it.
  try {
    ctx.sendReplay('not-declared-event', { ok: true }, { seq: 1, messageId: 'bad-1' })
  } catch (err) {
    const message = err instanceof Error ? err.message : String(err)
    ctx.log.warn('replay rejected an undeclared event', { message })
  }
  // ...resend your real rows
}
```

## The cascade behavior

A **top-level** custom replay sees more than just top-level messages. By default it also observes **channel** traffic — the cascade. So one `base.replay({ ... })` can record everything: top-level sends and every channel's sends, all into one store. That is why `msg.wire.channel` and `msg.wire.channelFamily` exist on the write hooks: persist them so the `replay` hook can filter accurately when a client asks for one scope.

A channel that registers **its own** `channel.replay({ ... })` claims that scope — the top-level cascade then skips it, and the channel-level hook owns it. This mirrors how built-in server-level and channel-level replay divide work.

Here is a cascading store that records the scope on every row and filters by it on resend:

::code-group

```typescript [cascade-write.ts]
base.replay({
  beforeSend: (ctx, msg) => {
    ctx.sql.exec(
      'INSERT INTO _cascade_replay (event, payload, seq, message_id, channel, channel_family) VALUES (?, ?, ?, ?, ?, ?)',
      msg.event,
      JSON.stringify(msg.payload),
      msg.wire.seq,
      msg.wire.messageId,
      msg.wire.channel, // null for top-level, the name inside a channel
      msg.wire.channelFamily, // null unless it is a dynamic family
    )
  },
  replay: (ctx, since) => {
    const requestedChannel = ctx.request.channel
    const requestedFamily = ctx.request.channelFamily
    type Row = {
      event: string
      payload: string
      seq: number
      message_id: string
      channel: string | null
      channel_family: string | null
    }

    const rows: Row[] = requestedChannel
      ? ctx.sql
          .exec<Row>(
            'SELECT event, payload, seq, message_id, channel, channel_family FROM _cascade_replay WHERE seq > ? AND channel = ? AND ((channel_family IS NULL AND ? IS NULL) OR channel_family = ?) ORDER BY seq ASC',
            since,
            requestedChannel,
            requestedFamily,
            requestedFamily,
          )
          .toArray()
      : ctx.sql
          .exec<Row>(
            'SELECT event, payload, seq, message_id, channel, channel_family FROM _cascade_replay WHERE seq > ? AND channel IS NULL ORDER BY seq ASC',
            since,
          )
          .toArray()

    for (const row of rows) {
      ctx.sendReplay(row.event, JSON.parse(row.payload), {
        seq: row.seq,
        messageId: row.message_id,
        channel: row.channel ?? undefined,
        channelFamily: row.channel_family ?? null,
      })
    }
  },
})
```

```typescript [cascade-channels.ts]
const lobby = base.channel('lobby', {
  outgoing: { emits: { note: t<v.InferOutput<typeof Note>>() } },
})

const room = base.channel(['rooms', 'room-{id}'], {
  outgoing: { emits: { note: t<v.InferOutput<typeof Note>>() } },
})

// Both channels' `note` sends flow into the one top-level store above,
// because no channel registered its own `.replay(...)`.
const handleLobbyNote = lobby.on('send-note', {
  input: SendNote,
  run(ctx, input) {
    ctx.channel.broadcast('note', { text: input.text })
  },
})
```

::

Notice the two reads. When the client asks for a **channel** scope, the query matches that channel and family. When the client asks at the **top level** (no channel), it matches only rows where `channel IS NULL` — true top-level messages, not channel traffic. That split is the cascade made explicit: one store, queried by scope.

## Channel-scoped custom replay

To give a channel its own store and resend, register `channel.replay({ ... })` on the channel builder. Like `base.replay({ ... })`, this needs `replay.custom()` listed — registering it without the capability throws at build. The hooks look the same, but the context is channel-shaped: the write `msg.wire.channel` is always present, and the `replay` ctx has `ctx.channel.name` instead of `ctx.request`.

```typescript [channel-replay.ts]
const customRoom = base.channel('custom-room', {
  outgoing: { emits: { 'room-note': t<v.InferOutput<typeof RoomNote>>() } },
})

customRoom.replay({
  beforeSend(ctx, msg) {
    ctx.sql.exec(
      'INSERT INTO _custom_room_replay (event, payload, seq, message_id) VALUES (?, ?, ?, ?)',
      msg.event,
      JSON.stringify(msg.payload),
      msg.wire.seq,
      msg.wire.messageId,
    )
  },
  replay(ctx, since) {
    const rows = ctx.sql
      .exec<{
        event: string
        payload: string
        seq: number
        message_id: string
      }>(
        'SELECT event, payload, seq, message_id FROM _custom_room_replay WHERE seq > ? ORDER BY seq ASC',
        since,
      )
      .toArray()

    for (const row of rows) {
      ctx.sendReplay(row.event, JSON.parse(row.payload), {
        seq: row.seq,
        messageId: row.message_id,
      })
    }
  },
})
```

## The membership gate

Channel replay is gated. A client cannot ask for a channel's history unless it is a **member** of that channel. If a non-member sends a replay request scoped to a channel, the engine returns nothing and no error — it does not even reveal that the channel exists. Your channel `replay` hook simply never runs for that connection.

So this hook is safe even though it hands back a secret: it only ever fires for members of `private`.

```typescript [membership-gate.ts]
const privateChannel = base.channel('private', {
  outgoing: { emits: { secret: t<v.InferOutput<typeof Secret>>() } },
})

privateChannel.replay({
  replay(ctx) {
    // Only runs for a connection that is actually subscribed to `private`.
    ctx.sendReplay(
      'secret',
      { text: 'top-secret-history' },
      { seq: 1, messageId: 'm1' },
    )
  },
})
```

You do not write the membership check yourself — WSKit runs it before calling your hook. (A top-level, unscoped replay request has no channel to gate on, so it always runs.)

## The family-key edge case

Dynamic channel families are addressed with `[familyKey, template]`, like `['rooms', 'room-{id}']`. The family key and the matched channel name are usually different — `rooms` versus `room-7`. But they can be **equal**: declare `['rooms', 'rooms']` and a subscribe to `rooms` matches with the family key `rooms` and the name `rooms`.

Replay handles this correctly. The channel is still treated as a **dynamic family**, and replay scoping still works — messages are stored and resent under the right family even when the key and the name happen to be the same string. (The example below uses built-in `replay.history()` to keep it short, but the same family-key handling applies to a custom `channel.replay({ ... })`.)

```typescript [family-key-equals-name.ts]
const base = define({
  env: t<Env>(),
  capabilities: [
    channels(),
    dedup(),
    sequence({ persist: true }),
    replay.history(),
  ],
})

// Family key and template are the same string. Still a dynamic family.
const rooms = base.channel(['rooms', 'rooms'], {
  replay: true,
  outgoing: {
    emits: { 'room-message': t<v.InferOutput<typeof RoomMessage>>() },
  },
})

const handleSendBatch = rooms.on('send-batch', {
  input: SendBatch,
  run(ctx, payload) {
    for (let i = 0; i < payload.count; i++) {
      ctx.channel.broadcast(
        'room-message',
        { text: `msg-${i}` },
        { excludeSelf: false },
      )
    }
  },
})
```

A client that subscribes to `rooms`, misses a batch, and reconnects gets the missed `room-message` events replayed under the `rooms` family — the equal key and name do not confuse the scoping.

## No automatic gap signal

The [eviction watermark and `__gap__` signal](/server/replay/built-in#the-gap-signal-and-the-eviction-watermark) are a **built-in** feature. They exist because WSKit owns the built-in store and knows exactly what it evicted. A custom store is yours, so WSKit can't know when your `replay` hook handed back a truncated tail — it doesn't emit a gap for you.

If your custom store has a bound and you want a reconnecting client to learn it missed evicted messages, track your own high-water-of-evicted-rows and send the frame yourself from the `replay` hook. `ctx.sendReplay` only carries real rows, so emit the gap as a normal declared event and have the client watch for it — you're not tied to WSKit's `onGap` here.

## Rules and limits

- **One hook per scope.** Registering `base.replay({ ... })` twice throws `Duplicate replay hook`. Same for a channel.
- **The capability must be listed.** Calling `base.replay({ ... })` without `replay.custom()` in the capability list throws — it tells you the hook needs the `replay.custom()` capability.
- **Do not list it twice.** Listing `replay.custom()` more than once throws.
- **Custom and built-in are mutually exclusive on a scope.** Listing `replay.history()` (or `replay.snapshot()`) together with `replay.custom()` and registering a hook fails the build with an error mentioning _both_. Pick one strategy per scope. See the [overview](/server/replay/overview).

Custom replay also respects [what replay does not store](/server/replay/overview): protocol frames, request/response replies, and stream chunks never reach your write hooks, so you do not have to filter them out yourself.
