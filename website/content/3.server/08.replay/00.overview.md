A WebSocket can drop. A laptop sleeps, a phone changes networks, a proxy times out. While the socket was gone, your server kept sending messages — chat lines, document updates, presence changes — and the client never saw them. **Replay** fixes that: the server records outgoing messages, and when the client comes back it resends the ones the client missed.

The client side is automatic. WSKit's client tracks the last sequence number it saw and, on reconnect, asks the server for everything newer. Your handlers do not change. Turn replay on, and a reconnecting client catches up on its own.

## When replay runs

Replay fires in two moments:

- **On reconnect.** The socket dropped and came back. The client sends its last known sequence number, and the server resends every recorded message after it.
- **On a fresh channel subscribe.** A client subscribes to a channel for the first time and gets the recent backlog for that channel — the last few messages, or the latest state, depending on the strategy. See [Channels](/server/channels/overview) for how subscribe-time replay ties into channel membership.

In both cases the flow is the same: the client names a cursor, the server reads its store, and the missing tail is sent back as replay frames the client de-duplicates against what it already has.

## Two ways to do it

WSKit ships two built-in strategies, and a hook for writing your own.

| Strategy               | Who stores the messages                  | Best for                                                                     |
| ---------------------- | ---------------------------------------- | ---------------------------------------------------------------------------- |
| `replay.history(...)`  | WSKit (every message kept)               | Chat, feeds, logs — anything where the full sequence matters                 |
| `replay.snapshot(...)` | WSKit (latest value per key)             | Documents, counters, presence — anything where only the newest state matters |
| `replay.custom()`      | You (your own SQL / KV / external store) | Custom storage, custom filtering, or talking to a database you already run   |

Built-in replay and custom replay are **mutually exclusive on the same scope**. Listing both `replay.history()` (or `replay.snapshot()`) and `replay.custom()` together, then registering a `base.replay({ ... })` hook, fails the build with an error that mentions you configured _both_. Pick one per scope.

- [Built-in replay](/server/replay/built-in) — `replay.history` and `replay.snapshot`, their config, and when to use which.
- [Custom replay](/server/replay/custom) — own the storage and the resend with a `base.replay({ ... })` hook.

The capability registration at a glance lives on the [`replay` capability page](/server/capabilities/replay); this chapter owns the deep behavior.

::note
Built-in replay (`history` / `snapshot`) requires `dedup()` and `sequence({ persist: true })` — it resends by sequence number, so both must be listed or the build fails. `replay.custom()` owns its own storage and needs neither.
::

Top-level replay **applies to channels too**: a channel that does not set its own replay scope is covered by the server-level store, so its messages replay as well. Opt one channel out with `replay: false` in its config, or give it its own strategy with `replay: true` / `channel.replay(...)`.

## What replay does not store

This is the important detail to understand. Replay records **your declared outgoing events** — the ones you send with `ctx.send`, `ctx.broadcast`, or their channel equivalents. It skips a few kinds of message on purpose, because resending them would be wrong.

| Message kind                                                                                                                     | Why it is skipped                                                                                                      |
| -------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Protocol and control frames** — subscribe acknowledgements, presence syncs, error frames, and other internal tracking messages | They carry no sequence number and are rebuilt on reconnect, so they are never recorded.                                |
| **Request/response replies** — a reply to a [request](/server/capabilities/requests), carrying a correlation ID                  | It belongs to one in-flight call. Replaying it later makes no sense.                                                   |
| **Stream chunks** — from a [stream](/server/streams/overview), carrying a stream ID                                              | They have their own resume machinery ([durable streams](/server/streams/durable-resumable)); replay leaves them alone. |

On top of that, built-in replay lets you name an `exclude` list of high-frequency events you never want resent — cursor moves, typing indicators, anything where stale data is just noise. Excluded events still send normally; they are only kept out of the replay store.

::note
Replay does not change what a client receives **live**. Every event still goes out the moment you send it. Replay only adds a recording so a client that was away can ask for the part it missed.
::

## Where the messages live

Built-in replay keeps its store in the server's **own** SQL storage (via `ctx.sql`) — the same place the persistent sequence counter lives. That is why the [capability page](/server/capabilities/replay) can say you do not list `persistence()` for built-in replay: it is not using the shared persistence surface, it manages its own tables.

The model is one **store per scope**, and there are only two kinds of scope:

- **One top-level store** for every message that isn't channel-scoped.
- **One store per channel** that runs its own replay (a channel with `replay: true`, or a channel-level strategy).

Each store is bounded on its own by [retention](/server/replay/built-in#history-config) — `maxMessages` and `maxAgeMs` apply _per store_, so a busy channel evicting old rows never touches the top-level backlog or another channel's. What a store holds depends on the mode: **history** keeps every replayable row, **snapshot** keeps only the latest row per logical key. Alongside each store the server also remembers how far it has evicted — the **eviction watermark** — which is what turns a bounded store into a truthful catch-up (see the next section).

One more property that matters for catch-up: a broadcast is stamped with **one** sequence number and **one** message ID shared by every recipient, so it becomes **one replay row**, not one per subscriber. The client orders replayed rows by `seq` and drops repeats by `messageId`, so a resend that overlaps what the client already had folds away cleanly.

## When catch-up has a hole

Retention is bounded, so a client can be away long enough that history it hadn't caught up on is already gone. The server can't resend rows it has deleted — but it doesn't let the hole pass silently either. It tracks, per store, the highest sequence it has **evicted** (the eviction watermark). When a reconnecting client asks to catch up from sequence _N_ and _N_ sits **below** that watermark, the server knows rows the client hadn't seen are gone, and sends a `__gap__` frame for that scope **before** the tail it can still resend.

The client's [`onGap`](/client/primitives/replay) surfaces it, carrying `missedThrough` — the highest sequence that was dropped — so the app knows to refetch from its API rather than assume it's up to date. This only applies to **history** mode: snapshot mode always resends the current state of every key, so there is nothing to be "behind" and no gap is ever emitted. A brand-new client loading from sequence `0` also never gets a gap — a gap is only meaningful against a cursor the client actually had.

The same `__gap__` signal marks an [inbox overflow](/server/inbox/overflow-and-gap), where a member's oldest held rows were evicted while they were behind — one signal, two sources, surfaced through the same `onGap`.
