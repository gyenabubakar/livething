A WebSocket connection starts as a normal HTTP request that asks the server to switch ("upgrade") the connection to the WebSocket protocol. This first exchange is the **handshake**. The `authenticate` option of `server(...)` runs when a connection opens. In it, you **authenticate** the request and decide whether to let the connection in.

LiveThing does not give you one environment object that works on every runtime. Configuration (API URLs, secret keys and similar values) belongs to the runtime you deploy on. Node code can read `process.env`. A Cloudflare Durable Object can read its **bindings** in three places: from `ctx.platform.env` inside a handler, from `ctx.platform.env` in your [`authenticate` function](#the-authenticate-ctx), or from the `env` argument of your Worker entry point. Read runtime-specific configuration in runtime-specific code. When shared handlers or plugins need a value, pass it to them directly.

`ctx.platform` is the runtime's own object. Use it only when you need a runtime feature that LiveThing does not wrap. On Cloudflare, type it with the `Platform` type from `@livething/server-cloudflare` (or with the `cloudflare:workers` types generated for your Worker):

```typescript [server/scout-health.ts]
import type { Platform } from '@livething/server-cloudflare'
import { base } from './base'

interface Env {
  SCOUT_API_KEY: string
}

export const handleCheckScoutHealth = base.on('check-scout-health', {
  run(ctx) {
    const platform = ctx.platform as Platform<Env>
    const configured = platform.env.SCOUT_API_KEY.length > 0
    ctx.send('notification', {
      title: 'Scout',
      body: configured ? 'ready' : 'not configured',
    })
  },
})
```

A plugin that needs configuration should take it as an argument of the function that creates the plugin (its **factory**). The app chooses the value when it adds the plugin, so the plugin does not read any hidden environment:

```typescript [polls/polls-definition.ts]
import { emits, server, t } from '@livething/server'
import { plugin } from '@livething/server/plugins'

export function pollsPlugin(config: { topic: string }) {
  const pluginBase = server({
    scope: 'plugin',
    capabilities: [
      emits({ 'poll-topic-set': t<{ topic: string }>() }),
    ],
  })
  const createPoll = pluginBase.on('create-poll', {
    run(ctx) {
      ctx.send('poll-topic-set', { topic: config.topic })
    },
  })
  return plugin('acme:polls', {
    definition: pluginBase.assemble({ handlers: [createPoll] }),
  })
}

const base = server({
  capabilities: [pollsPlugin({ topic: 'general' })()],
})
```

## `authenticate`: the auth hook

`authenticate` runs once per connection, when the connection opens and before any handler. It receives the raw `Request`, with everything an HTTP request carries: headers, URL and cookies. It also receives a `ctx` with storage, a logger and the platform (see [The `authenticate` ctx](#the-authenticate-ctx)). It decides whether the connection is accepted or rejected.

In the example below, the client sends its login token with the [`token` option](/client/connecting/auth-and-query#token-auth-with-token), and the server reads it from the `Authorization` header as `Bearer <token>`:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectAuth } from '@livething/server/errors'
import { verifySession } from './auth'

const base = server({
  async authenticate(request) {
    const token = request.headers
      .get('Authorization')
      ?.replace('Bearer ', '')
    const user = await verifySession(token)
    if (!user) {
      throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [],
})
```

A browser `WebSocket` cannot set an `Authorization` header, so the client sends the token in the handshake's `Sec-WebSocket-Protocol` header. LiveThing moves it to `Authorization` and removes it from `Sec-WebSocket-Protocol` before `authenticate` runs, so `authenticate` reads it the same way from every client. If the request already has a real `Authorization` header, that header wins. A token entry that does not decode gets HTTP `400`, and `authenticate` does not run. On the [server-sent events](/server/adapters/transports) transport, the client sends a normal `Authorization: Bearer` header when the stream opens, so `authenticate` reads the token the same way there too.

`authenticate` can be `async`. Return a value to **accept** the connection. Throw `RejectAuth(code, reason)` to **reject** it.

::note
Besides `token`, a browser can send a credential with **cookies**. It sends them automatically when the socket is on the same domain as the page (same-origin). Read them from the `cookie` header.
::

### Reading the request

The argument is a standard `Request`. These are the common values to read from it:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'

const base = server({
  async authenticate(request) {
    const url = new URL(request.url)
    const room = url.searchParams.get('room') // query string
    const cookie = request.headers.get('cookie') // cookies
    const auth = request.headers.get('authorization') // 'Bearer <token>' from the client's `token`

    // ... validate, then return the accept value
    return {}
  },
  capabilities: [],
})
```

### Client IP

When an adapter can safely find the real address of the client, it adds that address to the same request, in a header:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'

const base = server({
  async authenticate(request) {
    const clientIp = request.headers.get('LiveThing-Client-IP')

    if (clientIp) {
      // use the verified client address for your policy or audit record
    }

    return {}
  },
  capabilities: [],
})
```

`LiveThing-Client-IP` is optional. It is `null` when the runtime cannot verify an address. It is a header that LiveThing sets. It is not a standard `Request` property. If a client sends its own `LiveThing-Client-IP` header, the adapter removes it. Do not read a forwarded-address header (such as `X-Forwarded-For`) yourself here. The adapter decides which proxy addresses it trusts before it sets this value. See your adapter page for how that runtime finds the address.

### Guest join

A small, common pattern is a guest join: a room invite link carries only a display name, with no account behind it. Here `authenticate` does not call `verifySession`.

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectAuth } from '@livething/server/errors'

const base = server({
  async authenticate(request) {
    const name = new URL(request.url).searchParams.get('name')
    if (!name) {
      throw RejectAuth(CloseCodes.AUTH_INVALID, 'missing name')
    }

    return {
      userId: crypto.randomUUID(),
      meta: { name, role: 'guest' as const },
    }
  },
  capabilities: [],
})
```

### The `authenticate` `ctx`

The app's `authenticate` receives a second argument, `ctx`. It has the same four members as the [`onInit`](/server/lifecycle-and-intercept/hooks) context:

::field-group
::field{name="ctx.sql" type="SQLProvider"}
Your SQL database. Tables that you create in `onInit` already exist, because `onInit` finishes before the first handshake.
::

::field{name="ctx.kv" type="KVProvider"}
The key-value store.
::

::field{name="ctx.log" type="Logger"}
The structured logger.
::

::field{name="ctx.platform" type="unknown"}
The runtime's own object. On Cloudflare it is `Platform<Env>`, with `env` and part of the Durable Object state as `ctx`.
::
::

No connection exists yet, so `ctx` has no `user`, `meta`, `send` or `broadcast`. A session table in SQL is a typical use. This example reads sessions from SQL instead of calling `verifySession`, and it assumes that `onInit` creates a `sessions` table:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectAuth } from '@livething/server/errors'

const base = server({
  async authenticate(request, ctx) {
    const token = request.headers
      .get('Authorization')
      ?.replace('Bearer ', '')
    const session = ctx.sql
      .exec<{
        userId: string
        name: string
        role: 'admin' | 'member'
      }>(
        'SELECT user_id AS userId, name, role FROM sessions WHERE token = ?',
        token,
      )
      .one()
    if (!session) {
      throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: session.userId,
      meta: { name: session.name, role: session.role },
    }
  },
  capabilities: [],
})
```

::note
A plugin's `authenticate` receives `ctx` too, but it is the plugin's own scoped `ctx`: its `ctx.kv` keys are namespaced to the plugin, like the keys in its handlers. Inside it, `context.authenticate(pluginBase)` returns that `ctx`, where `pluginBase` is the plugin's own `server({ scope: 'plugin' })` result.
::

## What `authenticate` returns

The accept value is an `AuthReturn`. All three fields are optional.

::field-group
::field{name="userId" type="string"}
Optional. The stable ID of the user behind this socket. It is the key for stored per-user data, and channels use it to find the same user again after a reconnect. Leave it out (or return an empty string) to accept the connection as anonymous. The maximum length is 256 characters. The ID also cannot start with `__`, because LiveThing keeps that prefix for its own storage keys. If the ID breaks either rule, LiveThing throws an error when it accepts the connection. A longer ID is not shortened, because two long IDs shortened to the same text would share one storage row. Use a stable ID, such as the user's database ID or a ULID. Do not use a token. Almost every app sets this field.
::

::field{name="meta" type="TMeta"}
Optional. Per-connection data, which every handler reads as `ctx.meta`. Its type becomes the type of `ctx.meta`. For example, return `{ userId: 'u1' }` and `ctx.meta.userId` is typed as `string`. The default is `{}`.
::

::field{name="tags" type="{ ephemeral?: { group: key | key[] } }"}
Optional. The first ephemeral tags to attach before any handler runs. A tag is a label (a group name and a key) that you attach to a connection, so you can find or message every connection with that label. Ephemeral tags live only in memory. The keys of this object are the ephemeral group names that you declare in the `tags(...)` capability, so this field is only useful when `tags()` is in your `capabilities`. Each value is one key, or an array of keys when the connection belongs to several keys of the same group, for example a user in two teams. You cannot set persistent tags here. Add them in a handler, with the `add(key)` method of `ctx.tags.persistent(group)`.
::
::

This example adds a `role` tag group next to Huddle's `team` group:

```typescript [server/huddle-definition.ts]
import { server, t } from '@livething/server'
import { CloseCodes, RejectAuth } from '@livething/server/errors'
import { tags } from '@livething/server/tags'
import { verifySession } from './auth'

const base = server({
  async authenticate(request) {
    const token = request.headers
      .get('Authorization')
      ?.replace('Bearer ', '')
    const user = await verifySession(token)
    if (!user) {
      throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
      // teams is e.g. ['design', 'eng']
      tags: { ephemeral: { role: user.role, team: user.teams } },
    }
  },
  capabilities: [
    tags((ephemeral) => [
      ephemeral('role', t<string>()),
      ephemeral('team', t<string>()),
    ]),
  ],
})
```

::caution
The compiler checks the group names in `tags.ephemeral` only in some cases. If you list `tags(...)` and return only a misspelled group, you get a compile error. But if you return a correct group and a misspelled one together, or if `tags()` is not in your `capabilities`, the code compiles. At runtime, an undeclared group makes the handshake fail with HTTP `500` (`Authentication failed`). The error message is:

```text
onAuthenticate returned an ephemeral tag for group '<name>', which is not declared under tags (ephemeral)
```

Check that each group name matches the `tags(...)` capability exactly.

If the group has a schema (see [Tags](/server/capabilities/tags)), LiveThing checks the tag key against it too, the same check `ctx.tags.ephemeral(group).add(key)` runs later. A key that fails the schema also fails the handshake with HTTP `500`.
::

### `userId` is the durable key

`userId` is more than a label. LiveThing uses it as the key for stored per-user data, and to add a returning user back to the channels with `membership: 'persistent'` that they belong to. Give the same person the same `userId` on every connection, and their stored data and those memberships stay with them after a reconnect. For more about tags and rejoining channels, see [Channels](/server/channels/overview) and the [tags capability](/server/capabilities/tags).

Inside any handler or hook, read the value as `ctx.user.id`. It is a `string`, and it is empty for an anonymous socket. This handler goes in the same file as `base`:

```typescript [server/huddle-definition.ts]
export const handleWhoami = base.on('whoami', {
  run(ctx) {
    ctx.send('notification', {
      title: 'You',
      body: ctx.user.id, // the value from authenticate()
    })
  },
})
```

### The `AuthFn` and `AuthReturn` types

If you write the gate as a separate function (for example, to reuse it in more than one server), use these types:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectAuth } from '@livething/server/errors'
import type { AuthFn, AuthReturn } from '@livething/server'
import { verifySession } from './auth'

// AuthReturn<TMeta> = { userId?: string; meta?: TMeta; tags?: {...} }
// AuthFn<TMeta>     = (request: Request, ctx: InitContext) => AuthReturn<TMeta> | Promise<...>

type SessionMeta = {
  name: string
  role: 'admin' | 'member' | 'guest'
}

const requireSession: AuthFn<SessionMeta> = async (
  request,
): Promise<AuthReturn<SessionMeta>> => {
  const token = request.headers
    .get('Authorization')
    ?.replace('Bearer ', '')
  const user = await verifySession(token)
  if (!user) {
    throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
  }

  return {
    userId: user.id,
    meta: { name: user.name, role: user.role },
  }
}

const base = server({
  authenticate: requireSession,
  capabilities: [],
})
```

A plugin's scoped `authenticate` has the same shape. Its type is `ScopedAuthFn`, which the package also exports. [Plugins › Authoring](/server/plugins/authoring#the-scoped-authenticate) covers it.

## Anonymous connections

`authenticate` is optional. If you leave it out, the connection is still **accepted**, but it is anonymous:

- `userId` is `''`
- `meta` is `{}`
- there are no tags

```typescript [server/huddle-definition.ts]
const base = server({
  capabilities: [],
  // no authenticate: every connection is accepted as anonymous
})
```

An `authenticate` function can also accept a connection as anonymous. Return no `userId` (or an empty string):

```typescript [server/huddle-definition.ts]
const base = server({
  authenticate() {
    return { meta: {} } // accepted, anonymous
  },
  capabilities: [],
})
```

Anonymous connections do not share one user, and they do not become [users](/server/context-and-storage/users). Each one has no user identity. `ctx.user` exists, but it points to no user. Some stored data must not be shared between two anonymous sockets, for example the read position of each member of a broadcast stream. For that data, LiveThing uses the connection's own ID as the storage key internally. An anonymous connection cannot start a recorded stream at all: the server rejects it with `DurableStreamRequiresUser`. This is only a storage key, not a user identity.

Other stored data exists only to reconnect a returning user: durable channel memberships and persistent tags. An anonymous connection has no stable key to match on a reconnect, so LiveThing **skips** saving this data when `userId` is empty. It does not save it under the connection ID. If every socket must be authenticated, write an `authenticate` that throws `RejectAuth(...)` when credentials are missing.

## Rejecting a connection

Throw `RejectAuth(code, reason)` to refuse a connection when it opens. The `code` decides what the client sees: an HTTP error response, or a WebSocket that opens and closes at once.

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectAuth } from '@livething/server/errors'
import { verifySession } from './auth'

const base = server({
  async authenticate(request) {
    const token = request.headers
      .get('Authorization')
      ?.replace('Bearer ', '')
    if (!token) throw RejectAuth(401, 'Missing credentials')

    // HTTP 401
    const user = await verifySession(token)
    if (!user) {
      throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
    }
    // WS close 4002

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [],
})
```

### How the reject code is answered

LiveThing reads the number that you pass to `RejectAuth` by its range:

| `code` you pass                                                                                       | What the client gets                                                                                                                                                                       | When to use it                                                         |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| A valid WebSocket close code (`1000` to `1014` except `1004`, `1005` and `1006`, or `3000` to `4999`) | The handshake completes, then the server closes the socket at once with that code and reason. This is the **only** way a browser `WebSocket` can read the reason (from its `close` event). | When the client is a browser `WebSocket` and you want it to see _why_. |
| `400` to `599` (an HTTP status)                                                                       | That HTTP status, with `reason` as the response body.                                                                                                                                      | For a plain HTTP rejection that `fetch` or a proxy can read.           |
| Any other number (a decimal, a reserved code, or a number out of range)                               | HTTP `403 Forbidden`. The server logs the invalid code.                                                                                                                                    | This is a safe fallback. Use a valid code instead.                     |

So in `authenticate`, the first `throw` below lets a browser client read `'invalid session'` from the close event, and the second returns a real HTTP 401:

```ts
import { CloseCodes, RejectAuth } from '@livething/server/errors'

// The browser reads 'invalid session' from the close event.
throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')

// The client gets an HTTP 401 response.
throw RejectAuth(401, 'Missing credentials')
```

A value such as `4000.5` or `1006` does not become a close frame. It becomes the safe `403` response. Choose the range that matches how your client connects.

On the [server-sent events](/server/adapters/transports) transport, the answer has the same meaning. A close code opens the stream and sends only a `__close__` frame with the code and reason, so the client's `onClose` gets the same code as on a WebSocket. An HTTP status is a normal HTTP error, which the client turns into a close code: `401` becomes `4001` (`AUTH_EXPIRED`), `429` becomes `4005` (`RATE_LIMITED`), and `403` and the other `4xx` statuses become `4002` (`AUTH_INVALID`). See [Codes for a server-sent events stream](/core/close-codes#codes-for-a-server-sent-events-stream). A close code and these `4xx` statuses are final: the client does not try its next transport. A `404`, `405`, `426` or `5xx` means "no answer" to the client, so it tries its next transport.

Any other error thrown inside `authenticate` (anything that is not a `RejectAuth`) rejects the handshake with HTTP `500` and the body `Authentication failed`. LiveThing also logs this case on the server, so you can find the real cause: the client only ever sees the generic `Authentication failed` message.

::tip
WebSocket [close codes](/core/close-codes) from **4000 to 4999** are for application use. Use them when a browser client needs to tell your reasons apart.
::

### The non-WebSocket case

`authenticate` runs only for a request that opens a connection: a WebSocket handshake, or, when the server lists [`sse()`](/server/adapters/transports), a `GET` that opens a server-sent events stream. A POST that carries messages on an open stream does not run it: the user and `meta` come from the connection, set once by `authenticate`. Any other plain request never reaches your `authenticate`. Depending on the adapter, it gets HTTP `426 Upgrade Required` or goes on to your normal HTTP routes. So you do not need to guard against normal HTTP traffic inside it.

### Logging out

`authenticate` runs once, when the connection opens. When a user logs out, an open connection stays open, on every transport. Close it yourself when your app ends the session, with [`ctx.close(...)`](/server/context-and-storage/ctx#closing-the-connection) for one connection, or `ctx.users.get(userId).close(...)` for every connection of [the user](/server/context-and-storage/users#ctxusers-reaching-any-user-by-id).

## A scoped `authenticate`

A plugin can have its own `authenticate` in its scoped server definition (`server({ scope: 'plugin', ... })`). It runs before the app's `authenticate`, so it does not see the app's `userId`. Like the app's `authenticate`, it receives a `ctx` as its second argument, but a scoped one. Its `meta` is merged into the connection's `meta`. [Plugins › Authoring](/server/plugins/authoring) covers this variant.
