`server(config)` is the entry point for every LiveThing server. It takes a small config object and returns a **builder**. A builder is an object whose methods create the parts of your server. This section calls it `base`. Its methods create routed handlers (a routed handler is a function that runs for one named event) and register other server work. The types of those methods come from the config you passed. The path is always the same: call `server`, register handlers on `base`, then call `base.assemble(...)`.

## What `server` returns

The return value is a builder. It is **not** a running server, and it holds no state about any connection. It is a typed factory: you call its methods to create routed handler values or to register server work. Then you collect the routed values with `assemble`.

```typescript [server/huddle.ts]
import { emits, server, t } from '@livething/server'

const base = server({
  capabilities: [
    emits({
      'status-changed': t<{ userId: string; status: string }>(),
    }),
  ],
})

// base.on is always present
const handleSetStatus = base.on('set-status', {
  run(ctx) {
    ctx.broadcast('status-changed', {
      userId: ctx.user.id,
      status: 'active',
    })
  },
})

// base.request exists only when clientRequests() is in capabilities.
// It is not listed here, so calling base.request(...) is a compile error.

export const definition = base.assemble({
  handlers: [handleSetStatus],
})
```

The builder always has these methods:

- `base.on`
- the lifecycle hooks: `onInit`, `onConnect`, `onDisconnect`, `onPing`, `onPong`, `onError`, `onValidationError` and `onShutdown`
- the `onOutgoing` hook, which sees every frame the server sends
- `assemble`

Every other method exists only when the matching capability is in your `capabilities` list. A capability is an opt-in feature that you list in the config. These methods are `request`, `stream`, `resumableStream`, `recordedStream`, `channel`, `scheduled`, `intercept` (which sees every frame the server receives, and needs the `intercepts()` capability) and `replay` (a custom replay strategy). [Handlers](/server/handlers/overview) covers these methods. [Lifecycle and intercept](/server/lifecycle-and-intercept/overview) covers the hooks.

## The config shape

```typescript [server/huddle.ts]
const base = server({
  upgrade(request) {
    /* ... */
  }, // optional: the auth gate
  users: { maxConnections: 3, onExceed: 'replace' }, // optional: connection limit per user
  capabilities: [
    /* ... */
  ], // optional: opt-in features
  hibernation: { enabled: true }, // optional: Cloudflare hibernation
  translate: legacy, // optional: one translator for another wire format
})
```

| Field          | Required | What it does                                                                                                                                                                                                                                                                                                       |
| -------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `upgrade`      | no       | The handshake gate. It reads the raw `Request`. It returns `{ userId?, meta?, tags? }` to accept the connection, or throws `RejectUpgrade(code, reason)` to reject it. If you leave it out, every connection is accepted as anonymous (a connection with no user identity). See [Upgrade](/server/server/upgrade). |
| `users`        | no       | `{ maxConnections?, onExceed }`. It limits how many open connections one user can have at the same time. `onExceed: 'reject'` refuses the new connection. `'replace'` closes the user's oldest connection(s) to make room. Leave it out for no limit. See [Users](/server/context-and-storage/users).              |
| `capabilities` | no       | The list of opt-in features. Each one adds engine code to your bundle, and some add a builder method. Leave it out for a server that has only `base.on` and the hooks. See [Capabilities](/server/server/capabilities).                                                                                            |
| `hibernation`  | no       | `{ enabled: boolean }`. It turns on Cloudflare Durable Object hibernation, which removes idle objects from memory. Only the Cloudflare adapter supports it. Other adapters fail at startup when it is on. See [Hibernation](/server/server/hibernation).                                                           |
| `translate`    | no       | One server-only translator factory. A translator converts another WebSocket wire format (the shape of messages on the connection) to and from LiveThing's format, at the edge of each connection. It is not a capability or a plugin. See [Translation](/server/server/translation).                               |

That is the whole config. `server` holds only **bootstrap** settings: the things the runtime needs to start and accept a connection. Any other behavior is either a config field, such as `hibernation` or `translate`, or a capability in the `capabilities` list.

::note
There is one more form: `server({ scope: 'plugin', ... })`. It creates a server definition for a plugin. See [Plugins › Authoring](/server/plugins/authoring).
::

## The config sets the types

What you put in the config sets the builder's types:

- The return type of **`upgrade`** sets the type of `ctx.meta`. If `upgrade` returns `{ meta: { role: string } }`, then `ctx.meta.role` is typed as `string` in every handler.
- **`capabilities`** decide which builder methods exist and which `ctx` fields exist. For example, list `clientRequests()` and `base.request` appears. Leave it out and calling `base.request` is a compile error.

```typescript [typed.ts]
import { emits, server, t } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    clientRequests(),
    emits({ notification: t<{ title: string; body: string }>() }),
  ],
})

const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  run(ctx, input) {
    // ctx.meta.role  → 'admin' | 'member' | 'guest'   (from upgrade)
    // base.request   → exists                          (from clientRequests())
    return loadProfile(input.userId)
  },
})

export const definition = base.assemble({
  handlers: [handleGetProfile],
})
```

## From `server` to `assemble`

You always follow the same three steps:

::steps{level="3"}

### Call `server`

Pass the config. Store the returned builder in a `const`, usually named `base`.

```typescript [step-1.ts]
const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    emits({
      message: t<Message>(),
      notification: t<{ title: string; body: string }>(),
    }),
  ],
})
```

### Register handlers and hooks

Call builder methods to create routed handler values. Register lifecycle hooks and scheduled task bodies (the function that runs when a scheduled task fires) directly on `base`. Routed handlers are values you can export. Direct registrations return nothing.

```typescript [step-2.ts]
base.onConnect((ctx) => {
  ctx.send('notification', {
    title: 'Welcome',
    body: `hi, ${ctx.meta.name}`,
  })
})

export const handleSendMessage = base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

### Assemble

Pass every routed handler value to `assemble`. You do not pass the upgrade gate, hooks, scheduled task bodies, the intercept or the listed capabilities. `assemble` adds them for you. The result is a `ServerDefinition`, which an adapter runs.

```typescript [step-3.ts]
export const huddle = base.assemble({ handlers: [handleSendMessage] })
export type HuddleSocket = InferClient<typeof huddle>
```

::

`assemble` finalizes and checks the server. It throws when you build the server (before any connection opens) for mistakes like these:

- Two handlers on the same event name. This includes two different kinds of handler, for example an `on` and a `request` with the same name.
- A scheduled task declared in `scheduled({...})` with no body, or a `base.scheduled` body for a task that was never declared.
- A per-handler `rateLimit` setting when the `rateLimit()` capability is not listed.
- A capability passed to `assemble`. Capabilities belong in `server`. (This is also a type error.)

::warning
Lifecycle hooks (`onInit`, `onConnect`, `onDisconnect`, `onPing`, `onPong`, `onError`, `onValidationError`, `onShutdown`, `intercept`, `onOutgoing`) and scheduled task bodies are checked when you register them. A second hook for the same lifecycle event, or a second body for the same task ID, throws at once. It does not wait for `assemble`.
::

## Splitting across files

The builder and its handlers are plain values. So you can export `base` from one file and create handlers in other files. This keeps a large server readable.

::code-group

```typescript [server/huddle.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { requireSession } from './upgrade'

export const base = server({
  upgrade: (request) => requireSession(request),
  capabilities: [
    emits({ notification: t<{ title: string; body: string }>() }),
    channels(),
  ],
})
```

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { base } from './huddle'

export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
})

rooms.subscribe((ctx) => {
  ctx.channel.broadcast('message', {
    id: crypto.randomUUID(),
    text: `${ctx.meta.name} joined the room`,
    from: ctx.user.id,
    sentAt: Date.now(),
  })
})
```

```typescript [server/huddle-definition.ts]
import type { InferClient } from '@livething/server'
import { base } from './huddle'
import { rooms } from './rooms'

export const huddle = base.assemble({ handlers: [rooms] })
export type HuddleSocket = InferClient<typeof huddle>
```
