`server(config)` is the entry point for every LiveThing server. It takes a small config object and returns a **builder**. A builder is an object whose methods create the parts of your server. This section calls it `base`. Its methods create routed handlers. The types of those methods come from the config you passed. The path is always the same: call `server`, create handlers on `base`, then call `base.assemble(...)`.

## What `server` returns

The return value is a builder. It is **not** a running server, and it holds no state about any connection. It is a typed factory: you call its methods to create handler values. Then you collect them with `assemble`.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import * as v from 'valibot'

const base = server({
  capabilities: [
    emits({
      'status-changed': t<{
        userId: string
        status: 'active' | 'away' | 'busy'
      }>(),
    }),
  ],
})

// base.on is always present
const handleSetStatus = base.on('set-status', {
  input: v.object({ status: v.picklist(['active', 'away', 'busy']) }),
  run(ctx, input) {
    ctx.broadcast('status-changed', {
      userId: ctx.user.id,
      status: input.status,
    })
  },
})

// base.request exists only when clientRequests() is in capabilities.
// It is not listed here, so calling base.request(...) is a compile error.

export const huddle = base.assemble({
  handlers: [handleSetStatus],
})
```

The builder always has these methods:

- `base.on`
- `assemble`

Every other method exists only when the matching capability is in your `capabilities` list. A capability is an opt-in feature that you list in the config. These methods are `request`, `stream`, `recordedStream`, `channel` and `scheduled`. [Handlers](/server/handlers/overview) covers these methods.

Hooks are not methods. They are keys in the config: `onInit`, `onConnect`, `onDisconnect`, `onPing`, `onPong`, `onError`, `onShutdown`, `intercept` and `onOutgoing`. [Lifecycle and intercept](/server/lifecycle-and-intercept/overview) covers them.

## The config shape

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import { verifySession } from './auth'

const base = server({
  async authenticate(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    return { userId: user?.id }
  }, // optional: the auth hook
  users: { maxConnections: 3, onExceed: 'replace' }, // optional: connection limit per user
  capabilities: [clientRequests()], // optional: opt-in features
  hibernation: true, // optional: Cloudflare hibernation
  onDisconnect(ctx) {
    ctx.log.info(`${ctx.user.id} left`)
  }, // optional: hooks, after authenticate and capabilities
})
```

::field-group
::field{name="authenticate"}
The [auth hook](/server/server/authenticate). It reads the raw `Request` and gets a `ctx` with `sql`, `kv`, `log` and `platform`. It returns `{ userId?, meta?, tags? }` to accept the connection, or throws `RejectAuth(code, reason)` to reject it. If you leave it out, every connection is accepted as anonymous.
::
::field{name="users"}
`{ maxConnections?, onExceed }`. It limits how many open connections one [user](/server/context-and-storage/users) can have at the same time. `onExceed: 'reject'` refuses the new connection. `'replace'` closes the user's oldest connection(s) to make room. Leave it out for no limit.
::
::field{name="capabilities"}
The list of [opt-in features](/server/server/capabilities). Each one adds engine code to your bundle, and some add a builder method. Leave it out for a server that has only `base.on` and the hooks.
::
::field{name="hooks"}
`onInit`, `onConnect`, `onDisconnect`, `onPing`, `onPong`, `onError`, `onShutdown`, `intercept` and `onOutgoing`. Each is a function. Write them after `authenticate` and `capabilities`. TypeScript reads the object from top to bottom, so a [hook](/server/lifecycle-and-intercept/hooks) above `authenticate` sees `ctx.meta` as `unknown`.
::
::field{name="hibernation"}
`boolean`. `true` turns on Cloudflare Durable Object [hibernation](/server/server/hibernation), which removes idle objects from memory. Only the Cloudflare adapter supports it. Other adapters fail at startup when it is on.
::
::

That is the whole config. Any behavior is a config field, such as `hibernation`, `users` or a hook, or a capability in the `capabilities` list.

::note
There is one more form: `server({ scope: 'plugin', ... })`. It creates a server definition for a [plugin](/server/plugins/authoring).
::

## The config sets the types

What you put in the config sets the builder's types:

- The return type of **`authenticate`** sets the type of `ctx.meta`. If `authenticate` returns `{ meta: { role: string } }`, then `ctx.meta.role` is typed as `string` in every handler.
- **`capabilities`** decide which builder methods exist and which `ctx` fields exist. For example, list `clientRequests()` and `base.request` appears. Leave it out and calling `base.request` is a compile error.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import { CloseCodes, RejectAuth } from '@livething/server/errors'
import * as v from 'valibot'
import { verifySession } from './auth'
import { loadProfile } from './huddle-data'

const base = server({
  async authenticate(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user) {
      throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    clientRequests(),
    emits({ notification: t<{ title: string; body: string }>() }),
  ],
})

const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  run(ctx, input) {
    // ctx.meta.role  → 'admin' | 'member' | 'guest'   (from authenticate)
    // base.request   → exists                          (from clientRequests())
    return loadProfile(input.userId)
  },
})

export const huddle = base.assemble({
  handlers: [handleGetProfile],
})
```

## From `server` to `assemble`

You always follow the same three steps:

::steps{level="3"}

### Call `server`

Pass the config. Store the returned builder in a `const`, usually named `base`.

```typescript [server/session-authenticate.ts]
import { emits, server, t } from '@livething/server'
import { CloseCodes, RejectAuth } from '@livething/server/errors'
import { verifySession } from './auth'
import type { Message } from './base'

const base = server({
  async authenticate(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user) {
      throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    emits({
      message: t<Message>(),
      notification: t<{ title: string; body: string }>(),
    }),
  ],
})
```

### Create handlers

Call builder methods to create routed handler values. Scheduled task handlers are values too. Export them. Hooks are not created here: they are keys in the `server({ ... })` config.

```typescript [server/huddle-handlers.ts]
import * as v from 'valibot'
import { rooms } from './base'

export const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

### Assemble

Pass every routed handler value and every scheduled task handler to `assemble`. You do not pass the `authenticate` hook, the hooks or the listed capabilities. `assemble` adds them for you. The result is a `ServerDefinition`, which an adapter runs. A handler or channel created on a different `server()` base makes `assemble` throw, and so does the same handler passed twice. `server()` and `base.channel()` also throw on an unknown option or a hook that is not a function, so a misspelled option cannot silently drop a check when you write plain JavaScript.

```typescript [server/huddle-assembly.ts]
import type { InferClient } from '@livething/server'
import { base } from './base'
import {
  handleSendDigest,
  handleSendMessage,
} from './huddle-definition'

export const huddle = base.assemble({
  handlers: [handleSendDigest, handleSendMessage],
})
export type HuddleSocket = InferClient<typeof huddle>
```

::

`assemble` finalizes and checks the server. It throws when you build the server (before any connection opens) for mistakes like these:

- Two handlers on the same event name. This includes two different kinds of handler, for example an `on` and a `request` with the same name.
- A scheduled task declared in `scheduled({...})` whose handler you did not pass, or a `base.scheduled` handler for a task that was never declared.
- A per-handler `rateLimit` setting when the `rateLimit()` capability is not listed.
- A capability passed to `assemble`. Capabilities belong in `server`. (This is also a type error.)

When the [`handlers`](/server/handlers/overview) list has a known length (a literal array, or a list marked `as const`), TypeScript finds the first two mistakes at compile time. For a plain array, they are found when `assemble()` runs.

## Splitting across files

The builder and its handlers are plain values. So you can export `base` from one file and create handlers in other files. This keeps a large server readable. Here `rooms` also posts a "joined" message when someone subscribes.

::code-group

```typescript [server/base.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { requireSession } from './authenticate'

export type Message = {
  id: string
  text: string
  from: string
  sentAt: number
}

export const base = server({
  authenticate: (request) => requireSession(request),
  capabilities: [
    emits({ notification: t<{ title: string; body: string }>() }),
    channels(),
  ],
})
```

```typescript [server/authenticate.ts]
import { CloseCodes, RejectAuth } from '@livething/server/errors'
import { verifySession } from './auth'

export async function requireSession(request: Request) {
  const token = new URL(request.url).searchParams.get('token')
  const user = await verifySession(token)
  if (!user) {
    throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
  }

  return {
    userId: user.id,
    meta: { name: user.name, role: user.role },
  }
}
```

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { base } from './base'
import type { Message } from './base'

export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  onSubscribe(ctx) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: `${ctx.meta.name} joined the room`,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

```typescript [server/huddle-assembly.ts]
import type { InferClient } from '@livething/server'
import { base } from './base'
import { rooms } from './rooms'

export const huddle = base.assemble({ handlers: [rooms] })
export type HuddleSocket = InferClient<typeof huddle>
```
