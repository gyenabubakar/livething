A WebSocket connection starts as a normal HTTP request that asks the server to switch ("upgrade") the connection to the WebSocket protocol. This first exchange is the **handshake**. The `upgrade` field of `server(...)` runs during the handshake. In it, you **authenticate** the request (check who is connecting) and decide whether to let the socket in.

LiveThing does not give you one environment object that works on every runtime. Configuration (API URLs, secret keys and similar values) belongs to the runtime you deploy on. Node code can read `process.env`. A Cloudflare Durable Object (the Cloudflare object that runs your LiveThing server) can read its **bindings** (the variables and resources that Cloudflare gives your code) in two places: from `ctx.platform.env` inside a handler, or from the `env` argument of your Worker entry point. Read runtime-specific configuration in runtime-specific code. When shared handlers or plugins need a value, pass it to them directly.

`ctx.platform` is the runtime's own object. Use it only when you need a runtime feature that LiveThing does not wrap. On Cloudflare, type it with the `Platform` type from `@livething/server-cloudflare` (or with the `cloudflare:workers` types generated for your Worker):

```typescript [server/huddle.ts]
import type { Platform } from '@livething/server-cloudflare'

interface Env {
  SCOUT_API_KEY: string
}

base.on('check-scout-health', {
  run(ctx) {
    const platform = ctx.platform as Platform<Env>
    const configured = platform.env.SCOUT_API_KEY.length > 0
    ctx.send('notification', {
      title: 'Scout',
      body: configured ? 'ready' : 'not configured',
    })
  },
})
```

A plugin that needs configuration should take it as an argument of the function that creates the plugin (its **factory**). The app chooses the value when it adds the plugin, so the plugin does not read any hidden environment:

```typescript [polls/server.ts]
import { emits, server, t } from '@livething/server'
import { plugin } from '@livething/server/plugins'

export function pollsPlugin(config: { topic: string }) {
  const pluginBase = server({
    scope: 'plugin',
    capabilities: [emits({ 'poll-updated': t<{ topic: string }>() })],
  })
  const createPoll = pluginBase.on('create-poll', {
    run(ctx) {
      ctx.send('poll-updated', { topic: config.topic })
    },
  })
  return plugin('acme:polls', {
    definition: pluginBase.assemble({ handlers: [createPoll] }),
  })
}

const base = server({
  capabilities: [pollsPlugin({ topic: 'general' })()],
})
```

## `upgrade`: the auth gate

`upgrade` runs once per connection, during the handshake, before any handler. It receives the raw `Request`, with everything an HTTP request carries: headers, URL and cookies. It decides whether the connection is accepted or rejected.

A browser `WebSocket` cannot set custom headers (such as `Authorization`) on the handshake. So in the example below, the client puts its login token in the URL query string (`?token=...`), and the server reads it from the request URL:

```typescript [server/huddle.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [],
})
```

On the client, the `query()` primitive adds the token to the URL on every connect and reconnect. See [Client · Auth & Query](/client/connecting/auth-and-query).

`upgrade` can be `async`. Return a value to **accept** the connection. Throw `RejectUpgrade(code, reason)` to **reject** it.

::note
Besides the query string, there are two other ways to send a credential:

- **Cookies.** A browser sends them automatically when the socket is on the same domain as the page (same-origin). Read them from the `cookie` header.
- **Headers** such as `Authorization`. Only non-browser clients (a Node.js script, a mobile app, a server) can set these on the handshake.
  ::

### Reading the request

The argument is a standard `Request`. These are the common values to read from it:

```typescript [server/huddle.ts]
async upgrade(request) {
  const url = new URL(request.url)
  const token = url.searchParams.get('token')          // query string
  const cookie = request.headers.get('cookie')         // cookies
  const auth = request.headers.get('authorization')    // header (non-browser clients only)

  // ... validate and return
}
```

### Client IP

When an adapter can safely find the real address of the client, it adds that address to the same request, in a header:

```ts [server/huddle.ts]
async upgrade(request) {
  const clientIp = request.headers.get('LiveThing-Client-IP')

  if (clientIp) {
    // use the verified client address for your policy or audit record
  }
}
```

`LiveThing-Client-IP` is optional. It is `null` when the runtime cannot verify an address. It is a header that LiveThing sets. It is not a standard `Request` property. If a client sends its own `LiveThing-Client-IP` header, the adapter removes it. Do not read a forwarded-address header (such as `X-Forwarded-For`) yourself here. The adapter decides which proxy addresses it trusts before it sets this value. See your adapter page for how that runtime finds the address.

A small, common pattern is a guest join: a room invite link carries only a display name, with no account behind it.

```typescript [server/huddle.ts]
import { RejectUpgrade, CloseCodes } from '@livething/server/errors'

async upgrade(request) {
  const name = new URL(request.url).searchParams.get('name')
  if (!name) throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'missing name')
  return { userId: crypto.randomUUID(), meta: { name, role: 'guest' as const } }
}
```

::warning
Neither the app's `upgrade` nor a plugin's `upgrade` receives runtime configuration as an argument. Both receive only the `Request`. There is no `ctx` yet during the handshake. If authentication needs configuration or a service, make it available through a closure (a function that uses a variable from the code around it) or a module-level variable.
::

## What `upgrade` returns

The accept value is an `UpgradeReturn`. All three fields are optional.

::field-group
::field{name="userId" type="string"}
Optional. The stable ID of the user behind this socket. It is the key for stored per-user data, and channels use it to find the same user again after a reconnect. Leave it out (or return an empty string) to accept the connection as anonymous. The maximum length is 256 characters. The ID also cannot start with `__`, because LiveThing keeps that prefix for its own storage keys. If the ID breaks either rule, LiveThing throws an error when it accepts the connection. A longer ID is not shortened, because two long IDs shortened to the same text would share one storage row. Use a stable ID, such as the user's database ID or a ULID (a unique, sortable ID string). Do not use a token. Almost every app sets this field.
::

::field{name="meta" type="TMeta"}
Optional. Per-connection data, which every handler reads as `ctx.meta`. Its type becomes the type of `ctx.meta`. For example, return `{ userId: 'u1' }` and `ctx.meta.userId` is typed as `string`. The default is `{}`.
::

::field{name="tags" type="{ ephemeral?: { group: key } }"}
Optional. The first ephemeral tags to attach before any handler runs. A tag is a label (a group name and a key) that you attach to a connection, so you can find or message every connection with that label. Ephemeral tags live only in memory. The keys of this object are the ephemeral group names that you declare in the `tags(...)` capability, so this field is only useful when `tags()` is in your `capabilities`. You cannot set persistent tags (tags that are saved in storage) here. Add them in a handler with `ctx.tags.persistent(group).add(key)`.
::
::

```typescript [server/huddle.ts]
async upgrade(request) {
  const token = new URL(request.url).searchParams.get('token')
  const user = await verifySession(token)
  if (!user) throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
  return {
    userId: user.id,
    meta: { name: user.name, role: user.role },
    tags: { ephemeral: { role: user.role } },   // needs tags() with a 'role' group
  }
}
```

::caution
The compiler checks the group names in `tags.ephemeral` only in some cases. If you list `tags(...)` and return only a misspelled group, you get a compile error. But if you return a correct group and a misspelled one together, or if `tags()` is not in your `capabilities`, the code compiles. At runtime, an undeclared group makes the handshake fail with HTTP `500` (`Upgrade failed`). The error message is `onUpgrade returned an ephemeral tag for group '<name>', which is not declared under tags (ephemeral)`. Check that each group name matches the `tags(...)` capability exactly.

If the group has a schema (see [Tags](/server/capabilities/tags)), LiveThing checks the tag key against it too, the same check `ctx.tags.ephemeral(group).add(key)` runs later. A key that fails the schema also fails the handshake with HTTP `500`.
::

### `userId` is the durable key

`userId` is more than a label. LiveThing uses it as the key for stored per-user data, and to add a returning user back to the channels they belong to. Give the same person the same `userId` on every connection, and their saved channel memberships and stored data stay with them after a reconnect. For more about tags and rejoining channels, see [Channels](/server/channels/overview) and the [tags capability](/server/capabilities/tags).

Inside any handler or hook, read the value as `ctx.user.id`. It is a `string`, and it is empty for an anonymous socket:

```typescript [server/huddle.ts]
base.on('whoami', {
  run(ctx) {
    ctx.send('notification', {
      title: 'You',
      body: ctx.user.id, // the value from upgrade()
    })
  },
})
```

### The `UpgradeFn` and `UpgradeReturn` types

If you write the gate as a separate function (for example, to reuse it in more than one server), use these types:

```typescript [server/huddle.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import type { UpgradeFn, UpgradeReturn } from '@livething/server'

// UpgradeReturn<TMeta> = { userId?: string; meta?: TMeta; tags?: {...} }
// UpgradeFn<TMeta>     = (request: Request) => UpgradeReturn<TMeta> | Promise<...>

type SessionMeta = {
  name: string
  role: 'admin' | 'member' | 'guest'
}

const requireSession: UpgradeFn<SessionMeta> = async (
  request,
): Promise<UpgradeReturn<SessionMeta>> => {
  const token = new URL(request.url).searchParams.get('token')
  const user = await verifySession(token)
  if (!user)
    throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
  return {
    userId: user.id,
    meta: { name: user.name, role: user.role },
  }
}

const base = server({
  upgrade: requireSession,
  capabilities: [],
})
```

## Anonymous connections

`upgrade` is optional. If you leave it out, the connection is still **accepted**, but it is anonymous:

- `userId` is `''`
- `meta` is `{}`
- there are no tags

```typescript [server/huddle.ts]
const base = server({
  capabilities: [],
  // no upgrade: every connection is accepted as anonymous
})
```

An `upgrade` can also accept a connection as anonymous. Return no `userId` (or an empty string):

```typescript [server/huddle.ts]
const base = server({
  upgrade() {
    return { meta: {} } // accepted, anonymous
  },
  capabilities: [],
})
```

Anonymous connections do not share one user, and they do not become users. Each one has no user identity. `ctx.user` exists, but it points to no user. Some stored data must not be shared between two anonymous sockets, for example the read position of each member of a broadcast stream. For that data, LiveThing uses the connection's own ID as the storage key internally. An anonymous connection cannot start a resumable or recorded stream at all: the server rejects it with `DurableStreamRequiresUser`. This is only a storage key, not a user identity. See [Users](/server/context-and-storage/users) for the full model.

Other stored data exists only to reconnect a returning user: durable channel memberships and persistent tags. An anonymous connection has no stable key to match on a reconnect, so LiveThing **skips** saving this data when `userId` is empty. It does not save it under the connection ID. If every socket must be authenticated, write an `upgrade` that throws `RejectUpgrade(...)` when credentials are missing.

## Rejecting the upgrade

Throw `RejectUpgrade(code, reason)` to refuse a connection during the handshake. The `code` decides what the client sees: an HTTP error response, or a WebSocket that opens and closes at once.

```typescript [server/huddle.ts]
import { RejectUpgrade, CloseCodes } from '@livething/server/errors'

async upgrade(request) {
  const token = new URL(request.url).searchParams.get('token')
  if (!token) throw RejectUpgrade(401, 'Missing credentials')                    // HTTP 401
  const user = await verifySession(token)
  if (!user) throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')      // WS close 4002
  return { userId: user.id, meta: { name: user.name, role: user.role } }
}
```

### How the reject code is answered

LiveThing reads the number that you pass to `RejectUpgrade` by its range:

| `code` you pass                                                                                       | What the client gets                                                                                                                                                                       | When to use it                                                         |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- |
| A valid WebSocket close code (`1000` to `1014` except `1004`, `1005` and `1006`, or `3000` to `4999`) | The handshake completes, then the server closes the socket at once with that code and reason. This is the **only** way a browser `WebSocket` can read the reason (from its `close` event). | When the client is a browser `WebSocket` and you want it to see _why_. |
| `400` to `599` (an HTTP status)                                                                       | That HTTP status, with `reason` as the response body.                                                                                                                                      | For a plain HTTP rejection that `fetch` or a proxy can read.           |
| Any other number (a decimal, a reserved code, or a number out of range)                               | HTTP `403 Forbidden`. The server logs the invalid code.                                                                                                                                    | This is a safe fallback. Use a valid code instead.                     |

So `RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')` lets a browser client read `'invalid session'` from the close event, and `RejectUpgrade(401, 'Missing credentials')` returns a real HTTP 401. A value such as `4000.5` or `1006` does not become a close frame. It becomes the safe `403` response. Choose the range that matches how your client connects.

Any other error thrown inside `upgrade` (anything that is not a `RejectUpgrade`) rejects the handshake with HTTP `500` and the body `Upgrade failed`. LiveThing also logs this case on the server, so you can find the real cause: the client only ever sees the generic `Upgrade failed` message.

::tip
WebSocket close codes from **4000 to 4999** are for application use. Use them when a browser client needs to tell your reasons apart. See [Close codes](/core/close-codes) for the full list.
::

### The non-WebSocket case

A plain `GET` request with no `Upgrade: websocket` header never reaches your `upgrade`. Depending on the adapter, it gets HTTP `426 Upgrade Required` or goes on to your normal HTTP routes. So `upgrade` runs only for a real WebSocket handshake, and you do not need to guard against normal HTTP traffic inside it.

## A scoped `upgrade`

A plugin can have its own `upgrade` in its scoped server definition (`server({ scope: 'plugin', ... })`). It runs before the app's `upgrade`, so it sees only the raw request and not the app's `userId`. Its `meta` is merged into the connection's `meta`. [Plugins › Authoring](/server/plugins/authoring) covers this variant.
