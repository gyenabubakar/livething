A **capability** is a feature you turn on by listing it in `server({ capabilities: [...] })`. If you do not list it, the feature is off. This page explains how the list works: what listing a capability changes in your bundle and in `base` (the value `server(...)` returns, which you use to define handlers), how capabilities combine, and how LiveThing catches a missing requirement. For what each capability _does_, see the [Capabilities chapter](/server/capabilities/overview).

## The `capabilities` array

To create a capability, call its factory function, such as `emits(...)`, `clientRequests()` or `channels()`. Then put the result in the array.

```typescript [server/capabilities.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { clientRequests } from '@livething/server/client-requests'
import type { Message } from './base'

const base = server({
  capabilities: [
    emits({ message: t<Message>() }),
    clientRequests(),
    channels(),
  ],
})
```

Always create a capability with its factory. Do not build the object yourself. Each factory decides three things:

- the runtime code it adds to the server
- the contract slots it declares (a contract slot is one typed part of the contract between client and server, such as the list of events the server sends)
- the builder method it adds to `base`, if any

::warning
**Keep the exact types of the capability list.** Write the list inline in `server(...)`. If you need to reuse the list, add `as const` so TypeScript keeps it as a tuple (a fixed list where each item keeps its own type):

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { channels } from '@livething/server/channels'
import { clientRequests } from '@livething/server/client-requests'
import { dedup } from '@livething/server/dedup'

const capabilities = [clientRequests(), channels(), dedup()] as const

const base = server({
  capabilities,
})
```

Do not give the list the type `AnyCapability[]`, and do not spread a list that already has that type. Both remove the specific capability and plugin types before LiveThing can read them.
::

::note
Most capabilities have their own import path, such as `@livething/server/client-requests`, `@livething/server/channels` and `@livething/server/streams`. A few (`emits`, `errors`, `t`) come directly from `@livething/server`. The [Capabilities chapter](/server/capabilities/overview) lists the import for each one.
::

## Only listed capabilities go into your bundle

**The code for a feature goes into your bundle only when you list its capability.** If you leave out `channels()`, no channel code is in your bundle, which saves about 6.7 KB (minified and gzipped). A small server stays small, because you only pay for the features you use.

This is why capabilities are values you import, not flags you switch on. Your bundler sees the import and knows the code is needed. Without the import, the bundler leaves the code out.

## A capability does two jobs

Listing a capability can do two different things.

### 1. Add a builder method

Some capabilities add a method to `base`. The method exists only when its capability is listed. If you call it without the capability, you get a compile error. If the code runs anyway (for example, from plain JavaScript), the method throws an error.

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'
import { loadProfile } from './huddle-data'

const withRequests = server({
  capabilities: [clientRequests()],
})
export const handleGetProfile = withRequests.request('get-profile', {
  input: v.object({ userId: v.string() }),
  run: (ctx, input) => loadProfile(input.userId),
}) // OK: clientRequests() is listed

const without = server({
  capabilities: [],
})
// without.request(...)   ← compile error: base.request does not exist
```

This table shows which capability adds which method:

| Capability         | Builder method it adds |
| ------------------ | ---------------------- |
| `clientRequests()` | `base.request`         |
| `scheduled({...})` | `base.scheduled`       |
| `stream()`         | `base.stream`          |
| `recordedStream()` | `base.recordedStream`  |
| `channels()`       | `base.channel`         |

Other capabilities, such as `emits(...)`, `errors([...])`, `serverRequests(...)`, `tags(...)`, `keepalive(...)`, `dedup()`, `sequence()` and `rateLimit()`, add **no** method. Instead they declare a contract slot, add a field to `ctx`, or turn on a part of the server engine.

### 2. Add a field to `ctx`

Some capabilities add a field to the `ctx` (context) object that every handler receives. Like the methods, the field exists only when the capability is listed. If you read it without the capability, you get a compile error. The field is not there with a `null` value; it does not exist at all. Here Huddle's `send-digest` task also sets `retry: true`:

```typescript [server/huddle-definition.ts]
import { server, t } from '@livething/server'
import { scheduled } from '@livething/server/scheduled'

const base = server({
  capabilities: [
    scheduled({
      'send-digest': { data: t<{ userId: string }>(), retry: true },
    }),
  ],
})

const handleRequestDigest = base.on('request-digest', {
  run(ctx) {
    // ctx.schedule exists because scheduled(...) is listed
    ctx.schedule('send-digest', {
      time: Date.now() + 60_000,
      data: { userId: ctx.user.id },
    })
  },
})
```

The capabilities that add `ctx` fields:

- `scheduled(...)` adds `ctx.schedule` and `ctx.cancelScheduled`.
- `serverRequests(...)` adds `ctx.request`, `ctx.connections.get(ref).request` and `ctx.users.get(id).request`. These send requests from the server to the client.
- `channels()` adds `ctx.channels`.
- `tags(...)` adds `ctx.tags`.
- `keepalive(...)` adds `ctx.latency` and `ctx.quality`.
- `lastSeen()` adds `ctx.lastSeen`.
- A replay capability (`replay.history()` or `replay.snapshot()`) adds `ctx.sendReplay`.

The full `ctx` shape is covered in [Context and storage](/server/context-and-storage/overview).

::note
The `intercept` hook, `ctx.matches` and `ctx.unsafeCast` do not belong to any capability. They are on every server and every connection `ctx`.
::

## How capabilities combine

LiveThing merges the list. Each capability adds its own part of the client contract and its own runtime code. `server` combines all of them into one `base`, typed with every part. To keep the example in one file, it defines `RoomFull` inline. Huddle imports it from `../shared/errors`.

```typescript [server/room-errors.ts]
import { emits, error, errors, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'
import type { Message } from './base'

const RoomFull = error('room-full', v.object({ limit: v.number() }))

const base = server({
  capabilities: [
    emits({
      // events the server sends to the client
      message: t<Message>(),
    }),
    errors([RoomFull]), // typed server errors
    clientRequests(), // adds base.request
    channels(), // adds base.channel and ctx.channels
  ],
})
```

The contract parts add up. `emits` fills the events slot, `errors` fills the errors slot, and `clientRequests` and `channels` add their builder methods and contract slots. `serverRequests` adds requests that the server sends to the client. `InferClient<typeof definition>` reads the merged result, so the client gets every feature of every capability you listed.

Each capability can be listed only once. If you list the same one twice, you get a compile error. If the code runs anyway, `server(...)` throws:

```text
[livething] sequence() is listed more than once in server({ capabilities: [...] }). Each capability can be listed once per scope.
```

`replay.history()` and `replay.snapshot()` count as the same capability, so you can list only one of them.

## Requirements

Some features need other capabilities. Replay (sending missed messages to a client that reconnects) needs `dedup()` and `sequence({ persist: true })`. `dedup()` drops a message when the server has already seen its message ID. `sequence()` gives every outgoing message a number, so the client can see when it missed one, and `persist: true` keeps that counter when the server restarts. A channel's `inbox()` needs `channels()`, `dedup()` and a persistent `sequence()`. LiveThing checks these requirements for you.

When a feature needs a capability you did not list, `assemble` throws an error that names the missing capability:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { replay } from '@livething/server/replay'

const base = server({
  capabilities: [replay.history()], // replay needs dedup() and sequence({ persist: true })
})

// base.assemble({ handlers: [] })
//   → throws: [livething] The dedup() capability is required by replay but is not listed. Add dedup() to server({ capabilities: [...] }).
```

To fix it, list the required capabilities:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [
    dedup(),
    sequence({ persist: true }),
    replay.history(),
  ], // this assembles
})
```

The common requirements:

| Feature                                                                   | Requires                                                               |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Replay (`replay.history()` / `replay.snapshot()`)                         | `dedup()` and `sequence({ persist: true })`                            |
| A channel's `inbox()` (listed in the channel's own `capabilities`)        | `channels()`, `sequence({ persist: true })`, and `dedup()` on the host |
| A channel's `readReceipts()` (listed in the channel's own `capabilities`) | `inbox()` on the same channel                                          |

The check looks at top-level handlers and at handlers inside channels. So a feature inside a channel, such as `inbox()`, is checked in the same way as a top-level one.

::note
For replay, `assemble` only checks that `dedup()` and `sequence(...)` are in the list. It checks `persist: true` later, when the server starts. A plain `sequence()` passes `assemble`, but the server then throws at startup and asks for `sequence: { persist: true }`. List `sequence({ persist: true })` from the start.
::

::note
**Plugins** use the same check. A plugin that owns a channel with `inbox()` does not list `dedup()` or `sequence()` itself. It cannot list them, because only the host server can own those engines. LiveThing records the requirement from the channel and passes it to the host, and the host must list those capabilities. See [Plugins › dependsOn](/server/plugins/depends-on).
::

## Ordering

The order of the array does **not** change behavior. Listing `channels()` before or after `emits(...)` gives the same result. Use the order that is easiest to read. A good style is to put engine capabilities (`dedup`, `sequence`) first, then feature capabilities, and the `emits` block last.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { clientRequests } from '@livething/server/client-requests'
import { dedup } from '@livething/server/dedup'
import { sequence } from '@livething/server/sequence'
import { recordedStream } from '@livething/server/streams'

const base = server({
  capabilities: [
    // engines
    dedup(),
    sequence({ persist: true }),
    // features
    clientRequests(),
    channels(),
    recordedStream(),
    // the list of events, easy to read
    emits({
      notification: t<{ title: string; body: string }>(),
      'user-renamed': t<{ userId: string; name: string }>(),
    }),
  ],
})
```

The requirement check looks only at _presence_, not position: every required capability must be somewhere in the list.
