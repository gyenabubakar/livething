Translation lets an existing WebSocket client talk to a LiveThing server without changing that client first. The client keeps its own **wire format** (the exact text shape of each message on the WebSocket). A **translator** on the server changes each message between that foreign format and the LiveThing format.

This is useful when a team moves its server from a hosted realtime service, such as Pusher, to LiveThing. The team can keep the client that its users already have installed. Later, it can move that client to LiveThing when it is ready.

Translation is a **server-only** feature. A [LiveThing client](/client/overview) already uses the LiveThing format, so it needs no translator. When an app connects to a foreign service, that service's own client SDK is usually the right tool.

## Add one translator

Import `translator` from `@livething/server`. Pass it a **factory** (a function that creates a new object each time LiveThing calls it). Then set the result as `translate` in [`server`](/server/server/overview).

A LiveThing frame (one message on the WebSocket) is a JSON array with three items: the event name, the payload, and the metadata (`null` when there is none). The [wire protocol](/learn/wire-protocol) page describes it in full. In this example, the foreign client sends and receives objects such as `{ "type": "message", "name": "send-message", "body": { "text": "hi" } }`.

```typescript [server/huddle.ts]
import { server, translator } from '@livething/server'

const legacy = translator(() => ({
  inbound(raw) {
    const frame = JSON.parse(raw)
    if (frame.type !== 'message') return null

    return JSON.stringify([frame.name, frame.body, null]) // frame.name e.g. 'send-message'
  },
  outbound(outgoing) {
    if (outgoing === 'pong') return null

    const [event, payload] = JSON.parse(outgoing)
    return JSON.stringify({
      type: 'message',
      name: event,
      body: payload,
    })
  },
}))

const base = server({
  translate: legacy,
})
```

`outbound` returns `null` for the bare `pong` string, so that heartbeat reply reaches the client unchanged. Every other outgoing string is a LiveThing JSON frame.

One [server definition](/server/server/overview) has zero or one translator. `translate` does not accept an array, and LiveThing does not try to detect a protocol from the frames. If an app must serve two foreign protocols, create two server definitions and send each kind of client to its own endpoint.

`translator()` always takes a function. LiveThing calls that function once for every connection, so the variables inside it belong to that one connection.

```typescript [server/huddle.ts]
import { translator } from '@livething/server'

const counted = translator(() => {
  let count = 0

  return {
    inbound(raw) {
      count += 1
      console.log(`this connection has sent ${count} frames`)
      return raw
    },
  }
})
```

## What each method does

| Method                | Direction                      | Return value                                                      |
| --------------------- | ------------------------------ | ----------------------------------------------------------------- |
| `inbound(raw)`        | Client to server               | A LiveThing string, or `null` to keep the original string.        |
| `outbound?(outgoing)` | Server to client               | A foreign-protocol string, or `null` to keep the original string. |
| `hibernation?`        | When the connection hibernates | An object with both `serialize()` and `restore(state)`.           |

The factory, `inbound`, `outbound`, and both hibernation methods are synchronous. They must never return a Promise. `inbound` and `outbound` return a string or `null`. If you build an object, call `JSON.stringify` on it yourself. When you leave out `outbound`, server frames stay in the normal LiveThing wire format.

## Pipeline order

Inbound translation runs first. It runs before [LiveThing's pipeline](/server/under-the-hood/pipeline-execution-order) checks for the bare `ping` or `pong` strings, and before it parses a LiveThing JSON frame.

Outbound translation runs last. It receives the final LiveThing string, after LiveThing has turned the frame into text. This includes protocol messages, [errors](/core/error-model), [replay](/server/replay/overview) and [stream](/server/streams/overview) frames, and [pongs](/server/lifecycle-and-intercept/hooks).

::note
With Cloudflare [hibernation](/server/server/hibernation), the Cloudflare runtime normally answers a client's `ping` with `pong` itself, without starting the Durable Object. When `translate` is set, LiveThing turns off this automatic answer. Heartbeat frames (the small `ping` and `pong` messages that check a connection is still alive) then wake the Durable Object and pass through the translator. If the foreign protocol uses heartbeats, map them in the translator or let them pass through unchanged.
::

::translation-pipeline
::

So a translator only changes the wire format. It is not an [`intercept`](/server/lifecycle-and-intercept/intercept) or a [`plugin`](/server/plugins/overview). It receives no [`ctx`](/server/context-and-storage/ctx), no [storage](/server/context-and-storage/sql-and-kv), no user identity, and no [`send()`](/server/context-and-storage/ctx#messaging) method. It cannot register handlers or run other LiveThing operations.

## Validate foreign JSON first

Set `input` when the foreign protocol sends JSON. `input` takes a Standard Schema validator (for example a valibot or zod schema). LiveThing parses the raw frame as JSON and validates it before it calls `inbound`. Then it gives `inbound` the schema's typed output, the same way it does for [handler input](/server/handlers/overview). The validator must be synchronous too. An async validator is a translator configuration error.

```typescript [validated.ts]
import { translator } from '@livething/server'
import * as v from 'valibot'

const legacy = translator(() => ({
  input: v.object({
    type: v.literal('message'),
    body: v.string(),
  }),
  inbound(frame) {
    return JSON.stringify([
      'send-message',
      { text: frame.body },
      null,
    ])
  },
}))
```

If JSON parsing or `input` validation fails, LiveThing closes the connection with [`CloseCodes.PROTOCOL_ERROR` (`1002`)](/core/close-codes). A translated endpoint has one declared foreign protocol, so LiveThing never passes bad input on to the normal LiveThing message pipeline. An error thrown inside your own `inbound` function is different: it is a translator runtime failure, described next.

LiveThing closes the connection with `CloseCodes.INTERNAL_ERROR` (`1011`) when any of these throws: the factory, a translator method, `hibernation.serialize()`, or `hibernation.restore()`. It logs runtime failures. It throws configuration mistakes, such as a translator method that returns a Promise, so that you see them during development. A failed translator never makes LiveThing send the frame untranslated. During a broadcast, LiveThing skips the recipient whose translator failed and keeps delivering to the other recipients.

## Hibernation state

With Cloudflare Durable Object [hibernation](/server/server/hibernation), the object can be removed from memory while its WebSockets stay open. When that happens, the variables inside the factory are lost. Use `serialize` and `restore` to keep the small per-connection state that your translator needs after the object wakes.

```typescript [hibernation.ts]
import { translator } from '@livething/server'

const sequenced = translator(() => {
  let sequence = 0

  return {
    inbound(raw) {
      sequence += 1
      return raw
    },
    hibernation: {
      serialize() {
        return { sequence }
      },
      restore(state) {
        sequence = state?.sequence ?? 0
      },
    },
  }
})
```

`hibernation.serialize()` must return JSON-safe data (values that `JSON.stringify` can save and read back without change). It should only take a snapshot of the state. LiveThing can call it after inbound translation and right before it writes a server frame, so it must not change the translator's state. `hibernation.restore()` runs after a wake, before LiveThing handles any frame. `state` is `undefined` when nothing was saved. You must provide both methods together, because saved state is only useful when it is restored.
