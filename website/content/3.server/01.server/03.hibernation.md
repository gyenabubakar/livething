A Cloudflare Durable Object that holds open WebSocket connections normally stays in memory for as long as those connections are open, even when nobody sends anything. **Hibernation** lets Cloudflare evict (remove) that Durable Object from memory between messages. Cloudflare loads it again only when a new frame arrives. You do not pay for the idle time, so a mostly quiet room costs very little to keep open.

::warning
Hibernation is a feature of **Cloudflare Durable Objects**, so only the Cloudflare adapter (`@livething/server-cloudflare`) supports it. On Bun, Node or Deno, a server that turns it on fails at startup with an error that says the adapter does not support hibernation. See [Installation](/start/installation) for the adapter packages.
::

In LiveThing, you turn it on with one config flag.

## Turning it on

Set `hibernation: { enabled: true }` in `server()`.

```typescript [server/huddle.ts]
import { emits, server, t } from '@livething/server'

const base = server({
  hibernation: { enabled: true },
  capabilities: [emits({ message: t<Message>() })],
})
```

You do not need any other config.

## What it is

Without hibernation, a Durable Object instance stays in memory the whole time a socket is open. It keeps every connection in a normal in-memory map. With hibernation, Cloudflare may **evict the instance between frames**. The sockets stay open at the edge (Cloudflare's network, which holds the client connections). But the JavaScript object that owns them is gone until the next message wakes it up.

After a wake, you have a new instance with an empty connection map. So LiveThing must rebuild each connection from durable storage, not from memory. LiveThing does this for you.

## What survives

**In-memory variables do not survive an eviction. Durable storage does.**

| Survives hibernation                                    | Does not survive                                           |
| ------------------------------------------------------- | ---------------------------------------------------------- |
| The open WebSocket connections (kept at the edge)       | Module-level or instance-level variables you set in memory |
| `ctx.sql` and `ctx.kv` storage                          | A `Map` or counter you keep in memory                      |
| Each connection's `userId`, `meta`, and tags            | Anything you cached in a closure                           |
| Durable channel memberships, resumable/recorded streams | The in-memory connection map                               |
| Durable alarms behind `ctx.schedule`                    | `setTimeout` / `setInterval` timers held in memory         |
| Translator state returned by `hibernation.serialize()`  | Translator closure state without `hibernation`             |
| (durable streams reattach on wake)                      | Plain in-flight `base.stream` generators (see below)       |

When a socket wakes, LiveThing restores the connection's `userId`, `meta`, and tags from a saved per-connection snapshot. So your handlers see the same `ctx.user.id` and `ctx.meta` as before. LiveThing also saves durable channel memberships and durable streams to storage, so they come back too. A [translator](/server/server/translation) can save small per-connection state with `hibernation.serialize()` and get it back with `restore()`.

Plain (non-durable) streams are different. An in-flight `base.stream` generator lives only in memory, so LiveThing cannot rebuild it after an eviction. When the instance wakes, LiveThing aborts the stream. The client receives `StreamAborted` with `detail.reason === 'hibernation-wake'`, and it can start the stream again. The server sends the same error for resumable and recorded streams, but the LiveThing client does not pass it to your code. It sends a resume request instead, and the stream continues from its saved state. In-memory `setTimeout` and `setInterval` timers are also lost on a wake. For anything that must run after an idle period, use durable alarms (`ctx.schedule`).

The rule for your own code: if state must last through an idle period, **write it to `ctx.sql` or `ctx.kv`**, not to a plain variable.

```typescript [server/huddle.ts]
// WRONG under hibernation: this counter resets when the Durable Object is evicted.
let messageCount = 0
base.on('send-message', {
  input: v.object({ text: v.string() }),
  run() {
    messageCount += 1
  },
})

// RIGHT: durable storage survives the wake.
base.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx) {
    ctx.sql.exec(
      'INSERT INTO counters (id, n) VALUES (1, 1) ' +
        'ON CONFLICT(id) DO UPDATE SET n = n + 1',
    )
  },
})
```

::tip
This advice also applies without hibernation, because Cloudflare can evict a Durable Object for other reasons. The safe default: durable storage is the source of truth, and memory is only a cache. See [Context and storage](/server/context-and-storage/overview) for `ctx.sql` and `ctx.kv`.
::

## How LiveThing handles it

You do not write any wake-up code. When hibernation is on, LiveThing:

- Saves each connection's `userId`, `meta`, and tags in a per-socket snapshot. A woken instance uses it to rebuild that connection's `ctx`.
- On wake, before it handles any message, goes through every socket that Cloudflare gives back. For each one, it restores the connection state (`userId`, `meta`, `tags`, and channel membership) from the snapshot.
- Saves durable channel memberships and durable streams to storage, so they reattach after a wake.
- Restores translator state before the connection's first frame runs, when the connection uses a translator with hibernation state.
- Compares the sockets that Cloudflare gives back with the rows in storage. It keeps the connections that are still open and deletes the stored row of any socket that is gone.

For a handler, nothing changes. `ctx.user.id`, `ctx.meta`, `ctx.send`, `ctx.broadcast`, and storage all work the same way, whether or not the instance just woke.

::note
LiveThing restores all sockets **at once, one time per wake**. It does not restore them one by one as messages arrive. When a hibernated instance wakes, it first restores the state of every open socket in one pass. Then it handles the message that woke it. So a broadcast sent right after a wake reaches members who have not sent anything since the wake. This includes [inbox](/server/inbox/overview) fan-out, which writes a held row for each current member. A member who stayed connected but silent the whole time still gets the message.
::

::warning
The restore pass takes time in proportion to the number of sockets still open on that Durable Object, not to the one connection that caused the wake. A room with 2 open sockets restores almost instantly. A room with 5,000 open sockets does 5,000 rows of work on every wake, even if only one of them sent a message. Later messages in the same awake period do not repeat this work. But it means that hibernation saves less as a room gets more connections. For a busy room with many members, the restore cost can be larger than the CPU time you save by evicting between messages. Measure before you turn on hibernation for large rooms.
::

## The connection snapshot table

The per-socket snapshot is one row per live connection in a reserved SQLite table, `__livething_connections`. LiveThing creates this table the first time a hibernation-enabled instance starts. A wake reads these rows back to rebuild each connection's `ctx`.

| Column                  | Type               | What it holds                                                                 |
| ----------------------- | ------------------ | ----------------------------------------------------------------------------- |
| `connection_id`         | `TEXT` primary key | The socket's connection ID.                                                   |
| `user_id`               | `TEXT`             | The connection's user ID.                                                     |
| `meta`                  | `TEXT`             | The connection's `meta`, as JSON.                                             |
| `ephemeral_tags`        | `TEXT`             | The ephemeral `(group, key)` tag pairs the connection holds, as a JSON array. |
| `ephemeral_memberships` | `TEXT`             | The connection's ephemeral channel memberships, as a JSON array.              |
| `active_stream_ids`     | `TEXT`             | The IDs of the connection's in-flight non-durable streams, as a JSON array.   |
| `translator_state`      | `TEXT`             | JSON-safe state returned by the connection's translator, if it has one.       |
| `metadata`              | `TEXT`             | A reserved JSON value for future connection-level fields.                     |

The table has one index, `__livething_idx_connections_user_id`, on the `user_id` column. Both names start with the reserved `__livething_` prefix. Do not write to this table, and do not create a table with this name yourself, even before you turn hibernation on. LiveThing creates it with `IF NOT EXISTS`, so you get no "table already exists" error that would warn you about the clash. See the [full reserved-table list](/server/context-and-storage/sql-and-kv#reserved-livething-tables) for every table LiveThing owns.

## The trade-offs

Hibernation changes how the server checks that connections are still alive.

### Server pings are disabled

The ping timer of the [`keepalive()`](/server/capabilities/keepalive) capability does not run. With hibernation on and no [translation](/server/server/translation), the Cloudflare runtime answers the client's keepalive `"ping"` with `"pong"` **at the edge**. So Cloudflare does not wake a hibernated Durable Object just to answer a heartbeat. With translation configured, LiveThing turns off this edge reply, so heartbeat frames wake the Durable Object and go through the translator. The cost of the edge reply is that the server does not test each client on a timer.

This turns off only the pings the server **sends**. Without translation, the Workers runtime answers a ping from the client with `pong` and does not wake the Durable Object. The frame never reaches your code, so [`base.onPing(...)`](/server/lifecycle-and-intercept/hooks#onping) does **not** run under hibernation. With translation, the frame reaches your translator and then the normal inbound pipeline. [`base.onPong(...)`](/server/lifecycle-and-intercept/hooks#onpong) still runs. Without translation only `ping` gets an automatic answer, so LiveThing delivers a `pong` from the client as normal.

### The idle timeout does not run either

Without hibernation, `keepalive()` also starts an idle timer: if a connection sends nothing within `idleTimeoutMs`, the server closes it. Under hibernation this timer does not run at all. There are two reasons.

First, a `setTimeout` idle timer is itself in-memory state. To keep it running, the Durable Object would have to stay in memory just to count down. That removes the benefit of hibernation: you would pay for the instance to stay in memory while nothing happens.

Second, the timer would give wrong results. A client that is silent but still connected sends keepalive pings, and the edge answers them (see above). These pings never wake the Durable Object, so the instance never learns that the client is still there. A `setTimeout` that only sees traffic that reaches the instance would treat that silence as a lost client and close a healthy connection.

So under hibernation, `keepalive()` sends no server pings, measures no latency, and closes no idle connections. A timer cannot find and close connections that went silent, because the object is not in memory to run it. Use storage instead. Save a last-seen timestamp for each connection (for example in `ctx.sql`) whenever you see activity. Then check the timestamps when the instance wakes for another reason, or from a durable alarm (`ctx.schedule`) that runs on a regular schedule and closes every connection past its deadline.

### Latency and quality are null

The server does not run its own ping/pong round-trips, so it has no round-trip time to report. `ctx.latency` and `ctx.quality` exist only when you list `keepalive()`. Without it, reading them is a compile error, not `null`. So when you list `keepalive()` together with hibernation, both fields are always `null`.

```typescript [server/huddle.ts]
import { server } from '@livething/server'
import { keepalive } from '@livething/server/keepalive'

const base = server({
  hibernation: { enabled: true },
  capabilities: [
    keepalive({ pingIntervalMs: 30_000, idleTimeoutMs: 60_000 }),
  ],
})

base.on('check-connection-quality', {
  run(ctx) {
    // Under hibernation these are always null, because the server sends no pings.
    console.log(ctx.latency) // null
    console.log(ctx.quality) // null
  },
})
```

If you need latency measured by the server, leave hibernation off. If your main concern is the cost of idle rooms, and connection health checks on the client are enough, turn it on. The [keepalive capability](/server/capabilities/keepalive) page covers `keepalive()`, `ctx.latency` and `ctx.quality`.

## When to use it

Use hibernation when connections stay open much longer than they are active: chat rooms, presence channels, collaborative documents, and any app where a socket is idle for long periods. Leave it off when the server must measure each client's latency, or when the traffic is so constant that Cloudflare would rarely evict the instance.
