The admin surface belongs to the **running service**. This is the object that holds your live connections, your storage, and the running engine. How your outside code reaches it depends on the runtime. The operations do the same things on every runtime.

## Cloudflare Durable Objects

Only a Worker can reach a Durable Object (DO), so the admin surface is an RPC method on the DO. RPC (remote procedure call) means calling a method that runs in another process. A **stub** is the object your Worker uses to call one Durable Object instance. Your Worker calls `admin()` on the stub, then calls the operation on the result:

```typescript [worker.ts]
import { verifyClerkWebhook } from './huddle-data'
import type { Env } from './helpers'

export default {
  async fetch(request: Request, env: Env) {
    const url = new URL(request.url)

    if (url.pathname === '/webhooks/clerk') {
      const event = await verifyClerkWebhook(request)

      if (event.type === 'user.deleted') {
        const id = env.HUDDLE_SERVER.idFromName('global')
        const admin = await env.HUDDLE_SERVER.get(id).admin()
        await admin.purgeUser(event.data.id)
      }

      return new Response('ok')
    }

    // ...your normal WebSocket upgrade route
  },
}
```

Your Worker is already the place where HTTP requests enter your app. So [your own auth checks](#auth-is-your-boundary) (a webhook signature check, an IP allowlist, or any other check) protect the route before it calls `admin()`. LiveThing does not add its own auth layer.

::warning
Export your Durable Object with a **class declaration**, not `export const`:

```typescript [worker.ts]
import { bind } from '@livething/server-cloudflare'
import { huddle } from './server/huddle-definition'

export class HuddleServer extends bind(huddle) {}
```

`wrangler types` generates this type for the binding, which needs a **type** named `HuddleServer`:

```text
DurableObjectNamespace<import("./worker").HuddleServer>
```

A `const` export gives only a value:

```typescript [worker.ts]
import { bind } from '@livething/server-cloudflare'
import { huddle } from './server/huddle-definition'

// Wrong: no type named HuddleServer
export const HuddleServer = bind(huddle)
```

So that reference finds no type, and the binding becomes `any` with no warning. TypeScript then checks none of your `stub.admin()`, `stub.shutdown()`, or `stub.fetch()` calls.
::

### What crosses the stub

A Worker and a Durable Object are separate processes, so a call between them is RPC. The admin object on the stub has the **same shape** as the admin context inside your `api`: `connections`, `users`, `channels`, `connectionCount`, `broadcast`, `purgeUser`, and `closeConnections`, plus your own `api` methods. Each nested part is an RPC target, so you can chain calls without awaiting each level:

```typescript [worker.ts]
import type { Env } from './helpers'

export default {
  async fetch(request: Request, env: Env) {
    const id = env.HUDDLE_SERVER.idFromName('global')
    await env.HUDDLE_SERVER.get(id)
      .admin()
      .users.get('user_9')
      .broadcast('announcement', { text: 'your export is ready' })
    return new Response('ok')
  },
}
```

Or keep the admin object and make several calls:

```typescript [worker.ts]
import type { Env } from './helpers'

export default {
  async fetch(request: Request, env: Env) {
    const id = env.HUDDLE_SERVER.idFromName('global')
    const admin = await env.HUDDLE_SERVER.get(id).admin()

    const live = await admin.connectionCount
    await admin.channels.broadcast('announcements', 'announcement', {
      text: 'maintenance in 5m',
    })

    // `true` when the user has a live connection on this Durable Object.
    const userOnline = await admin.users.get('user_9').isOnline()

    // `users.get(id).ref()` builds the user ref inside the DO.
    await admin.channels
      .get('announcements')
      .kick(await admin.users.get('user_9').ref(), {
        reason: 'removed by a moderator',
      })

    // For a dynamic channel, name the family key and the instance name.
    await admin.channels.broadcast(
      { family: 'rooms', name: 'room:42' },
      'message',
      {
        id: crypto.randomUUID(),
        text: 'This room is closing.',
        from: 'system',
        sentAt: Date.now(),
      },
    )

    // Snapshots cross as data. Their `ref()` crosses as a function you can still call.
    for (const info of await admin.connections.all()) {
      if (info.quality === 'poor') {
        await admin.connections
          .get(await info.ref())
          .close(4000, 'slow connection')
      }
    }

    return Response.json({ live, userOnline })
  },
}
```

The types come from your server definition, the same as on Node. An event name your server does not emit, or a wrong payload, is a compile error in the Worker. `admin.channels.broadcast()` takes the channel, the event and the payload. It checks the event and payload against the channel you name, so an event of another channel is a compile error too.

To broadcast to a channel, use `admin.channels.broadcast`. The handle from `admin.channels.get(...)` has `members` and `kick`, but no `broadcast` on Cloudflare. The stub types cannot carry which name you passed to `get`, so a `broadcast` on the handle could not be checked against that channel's events.

The stub also has binary senders, from the binary events you declare. When the root lists [`binary({ emits })`](/server/binary/overview), it has the first three senders below. When a channel lists `binary({ emits })`, it has the last one:

<!-- docs-check: skip -->

```ts
admin.binary.broadcast(event, bytes, { info })
admin.users.get(id).binary.broadcast(event, bytes, { info })
admin.connections.get(ref).binary.send(event, bytes, { info })
admin.channels.binary.broadcast(event, bytes, { channel, info })
```

A scope with no binary events has no `.binary` sender on the stub's type, even when `binary()` is listed. The bytes are copied across the stub, like every argument.

Because the call crosses a process boundary, two more rules apply:

- Every call returns a promise, even when the operation returns nothing. Reading `admin.connectionCount` returns a promise too.
- Arguments and results are copied. Snapshots from `connections.all()` and `channel.members()` have the same fields as a [`ConnectionInfo`](/server/context-and-storage/connections). Their `ref()` method becomes a function that runs inside the DO, so call it with `await`. A connection ref or user ref that you build by hand in the Worker, with `instance: undefined`, means the DO that owns this admin surface. A ref that names a different instance is rejected.

Storage and the other internal services (`sql`, `kv`, `schedule`) are not on the stub at all. Your `api` methods use them **inside** the Durable Object, where your code already runs.

## Node.js

`setup().bind(huddle, options)` returns a WebSocket endpoint that runs in the same process as your HTTP server. Keep that endpoint, and call `admin()` on it from any other route. This example uses Express:

```typescript [huddle-server.ts]
import { setup } from '@livething/server-node'
import express from 'express'
import { verifyClerkWebhook } from './huddle-data'
import { huddle } from './server/huddle-definition'

const app = express()
const { bind } = setup()
const huddleEndpoint = bind(huddle, { sql: './data/huddle.sqlite' })

app.post('/webhooks/clerk', async (req, res) => {
  const event = await verifyClerkWebhook(req)
  if (event.type === 'user.deleted') {
    const admin = await huddleEndpoint.admin()
    await admin.purgeUser(event.data.id)
  }

  res.send('ok')
})
```

There is no stub here. The engine is in the memory of the same process, so `huddleEndpoint.admin()` gives you the **whole admin context**. It is the same object your `api` methods see: `admin.connections.all()`, `admin.users.get(id).broadcast(…)`, `admin.connectionCount`. It has the same shape as on Cloudflare, but nothing is copied and no call returns a promise unless the operation itself is async. Its types also come from your server definition. The Bun adapter also gives you the admin surface in the same process.

The route must use the **same** endpoint object that serves the WebSocket connections. Each `bind()` call starts a separate endpoint with its own connections, so an endpoint created somewhere else sees no connected users. In a plain Node server this is simple: create the endpoint once and use it in both places. In a framework that loads your route code through Vite or a build step, a shared module can be loaded twice. Each [Node framework section](/server/adapters/node#frameworks) ends with a tested admin route for that framework: [Nuxt](/server/adapters/node#call-the-admin-api-from-a-nuxt-route), [SolidStart](/server/adapters/node#call-the-admin-api-from-a-solidstart-route) and [TanStack Start](/server/adapters/node#call-the-admin-api-from-a-tanstack-start-route) share one server file, and [React Router](/server/adapters/node#call-the-admin-api-from-a-react-router-route), [SvelteKit](/server/adapters/node#call-the-admin-api-from-a-sveltekit-route) and [Astro](/server/adapters/node#call-the-admin-api-from-an-astro-route) keep one endpoint on `globalThis`.

## Auth is your boundary

Admin operations do not go through the WebSocket protocol. They do not run `authenticate`, a channel's `check` / `commit` gate, or any other check that protects client traffic. The engine fully trusts your server code.

So **you must protect the routes that call `admin()`**. On Cloudflare, only your Worker can reach the DO. Your Worker route is where you verify the webhook signature or check the token. On Node, the call happens inside your own HTTP server, where your existing auth middleware already runs.
