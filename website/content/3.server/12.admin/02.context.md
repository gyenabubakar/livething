Your `api` factory receives a `ctx`. The built-in admin operations run against the same `ctx`. This object is the **admin context**. Its type is `ConnectionlessContext`: it is a view of the whole server, not of one socket. So it has no `id`, no `send`, and no `meta`: no socket is the subject. The [`onShutdown`](/server/lifecycle-and-intercept/hooks#onshutdown) hook and [scheduled task](/server/handlers/scheduled) bodies get this same context, so everything on this page works there too. This page lists what it has.

## Broadcast to everyone

`ctx.broadcast(event, payload)` sends an event to every live connection. It is typed against your server's `emits(...)`. So a wrong event name or a wrong payload is a compile error.

Every `api` on this page is an example that replaces the `api` of Huddle's `assemble(...)` call.

```typescript [server/admin-api.ts]
import { base } from './base'
import { handleSendDigest } from './huddle-definition'

export const huddleWithAnnounce = base.assemble({
  handlers: [handleSendDigest],
  api: (ctx) => ({
    announce(text: string) {
      ctx.broadcast('announcement', { text })
    },
  }),
})
```

## Reach a channel by name

`ctx.channels.get(name)` returns a handle to one channel, found by its name. You are not a member of the channel. You act on it from outside. For a dynamic family, pass the family key and the instance name:

```ts
// Inside any Huddle handler
const room42 = ctx.channels.get('rooms', 'room:42')
```

A name that was never declared throws `ChannelNotFound`.

`ctx.channels` belongs to the [`channels()`](/server/capabilities/channels) capability. You must list it in `server({ capabilities: [...] })`. Without it, `ctx.channels` is not on the type, and reading it is a compile error. Your handlers follow the same rule.

The handle gives you the channel operations that do not need a connection: `broadcast`, `members`, `memberCount`, and `kick`, plus `binary.broadcast` when the channel declares binary events.

```typescript [server/admin-api.ts]
import { base } from './base'
import { handleSendDigest } from './huddle-definition'

export const huddleWithCloseRoom = base.assemble({
  handlers: [handleSendDigest],
  api: (ctx) => ({
    async closeRoom(roomId: string) {
      const channel = ctx.channels.get('rooms', `room:${roomId}`)
      channel.broadcast('message', {
        id: crypto.randomUUID(),
        text: 'This room is closing.',
        from: 'system',
        sentAt: Date.now(),
      }) // to the channel's members

      const userIds = new Set(
        channel.members().map((member) => member.userId),
      )
      for (const userId of userIds) {
        if (userId === '') continue

        // an anonymous connection has no user to kick
        await channel.kick(ctx.users.get(userId).ref(), {
          reason: 'room-closed',
        })
      }
    },
  }),
})
```

`channel.members()` returns a snapshot of the connections in the channel. An anonymous connection has an empty `userId`. `channel.memberCount()` returns how many connections are in the channel, without building the list.

`channel.kick(target, opts)` removes a user from the channel. The target is a `UserRef` or a `TagRef`. `reason` is required. When the kick removes a user's last connection in the channel, it also deletes the durable membership row, so the user does not join the channel again automatically on their next reconnect.

### Broadcast to one channel

`ctx.channels.broadcast()` sends an event to one channel's members. It takes the channel, the event and the payload. Name a static channel by its name, such as `'general'`. Name one channel of a dynamic family with `{ family, name }`, as the example below does for a room. The event and payload are checked against the `emits(...)` of the channel you name. So an event of another channel is a compile error.

```typescript [server/admin-api.ts]
import { base, rooms } from './base'
import { handleSendDigest } from './huddle-definition'

export const huddleWithSystemMessage = base.assemble({
  handlers: [handleSendDigest, rooms],
  api: (ctx) => ({
    postSystemMessage(roomId: string, text: string) {
      ctx.channels.broadcast(
        { family: 'rooms', name: `room:${roomId}` },
        'message',
        {
          id: crypto.randomUUID(),
          text,
          from: 'system',
          sentAt: Date.now(),
        },
      )
    },
  }),
})
```

It does the same as `.broadcast(event, payload)` on the handle from `ctx.channels.get(...)`. On Cloudflare, use `channels.broadcast`: [the channel handle you reach through the stub](/server/admin/reaching-it#what-crosses-the-stub) has no `broadcast`.

## Sending bytes

With [`binary()`](/server/binary/overview) listed, these senders have a `.binary` key with the same methods, for binary events:

<!-- docs-check: skip -->

```ts
ctx.binary.broadcast(event, bytes, { info })
ctx.channels.binary.broadcast(event, bytes, { channel, info })
ctx.users.get(id).binary.broadcast(event, bytes, { info })
ctx.connections.get(ref).binary.send(event, bytes, { info })
```

A channel handle from `ctx.channels.get(...)` has `.binary.broadcast(...)` only when that channel lists `binary({ emits })`. The info is checked against the `binary({ emits })` of the scope, as the payload of a JSON event is checked against its `emits(...)`.

## Remove a user everywhere

`ctx.purgeUser(userId)` is the one call you need when your auth provider tells you a user was deleted. It does all of this:

- removes the user from every channel they belong to, live and durable
- removes their persistent tags
- deletes their inbox rows and read receipts
- deletes their last-seen mark
- deletes the replay messages stored for them (messages to everyone stay)
- deletes their durable streams, and their subscriptions to broadcast streams
- closes every live socket they hold

It needs no capability of its own. It cleans up only the durable data that the user actually has. For a capability you did not list, there is nothing to clean up. Passing an empty string throws a `LiveThingConfigError`, because an empty ID would match every anonymous connection.

Every cleanup step runs, even if an earlier step throws. The live sockets are always closed. So a purge never stops halfway and leaves live connections open. If any step failed, `ctx.purgeUser` rejects after every step has run. The error is an `AggregateError` that holds all the failures. So a partial cleanup is reported to you and does not fail silently.

A handler or task that was already running when the purge started cannot write that user's membership, replay, tag, inbox or last-seen rows, even after the purge ends. Closing the socket writes no last-seen row either. Code that starts after the purge can write, so the same user ID can sign in again. The server remembers its last 10,000 purged users for this, in memory.

```typescript [server/admin-api.ts]
import { base } from './base'
import { handleSendDigest } from './huddle-definition'

export const huddleWithUserDeleted = base.assemble({
  handlers: [handleSendDigest],
  api: (ctx) => ({
    userDeleted(id: string) {
      return ctx.purgeUser(id)
    },
  }),
})
```

### Broadcast streams the user created

A [broadcast](/server/streams/broadcast) stream here is a [recorded](/server/streams/durable-recorded) stream created with `broadcast: true`. It belongs to the whole channel, not only to the connection that started it. So `ctx.purgeUser` must decide what happens to a stream that the purged user created but other people still read.

**By default, `ctx.purgeUser` deletes that content too**, like everything else the user owns. The stream and its recorded chunks are deleted. This is the safe default for a "delete this user's data" call. If a caller does not read the options, no data is left behind by mistake.

```typescript [server/admin-api.ts]
import { base } from './base'
import { handleSendDigest } from './huddle-definition'

export const huddle = base.assemble({
  handlers: [handleSendDigest],
  api: (ctx) => ({
    async deleteAccount(userId: string) {
      // Default: any broadcast stream this user created (the stream row and
      // its recorded chunks) is deleted, like everything else they own.
      await ctx.purgeUser(userId)
    },
  }),
})
```

In some apps, the broadcast content belongs to the channel, and other members should still read it after that user is gone. In that case, pass `{ keepBroadcastContent: true }`:

```typescript [server/admin-api.ts]
import { base } from './base'
import { handleSendDigest } from './huddle-definition'

export const huddle = base.assemble({
  handlers: [handleSendDigest],
  api: (ctx) => ({
    async deleteAccount(userId: string) {
      // Keep the channel-owned stream and its chunks.
      // The user is still removed as the stream's creator.
      await ctx.purgeUser(userId, { keepBroadcastContent: true })
    },
  }),
})
```

A stream that is still running stops either way. The chunks recorded so far stay and no new ones are added. The stream is marked as ended, so members can still read it.

With either option, the user is removed as the stream's creator. A purge never leaves a record that names a deleted user as its creator.

## Close connections

`ctx.closeConnections()` closes every live socket. Pass `{ userId }` to close only the sockets of one user. You can also pass a close code and a reason.

```typescript [server/admin-api.ts]
import { CloseCodes } from '@livething/server/errors'
import { base } from './base'
import { handleSendDigest } from './huddle-definition'

export const huddle = base.assemble({
  handlers: [handleSendDigest],
  api: (ctx) => ({
    closeEveryone() {
      ctx.closeConnections()
    },
    revokeSession(userId: string) {
      ctx.closeConnections(
        { userId },
        CloseCodes.AUTH_INVALID,
        'session revoked',
      )
    },
  }),
})
```

Each code has its own [meaning to the client](/core/close-codes).

## Inspect connections

`ctx.connections.all()` returns a snapshot of every live connection. `ctx.connectionCount` is the number of live connections right now. To reach one connection, use `ctx.connections.get(ref)`. To reach one user, use `ctx.users.get(id)`. `ctx.users.get(id).isOnline()` tells you if that user has a live connection on this server instance.

```typescript [server/admin-api.ts]
import { base } from './base'
import { handleSendDigest } from './huddle-definition'

export const huddleWithPresenceChecks = base.assemble({
  handlers: [handleSendDigest],
  api: (ctx) => ({
    onlineUsers() {
      return ctx.connections.all().map((c) => c.userId)
    },
    isTeammateOnline(userId: string) {
      return ctx.users.get(userId).isOnline()
    },
  }),
})
```

## Storage, scheduling, and platform

The admin context also has the storage and platform members. They have the same shapes as in your handlers:

::field-group
::field{name="sql" type="SQLProvider"}
Run SQL against the server's durable store, for example `ctx.sql.exec('UPDATE ...', ...)`.
::
::field{name="kv" type="KVProvider"}
Simple key-value storage with get, set, and delete.
::
::field{name="schedule / cancelScheduled" type="(taskId, ...) => void"}
Queue or cancel a scheduled task, the same as in a handler. These members belong to the [`scheduled()`](/server/capabilities/scheduled) capability. If you do not list it, neither member is on the type.
::
::field{name="log" type="Logger"}
The server's structured logger.
::
::field{name="platform" type="Platform"}
The raw platform object from the adapter.
::
::

::note
The admin context has no `tags` member. To work with tag groups, use a connection handler.
::
