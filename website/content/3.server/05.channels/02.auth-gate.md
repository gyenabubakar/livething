Before a connection becomes a member, a channel can run a gate. The gate has two parts that run in order: `check`, an async permission test, and `commit`, a synchronous final check. Either one can reject the subscribe by throwing. Both are optional — a channel with neither lets everyone in.

```typescript [room.ts]
import * as v from 'valibot'

const room = base.channel('room', {
  outgoing: { emits: { joined: t<{ username: string }>() } },
  subscribe: v.object({ token: v.string() }),
  async check(_ctx, input) {
    const role = await lookupRole(input.token) // your own lookup
    if (!role) throw new Error('unknown or missing token')
    return { role } // handed to commit
  },
  commit(ctx, { role }) {
    if (role === 'banned') throw new Error('banned role may not subscribe')
    if (ctx.channel.members().length >= 2) throw new Error('room is full')
  },
})
```

## `subscribe` — validate the payload first

A client passes a payload when subscribing. Declare a `subscribe` schema to validate it. The validated, typed value arrives as the second argument of `check`. A payload that fails the schema is rejected before `check` runs.

```typescript [room.ts]
const room = base.channel('room', {
  outgoing: { emits: { joined: t<{ username: string }>() } },
  subscribe: v.object({ token: v.string() }),
  async check(_ctx, input) {
    // `input` is typed `{ token: string }` — validated from the schema above.
    const { token } = input
    // ...
  },
})
```

Without a `subscribe` schema, `check`'s second argument is `unknown` — the connection may still send a payload, but it is not validated for you. A channel can take a `subscribe` schema with no `check`; then the payload is validated and the subscribe proceeds.

## `check` — the async gate

`check` runs once, on a first subscribe. It can be `async` (the engine awaits it), so use it for token checks, database reads, or any permission test that needs to await — a plain synchronous `check` works too. Throw to reject. Whatever it returns is passed straight to `commit`.

```typescript [room.ts]
const room = base.channel('room', {
  outgoing: { emits: { joined: t<{ username: string }>() } },
  async check(ctx) {
    if (ctx.meta.username === 'blocked-user') {
      throw new Error('blocked-user may not subscribe')
    }
    // return value is optional — undefined is fine when there is no commit
  },
})
```

The return value is fully typed. TypeScript infers it and types `commit`'s second argument to match — no manual annotation:

```typescript [room.ts]
const room = base.channel('room', {
  outgoing: { emits: { joined: t<{ username: string }>() } },
  async check(_ctx, input: { token: string }) {
    const role = await lookupRole(input.token) // 'member' | 'vip' | 'banned'
    return { role }
  },
  commit(ctx, { role }) {
    // `role` is typed from check's return — no annotation needed.
    if (role === 'banned') throw new Error('banned role may not subscribe')
  },
})
```

::note
`check` runs only on a **first** subscribe. When a member of a persistent channel reconnects, the channel auto-rejoins them and runs `revalidate` instead — see below. So `check` is the right place for one-time admission, and `revalidate` is the right place for revocation that must take effect across reconnects.
::

## `commit` — the synchronous final gate

`commit` runs right before the membership is written, in the same JavaScript tick. It is synchronous — **it must not be `async` or return a Promise.** If it returns a Promise (or any thenable), the engine throws:

```
commit() must be synchronous.
```

...the moment a subscribe runs through it. The subscribe fails — no membership is written — and because an async `commit` is a setup mistake rather than a per-user denial, the client receives an `internal-error` frame and the connection itself stays open. Use `commit` for a last-moment check on live state, like a capacity limit, where the count must not change between the check and the write.

```typescript [room.ts]
const room = base.channel('room', {
  outgoing: { emits: { joined: t<{ username: string }>() } },
  commit(ctx) {
    if (ctx.channel.members().length >= 2) {
      throw new Error('room is full')
    }
  },
})
```

Because `commit` runs in one tick with the membership write, `ctx.channel.members()` here is the exact current count — two members joining at once cannot both slip past a cap of two.

`commit` can be used on its own, with no `check`. Its second argument is then the value `check` returned, which is `undefined` when there is no `check`.

## How accept and reject work

The two gates are an AND: a subscribe is accepted only if neither throws.

| Outcome            | What you do                                      | What happens                                                              |
| ------------------ | ------------------------------------------------ | ------------------------------------------------------------------------- |
| Accept             | Let `check` and `commit` return normally         | The connection becomes a member; `subscribe` hook runs.                   |
| Reject in `check`  | Throw from `check`                               | No membership written; the subscriber gets an error; `commit` never runs. |
| Reject in `commit` | Throw from `commit`                              | No membership written; the subscriber gets an error.                      |
| Bad payload        | Send a payload that fails the `subscribe` schema | Rejected before `check`; a validation error reaches the subscriber.       |

A throw from either gate stops the subscribe and surfaces the error to the connection that tried to join. Throw a plain `Error`, or a typed [`error(...)`](/core/error-model) so the client can match on the code:

```typescript [room.ts]
import { error } from '@wskit/server'

const RoomFull = error('room-full')

const room = base.channel('room', {
  outgoing: { emits: { joined: t<{ username: string }>() } },
  commit(ctx) {
    if (ctx.channel.members().length >= 50) throw RoomFull()
  },
})
```

The shared error model — `error(...)`, `.matches()`, the built-in catalog — lives in [Core](/core/error-model). For server control-flow errors like `Block`, see [Errors](/server/capabilities/errors).

## Membership — what a subscribe gives the connection

When both gates pass, the connection is added to the channel's member list. From then on it receives the channel's broadcasts and may send the channel's events. Inside any channel handler, `ctx.channel.members()` returns the current members as `ConnectionInfo[]`.

A duplicate subscribe from a connection that is **already** a member is a complete no-op. The gates do not run a second time and no extra confirmation is sent — calling subscribe on an existing membership just means "make sure they are in".

You can also subscribe a connection from server code with `ctx.channels.get(...).subscribe(ref, payload?)`. It runs the same gate — `check` then `commit` — and is a no-op if the connection is already a member:

```typescript [auto-join.ts]
const handleJoin = base.on('trigger-server-subscribe', {
  input: v.object({}),
  async run(ctx) {
    // Same gate as a client subscribe; the payload feeds check.
    await ctx.channels.get('room2').subscribe(ctx.connection)
  },
})
```

## `revalidate` — re-check on auto-rejoin :badge[needs persistence()]

When the [`persistence()`](/server/capabilities/persistence) capability is listed, a member that drops keeps its membership and is auto-rejoined on reconnect. The auto-rejoin does **not** run `check` or `commit` again — the user already passed admission. To re-authorize on every reconnect (a ban, a lapsed permission, a closed room), add `revalidate`.

```typescript [archive.ts]
const archive = base.channel('archive-room', {
  outgoing: { emits: { entry: t<{ line: string }>() } },
  persistent: true,
  async check(ctx) {
    if (await isBanned(ctx.meta.username)) throw new Error('banned')
  },
  async revalidate(ctx) {
    // Runs on auto-rejoin only. Throw to revoke: the durable row is dropped
    // and the connection is not brought back into the channel.
    if (await isBanned(ctx.meta.username)) throw new Error('banned')
  },
})
```

`revalidate` is async, gets only `ctx` (no subscribe payload — the reconnect carries none), and ignores its return value. Throwing revokes the membership: the durable row is deleted and the connection stays out.

::warning
`revalidate` only fires on auto-rejoin, which only happens for persistent channels. Adding it to a non-persistent channel throws at startup with a message telling you to enable persistence or remove the hook — it would otherwise never run. Keep first-subscribe admission in `check`.
::

### When auto-rejoin runs, and what a reject looks like on the wire

Auto-rejoin runs for every durable membership the reconnecting user holds, all before your `onConnect(...)` hook fires — so by the time `onConnect` runs, the connection is already back in its old channels. Each membership is revalidated on its own:

- **Pass** — the connection is subscribed through the same server-side subscribe path as `channelHandle.subscribe(...)`. It gets `__subscribeOk__` for that channel; other members see `__memberOnline__`, not `__memberJoin__` (the group did not change, only this socket's presence).
- **Reject** (`revalidate` throws) — the durable row is deleted, and the connection receives a channel-scoped `__error__` frame with code `rejoin-rejected` instead of `__subscribeOk__`. The connection is not added back to that channel, but the rest of its memberships still rejoin normally.
- **Channel renamed or removed** since the row was written — that membership is skipped silently, no error frame. The orphaned row is swept later by the boot-time cleanup described in [persistence](/server/capabilities/persistence).

A storage failure or a config mistake (not a `revalidate` throw) never deletes the durable row — only a genuine `revalidate` rejection does.

## The subscription wire flow

Put together, a client-initiated subscribe runs this sequence.

::steps{level="3"}

### Validate the payload

If the channel has a `subscribe` schema, the client's payload is validated. A failure rejects the subscribe with a validation error and stops here.

### `check`

The async gate runs. A throw rejects the subscribe and sends the error to the subscriber. Its return value is kept for `commit`.

### `commit`

The sync gate runs in the same tick as the membership write. A throw rejects the subscribe.

### Confirm and sync

The server confirms the subscribe to the new member and sends it the current member list, so the joiner sees who is already there.

### Announce and run the hook

Existing members get presence frames marking the new arrival. Then your `subscribe` hook runs — push initial state here.

::

The confirmation tells the client whether this channel is persistent, so a persistent channel is left to server-driven auto-rejoin on reconnect rather than the client re-subscribing. The presence frames are covered on the [Membership & Presence](/server/channels/membership-and-presence) page.

## Leaving — the three paths

Leaving mirrors joining. Which hooks fire depends on how the connection left and whether the channel is persistent.

| Path                                            | Fires `unsubscribe` | Fires `sessionEnd` | Drops durable membership  |
| ----------------------------------------------- | ------------------- | ------------------ | ------------------------- |
| Client sends `__unsubscribe__`                  | Yes                 | Yes                | Yes                       |
| `kick(target, { revoke: false })` (the default) | Yes                 | Yes                | No (auto-rejoins later)   |
| `kick(target, { revoke: true })`                | Yes                 | Yes                | Yes (persistent channels) |
| Plain disconnect, persistent channel            | No                  | Yes                | No (auto-rejoin later)    |
| Plain disconnect, ephemeral channel             | Yes                 | Yes                | (no durable row)          |

`kick(target, { revoke: true })` is the true leave: on a persistent channel it deletes the durable membership row, so the kicked user is **not** auto-rejoined on their next reconnect — they must subscribe again. Omitting `revoke` (or passing `false`) boots the user's current sockets but leaves the durable row in place, so a later reconnect rejoins them automatically. (On an ephemeral channel there is no durable row to delete either way.)

The key difference is the last two rows. On a **persistent** channel a plain disconnect is not a true leave — the user keeps their seat and will be auto-rejoined — so only `sessionEnd` fires. On an **ephemeral** channel a disconnect _is_ a true leave, so both fire. Use `unsubscribe` for "the user left the group" cleanup and `sessionEnd` for "this socket is gone" cleanup.
