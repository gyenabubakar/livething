Some engines are **host-owned**: `dedup`, `sequence`, `keepalive`, `rateLimit`, and the whole `replay` family — built-in `replay.history()` / `replay.snapshot()` **and** `replay.custom()`. They are global to the whole server, so a plugin can never list one in its scoped [`define`](/server/plugins/authoring) — doing so is a compile error. A plugin that _needs_ one declares a prerequisite instead, and the host must satisfy it.

```typescript [host-only.ts]
const h = define({
  scope: 'plugin',
  capabilities: [
    resumableStream(), // OK — a plugin can own its own durable streams
    // dedup(),           // compile error: host-owned, a plugin can't list it
  ],
})
```

## Auto-derived requirements

A plugin's own channel can list `inbox()` in that channel's own `capabilities` — but `inbox()` needs `dedup()` and a durable `sequence()` on the host, and the plugin cannot list either itself. That requirement is **auto-derived**: WSKit reads it off the plugin's own capabilities and passes it up to the host as a dependency. The host must list `dedup()` and `sequence({ persist: true })`, or its `assemble` fails with a clear error. (This is the same requirement mechanism used in [Capabilities](/server/define/capabilities), applied across the plugin boundary.)

```typescript [auto-derived.ts]
import { channels } from '@wskit/server/channels'
import { inbox } from '@wskit/server/inbox'

const h = define({
  scope: 'plugin',
  capabilities: [channels()],
})

// The channel's own inbox() needs dedup() and a durable sequence() on the
// host — the plugin cannot list either, so the host must.
const feed = h.channel('feed', { capabilities: [inbox()] })
```

That fails the host's `assemble()` with a "does not list" error until the host adds `dedup()` and `sequence({ persist: true })` — the plugin never lists them itself.

::note
"Plugin-safe" is exactly "every capability except the host-owned engines listed above." Behavior capabilities a plugin _can_ own itself — `clientRequests`, `serverRequests`, `channels`, the stream kinds, `emits`, `errors`, `tags`, `intercepts` — are all fine in a scoped list. Note `base.replay` is not among them: even `replay.custom()` is host-owned, so a plugin cannot register its own custom replay strategy.
::

## Stating a prerequisite explicitly

Auto-derivation covers anything the plugin's own capabilities imply. When a plugin's _code_ needs a **host-owned** capability that nothing in its config implies — it reads `ctx.latency`, which only `keepalive()` provides, say — state it directly with `dependsOn`, passing the host capability factory. (Only the host-owned engines are valid `dependsOn` targets; behavior capabilities like `clientRequests()` a plugin simply lists itself, so they are never dependencies.)

```typescript [depends-on.ts]
import { keepalive } from '@wskit/server/keepalive'
import { plugin } from '@wskit/server/plugins'

export const Presence = plugin('acme:presence', {
  handler: h.assemble({ handlers: [] } /* ... */),
  dependsOn: [keepalive], // the host must list keepalive(...)
})
```

A missing prerequisite is a build error that names what to add, the same way a [capability requirement](/server/define/capabilities) does for a top-level server. Only host capability **factories** are accepted here — passing a plugin factory is a compile error.

::caution
Pass the capability **factory** itself, never a called capability: `dependsOn: [keepalive]`, not `dependsOn: [keepalive()]`. The check matches a `dependsOn` entry to a listed capability by reading an identity token off the factory — it never calls it. That is also why an arg-requiring factory like `keepalive` is a safe `dependsOn` target even though `keepalive({ pingIntervalMs, idleTimeoutMs })` needs a config object to run: the host is the one who calls it.
::
