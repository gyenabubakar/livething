Some capabilities are **host-owned**. A host-owned capability works for the whole server, so only the host server (the app's own `server()`, not a plugin) can list it. These are the host-owned capabilities:

- `dedup`
- `sequence`
- `keepalive`
- `rateLimit`
- `lastSeen`
- the whole `replay` family: `replay.history()` and `replay.snapshot()`

A plugin can never list one of these in its scoped [`server`](/server/plugins/authoring). If it does, TypeScript reports a compile error. A plugin that _needs_ one of them declares a prerequisite instead. A prerequisite is a capability that the host must list for the plugin to work.

```typescript [polls/server.ts]
import { server } from '@livething/server'
import { recordedStream } from '@livething/server/streams'

const h = server({
  scope: 'plugin',
  capabilities: [
    recordedStream(), // OK: a plugin can own its own durable streams
    // dedup(),           // compile error: dedup is host-owned, so a plugin can't list it
  ],
})
```

## Auto-derived requirements

A plugin's own channel can list `inbox()` in that channel's own `capabilities`. But `inbox()` needs `dedup()` and a durable `sequence()` on the host, and the plugin cannot list either of them. So LiveThing creates this requirement for you. It is **auto-derived**: LiveThing reads it from the plugin's own capabilities and passes it to the host as a dependency. The host must then list `dedup()` and `sequence({ persist: true })`. This is the same requirement check described in [Capabilities](/server/server/capabilities), applied to a plugin and its host.

```typescript [polls/server.ts]
import { server } from '@livething/server'
import { channels } from '@livething/server/channels'
import { inbox } from '@livething/server/inbox'
import { plugin } from '@livething/server/plugins'

const h = server({
  scope: 'plugin',
  capabilities: [channels()],
})

// The channel's own inbox() needs dedup() and a durable sequence() on the
// host. The plugin cannot list either one, so the host must.
const poll = h.channel('poll', {
  membership: 'persistent',
  capabilities: [inbox()],
})

export const Polls = plugin('acme:polls', {
  definition: h.assemble({ handlers: [poll] }),
})
```

If the host lists `Polls()` but not `dedup()` or `sequence()`, the host's `assemble()` throws an error. The error says that the plugin needs a capability the host does not list, and names that capability. If the host lists `sequence()` without `persist: true`, the server throws an error when it starts. The plugin itself never lists these capabilities.

::note
A capability is "plugin-safe" when it is not one of the host-owned capabilities listed above. A plugin can list plugin-safe capabilities in its own scoped list: `clientRequests`, `serverRequests`, `scheduled`, `channels`, the stream kinds, `emits`, `errors` and `tags`.
::

## Stating a prerequisite explicitly

Auto-derivation covers every requirement that the plugin's own capabilities create. Sometimes the plugin's _code_ needs a host-owned capability that nothing in its config asks for. For example, `acme:polls` wants every vote rate-limited, so one member can't spam a poll with votes. It needs the host's rate limiter, and only `rateLimit()` does that. In this case, state the prerequisite directly with `dependsOn`, and pass the host capability's factory function.

Only host-owned capabilities can go in `dependsOn`. A capability that a plugin can own, such as `clientRequests()`, is never a dependency: the plugin lists it in its own `capabilities` instead.

```typescript [polls/server.ts]
import { server } from '@livething/server'
import { plugin } from '@livething/server/plugins'
import { rateLimit } from '@livething/server/rate-limit'

const h = server({ scope: 'plugin' })

export const Polls = plugin('acme:polls', {
  definition: h.assemble({ handlers: [] }),
  dependsOn: [rateLimit], // the host must list rateLimit(...)
})
```

A missing prerequisite makes the host's `assemble()` throw an error that names the capability to add. A [capability requirement](/server/server/capabilities) on a top-level server works the same way. `dependsOn` accepts only host capability **factories**. If you pass a plugin factory or a plugin-safe capability factory, TypeScript reports a compile error.

::caution
Pass the capability **factory** itself, not a called capability: `dependsOn: [rateLimit]`, not `dependsOn: [rateLimit()]`. To match a `dependsOn` entry with a capability the host lists, LiveThing reads an identity token (a fixed name for each kind of capability) from the factory. It never calls the factory. So a factory that needs arguments, such as `rateLimit`, is still a safe `dependsOn` entry. `rateLimit({ windowMs, max })` needs a config object, but the host is the one that calls it.
::
