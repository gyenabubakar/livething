A plugin can register hooks — an `intercept` that runs before every incoming frame is routed, and an `onOutgoing` hook that runs before every outbound frame is sent. By default these hooks follow **least privilege**: a plugin's hooks see only the plugin's own (namespaced) frames. They never see the host app's frames, and they never see another plugin's frames.

That default is right for most plugins. A presence plugin only cares about its own heartbeats. But some plugins — a metrics counter, a request logger, an audit trail — exist _to_ watch the whole server. For those, you opt in.

::note
The hooks themselves come from the `intercepts()` capability, listed in the plugin's scoped `define`. See [intercepts](/server/define/capabilities) for the hook surface. This page is about **which frames** those hooks see across the plugin boundary.
::

## The default: own frames only

Here is a plugin that counts every frame its hooks see. With no opt-in, it counts only its own.

```typescript [counter.ts]
import { define, emits, t } from '@wskit/server'
import { intercepts } from '@wskit/server/intercepts'
import { plugin } from '@wskit/server/plugins'

const h = define({
  scope: 'plugin',
  capabilities: [intercepts(), emits({ counted: t<{ n: number }>() })],
})

let seen = 0

h.intercept((ctx, frame) => {
  seen += 1 // only the plugin's own incoming frames reach here
})

export const Counter = plugin('acme:counter', {
  handler: h.assemble({ handlers: [] } /* ... */),
})
```

The host lists it like any plugin — no extra wrapping:

```typescript [host.ts]
const base = define({
  env: t<Env>(),
  capabilities: [Counter()],
})
```

## Opting into host traffic

To see the host app's frames too, set `observesHostTraffic: true` in the manifest.

```typescript [metrics.ts]
import { define, t } from '@wskit/server'
import { intercepts } from '@wskit/server/intercepts'
import { plugin } from '@wskit/server/plugins'

const h = define({
  scope: 'plugin',
  capabilities: [intercepts()],
})

h.intercept((ctx, frame) => {
  // now the host app's frames reach here too
})

export const Metrics = plugin('acme:metrics', {
  handler: h.assemble({ handlers: [] } /* ... */),
  observesHostTraffic: true,
})
```

This is a privilege, and a wide one: an `intercept` return value replaces the app's own payload before its validator runs, and inside a host-observing hook you can throw the same control-flow errors on the app's traffic as on your own — `Block` to drop the app's frame, `Disconnect(code, reason)` to close the app's own connection. See [Blocking and disconnecting](/server/lifecycle-and-intercept/intercept#blocking-and-disconnecting). So WSKit makes the host grant it on purpose. When `observesHostTraffic` is the literal `true`, **listing the plugin bare is a type error** — you must wrap it with `observeHost(...)`.

::code-group

```typescript [granted.ts]
import { observeHost } from '@wskit/server/plugins'
import { Metrics } from './metrics'

const base = define({
  env: t<Env>(),
  capabilities: [observeHost(Metrics())], // privilege granted on purpose
})
```

```typescript [error.ts]
import { Metrics } from './metrics'

const base = define({
  env: t<Env>(),
  // ✗ type error: this plugin observes host traffic — wrap it in observeHost(...)
  capabilities: [Metrics()],
})
```

::

If the type check is bypassed — say `observesHostTraffic` was a non-literal boolean, so the brand never fired — the grant is still checked at `assemble()`. An ungranted host-observing plugin throws a clear build error naming the plugin and telling you to wrap it. When the grant _is_ present, WSKit logs a one-time warning that the plugin can see the app's frames, so the privilege is never silent.

::caution
`observeHost(...)` only changes what the plugin **observes**. It does not let the plugin's hooks see another plugin's frames — that boundary holds no matter what. A host-observing plugin sees its own frames plus the app's, and nothing else.
::

## `frame.owner` — who owns the frame

Every frame a hook receives carries an `owner` that says where it came from:

```typescript [owner-shape.ts]
type FrameOwner = { kind: 'app' } | { kind: 'plugin'; id: string }
```

The owner is derived from the event name. A plugin-owned event travels as `__<id>::<name>` on the wire (see [Namespacing](/server/plugins/namespacing)), so anything shaped that way is `{ kind: 'plugin', id }`; everything else is `{ kind: 'app' }`. A host-observing plugin uses `frame.owner` to tell its own frames from the app's and act only on what it means to.

```typescript [rewrite-own-vs-app.ts]
h.intercept((ctx, frame) => {
  if (frame.owner.kind === 'app' && frame.event === 'chat-message') {
    // a host frame — only visible because this plugin observes host traffic
    const payload = frame.payload as { text: string }
    return { ...payload, text: payload.text.trim() }
  }
})
```

On the **outgoing** side it is the same shape. Here a plugin tags its own outbound frame and leaves the app's alone:

```typescript [outgoing-own.ts]
h.onOutgoing((ctx, frame) => {
  if (!ctx) return // ctx is undefined for broadcast/task frames — no single connection
  if (frame.owner.kind === 'plugin' && frame.event === 'ready') {
    return { ...(frame.payload as Record<string, unknown>), hooked: true }
  }
})
```

::note
Two things to know about the frames a hook receives:

- **Short name vs wire name.** Inside a plugin's _own_ hook, `frame.event` for the plugin's own frame is the **short** name (`'ready'`). The host app's hook sees the same frame under its **wire** name (`'__acme:metrics::ready'`). Match on the form the hook in front of you actually receives.
- **`ctx` can be `undefined`.** In an `onOutgoing` hook, frames produced by a broadcast or a scheduled task arrive with no `ctx` — there is no single connection behind them — so guard with `if (!ctx) return` before reading it.
  ::

::note
On the host side, `frame.owner.id` is typed to the union of the plugin IDs the host actually registered. In an app-level `intercept` or `onOutgoing` hook, narrowing `frame.owner.kind === 'plugin'` gives you autocomplete for the real plugin IDs — a made-up ID is a type error.
::

## What sees what

| Hook owner                       | Its own frames | The app's frames   | Another plugin's frames |
| -------------------------------- | -------------- | ------------------ | ----------------------- |
| The host app                     | —              | yes (it owns them) | yes (every frame)       |
| A plugin (default)               | yes            | **no**             | no                      |
| A plugin with `observeHost(...)` | yes            | **yes**            | no                      |

The app's own hooks always see every frame — it is the host. A plugin starts locked to its own slice and only widens to the app's frames with an explicit grant. The cross-plugin wall never opens.

::note
A plugin channel's own `intercept` hook (registered with `room.intercept(...)`) follows the exact same rule as the plugin's top-level hooks — it inherits the plugin's `observesHostTraffic` setting. There's no separate opt-in for a channel's own hook.
::
