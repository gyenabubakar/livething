A plugin uses `ctx` in two places:

- **Inside** the plugin, its handlers receive a **scoped** `ctx`. "Scoped" means the `ctx` works only inside the plugin's own part of the server. Short names point to the plugin's own capabilities and emits.
- **Outside** the plugin, the host (the server that lists the plugin) calls the plugin's `api` through `ctx.plugin(id)`.

This page covers both.

## The scoped `ctx` inside a plugin

A plugin's handlers get the same `ctx` that a top-level server's handlers get: `ctx.send`, `ctx.kv`, `ctx.tags`, `ctx.channels`, `ctx.schedule`, and the rest. The difference is that every name points to the **plugin's own** part of the server. You write short names, and LiveThing adds the plugin's namespace for you (see [Namespacing](/server/plugins/namespacing)).

```typescript [scoped-ctx.ts]
import { emits, server, t } from '@livething/server'
import * as v from 'valibot'

const h = server({
  scope: 'plugin',
  capabilities: [emits({ 'user-online': t<{ id: string }>() })],
})

const heartbeat = h.on('heartbeat', {
  input: v.object({}),
  async run(ctx) {
    // 'user-online' is the plugin's own emit. It goes out as
    // __acme:presence::user-online, which matches the plugin's emits(...)
    ctx.send('user-online', { id: ctx.connection.id })

    // The ctx.kv key is namespaced too, so it never collides with the host's keys
    await ctx.kv.set('last-seen', Date.now())
  },
})
```

The plugin context has no runtime-specific configuration. If a plugin needs such values, it should accept them in its factory function and use them when it builds its scoped handlers (the handlers can read them because they are defined inside that function). See [Authoring](/server/plugins/authoring) for an example.

The scoped `ctx` only has the fields for the capabilities the plugin listed. For example, a plugin that lists `emits(...)` but not `channels()` has `ctx.send` but no `ctx.channels`. Reading a field the plugin did not declare is a compile error, the same as on a top-level server.

## The `api` a plugin exposes

A plugin can expose an **API** for each connection with the `api` field of its scoped `assemble(...)`. The `api` field is a factory function. It receives the plugin's own scoped `ctx` (the same `ctx` the plugin's `h.on(...)` handlers receive) and returns an object with the methods the host can call. You write it next to the handlers it uses. Then `plugin(...)` wraps the assembled result.

```typescript [presence.ts]
import { emits, server, t } from '@livething/server'
import { plugin } from '@livething/server/plugins'
import * as v from 'valibot'

const h = server({
  scope: 'plugin',
  capabilities: [emits({ 'user-online': t<{ id: string }>() })],
})

const heartbeat = h.on('heartbeat', {
  input: v.object({}),
  run(ctx) {
    ctx.send('user-online', { id: ctx.connection.id })
  },
})

const presence = h.assemble({
  handlers: [heartbeat],
  api(ctx) {
    return {
      announce() {
        // Uses the plugin's scoped ctx, so the event name is namespaced
        ctx.send('user-online', { id: ctx.connection.id })
      },
      whoAmI() {
        return ctx.connection.id
      },
    }
  },
})

export const Presence = plugin('acme:presence', {
  definition: presence,
})
```

## Calling the API with `ctx.plugin(id)`

Any host handler can get a registered plugin's API with `ctx.plugin(id)`. TypeScript suggests only the IDs of the plugins that the host listed. The return type is that plugin's `api` type, so the call is fully typed and needs no casts.

```typescript [host.ts]
import { server } from '@livething/server'
import * as v from 'valibot'
import { Presence } from './presence'

const base = server({
  capabilities: [Presence()],
})

const greet = base.on('greet', {
  input: v.object({}),
  run(ctx) {
    const presence = ctx.plugin('acme:presence') // typed to the plugin's api
    presence.announce()
    ctx.log.info('greeted', { who: presence.whoAmI() })
  },
})
```

LiveThing builds the API object the first time you call `ctx.plugin(id)`, and then stores it on that `ctx`. So repeated `ctx.plugin('acme:presence')` calls in the same handler return the same object, and the plugin's `api` factory runs at most once.

::note
Errors from a plugin are namespaced too. When a plugin handler throws an error that the plugin declared, such as `denied()`, the client receives the code `__acme:presence::denied`, not just `denied`. So a plugin's error codes never collide with the host's. See [Namespacing](/server/plugins/namespacing) and the [error model](/core/error-model).
::

::warning
`ctx.plugin(id)` only knows about plugins the host listed. Calling it with an ID that was never registered throws at runtime:

```text
[livething] ctx.plugin('acme:presence') — no plugin with id 'acme:presence' is registered. List the plugin in server({ capabilities: [...] }).
```

With an unknown ID, the call's return type is `unknown`, so using the result (for example `presence.announce()`) is a compile error. This usually shows the mistake before the code runs.
::

### A larger example

Here a notes plugin with the ID `acme:notes` exposes a database-style API with `insert` and `findAll` methods. The host's `base` lists `Notes()` and emits `note-added` and `note-list`. The host calls the plugin from two handlers:

```typescript [notes-host.ts]
const handleAddNote = base.on('add-note', {
  input: v.object({ title: v.string(), body: v.string() }),
  run(ctx, payload) {
    const notes = ctx.plugin('acme:notes')
    const note = notes.insert({
      title: payload.title,
      body: payload.body,
    })
    ctx.send('note-added', { id: note.id })
  },
})

const handleListNotes = base.on('list-notes', {
  input: v.object({}),
  run(ctx) {
    const notes = ctx.plugin('acme:notes')
    ctx.send('note-list', { notes: notes.findAll() })
  },
})
```

## One plugin per ID

A server can list each plugin **only once**. `plugin('acme:presence', ...)` returns a factory, and you list its result (`Presence()`) once. The host stores its plugins by ID, so the same plugin can't be registered twice. Listing an ID twice throws at `assemble()`:

```text
[livething] plugin('acme:presence') is listed more than once. Each plugin id owns a namespace and must be unique — list it once, or give the second one a different id.
```

If you need two of something, write two plugins with different IDs (`acme:cache-east`, `acme:cache-west`), or keep several copies inside one plugin's own state.

Client plugins follow the same rule: each client plugin ID can be registered only once on a socket. See [client Plugins](/client/plugins/overview) for the client side.
