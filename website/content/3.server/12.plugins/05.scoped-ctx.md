A plugin has two sides that meet the `ctx`:

- **Inside** the plugin, its handlers receive a `ctx` scoped to the plugin's own slice. Short names resolve against the plugin's own capabilities and emits.
- **Outside** the plugin, the host reaches the plugin's `api` through `ctx.plugin(id)`.

This page covers both.

## The scoped `ctx` inside a plugin

A plugin's handlers get the same `ctx` a top-level server's handlers get — `ctx.send`, `ctx.kv`, `ctx.tags`, `ctx.channels`, `ctx.schedule`, and the rest. The difference is that every name resolves against the **plugin's own** slice. You write short names; WSKit adds the plugin's namespace for you (see [Namespacing](/server/plugins/namespacing)).

```typescript [scoped-ctx.ts]
import { define, emits, t } from '@wskit/server'
import * as v from 'valibot'

const h = define({
  scope: 'plugin',
  capabilities: [emits({ 'user-online': t<{ id: string }>() })],
})

const heartbeat = h.on('heartbeat', {
  input: v.object({}),
  run(ctx) {
    // 'user-online' is the plugin's own emit — it goes out as
    // __acme:presence::user-online, matching the plugin's emits(...)
    ctx.send('user-online', { id: ctx.connection.id })

    // ctx.kv key is namespaced too — never collides with the host's keys
    ctx.kv.set('last-seen', Date.now())
  },
})
```

`ctx.env` is the one thing the plugin does **not** own: it is the host's environment value, passed through. A plugin may declare a type-only requirement for part of it, but it never supplies a separate value. See [Authoring](/server/plugins/authoring) for the environment requirement syntax.

The scoped `ctx` only exposes what the plugin actually listed. A plugin that lists `emits(...)` but not `channels()` has `ctx.send` but no `ctx.channels` — reading an undeclared field is a compile error, exactly as on a top-level server.

## The `api` a plugin exposes

A plugin can expose a per-connection **API** with the `api` field of its scoped `assemble(...)`. It is a factory that runs against the plugin's own scoped `ctx` — the same `ctx` the plugin's `h.on(...)` handlers see — and returns whatever object the host should be able to call. You author it right next to the handlers it wraps; `plugin(...)` then wraps the assembled result.

```typescript [presence.ts]
import { define, emits, t } from '@wskit/server'
import { plugin } from '@wskit/server/plugin'
import * as v from 'valibot'

const h = define({
  scope: 'plugin',
  capabilities: [emits({ 'user-online': t<{ id: string }>() })],
})

const heartbeat = h.on('heartbeat', {
  input: v.object({}),
  run(ctx) {
    ctx.send('user-online', { id: ctx.connection.id })
  },
})

const presence = h.assemble({
  handlers: [heartbeat],
  api(ctx) {
    return {
      announce() {
        // runs against the plugin's scoped ctx — the send is namespaced
        ctx.send('user-online', { id: ctx.connection.id })
      },
      whoAmI() {
        return ctx.connection.id
      },
    }
  },
})

export const Presence = plugin('acme:presence', { handler: presence })
```

## Reaching the API with `ctx.plugin(id)`

Any host handler reaches a registered plugin's API through `ctx.plugin(id)`. The ID is typed to the plugins the host actually listed, and the return type is that plugin's `api` type — so the call is fully typed, no casts.

```typescript [host.ts]
import { define, t } from '@wskit/server'
import { Presence } from './presence'

const base = define({
  env: t<Env>(),
  capabilities: [Presence()],
})

const greet = base.on('greet', {
  input: v.object({}),
  run(ctx) {
    const presence = ctx.plugin('acme:presence') // typed to the plugin's api
    presence.announce()
    ctx.log.info('greeted', { who: presence.whoAmI() })
  },
})
```

The API object is built lazily the first time you reach it and cached on the `ctx`, so repeated `ctx.plugin('acme:presence')` calls within the same handler return the same object and the plugin's `api` factory runs at most once.

::note
An error a plugin throws is namespaced too. When a plugin throws `denied()`, the client receives the code `__acme:presence::denied`, not a bare `denied`, so a plugin's error codes never collide with the host's. See [Namespacing](/server/plugins/namespacing) and the [error model](/core/error-model).
::

::warning
`ctx.plugin(id)` only knows about plugins the host listed. Reaching an ID that was never registered throws at runtime:

```text
[wskit] ctx.plugin('acme:presence') — no plugin with id 'acme:presence' is registered. List the plugin in define({ capabilities: [...] }).
```

The typed overload narrows `id` to the registered plugins, so this is usually caught at compile time first.
::

### A real example

The plugin handler in the e2e suite exposes a database-style API and the host reaches it from several handlers:

```typescript [db-host.ts]
const handleInsert = base.on('insert-record', {
  input: InsertRecord,
  run(ctx, payload) {
    const db = ctx.plugin('e2e:drizzle')
    const row = db.insert({ name: payload.name, value: payload.value })
    ctx.send('record-inserted', { id: row.id })
  },
})

const handleGetAll = base.on('get-all-records', {
  input: GetAllRecords,
  run(ctx) {
    const db = ctx.plugin('e2e:drizzle')
    ctx.send('record-list', { records: db.findAll() })
  },
})
```

## One plugin per ID

A server plugin is **one per ID**. `plugin('acme:presence', ...)` returns a factory you list once — `Presence()` — and the host's plugins are keyed by that ID, so the same plugin can't be registered twice. Listing an ID twice throws at `assemble()`:

```text
[wskit] plugin('acme:presence') is listed more than once. Each plugin id owns a namespace and must be unique — list it once, or give the second one a different id.
```

If you need two of something, author two plugins with distinct IDs (`acme:cache-east`, `acme:cache-west`), or build the multiplicity into one plugin's own state.

The client plugin system works the same way: a client plugin is also one per ID, with no way to register the same one twice on a socket. See [client Plugins](/client/plugins/overview) for the client side.
