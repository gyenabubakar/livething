Everything a plugin declares is kept separate from the host's names. This includes events, channels, client-to-server requests, server-to-client requests, scheduled tasks, storage keys and tags. Inside the plugin you write **short names**. LiveThing adds the plugin's ID to each one. This is called _namespacing_. Because of it, two plugins (or a plugin and the host) can use the same short name without a collision.

## The wire name: `__<id>::<name>`

The _wire_ is the WebSocket connection between the client and the server, and a _wire name_ is the name that the frames on it carry. A plugin-owned event travels with the plugin's ID inside its event name. For a plugin with the ID `acme:polls`, the event `vote` is sent as:

```text
__acme:polls::vote
```

The shape is `__`, then the plugin ID, then `::`, then the short name. LiveThing reserves `::` for its own use. It also marks a channel in the path keys that `contract.matches(...)` reads. A name that you declare can't contain it, so LiveThing can always split a wire name back into its `{ id, name }` parts without doubt.

You never type the long form. Inside the plugin you write the short name. LiveThing changes it to the long form when a frame goes out, and changes it back when a frame comes in:

```typescript [polls/polls-definition.ts]
import { emits, server, t } from '@livething/server'
import { plugin } from '@livething/server/plugins'
import * as v from 'valibot'

const h = server({
  scope: 'plugin',
  capabilities: [
    emits({
      'poll-updated': t<{
        pollId: string
        votes: Record<string, number>
      }>(),
    }),
  ],
})

const vote = h.on('vote', {
  input: v.object({ pollId: v.string(), option: v.string() }),
  async run(ctx, input) {
    const votes =
      ((await ctx.kv.get(`poll:${input.pollId}`)) as
        | Record<string, number>
        | undefined) ?? {}
    votes[input.option] = (votes[input.option] ?? 0) + 1
    await ctx.kv.set(`poll:${input.pollId}`, votes)
    // you write 'poll-updated'; the client receives __acme:polls::poll-updated,
    // matching this plugin's own emits(...) declaration
    ctx.send('poll-updated', { pollId: input.pollId, votes })
  },
})

export const Polls = plugin('acme:polls', {
  definition: h.assemble({ handlers: [vote] }),
})
```

So the `poll-updated` event of `Polls` never clashes with the host's own events, or with the events of another plugin.

Namespacing prevents name clashes. It does not limit access. A plugin is trusted code that runs inside your server: for example, its `ctx.sql` is your whole database, and its `ctx.platform` is the real platform object. Only add plugins that you trust.

## What gets namespaced

LiveThing namespaces every name that a plugin declares, and every name that a plugin passes as a string to a `ctx` method. You always use the short form. The long form is what goes on the wire or into storage.

| Surface                                                                | You write        | On the wire / in storage     |
| ---------------------------------------------------------------------- | ---------------- | ---------------------------- |
| Events (`ctx.send` / `broadcast` / `request` / `sendReplay`, `emits`)  | `'poll-updated'` | `__acme:polls::poll-updated` |
| Per-connection sends (`ctx.connections.get(ref).send`)                 | `'poll-updated'` | `__acme:polls::poll-updated` |
| Requests (`ctx.request`)                                               | `'confirm'`      | `__acme:polls::confirm`      |
| Errors (a code the plugin declares and throws, for example `denied()`) | `'denied'`       | `__acme:polls::denied`       |
| Channels (`h.channel`, `ctx.channels.get`)                             | `'poll'`         | `__acme:polls::poll`         |
| Scheduled tasks (`ctx.schedule` / `ctx.cancelScheduled`)               | `'close-poll'`   | `__acme:polls::close-poll`   |
| KV keys and prefixes (`ctx.kv.get` / `set` / `delete` / `list`)        | `'poll:42'`      | `__acme:polls::poll:42`      |
| Tag groups (`ctx.tags.<kind>`)                                         | `'role'`         | `__acme:polls::role`         |

The goal is the same for every row. A plugin reads and writes as if it were the only thing on the server, and the ID keeps the plugin's data private to it. Here the `acme:polls` plugin opens a poll in its own KV store:

```typescript [polls/polls-definition.ts]
import { h } from './polls-slice'

const handleOpenPoll = h.on('open-poll', {
  run(ctx) {
    // this key never collides with the host's 'poll:42' or another plugin's
    ctx.kv.set('poll:42', { yes: 0, no: 0 })
  },
})
```

The KV store (`ctx.kv`) is the server's key-value storage. When a plugin calls `ctx.kv.list()`, LiveThing **removes** the prefix from the results. The plugin sees its own short keys (`'poll:42'`), not the `__acme:polls::poll:42` form that is saved in storage. So the plugin uses short keys when it writes and gets short keys back when it reads. If you call `ctx.kv.list()` with no prefix, you get every key that the plugin owns. The list never includes the host's keys or the keys of another plugin.

A plugin's scoped `upgrade` works the same way. An ephemeral tag (a tag kept only in memory) that the plugin sets during the handshake, such as `tags: { ephemeral: { room: 'general' } }`, goes into the plugin's own namespaced group, not into the host's group. See [the scoped upgrade](/server/plugins/authoring#the-scoped-upgrade).

## Names you can't use

The reserved shape also limits the names that **you** choose, both inside a plugin and at the top level of a server. A name can't start or end with `__`, and it can't contain `::`. LiveThing uses these markers itself, so it rejects a name that contains one with an error. An event, tag group or scheduled task name that starts or ends with `__` throws when you declare it. A channel name that starts or ends with `__`, and an event or channel name that contains `::`, throw when the server starts. A KV key that starts with `__` or contains `::` throws when you write it. In every case the error happens before any frame with that name is sent.

::warning

```typescript [polls/polls-definition.ts]
import { h } from './polls-slice'

h.on('vote__', { run() {} })
// ✗ throws: "... ends with the reserved '__' suffix ..."

h.on('poll::updates', { run() {} })
// ✗ throws: "... contains '::', which is reserved as the separator ..."
```

This rule covers every name that a plugin declares itself: events, client-to-server requests, server-to-client requests, channels, tag groups, KV keys and scheduled tasks. Choose a plain short name. LiveThing adds the `__<id>::` part for you.
::

## Reading the owner back

The plugin ID is part of the event name, so LiveThing can find the owner of any frame. A hook (such as an `intercept` or `onOutgoing` function) reads the owner from `frame.owner`. For a `__<id>::<name>` event it is `{ kind: 'plugin', id }`. For every other event it is `{ kind: 'app' }`. A plugin can use it to tell its own frames apart from other frames that pass through the same hooks. In a plugin's own `onOutgoing` hook, `frame.event` for the plugin's own events is the short name it declared, without the `__<id>::` part.

To learn how to build the plugin that these names belong to, see [Authoring](/server/plugins/authoring).
