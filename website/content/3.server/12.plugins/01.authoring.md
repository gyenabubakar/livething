You author a plugin with a **scoped builder**: `define({ scope: 'plugin' })`. It looks and feels like a top-level `define` — same `base.on`, `base.request`, `base.channel`, same `ctx` — but it builds one **slice** of a server rather than the whole thing. You assemble that slice and wrap it with `plugin(...)`, and the result drops into any host.

## What a scoped define is for

A normal `define` produces the whole server. A scoped `define` produces one **slice** of a server, packaged so it can be dropped into any host. The plugin gets its own events, handlers, channels, and storage, all kept under its own namespace so it never collides with the host or with another plugin.

You author the slice with the scoped builder, assemble it, and hand the result to `plugin(...)`:

```typescript [presence.ts]
import { define, emits, t } from '@wskit/server'
import { plugin } from '@wskit/server/plugins'
import * as v from 'valibot'

// 1. a scoped builder — this plugin's own capabilities
const h = define({
  scope: 'plugin',
  capabilities: [emits({ 'user-online': t<{ id: string }>() })],
})

// 2. handlers, exactly like a top-level server
const heartbeat = h.on('heartbeat', {
  input: v.object({}),
  run(ctx) {
    ctx.send('user-online', { id: ctx.connection.id })
  },
})

// 3. assemble the handlers plus the api, then wrap with plugin(...)
const handler = h.assemble({
  handlers: [heartbeat],
  api(ctx) {
    return {
      ping() {
        ctx.send('user-online', { id: ctx.connection.id })
      },
    }
  },
})

export const Presence = plugin('acme:presence', { handler })
```

The host then lists `Presence()` like any other capability:

```typescript [host.ts]
import { define, t } from '@wskit/server'
import { Presence } from './presence'

const base = define({
  capabilities: [Presence()], // the plugin plugs in here
})
```

## How it differs from a top-level define

A scoped builder is the same builder type, but its config is smaller and a few rules are tighter.

|                           | Top-level `define`   | Scoped `define({ scope: 'plugin' })`                                                                    |
| ------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------- |
| `scope` field             | absent               | **`'plugin'`** — required                                                                               |
| `capabilities`            | any capability       | only **plugin-safe** capabilities (no host-owned engines — see [dependsOn](/server/plugins/depends-on)) |
| `upgrade`                 | the app's auth gate  | a scoped gate that runs before the app's (see below)                                                    |
| transport, global engines | owned by this server | inherited from the host                                                                                 |

The key idea: a plugin does not own the platform, transport, or global engines. It declares its namespaced slice. If it needs a secret, URL, or service, accept that value in the plugin factory and close over it when building the scoped handlers.

::warning
**The host must preserve the plugin's capability type.** Put `AuthPlugin()` directly in `define({ capabilities: [...] })`, or use an `as const` tuple when sharing the list:

```typescript [typed-plugin-list.ts]
const capabilities = [AuthPlugin()] as const

const base = define({
  capabilities,
})
```

Do not widen the list to `AnyCapability[]`. That tells TypeScript to forget which plugin is present and can erase its contract before WSKit receives it.
::

A plugin can keep configuration typed by accepting it in its factory:

```typescript [plugin-config.ts]
import { define, emits, t } from '@wskit/server'
import { plugin } from '@wskit/server/plugins'

export function auditPlugin(config: { topic: string }) {
  const h = define({
    scope: 'plugin',
    capabilities: [emits({ recorded: t<{ topic: string }>() })],
  })
  const record = h.on('record', {
    run(ctx) {
      ctx.send('recorded', { topic: config.topic })
    },
  })
  return plugin('acme:audit', {
    handler: h.assemble({ handlers: [record] }),
  })
}
```

The host reads its own runtime configuration and passes the value explicitly:

```typescript [host-config.ts]
const base = define({
  capabilities: [
    auditPlugin({ topic: process.env.AUDIT_TOPIC ?? 'audit-events' })(),
  ],
})
```

```typescript [scoped-plugin.ts]
const h = define({
  scope: 'plugin',
  capabilities: [emits({ tick: t<{ n: number }>() })],
})
```

A plugin can list its own behavior capabilities — `clientRequests`, `serverRequests`, `channels`, the stream kinds, `emits`, `errors`, `tags`, `intercepts`. What it **can't** list are the host-owned engines (`dedup`, `sequence`, `keepalive`, and friends); those it depends on instead. See [dependsOn](/server/plugins/depends-on).

## Hooks a plugin can register

The scoped builder exposes the same lifecycle hooks and shared hooks (the ones that run around every handler) a top-level server has, scoped to the plugin. A plugin can register `onInit` (server startup), `onConnect` / `onDisconnect` (per connection), `onPing` / `onPong` (heartbeat frames), `onShutdown` (server stop), `onError` and `onValidationError` (its own failures), and — with the `intercepts()` capability — `intercept` (inbound) and `onOutgoing` (outbound). Use them to set up the plugin's own storage, track its own state, or transform frames in the pipeline.

```typescript [hooks.ts]
const h = define({
  scope: 'plugin',
  capabilities: [intercepts(), emits({ tick: t<{ n: number }>() })],
})

h.onInit((ctx) => {
  ctx.sql.exec('CREATE TABLE IF NOT EXISTS ticks (n INTEGER)') // plugin's own table
})

h.onConnect((ctx) => {
  ctx.log.info('plugin saw a connection', { id: ctx.connection.id })
})

h.intercept((ctx, frame) => {
  // inspect or transform this frame before it is dispatched
})

h.onError((ctx, error, event) => {
  ctx.log.error('plugin handler failed', { event }) // only the plugin's own failures
})
```

A plugin's hooks are nested around the app's, in this order: plugin `onInit`/`onConnect` run before the app's, plugin `onDisconnect`/`onShutdown` after (shutdown is LIFO — the app runs first, then plugins in reverse registration order). A plugin's `onError`/`onValidationError` run before the app's. Plugin `intercept`/`onOutgoing` hooks run for every frame; see the [pipeline execution order](/server/under-the-hood/pipeline-execution-order).

## The scoped `upgrade`

A plugin may supply its own `upgrade` in the scoped config. It is the plugin's chance to inspect the handshake and contribute to the connection — for example to read a header the plugin cares about.

```typescript [scoped-upgrade.ts]
const h = define({
  scope: 'plugin',
  upgrade(request) {
    const region = request.headers.get('cf-ipcountry') ?? 'unknown'
    return { meta: { region } } // merged into the connection's meta
  },
  capabilities: [emits({ located: t<{ region: string }>() })],
})
```

A scoped `upgrade` differs from the app's in a few specific ways:

- **It runs first.** In the inbound order, every plugin's `upgrade` runs before the app's `upgrade`.
- **It sees only the raw request.** It does not see the app's `userId` or `meta` — it runs before those are decided.
- **Its `meta` is merged.** The plugin's returned `meta` is shallow-merged into the connection's metadata. On a key conflict, the **app wins**.
- **Its `tags` are concatenated.** Tags from the plugin and the app stack rather than overwrite.
- **Only one upgrade may own `userId`.** A plugin _may_ return `userId` — but only one upgrade hook across the whole server (the app's, or one plugin's) is allowed to. Two that return it is an error.
- **It can veto.** Throwing `RejectUpgrade(code, reason)` from a scoped `upgrade` rejects the whole handshake, exactly as the app's gate does. (See [Upgrade](/server/define/upgrade) for how the reject code is answered.)

## Assembling a scoped builder

A scoped builder's `assemble` works the same way — collect routed handler values, while lifecycle hooks and scheduled task bodies register directly — and the result is a scoped handler ready for `plugin(...)`. You never run a scoped definition directly through an adapter; it goes through `plugin(...)` and into a host.

```typescript [assemble.ts]
const heartbeat = h.on('heartbeat', {
  input: v.object({}),
  run(ctx) {
    ctx.send('user-online', { id: ctx.connection.id })
  },
})

export const Presence = plugin('acme:presence', {
  handler: h.assemble({ handlers: [heartbeat] }), // a scoped handler, not a runnable server
})
```

The id must match `/^[a-z0-9-]+:[a-z0-9-]+$/` — lowercase letters, digits, and hyphens on each side of a single colon. A malformed id (uppercase, missing colon, empty half) throws the moment `plugin(...)` is called, not later at assemble.

## The plugin manifest

`plugin(id, manifest)` takes the assembled scoped handler plus a small manifest object. This is the whole shape:

::field-group
::field{name="handler" type="ScopedHandler"}
Required. The result of `h.assemble(...)` on a scoped builder. `plugin(...)` throws if it was not built with `define({ scope: 'plugin' })`. Any `api` the host reaches with `ctx.plugin(id)` is authored on that `assemble`, not here — see [Scoped context and API](/server/plugins/scoped-ctx).
::
::field{name="dependsOn" type="HostCapabilityFactory[]"}
Optional. Host-owned capability factories (`dedup`, `sequence`, `keepalive`, `rateLimit`, the `replay` family) the host must list. See [dependsOn](/server/plugins/depends-on).
::
::
