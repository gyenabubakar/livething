You write a plugin with a **scoped builder**: `server({ scope: 'plugin' })`. It works like a top-level `server`. It has the same `base.on`, `base.request` and `base.channel` methods, and its handlers get the same `ctx`. The difference is that it builds one **slice** of a server (one self-contained part), not the whole server. You assemble that slice, wrap it with `plugin(...)`, and then any host can use it. The **host** is the app server that lists the plugin.

## What a scoped server definition is for

A normal `server` produces the whole server. A scoped `server` produces one slice of a server, packaged so that any host can add it. The plugin has its own events, handlers, channels and storage. LiveThing keeps all of them under the plugin's own namespace (a name prefix that belongs only to this plugin), so they never collide with the host or with another plugin.

You write the slice with the scoped builder, assemble it, and pass the result to `plugin(...)`:

```typescript [polls/server.ts]
import { emits, server, t } from '@livething/server'
import { plugin } from '@livething/server/plugins'
import * as v from 'valibot'

// 1. a scoped builder with this plugin's own capabilities
const h = server({
  scope: 'plugin',
  capabilities: [
    emits({
      'poll-updated': t<{
        pollId: string
        votes: Record<string, number>
      }>(),
    }),
  ],
})

// 2. handlers, written the same way as on a top-level server
const vote = h.on('vote', {
  input: v.object({ pollId: v.string(), option: v.string() }),
  async run(ctx, input) {
    const votes =
      ((await ctx.kv.get(`poll:${input.pollId}`)) as
        | Record<string, number>
        | undefined) ?? {}
    votes[input.option] = (votes[input.option] ?? 0) + 1
    await ctx.kv.set(`poll:${input.pollId}`, votes)
    ctx.send('poll-updated', { pollId: input.pollId, votes })
  },
})

// 3. assemble the handlers and the api, then wrap the result with plugin(...)
const definition = h.assemble({
  handlers: [vote],
  api(ctx) {
    return {
      async results(pollId: string) {
        return (
          ((await ctx.kv.get(`poll:${pollId}`)) as
            | Record<string, number>
            | undefined) ?? {}
        )
      },
    }
  },
})

export const Polls = plugin('acme:polls', { definition })
```

The host then lists `Polls()` like any other capability:

```typescript [server/huddle.ts]
import { server } from '@livething/server'
import { Polls } from './polls'

const base = server({
  capabilities: [Polls()], // the plugin is added here
})
```

## How it differs from a top-level server

A scoped builder has the same builder type. Its config accepts fewer options, and a few rules are stricter.

|                           | Top-level `server`   | Scoped `server({ scope: 'plugin' })`                                                                      |
| ------------------------- | -------------------- | --------------------------------------------------------------------------------------------------------- |
| `scope` field             | absent               | **`'plugin'`**, required                                                                                  |
| `capabilities`            | any capability       | only **plugin-safe** capabilities, so no host-owned engines (see [dependsOn](/server/plugins/depends-on)) |
| `upgrade`                 | the app's auth gate  | a scoped gate that runs before the app's gate (see below)                                                 |
| transport, global engines | owned by this server | come from the host                                                                                        |

A plugin does not own the platform, the transport or the global engines. It only declares its own namespaced slice. If the plugin needs a secret, a URL or a service, accept that value as an argument of a plugin factory function, and use it inside the scoped handlers.

::warning
**The host must keep the plugin's capability type.** Put `AuthPlugin()` directly in `server({ capabilities: [...] })`. If you share the list as a variable, make it an `as const` tuple:

```typescript [server/huddle.ts]
const capabilities = [AuthPlugin()] as const

const base = server({
  capabilities,
})
```

Do not widen the list to `AnyCapability[]`. With that type, TypeScript forgets which plugin is in the list, and the plugin's contract types can be lost.
::

A plugin can keep its configuration typed by taking it as an argument of a factory function:

```typescript [audit/server.ts]
import { emits, server, t } from '@livething/server'
import { plugin } from '@livething/server/plugins'

export function auditPlugin(config: { topic: string }) {
  const h = server({
    scope: 'plugin',
    capabilities: [emits({ recorded: t<{ topic: string }>() })],
  })
  const record = h.on('record', {
    run(ctx) {
      ctx.send('recorded', { topic: config.topic })
    },
  })
  return plugin('acme:audit', {
    definition: h.assemble({ handlers: [record] }),
  })
}
```

`auditPlugin(...)` returns the plugin factory, so the host calls it twice: once with the config, and once more to create the capability. The host reads its own runtime configuration and passes the value in:

```typescript [server/huddle.ts]
const base = server({
  capabilities: [
    auditPlugin({
      topic: process.env.AUDIT_TOPIC ?? 'audit-events',
    })(),
  ],
})
```

A scoped builder lists its capabilities the same way as a top-level server:

```typescript [polls/server.ts]
const h = server({
  scope: 'plugin',
  capabilities: [
    emits({
      'poll-updated': t<{
        pollId: string
        votes: Record<string, number>
      }>(),
    }),
  ],
})
```

A plugin can list its own behavior capabilities: `clientRequests`, `serverRequests`, `scheduled`, `channels`, the stream kinds, `emits`, `errors`, `tags` and `intercepts`. It **can't** list the host-owned engines: `dedup`, `sequence`, `keepalive`, `lastSeen`, `rateLimit` and the `replay` family. Listing one of them is a compile error. The plugin depends on them instead. See [dependsOn](/server/plugins/depends-on).

## Hooks a plugin can register

The scoped builder has the same lifecycle hooks as a top-level server, and each hook runs with the plugin's scoped `ctx`. A plugin can register:

- `onInit`: runs when the server starts.
- `onConnect` and `onDisconnect`: run for each connection.
- `onPing` and `onPong`: run for heartbeat frames.
- `onShutdown`: runs when the server stops.
- `onError` and `onValidationError`: run for the plugin's own failures. Inside them, `event` is the short name the plugin declared, not the namespaced wire name. A LiveThing protocol frame (such as `__subscribe__`) keeps its own name, because it has no plugin-owned short name to give back.
- `intercept` (inbound frames): needs the `intercepts()` capability.
- `onOutgoing` (outbound frames): needs no capability, the same as on a top-level server.

Use them to set up the plugin's own storage, to track its own state, or to change frames as they pass through the pipeline.

```typescript [polls/server.ts]
import { emits, server, t } from '@livething/server'
import { Block } from '@livething/server/errors'
import { intercepts } from '@livething/server/intercepts'

const h = server({
  scope: 'plugin',
  capabilities: [
    intercepts(),
    emits({
      'poll-updated': t<{
        pollId: string
        votes: Record<string, number>
      }>(),
    }),
  ],
})

h.onInit((ctx) => {
  // SQL table names are not namespaced, so use a name unique to the plugin
  ctx.sql.exec(
    'CREATE TABLE IF NOT EXISTS acme_poll_votes (poll_id TEXT, user_id TEXT, option TEXT)',
  )
})

h.intercept((ctx, frame) => {
  // Anyone can see polls, but only a signed-in user can vote.
  // An anonymous connection has an empty user id.
  if (frame.event === 'vote' && ctx.user.id === '') throw Block
})

h.onError((ctx, error, event) => {
  ctx.log.error('poll handler failed', { event }) // only the plugin's own failures
})
```

A plugin's hooks wrap around the app's hooks, like layers:

- Plugin `onInit`, `onConnect`, `onPing` and `onPong` run before the app's hooks, in the order the host lists the plugins.
- Plugin `onDisconnect` and `onShutdown` run after the app's hooks, in reverse order. The app runs first, then the last-listed plugin, and the first-listed plugin runs last.
- A plugin's `onError` and `onValidationError` run before the app's.
- Plugin `intercept` and `onOutgoing` hooks run for every frame. See the [pipeline execution order](/server/under-the-hood/pipeline-execution-order).

## The scoped `upgrade`

A plugin can give its own `upgrade` function in the scoped config. The plugin uses it to inspect the handshake (the HTTP request that opens the WebSocket) and to add data to the connection. For example, it can read a header that the plugin needs:

```typescript [polls/server.ts]
const h = server({
  scope: 'plugin',
  upgrade(request) {
    const region = request.headers.get('cf-ipcountry') ?? 'unknown'
    return { meta: { region } } // merged into the connection's meta
  },
  capabilities: [emits({ located: t<{ region: string }>() })],
})
```

A scoped `upgrade` is different from the app's `upgrade` in these ways:

- **It runs first.** Every plugin's `upgrade` runs before the app's `upgrade`, in the order the host lists the plugins.
- **It does not see the app's identity.** It does not see the app's `userId` or `meta`, because it runs before the app decides them.
- **It receives a scoped `ctx`.** Its second argument is a [`ctx`](/server/server/upgrade#the-upgrade-ctx), like the app's `upgrade` gets. Its `ctx.kv` keys are namespaced to the plugin, the same as in the plugin's handlers. Inside it, [`context.upgrade(h)`](/server/context-and-storage/context-anywhere) returns the same `ctx`, where `h` is the plugin's own `server(...)` result from the example above.
- **Its `meta` is merged.** LiveThing shallow-merges the plugin's returned `meta` into the connection's metadata (it copies the top-level keys). When the plugin and the app return the same key, the **app's value wins**.
- **Its `tags` are added together.** The tags from the plugin and the tags from the app are joined into one list. Neither list replaces the other.
- **Only one upgrade may return `userId`.** A plugin _may_ return `userId`. But across the whole server, only one upgrade function (the app's, or one plugin's) may return it. If two of them return a `userId`, the handshake fails with an error and the server rejects the connection with HTTP status 500.
- **It can reject the connection.** Throwing `RejectUpgrade(code, reason)` from a scoped `upgrade` rejects the whole handshake, the same way as in the app's gate. (See [Upgrade](/server/server/upgrade) for how LiveThing answers with the reject code.)

## Assembling a scoped builder

A scoped builder's `assemble` works the same way as on a top-level server. You pass it the routed handler values. Lifecycle hooks and scheduled task bodies register directly on the builder instead. The result is a scoped server definition, ready for `plugin(...)`. You never run a scoped server definition with an adapter. It always goes through `plugin(...)` and into a host.

```typescript [polls/server.ts]
const vote = h.on('vote', {
  input: v.object({ pollId: v.string(), option: v.string() }),
  async run(ctx, input) {
    const votes =
      ((await ctx.kv.get(`poll:${input.pollId}`)) as
        | Record<string, number>
        | undefined) ?? {}
    votes[input.option] = (votes[input.option] ?? 0) + 1
    await ctx.kv.set(`poll:${input.pollId}`, votes)
    ctx.send('poll-updated', { pollId: input.pollId, votes })
  },
})

export const Polls = plugin('acme:polls', {
  definition: h.assemble({ handlers: [vote] }), // a scoped server definition, not a runnable server
})
```

The plugin ID must match `/^[a-z0-9-]+:[a-z0-9-]+$/`. That means lowercase letters, digits and hyphens on each side of a single colon. A wrong ID (with uppercase letters, with no colon, or with an empty side) throws an error as soon as you call `plugin(...)`. It does not wait until `assemble`.

## The plugin manifest

`plugin(id, manifest)` takes the plugin ID and a small manifest object. The manifest holds the assembled scoped server definition and, if needed, the plugin's dependencies. This is the whole shape:

::field-group
::field{name="definition" type="ServerDefinition"}
Required. The result of `h.assemble(...)` on a scoped builder. `plugin(...)` throws an error if the definition was not built with `server({ scope: 'plugin' })`. You write the `api` that the host reaches with `ctx.plugin(id)` in that `assemble` call, not in the manifest. See [Scoped context and API](/server/plugins/scoped-ctx).
::
::field{name="dependsOn" type="HostCapabilityFactory[]"}
Optional. Factories of host-owned capabilities (`dedup`, `sequence`, `keepalive`, `lastSeen`, `rateLimit`, the `replay` family) that the host must list. See [dependsOn](/server/plugins/depends-on).
::
::
