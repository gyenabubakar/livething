Built-in replay stores messages for you in LiveThing's own table. With custom replay, **you** decide where messages are stored and how they are sent back. Use it when you want your own table layout, a database you already run, an external store, or filtering that the built-in modes do not offer.

You turn it on with the `replay.custom()` capability. Then you register a `base.replay({ ... })` hook with up to three functions: `beforeBroadcast`, `afterBroadcast`, and `replay`.

```typescript [server/huddle.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'
import * as v from 'valibot'

const Message = v.object({ text: v.string(), from: v.string() })
const SendMessage = v.object({ text: v.string() })

const base = server({
  capabilities: [
    emits({ message: t<v.InferOutput<typeof Message>>() }),
    channels(),
    dedup(),
    sequence({ persist: true }),
    replay.custom(),
  ],
})
```

::note
Unlike built-in replay, `replay.custom()` does **not** require `dedup()` or `sequence({ persist: true })`. The build does not check for them. But `sequence()` is what gives each message its sequence number (`msg.wire.deliverySeq`), and `dedup()` is what gives it a message ID (`msg.wire.messageId`). Without them, these two fields have no real value. So in practice you list both, as the example above does. `channels()` is only there because later examples on this page use channels.
::

## The three hooks

`base.replay({ ... })` takes three functions. Only `replay` (the function that resends) is required. `beforeBroadcast` and `afterBroadcast` only see **broadcasts**: a message sent with `ctx.broadcast`, `ctx.channel.broadcast`, `ctx.user.broadcast`, `ctx.users.get(id).broadcast`, or `ctx.channel.broadcastTo` a user. A send to one connection, tag, or group (`ctx.send`, `ctx.connections.get(ref).send`, `ctx.channel.send`, `ctx.channel.broadcastTo` a connection/tag/group) never reaches either hook. Each hook runs **once per broadcast**, even when no connection receives it live.

| Hook                        | When it runs                                            | What you do                                                                                                                                                             |
| --------------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `beforeBroadcast(ctx, msg)` | synchronously, before any recipient is sent the frame   | Write the message into your store. This is strict durability: if this hook throws, no recipient receives the broadcast.                                                 |
| `afterBroadcast(ctx, msg)`  | after every recipient was sent the frame (can be async) | Write the message into your store. This is best-effort durability: a throw or rejection here is logged, and never affects delivery, because the frame already went out. |
| `replay(ctx, since)`        | when a client reconnects and asks for replay            | Read your store for every message newer than `since`, and call `ctx.sendReplay(...)` for each one. **Required.**                                                        |

You usually pick **one** of `beforeBroadcast` / `afterBroadcast` to write, and use `replay` to read back. The example below uses both: `beforeBroadcast` inserts the row, and `afterBroadcast` marks it as confirmed after the send has happened.

```typescript [server/huddle.ts]
base.replay({
  beforeBroadcast(ctx, msg) {
    ctx.sql.exec(
      'INSERT INTO _custom_replay (event, payload, seq, message_id) VALUES (?, ?, ?, ?)',
      msg.event,
      JSON.stringify(msg.payload),
      msg.wire.deliverySeq,
      msg.wire.messageId,
    )
  },
  afterBroadcast(ctx, msg) {
    ctx.sql.exec(
      'UPDATE _custom_replay SET confirmed = 1 WHERE seq = ?',
      msg.wire.deliverySeq,
    )
  },
  replay(ctx, since) {
    const rows = ctx.sql
      .exec<{
        event: string
        payload: string
        seq: number
        message_id: string
      }>(
        'SELECT event, payload, seq, message_id FROM _custom_replay WHERE seq > ? ORDER BY seq ASC',
        since,
      )
      .toArray()

    for (const row of rows) {
      ctx.sendReplay(row.event, JSON.parse(row.payload), {
        deliverySeq: row.seq,
        messageId: row.message_id,
      })
    }
  },
})
```

Create the table once in `base.onInit(...)`:

```typescript [server/huddle.ts]
base.onInit((ctx) => {
  ctx.sql.exec(`
    CREATE TABLE IF NOT EXISTS _custom_replay (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      event TEXT NOT NULL,
      payload TEXT NOT NULL,
      seq INTEGER NOT NULL,
      message_id TEXT NOT NULL,
      confirmed INTEGER NOT NULL DEFAULT 0
    )
  `)
})
```

## What the hooks receive

### The message in `beforeBroadcast` / `afterBroadcast`

Each write hook gets `(ctx, msg)`. The `msg` has the event name and the payload, plus who may replay it and a `wire` object. You use the `wire` fields as a storage key and as a **cursor** (a position in the message list that tells you where to continue from):

::field-group
::field{name="msg.event" type="string"}
The event name.
::
::field{name="msg.payload" type="Readonly<Record<string, unknown>>"}
The application payload, without any LiveThing metadata.
::
::field{name="msg.userId" type="string | null"}
`null` when the broadcast went to everyone in its scope (`ctx.broadcast`, `ctx.channel.broadcast`). A user id when it went to one user (`ctx.user.broadcast`, `ctx.users.get(id).broadcast`, `ctx.channel.broadcastTo` a user). Store it with the row, so your `replay` hook can filter by it.
::
::field{name="msg.wire.deliverySeq" type="number"}
The message's sequence number, from [`sequence()`](/server/capabilities/sequence). It always goes up, and it is shared by all connections on the server. Use it as your replay cursor.
::
::field{name="msg.wire.messageId" type="string"}
A unique message ID, from [`dedup()`](/server/capabilities/dedup). A good storage key. The client uses it to drop duplicates.
::
::field{name="msg.wire.channel" type="string | null"}
The channel name when the message was sent in a channel, otherwise `null`.
::
::field{name="msg.wire.channelFamily" type="string | null"}
The family key when the channel is a dynamic channel, otherwise `null`.
::
::

The `ctx` here gives you `sql`, `kv`, `log`, and `platform`. It has no `meta`.

### The context in `replay`

The `replay` hook gets `(ctx, since)`. `since` is the last sequence number the client received. Resend everything after it. The `ctx` gives you:

- `ctx.sendReplay(event, payload, wire)`: resend one stored message. `wire` takes `deliverySeq` and `messageId`, and optionally `channel` and `channelFamily`.
- `ctx.userId`: the user id of the client asking for replay, or `null` for an anonymous connection. Send it only rows whose stored `msg.userId` is `null` (everyone-in-scope) or equal to this id (that user's own broadcasts).
- `ctx.request.channel` / `ctx.request.channelFamily`: the channel name and family key from the client's replay request. Both are `null` for a top-level request (a request with no channel). Use them to choose which rows to send back. In a channel-scoped hook you get `ctx.channel.name` instead.
- `ctx.id` (the connection ID of the client that asked for replay), `ctx.meta`, `ctx.sql`, `ctx.kv`, `ctx.log`, `ctx.platform`.

## The contract check on sendReplay

LiveThing checks each `ctx.sendReplay(...)` call at runtime, the same way it checks the built-in one. The event must be an outgoing event that is declared for the current scope, and the payload must be a plain object. If you send an event that is not declared, the call throws. Your `replay` hook can catch the error and log it, so the rest of the resend still runs:

```typescript [server/huddle.ts]
replay(ctx, since) {
  try {
    ctx.sendReplay('not-declared-event', { ok: true }, { deliverySeq: 1, messageId: 'bad-1' })
  } catch (err) {
    const message = err instanceof Error ? err.message : String(err)
    ctx.log.warn('replay rejected an undeclared event', { message })
  }
  // ...resend your real rows
}
```

## The cascade behavior

A **top-level** custom replay sees more than top-level messages. By default it also sees **channel** messages. This is called the **cascade**. So one `base.replay({ ... })` can record everything, top-level sends and the sends of every channel, into one store. This is why the write hooks get `msg.wire.channel` and `msg.wire.channelFamily`. Save them with each row, so the `replay` hook can pick the right rows when a client asks for one scope.

A channel that registers **its own** `channel.replay({ ... })` takes over its own scope. The top-level cascade then skips that channel, and the channel's hook handles it. Built-in replay splits the work between server-level and channel-level replay in the same way.

Here is a cascading store that saves the scope on every row and filters by it when it resends:

::code-group

```typescript [server/huddle.ts]
base.replay({
  beforeBroadcast: (ctx, msg) => {
    ctx.sql.exec(
      'INSERT INTO _cascade_replay (event, payload, seq, message_id, channel, channel_family) VALUES (?, ?, ?, ?, ?, ?)',
      msg.event,
      JSON.stringify(msg.payload),
      msg.wire.deliverySeq,
      msg.wire.messageId,
      msg.wire.channel, // null for top-level, the name inside a channel
      msg.wire.channelFamily, // null unless it is a dynamic family
    )
  },
  replay: (ctx, since) => {
    const requestedChannel = ctx.request.channel
    const requestedFamily = ctx.request.channelFamily
    type Row = {
      event: string
      payload: string
      seq: number
      message_id: string
      channel: string | null
      channel_family: string | null
    }

    const rows: Row[] = requestedChannel
      ? ctx.sql
          .exec<Row>(
            'SELECT event, payload, seq, message_id, channel, channel_family FROM _cascade_replay WHERE seq > ? AND channel = ? AND ((channel_family IS NULL AND ? IS NULL) OR channel_family = ?) ORDER BY seq ASC',
            since,
            requestedChannel,
            requestedFamily,
            requestedFamily,
          )
          .toArray()
      : ctx.sql
          .exec<Row>(
            'SELECT event, payload, seq, message_id, channel, channel_family FROM _cascade_replay WHERE seq > ? AND channel IS NULL ORDER BY seq ASC',
            since,
          )
          .toArray()

    for (const row of rows) {
      ctx.sendReplay(row.event, JSON.parse(row.payload), {
        deliverySeq: row.seq,
        messageId: row.message_id,
        channel: row.channel ?? undefined,
        channelFamily: row.channel_family ?? null,
      })
    }
  },
})
```

```typescript [server/rooms.ts]
const general = base.channel('general', {
  capabilities: [
    emits({ message: t<v.InferOutput<typeof Message>>() }),
  ],
})

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    emits({ message: t<v.InferOutput<typeof Message>>() }),
  ],
})

// The `message` sends of both channels go into the one top-level store above,
// because neither channel registered its own `.replay(...)`.
const handleGeneralMessage = general.on('send-message', {
  input: SendMessage,
  run(ctx, input) {
    ctx.channel.broadcast('message', {
      text: input.text,
      from: ctx.user.id,
    })
  },
})
```

::

Look at the two reads. When the client asks for a **channel** scope, the query matches that channel and family. When the client asks at the **top level** (no channel), the query matches only rows where `channel IS NULL`. Those are real top-level messages, not channel messages. So there is one store, and each read picks rows by scope.

## Channel-scoped custom replay

To give a channel its own store and its own resend, register `channel.replay({ ... })` on the channel. Like `base.replay({ ... })`, this needs `replay.custom()` in the server's capability list. If it is missing, the `channel.replay(...)` call throws. The hooks look the same, but the context is for a channel: in the write hooks, `msg.wire.channel` is always set, and the `replay` ctx has `ctx.channel.name` instead of `ctx.request`.

```typescript [server/support.ts]
const support = base.channel('support', {
  capabilities: [
    emits({ 'support-note': t<v.InferOutput<typeof SupportNote>>() }),
  ],
})

support.replay({
  beforeBroadcast(ctx, msg) {
    ctx.sql.exec(
      'INSERT INTO _support_replay (event, payload, seq, message_id) VALUES (?, ?, ?, ?)',
      msg.event,
      JSON.stringify(msg.payload),
      msg.wire.deliverySeq,
      msg.wire.messageId,
    )
  },
  replay(ctx, since) {
    const rows = ctx.sql
      .exec<{
        event: string
        payload: string
        seq: number
        message_id: string
      }>(
        'SELECT event, payload, seq, message_id FROM _support_replay WHERE seq > ? ORDER BY seq ASC',
        since,
      )
      .toArray()

      ctx.sendReplay(row.event, JSON.parse(row.payload), {
        deliverySeq: row.seq,

})
```

## The membership check

Channel replay has a membership check. A client can only get a channel's history if it is a **member** of that channel (it has subscribed to it). If a non-member sends a replay request for a channel, the server sends nothing back and no error. The response does not even show whether the channel exists. Your channel `replay` hook does not run for that connection.

So this hook is safe even though it sends back private data. It only runs for members of `staff`.

```typescript [server/staff.ts]
const staff = base.channel('staff', {
  capabilities: [
    emits({ 'staff-note': t<v.InferOutput<typeof StaffNote>>() }),
  ],
})

staff.replay({
  replay(ctx) {
    // Only runs for a connection that is subscribed to `staff`.
    ctx.sendReplay(
      'staff-note',
      { text: 'Server maintenance starts at 22:00.' },
      { deliverySeq: 1, messageId: 'staff-note-1' },
    )
  },
})
```

You do not write the membership check yourself. LiveThing runs it before it calls your hook. A top-level replay request has no channel to check, so it always runs.

## When the family key equals the channel name

A dynamic channel family is declared with `[familyKey, template]`, like `['rooms', 'room-{id}']`. The family key and the matched channel name are usually different: `rooms` and `room-7`. But they can be **equal**. Declare `['rooms', 'rooms']`, and a subscribe to `rooms` matches with the family key `rooms` and the name `rooms`.

Replay handles this case. The channel is still a **dynamic family**, and replay still works per scope: messages are stored and resent under the right family, even when the key and the name are the same string. The example below uses built-in `replay.history()` to keep it short. A custom `channel.replay({ ... })` handles the family key in the same way.

```typescript [server/rooms.ts]
const base = server({
  capabilities: [
    channels(),
    dedup(),
    sequence({ persist: true }),
    replay.history(),
  ],
})

// Family key and template are the same string. It is still a dynamic family.
const rooms = base.channel(['rooms', 'rooms'], {
  replay: true,
  capabilities: [
    emits({
      message: t<v.InferOutput<typeof Message>>(),
    }),
  ],
})

const handleSendBatch = rooms.on('send-batch', {
  input: SendBatch,
  run(ctx, payload) {
    for (let i = 0; i < payload.count; i++) {
      ctx.channel.broadcast(
        'message',
        { text: `Message ${i + 1}`, from: ctx.user.id },
        { includeSelf: true },
      )
    }
  },
})
```

A client subscribes to `rooms`, misses a batch, and reconnects. It gets the missed `message` events replayed under the `rooms` family. The equal key and name do not break the scoping.

## No automatic gap signal

The [eviction watermark and the `__gap__` signal](/server/replay/built-in#the-gap-signal-and-the-eviction-watermark) are a **built-in** replay feature. The watermark is the highest sequence number that the built-in store has evicted (deleted to stay within its limits). This feature exists because LiveThing owns the built-in store and knows which rows it evicted. A custom store belongs to you, so LiveThing cannot know when your `replay` hook sent back only part of the missed messages. It does not send a gap for you.

Your custom store may have a limit, and you may want a reconnecting client to know that it missed deleted messages. In that case, keep track of the highest sequence number you have deleted, and send the signal yourself from the `replay` hook. `ctx.sendReplay` only resends stored rows, so send the gap as a normal declared event and listen for that event on the client. The client's [`onGap`](/client/primitives/gaps) does not fire for it.

## Rules and limits

- **One hook per scope.** Registering `base.replay({ ... })` twice throws `Duplicate replay hook`. The same is true for a channel.
- **The capability must be listed.** Calling `base.replay({ ... })` without `replay.custom()` in the capability list throws. The error says that the hook needs the `replay.custom()` capability.
- **Do not list it twice.** Listing `replay.custom()` more than once is a type error, and `base.replay({ ... })` throws at runtime.
- **Custom and built-in replay cannot share a scope.** If you list `replay.history()` (or `replay.snapshot()`) together with `replay.custom()` and register a hook, `assemble()` throws an error that says both are configured. Pick one strategy per scope. See the [overview](/server/replay/overview).

Custom replay also follows the rules in [what replay does not store](/server/replay/overview#what-replay-does-not-store). Protocol frames, request replies and stream chunks never reach your write hooks, so you do not have to filter them out yourself.
