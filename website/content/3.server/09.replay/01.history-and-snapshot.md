With replay, LiveThing manages the storage for you. You list one capability. LiveThing then records every outgoing message. When a client reconnects, LiveThing resends the messages that the client missed. You write no handler code and manage no table.

There are two modes:

- **History** keeps every message, up to its retention limits. Without any, it still keeps at most 64 MiB for each audience (`retention.maxBytes`).
- **Snapshot** keeps only the latest value for each key.

## What both modes need

Replay does not work alone. It depends on two other capabilities. If either one is missing, the server throws an error when it starts, before it accepts any connection:

| Capability                                                     | Why it is required                                                                                                                                                                                                             |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| [`dedup()`](/server/capabilities/dedup)                        | Gives each message a unique message ID. Replay stores rows by this ID, and the client uses it to drop messages it already has.                                                                                                 |
| [`sequence({ persist: true })`](/server/capabilities/sequence) | Gives each message a sequence number that is kept across server restarts, so stored rows stay in the right order. You must pass `persist: true`. A sequence kept only in memory is not enough, and the start-up error says so. |

Replay also needs the platform `storage` capability. Your adapter provides it.

::code-group

```typescript [History]
import { server } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [
    dedup(),
    sequence({ persist: true }),
    replay.history(),
  ],
})
```

```typescript [Snapshot]
import { server } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [
    dedup(),
    sequence({ persist: true }),
    replay.snapshot(),
  ],
})
```

::

## History mode

`replay.history(...)` stores **every** message as its own row. On reconnect, the client says "the last sequence number I saw is N". The server then sends every recorded message after N, in order. Use history mode for a chat room, an activity feed, or a log: any case where the full list of events matters and the client must not skip any of them.

Here is a smaller version of Huddle with only `message` and replay. In this version `send-message` is a top-level handler. In Huddle it is a handler of `rooms`.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'
import * as v from 'valibot'
import { verifySession } from './auth'

type Message = {
  id: string
  text: string
  from: string
  sentAt: number
}

const SendMessage = v.object({ text: v.string() })

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    emits({
      message: t<Message>(),
      typing: t<{ from: string }>(),
    }),
    dedup(),
    sequence({ persist: true }),
    replay.history({
      retention: { maxMessages: 1000, maxAgeMs: 3_600_000 },
      durability: 'strict',
      exclude: ['typing'],
    }),
  ],
})

export const handleSendMessage = base.on('send-message', {
  input: SendMessage,
  run(ctx, payload) {
    const msg: Message = {
      id: crypto.randomUUID(),
      text: payload.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    }

    // includeSelf also sends it to the sender, as the same recorded message
    ctx.broadcast('message', msg, { includeSelf: true })
  },
})
```

You must include the returned `handleSendMessage` value in `base.assemble({ handlers: [...] })`. Only then does the server receive `send-message` frames. Defining the handler alone does not turn it on and does not add it to `InferClient`.

The handler does not mention replay. LiveThing records every `message` as it is sent. When the socket comes back, the client receives the messages it missed. Any `typing` events are not recorded, because `typing` is in the `exclude` list.

The handler uses `broadcast` with `includeSelf: true` to send one `message` to every connection, the sender too. A separate `ctx.send` for the sender's copy would be a second message with its own sequence number, recorded only for the sender's connection. That broadcast gets **one** delivery sequence number and **one** delivery ID, shared by all recipients. So it becomes **one** history row, not one row per recipient. The server resends rows in order of their sequence number (`metadata.delivery.seq`). The client's `dedup()` primitive drops any row that has a delivery ID (`metadata.delivery.id`) it has already seen. So if the resent rows overlap with messages the client already has, the client shows no duplicates.

### History config

::field-group
::field{name="durability" type="'strict' | 'best-effort'"}
Default: `'strict'`. `strict` writes the row before the message is sent. `best-effort` sends first, then stores the row in the background. This is faster, but a crash can lose the last row.
::
::field{name="retention.maxMessages" type="number"}
Default: none. Keep at most this many rows in each store. When a store grows past this number, the oldest rows are deleted.
::
::field{name="retention.maxBytes" type="number"}
Default: `67_108_864` (64 MiB). Keep at most this many bytes in each store. A row counts the UTF-8 bytes of its JSON payload, plus the bytes of a [binary event](/server/replay/overview#binary-events) (its info counts as the payload). When a store grows past this number, the oldest rows are deleted, strictly by sequence number, and the eviction watermark goes up as for `maxMessages`. One message bigger than `maxBytes` alone is not stored at all, so it never pushes out the older messages (see [Binary events](/server/replay/overview#binary-events)).
::
::field{name="retention.maxAgeMs" type="number"}
Default: none. Delete rows older than this many milliseconds. Old rows are removed when the server starts and each time a new message is stored.
::
::field{name="exclude" type="string[]"}
Default: `[]`. Event names that are never recorded, JSON or binary. These events are still sent live. They only never appear in replay.
::
::

All three `retention` values must be positive whole numbers.

::note
**How storage is organized.** Replay keeps one store per scope, and there are only two kinds of scope: **one top-level store** for messages that are not sent on a channel, plus **one store for each channel** whose messages are replayed. In history mode, a store keeps every replayable row. In snapshot mode, it keeps the latest row for each logical key. `maxMessages`, `maxBytes` and `maxAgeMs` limit each store **on its own**. For example, `maxMessages: 1000` means up to 1000 top-level rows _and_ up to 1000 rows for each replayed channel. When a busy channel deletes old rows, the other stores are not affected. Inside one store, `maxMessages` and `maxBytes` also count each **audience** on its own: the messages sent to everyone, the messages sent to each user (with `ctx.user.broadcast`, or to chosen connections of that user, such as `ctx.send`), and the messages sent to each anonymous connection's resume token. So a user's private messages never push the shared history out, one user's messages never push out another's, and the store can hold up to `maxMessages` messages and `maxBytes` bytes for each audience. A message sent to chosen connections, such as a tag broadcast, is stored once and counts once for each user and each anonymous token it reached. It stays until the last of them has evicted it. Anonymous tokens never come back after their client is gone, so one store keeps at most 1024 tokens' worth of them (`1024 * maxMessages` recipient rows). Past that, it deletes the oldest. In the same way, all the anonymous tokens of one store together hold at most `maxBytes` (64 MiB by default), not `maxBytes` each: past that, it deletes the oldest of their messages, strictly by sequence number. In both cases it raises one watermark that every anonymous client reads, so a client whose messages were deleted gets its gap. This holds with or without `maxMessages`. Each store also has its own eviction watermark (see [below](#the-gap-signal-and-the-eviction-watermark)). All of this is kept in the server's own SQL storage. Every adapter provides that storage, so you do not need to turn on anything extra for replay.
::

::note
Besides your `exclude` list, replay **always** skips three kinds of frames, so you never need to filter them yourself: replies to requests (they carry `metadata.exchange.id`), stream chunks (they carry `metadata.stream.id`), and internal protocol frames (the `__…__` events).
::

## Snapshot mode

`replay.snapshot(...)` keeps only the **latest** row for each logical key. A logical key is a string that names one piece of state, for example one document or one counter. A reconnecting client receives the current value of each key, not the full list of changes that led to it. Use snapshot mode for a document, a counter, or a presence map, where only the final state matters.

You can give it two functions:

- `snapshotKey(event, payload)` builds the key. Rows with the same key replace each other, so only one row is kept for each key. If you leave it out, the event name is the key. A message sent to one user, or to chosen connections, keeps its own row for that key, so it never replaces the row everyone else sees. That row belongs to the user. For an anonymous connection, it belongs to that connection's resume token, so each new anonymous connection adds rows. Set `retention.maxMessages` to limit them.
- `reduce(previous, next)` is optional. It combines the stored value with the new one, instead of always keeping the newest. Return an `{ event, payload }` object to store it, or `null` to delete the stored value for that key.

This version of Huddle keeps only the latest `status-changed` for each member. It also emits `session-ended`, which Huddle's definition does not have, so that `reduce` has something to delete.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'
import * as v from 'valibot'
import type { ReplaySnapshotValue } from '@livething/server/replay'

const StatusChanged = v.object({
  userId: v.string(),
  status: v.picklist(['active', 'away', 'busy']),
})
const SessionEnded = v.object({ userId: v.string() })

function reduceSnapshot(
  previous: ReplaySnapshotValue | null,
  next: ReplaySnapshotValue,
): ReplaySnapshotValue | null {
  if (next.event === 'session-ended') return null

  // forget this member's presence
  return next // latest status wins
}

const base = server({
  capabilities: [
    emits({
      'status-changed': t<v.InferOutput<typeof StatusChanged>>(),
      'session-ended': t<v.InferOutput<typeof SessionEnded>>(),
    }),
    dedup(),
    sequence({ persist: true }),
    replay.snapshot({
      snapshotKey: (_event, payload) => String(payload?.userId),
      reduce: reduceSnapshot,
      retention: { maxMessages: 10_000 },
      durability: 'best-effort',
    }),
  ],
})
```

In this example, each `status-changed` for the same `userId` replaces the previous one. A reconnecting client receives only the newest status for each member. For `session-ended`, the `reduce` function returns `null`, so that member's snapshot is removed from the store.

You can type `snapshotKey` and `reduce` as separate functions with the exported [`SnapshotKeyFn`](/server/capabilities/replay) and `SnapshotReducer` types, or you can write them inline as arrow functions.

### Snapshot config

Snapshot mode takes all the history mode fields (`durability`, `retention`, `exclude`) plus two of its own. It cannot store [binary events](/server/replay/overview#binary-events), because `reduce` cannot combine bytes: the server fails to start when a binary event would go into a snapshot store. Use history mode for them, or list them in `exclude`.

| Field         | Type                                | Default     | What it does                                                                                                                                                                |
| ------------- | ----------------------------------- | ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `snapshotKey` | `(event, payload) => string`        | event name  | The logical key. Rows with the same key replace each other.                                                                                                                 |
| `reduce`      | `(previous, next) => value \| null` | latest wins | Combines the stored value with the new event. `previous` is the stored value, or `null` if there is none. Return a value to store it, or `null` to delete that key's value. |

::tip
Snapshot mode also combines writes in memory. Suppose a handler sends many messages for the same key in one run, for example many counter updates. LiveThing combines them in memory while the handler runs, and writes only the final value once when the handler finishes. This avoids one SQL write per message.
::

::warning
`retention.maxAgeMs` works differently in snapshot mode than in history mode. It deletes a row because it is **old**, not because a newer value replaced it. So when a key stops getting updates, its **current** value becomes old and is deleted. This is useful for short-lived state such as presence or a heartbeat, where "no update for a while" should mean "gone". It is wrong for a value that stays true for a long time, such as a price or a document title: after the value is deleted, a reconnecting client gets nothing back for that key. To limit the size of a snapshot store without losing current values, limit the number of keys with `maxMessages` and do not set `maxAgeMs`.
::

## Durability: strict vs best-effort

`durability` decides the order of storing and sending:

| Mode               | Order                                       | Trade-off                                                                                                                                      | Good for                                                                                                          |
| ------------------ | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `strict` (default) | Store the row, then send.                   | The message is stored before any client can see it, so a crash never loses a message that was sent but not stored. Sending is a little slower. | Orders, payments, audit logs: cases where a missing message is a real problem.                                    |
| `best-effort`      | Send, then store the row in the background. | Sending is faster. But if the process crashes between the send and the store, the last message may never reach the store.                      | Cursors, presence, frequent snapshot updates: cases where speed matters more than the last message after a crash. |

With `strict`, a message is never sent when storing it fails. The server logs the error, the recipients get nothing, and a send to chosen connections (such as `ctx.send`) returns `false`. A message that reaches several connections is one row plus one recipient row per connection, and those rows are written together, so a failed send leaves no row for any of them.

## The gap signal and the eviction watermark

Retention keeps each store at a limited size. So a client can be away for so long that some messages it did not receive are already deleted. When the server cannot resend all the missed messages, it tells the client with a `__gap__` frame. It does not silently send a shorter list.

This uses the **eviction watermark**: the highest sequence number the server has deleted. Each time retention deletes rows (because of `maxMessages`, `maxBytes` or `maxAgeMs`), the server raises the watermark to the highest `seq` it just deleted. The watermark only goes **up**. A later delete that removes older rows never lowers it.

Each store keeps one watermark for each audience: the messages sent to everyone in that scope, the messages sent to each user (with `ctx.user.broadcast` or `ctx.channel.broadcastTo` a user, or to chosen connections of that user, such as `ctx.send` or a tag broadcast), and the messages sent to each anonymous connection's resume token. A client is checked against the highest of these numbers: the shared watermark and the watermarks of its own audiences. A signed-in client's audience is its user. An anonymous client's audiences are the tokens it shows. So when a message sent only to Alice is deleted, Bob does not get a gap, because that message was never meant for him, and one anonymous client does not get a gap from another's deleted messages. Two cases can still report a gap for a message the client never had: a deleted message sent to another tab of the same user, and an anonymous client after a store passes its limit of 1024 tokens, or the byte total of its anonymous tokens. Past that limit, the oldest token watermarks and rows fold into one number that all anonymous clients with a token read. This can report a gap that did not happen, and it never hides one that did.

When a client asks to catch up, the server checks it like this:

::steps

### A client reconnects and asks to catch up from sequence _N_

The `__replay__` request carries `lastKnownSeq: N`. N is the highest sequence number the client saw in that scope before the connection dropped.

### The server compares _N_ with the client's watermark in that scope

If `N > 0` **and** `N < watermark`, some messages the client did not see were deleted. If `N` is equal to or above the watermark, no message the client needs is missing.

### The server sends a gap first, then the rows that are left

When messages are missing, the server sends `__gap__ { missedThrough: watermark }` **before** the rows it can still resend. `missedThrough` is the watermark: every message with a sequence number equal to or below it is gone.
::

Two cases follow from this rule:

- **A fresh load (`lastKnownSeq: 0`) never gets a gap.** A gap only makes sense when the client had a real position. Sequence `0` means "I have seen nothing", so the client cannot be behind. The `N > 0` check skips it.
- **Snapshot mode never sends a gap.** Snapshot mode resends the current value of each key that changed after the client's position. There is no list of past events the client could fall behind on. Only history mode checks the watermark, and only history mode sends `__gap__`.

::note
The server compares with the eviction watermark, not with the lowest `seq` still in the store. Sequence numbers are not continuous inside one store, because one counter is shared by the whole server: excluded events and messages in other scopes also use numbers. So "the oldest row I still have" would give a wrong lower limit. Because the server records the highest sequence number it actually deleted, it can tell "you missed deleted messages" apart from "nothing was sent here".
::

The watermark is **per store**. When a channel store deletes rows, only that channel's watermark goes up, and only that channel's members get a channel gap. The top-level store and other channels are not affected. On the client, the [`gaps()`](/client/primitives/gaps) primitive passes a top-level gap to `socket.onGap` and a channel gap to `socket.channel(...).onGap`.

## Per-channel replay

Server-level replay **covers channels too**. By default, it records channel messages as well. To change this for one channel, set `replay` in the channel config:

These two channels are examples. Huddle's definition does not have them.

```typescript [server/channels.ts]
// Give this channel its own history store with default settings:
const general = base.channel('general', { replay: true })

// Turn replay off for this channel. Its messages are not stored or replayed:
const standup = base.channel('standup', { replay: false })
```

`replay: true` gives the channel its own replay instance in history mode with the default settings: `strict` durability, the default `maxBytes` of 64 MiB and no other retention limit, and no `exclude` list. It does not copy the options you passed to `replay.history(...)` or `replay.snapshot(...)` on the server. `replay: false` turns replay off for the channel: neither the server-level replay nor a channel-level replay records its messages. See [Channels](/server/channels/overview) for how replay works when a client subscribes to a channel.

::note
Channel replay is limited to members. If a connection is not a current member of the channel and asks for that channel's replay, it gets **zero rows**. The server does not send an error either, so a non-member cannot learn whether the channel exists. Separately, if the `lastKnownSeq` on a `__replay__` frame is not a whole number of 0 or more, the server replies with `__error__ { code: 'validation-failed' }`.
::

### When the family key equals the channel name

A dynamic channel family is declared with `[familyKey, template]`, like `['rooms', 'room-{id}']`. The family key and the matched channel name are usually different: `rooms` and `room-7`. But they can be **equal**. Declare `['rooms', 'rooms']`, and a subscribe to `rooms` matches with the family key `rooms` and the name `rooms`.

Replay handles this case. The channel is still a **dynamic family**, and replay still works per scope: messages are stored and resent under the right family, even when the key and the name are the same string.

Here `rooms` is a different version from Huddle's. It has one fixed name, `rooms`, and it has its own replay store.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'
import * as v from 'valibot'

type Message = {
  id: string
  text: string
  from: string
  sentAt: number
}

const base = server({
  capabilities: [
    channels(),
    dedup(),
    sequence({ persist: true }),
    replay.history(),
  ],
})

// Family key and template are the same string. It is still a dynamic family.
const rooms = base.channel(['rooms', 'rooms'], {
  replay: true,
  capabilities: [emits({ message: t<Message>() })],
})

const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast(
      'message',
      {
        id: crypto.randomUUID(),
        text: input.text,
        from: ctx.user.id,
        sentAt: Date.now(),
      },
      { includeSelf: true },
    )
  },
})
```

A client subscribes to `rooms`, misses some messages, and reconnects. It gets the missed `message` events replayed under the `rooms` family. The equal key and name do not break the scoping.

## Edge cases

The main flow is: store on send, resend on reconnect. A few special cases change that flow. Each one has a defined behavior.

::accordion
:::accordion-item{label="The best-effort crash window" icon="i-ph-warning-duotone"}
With `durability: 'best-effort'`, the row is written _after_ the send, in the background. If the process crashes in that short time, the last message reached live clients but was never stored. A client that reconnects right after the crash does not get that message in replay. `strict` removes this risk because it stores first, but sending is a little slower. Use `best-effort` only where losing the last row in a crash is acceptable (cursors, presence). Use `strict` where it is not (orders, audit logs).
:::

:::accordion-item{label="In snapshot mode, maxAgeMs is an expiry time" icon="i-ph-clock-duotone"}
In history mode, `maxAgeMs` deletes old _events_. In snapshot mode, it deletes a key's **current value**: when a key stops getting updates, its latest row expires after a while and is deleted. A reconnecting client then gets **nothing** back for that key. This is correct for short-lived state (presence, a heartbeat), where "no update for a while" should mean "gone". It is wrong for a value that stays true for a long time (a price, a document title), where an hour-old value is still correct. To limit a snapshot store without losing current values, limit the number of keys with `maxMessages` and do not set `maxAgeMs`.
:::

:::accordion-item{label="Snapshot writes combined in one handler" icon="i-ph-stack-duotone"}
When a snapshot handler sends many messages for the **same** key in one run (for example, many counter updates), LiveThing combines them in memory. It writes only the final value, once, when the handler finishes, instead of one SQL write per message. The `reduce` function still runs for every message, so a running total is still correct. Only the database write is combined.
:::

:::accordion-item{label="Frames that replay never stores" icon="i-ph-prohibit-duotone"}
Besides your `exclude` list, replay always skips three kinds of frames, because resending them would be wrong:

- Replies to requests, and server requests. They carry `metadata.exchange.id` and belong to one request that is in progress.
- Stream chunks. They carry `metadata.stream.id`, and streams have their own way to continue.
- Internal protocol frames (the `__…__` events). They carry no delivery sequence number, and LiveThing creates the ones it needs again after a reconnect.

You never need to filter these yourself.
:::

:::accordion-item{label="Only channel members get channel replay" icon="i-ph-lock-duotone"}
A channel replay request only runs for a **current member** of that channel. A non-member who asks for a channel's history gets zero rows and no error. The server does not even confirm that the channel exists. Top-level replay has no channel to check, so it always runs.
:::

:::accordion-item{label="A bad cursor is an error, a missing one is fine" icon="i-ph-hash-duotone"}
The cursor is the `lastKnownSeq` value on a `__replay__` frame. If it is not a whole number of 0 or more (for example `-1`, `2.5` or a string), the server replies with `__error__ { code: 'validation-failed' }`. The same happens for a bad `resume` list: more than 8 tokens, or a token that is not a string, is empty, or is longer than 64 characters. If the frame has no cursor at all, the server treats it as `lastKnownSeq: 0`. That means a fresh catch-up from the start of the store, which (as described above) never causes a gap.
:::
::

## Manual replay from a handler

Replay is automatic, but you can also resend a message yourself. This is useful when a client says it lost one message, and you want to send that message again. When replay is listed, the connection context has `ctx.sendReplay(event, payload, wire)`. This handler sends a stored Huddle message to the connection that asked:

```typescript [server/resend.ts]
import * as v from 'valibot'
import { base } from './base'
import { loadMessages } from './helpers'

export const handleResendMessage = base.on('resend-message', {
  input: v.object({ roomId: v.string(), messageId: v.string() }),
  async run(ctx, input) {
    const messages = await loadMessages(input.roomId)
    const message = messages.find((m) => m.id === input.messageId)
    if (!message) return

    ctx.sendReplay('message', message, {
      deliverySeq: 0,
      messageId: message.id,
    })
  },
})
```

The `wire` object sets the `deliverySeq` and the `messageId`. The client uses `deliverySeq` to remember how far it has read, and `messageId` to drop the frame if it is a duplicate. Here `deliverySeq: 0` never moves the client's cursor forward, because the client only keeps a higher number. The `messageId` is the message's own ID, so the client drops the frame when it already has that message.

**Inside a channel handler**, use `ctx.channel.sendReplay(...)`. You do not pass the channel name, because the handler already knows it. You pass only `deliverySeq` and `messageId`. In the type, `ctx.channel.sendReplay` is optional, because not every channel has replay turned on. Check that it exists before you call it:

```typescript [server/resend.ts]
import * as v from 'valibot'
import { rooms } from './base'
import { loadMessages } from './helpers'

export const handleResendRoomMessage = rooms.on(
  'resend-room-message',
  {
    input: v.object({ messageId: v.string() }),
    async run(ctx, input) {
      if (!ctx.channel.sendReplay) return

      const messages = await loadMessages(ctx.channel.params.roomId)
      const message = messages.find((m) => m.id === input.messageId)
      if (!message) return

      ctx.channel.sendReplay('message', message, {
        deliverySeq: 0,
        messageId: message.id,
      })
    },
  },
)
```

**From a top-level handler**, you can also target a channel, or one channel of a dynamic family. Set `channel` in the wire object to the channel's own declaration: a static channel's declared value directly, or `familyDeclaration.at(params)` for one channel of a dynamic family. The client then routes the frame to the right channel handle. The event and payload are checked against **that channel's** `emits(...)`, not against the top-level ones. `channel` must be the declaration itself, not a channel name string: passing a string is a type error, and the runtime check rejects it too.

```typescript [server/resend.ts]
import * as v from 'valibot'
import { base, rooms } from './base'
import { loadMessages } from './helpers'

export const handleResendToRoom = base.on('resend-to-room', {
  input: v.object({ roomId: v.string(), messageId: v.string() }),
  async run(ctx, input) {
    const messages = await loadMessages(input.roomId)
    const message = messages.find((m) => m.id === input.messageId)
    if (!message) return

    ctx.sendReplay('message', message, {
      deliverySeq: 0,
      messageId: message.id,
      channel: rooms.at({ roomId: input.roomId }),
    })
  },
})
```

::warning
`sendReplay` is checked against the contract at runtime. The event must be a declared outgoing event for that scope. When you set `channel` in the wire object, the scope is that channel, so the event must be declared on the channel. If the event is not declared, `sendReplay` throws `[livething] Outgoing event "..." was not declared in the active scope.`
::

### Resending a binary event

A [binary event](/server/capabilities/binary) is sent again with the binary version of the same method: `ctx.binary.sendReplay(event, info, bytes, wire)` and `ctx.channel.binary.sendReplay(event, info, bytes, wire)`. It takes the info and the bytes where `sendReplay` takes the payload, and the same `wire`, with `channel` too. The connection gets one binary frame. Like every `.binary` sender, it takes only `binary({ emits })` events, and `sendReplay` takes only JSON events. The wrong kind throws, the same as `ctx.binary.send`.

In Huddle, a member who opens a room late can ask for the last picture another member shared. This handler sends it from the app's own store:

```typescript [server/resend.ts]
import * as v from 'valibot'
import { rooms } from './base'
import { loadLastScreenPicture } from './helpers'

export const handleResendScreenFrame = rooms.on(
  'resend-screen-frame',
  {
    input: v.object({ from: v.string() }),
    async run(ctx, input) {
      if (!ctx.channel.binary.sendReplay) return

      const picture = await loadLastScreenPicture(
        ctx.channel.params.roomId,
        input.from,
      )
      if (!picture) return

      ctx.channel.binary.sendReplay(
        'screen-frame',
        { from: input.from },
        picture.bytes,
        { deliverySeq: 0, messageId: picture.id },
      )
    },
  },
)
```
