A WebSocket connection can drop. A laptop goes to sleep, a phone changes networks, or a proxy closes an idle connection. While the socket is gone, your server keeps sending messages (chat lines, document updates, presence changes), and the client does not receive them. **Replay** solves this. The server records the messages it sends. When the client reconnects, the server sends again the messages that the client missed.

Each recorded message has a **sequence number**: a number that grows with every message the server sends. On the client, add the [`replay()` primitive](/client/primitives/replay) together with `dedup()` and `reconnection()`. `replay()` remembers the highest sequence number the client has seen. After a reconnect, it asks the server for every message with a higher number. Your handlers do not change. Turn replay on in the server and in the client, and a reconnecting client catches up by itself.

## When replay runs

Replay runs when the socket **reconnects**. The client sends its last known sequence number, and the server sends again every recorded message after that number.

The client asks once for each **scope** it has seen messages in. A scope is either the top level of the socket or one channel. The top level and each channel keep their own sequence number, so each one catches up separately. Before the client asks for a channel's missed messages, it joins that channel again. See [Channels](/server/channels/overview) for channel membership.

Replay does not run when a client subscribes to a channel for the first time. A new subscriber gets only the messages sent after it joins.

For each scope, the steps are the same:

1. The client sends a **cursor**: the last sequence number it saw in that scope.
2. The server reads the messages after that cursor from its store.
3. The server sends them to the client as replay frames.
4. The client's `dedup()` drops any message it already has.

## Two strategies

LiveThing has two replay strategies.

| Strategy               | Who stores the messages          | Best for                                                                    |
| ---------------------- | -------------------------------- | --------------------------------------------------------------------------- |
| `replay.history(...)`  | LiveThing (every message kept)   | Chat, feeds, logs: anything where the full list of messages matters         |
| `replay.snapshot(...)` | LiveThing (latest value per key) | Documents, counters, presence: anything where only the newest state matters |

[History and snapshot](/server/replay/history-and-snapshot) covers `replay.history` and `replay.snapshot`, their config, and when to use each one.

For a short summary of how to register the capability, see the [`replay` capability page](/server/capabilities/replay). This chapter explains the full behavior.

::note
Replay (`history` or `snapshot`) requires the `dedup()` and `sequence({ persist: true })` capabilities. It resends messages by sequence number, so you must list both, or the server fails to start.
::

Top-level replay **also covers channels**. If a channel does not set its own replay, the server-level replay records its messages too, so they are also replayed. To turn replay off for one channel, set `replay: false` in its config. To give a channel its own replay store, set `replay: true`.

## What replay records

Replay records every message the server sends, JSON and [binary](#binary-events), and replays it only to a client it was addressed to:

- `ctx.broadcast` and `ctx.channel.broadcast` send to everyone who can read the scope (for a channel, its current members). Replay records the message once, and replays it to anyone who may read that scope.
- `ctx.user.broadcast`, `ctx.users.get(id).broadcast`, and `ctx.channel.broadcastTo` a user send to one user across every one of that user's connections (every open tab, for example). Replay records the message once for that user, and replays it only to a connection signed in as that same user. An anonymous connection never receives it.
- `ctx.send`, `ctx.connections.get(ref).send`, `ctx.channel.send`, `broadcastTo` a connection, a tag, or a group, and a tag broadcast send to **chosen connections**. Replay records the message once for each user it reached, and replays it only to a client that comes back from one of those connections.

A reconnect opens a new connection with a new ID, so the server needs proof that the client was on one of the chosen connections. When replay is on, the server gives each connection a secret, random **resume token** in a `__resume__` frame, right after it opens. The client's `replay()` keeps the tokens of its last 8 connections, and shows them in its catch-up request. The frame also carries a sequence number that marks where the connection started, so a client that drops before its first message still has a top-level cursor to catch up from. A message sent to chosen connections is stored once, with the tokens of those connections, however many users it reached. It is replayed only to a client that shows one of their tokens **and** has the same user (or is anonymous, when that connection was anonymous). Another tab of the same user has a different token, so it does not get the message.

A broadcast that leaves out its sender (the default for `ctx.broadcast` and `ctx.channel.broadcast`) stores that sender's token. A client that shows it does not get the message back from replay, because that connection sent it. Another tab of the same user has a different token, so it does get the message, and so does the sender with `includeSelf: true`. Snapshot mode is different: a snapshot is the current value, so everyone gets it, the sender too.

Snapshot mode is the exception. A snapshot is the current value for each key, so a message sent to chosen connections of a user is stored as that user's value, and any connection of that user gets it back, with no token. A message sent to anonymous connections is stored as the value of each one's token, because those connections have no user. Every new anonymous connection adds its own values, so set `retention.maxMessages` when anonymous connections get these messages, or their rows grow without limit. With it set, the total is limited too (see [history config](/server/replay/history-and-snapshot#history-config)).

Replay skips a few kinds of message on purpose, because sending them again would be wrong.

| Message kind                                                                                                      | Why it is skipped                                                                                                    |
| ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Protocol and control frames**: subscribe confirmations, presence syncs, error frames, and other internal frames | They have no sequence number, and LiveThing creates them again on reconnect, so they are never recorded.             |
| **Requests and their replies**: a reply to a request, or a server request, with a correlation ID                  | It belongs to one request that is waiting for it. Sending it again later has no meaning.                             |
| **Stream chunks**: parts of a [stream](/server/streams/overview), with a stream ID                                | Streams have their own way to continue ([durable streams](/server/streams/overview)), so replay does not store them. |

Replay also has an `exclude` option: a list of event names you never want replayed. Use it for frequent events where old data has no value, such as cursor moves or typing indicators. Excluded events are still sent live as normal. They are only kept out of the replay store.

::note
Replay does not change what a client receives **live**. Every event is still sent at the moment you send it. Replay only adds a recording, so a client that was away can ask for the part it missed.
::

### Binary events

Replay stores [binary events](/server/binary/overview) the same way as JSON events: it records each one, unless its name is in `exclude`. A stored binary event keeps its info and its bytes. On catch-up, the server sends it as **one binary frame**, with the same metadata the live frame had: the same `metadata.delivery.id` and `metadata.delivery.seq`, and the same channel. On the client, it reaches `binary.on` with the whole bytes, like a live one.

One store can hold JSON and binary events. They share one sequence order, and catch-up sends them strictly in that order. It does not send all the JSON events first and the binary events after them.

In Huddle, a member who drops out of a screen share in `room:general` and comes back gets the `screen-frame` pictures it missed, in order. Screen pictures are large, so `retention.maxBytes` (64 MiB for each audience by default) is what usually limits the store. See [history config](/server/replay/history-and-snapshot#history-config).

A few rules keep binary replay safe:

- **A message that is too big is not stored.** Three limits decide it. The message must fit in one row of the adapter's SQL storage: on Cloudflare a row is at most 8 MB, much smaller than the 32 MiB message limit, so a large binary event there is sent live only. On Node, the limit is SQLite's own (about 1 GB). It must fit in the adapter's send limit (32 MiB by default), or it could never be sent again. And it must not be bigger than `retention.maxBytes` alone, or storing it would push out every older message of its audience. The live send still works (when the message fits the send limit), but a client that was away misses it. LiveThing logs a warning the first time this happens for each event and limit. The same rules apply to JSON events. The missing message is not a `__gap__`, because sequence numbers already have gaps: a message sent to other users takes a number too.
- **Snapshot mode cannot store binary events.** A snapshot's `reduce` combines JSON values and cannot combine bytes. So `replay.snapshot()` refuses to start when a binary event would go into its store. Use `replay.history()`, or list the binary events in `exclude`.
- **Catch-up waits for slow sockets.** A reconnecting client can get many large rows one after the other. On a platform that reports its send buffer (Node), catch-up waits while the socket has more than 256 KiB waiting, the same as [`ctx.stream.drain()`](/server/streams/plain#backpressure-with-drain). All the waits of one catch-up share one budget of about 50 seconds. When it runs out, LiveThing closes the connection with `1013` (`TRY_AGAIN_LATER`), and the client reconnects and asks again from where it got to. Cloudflare does not report its send buffer, so catch-up there sends every row at once.
- **Live messages wait only when their order matters.** The client keeps the highest sequence number it saw in each store. So while a store catches up, a live message with a sequence number of **that** store waits, and goes out after the store's last replayed row. Everything else goes out at once: replies to requests, server requests, stream chunks, framework frames such as `__subscribeOk__`, and messages of other stores. The waiting messages count toward the slow-client rule of [`1013`](/core/close-codes): with the socket's buffer, they may stay over twice the send limit for at most 10 seconds.
- **Catch-up reads the store a page at a time** (256 rows, or about 4 MiB), so one catch-up never holds the whole store in memory. If retention deletes rows it has not sent yet while it waits, the client gets a `__gap__` for them before the rows that are left.

## Where the messages live

Replay keeps its store in the server's **own** SQL storage (the same storage your handlers use through `ctx.sql`). The persistent sequence counter is stored there too. Every adapter provides this storage, so replay creates and manages its own tables there. You do not need to turn on anything else.

Replay keeps one **store per scope**:

- **One top-level store** for every message that is not sent in a channel.
- **One store for each channel.** This is true when the channel uses the server-level replay, and when it sets its own `replay: true`.

[Retention](/server/replay/history-and-snapshot#history-config) limits each store separately. Retention is the rule for how many rows to keep and for how long. `maxMessages` and `maxBytes` apply _to each store_: when a busy channel deletes its old rows, the top-level store and the other channels keep theirs. Inside a store, it applies to each audience on its own: the messages sent to everyone, the messages for each user, and the messages for each anonymous connection's token. So private messages never push the shared history out, and one user's messages never push out another's. What a store holds depends on the mode. **History** mode keeps every message that can be replayed. **Snapshot** mode keeps only the latest row for each key. For each store, the server also saves the highest sequence number it has deleted. This number is the **eviction watermark**. The next section shows how the server uses it.

A broadcast gets **one** sequence number and **one** delivery ID, and every recipient gets the same ones. So a broadcast is stored as **one replay row**, not one row for each subscriber, and it is stored even when no connection is there to receive it live. A message sent to chosen connections is stored as one row for each user it reached, with the tokens of that user's connections. A tag broadcast that reaches 50 users stores 50 rows. These rows are written together: if one fails to store, none is kept. A message sent to chosen connections that reaches no connection is not stored, because no client can ask for it. The server sends replayed rows in `metadata.delivery.seq` order. The client's `dedup()` drops repeats by `metadata.delivery.id`, so when the server sends again a message the client already has, the client ignores it.

## When catch-up misses messages

Retention has limits, so a client can be away long enough for the server to delete messages the client has not received. The server cannot send deleted rows, but it tells the client that some messages are missing. For each store, the server keeps the eviction watermark: the highest sequence number it has deleted. Messages sent to only one user, or to chosen connections of one user, count only for that user, so another user never gets a gap for a message that was not meant for them. Messages sent to an anonymous connection count only for a client that shows that connection's resume token. A reconnecting client asks to catch up from sequence _N_. When _N_ is **below** that watermark, the server sends a `__gap__` frame for that scope **before** the messages that are still stored.

On the client, the [`gaps()` primitive](/client/primitives/gaps) passes this frame to your `onGap` callback. The callback gets `missedThrough`, the highest sequence number that was deleted. The app then knows it must load the missing data from its API, because it is not up to date. This only happens in **history** mode. Snapshot mode always sends the current state of every key, so the client cannot be behind, and the server never sends a gap. A new client that starts from sequence `0` also never gets a gap, because a gap only has meaning when the client had a real cursor.

The same `__gap__` frame is also used for an [inbox overflow](/server/inbox/overflow-and-gap). An inbox overflow happens when the server deletes a member's oldest stored rows while the member is behind. Both cases reach your app through the same `onGap` callback.
