A WebSocket connection can drop. A laptop goes to sleep, a phone changes networks, or a proxy closes an idle connection. While the socket is gone, your server keeps sending messages (chat lines, document updates, presence changes), and the client does not receive them. **Replay** solves this. The server records the messages it sends. When the client reconnects, the server sends again the messages that the client missed.

Each recorded message has a **sequence number**: a number that grows with every message the server sends. On the client, add the [`replay()` primitive](/client/primitives/replay) together with `dedup()` and `reconnection()`. `replay()` remembers the highest sequence number the client has seen. After a reconnect, it asks the server for every message with a higher number. Your handlers do not change. Turn replay on in the server and in the client, and a reconnecting client catches up by itself.

## When replay runs

Replay runs when the socket **reconnects**. The client sends its last known sequence number, and the server sends again every recorded message after that number.

The client asks once for each **scope** it has seen messages in. A scope is either the top level of the socket or one channel. The top level and each channel keep their own sequence number, so each one catches up separately. Before the client asks for a channel's missed messages, it joins that channel again. See [Channels](/server/channels/overview) for channel membership.

Replay does not run when a client subscribes to a channel for the first time. A new subscriber gets only the messages sent after it joins.

For each scope, the steps are the same:

1. The client sends a **cursor**: the last sequence number it saw in that scope.
2. The server reads the messages after that cursor from its store.
3. The server sends them to the client as replay frames.
4. The client's `dedup()` drops any message it already has.

## Two ways to do it

LiveThing has two built-in strategies, and a hook for writing your own.

| Strategy               | Who stores the messages                  | Best for                                                                    |
| ---------------------- | ---------------------------------------- | --------------------------------------------------------------------------- |
| `replay.history(...)`  | LiveThing (every message kept)           | Chat, feeds, logs: anything where the full list of messages matters         |
| `replay.snapshot(...)` | LiveThing (latest value per key)         | Documents, counters, presence: anything where only the newest state matters |
| `replay.custom()`      | You (your own SQL, KV or external store) | Custom storage, custom filtering, or a database you already run             |

You can use built-in replay or custom replay in one scope, but not both. If you list `replay.history()` (or `replay.snapshot()`) and `replay.custom()` together, and then register a `base.replay({ ... })` hook, the build fails. The error says that built-in replay and custom replay are both configured. Pick one per scope.

- [Built-in replay](/server/replay/built-in): `replay.history` and `replay.snapshot`, their config, and when to use each one.
- [Custom replay](/server/replay/custom): store and resend messages yourself with a `base.replay({ ... })` hook.

For a short summary of how to register the capability, see the [`replay` capability page](/server/capabilities/replay). This chapter explains the full behavior.

::note
Built-in replay (`history` or `snapshot`) requires the `dedup()` and `sequence({ persist: true })` capabilities. It resends messages by sequence number, so you must list both, or the build fails. `replay.custom()` manages its own storage and needs neither.
::

Top-level replay **also covers channels**. If a channel does not set its own replay, the server-level replay records its messages too, so they are also replayed. To turn replay off for one channel, set `replay: false` in its config. To give a channel its own replay store, set `replay: true`. For your own custom replay on one channel, call `channel.replay({ ... })` (this needs `replay.custom()`).

## What replay does not store

Replay only records a **broadcast**: a message sent to every connection in a scope, or to one user across every one of that user's connections.

- `ctx.broadcast` and `ctx.channel.broadcast` send to everyone who can read the scope (for a channel, its current members). Replay records the message once, and replays it to anyone who may read that scope.
- `ctx.user.broadcast`, `ctx.users.get(id).broadcast`, and `ctx.channel.broadcastTo` a user send to one user across every one of that user's connections (every open tab, for example). Replay records the message once for that user, and replays it only to a connection signed in as that same user. An anonymous connection never receives it.

A **send to one connection** is never recorded: `ctx.send`, `ctx.connections.get(ref).send`, `ctx.channel.send`, and `ctx.channel.broadcastTo` a connection, a tag, or a group. A tag broadcast is never recorded either. A reconnect opens a new connection with a new ID, so no later connection can prove it was the one addressed, and replaying the message to it would be a guess. To give the sender itself a copy it can replay later, broadcast with `ctx.broadcast(event, payload, { includeSelf: true })` instead of sending to that connection separately.

Beyond that rule, replay skips a few kinds of message on purpose, because sending them again would be wrong.

| Message kind                                                                                                         | Why it is skipped                                                                                                    |
| -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Protocol and control frames**: subscribe confirmations, presence syncs, error frames, and other internal frames    | They have no sequence number, and LiveThing creates them again on reconnect, so they are never recorded.             |
| **Request/response replies**: a reply to a request, with a correlation ID (the ID that links a reply to its request) | A reply belongs to one request that is waiting for it. Sending it again later has no meaning.                        |
| **Stream chunks**: parts of a [stream](/server/streams/overview), with a stream ID                                   | Streams have their own way to continue ([durable streams](/server/streams/overview)), so replay does not store them. |

Built-in replay also has an `exclude` option: a list of event names you never want replayed. Use it for frequent events where old data has no value, such as cursor moves or typing indicators. Excluded events are still sent live as normal. They are only kept out of the replay store.

::note
Replay does not change what a client receives **live**. Every event is still sent at the moment you send it. Replay only adds a recording, so a client that was away can ask for the part it missed.
::

## Where the messages live

Built-in replay keeps its store in the server's **own** SQL storage (the same storage your handlers use through `ctx.sql`). The persistent sequence counter is stored there too. Every adapter provides this storage, so built-in replay creates and manages its own tables there. You do not need to turn on anything else.

Replay keeps one **store per scope**:

- **One top-level store** for every message that is not sent in a channel.
- **One store for each channel.** This is true when the channel uses the server-level replay, and when it sets its own `replay: true`.

[Retention](/server/replay/built-in#history-config) limits each store separately. Retention is the rule for how many rows to keep and for how long. `maxMessages` applies _to each store_: when a busy channel deletes its old rows, the top-level store and the other channels keep theirs. What a store holds depends on the mode. **History** mode keeps every message that can be replayed. **Snapshot** mode keeps only the latest row for each key. For each store, the server also saves the highest sequence number it has deleted. This number is the **eviction watermark** ("eviction" means deleting old rows to stay inside the limit). The next section shows how the server uses it.

A broadcast (one message sent to many connections) gets **one** sequence number and **one** delivery ID, and every recipient gets the same ones. So a broadcast is stored as **one replay row**, not one row for each subscriber, and it is stored even when no connection is there to receive it live. The server sends replayed rows in `metadata.delivery.seq` order. The client's `dedup()` drops repeats by `metadata.delivery.id`, so when the server sends again a message the client already has, the client ignores it.

## When catch-up misses messages

Retention has limits, so a client can be away long enough for the server to delete messages the client has not received. The server cannot send deleted rows, but it tells the client that some messages are missing. For each store, the server keeps the eviction watermark: the highest sequence number it has deleted. Messages sent to only one user count only for that user, so another user never gets a gap for a message that was not meant for them. A reconnecting client asks to catch up from sequence _N_. When _N_ is **below** that watermark, the server sends a `__gap__` frame for that scope **before** the messages that are still stored.

On the client, the [`gaps()` primitive](/client/primitives/gaps) passes this frame to your `onGap` callback. The callback gets `missedThrough`, the highest sequence number that was deleted. The app then knows it must load the missing data from its API, because it is not up to date. This only happens in **history** mode. Snapshot mode always sends the current state of every key, so the client cannot be behind, and the server never sends a gap. A new client that starts from sequence `0` also never gets a gap, because a gap only has meaning when the client had a real cursor.

The same `__gap__` frame is also used for an [inbox overflow](/server/inbox/overflow-and-gap). An inbox overflow happens when the server deletes a member's oldest stored rows while the member is behind. Both cases reach your app through the same `onGap` callback.
