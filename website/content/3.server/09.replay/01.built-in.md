Built-in replay means WSKit owns the storage. You list one capability, and the engine records every outgoing message and resends the missing tail when a client reconnects. No handler code, no table to manage.

There are two modes: **history** keeps every message, **snapshot** keeps only the latest value per key.

## What both modes need

Built-in replay is not standalone. It depends on two other capabilities, and the build fails fast without them:

| Capability                                                     | Why it's required                                                                                                                                                                                      |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| [`dedup()`](/server/capabilities/dedup)                        | Stamps each message with the ID replay keys off and the client de-duplicates against.                                                                                                                  |
| [`sequence({ persist: true })`](/server/capabilities/sequence) | Gives each message a stable sequence number that survives a restart, so stored rows order correctly. The `persist: true` part is required; an in-memory sequence is not enough, and the build says so. |

It also needs the platform `storage` capability (the SQL store), which the adapter provides.

::code-group

```typescript [history-server.ts]
import { define, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { replay } from '@wskit/server/replay'
import { sequence } from '@wskit/server/sequence'

const base = define({
  capabilities: [dedup(), sequence({ persist: true }), replay.history()],
})
```

```typescript [snapshot-server.ts]
import { define, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { replay } from '@wskit/server/replay'
import { sequence } from '@wskit/server/sequence'

const base = define({
  capabilities: [dedup(), sequence({ persist: true }), replay.snapshot()],
})
```

::

## History mode

`replay.history(...)` keeps **every** message as its own row. On reconnect, the client says "I last saw sequence N" and gets every recorded message after N, in order. This is what you want for a chat room, an activity feed, or a log — anything where the full sequence of events matters and you cannot skip the middle.

```typescript [chat-server.ts]
import { define, emits, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { replay } from '@wskit/server/replay'
import { sequence } from '@wskit/server/sequence'
import * as v from 'valibot'

const ChatMsg = v.object({ text: v.string(), from: v.string() })
const SendMsg = v.object({ text: v.string() })

const base = define({
  capabilities: [
    emits({ 'chat-msg': t<v.InferOutput<typeof ChatMsg>>() }),
    dedup(),
    sequence({ persist: true }),
    replay.history({
      retention: { maxMessages: 1000, maxAgeMs: 3_600_000 },
      durability: 'strict',
      exclude: ['cursor'],
    }),
  ],
})

export const handleSendMsg = base.on('send-msg', {
  input: SendMsg,
  run(ctx, payload) {
    const msg = { text: payload.text, from: ctx.meta.username }
    ctx.send('chat-msg', msg)
    ctx.broadcast('chat-msg', msg)
  },
})
```

The returned `handleSendMsg` value must be included in `base.assemble({ handlers: [...] })` to receive `send-msg` frames. Defining it alone does not activate it or put it in `InferClient`.

Nothing in the handler mentions replay. Every `chat-msg` is recorded as it goes out. When the socket comes back, the client gets the ones it missed, and `cursor` events are skipped because they are in the `exclude` list.

Note the handler `broadcast`s one `chat-msg` to the whole room. That broadcast is stamped with **one** sequence number and **one** message ID for all recipients, so it becomes a **single** history row — not one per subscriber. A reconnecting client orders the resent rows by `seq` and drops any it already had by `messageId`, so an overlap between the resend and what it already saw folds away without a duplicate.

### History config

| Field                   | Type                        | Default    | What it does                                                                                                                                                                 |
| ----------------------- | --------------------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `durability`            | `'strict' \| 'best-effort'` | `'strict'` | `strict` writes the row before the send completes. `best-effort` sends first, then stores asynchronously — lower latency, small risk of losing the very last row on a crash. |
| `retention.maxMessages` | `number`                    | none       | Keep at most this many rows per store. When the store grows past it, the oldest rows are deleted.                                                                            |
| `retention.maxAgeMs`    | `number`                    | none       | Delete rows older than this many milliseconds. Pruned on boot and whenever a new message is stored.                                                                          |
| `exclude`               | `string[]`                  | `[]`       | Event names to never record. They still send live; they just never appear in replay.                                                                                         |

::note
**The storage model, behaviourally.** Replay keeps one store per scope, and there are only two kinds: **one top-level store** for non-channel messages, plus **one store per channel** that runs its own replay. History keeps every replayable row in its store; snapshot keeps the latest row per logical key. `maxMessages` and `maxAgeMs` bound each store **independently** — `maxMessages: 1000` means up to 1000 top-level rows _and_ up to 1000 rows for every replaying channel, and a busy channel evicting rows never touches another store. Each store also carries its own eviction watermark (see [above](#the-gap-signal-and-the-eviction-watermark)). It all lives in the server's own SQL storage, which every adapter guarantees, so built-in replay needs nothing extra enabled for it.
::

::note
On top of your `exclude` list, replay **automatically** skips three kinds of frame, so you never store them yourself: request/response replies (they carry a `correlationId`), stream chunks (they carry a `streamId`), and internal protocol frames (the `__…__` events).
::

## Snapshot mode

`replay.snapshot(...)` keeps only the **latest** row per logical key. A reconnecting client gets the current state of each key, not the full history of how it got there. This is what you want for a document, a counter, or a presence map — the journey does not matter, only where things landed.

You give it two functions:

- `snapshotKey(event, payload)` — builds the key that decides which rows replace each other. Rows with the same key collapse into one. If you omit it, the event name is the key.
- `reduce(previous, next)` — optional. Combines the stored value with the new one instead of always taking the newest. Return an `{ event, payload }` to store, or `null` to delete that key's snapshot.

```typescript [docs-server.ts]
import { define, emits, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { replay } from '@wskit/server/replay'
import { sequence } from '@wskit/server/sequence'
import * as v from 'valibot'
import type { ReplaySnapshotValue } from '@wskit/server/replay'

const DocSnapshot = v.object({ docId: v.string(), title: v.string() })
const DocDeleted = v.object({ docId: v.string() })
const CounterSnapshot = v.object({ key: v.string(), total: v.number() })

function reduceSnapshot(
  previous: ReplaySnapshotValue | null,
  next: ReplaySnapshotValue,
): ReplaySnapshotValue | null {
  if (next.event === 'doc-deleted') return null // forget this key
  if (next.event !== 'counter-snapshot') return next // latest wins

  // For counters, add the running total instead of replacing it.
  const previousTotal =
    previous?.event === 'counter-snapshot' ? Number(previous.payload.total) : 0
  return {
    event: next.event,
    payload: {
      ...next.payload,
      total: previousTotal + Number(next.payload.total),
    },
  }
}

const base = define({
  capabilities: [
    emits({
      'doc-snapshot': t<v.InferOutput<typeof DocSnapshot>>(),
      'doc-deleted': t<v.InferOutput<typeof DocDeleted>>(),
      'counter-snapshot': t<v.InferOutput<typeof CounterSnapshot>>(),
    }),
    dedup(),
    sequence({ persist: true }),
    replay.snapshot({
      snapshotKey: (_event, payload) => String(payload.docId ?? payload.key),
      reduce: reduceSnapshot,
      retention: { maxMessages: 5, maxAgeMs: 1_000 },
      durability: 'best-effort',
    }),
  ],
})
```

Here every `doc-snapshot` for the same `docId` replaces the last one — a reconnecting client gets only the newest title per document. A `doc-deleted` returns `null`, so that key drops out of the store entirely. A `counter-snapshot` adds to the running total instead of replacing it.

You can type `snapshotKey` and `reduce` as standalone functions with the exported [`SnapshotKeyFn`](/server/capabilities/replay) and `SnapshotReducer` types, or write them inline as arrows.

### Snapshot config

Snapshot mode takes everything history mode takes (`durability`, `retention`, `exclude`) plus two of its own:

| Field         | Type                                | Default     | What it does                                                                                                                                                 |
| ------------- | ----------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `snapshotKey` | `(event, payload) => string`        | event name  | Logical key. Rows sharing a key replace each other.                                                                                                          |
| `reduce`      | `(previous, next) => value \| null` | latest wins | Combine the stored snapshot with the new event. `previous` is the current value or `null`. Return a value to store, or `null` to delete that key's snapshot. |

::tip
Snapshot mode also coalesces in memory. If a handler sends many messages for the same key in one go — say a burst of counter increments — they fold together inside the open handler scope and only the final value is written once when the handler finishes, instead of one SQL write per send.
::

::warning
`retention.maxAgeMs` behaves differently on a snapshot than on history. It deletes a row for being **old**, not for being replaced — so once a key stops updating, its **current** value ages out and disappears. That is what you want for TTL-style state like presence or a heartbeat, where "no update in a while" should mean "gone". It is wrong for a durable current value like a price or a document title, where an hour-old value is still the truth: age it out and a reconnecting client gets nothing back for that key. To bound a snapshot's size without dropping live state, cap the number of keys with `maxMessages` and leave `maxAgeMs` off.
::

## Durability: strict vs best-effort

`durability` decides the order of storing and sending:

| Mode               | Order                            | Trade-off                                                                                                                                       | Good for                                                                                                               |
| ------------------ | -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `strict` (default) | Store the row, then send.        | The message is recorded before the client could have seen it, so a crash never loses a sent-but-unstored message. Slightly higher send latency. | Orders, payments, audit logs — anywhere missing a message would be a real problem.                                     |
| `best-effort`      | Send, then store asynchronously. | Lower latency, but if the process dies in the gap, the last message may not make it into the store.                                             | Cursors, presence, high-frequency snapshots — anywhere a bit of latency matters more than the last message in a crash. |

## The gap signal and the eviction watermark

Retention keeps stores bounded, which means a client can be away long enough that rows it hadn't caught up on are already deleted. When the server can't resend the full tail, it says so with a `__gap__` frame instead of quietly handing back a shorter list.

The mechanism is one number per store: the **eviction watermark** — the highest sequence that store has ever deleted. Every time retention prunes rows (by count or by age), the server raises that store's watermark to the highest `seq` it just dropped. The watermark only ever goes **up**; a later prune that happens to remove an older tail can never lower it.

On a catch-up request the check is exact:

::steps

### A client reconnects and asks to catch up from sequence _N_

The `__replay__` request carries `lastKnownSeq: N` — the highest sequence that scope had seen before the drop.

### The server compares _N_ to that scope's watermark

If `N > 0` **and** `N < watermark`, rows the client hadn't seen have been evicted. If `N` is at or above the watermark, nothing it was owed is missing.

### A gap is sent first, then the surviving tail

When the check trips, the server sends `__gap__ { missedThrough: watermark }` **before** the rows it can still resend. `missedThrough` is the watermark: everything at or below it is gone.
::

Two edges fall straight out of that rule:

- **A fresh load (`since: 0`) never gets a gap.** A gap is only meaningful against a cursor the client actually held. Sequence `0` means "I've seen nothing," so there's nothing to be behind on — the `N > 0` guard skips it.
- **Snapshot mode never gaps.** Snapshot always resends the _current_ state of every key, so a reconnecting client is never "behind" a point in a history it can't reach. Only history mode tracks a watermark and only history mode emits `__gap__`.

::note
The check is against the eviction watermark, not the lowest surviving `seq`. The global sequence counter is sparse — excluded events, protocol frames, and other scopes all consume numbers — so "the oldest row I still have" would be a misleading floor. Recording the highest sequence actually deleted is what lets the server tell "you missed evicted messages" apart from "nothing happened here."
::

The watermark is **per store**, so a channel that overflows raises only its own watermark and only its own members see a channel gap; the top-level scope and other channels are untouched. On the client, [`gaps()`](/client/primitives/gaps) routes a top-level gap to `socket.onGap` and a channel gap to `socket.channel(...).onGap`.

## Per-channel replay

Server-level replay **applies to channels too** — it records channel traffic by default. To override that for one channel, set `replay` in the channel config:

```typescript [rooms-server.ts]
// Inherit + enable the server-level strategy for this channel:
const busy = base.channel('busy-room', { replay: true })

// Opt this channel out entirely — its messages are not stored or replayed:
const quiet = base.channel('quiet-room', { replay: false })
```

`replay: true` gives the channel its own store using the server-level config. `replay: false` opts the channel out — messages on it are not recorded by either the server-level or a channel-level instance. See [Channels](/server/channels/overview) for the subscribe-time side of channel replay.

::note
A channel's replay is membership-gated: a connection that is not a live member of the channel gets **zero rows** when it asks for that channel's replay — the request is silently denied, not errored, so the channel's existence is never revealed to a non-member. And a malformed replay cursor (a non-numeric `lastKnownSeq` on the `__replay__` frame) comes back as `__error__ { code: 'validation-failed' }`.
::

## Edge cases worth knowing

The main flow is "store on send, resend on reconnect." A handful of corners bend that, and each has a deliberate behaviour.

::accordion
::accordion-item{label="The best-effort crash window" icon="i-ph-warning-duotone"}
With `durability: 'best-effort'` the row is written _after_ the send, in the background. If the process dies in that window, the very last message went out to live clients but never reached the store — so a client reconnecting right after the crash won't get it replayed. `strict` closes the window by storing first, at the cost of a little send latency. Pick `best-effort` only where a lost last-row-on-crash is acceptable (cursors, presence), and `strict` where it isn't (orders, audit logs).
::

::accordion-item{label="Snapshot maxAgeMs is a TTL, not a replacement clock" icon="i-ph-clock-duotone"}
On history, `maxAgeMs` ages out old _events_. On snapshot it ages out a key's **current value**: once a key stops updating, its latest row eventually expires and disappears, so a reconnecting client gets **nothing** back for that key. That's exactly right for TTL-style state (presence, a heartbeat) where "no update in a while" should mean "gone" — and wrong for a durable current value (a price, a document title), where an hour-old value is still the truth. To bound a snapshot without dropping live state, cap keys with `maxMessages` and leave `maxAgeMs` off.
::

::accordion-item{label="Snapshot coalescing inside one handler" icon="i-ph-stack-duotone"}
When a snapshot handler sends many messages for the **same** key in one run — a burst of counter ticks, say — they fold together in memory and only the final value is written once when the handler finishes, instead of one SQL write per send. The `reduce` function still runs across the burst, so a running total is correct; only the write is coalesced.
::

::accordion-item{label="Frames replay never stores, no matter what" icon="i-ph-prohibit-duotone"}
Beyond your `exclude` list, replay always skips three kinds of frame because resending them would be wrong: request/response replies (they carry a `correlationId` and belong to one in-flight call), stream chunks (they carry a `streamId` and have their own resume machinery), and internal protocol frames (the `__…__` events, which carry no sequence and are rebuilt on reconnect). You never filter these yourself.
::

::accordion-item{label="The channel membership gate" icon="i-ph-lock-duotone"}
A channel replay request only runs for a **live member** of that channel. A non-member asking for a channel's history gets zero rows and no error — the server won't even confirm the channel exists. Top-level replay has no channel to gate on, so it always runs.
::

::accordion-item{label="A malformed cursor is an error, an empty one is fine" icon="i-ph-hash-duotone"}
A `__replay__` frame with a non-numeric `lastKnownSeq` comes back as `__error__ { code: 'validation-failed' }`. A frame with no cursor at all is treated as `lastKnownSeq: 0` — a fresh catch-up from the start of the store, which (as above) never triggers a gap.
::
::

## Manual replay from a handler

Built-in replay is automatic, but you can also resend a stored message by hand — useful for a "load older history" button. With replay registered, the connection context gains `ctx.sendReplay(event, payload, wire)`:

```typescript [history-button.ts]
export const handleRequestHistory = base.on('request-history', {
  input: v.object({}),
  run(ctx) {
    ctx.sendReplay(
      'chat-msg',
      { text: 'injected-history', from: 'system' },
      { seq: 0, messageId: 'manual-001' },
    )
  },
})
```

The `wire` object names the `seq` and `messageId` the client uses to order and de-duplicate the frame.

**Inside a channel handler**, use `ctx.channel.sendReplay(...)`. The channel name is implicit, so you pass only `seq` and `messageId`:

```typescript [room-history.ts]
// chatRoom is a channel: const chatRoom = base.channel('room', { ... })
export const handleRoomHistory = chatRoom.on('request-room-history', {
  input: v.object({}),
  run(ctx) {
    ctx.channel.sendReplay(
      'room-msg',
      { text: 'injected-room-history', from: 'system' },
      { seq: 0, messageId: 'room-manual-001' },
    )
  },
})
```

**From a top-level handler**, to target a channel — or one instance of a dynamic family — stay on `ctx.sendReplay` and name the `channel` (and `channelFamily` for a family) in the wire, so client-side routing stays correct:

```typescript [family-history.ts]
ctx.sendReplay(
  'room-msg',
  { text: 'family-injected', from: 'system' },
  {
    seq: 0,
    messageId: 'fam-manual-001',
    channel: 'fam-1',
    channelFamily: 'fams',
  },
)
```

::warning
`sendReplay` is contract-checked at runtime. The event must be a declared outgoing event for that scope — sending an undeclared event throws `[wskit] Outgoing event "..." was not declared in the active scope.`. The type surface only offers declared events, so you hit this only if you cast past it.
::
