Before a connection becomes a member, a channel can run a **gate**: code that decides whether the connection may join. The gate has two parts that run in order. `check` is an async permission test. `commit` is a synchronous final check. Either one can reject the subscribe by throwing an error. Both are optional. A channel with neither lets everyone in. Huddle's own `rooms` has no gate, so every example on this page declares `rooms` again with the gate it shows.

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import * as v from 'valibot'
import { base, Message } from './base'
import { isRoomMember } from './helpers'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  subscribe: v.object({ inviteToken: v.optional(v.string()) }),
  async check(ctx, input) {
    const member = await isRoomMember(
      ctx.user.id,
      ctx.channel.params.roomId,
    )
    if (!member && !input.inviteToken)
      throw new Error('no membership and no invite token')
    return { member } // passed to commit
  },
  commit(ctx, { member }) {
    if (!member && ctx.channel.members().length >= 200)
      throw new Error('room is full')
  },
})
```

::note
You write `check`, `commit`, and `revalidate` inside the `base.channel('name', { ... })` object. The same object holds the channel's `capabilities` list: the array that turns on channel features like [`inbox()`](/server/inbox/delivery) and [`readReceipts()`](/server/inbox/receipts). TypeScript uses that `capabilities` list to decide what `ctx.channel` contains. It cannot use the list for a function that is written inside the same object, because it is still reading that object. So the `ctx` of these three functions has no `ctx.channel.inbox` and no `ctx.channel.readReceipts`. If you write `ctx.channel.inbox` in `check`, `commit`, or `revalidate`, TypeScript reports an error. The same is true for `ctx.channel.request` when the channel declares its own `serverRequests(...)`.

You write `dms.subscribe(...)`, `dms.unsubscribe(...)`, and `dms.sessionEnd(...)` (explained later on this page) after the `base.channel(...)` object is complete. At that point TypeScript knows the full list. The same is true for every `dms.on(...)` handler. Read `ctx.channel.inbox` or `ctx.channel.readReceipts` there. (This `dms` is cut down to `inbox()`. Huddle's `dms` also has `readReceipts()` and `emits(...)`.)

```typescript [server/dms.ts]
import { inbox } from '@livething/server/inbox'
import { base } from './base'

const dms = base.channel(['dms', 'dm:{pair}'], {
  membership: 'persistent',
  capabilities: [inbox()],
  commit(ctx) {
    // ctx.channel.inbox does not exist here.
  },
})

dms.subscribe((ctx) => {
  // ctx.channel.inbox exists here, because dms.subscribe(...)
  // is written after the base.channel(...) object is complete.
  ctx.channel.inbox.backfill(ctx.user.id, [])
})
```

The runtime follows the same rule. During `check`, `commit`, and `revalidate`, `ctx.channel` has no `inbox` or `readReceipts`, and handles returned by `ctx.channels.get(...)` do not have them either. Channel operations that only read or change membership, such as `members()`, are still available. When you need to read or write inbox or read-receipt state for a new member, do it in `subscribe`, `unsubscribe`, or `sessionEnd`.

::

## `subscribe`: validate the payload first

A client can send a payload (data) when it subscribes. Declare a `subscribe` schema to validate it. The validated, typed value is the second argument of `check`. If the payload does not match the schema, LiveThing rejects the subscribe before `check` runs.

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import * as v from 'valibot'
import { base, Message } from './base'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  subscribe: v.object({ inviteToken: v.optional(v.string()) }),
  async check(ctx, input) {
    // `input` has the type `{ inviteToken?: string }`, from the schema above.
    const { inviteToken } = input
    // ...
  },
})
```

Without a `subscribe` schema, the second argument of `check` has the type `unknown`. The client can still send a payload, but LiveThing does not validate it. A channel can have a `subscribe` schema and no `check`. In that case LiveThing validates the payload, and the subscribe continues if it is valid.

## `check`: the async gate

`check` runs once, on a connection's first subscribe. It can be `async`, and LiveThing waits for it to finish. Use it for token checks, database reads, or any permission test that needs `await`. A normal synchronous `check` also works. Throw an error to reject the subscribe. The value that `check` returns is passed to `commit` unchanged.

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { base, Message } from './base'
import { isUserBanned } from './helpers'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  async check(ctx) {
    if (await isUserBanned(ctx.user.id)) {
      throw new Error('banned users may not subscribe')
    }
    // A return value is optional. Returning nothing is fine when there is no commit.
  },
})
```

The return value is fully typed. TypeScript infers the type of the value that `check` returns, and gives `commit`'s second argument the same type. You do not need to write the type yourself:

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import * as v from 'valibot'
import { base, Message } from './base'
import { isRoomMember } from './helpers'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  subscribe: v.object({ inviteToken: v.optional(v.string()) }),
  async check(ctx, input) {
    const member = await isRoomMember(
      ctx.user.id,
      ctx.channel.params.roomId,
    )
    if (!member && !input.inviteToken)
      throw new Error('no membership and no invite token')
    return { member }
  },
  commit(ctx, { member }) {
    // `member` gets its type from the value check returns. No annotation needed.
    if (!member && ctx.channel.members().length >= 200)
      throw new Error('room is full')
  },
})
```

::note
`check` runs only on a **first** subscribe. When a member of a persistent channel reconnects, the channel adds it back automatically (this is called **auto-rejoin**) and runs `revalidate` instead of `check`. The `revalidate` section below explains it. So use `check` to decide who may join the first time. Use `revalidate` for access you take away later, such as a ban, that must also apply after a reconnect.
::

## `commit`: the synchronous final gate

`commit` runs just before LiveThing writes the membership, in the same JavaScript **tick** (one run of code with no `await` in between). It is synchronous. **It must not be `async`, and it must not return a Promise.** If it returns a Promise (or any other object with a `then` method), LiveThing throws this error when a subscribe reaches `commit`:

```
commit() must be synchronous.
```

The subscribe fails and no membership is written. An async `commit` is a mistake in your code, not a decision about one user. So the client receives an `internal-error` error, and the connection stays open. Use `commit` for a last-moment check on live state, such as a limit on the number of members. For this kind of check, the count must not change between the check and the write.

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { base, Message } from './base'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  commit(ctx) {
    if (ctx.channel.members().length >= 200) {
      throw new Error('room is full')
    }
  },
})
```

`commit` runs in the same tick as the membership write, so `ctx.channel.members()` returns the exact current list. The list does not include the connection that is joining. If two connections join at the same moment, they cannot both get past a limit of two.

You can use `commit` alone, with no `check`. Its second argument is the value that `check` returned, so it is `undefined` when there is no `check`.

## How accept and reject work

A subscribe is accepted only when both gates pass, which means neither one throws.

| Outcome            | What you do                                      | What happens                                                                   |
| ------------------ | ------------------------------------------------ | ------------------------------------------------------------------------------ |
| Accept             | Let `check` and `commit` return normally         | The connection becomes a member. The channel's `subscribe(...)` callback runs. |
| Reject in `check`  | Throw from `check`                               | No membership is written. The subscriber gets an error. `commit` does not run. |
| Reject in `commit` | Throw from `commit`                              | No membership is written. The subscriber gets an error.                        |
| Bad payload        | Send a payload that fails the `subscribe` schema | Rejected before `check` runs. The subscriber gets a `validation-failed` error. |

A throw from either gate stops the subscribe. LiveThing sends an error to the connection that tried to join. What the client sees depends on what you throw:

- A plain `Error` reaches the client as the built-in `internal-error` code. Its message stays on the server.
- A typed error made with [`error(...)`](/core/error-model) reaches the client with its own code, so the client can check for that code. Declare it in the [`errors([...])`](/server/capabilities/errors) capability. A typed error that is not declared there also reaches the client as `internal-error`.

Huddle's `errors([NotFound, Forbidden, RoomFull])` already lists `RoomFull`, which comes from the file that the server and the client share:

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { RoomFull } from '../shared/errors'
import { base, Message } from './base'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  commit(ctx) {
    if (ctx.channel.members().length >= 200)
      throw RoomFull({ limit: 200 })
  },
})
```

The shared error model (`error(...)`, `.matches()`, the built-in errors) is explained in [Core](/core/error-model). For server control-flow errors such as `Block`, see [Errors](/server/capabilities/errors).

## Membership: what a subscribe gives the connection

When both gates pass, LiveThing adds the connection to the channel's member list. From then on, the connection receives the channel's broadcasts and can send the channel's events. Inside any channel handler, `ctx.channel.members()` returns the current members as `ConnectionInfo[]`.

If a connection that is **already** a member subscribes again, LiveThing does nothing. The gates do not run again, and the server sends no second confirmation. A subscribe on an existing membership only means "make sure this connection is a member".

You can also subscribe a connection from server code with `ctx.channels.get(...).subscribe(ref, payload?)`. It runs the same gate (`check`, then `commit`). It does nothing if the connection is already a member. In this example, `rooms` is the one with the invite-token gate from the top of this page:

```typescript [server/huddle-handlers.ts]
import * as v from 'valibot'
import { base } from './base'

const handleJoinRoom = base.on('join-room', {
  input: v.object({
    roomId: v.string(),
    inviteToken: v.optional(v.string()),
  }),
  async run(ctx, input) {
    // Same gate as a client subscribe. The optional payload is passed to check.
    await ctx.channels
      .get('rooms', `room:${input.roomId}`)
      .subscribe(ctx.connection, { inviteToken: input.inviteToken })
  },
})
```

## `revalidate`: re-check on auto-rejoin

On a channel with `membership: 'persistent'`, LiveThing saves each membership as a row in storage (the **durable row**). When a member's connection drops, the member keeps the membership, and LiveThing adds the member back on reconnect (auto-rejoin). Auto-rejoin does **not** run `check` or `commit` again, because the user already passed them once. To check access again on every reconnect (for example a ban, a permission that expired, or a room that was closed), add `revalidate`.

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { base, Message } from './base'
import { isUserBanned } from './helpers'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  membership: 'persistent',
  async check(ctx) {
    if (await isUserBanned(ctx.user.id)) throw new Error('banned')
  },
  async revalidate(ctx) {
    // Runs on auto-rejoin only. Throw to remove the membership: the durable
    // row is deleted and the connection is not added back to the channel.
    if (await isUserBanned(ctx.user.id)) throw new Error('banned')
  },
})
```

`revalidate` can be `async`. It receives only `ctx`. It gets no subscribe payload, because a reconnect does not send one. LiveThing ignores its return value. If it throws, the membership is removed: LiveThing deletes the durable row, and the connection stays out of the channel.

::warning
`revalidate` runs only on auto-rejoin, and auto-rejoin happens only on a channel whose `membership` is `'persistent'`. If you add `revalidate` to an ephemeral channel (the default), the server throws an error at startup, because the function would never run. The message tells you to set `membership: 'persistent'` or remove `revalidate`. Keep the check for a first subscribe in `check`.
::

### When auto-rejoin runs, and what a reject looks like on the wire

When a user reconnects, auto-rejoin runs for every durable membership that user has. All of it finishes before your `onConnect(...)` hook runs, so in `onConnect` the connection is already back in its channels. LiveThing checks each membership separately:

- **Pass**: the connection is subscribed through the same server-side path as `channelHandle.subscribe(...)`. It receives `__subscribeOk__` for that channel. Other members receive `__memberOnline__`, not `__memberJoin__`, because the group did not change. Only this socket's presence changed.
- **Reject** (`revalidate` throws): LiveThing deletes the durable row. Instead of `__subscribeOk__`, the connection receives an `__error__` frame for that channel with the code `rejoin-rejected`. The connection is not added back to that channel. Its other memberships still rejoin as normal.
- **Channel renamed or removed** since the row was saved: when the server starts, a cleanup step deletes rows for channels that no longer exist, so these rows are normally gone before any user reconnects. See [Membership & Presence](/server/channels/membership-and-presence). If such a row is still found, LiveThing deletes it and sends the same `rejoin-rejected` error for that channel.

LiveThing deletes the durable row only when `revalidate` rejects or the channel no longer exists. A storage failure or a configuration mistake never deletes it.

## The subscription wire flow

A subscribe that the client starts runs these steps in order.

::steps{level="3"}

### Validate the payload

If the channel has a `subscribe` schema, LiveThing validates the client's payload. If it is not valid, the subscribe is rejected with a validation error, and the flow stops here.

### `check`

The async gate runs. If it throws, the subscribe is rejected and the subscriber gets the error. Its return value is kept for `commit`.

### `commit`

The synchronous gate runs in the same tick as the membership write. If it throws, the subscribe is rejected.

### Confirm and sync

The server confirms the subscribe to the new member. It also sends the current member list, so the new member sees who is already in the channel.

### Announce and run the callback

The existing members receive presence frames about the new member. Then the channel's `subscribe(...)` callback runs. Send the initial state to the new member here.

::

The confirmation tells the client whether the channel is persistent. On a persistent channel, the client does not subscribe again after a reconnect. It waits for the server's auto-rejoin. The presence frames are explained on the [Membership & Presence](/server/channels/membership-and-presence) page.

## Leaving: the three paths

A connection can leave a channel in three ways: it unsubscribes, the server kicks it, or it disconnects. Which callbacks run depends on the path and on whether the channel is persistent. In the table, `reason` is the text you pass to `kick`. It is required.

| Path                                 | Runs `unsubscribe` | Runs `sessionEnd` | Deletes the durable row   |
| ------------------------------------ | ------------------ | ----------------- | ------------------------- |
| Client sends `__unsubscribe__`       | Yes                | Yes               | Yes                       |
| `kick(target, { reason })`           | Yes                | Yes               | Yes                       |
| Plain disconnect, persistent channel | No                 | Yes               | No (auto-rejoins later)   |
| Plain disconnect, ephemeral channel  | Yes                | Yes               | (there is no durable row) |

`kick(target, { reason })` removes the user from the channel for good. On a persistent channel it deletes the durable row, so the kicked user is **not** added back on the next reconnect. The user must subscribe again. To boot a user's sockets but keep their membership, close the connections instead (`ctx.users.get(userId).close()`): that is a plain disconnect, so the user rejoins on their next connection.

The important difference is in the last two rows. On a **persistent** channel, a plain disconnect is not a real leave. The user keeps the membership and will be added back, so only `sessionEnd` runs. On an **ephemeral** channel, a disconnect is a real leave, so both run. A connection without a `userId` (an anonymous connection) has no durable row, so for it a disconnect is also a real leave on any channel. Use `unsubscribe` for cleanup when "the user left the group". Use `sessionEnd` for cleanup when "this socket is gone".
