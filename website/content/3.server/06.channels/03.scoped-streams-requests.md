Streams and requests can be scoped to a channel. They work the same as their top-level versions, but their context, addressing, and audience are bound to one channel instead of the whole socket. A channel-scoped stream broadcasts to that channel's members; a channel-scoped request asks one member (the current connection) or fans out to all of them.

This page covers what is **different** at the channel level. For the stream kinds themselves — plain, resumable, recorded, broadcast — see [Streams](/server/streams/overview). For the server-to-client request model, see [serverRequests](/server/capabilities/server-requests).

## Channel-scoped streams

Register a stream on the channel object with `channel.stream(...)`, `channel.resumableStream(...)`, or `channel.recordedStream(...)`. The config is identical to the top-level form; the difference is the `ctx`.

```typescript [room.ts]
import * as v from 'valibot'

const room = base.channel(['rooms', 'room:{id}'], {})

const handleRoomStream = room.stream('start-room-stream', {
  input: v.object({ count: v.number() }),
  chunk: t<{ index: number }>(),
  async *run(ctx, input) {
    // ctx.channel is bound to the room this stream was started in.
    for (let i = 0; i < input.count; i++) {
      yield { index: i }
      await new Promise((r) => setTimeout(r, 100))
    }
  },
})
```

`handleRoomStream` runs only when it is included in `base.assemble({ handlers: [...] })`. Passing `room` directly includes its config and lifecycle hooks, but not this stream.

Each stream method needs its capability listed: `stream()` for `channel.stream`, `resumableStream()` for `channel.resumableStream`, `recordedStream()` for `channel.recordedStream`. Using a method whose capability is missing throws a startup error naming the one to add.

### A channel broadcast stream

Set `broadcast: true` to fan one stream out to every member of the channel it was started in — not to the whole socket. The chunks reach only that channel's subscribers, and the connection that started the stream is excluded.

```typescript [room.ts]
const handleRoomBroadcast = room.stream('start-room-broadcast', {
  input: v.object({ count: v.number() }),
  chunk: t<{ index: number }>(),
  broadcast: true,
  async *run(_ctx, input) {
    for (let i = 0; i < input.count; i++) {
      yield { index: i }
      await new Promise((r) => setTimeout(r, 10))
    }
  },
})
```

This is the channel version of a top-level broadcast stream: top-level `broadcast: true` fans to the whole socket, channel `broadcast: true` fans to the channel's members. See [Broadcast Streams](/server/streams/broadcast) for the broadcast model.

## How channel ctx differs

Inside any channel handler — a stream, a request, an `on` handler — `ctx` carries `ctx.channel`, a handle bound to the exact channel the call came in on. Everything channel-scoped goes through it.

| On `ctx.channel`                             | What it does                                                                                                                                                         |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`                                       | The matched channel name (e.g. `'room:general'`).                                                                                                                    |
| `family`                                     | The family key (`'rooms'`), or `null` for a static channel.                                                                                                          |
| `params`                                     | The template captures, typed from the family pattern (`{ id: string }`). Empty for static channels.                                                                  |
| `send(event, payload, options?)`             | Send a channel event. Targets the current connection by default; pass `{ to }` to target a specific member instead. Returns the delivered socket count.              |
| `broadcast(event, payload, options?)`        | Fan a channel event out to the channel's members. Excludes the sender unless `{ includeSelf: true }`.                                                                |
| `members()`                                  | The connections currently in this channel, as `ConnectionInfo[]`.                                                                                                    |
| `subscribe(ref, payload?)`                   | Subscribe a connection to this channel from server code — runs `check` → `commit` → `onSubscribe`.                                                                   |
| `kick(target, opts)`                         | Remove a `UserRef`'s subscribed connections (or every socket matching a `TagRef`/`TagGroupHandle`). Pass `{ revoke: true }` to also drop the durable membership row. |
| `request(event, payload, options?)`          | A server→client request scoped to this channel. Targets the current connection by default; pass `{ to }` to ask a specific member. Needs `serverRequests()`.         |
| `broadcastRequest(event, payload, options?)` | A fan-out server→client request to the channel's members. Needs `serverRequests()`.                                                                                  |

The big difference from the top level: `ctx.channel.broadcast(...)` reaches only this channel's members, while top-level `ctx.broadcast(...)` reaches the whole socket. `ctx.channel.send(...)` and `ctx.channel.members()` are likewise scoped to this channel family — a `room:general` handler never sees `room:design`'s members.

```typescript [room.ts]
const handleSend = room.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    // Reaches only the members of the room this message came in on.
    ctx.channel.broadcast('room-message', {
      channel: ctx.channel.name,
      text: payload.text,
      from: ctx.meta.username,
    })
  },
})
```

::note
The `ctx.channel` handle is close to the handle you get from `ctx.channels.get(...)` outside a channel handler — `name`, `family`, `params`, `send`, `broadcast`, `members`, plus `broadcastRequest` when `serverRequests()` is listed. The one difference: `ctx.channel` also has `request` (it has a current connection to ask), while a handle from `ctx.channels.get(...)` does not — outside a channel handler there is no single member to target, so only the fan-out `broadcastRequest` is offered. The `ctx.channels` broadcast manager and its `get(...)` overloads are covered in [Context & Storage](/server/context-and-storage/overview).
::

## Targeting one member with `to`

`send` and `request` are channel-only — there is no top-level `to`. Top-level targeting goes through `ctx.connections.get(ref)` or `ctx.users.get(id)` instead (see [Connections](/server/context-and-storage/connections) and [Users](/server/context-and-storage/users)).

Omit `to` and the event goes to the current connection, exactly like before. Pass a `to` to reach someone else — always **intersected with channel membership**, so a recipient that is not currently subscribed to this channel gets nothing:

`ConnectionRef` and `UserRef` recipients must belong to the current server instance. Passing a ref from another instance is rejected with `CrossInstanceRef` before any local member is targeted; import it from `@wskit/server/errors`. Cross-instance routing needs a broker, which is not configured yet.

| `to`                        | Reaches                                                                                  |
| --------------------------- | ---------------------------------------------------------------------------------------- |
| _(omitted)_                 | The current connection — the member whose inbound event you are handling.                |
| `ConnectionRef`             | That one socket, if it is a member. Otherwise delivers to nobody.                        |
| `UserRef`                   | That user's member sockets — every tab/device they have subscribed to this channel.      |
| `TagRef` / `TagGroupHandle` | Members that **also** hold the tag — the intersection of channel membership and the tag. |

`send` returns the number of sockets it actually delivered to, so you can tell a no-op recipient (a `UserRef` for someone who left the channel, say) from a real delivery:

```typescript [notify-member.ts]
const handleNudgeUser = room.on('nudge-user', {
  input: v.object({ targetUserId: v.string() }),
  run(ctx, input) {
    const target = ctx.users.get(input.targetUserId).ref()
    const delivered = ctx.channel.send(
      'nudged',
      { from: ctx.user.id },
      { to: target },
    )
    ctx.send('nudge-result', { delivered }) // 0 if that user isn't a member here
  },
})
```

`request` works the same way — pass `to` to ask a specific member instead of the caller. When `to` matches more than one live socket (a `UserRef` with several tabs, or a `TagRef`/`TagGroupHandle`), the promise resolves to the **first valid answer**, and unlike `broadcastRequest` the result is the bare response — no `from`, since you already know who you asked:

```typescript [ask-member.ts]
const handleAskMember = room.on('ask-member', {
  input: v.object({ targetUserId: v.string() }),
  async run(ctx, input) {
    const target = ctx.users.get(input.targetUserId).ref()
    const answer = await ctx.channel.request(
      'volunteer',
      { turn: 1 },
      { to: target },
    )
    ctx.send('ask-result', { ready: answer.ready })
  },
})
```

## Channel-scoped requests

Declare server→client requests with `serverRequests(...)` in the channel's `capabilities`. Each entry pairs an `out` payload (what the server sends) with an `in` schema (what the client must answer). The root needs [`serverRequests()`](/server/capabilities/server-requests) to install the outbound runtime.

```typescript [lobby.ts]
import { serverRequests } from '@wskit/server/server-requests'
import * as v from 'valibot'

const lobby = base.channel('lobby', {
  capabilities: [
    serverRequests({
      volunteer: {
        out: t<{ turn: number }>(),
        in: v.object({ ready: v.boolean() }),
      },
    }),
  ],
})
```

A declaration is callable two ways — the verb you call decides targeted vs fan-out, not the declaration.

### `request` — ask the current member

`ctx.channel.request(event, payload, options?)` sends the request to **the current connection** — the member whose inbound event you are handling — and resolves to that member's typed answer. It is only available on `ctx.channel` inside a channel handler, where there is a current connection to ask; `ctx.channels.get(...)` exposes only `broadcastRequest`, never `request`.

```typescript [lobby.ts]
const handleAsk = lobby.on('ask-one', {
  input: v.object({ turn: v.number() }),
  async run(ctx, input) {
    // Asks the connection that sent 'ask-one'. Resolves to { ready: boolean }.
    const answer = await ctx.channel.request('volunteer', {
      turn: input.turn,
    })
    if (answer.ready) {
      // ...
    }
  },
})
```

Like the top-level `ctx.request`, this rejects with `timeout` if the member does not answer in time (default 10 000 ms) and with `disconnected` if that member drops before answering. Wrap it in a `try`/`catch` when either outcome matters.

### `broadcastRequest` — first answer wins

`ctx.channel.broadcastRequest(event, payload, options?)` fans the request out to every member of the channel and resolves with the **first valid answer** plus a ref to whoever sent it. The result is `{ response, from }` — `response` is the typed answer, `from` is a `ConnectionRef`. When called on `ctx.channel`, the calling connection is excluded by default; pass `{ includeSelf: true }` to ask it too.

```typescript [lobby.ts]
const handleTrigger = base.on('trigger', {
  input: v.object({ turn: v.number() }),
  async run(ctx, input) {
    const { response, from } = await ctx.channels
      .get(lobby)
      .broadcastRequest('volunteer', { turn: input.turn })

    ctx.send('outcome', {
      from: from.userId,
      ready: response.ready,
    })
  },
})
```

Pass a `timeout` to bound how long it waits. If nobody answers in time, the promise rejects — handle it:

```typescript [lobby.ts]
const handleTriggerTimeout = base.on('trigger-timeout', {
  input: v.object({ turn: v.number() }),
  async run(ctx, input) {
    try {
      const { response, from } = await ctx.channels
        .get(lobby)
        .broadcastRequest(
          'volunteer',
          { turn: input.turn },
          { timeout: 500 },
        )
      ctx.send('outcome', {
        from: from.userId,
        ready: response.ready,
      })
    } catch (error) {
      // Nobody volunteered before the timeout.
      const code = error instanceof Error ? error.message : 'unknown'
      ctx.send('error-outcome', { code })
    }
  },
})
```

`broadcastRequest` can be called both inside a channel handler (`ctx.channel.broadcastRequest(...)`) and from any handler through the manager (`ctx.channels.get(lobby).broadcastRequest(...)`). Both are typed to the channel's declared requests — calling an undeclared event is a compile error.

::tip
A channel request only reaches the channel's members. To send a server→client request to a connection that is not in a channel, use the top-level request surface — see [serverRequests](/server/capabilities/server-requests).
::

## Channel replay

A channel can opt into replay so reconnecting members refetch messages they missed. Two ways:

| Way             | How                                                                             | Needs                                     |
| --------------- | ------------------------------------------------------------------------------- | ----------------------------------------- |
| Built-in replay | Set `replay: true` in the channel config.                                       | `replay.history()` or `replay.snapshot()` |
| Custom replay   | Call `channel.replay({ replay, beforeSend, afterSend })` on the channel object. | `replay.custom()`                         |

Both are part of the broader replay model — the hook shapes, the wire metadata, and how a client requests missed messages live in [Replay](/server/replay/overview).
