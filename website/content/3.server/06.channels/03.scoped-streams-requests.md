Streams and requests can be **scoped** to a channel. This means they belong to one channel instead of the whole server. They work the same way as their top-level versions. The difference is their context (`ctx`), who they can address, and who receives them: all three are limited to one channel. A channel-scoped stream can send its chunks to that channel's members. A channel-scoped request asks one member (by default, the current connection) or sends the same question to all members.

This page covers only what is **different** at the channel level. For the stream kinds themselves (plain, cursor, recorded, and broadcast), see [Streams](/server/streams/overview). For how server-to-client requests work, see [serverRequests](/server/capabilities/server-requests).

The examples on this page use this server. It lists `channels()`, `stream()` and `serverRequests()`, and declares the top-level events that the handlers below send with `ctx.send`. The `upgrade` hook puts the username into `ctx.meta`:

```typescript [server/huddle.ts]
import { CloseCodes } from '@livething/core'
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { RejectUpgrade } from '@livething/server/errors'
import { serverRequests } from '@livething/server/server-requests'
import { recordedStream, stream } from '@livething/server/streams'

export const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    channels(),
    stream(),
    recordedStream(),
    serverRequests(),
    emits({
      'mention-result': t<{ delivered: number }>(),
      'ping-result': t<{ alive: boolean }>(),
      'room-check-result': t<{ from: string; alive: boolean }>(),
      'room-check-error': t<{ code: string }>(),
    }),
  ],
})
```

## Channel-scoped streams

Register a stream on the channel object with `channel.stream(...)`, `channel.cursorStream(...)`, or `channel.recordedStream(...)`. The config is the same as the top-level form. Only the `ctx` is different.

The `rooms` channel below also declares the events it sends (`emits`) and one server-to-client request (`ping-member`). Later sections on this page use them.

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { serverRequests } from '@livething/server/server-requests'
import * as v from 'valibot'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    emits({
      message: t<Message>(),
      mentioned: t<{ from: string }>(),
    }),
    serverRequests({
      'ping-member': {
        out: t<{}>(),
        in: v.object({ alive: v.boolean() }),
      },
    }),
  ],
})

const handleRoomSearch = rooms.stream('search-messages', {
  input: v.object({ query: v.string() }),
  chunk: t<{ hit: Message }>(),
  async *run(ctx, input) {
    // ctx.channel is bound to the room this stream was started in.
    for await (const hit of searchMessages(
      input.query,
      ctx.channel.params.roomId,
    )) {
      yield { hit }
    }
  },
})
```

`handleRoomSearch` runs only when you include it in `base.assemble({ handlers: [...] })`. If you pass the `rooms` object itself, `assemble` includes the channel's config and lifecycle hooks, but not this stream.

Each stream method needs its capability in the server's `capabilities` list: `stream()` for `channel.stream`, `cursorStream()` for `channel.cursorStream`, and `recordedStream()` for `channel.recordedStream`. If the capability is missing, the method throws an error when you call it. The error message names the capability to add.

### A channel broadcast stream

Set `broadcast: true` to send one stream's chunks to every member of the channel where it was started. Connections outside that channel do not receive them. The connection that started the stream (the **creator**) gets the chunks as its own stream, like any other stream. Every other member gets the same chunks as a broadcast.

Huddle's `ask-scout` is exactly this: one member asks the room's AI assistant, Scout, and its reply streams into the room for every member.

```typescript [server/scout.ts]
const handleAskScout = rooms.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ text: string }>(),
  broadcast: true,
  nudges: {
    stop: null,
    redirect: v.object({ instruction: v.string() }),
  },
  async *run(ctx, input) {
    const messages = [
      { role: 'user' as const, content: input.prompt },
    ]
    for await (const piece of llm.stream({
      messages,
      signal: ctx.stream.signal,
    })) {
      yield { text: piece }
    }
  },
})
```

This is the channel version of a top-level broadcast stream. A top-level `broadcast: true` stream sends to every connection on the server. A channel `broadcast: true` stream sends only to the channel's members. See [Broadcast Streams](/server/streams/broadcast) for how broadcast works.

## How channel ctx differs

Inside any channel handler (a stream, a request, or an `on` handler), `ctx` has `ctx.channel`. This is a **handle**: an object bound to the exact channel the call came in on. Everything scoped to the channel goes through it.

::field-group
::field{name="name" type="string"}
The matched channel name (for example `'room:general'`).
::
::field{name="family" type="string | null"}
The family key (`'rooms'`) for a dynamic channel. `null` for a static channel.
::
::field{name="params" type="Record<string, string>"}
The values captured from the family template, typed from the pattern (`{ id: string }`). An empty object for static channels.
::
::field{name="send" type="(event, payload) => number"}
Send a channel event to the current connection. Returns `1` when it is delivered and `0` when it is not.
::
::field{name="broadcastTo" type="(to, event, payload) => number"}
Send a channel event to selected members: a `ConnectionRef`, `UserRef`, `TagRef`, or `TagGroupHandle`. Returns the number of sockets it delivered to.
::
::field{name="broadcast" type="(event, payload, options?) => void"}
Send a channel event to all of the channel's members. Skips the calling connection unless you pass `{ includeSelf: true }`.
::
::field{name="members" type="() => ConnectionInfo[]"}
The connections in this channel right now, as `ConnectionInfo[]`.
::
::field{name="subscribe" type="(ref, payload?) => Promise<void>"}
Subscribe a connection to this channel from server code. Runs `check`, then `commit`, then the channel's `subscribe` hook.
::
::field{name="kick" type="(target, opts) => Promise<void>"}
Remove a `UserRef`'s connections from the channel (or every socket that matches a `TagRef` or `TagGroupHandle`). `opts` needs a `reason`. Add `revoke: true` to also delete the durable membership row.
::
::field{name="request" type="(event, payload, options?) => Promise<response>"}
A server-to-client request scoped to this channel. Asks the current connection by default. Pass `{ to }` to ask a specific member. Needs `serverRequests()`.
::
::field{name="broadcastRequest" type="(event, payload, options?) => Promise<{ response, from }>"}
A server-to-client request sent to all of the channel's members. Needs `serverRequests()`.
::
::

The main difference from the top level: `ctx.channel.broadcast(...)` reaches only this channel's members, while the top-level `ctx.broadcast(...)` reaches every connection on the server. `ctx.channel.send(...)`, `ctx.channel.broadcastTo(...)`, and `ctx.channel.members()` are also limited to this one channel. A `room:general` handler never sees the members of `room:design`.

```typescript [server/rooms.ts]
const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    // Reaches only the members of the room this message came in on.
    ctx.channel.broadcast('message', {
      id: newMessageId(),
      text: payload.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

::note
Outside a channel handler, `ctx.channels.get(...)` returns a similar handle. It has `name`, `family`, `params`, `send`, `broadcastTo`, `broadcast`, `members`, `subscribe`, and `kick`, plus `broadcastRequest` when `serverRequests()` is listed. There is one difference. `ctx.channel` also has `request`, because inside a channel handler there is a current connection to ask. A handle from `ctx.channels.get(...)` has no current member to ask, so it offers only `broadcastRequest`. For `ctx.channels` and the ways to call `get(...)`, see [Context & Storage](/server/context-and-storage/overview).
::

## Targeting channel members with `to`

`broadcastTo` and the `{ to }` option of `request` exist only on channel handles. The top-level `ctx` has no `to`. At the top level, you target connections with `ctx.connections.get(ref)` or `ctx.users.get(id)` instead (see [Connections](/server/context-and-storage/connections) and [Users](/server/context-and-storage/users)).

Use `ctx.channel.broadcastTo(to, event, payload)` to reach selected members. LiveThing always keeps only the targets that are also channel members. A recipient that is not subscribed to this channel right now gets nothing. `ctx.channel.send(event, payload)` still reaches only the current connection.

| `to`                        | Reaches                                                                                        |
| --------------------------- | ---------------------------------------------------------------------------------------------- |
| `ConnectionRef`             | That one socket, if it is a member. Otherwise nobody.                                          |
| `UserRef`                   | That user's sockets in this channel: every tab or device they have subscribed to this channel. |
| `TagRef` / `TagGroupHandle` | Only the members that **also** have the tag.                                                   |

A `ConnectionRef` or `UserRef` must belong to the current server instance (one running copy of your server). A ref from another instance makes the call throw a `CrossInstanceRef` error before anything is sent, because only the instance that owns a connection can address it. Import `CrossInstanceRef` from `@livething/server/errors`.

`broadcastTo` returns the number of sockets it delivered to. This lets you tell a real delivery from a call that reached nobody (for example, a `UserRef` for someone who left the channel):

```typescript [server/rooms.ts]
const handleMentionUser = rooms.on('mention-user', {
  input: v.object({ targetUserId: v.string() }),
  run(ctx, input) {
    const target = ctx.users.get(input.targetUserId).ref()
    const delivered = ctx.channel.broadcastTo(target, 'mentioned', {
      from: ctx.user.id,
    })
    ctx.send('mention-result', { delivered }) // 0 if that user is not a member here
  },
})
```

`request` also accepts `{ to }` to ask a specific member instead of the caller. The `to` target can match more than one live socket (a `UserRef` with several tabs, or a `TagRef` or `TagGroupHandle`). In that case the promise resolves to the **first valid answer**. Unlike `broadcastRequest`, the result is only the answer, with no `from`, because you already know who you asked:

```typescript [server/rooms.ts]
const handleCheckMember = rooms.on('check-member', {
  input: v.object({ targetUserId: v.string() }),
  async run(ctx, input) {
    const target = ctx.users.get(input.targetUserId).ref()
    const answer = await ctx.channel.request(
      'ping-member',
      {},
      { to: target },
    )
    ctx.send('ping-result', { alive: answer.alive })
  },
})
```

With `{ to }`, a socket that disconnects or sends an invalid answer is ignored, and the server keeps waiting for the others. If no valid answer arrives in time, or `to` matches no member, the promise rejects with `timeout`.

## Channel-scoped requests

Declare server-to-client requests with `serverRequests(...)` in the channel's `capabilities`. Each entry pairs an `out` payload (what the server sends) with an `in` schema (what the client must answer). The server's own `capabilities` must also list [`serverRequests()`](/server/capabilities/server-requests). If it does not, `base.channel(...)` throws an error.

```typescript [server/rooms.ts]
import { t } from '@livething/server'
import { serverRequests } from '@livething/server/server-requests'
import * as v from 'valibot'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    serverRequests({
      'ping-member': {
        out: t<{}>(),
        in: v.object({ alive: v.boolean() }),
      },
    }),
  ],
})
```

You can call each declared request in two ways. The method you call decides whether it asks one member or all members. The declaration does not decide this.

### `request`: ask the current member

`ctx.channel.request(event, payload, options?)` sends the request to **the current connection** (the member whose incoming event you are handling). It resolves to that member's typed answer. It exists only on `ctx.channel` inside a channel handler, where there is a current connection to ask. `ctx.channels.get(...)` has only `broadcastRequest`, never `request`.

```typescript [server/rooms.ts]
const handlePingMember = rooms.on('ping-one', {
  input: v.object({}),
  async run(ctx) {
    // Asks the connection that sent 'ping-one'. Resolves to { alive: boolean }.
    const answer = await ctx.channel.request('ping-member', {})
    if (answer.alive) {
      // ...
    }
  },
})
```

Like the top-level `ctx.request`, this rejects with `timeout` if the member does not answer in time (10 000 ms by default; pass `{ timeout }` in milliseconds to change it). It rejects with `disconnected` if that member disconnects before it answers. Use `try`/`catch` when you need to handle either case. For the full list of errors, see [serverRequests](/server/capabilities/server-requests).

### `broadcastRequest`: the first answer wins

`ctx.channel.broadcastRequest(event, payload, options?)` sends the request to every member of the channel. It resolves with the **first valid answer** and a ref to the member who sent it. The result is `{ response, from }`: `response` is the typed answer, and `from` is a `ConnectionRef`. On `ctx.channel`, the calling connection is not asked by default. Pass `{ includeSelf: true }` to ask it too. A handle from `ctx.channels.get(...)` has no calling member, so it asks every member.

```typescript [server/rooms.ts]
const handleCheckRoom = base.on('check-room', {
  input: v.object({ roomId: v.string() }),
  async run(ctx, input) {
    const { response, from } = await ctx.channels
      .get(rooms.at({ roomId: input.roomId }))
      .broadcastRequest('ping-member', {})

    ctx.send('room-check-result', {
      from: from.userId,
      alive: response.alive,
    })
  },
})
```

Pass a `timeout` (in milliseconds) to limit how long it waits. If nobody answers in time, the promise rejects with a `timeout` error, so catch it:

```typescript [server/rooms.ts]
import { LiveThingError } from '@livething/server/errors'

const handleCheckRoomTimeout = base.on('check-room-timeout', {
  input: v.object({ roomId: v.string() }),
  async run(ctx, input) {
    try {
      const { response, from } = await ctx.channels
        .get(rooms.at({ roomId: input.roomId }))
        .broadcastRequest('ping-member', {}, { timeout: 500 })
      ctx.send('room-check-result', {
        from: from.userId,
        alive: response.alive,
      })
    } catch (error) {
      // Nobody in the room answered before the timeout.
      const code =
        error instanceof LiveThingError ? error.code : 'unknown'
      ctx.send('room-check-error', { code })
    }
  },
})
```

You can call `broadcastRequest` inside a channel handler (`ctx.channel.broadcastRequest(...)`) and from any handler through `ctx.channels` (`ctx.channels.get(rooms.at({ roomId })).broadcastRequest(...)`). Both are typed from the channel's declared requests. Calling an event the channel does not declare is a compile error.

::tip
A channel request reaches only the channel's members. To send a server-to-client request to a connection that is not in a channel, use the top-level request methods. See [serverRequests](/server/capabilities/server-requests).
::

## Channel replay

**Replay** lets members that reconnect get back the messages they missed while they were away. A channel can turn it on in two ways:

| Way             | How                                                                                       | Needs                                     |
| --------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------- |
| Built-in replay | Set `replay: true` in the channel config.                                                 | `replay.history()` or `replay.snapshot()` |
| Custom replay   | Call `channel.replay({ replay, beforeBroadcast, afterBroadcast })` on the channel object. | `replay.custom()`                         |

Both follow the general replay model. For the hook shapes, the extra data on each message, and how a client asks for missed messages, see [Replay](/server/replay/overview).
