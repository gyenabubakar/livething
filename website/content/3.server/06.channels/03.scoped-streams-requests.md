Streams and requests can be **scoped** to a channel. This means they belong to one channel instead of the whole server. They work the same way as their top-level versions. The difference is their context (`ctx`), who they can address, and who receives them: all three are limited to one channel. A channel-scoped stream can send its chunks to that channel's members. A channel-scoped request asks one member: by default, the current connection.

This page covers only what is **different** at the channel level. For the stream kinds themselves (plain, recorded, and broadcast), see [Streams](/server/streams/overview). For how server-to-client requests work, see [serverRequests](/server/capabilities/server-requests).

The examples on this page use this server. It lists `channels()`, `stream()` and `serverRequests()`, and declares the top-level events that the handlers below send with `ctx.send`. The `upgrade` hook puts the username into `ctx.meta`. The `rooms` channel declares the events it sends (`emits`) and one server-to-client request (`ping-member`). Huddle's own `rooms` emits `message`, `reaction` and `typing`, and has no `mentioned` event and no `ping-member`, so this is a different `rooms` made for the examples. Later sections on this page use them:

```typescript [server/scoped-rooms.ts]
import { CloseCodes } from '@livething/core'
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { RejectUpgrade } from '@livething/server/errors'
import { serverRequests } from '@livething/server/server-requests'
import { recordedStream, stream } from '@livething/server/streams'
import * as v from 'valibot'
import { verifySession } from './auth'
import { Message } from './base'

export const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    channels(),
    stream(),
    recordedStream(),
    serverRequests(),
    emits({
      'mention-result': t<{ delivered: number }>(),
      'ping-result': t<{ alive: boolean }>(),
    }),
  ],
})

export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    emits({
      message: t<Message>(),
      mentioned: t<{ from: string }>(),
    }),
    serverRequests({
      'ping-member': {
        out: t<null>(),
        in: v.object({ alive: v.boolean() }),
      },
    }),
  ],
})
```

## Channel-scoped streams

Register a stream on the channel object with `channel.stream(...)` or `channel.recordedStream(...)`. The config is the same as the top-level form. Only the `ctx` is different.

This stream searches only the room it was started in. Huddle's own `search-messages` is a top-level stream that searches all messages.

```typescript [server/rooms.ts]
import { t } from '@livething/server'
import * as v from 'valibot'
import { Message } from './base'
import { searchRoomMessages } from './helpers'
import { rooms } from './scoped-rooms'

const handleRoomSearch = rooms.stream('search-messages', {
  input: v.object({ query: v.string() }),
  chunk: t<{ hit: Message }>(),
  async *run(ctx, input) {
    // ctx.channel is bound to the room this stream was started in.
    for await (const hit of searchRoomMessages(
      ctx.channel.params.roomId,
      input.query,
    )) {
      yield { hit }
    }
  },
})
```

`handleRoomSearch` runs only when you include it in `base.assemble({ handlers: [...] })`. If you pass the `rooms` object itself, `assemble` turns on the channel's config and hooks, but not this stream.

Each stream method needs its capability in the server's `capabilities` list: `stream()` for `channel.stream` and `recordedStream()` for `channel.recordedStream`. If the capability is missing, the method throws an error when you call it. The error message names the capability to add.

### A channel broadcast stream

Set `broadcast: true` to send one stream's chunks to every member of the channel where it was started. Connections outside that channel do not receive them. The connection that started the stream (the **creator**) gets the chunks as its own stream, like any other stream. Every other member gets the same chunks as a broadcast.

Huddle's `ask-scout` is this stream: one member asks the room's AI assistant, Scout, and its reply streams into the room for every member. Huddle's version also reads `stop` and `redirect` nudges. This one leaves them out.

```typescript [server/scout.ts]
import { t } from '@livething/server'
import * as v from 'valibot'
import { llm } from './llm'
import { rooms } from './scoped-rooms'

const handleAskScout = rooms.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ text: string }>(),
  broadcast: true,
  async *run(ctx, input) {
    const messages = [{ role: 'user', text: input.prompt }]
    for await (const piece of llm.stream({
      messages,
      signal: ctx.stream.signal,
    })) {
      yield { text: piece }
    }
  },
})
```

This is the channel version of a top-level broadcast stream. A top-level `broadcast: true` stream sends to every connection on the server. A channel `broadcast: true` stream sends only to the channel's members. See [Broadcast Streams](/server/streams/broadcast) for how broadcast works.

## How channel ctx differs

Inside any channel handler (a stream, a request, or an `on` handler), `ctx` has `ctx.channel`. This is a **handle**: an object bound to the exact channel the call came in on. Everything scoped to the channel goes through it.

::field-group
::field{name="name" type="string"}
The matched channel name (for example `'room:general'`).
::
::field{name="family" type="string | null"}
The family key (`'rooms'`) for a dynamic channel. `null` for a static channel.
::
::field{name="params" type="Record<string, string>"}
The values captured from the family template, typed from the pattern (`{ roomId: string }`). An empty object for static channels.
::
::field{name="send" type="(event, payload) => number"}
Send a channel event to the current connection. Returns `1` when it is delivered and `0` when it is not.
::
::field{name="broadcastTo" type="(to, event, payload) => number"}
Send a channel event to selected members: a `ConnectionRef`, `UserRef`, `TagRef`, or `TagGroupHandle`. Returns the number of sockets it delivered to.
::
::field{name="broadcast" type="(event, payload, options?) => void"}
Send a channel event to all of the channel's members. Skips the calling connection unless you pass `{ includeSelf: true }`.
::
::field{name="members" type="() => ConnectionInfo[]"}
The connections in this channel right now, as `ConnectionInfo[]`.
::
::field{name="subscribe" type="(ref, payload?) => Promise<void>"}
Subscribe a connection to this channel from server code. Runs `check`, then `commit`, then the channel's `onSubscribe` hook.
::
::field{name="kick" type="(target, opts) => Promise<void>"}
Remove a `UserRef`'s connections from the channel (or every socket that matches a `TagRef` or `TagGroupHandle`). `opts` needs a `reason`. The kick also deletes the durable membership row, so the user does not rejoin on reconnect.
::
::field{name="request" type="(event, payload, options?) => Promise<response>"}
A server-to-client request scoped to this channel. Asks the current connection by default. Pass `{ to }` with a `ConnectionRef` to ask one other member. Needs `serverRequests()`.
::
::

The main difference from the top level: `ctx.channel.broadcast(...)` reaches only this channel's members, while the top-level `ctx.broadcast(...)` reaches every connection on the server. `ctx.channel.send(...)`, `ctx.channel.broadcastTo(...)`, and `ctx.channel.members()` are also limited to this one channel. A `room:general` handler never sees the members of `room:design`.

```typescript [server/rooms.ts]
import * as v from 'valibot'
import { rooms } from './scoped-rooms'

const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    // Reaches only the members of the room this message came in on.
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: payload.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

::note
Outside a channel handler, `ctx.channels.get(...)` returns a similar handle. It has `name`, `family`, `params`, `send`, `broadcastTo`, `broadcast`, `members`, `subscribe`, and `kick`. There is one difference. `ctx.channel` also has `request`, because inside a channel handler there is a current connection to ask. A handle from `ctx.channels.get(...)` has no current member to ask, so it has no `request`. For `ctx.channels` and the ways to call `get(...)`, see [Context & Storage](/server/context-and-storage/overview).
::

## Targeting channel members with `to`

`broadcastTo` and the `{ to }` option of `request` exist only on channel handles. The top-level `ctx` has no `to`. At the top level, you target connections with `ctx.connections.get(ref)` or `ctx.users.get(id)` instead (see [Connections](/server/context-and-storage/connections) and [Users](/server/context-and-storage/users)).

Use `ctx.channel.broadcastTo(to, event, payload)` to reach selected members. LiveThing always keeps only the targets that are also channel members. A recipient that is not subscribed to this channel right now gets nothing. `ctx.channel.send(event, payload)` still reaches only the current connection.

| `to`                        | Reaches                                                                                        |
| --------------------------- | ---------------------------------------------------------------------------------------------- |
| `ConnectionRef`             | That one socket, if it is a member. Otherwise nobody.                                          |
| `UserRef`                   | That user's sockets in this channel: every tab or device they have subscribed to this channel. |
| `TagRef` / `TagGroupHandle` | Only the members that **also** have the tag.                                                   |

A `ConnectionRef` or `UserRef` must belong to the current server instance (one running copy of your server). A ref from another instance makes the call throw a `CrossInstanceRef` error before anything is sent, because only the instance that owns a connection can address it. Import `CrossInstanceRef` from `@livething/server/errors`.

`broadcastTo` returns the number of sockets it delivered to. This lets you tell a real delivery from a call that reached nobody (for example, a `UserRef` for someone who left the channel):

```typescript [server/rooms.ts]
import * as v from 'valibot'
import { rooms } from './scoped-rooms'

const handleMentionUser = rooms.on('mention-user', {
  input: v.object({ targetUserId: v.string() }),
  run(ctx, input) {
    const target = ctx.users.get(input.targetUserId).ref()
    const delivered = ctx.channel.broadcastTo(target, 'mentioned', {
      from: ctx.user.id,
    })
    ctx.send('mention-result', { delivered }) // 0 if that user is not a member here
  },
})
```

When `to` matches more than one socket, `broadcastTo` still sends **one** frame: every selected member gets the same payload and the same delivery metadata, and the [`onOutgoing`](/server/lifecycle-and-intercept/outgoing) hook sees the send once. A payload that is not a JSON object, or an event that the channel does not declare, throws before anything is sent. A failure to write to one socket is logged and not thrown, and the other selected sockets still get the frame.

`request` also accepts `{ to }` to ask one other member instead of the caller. `to` is a `ConnectionRef`, because a request waits for one answer from one socket. If the `to` connection is not a member of this channel when you call `request`, the promise rejects with `not-a-member` (`NotAMember` from `@livething/server/errors`) at once, without sending anything. A member can leave between `members()` and `request(...)`, so catch it. This error stays on the server and is never sent to the client:

```typescript [server/rooms.ts]
import { NotAMember } from '@livething/server/errors'
import * as v from 'valibot'
import { rooms } from './scoped-rooms'

const handleCheckMember = rooms.on('check-member', {
  input: v.object({ targetUserId: v.string() }),
  async run(ctx, input) {
    const member = ctx.channel
      .members()
      .find((info) => info.userId === input.targetUserId)
    if (!member) {
      ctx.send('ping-result', { alive: false })
      return
    }
    try {
      const answer = await ctx.channel.request('ping-member', null, {
        to: member.ref(),
      })
      ctx.send('ping-result', { alive: answer.alive })
    } catch (err) {
      if (!NotAMember.matches(err)) throw err
      ctx.send('ping-result', { alive: false }) // left the room before we asked
    }
  },
})
```

To ask every tab of one user, use `ctx.users.get(id).request(...)` (see [serverRequests](/server/capabilities/server-requests#ask-a-user)).

## Channel-scoped requests

Declare server-to-client requests with `serverRequests(...)` in the channel's `capabilities`. Each entry pairs an `out` payload (what the server sends) with an `in` schema (what the client must answer). The server's own `capabilities` must also list [`serverRequests()`](/server/capabilities/server-requests). If it does not, `base.channel(...)` throws an error.

```typescript [server/rooms.ts]
import { t } from '@livething/server'
import { serverRequests } from '@livething/server/server-requests'
import * as v from 'valibot'
import { base } from './scoped-rooms'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    serverRequests({
      'ping-member': {
        out: t<null>(),
        in: v.object({ alive: v.boolean() }),
      },
    }),
  ],
})
```

### `request`: ask the current member

`ctx.channel.request(event, payload, options?)` sends the request to **the current connection** (the member whose incoming event you are handling). It resolves to that member's typed answer. It exists only on `ctx.channel` inside a channel handler, where there is a current connection to ask. A handle from `ctx.channels.get(...)` has no `request`.

```typescript [server/rooms.ts]
import * as v from 'valibot'
import { rooms } from './scoped-rooms'

const handlePingMember = rooms.on('ping-one', {
  input: v.object({}),
  async run(ctx) {
    // Asks the connection that sent 'ping-one'. Resolves to { alive: boolean }.
    const answer = await ctx.channel.request('ping-member', null)
    ctx.send('ping-result', { alive: answer.alive })
  },
})
```

Like the top-level `ctx.request`, this rejects with `timeout` if the member does not answer in time (10 000 ms by default; pass `{ timeout }` in milliseconds to change it). It rejects with `disconnected` if that member disconnects before it answers. Use `try`/`catch` when you need to handle either case. For the full list of errors, see [serverRequests](/server/capabilities/server-requests).

`ctx.channel.request` is typed from the channel's declared requests. Calling an event the channel does not declare is a compile error.

::tip
A channel request reaches only the channel's members. To send a server-to-client request to a connection that is not in a channel, use the top-level request methods. See [serverRequests](/server/capabilities/server-requests).
::

## Binary streams and requests

A channel has the binary versions too, when [`binary()`](/server/capabilities/binary) is listed at the root: `rooms.binary.request(...)` (with `clientRequests()`), `rooms.binary.stream(...)` (with `stream()`), and `ctx.channel.binary.request(...)` for the binary server requests the channel lists in its own `binary({ serverRequests })` (with `serverRequests()` at the root). They follow the same rules as on this page: only members can use them, and `ctx.channel.binary.request` takes `{ to }` to ask one other member. See [binary](/server/capabilities/binary).

## Channel replay

**Replay** lets members that reconnect get back the messages they missed while they were away. To give a channel its own replay store, set `replay: true` in the channel config. This needs `replay.history()` or `replay.snapshot()` in the server's `capabilities`. Set `replay: false` to turn replay off for the channel.

Channel replay follows the general replay model. For the extra data on each message, and how a client asks for missed messages, see [Replay](/server/replay/overview).
