You declare a channel with `base.channel(...)`. The call takes a **pattern** (the channel's name or family template) and a **config object** (its events, gate, and flags), and returns a channel object whose methods register handlers.

```typescript [chat.ts]
import { define, emits, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'

const base = define({
  capabilities: [channels()],
})

const lobby = base.channel('lobby', {
  capabilities: [
    emits({ message: t<{ text: string; from: string }>() }),
  ],
})
```

## The pattern

The first argument names the channel. It is either a string or a `[familyKey, template]` tuple.

```typescript [patterns.ts]
// Static channel — one fixed name.
const lobby = base.channel('lobby', {
  /* ... */
})

// Family — one template that matches many names.
const rooms = base.channel(['rooms', 'room:{id}'], {
  /* ... */
})
```

An empty string (or an empty family key) throws when the channel is declared. Families have their own page — see [Dynamic Families](/server/channels/dynamic-families) for the template grammar and isolation rules. The rest of this page works with a static channel; everything except the pattern shape applies to both.

::note
A family is always declared with the `[familyKey, template]` tuple. The tuple is the only pattern shape `base.channel(...)` accepts — a string for a static channel, or a tuple for a family.
::

## The config object

Every field is optional except as noted. Here is the full shape, then each field in turn.

| Field                                 | Type                          | Purpose                                                                                                          |
| ------------------------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `capabilities: [emits(...)]`          | event map                     | Events the channel sends to its members.                                                                         |
| `capabilities: [serverRequests(...)]` | request map                   | Server→client requests scoped to members. Needs root [`serverRequests()`](/server/capabilities/server-requests). |
| `subscribe`                           | a schema                      | Validates the payload a client sends when subscribing.                                                           |
| `check`                               | `(ctx, payload) => result`    | Async auth gate. Throw to reject.                                                                                |
| `commit`                              | `(ctx, checkResult) => void`  | Sync gate, run as membership is written. Throw to reject.                                                        |
| `revalidate`                          | `(ctx) => void`               | Re-checks a durable membership on auto-rejoin. Needs a persistent channel.                                       |
| `membership`                          | `'persistent' \| 'ephemeral'` | Whether membership survives a reconnect. Defaults to `'persistent'`.                                             |
| `replay`                              | `boolean`                     | Per-channel replay opt-in. Needs a built-in [replay](/server/replay/overview) capability.                        |
| `capabilities`                        | array                         | This channel's `emits(...)`, `serverRequests(...)`, and channel-only capabilities.                               |
| `rateLimit`                           | `RateLimitConfig`             | A rate-limit rule for this channel's incoming events.                                                            |

### `emits(...)` — the channel's events

`emits(...)` lists the events the channel pushes to its members. Each value is a `t<Payload>()` call that types the payload. These become the events `ctx.channel.send(...)`, `ctx.channel.broadcastTo(...)`, and `ctx.channel.broadcast(...)` accept.

```typescript [room.ts]
const room = base.channel('room', {
  capabilities: [
    emits({
      'room-message': t<{
        text: string
        from: string
        kind: string
      }>(),
      'name-result': t<{ name: string; suffix: string }>(),
    }),
  ],
})
```

A channel with no events is legal — omit `emits(...)`. You might do this for a channel that only carries [scoped requests](/server/channels/scoped-streams-requests) or only tracks presence.

### `serverRequests(...)` — server→client requests

`serverRequests(...)` declares server-initiated requests scoped to this channel's members. Each entry pairs an `out` payload (what the server sends) with an `in` schema (what the client must answer). List bare `serverRequests()` at the root too, so it can install the shared outbound runtime.

```typescript [lobby.ts]
import { serverRequests } from '@wskit/server/server-requests'
import * as v from 'valibot'

const lobby = base.channel('lobby', {
  capabilities: [
    serverRequests({
      volunteer: {
        out: t<{ turn: number }>(),
        in: v.object({ ready: v.boolean() }),
      },
    }),
  ],
})
```

The full story of channel-scoped requests — `ctx.channel.request` vs `ctx.channel.broadcastRequest` — is on the [Scoped Streams & Requests](/server/channels/scoped-streams-requests) page.

### `subscribe`, `check`, `commit`, `revalidate` — the gate

`subscribe` is the schema for the payload a client sends when joining. `check` and `commit` decide whether the join is allowed; `revalidate` re-checks a durable membership on reconnect. These get their own page — see [Auth Gate](/server/channels/auth-gate).

### `membership` — durable membership for one channel

Every channel's membership is durable by default, at no capability cost: a member that drops is auto-rejoined on reconnect. Set `membership: 'ephemeral'` on a single channel to opt it out — a drop is then a full leave. Write `membership: 'persistent'` only when you want to be explicit; it changes nothing, since that is already the default.

```typescript [rooms.ts]
const archive = base.channel('archive', {
  capabilities: [emits({ entry: t<{ line: string }>() })],
  // membership omitted — members are auto-rejoined after a reconnect
})

const presence = base.channel('presence', {
  capabilities: [emits({ ping: t<{ at: number }>() })],
  membership: 'ephemeral', // a drop is a full leave
})
```

A member only gets a durable row when its connection carries a `userId` — set on `upgrade`. An anonymous connection (no `userId`) stays in the channel only for the live socket, on any channel, durable or not — there is no stable id to auto-rejoin against.

### `replay` — per-channel replay

`replay: true` opts a channel into the built-in replay capability so reconnecting members can fetch messages they missed. This needs `replay.history()` or `replay.snapshot()` listed — setting `replay` without one throws at startup. For custom replay, use the `replay(...)` method (below) instead. See [Replay](/server/replay/overview) for the full model.

### `rateLimit` — limit incoming events

`rateLimit` sets a rate-limit rule for the events members send to this channel. It uses the same `RateLimitConfig` shape as the top-level [`rateLimit()`](/server/capabilities/rate-limit) capability.

```typescript [room.ts]
const room = base.channel('room', {
  capabilities: [emits({ 'room-message': t<{ text: string }>() })],
  rateLimit: { enabled: true, max: 30 },
})
```

Individual channel handlers can override this — pass `rateLimit` in a handler's own config.

## Naming patterns

A static channel name is any non-empty string. Common shapes:

```typescript [names.ts]
base.channel('lobby', {
  /* ... */
}) // a single global room
base.channel('notifications', {
  /* ... */
}) // a per-feature channel
base.channel('room2', {
  /* ... */
}) // numbered rooms
```

For anything where the name varies at runtime — a room per ID, a thread per pair of IDs — reach for a family instead of declaring one static channel per value. A family is one declaration that matches them all:

```typescript [names.ts]
base.channel(['rooms', 'room:{id}'], {
  /* ... */
}) // room:general, room:design
base.channel(['threads', 'org:{org}/thread:{tid}'], {
  /* */
}) // two captures
```

See [Dynamic Families](/server/channels/dynamic-families) for the template grammar.

::note
A channel name (static name or family key) follows the same reserved-character rules as an event name: it cannot start with `@` or `#` (reserved for `ctx.matches(...)` path keys) or contain `::` (the path key separator). A static channel name has a 256-character wire limit; a family key has a 128-character limit. A bad name throws when `define(...)` compiles your server, not at connect time.
::

## Handler methods on the channel object

`base.channel(...)` returns an object with two groups of methods: **event handlers** that return a value you pass to `assemble(...)` to activate, and **lifecycle hooks** that register a callback and return nothing.

### Event handlers

These mirror the top-level `base.on` / `base.request` / `base.stream`, but the `ctx` they receive carries `ctx.channel`, scoped to this channel.

```typescript [room.ts]
import * as v from 'valibot'

// base.on equivalent — handle an event a member sends.
const handleSend = room.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('room-message', {
      text: payload.text,
      from: ctx.meta.username,
      kind: 'user',
    })
  },
})

// A channel-scoped stream (needs the matching stream capability).
const handleFeed = room.stream('start-channel-stream', {
  input: v.object({ count: v.number() }),
  chunk: t<{ index: number }>(),
  async *run(_ctx, payload) {
    for (let i = 0; i < payload.count; i++) yield { index: i }
  },
})
```

Pass `handleSend` and `handleFeed` to `base.assemble({ handlers: [...] })`. Passing `room` alone keeps its config and lifecycle hooks, but activates neither route.

| Method                           | Mirrors                | Notes                                                                    |
| -------------------------------- | ---------------------- | ------------------------------------------------------------------------ |
| `on(event, config)`              | `base.on`              | Handle an event a member sends.                                          |
| `request(event, config)`         | `base.request`         | A client→server request scoped to the channel. Needs `clientRequests()`. |
| `stream(event, config)`          | `base.stream`          | A plain stream. Needs `stream()`.                                        |
| `resumableStream(event, config)` | `base.resumableStream` | A durable resumable stream. Needs `resumableStream()`.                   |
| `recordedStream(event, config)`  | `base.recordedStream`  | A recorded stream. Needs `recordedStream()`.                             |

Using `request` or any stream method without its capability listed throws a clear startup error naming the capability to add. The stream kinds themselves are covered in [Streams](/server/streams/overview); the channel-scoped differences are on the [Scoped Streams & Requests](/server/channels/scoped-streams-requests) page.

### Lifecycle hooks

These register a callback for a membership change and return `void`. Each one can be attached at most once per channel — a second call throws.

```typescript [room.ts]
room.subscribe((ctx) => {
  // After a member joins — push initial state or announce them.
  ctx.channel.broadcast('room-message', {
    text: `${ctx.meta.username} entered`,
    from: 'system',
    kind: 'system',
  })
})

room.unsubscribe((ctx) => {
  // On a true leave — announce the departure.
  ctx.channel.broadcast('room-message', {
    text: `${ctx.meta.username} left`,
    from: 'system',
    kind: 'system',
  })
})

room.sessionEnd((ctx) => {
  // On any session end — a true leave OR a plain disconnect.
})
```

| Hook                   | Fires on                                                                                                        |
| ---------------------- | --------------------------------------------------------------------------------------------------------------- |
| `subscribe(handler)`   | After a first subscribe is confirmed. Not on auto-rejoin.                                                       |
| `unsubscribe(handler)` | A true leave only — `__unsubscribe__` or `kick`. Not on a plain disconnect of a persistent channel.             |
| `sessionEnd(handler)`  | Any time this connection's view of the channel ends — a true leave OR a plain disconnect.                       |
| `intercept(handler)`   | An incoming frame for this channel, before routing. See [Intercept](/server/lifecycle-and-intercept/intercept). |
| `replay(hooks)`        | Custom replay for this channel. Needs `replay.custom()`. See [Replay](/server/replay/overview).                 |

::note
The split between `unsubscribe` and `sessionEnd` matters most for persistent channels. There, a plain disconnect keeps the durable membership (the user is still "in" the room and will be auto-rejoined), so it fires `sessionEnd` but not `unsubscribe`. On an ephemeral channel a disconnect is a true leave, so both fire. The [Auth Gate](/server/channels/auth-gate) page covers the leave paths in detail.
::

## Assembling channels

Pass each channel handler's return value to `assemble(...)`, the same as top-level handlers. This includes `channel.request(...)` and every stream method — they return a handler value too, exactly like `channel.on(...)`. Passing the channel object directly includes its configuration and lifecycle behavior, but activates no routed handlers. Use that form for a channel with no handlers, or when its handlers are intentionally inactive.

```typescript [chat.ts]
// A channel with handlers: pass the handler values.
const handleSend = room.on('send-message', {
  /* ... */
})

// A channel with no handlers: pass the channel object itself.
const protoProbe = base.channel(['proto', 'proto:{id}'], {
  /* ... */
})

export const handler = base.assemble({
  handlers: [handleSend, protoProbe],
})
```

Each handler value carries a reference back to its channel, so `assemble` builds the channel once no matter how many of its handlers you list.
