You declare a channel with `base.channel(...)`. The call takes a **pattern** and an optional **config object**. It returns a channel object. You call methods on this object to create handlers, and pass them to `assemble()`. [A group of handlers](/server/handlers/overview#grouping-handlers) can live in a list, such as `roomHandlers`, that you spread in `assemble()`.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'

const base = server({
  capabilities: [channels()],
})

const announcements = base.channel('announcements', {
  capabilities: [emits({ announcement: t<{ text: string }>() })],
})
```

## The pattern

The first argument names the channel. It is either a string or a `[familyKey, template]` tuple.

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { base, Message } from './base'

// Static channel: one fixed name.
const announcements = base.channel('announcements', {
  capabilities: [emits({ announcement: t<{ text: string }>() })],
})

// Family: one template that matches many names.
const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
})
```

An empty name is an error. An empty family key throws when you declare the channel, and an empty static name throws when you call `assemble(...)`. Families have their own page: see [Dynamic Families](/server/channels/dynamic-families) for the template rules and how rooms in a family stay separate. The rest of this page uses `rooms`, a family, as its running example. Everything except the pattern works the same way for a static channel too.

::note
You always declare a family with the `[familyKey, template]` tuple. `base.channel(...)` accepts only two pattern shapes: a string for a static channel, or a tuple for a family.
::

## The config object

Every field is optional. Here is the full shape. Each field is described after the list. Huddle's own `rooms` has only `emits(...)`. Where an example below gives `rooms` more, it is only to show that field.

::field-group
::field{name="capabilities: [emits(...)]" type="emits({ event: t<Payload>() })"}
Events the channel sends to its members.
::
::field{name="capabilities: [serverRequests(...)]" type="serverRequests({ name: { out, in } })"}
Server→client requests sent to members of this channel. Needs [`serverRequests()`](/server/capabilities/server-requests) at the top level.
::
::field{name="capabilities: [binary({ emits, serverRequests })]" type="binary({ emits: { event: t<Info>() }, serverRequests: { event: { out, in } } })"}
Binary events the channel sends to its members, through `ctx.channel.binary`, and binary server requests it sends with `ctx.channel.binary.request`. Its binary handlers come from `rooms.binary.on(...)`, `rooms.binary.request(...)`, `rooms.binary.stream(...)` and `rooms.binary.recordedStream(...)`. Needs [`binary()`](/server/binary/overview) at the top level (and `serverRequests()` there for its `serverRequests`). With `inbox()`, each member gets a stored copy of each binary event too.
::
::field{name="subscribe" type="StandardSchemaV1"}
Validates the payload a client sends when it subscribes. Any [Standard Schema](https://standardschema.dev) library works, such as Valibot or Zod. A client that subscribes with no data sends `null`, so a schema whose fields are all optional must also accept `null` (for example `v.nullable(v.object({...}))`). Without a schema, `check` gets `null` as its input.
::
::field{name="check" type="(ctx, payload) => result"}
Auth gate. It can be async. Throw to reject.
::
::field{name="commit" type="(ctx, checkResult) => void"}
Sync gate that runs when the membership is written. Throw to reject.
::
::field{name="revalidate" type="(ctx) => void"}
Checks a stored membership again on auto-rejoin. Needs a persistent channel.
::
::field{name="membership" type="'persistent' | 'ephemeral'"}
Whether membership survives a reconnect. The default is `'ephemeral'`.
::
::field{name="replay" type="boolean"}
Turns replay on or off for this channel. Needs a [replay](/server/replay/overview) capability.
::
::field{name="capabilities" type="[emits(...), serverRequests(...), binary(...), inbox(), readReceipts()]"}
This channel's `emits(...)`, `serverRequests(...)`, `binary({ emits })`, and channel-only capabilities.
::
::field{name="onSubscribe / onUnsubscribe / onSessionEnd" type="(ctx) => void"}
[Lifecycle hooks](#lifecycle-hooks) that run when membership changes.
::
::field{name="intercept" type="(ctx, frame) => unknown | void"}
[Sees every incoming frame](/server/lifecycle-and-intercept/intercept) for this channel before LiveThing routes it.
::
::field{name="rateLimit" type="RateLimitConfig"}
A rate-limit rule for the events members send in this channel, or `false` to turn the limit off here. Needs the `rateLimit()` capability.
::
::

### `emits(...)`: the channel's events

`emits(...)` lists the events the channel sends to its members. Each value is a `t<Payload>()` call that sets the payload type. These are the events that `ctx.channel.send(...)`, `ctx.channel.broadcastTo(...)`, and `ctx.channel.broadcast(...)` accept.

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { base, Message } from './base'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    emits({
      message: t<Message>(),
      typing: t<{ from: string }>(),
    }),
  ],
})
```

A channel with no events is valid. Leave out `emits(...)`. For example, a channel can carry only [channel requests](/server/channels/scoped-streams-requests), or only track presence.

### `serverRequests(...)`: server→client requests

`serverRequests(...)` declares requests that the server sends to the members of this channel. Each entry has an `out` schema for what the server sends and an `in` schema for the answer the client sends back. Also list plain `serverRequests()` in the top-level `server({ capabilities })`. The top-level one adds the shared code that sends these requests and waits for the answers.

```typescript [server/rooms.ts]
import { t } from '@livething/server'
import { serverRequests } from '@livething/server/server-requests'
import * as v from 'valibot'
import { base } from './base'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    serverRequests({
      'ping-member': {
        out: t<null>(),
        in: v.object({ alive: v.boolean() }),
      },
    }),
  ],
})
```

The [Scoped Streams & Requests](/server/channels/scoped-streams-requests) page covers channel requests in full, including how `ctx.channel.request` asks one other member with `{ to }`.

### `subscribe`, `check`, `commit`, `revalidate`: the gate

`subscribe` is the schema for the payload a client sends when it joins. `check` and `commit` decide whether the join is allowed. `revalidate` checks a stored membership again after a reconnect. The [Auth Gate](/server/channels/auth-gate) page covers all four.

### `membership`: keep membership after a reconnect

By default, a channel is **ephemeral**: a membership lasts only as long as the connection. When a member's connection drops, the member leaves the channel completely. After a reconnect, the client subscribes again by itself.

Set `membership: 'persistent'` on a channel to keep its membership after a reconnect. You don't need an extra capability for it. The server stores the membership. When a member's connection drops and then reconnects, the server adds it back to the channel. This is called **auto-rejoin**. A channel that works this way is a **persistent** channel. A channel with `inbox()` or a `revalidate` hook must be persistent.

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { base, Message } from './base'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  membership: 'persistent', // members are added back after a reconnect
})

const announcements = base.channel('announcements', {
  capabilities: [emits({ announcement: t<{ text: string }>() })],
  // No membership field: every connection subscribes again on connect, so nothing needs to persist.
})
```

The server stores a membership only when the connection has a `userId`, which you set in the `authenticate` hook. An anonymous connection stays in a channel only while its socket is open. This is true on every channel, persistent or not, because there is no stable ID to add it back with.

### `replay`: replay for one channel

**[Replay](/server/replay/overview)** lets members that reconnect get the messages they missed. `replay: true` turns the replay capability on for this channel. `replay: false` turns it off for this channel. Either value needs `replay.history()` or `replay.snapshot()` in the server's capabilities. If neither is listed, `base.channel(...)` throws.

### `rateLimit`: limit incoming events

`rateLimit` sets one rate-limit rule for the events that members send in this channel. An object uses the same fields (`windowMs`, `maxMessages`, `maxBytes`, `per`) as the top-level [`rateLimit()`](/server/capabilities/rate-limit) capability. `false` turns the limit off for this channel. The field exists only when `rateLimit()` is in the server's capabilities. Without it, the field is a type error.

```typescript [server/rooms.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { rateLimit } from '@livething/server/rate-limit'
import { Message } from './base'

const base = server({ capabilities: [channels(), rateLimit()] })

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  rateLimit: { maxMessages: 30 },
})
```

A single channel handler can replace this rule with its own. Pass `rateLimit` in that handler's config.

## Naming patterns

A static channel name is a non-empty string that follows the rules in the note at the end of this section. Common shapes:

```typescript [server/announcements.ts]
import { emits, t } from '@livething/server'
import { base } from './base'

base.channel('announcements', {
  capabilities: [emits({ announcement: t<{ text: string }>() })],
}) // one channel for everyone
```

When the name changes at runtime (a room for each ID, a thread for each pair of user IDs), use a family. Don't declare one static channel for each value. One family declaration matches all the names. Here `dms` is cut down to its `membership` field:

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { base, Message } from './base'

base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
}) // room:general, room:design
base.channel(['dms', 'dm:{pair}'], {
  membership: 'persistent',
}) // dm:u_1+u_2, one capture: the sorted, joined pair of user ids
```

The `{pair}` capture follows the [template rules](/server/channels/dynamic-families) for families.

::note
A channel name (a static name or a family key) must follow these rules:

- It can't start or end with `__`. LiveThing uses that prefix and suffix for its own protocol names.
- It can't start with `@` or `#`, and it can't contain `::`. These characters are part of the path keys that [`ctx.matches(...)`](/server/lifecycle-and-intercept/intercept) reads (keys such as `@room::send-message`).
- A static name can be at most 256 characters. A family key can be at most 128 characters. These are the wire protocol limits.

A name that breaks one of these rules throws when the server starts, before any client connects.
::

## Handler methods on the channel object

`base.channel(...)` returns an object with two groups of methods:

- **Event handlers** (`on`, `request` and the stream methods) return a handler value. You pass it to `assemble(...)` to turn the handler on.
- **[Lifecycle hooks](#lifecycle-hooks)** are keys of the channel's config, not methods. They run when membership changes.

### Event handlers

These work like the top-level `base.on`, `base.request`, and `base.stream`. The difference is the `ctx` they receive: it has `ctx.channel`, which points to this channel.

```typescript [server/rooms.ts]
import * as v from 'valibot'
import { rooms } from './base'
import { searchRoomMessages } from './helpers'

// Like base.on: handle an event a member sends.
const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: payload.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})

// A stream that belongs to this channel (needs the stream() capability).
// It searches only this room. Huddle's own 'search-messages' is a top-level
// stream that searches all messages.
const handleRoomSearch = rooms.stream('search-messages', {
  input: v.object({ query: v.string() }),
  async *run(ctx, payload) {
    for await (const hit of searchRoomMessages(
      ctx.channel.params.roomId,
      payload.query,
    )) {
      yield { hit }
    }
  },
})
```

Pass `handleSendMessage` and `handleRoomSearch` to `base.assemble({ handlers: [...] })`. If you pass only `rooms`, LiveThing turns on its config and hooks, but neither handler. [To keep a channel's handlers together](/server/handlers/overview#grouping-handlers), export them as an `as const` list, such as `export const roomHandlers = [handleSendMessage, handleRoomSearch] as const`, and spread it in `assemble()`.

| Method                          | Works like            | Notes                                                                                                                     |
| ------------------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `on(event, config)`             | `base.on`             | Handles an event a member sends.                                                                                          |
| `request(event, config)`        | `base.request`        | A client→server request inside the channel. Needs `clientRequests()`.                                                     |
| `stream(event, config)`         | `base.stream`         | A plain stream. Needs `stream()`.                                                                                         |
| `recordedStream(event, config)` | `base.recordedStream` | A durable stream that saves every chunk, so a client that reconnects gets the chunks it missed. Needs `recordedStream()`. |

These methods exist on the channel object only when their capability is listed, so calling one without its capability is a type error. In plain JavaScript, the call throws an error that names the capability to add. [Streams](/server/streams/overview) covers each stream kind. The [Scoped Streams & Requests](/server/channels/scoped-streams-requests) page covers how they differ inside a channel.

### Lifecycle hooks

Each hook is a key in the channel's config. It runs when membership changes and returns `void`. A config has each key once, so a channel has at most one of each hook.

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { base, Message } from './base'

// Huddle does not add these hooks to rooms. They show the shape.
export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  onSubscribe(ctx) {
    // After a member joins: send the first state, or announce the member.
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: `${ctx.meta.name} entered`,
      from: 'system',
      sentAt: Date.now(),
    })
  },
  onUnsubscribe(ctx) {
    // On a true leave: announce that the member left.
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: `${ctx.meta.name} left`,
      from: 'system',
      sentAt: Date.now(),
    })
  },
  onSessionEnd(ctx) {
    // On every session end: a true leave or a plain disconnect.
    ctx.log.info('left room view', { userId: ctx.user.id })
  },
})
```

The hooks run once you pass the channel, or any of its handlers, to `assemble()`.

A **true leave** means the member left the channel on purpose (the client unsubscribed) or was removed with `kick`. A **plain disconnect** means the socket closed.

| Hook                                                     | Runs when                                                                                                                                     |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `onSubscribe`                                            | After a member's first subscribe is confirmed. It does not run on auto-rejoin.                                                                |
| `onUnsubscribe`                                          | Only on a true leave: an `__unsubscribe__` frame from the client, or `kick`. It does not run on a plain disconnect from a persistent channel. |
| `onSessionEnd`                                           | Every time this connection's view of the channel ends: a true leave or a plain disconnect.                                                    |
| [`intercept`](/server/lifecycle-and-intercept/intercept) | For each incoming frame for this channel, before LiveThing routes it.                                                                         |

::note
The difference between `onUnsubscribe` and `onSessionEnd` matters most on persistent channels. There, a plain disconnect keeps the stored membership. The user is still "in" the room, and the server will add them back on reconnect. So a plain disconnect runs `onSessionEnd` but not `onUnsubscribe`. On an ephemeral channel, a disconnect is a true leave, so both hooks run. The [Auth Gate](/server/channels/auth-gate) page covers the ways a member can leave in detail.
::

## Assembling channels

Pass the return value of each channel handler to `assemble(...)`, the same way you do for top-level handlers. This includes `channel.request(...)` and every stream method. They return a handler value too, like `channel.on(...)`. If you pass the channel object itself, LiveThing turns on its config and hooks, but none of its handlers. Pass the channel object for a channel that has no handlers, as Huddle does with `announcements`, or when you want its handlers turned off. Nothing changes a channel after `base.channel(...)` returns, so its config and hooks are complete when you create it.

```typescript [server/huddle-definition.ts]
import { base, rooms } from './base'
import { buildDigest } from './helpers'

// Huddle's one scheduled task needs its handler too.
const handleSendDigest = base.scheduled('send-digest', {
  run(ctx, data) {
    buildDigest(data.userId)
  },
})

// A channel with no handlers: pass the channel object itself.
const notifications = base.channel(
  ['notifications', 'notifications:{userId}'],
  {},
)

// A channel with handlers: pass the handler values.
const handleSendMessage = rooms.on('send-message', {
  run(ctx) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: 'hello',
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})

export const huddle = base.assemble({
  handlers: [handleSendDigest, handleSendMessage, notifications],
})
```

Each handler value keeps a reference to its channel. So `assemble` builds each channel only once, however many of its handlers you pass.
