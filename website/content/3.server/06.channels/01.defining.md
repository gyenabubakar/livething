You declare a channel with `base.channel(...)`. The call takes a **pattern** (the channel's name, or a family template) and an optional **config object** (its events, gate, and settings). It returns a channel object. You call methods on this object to register handlers.

```typescript [chat.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'

const base = server({
  capabilities: [channels()],
})

const lobby = base.channel('lobby', {
  capabilities: [
    emits({ message: t<{ text: string; from: string }>() }),
  ],
})
```

## The pattern

The first argument names the channel. It is either a string or a `[familyKey, template]` tuple (an array with exactly two items).

```typescript [patterns.ts]
// Static channel: one fixed name.
const lobby = base.channel('lobby', {
  /* ... */
})

// Family: one template that matches many names.
const rooms = base.channel(['rooms', 'room:{id}'], {
  /* ... */
})
```

An empty name is an error. An empty family key throws when you declare the channel, and an empty static name throws when you call `assemble(...)`. Families have their own page: see [Dynamic Families](/server/channels/dynamic-families) for the template rules and how rooms in a family stay separate. The rest of this page uses a static channel. Everything except the pattern works the same way for both.

::note
You always declare a family with the `[familyKey, template]` tuple. `base.channel(...)` accepts only two pattern shapes: a string for a static channel, or a tuple for a family.
::

## The config object

Every field is optional. Here is the full shape. Each field is described after the table.

| Field                                 | Type                          | Purpose                                                                                                                                    |
| ------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `capabilities: [emits(...)]`          | event map                     | Events the channel sends to its members.                                                                                                   |
| `capabilities: [serverRequests(...)]` | request map                   | Server→client requests sent to members of this channel. Needs [`serverRequests()`](/server/capabilities/server-requests) at the top level. |
| `subscribe`                           | a schema                      | Validates the payload a client sends when it subscribes.                                                                                   |
| `check`                               | `(ctx, payload) => result`    | Auth gate. It can be async. Throw to reject.                                                                                               |
| `commit`                              | `(ctx, checkResult) => void`  | Sync gate that runs when the membership is written. Throw to reject.                                                                       |
| `revalidate`                          | `(ctx) => void`               | Checks a stored membership again on auto-rejoin. Needs a persistent channel.                                                               |
| `membership`                          | `'persistent' \| 'ephemeral'` | Whether membership survives a reconnect. The default is `'persistent'`.                                                                    |
| `replay`                              | `boolean`                     | Turns built-in replay on or off for this channel. Needs a built-in [replay](/server/replay/overview) capability.                           |
| `capabilities`                        | array                         | This channel's `emits(...)`, `serverRequests(...)`, and channel-only capabilities.                                                         |
| `rateLimit`                           | `RateLimitConfig`             | A rate-limit rule for the events members send in this channel. Needs the `rateLimit()` capability.                                         |

### `emits(...)`: the channel's events

`emits(...)` lists the events the channel sends to its members. Each value is a `t<Payload>()` call that sets the payload type. These are the events that `ctx.channel.send(...)`, `ctx.channel.broadcastTo(...)`, and `ctx.channel.broadcast(...)` accept.

```typescript [room.ts]
const room = base.channel('room', {
  capabilities: [
    emits({
      'room-message': t<{
        text: string
        from: string
        kind: string
      }>(),
      typing: t<{ from: string }>(),
    }),
  ],
})
```

A channel with no events is valid. Leave out `emits(...)`. For example, a channel can carry only [channel requests](/server/channels/scoped-streams-requests), or only track presence (who is in the channel).

### `serverRequests(...)`: server→client requests

`serverRequests(...)` declares requests that the server sends to the members of this channel. Each entry has an `out` payload (what the server sends) and an `in` schema (the answer the client must send back). Also list plain `serverRequests()` in the top-level `server({ capabilities })`. The top-level one adds the shared code that sends these requests and waits for the answers.

```typescript [lobby.ts]
import { serverRequests } from '@livething/server/server-requests'
import * as v from 'valibot'

const lobby = base.channel('lobby', {
  capabilities: [
    serverRequests({
      volunteer: {
        out: t<{ turn: number }>(),
        in: v.object({ ready: v.boolean() }),
      },
    }),
  ],
})
```

The [Scoped Streams & Requests](/server/channels/scoped-streams-requests) page covers channel requests in full, including the difference between `ctx.channel.request` and `ctx.channel.broadcastRequest`.

### `subscribe`, `check`, `commit`, `revalidate`: the gate

`subscribe` is the schema for the payload a client sends when it joins. `check` and `commit` decide whether the join is allowed. `revalidate` checks a stored membership again after a reconnect. The [Auth Gate](/server/channels/auth-gate) page covers all four.

### `membership`: keep membership after a reconnect

By default, every channel keeps its membership after a reconnect, and you don't need an extra capability for it. The server stores the membership. When a member's connection drops and then reconnects, the server adds it back to the channel. This is called **auto-rejoin**. A channel that works this way is a **persistent** channel.

Set `membership: 'ephemeral'` on a channel to turn this off. On an **ephemeral** channel, a dropped connection leaves the channel completely. You can write `membership: 'persistent'`, but it changes nothing, because it is already the default.

```typescript [rooms.ts]
const archive = base.channel('archive', {
  capabilities: [emits({ entry: t<{ line: string }>() })],
  // No membership field: members are added back after a reconnect.
})

const presence = base.channel('presence', {
  capabilities: [emits({ ping: t<{ at: number }>() })],
  membership: 'ephemeral', // A dropped connection leaves the channel.
})
```

The server stores a membership only when the connection has a `userId`, which you set in the `upgrade` hook. An anonymous connection (one with no `userId`) stays in a channel only while its socket is open. This is true on every channel, persistent or not, because there is no stable ID to add it back with.

### `replay`: replay for one channel

**Replay** lets members that reconnect get the messages they missed. `replay: true` turns the built-in replay capability on for this channel. `replay: false` turns it off for this channel. Either value needs `replay.history()` or `replay.snapshot()` in the server's capabilities. If neither is listed, `base.channel(...)` throws. For your own replay logic, use the `replay(...)` method (see [Lifecycle hooks](#lifecycle-hooks) below) instead. See [Replay](/server/replay/overview) for the full model.

### `rateLimit`: limit incoming events

`rateLimit` sets one rate-limit rule for the events that members send in this channel. It uses the same `RateLimitConfig` shape as the top-level [`rateLimit()`](/server/capabilities/rate-limit) capability. The field exists only when `rateLimit()` is in the server's capabilities. Without it, the field is a type error.

```typescript [room.ts]
const room = base.channel('room', {
  capabilities: [emits({ 'room-message': t<{ text: string }>() })],
  rateLimit: { enabled: true, max: 30 },
})
```

A single channel handler can replace this rule with its own. Pass `rateLimit` in that handler's config.

## Naming patterns

A static channel name is a non-empty string that follows the rules in the note at the end of this section. Common shapes:

```typescript [names.ts]
base.channel('lobby', {
  /* ... */
}) // one room for everyone
base.channel('notifications', {
  /* ... */
}) // one channel for one feature
base.channel('room2', {
  /* ... */
}) // numbered rooms
```

When the name changes at runtime (a room for each ID, a thread for each pair of IDs), use a family. Don't declare one static channel for each value. One family declaration matches all the names:

```typescript [names.ts]
base.channel(['rooms', 'room:{id}'], {
  /* ... */
}) // room:general, room:design
base.channel(['threads', 'org:{org}/thread:{tid}'], {
  /* ... */
}) // two captures
```

See [Dynamic Families](/server/channels/dynamic-families) for the template rules.

::note
A channel name (a static name or a family key) must follow these rules:

- It can't start or end with `__`. LiveThing uses that prefix and suffix for its own protocol names.
- It can't start with `@` or `#`, and it can't contain `::`. These characters are part of the path keys that [`ctx.matches(...)`](/server/lifecycle-and-intercept/intercept) reads (keys such as `@room::send-message`).
- A static name can be at most 256 characters. A family key can be at most 128 characters. These are the wire protocol limits.

A name that breaks one of these rules throws when the server starts, before any client connects.
::

## Handler methods on the channel object

`base.channel(...)` returns an object with two groups of methods:

- **Event handlers** return a handler value. You pass it to `assemble(...)` to turn the handler on.
- **Lifecycle hooks** register a function that runs when membership changes. They return nothing.

### Event handlers

These work like the top-level `base.on`, `base.request`, and `base.stream`. The difference is the `ctx` they receive: it has `ctx.channel`, which points to this channel.

```typescript [room.ts]
import * as v from 'valibot'

// Like base.on: handle an event a member sends.
const handleSend = room.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('room-message', {
      text: payload.text,
      from: ctx.meta.username,
      kind: 'user',
    })
  },
})

// A stream that belongs to this channel (needs the stream() capability).
const handleCount = room.stream('start-count', {
  input: v.object({ count: v.number() }),
  chunk: t<{ index: number }>(),
  async *run(_ctx, payload) {
    for (let i = 0; i < payload.count; i++) yield { index: i }
  },
})
```

Pass `handleSend` and `handleCount` to `base.assemble({ handlers: [...] })`. If you pass only `room`, LiveThing keeps its config and lifecycle hooks, but turns on neither handler.

| Method                           | Works like             | Notes                                                                                                                     |
| -------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `on(event, config)`              | `base.on`              | Handles an event a member sends.                                                                                          |
| `request(event, config)`         | `base.request`         | A client→server request inside the channel. Needs `clientRequests()`.                                                     |
| `stream(event, config)`          | `base.stream`          | A plain stream. Needs `stream()`.                                                                                         |
| `resumableStream(event, config)` | `base.resumableStream` | A durable stream that runs again from a saved position after a reconnect. Needs `resumableStream()`.                      |
| `recordedStream(event, config)`  | `base.recordedStream`  | A durable stream that saves every chunk, so a client that reconnects gets the chunks it missed. Needs `recordedStream()`. |

These methods exist on the channel object only when their capability is listed, so calling one without its capability is a type error. In plain JavaScript, the call throws an error that names the capability to add. [Streams](/server/streams/overview) covers each stream kind. The [Scoped Streams & Requests](/server/channels/scoped-streams-requests) page covers how they differ inside a channel.

### Lifecycle hooks

Each hook registers a function for a membership change and returns `void`. You can attach each hook only once per channel. A second call throws.

```typescript [room.ts]
room.subscribe((ctx) => {
  // After a member joins: send the first state, or announce the member.
  ctx.channel.broadcast('room-message', {
    text: `${ctx.meta.username} entered`,
    from: 'system',
    kind: 'system',
  })
})

room.unsubscribe((ctx) => {
  // On a true leave: announce that the member left.
  ctx.channel.broadcast('room-message', {
    text: `${ctx.meta.username} left`,
    from: 'system',
    kind: 'system',
  })
})

room.sessionEnd((ctx) => {
  // On every session end: a true leave or a plain disconnect.
})
```

A **true leave** means the member left the channel on purpose (the client unsubscribed) or was removed with `kick`. A **plain disconnect** means the socket closed.

| Hook                   | Runs when                                                                                                                                                         |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `subscribe(handler)`   | After a member's first subscribe is confirmed. It does not run on auto-rejoin.                                                                                    |
| `unsubscribe(handler)` | Only on a true leave: an `__unsubscribe__` frame from the client, or `kick`. It does not run on a plain disconnect from a persistent channel.                     |
| `sessionEnd(handler)`  | Every time this connection's view of the channel ends: a true leave or a plain disconnect.                                                                        |
| `intercept(handler)`   | For each incoming frame (message) for this channel, before LiveThing routes it. Needs `intercepts()`. See [Intercept](/server/lifecycle-and-intercept/intercept). |
| `replay(hooks)`        | Your own replay logic for this channel. Needs `replay.custom()`. See [Replay](/server/replay/overview).                                                           |

::note
The difference between `unsubscribe` and `sessionEnd` matters most on persistent channels. There, a plain disconnect keeps the stored membership. The user is still "in" the room, and the server will add them back on reconnect. So a plain disconnect runs `sessionEnd` but not `unsubscribe`. On an ephemeral channel, a disconnect is a true leave, so both hooks run. The [Auth Gate](/server/channels/auth-gate) page covers the ways a member can leave in detail.
::

## Assembling channels

Pass the return value of each channel handler to `assemble(...)`, the same way you do for top-level handlers. This includes `channel.request(...)` and every stream method. They return a handler value too, like `channel.on(...)`. If you pass the channel object itself, LiveThing includes its config and lifecycle hooks, but turns on none of its handlers. Pass the channel object for a channel that has no handlers, or when you want its handlers turned off.

```typescript [chat.ts]
// A channel with handlers: pass the handler values.
const handleSend = room.on('send-message', {
  /* ... */
})

// A channel with no handlers: pass the channel object itself.
const notifications = base.channel(
  ['notifications', 'notifications:{userId}'],
  {
    /* ... */
  },
)

export const definition = base.assemble({
  handlers: [handleSend, notifications],
})
```

Each handler value keeps a reference to its channel. So `assemble` builds each channel only once, however many of its handlers you pass.
