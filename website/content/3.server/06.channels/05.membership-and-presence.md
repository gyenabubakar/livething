A channel keeps a list of its members. This page covers two sides of that list:

- **Managing** membership from server code: subscribing, kicking, and removing members.
- **Observing** membership through the presence frames that a channel broadcasts when members come and go.

Everything here works the same way for every channel, static or dynamic (a family).

You do these things through a **channel handle**: an object that points to one channel. Inside a channel handler, the handle is `ctx.channel`. From any other connection handler or lifecycle hook, get one with `ctx.channels.get(...)`.

::note
A persistent channel saves each membership as a **durable membership row**: a row in the database that lets the member rejoin after a reconnect (see [Channels](/server/capabilities/channels#capabilities-a-channel-may-need)). These rows live in a reserved SQLite table, `__livething_channel_memberships`, in the server's own SQL storage. LiveThing creates and manages this table. Do not create it or write to it yourself. The [reserved-table list](/server/context-and-storage/sql-and-kv#reserved-livething-tables) shows its columns and every other table that LiveThing owns.

If you rename or remove a channel between deploys, its old membership rows stay in the table. LiveThing deletes them the next time the server starts. It deletes the rows of every channel that no current definition declares as a persistent channel, and it writes one line to the log with the number of channels it cleaned up.
::

## Subscribing from the server

`channelHandle.subscribe(ref, payload?)` adds a connection to a channel from server code. It runs the same steps as a subscribe that a client starts (`check`, then `commit`, then the `onSubscribe` hook), so the auth gate still decides. This example adds a `notifications` channel to Huddle, one for each user, and puts every connection into its own. `ctx.channels.get(...)` finds only channels that `assemble()` received, so you must pass `notifications` to `assemble()`. A channel that you leave out makes `ctx.channels.get` fail.

The `onConnect` hook is a key of `server({ ... })`, and the channel is created from the result of `server({ ... })`. So the hook uses the channel inside its function body, which only runs later, when a connection opens:

::code-group

```typescript [server/base.ts]
import { server } from '@livething/server'
import { channels } from '@livething/server/channels'

export const base = server({
  capabilities: [channels()],
  async onConnect(ctx) {
    // Put every connection into its user's personal channel on connect.
    await ctx.channels
      .get(notifications.at({ userId: ctx.user.id }))
      .subscribe(ctx.connection)
  },
})

export const notifications = base.channel(
  ['notifications', 'notifications:{userId}'],
  {},
)
```

```typescript [server/huddle-definition.ts]
import { base, notifications } from './base'

export const huddle = base.assemble({ handlers: [notifications] })
```

::

- If the connection is already a member, the call does nothing.
- If `check` or `commit` throws, the call **rejects** and the connection is not added.
- LiveThing validates `payload` with the channel's `subscribe` schema and passes it to `check`, exactly like the payload of a client subscribe.

## Kicking members

`kick(target, { reason })` removes members from a channel for good. It forces the matching connections out, runs `onUnsubscribe` and then `onSessionEnd` for each one, and on a persistent channel deletes the durable membership row. A kicked user is **not** added back when they reconnect. To come back, their client must subscribe again, and the auth gate (`check`, then `commit`) decides again.

The `target` chooses which sockets are removed:

- a `UserRef`: every connection of that user that is in the channel (all tabs and devices).
- a `TagRef`: every socket that holds that exact `(kind, group, key)` tag. A `TagRef` already contains all three parts, so you only pass the ref.
- a tag group handle (from `ctx.tags.ephemeral(group)` or `ctx.tags.persistent(group)`): every socket that has any key in that group.

`kick` works on users and tags, not on one connection. To drop one specific socket and keep the user's other connections, use `ctx.connections.get(ref).close()` instead. Closing a connection is also how you boot a user for now without taking away their membership: on a persistent channel, `ctx.users.get(userId).close()` drops every socket of the user, and they rejoin automatically on their next connection.

Each kicked socket receives a `__kicked__ { reason }` frame. Then the channel broadcasts `__memberLeave__` and `__memberOffline__` to the remaining members.

If an `onUnsubscribe` or `onSessionEnd` hook throws for one socket, `kick` still removes every other matching socket. When it has finished, the promise rejects with an `AggregateError` whose `errors` list holds every hook failure.

Streams that a kicked socket was running in the channel stop, the same as when it unsubscribes (see [Streams in a channel](/server/channels/scoped-streams-requests)).

LiveThing deletes the durable row only when the kick removes the user's last connection in the channel. A `UserRef` target always does this, because it removes all of the user's connections. On a persistent channel, a `UserRef` kick also reaches a member who has no live connection right now: LiveThing deletes their row and the other members get `__memberLeave__`.

Huddle has no kick event. This `evict` event is an example that lets an admin remove a user from a room:

```typescript [server/huddle-handlers.ts]
import * as v from 'valibot'
import { Forbidden } from '../shared/errors'
import { base, rooms } from './base'

const handleEvict = base.on('evict', {
  input: v.object({ roomId: v.string(), targetUserId: v.string() }),
  async run(ctx, input) {
    if (ctx.meta.role !== 'admin') {
      throw Forbidden({ reason: 'only an admin may remove a user' })
    }

    const room = ctx.channels.get(rooms.at({ roomId: input.roomId })) // typed handle to room:<roomId>
    const target = ctx.users.get(input.targetUserId).ref()
    await room.kick(target, { reason: 'removed by an admin' })
  },
})
```

## The membership table

All durable membership rows live in one table, `__livething_channel_memberships`:

| Column           | Type      | Notes                                                                                    |
| ---------------- | --------- | ---------------------------------------------------------------------------------------- |
| `user_id`        | `TEXT`    | The member's user ID. Part of the primary key.                                           |
| `channel_name`   | `TEXT`    | The channel name (for a family, the full name of the instance). Part of the primary key. |
| `channel_family` | `TEXT`    | The family key, or `''` for a static channel. Part of the primary key.                   |
| `joined_at`      | `INTEGER` | The time the row was written, in Unix milliseconds.                                      |
| `metadata`       | `TEXT`    | A reserved JSON field. LiveThing does not read or write it.                              |

The primary key is `(user_id, channel_name, channel_family)`. When a member that already has a row subscribes again, LiveThing replaces that row instead of adding a second one.

An **anonymous connection** is a connection with no `userId` (your `upgrade` hook did not set one). It never gets a row in this table. A durable row exists only so that the same user can rejoin after a reconnect, and an anonymous connection has no stable ID to match. It stays in the channel only while its socket is open.

The row is stored per **user**, but a leave happens per **connection**. The same user can have the channel open in more than one tab or device at the same time. When one tab leaves and another tab of the same user is still a member, the row stays. LiveThing deletes the durable row (and clears the [inbox](/server/inbox/overview), if the channel uses one) only when the user's **last** live connection in that channel leaves. Until then, the other tabs keep receiving messages, and a page refresh in any of them still rejoins automatically.

```typescript [client/room.ts]
import { socket } from './socket'

// Tab A and Tab B are both subscribed to the same room as the same user.
// Tab A leaves. Tab B is still a member, so the durable row stays
// and Tab B keeps receiving messages.
// In Tab A:
await socket.channel('rooms', 'room:general').unsubscribe()

// When Tab B also leaves, the durable row (and the inbox) is deleted.
// In Tab B:
await socket.channel('rooms', 'room:general').unsubscribe()
```

## Presence: who is in, and who is online

A channel keeps every member's list up to date by broadcasting **presence frames**. There are two pairs:

- **`__memberJoin__` / `__memberLeave__`**: the **member list changed**. Someone was added to the channel or removed from it.
- **`__memberOnline__` / `__memberOffline__`**: an existing member got their first live connection in the channel, or lost their last one. The member list did not change.

There are two pairs because, on a persistent channel, a member can stay in the channel while they are disconnected. When their socket drops, they stay in the member list, because LiveThing adds them back when they reconnect. So a drop sends `__memberOffline__`, not `__memberLeave__`. When they reconnect, the member list is the same, so the channel sends `__memberOnline__`, not `__memberJoin__`.

On a persistent channel, a member is a **user**, identified by their `userId`. A user with two tabs open in the channel is one member: the join and the online frame go out for the first tab only, and the offline frame goes out only when the last tab is gone. An anonymous connection has no user to keep its place, so its disconnect is a real leave.

| Event               | Meaning                                                                 | Member list |
| ------------------- | ----------------------------------------------------------------------- | ----------- |
| `__memberJoin__`    | A new member joined                                                     | grew        |
| `__memberLeave__`   | A member really left (unsubscribed, or was kicked)                      | shrank      |
| `__memberOnline__`  | An existing member got their first live connection (joined or rejoined) | unchanged   |
| `__memberOffline__` | An existing member's last live connection dropped                       | unchanged   |

An example on a persistent channel:

::steps{level="3"}

### First subscribe

Alice joins `room:general`. The other members get `__memberJoin__` and then `__memberOnline__`, because she is a new member and she is now online.

### Network drop

Alice's connection drops. She stays a member (the channel is persistent), so the other members get only `__memberOffline__`. The member list still includes Alice.

### Reconnect

Alice's socket connects again and LiveThing adds it back to the channel automatically. The member list did not change, so the other members get only `__memberOnline__`. They do not get a second `__memberJoin__`.

### Real leave

Alice sends `__unsubscribe__` (or is kicked). Now she really leaves, so the other members get `__memberLeave__` and then `__memberOffline__`.

::

On an **ephemeral** channel (`membership: 'ephemeral'`), a member cannot stay in the channel while offline. A disconnect is a real leave, so it sends `__memberLeave__`. The difference between `__memberOnline__`/`__memberOffline__` and join/leave matters only on persistent channels.

A kick is a real leave too: the other members get `__memberLeave__` and `__memberOffline__`.

### Presence payloads

Every presence frame names the member with a **member ID**. On a persistent channel it is the member's `userId`. On an ephemeral channel, or for an anonymous connection, it is the connection ID.

| Event               | Payload                                      |
| ------------------- | -------------------------------------------- |
| `__memberJoin__`    | `{ memberId, meta? }`                        |
| `__memberLeave__`   | `{ memberId, meta? }`                        |
| `__memberOnline__`  | `{ memberId, meta? }`                        |
| `__memberOffline__` | `{ memberId }`                               |
| `__memberSync__`    | `{ members: { memberId, meta?, online }[] }` |

`meta` is the metadata that your upgrade hook set. Every presence frame also carries the name of its channel (and the family key for a family channel), so a client in several channels can tell which channel each frame is for.

::note
Right after a new member's subscribe is confirmed, the server sends that member a **member sync** (`__memberSync__`): the full member list. On a persistent channel, it also lists members who are offline right now, with `online: false`. The new member starts with the full list and does not need to build it from join frames. After that, the join, leave, online, and offline frames keep the list up to date.
::
