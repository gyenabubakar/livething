A channel keeps a list of its members. This page covers two sides of that list:

- **Managing** membership from server code: subscribing, kicking, and removing members.
- **Observing** membership through the presence frames that a channel broadcasts when members come and go.

Everything here works the same way for every channel, static or dynamic (a family).

You do these things through a **channel handle**: an object that points to one channel. Inside a channel handler, the handle is `ctx.channel`. From any other connection handler or lifecycle hook, get one with `ctx.channels.get(...)`.

::note
A persistent channel saves each membership as a **durable membership row**: a row in the database that lets the member rejoin after a reconnect (see [Channels](/server/capabilities/channels#capabilities-a-channel-may-need)). These rows live in a reserved SQLite table, `__livething_channel_memberships`, in the server's own SQL storage. LiveThing creates and manages this table. Do not create it or write to it yourself. The [reserved-table list](/server/context-and-storage/sql-and-kv#reserved-livething-tables) shows its columns and every other table that LiveThing owns.

If you rename or remove a channel between deploys, its old membership rows stay in the table. LiveThing deletes them the next time the server starts. It deletes the rows of every channel that no current definition declares as a persistent channel, and it writes one line to the log with the number of channels it cleaned up.
::

## Subscribing from the server

The `subscribe(ref, payload?)` method of a channel handle adds a connection to a channel from server code. It runs the same steps as a subscribe that a client starts (`check`, then `commit`, then the `onSubscribe` hook), so the auth gate still decides. This example adds a `notifications` channel to Huddle, one for each user, and puts every connection into its own. `ctx.channels.get(...)` finds only channels that `assemble()` received, so you must pass `notifications` to `assemble()`. A channel that you leave out makes `ctx.channels.get` fail.

The `onConnect` hook is a key of `server({ ... })`, and the channel is created from the result of `server({ ... })`. So the hook uses the channel inside its function body, which only runs later, when a connection opens:

::code-group

```typescript [server/base.ts]
import { server } from '@livething/server'
import { channels } from '@livething/server/channels'

export const base = server({
  capabilities: [channels()],
  async onConnect(ctx) {
    // Put every connection into its user's personal channel on connect.
    await ctx.channels
      .get(notifications.at({ userId: ctx.user.id }))
      .subscribe(ctx.connection)
  },
})

export const notifications = base.channel(
  ['notifications', 'notifications:{userId}'],
  {},
)
```

```typescript [server/huddle-definition.ts]
import { base, notifications } from './base'

export const huddle = base.assemble({ handlers: [notifications] })
```

::

- If the connection is already a member, the call does nothing.
- If `check` or `commit` throws, the call **rejects** and the connection is not added.
- LiveThing validates `payload` with the channel's `subscribe` schema and passes it to `check`, exactly like the payload of a client subscribe.

## Kicking members

`kick(target, { reason })` removes members from a channel. It forces the matching connections out, runs `onUnsubscribe` and then `onSessionEnd` for each one, and on a persistent channel deletes the durable membership row (see the rule below). When a kick removes the user's last connection in the channel, the user is **not** added back when they reconnect. To come back, their client must subscribe again, and the auth gate (`check`, then `commit`) decides again.

The `target` chooses which sockets are removed:

- a `UserRef`: every connection of that user that is in the channel (all tabs and devices).
- a `TagRef`: every socket that holds that exact `(kind, group, key)` tag. A `TagRef` already contains all three parts, so you only pass the ref.
- a tag group handle (from `ctx.tags.ephemeral(group)` or `ctx.tags.persistent(group)`): every socket that has any key in that group.

`kick` works on users and tags, not on one connection. To drop one specific socket and keep the user's other connections, use `ctx.connections.get(ref).close()` instead. Closing a connection is also how you disconnect a user for now without taking away their membership: on a persistent channel, `ctx.users.get(userId).close()` drops every socket of the user, and they rejoin automatically on their next connection.

Each kicked socket receives a `__kicked__ { reason }` frame. Then, when the channel has presence, the remaining members get a `leave` and an `offline` change (see [Presence](#presence-who-is-in-and-who-is-online)), unless the user still has another connection in a persistent channel.

If an `onUnsubscribe` or `onSessionEnd` hook throws for one socket, `kick` still removes every other matching socket. When it has finished, the promise rejects with an `AggregateError` whose `errors` list holds every hook failure.

Streams that a kicked socket was running in the channel stop, the same as when it unsubscribes (see [Streams in a channel](/server/channels/scoped-streams-requests)).

LiveThing deletes the durable row only when the kick removes the user's last connection in the channel. A `UserRef` target always does this, because it removes all of the user's connections. On a persistent channel, a `UserRef` kick also reaches a member who has no live connection right now: LiveThing deletes their row and the other members get a `leave` change.

Huddle has no kick event. This `evict` event is an example that lets an admin remove a user from a room:

```typescript [server/huddle-handlers.ts]
import * as v from 'valibot'
import { Forbidden } from '../shared/errors'
import { base, rooms } from './base'

const handleEvict = base.on('evict', {
  input: v.object({ roomId: v.string(), targetUserId: v.string() }),
  async run(ctx, input) {
    if (ctx.meta.role !== 'admin') {
      throw Forbidden({ reason: 'only an admin may remove a user' })
    }

    const room = ctx.channels.get(rooms.at({ roomId: input.roomId })) // typed handle to room:<roomId>
    const target = ctx.users.get(input.targetUserId).ref()
    await room.kick(target, { reason: 'removed by an admin' })
  },
})
```

## The membership table

All durable membership rows live in one table, `__livething_channel_memberships`:

| Column           | Type      | Notes                                                                                                                                                                            |
| ---------------- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `user_id`        | `TEXT`    | The member's user ID. Part of the primary key.                                                                                                                                   |
| `channel_name`   | `TEXT`    | The channel name (for a family, the full name of the instance). Part of the primary key.                                                                                         |
| `channel_family` | `TEXT`    | The family key, or `''` for a static channel. Part of the primary key.                                                                                                           |
| `joined_at`      | `INTEGER` | The time the row was written, in Unix milliseconds.                                                                                                                              |
| `metadata`       | `TEXT`    | A JSON field. LiveThing stores `{ meta }` here: the member's metadata at its last subscribe. It is the member's `meta` while the member is offline. Do not write to it yourself. |

The primary key is made of three columns: `user_id`, `channel_name` and `channel_family`. When a member that already has a row subscribes again, LiveThing replaces that row instead of adding a second one.

An **anonymous connection** is a connection with no `userId` (your `authenticate` hook did not set one). It never gets a row in this table. A durable row exists only so that the same user can rejoin after a reconnect, and an anonymous connection has no stable ID to match. It stays in the channel only while its socket is open.

The row is stored per **user**, but a leave happens per **connection**. The same user can have the channel open in more than one tab or device at the same time. When one tab leaves and another tab of the same user is still a member, the row stays. LiveThing deletes the durable row (and clears the [inbox](/server/inbox/overview), if the channel uses one) only when the user's **last** live connection in that channel leaves. Until then, the other tabs keep receiving messages, and a page refresh in any of them still rejoins automatically.

```typescript [client/room.ts]
import { socket } from './socket'

// Tab A and Tab B are both subscribed to the same room as the same user.
// Tab A leaves. Tab B is still a member, so the durable row stays
// and Tab B keeps receiving messages.
// In Tab A:
await socket.channel('rooms', 'room:general').unsubscribe()

// When Tab B also leaves, the durable row (and the inbox) is deleted.
// In Tab B:
await socket.channel('rooms', 'room:general').unsubscribe()
```

## Presence: who is in, and who is online

A channel keeps every member's list up to date with **presence**. Presence is on for every channel unless you [turn it off](#turning-presence-off). It is made of two frames:

- **`__memberSync__`**: right after a member's subscribe is confirmed, the server sends that member the list of the other members.
- **`__memberChanges__`**: after that, each change to the list reaches the member as an entry in this frame.

There are two kinds of change, each with two values:

- **`join` / `leave`**: the **member list changed**. Someone was added to the channel or removed from it.
- **`online` / `offline`**: an existing member got their first live connection in the channel, or lost their last one. The member list did not change.

There are two kinds because, on a persistent channel, a member can stay in the channel while they are disconnected. When their socket drops, they stay in the member list, because LiveThing adds them back when they reconnect. So a drop is an `offline` change, not a `leave`. When they reconnect, the member list is the same, so the change is `online`, not `join`.

On a persistent channel, a member is a **user**, identified by their `userId`. A user with two tabs open in the channel is one member: the `join` and the `online` change happen for the first tab only, and the `offline` change happens only when the last tab is gone. An anonymous connection has no user to keep its place, so its disconnect is a real leave.

| Change    | Meaning                                                                                    | Member list |
| --------- | ------------------------------------------------------------------------------------------ | ----------- |
| `join`    | A new member joined                                                                        | grew        |
| `leave`   | A member really left (unsubscribed, was kicked, or disconnected from an ephemeral channel) | shrank      |
| `online`  | An existing member got their first live connection (joined or rejoined)                    | unchanged   |
| `offline` | An existing member's last live connection dropped                                          | unchanged   |

An example on a persistent channel:

::steps{level="3"}

### First subscribe

Alice joins `room:general`. The other members get `join` and then `online`, because she is a new member and she is now online.

### Network drop

Alice's connection drops. She stays a member (the channel is persistent), so the other members get only `offline`. The member list still includes Alice.

### Reconnect

Alice's socket connects again and LiveThing adds it back to the channel automatically. The member list did not change, so the other members get only `online`. They do not get a second `join`.

### Real leave

Alice sends `__unsubscribe__` (or is kicked). Now she really leaves, so the other members get `leave` and then `offline`.

::

On an **ephemeral** channel (`membership: 'ephemeral'`), a member cannot stay in the channel while offline. A disconnect is a real leave, so the other members get `leave` and then `offline`, the same as for an unsubscribe. A member there is never in the list while offline, so the client always gets the two changes together.

A kick is a real leave too when it ends the member: the other members get `leave`, and `offline` if the kicked member was online. On a persistent channel, a user who keeps another connection there stays a member, so the others get no change. A persistent member who was kicked while disconnected was already offline, so only `leave` is sent.

### How changes are sent

Sending each change to each member on its own would cost too much in a big channel. When 2,000 people join one room, the last one to join would be announced to 1,999 members, with a `join` and an `online` change each. All the joins together would be about 4 million frames. So LiveThing sends changes in **batches**:

- The first change on a quiet channel goes out at once.
- The changes that come in the next 500 milliseconds (the **window**) wait, and then go out together in one `__memberChanges__` frame.
- A window with no change ends the batching. The next change goes out at once again.

A single join on a quiet channel reaches the other members with no delay. A burst of joins costs each member one frame per window, not one frame per join: in the 2,000-member room, a member who was there before the burst gets one frame every 500 milliseconds while the burst lasts, instead of up to 3,998. A channel event also sends the waiting changes first (see below), so a busy channel sends them more often than once per window.

The changes in a frame are in the order they happened. Two more rules keep the member list right:

- **A channel event never comes first.** Before your code sends a channel event to the channel's members, LiveThing sends them the changes that are still waiting. A member never gets an event from someone before they learn that this person joined.
- **A new member gets only what is new to it.** The member sync already shows every change before the new member joined. So its first `__memberChanges__` frame starts after its own join.

A member who joined and left within one window still shows as a `join` and then a `leave`, so the client fires both callbacks.

### Presence payloads

Every change names the member with a **member ID**. On a persistent channel it is the member's `userId`. On an ephemeral channel, or for an anonymous connection, it is the connection ID.

| Event               | Payload                                      |
| ------------------- | -------------------------------------------- |
| `__memberSync__`    | `{ members: { memberId, meta?, online }[] }` |
| `__memberChanges__` | `{ changes: { kind, memberId, meta? }[] }`   |

`kind` is `join`, `leave`, `online` or `offline`. `meta` is the metadata that your `authenticate` hook set, and an `offline` change has none. Both frames also carry the name of their channel (and the family key for a family channel), so a client in several channels can tell which channel each frame is for.

The member sync is the list of the other members, without the new member itself. On a persistent channel, it also lists members who are offline right now, with `online: false`. The new member starts with this list and does not need to build it from changes. On the client, [presence listeners](/client/channels/presence-listeners) and the `members` store do this work for you.

### Turning presence off

Presence is useful when members want to see each other, as in a chat room. In a channel that everyone joins but nobody looks at as a group, it only costs work. Set `presence: false` to turn it off. The Huddle `announcements` channel does this, because every user joins it and only the server sends to it:

```typescript [server/announcements.ts]
import { emits, t } from '@livething/server'
import { base } from './base'

// Everyone joins it, so its members get no presence.
export const announcements = base.channel('announcements', {
  presence: false,
  capabilities: [
    emits({
      announcement: t<{ text: string }>(),
    }),
  ],
})
```

With presence off, a member gets no `__memberSync__` and no `__memberChanges__`, and its client's member list stays empty. The server still knows the members: `members()`, `memberCount()`, broadcasts and kicks work as before.

To keep presence and change the window, pass `presence: { windowMs }` with a whole number of milliseconds, from 1 up to the longest a timer can hold (2,147,483,647). Any other value, or another key, makes `base.channel()` throw a `LiveThingConfigError`. A shorter window shows changes sooner. A longer one sends fewer frames during a burst. On Cloudflare, a Durable Object does not hibernate while a window is open, so a long window keeps it awake longer after each burst. A pending timer keeps the object in memory for at most 15 minutes, so a window longer than that can lose its waiting changes if Cloudflare evicts the object:

```typescript [server/base.ts]
// in server/base.ts, next to the other rooms options
export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  presence: { windowMs: 200 },
})
```

### Counting members

`memberCount()` on a channel handle returns how many connections are in the channel. It is the length of `members()`, but it builds no list, so it costs the same in a room of 10 and a room of 10,000. A user with two tabs in the channel counts twice.

A count is a cheap way to show a big channel's size when presence is off. Huddle's top-level `count-readers` event answers with the number of connections in `announcements`:

```typescript [server/huddle-handlers.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleCountReaders = base.on('count-readers', {
  input: v.object({}),
  run(ctx) {
    const count = ctx.channels.get('announcements').memberCount()
    ctx.send('reader-count', { count })
  },
})
```

The client sends `count-readers` when it shows the number. Sending a new count to every member on each join would cost as much as presence, because every join would reach every member again.

### Presence for a few users

Some screens care about a few people, not a whole channel: a contact list shows if each contact is online. `ctx.users.get(id).isOnline()` answers for one user, so a client can ask about the users it shows. Huddle's `who-is-online` event takes a list of user IDs and answers with the ones that are online:

```typescript [server/huddle-handlers.ts]
import * as v from 'valibot'
import { base } from './base'

export const handleWhoIsOnline = base.on('who-is-online', {
  input: v.object({ userIds: v.array(v.string()) }),
  run(ctx, input) {
    const userIds = input.userIds.filter((userId) =>
      ctx.users.get(userId).isOnline(),
    )
    ctx.send('online-users', { userIds })
  },
})
```

`isOnline()` knows about the connections on this server instance: one process on Node, one Durable Object on Cloudflare. Channel presence has the same limit.
