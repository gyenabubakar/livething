A channel tracks who is in it. This page covers the two sides of that roster: **managing** membership from server code — subscribing, kicking, and removing members — and **observing** it through the presence frames a channel broadcasts as members come and go. None of this is family-specific; it applies to every channel, static or dynamic.

You reach these through a **channel handle** — `ctx.channel` inside a channel handler, or `ctx.channels.get(...)` from any handler, hook, or scheduled task.

::note
A channel's durable membership rows (see [Channels](/server/capabilities/channels#capabilities-a-channel-may-need)) live in a reserved SQLite table, `__wskit_channel_memberships`, in the server's own SQL storage. Do not write to it or create it yourself — it is owned by the engine. See the [reserved-table list](/server/context-and-storage/sql-and-kv#reserved-wskit-tables) for its column shape and every other table WSKit owns.

If you rename or remove a channel between deploys, its stored membership rows would otherwise linger. WSKit purges these orphaned rows on the next engine boot: a channel that no current definition claims has its durable memberships swept, and the cleanup is noted in the log.
::

## Subscribing from the server

`channelHandle.subscribe(ref, payload?)` joins a connection to a channel from server code. It runs the same flow as a client-initiated subscribe — `check` → `commit` → `onSubscribe` — so the gate still decides:

```typescript [auto-join.ts]
base.onConnect(async (ctx) => {
  // Put every connection into a personal channel on connect.
  await ctx.channels
    .get(inbox.at({ user: ctx.user.id }))
    .subscribe(ctx.connection)
})
```

- It is a **no-op** if the connection is already a member.
- It **rejects** if `check` or `commit` throws — the connection is not added.
- `payload` is passed to the channel's `check` handler and validator, exactly like a client subscribe payload.

## Kicking members

`kick(target, opts)` forces connections out of a channel. One method covers both a soft boot and a hard revoke — the `opts.revoke` flag decides which.

| Call                                                   | Removes                                                           | Durable membership             | Hooks fired                          |
| ------------------------------------------------------ | ----------------------------------------------------------------- | ------------------------------ | ------------------------------------ |
| `kick(target, { reason })` (`revoke` defaults `false`) | live sockets matching `target`                                    | kept — user auto-rejoins later | `onUnsubscribe`, then `onSessionEnd` |
| `kick(target, { reason, revoke: true })`               | **every** live socket of that user (when `target` is a `UserRef`) | deleted (persistent channels)  | `onUnsubscribe`, then `onSessionEnd` |

The `target` chooses which sockets are hit:

- a `UserRef` — kick every one of that user's subscribed connections (all tabs/devices);
- a `TagRef` — kick every socket holding that exact `(kind, group, key)` tag (a `TagRef` already carries all three, so you only pass the ref);
- a tag group handle (from `ctx.tags.ephemeral(group)` / `.persistent(group)`) — kick every socket with any key in the group.

To drop one specific socket without kicking the rest of its user's connections, use `ctx.connections.get(ref).close()` instead — `kick` targets a user, not one connection.

Each kicked socket first receives a `__kicked__ { reason }` frame, then the channel broadcasts `__memberLeave__` / `__memberOffline__` to the remaining members. Pass `{ revoke: true }` to also delete the durable membership row on a persistent channel, so the kicked user is **not** auto-rejoined on their next reconnect — this is the call to reach for when revoking a user's access from an external event (an auth webhook, an admin action). Leaving `revoke` at its default `false` boots the user's current sockets but keeps their seat: a later reconnect auto-rejoins them.

```typescript [kick.ts]
const handleEvict = base.on('evict', {
  input: v.object({ id: v.string(), targetUserId: v.string() }),
  async run(ctx, input) {
    const room = ctx.channels.get(rooms.at({ id: input.id })) // typed handle to room:<id>
    const target = ctx.users.get(input.targetUserId).ref()
    await room.kick(target, {
      reason: 'removed by an admin',
      revoke: true,
    })
  },
})
```

## The membership table

A channel's durable membership rows live in one table, `__wskit_channel_memberships`:

| Column           | Type      | Notes                                                                    |
| ---------------- | --------- | ------------------------------------------------------------------------ |
| `user_id`        | `TEXT`    | The member's user id — part of the primary key.                          |
| `channel_name`   | `TEXT`    | The channel (or the resolved family instance) — part of the primary key. |
| `channel_family` | `TEXT`    | The family key, or `''` for a static channel — part of the primary key.  |
| `joined_at`      | `INTEGER` | Unix ms the membership row was written.                                  |
| `metadata`       | `TEXT`    | Reserved JSON blob for future fields; not read or written yet.           |

The primary key is `(user_id, channel_name, channel_family)`, so re-subscribing an already-durable member updates the row instead of duplicating it. A connection with no `userId` — an anonymous connection — never gets a row here at all: a durable row exists only to auto-rejoin the same user on a future reconnect, and an anonymous connection has no stable id to match against, so it stays in the channel only for the live socket.

The row is per **user**, but a leave is per **connection** — the same user can have this channel open in more than one tab or device at once. Leaving in one tab does not drop the row while another tab is still a member there: WSKit only deletes the durable row (and clears the [inbox](/server/inbox/overview), if the channel uses one) once the user's **last** live connection in that channel leaves. Until then, the other tabs keep receiving messages and the row stays in place, so a refresh in any of them still auto-rejoins.

```typescript [two-tabs.ts]
// Tab A and Tab B are both subscribed to the same room as the same user.
// Tab A leaves — Tab B is still a member, so the durable row survives
// and Tab B keeps receiving messages unaffected.
await roomInTabA.unsubscribe()

// Only once Tab B also leaves does the durable row (and the inbox) drop.
await roomInTabB.unsubscribe()
```

## Presence — who is in, and who is online

A channel keeps every member's roster in sync by broadcasting presence frames. There are two pairs, and the difference matters.

- **`__memberJoin__` / `__memberLeave__`** — the **member list changed**. Someone was added to or removed from the channel.
- **`__memberOnline__` / `__memberOffline__`** — a **socket for an existing member** connected or dropped. The member list did not change.

Why two pairs? On a persistent channel a member can be "in" the channel while temporarily disconnected. Their socket dropping does not remove them from the roster — they will be auto-rejoined on reconnect — so it fires `__memberOffline__`, not `__memberLeave__`. When they reconnect, the roster is unchanged, so it fires `__memberOnline__`, not `__memberJoin__`.

Put plainly:

| Event               | Means                                               | Member list |
| ------------------- | --------------------------------------------------- | ----------- |
| `__memberJoin__`    | A new member joined for the first time              | grew        |
| `__memberLeave__`   | A member truly left (unsubscribe, or kicked)        | shrank      |
| `__memberOnline__`  | An existing member's socket connected (or rejoined) | unchanged   |
| `__memberOffline__` | An existing member's socket dropped                 | unchanged   |

A concrete walk-through on a persistent channel:

::steps{level="3"}

### First subscribe

Alice joins `room:general`. Peers get `__memberJoin__` then `__memberOnline__` — she is both a new member and now online.

### Network blip

Alice's connection drops. She keeps her seat (persistent), so peers get only `__memberOffline__`. The roster still lists Alice.

### Reconnect

Alice's socket comes back and is auto-rejoined. The roster did not change, so peers get only `__memberOnline__` — no second `__memberJoin__`.

### True leave

Alice sends `__unsubscribe__` (or is kicked). Now she really leaves, so peers get `__memberLeave__` then `__memberOffline__`.

::

On an **ephemeral** channel (`membership: 'ephemeral'`) there is no "online but not joined" state — a disconnect is a true leave, so it fires `__memberLeave__`. The `__memberOnline__`/`__memberOffline__` distinction only matters on persistent channels.

### Presence payloads

`__memberJoin__`, `__memberLeave__`, and `__memberOnline__` each carry `{ connectionId, meta }` — the connection's ID and the metadata your upgrade hook set. `__memberOffline__` carries `{ connectionId }` only. Every presence frame is tagged with the channel it belongs to (and the family key for a family channel), so a client subscribed to several channels can tell them apart.

::note
A new member also receives a one-time member sync right after its subscribe is confirmed — the current roster, so it starts with the full list instead of rebuilding it from join frames. The join/online frames keep that list current from then on.
::
