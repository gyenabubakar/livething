A **channel** is a room that the server manages. Connections subscribe to it, and the server keeps the list of members. A broadcast sent to the channel reaches only its members. Each channel has its own events, its own **auth gate**, and its own member list. These are separate from the rest of the socket.

The [`channels()`](/server/capabilities/channels) capability turns channels on. When you list it, you get `base.channel(...)` to declare channels, and `ctx.channels` to reach any channel from any handler.

```typescript [server/rooms.ts]
import { CloseCodes } from '@livething/core'
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { RejectAuth } from '@livething/server/errors'
import { verifySession } from './auth'
import { Message } from './base'

const base = server({
  async authenticate(request) {
    const token = request.headers
      .get('Authorization')
      ?.replace('Bearer ', '')
    const user = await verifySession(token) // your auth: returns { id, name, role } or null
    if (!user) {
      throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [channels()],
})

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
})
```

The [`authenticate`](/server/server/authenticate) hook puts the user's name and role into `ctx.meta`, so the handlers below can read `ctx.meta.name` and `ctx.meta.role`.

## Two sides: contract and handlers

You declare a channel in one call, but it has two sides.

| Side     | What it is                                           | What it covers                                                                                                                                                                                                                                                                                                                                                                                                                                |
| -------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Contract | The config object                                    | The events the channel emits, the `subscribe` schema for the data a client sends when it subscribes, the auth gate functions (`check`, `commit`, `revalidate`), the lifecycle hooks (`onSubscribe`, `onUnsubscribe`, `onSessionEnd`), an `intercept`, and settings like `membership` or `rateLimit` (`rateLimit` exists only when the `rateLimit()` capability is listed). The contract sets the channel's types and the client's view of it. |
| Handler  | The methods on the value `base.channel(...)` returns | `on`, `request`, and the stream methods each return a **handler value**: an object that holds one handler for one event. Pass each value to `assemble()` to turn that handler on. A channel with no handlers, like Huddle's `announcements`, is passed to `assemble()` by itself.                                                                                                                                                             |

In this example, `rooms` also has a `check` that Huddle's own `rooms` does not have:

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import * as v from 'valibot'
import { base, Message } from './base'
import { isBanned } from './helpers'

// Contract side: the config object sets the channel's events and gate.
const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  check(ctx) {
    if (isBanned(ctx.user.id)) {
      throw new Error('banned users may not subscribe')
    }
  },
})

// Handler side: methods on the returned object run code for this channel.
const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: payload.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

The server gets the [channel config](/server/channels/defining) when you assemble either `rooms` or one of its handler values. Only `handleSendMessage` turns on the `send-message` route.

## Static channels vs families

A channel pattern is either a fixed string or a **family** template.

- A **static channel** has one fixed name. `base.channel('announcements', ...)` is exactly one room.
- A **family** matches many names from one template. Pass `base.channel()` the family name and the template in an array, such as `['rooms', 'room:{roomId}']`. This one matches `room:general`, `room:alpha-42`, and so on. Each name is a separate room, and all of them share the same code and the same gate.

```typescript [server/rooms.ts]
import { emits, t } from '@livething/server'
import { base, Message } from './base'

// One fixed room.
const announcements = base.channel('announcements', {
  presence: false, // everyone joins it, so nobody needs the member list
  capabilities: [emits({ announcement: t<{ text: string }>() })],
})

// A family: 'room:general', 'room:design', ... each is its own room.
const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
})
```

`rooms` is the **family key**. You use it to look up a room, for example `ctx.channels.get('rooms', name)`. `room:{roomId}` is the **template**. Inside a handler, `ctx.channel.name` is the matched name, `ctx.channel.family` is the family key, and `ctx.channel.params.roomId` is the part of the name that `{roomId}` matched. Families have their own page: [Dynamic Families](/server/channels/dynamic-families).

## The subscription lifecycle at a glance

When a client subscribes, the channel runs these steps in order before the connection becomes a member.

::steps{level="3"}

### Subscribe arrives

The client asks to join. If the channel config has a `subscribe` schema, the server first validates the data the client sent. Invalid data is rejected here.

### Auth gate: `check`

`check` can be `async`. Use it for token checks, database lookups, or any permission test. Throw an error to reject the subscribe request. The value that `check` returns is passed to `commit`.

### Auth gate: `commit`

`commit` is synchronous. It runs in the same JavaScript tick as the membership write. A tick is one run of code with no `await` in between, so no other code can run between `commit` and the write. Use `commit` for last-moment checks, like a limit on the number of members. Throw an error to reject. After `commit` passes, the connection becomes a member.

### Joined

The server confirms the subscribe to the new member and, when the channel has presence, sends it the current member list. The other members get a **presence** change. Then your `onSubscribe` hook runs. This hook is a good place to send the new member the room's current state.

### Messages and presence

The member can now send the channel's events, and it receives the channel's broadcasts. When other members join or leave, presence changes keep every member's list up to date, unless you turned [presence off](/server/channels/membership-and-presence#turning-presence-off).

::

::note
These steps are for a new subscribe. A channel's membership is **ephemeral** by default: it ends when the connection closes, and the client subscribes again after a reconnect. With `membership: 'persistent'`, the membership is saved, and the member joins the channel again automatically after a reconnect. On that automatic rejoin, the channel runs [`revalidate`](/server/channels/auth-gate) instead of `check` and `commit`. The saved membership already exists, so `revalidate` only confirms that the member may still be in the channel. If `revalidate` throws, the server deletes the saved membership and the connection does not rejoin.
::

The auth gate has its own page: [Auth Gate](/server/channels/auth-gate). The [Membership & Presence](/server/channels/membership-and-presence) page explains presence messages and how to manage members from server code.
