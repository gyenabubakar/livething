A **channel** is a room that the server manages. Connections subscribe to it (ask to join it), and the server keeps the list of members. A broadcast sent to the channel reaches only its members. Each channel has its own events, its own **auth gate** (the code that decides who may join), and its own member list. These are separate from the rest of the socket.

The [`channels()`](/server/capabilities/channels) capability turns channels on. When you list it, you get `base.channel(...)` to declare channels, and `ctx.channels` to reach any channel from any handler.

```typescript [chat.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { RejectUpgrade } from '@livething/server/errors'

const base = server({
  upgrade(request) {
    const username = new URL(request.url).searchParams.get('username')
    if (!username) throw RejectUpgrade(4002, 'Missing username')
    return { userId: username, meta: { username } }
  },
  capabilities: [channels()],
})

const lobby = base.channel('lobby', {
  capabilities: [
    emits({ message: t<{ text: string; from: string }>() }),
  ],
})
```

The `upgrade` hook puts the username into `ctx.meta`, so the handlers below can read `ctx.meta.username`. See [Upgrade](/server/server/upgrade) for how `upgrade` works.

## Two sides: contract and handlers

You declare a channel in one call, but it has two sides.

| Side     | What it is                                           | What it covers                                                                                                                                                                                                                                                                                                                                               |
| -------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Contract | The config object                                    | The events the channel emits, the `subscribe` schema for the data a client sends when it subscribes, the auth gate functions (`check`, `commit`, `revalidate`), and settings like `membership` or `rateLimit` (`rateLimit` exists only when the `rateLimit()` capability is listed). The contract sets the channel's types and the client's view of it.      |
| Handler  | The methods on the value `base.channel(...)` returns | `on`, `request`, and the stream methods each return a **handler value**: an object that holds one handler for one event. Pass each value to `assemble()` to turn that handler on. The lifecycle hooks `subscribe`, `unsubscribe`, and `sessionEnd` belong to the channel object. They run when you assemble the channel object or any of its handler values. |

```typescript [chat.ts]
import { emits, t } from '@livething/server'
import * as v from 'valibot'

// Contract side: the config object sets the channel's events and gate.
const room = base.channel('room', {
  capabilities: [
    emits({
      'room-message': t<{ text: string; from: string }>(),
    }),
  ],
  check(ctx) {
    if (ctx.meta.username === 'blocked-user') {
      throw new Error('blocked-user may not subscribe')
    }
  },
})

// Handler side: methods on the returned object run code for this channel.
const handleSend = room.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('room-message', {
      text: payload.text,
      from: ctx.meta.username,
    })
  },
})
```

The server gets the channel config when you assemble either `room` or one of its handler values. Only `handleSend` turns on the `send-message` route.

See [Defining Channels](/server/channels/defining) for the full contract config and every handler method.

## Static channels vs families

A channel pattern is either a fixed string or a **family** template.

- A **static channel** has one fixed name. `base.channel('lobby', ...)` is exactly one room.
- A **family** matches many names from one template. `base.channel(['rooms', 'room:{id}'], ...)` matches `room:general`, `room:alpha-42`, and so on. Each name is a separate room, and all of them share the same code and the same gate.

```typescript [rooms.ts]
// One fixed room.
const lobby = base.channel('lobby', {
  /* ... */
})

// A family: 'room:general', 'room:design-team', ... each is its own room.
const rooms = base.channel(['rooms', 'room:{id}'], {
  /* ... */
})
```

`rooms` is the **family key**. You use it to look up a room, for example `ctx.channels.get('rooms', name)`. `room:{id}` is the **template**. Inside a handler, `ctx.channel.name` is the matched name, `ctx.channel.family` is the family key, and `ctx.channel.params.id` is the part of the name that `{id}` matched. Families have their own page: [Dynamic Families](/server/channels/dynamic-families).

## The subscription lifecycle at a glance

When a client subscribes, the channel runs these steps in order before the connection becomes a member.

::steps{level="3"}

### Subscribe arrives

The client asks to join. If the channel config has a `subscribe` schema, the server first validates the data the client sent. Invalid data is rejected here.

### Auth gate: `check`

`check` can be `async`. Use it for token checks, database lookups, or any permission test. Throw an error to reject the subscribe request. The value that `check` returns is passed to `commit`.

### Auth gate: `commit`

`commit` is synchronous. It runs in the same JavaScript tick as the membership write. A tick is one run of code with no `await` in between, so no other code can run between `commit` and the write. Use `commit` for last-moment checks, like a limit on the number of members. Throw an error to reject. After `commit` passes, the connection becomes a member.

### Joined

The server confirms the subscribe to the new member and sends it the current member list. The other members get a **presence** update (a message that says who joined or who is online). Then your `subscribe` hook runs. This hook is a good place to send the new member the room's current state.

### Messages and presence

The member can now send the channel's events, and it receives the channel's broadcasts. When other members join or leave, presence messages keep every member's list up to date.

::

::note
These steps are for a new subscribe. A channel's membership is **persistent** by default: the membership is saved, and the member joins the channel again automatically after a reconnect. On that automatic rejoin, the channel runs `revalidate` instead of `check` and `commit`. The saved membership already exists, so `revalidate` only confirms that the member may still be in the channel. If `revalidate` throws, the server deletes the saved membership and the connection does not rejoin. See [Auth Gate](/server/channels/auth-gate).
::

The auth gate has its own page: [Auth Gate](/server/channels/auth-gate). The [Membership & Presence](/server/channels/membership-and-presence) page explains presence messages and how to manage members from server code.
