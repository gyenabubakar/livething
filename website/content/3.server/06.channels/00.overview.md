A **channel** is a server-managed room. Connections subscribe to it, the server tracks who is in, and a broadcast sent to the channel reaches only its members. Each channel has its own events, its own auth gate, and its own membership list — separate from the rest of the socket.

Channels are turned on by the [`channels()`](/server/capabilities/channels) capability. Listing it grants `base.channel(...)` for declaring channels and the `ctx.channels` accessor for reaching one from any handler.

```typescript [chat.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'

const base = server({
  capabilities: [channels()],
})

const lobby = base.channel('lobby', {
  capabilities: [
    emits({ message: t<{ text: string; from: string }>() }),
  ],
})
```

## Two sides: contract and handlers

A channel is declared in one call but has two sides.

| Side     | What it is                                           | What it covers                                                                                                                                                                                                                                                                    |
| -------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Contract | The config object                                    | The events it emits, the schema for the subscribe payload, the auth gates (`check`, `commit`, `revalidate`), and flags like `membership` or `rateLimit`. This shapes the channel's type and the client's view of it.                                                              |
| Handler  | The methods on the value `base.channel(...)` returns | `on`, `request`, and stream methods create routed handler values. Include each value in `assemble()` to run it. The lifecycle hooks `subscribe`, `unsubscribe`, and `sessionEnd` belong to the channel object and run when that object or any of its handler values is assembled. |

```typescript [chat.ts]
import { emits, t } from '@livething/server'
import * as v from 'valibot'

// Contract side: the config object shapes the channel's events and gate.
const room = base.channel('room', {
  capabilities: [
    emits({
      'room-message': t<{ text: string; from: string }>(),
    }),
  ],
  check(ctx) {
    if (ctx.meta.username === 'blocked-user') {
      throw new Error('blocked-user may not subscribe')
    }
  },
})

// Handler side: methods on the returned object run code for this channel.
const handleSend = room.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('room-message', {
      text: payload.text,
      from: ctx.meta.username,
    })
  },
})
```

The channel config reaches the server when you assemble either `room` or one of its handler values. Only `handleSend` activates the `send-message` route.

See [Defining Channels](/server/channels/defining) for the full contract config and every handler method.

## Static channels vs families

A channel pattern is either a fixed string or a **family** template.

- A **static channel** has one fixed name. `base.channel('lobby', ...)` is exactly one room.
- A **family** matches many names from one template. `base.channel(['rooms', 'room:{id}'], ...)` matches `room:general`, `room:alpha-42`, and so on — each a separate room, all sharing the same code and gate.

```typescript [rooms.ts]
// One fixed room.
const lobby = base.channel('lobby', {
  /* ... */
})

// A family: 'room:general', 'room:design-team', ... each its own room.
const rooms = base.channel(['rooms', 'room:{id}'], {
  /* ... */
})
```

`rooms` is the **family key** (used in `ctx.channels.get('rooms', name)` lookups) and `room:{id}` is the **template**. Inside a handler, `ctx.channel.name` is the matched name, `ctx.channel.family` is the key, and `ctx.channel.params.id` is the captured part. Families get their own page: [Dynamic Families](/server/channels/dynamic-families).

## The subscription lifecycle at a glance

When a client subscribes, the channel runs a fixed sequence before that connection becomes a member.

::steps{level="3"}

### Subscribe arrives

The client asks to join. If the channel declares a `subscribe` schema, the payload it sent is validated first. A bad payload is rejected here.

### Auth gate — `check`

`check` runs async. Use it for token checks, database lookups, or any permission test. Throw to reject the subscribe. Whatever it returns is handed to `commit`.

### Auth gate — `commit`

`commit` runs synchronously, in the same tick that membership is written. Use it for last-moment checks like a capacity limit. Throw to reject. This is the point where the connection actually becomes a member.

### Joined

The server confirms the subscribe to the new member and sends it the current member list. Existing members get a presence update. Then your `subscribe` hook runs — a good place to push initial state.

### Messages and presence flow

The member can now send the channel's events and receives its broadcasts. As others join or drop, presence frames keep every member's roster in sync.

::

::note
That sequence is for a fresh subscribe. When a member of a **persistent** channel reconnects, the channel runs `revalidate` instead of `check` / `commit` — the durable membership is already on record, so the gate re-confirms it rather than re-joining from scratch. A throw from `revalidate` drops the auto-rejoin. See [Auth Gate](/server/channels/auth-gate).
::

The auth gate gets its own page: [Auth Gate](/server/channels/auth-gate). Presence frames and server-side membership are explained on the [Membership & Presence](/server/channels/membership-and-presence) page.
