This page covers two kinds of server-side errors:

- **Typed errors.** You declare them so they appear on the client contract, and the client can check for them by code.
- **Server-side control-flow errors.** You throw them to close a socket, refuse an upgrade, drop a frame, or retry a message. They change what the server does next.

The shared error _model_ lives in the Core section: what a `LiveThingError` is, how `.matches()` works, the built-in errors, and the close codes. This page links to those pages and does not repeat them.

## Declaring typed errors

You build an error with `error('code', schema?)`. The schema is optional and describes the error's **detail** (the extra data sent with the error). Then you register the errors the client should know about with `errors([...])`. Both functions come from `@livething/server`. `error` is also exported from `@livething/core`, so you can use it in files that both the server and the client import.

```typescript [errors.ts]
import { error } from '@livething/server'
import * as v from 'valibot'

export const NotFound = error(
  'not-found',
  v.object({ id: v.string() }),
)
export const Forbidden = error(
  'forbidden',
  v.object({ reason: v.string() }),
)
```

`error(...)` returns a **factory**: a function that builds a new error value each time you call it. You call the factory and throw the value it returns. Registering the factories with `errors([...])` puts them on the client contract, so the client can match them by code:

```typescript [server.ts]
import { errors, server } from '@livething/server'
import { Forbidden, NotFound } from './errors'

const base = server({
  capabilities: [errors([NotFound, Forbidden])],
})
```

### The contract slice

`errors([...])` fills the `errors` key of the client contract. This key lists the typed error codes the client can receive and narrow on (narrowing means TypeScript knows the exact detail type after you check the code). The two errors above add these entries, next to the built-in error codes:

```typescript [chat-socket.ts]
interface ChatSocket {
  errors: {
    'not-found': { id: string }
    forbidden: { reason: string }
  }
}
```

See [The Error Model](/core/error-model) for the shared `LiveThingError` shape and `.matches()`.

::note
`error('code', schema?)` throws when you declare the error if the code is empty, starts or ends with `__`, or is a code that a LiveThing built-in error already uses (see [Built-in Errors](/core/builtin-errors)). `errors([...])` needs at least one error. An empty list is a type error. It also throws if you list the same code twice.
::

### Throwing from a handler

Call a registered factory and throw the result. LiveThing catches it and sends a typed error frame to the client:

```typescript [handlers.ts]
const handleLookup = base.on('lookup-room', {
  input: v.object({ roomId: v.string() }),
  run(ctx, input) {
    throw NotFound({ id: input.roomId })
  },
})
```

### Code-only errors

An error with no schema has no detail. Declare it with just a code. To throw it, **call the factory**. If you throw the factory function itself, LiveThing does not see it as an error, and the client receives `internal-error`:

```typescript [code-only.ts]
import { error } from '@livething/server'

const RoomFull = error('room-full')

const handleJoin = base.on('join-room', {
  input: v.object({ roomId: v.string() }),
  run() {
    throw RoomFull() // call it, do not throw RoomFull itself
  },
})
```

::caution
If you throw a `LiveThingError` whose code is **not** in your `errors([...])` list, LiveThing does not send that code to the client. It sends the built-in `internal-error` code instead and logs a warning on the server that the code was never declared. The client cannot narrow on a code the contract does not declare. Register an error to send its real code and detail to the client.
::

## Server-side control-flow errors

These are different from the typed errors above. They are not part of the shared error model, and most of them are never sent to the client. They control what the server does next. Import them from `@livething/server/errors`:

```typescript [imports.ts]
import {
  Block,
  CloseCodes,
  Defer,
  DeferExhausted,
  Disconnect,
  RejectUpgrade,
} from '@livething/server/errors'
```

| Error                         | Where to use it                               | What the client sees                               |
| ----------------------------- | --------------------------------------------- | -------------------------------------------------- |
| `Disconnect(code, reason)`    | any handler                                   | the socket closes with that code                   |
| `Block`                       | inbound `intercept` only                      | nothing; the frame is dropped                      |
| `RejectUpgrade(code, reason)` | `upgrade` hook only                           | the LiveThing connection is refused during upgrade |
| `Defer(delayMs)`              | `on()` handlers only                          | nothing; the server retries the message            |
| `DeferExhausted`              | passed to `onError` after the retries run out | nothing; it is a server-only signal                |

### Disconnect: close the socket

Throw `Disconnect(code, reason)` to stop a handler and close the connection. If you need to close the connection but keep running code (for example, to log or clean up), call `ctx.close(code, reason)` instead. `ctx.close` closes without throwing.

```typescript [disconnect.ts]
const handleForceDisconnect = base.on('force-disconnect', {
  input: v.object({}),
  run() {
    throw Disconnect(CloseCodes.BANNED, 'too many violations')
  },
})
```

`CloseCodes` is the set of named WebSocket close codes. See [Close Codes](/core/close-codes) for the valid ranges and the full list. If a server close call gets a code that is not a valid close code, LiveThing logs the mistake and closes with `1011` and the reason `Internal error` instead. The connection still closes, even though the bad value came from your code.

### Block: drop an inbound frame

Throw `Block` from an inbound `intercept` to drop the current frame. An **intercept** is a hook that runs for every incoming frame before validation and your handler (it needs the [`intercepts()`](/server/capabilities/intercepts) capability). `Block` is a plain value, so you throw it without calling it. The handler does not run and **no error is sent to the client**. LiveThing catches `Block` only on the inbound path. If you throw it from an `onOutgoing` hook, LiveThing does not recognize it and treats it as an unhandled error.

```typescript [block.ts]
import { Block } from '@livething/server/errors'

base.intercept((ctx, frame) => {
  if (frame.event === 'spam') throw Block // drop it; the client receives nothing
})
```

### RejectUpgrade: refuse the connection

Throw `RejectUpgrade(code, reason)` to refuse a WebSocket upgrade before LiveThing creates a connection. The **upgrade** is the first HTTP request that asks the server to switch to WebSocket. `RejectUpgrade` is **only valid inside the `upgrade` hook**. If you throw it anywhere else, LiveThing treats it as an unrecognized error.

A browser WebSocket cannot set custom headers, so this example reads the token from the URL query:

```typescript [upgrade.ts]
const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await validateToken(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid token')
    return { userId: user.id, meta: { userId: user.id } }
  },
})
```

You can use two kinds of code here:

- An HTTP error status from `400` to `599` rejects the HTTP upgrade request directly.
- A valid WebSocket close code, such as `CloseCodes.AUTH_INVALID` (`4002`), accepts the WebSocket handshake and then closes the socket right away with that code and reason.

If the code is not valid (for example a decimal number, a reserved close code such as `1006`, or an HTTP status outside `400` to `599`), LiveThing logs it and rejects the upgrade with HTTP `403`. This way a bad value still refuses the connection, and each platform adapter gets a known response to send.

### Defer: retry a message later

Throw `Defer(delayMs)` to put the current message back in the queue and run the handler again after a delay in milliseconds. The delay must be a positive whole number. Use `Defer` when the handler cannot finish yet, for example when a lock is held or a resource is not ready.

`Defer` retries up to **3 times**, so the handler runs **at most 4 times** in total (the first attempt plus 3 retries). It is valid **only in `on()` handlers**, because a retry runs the whole frame again. That is safe only for an `on()` event:

- A **request handler** would run again and send a second answer to a request the client has already finished.
- An **intercept** runs for every kind of frame (for example a request or a stream frame), not only `on()` events.
- A **stream handler** cannot restart a generator that has already sent chunks.

If you throw `Defer` from any of these, LiveThing logs a mistake and the client receives `internal-error`.

This handler is not ready on the first attempt, so it defers once and succeeds on the retry:

```typescript [defer.ts]
const handleSyncDraft = base.on('sync-draft', {
  input: v.object({}),
  async run(ctx) {
    const key = `sync-draft:${ctx.connection.id}`
    const attempts =
      ((await ctx.kv.get(key)) as number | undefined) ?? 0
    await ctx.kv.set(key, attempts + 1)
    if (attempts < 1) throw Defer(50) // not ready; try again in 50 ms
    await ctx.kv.delete(key)
    ctx.send('draft-synced', { received: true })
  },
})
```

### DeferExhausted: Defer ran out of retries

When a message still throws `Defer` after the last retry, LiveThing drops the message and calls your `onError` handler with a `DeferExhausted` error. The same happens when one connection already has 128 deferred messages waiting. `DeferExhausted` is **never sent to the client**. It is a server-only signal, so you can store or report the failed message yourself. Its `detail` has `event`, `payload`, and `retries`:

```typescript [error-hook.ts]
base.onError((ctx, error, event) => {
  if (DeferExhausted.matches(error)) {
    ctx.send('sync-failed', {
      event: event ?? 'unknown',
      retries: error.detail.retries,
    })
  }
})
```
