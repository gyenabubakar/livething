This page covers two kinds of server-side errors:

- **Typed errors.** You declare them so they appear on the client contract, and the client can check for them by code.
- **Server-side control-flow errors.** You throw them to close a socket, refuse an upgrade, or drop a frame. They change what the server does next.

The shared error _model_ lives in the Core section: what a `LiveThingError` is, how `.matches()` works, the built-in errors, and the close codes. This page links to those pages and does not repeat them.

## Declaring typed errors

You build an error with `error('code', schema?)`. The schema is optional and describes the error's **detail**. Then you register the errors the client should know about with `errors([...])`. Both functions come from `@livething/server`. `error` is also exported from `@livething/core`, so you can use it in files that both the server and the client import.

`error(...)` returns a **factory**: a function that builds a new error value each time you call it. You call the factory and throw the value it returns. Registering the factories with `errors([...])` puts them on the client contract, so the client can match them by code. Huddle keeps its errors in `shared/errors.ts`, so the server and the client can both import them. Its definition declares all three:

::code-group

```typescript [shared/errors.ts]
import { error } from '@livething/server'
import * as v from 'valibot'

export const NotFound = error(
  'not-found',
  v.object({ id: v.string() }),
)
export const Forbidden = error(
  'forbidden',
  v.object({ reason: v.string() }),
)
export const RoomFull = error(
  'room-full',
  v.object({ limit: v.number() }),
)
```

```typescript [server/huddle-definition.ts]
import { errors, server } from '@livething/server'
import { Forbidden, NotFound, RoomFull } from '../shared/errors'

const base = server({
  capabilities: [errors([NotFound, Forbidden, RoomFull])],
})
```

::

### The contract slice

`errors([...])` fills the `errors` key of the client contract. This key lists the typed error codes the client can receive and narrow on. The three errors above add these entries, next to the built-in error codes:

```typescript [shape]
interface HuddleSocket {
  errors: {
    'not-found': { id: string }
    forbidden: { reason: string }
    'room-full': { limit: number }
  }
}
```

See [The Error Model](/core/error-model) for the shared `LiveThingError` shape and `.matches()`.

::note
`error('code', schema?)` throws when you declare the error if the code is empty, starts or ends with `__`, or is a code that a LiveThing built-in error already uses (see [Built-in Errors](/core/builtin-errors)). `errors([...])` needs at least one error. An empty list is a type error. It also throws if you list the same code twice.
::

### Throwing from a handler

Call a registered factory and throw the result. LiveThing catches it and sends a typed error frame to the client:

In this version of `get-profile`, the handler throws `NotFound` when there is no profile. `NotFound` is defined inline here, to keep the example in one file:

```typescript [server/huddle-definition.ts]
import { error, errors, server } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'
import { loadProfile } from './huddle-data'

const NotFound = error('not-found', v.object({ id: v.string() }))

const base = server({
  capabilities: [clientRequests(), errors([NotFound])],
})

const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  async run(ctx, input) {
    const profile = await loadProfile(input.userId)
    if (!profile) throw NotFound({ id: input.userId })

    return profile
  },
})
```

### Code-only errors

An error with no schema has no detail. Declare it with just a code. To throw it, **call the factory**. If you throw the factory function itself, LiveThing does not see it as an error, and the client receives `internal-error`. `Banned` is an extra error for this example. Huddle does not declare it, so you would also add it to `errors([...])`, as the warning below explains:

```typescript [server/banned-error.ts]
import { error } from '@livething/server'
import * as v from 'valibot'
import { rooms } from './base'
import { isBanned } from './huddle-data'

const Banned = error('banned')

const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx) {
    if (isBanned(ctx.user.id)) throw Banned() // call it, do not throw Banned itself
  },
})
```

::caution
If you throw a `LiveThingError` whose code is **not** in your `errors([...])` list, LiveThing does not send that code to the client. It sends the built-in `internal-error` code instead and logs a warning on the server that the code was never declared. The client cannot narrow on a code the contract does not declare. Register an error to send its real code and detail to the client.
::

## Server-side control-flow errors

These are different from the typed errors above. They are not part of the shared error model, and most of them are never sent to the client. They control what the server does next. Import them from `@livething/server/errors`:

```typescript [server/huddle-definition.ts]
import {
  Block,
  CloseCodes,
  Disconnect,
  RejectUpgrade,
} from '@livething/server/errors'
```

| Error                         | Where to use it          | What the client sees                               |
| ----------------------------- | ------------------------ | -------------------------------------------------- |
| `Disconnect(code, reason)`    | any handler              | the socket closes with that code                   |
| `Block`                       | inbound `intercept` only | nothing; the frame is dropped                      |
| `RejectUpgrade(code, reason)` | `upgrade` hook only      | the LiveThing connection is refused during upgrade |

### Disconnect: close the socket

Throw `Disconnect(code, reason)` to stop a handler and close the connection. If you need to close the connection but keep running code (for example, to log or clean up), call `ctx.close(code, reason)` instead. `ctx.close` closes without throwing.

```typescript [server/disconnect-banned.ts]
import { CloseCodes, Disconnect } from '@livething/server/errors'
import * as v from 'valibot'
import { rooms } from './base'
import { isBanned } from './huddle-data'

const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx) {
    if (isBanned(ctx.user.id)) {
      throw Disconnect(CloseCodes.BANNED, 'too many violations')
    }
  },
})
```

`CloseCodes` is the set of named WebSocket close codes. See [Close Codes](/core/close-codes) for the valid ranges and the full list. If a server close call gets a code that is not a valid close code, LiveThing logs the mistake and closes with `1011` and the reason `Internal error` instead. The connection still closes, even though the bad value came from your code.

### Block: drop an inbound frame

Throw `Block` from an inbound `intercept` to drop the current frame. An **intercept** is a hook that runs for every incoming frame before validation and your handler (see [Intercept](/server/lifecycle-and-intercept/intercept)). `Block` is a plain value, so you throw it without calling it. The handler does not run and **no error is sent to the client**. `Block` exists only on the inbound path. The [`onOutgoing`](/server/lifecycle-and-intercept/outgoing) hook runs after a frame was sent, so it cannot drop one. A `Block` thrown there is logged as a failed hook, like any other error.

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { Block } from '@livething/server/errors'
import { isMuted } from './huddle-data'

export const base = server({
  intercept(ctx, frame) {
    // Muted users are dropped here, not shown an error.
    if (isMuted(ctx.user.id)) throw Block // drop it; the client receives nothing
  },
})
```

### RejectUpgrade: refuse the connection

Throw `RejectUpgrade(code, reason)` to refuse a WebSocket upgrade before LiveThing creates a connection. The **upgrade** is the first HTTP request that asks the server to switch to WebSocket. `RejectUpgrade` is **only valid inside the `upgrade` hook**. If you throw it anywhere else, LiveThing treats it as an unrecognized error.

A browser WebSocket cannot set custom headers, so this example reads the token from the URL query:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import { verifySession } from './auth'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user) {
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
})
```

You can use two kinds of code here:

- An HTTP error status from `400` to `599` rejects the HTTP upgrade request directly.
- A valid WebSocket close code, such as `CloseCodes.AUTH_INVALID` (`4002`), accepts the WebSocket handshake and then closes the socket right away with that code and reason.

If the code is not valid (for example a decimal number, a reserved close code such as `1006`, or an HTTP status outside `400` to `599`), LiveThing logs it and rejects the upgrade with HTTP `403`. This way a bad value still refuses the connection, and each platform adapter gets a known response to send.

### Retrying work that is not ready yet

When a handler cannot finish yet, for example because a service it calls is busy, retry inside the handler. Wait with `await` between tries. The connection's ordered handlers wait for this one to finish, so the next message from the same connection still runs after it, in order (see [Per-connection queue](/server/handlers/per-connection-queue)).

For work that should run later, even after a restart, queue a scheduled task with `ctx.schedule(taskId, { time, data })` from the [`scheduled({...})`](/server/capabilities/scheduled) capability. The handler returns at once, and the task body runs at `time`.
