A **channel** is a room that the server manages. Connections subscribe to it and become its **members**. Each channel has its own events and its own **gate** (a function that decides who may join). It also has its own **lifecycle hooks** (functions that run when a member joins or leaves). A chat lobby, a game table and a live editing session for one document are all examples of channels.

The `channels()` capability turns on `base.channel(name, config)` and the `ctx.channels` accessor. Import it from `@livething/server/channels`:

```typescript [server/rooms.ts]
import { channels } from '@livething/server/channels'
```

## Defining a channel

Add `channels()` to the capabilities list, then declare a channel with `base.channel(name, config)`. The call returns a channel object. You create the channel's handlers with its methods. Huddle's `rooms` family is a channel: each room is one member of that family, with its own gate and a message handler. The `upgrade` function stores each user's role in `ctx.meta`, so the handlers can read it:

```typescript [server/rooms.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import * as v from 'valibot'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [channels()],
})

export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
  check(ctx) {
    const isMember = ctx.sql
      .exec(
        'SELECT 1 FROM room_members WHERE room = ? AND user_id = ?',
        ctx.channel.params.roomId,
        ctx.user.id,
      )
      .one()
    if (!isMember) throw new Error('not a member of this room')
  },
})

export const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

::note
`rooms.on(...)` creates a handler value. Add `handleSendMessage` to `base.assemble({ handlers: [...] })`. Only then does the handler run and appear in `InferClient`. If you pass `rooms` itself, LiveThing includes the channel's config and lifecycle hooks, but none of its event handlers.
::

Inside a channel handler, `ctx.channel` has three ways to send:

- `ctx.channel.broadcast(...)` sends to every other member. By default it skips the connection that called the handler. Pass `{ includeSelf: true }` to include it.
- `ctx.channel.broadcastTo(...)` sends to a chosen group of members.
- `ctx.channel.send(...)` sends to the calling connection only.

For more detail on writing channels, see [Defining Channels](/server/channels/defining).

## The contract slice

The **client contract** is the TypeScript type that tells the client which events and requests the server has. `channels()` fills its `channels` key. Each channel has its own small contract inside that key, with the same `incoming` and `outgoing` keys, but only for that room:

```typescript [client/socket.ts]
interface HuddleSocket {
  channels: {
    rooms: {
      incoming: {
        message: Message
      }
      outgoing: {
        'send-message': { text: string }
      }
    }
  }
}
```

The directions switch in the same way as in the top-level contract. The events in the channel's `emits(...)` become the client's `incoming`, and the channel's handlers become the client's `outgoing`.

## Config at a glance

`base.channel(name, config)` accepts these config fields:

| Field                      | What it does                                                                                                                                   |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `subscribe`                | Schema that checks the payload a client sends when it subscribes.                                                                              |
| `capabilities`             | Capabilities for this channel only: `emits(...)`, `serverRequests(...)`, and the channel-only capabilities `inbox()` and `readReceipts()`.     |
| `check(ctx, input)`        | Auth gate. Throw to reject the subscribe. The value it returns goes to `commit`.                                                               |
| `commit(ctx, checkResult)` | Runs after `check` accepts the subscribe. Throw to reject.                                                                                     |
| `revalidate(ctx)`          | Checks an existing membership again when the member rejoins after a reconnect. Throw to drop the member.                                       |
| `membership`               | `'persistent'` (the default) or `'ephemeral'`. A persistent membership survives a reconnect. An ephemeral one ends when the connection closes. |
| `replay`                   | `true` or `false`. Turns on or off sending missed messages again after a reconnect, for this channel only.                                     |
| `rateLimit`                | Limits how fast a member can send to this channel. Present only when the `rateLimit()` capability is listed.                                   |

On the returned channel object you add handlers and lifecycle hooks: `.on`, `.request`, `.stream` / `.resumableStream` / `.recordedStream`, `.subscribe`, `.unsubscribe`, `.sessionEnd`, `.intercept`, and `.replay`. A family channel (see below) also has `.at(...)`.

For the auth gate in depth, see [Auth Gate](/server/channels/auth-gate). For streams and requests that belong to a channel, see [Scoped Streams & Requests](/server/channels/scoped-streams-requests).

## Dynamic families

A channel can be a **family**: one pattern that creates a separate channel for each ID. Declare it with a `[family, template]` pair. This is exactly how Huddle's rooms work: the family is `rooms`, and the template `room:{roomId}` matches names such as `room:general`:

```typescript [server/rooms.ts]
const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
})

const handleSendMessage = rooms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

To reach one channel in the family, build a reference with `.at(...)` and pass it to `ctx.channels.get(...)` inside any handler:

```typescript [server/rooms.ts]
const ref = rooms.at({ roomId: 'general' }) // resolves room:general
ctx.channels.get(ref).broadcast('message', {
  id: crypto.randomUUID(),
  text: 'the room will archive in 5 minutes',
  from: 'system',
  sentAt: Date.now(),
})
```

See [Dynamic Families](/server/channels/dynamic-families) for everything a family can do.

## Acting on a channel from the server

`ctx.channels.get(name)` returns a **channel handle**. For a family, use `.get(ref)` with a reference from `.at(...)`. A channel handle points to the same room that members use, but you can use it from any handler, lifecycle hook or scheduled task. If you pass a name that you never declared with `base.channel()`, it throws `ChannelNotFound`. The handle has these methods:

| Method                                | What it does                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `send(event, payload)`                | Sends a channel event to the current connection. Returns `1` when it is delivered and `0` when it is not.                                                                                                                                                                                                                                              |
| `broadcastTo(to, event, payload)`     | Sends to a chosen group of members: a `ConnectionRef`, `UserRef`, `TagRef` or tag group handle. Returns the number of sockets that received it.                                                                                                                                                                                                        |
| `broadcast(event, payload, options?)` | Sends to every member. It skips the calling connection by default. Pass `{ includeSelf: true }` to include it.                                                                                                                                                                                                                                         |
| `members()`                           | Lists the connections that are subscribed now (`ConnectionInfo[]`).                                                                                                                                                                                                                                                                                    |
| `subscribe(ref, payload?)`            | Subscribes a connection from server code. It runs the same steps as a client subscribe: `check`, then `commit`, then the channel's `.subscribe` hook. It does nothing if the connection is already a member. It rejects if `check` or `commit` throws.                                                                                                 |
| `kick(target, opts)`                  | Removes connections from the channel. `target` is a `UserRef` (all of that user's member sockets), a `TagRef` (every socket with that tag key), or a tag group handle (every socket in the group). Each removed socket receives `__kicked__ { reason }`, then `__memberLeave__` / `__memberOffline__` goes to the other members. `reason` is required. |

The handle also has `name`, `family` and `params`, and the `inbox()` and `readReceipts()` methods. Those two return `null` when the channel does not have that capability.

```typescript [admin.ts]
const handleModerate = base.on('kick-user', {
  input: v.object({ targetUserId: v.string(), roomId: v.string() }),
  async run(ctx, input) {
    const room = ctx.channels.get('rooms', `room:${input.roomId}`)
    const target = ctx.users.get(input.targetUserId).ref()
    await room.kick(target, {
      reason: 'removed by a moderator',
      revoke: true,
    })
  },
})
```

With `revoke: false` (the default), `kick` removes only the user's live connections from the channel. Their saved membership stays, so the user joins the channel again automatically on their next connection. With `revoke: true`, `kick` also deletes the user's saved membership, so they do not join again. [Membership & Presence](/server/channels/membership-and-presence) covers the full `kick` target rules and the `__kicked__` wire frame.

## Capabilities a channel may need

By default, a channel keeps its members across a reconnect, and this needs no extra capability. A channel needs extra capabilities only for the features in the table below. LiveThing checks each one. If one is missing, you get a type error or an error when the channel is defined, and the message names the capability to add.

| Feature                                                            | Needs                                                                                 |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| Channel streams (`.stream`, `.resumableStream`, `.recordedStream`) | The matching stream capability: `stream()`, `resumableStream()` or `recordedStream()` |
| Channel requests (`.request`)                                      | Root `clientRequests()`                                                               |
| Channel intercept (`.intercept`)                                   | Root `intercepts()`                                                                   |
| Channel `capabilities: [serverRequests(...)]`                      | Root `serverRequests()`                                                               |
| A custom `.replay`                                                 | `replay.custom()`                                                                     |
| `replay: true \| false`                                            | A built-in replay capability: `replay.history()` or `replay.snapshot()`               |
| `inbox()` in the channel's own `capabilities`                      | `channels()`, `sequence({ persist: true })` and `dedup()` on the host                 |
| `readReceipts()` in the channel's own `capabilities`               | `inbox()` on the same channel                                                         |

An app that uses only basic channels needs none of these. Add a capability only when a channel uses that feature. See [inbox](/server/capabilities/inbox) and [read receipts](/server/capabilities/read-receipts).
