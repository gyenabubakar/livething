**Awareness** is live state for each connection in a channel: the message a member is reading, where their cursor is, what they have selected. The client sets it, the server checks it, and the other members of the channel get it.

Only the newest value counts. The server keeps no history of it, and the state of a connection is gone when the connection leaves the channel. For data that must be kept, send normal channel events.

`awareness()` is a **channel-only** capability, like [`inbox()`](/server/capabilities/inbox). You list it inside a channel's own `capabilities`. You never list it in the top-level `server({ capabilities: [...] })` array. A server that never imports it does not ship the awareness runtime.

## How to enable

Import `awareness` from `@livething/server/awareness` and list `awareness()` in the channel's `capabilities`. Then set the channel's `awareness` option. The host needs only [`channels()`](/server/capabilities/channels). Huddle's `rooms` channel uses awareness to show who is reading which message:

```typescript [server/base.ts]
import { server } from '@livething/server'
import { awareness } from '@livething/server/awareness'
import { channels } from '@livething/server/channels'
import { CloseCodes, RejectAuth } from '@livething/server/errors'
import * as v from 'valibot'
import { verifySession } from './auth'

const base = server({
  async authenticate(request) {
    const token = request.headers
      .get('Authorization')
      ?.replace('Bearer ', '')
    const user = await verifySession(token)
    if (!user) {
      throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { userId: user.id, name: user.name, role: user.role },
    }
  },
  capabilities: [channels()],
})

// Huddle's `rooms` channel, with only its awareness.
export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [awareness()],
  awareness: {
    state: v.object({ viewingMessageId: v.nullable(v.string()) }),
    // Guests can read a room, but other members do not see where they are.
    check: (ctx) => ctx.meta.role !== 'guest',
  },
})
```

`awareness()` takes no options. It adds the awareness code to the channel, and the channel's `awareness` option configures it. `check` sits in the channel config with the other hooks, so it gets the same types they get: `ctx.meta`, `ctx.channel.params`, and the channel's events for `ctx.channel.send()` and `ctx.channel.broadcast()`.

On the client, the [`awareness()`](/client/primitives/awareness) primitive adds `awareness` to the handle of every channel that lists this capability.

## Options

These go in the channel's `awareness` option.

| Option     | Type                                | Default  | What it does                                                                                                                                     |
| ---------- | ----------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `state`    | Standard Schema                     | required | The schema of one connection's state. It must give a plain JSON object, and its input and output types must be the same. It must be synchronous. |
| `check`    | `(ctx, state, previous) => boolean` | none     | Return `false` to refuse an update. Synchronous. See [Checking updates](#checking-updates).                                                      |
| `windowMs` | `number`                            | `50`     | How long the server collects changes before it sends them, in ms. A whole number from 1 to 10,000.                                               |
| `maxBytes` | `number`                            | `1024`   | The largest state, as UTF-8 bytes of its JSON. A whole number up to 65,536.                                                                      |

`base.channel()` throws a `LiveThingConfigError` at once for an unknown option, a `state` that is not a Standard Schema, or a `windowMs` or `maxBytes` out of range.

`awareness()` and the `awareness` option go together. Listing `awareness()` without the option, or setting the option without `awareness()`, is a type error, and `base.channel()` throws if the type checker cannot see it.

The state type is the same on the server and the client, and the state travels as JSON. So the type checker refuses a `state` schema that:

- gives something that is not an object, such as a string, an array, a `Date`, a `Map` or a `Set`;
- changes the type of what it checks, such as a default value (`v.optional(v.string(), 'none')`), a transform to another type, or a brand (`v.brand()`);
- gives `any` or `unknown`, or takes `any` as its input.

The error message says which rule the schema breaks. A nested `Date` or `bigint` is not caught by the type check: the client sends the state as JSON, so such a value can never pass the schema. Keep every value a JSON value.

### Checks when the server starts

The server throws a `LiveThingConfigError` when it starts if:

- the channel has `presence: false`. Awareness sends each member's `meta` to the other members, and `presence: false` is how a channel keeps `meta` from its members;
- `maxBytes` plus 4 KiB is over the adapter's receive limit, or over half of its send limit (a sync frame must always fit at least one state);
- `maxBytes` plus 4 KiB is over the `http()` transport's `maxPostBytes`, when the server lists `http()`;
- the channel belongs to a [plugin](/server/plugins/overview). Plugin channels have no awareness.

Listing `awareness()` in `server({ capabilities: [...] })`, or twice in one channel, is a type error. If the type checker cannot see it (for example, an array built at run time), `assemble()` or `base.channel()` throws.

Awareness does not need `dedup()`, `sequence()` or `replay`. It works on ephemeral and persistent channels, and for anonymous connections.

## The client contract

`InferClient` puts the state type in the channel's entry of the [client contract](/learn/the-contract), under `awareness`. For Huddle's `rooms`, the entry has:

```typescript [shape]
interface HuddleSocket {
  channels: {
    rooms: {
      // The output type of the `state` schema.
      awareness: { viewingMessageId: string | null }
    }
  }
}
```

This is the output type of the `state` schema, as it looks after JSON. The client primitive reads it, so `channel.awareness.set()` and the states of the other members are typed with no extra code. A channel without `awareness()` has no `awareness` key.

## How updates travel

1. A member's client sends its new state. The client sends at most one update per channel every 50 ms by default (see [`throttleMs`](/client/primitives/awareness#options)).
2. On a quiet channel, the server handles the first update at once. Then it opens a **window** of `windowMs`. Updates that arrive in the window wait, and only the newest one from each connection is kept.
3. For each kept update, the server runs the schema, `maxBytes` and `check`. An update that passes replaces the connection's state. An update with the same JSON as the stored state changes nothing.
4. The server sends the changes to every member of the channel, the sender too, in one frame per window. A frame that would pass about half of the adapter's send limit (at most 256 KiB) is split into several frames, each with whole entries. The first change of a connection carries its `meta`. Later changes leave `meta` out, as the members already have it.

A member who joins the channel gets every state right after the member list. So the order is: the subscribe is confirmed, then the member list, then the states. A big list comes in several frames, split like the changes above. Every frame but the last has `more: true`, so a client knows the list is complete when a frame comes without it. Here the list of `room:general` comes in two frames, each shortened to one entry:

```jsonc
// First frame: more frames follow.
[
  "__awarenessSync__",
  {
    "entries": [
      {
        "connectionId": "c_7f3a",
        "memberId": "c_7f3a",
        "meta": { "userId": "u_amara", "name": "Amara", "role": "member" },
        "state": { "viewingMessageId": "msg_481" },
        "ageMs": 1200
      }
    ],
    "more": true
  },
  { "channel": { "name": "room:general", "family": "rooms" } }
]

// Last frame: no `more`, so the list is complete.
[
  "__awarenessSync__",
  {
    "entries": [
      {
        "connectionId": "c_91d0",
        "memberId": "c_91d0",
        "meta": { "userId": "u_100", "name": "Kofi", "role": "member" },
        "state": { "viewingMessageId": null },
        "ageMs": 300
      }
    ]
  },
  { "channel": { "name": "room:general", "family": "rooms" } }
]
```

`ageMs` is how long ago the server took the state. A list that fits in one frame comes in one frame, with no `more`. See [Reserved events](/learn/wire-protocol#reserved-events) for every field.

A connection's state is cleared, and the members get the clear, when:

- the client clears it, or a handler calls `set(connectionId, null)`;
- the connection leaves the channel: it unsubscribes, it is kicked, or its socket closes.

There is no timeout, such as "drop a cursor after 30 seconds without a move". A state stays until its connection clears it or leaves.

### Checking updates

`check` runs for the newest update of each connection, at most once per window. Its `ctx` is the sender's channel ctx, so it has `ctx.user`, `ctx.meta`, `ctx.connection` and the typed `ctx.channel.params`. `state` is the new state after the schema, and `previous` is the connection's current state, or `null`. Return `true` to accept the update and `false` to refuse it.

`check` must return `true` or `false` right away. An `async` function is a type error. At run time, a promise or any other value counts as a throw: the update is refused with `error`. This keeps updates in the order they arrived.

In `check`, `ctx.channel.awareness` has `list()` and `get()` but no `set()`: the update being checked would overwrite it at once.

### Refused updates

A refused update changes nothing, and only its sender hears about it. The sender gets an `AwarenessRefused` error with one of these reasons. The client primitive gives it to [`onRefused`](/client/primitives/awareness#refused-updates), not to `onServerError`.

| Reason      | When                                                                                                                                                                                                                                                                                                   |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `too-large` | The state is over `maxBytes`, or the connection holds over 1 MiB of state and `meta` in all channels.                                                                                                                                                                                                  |
| `invalid`   | The schema refused the state, or it is not a plain JSON object.                                                                                                                                                                                                                                        |
| `check`     | `check` returned `false`.                                                                                                                                                                                                                                                                              |
| `error`     | `check` threw or did not return `true` or `false`, or the schema threw or is async: your [`onError`](/server/lifecycle-and-intercept/hooks) hook gets the error first. Or the server could not send the entry, because the connection's `meta` cannot become JSON or is too large: the server logs it. |

An update from a connection that is not a member of the channel is dropped without an answer. So is a frame larger than every awareness channel's `maxBytes` plus 4 KiB: the server drops it before it reads it and writes a log line. The LiveThing client never sends one. A member who sends an update to a channel without `awareness()` gets an `UnsupportedProtocol` error.

## Reading and setting states

Channel handlers, the channel's lifecycle hooks (`onSubscribe`, `onUnsubscribe`, `onSessionEnd`) and its `intercept` have `ctx.channel.awareness`. The channel's subscribe gates (its own `check`, `commit` and `revalidate`) do not: a connection has no state before it joins. In `onUnsubscribe` and `onSessionEnd`, the leaving connection's state is already cleared, so `list()` and `get()` do not show it, and `set()` for it throws.

| Method                     | What it does                                             |
| -------------------------- | -------------------------------------------------------- |
| `list()`                   | Every connection in this channel that has a state now.   |
| `get(connectionId)`        | One connection's entry, or `null`.                       |
| `set(connectionId, state)` | Replace one connection's state, or clear it with `null`. |

Each entry has:

| Field          | What it is                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------------- |
| `connectionId` | The connection the state belongs to.                                                               |
| `memberId`     | As in presence: the user ID on a persistent channel with a signed-in user, else the connection ID. |
| `meta`         | The connection's `meta` when its state first appeared. A later `setMeta` does not change it.       |
| `state`        | The state, typed by the `state` schema.                                                            |
| `updatedAt`    | When the server took the state, in ms since 1970.                                                  |

`list()` and `get()` return copies. Changing them changes nothing.

Huddle's `list-viewers` request answers "who is reading this message?" from the states of the room:

```typescript [server/huddle-definition.ts]
import * as v from 'valibot'
import { rooms } from './base'

// Who is reading a message right now: the members whose awareness state points at it.
export const handleListViewers = rooms.request('list-viewers', {
  input: v.object({ messageId: v.string() }),
  run(ctx, input) {
    const viewers = ctx.channel.awareness
      .list()
      .filter(
        (entry) => entry.state.viewingMessageId === input.messageId,
      )

    return { names: viewers.map((entry) => entry.meta.name) }
  },
})
```

The list has one name per connection, so a person with two tabs on that message is listed twice. See [Many tabs of one person](#many-tabs-of-one-person).

### Setting a state from the server

`set(connectionId, state)` runs the schema and `maxBytes`, but not `check`. It throws, and changes nothing, when:

- the connection is not a member of the channel;
- the schema or `maxBytes` refuses the state, or the connection would hold over 1 MiB of state and `meta` in all channels;
- the connection's `meta` cannot become JSON, or is too large to send with the state.

When it succeeds, every member gets the change, the connection itself too. A waiting update from that connection is dropped.

A state set by the server lasts until the connection sends its own next update or leaves the channel. After a reconnect, the client sends its own last state again, not the one the server set. So `set()` cannot hold a rule: a rule that must always hold belongs in `check`. `set(connectionId, null)` is for clearing a state that should no longer show, such as the cursor of a member who just lost access.

## Many tabs of one person

Awareness is per connection, not per member. A person with two tabs open has two entries, and each tab can read a different message.

To group the tabs of one person, the client needs an ID that is the same in each tab. On a persistent channel with signed-in users, `memberId` is the user ID. On an ephemeral channel, `memberId` is the connection ID, so put an ID that is safe to share in `meta`. Huddle's `authenticate` puts `userId` in `meta` for this.

## Leaving and dead connections

The server clears a state when it sees the connection's socket close. A socket that dies without a close frame (a laptop that sleeps, a phone that loses its network) can stay open on the server for minutes. Its state stays on other members' screens until then.

On Node, and on Cloudflare without hibernation, list [`keepalive()`](/server/capabilities/keepalive) with awareness. It finds dead sockets in seconds. With `hibernation: true` on Cloudflare, `keepalive()` does not watch the sockets (a timer would keep the object awake), so how fast a dead socket goes depends on Cloudflare noticing it.

## Hibernation on Cloudflare

With [`hibernation: true`](/server/server/hibernation), each connection's states are saved in its connection row, so they come back when the Durable Object wakes.

- The server writes the row 5 seconds after a change, and at most once every 5 seconds per connection. It does not write on every change.
- The waiting write is a timer, and a timer keeps the object awake. So after the last change, the object can sleep up to 5 seconds later than it would without awareness.
- When the object wakes, the states come back for the channels each connection is still in. They are checked again with the current schema and `maxBytes`, as a deploy may have changed them while the object slept. A state that no longer passes is cleared, and the members get the clear.
- A crash in the 5 seconds before a write loses the newest state. A crash also closes the sockets, and each client sends its own state again when it rejoins, so the loss does not show.

## What it costs

- **Messages in.** Each active client sends up to 20 updates a second per channel with the default throttle. 100 active clients is 2,000 messages a second into one server. Cloudflare bills incoming WebSocket messages at 20 to 1, so that is about 100 billed requests a second, and a steady flow keeps the object awake.
- **Server work.** One schema run and one `check` per connection per window, however many updates arrive.
- **Messages out.** One frame per channel per window, or several when it is too large for one. Its size grows with the number of connections that changed. 100 moving cursors at about 120 bytes each is about 12 KB per frame, sent to 100 members 20 times a second. For big rooms, raise `windowMs` on the server and `throttleMs` on the client.
- **Joining.** Each new member gets every state. 500 states of 1 KB is about 500 KB per join.
- **Storage on Cloudflare.** At most one row write per connection every 5 seconds, and none while its state does not change.

Over the [`http()`](/client/transports/http) transport in batch mode, one POST is sent at a time. On a slow link, an awareness update waits until the updates and chat messages before it are sent. The server keeps only the newest, so the cost is delay, not extra work.

## Bytes

Awareness state is JSON only. To share bytes, such as a small drawing stroke or a thumbnail, send them as normal channel messages with [`binary()`](/server/binary/overview).

## Wire frames

Awareness uses three protocol frames. See [Reserved events](/learn/wire-protocol#reserved-events) for their payloads.

| Frame               | From   | What it carries                                                                |
| ------------------- | ------ | ------------------------------------------------------------------------------ |
| `__awarenessSet__`  | client | `{ state }`: the new state of the sender, or `null` to clear it.               |
| `__awarenessSync__` | server | Every state in the channel, sent to a member who joins, in one or more frames. |
| `__awareness__`     | server | The changes of one window.                                                     |
