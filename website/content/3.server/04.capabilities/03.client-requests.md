A **client request** is a message from a client that waits for an answer from your server. `clientRequests()` enables `base.request(...)` handlers and channel `.request(...)` handlers, and, with [`binary()`](/server/binary/overview), requests that carry bytes.

Import it from `@livething/server/client-requests`:

```typescript [server/huddle-definition.ts]
import { clientRequests } from '@livething/server/client-requests'
```

## Client-to-server requests

Add `clientRequests()` to `capabilities`. Then register a handler with `base.request(event, { input, run })`:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import * as v from 'valibot'
import { loadProfile } from './huddle-data'

const base = server({
  capabilities: [clientRequests()],
})

export const handleGetProfile = base.request('get-profile', {
  input: v.object({ userId: v.string() }),
  run(_ctx, input) {
    return loadProfile(input.userId) // your storage lookup, returns a Profile
  },
})
```

::note
`base.request(...)` creates a handler value. Pass it to `base.assemble({ handlers: [...] })`. Only then does the handler run, and only then does it appear in `InferClient`.
::

A request works like `base.on`, but the client waits for a reply. LiveThing infers the reply type from the value that `run` returns. In this example, the type is `Profile` (`{ id: string; name: string; status: Status }`).

::note
If `run` returns nothing (no `return` statement, or a return of `null` or `undefined`), the client's request finishes with a **void acknowledgement**. This is a reply with no value. It only tells the client that the server finished. To fail a request, throw an error. If your answer can be empty, wrap it in an object such as `{ value: null }`, because a bare `null` becomes a void acknowledgement.
::

For more handler details (`run`, explicit `respond`, acknowledgements and rejection), see [base.request](/server/handlers/request).

### Requests that carry bytes

With [`binary()`](/server/binary/overview) listed, `clientRequests()` also enables `base.binary.request(...)` and channel `.binary.request(...)`. The request and the reply are binary messages: `run` gets the request's info and its bytes, and returns `{ info, bytes }`. Huddle's [`get-thumbnail`](/server/binary/requests#binary-requests) replies with a small picture of a file. A thrown error goes back as the normal text `__error__` frame.

### The contract slice

The **contract** is the TypeScript type that describes everything a client can send and receive. `clientRequests()` fills the contract's `clientRequests` key. Each entry pairs the `payload` that the client sends with the `response` that it gets back:

```typescript [shape]
import type { Status } from '../server/base'

interface HuddleSocket {
  clientRequests: {
    'get-profile': {
      payload: { userId: string }
      response: { id: string; name: string; status: Status }
    }
  }
}
```

Channel handlers use the same capability. When `clientRequests()` is in your `server({ capabilities })` list (next to [`channels()`](/server/capabilities/channels)), `channel.request(event, { input, run })` handles a request from a channel member. It sends the return value of `run` back to that member only.

Binary requests are not in the `clientRequests` key. They are in the contract's [`binary` key](/server/binary/overview#the-contract-slice).
