`lastSeen()` saves one row per user with the last time LiveThing saw that user. The row is durable: it is stored in the server's SQL database, so it stays after a restart. You read it with `ctx.lastSeen`.

Saving the current time into a user's row is called **stamping**. By default, `lastSeen()` stamps a user when one of their connections opens and when it closes. With `track: 'activity'`, it also stamps on each message the client sends. This includes LiveThing's own protocol messages and your app events, but not keepalive pings. Activity stamps are throttled per user: LiveThing writes at most one activity stamp for a user in each time window, so a connection that sends many messages does not write to the database on every message.

Only connections that belong to a user are stamped. A connection belongs to a user when your `upgrade` step gives it a `userId`. Anonymous connections are never stamped. See [Users](/server/context-and-storage/users).

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import { lastSeen } from '@livething/server/last-seen'
import * as v from 'valibot'
import { verifySession } from './auth'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    lastSeen(),
    emits({
      'when-seen-result': t<{ at: number | null; online: boolean }>(),
    }),
  ],
})

export const handleWhenSeen = base.on('when-seen', {
  input: v.object({ userId: v.string() }),
  run(ctx, input) {
    const at = ctx.lastSeen.at(input.userId)
    ctx.send('when-seen-result', {
      at,
      online: ctx.users.get(input.userId).isOnline(),
    })
  },
})
```

`lastSeen()` keeps its table in the server's own SQL storage. Every LiveThing adapter provides this storage, so you do not need to set up anything else.

## How to enable

List `lastSeen()` once. With no options, it stamps only when a connection opens or closes:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { lastSeen } from '@livething/server/last-seen'

const base = server({
  capabilities: [lastSeen()],
})
```

Pass `{ track: 'activity' }` to also stamp when the client sends a message:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { lastSeen } from '@livething/server/last-seen'

const base = server({
  capabilities: [lastSeen({ track: 'activity', throttleMs: 30_000 })],
})
```

## Configuration

Every field on `LastSeenOptions` is optional.

| Option       | Type                         | Default        | What it does                                                                                                                                                                                                                      |
| ------------ | ---------------------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `track`      | `'connection' \| 'activity'` | `'connection'` | `'connection'` stamps only when a connection opens or closes. `'activity'` also stamps on each message the client sends (protocol messages and app events, but not keepalive pings), at most once per `throttleMs` for each user. |
| `throttleMs` | `number`                     | `60_000`       | In `'activity'` mode, the shortest time in milliseconds between two activity stamps for the same user. It must be a positive whole number. `'connection'` mode does not use it.                                                   |

Any other `track` value, or a `throttleMs` that is not a positive whole number, throws a `LiveThingConfigError` when you call `lastSeen()`.

A stamp never moves a user's time backwards. Writes can arrive out of order. For example, a late stamp from an old connection closing can arrive after a newer connection opened. The stored value is always the highest time saved for that user.

## `ctx.lastSeen`

Listing `lastSeen()` adds a `lastSeen` member to every handler `ctx`:

::field-group
::field{name="at(userId)" type="(userId: string) => number | null"}
The last-seen time for one user, as a timestamp in milliseconds, or `null` if this user has never been stamped.
::
::field{name="atMany(userIds)" type="(userIds: string[]) => Map<string, number>"}
Last-seen times for many users in one read. A user who has never been stamped is not in the map.
::
::

A user who is online now was stamped when their connection opened, so `at()` can return a time from some minutes ago. To show "online now", check [`ctx.users.get(userId).isOnline()`](/server/context-and-storage/users#checking-if-a-user-is-online) first: it is `true` when the user has a live connection on this server instance. That check reads memory, not storage. This `load-roster` request returns the whole roster in one reply:

```typescript [server/load-roster.ts]
import { server } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import { lastSeen } from '@livething/server/last-seen'
import * as v from 'valibot'

const base = server({
  capabilities: [lastSeen(), clientRequests()],
})

export const handleLoadRoster = base.request('load-roster', {
  input: v.object({ userIds: v.array(v.string()) }),
  run(ctx, input) {
    const seenAt = ctx.lastSeen.atMany(input.userIds)
    const rows = input.userIds.map((userId) => ({
      userId,
      online: ctx.users.get(userId).isOnline(),
      lastSeenAt: seenAt.get(userId) ?? null,
    }))
    return { rows }
  },
})
```

## It augments `ConnectionInfo` everywhere

With `lastSeen()` listed, every `ConnectionInfo` snapshot gets a `lastSeen()` method next to `id`, `userId` and the other fields. This includes the snapshots from `ctx.connections.all()`, from a channel handle's `members()` and from a tag's `connections()`. It returns the last-seen time of that connection's user. `UserInfo` (from `ctx.users.get(id).info()`) gets the same `lastSeen()` method. Without the capability, the returned objects do not have this method. See [Connections](/server/context-and-storage/connections#connectioninfo) for the rest of the snapshot shape.

Listing snapshots does not read storage. Each `lastSeen()` call reads one row, so call it only for the members you show. To read many users at once, pass their IDs to `ctx.lastSeen.atMany()` instead.

On Cloudflare, the snapshots from `stub.admin()` cross Workers RPC, so `lastSeen()` comes back as a stub you `await`, like `ref()`.

This code runs inside a handler, on a server that also lists [`channels()`](/server/capabilities/channels):

```typescript [server/rooms.ts]
// Inside a handler:
const room = ctx.channels.get('rooms', 'room:general')
const roster = room.members().map((member) => ({
  userId: member.userId,
  lastSeen: member.lastSeen?.() ?? null,
}))
```

## Host-only :badge[host-only]

lastSeen is a **host-only** capability. Only your app's own `server(...)` can list it. A plugin's scoped server definition (`server({ scope: 'plugin' })`) cannot list it, and trying to do so is a type error. If a plugin needs lastSeen, it declares a dependency on the host instead. See [Depending on host capabilities](/server/plugins/depends-on).

## Filling `inbox().backlog()`'s `lastSeenAt`

When you list `lastSeen()` together with [`inbox()`](/server/capabilities/inbox), the inbox `backlog()` read (`ctx.channel.inbox.backlog()`, or `handle.inbox()?.backlog()` on any channel handle) fills each entry's `lastSeenAt` from this same table. The backlog lists the members who still have messages waiting on a channel, so with `lastSeenAt` you also see when each of those members was last seen. Without `lastSeen()`, no entry has a `lastSeenAt` field. See [Delivery](/server/inbox/delivery) for the full backlog read.

::note
`lastSeen()` and `inbox()` do not depend on each other. Each one works when listed alone. When you list both, the backlog read uses the last-seen table, so you do not have to combine the two yourself.
::
