A **server request** is a question that your server sends to a client. The server then waits for the client's answer, and the answer is typed. `serverRequests(...)` declares the questions the server may ask.

Import it from `@livething/server/server-requests`:

```typescript [server/huddle-definition.ts]
import { serverRequests } from '@livething/server/server-requests'
```

## Declare server-to-client requests

Pass a declaration map (an object with one entry per request) to `serverRequests({...})`. Each key is the name of a request that the server can send. Huddle declares `confirm-delete`. This example adds two more requests, `clear-notifications` and `approve-room-upgrade`:

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { serverRequests } from '@livething/server/server-requests'
import * as v from 'valibot'

const base = server({
  capabilities: [
    emits({
      notification: t<{ title: string; body: string }>(),
    }),
    serverRequests({
      'confirm-delete': {
        out: t<{ preview: string }>(),
        in: v.object({ confirmed: v.boolean() }),
      },
      'clear-notifications': { out: t<{}>() },
      'approve-room-upgrade': {
        out: t<{ roomId: string; requestedLimit: number }>(),
        in: v.object({ approved: v.boolean() }),
      },
    }),
  ],
})
```

Every declaration has the shape `{ out, in? }`:

- `out` is the payload that the server sends. It is a `t<T>()` type marker, so it has no runtime check of its shape. LiveThing trusts it because your own server code creates it. Like every payload, it must be an object in JSON (a plain object, or a value whose `toJSON()` returns one), so `t<{}>()` is the empty payload and `t<string>()` is a compile error.
- `in` is an optional schema for the client's answer. LiveThing validates the answer against this schema.

| Declaration                   | Meaning                                                                                                                                                                                       |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{ out: t<T>() }`             | An acknowledgement request. The server sends `T`. The client confirms that it received and handled it. The server call returns `Promise<void>`.                                               |
| `{ out: t<T>(), in: schema }` | A two-way request. The server sends `out`, and the client answers with a value that matches `in`. If the answer does not match `in`, the server call rejects with `request-invalid-response`. |

::note
You can also call `serverRequests()` with no argument. This turns on the server request feature without declaring any top-level requests. Use this form when only your channels declare requests (see [Channel-scoped server requests](#channel-scoped-server-requests)).

A request name must be a non-empty string of at most 128 characters. It cannot start or end with `__`, because LiveThing uses those names for its own protocol messages.
::

### The contract slice

The declaration map fills the `serverRequests` key of the client contract. (The client contract is the type that tells the client what the server can send and ask.) The declarations above produce this part of it:

```typescript [shape]
interface HuddleSocket {
  serverRequests: {
    'confirm-delete': {
      payload: { preview: string }
      response: { confirmed: boolean }
    }
    'clear-notifications': {
      payload: {}
      response: void
    }
    'approve-room-upgrade': {
      payload: { roomId: string; requestedLimit: number }
      response: { approved: boolean }
    }
  }
}
```

The client answers these requests with `socket.onRequest(...)`. See [Server Requests on the client](/client/primitives/server-requests).

## Ask one connection

Inside a handler, `ctx.request(event, payload)` sends the request to the current connection and waits for its answer:

This is Huddle's `delete-message` request. It asks the sender to confirm before it deletes:

```typescript [server/delete-message.ts]
import * as v from 'valibot'
import { base } from './base'
import { deleteMessage, loadMessagePreview } from './helpers'

const handleDeleteMessage = base.request('delete-message', {
  input: v.object({ messageId: v.string() }),
  async run(ctx, input) {
    const preview = await loadMessagePreview(input.messageId)
    const answer = await ctx.request('confirm-delete', { preview })
    if (!answer.confirmed) return { deleted: false }

    await deleteMessage(input.messageId)
    return { deleted: true }
  },
})
```

The type of `answer` comes from the declaration's `in` schema.

The server waits **10 000 ms** (10 seconds) for an answer by default. To change this, pass `{ timeout: 500 }` as the third argument. The value is in milliseconds. It must be a positive whole number no larger than `2147483647` (`2 ** 31 - 1`, the longest a timer can hold). Any other value rejects with `LiveThingConfigError`, and nothing is sent.

`ctx.request(...)` rejects with one of these errors:

| Error code                 | When                                                                                                                                     |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `timeout`                  | No answer arrived before the timeout.                                                                                                    |
| `disconnected`             | The connection closed before it answered.                                                                                                |
| `request-invalid-response` | The answer does not match the declaration's `in` schema.                                                                                 |
| `request-no-response`      | The client has no `onRequest` handler for this request, or its handler threw an error.                                                   |
| `request-not-declared`     | The request name is not declared. This rejects at once, without sending anything.                                                        |
| `not-a-member`             | Only `ctx.channel.request(..., { to })`: `to` is not a member of that channel right now. This rejects at once, without sending anything. |

See [Built-in Errors](/core/builtin-errors) for all of these errors.

To ask a different connection, use `ctx.connections.get(ref).request(...)`. `ref` is the `ConnectionRef` of that connection (see [Connections](/server/context-and-storage/connections)).

## Ask a user

A user can have several connections open at once (several tabs or devices). `ctx.users.get(id).request(event, payload)` sends the request to every live connection of that user on this server instance. (An instance is one running copy of your server.) It resolves with the **first valid answer** as `{ response, from }`. `response` is the typed answer, and `from` is the `ConnectionRef` of the connection that sent it. `ctx.user.request(...)` does the same for the user of the current connection.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { serverRequests } from '@livething/server/server-requests'
import * as v from 'valibot'

const base = server({
  capabilities: [
    emits({
      notification: t<{ title: string; body: string }>(),
    }),
    serverRequests({
      'approve-room-upgrade': {
        out: t<{ roomId: string; requestedLimit: number }>(),
        in: v.object({ approved: v.boolean() }),
      },
    }),
  ],
})

const handleRequestRoomUpgrade = base.on('request-room-upgrade', {
  input: v.object({
    roomId: v.string(),
    requestedLimit: v.number(),
    approverId: v.string(),
  }),
  async run(ctx, input) {
    const { response } = await ctx.users
      .get(input.approverId)
      .request('approve-room-upgrade', {
        roomId: input.roomId,
        requestedLimit: input.requestedLimit,
      })
    ctx.send('notification', {
      title: 'Room upgrade',
      body: response.approved ? 'approved' : 'not approved',
    })
  },
})
```

A tab that does not answer, or that sends an invalid answer, is ignored. The server keeps waiting for the user's other tabs. If no valid answer arrives before the timeout, the call rejects with `timeout`. This also happens when the user has no live connection. Pass `{ timeout: 500 }` to change the timeout.

See [Users](/server/context-and-storage/users) for user handles.

## Channel-scoped server requests

A channel can declare its own server requests. Put `serverRequests({...})` in the channel's `capabilities` list. The root `server({...})` must also list `serverRequests()`, with or without its own declarations. If it does not, `base.channel(...)` throws an error. Here `rooms` also declares a request to pin a message. Huddle's `rooms` does not have it:

```typescript [server/rooms.ts]
import { t } from '@livething/server'
import { serverRequests } from '@livething/server/server-requests'
import * as v from 'valibot'
import { base } from './base'

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    serverRequests({
      'approve-message-pin': {
        out: t<{ messageId: string }>(),
        in: v.object({ approved: v.boolean() }),
      },
    }),
  ],
})
```

Inside a handler of that channel:

- `ctx.channel.request(...)` asks the current member and waits for its answer.
- `ctx.channel.request(..., { to: connectionRef })` asks one other member of the channel instead.

Each channel keeps its own declarations, so two different channel families can both declare `approve-message-pin`. See [Scoped Streams and Requests](/server/channels/scoped-streams-requests) for more about channel requests.
