A **binary message** carries raw **bytes**, such as a picture or a file, with JSON **info** next to them. The `binary()` capability turns binary messages on. Import it from `@livething/server/binary`.

This page shows how to turn binary on and its size limits. For how binary messages work, see [Binary](/server/binary/overview). That section has a page for each kind of message: [Binary events](/server/binary/events), [Binary requests](/server/binary/requests) and [Binary streams](/server/binary/streams). For large files sent in pieces, see the [uploads](/server/capabilities/uploads) capability.

## How to enable

Import `binary` from `@livething/server/binary` and list it in `server({ capabilities: [...] })`. Its `emits` lists the binary events the server sends, the way [`emits`](/server/capabilities/emits) lists JSON events. Each value is the type of that event's info:

```typescript [server/base.ts]
import { server, t } from '@livething/server'
import { binary } from '@livething/server/binary'
import { channels } from '@livething/server/channels'

export const base = server({
  capabilities: [
    binary({ emits: { 'avatar-preview': t<null>() } }),
    channels(),
  ],
})

// A room: its members share their screens with each other.
export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    binary({ emits: { 'screen-frame': t<{ from: string }>() } }),
  ],
})
```

A channel lists its own binary events in its own `capabilities`. The root must list `binary()` too, even when the root itself sends no binary events. Without it, a channel's `binary()` is a type error, and `base.channel()` throws.

Without `binary()`, LiveThing does not read binary messages at all: a binary message closes the socket with code `1003` (`UNSUPPORTED_DATA`), and none of the binary methods can be used: `base.binary` does not exist, and every `.binary` key has the type `never`.

## Configuration

Both fields of `binary({...})` are optional. `binary()` with no options turns binary on, with no binary events and no binary requests of its own.

::field-group
::field{name="emits" type="Record<string, t<Info>()>"}
The binary events this scope sends. Each value is the type of the event's info: a plain object, or `null`. The bytes are not typed.
::
::field{name="serverRequests" type="Record<string, { out, in }>"}
The binary requests the server sends to a client. `out` is the type of the info the server sends, and the `in` schema checks the info of the client's answer. You send one with [`ctx.binary.request(...)`](/server/binary/requests#binary-server-requests), which also needs `serverRequests()`.
::
::

## Size limits

Two limits apply to every binary message:

- **The info and the metadata** together are at most 64 KiB, so a client never gets a message it must drop. Keep the info small, and put large data in the bytes.
- **The whole message** must fit in the adapter's message limit, 32 MiB by default. A message that arrives over it closes the socket with `1009`.

A send over a limit does not go out. What the method does then is the same as for a JSON event with a bad payload:

| Method                                                                                                              | Over 64 KiB of info and metadata        | Over the message limit                                                     |
| ------------------------------------------------------------------------------------------------------------------- | --------------------------------------- | -------------------------------------------------------------------------- |
| `ctx.binary.send`, `ctx.channel.binary.send`, `ctx.connections.get(ref).binary.send`                                | Throws                                  | Throws                                                                     |
| `ctx.user.binary.broadcast`, `ctx.users.get(id).binary.broadcast`, `ctx.channel.binary.broadcastTo`                 | Throws                                  | Logs the error for each socket and sends to none of them; the count is `0` |
| `ctx.binary.broadcast`, `ctx.channel.binary.broadcast`, `ctx.channels…binary.broadcast`, a tag's `binary.broadcast` | Logs the error once and sends to nobody | Logs the error for each socket and sends to none of them                   |

A large file does not have to fit in one message: an [upload](/server/binary/uploads) sends it in pieces, and can resume after a drop.

On [`http()`](/server/adapters/transports), a client's message goes up in a POST, so it must also fit in `http({ maxPostBytes })`, 512 KiB by default. The client refuses a bigger send before it goes out. Messages from the server go down as base64 text there, about a third bigger, so the same bytes take more of the network. Uploads work on `http()` too.

A handler's `maxBytes` is a third limit, for the bytes of the messages that handler receives. Without it, the limit is what always fits in the adapter's message limit: that limit, less the 9-byte header and the 64 KiB the info and the metadata may take (32 MiB − 65,545 bytes by default). A `maxBytes` above that makes the server fail when it starts. On an adapter whose message limit is not more than 64 KiB plus 9 bytes, you cannot set `maxBytes`, and the error says so.
