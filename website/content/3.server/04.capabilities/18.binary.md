`binary()` turns on **binary messages**. A JSON payload is fine for text and small data, but a picture or a file is bytes. Putting bytes in JSON (as base64 text, for example) makes them about a third bigger, and costs time to turn them back. A binary message carries the bytes as they are.

Each binary message has two parts:

- The **info** is JSON, such as the type of a file or who sent it. It works like any payload: a schema can check it, and its type comes from a `t<Shape>()` marker. It is an object, or `null` when there is nothing to say.
- The **bytes** are the data itself. No schema checks them. They can be anything: a picture, a sound, a file, or your own format.

The info always comes before the bytes, in handlers and in senders.

## Turning binary on

Import `binary` from `@livething/server/binary` and list it in `server({ capabilities: [...] })`. Its `emits` lists the binary events the server sends, the way [`emits`](/server/capabilities/emits) lists JSON events. Each value is the type of that event's info:

```typescript [server/base.ts]
import { server, t } from '@livething/server'
import { binary } from '@livething/server/binary'
import { channels } from '@livething/server/channels'

export const base = server({
  capabilities: [
    binary({ emits: { 'avatar-preview': t<null>() } }),
    channels(),
  ],
})

// A room: its members share their screens with each other.
export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    binary({ emits: { 'screen-frame': t<{ from: string }>() } }),
  ],
})
```

A channel lists its own binary events in its own `capabilities`. The root must list `binary()` too, even when the root itself sends no binary events. Without it, a channel's `binary()` is a type error, and `base.channel()` throws.

`binary()` can also list the binary requests the server sends to a client, under `serverRequests`. See [Binary server requests](#binary-server-requests).

Without `binary()`, LiveThing does not read binary messages at all: a binary message closes the socket with code `1003` (`UNSUPPORTED_DATA`), and none of the methods on this page can be used: `base.binary` does not exist, and every `.binary` key has the type `never`.

## Handling binary events

`base.binary.on(name, config)` creates the handler for one binary event that a client sends. A channel has the same method: `rooms.binary.on(...)`. Pass the handler to `base.assemble()`, as you do for every handler:

```typescript [server/avatars.ts]
import * as v from 'valibot'
import { base } from './base'
import { resizeAvatar, saveAvatar } from './helpers'

export const handleUploadAvatar = base.binary.on('upload-avatar', {
  input: v.object({
    fileType: v.picklist(['image/png', 'image/jpeg']),
  }),
  maxBytes: 2 * 1024 * 1024,
  async run(ctx, input, bytes) {
    await saveAvatar(ctx.user.id, input.fileType, bytes.slice())
    ctx.binary.send('avatar-preview', null, await resizeAvatar(bytes))
  },
})
```

- **`input`** is the schema for the info. It works like `input` on `base.on`: it is optional, and the handler gets the checked info as its second argument.
- **`maxBytes`** limits the bytes of each message. It is optional. Without it, the limit is what always fits in the adapter's message limit, with the header and up to 64 KiB of info. A value that cannot fit makes the server fail when it starts (see [Size limits](#size-limits)).
- **`run(ctx, input, bytes)`** gets the bytes as a plain `Uint8Array`. The array is a view of the message that arrived, not a copy. Call `bytes.slice()` for a copy when your code keeps the bytes after `run` returns.
- `rateLimit` and `allowInterleaving` work as they do on `base.on`.

A channel handler gets `ctx.channel`, as any channel handler does. Huddle's room handler sends each picture of a shared screen on to the other members:

```typescript [server/screen-share.ts]
import * as v from 'valibot'
import { rooms } from './base'

export const handleShareScreenFrame = rooms.binary.on(
  'share-screen-frame',
  {
    input: v.null(),
    maxBytes: 1024 * 1024,
    run(ctx, _input, bytes) {
      ctx.channel.binary.broadcast(
        'screen-frame',
        { from: ctx.user.id },
        bytes,
      )
    },
  },
)
```

::warning
The info describes the bytes, but it proves nothing about them: **a client can send any info and any bytes**. So `saveAvatar` must still check that the bytes really are a picture of that type. Set facts such as `from` on the server, as `handleShareScreenFrame` does. If the client set `from`, it could say it is someone else.
::

A binary event goes through the same steps as a JSON event, in the same order: the channel membership check, the [intercepts](/server/lifecycle-and-intercept/intercept), the rate limit, then the checks on the info and the bytes. A non-member gets `channel-not-subscribed`, and info that fails `input`, or bytes over `maxBytes`, gets `validation-failed`. See [Binary frames](/learn/wire-protocol#binary-frames) for every message the server refuses.

## Binary requests

`base.binary.request(name, config)` is [`base.request`](/server/capabilities/client-requests) for bytes. The client sends a binary message, and the reply is **one** binary message with the same exchange ID, so the client can match it to its request. It needs [`clientRequests()`](/server/capabilities/client-requests) too. Without it, `base.binary.request` does not exist on the type, and calling it throws.

Huddle shows a small picture of a file before someone downloads it:

```typescript [server/attachments.ts]
import * as v from 'valibot'
import { base } from './base'
import { makeThumbnail } from './helpers'

export const handleGetThumbnail = base.binary.request(
  'get-thumbnail',
  {
    input: v.object({ attachmentId: v.string() }),
    async run(ctx, input, _bytes) {
      const thumbnail = await makeThumbnail(input.attachmentId)
      return {
        info: { fileType: thumbnail.fileType },
        bytes: thumbnail.bytes,
      }
    },
  },
)
```

- **`run(ctx, input, bytes)`** gets the request's checked info and its bytes. The bytes of a request are often empty, as here.
- **`run` returns `{ info, bytes }`**. The info is a plain object, or `null`. The bytes are a `Uint8Array` or an `ArrayBuffer`, and you can leave them out. Any other key is a compile error, so a typo such as `byte` cannot turn into a reply with no bytes. As with `base.request`, the type of the reply comes from what `run` returns.
- **A value that is not `{ info, bytes }`** (possible in plain JavaScript) is a bug in the handler: the client gets `internal-error`, and the server logs a `[livething]` message that names the handler. The same goes for a stream chunk.
- **A registered error** that `run` throws goes back as the normal **text** `__error__` frame, the same as for a JSON request. Only a reply is binary.
- `input`, `maxBytes`, `rateLimit` and `allowInterleaving` work as they do on `base.binary.on`. A channel has the same method: `rooms.binary.request(...)`.

## Binary streams

`base.binary.stream(name, config)` is [`base.stream`](/server/streams/plain) for bytes. Each value the generator yields is `{ info, bytes }`, and goes out as one binary message. It needs [`stream()`](/server/capabilities/streams) too. Without it, `base.binary.stream` does not exist on the type, and calling it throws.

Huddle sends a stored file in pieces:

```typescript [server/attachments.ts]
import { t } from '@livething/server'
import * as v from 'valibot'
import { base } from './base'
import { openAttachment } from './helpers'

type FileInfo = { fileName: string; fileType: string }

export const handleDownloadAttachment = base.binary.stream(
  'download-attachment',
  {
    input: v.object({
      attachmentId: v.string(),
      fromByte: v.number(),
    }),
    chunk: t<FileInfo | null>(),
    async *run(ctx, input, _bytes) {
      const file = await openAttachment(
        input.attachmentId,
        input.fromByte,
      )
      // The first chunk says what the file is. The others need no info.
      let info: FileInfo | null = {
        fileName: file.name,
        fileType: file.type,
      }
      for await (const piece of file.pieces(ctx.stream.signal)) {
        yield { info, bytes: piece }
        info = null
        await ctx.stream.drain()
      }
    },
  },
)
```

- **`input`** checks the info of the binary message that starts the stream, and `run` gets that message's bytes as its third argument.
- **`chunk`** is the type of each chunk's info. It is optional: without it, the type comes from what `run` yields. Like every outgoing payload, it is not checked when the server runs.
- **`ctx.stream`** is the same as in a JSON stream: `signal` fires when the client cancels or leaves, `drain()` waits until the socket's buffer is small again, and `nudges()` reads the [nudges](/server/streams/config-and-lifecycle) that arrived. Call `drain()` after each piece, as here: binary chunks are large, and the generator can make them faster than the client reads them. On Cloudflare, `drain()` does nothing, because the platform does not report how full the socket is.
- `nudges`, `broadcast`, `allowConcurrent` and `maxBytes` work as they do on `base.stream` and `base.binary.on`. A channel has the same method: `rooms.binary.stream(...)`.

Only the chunks are binary. `__streamOk__`, `__streamEnd__`, an `__error__` that ends the stream, the client's `__streamCancel__`, and every nudge stay **text** frames. A nudge sent as a binary message gets `wrong-frame-kind`. Each chunk carries the same stream metadata as a JSON chunk: the stream ID, `durability: 'ephemeral'`, and a `seq` that starts at `1`. `__streamEnd__` carries the last `seq`.

There is no recorded binary stream yet, so `binary.recordedStream` does not exist, and calling it throws when the server starts. Put a position in the stream's `input` instead, as `download-attachment` does with `fromByte`. When the connection drops, the client starts the stream again from the last byte it got. A [hibernation](/server/server/hibernation) wake ends a running binary stream with `stream-aborted` and the reason `'hibernation-wake'`, the same as a JSON stream, and the client can start it again from its position.

## Sending binary events

Every object that can send a JSON event has a `.binary` key with the same methods. Each one reaches the same connections, takes the same options, and returns the same value as its JSON version:

| JSON sender                                   | Binary sender                                               | Returns                                    |
| --------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------ |
| `ctx.send(event, payload)`                    | `ctx.binary.send(event, info, bytes)`                       | `false` when the adapter refused the frame |
| `ctx.broadcast(event, payload, options)`      | `ctx.binary.broadcast(event, info, bytes, options)`         | nothing                                    |
| `ctx.channel.send(event, payload)`            | `ctx.channel.binary.send(event, info, bytes)`               | `1` when delivered, else `0`               |
| `ctx.channel.broadcastTo(to, event, payload)` | `ctx.channel.binary.broadcastTo(to, event, info, bytes)`    | the number of sockets reached              |
| `ctx.channel.broadcast(event, payload)`       | `ctx.channel.binary.broadcast(event, info, bytes, options)` | nothing                                    |
| `ctx.channels.get(...).broadcast(...)`        | `ctx.channels.get(...).binary.broadcast(...)`               | nothing                                    |
| `ctx.user.broadcast(event, payload)`          | `ctx.user.binary.broadcast(event, info, bytes)`             | the number of sockets reached              |
| `ctx.connections.get(ref).send(...)`          | `ctx.connections.get(ref).binary.send(...)`                 | `false` when it is not live                |
| `ctx.tags.ephemeral(group).broadcast(...)`    | `ctx.tags.ephemeral(group).binary.broadcast(...)`           | nothing                                    |

The same goes for `ctx.users.get(id)`, a tag's `.ref(key)`, and connectionless code: [scheduled tasks](/server/capabilities/scheduled), `onShutdown` and the in-process [admin API](/server/admin/overview) on Node have `ctx.binary.broadcast`, `ctx.channels.get(...).binary.broadcast` and `ctx.channels.binary.broadcast`, plus `.binary` on `ctx.users.get(id)` and `ctx.connections.get(ref)`. The Cloudflare admin stub has the same, except on `admin.channels.get(...)`, which has no `broadcast` at all: use `admin.channels.binary.broadcast(channel, event, info, bytes)`. See [Reaching the admin API](/server/admin/reaching-it).

The arguments come in this order: the event, the info, the bytes, then the options. The event and the info are typed from the `binary({ emits })` that declares the event, so a JSON event name, a typo or the wrong info is a compile error. The bytes are a `Uint8Array` or an `ArrayBuffer`, and you can leave them out.

The `handleUploadAvatar` handler from the top of this page sends the preview only to the tab that uploaded the avatar. To show it in every tab of that user, change `ctx.binary.send` to `ctx.user.binary.broadcast`. The rest of the handler stays the same:

```typescript [server/avatars.ts]
import * as v from 'valibot'
import { base } from './base'
import { resizeAvatar, saveAvatar } from './helpers'

export const handleUploadAvatar = base.binary.on('upload-avatar', {
  input: v.object({
    fileType: v.picklist(['image/png', 'image/jpeg']),
  }),
  maxBytes: 2 * 1024 * 1024,
  async run(ctx, input, bytes) {
    await saveAvatar(ctx.user.id, input.fileType, bytes.slice())
    const preview = await resizeAvatar(bytes)
    const tabs = ctx.user.binary.broadcast(
      'avatar-preview',
      null,
      preview,
    )
    ctx.log.info('avatar preview sent', { tabs })
  },
})
```

To pass an `ArrayBuffer`, pass one the bytes own entirely, such as `bytes.slice().buffer`. A `Uint8Array` can be a view into a bigger buffer (a Node `Buffer` often is), so its `.buffer` can hold other data too.

For each send, LiveThing:

- Adds the same metadata as for a JSON event: the channel, and the message ID and sequence number when [`dedup()`](/server/capabilities/dedup) and [`sequence()`](/server/capabilities/sequence) are listed. JSON and binary events in a scope share one sequence counter, so they keep one order.
- Copies the bytes into the message once. Your code can change its own bytes after the send returns.
- Builds the message **once** for a broadcast, and writes that same message to each socket.
- Runs the [`onOutgoing`](/server/lifecycle-and-intercept/outgoing) hook once. Its `frame.payload` is the info, and `frame.bytes` is the bytes.

Only data is binary: events, request replies, stream chunks and server requests with their answers. Every framework message stays text, such as `__error__`, `__subscribeOk__`, `__streamOk__`, `__streamEnd__` and `__nudgeOk__`.

## Binary server requests

A [server request](/server/capabilities/server-requests) asks a client a question and waits for its answer. A **binary** server request sends one binary message, and waits for one binary message back. List it in `binary({ serverRequests })`, with the same `out` and `in` as a JSON server request: `out` is the type of the info the server sends, and the `in` schema checks the info of the answer. It needs [`serverRequests()`](/server/capabilities/server-requests) too, the same as a JSON one. Without it, `assemble()` throws. A server with no binary server requests has no `ctx.binary.request` on its type.

```typescript [server/base.ts]
import { server, t } from '@livething/server'
import { binary } from '@livething/server/binary'
import { channels } from '@livething/server/channels'
import { serverRequests } from '@livething/server/server-requests'
import * as v from 'valibot'

export const base = server({
  capabilities: [
    binary({
      serverRequests: {
        'capture-screen': {
          out: t<{ maxWidth: number }>(),
          in: v.object({ fileType: v.literal('image/png') }),
        },
      },
    }),
    channels(),
    serverRequests(),
  ],
})

export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    binary({ emits: { 'screen-frame': t<{ from: string }>() } }),
  ],
})
```

`ctx.binary.request(name, info, bytes, options)` sends it. The bytes are optional, and so are the options (`timeout`, as for `ctx.request`). It resolves with the answer's checked info and its bytes. When a member starts sharing their screen, Huddle asks their client for one full picture, and sends it to the room, so members who joined late see the screen at once:

```typescript [server/screen-share.ts]
import * as v from 'valibot'
import { rooms } from './base'

export const handleStartScreenShare = rooms.on('start-screen-share', {
  input: v.object({}),
  async run(ctx) {
    const { bytes } = await ctx.binary.request('capture-screen', {
      maxWidth: 1280,
    })
    ctx.channel.binary.broadcast(
      'screen-frame',
      { from: ctx.user.id },
      bytes,
    )
  },
})
```

`.binary.request` is on every sender that has `request`, with the same audience and the same options:

| JSON request                                  | Binary request                                           | Resolves with           |
| --------------------------------------------- | -------------------------------------------------------- | ----------------------- |
| `ctx.request(event, payload)`                 | `ctx.binary.request(event, info, bytes)`                 | `{ info, bytes }`       |
| `ctx.connections.get(ref).request(...)`       | `ctx.connections.get(ref).binary.request(...)`           | `{ info, bytes }`       |
| `ctx.user.request(event, payload)`            | `ctx.user.binary.request(event, info, bytes)`            | `{ info, bytes, from }` |
| `ctx.channel.request(event, payload, { to })` | `ctx.channel.binary.request(event, info, bytes, { to })` | `{ info, bytes }`       |

The same goes for `ctx.users.get(id)`. A channel lists its own binary server requests in its own `binary({ serverRequests })`. As with a channel's `serverRequests(...)`, the root must list `serverRequests()`.

The answer must be a binary message too. The server treats every other answer like any answer that is not valid:

- **A text answer**, or a binary answer whose info fails `in`: a request to one connection rejects with `request-invalid-response`. A user request, which asks every socket of the user and takes the first good answer, ignores it, and waits for the other sockets.
- **A text `__error__`** from the client is a client that declines, the same as for a JSON server request: the promise rejects with that error.
- **A binary message named `__error__`** is not a decline. It is an answer of the wrong kind, so it is treated as above.

A name belongs to one server request in a scope: `capture-screen` cannot be in both `serverRequests({...})` and `binary({ serverRequests })`. `ctx.request` cannot send a binary server request, and `ctx.binary.request` cannot send a JSON one. Each is a compile error, and rejects with `request-not-declared`.

## Size limits

Two limits apply to every binary message:

- **The info and the metadata** together are at most 64 KiB, so a client never gets a message it must drop. Keep the info small, and put large data in the bytes.
- **The whole message** must fit in the adapter's message limit, 32 MiB by default. A message that arrives over it closes the socket with `1009`.

A send over a limit does not go out. What the method does then is the same as for a JSON event with a bad payload:

| Method                                                                                                              | Over 64 KiB of info and metadata        | Over the message limit                                                     |
| ------------------------------------------------------------------------------------------------------------------- | --------------------------------------- | -------------------------------------------------------------------------- |
| `ctx.binary.send`, `ctx.channel.binary.send`, `ctx.connections.get(ref).binary.send`                                | Throws                                  | Throws                                                                     |
| `ctx.user.binary.broadcast`, `ctx.users.get(id).binary.broadcast`, `ctx.channel.binary.broadcastTo`                 | Throws                                  | Logs the error for each socket and sends to none of them; the count is `0` |
| `ctx.binary.broadcast`, `ctx.channel.binary.broadcast`, `ctx.channels…binary.broadcast`, a tag's `binary.broadcast` | Logs the error once and sends to nobody | Logs the error for each socket and sends to none of them                   |

A handler's `maxBytes` is a third limit, for the bytes of the messages that handler receives. Without it, the limit is what always fits in the adapter's message limit: that limit, less the 9-byte header and the 64 KiB the info and the metadata may take (32 MiB − 65,545 bytes by default). A `maxBytes` above that makes the server fail when it starts. On an adapter whose message limit is not more than 64 KiB plus 9 bytes, you cannot set `maxBytes`, and the error says so.

## What binary does not do yet

- **Replay** does not store binary events. They still get a sequence number, but a client that was away misses them. See [Replay](/server/replay/overview#binary-events).
- **A channel with `inbox()`** cannot list binary events: `assemble()` throws. See [Inbox](/server/inbox/overview#binary-events).
- **A recorded binary stream** does not exist yet. See [Binary streams](#binary-streams).
- **The `@livething/client` package** does not send or receive binary messages yet. A client that follows the [binary frame layout](/reference/wire-format#binary-frames) can already speak to your server.

## The contract slice

`InferClient` adds a `binary` key to the client contract for each scope with binary events, requests or streams. Each entry has the type of the info, because the bytes are always bytes:

- `incoming` holds the events the client receives, and `outgoing` the events it sends.
- `clientRequests` holds the binary requests the client sends: `payload` is the info it sends, and `response` the info of the reply.
- `serverRequests` holds the binary requests the server sends: `payload` is the info the client gets, and `response` the info of its answer.
- `streams` holds the binary streams: `payload` is the info that starts the stream, and `chunk` the info of each chunk.

```typescript [shape]
interface HuddleSocket {
  binary: {
    incoming: { 'avatar-preview': null }
    outgoing: {
      'upload-avatar': { fileType: 'image/png' | 'image/jpeg' }
    }
    clientRequests: {
      'get-thumbnail': {
        payload: { attachmentId: string }
        response: { fileType: 'image/png' }
      }
    }
    serverRequests: {
      'capture-screen': {
        payload: { maxWidth: number }
        response: { fileType: 'image/png' }
      }
    }
    streams: {
      'download-attachment': {
        payload: { attachmentId: string; fromByte: number }
        chunk: { fileName: string; fileType: string } | null
        kind: 'ephemeral'
      }
    }
  }
}
```

A channel's `binary` key sits in the same place inside that channel's entry. The JSON `clientRequests`, `serverRequests` and `streams` maps of the contract do not list the binary ones.

## Names

A binary event, request or stream name follows the same rules as a JSON one: a non-empty string of up to 128 characters, which does not start or end with `__` and does not contain `::`. In a [plugin](/server/plugins/overview), the 128 characters include the `__<id>::` prefix that LiveThing adds on the wire. In one scope, a name belongs to one declaration and one handler: `screen-frame` cannot be both a JSON event and a binary event. Two declarations of one name throw when the adapter loads your server definition, and two handlers of one name are a compile error.
