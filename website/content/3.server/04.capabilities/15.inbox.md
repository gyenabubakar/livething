Replay is best-effort catch-up on a channel: it keeps one shared log and a reconnecting client asks for the tail it missed. **Inbox** is guaranteed delivery to each eligible recipient: on every broadcast the engine writes one durable row per member who receives it and holds that row until the member confirms it arrived — so an offline member still gets it, drained automatically on their next reconnect. The sender is excluded by default, just like a normal channel broadcast; pass `{ includeSelf: true }` when the sender should receive its own message too.

`inbox()` is a **channel-only** capability: it is listed inside one channel's own `capabilities`, never in the top-level `define({ capabilities: [...] })` array.

This page is the enable-and-configure reference. For how inbox behaves on the wire — the held-until-acknowledged flow, the reconnect drain, receipts, and the overflow gap — see [Inbox](/server/inbox/overview), split into [Delivery and acknowledgements](/server/inbox/delivery), [Receipts](/server/inbox/receipts), and [Overflow and the gap signal](/server/inbox/overflow-and-gap).

## Requirements

Inbox is durable per-member delivery, so the channel must use `membership: 'persistent'` and the host needs three other capabilities — the top-level `define({ capabilities: [...] })` array. An inbox channel with ephemeral membership fails validation at server startup because there is no durable membership roster to fan out to or auto-rejoin. Leaving a host capability out entirely fails at `assemble()` with a message naming the fix. `sequence()` is a special case: listing it at all satisfies `assemble()`, but inbox also needs `persist: true` on it — that part is checked one step later, at server startup.

| Capability                                                     | Why it's required                                                                                                                                 |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`channels()`](/server/capabilities/channels)                  | Inbox is channel-scoped — it delivers to a channel's members.                                                                                     |
| `membership: 'persistent'`                                     | Inbox needs a durable member roster for offline fan-out and reconnect drain; an ephemeral inbox channel is rejected at startup.                   |
| [`sequence({ persist: true })`](/server/capabilities/sequence) | Held rows order and settle by sequence number, which must survive a restart. A plain `sequence()` passes `assemble()` but is rejected at startup. |
| [`dedup()`](/server/capabilities/dedup)                        | The reconnect drain re-delivers held rows; dedup drops any the client already saw live.                                                           |

Every adapter guarantees durable SQL storage, so the held rows and per-member cursors always have somewhere to live — nothing extra needs to be turned on for that.

::note
Inbox delivers to a **member's user id**, so members need a stable `userId` — set one on upgrade (here `requireUsername`). An anonymous connection still gets messages live while it is connected, but has no durable queue, so it gets no offline drain and no guarantee.
::

## How to enable

Import `inbox` from `@wskit/server/inbox`, list the host requirements once on `define(...)`, then list `inbox()` inside the channel's own `capabilities` — it takes no config unless you want to tune it:

```typescript [inbox-server.ts]
import { define, emits, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { dedup } from '@wskit/server/dedup'
import { inbox } from '@wskit/server/inbox'
import { sequence } from '@wskit/server/sequence'
import * as v from 'valibot'

const base = define({
  upgrade: (request) => requireUsername(request),
  capabilities: [channels(), sequence({ persist: true }), dedup()],
})

const chat = base.channel('chat', {
  capabilities: [
    inbox(),
    emits({ 'room-msg': t<{ text: string; from: string }>() }),
  ],
})

export const handleSend = chat.on('send-room-msg', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('room-msg', {
      text: payload.text,
      from: ctx.meta.username,
    })
  },
})
```

Nothing in the handler mentions inbox. You broadcast as usual; the engine turns each broadcast into a durable per-member delivery.

To tune one channel, pass an options object to `inbox(...)`:

```typescript [inbox-options-server.ts]
const chat = base.channel('chat', {
  capabilities: [
    inbox({ retention: { maxMessages: 1 } }),
    emits({ 'room-msg': t<{ text: string; from: string }>() }),
  ],
})
```

## Configuration

Every field on `InboxOptions` is optional.

| Option               | Type                                          | Default    | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------- | --------------------------------------------- | ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `onDelivered`        | `'delete' \| 'retain'`                        | `'delete'` | After a member acks a row, `delete` drops it; `retain` keeps it. `retain` **requires** `retention` — the build throws without it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `retention`          | `{ maxMessages?: number; maxAgeMs?: number }` | none       | Bounds held rows **per member**. `maxMessages`: keep at most N rows; in `delete` mode acknowledged rows are already gone, while in `retain` mode acknowledged rows count too and may be pruned. A `backfill` or broadcast that inserts past the bound evicts the oldest rows. Only evicted undelivered rows raise that member's overflow watermark. The bound is also reconciled at boot, so a changed config applies to rows already stored. `maxAgeMs`: age rows out by time and sweep them with the shared durable alarm even when the channel is quiet. Rows are removed only once strictly older than the limit; expired undelivered rows raise the [overflow gap](/server/inbox/overflow-and-gap). Valid in both modes; with `retain` it is required to age kept rows out. |
| `broadcastReceipts`  | `boolean`                                     | `false`    | Push a member's delivered `__received__` tick to the other members so they can show the grey double-check. Off by default: the received cursor is always stored and stays readable via `receiversOf` — this only controls the live push to other members.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `maxReceiptAudience` | `number`                                      | `256`      | When `broadcastReceipts` is on, only push the tick while the channel has at most this many members. Above it the received cursor is still tracked and stays readable via `receiversOf`, but no live tick fires — its fan-out is O(members²).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

::note
`onDelivered: 'retain'` without `retention` fails the build: with delivered rows never dropped, an unbounded queue would grow forever, so a bound is mandatory.
::

## What it adds to the client contract

An inbox channel gains a received surface on its client handle — `receivers`, `onReceived`, and `receiversOf` — because inbox already tracks each member's acknowledgement. These appear only on channels whose contract has `inbox: true`. The `receivers` store and `onReceived` are fed by the live `__received__` tick, so they only fill when the channel opts in with `broadcastReceipts: true`; `receiversOf` reads the stored cursor and answers either way.

For that flag to reach the client type, pass a routed handler from the inbox channel to `base.assemble(...)`. Its handler value carries the channel contract, including `inbox: true`:

```typescript [inbox-assemble.ts]
export const inboxHandler = base.assemble({
  handlers: [handleSend],
})

export type InboxClient = InferClient<typeof inboxHandler>
```

On the client, the [`inbox()`](/client/primitives/inbox) primitive reads that flag and exposes the surface — a live `receivers` store, an `onReceived` listener, and the authoritative `receiversOf` query. Read receipts — the blue check, who has _read_ a message — are a separate opt-in; see [`readReceipts`](/server/capabilities/read-receipts).
