[Replay](/server/capabilities/replay) is best-effort catch-up on a channel. It keeps one shared log, and a client that reconnects asks for the part of the log it missed. **Inbox** is guaranteed delivery to each member who should receive a message. On every broadcast, LiveThing writes one stored row (one database record) for each member who receives the message. It keeps that row until the member **acknowledges** it, which means the member's client confirms that the message arrived. So a member who is offline still gets the message: when they reconnect, LiveThing sends all their waiting rows automatically. This is called the **reconnect drain**.

The sender does not receive its own message by default, the same as a normal channel broadcast. Pass `{ includeSelf: true }` when the sender should receive its own message too.

`inbox()` is a **channel-only** capability. You list it inside one channel's own `capabilities`. You never list it in the top-level `server({ capabilities: [...] })` array.

This page shows how to turn inbox on and configure it. For how inbox works over the connection (rows kept until acknowledged, the reconnect drain, receipts, and the overflow gap), see [Inbox](/server/inbox/overview). That section has three parts: [Delivery and acknowledgements](/server/inbox/delivery), [Receipts](/server/inbox/receipts), and [Overflow and the gap signal](/server/inbox/overflow-and-gap).

## Requirements

Inbox stores messages for each member, so it has these requirements:

- The channel must have persistent membership (`membership: 'persistent'`). This is the default, so it only fails when you set `membership: 'ephemeral'`. Persistent membership means LiveThing keeps a stored list of the channel's members (the **roster**). Inbox writes rows for the members on this list, and a member rejoins from this list when they reconnect. An inbox channel with `membership: 'ephemeral'` fails validation when the server starts.
- The host needs three other capabilities in the top-level `server({ capabilities: [...] })` array: `channels()`, `sequence({ persist: true })`, and `dedup()`. If you leave one of them out completely, `assemble()` throws an error that names the fix.

`sequence()` is a special case. Listing `sequence()` in any form is enough for `assemble()`. But inbox also needs `persist: true` on it, and LiveThing checks that one step later, when the server starts.

| Requirement                                                    | Why inbox needs it                                                                                                                                                  |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`channels()`](/server/capabilities/channels)                  | Inbox belongs to a channel. It delivers to that channel's members.                                                                                                  |
| `membership: 'persistent'`                                     | Inbox needs the stored member roster to write rows for offline members and to run the reconnect drain. An ephemeral inbox channel fails at startup.                 |
| [`sequence({ persist: true })`](/server/capabilities/sequence) | Stored rows are ordered and acknowledged by sequence number, and that number must survive a restart. A plain `sequence()` passes `assemble()` but fails at startup. |
| [`dedup()`](/server/capabilities/dedup)                        | The reconnect drain sends stored rows again. Dedup drops any row the client already received while it was connected.                                                |

Every adapter provides durable SQL storage (storage that survives a restart). So the stored rows and each member's delivery position always have a place to live. You do not need to turn anything else on for that.

::note
Inbox delivers to a **member's user ID**, so members need a stable `userId`. Set one in your `upgrade` function. The example below uses `verifySession` from [Upgrade](/server/server/upgrade). An anonymous connection still gets messages while it is connected. But it has no stored queue, so it gets no reconnect drain and no delivery guarantee.
::

## How to enable

Import `inbox` from `@livething/server/inbox`. List the host requirements once on `server(...)`. Then list `inbox()` inside the channel's own `capabilities`. It takes no options unless you want to change the defaults. Huddle's direct messages use exactly this: a DM is delivered even if the other person is offline right now.

```typescript [server/dms.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { dedup } from '@livething/server/dedup'
import { inbox } from '@livething/server/inbox'
import { sequence } from '@livething/server/sequence'
import * as v from 'valibot'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [channels(), sequence({ persist: true }), dedup()],
})

export const dms = base.channel(['dms', 'dm:{pair}'], {
  capabilities: [inbox(), emits({ message: t<Message>() })],
})

export const handleSendMessage = dms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

The handler does not mention inbox. You broadcast as usual, and LiveThing turns each broadcast into a stored delivery for each member.

To change the settings for one channel, pass an options object to `inbox(...)`:

```typescript [inbox-options-server.ts]
export const dms = base.channel(['dms', 'dm:{pair}'], {
  capabilities: [
    inbox({ retention: { maxMessages: 1 } }),
    emits({ message: t<Message>() }),
  ],
})
```

## Configuration

Every field on `InboxOptions` is optional.

::field-group
::field{name="onDelivered" type="'delete' | 'retain'"}
Default: `'delete'`. What happens to a row after the member acknowledges it. `'delete'` removes it. `'retain'` keeps it. `'retain'` **requires** `retention` (see the note below).
::
::field{name="retention" type="{ maxMessages?: number; maxAgeMs?: number }"}
Default: none. Limits how many stored rows each member can have. Both values must be positive whole numbers.

`maxMessages` keeps at most this many rows per member. In `'delete'` mode, acknowledged rows are already gone, so the limit counts only rows not yet delivered. In `'retain'` mode, acknowledged rows count too and can be removed. When a broadcast or a `backfill` call adds rows past the limit, the oldest rows are removed. Removing a row that was not yet delivered raises that member's **overflow watermark** (the highest sequence number the member lost), so their next reconnect reports the lost range as an [overflow gap](/server/inbox/overflow-and-gap). Removing an acknowledged row does not. LiveThing also applies the limit when the server starts, so a changed setting applies to rows that are already stored.

`maxAgeMs` removes rows by age, in milliseconds. A stored alarm (a timer saved in storage, shared with other features) removes them even when the channel is quiet. A row is removed only when it is strictly older than the limit. Removing an expired row that was not yet delivered also raises the overflow gap. `maxAgeMs` works in both modes. In `'retain'` mode, you need it (or `maxMessages`) so kept rows are removed at some point.
::
::field{name="broadcastReceipts" type="boolean"}
Default: `false`. Sends a live "received" receipt (the `__received__` frame) to the other members each time a member acknowledges a message. Chat apps use this to show a "delivered" mark, often a grey double check. It is off by default. LiveThing always stores how far each member has received, and you can always read it with `receiversOf`. This option only controls the live push to other members.
::
::field{name="maxReceiptAudience" type="number"}
Default: `256`. When `broadcastReceipts` is on, LiveThing sends the live receipt only while the channel has this many members or fewer. Above this number, LiveThing still stores how far each member has received, and `receiversOf` still reads it, but it sends no live receipt. The reason: every member's receipt goes to every other member, so the work grows with the square of the member count.
::
::

::note
`onDelivered: 'retain'` without `retention` is a type error, and `base.channel(...)` also throws an error at runtime. Acknowledged rows are never removed in `'retain'` mode, so without a limit the queue would grow forever.
::

## What it adds to the client contract

An inbox channel adds three members to its client handle: `receivers`, `onReceived`, and `receiversOf`. Inbox already stores each member's acknowledgements, so the client can ask who has received a message. These members appear only on channels whose contract has `inbox: true`. The `receivers` store and `onReceived` get their data from the live `__received__` receipts, so they only fill when the channel sets `broadcastReceipts: true`. `receiversOf` reads the stored position and works in both cases.

The `inbox: true` flag reaches the client type through the channel's handlers. When you pass a handler from the inbox channel to `base.assemble(...)`, that handler carries the channel's contract, including `inbox: true`:

```typescript [inbox-assemble.ts]
export const huddle = base.assemble({
  handlers: [handleSendMessage],
})

export type HuddleSocket = InferClient<typeof huddle>
```

On the client, the [`inbox()`](/client/primitives/inbox) primitive reads that flag and adds these members to the handle: a live `receivers` store, an `onReceived` listener, and the `receiversOf` query, which gives the stored (always correct) answer. Read receipts are a separate option. They show who has _read_ a message, often a blue check in chat apps. See [`readReceipts`](/server/capabilities/read-receipts).
