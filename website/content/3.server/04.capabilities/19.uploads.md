An **upload** sends one large file from a client to the server in pieces. The client can cancel it, and can resume it after a drop. The `uploads()` capability turns uploads on and adds `base.binary.upload(...)`. Import it from `@livething/server/uploads`.

This page shows how to turn uploads on and configure them. For how to write an upload handler, see [Uploads](/server/binary/uploads). These pages go further: [Resuming and cleanup](/server/binary/resuming), [Speed and limits](/server/binary/speed-and-limits), [S3 and R2 parts](/server/binary/s3-and-r2), [Upload, then post](/server/binary/upload-then-post), [Post from run](/server/binary/post-from-run), [Several files with one caption](/server/binary/several-files) and [Checking downloads](/server/binary/checking-downloads).

## How to enable

Import `uploads` from `@livething/server/uploads` and list it in `server({ capabilities: [...] })`, next to `binary()`. Uploads send their pieces as binary messages, so `uploads()` needs [`binary()`](/server/capabilities/binary):

```typescript [server/base.ts]
import { server } from '@livething/server'
import { binary } from '@livething/server/binary'
import { uploads } from '@livething/server/uploads'
import { verifySession } from './auth'

export const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    return { userId: user?.id }
  },
  capabilities: [binary(), uploads()],
})
```

An upload belongs to a **user**, so a connection with no `userId` cannot start one: it gets `durable-stream-requires-user`, the same error as for a durable stream. The user can then resume the upload from another connection, for example after a page reload.

## Configuration

`uploads()` takes two options, both in milliseconds. Both are optional:

::field-group
::field{name="expireAfterMs" type="number"}
An upload that gets no pieces and no `ctx.upload.saved()` for this long expires. Its `onDiscard` runs, and its record is deleted. An upload that a connection is still sending never expires. The default is 24 hours.
::
::field{name="retentionAfterDoneMs" type="number"}
How long the record of a finished upload keeps its reply. A client that lost the reply in a drop gets it again when it starts the upload again. The default is 10 minutes.
::
::

```typescript [server/base.ts]
import { server } from '@livething/server'
import { binary } from '@livething/server/binary'
import { uploads } from '@livething/server/uploads'

export const base = server({
  capabilities: [
    binary(),
    uploads({ expireAfterMs: 6 * 60 * 60 * 1000 }), // 6 hours
  ],
})
```

A server has **one** upload engine, and the host and its [plugins](/server/binary/uploads#uploads-in-a-plugin) share it. So each time is set in one place: a `uploads()` with no options uses the times that another `uploads(...)` set, or the defaults. Two `uploads(...)` calls that give the same option different values fail when the server starts. Two calls that set different options are fine.

## Storage

LiveThing keeps one row per upload in its reserved table `__livething_uploads`, in the server's own SQL storage. Every adapter has this storage, so you do not need to turn anything else on. See [The upload record](/server/binary/resuming#the-upload-record).
