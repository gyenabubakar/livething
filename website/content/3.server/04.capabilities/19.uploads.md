`uploads()` lets a client send the server **one large file in pieces**. A [binary message](/server/capabilities/binary) is fine for an avatar of 2 MiB: it arrives as one message, and the handler gets all of its bytes at once. A file of 500 MiB is different. It does not fit in one message, it takes minutes to send, and the connection can drop on the way. An upload handles this for you:

- The client cuts the file into **pieces**, and the server's `run` reads them one by one with `for await`.
- The server tells the client how many bytes it has read, so the client never sends much more than the server can take. This is the **window**.
- `run` says which bytes are really stored. After a drop, the client **resumes** the upload from there, and does not send the whole file again.
- The client can **cancel** the upload, and the server runs your `onDiscard` to delete what was stored.

Each upload has JSON **input**, sent once at the start, such as the name and type of the file. When `run` is done, it returns JSON **info**. That is the reply the client gets.

Where the bytes go is up to your `run`: a disk, a database, or a bucket in S3 or R2. LiveThing keeps only a small record of each upload, so it can resume it.

## Turning uploads on

Import `uploads` from `@livething/server/uploads` and list it in `server({ capabilities: [...] })`, next to `binary()`. Uploads send their pieces as binary messages, so `uploads()` needs `binary()`:

```typescript [server/base.ts]
import { server } from '@livething/server'
import { binary } from '@livething/server/binary'
import { uploads } from '@livething/server/uploads'
import { verifySession } from './auth'

export const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    return { userId: user?.id }
  },
  capabilities: [binary(), uploads()],
})
```

An upload belongs to a **user**, so a connection with no `userId` cannot start one: it gets `durable-stream-requires-user`, the same error as for a durable stream. The user can then resume the upload from another connection, for example after a page reload.

`uploads()` takes two options, both in milliseconds:

::field-group
::field{name="expireAfterMs" type="number"}
An upload that gets no pieces and no `ctx.upload.saved()` for this long expires. Its `onDiscard` runs, and its record is deleted. An upload that a connection is still sending never expires. The default is 24 hours.
::
::field{name="retentionAfterDoneMs" type="number"}
How long the record of a finished upload keeps its reply. A client that lost the reply in a drop gets it again when it starts the upload again. The default is 10 minutes.
::
::

```typescript [server/base.ts]
import { server } from '@livething/server'
import { binary } from '@livething/server/binary'
import { uploads } from '@livething/server/uploads'

export const base = server({
  capabilities: [
    binary(),
    uploads({ expireAfterMs: 6 * 60 * 60 * 1000 }), // 6 hours
  ],
})
```

A server has **one** upload engine, and the host and its [plugins](#uploads-in-a-plugin) share it. So each time is set in one place: a `uploads()` with no options uses the times that another `uploads(...)` set, or the defaults. Two `uploads(...)` calls that give the same option different values fail when the server starts. Two calls that set different options are fine.

## An upload handler

`base.binary.upload(event, config)` creates the handler of one upload. Pass it to `base.assemble()`, as you do for every handler. An upload belongs to no channel, so a channel has no `binary.upload`. A [plugin](#uploads-in-a-plugin) can declare uploads too.

Huddle's `upload-attachment` handler stores one file in four steps. Its small helpers are in `server/attachment-files.ts`, and both full files are below the steps.

::steps{level="3"}

### Give the upload a file

A new upload gets a new attachment ID, and keeps it in the upload's **state**. A resumed run finds the ID there, so it writes to the same file:

<!-- docs-check: skip -->

```typescript [server/attachment-files.ts]
export function attachmentIdOf(upload: UploadRunHandle): string {
  if (typeof upload.state === 'string') return upload.state

  const attachmentId = crypto.randomUUID()
  upload.saved(upload.savedThrough, { state: attachmentId })

  return attachmentId
}
```

### Write each piece, then call `saved()`

`writePieces` puts each piece into the file at its offset. Then `ctx.upload.saved()` records that the bytes up to the end of that piece are stored:

<!-- docs-check: skip -->

```typescript [server/attachment-files.ts]
for await (const { bytes, offset } of pieces) {
  await writeAttachmentBytes(attachmentId, offset, bytes)
  size = offset + bytes.byteLength
  upload.saved(size)
}
```

### Return the reply

When the loop ends, every byte is stored. `run` saves the attachment's record, and returns its ID. That is the reply the client gets:

<!-- docs-check: skip -->

```typescript [server/attachments.ts]
async run(ctx, input, pieces) {
  const attachmentId = attachmentIdOf(ctx.upload)
  const size = await writePieces(ctx.upload, attachmentId, pieces)

  await saveAttachment({
    attachmentId,
    ownerId: ctx.user.id,
    roomId: null,
    fileName: input.fileName,
    fileType: input.fileType,
    size,
  })

  return { info: { attachmentId } }
},
```

### Delete the file in `onDiscard`

An upload that ends without finishing deletes its file. `deleteAttachment` does nothing when the file is already gone, so this is safe to run twice:

<!-- docs-check: skip -->

```typescript [server/attachment-files.ts]
export async function discardAttachment(
  upload: UploadDiscardHandle,
): Promise<void> {
  if (typeof upload.state === 'string')
    await deleteAttachment(upload.state)
}
```

```typescript [server/attachment-files.ts]
import type {
  UploadDiscardHandle,
  UploadPiece,
  UploadRunHandle,
} from '@livething/server/uploads'
import {
  deleteAttachment,
  isRoomMember,
  loadAttachment,
  writeAttachmentBytes,
} from './helpers'

/** The attachment an upload writes. A new upload gets a new ID, and a resumed one finds it in its state. */
export function attachmentIdOf(upload: UploadRunHandle): string {
  if (typeof upload.state === 'string') return upload.state

  const attachmentId = crypto.randomUUID()
  upload.saved(upload.savedThrough, { state: attachmentId })

  return attachmentId
}

/** Writes each piece into the attachment's file, and returns the size of the file. */
export async function writePieces(
  upload: UploadRunHandle,
  attachmentId: string,
  pieces: AsyncIterable<UploadPiece>,
): Promise<number> {
  let size = upload.savedThrough

  for await (const { bytes, offset } of pieces) {
    await writeAttachmentBytes(attachmentId, offset, bytes)
    size = offset + bytes.byteLength
    upload.saved(size)
  }

  return size
}

/** Deletes the file of an upload that did not finish. Safe to run twice. */
export async function discardAttachment(
  upload: UploadDiscardHandle,
): Promise<void> {
  if (typeof upload.state === 'string')
    await deleteAttachment(upload.state)
}

/** The owner can read an attachment, and so can the members of the room it was posted in. */
export async function canReadAttachment(
  userId: string,
  attachmentId: string,
): Promise<boolean> {
  const attachment = await loadAttachment(attachmentId)
  if (!attachment) return false

  if (attachment.ownerId === userId) return true

  return (
    attachment.roomId !== null &&
    (await isRoomMember(userId, attachment.roomId))
  )
}
```

::field-group
::field{name="input"}
The schema for the input. It works like `input` on `base.on`: it is optional, and `run` gets the checked input as its second argument. LiveThing keeps the input in the upload's record, and `onDiscard` gets it too.
::
::field{name="maxBytes" type="number"}
The most bytes of the **whole upload**, not of one piece. The default is 100 MiB. The client sends the size of a `Blob` or of bytes at the start, so the server refuses a file that is too big before any piece is sent.
::
::field{name="pieceBytes" type="number"}
The biggest piece the client may send. The default is 256 KiB. A piece is one binary message, so `pieceBytes` must fit in the adapter's message limit, with a little room for the header. A value that does not fit makes the server fail when it starts.
::
::field{name="windowBytes" type="number"}
How many bytes more than the bytes that `run` has read the client may send. The default is 2 MiB. It must be at least `pieceBytes`, and `windowBytes + pieceBytes` must be at most the adapter's message limit, or the server fails when it starts. The pieces in the window count against the connection's [byte limit](/server/handlers/per-connection-queue) of twice that limit, so this keeps room for the connection's other messages.
::
::field{name="run" required}
`run(ctx, input, pieces)` reads the pieces with `for await`. Each piece is `{ bytes, offset }`: the bytes, and where they start in the whole file. It returns `{ info }`. The info is a plain object, or `null`, and any other key is a compile error, as for a [binary request](/server/capabilities/binary#binary-requests). The client's `start()` resolves with that info.
::
::field{name="onDiscard"}
`onDiscard(ctx, input)` runs when an upload ends without finishing. See [onDiscard](#ondiscard).
::
::field{name="rateLimit"}
Limits how often the upload **starts**, as it does for a message on `base.on`. Its pieces are not counted, so it does not limit the bytes: the [window](#speed-and-limits) does that. It exists only when you list the [`rateLimit()`](/server/capabilities/rate-limit) capability.
::
::

When `run` throws, the client gets the error, as for a request: a registered error goes back with its code and detail, and any other error becomes `internal-error`. Then `onDiscard` runs.

## `ctx.upload`

`run` gets the normal handler `ctx`, plus `ctx.upload`:

::field-group
::field{name="ctx.upload.savedThrough" type="number"}
Where this run starts. It is `0` for a new upload. For a resumed one, it is the last offset given to `saved()`, and the first piece starts there.
::
::field{name="ctx.upload.state" type="unknown"}
The last `state` given to `saved()`, or `undefined`. Check it before you use it, as `attachmentIdOf` does.
::
::field{name="ctx.upload.saved(offset, { state }?)" type="void"}
Says that the bytes up to `offset` are really stored, so a resume starts there. Give `state` to keep a small JSON value with it, such as a file ID or the parts of a multipart upload. The offset and the state are written in **one SQL write**, so they always match. It throws a `RangeError` when the offset goes back, when it is more than the bytes `run` has read, or when the state is more than 64 KiB of JSON.
::
::field{name="ctx.upload.signal" type="AbortSignal"}
Fires when the client cancels, when the connection closes, or when another connection [takes over](#taking-over) the upload. The `for await` loop throws at the next piece anyway. Pass the signal to every slow call, such as a write to S3, so `run` stops soon, and check it before any side effect, such as posting a message.
::
::

::warning
Stop `run` on `ctx.upload.signal`. When `run` has not settled 10 seconds after it was stopped (a cancel, a takeover, a closed connection, a purge or a failed upload), LiveThing stops waiting for it. The upload continues without it, so a new start can run, and what the old `run` does later is ignored and logged. A `ctx.upload.saved()` from that old `run` throws, so it cannot write over the record of the run that took its place. But a `run` that ignores its signal can still write bytes or post a message after the upload moved on.
::

Call `saved()` only after the bytes are really stored. If the connection drops after a `saved()`, the client sends the bytes after that offset again, and the bytes before it are never sent again. So a `saved()` too early loses bytes, and a `saved()` that comes late only sends some bytes twice. Write the bytes so that the same bytes written twice give the same file, as `writeAttachmentBytes` does with its offset.

## Resuming

A drop does not end an upload. The record stays, and the client starts the upload again with the same upload ID, usually as soon as the socket is open again. On every start, `run` runs **again**, from `ctx.upload.savedThrough`:

1. The first run of `upload-attachment` reads 3 MiB, and calls `saved()` after each piece.
2. The connection drops. The `for await` loop throws `Disconnected`, so `run` stops.
3. The client reconnects and starts the upload again. LiveThing reads the record: the input, the saved offset (3 MiB) and the state (the attachment ID).
4. `run` runs again. `ctx.upload.savedThrough` is 3 MiB, and the first piece has the offset 3 MiB.

The client can resume from another tab, or after a page reload, if it kept the upload ID. A resume must send the same input as the first start, and the same size, or it gets `upload-aborted` with the reason `'input-mismatch'`. See [Resuming after a reload](/client/primitives/uploads#resuming-after-a-reload) on the client.

When `run` returns, the upload is done. If the reply is lost in a drop, the client starts the upload again, and the server sends it the stored reply. `run` does not run a second time. The reply is kept for `retentionAfterDoneMs`.

### Taking over

An upload belongs to its user, and one connection runs it at a time. When another connection of the same user starts the same upload ID, for example a second tab, it **takes over**: the first connection gets `upload-aborted` with the reason `'taken-over'`, its `run` stops, and the new connection resumes the upload once that `run` has settled.

## onDiscard

`onDiscard(ctx, input)` runs when an upload ends without finishing:

- the client cancels it,
- it expires (see [The upload record](#the-upload-record)),
- `run` throws,
- the client breaks the protocol, for example with a piece that is too big,
- or the user is purged with [`purgeUser`](/server/admin/authoring#purgeuser-cleans-up-all-durable-data).

Delete what the upload stored there, or abort a multipart upload. `onDiscard` runs with no connection, like a [scheduled task](/server/handlers/scheduled): its `ctx` has no `ctx.send`, but it has the senders that need no connection. `ctx.upload` holds what the record kept: `savedThrough` and `state`. The `input` is the one the record kept too: what the client sent, after the `input` schema, as JSON. So a schema that makes a `Date` or a `Map` gives `onDiscard` its JSON form, not the object `run` got.

`onDiscard` runs **at least once**. When it throws, LiveThing logs the error, keeps the record, and runs it again about a minute later. So it can run twice for one upload, and it must be safe to run twice: deleting a file that is already deleted must not throw. A drop does not run `onDiscard`, because the upload can still resume.

## The upload record

LiveThing keeps one row per upload in its reserved table `__livething_uploads`, in the server's own SQL storage. Do not write to it yourself.

| Column          | Holds                                                                                                             |
| --------------- | ----------------------------------------------------------------------------------------------------------------- |
| `user_id`       | The user the upload belongs to                                                                                    |
| `upload_id`     | The client's upload ID. The primary key is `user_id` and `upload_id`.                                             |
| `event`         | The upload's event name                                                                                           |
| `input`         | The checked input, as JSON                                                                                        |
| `size`          | The size the client sent at the start, or `NULL`                                                                  |
| `saved_through` | The last offset given to `saved()`                                                                                |
| `state`         | The last state given to `saved()`, as JSON, or `NULL`                                                             |
| `status`        | `'active'`, `'done'` or `'discarding'`                                                                            |
| `reply`         | The reply's info, as JSON, once the upload is done                                                                |
| `updated_at`    | The last time the upload moved: a `saved()`, a piece (at most once a minute), or the end of a run that can resume |

An `active` upload can start or resume. When it gets no piece and no `saved()` for `expireAfterMs`, it **expires**: `onDiscard` runs, then the row is deleted. An upload that a connection is running never expires, even when `run` is slow. A `done` row keeps the reply for `retentionAfterDoneMs`, then it is deleted. A `discarding` row waits for its `onDiscard` to succeed.

LiveThing checks these times with the server's durable alarm, and again each time the server starts. So an upload expires after the server was down too.

`purgeUser` stops the user's running uploads: the client gets `upload-aborted` with the reason `'gone'`. Then `onDiscard` runs for each of the user's uploads that is not done.

## Speed and limits

The client sends pieces until it has sent `windowBytes` more than the bytes that `run` has read. Each time `run` reads a piece, the server tells the client, and the client sends more. So a slow `run`, such as one that waits for S3, slows the client down, and the server never holds much more than `windowBytes` of one upload in memory.

The first message of an upload goes through the same steps as a request: the [intercepts](/server/lifecycle-and-intercept/intercept), with `frame.kind === 'upload'`, then the rate limit, then the `input` check. The pieces skip the intercepts and the rate limit, because the window already limits how fast they come. Until `run` reads a piece, its bytes count against the connection's [byte limit](/server/handlers/per-connection-queue).

The server stops an upload with `upload-aborted` when it cannot continue. For a piece or an end that breaks a rule (`'too-large'`, `'bad-piece'` and `'window'`), the upload is then discarded, and `onDiscard` runs. A size over `maxBytes` at the start is refused before any record exists, so nothing is discarded and `onDiscard` does not run:

| Reason             | When                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| `'too-large'`      | The size at the start, or the bytes that came, are over `maxBytes` or over the size at the start |
| `'input-mismatch'` | A resume sent another input, size or event than the first start                                  |
| `'bad-piece'`      | A piece came with the wrong number, was empty or over `pieceBytes`, or the end did not match     |
| `'window'`         | The client sent more than `windowBytes` more than the bytes `run` has read                       |
| `'taken-over'`     | Another connection of the user started the same upload. The upload continues there.              |
| `'gone'`           | The upload is being discarded: it was cancelled, it failed, or its user was purged               |
| `'interrupted'`    | A piece or the end came for an upload that this server is not running                            |
| `'cancelled'`      | A start came after its own cancel                                                                |

`'interrupted'` happens when the server lost the running upload while the socket stayed open, for example when Cloudflare restarted or moved the Durable Object. The server says it once for each upload on a connection, and for at most 32 different uploads per connection. Pieces for more uploads are dropped with no answer. The record is kept. For a `Blob` or bytes, the LiveThing client starts the upload again by itself, and the upload resumes from its saved offset. The client gives up after 3 tries in a row that store no new bytes. An `AsyncIterable` cannot be read again, so its `start()` rejects with `'not-resumable'` instead, and the client tells the server to discard the upload, so `onDiscard` runs at once.

A cancel can also reach the server while its start is still being handled: a slow intercept holds the start, or the start waits for an older run of the same upload to stop. The server then refuses that start with `'cancelled'`, and discards the stored upload if there is one. This covers only a start **from the same connection** as the cancel, and only while that start is being handled, so a later start of the same `uploadId` runs as normal.

The LiveThing client never breaks the other rules, so `'bad-piece'` and `'window'` point to a bug in another client. On the client, `UploadAborted` has one more reason: `'not-resumable'`, and it creates `'cancelled'` itself when you call `upload.cancel()`. See [Errors](/client/primitives/uploads#errors). Without `uploads()`, the server answers a client's `__uploadEnd__` and `__uploadCancel__` with `unsupported-protocol`.

## S3 and R2 parts

`ctx.upload.saved()` with a state is made for multipart uploads to S3 or R2. They have rules that a piece of 256 KiB does not meet:

- Each part but the last must be at least 5 MiB.
- An upload has at most 10,000 parts.
- R2 wants every part but the last to be the same size.

So `run` collects the pieces into parts of one fixed size, uploads each part, and calls `saved()` after each one, with the list of uploaded parts in the state. After a drop, the next run continues from the end of the last part. This is Huddle's `upload-attachment` when the files go to a bucket instead of a disk. The helpers wrap the bucket's multipart API. The handler has four steps, and the full file is below them.

::steps{level="3"}

### Keep the multipart ID in the state

A new upload starts a multipart upload in the bucket, and keeps its IDs in `ctx.upload.state`, with an empty list of parts. A resumed run finds them there, and continues the same multipart upload:

<!-- docs-check: skip -->

```typescript [server/attachments.ts]
let multipart = ctx.upload.state as Multipart | undefined

if (!multipart) {
  const attachmentId = crypto.randomUUID()
  const multipartId = await startAttachmentUpload(attachmentId)
  multipart = { attachmentId, multipartId, parts: [] }

  ctx.upload.saved(ctx.upload.savedThrough, { state: multipart })
}
```

### Cut the pieces into parts of one size

`partsOf(pieces, PART_BYTES)` is a small Huddle helper. It joins the pieces into parts of exactly `PART_BYTES` bytes, and one shorter last part. After a drop, the pieces start at `ctx.upload.savedThrough`, the end of the last uploaded part, so every part but the last keeps the same size:

<!-- docs-check: skip -->

```typescript [server/attachments.ts]
// Every part but the last has this size. S3 and R2 want at least 5 MiB.
const PART_BYTES = 8 * 1024 * 1024
```

### Upload each part, then call `saved()`

`saved()` comes only after a part is uploaded, with the new list of parts in the state. The bytes of a part that was not uploaded yet are lost in a drop, and the client sends them again. That is at most one part, here 8 MiB. `uploadAttachmentPart` gets `ctx.upload.signal`, so a cancel stops a part that is still being sent:

<!-- docs-check: skip -->

```typescript [server/attachments.ts]
for await (const part of partsOf(pieces, PART_BYTES)) {
  const partNumber = parts.length + 1
  parts.push(
    await uploadAttachmentPart(
      attachmentId,
      multipartId,
      partNumber,
      part,
      ctx.upload.signal,
    ),
  )

  size += part.byteLength
  ctx.upload.saved(size, {
    state: { attachmentId, multipartId, parts },
  })
}
```

### Complete the file, or abort it in `onDiscard`

When the loop ends, `run` completes the multipart upload. An empty file has no parts, and a multipart upload cannot complete with none, so `run` refuses it with `validation-failed`. `onDiscard` aborts the multipart upload, and deletes the file too, in case `run` completed it and then failed:

<!-- docs-check: skip -->

```typescript [server/attachments.ts]
async onDiscard(ctx) {
  const multipart = ctx.upload.state as Multipart | undefined
  if (!multipart) return

  await abortAttachmentUpload(
    multipart.attachmentId,
    multipart.multipartId,
  )
  await deleteAttachment(multipart.attachmentId)
},
```

::

::code-collapse

```typescript [server/attachments.ts]
import { ValidationFailed } from '@livething/server/errors'
import * as v from 'valibot'
import { base } from './base'
import {
  abortAttachmentUpload,
  completeAttachmentUpload,
  deleteAttachment,
  partsOf,
  saveAttachment,
  startAttachmentUpload,
  uploadAttachmentPart,
} from './helpers'

// Every part but the last has this size. S3 and R2 want at least 5 MiB.
const PART_BYTES = 8 * 1024 * 1024

type Multipart = {
  attachmentId: string
  multipartId: string
  parts: { partNumber: number; etag: string }[]
}

export const handleUploadAttachment = base.binary.upload(
  'upload-attachment',
  {
    input: v.object({ fileName: v.string(), fileType: v.string() }),
    maxBytes: 512 * 1024 * 1024,
    async run(ctx, input, pieces) {
      let multipart = ctx.upload.state as Multipart | undefined

      if (!multipart) {
        const attachmentId = crypto.randomUUID()
        const multipartId = await startAttachmentUpload(attachmentId)
        multipart = { attachmentId, multipartId, parts: [] }

        ctx.upload.saved(ctx.upload.savedThrough, {
          state: multipart,
        })
      }

      const { attachmentId, multipartId } = multipart
      const parts = [...multipart.parts]
      let size = ctx.upload.savedThrough

      for await (const part of partsOf(pieces, PART_BYTES)) {
        const partNumber = parts.length + 1
        parts.push(
          await uploadAttachmentPart(
            attachmentId,
            multipartId,
            partNumber,
            part,
            ctx.upload.signal,
          ),
        )

        size += part.byteLength
        ctx.upload.saved(size, {
          state: { attachmentId, multipartId, parts },
        })
      }

      // A multipart upload cannot complete with no parts, so refuse an empty file.
      if (parts.length === 0)
        throw ValidationFailed({
          event: 'upload-attachment',
          issues: [{ message: 'The file is empty.' }],
        })

      await completeAttachmentUpload(attachmentId, multipartId, parts)
      await saveAttachment({
        attachmentId,
        ownerId: ctx.user.id,
        roomId: null,
        fileName: input.fileName,
        fileType: input.fileType,
        size,
      })

      return { info: { attachmentId } }
    },
    async onDiscard(ctx) {
      const multipart = ctx.upload.state as Multipart | undefined
      if (!multipart) return

      await abortAttachmentUpload(
        multipart.attachmentId,
        multipart.multipartId,
      )
      // run may have completed the file, then failed later.
      await deleteAttachment(multipart.attachmentId)
    },
  },
)
```

::

- The list of parts must fit in the 64 KiB of the state. With 8 MiB parts, a file of 512 MiB has at most 64 parts. For bigger files, use bigger parts, or keep the list in your own table and only its ID in the state.
- While `run` waits for a part to upload, the client stops at `windowBytes` more than the last piece `run` read. So the server holds at most one part and one window in memory.

## Patterns

An upload often goes with a message: a file in a chat room, with some text. These are three ways to build it in Huddle, and one check that every way needs. In which order the app does things is its own choice: it can post the text first and show a spinner on the file, or post nothing until the file is stored.

### Upload first, then post

The client uploads the file with `upload-attachment`, and gets the attachment ID. Then it sends a normal JSON event to the room, `post-files`, with the text and the IDs. The `rooms` channel runs the handler only for its members, so the membership check happens when the message is sent. The handler has two steps:

::steps{level="4"}

#### Check each file

`run` removes repeated IDs, then loads each attachment. A user posts only their own files, and each file only once, so any other ID gets `NotFound`:

<!-- docs-check: skip -->

```typescript [server/attachments.ts]
const attachmentIds = [...new Set(input.attachmentIds)]
const files: PostedFile[] = []

for (const attachmentId of attachmentIds) {
  const attachment = await loadAttachment(attachmentId)
  if (
    !attachment ||
    attachment.ownerId !== ctx.user.id ||
    attachment.roomId !== null
  )
    throw NotFound({ id: attachmentId })

  const { fileName, fileType, size } = attachment
  files.push({ attachmentId, fileName, fileType, size })
}
```

#### Post the files

`attachToRoom` puts the files in the room, so its members can download them. Then every member gets one `files-posted` event:

<!-- docs-check: skip -->

```typescript [server/attachments.ts]
await attachToRoom(attachmentIds, ctx.channel.params.roomId)
ctx.channel.broadcast('files-posted', {
  id: crypto.randomUUID(),
  text: input.text,
  files,
  from: ctx.user.id,
  sentAt: Date.now(),
})
```

::

::code-collapse

```typescript [server/attachments.ts]
import * as v from 'valibot'
import { NotFound } from '../shared/errors'
import { rooms } from './base'
import { attachToRoom, loadAttachment } from './helpers'
import type { PostedFile } from './base'

export const handlePostFiles = rooms.on('post-files', {
  input: v.object({
    text: v.string(),
    attachmentIds: v.array(v.string()),
  }),
  async run(ctx, input) {
    const attachmentIds = [...new Set(input.attachmentIds)]
    const files: PostedFile[] = []

    for (const attachmentId of attachmentIds) {
      const attachment = await loadAttachment(attachmentId)
      // A user posts only their own files, and each file only once.
      if (
        !attachment ||
        attachment.ownerId !== ctx.user.id ||
        attachment.roomId !== null
      )
        throw NotFound({ id: attachmentId })

      const { fileName, fileType, size } = attachment
      files.push({ attachmentId, fileName, fileType, size })
    }

    await attachToRoom(attachmentIds, ctx.channel.params.roomId)
    ctx.channel.broadcast('files-posted', {
      id: crypto.randomUUID(),
      text: input.text,
      files,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

::

This keeps the upload simple, and the same file can be uploaded before the user picks a room. But a user can upload a file and never post it. So the app deletes old attachments that no message uses, for example with a [scheduled task](/server/handlers/scheduled) that deletes each attachment whose `roomId` is still `null` after a day.

### Post from `run`

Here one upload does both. The input carries the room and the text, and `run` posts the message itself when the file is stored. It checks that the user is in the room at the start, so a user who is not a member sends no bytes. It checks again at the end, because the user may have left the room while the file was still being sent. When the check fails, `run` throws, the client gets `Forbidden`, and `onDiscard` deletes the file.

`post-attachment` is `upload-attachment` with a room and a text in its input, and these lines around the same `writePieces` call:

<!-- docs-check: skip -->

```typescript [server/attachments.ts]
if (!(await isRoomMember(ctx.user.id, input.roomId)))
  throw Forbidden({ reason: 'not a member of this room' })

const attachmentId = attachmentIdOf(ctx.upload)
const size = await writePieces(ctx.upload, attachmentId, pieces)

// The user may have left the room while the file was still being sent.
if (!(await isRoomMember(ctx.user.id, input.roomId)))
  throw Forbidden({ reason: 'not a member of this room' })
```

After it saves the attachment's record with the room, it checks the signal and posts the message:

<!-- docs-check: skip -->

```typescript [server/attachments.ts]
// A cancel stops run only through its signal: do not post a cancelled file.
ctx.upload.signal.throwIfAborted()
ctx.channels
  .get('rooms', `room:${input.roomId}`)
  .broadcast('files-posted', {
    id: crypto.randomUUID(),
    text: input.text,
    files: [file],
    from: ctx.user.id,
    sentAt: Date.now(),
  })
```

::code-collapse

```typescript [server/attachments.ts]
import * as v from 'valibot'
import { Forbidden } from '../shared/errors'
import {
  attachmentIdOf,
  discardAttachment,
  writePieces,
} from './attachment-files'
import { base } from './base'
import { isRoomMember, saveAttachment } from './helpers'

export const handlePostAttachment = base.binary.upload(
  'post-attachment',
  {
    input: v.object({
      roomId: v.string(),
      text: v.string(),
      fileName: v.string(),
      fileType: v.string(),
    }),
    maxBytes: 512 * 1024 * 1024,
    async run(ctx, input, pieces) {
      if (!(await isRoomMember(ctx.user.id, input.roomId)))
        throw Forbidden({ reason: 'not a member of this room' })

      const attachmentId = attachmentIdOf(ctx.upload)
      const size = await writePieces(ctx.upload, attachmentId, pieces)

      // The user may have left the room while the file was still being sent.
      if (!(await isRoomMember(ctx.user.id, input.roomId)))
        throw Forbidden({ reason: 'not a member of this room' })

      const file = {
        attachmentId,
        fileName: input.fileName,
        fileType: input.fileType,
        size,
      }

      await saveAttachment({
        ...file,
        ownerId: ctx.user.id,
        roomId: input.roomId,
      })

      // A cancel stops run only through its signal: do not post a cancelled file.
      ctx.upload.signal.throwIfAborted()
      ctx.channels
        .get('rooms', `room:${input.roomId}`)
        .broadcast('files-posted', {
          id: crypto.randomUUID(),
          text: input.text,
          files: [file],
          from: ctx.user.id,
          sentAt: Date.now(),
        })

      return { info: { attachmentId } }
    },
    onDiscard(ctx) {
      return discardAttachment(ctx.upload)
    },
  },
)
```

::

An upload belongs to no channel, so `run` reaches the room with `ctx.channels.get(...)`, and checks membership with Huddle's own room list. A cancel does not throw in `run` by itself after the last piece: it only fires `ctx.upload.signal`. So `run` must check `ctx.upload.signal` before any side effect, such as posting a message, as `throwIfAborted()` does here. Then the message and the file come together: no member sees a message whose file is missing, and no file stays without its message.

### Several files with one caption

To send several photos with one caption, the client joins them into one `Blob`: `new Blob(files)`. This copies nothing, and the upload can still resume. The input lists each photo's name, type and size, in the same order, and `run` cuts the bytes apart by offset. The photos are posted together in one message, or not at all. `run` checks the membership at the start and at the end, as `post-attachment` does, and has four steps of its own:

::steps{level="4"}

#### Check the sizes in the input

The client sends the size of the `Blob` at the start, so photos over `maxBytes` are refused before any piece. `run` still checks the sizes in the input, because a client can send any input:

<!-- docs-check: skip -->

```typescript [server/photos.ts]
const total = input.photos.reduce((sum, photo) => sum + photo.size, 0)
if (total > PHOTOS_MAX_BYTES) throw wrongSize
```

#### Collect the bytes

The photos come one after another. `collectBytes(pieces, total)` is a small Huddle helper: it puts each piece at its offset in one array, and gives `null` when the bytes do not match the sizes. So `run` keeps the photos in memory until all of them have come:

<!-- docs-check: skip -->

```typescript [server/photos.ts]
const bytes = await collectBytes(pieces, total)
if (!bytes) throw wrongSize
```

#### Keep the IDs before writing

`run` calls `saved()` only once, with the IDs, before it writes any file. So `onDiscard` can delete every file. A drop sends the photos again from the first byte, and a run that starts again after the IDs were saved finds them in the state, and writes the same files:

<!-- docs-check: skip -->

```typescript [server/photos.ts]
const attachmentIds = Array.isArray(ctx.upload.state)
  ? (ctx.upload.state as string[])
  : input.photos.map(() => crypto.randomUUID())
ctx.upload.saved(ctx.upload.savedThrough, { state: attachmentIds })
```

That is fine for photos. For large files, store each piece as it comes, as `writePieces` does.

#### Write each photo, then post them

`run` cuts the bytes apart by size, and checks the signal before each photo and before the message. `onDiscard` deletes every ID in the state:

<!-- docs-check: skip -->

```typescript [server/photos.ts]
const files: PostedFile[] = []
let start = 0

for (const [index, photo] of input.photos.entries()) {
  ctx.upload.signal.throwIfAborted()
  const file = {
    attachmentId: attachmentIds[index]!,
    fileName: photo.fileName,
    fileType: photo.fileType,
    size: photo.size,
  }

  const photoBytes = bytes.subarray(start, start + photo.size)
  await writeAttachmentBytes(file.attachmentId, 0, photoBytes)
  await saveAttachment({
    ...file,
    ownerId: ctx.user.id,
    roomId: input.roomId,
  })

  files.push(file)
  start += photo.size
}
```

::

The full file then posts one `files-posted` message with the caption as its text:

::code-collapse

```typescript [server/photos.ts]
import { ValidationFailed } from '@livething/server/errors'
import * as v from 'valibot'
import { Forbidden } from '../shared/errors'
import { base } from './base'
import {
  collectBytes,
  deleteAttachment,
  isRoomMember,
  saveAttachment,
  writeAttachmentBytes,
} from './helpers'
import type { PostedFile } from './base'

const PHOTOS_MAX_BYTES = 50 * 1024 * 1024

export const handlePostPhotos = base.binary.upload('post-photos', {
  input: v.object({
    roomId: v.string(),
    caption: v.string(),
    photos: v.array(
      v.object({
        fileName: v.string(),
        fileType: v.string(),
        size: v.pipe(v.number(), v.integer(), v.minValue(1)),
      }),
    ),
  }),
  maxBytes: PHOTOS_MAX_BYTES,
  async run(ctx, input, pieces) {
    if (!(await isRoomMember(ctx.user.id, input.roomId)))
      throw Forbidden({ reason: 'not a member of this room' })

    const wrongSize = ValidationFailed({
      event: 'post-photos',
      issues: [
        { message: 'The photo sizes do not match the bytes.' },
      ],
    })

    const total = input.photos.reduce(
      (sum, photo) => sum + photo.size,
      0,
    )
    if (total > PHOTOS_MAX_BYTES) throw wrongSize

    const bytes = await collectBytes(pieces, total)
    if (!bytes) throw wrongSize

    if (!(await isRoomMember(ctx.user.id, input.roomId)))
      throw Forbidden({ reason: 'not a member of this room' })

    // Keep the IDs before writing, so onDiscard can delete every file. A resumed
    // run finds them in the state, and writes the same files again.
    const attachmentIds = Array.isArray(ctx.upload.state)
      ? (ctx.upload.state as string[])
      : input.photos.map(() => crypto.randomUUID())
    ctx.upload.saved(ctx.upload.savedThrough, {
      state: attachmentIds,
    })

    const files: PostedFile[] = []
    let start = 0

    for (const [index, photo] of input.photos.entries()) {
      ctx.upload.signal.throwIfAborted()
      const file = {
        attachmentId: attachmentIds[index]!,
        fileName: photo.fileName,
        fileType: photo.fileType,
        size: photo.size,
      }

      const photoBytes = bytes.subarray(start, start + photo.size)
      await writeAttachmentBytes(file.attachmentId, 0, photoBytes)
      await saveAttachment({
        ...file,
        ownerId: ctx.user.id,
        roomId: input.roomId,
      })

      files.push(file)
      start += photo.size
    }

    ctx.upload.signal.throwIfAborted()
    ctx.channels
      .get('rooms', `room:${input.roomId}`)
      .broadcast('files-posted', {
        id: crypto.randomUUID(),
        text: input.caption,
        files,
        from: ctx.user.id,
        sentAt: Date.now(),
      })

    return { info: { attachmentIds } }
  },
  async onDiscard(ctx) {
    const attachmentIds = ctx.upload.state
    if (!Array.isArray(attachmentIds)) return

    for (const attachmentId of attachmentIds)
      await deleteAttachment(attachmentId)
  },
})
```

::

See [Several files with one caption](/client/primitives/uploads#several-files-with-one-caption) for the client.

### Checking downloads

An uploaded file is only as private as the handlers that read it. Huddle's [`get-thumbnail`](/server/capabilities/binary#binary-requests) and [`download-attachment`](/server/capabilities/binary#binary-streams) check that the user may read the attachment before they send a byte: the user who uploaded it can, and so can the members of the room it was posted in.

```typescript [server/attachments.ts]
import * as v from 'valibot'
import { NotFound } from '../shared/errors'
import { canReadAttachment } from './attachment-files'
import { base } from './base'
import { makeThumbnail } from './helpers'

export const handleGetThumbnail = base.binary.request(
  'get-thumbnail',
  {
    input: v.object({ attachmentId: v.string() }),
    async run(ctx, input) {
      if (!(await canReadAttachment(ctx.user.id, input.attachmentId)))
        throw NotFound({ id: input.attachmentId })

      const thumbnail = await makeThumbnail(input.attachmentId)
      return {
        info: { fileType: thumbnail.fileType },
        bytes: thumbnail.bytes,
      }
    },
  },
)
```

The answer is `NotFound`, not `Forbidden`, so a user who guesses an ID cannot learn that the attachment exists. The user may not be subscribed to the room when they download, so `canReadAttachment` checks Huddle's own room list, not the channel.

## Uploads in a plugin

A [plugin](/server/plugins/overview) can declare its own uploads. It lists `binary()` and `uploads()` in its scoped `server({ scope: 'plugin', capabilities })`, and calls `binary.upload(name, config)` on its builder. Here the `acme:polls` plugin takes a picture for a poll:

```typescript [polls/poll-images.ts]
import { server } from '@livething/server'
import { binary } from '@livething/server/binary'
import { uploads } from '@livething/server/uploads'
import * as v from 'valibot'
import { writePollImageBytes } from './helpers'

const h = server({
  scope: 'plugin',
  capabilities: [binary(), uploads()],
})

export const handleUploadPollImage = h.binary.upload(
  'upload-poll-image',
  {
    input: v.object({ pollId: v.string() }),
    maxBytes: 5 * 1024 * 1024,
    async run(ctx, input, pieces) {
      for await (const { bytes, offset } of pieces) {
        await writePollImageBytes(input.pollId, offset, bytes)
        ctx.upload.saved(offset + bytes.byteLength)
      }

      return { info: { pollId: input.pollId } }
    },
  },
)
```

- **The wire name** is namespaced like every plugin name: `upload-poll-image` travels as `__acme:polls::upload-poll-image`. See [Namespacing](/server/plugins/namespacing).
- **`run` and `onDiscard`** get the plugin's scoped `ctx`, so its `ctx.kv` keys and its sends are namespaced too.
- **A plugin error** that `run` throws, one the plugin declares with `errors([...])` in its own `capabilities`, reaches the client as `__acme:polls::<code>`. The plugin's client half sees its own short code.
- **List `uploads()` with no options.** The plugin shares the host's upload engine, and the host sets the times.

On the client, the plugin's [scoped socket](/client/plugins/scoped-socket#binary-needs-binary) has `binary.upload('upload-poll-image', input, source)` with the short name. The plugin lists `binary` and `uploads` in its `dependencies`, and the app registers `uploads()`. The app's own contract lists the upload under `binary.uploads['__acme:polls::upload-poll-image']`.

## The contract slice

`InferClient` adds an `uploads` key to the top-level `binary` key of the client contract. Each entry has the type of the input as `payload`, and the type of the reply's info as `response`:

```typescript [shape]
interface HuddleSocket {
  binary: {
    uploads: {
      'upload-attachment': {
        payload: { fileName: string; fileType: string }
        response: { attachmentId: string }
      }
      'post-photos': {
        payload: {
          roomId: string
          caption: string
          photos: {
            fileName: string
            fileType: string
            size: number
          }[]
        }
        response: { attachmentIds: string[] }
      }
    }
  }
}
```

On the client, the [`uploads()`](/client/primitives/uploads) primitive adds `socket.binary.upload(...)` for these entries.

## Names

An upload's name follows the same rules as a binary event's: a non-empty string of up to 128 characters, which does not start or end with `__` and does not contain `::`. In one scope, a name belongs to one handler: `upload-attachment` cannot also be a JSON event or a binary event.

See [Uploads](/learn/wire-protocol#uploads) in the wire protocol for the messages an upload sends.
