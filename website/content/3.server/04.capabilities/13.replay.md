When a client loses its connection and then reconnects, it may have missed messages that the server sent while it was away. **Replay** records the messages the server sends. When the client reconnects, the server sends again the messages that the client missed, so the client catches up. On the client, add the [`replay()` primitive](/client/primitives/replay) together with `dedup()`. It asks the server for the missed messages after each reconnect. Your handlers do not change.

`replay` is an object with three factory functions (functions that create a capability). Two are built-in and need no handler code. The third lets you write the storage and the resend yourself:

| Factory                    | What it does                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------ |
| `replay.history(config?)`  | Built-in. Stores every replayable message as its own row, and resends every message the client missed. |
| `replay.snapshot(config?)` | Built-in. Stores only the latest row for each logical key, and resends that latest state.              |
| `replay.custom()`          | You write the storage and the resend, and register them with `base.replay({ ... })`.                   |

This page shows how to turn replay on and configure it. For how replay works on the wire (the frames the client and server exchange), and for a full guide to writing a custom store, see [Replay](/server/replay/overview). It has two parts: [Built-in replay](/server/replay/built-in) and [Custom replay](/server/replay/custom).

## What replay never stores

Replay records only **broadcasts**: `ctx.broadcast`, `ctx.channel.broadcast`, and a broadcast to one user (`ctx.user.broadcast`, `ctx.users.get(id).broadcast`). It never records a send to one connection, tag, or group (`ctx.send`, `ctx.connections.get(ref).send`, `ctx.channel.send`, `ctx.channel.broadcastTo` a connection/tag/group), because a reconnect gets a new connection ID and no later connection could prove it was the one addressed. It also never stores protocol frames (the internal messages LiveThing uses to run the connection), replies to requests, or stream chunks. See [what replay does not store](/server/replay/overview#what-replay-does-not-store) for the full rule. So a reconnecting client gets back only the broadcasts it missed.

## Built-in replay

### Requirements

Built-in replay (`history` and `snapshot`) finds missed messages by their sequence number (a number that goes up by one for each message sent). So it needs two other capabilities:

- `dedup()`: gives each message a message ID, so the client can drop a replayed message it already has.
- `sequence({ persist: true })`: the sequence number must survive a server restart. A plain `sequence()` is not enough. The server fails to start, and the error tells you to set `persist: true`.

If you leave out `dedup()` or `sequence()`, the build fails with an error that names the missing capability.

Replay and the persistent sequence counter both write to the server's own SQL storage (`ctx.sql`). Every adapter provides this storage, so you do not need to turn on anything extra for it.

### Enabling history mode

History mode keeps every replayable message. When the client reconnects, it gets back every message it missed:

```typescript [history-server.ts]
import { emits, server, t } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [
    emits({ message: t<Message>() }),
    dedup(),
    sequence({ persist: true }),
    replay.history({
      retention: { maxMessages: 100, maxAgeMs: 60_000 },
      durability: 'strict',
      exclude: ['notification'],
    }),
  ],
})
```

### Enabling snapshot mode

Snapshot mode keeps only the latest row for each logical key. Use it for state where each new value replaces the old one, such as the current title of a document or the current value of a counter. A reconnecting client only needs the most recent value, not every change:

```typescript [snapshot-server.ts]
import { emits, server, t } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'
import type { ReplaySnapshotValue } from '@livething/server/replay'

function reduceSnapshot(
  _previous: ReplaySnapshotValue | null,
  next: ReplaySnapshotValue,
): ReplaySnapshotValue | null {
  return next // the newest status always replaces the last one
}

const base = server({
  capabilities: [
    emits({
      'status-changed': t<{ userId: string; status: Status }>(),
    }),
    dedup(),
    sequence({ persist: true }),
    replay.snapshot({
      snapshotKey: (_event, payload) => String(payload.userId),
      reduce: reduceSnapshot,
      retention: { maxMessages: 1 },
      durability: 'best-effort',
    }),
  ],
})
```

Each user's status keeps only its own latest row: a reconnecting client only needs to know where everyone stands right now, not the history of every status change.

### Where it stores rows

Built-in replay keeps one store per scope in the server's own SQL storage. There is **one top-level store** for messages that are not sent on a channel, plus **one store for each channel** whose messages are replayed. In history mode, a store keeps every replayable row. In snapshot mode, it keeps the latest row for each logical key. `retention` limits each store on its own. For the full behavior, including the eviction watermark and the gap signal, see [Built-in replay](/server/replay/built-in#the-gap-signal-and-the-eviction-watermark).

### Built-in config fields

History mode reads `durability`, `retention` and `exclude`. Snapshot mode reads those three, plus `snapshotKey` and `reduce`. Every field is optional.

::field-group
::field{name="durability" type="'strict' | 'best-effort'"}
Default: `'strict'`. `strict` writes the row to storage before the message is sent. `best-effort` sends first, then stores the row in the background. This makes sending faster.
::
::field{name="retention" type="{ maxAgeMs?: number; maxMessages?: number }"}
Default: none. `maxAgeMs`: rows older than this many milliseconds are deleted when the server starts and when new rows are stored. `maxMessages`: when a store has more rows than this, the oldest rows are deleted. Each store has its own limit (one top-level store, plus one for each channel).
::
::field{name="exclude" type="readonly string[]"}
Default: none. Names of outgoing events to skip. The server still sends an excluded event as normal. It just never records or replays it.
::
::field{name="snapshotKey" type="(event, payload) => string"}
Default: the event name. **Snapshot only.** Builds the logical key for a row. Rows with the same key replace each other, so replay keeps only the latest row for each key.
::
::field{name="reduce" type="(previous, next) => value | null"}
Default: latest wins. **Snapshot only.** Combines rows over time. `previous` is the stored value, or `null` if there is none. Return an `{ event, payload }` object to store it, or `null` to delete the snapshot for that key.
::
::

::note
`snapshotKey` and `reduce` only work in snapshot mode. Passing them to `replay.history(...)` is a type error, because the history config does not accept them.
::

### Built-in replay and custom replay cannot be combined

Each scope uses one kind of replay. If you list a built-in factory (`replay.history` or `replay.snapshot`) and also register custom hooks with `base.replay(...)` at the same scope, the build fails.

## Custom replay

`replay.custom()` turns on replay where **you** write the storage and the resend. List the capability, then register your hooks with `base.replay({ ... })`.

Like built-in replay, `replay.custom()` needs `dedup()` and `sequence({ persist: true })`, and the server fails at startup without them. `dedup()` gives each message its ID (`msg.wire.messageId`). `sequence()` gives it a sequence number (`msg.wire.deliverySeq`), and `persist: true` keeps those numbers valid after a restart, so the rows your store keeps still make sense:

```typescript [custom-server.ts]
import { emits, server, t } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [
    emits({ message: t<Message>() }),
    dedup(),
    sequence({ persist: true }),
    replay.custom(),
  ],
})

base.onInit((ctx) => {
  ctx.sql.exec(`
    CREATE TABLE IF NOT EXISTS replay_log (
      seq INTEGER NOT NULL,
      message_id TEXT NOT NULL,
      event TEXT NOT NULL,
      payload TEXT NOT NULL,
      confirmed INTEGER NOT NULL DEFAULT 0
    )
  `)
})

base.replay({
  beforeBroadcast(ctx, msg) {
    ctx.sql.exec(
      'INSERT INTO replay_log (seq, message_id, event, payload) VALUES (?, ?, ?, ?)',
      msg.wire.deliverySeq,
      msg.wire.messageId,
      msg.event,
      JSON.stringify(msg.payload),
    )
  },
  async replay(ctx, since) {
    const rows = ctx.sql
      .exec<{
        event: string
        payload: string
        seq: number
        message_id: string
      }>(
        'SELECT event, payload, seq, message_id FROM replay_log WHERE seq > ? ORDER BY seq ASC',
        since,
      )
      .toArray()
    for (const row of rows) {
      ctx.sendReplay(row.event, JSON.parse(row.payload), {
        deliverySeq: row.seq,
        messageId: row.message_id,
      })
    }
  },
})
```

The hooks only see **broadcasts** (`ctx.broadcast`, `ctx.channel.broadcast`, `ctx.user.broadcast`, and similar). A send to one connection, tag, or group never reaches them.

| Hook              | Required | When it runs                             | Durability                                                       |
| ----------------- | -------- | ---------------------------------------- | ---------------------------------------------------------------- |
| `beforeBroadcast` | no       | before any recipient is sent the frame   | strict: if this hook throws, no recipient receives the broadcast |
| `afterBroadcast`  | no       | after every recipient was sent the frame | best-effort: a throw or rejection here is only logged            |
| `replay`          | **yes**  | when a client reconnects                 | reads your store and resends the messages the client missed      |

Your `replay` hook receives the last sequence number the client saw, as `since`. Read every row newer than `since` and call `ctx.sendReplay(event, payload, wire)` for each one. `wire` is `{ deliverySeq, messageId, channel?, channelFamily? }`.

Use `afterBroadcast` when you want to mark a row as confirmed after the message was actually sent. Here is a version of the same hooks that does this:

```typescript [confirm-server.ts]
base.replay({
  beforeBroadcast(ctx, msg) {
    ctx.sql.exec(
      'INSERT INTO replay_log (seq, message_id, event, payload, confirmed) VALUES (?, ?, ?, ?, 0)',
      msg.wire.deliverySeq,
      msg.wire.messageId,
      msg.event,
      JSON.stringify(msg.payload),
    )
  },
  afterBroadcast(ctx, msg) {
    ctx.sql.exec(
      'UPDATE replay_log SET confirmed = 1 WHERE seq = ?',
      msg.wire.deliverySeq,
    )
  },
  async replay(ctx, since) {
    // ...read and resend rows newer than `since`
  },
})
```

In the `replay` hook, `ctx.request` is a `{ channel: string | null; channelFamily: string | null }` value. It names the channel the client's replay request is for. Both fields are `null` for a top-level request (a request that is not for a channel). One top-level `base.replay({...})` can serve several channels: check `ctx.request.channel` to choose which rows to read. In `beforeBroadcast` and `afterBroadcast`, `msg.wire.channel` and `msg.wire.channelFamily` tell you which channel a message was sent on, so you can store that with the row.

`ctx.sendReplay(event, payload, wire)` checks that `event` is declared in the active scope. If it is not, the call throws.

See [Custom replay](/server/replay/custom) for the full guide.

## Per-channel replay

Built-in replay records top-level messages and channel messages. Each channel gets its own replay store. To change replay for one channel, set the `replay` field in that channel's config:

- No `replay` field: the channel uses the server-level replay that you listed in `capabilities`.
- `replay: true`: the channel gets its own replay in history mode with the default settings (`strict` durability, no retention limits, no `exclude` list). It does not copy the options you passed to `replay.history(...)` or `replay.snapshot(...)`.
- `replay: false`: turns replay off for this channel only.

```typescript [channel-replay-server.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { dedup } from '@livething/server/dedup'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'
import * as v from 'valibot'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    emits({ message: t<Message>() }),
    dedup(),
    sequence({ persist: true }),
    replay.history(),
    channels(),
  ],
})

// Uses the server-level replay: messages here are recorded and replayed.
export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
})

// Opts out: nothing in this channel is recorded or replayed. A typing
// indicator is stale the moment the reconnect finishes, so there is
// nothing worth catching up on.
export const typingIndicators = base.channel('typing-indicators', {
  replay: false,
  capabilities: [
    emits({ typing: t<{ from: string; room: string }>() }),
  ],
})

export const handleStartTyping = typingIndicators.on('start-typing', {
  input: v.object({ room: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('typing', {
      from: ctx.user.id,
      room: input.room,
    })
  },
})
```

A channel can also run **custom** replay with its own store. Call `channelHandle.replay({ ... })` with the same `beforeBroadcast`, `afterBroadcast` and `replay` hooks. See [Custom replay](/server/replay/custom).

## Host-only capability :badge[host-only]

The `replay.*` capabilities are **host-only**. They record messages for the whole connection, so you cannot list them inside a plugin's scoped server definition. A plugin that needs replay declares a dependency on the host's replay instead. See [Depending on host capabilities](/server/plugins/depends-on).

## What it adds to the client contract

Nothing. Replay adds no keys to the client contract and no methods to the client socket. With the client's `replay()` primitive in place, a reconnecting client receives the events it missed, on the same channels and with the same event names it already knows.
