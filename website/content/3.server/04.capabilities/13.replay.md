When a client drops and reconnects, it may have missed messages the server sent while it was gone. **Replay** records outgoing messages and re-sends the missing tail on reconnect, so the client catches up. The client does nothing — replay is transparent reconnect recovery.

`replay` is an object with three factories. Two are built-in (no handler code); one hands the storage and resend to you:

| Factory                    | What it does                                                                    |
| -------------------------- | ------------------------------------------------------------------------------- |
| `replay.history(config?)`  | Built-in. Keeps every replayable message as its own row, re-sends the tail.     |
| `replay.snapshot(config?)` | Built-in. Keeps only the latest row per logical key, re-sends the latest state. |
| `replay.custom()`          | You own the storage and the resend, wired through `base.replay({ ... })`.       |

This page is the enable-and-configure reference. For how replay behaves on the wire and how to author a custom store end to end, see [Replay](/server/replay/overview) — split into [Built-in replay](/server/replay/built-in) and [Custom replay](/server/replay/custom).

## What replay never stores

Replay only records your own outgoing application events. It never stores protocol frames, request/response replies, or stream chunks. So a reconnecting client gets back the events it missed, not the plumbing.

## Built-in replay

### Requirements

Built-in replay (`history` and `snapshot`) re-sends by sequence number, so it requires two other capabilities:

- `dedup()` — so a replayed message the client already has is dropped.
- `sequence({ persist: true })` — the sequence number has to survive a restart. A plain `sequence()` is not enough; the build fails and tells you to set `persist: true`.

Both replay and the persistent sequence counter write to the server's own SQL storage (via `ctx.sql`) — every adapter guarantees that storage, so there is nothing extra to turn on for it. Leave `dedup()` or `sequence({ persist: true })` out and the build fails at boot with a message naming the fix.

### Enabling history mode

History mode keeps every replayable message. On reconnect the client gets back the full tail it missed:

```typescript [history-server.ts]
import { emits, server, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { replay } from '@wskit/server/replay'
import { sequence } from '@wskit/server/sequence'

const base = server({
  capabilities: [
    emits({ 'chat-msg': t<{ text: string; from: string }>() }),
    dedup(),
    sequence({ persist: true }),
    replay.history({
      retention: { maxMessages: 100, maxAgeMs: 60_000 },
      durability: 'strict',
      exclude: ['cursor'],
    }),
  ],
})
```

### Enabling snapshot mode

Snapshot mode keeps only the latest row per logical key. It is for state that overwrites itself — a document's current title, a counter's current value — where a reconnecting client only needs the most recent value, not every step:

```typescript [snapshot-server.ts]
import { emits, server, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { replay } from '@wskit/server/replay'
import { sequence } from '@wskit/server/sequence'
import type { ReplaySnapshotValue } from '@wskit/server/replay'

function reduceSnapshot(
  previous: ReplaySnapshotValue | null,
  next: ReplaySnapshotValue,
): ReplaySnapshotValue | null {
  if (next.event === 'doc-deleted') return null // drop the snapshot for this key
  if (next.event !== 'counter-snapshot') return next // latest wins

  const previousTotal =
    previous?.event === 'counter-snapshot'
      ? Number(previous.payload.total)
      : 0
  return {
    event: next.event,
    payload: {
      ...next.payload,
      total: previousTotal + Number(next.payload.total),
    },
  }
}

const base = server({
  capabilities: [
    emits({
      'doc-snapshot': t<{ docId: string; title: string }>(),
      'doc-deleted': t<{ docId: string }>(),
      'counter-snapshot': t<{ key: string; total: number }>(),
    }),
    dedup(),
    sequence({ persist: true }),
    replay.snapshot({
      snapshotKey: (_event, payload) =>
        String(payload.docId ?? payload.key),
      reduce: reduceSnapshot,
      retention: { maxMessages: 5 },
      durability: 'best-effort',
    }),
  ],
})
```

### Where it stores rows

Built-in replay keeps one store per scope in the server's own SQL storage: **one top-level store** for non-channel messages, plus **one store per channel** that runs its own replay. History keeps every replayable row; snapshot keeps the latest row per logical key. `retention` bounds each store independently. Full behaviour — including the eviction watermark and the gap signal — is on [Built-in replay](/server/replay/built-in#the-gap-signal-and-the-eviction-watermark).

### Built-in config fields

History mode reads `durability`, `retention`, and `exclude`. Snapshot mode reads those three plus `snapshotKey` and `reduce`. Every field is optional.

| Field         | Type                                          | Default        | What it does                                                                                                                                                                                                               |
| ------------- | --------------------------------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `durability`  | `'strict' \| 'best-effort'`                   | `'strict'`     | `strict` writes to storage before the send completes; `best-effort` sends first, then stores in the background for lower latency.                                                                                          |
| `retention`   | `{ maxAgeMs?: number; maxMessages?: number }` | none           | `maxAgeMs`: rows older than this are deleted on boot and when new rows are stored. `maxMessages`: past this count, the oldest rows are deleted. The limit is per replay store (one top-level store, plus one per channel). |
| `exclude`     | `readonly string[]`                           | none           | Outgoing event names to skip. An excluded event is still sent normally — it is just never recorded and never replayed.                                                                                                     |
| `snapshotKey` | `(event, payload) => string`                  | the event name | **Snapshot only.** Builds the logical key for a row. Rows that share a key replace each other, so replay keeps only the latest per key.                                                                                    |
| `reduce`      | `(previous, next) => value \| null`           | latest wins    | **Snapshot only.** Combines rows over time. `previous` is the stored value or `null`. Return an `{ event, payload }` to store, or `null` to delete the snapshot for that key.                                              |

::note
`snapshotKey` and `reduce` only do anything in snapshot mode. Passing them to `replay.history(...)` is a type error — the history config does not accept them.
::

### history and snapshot are mutually exclusive with custom

At one scope you pick one approach. Listing a built-in factory (`replay.history` or `replay.snapshot`) and `replay.custom()` together is a build error — you cannot mix automatic replay with your own store at the same scope.

## Custom replay

`replay.custom()` enables replay where **you** own the storage and the resend. Unlike built-in replay, it does not require `dedup` or `sequence` — you control how messages are keyed and read back. List the capability, then register the hooks with `base.replay({ ... })`:

```typescript [custom-server.ts]
import { emits, server, t } from '@wskit/server'
import { replay } from '@wskit/server/replay'

const base = server({
  capabilities: [
    emits({ note: t<{ text: string; author: string }>() }),
    replay.custom(),
  ],
})

base.onInit((ctx) => {
  ctx.sql.exec(`
    CREATE TABLE IF NOT EXISTS replay_log (
      seq INTEGER NOT NULL,
      message_id TEXT NOT NULL,
      event TEXT NOT NULL,
      payload TEXT NOT NULL
    )
  `)
})

base.replay({
  beforeSend(ctx, msg) {
    ctx.sql.exec(
      'INSERT INTO replay_log (seq, message_id, event, payload) VALUES (?, ?, ?, ?)',
      msg.wire.seq,
      msg.wire.messageId,
      msg.event,
      JSON.stringify(msg.payload),
    )
  },
  async replay(ctx, since) {
    const rows = ctx.sql
      .exec<{
        event: string
        payload: string
        seq: number
        message_id: string
      }>(
        'SELECT event, payload, seq, message_id FROM replay_log WHERE seq > ? ORDER BY seq ASC',
        since,
      )
      .toArray()
    for (const row of rows) {
      ctx.sendReplay(row.event, JSON.parse(row.payload), {
        seq: row.seq,
        messageId: row.message_id,
      })
    }
  },
})
```

The hooks:

| Hook         | Required | When it runs                         | Durability                                     |
| ------------ | -------- | ------------------------------------ | ---------------------------------------------- |
| `beforeSend` | no       | before each outgoing message is sent | strict — stored before the send completes      |
| `afterSend`  | no       | after each outgoing message is sent  | best-effort — stored in the background         |
| `replay`     | **yes**  | on reconnect                         | reads your store and re-sends the missing tail |

Your `replay` hook receives the client's last known sequence number as `since`. Read everything newer than `since` and call `ctx.sendReplay(event, payload, wire)`, where `wire` is `{ seq, messageId, channel?, channelFamily? }`. Use `afterSend` when you want to mark a row as confirmed once the send actually went out:

```typescript [confirm-server.ts]
base.replay({
  beforeSend(ctx, msg) {
    ctx.sql.exec(
      'INSERT INTO replay_log (seq, event, payload, confirmed) VALUES (?, ?, ?, 0)',
      msg.wire.seq,
      msg.event,
      JSON.stringify(msg.payload),
    )
  },
  afterSend(ctx, msg) {
    ctx.sql.exec(
      'UPDATE replay_log SET confirmed = 1 WHERE seq = ?',
      msg.wire.seq,
    )
  },
  async replay(ctx, since) {
    // ...read and re-send rows newer than `since`
  },
})
```

The hook `ctx` also carries `ctx.request` — a `{ channel: string | null; channelFamily: string | null }` value naming the channel scope a frame belongs to, both `null` for a top-level frame. A single top-level `base.replay({...})` that covers several channels can branch on `ctx.request.channel` to store or read the right rows.

`ctx.sendReplay(event, payload, wire)` validates the `event` name exactly like `ctx.send` — re-sending an event the active scope never declared throws.

See [Custom replay](/server/replay/custom) for the full authoring walkthrough.

## Per-channel replay

Built-in replay records both top-level messages and per-channel messages. Each channel gets its own replay store. You can tune one channel from its config with the `replay` field:

- `replay: true` — inherit the global settings and enable replay for this channel.
- `replay: false` — turn replay off for this channel only.

```typescript [channel-replay-server.ts]
import { emits, server, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { dedup } from '@wskit/server/dedup'
import { replay } from '@wskit/server/replay'
import { sequence } from '@wskit/server/sequence'
import * as v from 'valibot'

const base = server({
  capabilities: [
    emits({ 'room-msg': t<{ text: string; from: string }>() }),
    dedup(),
    sequence({ persist: true }),
    replay.history(),
    channels(),
  ],
})

// Inherits global replay — messages here are recorded and replayed.
const replayRoom = base.channel('replay-room', {
  capabilities: [
    emits({ 'room-msg': t<{ text: string; from: string }>() }),
  ],
})

// Opts out — nothing in this channel is recorded or replayed.
const optoutRoom = base.channel('optout-room', {
  replay: false,
  capabilities: [
    emits({ 'room-msg': t<{ text: string; from: string }>() }),
  ],
})

export const handleSend = optoutRoom.on('send-room-msg', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('room-msg', {
      text: payload.text,
      from: ctx.meta.username,
    })
  },
})
```

A channel can also run **custom** replay on its own store with `channelHandle.replay({ ... })`, with the same `beforeSend` / `afterSend` / `replay` hooks. See [Custom replay](/server/replay/custom).

## Host-only capability :badge[host-only]

The `replay.*` family is **host-only** — it owns connection-wide recording, so you cannot list it inside a plugin's scoped server definition. A plugin that needs replay declares a dependency on the host instead. See [Depending on host capabilities](/server/plugins/depends-on).

## What it adds to the client contract

Nothing. Replay is transparent: it adds no keys to the client contract and no methods to the client socket. A reconnecting client simply receives the events it missed, on the same channels and event names it already knows.
