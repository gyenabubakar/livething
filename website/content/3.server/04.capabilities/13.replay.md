When a client loses its connection and then reconnects, it may have missed messages that the server sent while it was away. **Replay** records the messages the server sends. When the client reconnects, the server sends again the messages that the client missed, so the client catches up. On the client, add the [`replay()` primitive](/client/primitives/replay) together with `dedup()`. It asks the server for the missed messages after each reconnect. Your handlers do not change.

`replay` is an object with two factory functions. Neither needs handler code:

| Factory                    | What it does                                                                                 |
| -------------------------- | -------------------------------------------------------------------------------------------- |
| `replay.history(config?)`  | Stores every replayable message as its own row, and resends every message the client missed. |
| `replay.snapshot(config?)` | Stores only the latest row for each logical key, and resends that latest state.              |

This page shows how to turn replay on and configure it. For how replay works on the wire, and for the full behavior of each mode, see [Replay](/server/replay/overview) and [History and snapshot](/server/replay/history-and-snapshot).

## What replay records

[Replay records](/server/replay/overview#what-replay-records) every message the server sends: broadcasts (`ctx.broadcast`, `ctx.channel.broadcast`), broadcasts to one user (`ctx.user.broadcast`, `ctx.users.get(id).broadcast`), and sends to chosen connections (`ctx.send`, `ctx.connections.get(ref).send`, `ctx.channel.send`, `broadcastTo` a connection, tag or group, and tag broadcasts). A reconnecting client gets back only what was addressed to it. For a send to chosen connections, the client proves it with the secret resume token its earlier connection got. Replay never stores protocol frames, replies to requests, or stream chunks.

## History and snapshot

### Requirements

Replay (`history` and `snapshot`) finds missed messages by their sequence number. So it needs two other capabilities:

- `dedup()`: gives each message a message ID, so the client can drop a replayed message it already has.
- `sequence({ persist: true })`: the sequence number must survive a server restart. A plain `sequence()` is not enough. The server fails to start, and the error tells you to set `persist: true`.

If you leave out `dedup()` or `sequence()`, the build fails with an error that names the missing capability.

Replay and the persistent sequence counter both write to the server's own SQL storage (`ctx.sql`). Every adapter provides this storage, so you do not need to turn on anything extra for it. Even with no `retention` set, each store keeps at most 64 MiB of messages for each audience (`retention.maxBytes`), and deletes the oldest past that.

### Enabling history mode

History mode keeps every replayable message. When the client reconnects, it gets back every message it missed:

```typescript [server/replay-history.ts]
import { emits, server, t } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'
import type { Message } from './base'

const base = server({
  capabilities: [
    emits({ message: t<Message>() }),
    dedup(),
    sequence({ persist: true }),
    replay.history({
      retention: { maxMessages: 100, maxAgeMs: 60_000 },
      durability: 'strict',
      exclude: ['notification'],
    }),
  ],
})
```

### Enabling snapshot mode

Snapshot mode keeps only the latest row for each logical key. Use it for state where each new value replaces the old one, such as the current title of a document or the current value of a counter. A reconnecting client only needs the most recent value, not every change:

```typescript [server/replay-snapshot.ts]
import { emits, server, t } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'
import type { ReplaySnapshotValue } from '@livething/server/replay'
import type { Status } from './base'

function reduceSnapshot(
  _previous: ReplaySnapshotValue | null,
  next: ReplaySnapshotValue,
): ReplaySnapshotValue | null {
  return next // the newest status always replaces the last one
}

const base = server({
  capabilities: [
    emits({
      'status-changed': t<{ userId: string; status: Status }>(),
    }),
    dedup(),
    sequence({ persist: true }),
    replay.snapshot({
      snapshotKey: (_event, payload) => String(payload?.userId),
      reduce: reduceSnapshot,
      durability: 'best-effort',
    }),
  ],
})
```

Each user's status keeps only its own latest row: a reconnecting client only needs to know where everyone stands right now, not the history of every status change. This example sets no `retention.maxMessages` on purpose. A broadcast's rows all share one audience, and `maxMessages` counts rows for each audience, so a small cap would delete other users' latest rows.

### Where it stores rows

Replay keeps one store per scope in the server's own SQL storage. There is **one top-level store** for messages that are not sent on a channel, plus **one store for each channel** whose messages are replayed. In history mode, a store keeps every replayable row. In snapshot mode, it keeps the latest row for each logical key. `retention` limits each store on its own, and inside a store it limits the messages sent to everyone, each user's messages, and each anonymous connection's messages separately. For the full behavior, including the eviction watermark and the gap signal, see [History and snapshot](/server/replay/history-and-snapshot#the-gap-signal-and-the-eviction-watermark).

### Config fields

History mode reads `durability`, `retention` and `exclude`. Snapshot mode reads those three, plus `snapshotKey` and `reduce`. Every field is optional.

::field-group
::field{name="durability" type="'strict' | 'best-effort'"}
Default: `'strict'`. `strict` writes the row to storage before the message is sent. `best-effort` sends first, then stores the row in the background. This makes sending faster.
::
::field{name="retention" type="{ maxAgeMs?: number; maxMessages?: number; maxBytes?: number }"}
Default: `maxBytes` of 64 MiB, and no other limit. `maxAgeMs`: rows older than this many milliseconds are deleted when the server starts and when new rows are stored. `maxMessages`: when a store has more rows than this, the oldest rows are deleted. `maxBytes`: when a store holds more bytes than this (each row's JSON payload in UTF-8, plus the bytes of a binary event), the oldest rows are deleted. Each store has its own limit (one top-level store, plus one for each channel).
::
::field{name="exclude" type="readonly string[]"}
Default: none. Names of outgoing events to skip, JSON or binary. The server still sends an excluded event as normal. It just never records or replays it.
::
::field{name="snapshotKey" type="(event, payload) => string"}
Default: the event name. **Snapshot only.** Builds the logical key for a row. Rows with the same key replace each other, so replay keeps only the latest row for each key. `payload` is `null` for an event sent with no payload, so read it with `?.`.
::
::field{name="reduce" type="(previous, next) => value | null"}
Default: latest wins. **Snapshot only.** Combines rows over time. `previous` is the stored value, or `null` if there is none. Return an `{ event, payload }` object to store it, or `null` to delete the snapshot for that key.
::
::

::note
`snapshotKey` and `reduce` only work in snapshot mode. Passing them to `replay.history(...)` is a type error, because the history config does not accept them.
::

History replay stores [binary events](/server/binary/overview) with their bytes, in the same order as JSON events. `replay.snapshot(...)` fails at startup when a [binary event would go into its store](/server/replay/overview#binary-events), because `reduce` cannot combine bytes.

## Per-channel replay

Replay records top-level messages and channel messages. Each channel gets its own replay store. To change replay for one channel, set the `replay` field in that channel's config:

- No `replay` field: the channel uses the server-level replay that you listed in `capabilities`.
- `replay: true`: the channel gets its own replay in history mode with the default settings (`strict` durability, the default `maxBytes` of 64 MiB and no other retention limit, no `exclude` list). It does not copy the options you passed to `replay.history(...)` or `replay.snapshot(...)`.
- `replay: false`: turns replay off for this channel only.

Huddle's `rooms` uses the server-level replay. This example also adds a `typingIndicators` channel that is not part of Huddle, to show the opt-out:

```typescript [server/replay-per-channel.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { dedup } from '@livething/server/dedup'
import { CloseCodes, RejectAuth } from '@livething/server/errors'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'
import * as v from 'valibot'
import { verifySession } from './auth'
import type { Message } from './base'

const base = server({
  async authenticate(request) {
    const token = request.headers
      .get('Authorization')
      ?.replace('Bearer ', '')
    const user = await verifySession(token)
    if (!user) {
      throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { userId: user.id, name: user.name, role: user.role },
    }
  },
  capabilities: [
    emits({ message: t<Message>() }),
    dedup(),
    sequence({ persist: true }),
    replay.history(),
    channels(),
  ],
})

// Uses the server-level replay: messages here are recorded and replayed.
export const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ message: t<Message>() })],
})

// Opts out: nothing in this channel is recorded or replayed. A typing
// indicator is stale the moment the reconnect finishes, so there is
// nothing worth catching up on.
export const typingIndicators = base.channel(
  ['typing-indicators', 'typing:{roomId}'],
  {
    replay: false,
    capabilities: [emits({ typing: t<{ from: string }>() })],
  },
)

export const handleStartTyping = typingIndicators.on('start-typing', {
  input: v.object({}),
  run(ctx) {
    ctx.channel.broadcast('typing', { from: ctx.user.id })
  },
})
```

## Host-only capability :badge[host-only]

The `replay.*` capabilities are **host-only**. They record messages for the whole connection, so you cannot list them inside a plugin's scoped server definition. A plugin that needs replay [declares a dependency on the host's replay](/server/plugins/depends-on) instead.

## What it adds to the client contract

Nothing. Replay adds no keys to the client contract and no methods to the client socket. With the client's `replay()` primitive in place, a reconnecting client receives the events it missed, on the same channels and with the same event names it already knows.
