`rateLimit(config?)` caps how many messages a connection can send in a window. It is off by default. Listing the capability is **required** to use any rate limit at all — even a single per-handler override needs the capability to be on the server.

## What it does

Rate limiting runs before validation and before your handler, so a throttled frame never reaches your code. It uses a token bucket: each bucket refills continuously and a frame spends one token. When the bucket is empty, the frame is rejected with the built-in `RateLimited` error.

You enable it in one of two ways:

- **With a global rule** — `rateLimit({ windowMs, max, per })` sets a default every event shares.
- **With no argument** — `rateLimit()` turns the capability on without a global default, so only handlers that set their own `rateLimit` override are limited.

## How to enable

Import it from its subpath and add it to your capability array. A global rule applies to every event:

```typescript [server.ts]
import { define, t } from '@wskit/server'
import { rateLimit } from '@wskit/server/rate-limit'

const base = define({
  env: t<Env>(),
  capabilities: [rateLimit({ windowMs: 60_000, max: 100 })],
})
```

To limit only a few handlers and leave the rest unlimited, list it with no argument:

```typescript [no-global-server.ts]
import { define, t } from '@wskit/server'
import { rateLimit } from '@wskit/server/rate-limit'

const base = define({
  env: t<Env>(),
  capabilities: [rateLimit()], // on, but no global default
})
```

## The global rule

The argument to `rateLimit(...)` is the server-wide default. Every field is optional.

| Field      | Type              | Default                              | What it does                                                                                                                                          |
| ---------- | ----------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `windowMs` | `number`          | `60000`                              | Length of the rolling window, in milliseconds.                                                                                                        |
| `max`      | `number`          | `60`                                 | Maximum events allowed per window.                                                                                                                    |
| `per`      | `(ctx) => string` | `ctx.connection.id` (per-connection) | Picks the bucket key. The default gives each connection its own budget. Return `ctx.user.id` to share one budget across every socket a user has open. |

The bucket refills continuously at `max / windowMs` tokens per millisecond, capped at `max`. So a window of `60_000` ms and `max: 60` means one token back per second, up to 60 in hand.

## Per-handler and per-channel overrides

Any handler or channel can override the rule with its own `rateLimit` config. The override shape is the same at every level, plus an `enabled` switch:

| Field      | Type              | Default   | What it does                                                                            |
| ---------- | ----------------- | --------- | --------------------------------------------------------------------------------------- |
| `enabled`  | `boolean`         | —         | `true` turns the rule on at this scope; `false` disables it and stops the cascade here. |
| `windowMs` | `number`          | inherited | Window length. Omit to keep the parent's.                                               |
| `max`      | `number`          | inherited | Max events per window. Omit to keep the parent's.                                       |
| `per`      | `(ctx) => string` | inherited | Bucket key. Omit to keep the parent's.                                                  |

An override is a **partial** override: a channel's `{ enabled: true, max: 200 }` keeps the parent's `windowMs` and `per`, and only changes `max`.

You can set `rateLimit` on:

- A `base.on(...)` or `base.request(...)` handler config.
- A channel handler's `.on(...)` or `.request(...)` config.
- A channel's own config — a channel-level rule that all its events share.

::note
The override applies to message handlers (`on` and `request`). Stream handlers do not carry a per-handler `rateLimit` field — limit the event that starts a stream, or set a channel-level rule, instead.
::

### Tighten one handler

```typescript [expensive-server.ts]
import { define, emits, t } from '@wskit/server'
import { rateLimit } from '@wskit/server/rate-limit'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [
    rateLimit({ windowMs: 60_000, max: 60 }),
    emits({ 'expensive-done': t<{}>() }),
  ],
})

// One expensive call per window, even though the global cap is 60.
export const handleExpensive = base.on('expensive', {
  input: v.object({}),
  rateLimit: { enabled: true, max: 1 },
  run(ctx) {
    ctx.send('expensive-done', {})
  },
})
```

### Share a budget across a user's sockets with a custom `per`

```typescript [shared-server.ts]
import { define, emits, t } from '@wskit/server'
import { rateLimit } from '@wskit/server/rate-limit'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [rateLimit(), emits({ 'shared-done': t<{}>() })],
})

// Two sockets with the same username draw from one bucket.
export const handleSharedTick = base.on('shared-tick', {
  input: v.object({}),
  rateLimit: { enabled: true, max: 2, per: (ctx) => ctx.meta.username },
  run(ctx) {
    ctx.send('shared-done', {})
  },
})
```

### A channel rule plus an inner handler override

```typescript [channel-server.ts]
import { define, emits, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { rateLimit } from '@wskit/server/rate-limit'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [rateLimit({ windowMs: 60_000, max: 60 }), channels()],
})

// Channel-level rule: everything in `rooms` shares a cap of 50 per window.
const rooms = base.channel('rooms', {
  capabilities: [emits({ 'chatter-broadcast': t<{ text: string }>() })],
  rateLimit: { enabled: true, max: 50 },
})

// One handler inside the channel tightens its own cap to 1.
export const handleChatter = rooms.on('chatter', {
  input: v.object({ text: v.string() }),
  rateLimit: { enabled: true, max: 1 },
  run(ctx, payload) {
    ctx.channel.broadcast('chatter-broadcast', payload, { includeSelf: true })
  },
})
```

### Exempt a channel from the cap

Set `{ enabled: false }` to disable the rule and stop the cascade at that scope:

```typescript [exempt-server.ts]
import { define, emits, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { rateLimit } from '@wskit/server/rate-limit'
import * as v from 'valibot'

const base = define({
  env: t<Env>(),
  capabilities: [rateLimit({ windowMs: 60_000, max: 60 }), channels()],
})

// No cap on this channel — events here are never throttled.
const noLimit = base.channel('no-limit', {
  capabilities: [emits({ msg: t<{ text: string }>() })],
  rateLimit: { enabled: false },
})

export const handleNoLimitSend = noLimit.on('send', {
  input: v.object({ text: v.string() }),
  run(ctx, payload) {
    ctx.channel.broadcast('msg', payload, { includeSelf: true })
  },
})
```

## The cascade

When several rules could apply to one event, the most specific wins:

::steps

### Per-handler override

A `rateLimit` on the handler itself. Highest precedence.

### Channel-level rule

The `rateLimit` on the channel config, for events inside that channel.

### Global rule

The `rateLimit(...)` rule from the capability. The fallback for everything else.
::

A channel with no rule of its own still inherits the global rule — its events share the top-level bucket rather than passing through unlimited. An `{ enabled: false }` at any level disables the rule there and stops the cascade, so nothing further up applies. A child scope can opt back in, though: setting `{ enabled: true }` below a disabled parent re-enables limiting at that scope, with default values filling any field the child leaves unset.

## What a throttled frame looks like

A rejected frame comes back as the built-in `RateLimited` error. Its `detail.retryAfterMs` is the number of milliseconds to wait before trying again — always at least `1000`. The frame's correlation ID is kept, so a throttled `request` still settles on the client (it rejects with the error rather than hanging). See the [built-in errors catalog](/core/builtin-errors) for the `RateLimited` shape.

::caution
Buckets are in-memory only. They are **not** persisted across hibernation — when the server hibernates and wakes, every bucket starts full again. Rate limiting protects against bursts within a live session, not across restarts.
::

## Host-only capability

`rateLimit` is **host-only** — it owns connection-wide throttling, so you cannot list it inside a plugin's scoped handler. A plugin that needs rate limiting declares a dependency on the host instead. See [Depending on host capabilities](/server/plugins/depends-on).

## What it adds to the client contract

Nothing directly. `rateLimit` adds no keys to the client contract and no methods to the client socket. The one thing a client sees is a throttle surfacing as the built-in `RateLimited` error — covered in the [built-in errors catalog](/core/builtin-errors).
