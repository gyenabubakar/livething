`rateLimit(config?)` limits how many messages a connection can send in a period of time. It is off by default. You **must** list this capability to use any rate limit at all. Even one per-handler rule needs the capability on the server.

## What it does

Rate limiting runs before validation and before your handler, so a rejected frame (one message on the socket) never reaches your code. It uses a **token bucket**. A bucket holds a number of tokens and refills at a steady speed. Each incoming frame spends one token. When the bucket is empty, LiveThing rejects the frame with the built-in `RateLimited` error.

You can turn it on in two ways:

- **With a global rule.** `rateLimit({ windowMs, max, per })` sets a default rule that every event uses.
- **With no argument.** `rateLimit()` turns the capability on with no global rule. Only handlers and channels that set their own `rateLimit` are limited.

## How to enable

Import it from its subpath and add it to your capability array. A global rule applies to every event:

```typescript [server.ts]
import { server } from '@livething/server'
import { rateLimit } from '@livething/server/rate-limit'

const base = server({
  capabilities: [rateLimit({ windowMs: 60_000, max: 100 })],
})
```

To limit only a few handlers and leave the rest unlimited, list it with no argument:

```typescript [no-global-server.ts]
import { server } from '@livething/server'
import { rateLimit } from '@livething/server/rate-limit'

const base = server({
  capabilities: [rateLimit()], // on, but no global rule
})
```

List `rateLimit` only once. If it appears twice in the capability array, you get a compile error, and `server(...)` throws an error at runtime.

## The global rule

The argument to `rateLimit(...)` is the server-wide default. Every field is optional.

| Field      | Type              | Default                              | What it does                                                                                                                                                          |
| ---------- | ----------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `windowMs` | `number`          | `60000`                              | The time, in milliseconds, that an empty bucket takes to fill up to `max` again. Must be a positive whole number.                                                     |
| `max`      | `number`          | `60`                                 | The size of the bucket: the most events a connection can send in one burst, and the number of tokens added back over one `windowMs`. Must be a positive whole number. |
| `per`      | `(ctx) => string` | `ctx.connection.id` (per-connection) | Returns the bucket key. The default gives each connection its own budget. Return `ctx.user.id` to share one budget across every socket a user has open.               |

The bucket refills continuously at `max / windowMs` tokens per millisecond, up to `max`. For example, `windowMs: 60_000` with `max: 60` gives back one token per second, and the bucket never holds more than 60 tokens. If `windowMs` or `max` is not a positive whole number, `assemble()` throws an error.

When `per` returns an empty string, LiveThing uses the connection's own budget. For example, `ctx.user.id` is an empty string on an anonymous connection (one with no user). So anonymous connections never share one bucket.

## Per-handler and per-channel overrides

Any handler or channel can replace the global rule with its own `rateLimit` config. LiveThing picks one rule for each event, from the most specific level to the least specific. This order is the **cascade** (see [The cascade](#the-cascade)). The override has the same fields at every level, plus an `enabled` switch:

| Field      | Type              | Default   | What it does                                                                             |
| ---------- | ----------------- | --------- | ---------------------------------------------------------------------------------------- |
| `enabled`  | `boolean`         | required  | `true` turns the rule on at this level. `false` turns it off and stops the cascade here. |
| `windowMs` | `number`          | inherited | Refill time. Leave it out to keep the value from the level above.                        |
| `max`      | `number`          | inherited | Bucket size. Leave it out to keep the value from the level above.                        |
| `per`      | `(ctx) => string` | inherited | Bucket key. Leave it out to keep the value from the level above.                         |

An override only needs the fields it changes. A channel's `{ enabled: true, max: 200 }` keeps `windowMs` and `per` from the level above and changes only `max`.

You can set `rateLimit` on:

- A `base.on(...)` or `base.request(...)` handler config.
- A channel handler's config: `.on(...)`, `.request(...)`, `.stream(...)`, `.resumableStream(...)` or `.recordedStream(...)`.
- A channel's own config. This is a channel-level rule that all events in the channel use.

::note
Top-level stream handlers (`base.stream(...)`, `base.resumableStream(...)` and `base.recordedStream(...)`) have no `rateLimit` field. The global rule still counts the frame that starts one of these streams.
::

### Tighten one handler

```typescript [export-server.ts]
import { emits, server, t } from '@livething/server'
import { rateLimit } from '@livething/server/rate-limit'
import * as v from 'valibot'
import { exportChatHistory } from './chat-export'

const base = server({
  capabilities: [
    rateLimit({ windowMs: 60_000, max: 60 }),
    emits({ 'export-ready': t<{ url: string }>() }),
  ],
})

// At most one export per minute, even though the global rule allows 60 events.
export const handleExportChat = base.on('export-chat', {
  input: v.object({ roomId: v.string() }),
  rateLimit: { enabled: true, max: 1 },
  async run(ctx, input) {
    const url = await exportChatHistory(input.roomId)
    ctx.send('export-ready', { url })
  },
})
```

### Share a budget across a user's sockets with a custom `per`

```typescript [reactions-server.ts]
import { emits, server, t } from '@livething/server'
import { rateLimit } from '@livething/server/rate-limit'
import * as v from 'valibot'

const base = server({
  capabilities: [
    rateLimit(),
    emits({
      'reaction-added': t<{ messageId: string; emoji: string }>(),
    }),
  ],
})

// All sockets of one user spend tokens from one bucket.
export const handleAddReaction = base.on('add-reaction', {
  input: v.object({ messageId: v.string(), emoji: v.string() }),
  rateLimit: {
    enabled: true,
    max: 10,
    per: (ctx) => ctx.user.id,
  },
  run(ctx, input) {
    ctx.broadcast('reaction-added', input)
  },
})
```

### A channel rule plus an inner handler override

```typescript [channel-server.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { rateLimit } from '@livething/server/rate-limit'
import * as v from 'valibot'

const base = server({
  capabilities: [
    rateLimit({ windowMs: 60_000, max: 60 }),
    channels(),
  ],
})

// Channel-level rule: all events in `rooms` share a limit of 50 per window.
const rooms = base.channel('rooms', {
  capabilities: [
    emits({ 'poll-created': t<{ question: string }>() }),
  ],
  rateLimit: { enabled: true, max: 50 },
})

// One handler in the channel sets its own, lower limit of 1.
export const handleCreatePoll = rooms.on('create-poll', {
  input: v.object({ question: v.string() }),
  rateLimit: { enabled: true, max: 1 },
  run(ctx, input) {
    ctx.channel.broadcast('poll-created', input, {
      includeSelf: true,
    })
  },
})
```

### Exempt a channel from the limit

Set `{ enabled: false }` to turn the rule off and stop the cascade at that level. Here, cursor moves are sent many times per second, so the `cursors` channel has no limit:

```typescript [exempt-server.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { rateLimit } from '@livething/server/rate-limit'
import * as v from 'valibot'

const base = server({
  capabilities: [
    rateLimit({ windowMs: 60_000, max: 60 }),
    channels(),
  ],
})

// No limit on this channel. Events here are never rejected by the rate limit.
const cursors = base.channel('cursors', {
  capabilities: [
    emits({ 'cursor-moved': t<{ x: number; y: number }>() }),
  ],
  rateLimit: { enabled: false },
})

export const handleMoveCursor = cursors.on('move', {
  input: v.object({ x: v.number(), y: v.number() }),
  run(ctx, input) {
    ctx.channel.broadcast('cursor-moved', input)
  },
})
```

## The cascade

When several rules could apply to one event, the most specific one wins:

::steps

### Per-handler override

A `rateLimit` on the handler itself. This has the highest priority.

### Channel-level rule

The `rateLimit` on the channel config, for events inside that channel.

### Global rule

The rule passed to the `rateLimit(...)` capability. It is used for everything else.
::

Only one rule applies to each event, and each rule has its own buckets. A frame for a handler with an override spends a token from the override's bucket only. It does not also spend a token from the channel or global bucket.

A channel with no rule of its own uses the global rule. Its events spend tokens from the same bucket as top-level events, so they are still limited. A channel rule is shared by every channel in a [dynamic family](/server/channels/dynamic-families) (one declaration, such as `room:{id}`, that matches many channel names). For one connection, `room:general` and `room:design` spend tokens from one bucket.

`{ enabled: false }` at any level turns the rule off there and stops the cascade, so no rule from a higher level applies. A lower level can turn limiting back on: `{ enabled: true }` under a turned-off parent enables a rule at that level. Any field it leaves out uses the default value (`windowMs: 60000`, `max: 60`, one budget per connection).

## What a rejected frame looks like

A rejected frame comes back to the client as the built-in `RateLimited` error. Its `detail.retryAfterMs` is the number of milliseconds to wait before trying again. It is always at least `1000`. The error keeps the frame's correlation ID (the ID that matches a reply to its request), so a rejected `request` still ends on the client: its promise rejects with the error and does not wait forever. See the [built-in errors catalog](/core/builtin-errors) for the `RateLimited` shape.

::caution
Buckets are kept in memory only. They are **not** saved across hibernation. When the server hibernates and wakes up, or restarts, every bucket starts full again. Rate limiting protects against bursts of traffic while the server is running. It does not count traffic across restarts.
::

## Closing a client that keeps going over the limit

LiveThing never closes a connection for going over the limit. It only rejects the extra frames, so a short burst from a normal user does not cost them their connection.

Every rejected frame also reaches your server's `onError` hook as a `RateLimited` error. So you can decide what "too much" means for your app. For example, count the rejections for each connection, and close the connection yourself after a few. Use the `RATE_LIMITED` close code (`4005`), so the client knows why:

```typescript [chat.ts]
import { CloseCodes, RateLimited } from '@livething/core'

const strikes = new Map<string, number>()

base.onError((ctx, error) => {
  if (!RateLimited.matches(error)) return

  const count = (strikes.get(ctx.connection.id) ?? 0) + 1
  strikes.set(ctx.connection.id, count)
  if (count >= 3)
    ctx.close(CloseCodes.RATE_LIMITED, 'Too many messages')
})
```

This map lives in memory, like the buckets. Remove a connection's entry in `onDisconnect` if you keep it for a long time.

## Host-only capability

`rateLimit` is **host-only**. It controls throttling for the whole connection, so you cannot list it in a plugin's scoped server definition. A plugin that needs rate limiting lists it in `dependsOn` instead, so the host must provide it. See [Depending on host capabilities](/server/plugins/depends-on).

## What it adds to the client contract

Nothing. `rateLimit` adds no keys to the client contract and no methods to the client socket. The client sees a rate limit only as the built-in `RateLimited` error. See the [built-in errors catalog](/core/builtin-errors).
