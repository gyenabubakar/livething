`rateLimit(config?)` limits how many messages, and optionally how many bytes, a connection can send in a period of time. It is off by default. You **must** list this capability to use any rate limit at all. Even one per-handler rule needs the capability on the server.

## What it does

Rate limiting runs before validation and before your handler, so a rejected frame never reaches your code. It uses a **token bucket**. A bucket holds a number of tokens and refills at a steady speed. Each incoming frame spends one token. With `maxBytes`, it also spends its size from a second bucket of bytes. When a bucket does not have enough, LiveThing rejects the frame with the built-in `RateLimited` error. A frame that waits behind a pending channel subscribe spends its tokens when it arrives.

You can turn it on in two ways:

- **With a global rule.** `rateLimit({ windowMs, maxMessages, maxBytes, per })` sets a default rule that every event uses.
- **With no argument.** `rateLimit()` turns the capability on with no global rule. Only handlers and channels that set their own `rateLimit` are limited.

## How to enable

Import it from its subpath and add it to your capability array. A global rule applies to every event:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { rateLimit } from '@livething/server/rate-limit'

const base = server({
  capabilities: [rateLimit({ windowMs: 60_000, maxMessages: 100 })],
})
```

To limit only a few handlers and leave the rest unlimited, list it with no argument:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { rateLimit } from '@livething/server/rate-limit'

const base = server({
  capabilities: [rateLimit()], // on, but no global rule
})
```

List `rateLimit` only once. If it appears twice in the capability array, you get a compile error, and `server(...)` throws an error at runtime.

## The global rule

The argument to `rateLimit(...)` is the server-wide default. Every field is optional.

::field-group
::field{name="windowMs" type="number"}
Default: `60000`. The time, in milliseconds, that an empty bucket takes to fill up to `maxMessages` again. Must be a positive whole number.
::
::field{name="maxMessages" type="number"}
Default: `60`. The size of the bucket: the most messages a connection can send in one burst, and the number of tokens added back over one `windowMs`. Must be a positive whole number.
::
::field{name="maxBytes" type="number"}
Default: no byte limit. A second bucket, counted in bytes: the most bytes a connection can send in one burst, and the number of bytes added back over one `windowMs`. A frame's size is its whole length on the wire, in UTF-8 bytes for a text frame. For a [binary message](/server/binary/overview), it is the whole message: the 9-byte header, the info and its metadata, and the bytes. A binary message counts as one message in the `maxMessages` bucket. A frame passes only when both buckets have enough. A frame bigger than `maxBytes` could never pass, so it costs the whole bucket instead: it passes only when the bucket is full, and it empties it. Must be a positive whole number.
::
::field{name="per" type="(ctx) => string"}
Default: `ctx.connection.id` (per-connection). Returns the bucket key. The default gives each connection its own budget. Return `ctx.user.id` to share one budget across every socket a user has open.
::
::

The bucket refills continuously at `maxMessages / windowMs` tokens per millisecond, up to `maxMessages`. For example, `windowMs: 60_000` with `maxMessages: 60` gives back one token per second, and the bucket never holds more than 60 tokens. The byte bucket refills the same way, up to `maxBytes`. If `windowMs`, `maxMessages` or `maxBytes` is not a positive whole number, `assemble()` throws an error.

The message count protects the server's work, because each message runs a handler. The byte count protects memory and the network. For example, `rateLimit({ windowMs: 60_000, maxMessages: 60, maxBytes: 5 * 1024 * 1024 })` lets a connection send 60 messages and 5 MiB each minute.

When `per` returns an empty string, LiveThing uses the connection's own budget. For example, `ctx.user.id` is an empty string on an anonymous connection. So anonymous connections never share one bucket.

## Per-handler and per-channel overrides

Any handler or channel can replace the global rule with its own `rateLimit` config. LiveThing picks one rule for each event, from the most specific level to the least specific. This order is the **cascade** (see [The cascade](#the-cascade)). The override is either an object or `false`. An object turns the rule on at this level and has the same fields at every level. `false` turns the rule off and stops the cascade here.

| Field         | Type              | Default   | What it does                                                           |
| ------------- | ----------------- | --------- | ---------------------------------------------------------------------- |
| `windowMs`    | `number`          | inherited | Refill time. Leave it out to keep the value from the level above.      |
| `maxMessages` | `number`          | inherited | Bucket size. Leave it out to keep the value from the level above.      |
| `maxBytes`    | `number`          | inherited | Byte bucket size. Leave it out to keep the value from the level above. |
| `per`         | `(ctx) => string` | inherited | Bucket key. Leave it out to keep the value from the level above.       |

An override only needs the fields it changes. A channel's `{ maxMessages: 200 }` keeps `windowMs` and `per` from the level above and changes only `maxMessages`.

You can set `rateLimit` on:

- A `base.on(...)` or `base.request(...)` handler config.
- A channel handler's config: `.on(...)`, `.request(...)`, `.stream(...)` or `.recordedStream(...)`.
- A channel's own config. This is a channel-level rule that all events in the channel use.

::note
Top-level stream handlers (`base.stream(...)` and `base.recordedStream(...)`) have no `rateLimit` field. The global rule still counts the frame that starts one of these streams.
::

### Tighten one handler

`remind-me` is not part of Huddle. It shows a per-handler limit on a scheduled reminder:

```typescript [server/remind-me.ts]
import { emits, server, t } from '@livething/server'
import { rateLimit } from '@livething/server/rate-limit'
import { scheduled } from '@livething/server/scheduled'
import * as v from 'valibot'
import type { ConnectionRef } from '@livething/server'

const base = server({
  capabilities: [
    rateLimit({ windowMs: 60_000, maxMessages: 60 }),
    scheduled({
      remind: {
        data: t<{ connection: ConnectionRef; text: string }>(),
      },
    }),
    emits({ notification: t<{ title: string; body: string }>() }),
  ],
})

export const handleRemind = base.scheduled('remind', {
  run(ctx, data) {
    ctx.connections.get(data.connection).send('notification', {
      title: 'Reminder',
      body: data.text,
    })
  },
})

// At most one reminder request per minute, even though the global rule allows 60 events.
export const handleRemindMe = base.on('remind-me', {
  input: v.object({ text: v.string(), delayMs: v.number() }),
  rateLimit: { maxMessages: 1 },
  run(ctx, input) {
    ctx.schedule('remind', {
      time: Date.now() + input.delayMs,
      data: { connection: ctx.connection, text: input.text },
    })
  },
})
```

### Share a budget across a user's sockets with a custom `per`

```typescript [server/set-status.ts]
import { emits, server, t } from '@livething/server'
import { rateLimit } from '@livething/server/rate-limit'
import * as v from 'valibot'
import type { Status } from './base'

const base = server({
  capabilities: [
    rateLimit(),
    emits({
      'status-changed': t<{ userId: string; status: Status }>(),
    }),
  ],
})

// All sockets of one user spend tokens from one bucket.
export const handleSetStatus = base.on('set-status', {
  input: v.object({ status: v.picklist(['active', 'away', 'busy']) }),
  rateLimit: {
    maxMessages: 10,
    per: (ctx) => ctx.user.id,
  },
  run(ctx, input) {
    ctx.broadcast('status-changed', {
      userId: ctx.user.id,
      status: input.status,
    })
  },
})
```

### A channel rule plus an inner handler override

```typescript [server/rooms.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { rateLimit } from '@livething/server/rate-limit'
import * as v from 'valibot'

const base = server({
  capabilities: [
    rateLimit({ windowMs: 60_000, maxMessages: 60 }),
    channels(),
  ],
})

// Channel-level rule: all events in `rooms` share a limit of 50 per window.
const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    emits({
      reaction: t<{
        messageId: string
        emoji: string
        from: string
      }>(),
    }),
  ],
  rateLimit: { maxMessages: 50 },
})

// react is limited per user, on its own lower budget, across every room they're in.
export const handleReact = rooms.on('react', {
  input: v.object({ messageId: v.string(), emoji: v.string() }),
  rateLimit: { maxMessages: 5, per: (ctx) => ctx.user.id },
  run(ctx, input) {
    ctx.channel.broadcast('reaction', {
      messageId: input.messageId,
      emoji: input.emoji,
      from: ctx.user.id,
    })
  },
})
```

### Exempt a channel from the limit

Set `rateLimit: false` to turn the rule off and stop the cascade at that level. Here, `start-typing` fires on every keystroke, so it is exempt from the room's rate limit even though other room events are not:

```typescript [server/rooms.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { rateLimit } from '@livething/server/rate-limit'
import * as v from 'valibot'

const base = server({
  capabilities: [
    rateLimit({ windowMs: 60_000, maxMessages: 60 }),
    channels(),
  ],
})

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [emits({ typing: t<{ from: string }>() })],
})

// No limit on this event. It is never rejected by the rate limit.
export const handleStartTyping = rooms.on('start-typing', {
  input: v.object({}),
  rateLimit: false,
  run(ctx) {
    ctx.channel.broadcast('typing', { from: ctx.user.id })
  },
})
```

## The cascade

When several rules could apply to one event, the most specific one wins:

::steps

### Per-handler override

A `rateLimit` on the handler itself. This has the highest priority.

### Channel-level rule

The `rateLimit` on the channel config, for events inside that channel.

### Global rule

The rule passed to the `rateLimit(...)` capability. It is used for everything else.
::

Only one rule applies to each event, and each rule has its own buckets. A frame for a handler with an override spends a token from the override's bucket only. It does not also spend a token from the channel or global bucket.

A channel with no rule of its own uses the global rule. Its events spend tokens from the same bucket as top-level events, so they are still limited. A channel rule is shared by every channel in a [dynamic family](/server/channels/dynamic-families). For one connection, `room:general` and `room:design` spend tokens from one bucket.

`rateLimit: false` at any level turns the rule off there and stops the cascade, so no rule from a higher level applies. A lower level can turn limiting back on: an object under a turned-off parent enables a rule at that level. Any field it leaves out uses the default value (`windowMs: 60000`, `maxMessages: 60`, one budget per connection).

## What a rejected frame looks like

A rejected frame comes back to the client as the built-in `RateLimited` error. Its `detail.retryAfterMs` is the number of milliseconds to wait before trying again. It is always at least `1000`. The error keeps the frame's correlation ID, so a rejected `request` still ends on the client: its promise rejects with the error and does not wait forever. See the [built-in errors catalog](/core/builtin-errors) for the `RateLimited` shape.

::caution
Buckets are kept in memory only. They are **not** saved across hibernation. When the server hibernates and wakes up, or restarts, every bucket starts full again. Rate limiting protects against bursts of traffic while the server is running. It does not count traffic across restarts.
::

LiveThing removes a connection's own bucket when the connection closes. It also removes, from time to time, any bucket that has filled back up, such as the bucket of a user who went quiet. A new bucket starts full, so this changes nothing for the client. It only keeps memory flat on a server that runs for a long time.

## Closing a client that keeps going over the limit

LiveThing never closes a connection for going over the limit. It only rejects the extra frames, so a short burst from a normal user does not cost them their connection.

Every rejected frame also reaches your server's `onError` hook as a `RateLimited` error. So you can decide what "too much" means for your app. For example, count the rejections for each connection, and close the connection yourself after a few. Use the `RATE_LIMITED` close code (`4005`), so the client knows why:

```typescript [server/huddle-definition.ts]
import { CloseCodes, RateLimited } from '@livething/core'
import { server } from '@livething/server'

const strikes = new Map<string, number>()

export const base = server({
  onError(ctx, error) {
    if (!RateLimited.matches(error)) return

    const count = (strikes.get(ctx.connection.id) ?? 0) + 1
    strikes.set(ctx.connection.id, count)
    if (count >= 3) {
      ctx.close(CloseCodes.RATE_LIMITED, 'Too many messages')
    }
  },
})
```

This map lives in memory, like the buckets. Remove a connection's entry in `onDisconnect` if you keep it for a long time.

## Host-only capability

`rateLimit` is **host-only**. It controls throttling for the whole connection, so you cannot list it in a plugin's scoped server definition. A plugin that needs rate limiting lists it in `dependsOn` instead, so the host must provide it. See [Depending on host capabilities](/server/plugins/depends-on).

## What it adds to the client contract

Nothing. `rateLimit` adds no keys to the client contract and no methods to the client socket. The client sees a rate limit only as the built-in `RateLimited` error. See the [built-in errors catalog](/core/builtin-errors).
