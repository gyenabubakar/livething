When a client retries a send over a flaky network, the same message can arrive twice. Without protection, the handler runs twice — a double charge, a double post. **dedup** stops that. It stamps an ID on every outgoing message and remembers the most recent inbound IDs per connection, dropping any frame whose ID it has already seen.

## How it works

dedup acts in both directions:

- **Outgoing** — every server-to-client application message gets a unique ID in `metadata.delivery.id`, so clients can drop duplicates from a replay or reconnect. Protocol frames (pings, subscribe acks, and the like) are skipped because they do not need delivery IDs.
- **Incoming** — when a frame arrives with a `metadata.delivery.id` the connection has seen recently, dedup drops it before any handler runs.

Each connection keeps a small ring of recent IDs. The ring size — the `cap` — is how many IDs it remembers.

A frame with **no delivery ID** is never treated as a duplicate. It always dispatches. So dedup is at-least-once by default: a client opts into deduplication by attaching the same ID to its retries, and a send without an ID always goes through.

dedup adds nothing to the client contract. The delivery ID lives in metadata, not in your typed payloads; `InferClient` is unchanged.

## Enable it

Import `dedup` from `@livething/server/dedup` and list it in `capabilities`. The options object is optional.

::code-group

```typescript [socket.ts]
import { server, t } from '@livething/server'
import { dedup } from '@livething/server/dedup'

const base = server({
  capabilities: [dedup()],
})
```

```typescript [socket.ts (custom ring size)]
import { server, t } from '@livething/server'
import { dedup } from '@livething/server/dedup'

const base = server({
  capabilities: [dedup({ cap: 256 })],
})
```

::

## Configuration

| Option | Type     | Required | Default | What it is                                                      |
| ------ | -------- | -------- | ------- | --------------------------------------------------------------- |
| `cap`  | `number` | no       | `256`   | How many recent inbound delivery IDs to remember per connection |

`cap` must be a positive integer if given — passing an invalid value throws immediately, at the `dedup()` call, not later at assemble. A larger ring catches retries spread over a longer window at the cost of a little more memory per connection; the default of `256` covers a few seconds of burst retries on a flaky link.

## Host-only :badge[host-only]

dedup is a **host-only** capability. It cannot be listed inside a plugin's scoped server definition — only the top-level `server(...)` may enable it.

## Pairs with sequence and replay

dedup is often listed alongside [sequence](/server/capabilities/sequence), which numbers every outgoing message so a reconnecting client can catch up from where it left off. Together they give the client both halves of reliable delivery: dedup drops what arrived twice, sequence brings back what it missed while away.

Built-in [replay](/server/capabilities/replay) also requires `dedup()` — the delivery ID is what replay uses to skip messages the client already has. The three are usually listed together:

```typescript [reliable.ts]
import { server, t } from '@livething/server'
import { dedup } from '@livething/server/dedup'
import { replay } from '@livething/server/replay'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [
    dedup(),
    sequence({ persist: true }),
    replay.history(), // built-in replay needs both of the above
  ],
})
```
