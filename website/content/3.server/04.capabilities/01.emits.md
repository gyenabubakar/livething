`emits` declares the events your server can send to clients. These events are **fire-and-forget**: the server sends the message and does not wait for a reply. The client receives each declared event. On the server, `emits` gives your handlers three ways to send:

- `ctx.send` sends to the current connection.
- `ctx.broadcast` sends to many connections.
- `ctx.connections.get(ref).send` sends to one specific connection. `ref` is a `ConnectionRef`, a small object that identifies one connection.

## Declaring events

Import `emits` from `@livething/server` and list it in your capabilities. Each key is an event name. Each value is a `t<Shape>()` marker, which sets the payload type:

```typescript [server/emits.ts]
import { emits, server, t } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import { verifySession } from './auth'
import type { Message } from './base'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token) // your auth: returns { id, name, role } or null
    if (!user) {
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [
    emits({
      message: t<Message>(),
      'user-renamed': t<{ userId: string; name: string }>(),
      notification: t<{ title: string; body: string }>(),
    }),
  ],
})
```

The `upgrade` step checks who is connecting and sets `ctx.meta`. Here it sets `ctx.meta.name`, which the handlers below use. `verifySession` is your own auth function. See [Upgrade](/server/server/upgrade).

The marker exists **only at the type level**. Your own server code creates outgoing payloads, so LiveThing does not validate them against the shape you declared. It only checks that each payload is an object or `null` in JSON (see below). The type goes into `ctx.send`, `ctx.broadcast` and the generated client types. You write only the shape here, not a validation schema.

## The contract slice

The **contract** is the list of typed events that the server and the client share. `emits` fills the client's `incoming` key, which lists the events the client receives. The direction changes from one side to the other: what the server _emits_, the client takes _in_. The events above produce this part of the client contract:

```typescript [shape]
import type { Message } from '../server/base'

interface HuddleSocket {
  incoming: {
    message: Message
    'user-renamed': { userId: string; name: string }
    notification: { title: string; body: string }
  }
}
```

The client then listens with full typing. You do not write these types yourself:

```typescript [client/messages.ts]
import { socket } from './socket'

socket.on('message', (data) => {
  // data: Message, which is { id: string; text: string; from: string; sentAt: number }
})
```

See [The Contract](/learn/the-contract) for how the server definition maps to the client types.

## Sending events from a handler

When you list `emits`, your handlers get `ctx.send`, `ctx.broadcast` and `ctx.connections.get(ref).send`. All three accept only the events you declared:

- `ctx.send(event, payload)` sends to the **current** connection.
- `ctx.broadcast(event, payload)` sends to **every other** connection on the server. By default, the calling connection does not receive it. Pass `{ includeSelf: true }` to include it.
- `ctx.connections.get(ref).send(event, payload)` sends to **one specific** connection, which you choose by its `ConnectionRef`. It returns `false` when that socket is closed or is not on this server instance.

```typescript [server/notifications.ts]
import * as v from 'valibot'
import { base } from './base'

const handleWhoAmI = base.on('whoami', {
  input: v.object({}),
  run(ctx) {
    ctx.send('notification', {
      title: 'You',
      body: ctx.connection.id,
    })
  },
})

const handleAnnounce = base.on('announce', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    // Every connection receives this, except the sender.
    ctx.broadcast('announcement', { text: input.text })
  },
})
```

::note
Each `base.on(...)` call creates a handler value. The handler runs, and appears in `InferClient`, only when you include that value in `base.assemble({ handlers: [...] })`.
::

To send to one specific socket, get its `ConnectionRef`. `ctx.connection` is the ref of the current connection. Every connection snapshot (for example, an item from `ctx.connections.all()`) has a `.ref()` method that returns its ref. Pass the ref to `ctx.connections.get(ref)`:

```typescript [server/private-note.ts]
import * as v from 'valibot'
import { base } from './base'

const handleSendPrivateNote = base.on('send-private-note', {
  input: v.object({ toUserId: v.string(), text: v.string() }),
  run(ctx, input) {
    const target = ctx.connections
      .all()
      .find((c) => c.userId === input.toUserId)
    if (!target) return

    const delivered = ctx.connections
      .get(target.ref())
      .send('notification', {
        title: 'Private note',
        body: input.text,
      })
    if (!delivered) {
      ctx.log.warn('note target is offline', {
        toUserId: input.toUserId,
      })
    }
  },
})
```

All three methods are typed against the declared events. `ctx.send('not-declared', ...)` is a compile error. A payload that does not match the marker is also a compile error.

An event whose data is bytes, such as Huddle's [`avatar-preview`](/server/binary/events#handling-binary-events), is declared in [`binary({ emits })`](/server/capabilities/binary#how-to-enable) instead, and sent with `ctx.binary.send` and the other `.binary` senders. One name is either a JSON event or a binary event in a scope, never both.

## Config field reference

| Field            | Value                                    | Notes                                                                                                                                                                                                                                                                                            |
| ---------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| event name (key) | a non-empty string, up to 128 characters | The name of the event on the wire. Put it in quotes if it has a hyphen, for example `'user-joined'`. It cannot start or end with `__` (LiveThing uses these names internally). It cannot contain `::` (the separator in `ctx.matches` keys). It cannot be `ping` or `pong` (keepalive messages). |
| payload (value)  | `t<Shape>()`                             | A marker that exists only at the type level. LiveThing does not validate outgoing payloads at runtime.                                                                                                                                                                                           |

## Edge cases

**Names with a hyphen need quotes.** A key with a hyphen, or with any other character that is not allowed in a JavaScript identifier, must be a string literal:

```typescript [server/huddle-definition.ts]
import { emits, t } from '@livething/server'

emits({
  'user-renamed': t<{ userId: string; name: string }>(),
})
```

**No payload.** For an event that carries no data, declare it with `t<null>()`, and send `null`. A handler whose client sends no data checks it with `v.null()`:

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import * as v from 'valibot'

const base = server({
  capabilities: [emits({ 'history-cleared': t<null>() })],
})

const handleClearHistory = base.on('clear-history', {
  input: v.null(),
  run(ctx) {
    ctx.send('history-cleared', null)
  },
})
```

**The payload must be an object or `null`.** LiveThing sends the payload as JSON, and it refuses a payload that would not be a JSON object or `null`. `ctx.send`, a send to one user or connection, and `ctx.channel.broadcastTo(...)` throw. A broadcast to many clients (`ctx.broadcast`, a channel broadcast, a tag broadcast) logs the error once and sends to nobody. A broadcast that has no recipients may send nothing without checking the payload, so test a payload with a client connected. A payload is refused when it is a string, a number, a boolean, an array, a function, a `Map` or a `Set` with no `toJSON()` of its own (JSON turns them into `{}` and loses the data), a boxed value such as `new Number(7)`, or an object whose `toJSON()` does not return an object, such as a `Date` (JSON turns it into a string). A class instance is fine, because JSON keeps its fields as an object, and so is a record whose `toJSON()` returns an object. The client gets that object, and its types say so: the event is typed as what `toJSON()` returns. LiveThing checks the JSON it is about to send, so it calls `toJSON()` once, the same way `JSON.stringify` does. `emits` checks the same rule in the types, so a marker for any of those is a compile error. `t()` itself accepts any type, because it is only a type marker. `t<{}>()` means an empty object, so `ctx.send(event, {})` compiles and `ctx.send(event, 'text')` does not. For a single value, declare the marker as an object shape that holds the value:

```typescript [server/emit-payloads.ts]
import { emits, t } from '@livething/server'
import type { Message } from './base'

// Wrong: a compile error, because the payload is an array.
emits({
  // @ts-expect-error: an array is not a JSON object
  'bad-example': t<Message[]>(),
})

// Right: put the value inside an object.
emits({
  'load-history-result': t<{ messages: Message[] }>(),
})
```

**Reserved names throw at startup.** A name that starts or ends with `__` throws when `emits({...})` runs. A name that contains `::`, is longer than 128 characters, or is `ping` or `pong` throws when the adapter loads your server definition (for example, in `bind(...)` on Node). Both happen before your server handles any message, so a bad name never fails later at send time.

## Channels declare their own events

The top-level `emits` covers events on the main socket. A channel has its own contract. It declares its own events with `emits(...)` in its own `capabilities` list. `ctx.channel.send`, `ctx.channel.broadcastTo` and `ctx.channel.broadcast` accept those events. See [Defining channels](/server/channels/defining).
