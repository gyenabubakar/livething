The `intercepts()` capability turns on the **inbound intercept hook** — code that runs for every incoming frame, before validation and your handler. List it to grant `base.intercept(...)` and the channel-scoped `channel.intercept(...)`. Import it from `@livething/server/intercepts`:

```typescript [server.ts]
import { server, t } from '@livething/server'
import { intercepts } from '@livething/server/intercepts'

const base = server({
  capabilities: [intercepts()],
})
```

## What it grants

| Surface                                | What it is                                                                                    |
| -------------------------------------- | --------------------------------------------------------------------------------------------- |
| `base.intercept((ctx, frame) => …)`    | The inbound hook — runs before validation and the handler. Inspect, rewrite, or drop a frame. |
| `channel.intercept((ctx, frame) => …)` | The same hook, scoped to one channel.                                                         |

The hook mechanics — the `frame` shape, rewrite-vs-drop, channel ordering, `frame.owner`, and the nudge branch — live on the [Intercept](/server/lifecycle-and-intercept/intercept) page. This page covers **enabling** the capability.

::note
The `onOutgoing` hook (`base.onOutgoing(...)`) is _not_ gated by `intercepts()` — it is always available. Only the inbound `intercept` needs this capability.
::

::note
Narrowing a frame with `ctx.matches` / `ctx.unsafeCast` does **not** need `intercepts()` — they are core `ctx` methods, on every connection. Their full API is on the [Core Context](/server/context-and-storage/ctx#frame-guards) page. An intercept is just the most common place to reach for them, because its `frame.payload` arrives typed `unknown`.
::

## The contract slice

`intercepts()` adds **nothing** to the client contract. Hooks are a server-side concern — they run at the transport layer, so `InferClient` is unchanged.
