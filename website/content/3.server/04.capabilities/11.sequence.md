After a reconnect, a client needs to know if it missed any messages while the socket was closed. The **sequence** capability helps with this. It adds a number to every message the server sends, and each new number is bigger than the one before. The client remembers the highest number it has seen. After a reconnect, it asks the server for every message after that number.

## How it works

Every message that the server sends for your app gets a number in `metadata.delivery.seq`. This number is the **delivery sequence**. Each new message gets a bigger number than the last one. Protocol frames do not get a delivery sequence.

The client's [replay](/client/primitives/replay) primitive remembers the highest delivery sequence it has received. It keeps one value for the top level of the socket and one for each channel. When the socket reconnects, it sends that number to the server, and the server sends again every message with a higher number. The delivery sequence is a **high-water mark**: the highest point reached so far. The client does not expect the numbers to arrive one by one with no gaps.

This is important because the server has only one counter, and all connections share it. The numbers go up across all sockets together, not per connection. One client sees only the messages sent to it, so the numbers it receives have gaps. For example, a client that gets `41` and then `45` did not lose three messages. Messages `42`, `43` and `44` went to other sockets or other channels. The client only needs the numbers to go up. So "the last number I saw" is a correct point to catch up from.

A send to many connections gets **one** number. `ctx.broadcast`, a channel broadcast, a user broadcast, `broadcastTo`, and a tag broadcast each send one shared frame, so every recipient gets the same `metadata.delivery.seq`. A request to one user also has one number across that user's sockets, though each socket's frame has its own `correlationId`.

There is one exception: stream chunks, from plain and durable streams alike. They carry their own `metadata.stream.seq` and do not get a `metadata.delivery.seq`.

sequence does not change the client contract. `metadata.delivery.seq` is metadata that LiveThing adds to the message. It is not part of your typed payloads, and `InferClient` does not change.

## Enable it

Import `sequence` from `@livething/server/sequence` and list it in `capabilities`. The options object is optional.

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [sequence()],
})
```

This gives you a counter in memory. That is enough for a client to catch up after a reconnect.

## Configuration

| Option      | Type      | Required | Default | What it is                                                                            |
| ----------- | --------- | -------- | ------- | ------------------------------------------------------------------------------------- |
| `persist`   | `boolean` | no       | `false` | Keep the counter across server restarts (needs storage)                               |
| `batchSize` | `number`  | no       | `100`   | How many `seq` values to reserve in one storage write. Used only when `persist: true` |

If you give `batchSize`, it must be a positive integer. Otherwise `sequence()` throws an error.

### In memory (the default)

With `persist: false`, the counter is kept in memory. Each time the server starts, the counter starts again from 1. This is fine for catch-up, because the client uses `seq` as a high-water mark to continue from. It does not use `seq` as a unique ID. This mode does not write to storage.

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [sequence()], // same as sequence({ persist: false })
})
```

### Persistent

With `persist: true`, the counter is saved in storage and is kept after a server restart. So sequence numbers never repeat across reconnects. The counter is saved in the server's own SQL storage (the same database as [`ctx.sql`](/server/context-and-storage/sql-and-kv)). Every LiveThing adapter gives the server this storage, so you do not need to list another capability for it. On Node, the default database is in memory, so give the adapter a [file path](/runtimes/adapters/node#storage-timers-and-websockets) if the counter must survive a process restart.

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [sequence({ persist: true })],
})
```

### Tuning `batchSize`

With `persist: true`, the counter does not write to storage for every message. It reserves a range of `batchSize` numbers in one write and gives them out from memory. When all the numbers in the range are used, it reserves the next range. With the default of `100`, there is about one storage write for every 100 messages.

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [sequence({ persist: true, batchSize: 100 })],
})
```

A larger `batchSize` means fewer storage writes, but a bigger possible jump in the numbers. If the server crashes in the middle of a range, the unused numbers in that range are never sent. After the restart, the counter continues after the end of that range, so the `seq` values on the wire jump. This jump causes no problems, because the client always continues from the highest `seq` it saw. But a very large jump can look strange in logs. `batchSize` is **ignored** when `persist` is `false`, because the counter in memory does not write to storage.

## Host-only :badge[host-only]

sequence is a **host-only** capability. Only the top-level `server(...)` can turn it on. If you list it in a plugin's server definition (`server({ scope: 'plugin', ... })`), TypeScript shows a type error.

## Pairs with dedup and replay

sequence is often used with [dedup](/server/capabilities/dedup). sequence lets a reconnecting client continue from where it stopped. dedup drops a message that arrives twice. The [replay](/server/capabilities/replay) capability uses both. It needs `dedup()` and `sequence({ persist: true })` together, so that it can send again exactly the messages that a reconnecting client missed. If the sequence counter is not persistent, replay throws an error when the server starts.

## SQLite table

With `persist: true`, sequence creates one table in the server's own SQL storage: `__livething_sequence`. The name starts with the reserved `__livething_` prefix. Do not create a table with this name yourself, even before you turn on `persist`. LiveThing creates the table only if it does not exist yet, so you would get no "table already exists" error to warn you about the clash. See the [full reserved-table list](/server/context-and-storage/sql-and-kv#reserved-livething-tables) for every table LiveThing owns.

| Column     | Type               | Notes                                                                      |
| ---------- | ------------------ | -------------------------------------------------------------------------- |
| `scope`    | `TEXT` primary key | Always `'global'`. There is one counter per server instance.               |
| `nextSeq`  | `INTEGER`          | The next `seq` value to give out (the start of the next range to reserve). |
| `metadata` | `TEXT`             | Reserved by LiveThing. Always `'{}'`.                                      |

With `persist: false` (the default), sequence never uses storage, and this table is never created.
