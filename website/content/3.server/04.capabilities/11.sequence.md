After a reconnect, a client needs to know whether it missed anything while the socket was down. **sequence** answers that. It stamps a monotonically increasing number on every outgoing message, so the client can remember the highest number it has seen and, on reconnect, ask the server for everything after it.

## How it works

Every server-to-client application message gets a monotonically increasing `metadata.delivery.seq`. Protocol frames have no delivery sequence. The client's [replay](/client/primitives/replay) primitive tracks the highest delivery sequence it has received per scope; when the socket reconnects it sends that number to the server, which resends every message above it. The delivery sequence is a **high-water mark**, not a checklist — the client never assumes the numbers arrive one-by-one with no gaps.

That matters because the counter is a single Durable-Object-level value, shared across every connection on that instance — so delivery sequences climb monotonically across all concurrent sockets, not per connection. Any one client sees only the messages sent to it, so the numbers it receives are naturally _not_ contiguous: a client watching `41` then `45` didn't lose three messages — those three went to other sockets or other channels. What the client relies on is only that the numbers rise, so "the last one I saw" is a valid cursor to catch up from. Durable and resumable stream chunks are the one exception: they carry their own `metadata.stream.seq`, which the global stamper does not overwrite.

sequence adds nothing to the client contract. `metadata.delivery.seq` is transport metadata, not part of your typed payloads; `InferClient` is unchanged.

## Enable it

Import `sequence` from `@livething/server/sequence` and list it in `capabilities`. The options object is optional.

```typescript [server/socket.ts]
import { server, t } from '@livething/server'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [sequence()],
})
```

That gives you an in-memory counter, which is enough for reconnect catch-up.

## Configuration

| Option      | Type      | Required | Default | What it is                                                                          |
| ----------- | --------- | -------- | ------- | ----------------------------------------------------------------------------------- |
| `persist`   | `boolean` | no       | `false` | Keep the counter across server restarts (needs storage)                             |
| `batchSize` | `number`  | no       | `100`   | How many `seq` values to reserve per storage write — only used when `persist: true` |

`batchSize` must be a positive integer if given.

### In-memory (the default)

With `persist: false`, the counter lives in memory and resets to zero each time the server starts. That is fine for catch-up: the client uses `seq` as a high-water mark to resume from, not as a globally unique ID. This mode does no storage writes.

```typescript [server/socket.ts]
const base = server({
  capabilities: [sequence()], // same as sequence({ persist: false })
})
```

### Persistent

With `persist: true`, the counter is stored durably and survives a server restart, so sequence numbers never repeat across reconnections. It writes to the server's own SQL storage (via `ctx.sql`), which every LiveThing adapter provides automatically — there is no separate capability to list for this.

```typescript [server/socket.ts]
import { server, t } from '@livething/server'
import { sequence } from '@livething/server/sequence'

const base = server({
  capabilities: [sequence({ persist: true })],
})
```

### Tuning `batchSize`

When persistent, the counter does not hit storage on every send. It reserves a range of `batchSize` numbers in one write, hands them out from memory, then reserves the next range when the batch runs dry. The default of `100` means about one storage write per hundred messages.

```typescript [server/socket.ts]
const base = server({
  capabilities: [sequence({ persist: true, batchSize: 100 })],
})
```

A larger `batchSize` means fewer storage writes but a bigger possible jump: if the server crashes mid-batch, the unused numbers in that range are never sent, leaving a jump in the `seq` values on the wire. That jump is harmless — the client only ever resumes from the highest `seq` it saw, so an unused range in the middle changes nothing — but a very large jump can look surprising in logs. `batchSize` is **ignored** when `persist` is `false`, since the in-memory counter does no writes to batch.

## Host-only :badge[host-only]

sequence is a **host-only** capability. It cannot be listed inside a plugin's scoped server definition — only the top-level `server(...)` may enable it.

## Pairs with dedup and replay

sequence is the natural partner of [dedup](/server/capabilities/dedup): sequence lets a reconnecting client resume from where it left off, dedup drops what arrived twice. Built-in [replay](/server/capabilities/replay) builds on both — it needs `dedup()` and `sequence({ persist: true })` together so it can re-send exactly the messages a reconnecting client missed.

## SQLite table

With `persist: true`, sequence creates one table in the server's own SQL storage: `__livething_sequence`. The name starts with the reserved `__livething_` prefix — do not create a table with this name yourself, even before you turn on `persist`, since there is no "table already exists" error to catch the collision. See the [full reserved-table list](/server/context-and-storage/sql-and-kv#reserved-livething-tables) for every table LiveThing owns.

| Column     | Type               | Notes                                                                       |
| ---------- | ------------------ | --------------------------------------------------------------------------- |
| `scope`    | `TEXT` primary key | Always `'global'` today — one counter per server instance.                  |
| `nextSeq`  | `INTEGER`          | The next `seq` value to hand out (or the start of the next reserved batch). |
| `metadata` | `TEXT`             | Reserved JSON blob for future fields; not read or written yet.              |

With `persist: false` (the default), sequence never touches storage and this table is never created.
