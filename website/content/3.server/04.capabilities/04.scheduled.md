The `scheduled()` capability lets your server run work later. A task can run once at a chosen time, or again and again on a repeating interval. A task has no connection behind it. It runs on the server itself. Use it for cleanup jobs, heartbeats (small messages sent on a fixed interval), or any other work that should happen later.

::warning
**Scheduled work is not a replacement for a durable job queue** (a separate service that stores jobs and runs them even when your app is down). On Cloudflare, the platform can start a Durable Object again to run its alarm (a timer that the platform stores). The Node adapter uses a timer inside your running Node process. If that process is stopped, pending work stays in SQLite and runs when the service starts again, but only if you gave the adapter a file path. The default Node storage is in memory, so a stopped process loses its pending work. LiveThing cannot start a stopped process.<br/><br/>

Use a durable job queue or an external scheduler for business-critical jobs that must run even when the process is down, a deployment fails, or the machine restarts. Use LiveThing scheduled tasks for work that belongs to a running WebSocket server, where running late after a restart is acceptable.
::

## Declaring tasks

Import it from `@livething/server/scheduled`:

```typescript [server/huddle-definition.ts]
import { scheduled } from '@livething/server/scheduled'
```

You pass a map to `scheduled({...})`. Each key is a task ID. Each value declares how that task behaves. Huddle declares `send-digest`. This example adds two more tasks, `purge-old-drafts` and `expire-invites`, and it keeps them in `huddle-jobs.ts` so the later examples can import them:

```typescript [server/huddle-jobs.ts]
import { emits, server, t } from '@livething/server'
import { scheduled } from '@livething/server/scheduled'

export const base = server({
  capabilities: [
    scheduled({
      'purge-old-drafts': null,
      'expire-invites': { every: 3_600_000 },
      'send-digest': { data: t<{ userId: string }>(), retry: true },
    }),
    emits({
      notification: t<{ title: string; body: string }>(),
      'digest-sent': t<{ userId: string }>(),
      'schedule-error': t<{ message: string }>(),
      'dead-letter-result': t<{ taskId: string; attempts: number }>(),
    }),
  ],
})
```

The `emits({...})` list declares the events that the examples on this page send to clients.

A task ID cannot start or end with `__`. That prefix and suffix are reserved for LiveThing.

The declaration value is one of these shapes:

| Value                                  | Meaning                                                                                                                                                                                                                                                                         |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `null`                                 | A one-shot task (it runs once each time you schedule it) with no payload.                                                                                                                                                                                                       |
| `{ every: ms }`                        | A recurring task that runs every `ms` milliseconds. `ms` must be a positive integer. You cannot combine it with `data`, because nobody calls a recurring task, so nobody can pass a payload. A new value applies at the next server start, and removing `every` stops the task. |
| `{ data: t<T>() \| schema }`           | A typed payload. `t<T>()` only sets the type. A schema also checks the payload at runtime. You cannot combine it with `every`.                                                                                                                                                  |
| `{ retry: true \| false \| number[] }` | A retry policy. `true` uses the default policy (3 retries). `false` turns retries off. A `number[]` is a custom backoff: the wait in milliseconds before each retry. You can add `retry` next to `data` or `every`.                                                             |

When you leave out `retry`, the task uses the default policy, the same as `retry: true`.

A custom backoff array must hold positive integers, and it cannot be empty. An empty array is an error.

## Writing a task handler

Every declared task needs a handler. Create it with `base.scheduled(taskId, { run })`. The call returns a handler value. Export it and pass it to `assemble({ handlers })`, as you do for any routed handler. A declared task whose handler you did not pass is an error: a compile error when the `handlers` list has a known length, and an error when `assemble()` runs when it does not. A handler for a task ID that you did not declare is a type error, and also an error when you assemble:

```typescript [server/jobs.ts]
import { buildDigest } from './huddle-data'
import { base } from './huddle-jobs'

export const handlePurgeOldDrafts = base.scheduled(
  'purge-old-drafts',
  {
    run(ctx) {
      ctx.broadcast('notification', {
        title: 'Drafts',
        body: 'old drafts cleared',
      })
    },
  },
)

export const handleExpireInvites = base.scheduled('expire-invites', {
  run(ctx) {
    ctx.sql.exec(
      'DELETE FROM invites WHERE expires_at < ?',
      Date.now(),
    )
  },
})

export const handleSendDigest = base.scheduled('send-digest', {
  run(ctx, data) {
    // data: { userId: string }
    buildDigest(data.userId)
    ctx.users
      .get(data.userId)
      .broadcast('digest-sent', { userId: data.userId })
  },
})

export const huddle = base.assemble({
  handlers: [
    handlePurgeOldDrafts,
    handleExpireInvites,
    handleSendDigest,
  ],
})
```

A task body receives a **connectionless context** (`ConnectionlessContext`), the same `ctx` that the `onShutdown` hook and the [admin `api`](/server/admin/context) get. This is a different `ctx` from the one a connection handler gets. It has no `ctx.send`, because no single connection owns the run. You reach connections through the server instead:

- `ctx.broadcast(event, payload)` sends an event to every connection.
- `ctx.channels.broadcast(channel, event, payload)` or `ctx.channels.get(...).broadcast(event, payload)` sends an event to one channel's members, when you list [`channels()`](/server/capabilities/channels).
- `ctx.connections.get(ref).send(event, payload)` sends to one connection by its reference. It returns `false` if that socket is gone.
- `ctx.connections.all()` lists the live connections, for example to pick some of them by tag. When you only need the number, use `ctx.connectionCount`. It costs less than `ctx.connections.all().length`.
- `ctx.users.get(id)` reaches every socket that one user has open.
- `ctx.sql` and `ctx.kv` read and write durable storage.
- `ctx.log` and `ctx.platform` are the same logger and platform object that your connection handlers get.
- `ctx.schedule(...)` and `ctx.cancelScheduled(...)` work inside a task body too. A task can use them to schedule more work, or to cancel pending runs.

For more about writing task bodies, see [base.scheduled](/server/handlers/scheduled).

## Triggering and cancelling

Listing `scheduled()` also adds `ctx.schedule(...)` and `ctx.cancelScheduled(...)` to your connection handlers. To schedule a one-shot task, give it a time. The time is a Unix timestamp in milliseconds:

```typescript [server/jobs.ts]
import * as v from 'valibot'
import { base } from './huddle-jobs'

const handleRequestDraftPurge = base.on('request-draft-purge', {
  input: v.object({ delayMs: v.number() }),
  run(ctx, input) {
    ctx.schedule('purge-old-drafts', {
      time: Date.now() + input.delayMs,
    })
  },
})
```

For a task that carries a payload, pass `data`:

```typescript [server/jobs.ts]
import * as v from 'valibot'
import { base } from './huddle-jobs'

const handleRequestDigest = base.on('request-digest', {
  input: v.object({}),
  run(ctx) {
    ctx.schedule('send-digest', {
      time: Date.now() + 60_000,
      data: { userId: ctx.user.id },
    })
  },
})
```

`ctx.schedule(...)` checks its arguments **synchronously** (right away, before it returns). It throws an error when:

- the task ID is not registered,
- `time` is not a positive integer (for example `NaN`, `Infinity`, `0`, a negative number or a fraction),
- `time` is past `9223372036854` (April 2262), the latest time a Cloudflare alarm can hold. The limit is the same on every platform, and nothing is stored,
- you pass `data` to a task that did not declare a payload,
- `data` fails the schema that the task declared,
- `data` cannot be stored as JSON, such as a `BigInt` or an object that refers to itself.

LiveThing stores `data` as JSON, and the task receives that JSON, so it gets the same value before and after a server restart. The task's `data` type says so too. A value with a `toJSON()` arrives as what that returns: a valid `Date` arrives as its ISO string, and an invalid one as `null`. A class instance without a `toJSON()` arrives as its fields, with no methods.

A `time` in the past is allowed. The run is due right away. Catch the error if you want to handle the failure:

```typescript [server/jobs.ts]
import * as v from 'valibot'
import { base } from './huddle-jobs'

const handleGuarded = base.on('guarded-schedule', {
  input: v.object({}),
  run(ctx) {
    try {
      ctx.schedule('purge-old-drafts', { time: Number.NaN })
    } catch (error) {
      ctx.send('schedule-error', {
        message:
          error instanceof Error ? error.message : String(error),
      })
    }
  },
})
```

`ctx.cancelScheduled(taskId)` cancels the pending runs of a task. Pass a data filter to cancel only the runs whose payload matches every key in the filter:

```typescript [server/jobs.ts]
import * as v from 'valibot'
import { base } from './huddle-jobs'

const handleCancelPurge = base.on('cancel-draft-purge', {
  input: v.object({}),
  run(ctx) {
    ctx.cancelScheduled('purge-old-drafts') // cancel every pending purge
  },
})

const handleCancelDigest = base.on('cancel-digest', {
  input: v.object({}),
  run(ctx) {
    ctx.cancelScheduled('send-digest', { userId: ctx.user.id }) // only runs with this payload
  },
})
```

When a task has nothing pending, `ctx.cancelScheduled(...)` does not throw and logs nothing. The run may have fired already, so this is normal.

A filter value of `undefined` throws. Pass a real value, or leave the key out. An `undefined` entry would match runs whose payload does not have that key at all.

Only the form without a filter stops a recurring task. A filter never removes recurring runs. Once you stop a recurring task this way, it stays stopped: it does not start again on its own, not even after a restart or, on Cloudflare, a Durable Object waking from hibernation (going idle and losing its in-memory state). To start it again, call `ctx.schedule(taskId, { time })`. The first run happens at `time`, and the task then goes back to running every `every` milliseconds.

## Retries and the dead-letter queue

When a task body throws, LiveThing runs it again based on the task's retry policy. The default policy (`retry: true`) is 3 retries, with a backoff of **`[1000, 5000, 25000]` ms**. So the body runs at most 4 times. When no retries are left, the run moves to a **dead-letter queue**: a durable table named `__livething_scheduled_dlq` that keeps a record of runs that failed for good. The retry policy is the same on every adapter. An adapter's timer only starts the due runs. It does not add a retry policy of its own. If writing that record fails, the server keeps it and writes it with the next scheduler change, so one failed write does not lose it. A restart in between runs the task again, because its queued row is still there.

A **recurring** task (`{ every }`) works a little differently. A failed run is still retried, and it can still end up in the dead-letter queue. After the run succeeds or moves to the dead-letter queue, the task schedules its next run. One failed run does not stop the interval.

To read the dead-letter queue, query the table with `ctx.sql`:

```typescript [server/jobs.ts]
import * as v from 'valibot'
import { base } from './huddle-jobs'

const handleQueryDeadLetter = base.on('query-dead-letter', {
  input: v.object({}),
  run(ctx) {
    const rows = ctx.sql
      .exec<{
        taskId: string
        attempts: number
        error: string
      }>(
        'SELECT taskId, attempts, error FROM __livething_scheduled_dlq ORDER BY failedAt DESC LIMIT 1',
      )
      .toArray()
    const row = rows[0]
    if (!row) return
    ctx.send('dead-letter-result', {
      taskId: row.taskId,
      attempts: row.attempts,
    })
  },
})
```

::note
The `scheduled` part of the contract is **server-only**. It does not reach the client. Tasks run only inside the server, so listing `scheduled()` adds no key to the client contract.
::

## At-least-once delivery

A scheduled run happens **at least once**. It never runs zero times, but it can run more than once. Two things cause a second run:

- **A retry**, when the body threw (see above).
- **A run again after a crash.** LiveThing deletes a pending run from storage only after its body finishes. If the server stops in the middle of a run, the stored row is still there, and the run starts again when the server comes back. This is true for one-shot tasks too, not only recurring ones.

This is still true when the body calls `ctx.schedule(...)` or `ctx.cancelScheduled(...)` before it finishes. For example, a `ban-user` task schedules a `send-ban-notice` task and then writes the ban:

```typescript [server/ban-jobs.ts]
import { emits, server, t } from '@livething/server'
import { scheduled } from '@livething/server/scheduled'

const base = server({
  capabilities: [
    emits({ notification: t<{ title: string; body: string }>() }),
    scheduled({
      'ban-user': { data: t<{ userId: string; reason: string }>() },
      'send-ban-notice': {
        data: t<{ userId: string; reason: string }>(),
      },
    }),
  ],
  onInit(ctx) {
    ctx.sql.exec(
      'CREATE TABLE IF NOT EXISTS bans (user_id TEXT PRIMARY KEY, reason TEXT NOT NULL)',
    )
  },
})

const handleBanUser = base.scheduled('ban-user', {
  run(ctx, data) {
    ctx.schedule('send-ban-notice', {
      time: Date.now(),
      data: { userId: data.userId, reason: data.reason },
    })
    ctx.sql.exec(
      'INSERT INTO bans (user_id, reason) VALUES (?, ?)',
      data.userId,
      data.reason,
    )
  },
})

const handleSendBanNotice = base.scheduled('send-ban-notice', {
  run(ctx, data) {
    ctx.users.get(data.userId).broadcast('notification', {
      title: 'Account banned',
      body: data.reason,
    })
  },
})

export const huddle = base.assemble({
  handlers: [handleBanUser, handleSendBanNotice],
})
```

Say the server stops right after `ctx.schedule('send-ban-notice', ...)` runs, but before `ban-user` finishes. The stored row for `ban-user` is still there. LiveThing does not delete it because the body scheduled another task. When the server starts again, `ban-user` runs again, and the stored `send-ban-notice` run also runs. (`INSERT` would then fail on the repeated `user_id`, which is one more reason to write bodies that are safe to repeat.)

Because of this, **task bodies must be idempotent**: running the same body twice must not apply its effect twice. For an effect inside the server (an upsert, or setting a value), this is often already true. For an effect outside the server, such as charging a card or sending an email, add a guard. Give the run a stable key and send it to the other system as an idempotency key. Or store a record that the effect happened, and check that record before you do it again.

## SQLite tables

`scheduled()` creates three tables in the server's own SQL storage the first time it runs. All three names start with the reserved `__livething_` prefix. Do not create a table with any of these names yourself, especially before you add `scheduled()`. LiveThing creates these tables only if they do not exist yet, so you get no "table already exists" error. See the [full list of reserved tables](/server/context-and-storage/sql-and-kv#reserved-livething-tables) for every table LiveThing owns.

**`__livething_scheduled`** has one row per pending run. LiveThing deletes the row when the run completes.

| Column      | Type               | Notes                                                              |
| ----------- | ------------------ | ------------------------------------------------------------------ |
| `id`        | `TEXT` primary key | The ID of this run, not the task ID.                               |
| `taskId`    | `TEXT`             | The key you declared in `scheduled({...})`.                        |
| `time`      | `INTEGER`          | The Unix time in milliseconds when this run is due.                |
| `data`      | `TEXT`             | The task's payload as JSON. `NULL` for a task with no payload.     |
| `everyMs`   | `INTEGER`          | The interval of a recurring task. `NULL` for a one-shot task.      |
| `attempts`  | `INTEGER`          | How many retries this run has used so far.                         |
| `recurring` | `INTEGER`          | `0` or `1`: whether this row schedules itself again after it runs. |
| `retry`     | `INTEGER`          | The run's retry policy, stored in encoded form.                    |
| `metadata`  | `TEXT`             | Reserved JSON column. LiveThing does not use it.                   |

**`__livething_scheduled_dlq`** has one row per run that used all its retries. LiveThing never deletes these rows, so the table grows until you delete them. Delete old rows yourself with `ctx.sql`, for example from a recurring task or a handler:

```typescript [server/jobs.ts]
import * as v from 'valibot'
import { base } from './huddle-jobs'

const THIRTY_DAYS_MS = 30 * 24 * 60 * 60 * 1000

const handlePruneDeadLetters = base.on('prune-dead-letters', {
  input: v.object({}),
  run(ctx) {
    ctx.sql.exec(
      'DELETE FROM __livething_scheduled_dlq WHERE failedAt < ?',
      Date.now() - THIRTY_DAYS_MS,
    )
  },
})
```

| Column     | Type               | Notes                                                                                                                   |
| ---------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `id`       | `TEXT` primary key | The ID of the original run.                                                                                             |
| `taskId`   | `TEXT`             | The ID of the task that failed.                                                                                         |
| `time`     | `INTEGER`          | The time the run was first due.                                                                                         |
| `failedAt` | `INTEGER`          | The Unix time in milliseconds when the row moved to the dead-letter queue.                                              |
| `data`     | `TEXT`             | The task's payload as JSON. `NULL` if it had none.                                                                      |
| `attempts` | `INTEGER`          | How many times the body ran before LiveThing stopped trying.                                                            |
| `error`    | `TEXT`             | The last error the body threw, as JSON. It has `message`, plus `name` and `stack` when the thrown value was an `Error`. |
| `metadata` | `TEXT`             | Reserved JSON column. LiveThing does not use it.                                                                        |

**`__livething_scheduled_stopped`** has one row per recurring (`every`) task that `ctx.cancelScheduled(taskId)` stopped. A server start does not schedule a stopped task again. `ctx.schedule(taskId, ...)` starts it again and removes the row.

| Column      | Type               | Notes                                                    |
| ----------- | ------------------ | -------------------------------------------------------- |
| `taskId`    | `TEXT` primary key | The ID of the stopped task.                              |
| `stoppedAt` | `INTEGER`          | The Unix time in milliseconds when the task was stopped. |
