The `scheduled()` capability lets your server run work later — once at a chosen time, or on a repeating interval. A task has no connection behind it; it runs on the server itself. Use it for cleanup jobs, heartbeats, or any deferred work.

::warning
**Scheduled work is not a replacement for a durable job queue.** Cloudflare can wake a Durable Object for its alarm, but the Node adapter uses a timer inside your running Node process. If that process is stopped, pending work waits in SQLite and catches up when the service starts again; LiveThing cannot start a stopped process.<br/><br/>

Use a durable queue or external scheduler for business-critical jobs that must run during process outages, failed deployments, or machine restarts. Use LiveThing scheduled tasks for work owned by a running WebSocket server, where catch-up after restart is acceptable.
::

## Declaring tasks

Import it from `@livething/server/scheduled`:

```typescript [server.ts]
import { scheduled } from '@livething/server/scheduled'
```

You pass a map to `scheduled({...})`. Each key is a task ID; each value declares how that task behaves:

```typescript [server.ts]
import { server, t } from '@livething/server'
import { scheduled } from '@livething/server/scheduled'

const base = server({
  capabilities: [
    scheduled({
      cleanup: null,
      heartbeat: { every: 30_000 },
      report: { data: t<{ userId: string }>(), retry: true },
    }),
  ],
})
```

The declaration value is one of these shapes:

| Value                                  | Meaning                                                                                                                                                                      |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `null`                                 | No payload, a one-shot task.                                                                                                                                                 |
| `{ every: ms }`                        | A recurring interval. Cannot combine with `data` — a recurring task has no caller to supply a payload.                                                                       |
| `{ data: t<T>() \| schema }`           | A typed payload. `t<T>()` types it only; a schema also validates it at runtime. Cannot combine with `every`.                                                                 |
| `{ retry: true \| false \| number[] }` | A retry policy. `true` uses the default (3 retries), `false` turns retries off, and `number[]` is a custom backoff in milliseconds. `retry` may accompany `data` or `every`. |

A custom backoff array must hold positive integers, and it cannot be empty — an empty array is an error.

## Binding a task body

Every declared task needs a body, registered with `base.scheduled(taskId, { run })`. Like a lifecycle hook, this call returns nothing and is included automatically when you assemble the server. A task declared with no body, or a body with no matching declaration, is a build error:

```typescript [tasks.ts]
base.scheduled('cleanup', {
  run(ctx) {
    ctx.broadcast('cleanup-done', { at: Date.now() })
  },
})

base.scheduled('report', {
  run(ctx, data) {
    // data: { userId: string }
    ctx.broadcast('report-ready', { userId: data.userId })
  },
})
```

A task body receives a **task context** — not a per-connection one. There is no `ctx.send`, because no single connection owns the run. You reach connections through the server instead:

- `ctx.broadcast(event, payload)` — push to every connection.
- `ctx.connections.get(ref).send(event, payload)` — push to one connection by reference (returns `false` if that socket is gone).
- `ctx.connections.all()` — list connections, for example to pick by tag. Use `ctx.connectionCount` when you only need the number — it is cheaper than `connections.all().length`.
- `ctx.sql` and `ctx.kv` — read and write durable storage.
- `ctx.log` and `ctx.platform` — the same platform surfaces your connection handlers get.
- `ctx.schedule(...)` and `ctx.cancelScheduled(...)` — available inside a task body too, so a task can chain follow-up work or cancel pending runs.

For the deep body-authoring detail, see [base.scheduled](/server/handlers/scheduled).

## Triggering and cancelling

Listing `scheduled()` also adds `ctx.schedule(...)` and `ctx.cancelScheduled(...)` to your connection handlers. Schedule a one-shot task by giving it a time:

```typescript [trigger.ts]
const handleStart = base.on('start-cleanup', {
  input: v.object({ delayMs: v.number() }),
  run(ctx, input) {
    ctx.schedule('cleanup', { time: Date.now() + input.delayMs })
  },
})
```

For a task that carries a payload, pass `data`:

```typescript [trigger-data.ts]
const handleQueueReport = base.on('queue-report', {
  input: v.object({ userId: v.string() }),
  run(ctx, input) {
    ctx.schedule('report', {
      time: Date.now() + 60_000,
      data: { userId: input.userId },
    })
  },
})
```

`ctx.schedule(...)` checks its arguments **synchronously** and throws on a mistake — an unregistered task ID, a bad `time` (anything that is not a positive integer, including `NaN` or a time in the past), passing `data` to a task that did not declare a payload, or `data` that fails the task's declared schema validator. Catch it if you want to handle the failure:

```typescript [guard.ts]
const handleGuarded = base.on('guarded-schedule', {
  input: v.object({}),
  run(ctx) {
    try {
      ctx.schedule('cleanup', { time: Number.NaN })
    } catch (error) {
      ctx.send('schedule-error', {
        message:
          error instanceof Error ? error.message : String(error),
      })
    }
  },
})
```

`ctx.cancelScheduled(taskId)` cancels pending runs of a task. Pass a data filter to cancel only the runs whose payload matches:

```typescript [cancel.ts]
const handleCancelAll = base.on('cancel-cleanup', {
  input: v.object({}),
  run(ctx) {
    ctx.cancelScheduled('cleanup') // cancel every pending cleanup
  },
})

const handleCancelOne = base.on('cancel-report', {
  input: v.object({ userId: v.string() }),
  run(ctx, input) {
    ctx.cancelScheduled('report', { userId: input.userId }) // only runs with this payload
  },
})
```

Cancelling a task that has nothing pending is a no-op, not an error. A filter value of `undefined` throws — pass a real value or omit the key, since an `undefined` entry would match runs whose payload never had that key. A recurring task is only stopped by the no-filter form; a filter never removes recurring runs.

## Retries and the dead-letter queue

When a task body throws, the **engine** retries it by the task's policy. The default (`retry: true`) is 3 retries with a backoff of **`[1000, 5000, 25000]` ms**, so the body runs at most 4 times. Once the retries run out, the task moves to a **dead-letter queue** — a durable table named `__livething_scheduled_dlq` — so a permanent failure is recorded instead of lost. This policy is the same on every adapter; an adapter's timer only wakes the engine and does not invent another retry policy for task bodies.

A **recurring** task (`{ every }`) behaves a little differently: a failed tick is still retried and may land in the dead-letter queue, but the task keeps scheduling its next tick either way — one bad run does not stop the interval.

```typescript [dead-letter.ts]
const handleQueryDeadLetter = base.on('query-dead-letter', {
  input: v.object({}),
  run(ctx) {
    const rows = ctx.sql
      .exec<{
        taskId: string
        attempts: number
        error: string
      }>(
        'SELECT taskId, attempts, error FROM __livething_scheduled_dlq ORDER BY failedAt DESC LIMIT 1',
      )
      .toArray()
    const row = rows[0]
    if (!row) return
    ctx.send('dead-letter-result', {
      taskId: row.taskId,
      attempts: row.attempts,
    })
  },
})
```

::note
The `scheduled` contract slot is **server-only** — it does not reach the client. Tasks are an internal server concern, so listing `scheduled()` adds no key to the client contract.
::

## At-least-once delivery

A scheduled run fires **at least once** — never zero times, but sometimes more than once. Two things cause a re-run:

- **A retry**, when the body threw (above).
- **A re-fire after a crash.** A pending run is cleared from storage only once its body finishes, so if the server dies mid-run the row survives and fires again when the server comes back. This holds for a one-shot task too, not only recurring ones.

This guarantee holds even when the body itself calls `ctx.schedule(...)` or `ctx.cancelScheduled(...)` before it finishes. Say a `processRefund` task schedules a `sendReceipt` task and then does the refund:

```typescript [chained-task.ts]
base.scheduled('processRefund', {
  run(ctx, data) {
    ctx.schedule('sendReceipt', {
      time: Date.now(),
      data: { orderId: data.orderId },
    })
    // ...do the refund...
  },
})
```

If the server dies right after `ctx.schedule('sendReceipt', ...)` runs but before `processRefund` finishes, `processRefund`'s own row is still on disk — it is not dropped just because it made a nested scheduling call. On restart, `processRefund` fires again alongside the now-durable `sendReceipt` run.

Because of this, **task bodies must be idempotent** — running the same body twice must not apply its effect twice. For an effect that stays inside the server (an upsert, setting a value), that is often already true. For an effect on the outside world — charging a card, sending a mail — guard it: give the run a stable key and pass it to the other system as an idempotency key, or record that the effect happened and check that record before repeating it.

## SQLite tables

`scheduled()` creates two tables in the server's own SQL storage the first time it runs. Both names start with the reserved `__livething_` prefix — do not create a table with either name yourself, especially before `scheduled()` is installed, since there is no "table already exists" error to warn you. See the [full reserved-table list](/server/context-and-storage/sql-and-kv#reserved-livething-tables) for every table LiveThing owns.

**`__livething_scheduled`** — one row per pending run, cleared once the run completes.

| Column      | Type               | Notes                                                            |
| ----------- | ------------------ | ---------------------------------------------------------------- |
| `id`        | `TEXT` primary key | The run's own id, not the task id.                               |
| `taskId`    | `TEXT`             | The key you declared in `scheduled({...})`.                      |
| `time`      | `INTEGER`          | Unix ms this run is due.                                         |
| `data`      | `TEXT`             | The task's payload, JSON-encoded; `NULL` for a no-payload task.  |
| `everyMs`   | `INTEGER`          | The interval for a recurring task; `NULL` for a one-shot.        |
| `attempts`  | `INTEGER`          | Retries used so far for this run.                                |
| `recurring` | `INTEGER`          | `0`/`1` flag — whether this row reschedules itself after firing. |
| `retry`     | `INTEGER`          | The row's retry policy, encoded.                                 |
| `metadata`  | `TEXT`             | Reserved JSON blob for future fields; not read or written yet.   |

**`__livething_scheduled_dlq`** — one row per run that exhausted its retries.

| Column     | Type               | Notes                                                          |
| ---------- | ------------------ | -------------------------------------------------------------- |
| `id`       | `TEXT` primary key | The original run's id.                                         |
| `taskId`   | `TEXT`             | The failed task's id.                                          |
| `time`     | `INTEGER`          | The run's original due time.                                   |
| `failedAt` | `INTEGER`          | Unix ms the row was moved to the dead-letter queue.            |
| `data`     | `TEXT`             | The task's payload, JSON-encoded; `NULL` if it had none.       |
| `attempts` | `INTEGER`          | Total attempts made before giving up.                          |
| `error`    | `TEXT`             | The last thrown error, stringified.                            |
| `metadata` | `TEXT`             | Reserved JSON blob for future fields; not read or written yet. |
