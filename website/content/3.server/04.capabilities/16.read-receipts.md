Many chat apps show two kinds of ticks on a message: a grey double tick for "received" and a blue tick for "read". An inbox channel already tracks who has _received_ each message. This data is called the **received cursor**: for each member, the highest message sequence number that member has confirmed. You can query it with `receiversOf`, with no extra setup. Sending the grey double tick live to other members is a separate flag, `broadcastReceipts`, on `inbox()`.

**readReceipts** adds the blue tick: who has _read_ a message, not only received it. Each member has a **read cursor**. When the member reads messages, the client moves the read cursor forward, and the server stores which member has read up to which message.

`readReceipts()` is a **channel-only** capability, like `inbox()`. You list it inside a channel's own `capabilities`, next to `inbox()`. You never list it in the top-level `server({ capabilities: [...] })` array.

This page shows how to turn on and configure read receipts. For how receipts work on the wire (the `__received__` and `__read__` live updates, `receiversOf` and `readersOf`, and the member limit), see [Receipts](/server/inbox/receipts).

## Requirements :badge[needs inbox()]

Read receipts are built on inbox. They use the same per-member cursors, sequence numbers and storage. So a channel that lists `readReceipts()` must also list `inbox()` in the same channel's `capabilities`. TypeScript checks this: a channel whose `capabilities` has `readReceipts()` without `inbox()` is a type error. `inbox()` has its own requirements on the host: `channels()`, `sequence({ persist: true })` and `dedup()`. See [`inbox`](/server/capabilities/inbox) for that list.

::note
Reading a message also means receiving it. So a `__read__` frame (the client's "I have read up to here" message) also settles that member's held inbox rows up to the read mark. A client can mark a message as read before it confirms that the message arrived. Inbox then moves the received cursor up to the read mark.
::

## How to enable

Import both `inbox` and `readReceipts` from `@livething/server/inbox`. Then list them together in the channel's own `capabilities`:

```typescript [server/dms.ts]
import { emits, server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { dedup } from '@livething/server/dedup'
import { inbox, readReceipts } from '@livething/server/inbox'
import { sequence } from '@livething/server/sequence'
import * as v from 'valibot'
import { requireSession } from './upgrade'

const base = server({
  upgrade: (request) => requireSession(request),
  capabilities: [
    channels(),
    sequence({ persist: true }),
    dedup(),
    emits({
      'cursor-answer': t<{ seq: number; userIds: string[] }>(),
    }),
  ],
})

export const dms = base.channel(['dms', 'dm:{pair}'], {
  capabilities: [
    inbox(),
    readReceipts(),
    emits({ message: t<Message>() }),
  ],
})

export const handleSendMessage = dms.on('send-message', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.channel.broadcast('message', {
      id: crypto.randomUUID(),
      text: input.text,
      from: ctx.user.id,
      sentAt: Date.now(),
    })
  },
})
```

Here `requireSession` is your own `upgrade` function. It gives each connection a `userId` and `meta: { name, role }`. Read cursors are stored by `userId`, so members need one. See [Upgrade](/server/server/upgrade).

To change the member limit, pass an options object to `readReceipts(...)`:

```typescript [read-receipts-options-server.ts]
export const dms = base.channel(['dms', 'dm:{pair}'], {
  capabilities: [
    inbox(),
    readReceipts({ maxReceiptAudience: 512 }),
    emits({ message: t<Message>() }),
  ],
})
```

## Configuration

`ReadReceiptsOptions` has one field, and it is optional.

| Option               | Type     | Default | What it does                                                                                                                                                                                                                                |
| -------------------- | -------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maxReceiptAudience` | `number` | `256`   | The server sends the live `__read__` update only while the channel has this many members or fewer. When the channel has more members, the server still stores the read cursor and `readersOf` still returns it, but no live update is sent. |

## Querying who has read

Inside a handler of the `dms` channel, `ctx.channel.readReceipts` is the channel's `ChannelReadReceipts` object. It is typed, and it is never `null` there, because `dms` lists `readReceipts()` in its own `capabilities`:

```typescript [readers-of-server.ts]
export const handleAskRead = dms.on('ask-read', {
  input: v.object({ seq: v.number() }),
  run(ctx, input) {
    const userIds = ctx.channel.readReceipts.readersOf(input.seq)
    ctx.send('cursor-answer', { seq: input.seq, userIds })
  },
})
```

`readersOf(seq)` returns the user IDs whose read cursor has reached `seq`.

From any other place (another handler, a hook, a scheduled task), use `ctx.channels.get('dms', 'dm:...').readReceipts()`. This method returns the same object, or `null` when that channel does not list `readReceipts()`. So check for `null` first:

```typescript [readers-of-anywhere-server.ts]
export const handleWhoRead = base.on('who-read', {
  input: v.object({ pair: v.string(), seq: v.number() }),
  run(ctx, input) {
    const receipts = ctx.channels
      .get('dms', `dm:${input.pair}`)
      .readReceipts()
    if (receipts) {
      const userIds = receipts.readersOf(input.seq)
      ctx.send('cursor-answer', { seq: input.seq, userIds })
    }
  },
})
```

## What it adds to the client contract

When a channel lists `readReceipts()`, its client contract has `readReceipts: true`. If the client also registers the client [`readReceipts()`](/client/primitives/read-receipts) primitive, that channel's client handle gets four members:

- `readers`: a readable store (a value you read with `get()` and watch with `subscribe()`). It holds each member's read cursor and updates when a `__read__` frame arrives.
- `onRead(callback)`: runs `callback` each time a member's read cursor moves forward.
- `markAsRead(seq?)`: moves this member's read cursor forward to `seq`. Without `seq`, it marks everything received so far as read.
- `readersOf(seq)`: asks the server who has read up to `seq`.

As with inbox, the flag reaches `InferClient` through the channel's handlers: pass a handler from that channel (such as `handleSendMessage`) to `base.assemble(...)`. See [Receipts](/server/inbox/receipts) for the full behavior.
