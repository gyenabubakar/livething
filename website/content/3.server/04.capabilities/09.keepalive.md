A WebSocket connection can stop working without either side knowing. For example, a phone goes into a tunnel, a laptop goes to sleep, or a router drops the link. In your code the socket is still "open", but no data moves. The **keepalive** capability finds these dead connections. The server sends a `ping` frame on a timer. A live client answers with a `pong` frame. The server closes any connection that stops sending frames.

A `ping` and a `pong` are heartbeat frames: very small plain-text messages (not JSON) that only check that the other side is still there.

## How it works

Two timers run for each connection:

1. **The ping timer.** Every `pingIntervalMs`, the server sends a `ping` frame. A live client answers with `pong` automatically. You do not write any code for this.
2. **The idle timer.** Every inbound frame (a frame the client sends to the server) restarts this timer. That includes app messages _and_ the automatic `pong`. If `idleTimeoutMs` passes with no inbound frame, the server closes the socket with the `IDLE` close code (`4004`).

The ping makes sure that a client that is quiet but still alive sends a frame in time. A client that is really gone sends nothing, not even a `pong`. So its idle time runs out, and the server closes it.

keepalive adds nothing to the client contract (the typed list of events and requests the client can use). It works only on the connection itself, so `InferClient` does not change.

### Under hibernation, neither timer runs

Both timers need the connection's Durable Object to stay in memory. So when [hibernation](/server/server/hibernation) is on, keepalive turns both timers off:

- The **ping timer** does not run. The Workers runtime answers a client's own `ping` at the edge (Cloudflare's network), without waking the Durable Object. A server ping would wake the object on every tick, which removes the savings of hibernation.
- The **idle timer** does not run either. The timer is a `setTimeout` in memory, so the Durable Object would have to stay in memory just to count down. This also removes the savings of hibernation.

So a server with hibernation on never closes a connection for being idle, and `ctx.quality` never becomes `'poor'` by itself. See [hibernation's trade-offs](/server/server/hibernation#the-trade-offs) to learn how to find connections that went quiet while the object was not in memory.

## What needs keepalive and what does not

Heartbeats go in **both directions**. This capability controls only one direction: the pings the **server sends**. All other heartbeat behavior works on every server, with no capability listed.

| Behavior                                                           | Needs `keepalive()`?                                                                                              |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| The server answers a client's `ping` with `pong`                   | **No**. Always on.                                                                                                |
| The `onPing` / `onPong` hooks observe heartbeat frames             | **No**. Always available. (One exception: with [hibernation](/server/server/hibernation), `onPing` does not run.) |
| The server sends a `ping` every `pingIntervalMs`                   | **Yes**                                                                                                           |
| The round-trip time is measured into `ctx.latency` / `ctx.quality` | **Yes**                                                                                                           |
| A connection that goes quiet is closed with `4004`                 | **Yes**                                                                                                           |

This has two results:

**A server without `keepalive()` never sends a ping.** It never starts a heartbeat. It only answers the pings that a client sends. This is fine even when the _client_ runs its own keepalive. The client sends pings, and the server always answers with `pong`. Every server answers pings, so this does not depend on the capability.

**Only `keepalive()` can send a `ping`.** There is no `ctx.ping()`, on purpose. A `pong` frame has no ID. So keepalive can only know which `ping` a `pong` answers because it is the only sender of pings. A second sender would make `keepalive()` time the wrong ping and report a wrong `ctx.latency`. You can still use the hooks, but you cannot send pings yourself.

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'

// No keepalive() listed. The hooks still work.
const base = server({
  capabilities: [],
  onPing(ctx) {
    ctx.log.info('client sent a ping', {
      connectionId: ctx.connection.id,
    })
  },
  onPong(ctx) {
    ctx.log.info('client sent a pong', {
      connectionId: ctx.connection.id,
    })
  },
})
```

## Enable it

Import `keepalive` from `@livething/server/keepalive` and list it in `capabilities`. Both options are optional. `keepalive()` with no arguments pings every 30 seconds and closes a connection after 60 seconds with no frames.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { keepalive } from '@livething/server/keepalive'

type Quality = 'excellent' | 'good' | 'degraded' | 'poor'

const base = server({
  capabilities: [
    keepalive(),
    emits({
      health: t<{
        latencyMs: number | null
        quality: Quality | null
      }>(),
    }),
  ],
})
```

This server uses the defaults: a ping every 30 seconds, and it closes any connection that sends nothing for 60 seconds. To change them, pass either option, for example `keepalive({ pingIntervalMs: 15_000 })`. The `health` event is used in the example [further down](#what-it-adds-to-the-context).

## Configuration

| Option           | Type     | Default  | What it is                                                                            |
| ---------------- | -------- | -------- | ------------------------------------------------------------------------------------- |
| `pingIntervalMs` | `number` | `30_000` | How often the server sends a `ping`, in milliseconds                                  |
| `idleTimeoutMs`  | `number` | `60_000` | How long a connection can send no frames before the server closes it, in milliseconds |

Both must be positive whole numbers (integers). Also, `pingIntervalMs` must be **smaller than** `idleTimeoutMs`. This check also uses the default for any option you leave out, so `keepalive({ pingIntervalMs: 60_000 })` throws because 60 000 is not smaller than the default 60 000. Neither timer runs under [hibernation](/server/server/hibernation) (see above).

::warning
**`pingIntervalMs` must be smaller than `idleTimeoutMs`.** The ping must arrive, and the pong must come back, before the idle time runs out. If the interval is greater than or equal to the timeout, `keepalive(...)` throws a `LiveThingConfigError` when you call it. Otherwise a client that is quiet but alive would be closed before it got a ping to answer. Leave extra time: with a 1-second ping and a 2-second timeout, the pong has one full second to come back.
::

```typescript [server/huddle-definition.ts]
import { keepalive } from '@livething/server/keepalive'

// Throws: 60_000 is not smaller than 60_000.
keepalive({ pingIntervalMs: 60_000, idleTimeoutMs: 60_000 })
```

## What it adds to the context

With keepalive listed, the server measures the round-trip time of each ping and pong (the time from sending the `ping` to getting the `pong` back). It adds two fields to the handler context:

- `ctx.latency`: the average round-trip time of the last 5 completed pings (or fewer, if fewer have completed), in milliseconds, rounded to a whole number. It is `null` before the first ping and pong complete.
- `ctx.quality`: a simple rating based on `ctx.latency`: `'excellent' | 'good' | 'degraded' | 'poor'`, or `null`.

```typescript [server/huddle-definition.ts]
const handleCheckHealth = base.on('check-health', {
  run(ctx) {
    ctx.send('health', {
      latencyMs: ctx.latency,
      quality: ctx.quality,
    })
  },
})
```

The ratings match latency like this:

| Rating        | Round-trip       |
| ------------- | ---------------- |
| `'excellent'` | under 100 ms     |
| `'good'`      | 100 to 299 ms    |
| `'degraded'`  | 300 to 999 ms    |
| `'poor'`      | 1000 ms and more |

::note
`ctx.latency` and `ctx.quality` are both `null` until the first ping and pong complete. `ctx.quality` is always `null` under hibernation, because the server sends no pings. The two fields exist on `ctx` only when `keepalive()` is listed. Reading them without it is a compile error.
::

A missed pong can also make `ctx.quality` `'poor'`, before the idle timer closes the socket. This happens once a connection has been measured at least once. When the next ping is due and the last ping still has no answer, the server sets `ctx.quality` to `'poor'` at that moment. It does not wait for `idleTimeoutMs`. `ctx.latency` keeps its last measured value. Only the rating changes. When a later pong arrives, the server measures the round-trip again and sets the rating from the new average.

::note
A client that never answers any ping is different. `ctx.quality` stays `null` and does not become `'poor'`. This is because `ctx.quality` comes from `ctx.latency`, and no round-trip was ever measured. Without hibernation, the server closes such a connection with `4004` when `idleTimeoutMs` runs out. Under hibernation the idle timer does not run, so the server does not close it for being quiet. Read `null` as "unknown", not as "healthy".
::

## Watching the heartbeat yourself

The `onPong` hook runs on every pong. keepalive has already recorded the round-trip before your hook runs. So this hook is a good place to log or report connection health. In `server({ ... })`:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { keepalive } from '@livething/server/keepalive'

export const base = server({
  capabilities: [keepalive()],
  onPong(ctx) {
    if (ctx.quality === 'poor') {
      ctx.log.warn('a client has a slow connection', {
        connectionId: ctx.connection.id,
        latencyMs: ctx.latency,
      })
    }
  },
})
```

The order is fixed. It does not depend on where you write the hook in the object. For each `pong`, LiveThing runs the capability hooks first (including the keepalive measurement), then plugin hooks, and your `onPong` hook last. So the measurement is always done before your hook runs. See [Lifecycle Hooks](/server/lifecycle-and-intercept/hooks#onpong).
