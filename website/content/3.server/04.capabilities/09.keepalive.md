A WebSocket can die without either side noticing — a phone goes through a tunnel, a laptop sleeps, a router drops the link. The socket stays "open" in code while no bytes flow. **keepalive** catches this. The server sends a `ping` on a timer, a live client answers `pong`, and any connection that stops answering is closed.

## How it works

Two timers run per connection:

1. **The ping timer.** Every `pingIntervalMs`, the server sends a `ping` frame. A live client answers `pong` automatically — you write no code for this.
2. **The idle timer.** Every inbound frame resets it. That includes app messages _and_ the automatic `pong`. If `idleTimeoutMs` passes with nothing inbound, the engine closes the socket with the `IDLE` close code (`4004`).

The ping exists so a quiet-but-alive client still produces a frame in time. A client that has truly gone away sends nothing — not even a pong — so its idle window elapses and it gets closed.

keepalive adds nothing to the client contract. It runs at the transport layer; `InferClient` is unchanged.

### Under hibernation, neither timer runs

Both timers depend on the connection's Durable Object being in memory, so [hibernation](/server/define/hibernation) turns both off:

- The **ping timer** does not run. Without [translation](/server/define/translation), the Workers runtime answers a client's own `ping` at the edge without waking the instance. With translation, the frame wakes the instance so it can pass through the translator; a server ping would still wake it up for no useful timing measurement.
- The **idle timer** does not run either. Arming it would mean keeping a `setTimeout` alive, which forces the instance to stay resident just to count down — defeating hibernation. Translation can make heartbeat frames visible, but it does not make an in-memory timer survive eviction.

So a hibernating server never closes a connection for going idle, and `ctx.quality` never turns `'poor'` on its own — see [hibernation's trade-offs](/server/define/hibernation#the-trade-offs) for what to do instead if you need to detect connections that went quiet while the object was asleep.

## What keepalive owns, and what is free

Ping and pong run in **both directions**, and this capability only owns one of them: the pings the **server sends**. Everything else about heartbeats works on every server, with no capability listed.

| Behavior                                                         | Needs `keepalive()`?                                                                                                        |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| The server answers a client's `ping` with `pong`                 | **No** — always on                                                                                                          |
| `base.onPing(...)` / `base.onPong(...)` observe heartbeat frames | **No** — always available (`onPing` is the one exception: it does not fire under [hibernation](/server/define/hibernation)) |
| The server sends a `ping` every `pingIntervalMs`                 | **Yes**                                                                                                                     |
| The round-trip is measured into `ctx.latency` / `ctx.quality`    | **Yes**                                                                                                                     |
| A connection that goes quiet is closed with `4004`               | **Yes**                                                                                                                     |

Two consequences worth being clear about:

**A server with no `keepalive()` never sends a ping.** It stays quiet until a client speaks first. That is fine even when the _client_ runs its own keepalive: the client pings, and the server always answers `pong`. Answering a probe is a courtesy every server owes, so it does not depend on this capability.

**Only `keepalive()` may send a `ping`.** There is no `ctx.ping()`, and that is deliberate. A `pong` frame carries no id, so the only way to know which `ping` it answers is for one thing to be sending them. A second sender would make `keepalive()` time the wrong ping and report a wrong `ctx.latency`. The hooks stay open to you; the timer does not.

```typescript [free-heartbeat.ts]
import { define, t } from '@wskit/server'

// No keepalive() listed — the hooks still work.
const base = define({ capabilities: [] })

base.onPing((ctx) => {
  ctx.log.info('the client checked on us', {
    connectionId: ctx.connection.id,
  })
})

base.onPong((ctx) => {
  ctx.log.info('the client answered', {
    connectionId: ctx.connection.id,
  })
})
```

## Enable it

Import `keepalive` from `@wskit/server/keepalive` and list it in `capabilities`. Both options are required — there are no defaults.

```typescript [server/socket.ts]
import { define, t } from '@wskit/server'
import { keepalive } from '@wskit/server/keepalive'

const base = define({
  capabilities: [
    keepalive({ pingIntervalMs: 30_000, idleTimeoutMs: 60_000 }),
  ],
})
```

This pings every 30 seconds and closes any connection that sends nothing for 60 seconds.

## Configuration

| Option           | Type     | Required | Default | What it is                                                                              |
| ---------------- | -------- | -------- | ------- | --------------------------------------------------------------------------------------- |
| `pingIntervalMs` | `number` | yes      | none    | How often the server sends a `ping`, in milliseconds                                    |
| `idleTimeoutMs`  | `number` | yes      | none    | How long a connection may go with no inbound frame before it is closed, in milliseconds |

Both must be positive integers. And `pingIntervalMs` must be **strictly less than** `idleTimeoutMs`. Neither timer runs under [hibernation](/server/define/hibernation) — see above.

::warning
**`pingIntervalMs` must be less than `idleTimeoutMs`.** The ping has to land — and the pong come back — before the idle window closes. If the interval is greater than or equal to the timeout, the build throws a clear error, because a quiet-but-alive client would be dropped before it ever got a ping to answer. Leave headroom: a 1-second ping against a 2-second timeout gives the pong a full second of margin.
::

```typescript [server/socket.ts]
// Throws at build: 60_000 is not less than 60_000.
keepalive({ pingIntervalMs: 60_000, idleTimeoutMs: 60_000 })
```

## What it adds to the context

With keepalive listed, the round-trip time of each ping/pong is measured and surfaced on the handler context:

- `ctx.latency` — the most recent measured round-trip in milliseconds, or `null` before the first ping/pong completes.
- `ctx.quality` — a simple rating derived from latency: `'excellent' | 'good' | 'degraded' | 'poor'`, or `null`.

```typescript [server/handlers.ts]
const handlePing = base.on('check-health', {
  run(ctx) {
    ctx.send('health', {
      latencyMs: ctx.latency,
      quality: ctx.quality,
    })
  },
})
```

The bands map latency like this:

| Band          | Round-trip     |
| ------------- | -------------- |
| `'excellent'` | under 100 ms   |
| `'good'`      | 100–299 ms     |
| `'degraded'`  | 300–999 ms     |
| `'poor'`      | 1000 ms and up |

::note
Both `ctx.latency` and `ctx.quality` are `null` until the first ping/pong completes, and `ctx.quality` is always `null` under hibernation (no server-side ping runs). They only exist on `ctx` when `keepalive()` is listed — reading them without it is a compile error.
::

Once a connection has been measured at least once, a missed pong drops `ctx.quality` to `'poor'` right away — the server does not wait for the idle timeout to say so. If a ping goes unanswered before the next one is due, quality flips to `'poor'` on that next tick, well before `idleTimeoutMs` would close the socket. The last measured `ctx.latency` is kept as-is; only the quality rating changes.

::note
A client that never answers a single ping is the exception. `ctx.quality` stays `null` rather than turning `'poor'`, because `ctx.quality` is derived from `ctx.latency` and no round-trip was ever measured. Without hibernation, such a connection is closed with `4004` when `idleTimeoutMs` elapses. Under hibernation the idle timer does not run, so it is not closed for going quiet at all. Treat `null` as "unknown", not as "healthy".
::

## Watching the heartbeat yourself

`base.onPong(...)` fires on every pong, and keepalive has already recorded the round-trip by then. That makes it the place to log or report connection health:

```typescript [watch-health.ts]
base.onPong((ctx) => {
  if (ctx.quality === 'poor') {
    ctx.log.warn('a client is struggling', {
      connectionId: ctx.connection.id,
      latencyMs: ctx.latency,
    })
  }
})
```

The ordering is fixed and does not depend on where you write the hook: keepalive registers its `onPong` while the capability is being set up, and `base.onPong(...)` registers afterwards. The capability's measurement always lands first. See [Lifecycle Hooks](/server/lifecycle-and-intercept/hooks#onpong).
