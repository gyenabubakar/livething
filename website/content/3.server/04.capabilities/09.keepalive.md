A connection can stop working without either side knowing. For example, a phone goes into a tunnel, a laptop goes to sleep, or a router drops the link. In your code the socket is still "open", but no data moves. The **keepalive** capability finds these dead connections. The server sends a `ping` frame on a timer. A live client answers with a `pong` frame. The server closes any connection that stops sending frames.

A `ping` and a `pong` are heartbeat frames: very small plain-text messages (not JSON) that only check that the other side is still there.

## How it works

Two timers run for each connection:

1. **The ping timer.** Every `pingIntervalMs`, the server sends a `ping` frame. A live client answers with `pong` automatically. You do not write any code for this.
2. **The idle timer.** Every inbound frame restarts this timer. That includes app messages _and_ the automatic `pong`. If `idleTimeoutMs` passes with no inbound frame, the server closes the socket with the `IDLE` close code (`4004`).

The ping makes sure that a client that is quiet but still alive sends a frame in time. A client that is really gone sends nothing, not even a `pong`. So its idle time runs out, and the server closes it.

keepalive adds nothing to the client contract. It works only on the connection itself, so `InferClient` does not change.

### Under hibernation, neither timer runs for a hibernating WebSocket

Both timers need the connection's Durable Object to stay in memory. So when [hibernation](/server/server/hibernation) is on, keepalive turns both timers off for each WebSocket that the platform holds while the object sleeps:

- The **ping timer** does not run. The Workers runtime answers a client's own `ping` at the edge, without waking the Durable Object. A server ping would wake the object on every tick, which removes the savings of hibernation.
- The **idle timer** does not run either. The timer is a `setTimeout` in memory, so the Durable Object would have to stay in memory just to count down. This also removes the savings of hibernation.

So on a server with [hibernation](/server/server/hibernation) on, such a connection is never closed for being idle, and its `ctx.quality` stays `null`. [Hibernation's trade-offs](/server/server/hibernation#the-trade-offs) explain how to find connections that went quiet while the object was not in memory. For these connections, the `__connected__` frame sends `null` for both timings, so the client pings on its own fixed 30-second interval.

This choice is made for each connection. An [`http()`](/server/adapters/transports) connection keeps the object awake anyway, so both timers run for it, and it has a `ctx.quality` value, even on a server with hibernation on.

### `http()` needs keepalive

The [`http()`](/server/adapters/transports) transport needs `keepalive()` in the definition. A stream that sends nothing looks the same as a stream that a proxy cut, so only the ping and the idle timer can find a dead one. When `http()` is listed and `keepalive()` is not, `bind()` throws at startup and says to add it. On `http()` the client always answers a ping with a `pong` POST.

## What needs keepalive and what does not

Heartbeats go in **both directions**. This capability controls only one direction: the pings the **server sends**. All other heartbeat behavior works on every server, with no capability listed.

| Behavior                                                           | Needs `keepalive()`?                                                                                                                                                                  |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The server answers a client's `ping` with `pong`                   | **No**. Always on.                                                                                                                                                                    |
| The `onPing` / `onPong` hooks observe heartbeat frames             | **No**. Always available. (One exception: with [hibernation](/server/server/hibernation), `onPing` does not run for a hibernating WebSocket, because the runtime answers its `ping`.) |
| The server sends a `ping` every `pingIntervalMs`                   | **Yes**                                                                                                                                                                               |
| The round-trip time is measured into `ctx.latency` / `ctx.quality` | **Yes**                                                                                                                                                                               |
| A connection that goes quiet is closed with `4004`                 | **Yes**                                                                                                                                                                               |

This has two results:

**A server without `keepalive()` never sends a ping.** It never starts a heartbeat. It only answers the pings that a client sends. This is fine even when the _client_ runs its own keepalive. The client sends pings, and the server always answers with `pong`. Every server answers pings, so this does not depend on the capability.

**Only `keepalive()` can send a `ping`.** There is no `ctx.ping()`, on purpose. A `pong` frame has no ID. So keepalive can only know which `ping` a `pong` answers because it is the only sender of pings. A second sender would make `keepalive()` time the wrong ping and report a wrong `ctx.latency`. You can still use the hooks, but you cannot send pings yourself.

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'

// No keepalive() listed. The hooks still work.
const base = server({
  capabilities: [],
  onPing(ctx) {
    ctx.log.info('client sent a ping', {
      connectionId: ctx.connection.id,
    })
  },
  onPong(ctx) {
    ctx.log.info('client sent a pong', {
      connectionId: ctx.connection.id,
    })
  },
})
```

## Enable it

Import `keepalive` from `@livething/server/keepalive` and list it in `capabilities`. Both options are optional. `keepalive()` with no arguments pings every 30 seconds and closes a connection after 60 seconds with no frames.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { keepalive } from '@livething/server/keepalive'

type Quality = 'excellent' | 'good' | 'degraded' | 'poor'

const base = server({
  capabilities: [
    keepalive(),
    emits({
      health: t<{
        latencyMs: number | null
        quality: Quality | null
      }>(),
    }),
  ],
})
```

This server uses the defaults: a ping every 30 seconds, and it closes any connection that sends nothing for 60 seconds. To change them, pass either option. For example, in the server's `capabilities`:

```ts
import { keepalive } from '@livething/server/keepalive'

// A ping every 15 seconds
keepalive({ pingIntervalMs: 15_000 })
```

The `health` event is used in the example [further down](#what-it-adds-to-the-context).

## Configuration

| Option           | Type     | Default  | What it is                                                                            |
| ---------------- | -------- | -------- | ------------------------------------------------------------------------------------- |
| `pingIntervalMs` | `number` | `30_000` | How often the server sends a `ping`, in milliseconds                                  |
| `idleTimeoutMs`  | `number` | `60_000` | How long a connection can send no frames before the server closes it, in milliseconds |

Both must be positive whole numbers, no larger than `2147483647` (`2 ** 31 - 1`, the longest a timer can hold). Also, `pingIntervalMs` must be **smaller than** `idleTimeoutMs`. This check also uses the default for any option you leave out. So this call throws, because 60 000 is not smaller than the default 60 000:

```ts
import { keepalive } from '@livething/server/keepalive'

// Throws a LiveThingConfigError: idleTimeoutMs is 60_000 by default
keepalive({ pingIntervalMs: 60_000 })
```

The server sends both values to the client in the first frame, `__connected__`, and the client's own [`keepalive()`](/client/primitives/keepalive) pings at the same interval. You set them on the server only. Neither timer runs for a WebSocket that [hibernates](/server/server/hibernation) (see above).

::warning
**`pingIntervalMs` must be smaller than `idleTimeoutMs`.** The ping must arrive, and the pong must come back, before the idle time runs out. If the interval is greater than or equal to the timeout, `keepalive(...)` throws a `LiveThingConfigError` when you call it. Otherwise a client that is quiet but alive would be closed before it got a ping to answer. Leave extra time: with a 1-second ping and a 2-second timeout, the pong has one full second to come back.
::

```typescript [server/huddle-definition.ts]
import { keepalive } from '@livething/server/keepalive'

// Throws: 60_000 is not smaller than 60_000.
keepalive({ pingIntervalMs: 60_000, idleTimeoutMs: 60_000 })
```

## What it adds to the context

With keepalive listed, the server measures the round-trip time of each ping and pong. It adds two fields to the handler context:

- `ctx.latency`: the average round-trip time of the last 5 completed pings (or fewer, if fewer have completed), in milliseconds, rounded to a whole number. It is `null` before the first ping and pong complete. A pong carries no ID, so the server keeps only one ping in flight at a time on each connection, and each pong answers that ping. A pong slower than `pingIntervalMs` therefore still reports its real round trip.
- `ctx.quality`: a simple rating based on `ctx.latency`: one of `'excellent'`, `'good'`, `'degraded'` and `'poor'`, or `null`.

```typescript [server/huddle-definition.ts]
const handleCheckHealth = base.on('check-health', {
  run(ctx) {
    ctx.send('health', {
      latencyMs: ctx.latency,
      quality: ctx.quality,
    })
  },
})
```

The ratings match latency like this:

| Rating        | Round-trip       |
| ------------- | ---------------- |
| `'excellent'` | under 100 ms     |
| `'good'`      | 100 to 299 ms    |
| `'degraded'`  | 300 to 999 ms    |
| `'poor'`      | 1000 ms and more |

::note
`ctx.latency` and `ctx.quality` are both `null` until the first ping and pong complete. `ctx.quality` is always `null` for a WebSocket that hibernates, because the server sends it no pings. The two fields exist on `ctx` only when `keepalive()` is listed. Reading them without it is a compile error.
::

A missed pong can also make `ctx.quality` `'poor'`, before the idle timer closes the socket. This happens once a connection has been measured at least once. When the next ping is due and the last ping still has no answer, the server sends no new ping and sets `ctx.quality` to `'poor'` at that moment. It does not wait for `idleTimeoutMs`. `ctx.latency` keeps its last measured value. Only the rating changes. When the pong arrives, the server measures the round-trip again and sets the rating from the new average, and the pings start again.

A lost ping never gets a pong, so the server sends no more pings on that connection and `ctx.quality` stays `'poor'`. A client that stopped answering usually sends nothing else either, so `idleTimeoutMs` runs out and the server closes the socket with `4004`. That is the missed-pong close on the server. A client that still sends app messages keeps its idle timer fresh, so its connection stays open.

::note
A client that never answers any ping is different. `ctx.quality` stays `null` and does not become `'poor'`. This is because `ctx.quality` comes from `ctx.latency`, and no round-trip was ever measured. Without hibernation, the server closes such a connection with `4004` when `idleTimeoutMs` runs out. For a WebSocket that hibernates, the idle timer does not run, so the server does not close it for being quiet. Read `null` as "unknown", not as "healthy".
::

## Watching the heartbeat yourself

The `onPong` hook runs on every pong. keepalive has already recorded the round-trip before your hook runs. So this hook is a good place to log or report connection health. In `server({ ... })`:

```typescript [server/huddle-definition.ts]
import { server } from '@livething/server'
import { keepalive } from '@livething/server/keepalive'

export const base = server({
  capabilities: [keepalive()],
  onPong(ctx) {
    if (ctx.quality === 'poor') {
      ctx.log.warn('a client has a slow connection', {
        connectionId: ctx.connection.id,
        latencyMs: ctx.latency,
      })
    }
  },
})
```

The order is fixed. It does not depend on where you write the hook in the object. For each `pong`, LiveThing runs the capability hooks first (including the keepalive measurement), then plugin hooks, and your [`onPong` hook](/server/lifecycle-and-intercept/hooks#onpong) last. So the measurement is always done before your hook runs.
