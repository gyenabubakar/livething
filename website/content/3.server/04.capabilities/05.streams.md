A **stream** is progressive, chunked data the server pushes piece by piece instead of all at once — LLM tokens, query rows, a live feed. WSKit has three stream capabilities, all imported from `@wskit/server/streams`:

```typescript [server.ts]
import { recordedStream, resumableStream, stream } from '@wskit/server/streams'
```

Each one enables a different handler and a different durability story. This page is the "enable + what each kind is + contract" reference. For the deep behavior — durability, broadcast, backpressure, lifecycle — follow the links to the [Streams](/server/streams/overview) chapter.

## Plain streams

`stream()` enables `base.stream(name, { input, chunk?, run })`. The `run` is an async generator: each value it yields is sent to the client as one chunk. A plain stream is ephemeral — it does not survive a disconnect.

```typescript [server.ts]
import { define, t } from '@wskit/server'
import { stream } from '@wskit/server/streams'
import * as v from 'valibot'

const base = define({
  capabilities: [stream()],
})

export const handleFeed = base.stream('feed', {
  input: v.object({ count: v.number() }),
  chunk: t<{ index: number }>(),
  async *run(ctx, input) {
    for (let i = 0; i < input.count; i += 1) {
      yield { index: i }
    }
  },
})
```

::note
Every stream builder creates a handler value. Include `handleFeed` (and every resumable or recorded stream value) in `base.assemble({ handlers: [...] })` for it to run and enter `InferClient`.
::

`chunk` is an optional `t<T>()` marker that types each yielded chunk. Leave it off and the chunk type is inferred from what `run` yields.

See [Plain Streams](/server/streams/plain) for the full plain-stream behavior.

## Resumable streams

`resumableStream()` enables `base.resumableStream(name, { input, cursor?, run })`. The generator records a cursor with each chunk through `ctx.stream.withCursor(chunk, cursor)`. After a reconnect it re-runs from the saved cursor, read from `ctx.stream.cursor`, so the client picks up where it left off. The cursor is stored durably, in the server's own SQL storage, which every WSKit adapter provides automatically.

```typescript [resumable.ts]
import { define, t } from '@wskit/server'
import { resumableStream } from '@wskit/server/streams'
import * as v from 'valibot'

const base = define({
  capabilities: [resumableStream()],
})

export const handlePaginate = base.resumableStream('paginate', {
  input: v.object({}),
  cursor: t<{ row: number }>(),
  async *run(ctx) {
    const start = ctx.stream.cursor?.row ?? 0
    for (let i = start + 1; i <= 100; i += 1) {
      yield ctx.stream.withCursor({ row: i }, { row: i })
    }
  },
})
```

`cursor` is an optional `t<T>()` marker that types the cursor only. Pass a schema instead to also runtime-check a cursor restored after reconnect.

Each run also exposes `ctx.stream.attempt` — `1` on the first run, incremented on every reconnect — useful for logging or capping how many times you re-run.

See [Resumable](/server/streams/durable-resumable) for cursor restore and durability detail.

## Recorded streams

`recordedStream()` enables `base.recordedStream(name, { input, maxChunks?, run })`. Chunks are buffered as they emit; on reconnect the client receives the chunks it missed and the generator does **not** re-run. This suits a source you cannot replay — model tokens, for example. The chunk buffer is stored durably, in the server's own SQL storage, which every WSKit adapter provides automatically.

```typescript [recorded.ts]
import { define, t } from '@wskit/server'
import { recordedStream } from '@wskit/server/streams'
import * as v from 'valibot'

const base = define({
  capabilities: [recordedStream()],
})

export const handleTokens = base.recordedStream('tokens', {
  input: v.object({ prompt: v.string() }),
  async *run(ctx, input) {
    for (const token of await generateTokens(input.prompt)) {
      yield { token }
    }
  },
})
```

The difference from resumable: a resumable stream re-runs the generator from the cursor, while a recorded stream replays the buffered chunks and never re-runs. See [Recorded](/server/streams/durable-recorded) for buffering and `maxChunks` detail.

When a recorded stream reaches its `maxChunks` cap, the next `yield` throws `StreamAborted` with `detail.reason === 'buffer-full'` into the generator. Catch it to stop cleanly:

```typescript [buffer-full.ts]
import { StreamAborted } from '@wskit/server/errors'

export const handleCapped = base.recordedStream('capped', {
  input: v.object({}),
  maxChunks: 100,
  async *run() {
    for (let n = 1; ; n += 1) {
      try {
        yield { n }
      } catch (err) {
        if (StreamAborted.matches(err) && err.detail.reason === 'buffer-full')
          return
        throw err
      }
    }
  },
})
```

## The stream context (`ctx.stream`)

Inside any stream generator, `ctx.stream` carries the controls for the running stream:

::field-group
::field{name="ctx.stream.signal" type="AbortSignal"}
Fires when the client cancels, unsubscribes, or the stream is otherwise torn down. Wire it into any long await so the generator exits early instead of hanging.
::

::field{name="ctx.stream.drain()" type="() => Promise<void>"}
Waits until the outbound buffer falls back under `highWaterMark` (256 KB by default). Call it after a large yield to apply backpressure and avoid flooding a slow client.
::

::field{name="ctx.stream.nudges(yield chunk)" type="(chunk: T) => Nudge[]"}
Reads the client nudges that arrived since the last yield (see Nudges below).
::

::field{name="ctx.stream.withCursor(chunk, cursor)" type="(chunk, cursor) => Chunk"}
Attaches a cursor to a yielded chunk, for resumable streams.
::

::field{name="ctx.stream.cursor" type="Cursor | undefined"}
The cursor saved from the last successful run, for resumable streams.
::

::field{name="ctx.stream.attempt" type="number"}
`1` on the first run, incremented on every reconnect, for resumable streams.
::
::

```typescript [stream-ctx.ts]
export const handleFeed = base.stream('feed', {
  input: v.object({}),
  async *run(ctx) {
    for (const row of await loadRows()) {
      yield row
      await ctx.stream.drain() // pause until the client catches up
      if (ctx.stream.signal.aborted) return // client went away — stop early
    }
  },
})
```

### Nudges — messages into a running stream

Declare `nudges` as an object map (event name → schema). Inside the generator, `ctx.stream.nudges(yield chunk)` returns the nudges the client sent since the previous yield:

```typescript [nudges.ts]
export const handleTokens = base.stream('tokens', {
  input: v.object({ prompt: v.string() }),
  nudges: {
    pause: v.strictObject({}),
    'speed-up': v.object({ factor: v.number() }),
  },
  async *run(ctx, input) {
    for (const word of input.prompt.split(' ')) {
      const nudges = ctx.stream.nudges(yield { token: word })
      if (nudges.some((n) => n.event === 'pause')) await waitForResume()
    }
  },
})
```

## The contract slice

Any stream capability fills the client contract's `streams` key. Each entry pairs the `payload` that starts the stream with the `chunk` shape it yields, plus a `kind` — `'ephemeral'` for plain, `'persistent'` for resumable and recorded — and optional `nudges`:

```typescript [feed-socket.ts]
interface FeedSocket {
  streams: {
    feed: {
      payload: { count: number }
      chunk: { index: number }
      kind: 'ephemeral'
    }
    paginate: {
      payload: {}
      chunk: { row: number }
      kind: 'persistent'
    }
  }
}
```

## Configuration at a glance

The stream handlers accept config beyond `input` and `run`. These are the fields:

| Field                 | Streams             | Default               | What it does                                                                                                                                                                                                                                                       |
| --------------------- | ------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `chunk` / `cursor`    | all / resumable     | inferred              | Type marker for each chunk, or for the resume cursor. Leave off and the type is inferred from `run`.                                                                                                                                                               |
| `nudges`              | all                 | none                  | Typed messages the client can send into a running stream.                                                                                                                                                                                                          |
| `broadcast`           | all                 | `false`               | Fan the stream out to many clients instead of one.                                                                                                                                                                                                                 |
| `allowConcurrent`     | all                 | `false`               | Allow more than one active stream of this event per connection.                                                                                                                                                                                                    |
| `highWaterMark`       | all                 | 256 KB                | Outbound backpressure limit **in bytes**, used by `ctx.stream.drain()`.                                                                                                                                                                                            |
| `onDisconnect`        | resumable, recorded | `'cancel-but-buffer'` | `'cancel-but-buffer'` suspends and keeps buffered data, or `'keep-running'` lets the generator keep going after the client drops. `'keep-running'` requires `broadcast: true` — it throws at `base.resumableStream()`/`base.recordedStream()` call time otherwise. |
| `maxAgeMs`            | resumable, recorded | 5 minutes             | How long a suspended stream is kept after the client drops.                                                                                                                                                                                                        |
| `retentionAfterEndMs` | resumable, recorded | 30 seconds            | How long an ended stream is kept so a quick reconnect can still resume.                                                                                                                                                                                            |
| `maxChunks`           | recorded            | `500`                 | Hard cap on how many chunks the buffer holds.                                                                                                                                                                                                                      |

For how each of these actually behaves — broadcast, backpressure and drain, the durable lifecycle — see [Configuration & Lifecycle](/server/streams/config-and-lifecycle) and [Broadcast](/server/streams/broadcast).

## Channel streams

A channel can host any of these stream kinds with `.stream`, `.resumableStream`, and `.recordedStream`. Each needs the matching stream capability listed, or assembly fails with a message naming what to add. See [Scoped Streams & Requests](/server/channels/scoped-streams-requests).
