A **stream** sends data from the server to the client in pieces, one piece at a time, instead of all at once. Each piece is called a **chunk**. Examples are the tokens of an AI answer, the rows of a query, or a live feed. LiveThing has three stream capabilities. You import all of them from `@livething/server/streams`:

```typescript [server.ts]
import {
  recordedStream,
  resumableStream,
  stream,
} from '@livething/server/streams'
```

Each one enables a different handler. They also differ in what happens when the client disconnects. This page shows how to enable each kind, what each kind is, and how it appears in the client contract. For the full behavior (durability, broadcast, backpressure, lifecycle), follow the links to the [Streams](/server/streams/overview) chapter.

## Plain streams

`stream()` enables `base.stream(name, { input, chunk?, run })`. `run` is an async generator (an `async function*` that can `yield` many values over time). Each value it yields is sent to the client as one chunk. A plain stream is **ephemeral**: it stops when the client disconnects and does not continue after a reconnect.

```typescript [server.ts]
import { server, t } from '@livething/server'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'

const base = server({
  capabilities: [stream()],
})

export const handleFeed = base.stream('feed', {
  input: v.object({ count: v.number() }),
  chunk: t<{ index: number }>(),
  async *run(ctx, input) {
    for (let i = 0; i < input.count; i += 1) {
      yield { index: i }
    }
  },
})
```

::note
Every stream builder returns a handler value. Pass `handleFeed` (and every resumable or recorded stream value) to `base.assemble({ handlers: [...] })`. Only then does the stream run and appear in `InferClient`.
::

`chunk` is an optional `t<T>()` marker. A marker gives a type only and runs no check. It sets the type of each yielded chunk. If you leave it off, LiveThing infers the chunk type from what `run` yields.

See [Plain Streams](/server/streams/plain) for the full plain-stream behavior.

## Resumable streams

`resumableStream()` enables `base.resumableStream(name, { input, chunk?, cursor?, run })`. A **cursor** is a small value that marks a position in your data, such as a row number. The generator saves a cursor with each chunk through `ctx.stream.withCursor(chunk, cursor)`. This saved position is called a **checkpoint**. After a reconnect, LiveThing runs the generator again. `ctx.stream.cursor` then holds the last checkpoint the client confirmed, so the generator can continue from there. The client gets the rest of the data without gaps.

LiveThing saves checkpoints in the server's SQL storage (the same database as [`ctx.sql`](/server/context-and-storage/sql-and-kv)). Every adapter provides this storage. On Node, the default database is in memory, so give the adapter a file path if checkpoints must survive a server restart.

```typescript [resumable.ts]
import { server, t } from '@livething/server'
import { resumableStream } from '@livething/server/streams'
import * as v from 'valibot'

const base = server({
  capabilities: [resumableStream()],
})

export const handlePaginate = base.resumableStream('paginate', {
  input: v.object({}),
  chunk: t<{ row: number }>(),
  cursor: t<{ row: number }>(),
  async *run(ctx) {
    const start = ctx.stream.cursor?.row ?? 0
    for (let i = start + 1; i <= 100; i += 1) {
      yield ctx.stream.withCursor({ row: i }, { row: i })
    }
  },
})
```

`cursor` is an optional `t<T>()` marker that sets the cursor type only. Pass a schema instead to also check, at runtime, each cursor LiveThing restores after a reconnect. If a restored cursor fails the check, the client gets a `StreamAborted` error with `reason: 'cursor-invalid'`.

A resumable stream needs the `chunk` marker when every chunk goes through `withCursor`. TypeScript cannot infer the chunk type from `withCursor` alone, so without `chunk` the client sees the chunk type as `unknown`.

Each run also gets `ctx.stream.attempt`. It is `1` on the first run and `2` or higher on a run after a reconnect. Use it, for example, to log resumes or to change behavior after a resume.

See [Resumable](/server/streams/durable-resumable) for more about restoring the cursor and about durability.

## Recorded streams

`recordedStream()` enables `base.recordedStream(name, { input, maxChunks?, run })`. LiveThing saves each chunk in a buffer when the generator yields it. After a reconnect, the client receives the chunks it missed from the buffer, and the generator does **not** run again. Use a recorded stream for a source you cannot run again from a position, such as the tokens of an AI model. Like checkpoints, the buffer is saved in the server's SQL storage.

```typescript [recorded.ts]
import { server, t } from '@livething/server'
import { recordedStream } from '@livething/server/streams'
import * as v from 'valibot'

const base = server({
  capabilities: [recordedStream()],
})

export const handleTokens = base.recordedStream('tokens', {
  input: v.object({ prompt: v.string() }),
  async *run(ctx, input) {
    for (const token of await generateTokens(input.prompt)) {
      yield { token }
    }
  },
})
```

The difference from a resumable stream: a resumable stream runs the generator again from the cursor. A recorded stream sends the saved chunks again and never runs the generator again. See [Recorded](/server/streams/durable-recorded) for more about the buffer and `maxChunks`.

`maxChunks` is the most chunks the buffer can hold. When a recorded stream reaches this limit, the next `yield` throws `StreamAborted` into the generator, with `detail.reason === 'buffer-full'`. Catch it to stop the stream cleanly:

```typescript [buffer-full.ts]
import { StreamAborted } from '@livething/server/errors'

export const handleCapped = base.recordedStream('capped', {
  input: v.object({}),
  maxChunks: 100,
  async *run() {
    for (let n = 1; ; n += 1) {
      try {
        yield { n }
      } catch (err) {
        if (
          StreamAborted.matches(err) &&
          err.detail.reason === 'buffer-full'
        )
          return
        throw err
      }
    }
  },
})
```

## The stream context (`ctx.stream`)

Inside any stream generator, `ctx.stream` holds the controls for the running stream:

::field-group
::field{name="ctx.stream.signal" type="AbortSignal"}
An `AbortSignal` (the standard web object that tells work to stop). It fires when the stream is cancelled, when the client disconnects, or when the server shuts down. Pass it into long awaited work, such as `fetch`, so the generator stops early instead of waiting.
::

::field{name="ctx.stream.drain()" type="() => Promise<void>"}
Waits until the outgoing buffer is below `highWaterMark` again (256 KB by default). Call it after a large yield. This is **backpressure**: the server waits so that it does not send data faster than a slow client can receive it.
::

::field{name="ctx.stream.nudges(yielded)" type="(yielded: unknown) => { event, payload }[]"}
Returns the nudges the client sent since the last yield. Pass it the value of the `yield` expression. It exists only when the stream declares `nudges` (see Nudges below).
::

::field{name="ctx.stream.withCursor(chunk, cursor)" type="(chunk, cursor) => Chunk"}
Saves a cursor with a yielded chunk. Resumable streams only.
::

::field{name="ctx.stream.cursor" type="Cursor | null"}
The last checkpoint the client confirmed, or `null` on the first run. Resumable streams only.
::

::field{name="ctx.stream.attempt" type="number"}
`1` on the first run, `2` or higher on a run after a reconnect. Resumable streams only.
::
::

```typescript [stream-ctx.ts]
export const handleFeed = base.stream('feed', {
  input: v.object({}),
  async *run(ctx) {
    for (const row of await loadRows()) {
      yield row
      await ctx.stream.drain() // wait until the client has received the data
      if (ctx.stream.signal.aborted) return // the stream was stopped, so stop early
    }
  },
})
```

### Nudges: messages into a running stream

A **nudge** is a small message the client sends into a stream that is already running, for example "pause" or "go faster". Declare `nudges` as an object that maps each nudge name to a schema. Use `null` for a nudge with no payload. Inside the generator, `ctx.stream.nudges(yield chunk)` returns the nudges the client sent since the previous yield:

```typescript [nudges.ts]
export const handleTokens = base.stream('tokens', {
  input: v.object({ prompt: v.string() }),
  nudges: {
    pause: null,
    'speed-up': v.object({ factor: v.number() }),
  },
  async *run(ctx, input) {
    for (const word of input.prompt.split(' ')) {
      const nudges = ctx.stream.nudges(yield { token: word })
      if (nudges.some((n) => n.event === 'pause'))
        await waitForResume()
    }
  },
})
```

## The contract slice

Every stream capability adds entries to the `streams` key of the client contract. Each entry has:

- `payload`: the value that starts the stream.
- `chunk`: the type of each chunk the stream yields.
- `kind`: `'ephemeral'` for a plain stream, `'persistent'` for a resumable or recorded stream.
- `cursor`: only on a resumable stream that declares a `cursor`.
- `nudges`: only on a stream that declares nudges.

```typescript [feed-socket.ts]
interface FeedSocket {
  streams: {
    feed: {
      payload: { count: number }
      chunk: { index: number }
      kind: 'ephemeral'
    }
    paginate: {
      payload: {}
      chunk: { row: number }
      kind: 'persistent'
    }
  }
}
```

## Configuration at a glance

The stream handlers accept more options than `input` and `run`:

| Field                 | Streams             | Default               | What it does                                                                                                                                                                                                                                                  |
| --------------------- | ------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `chunk` / `cursor`    | all / resumable     | inferred / `unknown`  | Type marker for each chunk, or for the cursor. Without `chunk`, the chunk type is inferred from what `run` yields. Without `cursor`, the cursor type is `unknown`.                                                                                            |
| `nudges`              | all                 | none                  | Typed messages the client can send into a running stream.                                                                                                                                                                                                     |
| `broadcast`           | all                 | `false`               | Send the stream to many clients instead of one: every connection, or every member of the channel for a channel stream.                                                                                                                                        |
| `allowConcurrent`     | all                 | `false`               | Allow more than one active stream of this event on one connection.                                                                                                                                                                                            |
| `highWaterMark`       | all                 | 256 KB                | Outgoing buffer limit **in bytes**, used by `ctx.stream.drain()`.                                                                                                                                                                                             |
| `onDisconnect`        | resumable, recorded | `'cancel-but-buffer'` | What happens when the client drops. `'cancel-but-buffer'` stops the generator and keeps the saved data. `'keep-running'` lets the generator continue. On a resumable stream, `'keep-running'` requires `broadcast: true`, or `base.resumableStream()` throws. |
| `maxAgeMs`            | resumable, recorded | 5 minutes             | How long LiveThing keeps a stopped stream after the client drops.                                                                                                                                                                                             |
| `retentionAfterEndMs` | resumable, recorded | 30 seconds            | How long LiveThing keeps a finished stream, so a client that reconnects quickly can still resume it.                                                                                                                                                          |
| `maxChunks`           | recorded            | `500`                 | The most chunks the buffer can hold.                                                                                                                                                                                                                          |

For how each option behaves (broadcast, backpressure and drain, the durable lifecycle), see [Configuration & Lifecycle](/server/streams/config-and-lifecycle) and [Broadcast](/server/streams/broadcast).

## Channel streams

A channel can have any of these stream kinds, with `.stream`, `.resumableStream`, and `.recordedStream`. Each one needs the matching stream capability in `capabilities`. Without it, the method does not exist on the channel type, and calling it throws an error that names the capability to add. See [Scoped Streams & Requests](/server/channels/scoped-streams-requests).
