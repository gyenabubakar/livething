A **stream** sends data from the server to the client in pieces, one piece at a time, instead of all at once. Each piece is called a **chunk**. Examples are the tokens of an AI answer, the rows of a query, or a live feed. LiveThing has three stream capabilities. You import all of them from `@livething/server/streams`:

```typescript [server/huddle.ts]
import {
  cursorStream,
  recordedStream,
  stream,
} from '@livething/server/streams'
```

Each one enables a different handler. They also differ in what happens when the client disconnects. This page shows how to enable each kind, what each kind is, and how it appears in the client contract. For the full behavior (durability, broadcast, backpressure, lifecycle), follow the links to the [Streams](/server/streams/overview) chapter.

## Plain streams

`stream()` enables `base.stream(name, { input, chunk?, run })`. `run` is an async generator (an `async function*` that can `yield` many values over time). Each value it yields is sent to the client as one chunk. A plain stream is **ephemeral**: it stops when the client disconnects and does not continue after a reconnect.

```typescript [server/scout.ts]
import { server, t } from '@livething/server'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'

const base = server({
  capabilities: [stream()],
})

export const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  chunk: t<{ hit: Message }>(),
  allowConcurrent: true,
  async *run(ctx, input) {
    for (const hit of await searchMessages(input.query)) {
      yield { hit }
    }
  },
})
```

::note
Every stream builder returns a handler value. Pass `handleSearchMessages` (and every cursor or recorded stream value) to `base.assemble({ handlers: [...] })`. Only then does the stream run and appear in `InferClient`.
::

`chunk` is an optional `t<T>()` marker. A marker gives a type only and runs no check. It sets the type of each yielded chunk. If you leave it off, LiveThing infers the chunk type from what `run` yields.

See [Plain Streams](/server/streams/plain) for the full plain-stream behavior.

## Cursor streams

`cursorStream()` enables `base.cursorStream(name, { input, chunk?, cursor?, run })`. A **cursor** is a small value that marks a position in your data, such as a row number. The generator saves a cursor with each chunk through `ctx.stream.withCursor(chunk, cursor)`. This saved position is called a **checkpoint**. After a reconnect, LiveThing runs the generator again. `ctx.stream.cursor` then holds the last checkpoint the client confirmed, so the generator can continue from there. The client gets the rest of the data without gaps.

LiveThing saves checkpoints in the server's SQL storage (the same database as [`ctx.sql`](/server/context-and-storage/sql-and-kv)). Every adapter provides this storage. On Node, the default database is in memory, so give the adapter a file path if checkpoints must survive a server restart.

```typescript [server/rooms.ts]
import { server, t } from '@livething/server'
import { cursorStream } from '@livething/server/streams'
import * as v from 'valibot'

const base = server({
  capabilities: [cursorStream()],
})

export const handleExportRoom = base.cursorStream('export-room', {
  input: v.object({ roomId: v.string() }),
  chunk: t<{ messages: Message[] }>(),
  cursor: t<{ before: number }>(),
  async *run(ctx, input) {
    let before = ctx.stream.cursor?.before ?? Date.now()
    while (true) {
      const messages = await loadMessagesBefore(input.roomId, before)
      const last = messages.at(-1)
      if (!last) return
      before = last.sentAt
      yield ctx.stream.withCursor({ messages }, { before })
    }
  },
})
```

`cursor` is an optional `t<T>()` marker that sets the cursor type only. Pass a schema instead to also check, at runtime, each cursor LiveThing restores after a reconnect. If a restored cursor fails the check, the client gets a `StreamAborted` error with `reason: 'cursor-invalid'`.

A cursor stream needs the `chunk` marker when every chunk goes through `withCursor`. TypeScript cannot infer the chunk type from `withCursor` alone, so without `chunk` the client sees the chunk type as `unknown`.

Each run also gets `ctx.stream.attempt`. It is `1` on the first run and `2` or higher on a run after a reconnect. Use it, for example, to log reconnect runs or to change behavior after a reconnect.

See [Cursor](/server/streams/durable-cursor) for more about restoring the cursor and about durability.

## Recorded streams

`recordedStream()` enables `base.recordedStream(name, { input, maxChunks?, run })`. LiveThing saves each chunk in a buffer when the generator yields it. After a reconnect, the client receives the chunks it missed from the buffer, and the generator does **not** run again. Use a recorded stream for a source you cannot run again from a position, such as the tokens of an AI model. Like checkpoints, the buffer is saved in the server's SQL storage.

```typescript [server/scout.ts]
import { server, t } from '@livething/server'
import { recordedStream } from '@livething/server/streams'
import * as v from 'valibot'

const base = server({
  capabilities: [recordedStream()],
})

export const handleAskScout = base.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ text: string }>(),
  broadcast: true,
  nudges: {
    stop: null,
    redirect: v.object({ instruction: v.string() }),
  },
  async *run(ctx, input) {
    let prompt = input.prompt
    // A model cannot be paused or sped up mid-reply. `stop` ends the stream;
    // `redirect` aborts the current call and starts a new one instead.
    while (true) {
      const controller = new AbortController()
      let reply = ''
      let redirected = false
      for await (const text of llm.stream({
        messages: [{ role: 'user', content: prompt }],
        signal: controller.signal,
      })) {
        reply += text
        const nudges = ctx.stream.nudges(yield { text })
        for (const nudge of nudges) {
          if (nudge.event === 'stop') return
          if (nudge.event === 'redirect') {
            controller.abort()
            prompt = `${reply}\n\n${nudge.payload.instruction}`
            redirected = true
          }
        }
        if (redirected) break
      }
      if (!redirected) return
    }
  },
})
```

The difference from a cursor stream: a cursor stream runs the generator again from the cursor. A recorded stream sends the saved chunks again and never runs the generator again. See [Recorded](/server/streams/durable-recorded) for more about the buffer and `maxChunks`.

`maxChunks` is the most chunks the buffer can hold. When a recorded stream reaches this limit, the next `yield` throws `StreamAborted` into the generator, with `detail.reason === 'buffer-full'`. Catch it to stop the stream cleanly:

```typescript [server/scout.ts]
import { StreamAborted } from '@livething/server/errors'

export const handleAskScout = base.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ text: string }>(),
  maxChunks: 500,
  async *run(ctx, input) {
    for await (const text of llm.stream({
      messages: [{ role: 'user', content: input.prompt }],
      signal: ctx.stream.signal,
    })) {
      try {
        yield { text }
      } catch (err) {
        if (
          StreamAborted.matches(err) &&
          err.detail.reason === 'buffer-full'
        )
          return
        throw err
      }
    }
  },
})
```

## The stream context (`ctx.stream`)

Inside any stream generator, `ctx.stream` holds the controls for the running stream:

::field-group
::field{name="ctx.stream.signal" type="AbortSignal"}
An `AbortSignal` (the standard web object that tells work to stop). It fires when the stream is cancelled, when the client disconnects, or when the server shuts down. Pass it into long awaited work, such as `fetch`, so the generator stops early instead of waiting.
::

::field{name="ctx.stream.drain()" type="() => Promise<void>"}
Waits until the outgoing buffer is below `highWaterMark` again (256 KB by default). Call it after a large yield. This is **backpressure**: the server waits so that it does not send data faster than a slow client can receive it.
::

::field{name="ctx.stream.nudges(yielded)" type="(yielded: unknown) => { event, payload }[]"}
Returns the nudges the client sent since the last yield. Pass it the value of the `yield` expression. It exists only when the stream declares `nudges` (see Nudges below).
::

::field{name="ctx.stream.withCursor(chunk, cursor)" type="(chunk, cursor) => Chunk"}
Saves a cursor with a yielded chunk. Cursor streams only.
::

::field{name="ctx.stream.cursor" type="Cursor | null"}
The last checkpoint the client confirmed, or `null` on the first run. Cursor streams only.
::

::field{name="ctx.stream.attempt" type="number"}
`1` on the first run, `2` or higher on a run after a reconnect. Cursor streams only.
::
::

```typescript [server/scout.ts]
export const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  async *run(ctx, input) {
    for (const hit of await searchMessages(input.query)) {
      yield { hit }
      await ctx.stream.drain() // wait until the client has received the data
      if (ctx.stream.signal.aborted) return // the stream was stopped, so stop early
    }
  },
})
```

### Nudges: messages into a running stream

A **nudge** is a small message the client sends into a stream that is already running, for example "stop" or "show only errors". Declare `nudges` as an object that maps each nudge name to a schema. Use `null` for a nudge with no payload. Inside the generator, `ctx.stream.nudges(yield chunk)` returns the nudges the client sent since the previous yield.

Huddle's admin log uses a nudge to change its filter while it runs. The admin sees fewer lines without restarting the stream:

```typescript [server/admin.ts]
const levels = ['info', 'warn', 'error'] as const

export const handleTailAuditLog = base.stream('tail-audit-log', {
  input: v.object({}),
  chunk: t<{ line: string }>(),
  nudges: {
    'set-level': v.object({ level: v.picklist(levels) }),
  },
  async *run(ctx) {
    let minLevel = 0 // index into `levels`: 0 shows every line
    for await (const entry of auditLogEntries(ctx.stream.signal)) {
      if (levels.indexOf(entry.level) < minLevel) continue
      const nudges = ctx.stream.nudges(yield { line: entry.line })
      for (const nudge of nudges)
        minLevel = levels.indexOf(nudge.payload.level)
    }
  },
})
```

The generator reads nudges only when it yields. Here, a new level takes effect at the next line that passes the current filter.

## The contract slice

Every stream capability adds entries to the `streams` key of the client contract. Each entry has:

- `payload`: the value that starts the stream.
- `chunk`: the type of each chunk the stream yields.
- `kind`: `'ephemeral'` for a plain stream, `'persistent'` for a cursor or recorded stream.
- `nudges`: only on a stream that declares nudges.

```typescript [client/socket.ts]
interface HuddleSocket {
  streams: {
    'search-messages': {
      payload: { query: string }
      chunk: { hit: Message }
      kind: 'ephemeral'
    }
    'export-room': {
      payload: { roomId: string }
      chunk: { messages: Message[] }
      kind: 'persistent'
    }
  }
}
```

## Configuration at a glance

The stream handlers accept more options than `input` and `run`:

::field-group
::field{name="chunk / cursor"}
Default: inferred for `chunk`, `unknown` for `cursor`. Type marker for each chunk, or for the cursor. Without `chunk`, the chunk type is inferred from what `run` yields. Without `cursor`, the cursor type is `unknown`. `chunk` applies to all stream kinds. `cursor` applies to cursor streams only.
::
::field{name="nudges"}
Default: none. Typed messages the client can send into a running stream. Applies to all stream kinds.
::
::field{name="broadcast" type="boolean"}
Default: `false`. Send the stream to many clients instead of one: every connection, or every member of the channel for a channel stream. Applies to all stream kinds.
::
::field{name="allowConcurrent" type="boolean"}
Default: `false`. Allow more than one active stream of this event on one connection. Applies to all stream kinds.
::
::field{name="highWaterMark" type="number"}
Default: 256 KB. Outgoing buffer limit **in bytes**, used by `ctx.stream.drain()`. Applies to all stream kinds.
::
::field{name="onDisconnect" type="'cancel-but-buffer' | 'keep-running'"}
Default: `'cancel-but-buffer'`. What happens when the client drops. `'cancel-but-buffer'` stops the generator and keeps the saved data. `'keep-running'` lets the generator continue. On a cursor stream, `'keep-running'` requires `broadcast: true`, or `base.cursorStream()` throws. Applies to cursor and recorded streams.
::
::field{name="maxAgeMs" type="number"}
Default: 5 minutes. How long LiveThing keeps a stopped stream after the client drops. Applies to cursor and recorded streams.
::
::field{name="retentionAfterEndMs" type="number"}
Default: 30 seconds. How long LiveThing keeps a finished stream, so a client that reconnects quickly can still continue it. Applies to cursor and recorded streams.
::
::field{name="maxChunks" type="number"}
Default: `500`. The most chunks the buffer can hold. Applies to recorded streams only.
::
::

For how each option behaves (broadcast, backpressure and drain, the durable lifecycle), see [Configuration & Lifecycle](/server/streams/config-and-lifecycle) and [Broadcast](/server/streams/broadcast).

## Channel streams

A channel can have any of these stream kinds, with `.stream`, `.cursorStream`, and `.recordedStream`. Each one needs the matching stream capability in `capabilities`. Without it, the method does not exist on the channel type, and calling it throws an error that names the capability to add. See [Scoped Streams & Requests](/server/channels/scoped-streams-requests).
