A **stream** sends data from the server to the client in pieces, one piece at a time, instead of all at once. Each piece is called a **chunk**. Examples are the tokens of an AI answer, the rows of a query, a live feed, or the pieces of a file. LiveThing has two stream capabilities. You import both from `@livething/server/streams`:

```typescript [server/huddle-definition.ts]
import { recordedStream, stream } from '@livething/server/streams'
```

Each one enables a different handler. They also differ in what happens when the client disconnects. This page shows how to enable each kind, what each kind is, and how it appears in the client contract. For the full behavior (durability, broadcast, backpressure, lifecycle), follow the links to the [Streams](/server/streams/overview) chapter.

## Plain streams

`stream()` enables `base.stream(name, { input, chunk?, run })`. `run` is an async generator (an `async function*` that can `yield` many values over time). Each value it yields is sent to the client as one chunk. A plain stream is **ephemeral**: it stops when the client disconnects and does not continue after a reconnect. Here a version of Huddle's `search-messages` also sets `allowConcurrent: true` (Huddle's own does not), so one connection can run several searches at once:

```typescript [server/search.ts]
import { server, t } from '@livething/server'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'
import { searchMessages } from './huddle-data'
import type { Message } from './base'

const base = server({
  capabilities: [stream()],
})

export const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  chunk: t<{ hit: Message }>(),
  allowConcurrent: true,
  async *run(ctx, input) {
    for await (const hit of searchMessages(input.query)) {
      yield { hit }
    }
  },
})
```

::note
Every stream builder returns a handler value. Pass `handleSearchMessages` (and every recorded stream value) to `base.assemble({ handlers: [...] })`. Only then does the stream run and appear in `InferClient`.
::

`chunk` is an optional `t<T>()` marker. A marker gives a type only and runs no check. It sets the type of each yielded chunk. If you leave it off, LiveThing infers the chunk type from what `run` yields.

See [Plain Streams](/server/streams/plain) for the full plain-stream behavior. When the data can start again from a position (database pages, a row ID), give the plain stream a `before` or `after` field in its input, and let the client start a new stream from the last item it got after a drop. See [Starting again from a position](/server/streams/plain#starting-again-from-a-position).

## Recorded streams

`recordedStream()` enables `base.recordedStream(name, { input, maxChunks?, run })`. LiveThing saves each chunk in a buffer when the generator yields it. The generator keeps running when the client drops. After a reconnect, the client receives the chunks it missed from the buffer, then the live chunks. Use a recorded stream for a source you cannot run again from a position, such as the tokens of an AI model. The buffer is saved in the server's SQL storage (the same database as [`ctx.sql`](/server/context-and-storage/sql-and-kv)). Every adapter provides this storage. On Node, the default database is in memory, so give the adapter a file path if streams must survive a server restart.

This is a smaller version of Huddle's `ask-scout`. Huddle puts it on the `rooms` channel, so the whole room sees the reply. Here it is on `base`, to keep the example about streams:

```typescript [server/scout.ts]
import { server, t } from '@livething/server'
import { recordedStream } from '@livething/server/streams'
import * as v from 'valibot'
import { llm } from './llm'

const base = server({
  capabilities: [recordedStream()],
})

export const handleAskScout = base.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ text: string }>(),
  broadcast: true,
  nudges: {
    stop: null,
    redirect: v.object({ instruction: v.string() }),
  },
  async *run(ctx, input) {
    let prompt = input.prompt
    // A model cannot be paused or sped up mid-reply. `stop` ends the stream;
    // `redirect` aborts the current call and starts a new one instead.
    while (true) {
      const controller = new AbortController()
      let reply = ''
      let redirected = false
      for await (const text of llm.stream({
        messages: [{ role: 'user', text: prompt }],
        signal: controller.signal,
      })) {
        reply += text
        const nudges = ctx.stream.nudges(yield { text })
        for (const nudge of nudges) {
          if (nudge.event === 'stop') return
          if (nudge.event === 'redirect') {
            controller.abort()
            prompt = `${reply}\n\n${nudge.payload.instruction}`
            redirected = true
          }
        }
        if (redirected) break
      }
      if (!redirected) return
    }
  },
})
```

If the generator stops before it finishes (it throws, or the server restarts while it runs), a client that continues the stream gets the saved chunks and then a `StreamAborted` error with `reason: 'interrupted'`. See [Recorded](/server/streams/durable-recorded) for more about the buffer, `maxChunks`, and interrupted streams.

`maxChunks` is the most chunks the buffer can hold. When a recorded stream reaches this limit, the next `yield` throws `StreamAborted` into the generator, with `detail.reason === 'buffer-full'`. Catch it to stop the stream cleanly. Huddle's `ask-scout` keeps the default of 500 chunks. This version sets a lower limit so that it can reach the end of the buffer:

```typescript [server/scout.ts]
import { t } from '@livething/server'
import { StreamAborted } from '@livething/server/errors'
import * as v from 'valibot'
import { base } from './base'
import { llm } from './llm'

export const handleAskScout = base.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ text: string }>(),
  maxChunks: 200,
  async *run(ctx, input) {
    for await (const text of llm.stream({
      messages: [{ role: 'user', text: input.prompt }],
      signal: ctx.stream.signal,
    })) {
      try {
        yield { text }
      } catch (err) {
        if (
          StreamAborted.matches(err) &&
          err.detail.reason === 'buffer-full'
        )
          return
        throw err
      }
    }
  },
})
```

## The stream context (`ctx.stream`)

Inside any stream generator, `ctx.stream` holds the controls for the running stream:

::field-group
::field{name="ctx.stream.signal" type="AbortSignal"}
An `AbortSignal` (the standard web object that tells work to stop). It fires when the stream is cancelled, when the client leaves the stream's channel, or when the server shuts down. On a plain stream it also fires when the client disconnects. A recorded stream keeps running after a disconnect. Pass it into long awaited work, such as `fetch`, so the generator stops early instead of waiting.
::

::field{name="ctx.stream.drain()" type="() => Promise<void>"}
Waits until the outgoing buffer is below 256 KB again. Call it after a large yield. This is **backpressure**: the server waits so that it does not send data faster than a slow client can receive it.
::

::field{name="ctx.stream.nudges(yielded)" type="(yielded: unknown) => { event, payload }[]"}
Returns the nudges the client sent since the last yield. Pass it the value of the `yield` expression. It exists only when the stream declares `nudges` (see Nudges below).
::
::

This version of `search-messages` waits for the client between hits:

```typescript [server/search.ts]
import * as v from 'valibot'
import { base } from './base'
import { searchMessages } from './huddle-data'

export const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  async *run(ctx, input) {
    for await (const hit of searchMessages(input.query)) {
      yield { hit }
      await ctx.stream.drain() // wait until the client has received the data
      if (ctx.stream.signal.aborted) return // the stream was stopped, so stop early
    }
  },
})
```

### Nudges: messages into a running stream

A **nudge** is a small message the client sends into a stream that is already running, for example "stop" or "show only errors". Declare `nudges` as an object that maps each nudge name to a schema. Use `null` for a nudge with no payload. Inside the generator, `ctx.stream.nudges(yield chunk)` returns the nudges the client sent since the previous yield.

Huddle's admin log uses a nudge to change its filter while it runs. The admin sees fewer lines without restarting the stream. This is a smaller version of Huddle's `tail-audit-log`, with only the `set-level` nudge:

```typescript [server/tail-audit-log.ts]
import { t } from '@livething/server'
import * as v from 'valibot'
import { auditLogEntries } from './audit-log'
import { base } from './base'

const levels = ['info', 'warn', 'error'] as const

export const handleTailAuditLog = base.stream('tail-audit-log', {
  input: v.object({}),
  chunk: t<{ line: string }>(),
  nudges: {
    'set-level': v.object({ level: v.picklist(levels) }),
  },
  async *run(ctx) {
    let minLevel = 0 // index into `levels`: 0 shows every line
    for await (const entry of auditLogEntries(ctx.stream.signal)) {
      if (levels.indexOf(entry.level) < minLevel) continue
      const nudges = ctx.stream.nudges(yield { line: entry.line })
      for (const nudge of nudges)
        minLevel = levels.indexOf(nudge.payload.level)
    }
  },
})
```

The generator reads nudges only when it yields. Here, a new level takes effect at the next line that passes the current filter.

## Streams that carry bytes

With [`binary()`](/server/capabilities/binary) listed, `stream()` also enables `base.binary.stream(...)` and a channel's `.binary.stream(...)`. Each chunk is `{ info, bytes }` and goes out as one binary message. Huddle's `download-attachment` sends a file in pieces this way. The other stream frames are text, and `ctx.stream` works as above. `recordedStream()` enables `base.binary.recordedStream(...)` and a channel's `.binary.recordedStream(...)` in the same way: each chunk is stored with its bytes, as in Huddle's `export-room-pdf`. See [Binary streams](/server/capabilities/binary#binary-streams).

## The contract slice

Every stream capability adds entries to the `streams` key of the client contract. Each entry has:

- `payload`: the value that starts the stream.
- `chunk`: the type of each chunk the stream yields.
- `kind`: `'ephemeral'` for a plain stream, `'persistent'` for a recorded stream.
- `nudges`: only on a stream that declares nudges.

```typescript [shape]
import type { Message } from '../server/base'

interface HuddleSocket {
  streams: {
    'search-messages': {
      payload: { query: string }
      chunk: { hit: Message }
      kind: 'ephemeral'
    }
    'ask-scout': {
      payload: { prompt: string }
      chunk: { text: string }
      kind: 'persistent'
      nudges: { stop: undefined; redirect: { instruction: string } }
    }
  }
}
```

## Configuration at a glance

The stream handlers accept more options than `input` and `run`:

::field-group
::field{name="chunk"}
Default: inferred. Type marker for each chunk. Without `chunk`, the chunk type is inferred from what `run` yields. Applies to all stream kinds.
::
::field{name="nudges"}
Default: none. Typed messages the client can send into a running stream. Applies to all stream kinds.
::
::field{name="broadcast" type="boolean"}
Default: `false`. Send the stream to many clients instead of one: every connection, or every member of the channel for a channel stream. Applies to all stream kinds.
::
::field{name="allowConcurrent" type="boolean"}
Default: `false`. Allow more than one active stream of this event on one connection. Applies to all stream kinds.
::
::field{name="maxAgeMs" type="number"}
Default: 5 minutes. How long LiveThing keeps a stream whose generator stopped mid-stream (for example after a server restart), so a reconnecting client can still get its chunks and learn it was interrupted. Applies to recorded streams only.
::
::field{name="retentionAfterEndMs" type="number"}
Default: 30 seconds. How long LiveThing keeps a finished stream, so a client that reconnects quickly can still continue it. Applies to recorded streams only.
::
::field{name="maxChunks" type="number"}
Default: `500`. The most chunks the buffer can hold. Applies to recorded streams only.
::
::field{name="maxBufferBytes" type="number"}
Default: 64 MiB. The most bytes the buffer can hold: each chunk as JSON, plus the bytes of a binary chunk. Applies to recorded streams only.
::
::

For how each option behaves (broadcast, backpressure and drain, the durable lifecycle), see [Configuration & Lifecycle](/server/streams/config-and-lifecycle) and [Broadcast](/server/streams/broadcast).

## Channel streams

A channel can have both stream kinds, with `.stream` and `.recordedStream`. Each one needs the matching stream capability in `capabilities`. Without it, the method does not exist on the channel type, and calling it throws an error that names the capability to add. See [Scoped Streams & Requests](/server/channels/scoped-streams-requests).
