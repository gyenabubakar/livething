A **tag** is a label that you attach to a connection. When a connection has a tag, you can find every connection with that same tag, count them, or broadcast an event to all of them at once. With tags, you address connections by who they are (`role:admin`) or by what they care about (`topic:billing`). You do not have to keep your own list of socket IDs.

You declare named **groups** first, for example `role` and `team`. Each group holds a set of string **keys** for each connection. LiveThing groups connections by three values together: the kind (ephemeral or persistent, explained below), the group, and the key. For example, every connection that added the key `admin` under the ephemeral `role` group is one set that you can address.

## What you get

- A typed `ctx.tags` object inside handlers. You use it to add, remove, and count tags, and to send to every connection with a tag.
- Optional initial tags that you return from `upgrade(...)` when the connection opens.
- Two storage kinds: **ephemeral** (kept in memory) and **persistent** (saved in the server's SQL storage). The kind decides how long a tag lives.

Tags add nothing to the client contract. They exist only on the server, to group connections. They are not wire messages. The client never sees them, and `InferClient` gives the same client type with or without tags.

## Enable it

Import `tags` from `@livething/server/tags` and list it in `capabilities`. The `tags` function takes one callback. The callback receives two builder functions, `ephemeral` and `persistent`. Each call to a builder declares one group. The callback returns an array with every group.

```typescript [server/huddle.ts]
import { server, t } from '@livething/server'
import { tags } from '@livething/server/tags'
import * as v from 'valibot'

const base = server({
  capabilities: [
    tags((ephemeral) => [
      ephemeral('role', v.picklist(['admin', 'member', 'guest'])),
      ephemeral('team', t<string>()),
    ]),
  ],
})
```

Each builder call is `ephemeral(name, type?)` or `persistent(name, type?)`. The optional second argument sets the type of the keys in that group:

- A `t<T>()` marker sets the key type at compile time only. It adds no runtime cost, and no validation runs.
- A Standard Schema (a validator from a library such as Valibot or Zod, for example `v.picklist([...])`) sets the key type **and** validates the key on every `add()`.

In the example above, `team` accepts any string. `role` throws a `ValidationFailed` error when you add a key other than `'admin'`, `'member'`, or `'guest'`.

## Configuration

The callback returns an array of group declarations. Each declaration comes from one of the two builders:

| Builder                   | What it declares   | How long a tag lives                                                   | Needs         |
| ------------------------- | ------------------ | ---------------------------------------------------------------------- | ------------- |
| `ephemeral(name, type?)`  | An in-memory group | Survives a hibernation wake on the same socket. Removed on disconnect. | nothing extra |
| `persistent(name, type?)` | A saved group      | Saved by user ID. Survives disconnect, reconnect, and server restarts. | nothing extra |

The `type?` argument on either builder:

| `type?` argument                                    | Effect                                                                |
| --------------------------------------------------- | --------------------------------------------------------------------- |
| omitted                                             | Keys have the type `string`. No runtime validation.                   |
| `t<T extends string>()`                             | Keys have the type `T`. No runtime validation.                        |
| a Standard Schema (for example `v.picklist([...])`) | Keys get their type from the schema **and** are validated on `add()`. |

### Ephemeral vs persistent

The two kinds differ only in how long a tag lives:

- **Ephemeral** tags live in memory for the connection. They survive a [hibernation](/server/server/hibernation) wake on the same socket. When the connection disconnects, its ephemeral tags are removed. Use them for labels that only matter during this session, for example this connection's role, or which team it belongs to.
- **Persistent** tags are saved in SQL storage under the connection's `userId`. They survive a disconnect and reconnect, and they survive server restarts. Use them for a label that should come back when the user connects again, for example a saved preference like `starred-room`.

A persistent tag is saved only when the connection has a `userId`. On an anonymous connection (one where `upgrade(...)` returned no `userId`), `persistent(group).add(key)` tags only that connection, and the tag is removed when it disconnects.

You can declare the same group name in both kinds. `ephemeral('role')` and `persistent('role')` are two separate groups. If you declare the same name twice in the _same_ kind, `tags(...)` throws an error. A group name must be a non-empty string, and it cannot start or end with `__`.

### Removing a persistent group

The saved rows of a `persistent(...)` group stay in the `__livething_tags` table after you remove that group from the `tags(...)` declaration. LiveThing removes these old rows for you. Each time a connection connects (or wakes from hibernation), LiveThing reads that user's saved rows and checks each one:

- If the row's group is no longer declared, LiveThing does not add the tag to the connection, and it deletes the row from `__livething_tags`. The row does not come back on later connects.
- If the group is still declared and has a schema, LiveThing validates the saved key. A key that fails the schema is also deleted and not restored.
- Every other row is restored onto the connection.

LiveThing cleans up one user at a time: each affected user's old rows are deleted the next time that user connects. You do not need a migration step to remove a persistent group from a live server.

## The `ctx.tags` object

When you list `tags(...)`, every handler gets `ctx.tags`. Two of its methods return a group handle (an object that acts on one group):

```typescript [server/handlers.ts]
const handleJoinTeam = base.on('join-team', {
  input: v.object({ team: v.string() }),
  run(ctx, input) {
    const team = ctx.tags.ephemeral('team') // a TagGroupHandle
    team.add(input.team)
  },
})
```

A group name that you did not declare is a **type error**. `ephemeral(...)` accepts only declared ephemeral names, and `persistent(...)` accepts only declared persistent names.

### Group handle methods

`ctx.tags.ephemeral(group)` and `ctx.tags.persistent(group)` return a `TagGroupHandle`. Some methods act on the current connection (the connection that is running the handler). The others act on every connection on this server instance (one running copy of your server).

| Method                       | Returns             | What it does                                                               |
| ---------------------------- | ------------------- | -------------------------------------------------------------------------- |
| `.add(key)`                  | `void`              | Adds `key` to the current connection under this group                      |
| `.remove(key)`               | `void`              | Removes `key` from the current connection                                  |
| `.has(key)`                  | `boolean`           | Whether the current connection has `key`                                   |
| `.list()`                    | `readonly TagRef[]` | The current connection's keys under this group                             |
| `.keys()`                    | `readonly string[]` | Every key in use under this group, across all connections on this instance |
| `.connections()`             | `ConnectionInfo[]`  | A snapshot of every connection that has any key in this group              |
| `.count()`                   | `number`            | The number of different connections that have any key in this group        |
| `.broadcast(event, payload)` | `void`              | Sends an event to every connection that has any key in this group          |
| `.ref(key)`                  | `TagRefHandle`      | A handle for one exact kind, group, and key                                |

An empty string key does nothing: `.add('')` and `.ref('').broadcast(...)` have no effect. So a `t<string>()` group can never create an empty `""` tag.

A tag broadcast also reaches the current connection when it has the tag. This is different from `ctx.broadcast(...)`, which skips the calling connection by default.

### Ref handle methods

`.ref(key)` narrows the handle from the whole group to one exact key. The returned `TagRefHandle` has the data fields `kind`, `group`, and `key`, plus methods that act on the connections with that one tag:

| Method                       | Returns            | What it does                                                                 |
| ---------------------------- | ------------------ | ---------------------------------------------------------------------------- |
| `.broadcast(event, payload)` | `void`             | Sends to every connection on this instance with this exact tag               |
| `.connections()`             | `ConnectionInfo[]` | A snapshot of those connections                                              |
| `.count()`                   | `number`           | How many connections have this exact tag                                     |
| `.has(ref)`                  | `boolean`          | Whether the connection that `ref` (a `ConnectionRef`) points to has this tag |

You can pass a `TagRefHandle` anywhere a plain `TagRef` is accepted, for example to a channel handle's `kick(...)`. LiveThing reads only its `kind`, `group`, and `key` fields.

### Listing every tag on the connection

`ctx.tags.list()` returns every tag ref on the current connection, across all groups and both kinds. Each ref has `kind`, `group`, and `key`:

```typescript [server/handlers.ts]
const handleListMyTags = base.on('list-my-tags', {
  input: v.object({}),
  run(ctx) {
    const mine = ctx.tags.list().map((ref) => ({
      kind: ref.kind,
      group: ref.group,
      key: ref.key,
    }))
    ctx.log.info('current tags', { mine })
  },
})
```

## A handler that uses ref, broadcast, and count

A handler can address everyone with a tag and report how many connections have it:

```typescript [server/handlers.ts]
import { emits, server, t } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import { tags } from '@livething/server/tags'
import * as v from 'valibot'

const base = server({
  capabilities: [
    tags((ephemeral) => [
      ephemeral('role', v.picklist(['admin', 'member', 'guest'])),
    ]),
    clientRequests(),
    emits({
      announcement: t<{ text: string }>(),
      notification: t<{ title: string; body: string }>(),
    }),
  ],
})

// Send one event to everyone with role:admin.
const handleAnnounceToAdmins = base.on('announce-to-admins', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.tags
      .ephemeral('role')
      .ref('admin')
      .broadcast('announcement', {
        text: input.text,
      })
  },
})

// Count how many admins are online right now.
const handleCountAdmins = base.request('count-admins', {
  input: v.object({}),
  run(ctx) {
    return { count: ctx.tags.ephemeral('role').ref('admin').count() }
  },
})
```

## Initial tags from `upgrade`

You can attach **ephemeral** tags when a connection opens. Return them from `upgrade(...)` under `tags.ephemeral`, as an object with one entry per group: `{ group: key }`.

```typescript [server/upgrade.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'
import { tags } from '@livething/server/tags'
import * as v from 'valibot'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
      tags: { ephemeral: { role: user.role } },
    }
  },
  capabilities: [
    tags((ephemeral) => [
      ephemeral('role', v.picklist(['admin', 'member', 'guest'])),
    ]),
  ],
})
```

Only declared ephemeral group names are accepted here, and only one key per group. You cannot set persistent tags from `upgrade(...)`. Add them inside a handler with `ctx.tags.persistent(group).add(key)`.

## With `serverRequests()`: send a request to a tag

If you also list `serverRequests()`, the group handle and the ref handle both get `.broadcastRequest(event, payload)`. It sends a server request to every connection in that set. It resolves with the first valid answer as `{ response, from }`, where `from` is the `ConnectionRef` of the connection that answered:

```typescript [server/rooms.ts]
import { emits, server, t } from '@livething/server'
import { serverRequests } from '@livething/server/server-requests'
import { tags } from '@livething/server/tags'
import * as v from 'valibot'

const base = server({
  capabilities: [
    tags((ephemeral) => [
      ephemeral('role', v.picklist(['admin', 'member', 'guest'])),
    ]),
    serverRequests({
      'approve-room-upgrade': {
        out: t<{ roomId: string; requestedLimit: number }>(),
        in: v.object({ approved: v.boolean() }),
      },
    }),
    emits({
      notification: t<{ title: string; body: string }>(),
    }),
  ],
})

const handleRequestRoomUpgrade = base.on('request-room-upgrade', {
  input: v.object({ roomId: v.string(), requestedLimit: v.number() }),
  async run(ctx, input) {
    // Every online admin gets the question. The first valid answer wins.
    const { response, from } = await ctx.tags
      .ephemeral('role')
      .ref('admin')
      .broadcastRequest('approve-room-upgrade', {
        roomId: input.roomId,
        requestedLimit: input.requestedLimit,
      })
    ctx.send('notification', {
      title: 'Room upgrade',
      body: response.approved
        ? `approved by ${from.userId}`
        : 'not approved',
    })
  },
})
```

When you do not list `serverRequests()`, the handles have no `.broadcastRequest`, and calling it is a type error. See [serverRequests](/server/capabilities/server-requests) for the full request model.

## SQLite table

The rows of a `persistent(...)` group are saved in `__livething_tags`, a table in the server's own SQL storage. Ephemeral groups never use this table. They exist only in memory. The table name starts with the reserved `__livething_` prefix. Never create a table with this name yourself, even before you add `tags(...)`. LiveThing creates the table only if it does not exist, so no error tells you about the name clash. See the [full list of reserved tables](/server/context-and-storage/sql-and-kv#reserved-livething-tables) for every table LiveThing owns.

| Column       | Type      | Notes                                                                   |
| ------------ | --------- | ----------------------------------------------------------------------- |
| `user_id`    | `TEXT`    | The connection's user ID. Part of the primary key.                      |
| `group_name` | `TEXT`    | The `persistent(...)` group name. Part of the primary key.              |
| `key`        | `TEXT`    | The tag key added under that group. Part of the primary key.            |
| `added_at`   | `INTEGER` | When the tag was added, as a Unix time in milliseconds.                 |
| `metadata`   | `TEXT`    | Reserved JSON field for later use. LiveThing does not read or write it. |

The primary key is `(user_id, group_name, key)`. So when you add the same key twice for the same user and group, the table still has one row.
