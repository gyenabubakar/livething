A **capability** is an opt-in feature you turn on for a server by listing it in `define({ capabilities: [...] })`. Emitting events, typed errors, requests, streams, channels, dedup, rate limiting — each one is a capability. You add the ones your app needs and leave the rest out.

## What a capability is

When you call `define`, you hand it your environment type and an array of capabilities:

```typescript [chat.ts]
import { define, emits, errors, t } from '@wskit/server'
import { requests } from '@wskit/server/requests'

const base = define({
  env: t<Env>(),
  capabilities: [
    emits({ message: t<{ text: string; from: string }>() }),
    requests(),
    errors([NotFound]),
  ],
})
```

Listing a capability pulls in its engine code. Leaving it out costs nothing — its code never reaches your bundle. This is the whole point: **you pay for what you use.** A tiny app that only pushes events lists `emits` and nothing else, and never ships the request, stream, or channel machinery.

::note
The capability array is the single switch. There is no global config flag and no "enable everything" mode. If a feature is not in the array, the methods it would add are not on `ctx`, and the keys it would add are not on the client contract.
::

## How capabilities shape your app

A capability contributes to one or both of two places:

- The **client contract** — the type `InferClient<typeof handler>` produces. Adding `emits` fills the client's `incoming` key; adding `errors` fills its `errors` key; adding `channels` fills its `channels` key, and so on. The client gains the matching typed methods with no extra work. See [The Contract](/learn/the-contract) for how the contract flows from server to client.
- The handler **`ctx`** — the context object your handlers receive. Adding `tags` puts `ctx.tags` on it; adding `channels` puts `ctx.channels` and channel methods on it. A capability you did not list is simply not there.

| [dedup](/server/capabilities/dedup)           | `@wskit/server/dedup`      | Drop duplicate incoming messages                                                                                     |
| [sequence](/server/capabilities/sequence)     | `@wskit/server/sequence`   | Number outgoing messages so the client can detect gaps                                                               |
| [replay](/server/capabilities/replay)         | `@wskit/server/replay`     | Re-send missed messages on reconnect — `replay.history`, `replay.snapshot`, `replay.custom`                          |
| [rateLimit](/server/capabilities/rate-limit)  | `@wskit/server/rate-limit` | Throttle how fast a connection can send                                                                              |

The top-level imports (`emits`, `errors`) come straight from `@wskit/server`. Everything else lives behind its own subpath so it tree-shakes cleanly.

Two capabilities are not in this table because they never go in `define({ capabilities: [...] })` — they go inside a channel's own `capabilities` list instead: [inbox](/server/capabilities/inbox) and [readReceipts](/server/capabilities/read-receipts). See [Channels](/server/capabilities/channels#capabilities-a-channel-may-need) for how a channel opts into them.

## Capabilities that plugins cannot list :badge[host-only]

Some capabilities own connection-wide state that belongs to the whole server, not to a single feature. These are **host-only**: `keepalive`, `dedup`, `sequence`, `rateLimit`, and the `replay.*` family. You cannot list them inside a plugin's scoped handler — a `define({ scope: 'plugin' })` — because a plugin is meant to be a self-contained add-on, and these reach across the entire connection.

If a plugin needs one of these, it declares a dependency on the host instead of listing the capability itself. See [Depending on host capabilities](/server/plugins/depends-on).

## Requirements checked at assemble

A few capabilities need others to be listed too. The check runs when you call `assemble()`, and a missing prerequisite is a build error that names exactly what to add:

- **Built-in replay** (`replay.history()` and `replay.snapshot()`) needs `dedup()` and `sequence({ persist: true })` — it re-sends by sequence number, so both have to be on and the sequence has to be durable. `replay.custom()` owns its own storage and resend, so it needs neither.
- **A channel's `inbox()`** (listed in the channel's own `capabilities`) needs `channels()`, `sequence({ persist: true })`, and `dedup()` on the host. **`readReceipts()`** needs `inbox()` on the same channel. See [Channels](/server/capabilities/channels#capabilities-a-channel-may-need).

```typescript [server.ts]
import { define, t } from '@wskit/server'
import { dedup } from '@wskit/server/dedup'
import { replay } from '@wskit/server/replay'
import { sequence } from '@wskit/server/sequence'

const base = define({
  env: t<Env>(),
  capabilities: [dedup(), sequence({ persist: true }), replay.history()],
})
```

There is one exception on a plugin's scoped handler: when the plugin uses something that needs a host-owned prerequisite, that prerequisite is recorded as a dependency on the host automatically — you do not re-list it inside the plugin.
