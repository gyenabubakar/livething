The admin surface lives on the **live service** — the thing that actually holds your connections, storage, and running engine. How your outside code gets to it depends on the runtime, but the operations are the same.

## Cloudflare Durable Objects

A Durable Object is only reachable through a Worker, so the admin surface is an RPC method on the DO. Your Worker calls `admin()` on the stub, then the operation on the result:

```typescript [worker.ts]
export default {
  async fetch(request: Request, env: Env) {
    const url = new URL(request.url)

    if (url.pathname === '/webhooks/clerk') {
      const event = await verifyClerkWebhook(request)

      if (event.type === 'user.deleted') {
        const id = env.CHAT_DO.idFromName('global')
        const admin = await env.CHAT_DO.get(id).admin()
        await admin.purgeUser(event.data.id)
      }

      return new Response('ok')
    }

    // ...your normal WebSocket upgrade route
  },
}
```

Your Worker is already your HTTP boundary, so your own auth — signature checks, an IP allowlist, whatever — gates the route before it reaches `admin()`. WSKit does not add an auth layer of its own; see [Auth is your boundary](#auth-is-your-boundary) below.

::warning
Export your Durable Object with a **class declaration**, not `export const`:

```typescript [worker.ts]
export class ChatRoom extends server(chatHandler) {}
```

`wrangler types` generates `DurableObjectNamespace<import("./worker").ChatRoom>`, which needs a **type** named `ChatRoom`. `export const ChatRoom = server(chatHandler)` exports only a value, so that reference has no type to find and the binding quietly becomes `any` — every `stub.admin()`, `stub.shutdown()`, and `stub.fetch()` call then goes completely unchecked.
::

### What crosses the stub

A Worker and a Durable Object are separate processes, so a call between them is **RPC** (remote procedure call): the arguments and the result are copied across, and only _methods_ are callable. That means the admin context's grouped objects — `ctx.connections`, `ctx.users`, `ctx.channels` — cannot travel as-is. On Cloudflare they arrive as flat methods instead, one per operation:

| Inside your `api`, in the DO          | On the Worker's stub                      |
| ------------------------------------- | ----------------------------------------- |
| `ctx.connectionCount`                 | `admin.connectionCount()`                 |
| `ctx.connections.all()`               | `admin.listConnections()`                 |
| `ctx.connections.get(ref).send(…)`    | `admin.sendToConnection(connectionId, …)` |
| `ctx.users.get(id).send(…)`           | `admin.sendToUser(userId, …)`             |
| `ctx.users.get(id).close(…)`          | `admin.closeUser(userId, …)`              |
| `ctx.channels.get(name).broadcast(…)` | `admin.channelBroadcast(name, …)`         |
| `ctx.channels.get(name).members()`    | `admin.channelMembers(name)`              |
| `ctx.channels.get(name).kick(…)`      | `admin.channelKick(name, target, opts)`   |

```typescript [worker.ts]
const admin = await env.CHAT_DO.get(id).admin()

const live = await admin.connectionCount()
await admin.sendToUser('user_9', 'notice', { text: 'your export is ready' })
await admin.channelBroadcast('lobby', 'notice', { text: 'maintenance in 5m' })

// A user-ref target is plain data at the RPC boundary. An omitted `instance`
// means the DO that owns this admin surface; an explicit other instance is
// rejected rather than routed accidentally.
await admin.channelKick(
  'lobby',
  { __wskit: 'user-ref', id: 'user_9', instance: undefined },
  { reason: 'removed by a moderator', revoke: true },
)

// A dynamic channel takes its family and instance name together.
await admin.channelBroadcast(
  { family: 'rooms', instance: 'rooms:42' },
  'notice',
  { text: 'closing' },
)
```

Two things follow from the copying. Every call returns a promise, even one whose operation returns nothing. And `listConnections()` / `channelMembers()` give you plain data — the same fields as a [`ConnectionInfo`](/server/context-and-storage/connections) minus its `ref()` method, since a method cannot be copied. Use the `id` you get back with `sendToConnection`, which resolves the reference inside the DO for you.

Storage and the rest of the plumbing (`sql`, `kv`, `env`, `schedule`) stay off the stub entirely. They are there for your `api` methods to use **inside** the Durable Object, which is where your code already runs.

## Bun, Node, and Deno

The service object returned by `server(handler, options)` runs in the same process as your HTTP server. Keep the reference and call `admin()` from any other route:

```typescript [server.ts]
import { server } from '@wskit/server-bun'
import { handler } from './handler'

const service = server(handler, { port: 3000 })

app.post('/webhooks/clerk', async (c) => {
  const event = await verifyClerkWebhook(c.req)
  if (event.type === 'user.deleted') {
    await service.admin().purgeUser(event.data.id)
  }
  return c.text('ok')
})
```

There is no stub here — the engine is right there in memory, so `service.admin()` is a plain in-process call. Nothing is copied across a process boundary, so you get the **whole admin context**, exactly as your `api` methods see it: `service.admin().connections.all()`, `service.admin().users.get(id).send(…)`, `service.admin().connectionCount`. The flat method names in the table above are specific to Cloudflare's RPC and are not needed here.

## Auth is your boundary

Admin operations skip the WebSocket protocol entirely. They do not run `upgrade`, a channel's `check` / `commit` gate, or any guard that protects client traffic — your host code is fully trusted by the engine.

So **gating the routes that call `admin()` is your job**. On Cloudflare, only your Worker can reach the DO, and your Worker route is where you verify the webhook signature or check the token. On Bun / Node / Deno, the call happens inside your own HTTP server, where your existing auth middleware already runs.
