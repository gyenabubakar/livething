`binary()` turns on **binary messages**. A JSON payload is fine for text and small data, but a picture or a file is bytes. Putting bytes in JSON (as base64 text, for example) makes them about a third bigger, and costs time to turn them back. A binary message carries the bytes as they are.

Each binary message has two parts:

- The **info** is JSON, such as the type of a file or who sent it. It works like any payload: a schema can check it, and its type comes from a `t<Shape>()` marker. It is an object, or `null` when there is nothing to say.
- The **bytes** are the data itself. No schema checks them. They can be anything: a picture, a sound, a file, or your own format.

The info always comes before the bytes, in handlers and in senders.

To turn binary on and see its size limits, see the [binary](/server/capabilities/binary) capability.

## Replay

[Replay](/server/replay/overview#binary-events) stores binary events like JSON events, with their bytes, and a client that reconnects gets each missed one back as one binary frame, in sequence order with the JSON events. Two limits are special to binary:

- Only `replay.history()` stores binary events. `replay.snapshot()` fails at startup when a binary event would go into its store, unless the event is in `exclude`.
- A message bigger than one row of the adapter's SQL storage is sent live but not stored. On Cloudflare that limit is 8 MB.

To [send one binary event again](/server/replay/history-and-snapshot#resending-a-binary-event) yourself, use `ctx.binary.sendReplay()`, or `ctx.channel.binary.sendReplay()` in a channel handler. Both take the event, the info, the bytes and a `wire` object.

## Inbox

A channel with [`inbox()`](/server/inbox/overview#binary-events) can list binary events. Each member gets a stored copy of each binary broadcast, with its bytes, and a member who was away gets it as one binary frame, in sequence order with the JSON messages. Huddle's `dms` channel sends voice notes this way.

An inbox promises each member every message, so a message it cannot store goes to **nobody**, not even the members who are online. That is a message bigger than one row of the adapter's SQL storage, bigger than the adapter's send limit, or bigger than the inbox's `retention.maxBytes` on its own. The server logs an error, once for each event and limit. A channel with binary events gets `retention.maxBytes` of 64 MiB per member when it sets none, and the channel's [`inbox.binary.backfill()`](/server/inbox/delivery#backfilling-binary-messages) seeds a member's inbox with binary messages.

On the client, the [`binary()`](/client/primitives/binary) primitive of `@livething/client` uses everything on this page: `binary.on` and `binary.send` for events, `binary.request` for binary requests, `binary.stream`, `binary.onStream` and `binary.continueStream` for binary streams, and `binary.onRequest` to answer binary server requests. With the [`uploads()`](/client/primitives/uploads) primitive, `binary.upload` sends a file to an [upload handler](/server/binary/uploads).

## The contract slice

`InferClient` adds a `binary` key to the client contract for each scope with binary events, requests or streams. Each entry has the type of the info, because the bytes are always bytes:

- `incoming` holds the events the client receives, and `outgoing` the events it sends.
- `clientRequests` holds the binary requests the client sends: `payload` is the info it sends, and `response` the info of the reply.
- `serverRequests` holds the binary requests the server sends: `payload` is the info the client gets, and `response` the info of its answer.
- `streams` holds the binary streams: `payload` is the info that starts the stream, and `chunk` the info of each chunk. `kind` is `'persistent'` for a recorded binary stream, and `'ephemeral'` for the others.
- `uploads` holds the [uploads](/server/binary/uploads#the-contract-slice), never in a channel's entry (a plugin's uploads are listed here with their `__<id>::` names): `payload` is the input, and `response` the info of the reply.

```typescript [shape]
interface HuddleSocket {
  binary: {
    incoming: { 'avatar-preview': null }
    outgoing: {
      'upload-avatar': { fileType: 'image/png' | 'image/jpeg' }
    }
    clientRequests: {
      'get-thumbnail': {
        payload: { attachmentId: string }
        response: { fileType: 'image/png' }
      }
    }
    serverRequests: {
      'capture-screen': {
        payload: { maxWidth: number }
        response: { fileType: 'image/png' }
      }
    }
    streams: {
      'download-attachment': {
        payload: { attachmentId: string; fromByte: number }
        chunk: { fileName: string; fileType: string } | null
        kind: 'ephemeral'
      }
      'export-room-pdf': {
        payload: { roomId: string }
        chunk: { fileName: string } | null
        kind: 'persistent'
      }
    }
  }
}
```

A channel's `binary` key sits in the same place inside that channel's entry. The JSON `clientRequests`, `serverRequests` and `streams` maps of the contract do not list the binary ones.

## Names

A binary event, request or stream name follows the same rules as a JSON one: a non-empty string of up to 128 characters, which does not start or end with `__` and does not contain `::`. In a [plugin](/server/plugins/overview), the 128 characters include the `__<id>::` prefix that LiveThing adds on the wire. In one scope, a name belongs to one declaration and one handler: `screen-frame` cannot be both a JSON event and a binary event. Two declarations of one name throw when the adapter loads your server definition, and two handlers of one name are a compile error.
