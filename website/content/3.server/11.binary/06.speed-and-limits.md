This page builds on [Uploads](/server/binary/uploads), which shows how to write an upload handler.

The client sends pieces until it has sent `windowBytes` more than the bytes that `run` has read. Each time `run` reads a piece, the server tells the client, and the client sends more. So a slow `run`, such as one that waits for S3, slows the client down, and the server never holds much more than `windowBytes` of one upload in memory.

The first message of an upload goes through the same steps as a request: the rate limit, then the [intercepts](/server/lifecycle-and-intercept/intercept), with `frame.kind === 'upload'`, then the `input` check. The pieces skip the intercepts and the rate limit, because the window already limits how fast they come. Until `run` reads a piece, its bytes count against the connection's [byte limit](/server/handlers/per-connection-queue).

The server stops an upload with `upload-aborted` when it cannot continue. For a piece or an end that breaks a rule (`'too-large'`, `'bad-piece'` and `'window'`), the upload is then discarded, and `onDiscard` runs. A size over `maxBytes` at the start is refused before any record exists, so nothing is discarded and `onDiscard` does not run:

| Reason             | When                                                                                                                                                   |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `'too-large'`      | The size at the start, or the bytes that came, are over `maxBytes` or over the size at the start                                                       |
| `'input-mismatch'` | A resume sent another input, size or event than the first start                                                                                        |
| `'bad-state'`      | On a resume, the stored state failed the handler's [`state` schema](/server/binary/resuming#the-state). The upload is discarded, and `onDiscard` runs. |
| `'bad-piece'`      | A piece came with the wrong number, was empty or over `pieceBytes`, or the end did not match                                                           |
| `'window'`         | The client sent more than `windowBytes` more than the bytes `run` has read                                                                             |
| `'taken-over'`     | Another connection of the user started the same upload. The upload continues there.                                                                    |
| `'gone'`           | The upload is being discarded: it was cancelled, it failed, its stored state failed the `state` schema (`'bad-state'`), or its user was purged         |
| `'interrupted'`    | A piece or the end came for an upload that this server is not running                                                                                  |
| `'cancelled'`      | A cancel came while the server was still handling this start                                                                                           |

`'interrupted'` happens when the server lost the running upload while the socket stayed open, for example when Cloudflare restarted or moved the Durable Object. The server says it once for each upload on a connection, and for at most 32 different uploads per connection. Pieces for more uploads are dropped with no answer. The record is kept. For a `Blob` or bytes, the LiveThing client starts the upload again by itself, and the upload resumes from its saved offset. The client gives up after 3 tries in a row that store no new bytes. An `AsyncIterable` cannot be read again, so its `start()` rejects with `'not-resumable'` instead, and the client tells the server to discard the upload, so `onDiscard` runs at once.

A cancel can also reach the server while its start is still being handled: a slow intercept holds the start, or the start waits for an older run of the same upload to stop. The server then refuses that start with `'cancelled'`, and discards the stored upload if there is one. This covers only a start **from the same connection** as the cancel, and only a start that arrived before the cancel. A refused start does not stop a start that arrives after the cancel. But the cancel discards the upload, and `onDiscard` can take a while. Until it is done, a new start with the same upload ID gets `'gone'`. After that, a new start with that ID is a new upload.

The LiveThing client never breaks the other rules, so `'bad-piece'` and `'window'` point to a bug in another client. On the client, [`UploadAborted`](/client/primitives/uploads#errors) has one more reason: `'not-resumable'`, and it creates `'cancelled'` itself when you call `upload.cancel()`. Without `uploads()`, the server answers a client's `__uploadEnd__` and `__uploadCancel__` with `unsupported-protocol`.
