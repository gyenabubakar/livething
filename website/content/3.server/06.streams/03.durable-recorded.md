A **recorded stream** survives a client disconnect by **buffering every chunk** as it goes out. When the client reconnects, it gets the chunks it missed straight from the buffer — the generator does **not** re-run. This is the right kind when your source is one-shot and can't be replayed: LLM tokens, a third-party push API, anything you can't ask for "from position N" again.

To enable the builder, list `recordedStream()` in your capabilities — see [Stream capabilities](/server/capabilities/streams). It also needs [`persistence()`](/server/capabilities/persistence), since the chunk buffer is stored durably: register a `recordedStream` without it and `assemble(...)` throws at build time (`[wskit] The persistence() capability is required by ... but is not listed.`). The plain-stream basics (generator, `signal`, `drain()`, ending) are on [Plain Streams](/server/streams/plain); this page covers only what recording adds.

## What "recorded" means

Every chunk you yield is appended to storage *before* it is sent. If the client drops at chunk 3 and reconnects, the framework replays chunks 4, 5, … from the buffer. Your generator never restarts and has no idea a replay happened — that is the core difference from resumable. What happens to the generator *during* the disconnect is set by `onDisconnect`: the default `'cancel-but-buffer'` stops it and keeps the buffer, while `'keep-running'` lets it run to the end and buffer as it goes (see [Configuration & Lifecycle](/server/streams/config-and-lifecycle#disconnect-behavior-durable-only)).

```ts [recorded.ts]
import { define, t } from '@wskit/server'
import { persistence } from '@wskit/server/persistence'
import { recordedStream } from '@wskit/server/streams'
import * as v from 'valibot'

const TokenChunk = t<{ idx: number }>()

const base = define({
  env: t<Env>(),
  capabilities: [persistence(), recordedStream()],
})

export const handleCountTokens = base.recordedStream('count-tokens', {
  input: v.object({}),
  chunk: TokenChunk,
  maxChunks: 100,
  maxAgeMs: 60_000,
  retentionAfterEndMs: 30_000,
  async *run() {
    for (let i = 1; i <= 5; i += 1) {
      yield { idx: i }
      await new Promise((r) => setTimeout(r, 400))
    }
  },
})
```

There is no cursor and no `withCursor` — you just yield chunks. The framework keeps the buffer for you. Notice the generator has no `ctx.stream.cursor` to read; recording is fully transparent to your code.

## How it differs from resumable

Both kinds are durable, but they store different things and behave differently on resume.

| | `recordedStream` | `resumableStream` |
|---|---|---|
| What is stored | **Every chunk** | **Only the cursor** |
| On resume | Replays missed chunks from the buffer | Re-runs the generator from the saved cursor |
| Does the generator re-run? | No | Yes |
| Best for | One-shot sources (LLM tokens, push API) | Re-runnable sources (DB pagination, file offset) |
| `maxChunks` | Yes — caps the buffer | No — buffers nothing |
| `cursor` config | No | Yes |

If your source *can* be re-run from a position, prefer [resumable](/server/streams/durable-resumable) — it stores far less. Use recorded only when the source genuinely can't be replayed.

## The buffer cap and StreamAborted

The buffer is bounded by `maxChunks` (default **500**). When the buffer is full and the generator tries to yield another chunk, the framework throws `StreamAborted` with `reason: 'buffer-full'` **into the generator's `yield`**. That gives your code a chance to stop cleanly instead of crashing.

```ts [buffer-full.ts]
import { StreamAborted } from '@wskit/server/errors'

export const handleBufferFull = base.recordedStream('buffer-full-demo', {
  input: v.object({}),
  chunk: t<{ n: number }>(),
  maxChunks: 2, // tiny cap to show the behavior
  async *run() {
    for (let n = 1; n <= 5; n += 1) {
      try {
        yield { n }
      } catch (err) {
        if (StreamAborted.matches(err) && err.detail.reason === 'buffer-full') {
          return // stop cleanly — the buffer is full
        }
        throw err
      }
    }
  },
})
```

If you don't catch it, the `StreamAborted` propagates and the stream ends with that error on the wire. Wrapping the `yield` in `try/catch` lets you decide: stop, drop older work, or surface a "slow down" hint. `StreamAborted` is a built-in error from `@wskit/core` — see the [built-in errors catalog](/core/builtin-errors) and the full list of [abort reasons](/server/streams/config-and-lifecycle#abort-reasons).

::caution
`maxChunks` is a hard ceiling on how many chunks the buffer holds **at once**. The buffer is not trimmed as the client reads — it grows with every `yield`. The moment a `yield` pushes the count past `maxChunks`, the framework trims back to the cap, throws `StreamAborted({ reason: 'buffer-full' })` into that `yield`, and ends the stream. So a recorded stream cannot quietly keep producing past `maxChunks`: catch the throw to stop cleanly, or set a cap large enough for the whole run.
::

## The contract slice

A recorded stream contributes to the `recordedStreams` slot of the **server** contract. Its entry has the same shape as a plain stream — `payload`, `chunk`, `nudges` — with no cursor.

```ts [server-contract-slice.ts]
interface ServerContract {
  recordedStreams: {
    'count-tokens': {
      payload: {}
      chunk: { idx: number }
      nudges: {}
    }
  }
}
```

On the client, `InferClient` folds this into the one merged `streams` map (see the [overview](/server/streams/overview)): the entry lands under `count-tokens` with `kind: 'persistent'`, the same tag a resumable stream gets, and drops the empty `nudges`.

```ts [client-streams-view.ts]
type ClientStreams = {
  'count-tokens': {
    payload: {}
    chunk: { idx: number }
    kind: 'persistent'
  }
}
```

The durability is server-side. The client uses the same `resumeStream(...)` and reconnect-resume machinery as resumable streams; the difference (replay vs re-run) is invisible to it.

## Nudges survive a resume

Nudges work the same as on a plain stream, and buffered nudges survive a resume — a stream stopped by a nudge before a drop stays stopped after reconnect.

```ts [recorded-nudge.ts]
export const handleCountTokensNudged = base.recordedStream('count-tokens-nudged', {
  input: v.object({}),
  chunk: TokenChunk,
  nudges: { stop: v.object({}) },
  maxChunks: 100,
  async *run(ctx) {
    for (let i = 1; i <= 20; i += 1) {
      const recent = ctx.stream.nudges(yield { idx: i })
      if (recent.some((n) => n.event === 'stop')) return
      await new Promise((r) => setTimeout(r, 100))
    }
  },
})
```

## Retention and disconnect behavior

A recorded stream's buffer is kept in storage so a returning client can replay it. How long, and what the generator does the moment the client drops, are set by `maxAgeMs`, `retentionAfterEndMs`, and `onDisconnect`. The defaults: a suspended stream is kept for **5 minutes**, an ended stream for **30 seconds**, and on disconnect the generator is cancelled but its buffer is kept for resume. Because the generator keeps no resumable position of its own, recorded is the natural fit for `onDisconnect: 'keep-running'` — the generator runs to the end while the client is away, buffering as it goes. Full details on [Configuration & Lifecycle](/server/streams/config-and-lifecycle).
