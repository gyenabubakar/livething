This is the reference page for stream configuration and runtime behavior across all three kinds. The earlier pages show each kind in use; this one lists every option, its default, and the lifecycle details — nudge buffering, retention windows, disconnect handling, and the abort reasons a stream can surface.

## Nudges

A **nudge** is a typed client→server message delivered _into_ a running stream. Declare nudges as a map: event name → schema, or `null` for a nudge with no payload. Inside the generator, `ctx.stream.nudges(yield ...)` returns the nudges that arrived since the last yield, each `{ event, payload }`.

```ts [nudges.ts]
import { define, t } from '@wskit/server'
import { stream } from '@wskit/server/streams'
import * as v from 'valibot'

const base = define({ env: t<Env>(), capabilities: [stream()] })

export const handleNudged = base.stream('nudged', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ token: string }>(),
  nudges: {
    pause: null, // no payload
    'speed-up': v.object({ factor: v.number() }), // typed payload
  },
  async *run(ctx, input) {
    let delay = 50
    for (const word of input.prompt.split(' ')) {
      const recent = ctx.stream.nudges(yield { token: word + ' ' })
      for (const n of recent) {
        if (n.event === 'pause') return
        if (n.event === 'speed-up')
          delay = Math.max(1, delay / n.payload.factor)
      }
      await new Promise((r) => setTimeout(r, delay))
    }
  },
})
```

The `nudges()` reader exists on `ctx.stream` only when the stream declares at least one nudge. Each message is narrowed by its `event`, so `n.payload` is typed per event.

### Nudge buffering and overflow

Nudges that arrive between yields are buffered and handed to your generator at the next `yield`. The buffer has a cap. If the client pushes nudges faster than the generator drains them and the buffer fills, the extra nudge is rejected with `NudgeOverflow` — and this rejection is **non-terminal**: only that one nudge fails, the stream keeps running.

```ts [nudge-overflow.ts]
// On the client side, a rejected nudge surfaces as NudgeOverflow.
// The stream is NOT torn down — it is backpressure, not a teardown.
// `tokens` is a stream handle the client opened with stream(...).
import { NudgeOverflow } from '@wskit/core'

try {
  await tokens.nudge('add-context', { context })
} catch (err) {
  if (NudgeOverflow.matches(err)) {
    // Sending too fast. Back off — the stream is still alive.
    // err.detail.cap is the buffer limit so you can pace yourself.
  }
}
```

`NudgeOverflow` carries `detail.cap`, the buffer limit, so the client can pace itself. The cap is **256** pending nudges and is the same for every stream kind — plain, resumable, and recorded all share one nudge-buffering path. It is fixed; there is no config field to change it. Whether buffered nudges survive a resume depends on `onDisconnect`: with `'keep-running'` the generator never stops, so its nudge buffer carries through the disconnect; with the default `'cancel-but-buffer'` the generator is cancelled when the client drops and its nudge buffer is discarded — only the resume state is kept (a recorded stream's chunk buffer, or a resumable stream's cursor). `NudgeOverflow` is a built-in error; see the [built-in errors catalog](/core/builtin-errors).

## Retention windows (durable only)

Durable streams are kept in storage so a returning client can resume or replay. Two windows control how long.

| Option                | Default    | What it bounds                                                                                                                                                                        |
| --------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maxAgeMs`            | 5 minutes  | How long a **suspended** stream (client dropped, generator paused) is kept before it ages out and is deleted. A resume after this window gets `StreamAborted({ reason: 'expired' })`. |
| `retentionAfterEndMs` | 30 seconds | How long an **ended** stream is kept after it finishes, so a quick reconnect can still resume/replay. A resume after this window gets `StreamAborted({ reason: 'not-found' })`.       |

```ts [retention.ts]
export const handleShortWindow = base.recordedStream('short-window', {
  input: v.object({}),
  chunk: t<{ idx: number }>(),
  maxChunks: 10,
  maxAgeMs: 300, // suspended streams age out fast
  retentionAfterEndMs: 30_000, // but ended ones stay for 30s
  async *run() {
    for (let i = 1; i <= 5; i += 1) yield { idx: i }
  },
})
```

A background sweep runs about every 60 seconds and deletes rows past their window, so expired streams don't pile up.

## Disconnect behavior (durable only)

`onDisconnect` decides what happens to the running generator the moment its owning connection drops.

| Value                             | Behavior                                                                                                                                                                         |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `'cancel-but-buffer'` _(default)_ | Cancel the generator but keep what's stored (the cursor for resumable, the buffer for recorded), so the client can resume when it returns.                                       |
| `'keep-running'`                  | Leave the generator running while the client is away. It keeps producing into the buffer (recorded) or advancing the cursor (resumable), and the client catches up on reconnect. |

```ts [keep-running.ts]
export const handleKeepRunning = base.recordedStream('keep-running-feed', {
  input: v.object({}),
  chunk: t<{ idx: number }>(),
  maxChunks: 50,
  onDisconnect: 'keep-running', // runs to the end even while the client is gone
  async *run() {
    for (let i = 1; i <= 20; i += 1) {
      yield { idx: i }
      await new Promise((r) => setTimeout(r, 80))
    }
  },
})
```

::tip
`'keep-running'` fits **recorded** streams best, since they buffer every chunk while the client is away. A resumable stream only stores a cursor, so leaving it running mostly helps when it is a broadcast that other connections are still watching.
::

## The abort signal

Every stream generator gets `ctx.stream.signal`, an `AbortSignal` that fires when the stream is cancelled, the client disconnects, or the server shuts down. Pass it into awaited work so the work stops the instant the stream is torn down. See [Plain Streams](/server/streams/plain#the-abort-signal) for the full pattern.

## Abort reasons

When the framework has to tear a stream down — or refuse a resume — it sends `StreamAborted` to the client with a `reason`. A client SDK reads the reason to decide whether to fast-resume, restart, or surface an error. `StreamAborted` is a built-in error from `@wskit/core`.

| `reason`             | When it happens                                                                                                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `'cancelled'`        | The stream was cancelled (client cancel or server-side teardown).                                                                                                                           |
| `'buffer-full'`      | A recorded stream's buffer hit `maxChunks`. Thrown **into** the generator's `yield` so you can catch it.                                                                                    |
| `'expired'`          | A suspended durable stream aged out past `maxAgeMs` before the client returned.                                                                                                             |
| `'not-found'`        | A resume named a stream ID the server doesn't recognize (or one past `retentionAfterEndMs`).                                                                                                |
| `'hibernation-wake'` | A non-durable stream was lost because the server dropped in-memory state (e.g. a Durable Object waking from hibernation). The connection is still alive; only the in-flight stream is gone. |
| `'unsubscribed'`     | The client previously cancelled this broadcast stream, so the server stopped fanning to it. The stream stays running for everyone else.                                                     |
| `'cursor-invalid'`   | On resume, a stored cursor failed the `resumableStream` validator. The row stays in place; the client picks a recovery strategy.                                                            |
| `'aborted'`          | Catch-all for an internal teardown that matches none of the above.                                                                                                                          |

```ts [abort-reasons.ts]
// Client-side: branch on the reason to recover.
import { StreamAborted } from '@wskit/core'

try {
  for await (const chunk of handle) {
    // ...
  }
} catch (err) {
  if (StreamAborted.matches(err)) {
    if (err.detail.reason === 'hibernation-wake') restartStream()
    else if (err.detail.reason === 'buffer-full') showSlowDownToast()
    else if (err.detail.reason === 'expired') startFresh()
  }
}
```

`buffer-full` is the one reason the server side handles directly — the framework throws it into the generator so handler code can catch and stop cleanly. See [Recorded streams](/server/streams/durable-recorded#the-buffer-cap-and-streamaborted). The shared error model (matching, codes, detail) lives in [Error model](/core/error-model).

## Stream ID and collisions

A client may start a stream with its own stream ID (a non-empty string, up to 128 characters) so it can use a domain ID — a conversation ID, a job ID — as the resume handle. If that ID is already in use by another active stream for the same connection, the start is rejected with `StreamIdCollision`. Otherwise the framework generates an ID. Resuming a stream that already has another stream of the same event running (without `allowConcurrent`) surfaces `StreamAlreadyActive`. Both are built-in errors — see the [built-in errors catalog](/core/builtin-errors).

## Storage layout (durable streams)

When you list `resumableStream()` or `recordedStream()` alongside `persistence()`, durable streams live in three SQL tables inside the server's own SQLite storage, reachable through `ctx.sql`. The framework creates them with `CREATE TABLE IF NOT EXISTS` the first time a durable stream is triggered on a given server instance — not at declare time, and not when the server first boots.

| Table                        | One row per                                                               | Key columns, in plain terms                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `__wskit_streams`            | One durable stream, resumable or recorded                                 | Who owns it and what started it (`identity`, `stream_id`, `creator_identity`, `event`, `payload`); which kind (`kind`); lifecycle (`status`: active, suspended, or ended; `started_at`, `last_activity_at`, `ended_at`); resume state (`cursor`, `last_seq` — only resumable streams write `cursor`); scope (`channel_key`, `channel_family`, `broadcast`); the retention knobs (`max_chunks`, `max_age_ms`, `retention_after_end_ms`) |
| `__wskit_stream_chunks`      | One buffered chunk of a **recorded** stream — never written for resumable | Which stream it belongs to (`identity`, `stream_id`), its order (`seq`), the chunk itself as JSON (`payload`), and when it was emitted (`emitted_at`)                                                                                                                                                                                                                                                                                  |
| `__wskit_stream_subscribers` | One subscriber of a **broadcast** stream                                  | Which stream and who (`identity`, `stream_id`, `subscriber_identity`), how far a resume has caught them up (`caught_up_seq`), and when they opted out (`unsubscribed_at`, `null` while still subscribed)                                                                                                                                                                                                                               |

`identity` is not always a connection's own identity: for a broadcast stream it is a synthetic key derived from the channel scope, so every subscriber's resume finds the same row regardless of whose identity is asking. Deleting a stream's `__wskit_streams` row cascades to its chunks and its subscriber rows.

::warning
Every table WSKit owns uses the reserved `__wskit_` prefix, including the three above. Never create your own table under that prefix — `ctx.sql` is the same SQLite database WSKit writes to. Because these tables are created with `CREATE TABLE IF NOT EXISTS`, a name collision does not fail loudly: if a table like `__wskit_streams` already exists — say, one you created yourself before ever listing `resumableStream()` or `recordedStream()` — WSKit's `CREATE TABLE IF NOT EXISTS` silently keeps your existing, incompatible schema instead of erroring. Durable streams then break at runtime with confusing SQL errors, not a clear "table already exists" failure at the moment you could have caught it.
::

## Full option reference

Every option across the three builders, with defaults. A blank "Kinds" cell means all three.

| Option                | Kinds     | Default               | Purpose                                                                                                                                                                    |
| --------------------- | --------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `input`               | all       | (none)                | Validator for the start-payload the client sends. The second argument to `run` is the validated value.                                                                     |
| `chunk`               | all       | (inferred)            | Optional [type marker](/server/define/overview) typing each chunk. Chunks go out, so it is never validated. Omit it and the chunk type is inferred from what `run` yields. |
| `nudges`              | all       | `{}`                  | Map of nudge event → schema (or `null` for no payload). Read with `ctx.stream.nudges(yield ...)`.                                                                          |
| `broadcast`           | all       | `false`               | Fan chunks to every connection in scope instead of just the trigger connection.                                                                                            |
| `allowConcurrent`     | all       | `false`               | Allow more than one stream of the same event at once on a connection. Otherwise a second start is rejected with `stream-already-active`.                                   |
| `highWaterMark`       | all       | 256 KB                | Outbound buffer limit in bytes that `ctx.stream.drain()` paces against.                                                                                                    |
| `cursor`              | resumable | (none)                | `t<T>()` for a type-only cursor, or a schema to also runtime-check restored cursors.                                                                                       |
| `maxChunks`           | recorded  | 500                   | Hard cap on buffered chunks. Hitting it throws `StreamAborted({ reason: 'buffer-full' })` into the generator. Resumable does not accept it.                                |
| `maxAgeMs`            | durable   | 5 minutes             | How long a suspended stream is kept before it ages out and is deleted.                                                                                                     |
| `retentionAfterEndMs` | durable   | 30 seconds            | How long an ended stream is kept so a quick reconnect can still resume.                                                                                                    |
| `onDisconnect`        | durable   | `'cancel-but-buffer'` | What the generator does when the owning connection drops: cancel-and-buffer, or `'keep-running'`.                                                                          |
| `run`                 | all       | (required)            | The async generator. Each yielded value is sent as one chunk.                                                                                                              |
