If your runtime is not in the [adapter table](/server/adapters/overview#adapter-packages), you can write your own adapter. An adapter connects two things:

- the **engine**: the runtime object that LiveThing builds from your server definition. It routes messages, runs your handlers and owns connection state.
- your platform's **WebSocket lifecycle**: the upgrade (the HTTP request that asks to switch to a WebSocket), and the `message`, `close` and `error` events of each socket.

Everything you need comes from one subpath:

```ts [imports.ts]
import { CloseCodes } from '@livething/core'
import {
  adapter,
  normalizeCloseReason,
  rejectAsyncTransactionCallback,
  rejectAsyncTransactionResult,
} from '@livething/server/adapters'
import type {
  AdapterConfig,
  ConnectionDescriptor,
  ConnectionHandle,
  Engine,
  EngineRuntimeOptions,
  ServerDefinition,
  UpgradeDecision,
} from '@livething/server/adapters'
```

## The `adapter` factory

`adapter(config)` returns a function. That function takes a server definition and your platform options. It returns the service shape that your platform needs, such as a class, a server object or a request function. Your package exports a public function that calls this returned function. The official adapters name it `bind`.

<!-- docs-check: skip -->

```ts [my-adapter.ts]
import { AsyncLocalStorage } from 'node:async_hooks'
import { adapter } from '@livething/server/adapters'
import type { ServerDefinition } from '@livething/server/adapters'

export interface MyOptions {
  port: number
}

export interface MyService {
  admin(): unknown
}

// adapter<TOptions, TService>(...): TOptions is what callers pass to your
// bind(). TService is what your bind() returns.
export const build = adapter<MyOptions, MyService>({
  id: 'my-platform',
  asyncContextFactory: () => new AsyncLocalStorage(),

  setup(createEngine, options) {
    // ... connect the platform here, and return a MyService ...
  },
})

export function bind(
  definition: ServerDefinition,
  options: MyOptions,
): MyService {
  return build(definition, options)
}
```

## The config fields

The object you pass to `adapter(...)` is an `AdapterConfig`. It declares the fixed capabilities of your platform.

::field-group
::field{name="id" required}
A stable string that names the adapter (`'cloudflare'`, `'node'`, and so on). The engine uses it in its error messages.
::
::field{name="asyncContextFactory" required}
A function that returns an async-context store for this runtime. An async-context store keeps track of which connection the current code runs for, across `await` points. On Node-like runtimes this is `() => new AsyncLocalStorage()`. It must return a new store on every call, because LiveThing keeps several stores apart, such as the one that [`context.connection(base)` and the other `context` accessors](/server/context-and-storage/context-anywhere) read.
::
::field{name="hibernation"}
A synchronous `persist`/`restore` pair. Add it only if your platform can keep sockets open while it removes the instance from memory.
::
::field{name="setup" required}
The function that connects the platform to the engine and returns your service.
::
::

### The hibernation signal

Hibernation means the platform removes an idle instance from memory but keeps its sockets open. The next message wakes the instance again. There is no separate `true`/`false` flag for this capability. If the `hibernation` object is present, your adapter supports hibernation. If your platform can keep sockets open while the instance is out of memory, add a synchronous `persist`/`restore` pair:

- LiveThing calls `persist` with a small snapshot each time the saved state of a socket changes. Store the snapshot with that socket.
- LiveThing calls `restore` when the socket wakes. Return the last snapshot you stored.

Both callbacks must be synchronous. A wake updates the socket attachment, the stored connection row and the in-memory indexes as one synchronous operation. If either callback returns a Promise (or any object with a `then` method), LiveThing throws a configuration error.

<!-- docs-check: skip -->

```ts [hibernation.ts]
const build = adapter<MyOptions, MyService>({
  id: 'my-platform',
  asyncContextFactory: () => new AsyncLocalStorage(),
  hibernation: {
    persist(wsKey, snapshot) {
      // store `snapshot` with this socket
    },
    restore(wsKey) {
      // return the most recent snapshot for this socket
      return null
    },
  },
  // setup(...)
})
```

If you leave out `hibernation`, the engine rejects any definition that turns hibernation on (`hibernation: true`). This happens in `initialize()`, with an error that names your adapter. So a definition can never run on a platform that cannot do what it asks for.

## Inside `setup`

`setup(createEngine, options)` is where you connect the platform. It receives a `createEngine` function and the options the caller passed. Call `createEngine(...)` to get an `Engine`. Then connect your platform's WebSocket events to it.

`createEngine` accepts `EngineRuntimeOptions`. This is a smaller object than the engine's full internal options. The adapter factory adds its own `adapterId`, async-context factory and hibernation capability. Application developers configure only the options that your adapter exposes through `TOptions`.

`createEngine` needs the runtime parts that the engine cannot create by itself:

| Runtime option  | What you pass                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `platform`      | An object specific to your platform. Handlers read it as `ctx.platform`.                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `logger`        | A `{ info, warn, error }` logger. Handlers read it as `ctx.log`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `storage`       | A durable SQL and key-value storage provider (`{ sql, kv }`). Durable means the data stays after the instance restarts. Every adapter must supply it. It stores channel membership, durable streams, persistent tags and every other feature that lasts longer than one connection. Its `sql` part must include `limits` (see below).                                                                                                                                                                                               |
| `timers`        | A durable alarm provider (`setAlarm`, `deleteAlarm`). An alarm is a timer that wakes the instance at a set time. Every adapter must supply it. It powers `ctx.schedule(...)` and every capability that needs to wake the instance later.                                                                                                                                                                                                                                                                                            |
| `messageLimits` | Optional. `{ receiveBytes, sendBytes }`: the largest message your platform receives and sends, in bytes. Default: 32 MiB each. The engine closes a connection with `1009` (`MESSAGE_TOO_BIG`) when a message over `receiveBytes` arrives, and it throws instead of sending a message over `sendBytes`, so your platform never gets one it would drop. Your platform should also refuse a bigger message before LiveThing reads it, if it can. The bytes one connection may hold before its handlers start are twice `receiveBytes`. |

### The `transaction` contract

`transaction(fn)` takes a synchronous callback with no arguments. The callback calls your provider's `exec(...)` directly, so your `exec` must join the open transaction. If the callback throws, everything it wrote must be rolled back, and `transaction` must throw the same error. If your SQL engine can hand `exec` a different connection while a transaction is open (for example a connection pool), your provider must route `exec` to the transaction's connection. SQLite on one connection, including Cloudflare Durable Objects SQLite, does this already.

LiveThing calls `transaction` inside another `transaction`. It runs the outermost `ctx.sql.transaction` inside one more transaction, and code inside a handler's transaction, such as a sequence reservation, can start its own. Support nesting. An inner failure that the outer callback catches must undo only the inner writes, and an outer failure must undo everything. SQLite does not nest a second `BEGIN` for you: your provider must run `BEGIN` only for the outermost call, and use `SAVEPOINT`, `RELEASE` and `ROLLBACK TO` for the nested ones, unless your driver already does this (better-sqlite3's `transaction()` does). If the final commit fails, for example on a deferred foreign key, roll back and throw, so no transaction stays open.

After a rollback, LiveThing runs the `ctx.kv` writes and the `setAlarm` and `deleteAlarm` calls that were made inside the callback again. It does this on every adapter, because it cannot know whether your platform undid them. A `kv` that shares the SQL connection, or a platform that ties alarm changes to the transaction, does lose them on a rollback. So `set`, `delete`, `setAlarm` and `deleteAlarm` must be safe to run twice.

Reject an async callback, or a callback that returns a Promise. Otherwise the transaction ends before the async work runs. `@livething/server/adapters` exports two helpers for this. Call `rejectAsyncTransactionCallback(fn)` before the transaction starts, and `rejectAsyncTransactionResult(result)` with the value the callback returned, before the transaction commits. Both throw the same `TypeError` that the built-in adapters throw. Read all rows inside `exec`, as the Node adapter does. A lazy cursor, such as the one that Cloudflare's SQLite returns, is not a stable snapshot once the code that holds it awaits.

### Declaring your engine's SQL limits

The `sql` part of `storage` is an `SQLProvider`. It has `exec`, `transaction`, and a required `limits` field of type `SqlLimits`:

```ts [sql-limits.ts]
import type { SqlLimits } from '@livething/server/adapters'

const limits: SqlLimits = {
  maxBoundParams: 32_766, // most `?` placeholders one statement may bind
  maxStatementBytes: 1_000_000_000, // most bytes one statement's SQL text may be
  maxValueBytes: 1_000_000_000, // most bytes one stored string, BLOB (raw bytes), or whole row may be
}
```

Some LiveThing code builds SQL with a variable number of bound values, for example batched inserts or `WHERE id IN (...)`. That code reads `maxBoundParams` and splits the work into several statements, so it stays under the real limit of your SQL engine. Give the other two numbers too, so the limits describe your whole engine. Each SQL engine has different limits, and some are very low. For example, Cloudflare's Durable Objects SQLite allows only 100 bound parameters per statement. Take the numbers from your own engine's documentation. Do not copy them from another adapter:

- **Cloudflare Durable Objects SQLite**: [developers.cloudflare.com/durable-objects/platform/limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
- **Standard SQLite** (`node:sqlite`, `bun:sqlite`, `better-sqlite3`, and similar): [sqlite.org/limits.html](https://sqlite.org/limits.html)

If your platform uses standard SQLite directly and does not lower any of these limits itself, use the numbers from [sqlite.org/limits.html](https://sqlite.org/limits.html). They are the numbers in the example above.

## The connection lifecycle

After you have an engine, these five steps take a connection from upgrade to close.

::steps

### Build a standard request

Before you call the engine, turn the platform's incoming request into a complete Web API `Request`. Keep the URL, method, headers and cookies. Add a signal that aborts when the request or the connection is abandoned. The engine cannot read `IncomingMessage`, a framework request, or any other platform object.

If the platform can find a trusted client address, set the `LiveThing-Client-IP` header on the request that you pass to `handleUpgrade`. Always delete any `LiveThing-Client-IP` header that the client sent first, so a client cannot choose its own address. Leave the header out when the address is unknown or cannot be checked. The [Upgrade guide](/server/server/upgrade#client-ip) shows how application code reads it.

### Decide the upgrade

Pass the request to `engine.handleUpgrade(request)`. It returns an `UpgradeDecision`. The decision is either a reject (`reject: true`, with an optional `code` and `reason`) or an accept, which carries the connection's `userId`, `meta` and `tags`. Each of these three fields can be missing on an accept, for example when the app has no `upgrade` hook.

```ts [upgrade.ts]
import type {
  Engine,
  UpgradeDecision,
} from '@livething/server/adapters'

async function decideUpgrade(engine: Engine, request: Request) {
  const decision: UpgradeDecision =
    await engine.handleUpgrade(request)
  if (decision.reject) {
    // close or respond with decision.code / decision.reason
    return
  }

  return decision
}
```

`decision.code` on a reject is already safe to send. A value from `400` to `599` is an HTTP status for the rejection. Any other code is a valid WebSocket close code. In that case, accept the socket and close it at once with that code and reason. If app code gave an invalid rejection code, the engine has already logged it and changed the decision to HTTP `403`. Do not add your own close-code check or a platform-specific fallback around an engine decision.

### Build a connection descriptor

For an accepted socket, build a `ConnectionDescriptor`. This is the set of low-level callbacks that the engine uses to send data to the client. `backpressureSupported` tells the engine whether `bufferedAmount()` reports the real amount of data waiting to be sent (the outbound buffer). Set it to `false` when your platform does not expose that number.

```ts [descriptor.ts]
import type {
  ConnectionDescriptor,
  UpgradeDecision,
} from '@livething/server/adapters'

function describeSocket(
  socket: WebSocket,
  decision: UpgradeDecision,
) {
  const descriptor: ConnectionDescriptor = {
    send: (data) => {
      // A socket that is closing or closed must not throw.
      if (socket.readyState !== WebSocket.OPEN) return false

      socket.send(data)
      return true
    },
    close: (code, reason) => socket.close(code, reason),
    bufferedAmount: () => socket.bufferedAmount,
    backpressureSupported: true,
    userId: decision.userId ?? '',
    meta: decision.meta ?? {},
    tags: decision.tags ?? [],
  }

  return descriptor
}
```

An empty `userId` means the connection is anonymous.

Before the engine calls your `close()`, it checks the close code and cuts the reason to the WebSocket limit of 123 bytes. Your callback always gets a valid outgoing code (`1000` when the caller gave none), so it only needs to call the platform's socket API. Use `normalizeCloseReason()` only when the adapter closes a socket without the engine, for example when it rejects an upgrade before `engine.accept()` runs.

`send()` returns `false` when the frame was not sent. The engine then does not count that frame as delivered. Check the socket is open before you send: a send on a closing or closed socket must return `false`, never throw. Platforms differ here. Cloudflare's `send()` throws after the socket closes, and the Node `ws` library drops the frame without an error, which would count it as delivered. App code such as an `onError` hook can send while the socket is going away, so this must be safe. `bufferedAmount()` must report the platform's real outbound buffer. Set `backpressureSupported` to `true` only when that value is real and usable.

### Accept the connection

Pass the socket key and the descriptor to `engine.accept(...)`. The socket key is any value that identifies this socket on your platform, often the socket object itself. `accept` returns a `ConnectionHandle`. This is the set of callbacks that **you** call when the socket has traffic.

```ts [accept.ts]
import type {
  ConnectionDescriptor,
  ConnectionHandle,
  Engine,
} from '@livething/server/adapters'

function acceptSocket(
  engine: Engine,
  socket: WebSocket,
  descriptor: ConnectionDescriptor,
) {
  const connection: ConnectionHandle = engine.accept(
    socket,
    descriptor,
  )
  return connection
}
```

### Forward socket events

Connect your platform's `message`, `close` and `error` events to the handle. Forward string frames. Close the socket when a binary frame arrives:

```ts [wire.ts]
import { CloseCodes } from '@livething/core'
import type { ConnectionHandle } from '@livething/server/adapters'

function forwardSocketEvents(
  socket: WebSocket,
  connection: ConnectionHandle,
) {
  socket.addEventListener('message', (event) => {
    if (typeof event.data === 'string') {
      connection.handleMessage(event.data)
    } else {
      socket.close(
        CloseCodes.UNSUPPORTED_DATA,
        '[livething] binary frames are not supported yet',
      )
    }
  })
  socket.addEventListener('close', (event) => {
    connection.handleClose(event.code, event.reason)
  })
  socket.addEventListener('error', (event) => {
    connection.handleError(event)
  })
}
```

The three handle methods return promises. Handle rejected promises, but do not force unrelated socket events to run one after another unless the platform itself needs that order. The close code from the other side is information about what happened, not a code you send. Forward it unchanged, even when it is a value such as `1006` that you cannot put in a close frame yourself. If accepting the socket or connecting its events fails, close the socket with `CloseCodes.INTERNAL_ERROR` (`1011`) and clean up the connection.

::

## Startup, alarms, and shutdown

The adapter needs a few more engine calls:

- `await engine.initialize()`: run it once when the instance starts, before you accept connections. It loads durable state.
- `engine.usesHibernation()`: returns `true` when the definition turned hibernation on. Use it to choose the hibernation path when you accept sockets.
- `engine.setInstanceId(id)`: call it before you accept connections when your adapter runs more than one instance and callers choose an instance by ID (like a Durable Object). Use a stable ID from the platform. This way, connection and user references from different instances cannot be mixed up.

Right after `initialize()`, tell the engine which connections survived the cold start (the start of a new instance that has nothing in memory yet). The call depends on whether the platform supports hibernation:

- **No hibernation**: call `engine.reconcileConnections(new Set())`. No connection carries over between instances, so this deletes any leftover connection rows.
- **Hibernation**: call `await engine.restoreHibernatedConnections(sockets)` and pass every socket that the platform still holds open (on Cloudflare, `ctx.getWebSockets()`). It wakes each socket through the engine. It rebuilds the socket's identity, tags and channel membership, so a broadcast reaches the socket even before the socket sends anything. Then it deletes the rows of every socket that did not survive. The Promise rejects if a socket cannot be restored, so do not handle events until it completes. It calls `reconcileConnections` internally, so do not call both.

Three more calls complete the connection lifecycle:

- `engine.handleHibernationWake(socket)`: on a hibernating platform, wakes **one** socket when you need it (from inside your `message`, `close` or `error` callback) and returns its `ConnectionHandle`. A non-hibernating adapter keeps each handle in memory instead.
- `await engine.handleAlarm()`: call it from the platform's timer or alarm callback. It runs the durable timers that are due.
- `await engine.handleShutdown()`: runs every `onShutdown` hook and closes every socket cleanly. Call it when you want to empty the instance of connections. On a hibernating platform, first call `engine.handleHibernationWake(...)` for every socket the platform still holds. An instance that just woke up knows only the sockets it has already woken. If you skip this step, hibernated sockets stay open. If your adapter is about to close its `storage` or `timers` provider because its process is ending, call `await engine.handleShutdown({ terminal: true })` instead. This cancels LiveThing's own pending alarm retries before those providers close. Use the plain call for a temporary shutdown on platforms that may get more work later, such as a Durable Object.

Your `TimerProvider` must keep its alarm across restarts. When the instance starts again, it must read the stored alarm time and set the alarm again. The engine runs the retries for scheduled-task handlers and for its own durable internal work. After it schedules that work, `engine.handleAlarm()` normally completes, even when a task or hook failed. When `engine.handleAlarm()` rejects, the delivery itself could not complete, for example because the engine could not save its next shared alarm. If your platform has its own retry policy for alarm delivery, follow that policy for this rejection. Do not build a second retry policy for scheduled-task handlers on top of the platform's delivery retry.

## Exposing the admin surface

`engine.admin()` returns the [admin context](/server/admin/context) merged with the app's own [`api`](/server/admin/authoring). When an app method has the same name as a built-in member, the built-in member is used. Your adapter decides how outside code reaches this object.

An in-process service can return the whole object. When the caller is behind a boundary that copies data between processes (a serializing boundary), the adapter must wrap it in objects that the boundary can call into. Keep the same shape, so admin code reads the same on every runtime. The engine also rejects app `api` method names that JavaScript itself already uses, such as `then` and `constructor`. For example, a `then` method makes the admin object a thenable (an object that `await` treats like a Promise), so `await admin()` never finishes.

If your service runs **in the same process** as the caller, return the object whole. Nothing is copied, so the managers work the same way as inside a handler:

<!-- docs-check: skip -->

```ts [in-process.ts]
const build = adapter<MyOptions, MyService>({
  id: 'my-platform',
  asyncContextFactory: () => new AsyncLocalStorage(),
  setup(createEngine, options) {
    const engine = createEngine({
      /* ... */
    })
    return {
      admin: () => engine.admin(),
      // ...the rest of your service
    }
  },
})
```

If your platform has a **serializing boundary** between the caller and the engine, the context cannot cross it as it is. Cloudflare's Worker-to-Durable-Object RPC is one example: it sees only methods and getters on a class's prototype chain, not the fields of a plain object. The Cloudflare adapter wraps each part (`connections`, `users`, `channels`, and the handles their `get(...)` returns) in its own `RpcTarget` class, and exposes the nested parts as getters. So `stub.admin().users.get(id).broadcast(…)` works from the Worker. Leave out what should stay inside the instance, such as `sql`, `kv`, and `platform`.

`ADMIN_CONTEXT_MEMBERS` tells the two groups apart. Any key on the returned object that is **not** in this set came from the app's own `api`, so those are the methods to forward.

```ts [split.ts]
import { ADMIN_CONTEXT_MEMBERS } from '@livething/server/adapters'
import type { Engine } from '@livething/server/adapters'

function appMethodsOf(engine: Engine) {
  const surface = engine.admin()
  return Object.entries(surface).filter(
    ([key, value]) =>
      typeof value === 'function' && !ADMIN_CONTEXT_MEMBERS.has(key),
  )
}
```

### Typing what your `bind()` returns

`adapter<TOptions, TService>` sets `TService` once, when you create the adapter. TypeScript cannot make it depend on the `api` type of each server definition. So the app's admin methods do not appear in the caller's types by themselves.

To fix this, write a small generic wrapper. Keep `TService` as your base shape, and let your package's public `bind(...)` give the result a more exact type, based on the server definition it received:

- `AdminOf<TDefinition>` reads the whole admin type: the connectionless context, typed against the definition's own `emits(...)`, channels and scheduled tasks, plus the `api` methods. An in-process adapter's `admin()` should resolve to this type. The Node.js adapter does this.
- `ApiOf<TDefinition>` reads the `api` type from the definition.
- `MetaOf<TDefinition>` reads the connection metadata type. You need it when your service returns connection snapshots, because a serializing boundary cannot accept the general `Record<string, unknown>` type.

```ts [typed-bind.ts]
import type {
  ApiOf,
  MetaOf,
  ServerDefinition,
} from '@livething/server/adapters'
import { build } from './my-adapter'
import type { MyOptions } from './my-adapter'

interface MyService<TApi, TMeta> {
  admin(): TApi
  connections(): TMeta[]
}

export function bind<TDefinition extends ServerDefinition>(
  definition: TDefinition,
  options: MyOptions,
): MyService<ApiOf<TDefinition>, MetaOf<TDefinition>> {
  return build(definition, options) as MyService<
    ApiOf<TDefinition>,
    MetaOf<TDefinition>
  >
}
```

Inside `setup`, `createEngine` already returns an `Engine<TApi>`, so `engine.admin()` carries the `api` methods there. It does not carry the definition's event types, so give the public result its exact type in the wrapper.

`TOptions` is the adapter's option type. `TApi` comes from the server definition. The public wrapper should keep `ApiOf<TDefinition>` and `MetaOf<TDefinition>`, so that application code never has to pass those generics by hand.

## The reference adapter

The Cloudflare adapter follows every step on this page for Durable Objects, including the hibernation path. The Node.js adapter follows the non-hibernating path. See the [Cloudflare adapter](/server/adapters/cloudflare) and [Node.js adapter](/server/adapters/node/node-http) pages for how application code uses them. The [adapters overview](/server/adapters/overview) explains how a definition reaches an adapter.
