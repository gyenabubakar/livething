If your runtime is not in the [adapter table](/server/adapters/overview#adapter-packages), you can write your own adapter. An adapter's whole job is to bridge two things: the **engine** (the runtime that WSKit builds from your definition) and your platform's **WebSocket lifecycle** (upgrade, message, close, error).

Everything you need is in one subpath:

```ts [imports.ts]
import { CloseCodes } from '@wskit/core'
import { adapter, normalizeCloseReason } from '@wskit/server/adapters'
import type {
  AdapterConfig,
  ConnectionDescriptor,
  ConnectionHandle,
  Engine,
  EngineRuntimeOptions,
  ServerDefinition,
  UpgradeDecision,
} from '@wskit/server/adapters'
```

## The `adapter` factory

`adapter(config)` returns a function. That function takes a server definition plus your platform options and returns whatever service shape your platform wants — a class, a server object, or a request function. You wrap that returned function in your package's public `server(...)` entry.

```ts [my-adapter.ts]
import { adapter } from '@wskit/server/adapters'
import type { ServerDefinition } from '@wskit/server/adapters'

// `adapter<TOptions, TService>(...)` — TOptions is what callers pass to your
// server(); TService is what your server() returns.
const build = adapter<MyOptions, MyService>({
  id: 'my-platform',
  asyncContextFactory: () => new AsyncLocalStorage(),

  setup(createEngine, options) {
    // ... wire the platform here, return a MyService ...
  },
})

export function server(
  definition: ServerDefinition,
  options: MyOptions,
): MyService {
  return build(definition, options)
}
```

## The config fields

The object you pass to `adapter(...)` is an `AdapterConfig`. It declares the static capabilities of your platform.

| Field                 | Required | What it is                                                                                                                    |
| --------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `id`                  | Yes      | A stable string identifying the adapter (`'cloudflare'`, `'bun'`, …). Used for wake/hibernate routing on cold start.          |
| `asyncContextFactory` | Yes      | A factory returning an async-context store for this runtime. On Node-like runtimes this is `() => new AsyncLocalStorage()`.   |
| `hibernation`         | No       | A synchronous `persist`/`restore` pair if your platform can keep sockets alive while the instance is evicted. Omit it if not. |
| `setup`               | Yes      | The callback that wires the platform to the engine and returns your service.                                                  |

### The hibernation signal

The **presence** of the `hibernation` object is the capability signal — there is no separate boolean. If your platform can hold sockets open across an eviction, provide a synchronous `persist`/`restore` pair. WSKit writes a snapshot through `persist` whenever per-socket state changes, and reads it back through `restore` on wake. These callbacks must not return a Promise: a wake updates the socket attachment, durable row, and in-memory indexes as one synchronous operation. WSKit throws a configuration error if either callback returns a Promise or thenable.

```ts [hibernation.ts]
const config = {
  id: 'my-platform',
  asyncContextFactory: () => new AsyncLocalStorage(),
  hibernation: {
    persist(wsKey, snapshot) {
      // store `snapshot` against this socket
    },
    restore(wsKey) {
      // return the most recent snapshot for this socket
      return null
    },
  },
  // ...
}
```

If you omit `hibernation`, the engine rejects any definition that opted into hibernation (`hibernation: { enabled: true }`) at `initialize()` time, with a clear error. So you never get a silent capability mismatch.

## Inside `setup`

`setup(createEngine, options)` is where the real work happens. You get a `createEngine` factory and the options the caller passed. Call `createEngine(...)` to get an `Engine`, then wire your platform's WebSocket events to it.

`createEngine` accepts `EngineRuntimeOptions`, not the engine's full internal option object. The adapter factory supplies its own `adapterId`, async-context factory, and hibernation capability. Application developers should configure only the options your adapter exposes through `TOptions`.

`createEngine` needs the runtime surfaces the engine cannot make for itself:

| Runtime option | What you pass                                                                                                                                                                                                                                      |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `platform`     | A platform-specific object, exposed as `ctx.platform`.                                                                                                                                                                                             |
| `logger`       | A `{ info, warn, error }` logger, exposed as `ctx.log`.                                                                                                                                                                                            |
| `storage`      | A durable SQL and key-value storage provider. Every adapter must supply this — it backs channel membership, durable streams, persistent tags, and every other feature that outlives a connection. Its `sql` half must supply `limits` — see below. |
| `timers`       | A durable alarm provider. Every adapter must supply this — it backs `ctx.schedule(...)` and any capability that needs to wake the instance later.                                                                                                  |

### Declaring your engine's SQL limits

The `sql` half of `storage` is an `SQLProvider` — `exec`, `transaction`, and a required `limits` field of type `SqlLimits`:

```ts [sql-limits.ts]
import type { SqlLimits } from '@wskit/server/adapters'

const limits: SqlLimits = {
  maxBoundParams: 32_766, // most `?` placeholders one statement may bind
  maxStatementBytes: 1_000_000_000, // most bytes one statement's SQL text may be
  maxValueBytes: 1_000_000_000, // most bytes one stored string, BLOB, or whole row may be
}
```

`limits` is required, not optional — WSKit code that builds SQL with a variable number of bound values (batched inserts, `WHERE id IN (...)`) reads these three numbers to stay under your engine's real ceiling instead of assuming a generous one. Every SQL engine caps this differently, and some caps are surprisingly low (Cloudflare's Durable Objects SQLite allows only 100 bound parameters per statement), so find your own engine's real numbers from its own documentation rather than reusing another adapter's:

- **Cloudflare Durable Objects SQLite** — [developers.cloudflare.com/durable-objects/platform/limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
- **Stock SQLite** (`node:sqlite`, `bun:sqlite`, `better-sqlite3`, and similar) — [sqlite.org/limits.html](https://sqlite.org/limits.html)

If your platform wraps stock SQLite directly and does not lower any of these ceilings itself, the [sqlite.org/limits.html](https://sqlite.org/limits.html) numbers are your `limits`.

## The connection lifecycle

Once you have an engine, a request boundary and four engine operations carry a connection from upgrade to close.

::steps

### Build a standard request

Before calling the engine, turn the platform's incoming request into a complete Web API `Request`. Preserve the URL, method, headers, cookies, and a signal that aborts when the request or connection is abandoned. The engine does not know how to read `IncomingMessage`, a framework request, or any other platform object.

If the platform can determine a trusted client address, set the `WSKit-Client-IP` header on the request you pass to `handleUpgrade`. Leave it out when the address is unknown or cannot be validated. The [Upgrade guide](/server/server/upgrade#client-ip) explains how application code reads it.

### Decide the upgrade

Hand the request to `engine.handleUpgrade(request)`. It returns an `UpgradeDecision`: `reject` (with optional `code`/`reason`), or an accept carrying the connection `userId`, `meta`, and `tags`.

```ts [upgrade.ts]
const decision: UpgradeDecision = await engine.handleUpgrade(request)
if (decision.reject) {
  // close or respond with decision.code / decision.reason
  return
}
```

`decision.code` on a reject is already safe to put on the wire. A value in `400`–`599` is an HTTP rejection status. Any other present code is a valid WebSocket close code, so accept the socket only long enough to close it with that code and reason. If app code supplied an invalid rejection value, the engine has already logged it and returned the generic HTTP `403` decision. Do not add a second close-code validator or a platform-specific fallback around an engine decision.

### Build a connection descriptor

For an accepted socket, build a `ConnectionDescriptor` — the low-level callbacks the engine uses to push data out. `backpressureSupported` tells the engine whether `bufferedAmount()` reports real outbound pressure; set `false` when your platform does not expose it.

```ts [descriptor.ts]
const descriptor: ConnectionDescriptor = {
  send: (data) => socket.send(data),
  close: (code, reason) => socket.close(code, reason),
  bufferedAmount: () => socket.bufferedAmount,
  backpressureSupported: true,
  userId: decision.userId ?? '',
  meta: decision.meta ?? {},
  tags: decision.tags ?? [],
}
```

The engine applies the WebSocket close-code rule and close-reason byte limit to an accepted descriptor before it calls `close()`. Your callback receives a valid outbound code (including `1000` when the caller omitted one), so keep it focused on the platform's socket API. Use `normalizeCloseReason()` only when the adapter closes a socket outside the engine, such as rejecting an upgrade before `engine.accept()` runs.

`send()` may return `false` when the adapter deliberately did not put the frame on the wire. The engine uses that result to skip `afterSend` work. `bufferedAmount()` must report the platform's actual outbound buffer, and `backpressureSupported` must be `true` only when that value represents usable pressure information.

### Accept the connection

Pass the socket key and descriptor to `engine.accept(...)`. It returns a `ConnectionHandle` — the callbacks **you** call when the socket sees traffic.

```ts [accept.ts]
const connection: ConnectionHandle = engine.accept(socket, descriptor)
```

### Forward socket events

Wire your platform's `message`, `close`, and `error` events to the handle. WSKit only supports string frames today; reject binary.

```ts [wire.ts]
socket.addEventListener('message', (event) => {
  if (typeof event.data === 'string') {
    connection.handleMessage(event.data)
  } else {
    socket.close(
      CloseCodes.UNSUPPORTED_DATA,
      '[wskit] binary frames are not supported yet',
    )
  }
})
socket.addEventListener('close', (event) => {
  connection.handleClose(event.code, event.reason)
})
socket.addEventListener('error', (event) => {
  connection.handleError(event)
})
```

The three handle methods return promises. Observe rejected promises, but do not serialize unrelated socket events unless the platform itself requires that ordering. A peer close code is an observation, not an outbound command: forward it unchanged, even when it is a value such as `1006` that cannot appear in a close frame you send. If accepting the socket or wiring its events fails, close the socket with `CloseCodes.INTERNAL_ERROR` (`1011`) and clean up the connection.

## Startup, alarms, and shutdown

A few more engine calls complete the adapter:

- `await engine.initialize()` — run once when the instance comes up, before accepting connections. It loads durable state.
- `engine.usesHibernation()` — `true` when the definition opted into hibernation, so you take the hibernatable accept path.
- `engine.setInstanceId(id)` — call before accepting connections when your adapter has multiple addressable instances. Use a stable identifier from the platform so connection and user references cannot be confused across instances.

Right after `initialize()`, tell the engine which connections survived the cold start. Which call you make depends on whether the platform supports hibernation:

- **Not hibernating** — call `engine.reconcileConnections(new Set())`. Nothing carries over between instances, so this wipes any leftover connection rows.
- **Hibernating** — `await engine.restoreHibernatedConnections(sockets)`, passing every socket the platform still holds open (on Cloudflare, `ctx.getWebSockets()`). It wakes each socket through the engine, rebuilding its identity, tags, and channel membership so a broadcast reaches it even before it sends anything, then drops rows for any socket that did not survive. The Promise rejects if a socket cannot be restored, so do not handle events until it completes. This calls `reconcileConnections` internally, so do not call both.

Two more calls round out the connection lifecycle:

- `engine.handleHibernationWake(socket)` — on a hibernating platform, wake **one** socket on demand (from inside your `message`/`close`/`error` callback) and get its `ConnectionHandle` back, instead of holding a handle in memory the way a non-hibernating adapter does.
- `await engine.handleAlarm()` — call from the platform's timer/alarm callback to fire due durable timers.
- `await engine.handleShutdown()` — run every `onShutdown` hook and close every socket cleanly when you want to drain the instance. On a hibernating platform, call `engine.handleHibernationWake(...)` for every socket the platform still holds **before** calling `handleShutdown()` — a freshly woken instance only knows about sockets it has already wakened, so skipping this step leaves hibernated sockets stuck open. If your adapter is about to close the `storage` or `timers` bindings because its process is ending, call `await engine.handleShutdown({ terminal: true })` instead. This cancels WSKit's own pending alarm retries before those bindings close. Keep the plain call for a temporary drain on platforms that may handle more work later, such as a Durable Object.

Your `TimerProvider` must restore its stored alarm when the instance starts and re-arm it after a restart. The engine owns retries for scheduled-task handlers and durable engine hooks. It normally completes `engine.handleAlarm()` after scheduling that work, even when a task or hook failed. A rejected `engine.handleAlarm()` instead means the delivery could not complete, for example because the engine could not persist its next shared alarm. If your platform has a native alarm-delivery retry policy, follow it for that rejection. Do not turn that platform delivery retry into another retry policy for scheduled task handlers.

## Exposing the admin surface

`engine.admin()` returns the [admin context](/server/admin/context) with the app's own [`api`](/server/admin/authoring) merged in — built-in members win on a name clash. Your adapter decides how outside code reaches it.

An in-process service can return this whole object. A serializing boundary must project it into methods that accept and return plain data. Do not expose grouped managers or connection refs directly. The engine also rejects app API names that are reserved by the admin object or JavaScript itself, especially `then`, because a thenable admin object makes `await admin()` behave incorrectly.

If your service runs **in the same process** as the caller, hand it back whole. Nothing is copied, so the managers work as they do inside a handler:

```ts [in-process.ts]
setup(createEngine, options) {
  const engine = createEngine({ /* ... */ })
  return {
    admin: () => engine.admin(),
    // ...the rest of your service
  }
}
```

If your platform puts a **serializing boundary** between the caller and the engine — Cloudflare's Worker→Durable Object RPC is the shipped example — the context cannot cross as-is. Grouped members (`connections`, `users`, `channels`) are objects, and snapshots carry methods like `ConnectionInfo.ref()`; neither survives being copied. Project what you want to expose onto flat methods that take and return plain data, the way the Cloudflare adapter does with `listConnections()`, `sendToConnection(id, …)`, and `channelBroadcast(name, …)`.

`ADMIN_CONTEXT_MEMBERS` tells the two layers apart: any key on the returned surface that is **not** in that set came from the app's own `api`, so that is what you forward.

```ts [split.ts]
import { ADMIN_CONTEXT_MEMBERS } from '@wskit/server/adapters'

const surface = engine.admin()
const appMethods = Object.entries(surface).filter(
  ([key, value]) =>
    typeof value === 'function' && !ADMIN_CONTEXT_MEMBERS.has(key),
)
```

### Typing what your `server()` returns

`adapter<TOptions, TService>` fixes `TService` up front, and TypeScript cannot make it depend on the server definition's `api` type. So the app's admin methods do not reach the caller's types on their own.

The fix is a thin generic wrapper: keep `TService` as your base shape, and have your package's public `server(...)` re-type the result from the server definition it was given. `ApiOf<TDefinition>` reads the `api` type off the definition, and `MetaOf<TDefinition>` reads the connection metadata type — the latter matters when your service returns connection snapshots, because a `Record<string, unknown>` meta is not something a serializing boundary can accept.

```ts [typed-server.ts]
import type {
  ApiOf,
  MetaOf,
  ServerDefinition,
} from '@wskit/server/adapters'

export function server<TDefinition extends ServerDefinition>(
  definition: TDefinition,
  options: MyOptions,
): MyService<ApiOf<TDefinition>, MetaOf<TDefinition>> {
  return build(definition, options) as MyService<
    ApiOf<TDefinition>,
    MetaOf<TDefinition>
  >
}
```

Inside `setup`, `createEngine` already hands you an `Engine<TApi>`, so `engine.admin()` is typed there without any of this.

The `TOptions` generic is the adapter's option type, while `TApi` comes from the server definition. The public wrapper should preserve `ApiOf<TDefinition>` and `MetaOf<TDefinition>` without making application code provide those generics manually.
