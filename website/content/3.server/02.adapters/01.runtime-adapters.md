You write a server once with `server`, capabilities, handlers, and `assemble`. The result is a **server definition**. A server definition is a frozen description of your server. It knows your contract, but it does not know how WebSockets run on your platform. An **adapter** is the package that connects a server definition to one runtime, such as Node.js or Cloudflare.

The same definition can run on different platforms. Only the adapter changes.

**Part 1: the definition.** This part does not depend on any platform. It uses `server`, capabilities, handlers, and `assemble`. It knows your contract but never names a runtime.

```ts [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import * as v from 'valibot'

const base = server({
  capabilities: [
    emits({ 'user-renamed': t<{ userId: string; name: string }>() }),
  ],
})

const handleRename = base.on('rename', {
  input: v.object({ name: v.string() }),
  run(ctx, input) {
    ctx.user.setMeta({ name: input.name })
    ctx.broadcast('user-renamed', {
      userId: ctx.user.id,
      name: input.name,
    })
  },
})

export const huddle = base.assemble({ handlers: [handleRename] })
```

**Part 2: the adapter.** The adapter turns that definition into something your runtime can run. You give the same `huddle` to the adapter for your platform. This example shows Node.js and Cloudflare:

::code-group

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const httpServer = createServer((request, response) => {
  response.writeHead(404).end()
})
const { bind, ready } = setup()
const huddleEndpoint = bind(huddle, { sql: './data/huddle.sqlite' })

httpServer.on('upgrade', (request, socket, head) => {
  huddleEndpoint.upgrade(request, socket, head)
})

await ready()
httpServer.listen(3000)
```

```ts [worker.ts]
import { bind } from '@livething/server-cloudflare'
import { huddle } from './server/huddle-definition'

// Cloudflare's bind(...) turns the definition into a Durable Object class.
export class HuddleServer extends bind(huddle) {}
```

::

You can give the same `huddle` definition to any adapter. When you switch platforms, only the adapter file changes. Your `server` and handler code stays the same.

::note
To learn how the definition itself is built (`server`, capabilities, event handlers, `assemble`), see [the server() overview](/server/server/overview). This chapter covers only the last step: running a finished definition.
::

## What an adapter does

An adapter does the platform-specific work that a definition leaves out on purpose:

- It accepts or rejects each new connection. A connection opens with a WebSocket upgrade (the HTTP request that a client sends to open a WebSocket) or, when the app lists [`http()`](/server/adapters/transports), with a stream request. The `transports` option of `bind()` says which ones the adapter accepts.
- On `http()`, it serves the stream, the client's POST requests and the CORS preflight, and it gives the engine each POSTed message as if it came from a socket.
- It gives your `authenticate(request)` function a standard Web API `Request`. The URL, method, headers, cookies, and the request's abort signal stay the same.
- It sends outgoing frames to each connection, and it closes connections when LiveThing asks it to.
- It gives your handlers the platform's storage, timers, logger, and raw platform object, as `ctx.sql`, `ctx.kv`, `ctx.schedule`, `ctx.log`, and `ctx.platform`. Runtime-specific bindings stay on the adapter's platform object.
- It declares whether the platform supports **hibernation** and **outbound backpressure**, so the engine can adjust to the platform. Hibernation means the platform can unload your server from memory while its sockets stay open. Outbound backpressure means the platform reports how much outgoing data is still waiting in a socket's buffer.

The **engine** is the LiveThing runtime that the adapter builds from your definition. The adapter handles platform input and output. The engine handles LiveThing's own rules. For example:

- The engine checks every close that your application requests before that close reaches an accepted socket.
- The engine runs the retries for scheduled-task handlers. When a task still fails after its last retry, the engine moves it to a dead-letter list. The engine also retries its own durable internal work.
- When `engine.handleAlarm()` rejects, an adapter may use its platform's normal alarm retry. An adapter must not add its own retry policy for a scheduled-task handler.

Hibernation and backpressure depend on the adapter. So two adapters that run the same definition can behave differently. The definition states what you want, and the engine matches that with what the adapter supports. Cloudflare supports hibernation but does not report the outgoing buffer size of a WebSocket. So on a Cloudflare WebSocket, `ctx.stream.drain()` does nothing and returns at once. The Node and Bun adapters report the real buffer size, and so does Cloudflare for an `http()` stream, so there `drain()` makes a stream generator wait until the buffer has room. [Capability negotiation](/server/under-the-hood/capability-negotiation) explains how this matching works.

You can move the server definition and its TypeScript contract between platforms. Runtime behavior still depends on the adapter:

| Capability                              | Cloudflare Durable Objects                                                                                   | Node.js                                                                 |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| Transports                              | WebSocket, and `http()` (server-sent events and POST requests)                                               | WebSocket, and `http()` (server-sent events and POST requests)          |
| Hibernation                             | Supported when the definition enables it, for WebSocket only; an open `http()` stream keeps the object awake | Not supported; a definition that enables it fails during initialization |
| Outbound backpressure                   | Not reported for a WebSocket, so `ctx.stream.drain()` resolves at once; reported for an `http()` stream      | Supported through the live buffer of the WebSocket or the stream        |
| Storage durability                      | Durable Object instance storage                                                                              | Depends on the SQLite source you configure; the default is in-memory    |
| Admin access                            | The same admin shape, through RPC targets                                                                    | The full admin context, in the same process                             |
| Direct platform access (`ctx.platform`) | Durable Object state and runtime bindings                                                                    | Nothing extra; your application keeps its own Node HTTP server          |

Storage and timers are contracts that the adapter provides. The definition can use their APIs, but the adapter decides how long data lives, what the limits are, whether data is saved to disk, and what happens after a restart.

## Adapter packages

| Adapter package                | Runtime                    |
| ------------------------------ | -------------------------- |
| `@livething/server-cloudflare` | Cloudflare Durable Objects |
| `@livething/server-bun`        | Bun                        |
| `@livething/server-node`       | Node.js                    |

Deno has no adapter of its own. The Node.js adapter can run on Deno through Deno's Node compatibility, with a `node:sqlite` database, but Deno is not a supported runtime. [Deno](/server/adapters/deno) has the setup.

The server code you write is the same for every adapter. Only the adapter entry file changes when you switch platforms. Each adapter has its own [install commands](/start/installation).

## Authoring an adapter

If your platform is not in the table above, you can write your own adapter. The building blocks are in a separate subpath:

```ts [adapter-imports.ts]
import { adapter } from '@livething/server/adapters'
import type {
  AdapterConfig,
  AuthDecision,
  ConnectionDescriptor,
  ConnectionHandle,
  Engine,
  EngineRuntimeOptions,
  Logger,
  ServerDefinition,
  StorageProvider,
  TimerProvider,
} from '@livething/server/adapters'
```

The `adapter` factory takes a config object. The config names your adapter, declares what your platform supports (such as hibernation), and has a `setup` callback. The `setup` callback connects your platform's connections, WebSocket or `http()`, to the engine. The [Custom adapters](/server/adapters/custom-adapters) page explains the full interface with a complete example.
