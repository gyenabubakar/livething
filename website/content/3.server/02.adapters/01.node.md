`@wskit/server-node` runs a WSKit server definition on [Node.js](https://nodejs.org). Your `define`, capabilities, handlers, and `assemble` code stays the same; the Node entry file creates a service and attaches it to a Node HTTP server.

For how to implement a custom adapter, see [Custom adapters](/server/adapters/custom-adapters).

## Install

```bash [pnpm]
pnpm add @wskit/server @wskit/server-node @wskit/core
```

The adapter uses [the `ws` package](https://github.com/websockets/ws) for the WebSocket server and `better-sqlite3` for its default SQL provider. They are installed as adapter dependencies. WSKit requires Node.js 24 or newer. `better-sqlite3` 12.11.1 provides prebuilt binaries for Node.js LTS releases; on an unsupported OS or CPU target, installation falls back to `node-gyp` and requires a native C/C++ build toolchain.

## Create the service

`server(handler, options)` returns a live service object:

```ts [server.ts]
import { server } from '@wskit/server-node'
import { chatHandler } from './handler'

const service = server(chatHandler, {
  port: 3000,
  sql: './data/chat.sqlite',
})

await service.ready
```

The options must contain exactly one server ownership choice:

- `port` makes WSKit create, listen on, and later close a Node HTTP server.
- `server` attaches WSKit to an existing `node:http` `Server`, such as one created by your application.

Do not pass both. When you pass an existing server, WSKit only registers its WebSocket upgrade listener; your application keeps control of ordinary HTTP requests and server shutdown.

When WSKit owns the server, ordinary HTTP requests receive `404`. WSKit only handles WebSocket upgrades; it is not an HTTP router.

## Runtime configuration and the upgrade request

The Node adapter does not copy environment variables into WSKit context. Read Node configuration from `process.env` in your Node entry point, or pass explicit values into the handler or plugin factory that needs them:

```ts [node-config.ts]
const apiUrl = process.env.API_URL ?? ''
const service = server(chatHandler, { port: 3000 })
```

The `upgrade(request)` function receives a complete standard Web API `Request`, built from Node's `IncomingMessage`. It contains the request URL, method, headers, cookies, and an abort signal connected to the request/socket lifetime:

```ts [handler.ts]
async upgrade(request) {
  const url = new URL(request.url)
  const token = request.headers.get('authorization')
  const cookie = request.headers.get('cookie')
  const clientIp = request.headers.get('WSKit-Client-IP')

  // authenticate and return the connection identity
}
```

The adapter supplies no body (`body: null`) because this is an upgrade request. See [Upgrade](/server/define/upgrade) for the return and rejection rules.

## Client IP

Node does not have one universally correct end-user IP. Configure the adapter only when you know how your deployment reaches Node:

```ts [direct.ts]
const service = server(chatHandler, {
  port: 3000,
  clientIp: { mode: 'direct' },
})
```

`direct` reads the TCP peer address. If Node is behind a proxy, that value may be the proxy's address.

For a trusted proxy chain, configure the proxy networks explicitly:

```ts [proxy.ts]
const service = server(chatHandler, {
  port: 3000,
  clientIp: {
    mode: 'proxy',
    trustedProxies: ['127.0.0.1/32', '10.0.0.0/8'],
  },
})
```

The adapter uses the forwarded address only when the chain starts at a trusted proxy and can be validated. If it cannot safely determine the client address, it omits `WSKit-Client-IP`. The header is a WSKit convention; it is not a standard `Request` property.

## Storage and timers

The default SQL source is an in-memory `better-sqlite3` database. With the default providers, SQL, KV, and scheduled-timer state disappears when the process exits, so this setup is useful for development rather than persistence.

Use a file path for persistence across restarts:

```ts
const service = server(chatHandler, {
  port: 3000,
  sql: './data/wskit.sqlite',
})
```

When no `kv` provider is supplied, Node stores `ctx.kv` in the same SQLite database as `ctx.sql`. If you inject a custom `SQLProvider`, also inject a `KVProvider`; WSKit cannot create its default KV table without a SQLite database it controls.

The timer provider stores the current durable alarm in SQL and restores it when the service starts. A persistent SQL source is therefore required if scheduled work must survive a process restart.

If alarm delivery itself fails — including a rejected `engine.handleAlarm()` call — Node makes up to six more delivery attempts, after 2, 4, 8, 16, 32, and 64 seconds. This is the same delivery retry limit Cloudflare uses. A later `setAlarm()` call starts a fresh delivery budget. If all seven deliveries fail, Node leaves the alarm row in SQL without adding a row to the scheduled-task DLQ: it does not know which scheduled task, if any, caused the delivery failure. The alarm can be delivered again after a later `setAlarm()` call or a server restart.

This is separate from product scheduled-task failures. When your scheduled handler throws, the engine uses the retry policy you declared with `scheduled({...})` and moves the failed task run to its DLQ when that policy runs out. `ctx.kv` TTL values are milliseconds.

::warning
**Node cannot run scheduled tasks while your Node server is offline.** A file-backed database keeps pending work safe, but the timer can only fire while the Node server is running. Work that became due during downtime runs after the server starts again.

If a job must run during an outage instead of catching up later, use a durable queue or an external scheduler that can start or notify a worker independently of this Node process.
::

You can also pass an existing `better-sqlite3` database or your own SQL/KV providers through the server options. WSKit closes databases it created; it does not close injected resources.

## WebSocket behavior

The adapter forwards text frames, close events, and errors to the engine. Binary frames are closed with `CloseCodes.UNSUPPORTED_DATA` (`1003`) because WSKit currently accepts string frames only. Incoming close events are observations from the peer, so the adapter forwards their code unchanged; the engine only validates outbound close commands before asking Node to send them.

Node exposes the live `ws.bufferedAmount`, so `ctx.stream.drain()` can pace outbound work against real socket pressure. This differs from Cloudflare, where buffer fullness is not exposed and `drain()` is a no-op.

Node does not support hibernation. If the definition enables hibernation, the service fails during initialization instead of silently running with different behavior.

## Admin and shutdown

The Node admin surface is in-process:

```ts
const service = server(chatHandler, { port: 3000 })

const admin = await service.admin()

await admin.purgeUser('user_9')

const count = admin.connectionCount
```

`service.admin()` resolves to the full admin context plus the custom methods from the definition's `assemble({ api })`. Await it once before using the returned object normally. Protect routes that call it with your normal application authentication; WSKit does not add an admin auth layer.

The custom admin API is inferred from the handler. `server(handler, options)` carries `ApiOf<typeof handler>` into `service.admin()`, so you do not need to provide an admin generic argument yourself. Custom method arguments and return types remain checked by TypeScript.

For an owned server, the adapter listens for `SIGINT` and `SIGTERM` by default. Shutdown waits for in-flight upgrades, runs `onShutdown` hooks, closes connected WebSockets cleanly, stops timers, closes WSKit-owned storage, and closes the owned HTTP server. Set `shutdownOnSignal: false` when the host process owns signal handling.

## Node platform escape hatch

Most handlers should use the portable WSKit context. When Node-specific access is needed, cast `ctx.platform` to the exported `Platform` type:

```ts
import type { Platform } from '@wskit/server-node'

const platform = ctx.platform as Platform
platform.server // node:http Server
```

Keep this code at the runtime edge so the rest of the definition remains portable.
