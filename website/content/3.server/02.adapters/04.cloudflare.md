`@livething/server-cloudflare` turns a server definition into a Cloudflare **Durable Object** class. A Durable Object is a small server that Cloudflare runs for you, and that keeps its own state (data that stays between requests). Each Durable Object has a unique ID, and Cloudflare runs at most one instance for each ID. Each instance owns its own WebSocket connections, its own SQLite-backed storage, and its own scheduled **alarm** (a timer that Cloudflare fires even when the instance is not in memory). This makes one instance a good fit for one room, one document, one game, or any other unit of shared state.

This page sets one up from start to finish: the server definition, the Durable Object class, the Worker `fetch` entry point, the environment binding, and the `wrangler.jsonc` config. A **Worker** is Cloudflare's serverless function. It receives every HTTP request for your app first. **Wrangler** is Cloudflare's command-line tool for running and deploying Workers.

::note
Install with `npm install @livething/server @livething/server-cloudflare @livething/core` (or the same command in your package manager). `@livething/server` is a peer dependency of the adapter, so you install it yourself. See [Installation](/start/installation).
::

## The whole picture

Four files, each with one job.

::steps

### Write the server definition

This is your server definition. It does not depend on any platform, and nothing here mentions Cloudflare.

```ts [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'

const base = server({
  capabilities: [
    emits({ 'user-renamed': t<{ userId: string; name: string }>() }),
  ],
})

const handleRename = base.on('rename', {
  input: v.object({ name: v.string() }),
  run(ctx, input) {
    ctx.user.setMeta({ name: input.name })
    ctx.user.broadcast('user-renamed', {
      userId: ctx.user.id,
      name: input.name,
    })
  },
})

export const huddle = base.assemble({
  handlers: [handleRename],
})

export type HuddleSocket = InferClient<typeof huddle>
```

### Turn it into a Durable Object class

`bind(definition)` returns a Durable Object **class**, not an instance. Export it from your Worker module. Cloudflare then creates one instance of the class for each ID you ask for with `idFromName(...)`.

```ts [worker.ts]
import { bind } from '@livething/server-cloudflare'
import { huddle } from './server/huddle-definition'

export class HuddleServer extends bind(huddle) {}
```

::warning
**Use a class declaration, not `export const`.** `wrangler types` writes your binding as `DurableObjectNamespace<import("./worker").HuddleServer>`, which needs a **type** named `HuddleServer`. A `const` exports only a value, so that reference finds no type and the binding becomes `any`.

TypeScript shows no error in this case. It stops checking the calls instead. Every `stub.fetch()`, `stub.shutdown()`, and `stub.admin()` call goes unchecked, including the method names and argument types of your own [admin `api`](/server/admin/authoring). (A **stub** is the object your Worker uses to call one Durable Object instance.) `skipLibCheck` is on in most Worker setups, and it also hides the broken reference, so you see no warning anywhere.

```ts
export class HuddleServer extends bind(huddle) {} // ✓ typed stub
export const HuddleServer = bind(huddle) // ✗ stub silently becomes any
```

::

### Send requests to it from the Worker `fetch`

The Worker's default export receives every HTTP request. Choose a Durable Object ID (here, from a `room` query parameter), get the stub for that ID, and forward the request to it. The adapter handles the WebSocket upgrade inside the Durable Object.

```ts [worker.ts]
export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url)
    const room = url.searchParams.get('room') ?? 'default'

    const id = env.HUDDLE_SERVER.idFromName(room)
    return env.HUDDLE_SERVER.get(id).fetch(request)
  },
} satisfies ExportedHandler<Env>
```

### Bind the class in `wrangler.jsonc`

A **binding** connects a name on `env` to a Cloudflare resource. The binding name (`HUDDLE_SERVER`) is the property you read on `env`. The `class_name` is the exported class. List each new Durable Object class in a `migrations` entry under `new_sqlite_classes`, so that it gets SQLite storage.

```jsonc [wrangler.jsonc]
{
  "name": "huddle",
  "main": "src/worker.ts",
  "compatibility_date": "2026-04-07",
  "compatibility_flags": ["nodejs_compat"],
  "durable_objects": {
    "bindings": [
      { "name": "HUDDLE_SERVER", "class_name": "HuddleServer" },
    ],
  },
  "migrations": [
    { "tag": "v1", "new_sqlite_classes": ["HuddleServer"] },
  ],
  "observability": {
    "enabled": true,
    "logs": { "head_sampling_rate": 1 },
  },
}
```

::

That is a complete deployment. `wrangler dev` runs it on your machine, and `wrangler deploy` deploys it to Cloudflare.

::caution
Treat `migrations` as a history of changes, not as a list of your current classes. Cloudflare uses each `tag` to remember which migrations it has already applied, and it applies each tag only once per environment. When you add a new Durable Object class to an app that is already deployed, add a **new** entry with a new `tag` and list the class under its `new_sqlite_classes`. Do not add the class to an existing tag, and do not edit `v1` after you deploy it: Cloudflare has already applied that tag, so it will not apply your change.
::

## The `compatibility_date` requirement

LiveThing requires a `compatibility_date` of **`2026-04-07` or later**. Do not use an earlier date.

```jsonc [wrangler.jsonc]
{
  "compatibility_date": "2026-04-07",
}
```

To close a WebSocket, one side sends a close message and the other side answers with its own close message. This exchange is the **close handshake**. From `2026-04-07`, the Workers runtime answers a close that the client starts. With an earlier date it does not answer, so a client that calls `socket.disconnect()` (or `ws.close()`) can wait until a timeout instead of closing quickly. Closes that the server starts work the same on any date.

::tip
Keep the `nodejs_compat` flag turned on. The adapter imports `node:async_hooks` to keep context for each request across `await` calls, and this import needs the flag.
::

## What the server receives

The adapter passes the original Web API `Request` to your definition's `upgrade(request)` function. The URL, method, headers, cookies, and request signal are all still there, so your authentication code can use the same standard `Request` APIs that it would use in a Worker.

Cloudflare does not add an IP property to `Request`. When the `CF-Connecting-IP` header is present, the adapter copies its value into a `LiveThing-Client-IP` header before it calls `upgrade(request)`. The adapter first removes any `LiveThing-Client-IP` header that the client sent, so a client cannot fake its address. When Cloudflare has no address to give, the adapter leaves that header out. See [reading the client IP](/server/server/upgrade#client-ip) to use it in your code.

The Durable Object only handles WebSocket upgrades. A request without `Upgrade: websocket` gets the response `426 Expected Upgrade: websocket`. Put normal HTTP routes in the Worker.

After a socket opens, the adapter passes Cloudflare's `webSocketMessage`, `webSocketClose`, and `webSocketError` Durable Object callbacks directly to the engine. There is no extra parsing or routing step between them.

LiveThing accepts text (string) messages only. If a client sends a binary frame, the adapter closes the socket with `CloseCodes.UNSUPPORTED_DATA` (`1003`, unsupported data) and the reason `[livething] binary frames are not supported yet`. This is the same with and without hibernation. Send JSON (or any other text format) from the client instead.

::tip
`ctx.log` writes with `console.log`, `console.warn`, and `console.error`. Turn on `observability.logs` in `wrangler.jsonc` (as in the config above) to see these logs in the Cloudflare dashboard and in `wrangler tail`.
::

## Bindings and runtime configuration

The `name` you give a Durable Object binding in `wrangler.jsonc` is the property you read on `env`. Add it to your `Env` type so that `env.HUDDLE_SERVER` is typed:

```ts [env.d.ts]
interface Env {
  HUDDLE_SERVER: DurableObjectNamespace<
    import('./worker').HuddleServer
  >
}
```

The handler context has no environment field that works on every platform. In the Worker entry point, read bindings from the `env` argument as usual. Inside a Durable Object handler, use `ctx.platform` with the adapter's `Platform<Env>` type when you need a binding such as a KV namespace, a secret, or another Durable Object. The `ctx.platform` section below shows an example.

::tip
`wrangler types` writes this `Env` interface for you from `wrangler.jsonc`, including the `DurableObjectNamespace<...HuddleServer>` type. Run it again each time you add or rename a binding.
::

## Storage and instance scope

`ctx.sql` and `ctx.kv` belong to the current Durable Object instance. They are not global stores. Two IDs created with `idFromName(...)` have separate connections and separate storage.

Cloudflare's SQLite limits are lower than those of normal SQLite. The adapter tells the engine the real limits, so the queries LiveThing builds stay inside them:

- 100 bound parameters per statement
- 100 KB of SQL statement text
- 2 MB for one stored value or row

`ctx.sql.transaction(...)` is atomic (all its writes happen, or none do). It needs the runtime's `storage.transactionSync()` support. If the runtime does not have it, the adapter throws a clear error. It never runs the callback without a transaction. `ctx.kv` TTL (time-to-live) values are in milliseconds. The adapter removes an expired value when you read it or list it.

Scheduled work uses the Durable Object `alarm()` method. When a scheduled task is due, Cloudflare calls `alarm()`, and the adapter passes the call to LiveThing's timer system, which keeps its timers in storage.

## How it relates to hibernation

A Durable Object that only waits for the next WebSocket message still costs money while it stays in memory. **Hibernation** lets Cloudflare remove the instance from memory (evict it) while it keeps the sockets open at the edge (Cloudflare's network, which holds the client connections). Cloudflare loads the instance again only when a frame arrives.

The adapter turns hibernation on when your definition sets `hibernation: { enabled: true }`. You do not call a separate adapter method. With it on:

- The adapter accepts sockets with `ctx.acceptWebSocket(...)` (Cloudflare's hibernation API) instead of a plain `accept()`.
- Without `translate`, the adapter sets up an automatic reply at the edge: when the client sends `ping`, Cloudflare answers `pong`. So Cloudflare answers the client's keepalive messages without waking the instance. With [translation](/server/server/translation), the adapter turns this reply off. Then every message in both directions goes through the translator, and each keepalive `ping` wakes the instance.
- The server does not send its own pings under hibernation. So when you use the `keepalive()` capability, `ctx.latency` and `ctx.quality` are always `null` while hibernation is on. This is true the whole time, not only while the instance is evicted.
- The adapter saves each socket's connection ID in Cloudflare's WebSocket attachment (a small value that Cloudflare stores with each socket). LiveThing keeps the rest of the connection's state in a SQLite table. Both survive an eviction, and LiveThing uses them to restore the connection on wake.

```ts [hibernating-handler.ts]
import { emits, server, t } from '@livething/server'

const base = server({
  hibernation: { enabled: true },
  capabilities: [emits({ message: t<Message>() })],
})
```

::callout{icon="i-ph-moon-duotone" to="/server/server/hibernation"}
The **Hibernation** page explains what survives a hibernation cycle, the storage rules, and the full config.
::

## Graceful shutdown

Cloudflare does not send a shutdown signal. So the Durable Object class that the adapter returns has a `shutdown()` RPC method, which lets you **drain** an instance on purpose (close it cleanly, for example before a deploy or during maintenance). **RPC** (remote procedure call) means your Worker calls a method on the Durable Object through its stub, as if it were a normal method. `shutdown()` runs every `onShutdown` hook you registered and closes every open socket cleanly. Clients then reconnect to a fresh instance.

Call it from the Worker like any other Durable Object RPC method:

```ts [worker.ts]
export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url)
    const room = url.searchParams.get('room') ?? 'default'

    if (url.pathname === '/admin/drain') {
      const id = env.HUDDLE_SERVER.idFromName(room)
      await env.HUDDLE_SERVER.get(id).shutdown()
      return new Response(null, { status: 204 })
    }

    const id = env.HUDDLE_SERVER.idFromName(room)
    return env.HUDDLE_SERVER.get(id).fetch(request)
  },
} satisfies ExportedHandler<Env>
```

Protect a route like `/admin/drain` with your own auth check before you deploy it.

Under hibernation, `shutdown()` first wakes every hibernated socket through the engine, so the drain reaches all of them. A fresh instance starts with an empty list of connections in memory. Without the wake step, those clients would stay connected and never get the close.

## Admin over RPC

`stub.admin()` is asynchronous because the call goes from the Worker to the Durable Object over RPC. It returns the built-in admin operations together with the custom `api` methods from your server definition.

The returned object is built for RPC. The connection and channel managers become flat methods such as `listConnections()`, `sendToConnection()`, and `channelBroadcast()`. Their arguments and results must be serializable (plain data that can be copied between the Worker and the Durable Object). The connection snapshots do not include the `ref()` method. See [Reaching the admin surface](/server/admin/reaching-it) for the full list and for how to protect it with auth.

## Extending the Durable Object class

`bind(...)` returns a real class. You can `extend` it to add your own RPC methods. If you add a constructor, call `super(ctx, env)` first.

```ts [worker.ts]
import { bind } from '@livething/server-cloudflare'
import { huddle } from './server/huddle-definition'

const Base = bind(huddle)

export class HuddleServer extends Base {
  async memberCount(): Promise<number> {
    const admin = await this.admin()
    return admin.connectionCount()
  }
}
```

The Worker can call the new `memberCount()` method as a Durable Object RPC method, next to the built-in `shutdown()` and `admin()`.

## The direct Cloudflare access point: `ctx.platform`

Most handler code should use the LiveThing APIs: `ctx.sql`, `ctx.kv`, and `ctx.schedule`. When you need a Cloudflare feature that LiveThing does not wrap, use `ctx.platform`. It gives you the Durable Object state and your env bindings.

`ctx.platform` has the type `unknown`, because the core engine does not depend on any platform. Cast it with the `Platform<Env>` type that the Cloudflare adapter exports. In this example, `ROOM_TOPICS` is a KV namespace binding in your `Env`, and `base` declares a `room-topic` event:

```ts [room-topic.ts]
import type { Platform } from '@livething/server-cloudflare'

const handleGetTopic = base.on('get-room-topic', {
  input: v.object({ room: v.string() }),
  async run(ctx, input) {
    const platform = ctx.platform as Platform<Env>
    const topic = await platform.env.ROOM_TOPICS.get(input.room)
    ctx.send('room-topic', { topic: topic ?? '' })
  },
})
```

`Platform<Env>` has two parts:

- `platform.ctx`: part of the Durable Object state. It has `getWebSockets(tag?)`, `blockConcurrencyWhile(...)`, `waitUntil(...)`, and `storage`.
- `platform.env`: your typed bindings.

`getWebSockets()` lists only the sockets accepted through the hibernation API, so it returns sockets only when hibernation is on. LiveThing does not add its own tags to Cloudflare's per-socket tag list, so `getWebSockets(tag)` with a LiveThing tag finds no sockets. Use [`ctx.connections`](/server/context-and-storage/connections) to find connections instead.

`waitUntil(...)` exists so the type matches Cloudflare's API, but it has no effect in a Durable Object. It does not make the instance live longer, and it does not change when a request completes.

Use `ctx.platform` only when the LiveThing APIs cannot do what you need. [Context and storage](/server/context-and-storage/overview) covers most needs with typed APIs.

## Running multiple server definitions

A real app often has more than one server definition. Huddle itself is one Durable Object class, but a bigger deployment can add more, each with its own contract — for example, the main chat server and a separate presence tracker. LiveThing has no `router()` API. You run several server definitions the normal Cloudflare way: one Worker `fetch`, several Durable Object classes, and a lookup on the request path.

### One class per server definition

`bind(...)` turns each server definition into its own Durable Object class:

```ts [servers.ts]
import { bind } from '@livething/server-cloudflare'
import { huddle } from './server/huddle-definition'
import { presence } from './server/presence-definition'

export class HuddleServer extends bind(huddle) {}
export class Presence extends bind(presence) {}
```

### Route in the Worker `fetch`

Match the path, choose the matching binding, and forward the request. When you have more than two routes, a lookup table is easier to read than many `if` statements:

```ts [worker.ts]
export { HuddleServer, Presence } from './servers'

type ServerBinding = 'HUDDLE_SERVER' | 'PRESENCE'

const ROUTES: Record<string, ServerBinding | undefined> = {
  '/huddle': 'HUDDLE_SERVER',
  '/presence': 'PRESENCE',
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url)
    const room = url.searchParams.get('room') ?? 'default'

    const bindingName = ROUTES[url.pathname]
    if (bindingName) {
      const namespace = env[bindingName]
      return namespace.get(namespace.idFromName(room)).fetch(request)
    }

    return new Response('not found', { status: 404 })
  },
} satisfies ExportedHandler<Env>
```

### Bind every class in `wrangler.jsonc`

Each class needs a binding. List each class under `new_sqlite_classes` in a `migrations` entry. For a new app, one `v1` tag can hold both:

```jsonc [wrangler.jsonc]
{
  "name": "app",
  "main": "src/worker.ts",
  "compatibility_date": "2026-04-07",
  "compatibility_flags": ["nodejs_compat"],
  "durable_objects": {
    "bindings": [
      { "name": "HUDDLE_SERVER", "class_name": "HuddleServer" },
      { "name": "PRESENCE", "class_name": "Presence" },
    ],
  },
  "migrations": [
    {
      "tag": "v1",
      "new_sqlite_classes": ["HuddleServer", "Presence"],
    },
  ],
}
```

Each `idFromName(room)` keeps rooms separate. `/huddle?room=lobby` and `/huddle?room=staff` are two Durable Object instances of the same `HuddleServer` class, with separate connections and separate storage. The `room` value can be anything that names an instance: a user ID, a room ID, or a tenant ID.
