[H3](https://h3.dev) is a small HTTP framework. [CrossWS](https://crossws.h3.dev) is the WebSocket library that H3 uses. CrossWS connects H3 to the WebSocket transport of the host. LiveThing has a separate binding for H3 v2 and for H3 v1. In both versions, H3 matches the URL, CrossWS runs the WebSocket connection, and LiveThing runs the endpoint after the upgrade.

| Host                    | Import                         | WebSocket transport | `clientIp`                                            |
| ----------------------- | ------------------------------ | ------------------- | ----------------------------------------------------- |
| H3 v2                   | `@livething/server-node/h3`    | CrossWS 0.4         | Available when the host provides the raw Node request |
| H3 v1, including Nuxt 4 | `@livething/server-node/h3/v1` | CrossWS 0.3         | Not supported                                         |

## H3 v2

Use `@livething/server-node/h3` with H3 v2 and CrossWS 0.4.

```bash [pnpm]
pnpm add @livething/server @livething/server-node @livething/core h3@^2.0.1-rc.31 crossws@^0.4.12
```

`h3` handles HTTP routing. `crossws` handles the WebSocket handshake and transport for H3. Install the versions shown here, because the transport APIs of H3 v1 and H3 v2 are different.

```ts [huddle-server.ts]
import { setup } from '@livething/server-node/h3'
import { serve } from 'crossws/server/node'
import { H3 } from 'h3/node'
import { huddle } from './server/huddle-definition'

const app = new H3()

const { bind, ready, shutdown } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})

app.get('/huddle', huddleEndpoint.connect)

await ready()

const server = serve({
  fetch: app.fetch,
  websocket: {},
  hostname: '127.0.0.1',
  port: 3000,
})

process.once('SIGTERM', async () => {
  await shutdown()
  await server.close()
})
```

H3 matches the route. Inside `authenticate(request)`, the definition can read the path or query string with `new URL(request.url)`.

When the definition rejects the upgrade with an HTTP response, CrossWS sends that response before the WebSocket handshake. When it rejects with a close code, CrossWS completes the handshake and then closes the socket with that code.

### Server-sent events

With [`sse()`](/server/adapters/node/node-http#server-sent-events) in `transports`, a plain `GET` to the `connect` route opens the server-sent events stream. Add `huddleEndpoint.handle` on the same path, for the `POST` requests and the CORS preflight:

```ts [huddle-server.ts]
import { sse, websocket } from '@livething/server-node'
import { setup } from '@livething/server-node/h3'
import { H3 } from 'h3/node'
import { huddle } from './server/huddle-definition'

const app = new H3()
const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocket(), sse()],
})

app.get('/huddle', huddleEndpoint.connect)
app.all('/huddle', huddleEndpoint.handle)
```

The stream needs the original Node request, so it works only when H3 runs on a Node server, such as the `serve()` of `crossws/server/node`. On a development server that gives the binding only a Web API `Request`, `handle` answers `500`.

### Client IP

The H3 v2 binding supports the same `clientIp` options as [`node:http`](/server/adapters/node/node-http#client-ip). This works only when the H3 host gives the binding its original Node request:

```ts
import { setup } from '@livething/server-node/h3'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  clientIp: { mode: 'direct' },
})
```

If your server runs behind a trusted proxy chain, use `mode: 'proxy'` and list the proxy networks in `trustedProxies`.

Some H3 development servers provide only a Web API `Request`. LiveThing still accepts WebSocket connections there, but it cannot read the raw socket address. If you set `clientIp` in that environment, the upgrade throws an error. LiveThing does not fall back to a header that the client could fake.

## H3 v1

Use `@livething/server-node/h3/v1` with H3 v1 and CrossWS 0.3.

```bash [pnpm]
pnpm add @livething/server @livething/server-node @livething/core h3@^1.15.11 crossws@^0.3.5
```

Nuxt 4 and Nitro 2 use these same major versions of H3 and CrossWS.

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { setup } from '@livething/server-node/h3/v1'
import nodeWebSocketAdapter from 'crossws/adapters/node'
import { createApp, createRouter, toNodeListener } from 'h3'
import { huddle } from './server/huddle-definition'

const app = createApp()
const router = createRouter()

const { bind, ready, shutdown } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})

router.get('/huddle', huddleEndpoint.connect)
app.use(router)

const websocket = nodeWebSocketAdapter(app.websocket)
const server = createServer(toNodeListener(app))
server.on('upgrade', websocket.handleUpgrade)

await ready()

server.listen(3000, '127.0.0.1')

process.once('SIGTERM', async () => {
  await shutdown()
  server.close()
})
```

H3 v1 gives the binding the request URL and headers, but not the original Node request. For this reason, this binding does not accept the `clientIp` option. Passing it is a type error. If your server must get a trusted client IP from the socket or from a proxy chain, use another Node binding.

H3 v1 also does not report when a client leaves while your asynchronous `authenticate(request)` check is still running. For example, a database permission check keeps running even after the browser has closed the connection, and LiveThing cannot cancel it early. When the check finishes, the connection can open for a short time: `onConnect` runs, and then `onDisconnect` runs when CrossWS reports the close. Keep upgrade checks short, and make them safe to finish after the client has left. If this work must stop as soon as the client leaves, use the H3 v2 binding.

With [`sse()`](/server/adapters/node/node-http#server-sent-events) in `transports`, a plain `GET` to the `connect` route opens the server-sent events stream. Add `huddleEndpoint.handle` to the router on the same path, for the `POST` requests and the CORS preflight:

```ts [huddle-server.ts]
import { sse, websocket } from '@livething/server-node'
import { setup } from '@livething/server-node/h3/v1'
import { createRouter } from 'h3'
import { huddle } from './server/huddle-definition'

const router = createRouter()
const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocket(), sse()],
})

router.get('/huddle', huddleEndpoint.connect)
router.use('/huddle', huddleEndpoint.handle)
```

When your `authenticate(request)` check rejects with an HTTP response, the client gets its status code and body, but no headers. CrossWS 0.3, the WebSocket library that H3 v1 uses, has a bug: it URL-encodes the headers of a refused upgrade, so `text/plain` would arrive as `text%2Fplain`. CrossWS fixed this in 0.4.5 ([crossws#186](https://github.com/h3js/crossws/issues/186)), but no 0.3 release has the fix, so the binding leaves the headers out. For example, a `RejectAuth(403, 'Forbidden')` reaches the client as a 403 with the body `Forbidden` and no `content-type` header. A rejection with a WebSocket close code works the same way as on H3 v2.

## Call the admin API from a route

The endpoint's [admin API](/server/admin/overview) runs in the same process as H3, so a normal H3 route can use it. For example, Huddle's moderators post an announcement from an internal dashboard:

::code-group

```ts [H3 v2]
import { H3 } from 'h3'
import { verifySession } from './auth'
import { huddleEndpoint } from './huddle-endpoint'

const app = new H3()

app.post('/admin/announcements', async (event) => {
  const token = event.req.headers
    .get('authorization')
    ?.replace(/^Bearer /i, '')
  const user = await verifySession(token) // your auth
  if (user?.role !== 'admin') {
    event.res.status = 401
    return null
  }

  const { text } = (await event.req.json()) as { text: string }

  const admin = await huddleEndpoint.admin()
  await admin.announce(text)
  event.res.status = 204

  return null
})
```

```ts [H3 v1]
import {
  createRouter,
  defineEventHandler,
  getHeader,
  readBody,
  setResponseStatus,
} from 'h3'
import { verifySession } from './auth'
import { huddleEndpoint } from './huddle-endpoint'

export function addAdminRoutes(
  router: ReturnType<typeof createRouter>,
) {
  router.post(
    '/admin/announcements',
    defineEventHandler(async (event) => {
      const token = getHeader(event, 'authorization')?.replace(
        'Bearer ',
        '',
      )
      const user = await verifySession(token) // your auth
      if (user?.role !== 'admin') {
        setResponseStatus(event, 401)
        return null
      }

      const { text } = (await readBody(event)) as { text: string }

      const admin = await huddleEndpoint.admin()
      await admin.announce(text)
      setResponseStatus(event, 204)

      return null
    }),
  )
}
```

::

In H3 v2, add the route to your `app`. In H3 v1, call `addAdminRoutes(router)`. Here `huddleEndpoint` is the endpoint from `bind(huddle, ...)`, exported from its own module (`huddle-endpoint.ts`) so the WebSocket route and the admin route share it. `announce` comes from Huddle's [admin `api`](/server/admin/authoring). The same object also has the built-in operations, such as `purgeUser` and `connectionCount`. An [admin call](/server/adapters/node/node-http#call-the-admin-api-from-your-app) skips every check that protects the socket side, so protect each admin route with your own auth.

## Message size limit

h3 creates the WebSocket server, so LiveThing does not set its limit. Set it in both places: give that server a [message limit](/server/adapters/node/node-http#message-size-limit), and pass the same value as the endpoint's `maxMessageBytes`. If you set only the server's limit, LiveThing still closes a connection with `1009` at its own 32 MiB default.

## Compression

CrossWS creates the `ws` server, so you turn on WebSocket compression (`permessage-deflate`) there, with `perMessageDeflate` in its `serverOptions`. LiveThing asks for every message it sends to be compressed, and `ws` does it when the client agreed to compression. With `perMessageDeflate: true`, `ws` compresses every message, even a small one: its size threshold works only when the context takeover options are off. To skip messages under 1 KiB, as LiveThing's own `compression` option does, pass this object as `perMessageDeflate` instead of `true`:

```ts
const perMessageDeflate = {
  threshold: 1024,
  serverNoContextTakeover: true,
  clientNoContextTakeover: true,
}
```

In H3 v2, put it under `websocket.options.node` in `serve()`:

```ts [huddle-server.ts]
import { serve } from 'crossws/server/node'
import { H3 } from 'h3/node'

const app = new H3()
const server = serve({
  fetch: app.fetch,
  websocket: {
    options: { node: { serverOptions: { perMessageDeflate: true } } },
  },
  hostname: '127.0.0.1',
  port: 3000,
})
```

In H3 v1, pass it to the CrossWS Node adapter:

```ts [huddle-server.ts]
import nodeWebSocketAdapter from 'crossws/adapters/node'
import { createApp } from 'h3'

const app = createApp()
const websocket = nodeWebSocketAdapter({
  ...app.websocket,
  serverOptions: { perMessageDeflate: true },
})
```

[Compression](/server/adapters/node/node-http#compression) helps JSON and text a lot, but not bytes that are already compressed, such as images, audio and video. It costs CPU and memory for every connection, so it is off by default.

## Server ownership

`setup()` does not create an HTTP server or listen on a port. Your application starts the server, and it closes the server after `shutdown()` finishes. If an upgrade request arrives after shutdown starts, the H3 v1 binding answers with HTTP 503. The H3 v2 binding closes the raw socket without a response when it has the Node request, and answers with HTTP 503 when the host gives it only a Web API `Request`.
