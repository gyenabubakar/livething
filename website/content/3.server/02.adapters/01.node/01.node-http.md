`@wskit/server-node` runs a WSKit definition on Node.js. Your application owns the HTTP server, its routes, and its signal handling. WSKit owns one endpoint's engine, storage, timers, connections, and shutdown work.

## Install

```bash [pnpm]
pnpm add @wskit/server @wskit/server-node @wskit/core
```

The adapter uses [`ws`](https://github.com/websockets/ws) for raw Node upgrades and `better-sqlite3` for its default SQL provider. They are normal adapter dependencies. WSKit requires Node.js 24 or newer.

## node:http

Call `setup()` once for the group of endpoints that should shut down together. Its `bind()` method creates one endpoint from one definition.

```ts [server.ts]
import { createServer } from 'node:http'
import { setup } from '@wskit/server-node'
import { chatDefinition } from './definition'

const { bind, ready, shutdown } = setup()
const chat = bind(chatDefinition, {
  sql: './data/chat.sqlite',
})

const app = createServer((request, response) => {
  response.statusCode = 404
  response.end()
})

app.on('upgrade', (request, socket, head) => {
  const url = new URL(
    request.url ?? '/',
    `http://${request.headers.host}`,
  )

  if (url.pathname === '/ws/chat') {
    chat.upgrade(request, socket, head)
    return
  }

  socket.destroy()
})

await ready()
app.listen(3000)

process.once('SIGTERM', async () => {
  await shutdown()
  app.close()
})
```

`chat.upgrade` does not match paths. That is your application's job. This keeps Node's basic API small and lets you choose any routing library or matching code. For framework routes and route parameters, use the matching framework entry point: `@wskit/server-node/hono`, `@wskit/server-node/fastify`, or `@wskit/server-node/h3`.

## Runtime configuration and the upgrade request

The Node adapter does not copy environment variables into WSKit context. Read Node configuration from `process.env` in your Node entry point, or pass explicit values into the server-definition or plugin factory that needs them.

The `upgrade(request)` function receives a standard Web API `Request`, built from Node's `IncomingMessage`. It contains the request URL, method, headers, cookies, and an abort signal. The signal aborts if the client leaves before the handshake finishes or when `shutdown()` begins:

```ts [definition.ts]
async upgrade(request) {
  const url = new URL(request.url)
  const token = request.headers.get('authorization')
  const cookie = request.headers.get('cookie')

  // authenticate and return the connection identity
}
```

The adapter supplies no body because this is an upgrade request. See [Upgrade](/server/server/upgrade) for return and rejection rules.

## Client IP

Read the client address in [`upgrade(request)`](/server/server/upgrade#client-ip). Node does not have one universally correct end-user IP, so configure the endpoint only when you know how your deployment reaches Node:

```ts
const chat = bind(chatDefinition, {
  clientIp: { mode: 'direct' },
})
```

`direct` reads the TCP peer address. If Node is behind a proxy, that value may be the proxy's address. For a trusted proxy chain, configure the proxy networks explicitly:

```ts
const chat = bind(chatDefinition, {
  clientIp: {
    mode: 'proxy',
    trustedProxies: ['127.0.0.1/32', '10.0.0.0/8'],
  },
})
```

The adapter uses a forwarded address only when the full chain starts at a trusted proxy and can be validated. Otherwise it omits `WSKit-Client-IP`.

## Storage, timers, and WebSockets

The default SQL source is an in-memory `better-sqlite3` database. Use a file path when SQL, KV, or scheduled work must survive a restart:

```ts
const chat = bind(chatDefinition, {
  sql: './data/wskit.sqlite',
})
```

When no `kv` provider is supplied, Node stores `ctx.kv` in the same SQLite database as `ctx.sql`. WSKit closes resources it creates but never closes injected SQL or KV resources.

The endpoint forwards text frames, close events, and errors to the engine. Binary frames close with `1003`; WSKit currently accepts string frames only. Raw Node endpoints expose the live `ws.bufferedAmount`, so `ctx.stream.drain()` can use real socket pressure.

Node does not support hibernation. A definition that enables hibernation fails during initialization.

## Admin and shutdown

The admin surface is in-process and belongs to the endpoint:

```ts
const admin = await chat.admin()

await admin.purgeUser('user_9')
const count = admin.connectionCount
```

`chat.admin()` includes the built-in admin context and custom methods from `assemble({ api })`. Its type is inferred from the server definition.

Your application decides when to stop. `shutdown()` waits for active upgrades, runs `onShutdown` hooks, closes connected WebSockets, stops timers, and closes WSKit-owned storage. It does not close your HTTP server or install signal handlers. If an upgrade arrives after shutdown begins but before your HTTP server closes, WSKit drops that socket without starting the definition.

## Authoring a Node integration

`@wskit/server-node/binding` is the public seam for authors of a Node WebSocket integration. Application code should use `setup()` from `@wskit/server-node` or a ready-made integration such as `@wskit/server-node/hono`.

The following Hono example builds an integration in small steps.

Start with the host's existing WebSocket setup and the outer shape of its binding:


Finally, return `{ upgrade, ready: endpoint.ready, admin: endpoint.admin }` from `bind()`, and return `{ websocket: { server }, bind, ready: node.ready, shutdown: () => lifecycle.shutdown(node.shutdown) }` from `setup()`. This complete sequence was run against real HTTP and WebSocket rejection paths, a successful connection, and a text message.

The application only binds the endpoint to its Hono route:

```ts [server.ts]
import { Hono } from 'hono'
import { chatDefinition } from './definition'
import { setup } from './hono-binding'

const app = new Hono()
const wskit = setup()
const chat = wskit.bind(chatDefinition, { sql: './data/chat.sqlite' })

app.get('/ws/:room', chat.upgrade)

await wskit.ready()
```

The application keeps its existing Hono Node bootstrap. Give that bootstrap `app.fetch` and `wskit.websocket` where it already configures Hono's WebSocket host. WSKit does not create, listen on, or close the server.

`lifecycle.prepare()` accepts Hono's original Node `IncomingMessage` and returns `undefined` when the request was cancelled before a decision or WSKit is already shutting down. In that case, destroy the Node socket and do not handshake. Otherwise it returns one of three results. Return `result.response` when it is `http`. For `socket`, complete the host handshake and close with its code and reason. For `accept`, complete the host handshake, pass its socket methods as a `ConnectionTransport` to `result.accept(transport)`, then forward text messages, close events, and errors through the returned connection.

`prepare()` removes any client-supplied `WSKit-Client-IP` header. A Fetch-based host may call `endpoint.prepare(request, { clientIp })` only after it has derived that address from trusted connection or proxy data. `prepareNode()` is for a host that has Node's `IncomingMessage`; it applies the endpoint's `clientIp` configuration itself.

You can bind several endpoints to the same server:

```ts
const chat = bind(chatDefinition, { sql: './data/chat.sqlite' })
const presence = bind(presenceHandler, {
  sql: './data/presence.sqlite',
})

app.on('upgrade', (request, socket, head) => {
  const pathname = new URL(
    request.url ?? '/',
    `http://${request.headers.host}`,
  ).pathname

  if (pathname === '/ws/chat')
    return chat.upgrade(request, socket, head)
  if (pathname === '/ws/presence')
    return presence.upgrade(request, socket, head)

  socket.destroy()
})
```

Wait for `ready()` before listening. It waits for every endpoint currently created through that setup. If you create endpoints later, wait for their individual `ready()` method before sending traffic to them.
