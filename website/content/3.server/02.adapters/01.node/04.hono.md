Use `@livething/server-node/hono` when Hono matches your routes. This binding does not create an HTTP server and does not start listening on a port. Your app does that with `@hono/node-server`.

```bash [pnpm]
pnpm add @livething/server @livething/server-node @livething/core hono @hono/node-server
```

```ts [server.ts]
import { createAdaptorServer } from '@hono/node-server'
import { setup } from '@livething/server-node/hono'
import { Hono } from 'hono'
import { huddle } from './server/huddle-definition'

const app = new Hono()

const { bind, ready, shutdown, websocket } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})

app.get('/huddle', huddleEndpoint.upgrade)

await ready()

const server = createAdaptorServer({
  fetch: app.fetch,
  websocket,
})

server.listen(3000)
```

`setup()` returns a `websocket` object. Pass it to `createAdaptorServer()` so that Hono's Node server can complete WebSocket handshakes.

## Custom WebSocket server

If your app already creates a `WebSocketServer` from the `ws` package, pass it to `setup()`. LiveThing uses that server and does not close it. The `websocket` object that `setup()` returns then holds your server, so pass `websocket` to `createAdaptorServer()` in the same way:

```ts
import { WebSocketServer } from 'ws'

const webSocketServer = new WebSocketServer({ noServer: true })
const { bind, ready, shutdown, websocket } = setup({
  webSocketServer,
})
```

## Routes and rejections

Your normal Hono middleware runs before the endpoint. LiveThing's [`upgrade(request)`](/server/server/upgrade) receives the full request URL, so read the query string or headers from it when the definition needs them:

```ts [server/huddle.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectUpgrade } from '@livething/server/errors'

const base = server({
  async upgrade(request) {
    const token = new URL(request.url).searchParams.get('token')
    const user = await verifySession(token)
    if (!user)
      throw RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')
    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
})
```

Call `bind()` once for each LiveThing definition. Then pass that endpoint's `upgrade` handler to its Hono route.

The LiveThing route only handles WebSocket upgrade requests. A plain HTTP request to the same path goes to the next Hono handler, and your `upgrade` hook does not run. If no other handler matches, Hono answers `404`.

`upgrade(request)` can reject a connection in two ways:

- **HTTP rejection** (a status from `400` to `599`). The binding returns it as a Hono response, before the WebSocket handshake. When the client sent a WebSocket upgrade request, `@hono/node-server` sends the status and headers of that response, but not its body.
- **Close-code rejection** (a WebSocket close code). The binding completes the handshake, then closes the socket with that code.

## Client IP

Hono's Node server gives this binding the original Node request. So `clientIp` works the same way as it does with [`node:http`](/server/adapters/node/node-http#client-ip):

```ts
const huddleEndpoint = bind(huddle, {
  clientIp: { mode: 'direct' },
})
```

If your app runs behind proxies you trust, use `mode: 'proxy'` and list their networks in `trustedProxies`. The binding does not trust forwarding headers from the request unless you configure proxy mode.

## Shutdown

LiveThing does not close your HTTP server. Your app stops both parts:

```ts
process.once('SIGTERM', async () => {
  await shutdown()
  server.close()
})
```

An upgrade can arrive after `shutdown()` starts but before `server.close()` runs. The binding closes the network socket of that upgrade and does not run `upgrade(request)`.
