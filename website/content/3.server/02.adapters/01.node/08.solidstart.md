description: Run a LiveThing WebSocket endpoint inside a SolidStart v2 Node server.

SolidStart v2 can use Nitro 3 for both development and its production Node server. LiveThing plugs into Nitro through its H3 v2 binding.

## Install

```bash [pnpm]
pnpm add @livething/core @livething/server @livething/server-node h3@^2.0.1-rc.31 crossws@^0.4.12 nitro
```

Nitro provides the Node server, route files, and lifecycle hooks. H3 routes its HTTP and WebSocket requests, and CrossWS provides the WebSocket transport. If pnpm blocks native install scripts, allow `better-sqlite3` and `esbuild` through `pnpm.onlyBuiltDependencies` in `package.json`. LiveThing's default Node SQL provider uses `better-sqlite3` for durable data.

## Configure Nitro

Add Nitro after the SolidStart Vite plugin, enable WebSockets, and select the Node server preset:

```ts [vite.config.ts]
import { solidStart } from '@solidjs/start/config'
import { nitro } from 'nitro/vite'
import { defineConfig } from 'vite'

export default defineConfig({
  plugins: [solidStart(), nitro()],
  nitro: {
    serverDir: './server',
    preset: 'node_server',
    features: {
      websocket: true,
    },
  },
})
```

Keep your other Vite plugins and SolidStart options. `serverDir` tells Nitro where the route and plugin files live, `node_server` builds a Node process, and `features.websocket` enables Nitro's WebSocket upgrade path.

## Add the LiveThing route

Keep the LiveThing endpoint in the route that owns it. Nitro turns this file path into `/ws/chat`:

The example expects `server/chat-definition.ts` to export the [server definition](/server/server/overview) that contains your chat event handlers.

```ts [server/routes/ws/chat.ts]
import { setup } from '@livething/server-node/h3'
import { chatDefinition } from '../../chat-definition'

const livething = setup()

const chat = livething.bind(chatDefinition, {
  sql: './data/chat.sqlite',
})

export const ready = livething.ready
export const shutdown = livething.shutdown
export default chat.upgrade
```

`setup()` creates the shared adapter, `bind()` connects the server definition, and `chat.upgrade` handles this route's WebSocket handshake. The SQLite file keeps LiveThing's durable data across server restarts. Start and stop this chat server with a Nitro plugin named after it:

```ts [server/plugins/chat.ts]
import { definePlugin } from 'nitro'
import { ready, shutdown } from '../routes/ws/chat'

export default definePlugin(async (nitroApp) => {
  await ready()
  nitroApp.hooks.hook('close', shutdown)
})
```

The client connects to `/ws/chat`. `definePlugin` runs during Nitro's server lifecycle. It waits for storage and the WebSocket adapter to be ready before Nitro accepts traffic, then closes them when Nitro stops. It is not an HTTP route.

Run `pnpm dev` during development. Build and run the production Node server with:

```bash
pnpm build
HOST=0.0.0.0 PORT=3000 node .output/server/index.mjs
```

Some Nitro development servers provide only a Web API `Request`, while the built Node server also provides the raw Node request. The route works in both cases. Do not configure LiveThing's `clientIp` option unless your Nitro host provides the raw Node request.
