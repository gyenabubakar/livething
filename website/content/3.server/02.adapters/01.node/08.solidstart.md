SolidStart v2 can run on [Nitro](https://nitro.build) 3. Nitro is the server layer that SolidStart uses for both the development server and the production Node server. Nitro 3 uses H3 v2 for routing, so LiveThing connects to it through its [H3 v2 binding](/server/adapters/node/h3#h3-v2).

## Install

```bash [pnpm]
pnpm add @livething/core @livething/server @livething/server-node h3@^2.0.1-rc.31 crossws@^0.4.12 nitro
```

Each package has one job:

- Nitro provides the Node server, the route files, and the lifecycle hooks (functions that run when the server starts or stops).
- H3 sends each HTTP request and WebSocket request to the right route.
- CrossWS runs the WebSocket connection for H3.

LiveThing's default Node SQL provider uses the native `better-sqlite3` package to store durable data (data that must survive a server restart). If pnpm blocks native install scripts, allow `better-sqlite3` and `esbuild` through `pnpm.onlyBuiltDependencies` in `package.json`.

## Configure Nitro

In `vite.config.ts`, add the Nitro Vite plugin after the SolidStart Vite plugin. Then turn on WebSockets and choose the Node server preset:

```ts [vite.config.ts]
import { solidStart } from '@solidjs/start/config'
import { nitro } from 'nitro/vite'
import { defineConfig } from 'vite'

export default defineConfig({
  plugins: [solidStart(), nitro()],
  nitro: {
    serverDir: './server',
    preset: 'node_server',
    features: {
      websocket: true,
    },
  },
})
```

Merge these values into your existing config. Keep your other Vite plugins and SolidStart options.

- `serverDir` is the folder that holds Nitro's route files and plugin files.
- A preset is a Nitro build target. `node_server` builds a Node process.
- `features.websocket` turns on Nitro's WebSocket upgrade path. A WebSocket connection starts as an HTTP request that asks the server to "upgrade" to a WebSocket.

## Add the LiveThing route

Put the LiveThing endpoint in the Nitro route file that serves it. Nitro turns the file path `server/routes/ws/chat.ts` into the URL `/ws/chat`.

The example expects `server/chat-definition.ts` to export the [server definition](/server/server/overview) that contains your chat event handlers.

```ts [server/routes/ws/chat.ts]
import { setup } from '@livething/server-node/h3'
import { chatDefinition } from '../../chat-definition'

const livething = setup()

const chat = livething.bind(chatDefinition, {
  sql: './data/chat.sqlite',
})

export const ready = livething.ready
export const shutdown = livething.shutdown
export default chat.upgrade
```

- `setup()` creates the shared adapter.
- `bind()` connects the server definition to the adapter.
- `chat.upgrade` is the H3 WebSocket handler for this route. It runs the WebSocket handshake.

The SQLite file keeps LiveThing's durable data across server restarts. Create the `data` folder before you start the server. SQLite does not create missing folders, so `bind()` throws an error when the folder does not exist.

Add a Nitro plugin that starts and stops this chat server. A Nitro plugin is a file in `server/plugins/` that runs once when Nitro starts. It is not an HTTP route. Name the file after the chat server:

```ts [server/plugins/chat.ts]
import { definePlugin } from 'nitro'
import { ready, shutdown } from '../routes/ws/chat'

export default definePlugin((nitroApp) => {
  nitroApp.hooks.hook('close', shutdown)

  ready().catch((error) => {
    console.error('LiveThing chat server failed to start', error)
    process.exit(1)
  })
})
```

The plugin does two things:

- It registers `shutdown` on Nitro's `close` hook. When Nitro stops, LiveThing closes its connections, timers, and storage.
- It calls `ready()`, which resolves when LiveThing's storage and timers have started. When startup fails, the plugin logs the error and stops the process.

Nitro does not wait for a plugin's promise, so the plugin does not `await` `ready()`. This is not a problem for early traffic: the route waits until LiveThing is ready before it accepts a WebSocket upgrade.

The client connects to `/ws/chat`.

Run `pnpm dev` during development. Build and run the production Node server with:

```bash
pnpm build
HOST=0.0.0.0 PORT=3000 node .output/server/index.mjs
```

`HOST=0.0.0.0` makes the server accept connections from other machines, not only from `localhost`.

Some Nitro development servers give the route only a Web API `Request`. The built Node server also gives it the raw Node request. The route accepts WebSocket connections in both cases.

LiveThing's `clientIp` option needs the raw Node request, because it reads the socket address from it. Set `clientIp` only when your Nitro host provides the raw Node request. If you set `clientIp` and the host gives only a Web API `Request`, every upgrade to this route throws an error. See [Client IP](/server/adapters/node/h3#client-ip) on the H3 page.
