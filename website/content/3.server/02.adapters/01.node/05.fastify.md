Use `@livething/server-node/fastify` with the [`@fastify/websocket`](https://github.com/fastify/fastify-websocket) plugin. Register the plugin before you add your routes. The plugin adds WebSocket support only to routes that are added after it.

```bash [pnpm]
pnpm add @livething/server @livething/server-node @livething/core fastify @fastify/websocket
```

```ts [huddle-server.ts]
import websocket from '@fastify/websocket'
import { setup } from '@livething/server-node/fastify'
import Fastify from 'fastify'
import { huddle } from './server/huddle-definition'

const app = Fastify()
await app.register(websocket)

const { bind, ready, shutdown } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})

app.get('/huddle', huddleEndpoint.upgrade)

await ready()
await app.listen({ port: 3000 })
```

`huddleEndpoint.upgrade` is a Fastify route options object. It contains a `preHandler` hook (a Fastify function that runs before the route handler), a normal HTTP `handler`, and a `wsHandler` (the function `@fastify/websocket` calls for a WebSocket connection). Fastify runs its normal lifecycle hooks for the route. After `@fastify/websocket` accepts the socket, LiveThing takes over the connection.

Do not add `websocket: true` to this route. The route object already has the `wsHandler` and the HTTP handler it needs. Fastify's route parameters (`request.params`) do not reach LiveThing. When your definition needs a value from the path, read it from `new URL(request.url).pathname` inside the definition's [`upgrade(request)`](/server/server/upgrade) function.

A plain HTTP request to the route gets `426 Upgrade Required`, and your `upgrade` hook does not run. An upgrade request whose `Upgrade` header is not `websocket` gets `400`.

When `upgrade(request)` rejects with an HTTP status, such as `RejectUpgrade(401, 'Missing credentials')`, the `preHandler` sends that HTTP response. The socket is never accepted. When it rejects with a WebSocket close code, such as `RejectUpgrade(CloseCodes.AUTH_INVALID, 'invalid session')`, the socket is accepted first and then closed with that code and reason.

## Call the admin API from a route

The endpoint's [admin API](/server/admin/overview) runs in the same process as Fastify, so a normal Fastify route can use it. For example, Huddle's moderators post an announcement from an internal dashboard:

```ts [admin-routes.ts]
import Fastify from 'fastify'
import { verifySession } from './auth'
import { huddleEndpoint } from './huddle-endpoint'

export function addAdminRoutes(app: ReturnType<typeof Fastify>) {
  app.post('/admin/announcements', async (request, reply) => {
    const token = request.headers.authorization?.replace(
      /^Bearer /i,
      '',
    )
    const user = await verifySession(token) // your auth
    if (user?.role !== 'admin') return reply.code(401).send()

    const { text } = request.body as { text: string }
    const admin = await huddleEndpoint.admin()
    await admin.announce(text)
    return reply.code(204).send()
  })
}
```

Call `addAdminRoutes(app)` with the same `app` that serves the WebSocket route. Here `huddleEndpoint` is the endpoint from `bind(huddle, ...)`, exported from its own module (`huddle-endpoint.ts`) so the WebSocket route and the admin route share it.

`announce` comes from Huddle's [admin `api`](/server/admin/authoring). The same object also has the built-in operations, such as `purgeUser` and `connectionCount`. An admin call skips every check that protects the socket side, so protect each admin route with your own auth. See [Call the admin API from your app](/server/adapters/node/node-http#call-the-admin-api-from-your-app).

## Message size limit

Fastify creates the `ws` server, so LiveThing does not set its limit. Set it in both places: give the `ws` server a `maxPayload`, and pass the same value as the endpoint's `maxMessageBytes`. If you set only the server's limit, LiveThing still closes a connection with `1009` at its own 32 MiB default. See [Message size limit](/server/adapters/node/node-http#message-size-limit).

## Client IP

This binding passes Fastify's original Node request (`request.raw`) to LiveThing. So the `clientIp` option works the same way as it does with [`node:http`](/server/adapters/node/node-http#client-ip):

```ts
import { setup } from '@livething/server-node/fastify'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  clientIp: { mode: 'direct' },
})
```

When your server runs behind proxies you trust, use `mode: 'proxy'` and list their addresses or networks in `trustedProxies`. LiveThing does not use Fastify's `request.ip` or Fastify's `trustProxy` setting. Set this endpoint option so LiveThing follows one clear trust rule.

## Shutdown

Call `shutdown()` before you close the Fastify app:

```ts
import { setup } from '@livething/server-node/fastify'
import Fastify from 'fastify'

const app = Fastify()
const { shutdown } = setup()

process.once('SIGTERM', async () => {
  await shutdown()
  await app.close()
})
```

An upgrade request can arrive after `shutdown()` starts but before `app.close()` finishes. The binding destroys the network socket of that request without a WebSocket handshake, and it does not run `upgrade(request)`.
