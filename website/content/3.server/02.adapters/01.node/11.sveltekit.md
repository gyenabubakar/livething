title: SvelteKit
description: Run a LiveThing WebSocket endpoint on SvelteKit's development server and on an adapter-node production server.
---

A WebSocket connection starts as a normal HTTP request that asks the server to switch protocols. This request is called an upgrade request. SvelteKit `+server` files cannot receive upgrade requests, so LiveThing must be attached to the Node HTTP server itself. This page does that in two places:

- In development, you attach LiveThing to the Node server that Vite (the development server and build tool that SvelteKit uses) creates.
- In production, you write a small custom Node server around the request handler that `adapter-node` builds.

## Install

```bash [pnpm]
pnpm add @livething/core @livething/server @livething/server-node
pnpm add -D @sveltejs/adapter-node
```

`adapter-node` builds your SvelteKit app as a Node request handler. This handler serves the built browser files, the prerendered pages and your SvelteKit routes.

Configure the adapter:

```js [svelte.config.js]
import adapter from '@sveltejs/adapter-node'

export default {
  kit: {
    adapter: adapter(),
  },
}
```

The build creates `build/handler.js`. The production server below imports it.

LiveThing's default Node SQL storage uses `better-sqlite3`, which runs a native build script when it installs. If pnpm blocks install scripts, allow `better-sqlite3` and `esbuild` through `pnpm.onlyBuiltDependencies` in `package.json`.

The finished server setup uses these files:

```text
livething.js
server.js
src/lib/server/definition.ts
svelte.config.js
vite.config.ts
```

`livething.js` and `server.js` are server-only. The runtime values in `definition.ts` are also server-only. Client code may import the inferred client contract (the client type made with `InferClient`) from `definition.ts` with `import type`. TypeScript removes type-only imports, so that import is not in the browser build.

## Create the shared LiveThing setup

```js [livething.js]
import { setup } from '@livething/server-node'
import { huddle } from './src/lib/server/definition.ts'

export const livething = setup()
export const huddleEndpoint = livething.bind(huddle, {
  sql: './data/huddle.sqlite',
})

export function handleLiveThingUpgrade(request, socket, head) {
  const url = new URL(
    request.url ?? '/',
    `http://${request.headers.host}`,
  )
  if (url.pathname !== '/ws') return false

  huddleEndpoint.upgrade(request, socket, head)
  return true
}
```

`huddle` is the [server definition](/server/server/overview) that contains your event handlers. Keep that file in TypeScript so it can export `InferClient<typeof huddle>` for your client. Node.js 24 runs the `.ts` file directly. The SQLite file keeps LiveThing's durable data across server restarts.

`handleLiveThingUpgrade` sends upgrade requests for `/ws` to LiveThing and returns `true`. For any other path, it does nothing and returns `false`.

The development config and the production server both import this module, so both use the same endpoint and the same `/ws` path. Each process still creates its own LiveThing runtime.

## Development server

During development, SvelteKit runs on Vite's Node HTTP server. A small Vite plugin connects LiveThing to that server. In the plugin's `configureServer` hook, it waits for LiveThing to be ready and adds the upgrade listener. Vite runs this hook before the server starts listening. Add the plugin before `sveltekit()`:

```ts [vite.config.ts]
import { sveltekit } from '@sveltejs/kit/vite'
import { defineConfig } from 'vite'
import { handleLiveThingUpgrade, livething } from './livething.js'

export default defineConfig({
  plugins: [
    {
      name: 'livething-huddle',
      async configureServer(vite) {
        if (!vite.httpServer) {
          throw new Error('Vite did not create an HTTP server')
        }

        await livething.ready()
        vite.httpServer.on('upgrade', handleLiveThingUpgrade)
        vite.httpServer.once('close', () => void livething.shutdown())
      },
    },
    sveltekit(),
  ],
})
```

Vite has its own WebSocket for hot updates (it sends code changes to the browser without a full reload). The upgrade function returns `false` for every path except `/ws`, so Vite can still handle that WebSocket. When the development server stops, the `close` listener calls `livething.shutdown()`, which closes LiveThing's connections, timers and storage.

## Production server

Build SvelteKit with `adapter-node`. Then import the generated request handler into a Node server that your app owns:

```js [server.js]
import { createServer } from 'node:http'
import { handler } from './build/handler.js'
import { handleLiveThingUpgrade, livething } from './livething.js'

const server = createServer(handler)

server.on('upgrade', (request, socket, head) => {
  if (!handleLiveThingUpgrade(request, socket, head)) socket.destroy()
})

await livething.ready()
server.listen(
  Number(process.env.PORT ?? 3000),
  process.env.HOST ?? '0.0.0.0',
)

process.once('SIGTERM', async () => {
  await livething.shutdown()
  server.close()
})
```

`handler` answers normal HTTP requests. The `upgrade` listener sends `/ws` to LiveThing. This production process has no Vite hot-update WebSocket, so the server closes every other upgrade request. `livething.ready()` waits for LiveThing's storage to start before the server accepts requests. On `SIGTERM` (the signal that asks the process to stop), `shutdown()` closes LiveThing first, and then `server.close()` stops the HTTP server.

Point your `start` script at the custom server:

```json [package.json]
{
  "scripts": {
    "start": "node server.js"
  }
}
```

Run `pnpm dev` during development. Run `pnpm build` and then `pnpm start` in production. The client connects to `/ws` in both modes.
