This page is for a React Router app in framework mode that already has a custom Express server. Express still handles normal HTTP requests. Vite still sends code updates to the browser during development. LiveThing handles only the `/huddle` path.

The default React Router server does not give your code access to its Node HTTP server. If your app uses the default server, first switch to React Router's [custom Node server setup](https://reactrouter.com/start/framework/deploying#node-with-docker-custom-server). LiveThing needs the HTTP server's `upgrade` event. Node emits this event when a client asks to turn an HTTP request into a WebSocket connection.

## Install LiveThing

```bash [pnpm]
pnpm add @livething/core @livething/server @livething/server-node
```

LiveThing's default Node SQL provider uses `better-sqlite3` to store durable data. `better-sqlite3` and `esbuild` run native install scripts. If pnpm blocks these scripts, allow both packages in `pnpm.onlyBuiltDependencies` in `package.json`.

## Bind the server definition

Put the Node-only Huddle endpoint in its own server module. `setup()` creates the adapter. `bind()` connects your server definition to it:

```js [server/huddle-endpoint.js]
import { setup } from '@livething/server-node'
import { huddle } from './huddle-definition.ts'

const shared = (globalThis[Symbol.for('huddle.endpoint')] ??=
  createHuddleEndpoint())

function createHuddleEndpoint() {
  const huddleNode = setup()
  const huddleEndpoint = huddleNode.bind(huddle, {
    sql: './data/huddle.sqlite',
  })
  return { huddleNode, huddleEndpoint }
}

export const { huddleNode, huddleEndpoint } = shared
```

Your custom server (`huddle-server.js`) loads this module directly. When your React Router route code imports it too, for example to call the [admin API](#call-the-admin-api-from-a-route), Vite (in development) or the production build loads a **second copy** of the module. Without the `globalThis` check, that copy would call `setup()` again and start a second LiveThing endpoint with no connected users. `Symbol.for('huddle.endpoint')` returns the same key in every copy, so the first copy creates the endpoint and every later copy uses it. The imports in this module end in `.ts` and `.js` because plain Node loads it, not Vite. The route code below is built by Vite, so its imports leave out the extension.

`huddle` is the [server definition](/server/server/overview) that contains your event handlers. Write it in TypeScript, so the same file can also export `InferClient<typeof huddle>` for your client. Node.js 24 runs the `.ts` file directly. The browser code imports only the client type with `import type`, and TypeScript removes that import from the browser build. The SQLite file at `./data/huddle.sqlite` keeps LiveThing's durable data across server restarts.

## Add LiveThing to the custom server

Make the following changes to the `huddle-server.js` file that starts your Express app. The diffs below use the React Router custom server template. Your file may have different line numbers.

### 1. Create a Node HTTP server

An Express app is a function that handles HTTP requests. It is not the HTTP server. Pass it to `createServer()` from `node:http`, so your code has a server that receives WebSocket upgrade requests:

```diff [huddle-server.js]
diff --git a/huddle-server.js b/huddle-server.js
--- a/huddle-server.js
+++ b/huddle-server.js
@@ -1,2 +1,3 @@
+import { createServer } from 'node:http'
 import compression from 'compression'
 import express from 'express'
@@ -10 +11,2 @@
 const app = express()
+const server = createServer(app)
```

Keep the rest of your Express middleware on `app`.

### 2. Share that server with Vite

In development, Vite sends code updates to the browser over its own WebSocket. This is called hot module replacement (HMR). Give Vite the same HTTP server, so the Vite WebSocket and LiveThing use one port:

```diff [huddle-server.js]
diff --git a/huddle-server.js b/huddle-server.js
--- a/huddle-server.js
+++ b/huddle-server.js
@@ -19,5 +19,5 @@
   const viteDevServer = await import('vite').then((vite) =>
     vite.createServer({
-      server: { middlewareMode: true },
+      server: { middlewareMode: true, hmr: { server } },
     }),
   )
```

Do not remove your Vite middleware or your React Router request handler. This change only tells Vite which HTTP server to use for its HMR WebSocket.

### 3. Send `/huddle` upgrades to LiveThing

Import the module from the previous section. Then listen for WebSocket upgrade requests:

```diff [huddle-server.js]
diff --git a/huddle-server.js b/huddle-server.js
--- a/huddle-server.js
+++ b/huddle-server.js
@@ -3 +3,2 @@
 import express from 'express'
+import { huddleEndpoint, huddleNode } from './server/huddle-endpoint.js'
@@ -46,0 +48,13 @@
+server.on('upgrade', (request, socket, head) => {
+  const url = new URL(
+    request.url ?? '/',
+    `http://${request.headers.host}`,
+  )
+
+  if (url.pathname === '/huddle') {
+    huddleEndpoint.upgrade(request, socket, head)
+    return
+  }
+
+  if (!DEVELOPMENT) socket.destroy()
+})
```

Node gives the listener three values. `request` is the HTTP request. `socket` is the network connection. `head` contains any bytes that Node already read after the HTTP headers. LiveThing needs all three to finish the WebSocket handshake.

The path check matters. `DEVELOPMENT` is the constant that the template sets from `NODE_ENV`. In development, the listener does not touch other upgrade requests, so Vite can handle its own HMR WebSocket. In production, nothing else on this server handles WebSockets, so the listener closes the socket of any other upgrade request. Without this, those sockets stay open.

### 4. Start the HTTP server after LiveThing is ready

Replace the `app.listen()` call. First wait until LiveThing has set up its storage and timers. Then start the shared Node server:

```diff [huddle-server.js]
diff --git a/huddle-server.js b/huddle-server.js
--- a/huddle-server.js
+++ b/huddle-server.js
@@ -61,3 +61,4 @@
-app.listen(PORT, () => {
+await huddleNode.ready()
+server.listen(PORT, () => {
   console.log(`Server is running on http://localhost:${PORT}`)
 })
```

Call `listen()` only once, on `server`. Express requests and WebSocket upgrades both arrive through `server`.

### 5. Close LiveThing during shutdown

Add shutdown handling at the end of `huddle-server.js`:

```diff [huddle-server.js]
diff --git a/huddle-server.js b/huddle-server.js
--- a/huddle-server.js
+++ b/huddle-server.js
@@ -62,3 +62,8 @@
 server.listen(PORT, () => {
   console.log(`Server is running on http://localhost:${PORT}`)
 })
+
+process.once('SIGTERM', async () => {
+  await huddleNode.shutdown()
+  server.close()
+})
```

`shutdown()` closes LiveThing's connections, timers, and storage. `server.close()` then stops the HTTP server. If your deployment uses other shutdown signals, run the same two steps for them too.

Run `pnpm dev` for development. For production, run `pnpm build` and then `pnpm start` to start the built Node server. In both modes, the client connects to `/huddle`.

## Message size limit

`bind()` takes `maxMessageBytes`, the largest message the endpoint accepts, in bytes. The default is 32 MiB. `bind()` creates the `ws` server and sets its `maxPayload` to the same value, so you set the limit in one place. A client message over it closes the socket with `1009`. See [Message size limit](/server/adapters/node/node-http#message-size-limit).

## Compression

`bind()` also takes `compression: true`, which turns on WebSocket compression (`permessage-deflate`) for the `ws` server it creates. It helps JSON and text a lot, but not bytes that are already compressed, such as images, audio and video. It costs CPU and memory for every connection, so it is off by default. See [Compression](/server/adapters/node/node-http#compression).

## Call the admin API from a route

The endpoint's [admin API](/server/admin/overview) runs in the same process as your React Router app, so a route action can use it. For example, Huddle's moderators post an announcement from an internal dashboard. Add a resource route and register it:

<!-- docs-check: skip -->

```ts [app/routes.ts]
import { route } from '@react-router/dev/routes'
import type { RouteConfig } from '@react-router/dev/routes'

export default [
  route('admin/announcements', 'routes/admin.announcements.ts'),
] satisfies RouteConfig
```

```ts [app/routes/admin.announcements.ts]
import { verifySession } from '../../server/auth'
import { huddleEndpoint } from '../../server/huddle-endpoint'

export async function action({ request }: { request: Request }) {
  const token = request.headers
    .get('authorization')
    ?.replace(/^Bearer /i, '')
  const user = await verifySession(token) // your auth
  if (user?.role !== 'admin') {
    return new Response(null, { status: 401 })
  }

  const { text } = (await request.json()) as { text: string }

  const admin = await huddleEndpoint.admin()
  await admin.announce(text)

  return new Response(null, { status: 204 })
}
```

The route imports the same `server/huddle-endpoint.js` module as `huddle-server.js`, and the `globalThis` check in that module makes sure both get the one running endpoint. So the admin call reaches the users connected to `/huddle`, in development and in production. `announce` comes from Huddle's [admin `api`](/server/admin/authoring). The same object also has the built-in operations, such as `purgeUser` and `connectionCount`. An admin call skips every check that protects the socket side, so protect each admin route with your own auth. See [Call the admin API from your app](/server/adapters/node/node-http#call-the-admin-api-from-your-app).

::warning
Do not put `express.json()` (or another body parser) in front of the React Router request handler in `huddle-server.js`. It reads the request body first, and then `request.json()` in the action fails because the body is empty.
::
