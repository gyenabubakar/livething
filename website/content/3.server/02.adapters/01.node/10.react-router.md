---
title: React Router
description: Share a custom React Router Node server with a LiveThing WebSocket endpoint.
---

This page assumes your React Router framework-mode app already has a custom Express server. Express keeps handling normal requests, Vite keeps handling development updates, and LiveThing handles only `/ws`.

The default React Router server does not expose its Node HTTP server to application code. If your app still uses it, move to React Router's [custom Node server setup](https://reactrouter.com/start/framework/deploying#node-with-docker-custom-server) first. LiveThing needs access to the HTTP server's `upgrade` event because that event starts a WebSocket connection.

## Install LiveThing

```bash [pnpm]
pnpm add @livething/core @livething/server @livething/server-node
```

If pnpm blocks native install scripts, allow `better-sqlite3` and `esbuild` through `pnpm.onlyBuiltDependencies` in `package.json`. LiveThing's default Node SQL provider uses `better-sqlite3` for durable data.

## Bind the server definition

Keep the Node-only LiveThing setup in its own server module. `setup()` creates the adapter once, and `bind()` connects your chat server definition to it:

```js [server/livething.js]
import { setup } from '@livething/server-node'
import { chatDefinition } from './chat-definition.ts'

export const livething = setup()
export const chat = livething.bind(chatDefinition, {
  sql: './data/chat.sqlite',
})
```

`chatDefinition` is the [server definition](/server/server/overview) that contains your chat event handlers. Keep it in TypeScript so it can also export `InferClient<typeof chatDefinition>` for your client. Node.js 24 runs the `.ts` file directly, while the browser imports only its erased type. The SQLite file keeps LiveThing's durable data across server restarts.

## Add LiveThing to the custom server

Make the following changes to the `server.js` file that already starts your Express app.

### 1. Create a Node HTTP server

An Express app is an HTTP request handler, not the HTTP server itself. Wrap it with `createServer()` so your code can receive WebSocket upgrades:

```diff [server.js]
diff --git a/server.js b/server.js
--- a/server.js
+++ b/server.js
@@ -1 +1,2 @@
+import { createServer } from 'node:http'
 import express from 'express'
@@ -10 +11,2 @@
 const app = express()
+const server = createServer(app)
```

Keep the rest of your Express middleware on `app` as it is.

### 2. Share that server with Vite

In development, Vite uses a WebSocket for hot updates. Give Vite the same HTTP server so its WebSocket and LiveThing can share one port:

```diff [server.js]
diff --git a/server.js b/server.js
--- a/server.js
+++ b/server.js
@@ -19,5 +19,5 @@
  const vite = await import('vite').then(({ createServer }) =>
    createServer({
-      server: { middlewareMode: true },
+      server: { middlewareMode: true, hmr: { server } },
    }),
  )
```

Do not remove your existing Vite middleware or React Router request handler. This change only tells Vite which HTTP server owns its hot-update WebSocket.

### 3. Send `/ws` upgrades to LiveThing

Import the setup from the previous section, then listen for WebSocket upgrade requests:

```diff [server.js]
diff --git a/server.js b/server.js
--- a/server.js
+++ b/server.js
@@ -2 +2,2 @@
 import express from 'express'
+import { chat, livething } from './server/livething.js'
@@ -47,0 +48,13 @@
+server.on('upgrade', (request, socket, head) => {
+  const url = new URL(
+    request.url ?? '/',
+    `http://${request.headers.host}`,
+  )
+
+  if (url.pathname === '/ws') {
+    chat.upgrade(request, socket, head)
+    return
+  }
+
+  if (!DEVELOPMENT) socket.destroy()
+})
```

Node provides the HTTP `request`, the network `socket`, and any bytes already read after the HTTP headers as `head`. LiveThing needs all three to finish the WebSocket handshake.

The path check is important. In development, the listener leaves other upgrades alone so Vite can handle its own hot-update WebSocket. In production, this server has no other WebSocket owner, so it closes unknown upgrades instead of leaving their sockets open.

### 4. Start the HTTP server after LiveThing is ready

Replace Express's `app.listen()` call. Wait for LiveThing's storage and WebSocket adapter first, then start the shared Node server:

```diff [server.js]
diff --git a/server.js b/server.js
--- a/server.js
+++ b/server.js
@@ -60,3 +60,4 @@
-app.listen(PORT, () => {
+await livething.ready()
+server.listen(PORT, () => {
   console.log(`Server is running on http://localhost:${PORT}`)
 })
```

Only one process should call `listen()`. Both Express requests and WebSocket upgrades now enter through `server`.

### 5. Close LiveThing during shutdown

Add shutdown handling near the end of `server.js`:

```diff [server.js]
diff --git a/server.js b/server.js
--- a/server.js
+++ b/server.js
@@ -61,3 +61,8 @@
 server.listen(PORT, () => {
   console.log(`Server is running on http://localhost:${PORT}`)
 })
+
+process.once('SIGTERM', async () => {
+  await livething.shutdown()
+  server.close()
+})
```

`shutdown()` closes LiveThing connections, timers, and storage. `server.close()` then stops the HTTP server. Add the same sequence to any other shutdown signal your deployment uses.

Run `pnpm dev` for development. Run `pnpm build` and `pnpm start` for the built Node server. The client connects to `/ws` in both modes.
