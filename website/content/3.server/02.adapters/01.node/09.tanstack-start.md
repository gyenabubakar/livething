---
title: TanStack Start
description: Run a LiveThing WebSocket endpoint inside a TanStack Start app that runs on a Nitro Node server.
---

TanStack Start can run on Nitro 3. [Nitro](https://nitro.build) is the server toolkit that builds and runs the server side of the app. Nitro 3 uses H3 v2 for routing, so LiveThing connects to it through the [H3 v2 binding](/server/adapters/node/h3#h3-v2).

TanStack Start has no WebSocket route of its own. Its server functions handle normal HTTP requests and responses, so they cannot accept a WebSocket upgrade. Instead, you add a Nitro WebSocket route next to your TanStack Start app. The same route serves `/ws/chat` in development and in production.

## Install

```bash [pnpm]
pnpm add @livething/core @livething/server @livething/server-node h3@^2.0.1-rc.31 crossws@^0.4.12 nitro
```

Nitro provides the Node server, route files, and lifecycle hooks. H3 routes the HTTP and WebSocket requests. CrossWS runs the WebSocket connection. LiveThing's default Node SQL provider uses `better-sqlite3`, a SQLite library with native code, to store durable data. If pnpm blocks native install scripts, allow `better-sqlite3` and `esbuild` in `pnpm.onlyBuiltDependencies` in `package.json`.

## Configure Nitro

Add the Nitro Vite plugin after the TanStack Start plugin and before the React plugin. Then enable WebSockets and choose the Node server preset:

```ts [vite.config.ts]
import { tanstackStart } from '@tanstack/react-start/plugin/vite'
import react from '@vitejs/plugin-react'
import { nitro } from 'nitro/vite'
import { defineConfig } from 'vite'

export default defineConfig({
  plugins: [tanstackStart(), nitro(), react()],
  nitro: {
    serverDir: './server',
    preset: 'node_server',
    features: {
      websocket: true,
    },
  },
})
```

Keep any other Vite plugins and TanStack Start options that your project already has.

- `serverDir` is the folder where Nitro looks for route and plugin files.
- `preset` selects the build target. `node_server` builds a Node.js server.
- `features.websocket` turns on WebSocket upgrades in Nitro. They are off by default.

## Add the LiveThing route

Put the LiveThing endpoint in the Nitro route file for its URL. Nitro turns the file path `server/routes/ws/chat.ts` into the URL `/ws/chat`.

The example expects `server/chat-definition.ts` to export the [server definition](/server/server/overview) that contains your chat event handlers.

```ts [server/routes/ws/chat.ts]
import { setup } from '@livething/server-node/h3'
import { chatDefinition } from '../../chat-definition'

const livething = setup()

const chat = livething.bind(chatDefinition, {
  sql: './data/chat.sqlite',
})

export const ready = livething.ready
export const shutdown = livething.shutdown
export default chat.upgrade
```

- `setup()` creates the shared adapter.
- `bind()` connects the server definition to the adapter and returns the endpoint.
- `chat.upgrade` is the Nitro route handler. It handles the WebSocket handshake (the HTTP request that asks to switch the connection to WebSocket) for this route.

The SQLite file keeps LiveThing's durable data when the server restarts.

Next, add a Nitro plugin to start and stop this chat server. A Nitro plugin is a file that runs once when the Nitro server starts. It is not an HTTP route. Name the file after the chat server:

```ts [server/plugins/chat.ts]
import { definePlugin } from 'nitro'
import { ready, shutdown } from '../routes/ws/chat'

export default definePlugin(async (nitroApp) => {
  nitroApp.hooks.hook('close', shutdown)
  await ready()
})
```

The plugin adds the `close` hook first, so shutdown also runs when startup fails. The `close` hook runs when Nitro stops. It calls `shutdown()`, which closes LiveThing's connections, timers, and storage. `ready()` waits until LiveThing's storage and timers are ready. Nitro does not wait for an async plugin before it accepts requests. This is safe, because each WebSocket upgrade also waits until LiveThing is ready.

The client connects to `/ws/chat`.

Run `pnpm dev` during development. Build and run the Node output with:

```bash
pnpm build
HOST=0.0.0.0 PORT=3000 node .output/server/index.mjs
```

In development, Nitro can give the route only a Web API `Request`. The built Node server also gives it the raw Node request. The route works in both cases. Do not set LiveThing's [`clientIp`](/server/adapters/node/h3#h3-v2) option unless your Nitro host gives the route the raw Node request. Without it, the upgrade throws an error.
