title: Nuxt

Nuxt 4 runs its server code on Nitro 2, the server engine inside Nuxt. Nitro 2 uses H3 v1, a small HTTP framework, to match URLs to route files. LiveThing has a binding for H3 v1, so one WebSocket route file works both in development and in the built Node server.

## Install

```bash [pnpm]
pnpm add @livething/core @livething/server @livething/server-node h3@^1.15.11 crossws@^0.3.5
```

Nitro 2 uses H3 v1 for routing and CrossWS 0.3 for WebSockets. CrossWS is the library that connects H3 routes to the server's WebSocket transport. Because of these versions, this guide uses the `@livething/server-node/h3/v1` binding, not the H3 v2 binding at `@livething/server-node/h3`.

LiveThing's default Node SQL storage uses `better-sqlite3`. This package contains native code, so it runs a build script when you install it. Nuxt's build tools use `esbuild`, which also has an install script. pnpm can block install scripts, so allow these two packages in `package.json`:

```json [package.json]
{
  "pnpm": {
    "onlyBuiltDependencies": ["better-sqlite3", "esbuild"]
  }
}
```

## Enable WebSockets

Enable Nitro's WebSocket support in the Nuxt config:

```ts [nuxt.config.ts]
import { defineNuxtConfig } from 'nuxt/config'

export default defineNuxtConfig({
  nitro: {
    experimental: {
      websocket: true,
    },
  },
})
```

## Create the Huddle endpoint

Create the LiveThing endpoint in a shared server file. The WebSocket route, the startup plugin, and any server route that calls the [admin API](#call-the-admin-api-from-a-route) all import it from here, so they all use the same running endpoint.

The example expects `server/huddle-definition.ts` to export `huddle`, the [server definition](/server/server/overview) that holds your event handlers.

```ts [server/utils/huddle-endpoint.ts]
import { setup } from '@livething/server-node/h3/v1'
import { huddle } from '../huddle-definition'

export const huddleNode = setup()
export const huddleEndpoint = huddleNode.bind(huddle, {
  sql: './data/huddle.sqlite',
})
```

- `setup()` creates the Node adapter.
- `bind()` connects your server definition to the adapter. It also opens the SQLite file and starts LiveThing's startup work.

LiveThing keeps its durable data in the SQLite file. `better-sqlite3` creates the file but not the folder, so create the `data` folder before you start the server.

::warning
Call `setup()` and `bind()` only in this one file. Each `bind()` call starts a separate LiveThing endpoint with its own connections. An endpoint created in another file sees no connected users.
::

## Add the WebSocket route

Nitro turns the file path `server/routes/huddle.ts` into the URL `/huddle`:

```ts [server/routes/huddle.ts]
import { huddleEndpoint } from '../utils/huddle-endpoint'

export default huddleEndpoint.upgrade
```

`huddleEndpoint.upgrade` is the route handler. It handles the WebSocket handshake. The client connects to `/huddle`.

## Start and stop LiveThing with Nitro

A Nitro plugin is a file in `server/plugins/` that runs once when the Nitro server starts. Use one to start and stop LiveThing together with Nitro. The route file handles WebSocket upgrades. The plugin handles only startup and shutdown:

```ts [server/plugins/huddle.ts]
import { defineNitroPlugin } from 'nitropack/runtime'
import { huddleNode } from '../utils/huddle-endpoint'

export default defineNitroPlugin((nitroApp) => {
  nitroApp.hooks.hook('close', huddleNode.shutdown)

  huddleNode.ready().catch((error) => {
    console.error('LiveThing huddle server failed to start', error)
    process.exit(1)
  })
})
```

The plugin does two things:

- It adds `shutdown` to Nitro's `close` hook. When Nitro closes, LiveThing closes its connections, stops its timers, and closes the SQLite file.
- It calls `ready()`, which resolves when LiveThing's storage and timers have started. When startup fails (for example, the SQLite file cannot open), the plugin logs the error and stops the process, so you see the failure at startup and not on the first connection.

Nitro does not wait for a plugin's promise, so the plugin does not `await` `ready()`. This is not a problem for early traffic: a WebSocket upgrade that arrives before startup finishes waits until LiveThing is ready.

Nuxt also auto-imports `defineNitroPlugin`, so you can leave out that import in a Nuxt project.

## Message size limit

Nitro creates the WebSocket server, so LiveThing does not set its limit. Set it in both places: give that server a message limit, and pass the same value to `bind()` as `maxMessageBytes`. The default of `maxMessageBytes` is 32 MiB. If you set only the server's limit, LiveThing still closes a connection with `1009` at its own limit. See [h3 · Message size limit](/server/adapters/node/h3#message-size-limit).

## Compression

Nitro runs the WebSocket server, so LiveThing cannot turn on WebSocket compression (`permessage-deflate`) here. In Nuxt 4, Nitro's Node server preset does not pass any options to its WebSocket server, so compression stays off. See [h3 · Compression](/server/adapters/node/h3#compression) for what compression does on a server where you can turn it on.

## Call the admin API from a route

The endpoint's [admin API](/server/admin/overview) runs in the same Nitro server, so a normal Nuxt server route can use it. For example, Huddle's moderators post an announcement from an internal dashboard:

```ts [server/api/admin/announcements.post.ts]
import {
  defineEventHandler,
  getHeader,
  readBody,
  setResponseStatus,
} from 'h3'
import { verifySession } from '../../utils/auth'
import { huddleEndpoint } from '../../utils/huddle-endpoint'

export default defineEventHandler(async (event) => {
  const token = getHeader(event, 'authorization')?.replace(
    'Bearer ',
    '',
  )
  const user = await verifySession(token) // your auth
  if (user?.role !== 'admin') {
    setResponseStatus(event, 401)
    return null
  }

  const { text } = (await readBody(event)) as { text: string }

  const admin = await huddleEndpoint.admin()
  await admin.announce(text)
  setResponseStatus(event, 204)

  return null
})
```

The route imports `huddleEndpoint` from the same shared file as the WebSocket route, so the admin call reaches the users connected to `/huddle`. `announce` comes from Huddle's [admin `api`](/server/admin/authoring). The same object also has the built-in operations, such as `purgeUser` and `connectionCount`. An admin call skips every check that protects the socket side, so protect each admin route with your own auth. See [Call the admin API from your app](/server/adapters/node/node-http#call-the-admin-api-from-your-app).

Run `pnpm dev` during development. Build with `pnpm build`, then run the Node output:

```bash
HOST=0.0.0.0 PORT=3000 node .output/server/index.mjs
```

The H3 v1 binding does not support the `clientIp` option. That option needs the original Node request, and H3 v1 does not give it to the route. See [H3 on Node.js](/server/adapters/node/h3#h3-v1) for the other H3 v1 limits.
