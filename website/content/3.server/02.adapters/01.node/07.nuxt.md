title: Nuxt
description: Run a LiveThing WebSocket endpoint inside a Nuxt 4 Node server.
---

Nuxt 4 runs its server code on Nitro 2, the server engine inside Nuxt. Nitro 2 uses H3 v1, a small HTTP framework, to match URLs to route files. LiveThing has a binding for H3 v1, so one WebSocket route file works both in development and in the built Node server.

## Install

```bash [pnpm]
pnpm add @livething/core @livething/server @livething/server-node h3@^1.15.11 crossws@^0.3.5
```

Nitro 2 uses H3 v1 for routing and CrossWS 0.3 for WebSockets. CrossWS is the library that connects H3 routes to the server's WebSocket transport. Because of these versions, this guide uses the `@livething/server-node/h3/v1` binding, not the H3 v2 binding at `@livething/server-node/h3`.

LiveThing's default Node SQL storage uses `better-sqlite3`. This package contains native code (compiled C code), so it runs a build script when you install it. Nuxt's build tools use `esbuild`, which also has an install script. pnpm can block install scripts, so allow these two packages in `package.json`:

```json [package.json]
{
  "pnpm": {
    "onlyBuiltDependencies": ["better-sqlite3", "esbuild"]
  }
}
```

## Enable WebSockets

Enable Nitro's WebSocket support in the Nuxt config:

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  nitro: {
    experimental: {
      websocket: true,
    },
  },
})
```

## Add the WebSocket route

Put the LiveThing endpoint in a Nitro route file. Nitro turns the file path `server/routes/ws.ts` into the URL `/ws`.

The example expects `server/definition.ts` to export `huddle`, the [server definition](/server/server/overview) that holds your event handlers.

```ts [server/routes/ws.ts]
import { setup } from '@livething/server-node/h3/v1'
import { huddle } from '../definition'

const livething = setup()

const huddleEndpoint = livething.bind(huddle, {
  sql: './data/huddle.sqlite',
})

export const ready = livething.ready
export const shutdown = livething.shutdown
export default huddleEndpoint.upgrade
```

- `setup()` creates the Node adapter.
- `bind()` connects your server definition to the adapter. It also opens the SQLite file and starts LiveThing's startup work.
- `huddleEndpoint.upgrade` is the route handler. It handles the WebSocket handshake (the first HTTP request that turns into a WebSocket connection).

LiveThing keeps its durable data (data that must survive a server restart) in the SQLite file. `better-sqlite3` creates the file but not the folder, so create the `data` folder before you start the server.

The route file also exports `ready` and `shutdown`. The Nitro plugin in the next section uses them.

The client connects to `/ws`.

## Start and stop LiveThing with Nitro

A Nitro plugin is a file in `server/plugins/` that runs once when the Nitro server starts. Use one to start and stop LiveThing together with Nitro. The route file handles WebSocket upgrades. The plugin handles only startup and shutdown:

```ts [server/plugins/huddle.ts]
import { ready, shutdown } from '../routes/ws'

export default defineNitroPlugin(async (nitroApp) => {
  nitroApp.hooks.hook('close', shutdown)
  await ready()
})
```

The plugin does two things:

- It adds `shutdown` to Nitro's `close` hook. When Nitro closes, LiveThing closes its connections, stops its timers, and closes the SQLite file. The plugin adds this hook first, so shutdown also runs when startup fails.
- It calls `ready()` when the server starts. If startup fails (for example, the SQLite file cannot open), the error shows in the server log at startup, not on the first connection. Nitro does not wait for this promise. A WebSocket upgrade that arrives before startup finishes waits until LiveThing is ready.

Nuxt auto-imports `defineNitroPlugin`, so this file does not need to import it.

Run `pnpm dev` during development. Build with `pnpm build`, then run the Node output:

```bash
HOST=0.0.0.0 PORT=3000 node .output/server/index.mjs
```

The H3 v1 binding does not support the `clientIp` option. That option needs the original Node request, and H3 v1 does not give it to the route. See [H3 on Node.js](/server/adapters/node/h3#h3-v1) for the other H3 v1 limits.
