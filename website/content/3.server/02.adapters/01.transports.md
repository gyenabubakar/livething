LiveThing connects over WebSocket by default. Some networks block WebSocket, for example company proxies, some antivirus tools and some restricted networks. For them, LiveThing has **fallback transports**: the server sends with **server-sent events** (SSE), and the client sends with POST requests to the same URL. Your app code does not change. Every message, channel, request, stream, upload and [binary message](/server/binary/overview) works the same way on both transports.

You choose the transports in two places:

- The server lists the transports it accepts, in the `transports` option of the adapter's `bind()`. This page covers the server side.
- The client lists the transports it tries, in order, in the [`transports`](/client/connecting/connect-options#transports) option of `connect()`.

The two lists must agree. A client that tries a transport the server does not accept moves on to the next one in its list.

## Turn on server-sent events

Import `websocket()` and `sse()` from your adapter package, and list both in `transports`:

```ts [huddle-server.ts]
import { setup, sse, websocket } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocket(), sse()],
})
```

The default is `[websocket()]`. The order of the list does not matter on the server, because the client chooses the order. A list with one transport offers only that transport, so `transports: [sse()]` turns WebSocket off. `bind()` throws at startup for an empty list, for a transport listed twice, and for an entry that is not a transport.

`sse()` needs the [`keepalive()`](/server/capabilities/keepalive) capability in the server definition. A proxy can keep a stream open after the client is gone, and only pings find that out. `bind()` throws at startup when `sse()` is listed and the definition has no `keepalive()`. Huddle's definition already lists it:

```ts [server/huddle-definition.ts]
import { server } from '@livething/server'
import { keepalive } from '@livething/server/keepalive'

const base = server({
  capabilities: [keepalive()],
})
```

The rest of this page shows the server side for each runtime and each Node framework: [Node.js](#nodejs), the [Node frameworks](#node-frameworks), [Cloudflare](#cloudflare), and [Bun and Deno](#bun-and-deno).

## The transport functions

| Function                | What it offers                                                                                     |
| ----------------------- | -------------------------------------------------------------------------------------------------- |
| `websocket()`           | WebSocket. It takes no options. The adapter's own options, such as `compression`, configure it.    |
| `sse({ maxPostBytes })` | Server-sent events from the server, and POST requests from the client, both on the endpoint's URL. |

`sse()` takes one option:

| Option         | Default | What it does                                                                                                                                                                                                                                                                                              |
| -------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maxPostBytes` | 512 KiB | The largest POST body, in bytes. It must be at most half of the endpoint's largest message (`maxMessageBytes` on Node, 32 MiB on Cloudflare), or startup fails. A message that does not fit in one POST fails on the client when you send it, so send large files with [uploads](/server/binary/uploads). |

Every upload piece must fit in one POST, with about 4 KiB of room for the frame around it. The default piece of 256 KiB fits the default `maxPostBytes`. When an upload's `pieceBytes` does not fit, startup fails with a message that names both values.

## How the client picks a transport

The client tries its transports in its own list order. The first one is the one you prefer, and the rest are fallbacks. A transport works when the server's first frame, `__connected__`, arrives.

- **No answer moves on.** A wait that runs out, a WebSocket close with `1006`, a network error, a 5xx status, or a status that LiveThing did not make (one from a proxy) moves the client to the next transport, with no `onClose`, no `onError` and no backoff in between.
- **An answer is final.** A close code, or an error status from LiveThing such as a `401` from [`authenticate`](/server/server/authenticate), goes to the app and to `reconnection()`. The client does not try the next transport. LiveThing marks its own error responses with a `LiveThing-Error` header, so the client can tell them apart from a proxy's.
- **Failed transports are skipped for 5 minutes.** When a transport fails while it connects and a later one then connects, the client skips the failed one for 5 minutes. It also skips `sse()` at once when the stream opens but its first POST fails. After 5 minutes, it tries the first transport again.

The wait is [`connectTimeoutMs`](/client/connecting/connect-options#connecttimeoutms): 5 seconds with several transports, and 30 seconds with one. `socket.transport` shows the transport in use, so the app can show a banner while it runs on the fallback. [Failover](/client/connecting/connect-options#failover) on the connect options page has every rule.

## When a transport is not offered

A server answers a transport that it does not offer, so that a client with several transports moves on:

| Request                               | Node.js                        | Cloudflare                     |
| ------------------------------------- | ------------------------------ | ------------------------------ |
| A WebSocket upgrade, no `websocket()` | `404`                          | `426`                          |
| A plain HTTP request, no `sse()`      | `426 Upgrade Required`         | `426 Upgrade Required`         |
| A method other than `GET` and `POST`  | `405`, with `Allow: GET, POST` | `405`, with `Allow: GET, POST` |

A browser cannot read the status of a WebSocket handshake. It sees close `1006` for any failed handshake, and the client moves on.

## Origins, CORS and proxies

The Origin check covers both transports. A request with an `Origin` header must have the same host and port as its `Host` header, or its origin must be in `allowedOrigins`. Otherwise it gets `403`, and `authenticate` does not run. The [Node.js](/server/adapters/node/node-http#allowed-origins) and [Cloudflare](/server/adapters/cloudflare#allowed-origins) pages show the option.

A client on another origin needs CORS for server-sent events, because the stream and the POSTs are `fetch` requests. LiveThing does the CORS part for every origin in `allowedOrigins`:

- It answers the preflight `OPTIONS` request. It allows the `Authorization`, `LiveThing-Secret`, `LiveThing-Lane` and `Content-Type` headers, and sets `Access-Control-Max-Age` to 600 seconds, so a browser does not repeat the preflight before each POST.
- It adds `Access-Control-Allow-Origin` and `Vary: Origin` to the stream, the POSTs and every error response, and exposes the `LiveThing-Error` header, so the client can read an error status.

A request from an origin that is not allowed gets no CORS headers, so the browser reports a network error. Set `allowedOrigins` for every origin that serves your pages. The stream and the POSTs send cookies to the same origin only. A client on another origin logs in with the [`token`](/client/connecting/auth-and-query#token-auth-with-token) option, which goes in an `Authorization` header when the stream opens. Keep tokens small: a request whose headers are too large fails with `431`.

A preflight has no `Authorization` header, no cookies and no LiveThing headers. So a proxy, a Worker or a middleware in front of LiveThing must let `OPTIONS` requests through to the endpoint, or answer them itself. A reverse proxy that changes the `Host` header needs `allowedOrigins`, because the same-origin check reads `Host`.

The stream response has `Cache-Control: no-store, no-transform` and `X-Accel-Buffering: no`. `no-transform` tells a proxy not to compress the stream, because a proxy that compresses holds data until a block fills. `X-Accel-Buffering: no` tells nginx not to buffer it.

## Costs and limits

Server-sent events cost more than WebSocket. Use them as a fallback, and keep WebSocket first in the client's list.

- **Binary is bigger going down.** The server sends a binary message as base64 text on the stream, which is about a third bigger than on WebSocket (for example, 40,121 characters for 30,088 bytes). The client sends binary up as raw bytes.
- **One POST at a time.** The client sends its messages in POST batches, one batch at a time, in order. A batch holds at most 255 messages and `maxPostBytes` of data. A second lane carries only `ping`, `pong` and the close, so a slow upload cannot delay a `pong`. Each POST goes to the exact URL of its stream, query included.
- **Serve over HTTP/2 or HTTP/3.** HTTP/1.1 allows six connections per site, shared by all tabs, and one client on server-sent events can use three: the stream and the two POST lanes. Browsers use HTTP/2 only over TLS, so plain `http://localhost` is HTTP/1.1. For local development of an app that lists only `sse()`, use a local certificate. LiveThing does not share one connection between tabs.
- **Delivery is at most once**, as on WebSocket. A message can be lost when the connection drops, and the client does not send it again. If your app needs a retry, the app sends the message again. A browser or a proxy can repeat a POST on a network connection that was reset, and the server's [dedup](/server/capabilities/dedup) capability drops such a copy.
- **A logout does not close an open stream.** The login check runs once, when the stream opens. Each POST carries only the connection's secret, not the login token. So your logout code must close the user's connections, for example with [`ctx.closeConnections({ userId })`](/server/admin/context#close-connections). This is the same as on WebSocket.
- **Several Node instances need sticky routing.** The stream and its POSTs must reach the same Node process. Run one instance, or use a load balancer that sends the stream and its POSTs to the same instance. LiveThing does not forward requests between instances. A POST that reaches another instance gets `404`, and the client opens a new stream and resumes.
- **On Cloudflare, an open stream keeps the Durable Object awake.** See [Cloudflare](#cloudflare).

## Node.js

On Node, server-sent events are plain HTTP requests, not upgrades, so they do not reach `huddleEndpoint.upgrade`. Pass every request to the endpoint's path to `huddleEndpoint.handle`. It serves the stream, the POSTs and the CORS preflight:

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { setup, sse, websocket } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind, ready } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocket(), sse()],
})

function isHuddlePath(url = '/'): boolean {
  return new URL(url, 'http://localhost').pathname === '/huddle'
}

const app = createServer((request, response) => {
  if (isHuddlePath(request.url)) {
    huddleEndpoint.handle(request, response)
    return
  }

  response.statusCode = 404
  response.end()
})

app.on('upgrade', (request, socket, head) => {
  if (isHuddlePath(request.url)) {
    huddleEndpoint.upgrade(request, socket, head)
    return
  }

  socket.destroy()
})

await ready()
app.listen(3000)
```

`handle`, like `upgrade`, does not check the path. Your app does. `handle` also takes a request and a response from a `node:http2` compatibility server, which is how you serve server-sent events over HTTP/2 on Node.

`shutdown()` closes the open streams with the other connections, and drops a stream request that is still in `authenticate`. Node's server timeouts do not cut an open stream, so you do not need to change them. A POST body follows Node's `requestTimeout`, which is 300 seconds by default.

## Node frameworks

Each [Node framework](/server/adapters/node/node-http) binding has a matching route for server-sent events. Hono, Fastify and H3 have their own `handle` route. The other frameworks run on a Node HTTP server that your app owns, so they use `huddleEndpoint.handle` from `@livething/server-node`.

### Express, Koa, React Router, SvelteKit and Astro

These framework pages bind Huddle with `@livething/server-node`. Add `transports` to that `bind()` call, and add a function that sends server-sent events requests for `/huddle` to LiveThing and passes every other request on:

```js [huddle-endpoint.js]
import { setup, sse, websocket } from '@livething/server-node'
import { huddle } from './server/huddle-definition.ts'

export const huddleNode = setup()
export const huddleEndpoint = huddleNode.bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocket(), sse()],
})

export function handleHuddleRequest(request, response, next) {
  const url = new URL(
    request.url ?? '/',
    `http://${request.headers.host}`,
  )
  if (url.pathname !== '/huddle') return next()

  huddleEndpoint.handle(request, response)
}
```

`handleHuddleRequest` has the shape of a Connect or Express middleware: `(request, response, next)`. On the React Router, SvelteKit and Astro pages, the module also keeps its `globalThis` guard and its `handleHuddleUpgrade` function. The `upgrade` listener of each page stays as it is.

### Express

Mount the function first, so no body parser reads the POST body before LiveThing does:

```ts [huddle-server.ts]
import express from 'express'
import { handleHuddleRequest } from './huddle-endpoint'

const app = express()
app.use(handleHuddleRequest)
```

The rest of the [Express](/server/adapters/node/express) setup stays the same.

### Koa

Send the request to LiveThing before it reaches Koa, so Koa does not answer it too:

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import Koa from 'koa'
import { handleHuddleRequest } from './huddle-endpoint'

const app = new Koa()
const handleKoa = app.callback()
const httpServer = createServer((request, response) => {
  handleHuddleRequest(request, response, () => {
    void handleKoa(request, response)
  })
})
```

Add the `upgrade` listener of the [Koa](/server/adapters/node/koa) page to this `httpServer`.

### Hono

Mount `huddleEndpoint.handle` on the same path as `upgrade`, for every method. It serves the stream, the POSTs and the CORS preflight. A WebSocket upgrade passes through it to the next handler:

```ts [huddle-server.ts]
import { createAdaptorServer } from '@hono/node-server'
import {
  sse,
  websocket as websocketTransport,
} from '@livething/server-node'
import { setup } from '@livething/server-node/hono'
import { Hono } from 'hono'
import { huddle } from './server/huddle-definition'

const app = new Hono()
const { bind, ready, websocket } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocketTransport(), sse()],
})

app.get('/huddle', huddleEndpoint.upgrade)
app.all('/huddle', huddleEndpoint.handle)

await ready()
createAdaptorServer({ fetch: app.fetch, websocket }).listen(3000)
```

`setup()` of the Hono binding returns its own `websocket` object for `createAdaptorServer()`, so the example imports the transport function as `websocketTransport`.

### Fastify

With `sse()` listed, a plain `GET` to the `connect` route opens the stream. Add `huddleEndpoint.handle` as a second route on the same path, for `POST` and `OPTIONS`. It answers in `onRequest`, before Fastify reads the body, so you need no content type parser:

```ts [huddle-server.ts]
import websocket from '@fastify/websocket'
import {
  sse,
  websocket as websocketTransport,
} from '@livething/server-node'
import { setup } from '@livething/server-node/fastify'
import Fastify from 'fastify'
import { huddle } from './server/huddle-definition'

const app = Fastify()
await app.register(websocket)

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocketTransport(), sse()],
})

app.get('/huddle', huddleEndpoint.connect)
app.route({
  method: ['POST', 'OPTIONS'],
  url: '/huddle',
  ...huddleEndpoint.handle,
})
```

### H3 v2

With `sse()` listed, a plain `GET` to the `connect` route opens the stream. Add `huddleEndpoint.handle` on the same path, for the POSTs and the CORS preflight:

import { sse, websocket } from '@livething/server-node'
import { setup } from '@livething/server-node/h3'
import { H3 } from 'h3/node'

const app = new H3()

### React Router

In the custom Express server of the [React Router](/server/adapters/node/react-router) page, mount the function before the other middleware, such as `compression()` and the Vite middleware:

```js [huddle-server.js]

import { handleHuddleRequest } from './server/huddle-endpoint.js'

```

### SvelteKit

In development, add `vite.middlewares.use(handleHuddleRequest)` to the plugin's `configureServer` hook on the [SvelteKit](/server/adapters/node/sveltekit) page, next to the `upgrade` listener. Vite runs that middleware before its own. In production, send each request to LiveThing first, and then to SvelteKit's handler:

```js [huddle-server.js]
import { createServer } from 'node:http'
import { handler } from './build/handler.js'
import { handleHuddleRequest } from './huddle-endpoint.js'

const server = createServer((request, response) => {
  handleHuddleRequest(request, response, () =>
    handler(request, response),
  )
})
```

The `upgrade` listener, `ready()` and the shutdown code of the production server stay the same.

### Astro

In development, add `server.middlewares.use(handleHuddleRequest)` to the `astro:server:setup` hook on the [Astro](/server/adapters/node/astro) page, next to the `upgrade` listener. In production, send each request to LiveThing first, then to the static files, then to Astro:

```js [huddle-server.js]
import { createServer } from 'node:http'
import sirv from 'sirv'
import { handler } from './dist/server/entry.mjs'
import { handleHuddleRequest } from './huddle-endpoint.mjs'

const assets = sirv('dist/client', { gzip: true })
const server = createServer((request, response) => {
  handleHuddleRequest(request, response, () =>
    assets(request, response, () => handler(request, response)),
  )
})
```

The `upgrade` listener, `ready()` and the shutdown code of the production server stay the same.

## Cloudflare

List the transports in the second argument of `bind()`:

```ts [worker.ts]
import { bind, sse, websocket } from '@livething/server-cloudflare'
import { huddle } from './server/huddle-definition'

export class HuddleServer extends bind(huddle, {
  transports: [websocket(), sse()],
}) {}
```

The Durable Object's `fetch` serves the stream, the POSTs and the CORS preflight, next to WebSocket upgrades. The Worker `fetch` of the [Cloudflare](/server/adapters/cloudflare) page does not change: it passes every request to the Durable Object. Two rules keep it working:

- **Route by the URL.** The Worker must send each POST to the same Durable Object as its stream. Each POST goes to the exact URL of its stream, query included, so a Worker that chooses the object from the path or a query value works. A POST carries no `Authorization` header and no header of your own, so a Worker cannot route by a header or by the login token. Put the routing key in the URL.
- **Pass the request on as it is.** `stub.fetch(request)` keeps the browser's `Host` header, which the Origin check reads. The Worker must also pass `OPTIONS` requests on, or the cross-origin preflight fails.

**An open stream keeps the Durable Object awake.** A WebSocket with [hibernation](/server/server/hibernation) lets Cloudflare remove the object from memory between messages. A server-sent events stream does not: the object stays in memory while the stream is open, so it gets no hibernation savings. One open stream keeps the whole object awake, so the WebSocket clients in the same object lose their savings too. Cloudflare bills duration while the object is in memory, at 128 MB per object, not per client. Each POST is a billed request too: with the default 30-second ping, a client answers the server's ping with a POST every 30 seconds, which is 2,880 requests a day, and twice that when the client also runs its own [`keepalive()`](/client/primitives/keepalive).

**Unread data has two caps.** A Durable Object has 128 MB of memory, and a client that stops reading keeps everything sent to it there. So the adapter drops a stream at once when its unread data would pass 48 MiB, and when the unread data of all streams of one object would pass 64 MiB, it drops the stream with the most unread data. One 32 MiB message is about 43 MiB as base64, so the cap per stream cannot be lower. A dropped stream closes with `1013` on the server. The client sees the stream fail, reconnects, and [replay](/server/replay/overview) sends what it missed. Streams and catch-up wait for the client at 256 KiB, so only a burst of plain sends reaches the caps. On a stream, `ctx.stream.drain()` waits for the client, as it does on Node.

When Cloudflare restarts the object, the stream is cut. The client reconnects and resumes, as it does on WebSocket.

## Bun and Deno

The [Bun](/server/adapters/bun) and [Deno](/server/adapters/deno) adapters take the same `transports` list. Import `websocket()` and `sse()` from the adapter package, `@livething/server-bun` or `@livething/server-deno`, and list them in the `transports` option of the adapter's `bind()`. `sse()` needs `keepalive()` in the definition, and every rule on this page applies.
