`@livething/server-node` runs a LiveThing server definition on Node.js. Your application owns the HTTP server, its routes, and its signal handling (for example, what happens when the process gets `SIGTERM`). LiveThing owns one **endpoint** for each definition you bind. An endpoint is one running copy of a definition. It has its own engine, storage, timers, connections, and shutdown work.

The first part of this page sets up an endpoint with `node:http`. The options, limits, storage and shutdown steps in that part apply to every framework. Then [Frameworks](#frameworks) has one section for each framework, with only what is different there.

## Install

```bash [pnpm]
pnpm add @livething/server @livething/server-node @livething/core
```

The adapter uses two libraries: [`ws`](https://github.com/websockets/ws) to handle raw Node upgrades, and [`better-sqlite3`](https://github.com/WiseLibs/better-sqlite3) for its default SQL storage. Both are normal dependencies of the adapter, so the command above installs them for you. The adapter supports Node.js 22 and newer.

`better-sqlite3` contains native code, so it runs a build script when you install it. The build tools of many frameworks, such as Vite and Nuxt, use `esbuild`, which also has an install script. pnpm can block install scripts. If it does, allow these two packages in `package.json`:

```json [package.json]
{
  "pnpm": {
    "onlyBuiltDependencies": ["better-sqlite3", "esbuild"]
  }
}
```

## node:http

Call `setup()` once for the group of endpoints that should shut down together. Its `bind()` method creates one endpoint from one definition. `bind()` always takes an options object as its second argument.

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind, ready, shutdown } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})

const app = createServer((request, response) => {
  response.statusCode = 404
  response.end()
})

app.on('upgrade', (request, socket, head) => {
  const url = new URL(
    request.url ?? '/',
    `http://${request.headers.host}`,
  )

  if (url.pathname === '/huddle') {
    huddleEndpoint.upgrade(request, socket, head)
    return
  }

  socket.destroy()
})

await ready()
app.listen(3000)

process.once('SIGTERM', async () => {
  await shutdown()
  app.close()
})
```

`huddleEndpoint.upgrade` does not check the request path. Your application does that. It does check the request type: when the `Upgrade` header is not `websocket`, it answers `400` and your `authenticate` hook does not run. This keeps the basic Node API small, and you can use any routing library or your own matching code. For framework routes and route parameters, use the entry point for your framework: `@livething/server-node/hono`, `@livething/server-node/fastify`, or `@livething/server-node/h3`. [Frameworks](#frameworks) lists them all.

For networks that block WebSocket, the endpoint can also offer server-sent events. They are plain HTTP requests, not upgrades, so they go to `huddleEndpoint.handle` from your request listener. [Transports](/server/adapters/transports#nodejs) shows the setup.

You can bind several endpoints to the same server. Each one gets its own path. Here Huddle also runs a second definition, `presence`, next to `huddle`:

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'
import { presence } from './server/presence-definition'

const { bind, ready } = setup()
const huddleEndpoint = bind(huddle, { sql: './data/huddle.sqlite' })
const presenceEndpoint = bind(presence, {
  sql: './data/presence.sqlite',
})

const app = createServer((request, response) => {
  response.statusCode = 404
  response.end()
})

app.on('upgrade', (request, socket, head) => {
  const pathname = new URL(
    request.url ?? '/',
    `http://${request.headers.host}`,
  ).pathname

  if (pathname === '/huddle') {
    huddleEndpoint.upgrade(request, socket, head)
    return
  }

  if (pathname === '/presence') {
    presenceEndpoint.upgrade(request, socket, head)
    return
  }

  socket.destroy()
})

await ready()
app.listen(3000)
```

Wait for `ready()` before you call `listen()`. `ready()` waits for every endpoint that the setup has created at the time of the call. If you create an endpoint later, wait for that endpoint's own `ready()` method before you send traffic to it.

## Runtime configuration and the upgrade request

The Node adapter does not copy environment variables into the LiveThing context. Read Node configuration from `process.env` in your Node entry point. You can also pass the values directly into the server definition or plugin factory that needs them.

Your `authenticate(request)` function receives a standard Web API `Request`. The adapter builds it from Node's `IncomingMessage`. It contains the full request URL, method, headers, cookies, and an abort signal, so read the path, the query string or a header from it when the definition needs them. The signal aborts if the client leaves before the handshake finishes, or when `shutdown()` starts:

```ts [server/huddle-definition.ts]
import { server } from '@livething/server'
import { CloseCodes, RejectAuth } from '@livething/server/errors'
import { verifySession } from './auth'

const base = server({
  async authenticate(request) {
    const token = request.headers
      .get('Authorization')
      ?.replace('Bearer ', '')
    const user = await verifySession(token) // your auth: returns { id, name, role } or null
    if (!user) {
      throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { name: user.name, role: user.role },
    }
  },
  capabilities: [],
})
```

The request has no body, because it is an upgrade request. The [Authenticate](/server/server/authenticate) page shows what `authenticate` can return and how to reject a connection.

## Message size limit

Each endpoint has a largest message size, `maxMessageBytes`. The default is 32 MiB, the same as Cloudflare, so the same app behaves the same on both. It must be a whole number from 1 to `2147483647`, because `ws` keeps its `maxPayload` as a 32-bit number. A client message over the limit closes the socket with `1009` ([`MESSAGE_TOO_BIG`](/core/close-codes)), and a server send over the limit throws an error instead of sending. Raise it on purpose when an endpoint needs bigger messages:

```ts [huddle-server.ts]
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
// Huddle's file uploads need room for messages up to 64 MiB.
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  maxMessageBytes: 64 * 1024 * 1024,
})
```

`bind()` creates a `ws` server for each endpoint and sets its `maxPayload` to `maxMessageBytes`, so `ws` refuses a bigger message before LiveThing reads it. You set the limit in one place. When you pass your own `webSocketServer`, LiveThing does not change it. Set its `maxPayload` to the same value as `maxMessageBytes`. LiveThing also checks the length of every message when it arrives, so the limit holds even when only one of the two is set.

Fastify, H3 and the [Nitro apps](#nitro-apps-nuxt-solidstart-and-tanstack-start) create the WebSocket server themselves, so LiveThing does not set its limit there either. Set it in both places: give that server a message limit, and pass the same value to `bind()` as `maxMessageBytes`. If you set only the server's limit, LiveThing still closes a connection with `1009` at its own limit, which is 32 MiB by default. [Hono](#message-size-and-compression-on-hono) sets the limit in `setup()`.

One connection can also hold up to twice `maxMessageBytes` of [messages whose handlers have not started yet](/server/handlers/per-connection-queue).

## Allowed origins

A browser sends an `Origin` header with every WebSocket handshake: the scheme, host and port of the page that opens the socket. The endpoint compares the host and port of that `Origin` with the request's `Host` header. If they differ, it answers `403` and does not run `authenticate`. This stops another website from opening a socket with your users' cookies. A request with no `Origin` header, such as one from a Node or mobile client, is not checked. The endpoint does not read `X-Forwarded-Host`, because any client can send it.

When your pages are served from another origin, list that origin in `allowedOrigins`. You also need it behind a reverse proxy that changes the `Host` header:

```ts [huddle-server.ts]
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
// Huddle's web app runs on the Vite dev server during development.
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  allowedOrigins: ['http://localhost:5173'],
})
```

Write each entry as an origin: the scheme, host and port, with no path. `bind()` throws for any other value.

The same check covers [server-sent events](/server/adapters/transports#origins-cors-and-proxies), where `allowedOrigins` also decides which origins get CORS headers.

## Compression

`compression: true` turns on the WebSocket compression extension, `permessage-deflate`. Browsers and the `ws` client ask for it on their own, so the client needs no change. With it on, each message of at least 1024 bytes goes compressed, in both directions.

```ts [huddle-server.ts]
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
// Huddle's `load-history` pages are big JSON lists of messages, which compress well.
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  compression: true,
})
```

To change the smallest size that gets compressed, pass `compression: { threshold }`, in bytes. For example, `compression: { threshold: 4096 }`. A small message gains little and still costs CPU, so it goes as it is.

Compression helps JSON and text a lot, because they repeat the same keys and words. It does not help bytes that are already compressed, such as images, audio and video. Huddle's voice notes and screen frames, for example, stay about the same size. [Binary messages](/client/primitives/binary) still work with compression on.

Compression costs CPU for every message, and memory for every connection. For this reason it is off by default. Each message is compressed on its own, so a connection keeps no data from earlier messages. This uses less memory, but repeated small messages compress less well.

When you pass your own `webSocketServer`, set `perMessageDeflate` on it instead. `bind()` throws an error if it gets both `webSocketServer` and `compression`. When a framework creates the WebSocket server, you turn on compression there too. The framework sections show how.

## Client IP

Read the client address in [`authenticate(request)`](/server/server/authenticate#client-ip). The adapter puts it in the `LiveThing-Client-IP` request header. On Node, there is no single correct way to find the end user's IP address. By default the adapter does not add the header. Set the `clientIp` option only when you know how requests reach your Node process:

```ts
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  clientIp: { mode: 'direct' },
})
```

`direct` uses the TCP peer address. This is the address of the computer that opened the connection to Node. If Node runs behind a proxy, that address may be the proxy's address. When requests pass through proxies that you trust, list the proxy networks:

```ts
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  clientIp: {
    mode: 'proxy',
    trustedProxies: ['127.0.0.1/32', '10.0.0.0/8'],
  },
})
```

Each entry is an IP address or an address range in CIDR form. The list must not be empty.

In `proxy` mode, the TCP peer must be one of the trusted proxies. The adapter then reads the addresses in the `X-Forwarded-For` header, starting from the one nearest to Node. It uses the first address that is not a trusted proxy. If an address in that chain is not a valid IP address, or if every address is a trusted proxy, the adapter does not add `LiveThing-Client-IP`. The adapter never trusts forwarding headers unless you set `proxy` mode.

`clientIp` needs the original Node request, because it reads the socket address from it. Hono, Fastify and H3 v2 can give the binding that request. H3 v1, and so Nuxt, cannot. Each framework section says what it supports.

## Storage, timers, and WebSockets

By default, the `sql` storage is an in-memory `better-sqlite3` database, so its data is lost when the process stops. Give a file path when SQL data, KV data, or scheduled work must survive a restart:

```ts
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})
```

`better-sqlite3` and `node:sqlite` create the file but not its folder. Create the `data` folder before you start the server. When the folder does not exist, `bind()` throws an error.

The `sql` option also accepts a `better-sqlite3` database that you opened yourself, a `node:sqlite` database, or your own SQL provider. When you do not give a `kv` provider, Node stores `ctx.kv` in the same SQLite database as `ctx.sql`. If you give your own SQL provider, you must also give a `kv` provider. LiveThing closes the resources it creates. It never closes a SQL database or KV provider that you passed in.

### SQLite without a native module

Node.js has its own SQLite in the `node:sqlite` module. Pass a `DatabaseSync` as `sql`, and the adapter uses it in place of `better-sqlite3`, for `ctx.sql` and `ctx.kv`:

```ts [huddle-endpoint.ts]
import { DatabaseSync } from 'node:sqlite'
import { setup } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const huddleDatabase = new DatabaseSync('./data/huddle.sqlite')
const { bind } = setup()
export const huddleEndpoint = bind(huddle, { sql: huddleDatabase })
```

On Node 22, this needs 22.16 or newer. Node 22, Node 24 before 24.15, and Node 25 before 25.7 print an `ExperimentalWarning` when `node:sqlite` loads. `better-sqlite3` is still installed, and its build script still runs, but its native code never loads while every endpoint gets a `node:sqlite` database. The [Deno](/server/adapters/deno) setup uses the same option.

`ctx.sql` works the same on both, with two differences. When a query has fewer values than `?` placeholders, `better-sqlite3` throws, but `node:sqlite` stores `NULL` for the missing ones. And when a stored integer is bigger than `Number.MAX_SAFE_INTEGER`, `better-sqlite3` rounds it, but `node:sqlite` throws a `RangeError`.

The endpoint forwards messages, close events, and errors to the engine. It forwards a binary message as a plain `Uint8Array`. A server that lists [`binary()`](/server/binary/overview) routes it; without `binary()`, a binary frame closes the socket with code `1003` (unsupported data). Raw Node endpoints report the socket's real `ws.bufferedAmount`. So `ctx.stream.drain()` waits on the real socket buffer when a stream sends faster than the client can read.

Node does not support hibernation. If a definition enables hibernation, the endpoint fails when it starts, and `ready()` rejects with an error.

## Call the admin API from your app

Each endpoint has its own admin object. It runs in the same process as your HTTP server, so any code in that process can use it: an HTTP route, a webhook handler, or a background job. `huddleEndpoint.admin()` returns the built-in [admin context](/server/admin/context) plus the methods from [`assemble({ api })`](/server/admin/authoring). TypeScript infers its type from the server definition.

For example, Huddle's moderators post an announcement from an internal dashboard. The dashboard sends a `POST` request, and the route calls `announce` from Huddle's admin `api`, which sends the announcement on the `announcements` channel, so every member of that channel gets it:

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { verifySession } from './auth'
import { huddleEndpoint } from './huddle-endpoint'

const app = createServer(async (request, response) => {
  const url = new URL(
    request.url ?? '/',
    `http://${request.headers.host}`,
  )

  if (
    request.method === 'POST' &&
    url.pathname === '/admin/announcements'
  ) {
    const token = request.headers.authorization?.replace(
      'Bearer ',
      '',
    )
    const user = await verifySession(token) // your auth
    if (user?.role !== 'admin') {
      response.writeHead(401).end()
      return
    }

    let body = ''
    for await (const chunk of request) body += chunk
    const { text } = JSON.parse(body) as { text: string }

    const admin = await huddleEndpoint.admin()
    await admin.announce(text)
    response.writeHead(204).end()
    return
  }

  response.writeHead(404).end()
})
```

Here `huddleEndpoint` is the endpoint from `bind(huddle, ...)`, exported from its own module (`huddle-endpoint.ts`) so that the upgrade listener and the routes share it. The same object has the built-in operations. For example, a webhook from your auth provider can call `admin.purgeUser(userId)` when a user deletes their account, and a health route can read `admin.connectionCount`.

::warning
An admin call skips every check that protects the socket side: `authenticate`, channel `check` and `commit`, and rate limits. Protect every route that calls `admin()` with [your own auth](/server/admin/reaching-it#auth-is-your-boundary), as the `verifySession` check does above.
::

## Shutdown

Your application decides when to stop. `shutdown()` does these steps:

1. It waits for upgrades and server-sent events requests that are still in progress.
2. It runs your `onShutdown` hooks.
3. It closes the open connections: the WebSockets and the server-sent events streams.
4. It stops timers.
5. It closes the storage that LiveThing created.

`shutdown()` does not close your HTTP server, and it does not add signal handlers. Call `shutdown()` first, then close your server. If an upgrade or a request to `handle` arrives after shutdown starts but before your HTTP server closes, LiveThing destroys that socket or response, without a WebSocket handshake, and does not run the definition for it, so `authenticate` does not run either. H3 is different: see [H3 v2](#h3-v2) and [H3 v1](#h3-v1).

## Frameworks

Each framework section shows only what is different from the `node:http` setup above. Everything else works as the sections above explain.

| Framework                                    | Import                           | Where LiveThing gets the upgrade                        |
| -------------------------------------------- | -------------------------------- | ------------------------------------------------------- |
| Express, Koa, React Router, SvelteKit, Astro | `@livething/server-node`         | The `upgrade` event of a Node HTTP server your app owns |
| Hono                                         | `@livething/server-node/hono`    | A Hono route                                            |
| Fastify                                      | `@livething/server-node/fastify` | A Fastify route, with `@fastify/websocket`              |
| H3 v2, SolidStart, TanStack Start            | `@livething/server-node/h3`      | An H3 route, with CrossWS 0.4                           |
| H3 v1, Nuxt 4                                | `@livething/server-node/h3/v1`   | An H3 route, with CrossWS 0.3                           |

With `@livething/server-node`, `bind()` creates the `ws` server, so `maxMessageBytes` and `compression` work as [Message size limit](#message-size-limit) and [Compression](#compression) explain. The framework's routes, route parameters and middleware do not run for an upgrade request. Match the WebSocket path yourself in the `upgrade` listener. If you want to declare WebSocket routes with the framework's own router, with route parameters and middleware, use Hono, Fastify or H3.

Each section ends with an admin route for that framework. In it, `huddleEndpoint` is the endpoint from `bind(huddle, ...)`, exported from its own module so the WebSocket side and the admin route share it. `announce` comes from Huddle's [admin `api`](/server/admin/authoring), and the same object has the built-in operations, such as `purgeUser` and `connectionCount`. An admin call skips every check that protects the socket side, so protect each admin route with your own auth, as [Call the admin API from your app](#call-the-admin-api-from-your-app) explains.

### Express

Express handles normal HTTP routes. A WebSocket connection starts as an HTTP **upgrade** request: the client asks the server to switch the connection from HTTP to WebSocket. Express does not send upgrade requests through its routes or middleware. Node sends them to the `upgrade` event of the HTTP server instead. So you bind LiveThing to the Node HTTP server that runs your Express app, not to the Express app itself.

```bash [pnpm]
pnpm add @livething/server @livething/server-node @livething/core express
pnpm add -D @types/express
```

Express does not include TypeScript types, so the second command installs them.

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { setup } from '@livething/server-node'
import express from 'express'
import { huddle } from './server/huddle-definition'

const app = express()
app.get('/health', (_request, response) =>
  response.json({ ok: true }),
)

const httpServer = createServer(app)
const { bind, ready } = setup()
const huddleEndpoint = bind(huddle, { sql: './data/huddle.sqlite' })

httpServer.on('upgrade', (request, socket, head) => {
  const url = new URL(request.url ?? '/', 'http://localhost')
  if (url.pathname === '/huddle') {
    huddleEndpoint.upgrade(request, socket, head)
    return
  }

  socket.destroy()
})

await ready()
httpServer.listen(3000)
```

For networks that block WebSocket, the endpoint can also offer server-sent events. They are plain HTTP requests, so they go through Express: [Transports](/server/adapters/transports#express) shows the middleware.

#### Call the admin API from an Express route

```ts [admin-routes.ts]
import express from 'express'
import { verifySession } from './auth'
import { huddleEndpoint } from './huddle-endpoint'

export const adminRoutes = express.Router()

adminRoutes.post(
  '/announcements',
  express.json(),
  async (request, response) => {
    const token = request
      .header('authorization')
      ?.replace(/^Bearer /i, '')
    const user = await verifySession(token) // your auth
    if (user?.role !== 'admin') {
      response.sendStatus(401)
      return
    }

    const admin = await huddleEndpoint.admin()
    await admin.announce(request.body.text)
    response.sendStatus(204)
  },
)
```

Mount the router with `app.use('/admin', adminRoutes)`.

### Koa

Koa handles normal HTTP requests. Node sends upgrade requests to the HTTP server's `upgrade` event, not to Koa's middleware. This includes router middleware and its route parameters. So create a Node HTTP server from `app.callback()` and bind LiveThing to that server's `upgrade` event.

```bash [pnpm]
pnpm add @livething/server @livething/server-node @livething/core koa
pnpm add -D @types/koa
```

Koa does not include TypeScript types, so the second command installs them.

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { setup } from '@livething/server-node'
import Koa from 'koa'
import { huddle } from './server/huddle-definition'

const app = new Koa()
app.use(async (context, next) => {
  if (context.path === '/health') {
    context.body = { ok: true }

    return
  }

  await next()
})

const httpServer = createServer(app.callback())

const { bind, ready } = setup()
const huddleEndpoint = bind(huddle, { sql: './data/huddle.sqlite' })

httpServer.on('upgrade', (request, socket, head) => {
  const url = new URL(request.url ?? '/', 'http://localhost')
  if (url.pathname === '/huddle') {
    huddleEndpoint.upgrade(request, socket, head)
    return
  }

  socket.destroy()
})

await ready()
httpServer.listen(3000)
```

For networks that block WebSocket, the endpoint can also offer server-sent events. They are plain HTTP requests, so the HTTP server sends them to LiveThing before Koa: [Transports](/server/adapters/transports#koa) shows how.

#### Call the admin API from a Koa middleware

```ts [admin-announcements.ts]
import Koa from 'koa'
import { verifySession } from './auth'
import { huddleEndpoint } from './huddle-endpoint'

const app = new Koa()

app.use(async (context, next) => {
  if (
    context.method !== 'POST' ||
    context.path !== '/admin/announcements'
  ) {
    await next()
    return
  }

  const token = context.get('authorization').replace(/^Bearer /i, '')
  const user = await verifySession(token) // your auth
  if (user?.role !== 'admin') {
    context.status = 401
    return
  }

  let body = ''
  for await (const chunk of context.req) body += chunk
  const { text } = JSON.parse(body) as { text: string }

  const admin = await huddleEndpoint.admin()
  await admin.announce(text)
  context.status = 204
})
```

Add the middleware to the same `app` that serves your other routes.

### Hono

Use `@livething/server-node/hono` when Hono matches your routes. This binding does not create an HTTP server and does not start listening on a port. Your app does that with `@hono/node-server`.

```bash [pnpm]
pnpm add @livething/server @livething/server-node @livething/core hono @hono/node-server
```

```ts [huddle-server.ts]
import { createAdaptorServer } from '@hono/node-server'
import { setup } from '@livething/server-node/hono'
import { Hono } from 'hono'
import { huddle } from './server/huddle-definition'

const app = new Hono()

const { bind, ready, shutdown, websocket } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})

app.get('/huddle', huddleEndpoint.upgrade)

await ready()

const server = createAdaptorServer({
  fetch: app.fetch,
  websocket,
})

server.listen(3000)

process.once('SIGTERM', async () => {
  await shutdown()
  server.close()
})
```

`setup()` returns a `websocket` object. Pass it to `createAdaptorServer()` so that Hono's Node server can complete WebSocket handshakes. Call `bind()` once for each LiveThing definition, then pass that endpoint's `upgrade` handler to its Hono route. LiveThing does not close your HTTP server, so your app stops both parts, as the `SIGTERM` handler does.

For networks that block WebSocket, the endpoint can also offer server-sent events. Mount `huddleEndpoint.handle` on the same path for every method: [Transports](/server/adapters/transports#hono) shows the routes.

Hono's Node server gives this binding the original Node request. So [`clientIp`](#client-ip) works the same way as with `node:http`.

#### Routes and rejections on Hono

Your normal Hono middleware runs before the endpoint. The `upgrade` route only handles WebSocket upgrade requests. A plain HTTP request to the same path goes to the next Hono handler, and your `authenticate` hook does not run. If no other handler matches, Hono answers `404`. With [server-sent events](/server/adapters/transports#hono), that next handler is `huddleEndpoint.handle`.

[`authenticate(request)`](#runtime-configuration-and-the-upgrade-request) can reject a connection in two ways:

- **HTTP rejection** (a status from `400` to `599`). The binding returns it as a Hono response, before the WebSocket handshake. When the client sent a WebSocket upgrade request, `@hono/node-server` sends the status and headers of that response, but not its body.
- **Close-code rejection** (a WebSocket close code). The binding completes the handshake, then closes the socket with that code.

#### Use your own WebSocket server with Hono

If your app already creates a `WebSocketServer` from the `ws` package, pass it to `setup()`. LiveThing uses that server and does not close it. The `websocket` object that `setup()` returns then holds your server, so pass `websocket` to `createAdaptorServer()` in the same way:

```ts
import { setup } from '@livething/server-node/hono'
import { WebSocketServer } from 'ws'

const webSocketServer = new WebSocketServer({ noServer: true })
const { bind, ready, shutdown, websocket } = setup({
  webSocketServer,
})
```

#### Message size and compression on Hono

All Hono endpoints of one `setup()` share one `ws` server. Its `maxPayload` and its compression belong to the whole server, so you set both in `setup()`, for every endpoint:

```ts [huddle-server.ts]
import { setup } from '@livething/server-node/hono'
import { huddle } from './server/huddle-definition'

// Huddle's file uploads need room for messages up to 64 MiB.
const { bind } = setup({
  maxMessageBytes: 64 * 1024 * 1024,
  compression: true,
})
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  maxMessageBytes: 64 * 1024 * 1024,
})
```

`setup({ maxMessageBytes })` defaults to 32 MiB. Each endpoint's own `maxMessageBytes` (also 32 MiB by default) must not be larger: `bind()` throws an error if it is, because the shared server would refuse those messages first. `compression` takes `true` or `{ threshold }`, the same as on [`bind()`](#compression).

When you pass your own `webSocketServer`, set its `maxPayload` and `perMessageDeflate` yourself, and leave `maxMessageBytes` and `compression` out of `setup()`: `setup()` throws if it gets your server and either of them. LiveThing checks each endpoint's `maxMessageBytes` against your server's `maxPayload`.

#### Call the admin API from a Hono route

```ts [huddle-server.ts]
import { setup } from '@livething/server-node/hono'
import { Hono } from 'hono'
import { verifySession } from './auth'
import { huddle } from './server/huddle-definition'

const app = new Hono()
const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})

app.post('/admin/announcements', async (context) => {
  const token = context.req
    .header('authorization')
    ?.replace(/^Bearer /i, '')
  const user = await verifySession(token) // your auth
  if (user?.role !== 'admin') return context.body(null, 401)

  const { text } = (await context.req.json()) as { text: string }

  const admin = await huddleEndpoint.admin()
  await admin.announce(text)

  return context.body(null, 204)
})
```

The admin route and the WebSocket route use the same `huddleEndpoint`, so the admin call reaches the users connected to `/huddle`.

### Fastify

Use `@livething/server-node/fastify` with the [`@fastify/websocket`](https://github.com/fastify/fastify-websocket) plugin. Register the plugin before you add your routes. The plugin adds WebSocket support only to routes that are added after it.

```bash [pnpm]
pnpm add @livething/server @livething/server-node @livething/core fastify @fastify/websocket
```

```ts [huddle-server.ts]
import websocket from '@fastify/websocket'
import { setup } from '@livething/server-node/fastify'
import Fastify from 'fastify'
import { huddle } from './server/huddle-definition'

const app = Fastify()
await app.register(websocket)

const { bind, ready, shutdown } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})

app.get('/huddle', huddleEndpoint.connect)

await ready()
await app.listen({ port: 3000 })

process.once('SIGTERM', async () => {
  await shutdown()
  await app.close()
})
```

`huddleEndpoint.connect` is a Fastify route options object. It contains a `preHandler` hook, a normal HTTP `handler`, and a `wsHandler`. Fastify runs its normal lifecycle hooks for the route. After `@fastify/websocket` accepts the socket, LiveThing takes over the connection. Call `shutdown()` before you close the Fastify app.

Do not add `websocket: true` to this route. The route object already has the `wsHandler` and the HTTP handler it needs. Fastify's route parameters (`request.params`) do not reach LiveThing. When your definition needs a value from the path, read it from `new URL(request.url).pathname` inside the definition's [`authenticate(request)`](/server/server/authenticate) function.

A plain HTTP request to the route gets `426 Upgrade Required`, and your `authenticate` hook does not run. An upgrade request whose `Upgrade` header is not `websocket` gets `400`.

With [server-sent events](/server/adapters/transports#fastify) turned on, a plain `GET` to the same route opens the stream instead, and a second route, `huddleEndpoint.handle`, takes the `POST` and `OPTIONS` requests.

`authenticate(request)` can reject with an HTTP status or with a WebSocket close code:

```ts
import { CloseCodes, RejectAuth } from '@livething/server/errors'

// The preHandler sends this HTTP response. The socket is never accepted.
throw RejectAuth(401, 'Missing credentials')

// The socket is accepted first, then closed with this code and reason.
throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
```

This binding passes Fastify's original Node request (`request.raw`) to LiveThing. So [`clientIp`](#client-ip) works the same way as with `node:http`. LiveThing does not use Fastify's `request.ip` or Fastify's `trustProxy` setting. Set the endpoint option, so LiveThing follows one clear trust rule.

#### Message size and compression on Fastify

`@fastify/websocket` creates the `ws` server, so LiveThing does not set its limit or its compression. The plugin's `options` go to the `ws` server. Set `maxPayload` there to the endpoint's `maxMessageBytes`, and turn on WebSocket compression (`permessage-deflate`) with `perMessageDeflate`:

```ts [huddle-server.ts]
import websocket from '@fastify/websocket'
import { setup } from '@livething/server-node/fastify'
import Fastify from 'fastify'
import { huddle } from './server/huddle-definition'

// Huddle's file uploads need room for messages up to 64 MiB.
const maxMessageBytes = 64 * 1024 * 1024

const app = Fastify()
await app.register(websocket, {
  options: { maxPayload: maxMessageBytes, perMessageDeflate: true },
})

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  maxMessageBytes,
})
```

#### Call the admin API from a Fastify route

```ts [admin-routes.ts]
import Fastify from 'fastify'
import { verifySession } from './auth'
import { huddleEndpoint } from './huddle-endpoint'

export function addAdminRoutes(app: ReturnType<typeof Fastify>) {
  app.post('/admin/announcements', async (request, reply) => {

      /^Bearer /i,
      '',
    )

```

### H3 v2

[H3](https://h3.dev) is a small HTTP framework. [CrossWS](https://crossws.h3.dev) is the WebSocket library that H3 uses. It connects H3 to the WebSocket transport of the host. LiveThing has a separate binding for H3 v2 and for H3 v1. In both versions, H3 matches the URL, CrossWS runs the WebSocket connection, and LiveThing runs the endpoint after the upgrade. `setup()` does not create an HTTP server or listen on a port. Your application starts the server, and it closes the server after `shutdown()` finishes.

Use `@livething/server-node/h3` with H3 v2 and CrossWS 0.4.

```bash [pnpm]
pnpm add @livething/server @livething/server-node @livething/core h3@^2.0.1-rc.31 crossws@^0.4.12
```

`h3` handles HTTP routing. `crossws` handles the WebSocket handshake and transport for H3. Install the versions shown here, because the transport APIs of H3 v1 and H3 v2 are different.

```ts [huddle-server.ts]
import { setup } from '@livething/server-node/h3'
import { serve } from 'crossws/server/node'
import { H3 } from 'h3/node'
import { huddle } from './server/huddle-definition'

const app = new H3()

const { bind, ready, shutdown } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})

app.get('/huddle', huddleEndpoint.connect)

await ready()

const server = serve({
  fetch: app.fetch,
  websocket: {},
  hostname: '127.0.0.1',
  port: 3000,
})

process.once('SIGTERM', async () => {
  await shutdown()
  await server.close()
})
```

H3 matches the route. Inside `authenticate(request)`, the definition can read the path or query string with `new URL(request.url)`.

When the definition rejects the upgrade with an HTTP response, CrossWS sends that response before the WebSocket handshake. When it rejects with a close code, CrossWS completes the handshake and then closes the socket with that code.

With [server-sent events](/server/adapters/transports#h3-v2) turned on, a plain `GET` to the `connect` route opens the stream, and `huddleEndpoint.handle` on the same path takes the POSTs and the CORS preflight.

If an upgrade request arrives after shutdown starts, the H3 v2 binding closes the raw socket without a response when it has the Node request. It answers with HTTP 503 when the host gives it only a Web API `Request`.

#### Client IP on H3 v2

The H3 v2 binding supports the same [`clientIp`](#client-ip) options as `node:http`. This works only when the H3 host gives the binding its original Node request.

Some H3 development servers provide only a Web API `Request`. LiveThing still accepts WebSocket connections there, but it cannot read the raw socket address. If you set `clientIp` in that environment, the upgrade throws an error. LiveThing does not fall back to a header that the client could fake.

#### Message size and compression on H3

H3 creates the WebSocket server, so set its message limit and `maxMessageBytes` both, as [Message size limit](#message-size-limit) explains.

CrossWS creates the `ws` server, so you turn on WebSocket compression (`permessage-deflate`) there, with `perMessageDeflate` in its `serverOptions`. LiveThing asks for every message it sends to be compressed, and `ws` does it when the client agreed to compression. With `perMessageDeflate: true`, `ws` compresses every message, even a small one: its size threshold works only when the context takeover options are off. To skip messages under 1 KiB, as LiveThing's own `compression` option does, pass this object as `perMessageDeflate` instead of `true`:

```ts
const perMessageDeflate = {
  threshold: 1024,
  serverNoContextTakeover: true,
  clientNoContextTakeover: true,
}
```

In H3 v2, put it under `websocket.options.node` in `serve()`:

```ts [huddle-server.ts]
import { serve } from 'crossws/server/node'
import { H3 } from 'h3/node'

const app = new H3()
const server = serve({
  fetch: app.fetch,
  websocket: {
    options: { node: { serverOptions: { perMessageDeflate: true } } },
  },
  hostname: '127.0.0.1',
  port: 3000,
})
```

[H3 v1](#h3-v1) passes it to the CrossWS Node adapter instead.

#### Call the admin API from an H3 v2 route

```ts [admin-routes.ts]
import { H3 } from 'h3'
import { verifySession } from './auth'
import { huddleEndpoint } from './huddle-endpoint'

const app = new H3()

app.post('/admin/announcements', async (event) => {
  const token = event.req.headers
    .get('authorization')
    ?.replace(/^Bearer /i, '')
  const user = await verifySession(token) // your auth
  if (user?.role !== 'admin') {
    event.res.status = 401
    return null
  }

  const { text } = (await event.req.json()) as { text: string }

  const admin = await huddleEndpoint.admin()
  await admin.announce(text)
  event.res.status = 204

  return null
})
```

Add the route to the same `app` that serves the WebSocket route.

### H3 v1

Use `@livething/server-node/h3/v1` with H3 v1 and CrossWS 0.3. As with [H3 v2](#h3-v2), your application starts and closes the server.

```bash [pnpm]
pnpm add @livething/server @livething/server-node @livething/core h3@^1.15.11 crossws@^0.3.5
```

Nuxt 4 and Nitro 2 use these same major versions of H3 and CrossWS.

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { setup } from '@livething/server-node/h3/v1'
import nodeWebSocketAdapter from 'crossws/adapters/node'
import { createApp, createRouter, toNodeListener } from 'h3'
import { huddle } from './server/huddle-definition'

const app = createApp()
const router = createRouter()

const { bind, ready, shutdown } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
})

router.get('/huddle', huddleEndpoint.connect)
app.use(router)

const websocket = nodeWebSocketAdapter(app.websocket)
const server = createServer(toNodeListener(app))
server.on('upgrade', websocket.handleUpgrade)

await ready()

server.listen(3000, '127.0.0.1')

process.once('SIGTERM', async () => {
  await shutdown()
  server.close()
})
```

H3 v1 gives the binding the request URL and headers, but not the original Node request. For this reason, this binding does not accept the `clientIp` option. Passing it is a type error. If your server must get a trusted client IP from the socket or from a proxy chain, use another Node binding.

H3 v1 also does not report when a client leaves while your asynchronous `authenticate(request)` check is still running. For example, a database permission check keeps running even after the browser has closed the connection, and LiveThing cannot cancel it early. When the check finishes, the connection can open for a short time: `onConnect` runs, and then `onDisconnect` runs when CrossWS reports the close. Keep upgrade checks short, and make them safe to finish after the client has left. If this work must stop as soon as the client leaves, use the H3 v2 binding.

With [server-sent events](/server/adapters/transports#h3-v1) turned on, a plain `GET` to the `connect` route opens the stream, and `huddleEndpoint.handle` on the router's same path takes the POSTs and the CORS preflight.

When your `authenticate(request)` check rejects with an HTTP response, the client gets its status code and body, but no headers. CrossWS 0.3, the WebSocket library that H3 v1 uses, has a bug: it URL-encodes the headers of a refused upgrade, so `text/plain` would arrive as `text%2Fplain`. CrossWS fixed this in 0.4.5 ([crossws#186](https://github.com/h3js/crossws/issues/186)), but no 0.3 release has the fix, so the binding leaves the headers out. For example, a `RejectAuth(403, 'Forbidden')` reaches the client as a 403 with the body `Forbidden` and no `content-type` header. A rejection with a WebSocket close code works the same way as on H3 v2.

If an upgrade request arrives after shutdown starts, the H3 v1 binding answers with HTTP 503.

For the message limit and compression, follow [H3 v2](#message-size-and-compression-on-h3). In H3 v1, pass the `perMessageDeflate` options to the CrossWS Node adapter:

```ts [huddle-server.ts]
import nodeWebSocketAdapter from 'crossws/adapters/node'
import { createApp } from 'h3'

const app = createApp()
const websocket = nodeWebSocketAdapter({
  ...app.websocket,
  serverOptions: { perMessageDeflate: true },
})
```

#### Call the admin API from an H3 v1 route

```ts [admin-routes.ts]

```

### Nitro apps: Nuxt, SolidStart and TanStack Start

[Nitro](https://nitro.build) is the server layer under Nuxt, SolidStart and TanStack Start. It runs both the development server and the production Node server, and it provides the route files and the lifecycle hooks. Nitro uses H3 to send each HTTP request and WebSocket request to the right route, and CrossWS to run the WebSocket connection. Nuxt 4 runs on Nitro 2, which uses H3 v1. SolidStart v2 and TanStack Start run on Nitro 3, which uses H3 v2. So LiveThing connects to them through its H3 bindings, and one WebSocket route file works both in development and in the built Node server.

A Nitro app uses three LiveThing files:

- `server/utils/huddle-endpoint.ts` creates the endpoint. The WebSocket route, the startup plugin, and any server route that calls the admin API all import it from here, so they all use the same running endpoint.
- `server/routes/huddle.ts` is the WebSocket route. Nitro turns this file path into the URL `/huddle`, and the client connects to `/huddle`. For networks that block WebSocket, the endpoint can also offer server-sent events, and this route serves them too: Transports shows the change for [Nuxt](/server/adapters/transports#nuxt) and for [SolidStart and TanStack Start](/server/adapters/transports#solidstart-and-tanstack-start).
- `server/plugins/huddle.ts` starts and stops LiveThing together with Nitro. A Nitro plugin is a file in `server/plugins/` that runs once when the Nitro server starts. It is not an HTTP route. Name the file after the server it starts.

::warning
Call `setup()` and `bind()` only in the endpoint file. Each `bind()` call starts a separate LiveThing endpoint with its own connections. An endpoint created in another file sees no connected users.
::

The plugin does two things:

- It adds `shutdown` to Nitro's `close` hook. When Nitro closes, LiveThing closes its connections, stops its timers, and closes the SQLite file.
- It calls `ready()`, which resolves when LiveThing's storage and timers have started. When startup fails (for example, the SQLite file cannot open), the plugin logs the error and stops the process, so you see the failure at startup and not on the first connection.

Nitro does not wait for a plugin's promise, so the plugin does not `await` `ready()`. This is not a problem for early traffic: a WebSocket upgrade that arrives before startup finishes waits until LiveThing is ready.

Nitro creates the WebSocket server, so set its message limit and `maxMessageBytes` both, as [Message size limit](#message-size-limit) explains. Nitro also runs that server, so LiveThing cannot turn on WebSocket compression (`permessage-deflate`) there. Each framework section says what you can do.

Run `pnpm dev` during development. Build and run the production Node server with:

```bash
pnpm build
HOST=0.0.0.0 PORT=3000 node .output/server/index.mjs
```

`HOST=0.0.0.0` makes the server accept connections from other machines, not only from `localhost`.

Some Nitro development servers give the route only a Web API `Request`. The built Node server also gives it the raw Node request. The route accepts WebSocket connections in both cases. On SolidStart and TanStack Start, set LiveThing's [`clientIp`](#client-ip-on-h3-v2) option only when your Nitro host gives the route the raw Node request. If you set `clientIp` and the host gives only a Web API `Request`, every upgrade to this route throws an error. Nuxt does not support `clientIp` at all.

### Nuxt

Nuxt 4 runs its server code on Nitro 2, which uses H3 v1 for routing and CrossWS 0.3 for WebSockets. Because of these versions, Nuxt uses the [`@livething/server-node/h3/v1`](#h3-v1) binding, not the H3 v2 binding at `@livething/server-node/h3`. Read [Nitro apps](#nitro-apps-nuxt-solidstart-and-tanstack-start) first for what each file does.

```bash [pnpm]
pnpm add @livething/core @livething/server @livething/server-node h3@^1.15.11 crossws@^0.3.5
```

Enable Nitro's WebSocket support in the Nuxt config:

```ts [nuxt.config.ts]
import { defineNuxtConfig } from 'nuxt/config'

export default defineNuxtConfig({

    experimental: {
      websocket: true,
    },

})
```

Create the endpoint. The example expects `server/huddle-definition.ts` to export `huddle`, the [server definition](/server/server/overview) that holds your event handlers. `setup()` creates the Node adapter. `bind()` connects your server definition to the adapter, opens the SQLite file, and starts LiveThing's startup work:

```

export default defineEventHandler(async (event) => {
  const token = event.req.headers
    .get('authorization')
    ?.replace(/^Bearer /i, '')
  const user = await verifySession(token) // your auth
  if (user?.role !== 'admin') {
    event.res.status = 401
    return null
  }

```

The route imports `huddleEndpoint` from the same shared file as the WebSocket route, so the admin call reaches the users connected to `/huddle`.

### React Router

This section is for a React Router app in framework mode that already has a custom Express server. Express still handles normal HTTP requests. Vite still sends code updates to the browser during development. LiveThing handles only the `/huddle` path.

The default React Router server does not give your code access to its Node HTTP server. If your app uses the default server, first switch to React Router's [custom Node server setup](https://reactrouter.com/start/framework/deploying#node-with-docker-custom-server). LiveThing needs the HTTP server's `upgrade` event. Node emits this event when a client asks to turn an HTTP request into a WebSocket connection.

```bash [pnpm]

```

#### Share one endpoint with route code

Put the Node-only Huddle endpoint in its own server module. `setup()` creates the adapter. `bind()` connects your server definition to it:

```js [server/huddle-endpoint.js]

Without the `globalThis` check, that copy would call `setup()` again and start a second LiveThing endpoint with no connected users. `Symbol.for('huddle.endpoint')` returns the same key in every copy, so the first copy creates the endpoint and every later copy uses it. The imports in this module end in `.ts` and `.js` because plain Node loads it, not Vite. The route code below is built by Vite, so its imports leave out the extension.

`huddle` is the [server definition](/server/server/overview) that contains your event handlers. Write it in TypeScript, so the same file can also export `InferClient<typeof huddle>` for your client. Node.js 24 runs the `.ts` file directly. The browser code imports only the client type with `import type`, and TypeScript removes that import from the browser build.

### SvelteKit

A SvelteKit `+server` file answers with a `Response`, which cannot switch the connection to WebSocket: only the code that holds the Node socket can do that. So LiveThing must be attached to the Node HTTP server itself. This section does that in two places:

- In development, you attach LiveThing to the Node server that Vite creates.
- In production, you write a small custom Node server around the request handler that `adapter-node` builds.

```bash [pnpm]
pnpm add @livething/core @livething/server @livething/server-node
pnpm add -D @sveltejs/adapter-node
```

`adapter-node` builds your SvelteKit app as a Node request handler. This handler serves the built browser files, the prerendered pages and your SvelteKit routes.

Configure the adapter:

```js [svelte.config.js]
import adapter from '@sveltejs/adapter-node'

export default {
  kit: {
    adapter: adapter(),
  },
}
```

The build creates `build/handler.js`. The production server below imports it.

The finished server setup uses these files:

#### SvelteKit development server

During development, SvelteKit runs on Vite's Node HTTP server. A small Vite plugin connects LiveThing to that server. In the plugin's `configureServer` hook, it waits for LiveThing to be ready and adds the upgrade listener. Vite runs this hook before the server starts listening. Add the plugin before `sveltekit()`:

```ts [vite.config.ts]
import { sveltekit } from '@sveltejs/kit/vite'
import { defineConfig } from 'vite'
import { handleHuddleUpgrade, huddleNode } from './huddle-endpoint.js'

export default defineConfig({
  plugins: [
    {
      name: 'livething-huddle',
      async configureServer(vite) {
        if (!vite.httpServer) {
          throw new Error('Vite did not create an HTTP server')
        }

        await huddleNode.ready()
        vite.httpServer.on('upgrade', handleHuddleUpgrade)
        vite.httpServer.once(
          'close',
          () => void huddleNode.shutdown(),
        )
      },
    },
    sveltekit(),
  ],
})
```

Vite has its own WebSocket for hot updates. The upgrade function returns `false` for every path except `/huddle`, so Vite can still handle that WebSocket. When the development server stops, the `close` listener calls `huddleNode.shutdown()`, which closes LiveThing's connections, timers and storage.

#### SvelteKit production server

Build SvelteKit with `adapter-node`. Then import the generated request handler into a Node server that your app owns:

```js [huddle-server.js]
import { createServer } from 'node:http'
import { handler } from './build/handler.js'
import { handleHuddleUpgrade, huddleNode } from './huddle-endpoint.js'

const server = createServer(handler)

server.on('upgrade', (request, socket, head) => {
  if (!handleHuddleUpgrade(request, socket, head)) socket.destroy()
})

await huddleNode.ready()
server.listen(
  Number(process.env.PORT ?? 3000),
  process.env.HOST ?? '0.0.0.0',
)

process.once('SIGTERM', async () => {
  await huddleNode.shutdown()
  server.close()
})
```

`handler` answers normal HTTP requests. The `upgrade` listener sends `/huddle` to LiveThing. This production process has no Vite hot-update WebSocket, so the server closes every other upgrade request. `huddleNode.ready()` waits for LiveThing's storage to start before the server accepts requests. On `SIGTERM`, `shutdown()` closes LiveThing first, and then `server.close()` stops the HTTP server.

Point your `start` script at the custom server:

```json [package.json]
{
  "scripts": {
    "start": "node huddle-server.js"
  }
}
```

Run `pnpm dev` during development. Run `pnpm build` and then `pnpm start` in production. The client connects to `/huddle` in both modes.

For networks that block WebSocket, the endpoint can also offer server-sent events. They are plain HTTP requests, so both servers send them to LiveThing before SvelteKit: [Transports](/server/adapters/transports#sveltekit) shows the change.

## Authoring a Node integration

`@livething/server-node/binding` is the public API for people who build a Node WebSocket integration for a framework. Application code should use `setup()` from `@livething/server-node`, or a ready-made integration such as `@livething/server-node/hono`.

The following example builds a Hono integration in small steps. It needs `hono` and `@hono/node-server`.

Start with the host's existing WebSocket setup and the outer shape of its binding:

```ts [hono-binding.ts]
import { upgradeWebSocket } from '@hono/node-server'
import { WebSocketServer } from 'ws'

import type { Context, Next } from 'hono'

### 3. Prepare before Hono completes the handshake

Call `prepare()` or `prepareNode()` only for a WebSocket upgrade request. They run your `authenticate` hook, and the binding does not check the request type for you.

`lifecycle.prepare()` gives your callback an abort signal, and the callback passes that signal to `huddleEndpoint.prepareNode()`. Hono's Node server keeps the original `IncomingMessage` at `context.env.incoming`. `prepareNode()` reads it, so LiveThing can apply the endpoint's `clientIp` option.

`lifecycle.prepare()` returns `undefined` in three cases: the client left, shutdown started while preparation was running, or shutdown had already started. In these cases, destroy the Node socket and do not start a WebSocket handshake. Otherwise the result has one of three types:

- `http`: LiveThing rejected the upgrade with an HTTP response. Return `result.response` from the Hono route.
- `socket`: LiveThing rejected the upgrade with a WebSocket close code. Hono must complete the handshake first, then close the socket.
- `accept`: LiveThing accepted the upgrade. Hono must complete the handshake.

### 4. Reject or accept the socket

When Hono opens the socket, a `socket` result closes it at once with its code and reason. An `accept` result has an `accept()` method. Pass it a small transport object: the socket functions that LiveThing needs (`send`, `close`, `bufferedAmount`, and `backpressureSupported`). `send` gets a frame that is either `{ kind: 'text', text }` or `{ kind: 'bytes', bytes }`. It sends text as a text message and bytes as a binary message. `send` must return `false`, and must not throw, when the socket is no longer open, so LiveThing does not count the message as delivered. `accept()` returns the LiveThing connection. Save it for the later socket events. `accept()` can be called only once for each result.

### 5. Forward the socket events

Forward a text message to `message()` and a binary message to `binaryMessage()` as a `Uint8Array`. Hono's Node server gives each binary message as its own `ArrayBuffer`, so a plain `Uint8Array` over it holds exactly the message's bytes. LiveThing decides what to do with a binary message, so do not close the socket for one yourself. `closeWebSocket()` shortens the close reason when needed, because a WebSocket close reason can be at most 123 bytes. Report errors, but remove the saved connection only in `onClose`. Some hosts send an `error` event before their final `close` event.

Keep the Hono Node startup code that your application already has. Where that code configures Hono's WebSocket host, give it `app.fetch` and `websocket`. LiveThing does not create the server, start listening, or close the server.

### Give the application the admin API

An application reaches its endpoint's [admin API](/server/admin/overview) only through what your integration's `bind()` returns. So return `admin: endpoint.admin`, as step 6 does. If you leave it out, the application has no way to call `purgeUser`, `broadcast`, or its own `api` methods. You can pass the function on as it is: `endpoint.admin` does not depend on `this`.

The application then calls it from any route, in the same way as with a ready-made integration. The [Hono admin route](#call-the-admin-api-from-a-hono-route) works as it is, with `setup` imported from `./hono-binding` instead of `@livething/server-node/hono`. The admin route and the WebSocket route use the same `huddleEndpoint`, so the admin call reaches the users connected to `/huddle`.

### Client IP in an integration

Both `prepare()` and `prepareNode()` remove any `LiveThing-Client-IP` header that the client sent. `prepareNode()` is for a host that has Node's `IncomingMessage`. It applies the endpoint's `clientIp` option itself. A Fetch-based host calls `prepare(request, options)` instead, with the address in `options.clientIp`. Pass `clientIp` only when the host got that address from trusted connection or proxy data.
