TanStack Start can run on Nitro 3. [Nitro](https://nitro.build) is the server toolkit that builds and runs the server side of the app. Nitro 3 uses H3 v2 for routing, so LiveThing connects to it through the [H3 v2 binding](/server/adapters/node/h3#h3-v2).

TanStack Start has no WebSocket route of its own. Its server functions handle normal HTTP requests and responses, so they cannot accept a WebSocket upgrade. Instead, you add a Nitro WebSocket route next to your TanStack Start app. The same route serves `/huddle` in development and in production.

## Install

```bash [pnpm]
pnpm add @livething/core @livething/server @livething/server-node h3@^2.0.1-rc.31 crossws@^0.4.12 nitro
```

Nitro provides the Node server, route files, and lifecycle hooks. H3 routes the HTTP and WebSocket requests. CrossWS runs the WebSocket connection. LiveThing's default Node SQL provider uses `better-sqlite3`, a SQLite library with native code, to store durable data. If pnpm blocks native install scripts, allow `better-sqlite3` and `esbuild` in `pnpm.onlyBuiltDependencies` in `package.json`.

## Configure Nitro

Add the Nitro Vite plugin after the TanStack Start plugin and before the React plugin. Then enable WebSockets and choose the Node server preset:

```ts [vite.config.ts]
import { tanstackStart } from '@tanstack/react-start/plugin/vite'
import react from '@vitejs/plugin-react'
import { nitro } from 'nitro/vite'
import { defineConfig } from 'vite'

export default defineConfig({
  plugins: [tanstackStart(), nitro(), react()],
  nitro: {
    serverDir: './server',
    preset: 'node_server',
    features: {
      websocket: true,
    },
  },
})
```

Keep any other Vite plugins and TanStack Start options that your project already has.

- `serverDir` is the folder where Nitro looks for route and plugin files.
- `preset` selects the build target. `node_server` builds a Node.js server.
- `features.websocket` turns on WebSocket upgrades in Nitro. They are off by default.

## Create the Huddle endpoint

Create the LiveThing endpoint in a shared server file. The WebSocket route, the startup plugin, and any server route that calls the [admin API](#call-the-admin-api-from-a-route) all import it from here, so they all use the same running endpoint.

The example expects `server/huddle-definition.ts` to export `huddle`, the [server definition](/server/server/overview) that contains your event handlers.

```ts [server/utils/huddle-endpoint.ts]
import { setup } from '@livething/server-node/h3'
import { huddle } from '../huddle-definition'

export const huddleNode = setup()
export const huddleEndpoint = huddleNode.bind(huddle, {
  sql: './data/huddle.sqlite',
})
```

- `setup()` creates the shared adapter.
- `bind()` connects the server definition to the adapter and returns the endpoint.

The SQLite file keeps LiveThing's durable data when the server restarts.

::warning
Call `setup()` and `bind()` only in this one file. Each `bind()` call starts a separate LiveThing endpoint with its own connections. An endpoint created in another file sees no connected users.
::

## Add the LiveThing route

Nitro turns the file path `server/routes/huddle.ts` into the URL `/huddle`:

```ts [server/routes/huddle.ts]
import { huddleEndpoint } from '../utils/huddle-endpoint'

export default huddleEndpoint.connect
```

`huddleEndpoint.connect` is the Nitro route handler. It handles the WebSocket handshake for this route. For networks that block WebSocket, the endpoint can also offer server-sent events, and this route serves them too: [Transports](/server/adapters/transports#solidstart-and-tanstack-start) shows the change.

Next, add a Nitro plugin to start and stop this server. A Nitro plugin is a file that runs once when the Nitro server starts. It is not an HTTP route. Name the file after the server it starts:

```ts [server/plugins/huddle.ts]
import { definePlugin } from 'nitro'
import { huddleNode } from '../utils/huddle-endpoint'

export default definePlugin((nitroApp) => {
  nitroApp.hooks.hook('close', huddleNode.shutdown)

  huddleNode.ready().catch((error) => {
    console.error('LiveThing huddle server failed to start', error)
    process.exit(1)
  })
})
```

The plugin does two things:

- It registers `shutdown` on Nitro's `close` hook. When Nitro stops, LiveThing closes its connections, timers, and storage.
- It calls `ready()`, which resolves when LiveThing's storage and timers have started. When startup fails, the plugin logs the error and stops the process.

Nitro does not wait for a plugin's promise, so the plugin does not `await` `ready()`. This is not a problem for early traffic: each WebSocket upgrade waits until LiveThing is ready.

The client connects to `/huddle`.

## Message size limit

Nitro creates the WebSocket server, so LiveThing does not set its limit. Set it in both places: give that server a [message limit](/server/adapters/node/h3#message-size-limit), and pass the same value to `bind()` as `maxMessageBytes`. The default of `maxMessageBytes` is 32 MiB. If you set only the server's limit, LiveThing still closes a connection with `1009` at its own limit.

## Compression

Nitro runs the WebSocket server, so LiveThing cannot turn on [WebSocket compression](/server/adapters/node/h3#compression) (`permessage-deflate`) here. Whether you can turn it on depends on the WebSocket server options that TanStack Start and Nitro give you. When that server has compression on, LiveThing asks for each message to be compressed. `ws` compresses a message only when the client agreed to compression and the message is not under the server's size threshold. The [h3 page](/server/adapters/node/h3#compression) explains when that threshold works.

## Call the admin API from a route

The endpoint's [admin API](/server/admin/overview) runs in the same Nitro server, so a Nitro route can use it. Use a Nitro route, not a TanStack Start server function: a server function is called from your React code, and an admin endpoint is usually called by another system, such as an internal dashboard or a webhook. For example, Huddle's moderators post an announcement from an internal dashboard:

```ts [server/routes/admin/announcements.post.ts]
import { defineEventHandler } from 'h3'
import { verifySession } from '../../utils/auth'
import { huddleEndpoint } from '../../utils/huddle-endpoint'

export default defineEventHandler(async (event) => {
  const token = event.req.headers
    .get('authorization')
    ?.replace(/^Bearer /i, '')
  const user = await verifySession(token) // your auth
  if (user?.role !== 'admin') {
    event.res.status = 401
    return null
  }

  const { text } = (await event.req.json()) as { text: string }

  const admin = await huddleEndpoint.admin()
  await admin.announce(text)
  event.res.status = 204

  return null
})
```

The route imports `huddleEndpoint` from the same shared file as the WebSocket route, so the admin call reaches the users connected to `/huddle`. `announce` comes from Huddle's [admin `api`](/server/admin/authoring). The same object also has the built-in operations, such as `purgeUser` and `connectionCount`. An [admin call](/server/adapters/node/node-http#call-the-admin-api-from-your-app) skips every check that protects the socket side, so protect each admin route with your own auth.

## Run it

Run `pnpm dev` during development. Build and run the Node output with:

```bash
pnpm build
HOST=0.0.0.0 PORT=3000 node .output/server/index.mjs
```

In development, Nitro can give the route only a Web API `Request`. The built Node server also gives it the raw Node request. The route works in both cases. Do not set LiveThing's [`clientIp`](/server/adapters/node/h3#h3-v2) option unless your Nitro host gives the route the raw Node request. Without it, the upgrade throws an error.
