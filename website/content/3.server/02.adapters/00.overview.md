The server definition you build with `server`, capabilities, handlers and `assemble` says what your server does. It does not say where it runs or how clients reach it. This section covers those two choices:

- **The runtime.** A [runtime adapter](/server/adapters/runtime-adapters) runs the definition on one platform, such as Cloudflare or Node.js. You pass the definition to the adapter's `bind()`.
- **The transports.** A [transport](/server/adapters/transports) is how a client's messages travel. WebSocket is the default. `http()` (server-sent events and POST requests) can carry the whole app alone, or take over when a network blocks WebSocket. You list the transports in `bind()` on the server and in `connect()` on the client.

Both choices leave your definition and your app code the same.

## Transports

| Transport                           | Server        | Client        | Page                                                    |
| ----------------------------------- | ------------- | ------------- | ------------------------------------------------------- |
| WebSocket                           | `websocket()` | `websocket()` | [Transports](/server/adapters/transports)               |
| Server-sent events and POST         | `http()`      | `http()`      | [Transports](/server/adapters/transports)               |
| One you build, such as long polling | Your own      | Your own      | [Custom Transports](/server/adapters/custom-transports) |

Cloudflare, Node.js and Bun offer WebSocket and `http()`. Deno has no adapter of its own: it can run the Node.js adapter with a `node:sqlite` database, but it is not a supported runtime. When a client lists several transports, it tries them in order and moves on when one does not connect.
