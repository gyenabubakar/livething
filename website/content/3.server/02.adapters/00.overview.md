You write a server once with `define`, capabilities, handlers, and `assemble`. The result is a **server definition** — a frozen blueprint that knows your contract but nothing about how WebSockets actually run on your platform. An **adapter** is the piece that wires that blueprint to one runtime.

The same definition can run on different platforms. Only the adapter changes.

**Half 1 — the definition.** Platform-agnostic: `define`, capabilities, handlers, and `assemble`. It knows your contract but never names a runtime.

```ts [definition.ts]
import { define, emits, t } from '@wskit/server'
import * as v from 'valibot'

const base = define({
  capabilities: [emits({ pong: t<{ text: string }>() })],
})

const handlePing = base.on('ping', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.send('pong', { text: input.text })
  },
})

export const chat = base.assemble({ handlers: [handlePing] })
```

**Half 2 — the adapter.** It turns that definition into a runtime service. The same `chat` goes to whichever adapter matches your platform — here, Cloudflare:

::code-group

```ts [cloudflare.ts]
import { server } from '@wskit/server-cloudflare'
import { chat } from './definition'

// Cloudflare's server(...) turns the definition into a Durable Object class.
export class ChatRoom extends server(chat) {}
```

::

The `chat` definition is the same object you would hand to any adapter — only this second file changes when you switch platforms. Your `define`/handlers code does not.

::note
For how the definition itself is built — `define`, capabilities, handlers, `assemble` — see [the define overview](/server/define/overview). This chapter is only about the last step: running a finished definition.
::

## What an adapter does

An adapter owns the platform-specific work that a definition deliberately leaves out:

- It accepts or rejects the WebSocket upgrade for each new connection.
- It gives `upgrade(request)` a standard Web API `Request`, preserving the URL, method, headers, cookies, and request lifetime signal.
- It pushes outbound frames to each socket and closes sockets on demand.
- It exposes the platform's storage, timers, logger, and raw platform object to your handlers (as `ctx.sql`, `ctx.kv`, `ctx.schedule`, `ctx.log`, and `ctx.platform`). Runtime-specific bindings stay on the adapter's platform object.
- It declares whether the platform supports **hibernation** and **outbound backpressure**, so the engine can adapt.

The adapter owns platform I/O; the engine owns WSKit policy. In particular, the engine validates every application-requested outbound close before it reaches an accepted socket, and it owns retries and dead-lettering for scheduled-task handlers and retries for durable engine hooks. An adapter may follow its platform's normal alarm-delivery retry behaviour when `engine.handleAlarm()` itself rejects, but it must not add a separate retry policy for a scheduled task handler.

Because hibernation and backpressure are adapter capabilities, two adapters running the same definition can differ in behavior — the definition states intent, and the engine reconciles it with what the adapter supports. Cloudflare supports hibernation but does not expose outbound buffer pressure, so `ctx.stream.drain()` is a no-op there; a Node or Bun adapter would pace the generator against the live buffer. How that negotiation works is covered in [Capability negotiation](/server/under-the-hood/capability-negotiation).

The portable part is the server definition and its TypeScript contract. Runtime behavior still depends on the adapter:

| Capability            | Cloudflare Durable Objects                             | Node.js                                                           |
| --------------------- | ------------------------------------------------------ | ----------------------------------------------------------------- |
| Hibernation           | Supported when the definition enables it               | Not supported; an enabled definition fails during initialization  |
| Outbound backpressure | Not exposed; `ctx.stream.drain()` resolves immediately | Supported through the live WebSocket buffer                       |
| Storage durability    | Durable Object instance storage                        | Depends on the configured SQLite source; the default is in-memory |
| Admin access          | RPC-safe projected methods                             | Full in-process admin context                                     |
| Platform escape hatch | Durable Object state and runtime bindings              | None; your application keeps its Node HTTP server                 |

Storage and timers are adapter-provided contracts. The definition can rely on their APIs, but the adapter decides their lifetime, limits, persistence, and restart behavior.

## Adapter packages

| Adapter package            | Runtime                    |
| -------------------------- | -------------------------- |
| `@wskit/server-cloudflare` | Cloudflare Durable Objects |
| `@wskit/server-bun`        | Bun                        |
| `@wskit/server-node`       | Node.js                    |
| `@wskit/server-deno`       | Deno                       |

The server code you write is the same for every adapter — only the adapter entry changes when you switch platforms. See [Installation](/start/installation) for the install commands.

## Authoring an adapter

If your platform is not in the table above, you can write your own. The building blocks live in a dedicated subpath:

```ts [adapter-imports.ts]
import { adapter } from '@wskit/server/adapters'
import type {
  AdapterConfig,
  ConnectionDescriptor,
  ConnectionHandle,
  Engine,
  EngineRuntimeOptions,
  Logger,
  ServerDefinition,
  StorageProvider,
  TimerProvider,
  UpgradeDecision,
} from '@wskit/server/adapters'
```

The `adapter` factory takes a config that describes your platform's capabilities and a `setup` callback that wires the platform's WebSocket lifecycle to the engine. The [Custom adapters](/server/adapters/custom-adapters) page walks through the full interface with a worked example.
