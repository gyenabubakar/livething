LiveThing has two transports. **WebSocket** is the default. **`http()`** runs over plain HTTP requests: the server sends on a server-sent events (SSE) stream, and the client sends with POST requests to the same URL. Your app code does not change: every message, channel, request, stream, upload and [binary message](/server/binary/overview) behaves the same in your app on both transports.

You can use them in three ways:

- **WebSocket only**, the default.
- **`http()` only.** Your whole app runs over plain HTTP requests, with no WebSocket at all. This fits hosts and networks that allow only plain HTTP.
- **Both.** The client tries WebSocket first and moves to `http()` when WebSocket fails, for example behind a company proxy, some antivirus tools or a restricted network.

Under the hood the two transports work differently, and some of that costs more. [Costs and limits](#costs-and-limits) lists what changes for you.

You choose the transports in two places:

- The server lists the transports it accepts, in the `transports` option of the adapter's `bind()`. This page covers the server side.
- The client lists the transports it tries, in order, in the [`transports`](/client/connecting/connect-options#transports) option of `connect()`.

The two lists must agree. A client that tries a transport the server does not accept moves on to the next one in its list.

LiveThing has no long polling. [Custom Transports](/server/adapters/custom-transports) says why, and shows how to build it, or any other transport, yourself.

## Turn on `http()`

Import `websocket()` and `http()` from your adapter package, and list both in `transports`:

```ts [huddle-server.ts]
import { http, setup, websocket } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocket(), http()],
})
```

The default is `[websocket()]`. The order of the list does not matter on the server, because the client chooses the order. A list with one transport offers only that transport, so `transports: [http()]` turns WebSocket off. `bind()` throws at startup for an empty list, for a transport listed twice, and for an entry that is not a transport.

`http()` needs the [`keepalive()`](/server/capabilities/keepalive) capability in the server definition. A proxy can keep a stream open after the client is gone, and only pings find that out. `bind()` throws at startup when `http()` is listed and the definition has no `keepalive()`. Huddle's definition already lists it:

```ts [server/huddle-definition.ts]
import { server } from '@livething/server'
import { keepalive } from '@livething/server/keepalive'

const base = server({
  capabilities: [keepalive()],
})
```

The rest of this page shows the server side for each runtime and each Node framework: [Node.js](#nodejs), the [Node frameworks](#node-frameworks), [Cloudflare](#cloudflare), [Bun](#bun), and [Deno](#deno).

## The transport functions

| Function                 | What it offers                                                                                     |
| ------------------------ | -------------------------------------------------------------------------------------------------- |
| `websocket()`            | WebSocket. It takes no options. The adapter's own options, such as `compression`, configure it.    |
| `http({ maxPostBytes })` | Server-sent events from the server, and POST requests from the client, both on the endpoint's URL. |

`http()` takes one option:

| Option         | Default | What it does                                                                                                                                                                                                                                                                                                                                                      |
| -------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maxPostBytes` | 512 KiB | The largest POST body, in bytes, and the largest message in [stream mode](#stream-mode). It must be at most half of the endpoint's largest message (`maxMessageBytes` on Node, 32 MiB on Cloudflare), or startup fails. A message that does not fit in one POST fails on the client when you send it, so send large files with [uploads](/server/binary/uploads). |

Every upload piece must fit in one POST, with about 4 KiB of room for the frame around it. The default piece of 256 KiB fits the default `maxPostBytes`. When an upload's `pieceBytes` does not fit, startup fails with a message that names both values.

## How the client picks a transport

The client tries its transports in its own list order. The first one is the one you prefer, and the rest are fallbacks. A transport works when the server's first frame, `__connected__`, arrives.

- **No answer moves on.** A wait that runs out, a WebSocket close with `1006`, a network error, a 5xx status, or a status that LiveThing did not make (one from a proxy) moves the client to the next transport, with no `onClose`, no `onError` and no backoff in between.
- **An answer is final.** A close code, or an error status from LiveThing such as a `401` from [`authenticate`](/server/server/authenticate), goes to the app and to `reconnection()`. The client does not try the next transport. LiveThing marks its own error responses with a `LiveThing-Error` header, so the client can tell them apart from a proxy's.
- **Failed transports are skipped for 5 minutes.** When a transport fails while it connects and a later one then connects, the client skips the failed one for 5 minutes. It also skips `http()` at once when the stream opens but its first POST fails. After 5 minutes, the client tries the first transport again on its next connect.

The wait is [`connectTimeoutMs`](/client/connecting/connect-options#connecttimeoutms): 5 seconds with several transports, and 30 seconds with one. `socket.transport` shows the transport in use, so the app can show a banner while it runs on a later transport. [Failover](/client/connecting/connect-options#failover) on the connect options page has every rule.

## Stream mode

`http()` sends in one of two ways. Both use the same server and need no setup:

- **Batched POSTs**, where every client starts. One POST is in flight at a time. The messages you send while it is in flight go together in the next POST, up to 255 messages and `maxPostBytes`.
- **Stream mode**: one long POST whose body stays open, and each message goes in it as you send it. No new request per message, so it costs the server less and adds less delay, most of all behind a proxy.

The client moves to stream mode by itself, when it can:

1. After its first POST, the client checks that fetch can stream a request body and that the site is not on HTTP/1.1. Today this means Chrome and Edge over HTTP/2 or HTTP/3. The stable releases of Firefox and Safari do not stream a request body yet, and a browser refuses it on HTTP/1.1, so these clients stay on batched POSTs. The check runs on every connection, so a browser moves to stream mode once it supports it.
2. It opens the long POST and writes a small probe first. The server answers the probe on the stream at once.
3. When the answer comes, the client sends its next messages in the long POST. If it does not come within 2 seconds, or the request fails, the client stays on batched POSTs. It remembers this for the origin for 10 minutes, so the next connections do not try again.

The probe is needed because some proxies read the whole body of a request before they pass it on. Such a proxy holds the long POST and never fails it. nginx does this by default. To let stream mode through nginx, add `proxy_request_buffering off;` to the location of your endpoint. Without it, everything still works, on batched POSTs.

The server answers the long POST's messages on the stream, with one short answer for a burst of them. If the long POST dies later, the client sends every message that was not answered again, in batched POSTs. Each message has a number, so the server drops a message it already has, and no handler runs twice for one message. A long POST that sends nothing for 15 seconds sends a probe, so a dead path shows up there too.

After 8 MiB of messages, the client ends the long POST and opens a fresh one, with no probe, because proxies and hosts limit the size of one request body, and on Cloudflare one request also has a limit on CPU time. The fresh one starts again at the first message with no answer yet, and the server drops the ones it already has. So one long POST carries about 8 MiB of new messages, plus the ones it sends again, which are at most four times `maxPostBytes`. With the default `maxPostBytes` of 512 KiB, one long POST stays under about 12 MiB.

## When a transport is not offered

A server answers a transport that it does not offer, so that a client with several transports moves on:

| Request                               | Node.js                        | Cloudflare                     |
| ------------------------------------- | ------------------------------ | ------------------------------ |
| A WebSocket upgrade, no `websocket()` | `404`                          | `426`                          |
| A plain HTTP request, no `http()`     | `426 Upgrade Required`         | `426 Upgrade Required`         |
| A method other than `GET` and `POST`  | `405`, with `Allow: GET, POST` | `405`, with `Allow: GET, POST` |

A browser cannot read the status of a WebSocket handshake. It sees close `1006` for any failed handshake, and the client moves on.

## Origins, CORS and proxies

The Origin check covers both transports. A request with an `Origin` header must have the same host and port as its `Host` header, or its origin must be in `allowedOrigins`. Otherwise it gets `403`, and `authenticate` does not run. A request with no `Origin` header, such as one from a Node or mobile client, passes, unless its `Sec-Fetch-Site` header says it came from another site. The [Node.js](/server/adapters/node#allowed-origins) and [Cloudflare](/server/adapters/cloudflare#allowed-origins) pages show the option.

The check compares the host and port of the `Origin` with `Host`. So it does not stop DNS rebinding against a server that has no authentication, for example a local dev server. Add `authenticate` to such a server.

A browser can send a cross-site request with no `Origin` header, for example a `no-cors` `fetch`. To stop this on the stream, the client sends a `LiveThing-Protocol: livething-v1` header with every stream request. A plain cross-site request cannot carry this header, so the browser must send a preflight first, and the preflight carries `Origin`. The server answers a stream request without this header, or with another value, with `426` and `LiveThing-Error: not-offered`. This is the same answer as for a request without `Accept: text/event-stream`. So a page on another origin cannot open a stream without an `Origin` header.

A client on another origin needs CORS for `http()`, because the stream and the POSTs are `fetch` requests. LiveThing does the CORS part for every origin in `allowedOrigins`:

- It answers the preflight `OPTIONS` request. It allows the `Authorization`, `LiveThing-Secret`, `LiveThing-Lane`, `LiveThing-Seq`, `LiveThing-Upload`, `LiveThing-Protocol` and `Content-Type` headers, and sets `Access-Control-Max-Age` to 600 seconds, so a browser does not repeat the preflight before each POST.
- It adds `Access-Control-Allow-Origin` and `Vary: Origin` to the stream, the POSTs and every error response, and exposes the `LiveThing-Error` header, so the client can read an error status.

A request from an origin that is not allowed gets no CORS headers, so the browser reports a network error. Set `allowedOrigins` for every origin that serves your pages. The stream and the POSTs send cookies to the same origin only. A client on another origin logs in with the [`token`](/client/connecting/auth-and-query#token-auth-with-token) option, which goes in an `Authorization` header when the stream opens. Keep tokens small: a request whose headers are too large fails with `431`.

A preflight has no `Authorization` header, no cookies and no LiveThing headers. So a proxy, a Worker or a middleware in front of LiveThing must let `OPTIONS` requests through to the endpoint, or answer them itself. A reverse proxy that changes the `Host` header needs `allowedOrigins`, because the same-origin check reads `Host`. nginx changes it by default. Add `proxy_set_header Host $http_host;` to keep the browser's `Host`, or set `allowedOrigins`. A plain nginx `proxy_pass` with no `Upgrade` headers blocks WebSocket, and the client moves on to `http()`. nginx also reads a whole request body before it passes it on, which keeps clients on batched POSTs; see [Stream mode](#stream-mode).

The stream response has `Cache-Control: no-store, no-transform` and `X-Accel-Buffering: no`. `no-transform` tells a proxy not to compress the stream, because a proxy that compresses holds data until a block fills. `X-Accel-Buffering: no` tells nginx not to buffer it.

## Costs and limits

`http()` costs more than WebSocket. When you list both, keep WebSocket first in the client's list, so a client uses `http()` only when WebSocket fails.

- **Binary is bigger going down.** The server sends a binary message as base64 text on the stream, which is about a third bigger than on WebSocket (for example, 40,121 characters for 30,088 bytes). The client sends binary up as raw bytes.
- **One POST at a time.** On batched POSTs, the client sends its messages in POST batches, one batch at a time, in order. A batch holds at most 255 messages and `maxPostBytes` of data. A second lane carries only `ping`, `pong` and the close, so a slow upload cannot delay a `pong`. Each POST goes to the exact URL of its stream, query included. [Stream mode](#stream-mode) sends the messages in one long POST instead.
- **Serve over HTTP/2 or HTTP/3.** HTTP/1.1 allows six connections per site, shared by all tabs, and one client on `http()` can use three: the stream and the two POST lanes. On HTTP/2 and HTTP/3 they all share one connection, and only there can the client use stream mode. Browsers use HTTP/2 only over TLS, so plain `http://localhost` is HTTP/1.1. For local development of an app that lists only `http()`, use a local certificate. LiveThing does not share one connection between tabs.
- **Delivery is at most once**, as on WebSocket. A message can be lost when the connection drops, and the client does not send it again. If your app needs a retry, the app sends the message again. Within one connection, each message has a number, so the server drops a copy: a message that the client sends again after stream mode fails, or a POST that a browser or a proxy repeats on a network connection that was reset. A new connection starts new numbers, so make actions that change data idempotent.
- **A logout does not close an open stream.** The login check runs once, when the stream opens. Each POST carries only the connection's secret, not the login token. So your logout code must close the user's connections, for example with [`ctx.closeConnections({ userId })`](/server/admin/context#close-connections). This is the same as on WebSocket.
- **Several Node instances need sticky routing.** The stream and its POSTs must reach the same Node process. Run one instance, or use a load balancer that sends the stream and its POSTs to the same instance. LiveThing does not forward requests between instances. A POST that reaches another instance gets `404`, and the client opens a new stream and resumes.
- **On Cloudflare, an open stream keeps the Durable Object awake.** See [Cloudflare](#cloudflare).

### A tab that goes to sleep

A browser can freeze a background tab to save power. Chrome does it with Energy Saver on, for example. A frozen tab runs no code, so it cannot answer the server's [`keepalive()`](/server/capabilities/keepalive) pings, and the server closes the connection with `4004` (`IDLE`) after `idleTimeoutMs`. When the tab wakes, the client gets that close at once, and [`reconnection()`](/client/primitives/reconnection) connects again. Use [`replay()`](/server/capabilities/replay) for the messages sent while the tab was asleep. We tested this with `http()` in Chrome.

## Node.js

On Node, `http()` uses plain HTTP requests, not upgrades, so they do not reach `huddleEndpoint.upgrade`. Pass every request to the endpoint's path to `huddleEndpoint.handle`. It serves the stream, the POSTs and the CORS preflight:

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import { http, setup, websocket } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind, ready } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocket(), http()],
})

function isHuddlePath(url = '/'): boolean {
  return new URL(url, 'http://localhost').pathname === '/huddle'
}

const app = createServer((request, response) => {
  if (isHuddlePath(request.url)) {
    huddleEndpoint.handle(request, response)
    return
  }

  response.statusCode = 404
  response.end()
})

app.on('upgrade', (request, socket, head) => {
  if (isHuddlePath(request.url)) {
    huddleEndpoint.upgrade(request, socket, head)
    return
  }

  socket.destroy()
})

await ready()
app.listen(3000)
```

`handle`, like `upgrade`, does not check the path. Your app does. `handle` also takes a request and a response from a `node:http2` compatibility server, which is how you serve `http()` over HTTP/2 on Node, and how browser clients get [stream mode](#stream-mode). Browsers use HTTP/2 only over TLS, so use `createSecureServer` from `node:http2` with `allowHTTP1: true`, which keeps WebSocket working on HTTP/1.1.

`shutdown()` closes the open streams with the other connections, and drops a stream request that is still in `authenticate`. Node's server timeouts do not cut an open stream, so you do not need to change them. A POST body follows Node's `requestTimeout`, which is 300 seconds by default. On `node:http`, that timeout also ends the long POST of stream mode after 300 seconds, and the client moves back to batched POSTs. A `node:http2` server has no such timeout.

## Node frameworks

Each [Node framework](/server/adapters/node#frameworks) binding has a matching route for `http()`. Hono, Fastify and H3 have their own `handle` route. The other frameworks run on a Node HTTP server that your app owns, so they use `huddleEndpoint.handle` from `@livething/server-node`.

### Express, Koa, React Router, SvelteKit and Astro

These [framework sections](/server/adapters/node#frameworks) bind Huddle with `@livething/server-node`. Add `transports` to that `bind()` call, and add a function that sends the `http()` requests for `/huddle` to LiveThing and passes every other request on:

```js [huddle-endpoint.js]
import { http, setup, websocket } from '@livething/server-node'
import { huddle } from './server/huddle-definition.ts'

export const huddleNode = setup()
export const huddleEndpoint = huddleNode.bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocket(), http()],
})

export function handleHuddleRequest(request, response, next) {
  const url = new URL(
    request.url ?? '/',
    `http://${request.headers.host}`,
  )
  if (url.pathname !== '/huddle') return next()

  huddleEndpoint.handle(request, response)
}
```

`handleHuddleRequest` has the shape of a Connect or Express middleware: `(request, response, next)`. For React Router, SvelteKit and Astro, the module also keeps its `globalThis` guard, and for SvelteKit and Astro its `handleHuddleUpgrade` function. The `upgrade` listener of each framework stays as it is.

### Express

Mount the function first, so no body parser reads the POST body before LiveThing does:

```ts [huddle-server.ts]
import express from 'express'
import { handleHuddleRequest } from './huddle-endpoint'

const app = express()
app.use(handleHuddleRequest)
```

The rest of the [Express](/server/adapters/node#express) setup stays the same.

### Koa

Send the request to LiveThing before it reaches Koa, so Koa does not answer it too:

```ts [huddle-server.ts]
import { createServer } from 'node:http'
import Koa from 'koa'
import { handleHuddleRequest } from './huddle-endpoint'

const app = new Koa()
const handleKoa = app.callback()
const httpServer = createServer((request, response) => {
  handleHuddleRequest(request, response, () => {
    void handleKoa(request, response)
  })
})
```

Add the `upgrade` listener of the [Koa](/server/adapters/node#koa) section to this `httpServer`.

### Hono

Mount `huddleEndpoint.handle` on the same path as `upgrade`, for every method. It serves the stream, the POSTs and the CORS preflight. A WebSocket upgrade passes through it to the next handler:

```ts [huddle-server.ts]
import { createAdaptorServer } from '@hono/node-server'
import {
  http,
  websocket as websocketTransport,
} from '@livething/server-node'
import { setup } from '@livething/server-node/hono'
import { Hono } from 'hono'
import { huddle } from './server/huddle-definition'

const app = new Hono()
const { bind, ready, websocket } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocketTransport(), http()],
})

app.get('/huddle', huddleEndpoint.upgrade)
app.all('/huddle', huddleEndpoint.handle)

await ready()
createAdaptorServer({ fetch: app.fetch, websocket }).listen(3000)
```

`setup()` of the Hono binding returns its own `websocket` object for `createAdaptorServer()`, so the example imports the transport function as `websocketTransport`.

### Fastify

With `http()` listed, a plain `GET` to the `connect` route opens the stream. Add `huddleEndpoint.handle` as a second route on the same path, for `POST` and `OPTIONS`. It answers in `onRequest`, before Fastify reads the body, so you need no content type parser:

```ts [huddle-server.ts]
import websocket from '@fastify/websocket'
import {
  http,
  websocket as websocketTransport,
} from '@livething/server-node'
import { setup } from '@livething/server-node/fastify'
import Fastify from 'fastify'
import { huddle } from './server/huddle-definition'

const app = Fastify()
await app.register(websocket)

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocketTransport(), http()],
})

app.get('/huddle', huddleEndpoint.connect)
app.route({
  method: ['POST', 'OPTIONS'],
  url: '/huddle',
  ...huddleEndpoint.handle,
})
```

### SvelteKit

In development, add `vite.middlewares.use(handleHuddleRequest)` to the plugin's `configureServer` hook in the [SvelteKit](/server/adapters/node#sveltekit-development-server) section, next to the `upgrade` listener.
```js [huddle-server.js]
import { createServer } from 'node:http'

const server = createServer((request, response) => {
  handleHuddleRequest(request, response, () =>
    handler(request, response),

```

The `upgrade` listener, `ready()` and the shutdown code of the production server stay the same.

### Astro

In development, add `server.middlewares.use(handleHuddleRequest)` to the `astro:server:setup` hook in the [Astro](/server/adapters/node#astro-development-server) section, next to the `upgrade` listener. In production, send each request to LiveThing first, then to the static files, then to Astro:

```js [huddle-server.js]
import { createServer } from 'node:http'
import sirv from 'sirv'
import { handler } from './dist/server/entry.mjs'
import { handleHuddleRequest } from './huddle-endpoint.mjs'

const assets = sirv('dist/client', { gzip: true })
const server = createServer((request, response) => {
  handleHuddleRequest(request, response, () =>
    assets(request, response, () => handler(request, response)),
  )
})
```

The `upgrade` listener, `ready()` and the shutdown code of the production server stay the same.

## Cloudflare

List the transports in the second argument of `bind()`:

```ts [worker.ts]
import { bind, http, websocket } from '@livething/server-cloudflare'
import { huddle } from './server/huddle-definition'

export class HuddleServer extends bind(huddle, {
  transports: [websocket(), http()],
}) {}
```

The Durable Object's `fetch` serves the stream, the POSTs and the CORS preflight, next to WebSocket upgrades. The Worker `fetch` of the [Cloudflare](/server/adapters/cloudflare) page does not change: it passes every request to the Durable Object. Two rules keep it working:

- **Route by the URL.** The Worker must send each POST to the same Durable Object as its stream. Each POST goes to the exact URL of its stream, query included, so a Worker that chooses the object from the path or a query value works. A POST carries no `Authorization` header and no header of your own, so a Worker cannot route by a header or by the login token. Put the routing key in the URL.
- **Pass the request on as it is.** `stub.fetch(request)` keeps the browser's `Host` header, which the Origin check reads. The Worker must also pass `OPTIONS` requests on, or the cross-origin preflight fails.

**`http()` gets no hibernation savings.** A WebSocket with [hibernation](/server/server/hibernation) lets Cloudflare remove the object from memory between messages. An `http()` stream does not: the object stays in memory while the stream is open. One open stream keeps the whole object awake, so the WebSocket clients in the same object lose their savings too. Stream mode does not change this, because its long POST is open as long as the stream. Cloudflare bills duration while the object is in memory, at 128 MB per object, not per client. Each POST is a billed request too: with the default 30-second ping, a client answers the server's ping with a POST every 30 seconds, which is 2,880 requests a day, and twice that when the client also runs its own [`keepalive()`](/client/primitives/keepalive). On batched POSTs, each batch of messages is one more request; in stream mode, the messages share the one long POST.

**Stream mode on Cloudflare.** The Durable Object reads the long POST as it arrives, and the Worker `fetch` passes the body on as a stream. Whether Cloudflare's network passes it on as it streams, and not after the body ends, depends on the path to your Worker: the client's [probe](#stream-mode) checks this on every connection, and a client whose probe gets no answer stays on batched POSTs.

On Cloudflare, one request body may be at most 100 MB on the Free and Pro plans of your domain and 200 MB on Business, whatever your Workers plan. Enterprise has 500 MB by default and can raise it. One Durable Object request also has 30 seconds of CPU time by default, and the handlers that a long POST's messages run can count toward it. The client's [fresh long POST every 8 MiB](#stream-mode) keeps it under the body limit, and each fresh one is a new request with fresh CPU time. If your handlers use a lot of CPU time, raise `limits.cpu_ms` in your Wrangler config. When a long POST dies at a limit, nothing is lost: the client sends the messages with no answer again in batched POSTs, and stays on them until it reconnects.

**Unread data has two caps.** A Durable Object has 128 MB of memory, and a client that stops reading keeps everything sent to it there. So the adapter drops a stream at once when its unread data would pass 48 MiB, and when the unread data of all streams of one object would pass 64 MiB, it drops the stream with the most unread data. One 32 MiB message is about 43 MiB as base64, so the cap per stream cannot be lower. A dropped stream closes with `1013` on the server. The client sees the stream fail, reconnects, and [replay](/server/replay/overview) sends what it missed. Streams and catch-up wait for the client at 256 KiB, so only a burst of plain sends reaches the caps. On a stream, `ctx.stream.drain()` waits for the client, as it does on Node.

When Cloudflare restarts the object, the stream is cut. The client reconnects and resumes, as it does on WebSocket.

## Bun

The [Bun](/server/adapters/bun) adapter takes the same `transports` list. Import `websocket()` and `http()` from `@livething/server-bun`, and list them in the `transports` option of its `bind()`. `http()` needs `keepalive()` in the definition, and every rule on this page applies.

## Deno

Deno is not a supported runtime. On [Deno](/server/adapters/deno) you use the Node.js adapter, so the [Node.js](#nodejs) setup above does not change: `http()` from `@livething/server-node`, and `huddleEndpoint.handle` in your request listener.
