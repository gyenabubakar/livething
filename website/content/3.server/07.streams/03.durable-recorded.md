A **recorded stream** keeps working after a client disconnects because it **stores every chunk** it sends. This store is the stream's **buffer**. When the client reconnects, it gets the chunks it missed from the buffer. The generator does **not** run again. Use this kind when your source is one-shot, which means you can't ask it for the same data again "from position N". Examples: tokens from an AI model (LLM), or events from a third-party API that pushes data to you.

To enable the builder, list `recordedStream()` in your capabilities. See [Stream capabilities](/server/capabilities/streams). The buffer is saved in the server's own SQL storage, and every LiveThing adapter provides this storage automatically. The plain-stream basics (generator, `signal`, `drain()`, ending) are on [Plain Streams](/server/streams/plain). This page covers only what recording adds.

## What "recorded" means

Every chunk you yield is written to storage _before_ it is sent. If the client drops after chunk 3 and reconnects, LiveThing sends chunks 4, 5, and so on from the buffer. Your generator never restarts, and your code can't tell that a replay happened. This is the main difference from a cursor stream.

What happens to the generator _while_ the client is away is set by `onDisconnect`:

- `'cancel-but-buffer'` (the default) stops the generator and keeps the buffer.
- `'keep-running'` lets the generator run to the end and adds each new chunk to the buffer.

See [Configuration & Lifecycle](/server/streams/config-and-lifecycle#disconnect-behavior-durable-only).

```ts [server/scout.ts]
import { server, t } from '@livething/server'
import { recordedStream } from '@livething/server/streams'
import * as v from 'valibot'

const ReplyChunk = t<{ text: string }>()

const base = server({
  capabilities: [recordedStream()],
})

export const handleAskScout = base.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  chunk: ReplyChunk,
  maxChunks: 500,
  maxAgeMs: 300_000,
  retentionAfterEndMs: 30_000,
  async *run(ctx, input) {
    const messages = [
      { role: 'user' as const, content: input.prompt },
    ]
    for await (const piece of llm.stream({
      messages,
      signal: ctx.stream.signal,
    })) {
      yield { text: piece }
    }
  },
})
```

A recorded stream has no cursor and no `withCursor`. You only yield chunks, and LiveThing keeps the buffer. `ctx.stream` has no `cursor` property here, so recording needs no extra code in your generator.

How a chunk looks on the wire depends on its type:

- A **plain-object** chunk is sent as it is. Its keys become the frame payload. An object whose `toJSON()` returns an object is sent as that object.
- Any other chunk with JSON is wrapped as `{ value: <chunk> }`: a number, a string, `null`, an array, or an object whose `toJSON()` gives something else, such as a `Date`. The client reads it at `.value`, and the client's types say so: with `chunk: t<number>()`, each chunk is typed `{ value: number | null }`, because JSON sends `NaN` and `Infinity` as `null`.
- A chunk with no JSON is refused with an error: `undefined`, a function without `toJSON()`, a `symbol`, a `bigint`, and an iterable without `toJSON()` such as a `Map` (JSON would send `{}`).

Yield objects when you want the client to get the same shape you yielded.

## How it differs from cursor

Both kinds are durable (they are stored, so they continue after a reconnect). But they store different things and act differently on reconnect.

|                               | `recordedStream`                              | `cursorStream`                                         |
| ----------------------------- | --------------------------------------------- | ------------------------------------------------------ |
| What is stored                | **Every chunk**                               | Cursor **checkpoints**, never chunk payloads           |
| On reconnect                  | Sends the missed chunks from the buffer       | Runs the generator again from the saved checkpoint     |
| Does the generator run again? | No                                            | Yes                                                    |
| Best for                      | One-shot sources (AI model tokens, push APIs) | Sources you can re-read (database pages, file offsets) |
| `maxChunks`                   | Yes: sets the buffer size limit               | No: stores no chunks                                   |
| `cursor` config               | No                                            | Yes                                                    |

If your source _can_ start again from a position, use [cursor](/server/streams/durable-cursor) instead. A cursor checkpoint is usually much smaller than a chunk. Use recorded only when the source really can't send the same data again.

## The buffer limit and StreamAborted

The buffer holds at most `maxChunks` chunks (default **500**). When a yield would add one chunk more than that, LiveThing throws `StreamAborted` with `reason: 'buffer-full'` **at the generator's `yield`**. Your code can catch it and stop cleanly.

```ts [server/scout.ts]
import { StreamAborted } from '@livething/server/errors'

export const handleAskScoutShort = base.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  chunk: ReplyChunk,
  maxChunks: 2, // a very small limit, to show the behavior
  async *run(ctx, input) {
    const messages = [
      { role: 'user' as const, content: input.prompt },
    ]
    for await (const piece of llm.stream({
      messages,
      signal: ctx.stream.signal,
    })) {
      try {
        yield { text: piece }
      } catch (err) {
        if (
          StreamAborted.matches(err) &&
          err.detail.reason === 'buffer-full'
        ) {
          return // stop cleanly: the buffer is full
        }
        throw err
      }
    }
  },
})
```

The stream ends in both cases. The difference is what the client gets:

- If you catch the error and `return`, the stream ends normally.
- If you don't catch it, the `StreamAborted` error leaves the generator and the client gets it as the stream's error. Client code can use it, for example, to show a "slow down" message.

`StreamAborted` is a built-in error from `@livething/core`. See the [built-in errors catalog](/core/builtin-errors) and the full list of [abort reasons](/server/streams/config-and-lifecycle#abort-reasons).

::caution
`maxChunks` is a hard limit on how many chunks the buffer holds **at the same time**. Chunks are not removed from the buffer when the client reads them, so the buffer grows with every `yield`. When a `yield` makes the count go over `maxChunks`, LiveThing does three things. It deletes the oldest chunk so the buffer is back at the limit. It throws `StreamAborted({ reason: 'buffer-full' })` at that `yield`. And it ends the stream. The chunk from that last `yield` is not sent to the connected client. So a recorded stream can't produce more than `maxChunks` chunks. Catch the error to stop cleanly, or set a limit large enough for the whole run.
::

## The contract slice

Every server-pushed stream reaches the client through the one `streams` map that `InferClient` produces (see the [overview](/server/streams/overview)). A recorded stream's entry uses the stream name as its key and has `kind: 'persistent'`, the same as a cursor stream. It has no cursor, so it has the same fields as a plain stream's entry.

```ts [client/socket.ts]
type ClientStreams = {
  'ask-scout': {
    payload: { prompt: string }
    chunk: { text: string }
    kind: 'persistent'
  }
}
```

Recording happens only on the server. The client uses the same `continueStream(...)` call and the same automatic reconnect as for cursor streams. For the client, a replay and a new run of the generator look the same.

## Nudges and reconnect

Nudges work the same as on a plain stream. A nudge reaches only a **running** generator, because nudges are kept in memory, not in storage.

If a nudge stopped the stream before the client dropped, the stream stays stopped after the reconnect. The generator has returned, so the stream is marked as ended. A reconnect sends the recorded chunks up to that point and does not run the generator again.

A nudge that arrived but was not read yet may or may not survive a drop. This depends on `onDisconnect`: the default `'cancel-but-buffer'` drops it, and `'keep-running'` keeps it. See [Configuration & lifecycle](/server/streams/config-and-lifecycle).

```ts [server/scout.ts]
export const handleAskScoutStoppable = base.recordedStream(
  'ask-scout',
  {
    input: v.object({ prompt: v.string() }),
    chunk: ReplyChunk,
    nudges: { stop: null },
    maxChunks: 500,
    async *run(ctx, input) {
      const messages = [
        { role: 'user' as const, content: input.prompt },
      ]
      for await (const piece of llm.stream({
        messages,
        signal: ctx.stream.signal,
      })) {
        const recent = ctx.stream.nudges(yield { text: piece })
        if (recent.some((n) => n.event === 'stop')) return
      }
    },
  },
)
```

## Retention and disconnect behavior

A recorded stream's buffer is kept in storage so a client that comes back can get the missed chunks. Three options control this: how long the buffer is kept (`maxAgeMs`, `retentionAfterEndMs`) and what the generator does when the client drops (`onDisconnect`).

| Option                | Default               | What it controls                                                                |
| --------------------- | --------------------- | ------------------------------------------------------------------------------- |
| `maxAgeMs`            | 5 minutes             | How long the buffer is kept while the stream is suspended (client disconnected) |
| `retentionAfterEndMs` | 30 seconds            | How long the buffer is kept after the stream ends                               |
| `onDisconnect`        | `'cancel-but-buffer'` | What the generator does when the client drops                                   |

The generator has no position it can restart from, so `onDisconnect: 'keep-running'` is a good match for recorded streams. The generator runs to the end while the client is away and adds each chunk to the buffer. Full details are on [Configuration & Lifecycle](/server/streams/config-and-lifecycle).

If the server process stops while a recorded stream is running (a deploy, a crash, or a restart), the stream becomes suspended when the server starts again. A client that continues it gets the chunks in the buffer and then the end of the stream, because the generator cannot start again. If nobody continues it, LiveThing deletes it after `maxAgeMs`.
