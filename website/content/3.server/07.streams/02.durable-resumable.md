A **resumable stream** continues after a client disconnects. When the client comes back, LiveThing runs your generator again, starting from the checkpoint of the last chunk the client received. LiveThing does not store the chunks themselves. Use this kind when your source can run again from a position: database pagination, a file offset, a row ID.

To use `base.resumableStream`, list `resumableStream()` in your capabilities. See [Stream capabilities](/server/capabilities/streams). Cursor checkpoints are saved in the server's own SQL storage. Every LiveThing adapter gives the server this storage. On Node.js the default is an in-memory database, so pass a database file to `bind()` if checkpoints must survive a server restart (see [Node.js](/server/adapters/node/node-http)). The basics of plain streams (the generator, `signal`, `drain()`, ending a stream) are on [Plain Streams](/server/streams/plain). This page covers only what resumable streams add.

## What "resumable" means

Each chunk has a **sequence number** (`seq`): 1 for the first chunk, 2 for the second, and so on. You can attach a cursor to a chunk with `ctx.stream.withCursor(...)`. For each `withCursor(...)` call, LiveThing saves a small cursor checkpoint. It never saves the chunk itself.

If the client drops and reconnects, it sends the sequence number of the last chunk it received. LiveThing finds the latest checkpoint at or before that number, runs the generator again from that checkpoint, and sends the next chunks.

```ts [server/scout.ts]
import { server, t } from '@livething/server'
import { resumableStream } from '@livething/server/streams'
import * as v from 'valibot'

const ExportChunk = t<{ messages: Message[] }>()
const ExportCursor = v.object({ before: v.number() })

const base = server({
  capabilities: [resumableStream()],
})

export const handleExportRoom = base.resumableStream('export-room', {
  input: v.object({ roomId: v.string() }),
  chunk: ExportChunk,
  cursor: ExportCursor,
  async *run(ctx, input) {
    let before = ctx.stream.cursor?.before ?? Date.now()
    while (true) {
      const messages = await loadMessages(input.roomId, before)
      if (messages.length === 0) return
      before = messages[messages.length - 1].sentAt
      yield ctx.stream.withCursor({ messages }, { before })
    }
  },
})
```

On the first run, `ctx.stream.cursor` is `null`, so the export starts from now. Each `withCursor` call saves a cursor checkpoint before the chunk is sent. If the client last received messages down to `sentAt: 1_000`, and then reconnects, `ctx.stream.cursor` is `{ before: 1_000 }`, and the loop continues paging from there. If the server was loading the next page when the connection dropped, LiveThing does not count that page, and sends it again after the reconnect.

## The start payload is used again on resume

`run(ctx, payload)` gets the same second argument every time the generator starts, on the first run and on every resume. LiveThing stores the payload the client sent to start the stream, and passes the same value again on each resume. Only `ctx.stream.cursor` and `ctx.stream.attempt` change between runs. `payload` always holds the value from the first start.

```ts [server/scout.ts]
export const handleExportRoom = base.resumableStream('export-room', {
  input: v.object({ roomId: v.string() }),
  chunk: ExportChunk,
  cursor: ExportCursor,
  async *run(ctx, payload) {
    // payload.roomId is the same on every resume. The client does not send it again.
    let before = ctx.stream.cursor?.before ?? Date.now()
    while (true) {
      const messages = await loadMessages(payload.roomId, before)
      if (messages.length === 0) return
      before = messages[messages.length - 1].sentAt
      yield ctx.stream.withCursor({ messages }, { before })
    }
  },
})
```

::note
On resume, LiveThing does not check the stored payload against `input` again. Only the `cursor` is checked at runtime, and only when you give it a schema. If the stored payload is damaged, the resuming client gets the same error as for a bad cursor: `StreamAborted({ reason: 'cursor-invalid' })`.
::

## The resumable stream handle

In a resumable generator, `ctx.stream` has three more fields than the [base handle](/server/streams/plain#the-abort-signal) (`signal`, `drain`, and `nudges` when the stream declares nudges):

| Field                                  | What it is                                                                                                                  |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `ctx.stream.cursor`                    | The checkpoint for the last chunk the client received, or `null` on the first run. Its type comes from the `cursor` config. |
| `ctx.stream.attempt`                   | `1` on the first run, `2` or higher on a resume.                                                                            |
| `ctx.stream.withCursor(chunk, cursor)` | Attaches a cursor checkpoint to a chunk. LiveThing saves the checkpoint first, then sends the chunk.                        |

Use `attempt` when a resume must behave differently from the first run. For example, you can mark the chunks sent after a resume:

```ts [server/scout.ts]
export const handleExportRoom = base.resumableStream('export-room', {
  input: v.object({ roomId: v.string() }),
  chunk: t<{ messages: Message[]; resumed: boolean }>(),
  cursor: ExportCursor,
  async *run(ctx, input) {
    // attempt is 1 on the first run and 2 or higher on a resume.
    const resumed = ctx.stream.attempt > 1
    let before = ctx.stream.cursor?.before ?? Date.now()
    while (true) {
      const messages = await loadMessages(input.roomId, before)
      if (messages.length === 0) return
      before = messages[messages.length - 1].sentAt
      yield ctx.stream.withCursor({ messages, resumed }, { before })
    }
  },
})
```

## `withCursor` vs a plain `yield`

You do not have to save a cursor with every chunk. A plain `yield value` sends a chunk with no checkpoint. `yield ctx.stream.withCursor(chunk, cursor)` sends a chunk and saves a checkpoint. On resume, the generator starts from the latest checkpoint at or before the last sequence number the client received. Plain chunks after that checkpoint are produced again. The LiveThing client skips chunks with a sequence number it already has, so the user does not see them twice.

This example saves a checkpoint only every tenth page, to cut down on storage writes for a room with a long history:

```ts [server/scout.ts]
export const handleExportRoomBatched = base.resumableStream(
  'export-room',
  {
    input: v.object({ roomId: v.string() }),
    chunk: ExportChunk,
    cursor: ExportCursor,
    async *run(ctx, input) {
      let before = ctx.stream.cursor?.before ?? Date.now()
      let page = 0
      while (true) {
        const messages = await loadMessages(input.roomId, before)
        if (messages.length === 0) return
        before = messages[messages.length - 1].sentAt
        page += 1
        if (page % 10 === 0) {
          yield ctx.stream.withCursor({ messages }, { before })
        } else {
          yield { messages }
        }
      }
    },
  },
)
```

If the client last received page 47, the latest checkpoint is page 40. The generator runs again from page 41. The client already has pages 41 to 47, so it skips them and shows page 48 onward.

If a stream never calls `withCursor`, it has no checkpoints, and every resume starts with `ctx.stream.cursor` set to `null`.

::tip
Write your generator so it can run again safely. A resume runs `run` again from a past cursor, so every chunk between that cursor and the drop is produced again from the source. For `export-room`, this means "select the messages sent before `cursor.before`". That query is **idempotent** (running it twice gives the same result), so it is safe to run again. Do not put work that must happen exactly once per chunk inside the loop.
::

## The cursor type: marker vs validator

The `cursor` config can be a [type marker](/server/server/overview) (`t<T>()`, which gives a TypeScript type and does no runtime check) or a real schema. The difference: a schema checks the cursor at runtime when LiveThing reads it back from storage. A type marker does not.

::code-group

```ts [Type marker]
// t<T>() is type-only. The cursor has a type in the generator, but LiveThing
// does NOT check a cursor it reads back from storage. It uses it as it is.
export const handleExportRoom = base.resumableStream('export-room', {
  input: v.object({ roomId: v.string() }),
  chunk: ExportChunk,
  cursor: t<{ before: number }>(),
  async *run(ctx, input) {
    let before = ctx.stream.cursor?.before ?? Date.now()
    // ...
  },
})
```

```ts [Validated]
// A schema also checks every cursor LiveThing reads back from storage. If the
// stored value no longer matches (an older deploy wrote it, or someone edited
// the row), the resuming client gets StreamAborted({ reason: 'cursor-invalid' }).
const ExportCursor = v.object({ before: v.number() })

export const handleExportRoom = base.resumableStream('export-room', {
  input: v.object({ roomId: v.string() }),
  chunk: ExportChunk,
  cursor: ExportCursor,
  async *run(ctx, input) {
    let before = ctx.stream.cursor?.before ?? Date.now()
    // ...
  },
})
```

::

Use a schema when a stream lives long enough that its cursor could come from an older deploy, or when someone could change the stored row. A failed check does not crash the server. LiveThing deletes the stored stream, and the resuming client gets `StreamAborted` with `reason: 'cursor-invalid'`. The client can then start a new stream, or show the problem to the user. See [abort reasons](/server/streams/config-and-lifecycle#abort-reasons) for the full list.

## The contract slice

`InferClient` puts every server-pushed stream (plain, resumable and recorded) in one `streams` map (see the [overview](/server/streams/overview)). A resumable stream appears under its name with `kind: 'persistent'`. The `cursor` is not part of the client view: only the server reads it, and it never goes over the network.

```ts [client/socket.ts]
type ClientStreams = {
  'export-room': {
    payload: { roomId: string }
    chunk: { messages: Message[] }
    kind: 'persistent'
  }
}
```

The cursor is server-side state. The client never sets it or reads it, and it is never sent over the WebSocket. A resume uses the stream ID and `lastKnownSeq` (see [`resumeStream`](/client/streams/durable-and-resume)), not the cursor.

## Nudges and resume

A **nudge** is a typed message the client sends into a running stream. Nudges work the same way as on a plain stream: declare them in `nudges`, and read them with `ctx.stream.nudges(yield ...)`. A nudge reaches only a generator that is **running**. LiveThing keeps nudges that have not been read yet in memory only. It does not save them to storage.

Every resume of a resumable stream starts a new run of the generator, with no nudges waiting. So nudges the old run had not read yet are lost on a resume. This is true for both `onDisconnect` values. See [Configuration & Lifecycle](/server/streams/config-and-lifecycle) for `onDisconnect`.

When a nudge ends the stream (the generator returns, as with the `stop` nudge below), the stored stream is marked `ended`. A client that already received the end of the stream does not resume it. But if the client missed some chunks before the end, a resume runs the generator again from the checkpoint to produce those chunks. The `stop` nudge is not stored, so that new run does not see it. If a stop must hold after a resume, save that fact in your own storage and check it in the generator.

```ts [server/scout.ts]
export const handleExportRoomNudged = base.resumableStream(
  'export-room',
  {
    input: v.object({ roomId: v.string() }),
    chunk: ExportChunk,
    cursor: ExportCursor,
    nudges: { stop: null },
    async *run(ctx, input) {
      let before = ctx.stream.cursor?.before ?? Date.now()
      while (true) {
        const messages = await loadMessages(input.roomId, before)
        if (messages.length === 0) return
        before = messages[messages.length - 1].sentAt
        const recent = ctx.stream.nudges(
          yield ctx.stream.withCursor({ messages }, { before }),
        )
        if (recent.some((n) => n.event === 'stop')) return
      }
    },
  },
)
```

`stop: null` declares a nudge with no payload. The client sends it with `handle.nudge('stop')`.

## Retention and disconnect behavior

LiveThing keeps resumable cursor checkpoints in storage so a client that comes back can resume. It never stores the chunks. Three options control this: `maxAgeMs` and `retentionAfterEndMs` set how long the checkpoints stay, and `onDisconnect` sets what the generator does when the client drops. These options work the same way for both durable kinds, and [Configuration & Lifecycle](/server/streams/config-and-lifecycle) covers them.

| Setting                   | Default                                                                |
| ------------------------- | ---------------------------------------------------------------------- |
| Suspended stream kept for | **5 minutes**                                                          |
| Ended stream kept for     | **30 seconds**                                                         |
| On disconnect             | The generator is cancelled, but its cursor checkpoints stay for resume |

A **suspended** stream is one whose client has dropped and has not come back yet.

A stream that was still running when the server process stopped (a deploy, a crash, or a restart) also becomes suspended when the server starts again. The client can resume it as usual. If nobody resumes it, LiveThing deletes it after `maxAgeMs`, like any other suspended stream.

::warning
`onDisconnect: 'keep-running'` requires `broadcast: true`. If you set it on a stream that is not a broadcast, `base.resumableStream()` throws when you call it, not later at `assemble()`.
::

## Resumable vs recorded

`resumableStream` stores cursor checkpoints and runs the generator again. `recordedStream` stores every chunk and sends the missed chunks again without running the generator. Use resumable when the source can run again from a position. Use [recorded](/server/streams/durable-recorded) when it cannot (AI model tokens, a push API that sends each item only once).

::note
`resumableStream` does **not** accept `maxChunks`. That option limits the stored chunks of a recorded stream only. A resumable stream keeps its cursor checkpoints until the stream is deleted or expires. On a reconnect, LiveThing also deletes the checkpoints after the last chunk the client received.
::
