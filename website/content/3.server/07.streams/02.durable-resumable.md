A **resumable stream** survives a client disconnect. When the client comes back, the framework re-runs your generator from a cursor checkpoint for the last chunk the client confirmed receiving. It never stores the chunks themselves. This is the right kind when your source can be re-run from a position: database pagination, a file offset, a row ID.

To enable the builder, list `resumableStream()` in your capabilities — see [Stream capabilities](/server/capabilities/streams). Cursor checkpoints are stored durably in the server's own SQL storage, which every WSKit adapter provides automatically. The plain-stream basics (generator, `signal`, `drain()`, ending) are on [Plain Streams](/server/streams/plain); this page covers only what resumability adds.

## What "resumable" means

You record a cursor alongside each chunk. The framework persists a small cursor checkpoint for every `withCursor(...)` call — never the chunk payload. If the client drops and reconnects, it reports the last sequence it received. WSKit selects that checkpoint, re-runs the generator from it, and sends the next chunk again.

```ts [resumable.ts]
import { server, t } from '@wskit/server'
import { resumableStream } from '@wskit/server/streams'
import * as v from 'valibot'

const RowChunk = t<{ row: number }>()
const PaginateCursor = v.object({ idx: v.number() })

const base = server({
  capabilities: [resumableStream()],
})

export const handlePaginate = base.resumableStream('paginate', {
  input: v.object({}),
  chunk: RowChunk,
  cursor: PaginateCursor,
  async *run(ctx) {
    const startAt = ctx.stream.cursor?.idx ?? 0
    for (let i = startAt + 1; i <= 1000; i += 1) {
      yield ctx.stream.withCursor({ row: i }, { idx: i })
    }
  },
})
```

On the first run `ctx.stream.cursor` is `null`, so `startAt` is `0`. Each `withCursor` saves a cursor checkpoint before the chunk goes out. If the client confirms row 40 and reconnects, `ctx.stream.cursor` is `{ idx: 40 }`, and the loop resumes at row 41. If the server tried row 41 but the connection dropped first, WSKit ignores that attempt and sends row 41 again.

## The start payload is replayed on resume

`run(ctx, payload)` takes the same second argument every time the generator starts — a fresh start and every later resume alike. The framework stores the payload the client sent to start the stream, and hands it back unchanged on each resume attempt. Only `ctx.stream.cursor` and `ctx.stream.attempt` change between attempts; `payload` stays the value from the original start.

```ts [resumable-payload.ts]
export const handleSearchPaginate = base.resumableStream(
  'search-paginate',
  {
    input: v.object({ query: v.string() }),
    chunk: RowChunk,
    cursor: PaginateCursor,
    async *run(ctx, payload) {
      // payload.query is the same on every resume — the client never re-sends it.
      const startAt = ctx.stream.cursor?.idx ?? 0
      for (let i = startAt + 1; i <= 1000; i += 1) {
        yield ctx.stream.withCursor({ row: i }, { idx: i })
      }
    },
  },
)
```

::note
The stored payload is not re-validated against `input` on resume — only the `cursor` gets a runtime check, and only when you pass it a schema. A corrupted stored payload surfaces the same way a bad cursor does: `StreamAborted({ reason: 'cursor-invalid' })` on the resuming client.
::

## The resumable stream handle

A resumable generator's `ctx.stream` adds three things on top of the [base handle](/server/streams/plain#the-abort-signal) (`signal`, `drain`, and `nudges` when declared):

| Field                                  | What it is                                                                                                          |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `ctx.stream.cursor`                    | The checkpoint for the last chunk the client confirmed, or `null` on the first run. Typed from the `cursor` config. |
| `ctx.stream.attempt`                   | `1` on the first run; `2`, `3`, … on each resume.                                                                   |
| `ctx.stream.withCursor(chunk, cursor)` | Attach a cursor checkpoint to a chunk. The framework saves it before the chunk hits the wire, then sends the chunk. |

`attempt` is handy when the first run and a resume should behave differently — for example, sending a "reconnected" marker only on a resume.

```ts [attempt.ts]
export const handleAttempt = base.resumableStream('attempt-stream', {
  input: v.object({}),
  chunk: t<{ attempt: number }>(),
  cursor: t<{ idx: number }>(),
  async *run(ctx) {
    // attempt is 1 on the first run, 2+ after each resume.
    yield ctx.stream.withCursor(
      { attempt: ctx.stream.attempt },
      { idx: 1 },
    )
    // ...keep producing...
  },
})
```

## `withCursor` vs a bare `yield`

You do not have to record a cursor on every chunk. A bare `yield value` sends a chunk without adding a checkpoint; `yield ctx.stream.withCursor(chunk, cursor)` adds one. On resume, the generator starts from the latest checkpoint at or before the client-confirmed sequence. Bare-yield chunks after that checkpoint are generated again; the standard client drops repeated sequence numbers.

```ts [bare-yield.ts]
export const handlePaginateBare = base.resumableStream(
  'paginate-bare',
  {
    input: v.object({}),
    chunk: t<{ row: number }>(),
    async *run(ctx) {
      // No cursor recorded — a resume restarts from cursor === null.
      const offset = ctx.stream.cursor === null ? 0 : 100
      for (let i = 1; i <= 4; i += 1) {
        yield { row: offset + i }
      }
    },
  },
)
```

::tip
Make your generator replayable. Because a resume re-runs `run` from a past cursor, anything between the cursor and "now" is produced again from the source. For a database read that means "select rows after `cursor.idx`" — idempotent and safe to re-run. Avoid side effects that must happen exactly once per chunk inside the loop.
::

## The cursor type: marker vs validator

The `cursor` config can be either a [type marker](/server/server/overview) (`t<T>()`) or a real schema. They differ in one important way — whether the cursor is checked at runtime when it is restored from storage.

::code-group

```ts [type-only.ts]
// t<T>() is type-only. The cursor is typed in the generator, but a restored
// cursor is NOT validated — it is trusted as-is.
export const handle = base.resumableStream('paginate', {
  input: v.object({}),
  chunk: RowChunk,
  cursor: t<{ idx: number }>(),
  async *run(ctx) {
    const startAt = ctx.stream.cursor?.idx ?? 0
    // ...
  },
})
```

```ts [validated.ts]
// A schema also runtime-checks every cursor restored from storage. If the
// stored shape no longer matches (older deploy, tampered row), the resuming
// client gets StreamAborted({ reason: 'cursor-invalid' }).
const PaginateCursor = v.object({ idx: v.number() })

export const handle = base.resumableStream('paginate', {
  input: v.object({}),
  chunk: RowChunk,
  cursor: PaginateCursor,
  async *run(ctx) {
    const startAt = ctx.stream.cursor?.idx ?? 0
    // ...
  },
})
```

::

Use a schema when the cursor is long-lived enough that an old deploy or a tampered row is a real risk. A failed validation does not crash the stream — the row stays in place and the resuming client gets a `StreamAborted` with `reason: 'cursor-invalid'`, so it can drop the stream, start fresh, or surface the problem. See [abort reasons](/server/streams/config-and-lifecycle#abort-reasons) for the full list.

## The contract slice

`InferClient` exposes every server-pushed stream — plain, resumable, and recorded alike — in one merged `streams` map (see the [overview](/server/streams/overview)). A resumable stream lands under its name with `kind: 'persistent'`; when you declare a `cursor`, its type rides along too.

```ts [client-streams-view.ts]
type ClientStreams = {
  paginate: {
    payload: {}
    chunk: { row: number }
    cursor: { idx: number }
    kind: 'persistent'
  }
}
```

The `cursor` is server-side state — the client never sets it or reads it. Resume is driven by the stream id and `lastKnownSeq` (see [`resumeStream`](/client/streams/durable-and-resume)), not by the cursor: the cursor is never sent on the wire. The `cursor` type still rides along in the merged client entry above, but no client API consumes it.

## Nudges and resume

Nudges work the same as on a plain stream (declare them in `nudges`, read with `ctx.stream.nudges(yield ...)`). A nudge only reaches a **running** generator — it sits in an in-memory buffer, and WSKit does not persist it.

When a nudge ends the stream — the generator returns, as the `stop` nudge does below — the durable row goes to `ended`. Resuming an ended stream replays `__streamEnd__` and never re-runs the generator, so a stream a nudge stopped before a drop stays stopped after the reconnect. Whether an _unconsumed_ buffered nudge outlives a drop depends on `onDisconnect`: the default `'cancel-but-buffer'` discards the nudge buffer (a re-run starts empty), while `'keep-running'` never stops the generator, so its buffer carries through — see [Configuration & lifecycle](/server/streams/config-and-lifecycle).

```ts [resumable-nudge.ts]
export const handlePaginateNudged = base.resumableStream(
  'paginate-nudged',
  {
    input: v.object({}),
    chunk: RowChunk,
    nudges: { stop: v.object({}) },
    async *run(ctx) {
      const startAt = ctx.stream.cursor?.idx ?? 0
      for (let i = startAt + 1; i <= 1000; i += 1) {
        const recent = ctx.stream.nudges(
          yield ctx.stream.withCursor({ row: i }, { idx: i }),
        )
        if (recent.some((n) => n.event === 'stop')) return
      }
    },
  },
)
```

## Retention and disconnect behavior

Resumable cursor checkpoints are kept in storage so a returning client can resume — the chunks themselves are never stored. How long they stay, and what the generator does the moment the client drops, are set by `maxAgeMs`, `retentionAfterEndMs`, and `onDisconnect`. Those apply to both durable kinds and are covered together on [Configuration & Lifecycle](/server/streams/config-and-lifecycle).

| Setting                   | Default                                                              |
| ------------------------- | -------------------------------------------------------------------- |
| Suspended stream kept for | **5 minutes**                                                        |
| Ended stream kept for     | **30 seconds**                                                       |
| On disconnect             | Generator is cancelled, but its cursor checkpoints remain for resume |

::warning
`onDisconnect: 'keep-running'` requires `broadcast: true`. Setting it on a non-broadcast stream throws at `base.resumableStream()` call time, not at assemble.
::

## Resumable vs recorded

`resumableStream` stores cursor checkpoints and re-runs the generator. `recordedStream` stores every chunk and replays the missed ones without re-running. Pick resumable when the source can be re-run from a position; pick [recorded](/server/streams/durable-recorded) when it can't (LLM tokens, a one-shot push API).

::note
`resumableStream` does **not** accept `maxChunks` — that option caps recorded payload chunks only. Resumable streams store cursor checkpoints until the stream is deleted, expires, or a reconnect discards unconfirmed later checkpoints.
::
