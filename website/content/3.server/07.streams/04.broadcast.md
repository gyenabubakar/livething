**Broadcasting** runs one generator and sends each of its chunks to many connections at the same time. This is called **fan-out**: one source, many receivers. Set `broadcast: true` on a stream. The server runs the generator once, on the connection that started the stream (the **creator**). Every connection in scope receives the same chunks. You write the same generator as for any other stream. The only change is who receives the chunks.

Broadcast is an option on a stream. It is not a fourth stream kind. It works on plain, resumable, and recorded streams. This page covers the scope rules, durable broadcast, and channel-scoped broadcast. For how a client receives a broadcast (it only listens, with `onStream`), see [Broadcast (onStream)](/client/streams/broadcast-onstream).

## A plain broadcast stream

Add `broadcast: true`, and the generator's chunks go to every connection in scope. The **scope** is the set of connections that receive the chunks. For a top-level stream, the scope is every connection that is connected to the server.

```ts [server/admin.ts]
import { server, t } from '@livething/server'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'

const LogLine = t<{ line: string }>()

const base = server({
  capabilities: [stream()],
})

export const handleTailAuditLog = base.stream('tail-audit-log', {
  input: v.object({}),
  chunk: LogLine,
  broadcast: true,
  async *run(ctx) {
    for await (const line of auditLogEntries(ctx.stream.signal)) {
      yield line
    }
  },
})
```

One client starts the stream, and every connection in scope gets the chunks. Each chunk carries the same stream ID and the same sequence number (the chunk's position in the stream: 1, 2, 3, and so on) for every receiver. So every subscriber sees the chunks in the same order.

## How a broadcast ends for subscribers

A **subscriber** is a connection in scope that receives the chunks but did not start the stream. When the generator finishes or throws, the server sends a **terminal frame** (the last message of a stream) to every subscriber too. This frame carries the stream's event name, so each client knows which stream ended.

| Event                             | What subscribers see                                                    |
| --------------------------------- | ----------------------------------------------------------------------- |
| Generator completes               | A stream-end frame, sent to every subscriber.                           |
| Generator throws a defined error  | That error, as a terminal frame, sent to every subscriber.              |
| Generator throws an unknown error | `internal-error`, as a terminal frame, sent to every subscriber.        |
| Creator cancels the stream        | A stream-end frame. The stream is over for everyone.                    |
| A _subscriber_ cancels            | Only that subscriber stops. The stream keeps running for everyone else. |

The last two rows show who controls the run: the **creator**. A cancel from any other connection only removes that one subscriber.

```ts [server/admin.ts]
export const handleTailAuditLogBoom = base.stream('tail-audit-log', {
  input: v.object({}),
  chunk: LogLine,
  broadcast: true,
  async *run(ctx) {
    for await (const line of auditLogEntries(ctx.stream.signal)) {
      yield line
      if (!line.line) {
        // The creator and every subscriber get this terminal error.
        throw new Error('audit log source is unreachable')
      }
    }
  },
})
```

## Durable broadcast

Durable streams (resumable and recorded) can broadcast too. One generator runs, and its chunks go to everyone in scope. The two durable kinds store different things:

- A **recorded** broadcast stores the chunks themselves. A **late joiner** (a connection that joins the scope after the stream started) first gets the chunks it missed from storage, then gets new chunks as they come.
- A **resumable** broadcast stores only source checkpoints (cursors), not chunks. A subscriber that reconnects gets only the new chunks from that point.

A late joiner gets nothing from a durable broadcast until it resumes the stream by its stream ID. On the client, it does this with [`resumeStream`](/client/streams/durable-and-resume#cold-resume-with-resumestream). Connections that were already in scope when the stream started get the chunks from the start.

The next examples reuse this `base`. It lists `stream()` too, because the channel-scoped example further down uses `rooms.stream`.

```ts [server/rooms.ts]
import { server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import {
  recordedStream,
  resumableStream,
  stream,
} from '@livething/server/streams'
import * as v from 'valibot'

const Empty = v.object({})
const ReplyChunk = t<{ text: string }>()
const ExportChunk = t<{ messages: Message[] }>()

const base = server({
  capabilities: [
    channels(),
    stream(),
    recordedStream(),
    resumableStream(),
  ],
})

const rooms = base.channel(['rooms', 'room:{roomId}'], {})

// Recorded broadcast: late joiners get the stored chunks first, then new ones.
export const handleAskScout = rooms.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  chunk: ReplyChunk,
  broadcast: true,
  maxChunks: 500,
  async *run(ctx, input) {
    const messages = [
      { role: 'user' as const, content: input.prompt },
    ]
    for await (const piece of llm.stream({
      messages,
      signal: ctx.stream.signal,
    })) {
      yield { text: piece }
    }
  },
})

// Resumable broadcast: subscribers get only the chunks made after they joined.
export const handleExportRoom = rooms.resumableStream('export-room', {
  input: Empty,
  chunk: ExportChunk,
  broadcast: true,
  async *run(ctx) {
    let before =
      (ctx.stream.cursor as { before: number } | null)?.before ??
      Date.now()
    while (true) {
      const messages = await loadMessages(
        ctx.channel.params.roomId,
        before,
      )
      if (messages.length === 0) return
      before = messages[messages.length - 1].sentAt
      yield ctx.stream.withCursor({ messages }, { before })
    }
  },
})
```

The `export-room` example casts `ctx.stream.cursor` because it declares no `cursor` validator, so the cursor type stays `unknown`. To remove the cast, pass a `cursor` schema or a `t<T>()` marker. See [the cursor type on Resumable](/server/streams/durable-resumable#the-cursor-type-marker-vs-validator).

::note
In a **resumable** broadcast, subscribers and late joiners see only the chunks made **after** they joined. There are no stored chunks to send again, because a resumable stream stores only source checkpoints. A **recorded** broadcast stores its chunks, so a late joiner first gets the chunks it missed. Choose the kind by what late joiners need: the earlier chunks (recorded) or only the new ones (resumable).
::

### A subscriber cancel doesn't stop the stream

On a durable broadcast, when a subscriber (not the creator) cancels, the server records that this user unsubscribed. The stream keeps running for everyone else. If the same user later tries to resume the stream, it gets `StreamAborted` with `reason: 'unsubscribed'`. The user chose to leave, so there is nothing to resume. See [abort reasons](/server/streams/config-and-lifecycle#abort-reasons).

## Steering a broadcast with a nudge

A **nudge** is a message the client sends into a running stream (see [Nudges](/server/streams/plain#nudges-steering-a-running-stream)). Only the creator can nudge a broadcast, because the generator runs on the creator's connection. A nudge from the creator changes the stream for every subscriber. For example, a `stop` nudge ends the stream for every subscriber, not only for the creator.

```ts [server/rooms.ts]
export const handleAskScoutNudged = rooms.recordedStream(
  'ask-scout',
  {
    input: v.object({ prompt: v.string() }),
    chunk: ReplyChunk,
    broadcast: true,
    maxChunks: 500,
    nudges: { stop: null },
    async *run(ctx, input) {
      const messages = [
        { role: 'user' as const, content: input.prompt },
      ]
      for await (const piece of llm.stream({
        messages,
        signal: ctx.stream.signal,
      })) {
        const recent = ctx.stream.nudges(yield { text: piece })
        if (recent.some((n) => n.event === 'stop')) return // ends for everyone
      }
    },
  },
)
```

## Channel-scoped broadcast

The place where you _declare_ a stream sets its scope. A top-level `base.stream` sends its chunks to every connection. A stream declared on a channel (created with `base.channel(...)`) sends its chunks only to that channel's members. Use this for a private room or a feed for one tenant (one customer account in a shared app).

```ts [server/rooms.ts]
const rooms = base.channel(['rooms', 'room:{roomId}'], {})

export const handleAskScout = rooms.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ text: string }>(),
  broadcast: true,
  async *run(ctx, input) {
    const messages = [
      { role: 'user' as const, content: input.prompt },
    ]
    for await (const piece of llm.stream({
      messages,
      signal: ctx.stream.signal,
    })) {
      yield { text: piece }
    }
  },
})

export const huddle = base.assemble({
  handlers: [handleAskScout],
})
```

Only connections subscribed to that channel receive the chunks. For a **durable** channel-scoped stream, a connection must be subscribed to the channel to resume the stream. See [Scoped Streams & Requests](/server/channels/scoped-streams-requests) for how channel membership controls access to a stream. The [Channels](/server/channels/overview) chapter explains channels: families like `room:{roomId}`, membership, and auth. Broadcast uses whatever scope the stream is declared in.

### Leaving the channel stops the stream

A channel-scoped stream is tied to the connection's membership in that channel. When the connection leaves the channel (it unsubscribes, is kicked, or is removed some other way), LiveThing stops every stream that connection runs in that channel. The stream's generator gets a `return()` call, so its `finally` block still runs. The owning connection, if still open, gets a terminal `stream-aborted` error with `reason: 'unsubscribed'`. For a broadcast stream, every other subscriber gets `__streamEnd__`. A resumable or recorded stream is also deleted from storage, so nobody can resume it after the leave. This always happens: a stream in a channel never keeps running for a connection that is no longer a member.

## Backpressure across many clients

**Backpressure** means slowing down the generator when clients cannot read chunks fast enough. `ctx.stream.drain()` works on a broadcast stream too. It waits for the **healthiest** receiver (the one with the least buffered data), never the slowest. So one slow client cannot stop the whole broadcast. That client falls behind and catches up later, or reaches its own buffer limits. On Cloudflare, the platform does not report how full a buffer is, so `drain()` resolves at once and does nothing, as on any other stream.
