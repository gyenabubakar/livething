A **plain stream** is an async generator that sends chunks to one client. An async generator is an `async function*` that can `yield` many values over time. A plain stream is _short-lived_: it lives only as long as the connection. When the client disconnects or cancels, LiveThing calls the generator's `return()`, your `finally` blocks run, and the stream is gone. LiveThing stores nothing. If the client wants the data again, it must start a new stream.

This page covers plain-stream behavior in detail. For a first look at how to write a stream method, start at [`base.stream`](/server/handlers/stream). To enable the builder, list `stream()` in your capabilities. See [Stream capabilities](/server/capabilities/streams).

## The generator

`base.stream(event, config)` registers a stream. The `run` function is an async generator. Each value it yields is sent to the client as one chunk, and the type of each chunk comes from what it yields.

```ts [server/search.ts]
import { server } from '@livething/server'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'
import { searchMessages } from './helpers'

const base = server({
  capabilities: [stream()],
})

export const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  async *run(_ctx, input) {
    for await (const hit of searchMessages(input.query)) {
      yield { hit }
    }
  },
})
```

- `input` validates the start payload that the client sends. Inside `run`, the second argument is the validated, typed value.
- The chunk type is the type of each value `run` yields. It is only a type: LiveThing does not check a chunk against it, because your own server code produces it. It only checks that each chunk is a plain object or `null`, like every outgoing payload. Yielding a string, a number or an array is a compile error, and a cast past it ends the stream with an unknown error. A [recorded stream](/server/streams/durable-recorded) is different: it wraps such a chunk as `{ value }`.
- Each `yield` sends one wire frame. The generator decides the pace.

::note
To fix the chunk type yourself, write the generator's return type: `async *run(_ctx, input): AsyncGenerator<{ hit: Message }> { ... }`. Then a `yield` of any other shape is a type error. See [Typing the chunk](/server/handlers/stream#typing-the-chunk).
::

## How a stream ends

A plain stream can end in several ways. The table shows what LiveThing does in each case.

| How it ends           | What LiveThing does                                                                                                                                |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Normal completion** | The generator returns (it reaches the end, or it runs `return`). LiveThing sends a stream-end frame.                                               |
| **Empty stream**      | A generator that yields nothing still completes. The client gets a stream-end frame right away, with no chunks.                                    |
| **Defined error**     | The generator throws an error that is listed in `errors([...])`. The client gets that error, and the stream ends.                                  |
| **Unknown error**     | The generator throws anything else. The client gets `internal-error`, and the stream ends. The real error goes to `onError`, or to the server log. |
| **Client disconnect** | The socket closes. LiveThing fires the [abort signal](#the-abort-signal), then calls `generator.return()`, so your `finally` blocks run.           |
| **Client cancel**     | The client cancels the stream. LiveThing handles it like a disconnect: it fires the abort signal, calls `return()`, and your `finally` blocks run. |

A defined error reaches the client with its code and detail. To make an error "defined", build it with [`error()`](/core/error-model) and list it in the `errors([...])` capability. Any other thrown value becomes `internal-error`, so the client never sees your server internals. This includes an `error()` value that you did not list in `errors([...])`.

Huddle's [`errors([NotFound, Forbidden, RoomFull])`](/server/capabilities/errors#declaring-typed-errors) already lists `Forbidden`. In this version of `search-messages`, a guest may not search. The `ctx.meta.role` value comes from Huddle's [`upgrade` hook](/server/server/upgrade#the-upgrade-ctx):

```ts [server/search.ts]
import * as v from 'valibot'
import { Forbidden } from '../shared/errors'
import { base } from './base'
import { runScoutStep, searchMessages } from './helpers'

export const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  async *run(ctx, input) {
    if (
      ctx.meta.role === 'guest'
    ) // Reaches the client as { code: 'forbidden', detail: { reason } }.
    {
      throw Forbidden({ reason: 'guests may not search messages' })
    }

    for await (const hit of searchMessages(input.query)) yield { hit }
  },
})

export const handleRunTask = base.stream('run-task', {
  input: v.object({ roomId: v.string(), goal: v.string() }),
  async *run(_ctx, input) {
    yield {
      step: 'search',
      detail: await runScoutStep('search', input.goal),
    }

    // Reaches the client as { code: 'internal-error' }. The message stays on the server.
    throw new Error('the task runner is unreachable')
  },
})
```

For the full error model (defining errors, `.matches()`, the built-in list), see [Error model](/core/error-model).

## Cleaning up on disconnect

A client disconnect calls `generator.return()`, so a `try/finally` block is the right place to release resources or run a final action. On a _cancel_, the connection is still open. The client is still connected and only stopped this one stream. So a `ctx.send(...)` inside `finally` reaches the client. On a full disconnect, there is no connection to send to.

```ts [server/search.ts]
import { emits, server, t } from '@livething/server'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'
import { searchMessages } from './helpers'

const base = server({
  capabilities: [
    stream(),
    emits({ 'search-stopped': t<{ hitsSent: number }>() }),
  ],
})

export const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  async *run(ctx, input) {
    let hitsSent = 0
    let completed = false
    try {
      for await (const hit of searchMessages(input.query)) {
        yield { hit }

        hitsSent += 1
      }

      completed = true
    } finally {
      // Runs on normal completion, on cancel and on disconnect.
      if (!completed) ctx.send('search-stopped', { hitsSent })
    }
  },
})
```

## The abort signal

`ctx.stream.signal` is an `AbortSignal`. It fires when the client cancels the stream, when the client disconnects, or when the server shuts down. Pass it into slow awaited work. Then that work stops as soon as the stream stops, and does not keep running in the background.

Here the search takes the signal as a second argument. Huddle's own `search-messages` calls `searchMessages(input.query)` without it.

```ts [server/search.ts]
import * as v from 'valibot'
import { base } from './base'
import { searchMessages } from './helpers'

export const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  async *run(ctx, input) {
    const { signal } = ctx.stream

    // Pass the signal into the search. If the client cancels, the search
    // stops at once and does not keep the stream open.
    for await (const hit of searchMessages(input.query, signal)) {
      yield { hit }
    }
  },
})
```

`signal.aborted` is `true` after the signal fires, and `signal.reason` tells you why:

| Reason           | Meaning                                   |
| ---------------- | ----------------------------------------- |
| `'cancelled'`    | The client cancelled the stream.          |
| `'aborted'`      | The connection closed.                    |
| `'unsubscribed'` | The connection left the stream's channel. |
| `'shutdown'`     | The server is shutting down.              |

You can connect a timer, or any other awaited promise, to the signal. Then the generator continues as soon as the stream is cancelled, and does not wait for a long timeout to finish.

```ts [server/scout.ts]
import * as v from 'valibot'
import { base } from './base'
import { runScoutStep } from './huddle-data'

export const handleRunTask = base.stream('run-task', {
  input: v.object({ roomId: v.string(), goal: v.string() }),
  async *run(ctx, input) {
    const { signal } = ctx.stream
    yield {
      step: 'search',
      detail: await runScoutStep('search', input.goal),
    }

    // Cool down before the next step, but don't make a cancelled stream wait for it.
    await new Promise<void>((resolve, reject) => {
      const timer = setTimeout(resolve, 60_000)
      signal.addEventListener(
        'abort',
        () => {
          clearTimeout(timer)
          reject(new Error('aborted'))
        },
        { once: true },
      )
    }).catch(() => {
      // Ignore the rejection. The stream is already stopping.
    })
  },
})
```

## Backpressure with drain()

**Backpressure** is what happens when a sender produces data faster than the receiver can read it. If your generator produces chunks faster than the client reads them, the outgoing buffer grows. `ctx.stream.drain()` pauses the generator until the amount of buffered data is below 256 KB again, then resolves. Call it between yields when a fast producer sends to a slow client.

```ts [server/search.ts]
import * as v from 'valibot'
import { base } from './base'
import { searchMessages } from './helpers'

export const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  async *run(ctx, input) {
    for await (const hit of searchMessages(input.query)) {
      yield { hit }

      await ctx.stream.drain()
    }
  },
})
```

- The buffer limit is a fixed **256 KB** per connection. `drain()` resolves when the buffer is below it.
- When the client reads fast enough, the buffer stays below the limit and `drain()` resolves at once. The stream runs at full speed.
- `drain()` checks the buffer every 25 ms. It resolves after about 50 seconds even if the buffer is still full, so it never blocks the generator forever. It also resolves at once when the stream has stopped.
- A **broadcast** stream sends its chunks to many connections. For a broadcast stream, `drain()` waits only for the receiver with the _least_ buffered data, not for the slowest one. So one slow client cannot hold back the stream for everyone. If a slow client's buffer stays over twice the adapter's send limit (2 × 32 MiB = 64 MiB by default) for more than 10 seconds, LiveThing closes that connection with `1013` (`TRY_AGAIN_LATER`) and keeps sending to the others. If the client is too slow to read even the close frame, it sees the connection drop (`1006`) instead. The client reconnects, as after any close.

::caution
On Cloudflare, the platform does not report how full the outgoing buffer is. So there, `drain()` does nothing and resolves at once. Your generator must still work correctly and deliver every chunk without it. Think of `drain()` as "slow down here if the adapter can measure the buffer", not as "this always waits".
::

## One stream per event, by default

By default, a connection can run only one stream of a given event at a time. If a `search-messages` stream is already running and the client starts another `search-messages`, LiveThing rejects the second start with `stream-already-active`. The ID of the stream that is already running is in `detail.streamId`. Set `allowConcurrent: true` when you need several runs of the same event at the same time, for example several searches in parallel.

```ts [server/search.ts]
import * as v from 'valibot'
import { base } from './base'
import { searchMessages } from './helpers'

export const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  allowConcurrent: true, // the same client may run several 'search-messages' streams at once
  async *run(_ctx, input) {
    for await (const hit of searchMessages(input.query)) yield { hit }
  },
})
```

`stream-already-active` is a built-in error. See the [built-in errors list](/core/builtin-errors).

## Nudges: steering a running stream

A **nudge** is a typed message that the client sends _into_ a stream that is already running. Declare nudges in a `nudges` map: the key is the event name, and the value is a schema, or `null` for a nudge with no payload. After each `yield`, read the nudges that arrived with `ctx.stream.nudges(yield ...)`.

A model cannot be paused or sped up mid-reply: it only ever produces the next piece of text. So Huddle's `ask-scout` declares two nudges that fit what a model call actually supports: `stop` ends the model call for good, and `redirect` abandons the current reply and starts a new model call with the reply so far plus a new instruction. Reading nudges works the same on every stream kind, so the generator below reads the same way whether the surrounding builder is `base.stream` or, as `ask-scout` really is, a channel-scoped `recordedStream` (see [Recorded](/server/streams/durable-recorded)). This is a variant of Huddle's `ask-scout`. It also ties the model call to `ctx.stream.signal`.

```ts [server/rooms.ts]
import * as v from 'valibot'
import { rooms } from './base'
import { llm } from './llm'

export const handleAskScout = rooms.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  nudges: {
    stop: null,
    redirect: v.object({ instruction: v.string() }),
  },
  broadcast: true, // every member of the room sees the reply
  async *run(ctx, input) {
    let messages: { role: 'user' | 'assistant'; text: string }[] = [
      { role: 'user', text: input.prompt },
    ]

    while (true) {
      const controller = new AbortController()
      const onAbort = () => controller.abort()
      ctx.stream.signal.addEventListener('abort', onAbort, {
        once: true,
      })

      let replySoFar = ''
      let redirectTo: string | null = null

      try {
        for await (const piece of llm.stream({
          messages,
          signal: controller.signal,
        })) {
          replySoFar += piece
          const recent = ctx.stream.nudges(yield { text: piece })
          if (recent.some((n) => n.event === 'stop')) {
            controller.abort() // stop: end the model call and the stream
            return
          }

          const redirect = recent.find((n) => n.event === 'redirect')
          if (redirect) {
            redirectTo = redirect.payload.instruction
            controller.abort() // redirect: abort this model call, start a new one below
            break
          }
        }
      } finally {
        ctx.stream.signal.removeEventListener('abort', onAbort)
      }

      if (!redirectTo) return // the model finished its reply on its own

      // Start a new model call with the reply so far plus the new instruction.
      messages = [
        ...messages,
        { role: 'assistant', text: replySoFar },
        { role: 'user', text: redirectTo },
      ]
    }
  },
})
```

`ctx.stream.nudges(...)` returns the typed nudges that arrived since the last yield. Each one has the shape `{ event, payload }`. The `nudges()` reader exists on `ctx.stream` only when the stream declares at least one nudge. For nudges, their buffer limit and what happens when the buffer is full, see [Configuration & Lifecycle](/server/streams/config-and-lifecycle#nudges).

## Starting again from a position

A plain stream stores nothing, but many sources can start again from a position: database pages, a file offset, a row ID. For those, put the position in the stream's input. When the socket drops, the client's `for await` loop throws a `disconnected` error. The client catches it and starts a new stream from the last item it got.

Huddle's `export-room` sends a room's history page by page, newest first. Its input takes `before`, the time of the oldest message the client already has:

```ts [server/rooms.ts]
import * as v from 'valibot'
import { base } from './base'
import { loadMessages } from './huddle-data'

export const handleExportRoom = base.stream('export-room', {
  input: v.object({
    roomId: v.string(),
    before: v.optional(v.number()),
  }),
  async *run(ctx, input) {
    let before = input.before
    while (true) {
      const messages = await loadMessages(input.roomId, before)
      if (messages.length === 0) return

      before = messages[messages.length - 1].sentAt
      yield { messages }
    }
  },
})
```

On the client, keep the last position and start again after a drop:

```ts [client/export.ts]
import { Disconnected } from '@livething/client/errors'
import { saveMessages } from './huddle-data'
import { socket } from './socket'

let before: number | undefined
let done = false
while (!done) {
  try {
    const pages = await socket.stream('export-room', {
      roomId: 'general',
      before,
    })
    for await (const page of pages) {
      saveMessages(page.messages)
      before = page.messages[page.messages.length - 1].sentAt
    }

    done = true
  } catch (err) {
    if (!Disconnected.matches(err)) throw err

    // Wait for the reconnect, then ask again from `before`.
    await new Promise<void>((resolve) => {
      const stop = socket.onOpen(() => {
        stop()
        resolve()
      })
    })
  }
}
```

When every chunk must arrive and the source cannot start again, use a [recorded stream](/server/streams/durable-recorded) instead.

## Sending bytes

To send a file or other bytes, use [`base.binary.stream`](/server/binary/streams). It is a plain stream whose generator yields `{ info, bytes }`, and each chunk goes out as one binary message. Everything on this page works the same for it: the stream ends with a text `__streamEnd__`, `ctx.stream.signal` fires on a cancel, and you call `ctx.stream.drain()` after each piece. A position in the input, as above, is how a client starts a binary stream again after a drop. For bytes that cannot be made again, use a [recorded binary stream](/server/binary/streams#recorded-binary-streams) instead.
