A **plain stream** is an async generator that sends chunks to one client. An async generator is an `async function*` that can `yield` many values over time. A plain stream is _short-lived_: it lives only as long as the connection. When the client disconnects or cancels, LiveThing calls the generator's `return()`, your `finally` blocks run, and the stream is gone. LiveThing stores nothing. If the client wants the data again, it must start a new stream.

This page covers plain-stream behavior in detail. For a first look at how to write a stream method, start at [`base.stream`](/server/handlers/stream). To enable the builder, list `stream()` in your capabilities. See [Stream capabilities](/server/capabilities/streams).

## The generator

`base.stream(event, config)` registers a stream. The `run` function is an async generator. Each value it yields is sent to the client as one chunk, and the `chunk` marker gives each chunk its type.

```ts [plain-stream.ts]
import { server, t } from '@livething/server'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'

const Token = t<{ index: number }>()

const base = server({
  capabilities: [stream()],
})

export const handleStartTokens = base.stream('start-tokens', {
  input: v.object({ count: v.number() }),
  chunk: Token,
  async *run(_ctx, input) {
    for (let i = 0; i < input.count; i += 1) {
      yield { index: i }
      await new Promise((r) => setTimeout(r, 200))
    }
  },
})
```

- `input` validates the start payload that the client sends. Inside `run`, the second argument is the validated, typed value.
- `chunk` is a [type marker](/server/capabilities/emits), written `t<Shape>()`. A type marker only gives TypeScript a type. It does nothing at runtime. LiveThing never validates chunks, because your own server code produces them. If you leave `chunk` out, LiveThing infers the chunk type from what `run` yields.
- Each `yield` sends one wire frame. The generator decides the pace.

::note
The `chunk` marker is optional. `base.stream('feed', { input, async *run() { yield { index: 0 } } })` infers the chunk type from the yielded value. Pass `chunk` when you want a named type that you reuse, or when you want to write the shape explicitly.
::

## How a stream ends

A plain stream can end in several ways. The table shows what LiveThing does in each case.

| How it ends           | What LiveThing does                                                                                                                                |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Normal completion** | The generator returns (it reaches the end, or it runs `return`). LiveThing sends a stream-end frame.                                               |
| **Empty stream**      | A generator that yields nothing still completes. The client gets a stream-end frame right away, with no chunks.                                    |
| **Defined error**     | The generator throws an error that is listed in `errors([...])`. The client gets that error, and the stream ends.                                  |
| **Unknown error**     | The generator throws anything else. The client gets `internal-error`, and the stream ends. The real error message stays on the server.             |
| **Client disconnect** | The socket closes. LiveThing fires the [abort signal](#the-abort-signal), then calls `generator.return()`, so your `finally` blocks run.           |
| **Client cancel**     | The client cancels the stream. LiveThing handles it like a disconnect: it fires the abort signal, calls `return()`, and your `finally` blocks run. |

A defined error reaches the client with its code and detail. To make an error "defined", build it with [`error()`](/core/error-model) and list it in the `errors([...])` capability. Any other thrown value becomes `internal-error`, so the client never sees your server internals. This includes an `error()` value that you did not list in `errors([...])`.

```ts [stream-errors.ts]
import { error, errors, server, t } from '@livething/server'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'

const ModelMissing = error(
  'model-missing',
  v.object({ modelId: v.string() }),
)

const base = server({
  capabilities: [stream(), errors([ModelMissing])],
})

export const handleAsk = base.stream('ask', {
  input: v.object({ modelId: v.string() }),
  chunk: t<{ text: string }>(),
  async *run(_ctx, input) {
    yield { text: 'Loading model...' }
    // Reaches the client as { code: 'model-missing', detail: { modelId } }.
    throw ModelMissing({ modelId: input.modelId })
  },
})

export const handleSummarize = base.stream('summarize', {
  input: v.object({}),
  chunk: t<{ text: string }>(),
  async *run() {
    yield { text: 'Reading the document...' }
    // Reaches the client as { code: 'internal-error' }. The message stays on the server.
    throw new Error('summary service is down')
  },
})
```

For the full error model (defining errors, `.matches()`, the built-in list), see [Error model](/core/error-model).

## Cleaning up on disconnect

A client disconnect calls `generator.return()`, so a `try/finally` block is the right place to release resources or run a final action. On a _cancel_, the connection is still open. The client is still connected and only stopped this one stream. So a `ctx.send(...)` inside `finally` reaches the client. On a full disconnect, there is no connection to send to.

```ts [cleanup.ts]
import { emits, server, t } from '@livething/server'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'

const base = server({
  capabilities: [
    stream(),
    emits({ 'render-stopped': t<{ framesSent: number }>() }),
  ],
})

export const handleRenderPreview = base.stream('render-preview', {
  input: v.object({}),
  chunk: t<{ frame: number }>(),
  async *run(ctx) {
    let framesSent = 0
    let completed = false
    try {
      for (let i = 0; i < 20; i += 1) {
        yield { frame: i }
        framesSent += 1
        await new Promise((r) => setTimeout(r, 50))
      }
      completed = true
    } finally {
      // Runs on normal completion, on cancel and on disconnect.
      if (!completed) ctx.send('render-stopped', { framesSent })
    }
  },
})
```

## The abort signal

`ctx.stream.signal` is an `AbortSignal` (the standard web object for stopping async work). It fires when the client cancels the stream, when the client disconnects, or when the server shuts down. Pass it into slow awaited work. Then that work stops as soon as the stream stops, and does not keep running in the background.

```ts [signal.ts]
export const handleWeatherReport = base.stream('weather-report', {
  input: v.object({}),
  chunk: Token,
  async *run(ctx) {
    const { signal } = ctx.stream

    yield { index: 0 }

    // Pass the signal into the awaited work. If the client cancels, the
    // fetch stops at once and does not keep the stream open.
    const res = await fetch('https://example.com/slow', {
      signal,
    })
    const data = (await res.json()) as { index: number }
    yield data
  },
})
```

`signal.aborted` is `true` after the signal fires, and `signal.reason` tells you why:

| Reason        | Meaning                          |
| ------------- | -------------------------------- |
| `'cancelled'` | The client cancelled the stream. |
| `'aborted'`   | The connection closed.           |
| `'shutdown'`  | The server is shutting down.     |

You can connect a timer, or any other awaited promise, to the signal. Then the generator continues as soon as the stream is cancelled, and does not wait for a long timeout to finish.

```ts [signal-timer.ts]
export const handleCountdown = base.stream('countdown', {
  input: v.object({}),
  chunk: Token,
  async *run(ctx) {
    const { signal } = ctx.stream
    yield { index: 0 }

    await new Promise<void>((resolve, reject) => {
      const timer = setTimeout(resolve, 60_000)
      signal.addEventListener(
        'abort',
        () => {
          clearTimeout(timer)
          reject(new Error('aborted'))
        },
        { once: true },
      )
    }).catch(() => {
      // Ignore the rejection. The stream is already stopping.
    })
  },
})
```

## Backpressure with drain()

**Backpressure** is what happens when a sender produces data faster than the receiver can read it. If your generator produces chunks faster than the client reads them, the outgoing buffer grows. `ctx.stream.drain()` pauses the generator until the amount of buffered data is below the stream's `highWaterMark` again, then resolves. Call it between yields when a fast producer sends to a slow client.

```ts [drain.ts]
export const handleExportRows = base.stream('export-rows', {
  input: v.object({ count: v.number() }),
  chunk: Token,
  highWaterMark: 64 * 1024, // replaces the 256 KB default
  async *run(ctx, input) {
    for (let i = 0; i < input.count; i += 1) {
      yield { index: i }
      await ctx.stream.drain()
    }
  },
})
```

- `highWaterMark` is the buffer limit in bytes. The default is **256 KB**. `drain()` resolves when the buffer is below this limit.
- When the client reads fast enough, the buffer stays below the limit and `drain()` resolves at once. The stream runs at full speed.
- `drain()` checks the buffer every 25 ms. It resolves after about 50 seconds even if the buffer is still full, so it never blocks the generator forever. It also resolves at once when the stream has stopped.
- A **broadcast** stream sends its chunks to many connections. For a broadcast stream, `drain()` waits only for the receiver with the _least_ buffered data, not for the slowest one. So one slow client cannot hold back the stream for everyone.

::caution
On Cloudflare, the platform does not report how full the outgoing buffer is. So there, `drain()` does nothing and resolves at once. Your generator must still work correctly and deliver every chunk without it. Think of `drain()` as "slow down here if the adapter can measure the buffer", not as "this always waits".
::

## One stream per event, by default

By default, a connection can run only one stream of a given event at a time. If a `start-tokens` stream is already running and the client starts another `start-tokens`, LiveThing rejects the second start with `stream-already-active`. The ID of the stream that is already running is in `detail.streamId`. Set `allowConcurrent: true` when you need several runs of the same event at the same time, for example several searches in parallel.

```ts [concurrent.ts]
export const handleSearch = base.stream('search', {
  input: v.object({ query: v.string() }),
  chunk: Token,
  allowConcurrent: true, // the same client may run several 'search' streams at once
  async *run(_ctx, input) {
    // ...
  },
})
```

`stream-already-active` is a built-in error. See the [built-in errors list](/core/builtin-errors).

## Nudges: steering a running stream

A **nudge** is a typed message that the client sends _into_ a stream that is already running. Declare nudges in a `nudges` map: the key is the event name, and the value is a schema, or `null` for a nudge with no payload. After each `yield`, read the nudges that arrived with `ctx.stream.nudges(yield ...)`.

```ts [nudges.ts]
export const handleGenerateText = base.stream('generate-text', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ token: string }>(),
  nudges: {
    pause: null,
    'speed-up': v.object({ factor: v.number() }),
  },
  async *run(ctx, input) {
    let delay = 50
    for (const word of input.prompt.split(' ')) {
      const recent = ctx.stream.nudges(yield { token: word + ' ' })
      if (recent.some((n) => n.event === 'pause')) return
      const speed = recent.find((n) => n.event === 'speed-up')
      if (speed) delay = Math.max(1, delay / speed.payload.factor)
      await new Promise((r) => setTimeout(r, delay))
    }
  },
})
```

`ctx.stream.nudges(...)` returns the typed nudges that arrived since the last yield. Each one has the shape `{ event, payload }`. The `nudges()` reader exists on `ctx.stream` only when the stream declares at least one nudge. For nudges, their buffer limit and what happens when the buffer is full, see [Configuration & Lifecycle](/server/streams/config-and-lifecycle#nudges).
