A **stream** sends data to the client in small pieces, one after another, instead of all at once. Each piece is a **chunk**. Examples: the tokens an AI model writes, the rows of a database query, or a live feed.

On the server you write an **async generator**: an `async function*` that gives out values one at a time with `yield`. Each `yield` sends one chunk. LiveThing does the rest:

- **Routing:** each chunk goes to the right client.
- **Backpressure:** the generator can wait when the client cannot receive data fast enough.
- **Cancellation:** the generator stops when the client cancels the stream.
- **Resume:** for durable streams, the client gets the rest of the stream after its connection drops and comes back.

This chapter covers streams in full detail: the three stream kinds, durability, broadcast, and every config option. Two other pages cover smaller parts:

- [Stream capabilities](/server/capabilities/streams) shows how to turn streams on with `stream()`, `resumableStream()` and `recordedStream()` in `server(...)`.
- [`base.stream`](/server/handlers/stream) is a short introduction to writing a stream handler.

## The three kinds

Every stream is an async generator. The three kinds differ in what happens when the client disconnects and then reconnects. A **durable** stream is one that continues after a reconnect. A **cursor** is a small value that marks a position in your data source (for example, a row number). A **checkpoint** is a saved cursor.

| Kind                    | Builder                | Continues after a disconnect? | What is stored     | Use it when                                                                                                                                                                             |
| ----------------------- | ---------------------- | ----------------------------- | ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Plain (ephemeral)**   | `base.stream`          | No                            | Nothing            | The work is cheap to lose and start again: a live feed, a one-time render, anything the client can simply ask for again.                                                                |
| **Resumable (durable)** | `base.resumableStream` | Yes                           | Cursor checkpoints | The source can run again from a position: database pagination, a file offset, a row ID. On resume, the generator runs again from the checkpoint of the last chunk the client confirmed. |
| **Recorded (durable)**  | `base.recordedStream`  | Yes                           | Every chunk        | The source runs only once and cannot be run again: AI model tokens, a push API. On resume, the client gets the chunks it missed from a saved buffer. The generator does not run again.  |

Both durable kinds keep their state in the server's own SQL storage. Every LiveThing adapter provides this storage, so you do not add a separate capability for it. Each kind needs only its own capability: `stream()` for a plain stream, `resumableStream()` for a resumable stream, and `recordedStream()` for a recorded stream.

::note
Each stream message carries a `stream.durability` field in its metadata (the extra LiveThing data that travels with each message on the WebSocket). Plain streams send `ephemeral`. Both durable kinds send `persistent`.
::

## The same generator shape, three builders

All three builders take an event name and a config object with an async generator called `run`. Each value the generator yields is sent to the client as one chunk.

```ts [stream-kinds.ts]
import { server, t } from '@livething/server'
import {
  recordedStream,
  resumableStream,
  stream,
} from '@livething/server/streams'
import * as v from 'valibot'

const Token = t<{ index: number }>()

const base = server({
  capabilities: [stream(), resumableStream(), recordedStream()],
})

// Plain: stops when the client disconnects.
const handleFeed = base.stream('feed', {
  input: v.object({ count: v.number() }),
  chunk: Token,
  async *run(_ctx, input) {
    for (let i = 0; i < input.count; i += 1) yield { index: i }
  },
})

// Resumable: runs again from the last confirmed checkpoint after a reconnect.
const handlePaginate = base.resumableStream('paginate', {
  input: v.object({}),
  chunk: Token,
  cursor: t<{ idx: number }>(),
  async *run(ctx) {
    const start = ctx.stream.cursor?.idx ?? 0
    for (let i = start + 1; i <= 100; i += 1) {
      yield ctx.stream.withCursor({ index: i }, { idx: i })
    }
  },
})

// Recorded: saves chunks and sends the missed ones after a reconnect.
const handleTokens = base.recordedStream('tokens', {
  input: v.object({}),
  chunk: Token,
  async *run() {
    for (let i = 0; i < 100; i += 1) yield { index: i }
  },
})

export const definition = base.assemble({
  handlers: [handleFeed, handlePaginate, handleTokens],
})
```

## The contract slice a stream adds

The **contract** is the set of events and types that the client and server share. `InferClient` builds the client's view of the contract from your server definition. Plain, resumable and recorded streams all appear in the same place: one flat `streams` map, keyed by event name.

Each entry has these fields:

- `payload`: the data the client sends to start the stream.
- `chunk`: the type of each value the generator yields.
- `kind`: `'ephemeral'` for a plain stream, or `'persistent'` for the two durable kinds.

Fields with no useful information are left out. If a stream declares no nudges (messages the client sends to a running stream), the entry has no `nudges` field. The entry never has a `cursor` field, because only the server uses the cursor.

```ts [client-streams-view.ts]
// From a plain `feed`, a resumable `paginate`, and a recorded `tokens`.
// A cursor is server-only, so it never appears here.
type ClientStreams = {
  feed: {
    payload: { count: number }
    chunk: { index: number }
    kind: 'ephemeral'
  }
  paginate: {
    payload: {}
    chunk: { index: number }
    kind: 'persistent'
  }
  tokens: {
    payload: {}
    chunk: { index: number }
    kind: 'persistent'
  }
}
```

The client uses this map to type its `stream(...)`, `onStream(...)` and `resumeStream(...)` calls. Because of `kind`, `resumeStream(...)` accepts only durable streams. You never write this type yourself. LiveThing builds it from your handlers. See [`server`](/server/server/overview) for how the contract is built.

## Broadcasting is an option, not a fourth kind

Any of the three kinds can send its chunks to many connections instead of one. Set `broadcast: true`. The generator then runs once, and each chunk goes to every connection in scope. The scope depends on where you declare the stream:

- A top-level stream sends to every connection.
- A stream inside a `channel(...)` sends to that channel's members.

```ts [broadcast.ts]
const handleLiveFeed = base.stream('live-feed', {
  input: v.object({ count: v.number() }),
  chunk: Token,
  broadcast: true,
  async *run(_ctx, input) {
    for (let i = 0; i < input.count; i += 1) yield { index: i }
  },
})
```

Broadcast works for the durable kinds too. A **late joiner** is a connection that joins a broadcast stream after the stream has started. The two durable kinds treat late joiners differently:

- A **recorded** broadcast first sends its saved chunks to a late joiner, so it gets what it missed. After that, the late joiner gets new chunks as they are produced.
- A **resumable** broadcast stores only cursors, not chunks. A late joiner gets only the chunks produced after it joins the stream.

See [Broadcast](/server/streams/broadcast) for the full details.
