A **stream** sends data to the client in small pieces, one after another, instead of all at once. Each piece is a **chunk**. Examples: the tokens an AI model writes, the rows of a database query, a live feed, or the [pieces of a file](#chunks-of-bytes).

On the server you write an **async generator**: an `async function*` that gives out values one at a time with `yield`. Each `yield` sends one chunk. LiveThing does the rest:

- **Routing:** each chunk goes to the right client.
- **Backpressure:** the generator can wait when the client cannot receive data fast enough.
- **Cancellation:** the generator stops when the client cancels the stream.
- **Continue:** for recorded streams, the client gets the rest of the stream after its connection drops and comes back.

This chapter covers streams in full detail: the two stream kinds, durability, broadcast, and every config option. Two other pages cover smaller parts:

- [Stream capabilities](/server/capabilities/streams) shows how to turn streams on with `stream()` and `recordedStream()` in `server(...)`.
- [`base.stream`](/server/handlers/stream) is a short introduction to writing a stream handler.

## The two kinds

Every stream is an async generator. The two kinds differ in what happens when the client disconnects and then reconnects. A **durable** stream is one that continues after a reconnect.

| Kind                   | Builder               | Survives a disconnect? | What is stored | Use it when                                                                                                                                                                                                                      |
| ---------------------- | --------------------- | ---------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Plain (ephemeral)**  | `base.stream`         | No                     | Nothing        | The work is cheap to lose and start again: a live feed, a search, a page-by-page export the client can ask for again from where it stopped.                                                                                      |
| **Recorded (durable)** | `base.recordedStream` | Yes                    | Every chunk    | The source runs only once and cannot be run again: AI model tokens, a push API. The generator keeps running when the client drops. On reconnect, the client gets the chunks it missed from a saved buffer, then the live chunks. |

A recorded stream keeps its chunks in the server's own SQL storage. Every LiveThing adapter provides this storage, so you do not add a separate capability for it. Each kind needs only its own capability: `stream()` for a plain stream and `recordedStream()` for a recorded stream.

When the source _can_ start again from a position (database pages, a file offset, a row ID), use a plain stream and put the position in its input, for example `before` or `after`. When the socket drops, the client's `for await` loop throws a `disconnected` error. The app catches it and starts a new stream from the last item it got. See [Plain streams](/server/streams/plain#starting-again-from-a-position).

::note
Each stream message carries a `stream.durability` field in its metadata. Plain streams send `ephemeral`. Recorded streams send `persistent`.
::

## The same generator shape, two builders

Both builders take an event name and a config object with an async generator called `run`. Each value the generator yields is sent to the client as one chunk.

This example uses a smaller server with no channels, so `ask-scout` sits on `base`. In Huddle, `ask-scout` is on `rooms` and has `broadcast: true` and two nudges.

```ts [server/scout.ts]
import { server } from '@livething/server'
import { recordedStream, stream } from '@livething/server/streams'
import * as v from 'valibot'
import { searchMessages } from './helpers'
import { llm } from './llm'

const base = server({
  capabilities: [stream(), recordedStream()],
})

// Plain: stops when the client disconnects.
const handleSearchMessages = base.stream('search-messages', {
  input: v.object({ query: v.string() }),
  async *run(_ctx, input) {
    for await (const hit of searchMessages(input.query)) yield { hit }
  },
})

// Recorded: keeps running when the client drops, and saves every chunk so a
// reconnecting client gets the ones it missed.
const handleAskScout = base.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  async *run(ctx, input) {
    const messages = [{ role: 'user', text: input.prompt }]
    for await (const piece of llm.stream({
      messages,
      signal: ctx.stream.signal,
    })) {
      yield { text: piece }
    }
  },
})

export const huddle = base.assemble({
  handlers: [handleSearchMessages, handleAskScout],
})
```

## The contract slice a stream adds

The **contract** is the set of events and types that the client and server share. `InferClient` builds the client's view of the contract from your server definition. Plain and recorded streams both appear in the same place: one flat `streams` map, keyed by event name.

Each entry has these fields:

- `payload`: the data the client sends to start the stream.
- `chunk`: the type of each value `run` yields.
- `kind`: `'ephemeral'` for a plain stream, or `'persistent'` for a recorded stream.

Fields with no useful information are left out. If a stream declares no nudges, the entry has no `nudges` field.

```ts [shape]
import type { Message } from '../server/base'

// From a plain `search-messages` and a recorded `ask-scout`.
type ClientStreams = {
  'search-messages': {
    payload: { query: string }
    chunk: { hit: Message }
    kind: 'ephemeral'
  }
  'ask-scout': {
    payload: { prompt: string }
    chunk: { text: string }
    kind: 'persistent'
  }
}
```

The client uses this map to type its `stream(...)`, `onStream(...)` and `continueStream(...)` calls. Because of `kind`, `continueStream(...)` accepts only recorded streams. You never write this type yourself. LiveThing builds it from your handlers. See [`server`](/server/server/overview) for how the contract is built.

## Chunks of bytes

The chunks of `base.stream` and `base.recordedStream` are JSON. To send bytes, use [`base.binary.stream`](/server/binary/streams) or [`base.binary.recordedStream`](/server/binary/streams#recorded-binary-streams). Their generator yields `{ info, bytes }`, and each chunk goes out as one [binary message](/server/binary/overview), with the same stream metadata as a JSON chunk.

The rest of a binary stream is text and works as described on these pages: `__streamOk__`, `__streamEnd__`, an `__error__` that ends the stream, the client's `__streamCancel__`, and every nudge. `ctx.stream.signal`, `ctx.stream.drain()` and `broadcast: true` work the same way.

The frame kinds must match. A binary message that starts a JSON stream, a text message that starts a binary stream, and a binary nudge each get an `__error__` frame with the code `wrong-frame-kind`.

A recorded binary stream stores each chunk with its bytes. When a client continues it, the server sends the stored chunks again as binary frames, with the same `seq`. For a file you can read again from any position, a plain binary stream with the position in its `input` stores nothing, as Huddle's [`download-attachment`](/server/binary/streams#binary-streams) does with `fromByte`. Use a recorded one, such as Huddle's [`export-room-pdf`](/server/binary/streams#recorded-binary-streams), when the bytes are made once and cannot be made again.

## Broadcasting is an option, not a third kind

Both kinds can send their chunks to many connections instead of one. Set `broadcast: true`. The generator then runs once, and each chunk goes to every connection in scope. The scope depends on where you declare the stream:

- A top-level stream sends to every connection.
- A stream inside a `channel(...)` sends to that channel's members.

In Huddle, `ask-scout` is declared on the `rooms` channel, so every member of the room gets the reply:

```ts [server/scout.ts]
import * as v from 'valibot'
import { rooms } from './base'
import { llm } from './llm'

const handleAskScout = rooms.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  broadcast: true,
  async *run(ctx, input) {
    const messages = [{ role: 'user', text: input.prompt }]
    for await (const piece of llm.stream({
      messages,
      signal: ctx.stream.signal,
    })) {
      yield { text: piece }
    }
  },
})
```

A **late joiner** is a connection that joins a broadcast stream after the stream has started. A recorded broadcast sends its saved chunks to a late joiner only after the late joiner calls `continueStream` with the stream ID. Until then, the late joiner gets nothing. After that, it gets the saved chunks it missed, and then new chunks as they are produced.

See [Broadcast](/server/streams/broadcast) for the full details.
