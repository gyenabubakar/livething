This page is the reference for stream options and runtime behavior for all three stream kinds (plain, resumable and recorded). The earlier pages show each kind in use. This page lists every option and its default. It also covers the lifecycle details: how nudges are buffered, how long stored streams are kept, what happens when a client disconnects, and the reasons a stream can be stopped.

## Nudges

A **nudge** is a typed message that the client sends _into_ a stream that is already running. Declare nudges as a map from event name to schema. Use `null` for a nudge with no payload. Inside the generator, `ctx.stream.nudges(yield ...)` returns the nudges that arrived since the last `yield`. Each one has the shape `{ event, payload }`.

```ts [server/admin.ts]
import { error, errors, server, t } from '@livething/server'
import { stream } from '@livething/server/streams'
import * as v from 'valibot'

const Forbidden = error('forbidden', v.object({ reason: v.string() }))

const base = server({ capabilities: [stream(), errors([Forbidden])] })

const levels = ['info', 'warn', 'error'] as const

export const handleTailAuditLog = base.stream('tail-audit-log', {
  input: v.object({}),
  chunk: t<{ line: string }>(),
  nudges: {
    stop: null, // no payload
    'set-level': v.object({ level: v.picklist(levels) }), // typed payload
  },
  async *run(ctx) {
    if (ctx.meta.role !== 'admin')
      throw Forbidden({
        reason: 'only an admin may tail the audit log',
      })

    let minLevel = 0 // index into `levels`: 0 shows every line
    for await (const entry of auditLogEntries(ctx.stream.signal)) {
      if (levels.indexOf(entry.level) < minLevel) continue
      const recent = ctx.stream.nudges(yield { line: entry.line })
      for (const n of recent) {
        if (n.event === 'stop') return
        if (n.event === 'set-level')
          minLevel = levels.indexOf(n.payload.level)
      }
    }
  },
})
```

`ctx.stream.nudges()` exists only when the stream declares at least one nudge. TypeScript narrows each message by its `event`, so `n.payload` has the right type for that event.

### Nudge buffering and overflow

Nudges that arrive between two `yield`s wait in a buffer (an in-memory queue). Your generator gets them at the next `yield`. The buffer has a limit. If the client sends nudges faster than the generator reads them and the buffer is full, LiveThing rejects the extra nudge with `NudgeOverflow`. This error is **non-terminal**: only that one nudge fails, and the stream keeps running.

```ts [nudge-overflow.ts]
// Client code. `auditLog` is the handle from socket.stream('tail-audit-log', {}).
// A rejected nudge throws NudgeOverflow. The stream keeps running.
import { NudgeOverflow } from '@livething/core'

try {
  await auditLog.nudge('set-level', { level: 'error' })
} catch (err) {
  if (NudgeOverflow.matches(err)) {
    // Sending too fast. Wait a little, then try again.
    // err.detail.cap is the buffer limit.
  }
}
```

`NudgeOverflow` carries `detail.cap`, the buffer limit, so the client knows how many nudges can wait at once. The limit is **256** waiting nudges. It is the same for plain, resumable and recorded streams, and no option changes it.

Whether waiting nudges survive a disconnect depends on `onDisconnect` (see [Disconnect behavior](#disconnect-behavior-durable-only)):

- With `'keep-running'` on a recorded stream, the generator does not stop, so its nudge buffer stays. A resumable stream starts a new run of the generator on every resume, so its unread nudges are lost with either value (see [Resumable](/server/streams/durable-resumable#nudges-and-resume)).
- With the default `'cancel-but-buffer'`, LiveThing cancels the generator when the client drops, and the nudge buffer is lost. Only the resume state is kept: a recorded stream's stored chunks, or a resumable stream's cursor checkpoints.

`NudgeOverflow` is a built-in error. See the [built-in errors catalog](/core/builtin-errors).

## Retention windows (durable only)

Durable streams (resumable and recorded) are kept in storage, so a client that comes back can resume them. Two options control how long LiveThing keeps them.

| Option                | Default    | What it controls                                                                                                                                                                          |
| --------------------- | ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `maxAgeMs`            | 5 minutes  | How long a **suspended** stream (the client dropped and the generator stopped) is kept before LiveThing deletes it. A resume after this time gets `StreamAborted({ reason: 'expired' })`. |
| `retentionAfterEndMs` | 30 seconds | How long an **ended** stream is kept after it finishes, so a client that reconnects quickly can still resume it. A resume after this time gets `StreamAborted({ reason: 'not-found' })`.  |

```ts [retention.ts]
export const handleAskScout = base.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ text: string }>(),
  maxChunks: 500,
  maxAgeMs: 10_000, // a suspended stream is deleted after 10s
  retentionAfterEndMs: 30_000, // an ended stream is kept for 30s
  async *run(ctx, input) {
    const messages = [
      { role: 'user' as const, content: input.prompt },
    ]
    for await (const piece of llm.stream({
      messages,
      signal: ctx.stream.signal,
    })) {
      yield { text: piece }
    }
  },
})
```

A background job runs about every 60 seconds. It deletes stored streams whose time is over, so old streams do not fill up storage.

## Disconnect behavior (durable only)

`onDisconnect` decides what happens to the running generator when the connection that started the stream (its owner) drops.

| Value                             | Behavior                                                                                                                                                                                                                                          |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `'cancel-but-buffer'` _(default)_ | Cancel the generator but keep what is stored: the chunks of a recorded stream, or the cursor checkpoints of a resumable stream.                                                                                                                   |
| `'keep-running'`                  | Leave the generator running while the client is away. A recorded stream stores the chunks made while the client is gone. A resumable stream with this value must also set `broadcast: true`, or `base.resumableStream()` throws when you call it. |

```ts [keep-running.ts]
export const handleAskScout = base.recordedStream('ask-scout', {
  input: v.object({ prompt: v.string() }),
  chunk: t<{ text: string }>(),
  maxChunks: 500,
  onDisconnect: 'keep-running', // runs to the end even while the client is gone
  async *run(ctx, input) {
    const messages = [
      { role: 'user' as const, content: input.prompt },
    ]
    for await (const piece of llm.stream({
      messages,
      signal: ctx.stream.signal,
    })) {
      yield { text: piece }
    }
  },
})
```

::tip
`'keep-running'` fits **recorded** streams best, because they store every chunk while the client is away. A resumable stream stores only a cursor, not its chunks. With no other viewers, every chunk made while the client is gone would be lost. That is why LiveThing requires `broadcast: true` for a resumable stream with `'keep-running'`: other connections still receive the chunks.
::

## The abort signal

Every stream generator gets `ctx.stream.signal`, an `AbortSignal` (the standard web object that tells work to stop). It fires when the stream is cancelled, when the client disconnects, or when the server shuts down. A `'keep-running'` stream is not cancelled when the client disconnects, so its signal does not fire then. Pass the signal into awaited work, such as `fetch`, so that work stops as soon as the stream stops. See [Plain Streams](/server/streams/plain#the-abort-signal) for the full pattern.

## Abort reasons

When LiveThing has to stop a stream, or refuse a resume, it sends `StreamAborted` to the client with a `reason`. Client code reads the reason to decide what to do: resume, start again, or show an error. `StreamAborted` is a built-in error from `@livething/core`.

| `reason`             | When it happens                                                                                                                                                                                                                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `'cancelled'`        | The stream was cancelled, by the client or by the server.                                                                                                                                                                                                                                                           |
| `'buffer-full'`      | A recorded stream's buffer went over `maxChunks`. LiveThing throws it **into** the generator at the `yield`, so you can catch it.                                                                                                                                                                                   |
| `'expired'`          | A suspended durable stream was kept longer than `maxAgeMs` before the client came back.                                                                                                                                                                                                                             |
| `'not-found'`        | A resume named a stream ID the server does not know, or an ended stream older than `retentionAfterEndMs`.                                                                                                                                                                                                           |
| `'hibernation-wake'` | A running stream was lost because the server lost its in-memory state (for example, a Durable Object waking from hibernation). The connection is still open. Only the running stream is gone. For a durable stream, the LiveThing client resumes on its own, so only a plain stream shows this reason to your code. |
| `'unsubscribed'`     | The client cancelled this broadcast stream earlier, so the server stopped sending it chunks. The stream keeps running for everyone else.                                                                                                                                                                            |
| `'cursor-invalid'`   | On resume, a stored cursor or the stored start payload could not be restored (it failed the stream's `cursor` schema, or the saved data is damaged). LiveThing deletes the stored stream. The client decides how to recover, for example by starting a new stream.                                                  |
| `'aborted'`          | Any other internal reason that matches none of the above.                                                                                                                                                                                                                                                           |

```ts [abort-reasons.ts]
// Client code. `handle` is the handle from socket.stream(...).
import { StreamAborted } from '@livething/core'

try {
  for await (const chunk of handle) {
    // ...
  }
} catch (err) {
  if (StreamAborted.matches(err)) {
    if (err.detail.reason === 'hibernation-wake') restartStream()
    else if (err.detail.reason === 'buffer-full') showSlowDownToast()
    else if (err.detail.reason === 'expired') startFresh()
  }
}
```

`buffer-full` is the only reason that server code can handle directly. LiveThing throws it into the generator, so your handler can catch it and stop cleanly. See [Recorded streams](/server/streams/durable-recorded#the-buffer-limit-and-streamaborted). The shared error model (matching, codes, `detail`) is on the [Error model](/core/error-model) page.

## Stream ID and collisions

A client can start a stream with its own stream ID, using the `streamId` option of `socket.stream(...)`. The ID must be a non-empty string of up to 128 characters. This lets the client use an ID from its own app, such as a conversation ID or a job ID, to resume the stream later. If another running stream already uses that ID, LiveThing rejects the start with `StreamIdCollision`. When the client does not send an ID, LiveThing creates one.

A start is also rejected, with `StreamAlreadyActive`, when another stream of the same event is already running on the same connection. Set `allowConcurrent: true` on the stream to allow this.

Both are built-in errors. See the [built-in errors catalog](/core/builtin-errors).

## Storage layout (durable streams)

When you list `resumableStream()` or `recordedStream()`, LiveThing stores durable streams in four SQL tables. They are in the server's own SQLite storage, the same database you use through `ctx.sql`. LiveThing creates the tables with `CREATE TABLE IF NOT EXISTS` when the server starts (boots), not when the first stream starts. Every other capability with stored tables does the same. See [Initialize storage schema](/server/under-the-hood/compile-and-boot#initialize-storage-schema).

| Table                            | One row per                                                                    | Key columns, in plain terms                                                                                                                                                                                                                                                                                                                                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `__livething_streams`            | One durable stream, resumable or recorded                                      | Who owns it and what started it (`user_id`, `stream_id`, `creator_user_id`, `event`, `payload`); which kind (`kind`); lifecycle (`status`: active, suspended, or ended; `started_at`, `last_activity_at`, `ended_at`); the sequence number of the last chunk sent (`last_seq`); scope (`channel_key`, `channel_family`, `broadcast`); the retention options (`max_chunks`, `max_age_ms`, `retention_after_end_ms`) |
| `__livething_stream_chunks`      | One stored chunk of a **recorded** stream (not used by resumable streams)      | Which stream it belongs to (`user_id`, `stream_id`), its order (`seq`), the chunk itself as JSON (`payload`), and when it was sent (`emitted_at`)                                                                                                                                                                                                                                                                  |
| `__livething_stream_checkpoints` | One cursor checkpoint of a **resumable** stream (not used by recorded streams) | Which stream it belongs to (`user_id`, `stream_id`), the chunk sequence number it resumes after (`seq`), the cursor as JSON (`cursor`), and when LiveThing saved it (`saved_at`)                                                                                                                                                                                                                                   |
| `__livething_stream_subscribers` | One subscriber of a **broadcast** stream                                       | Which stream and who (`user_id`, `stream_id`, `subscriber_user_id`), the last chunk a resume has sent them (`caught_up_seq`), and when they cancelled (`unsubscribed_at`, `null` while still subscribed)                                                                                                                                                                                                           |

`user_id` is not always the user ID of a connection. For a broadcast stream, it is a key that LiveThing builds from the stream's scope (the whole server, or one channel). So every subscriber finds the same row when it resumes, whatever its own user ID is. Deleting a stream's `__livething_streams` row also deletes its chunks, checkpoints and subscriber rows (a cascade delete).

::warning
Every table LiveThing owns uses the reserved `__livething_` prefix, including the four above. Never create your own table with that prefix, because `ctx.sql` is the same SQLite database that LiveThing writes to. A name collision gives no error at startup. For example, say you created a table named `__livething_streams` before you listed `resumableStream()` or `recordedStream()`. LiveThing's `CREATE TABLE IF NOT EXISTS` then keeps your table and its different columns, with no error. Durable streams later fail at runtime with unclear SQL errors, instead of a clear "table already exists" error at startup.
::

## Full option reference

Every option of the three builders (`base.stream`, `base.resumableStream`, `base.recordedStream`), with its default. In the "Kinds" column, "all" means all three kinds and "durable" means resumable and recorded.

| Option                | Kinds     | Default               | Purpose                                                                                                                                                                                                 |
| --------------------- | --------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `input`               | all       | (none)                | Schema for the start payload the client sends. The second argument of `run` is the validated value.                                                                                                     |
| `chunk`               | all       | (inferred)            | Optional [type marker](/server/server/overview) (`t<T>()`) that sets the type of each chunk. Chunks go out, so LiveThing never validates them. Without it, the chunk type comes from what `run` yields. |
| `nudges`              | all       | `{}`                  | Map from nudge event name to schema (or `null` for no payload). Read with `ctx.stream.nudges(yield ...)`.                                                                                               |
| `broadcast`           | all       | `false`               | Send chunks to every connection in scope, not only the connection that started the stream.                                                                                                              |
| `allowConcurrent`     | all       | `false`               | Allow more than one stream of the same event at once on a connection. Without it, a second start is rejected with `stream-already-active`.                                                              |
| `highWaterMark`       | all       | 256 KB                | Limit, in bytes, of the outgoing buffer. `ctx.stream.drain()` waits until the buffer is below it.                                                                                                       |
| `cursor`              | resumable | (none)                | `t<T>()` to type the cursor only, or a schema to also check stored cursors at runtime when a stream resumes.                                                                                            |
| `maxChunks`           | recorded  | 500                   | Maximum number of stored chunks. Going over it throws `StreamAborted({ reason: 'buffer-full' })` into the generator. Resumable streams do not accept this option.                                       |
| `maxAgeMs`            | durable   | 5 minutes             | How long a suspended stream is kept before LiveThing deletes it.                                                                                                                                        |
| `retentionAfterEndMs` | durable   | 30 seconds            | How long an ended stream is kept, so a client that reconnects quickly can still resume it.                                                                                                              |
| `onDisconnect`        | durable   | `'cancel-but-buffer'` | What happens to the generator when the owning connection drops: `'cancel-but-buffer'` or `'keep-running'`.                                                                                              |
| `run`                 | all       | (required)            | The async generator. Each yielded value is sent as one chunk.                                                                                                                                           |
