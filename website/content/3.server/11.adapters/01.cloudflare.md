`@wskit/server-cloudflare` turns a server definition into a Cloudflare **Durable Object** class. Each Durable Object instance owns its own WebSocket connections, its own SQLite-backed storage, and its own scheduled alarm — which is exactly what you want for a room, a document, a game, or any other stateful unit.

This page wires one up end to end: the handler, the Durable Object class, the Worker `fetch` entry, the env binding, and the `wrangler.jsonc` config.

::note
Install with `npm install @wskit/server @wskit/server-cloudflare @wskit/core` (or your package manager's equivalent). `@wskit/server` is a peer dependency of the adapter, so you install it yourself. See [Installation](/start/installation).
::

## The whole picture

Four files, each with one job.

::steps

### Write the handler

This is your platform-agnostic server definition. Nothing here mentions Cloudflare.

```ts [handler.ts]
import { define, emits, t } from '@wskit/server'
import * as v from 'valibot'
import type { InferClient } from '@wskit/server'

const base = define({
  env: t<Env>(),
  capabilities: [emits({ 'echo-pong': t<{ text: string }>() })],
})

const handleEchoPing = base.on('echo-ping', {
  input: v.object({ text: v.string() }),
  run(ctx, input) {
    ctx.send('echo-pong', { text: input.text })
  },
})

export const chatHandler = base.assemble(handleEchoPing)

export type ChatClient = InferClient<typeof chatHandler>
```

### Turn it into a Durable Object class

`server(handler)` returns a Durable Object **class**, not an instance. Export it from your Worker module so the Cloudflare runtime can construct one instance per `idFromName(...)`.

```ts [worker.ts]
import { server } from '@wskit/server-cloudflare'
import { chatHandler } from './handler'

export const ChatRoom = server(chatHandler)
```

### Route requests to it from the Worker `fetch`

The Worker's default export receives every HTTP request. Pick a Durable Object ID (here from a `room` query param), get the stub, and forward the request to it. The adapter handles the WebSocket upgrade inside the Durable Object.

```ts [worker.ts]
export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url)
    const room = url.searchParams.get('room') ?? 'default'

    const id = env.CHAT_ROOM.idFromName(room)
    return env.CHAT_ROOM.get(id).fetch(request)
  },
} satisfies ExportedHandler<Env>
```

### Bind the class in `wrangler.jsonc`

The binding name (`CHAT_ROOM`) is what you read off `env`. The `class_name` is the exported class. New Durable Object classes go in a `migrations` entry as `new_sqlite_classes` so they get SQLite storage.

```jsonc [wrangler.jsonc]
{
  "name": "chat",
  "main": "src/worker.ts",
  "compatibility_date": "2026-04-07",
  "compatibility_flags": ["nodejs_compat"],
  "durable_objects": {
    "bindings": [{ "name": "CHAT_ROOM", "class_name": "ChatRoom" }],
  },
  "migrations": [{ "tag": "v1", "new_sqlite_classes": ["ChatRoom"] }],
  "observability": {
    "enabled": true,
    "logs": { "head_sampling_rate": 1 },
  },
}
```

::

That is a complete deployment. `wrangler dev` runs it locally; `wrangler deploy` ships it.

::caution
`migrations` entries are append-only history, not a snapshot of your current classes. When you add a new Durable Object class to an app that is already deployed, add a **new** `tag` with that class under `new_sqlite_classes` — do not add it to an existing tag or edit `v1` after it has shipped. Cloudflare replays the whole migration history on every deploy, so changing a past tag breaks existing instances.
::

## The `compatibility_date` requirement

WSKit requires a `compatibility_date` of **`2026-04-07` or later**. This is not optional.

```jsonc [wrangler.jsonc]
{
  "compatibility_date": "2026-04-07",
}
```

On that date the Workers runtime completes a client-initiated WebSocket close handshake itself. On earlier dates it does not, so a client that calls `socket.disconnect()` (or `ws.close()`) can hang until a timeout instead of closing promptly. Server-initiated closes are not affected. Set the date and client disconnects close cleanly.

::tip
The `nodejs_compat` flag is also recommended. The adapter uses `node:async_hooks` for per-request async context, which `nodejs_compat` provides.
::

## What reaches the engine

Once a socket is open, the adapter forwards Cloudflare's `webSocketMessage`, `webSocketClose`, and `webSocketError` Durable Object callbacks straight into the engine — there is no extra parsing or routing layer in between.

WSKit only understands string frames. If a client sends a binary frame, the adapter closes the socket with code `1003` (`unsupported data`) and the reason `[wskit] binary frames are not supported yet` — the connection does not stay open in a half-working state. Send JSON (or any other string encoding) from the client instead.

::tip
`ctx.log` writes through `console.log` / `console.warn` / `console.error`. Turn on `observability.logs` in `wrangler.jsonc` (as shown in the config above) so those calls show up in the Cloudflare dashboard and `wrangler tail`.
::

## The env binding

The `name` you give a Durable Object binding in `wrangler.jsonc` is the property you read off `env`. Add it to your `Env` type so `env.CHAT_ROOM` is typed:

```ts [env.d.ts]
interface Env {
  CHAT_ROOM: DurableObjectNamespace<ChatRoom>
}
```

Inside a handler, the same `env` is available as `ctx.env`, typed as the `Env` you passed to `define({ env: t<Env>() })`. So a handler can reach other bindings — a KV namespace, a secret, another Durable Object — through `ctx.env`.

::tip
Running `wrangler types` writes this `Env` interface for you from `wrangler.jsonc`, including the `DurableObjectNamespace<ChatRoom>` generic. Re-run it whenever you add or rename a binding.
::

## How it relates to hibernation

A Durable Object that just sits there waiting for the next WebSocket message costs money to keep in memory. **Hibernation** lets Cloudflare evict the instance from memory while keeping the sockets open at the edge, then wake it only when a frame actually arrives.

The adapter turns hibernation on automatically when your definition sets `hibernation: { enabled: true }` — you do not call a separate adapter method. With it on:

- The adapter accepts sockets through `ctx.acceptWebSocket(...)` (the hibernatable path) instead of a plain `accept()`.
- It registers a `ping`/`pong` auto-response at the edge, so the client's keepalive is answered without waking the instance. Because no server-side ping runs under hibernation, `ctx.latency` and `ctx.quality` are always `null` whenever hibernation is enabled — not just while the instance is evicted.
- Per-socket state is persisted into Cloudflare's WebSocket attachment, so it survives an eviction and is restored on wake.

```ts [hibernating-handler.ts]
import { define, emits, t } from '@wskit/server'

const base = define({
  env: t<Env>(),
  hibernation: { enabled: true },
  capabilities: [emits({ tick: t<{ n: number }>() })],
})
```

::callout{icon="i-ph-moon-duotone" to="/server/define/hibernation"}
What survives a hibernation cycle, the storage rules, and the full config live in the **Hibernation** page.
::

## Graceful shutdown

Cloudflare does not emit a native shutdown signal. The Durable Object class the adapter returns exposes a `shutdown()` RPC method so you can drain an instance on purpose — before a deploy or a maintenance window. Calling it runs every `onShutdown` hook you registered and closes every open socket cleanly, so clients reconnect to a fresh instance.

Call it from the Worker like any other Durable Object RPC:

```ts [worker.ts]
export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url)
    const room = url.searchParams.get('room') ?? 'default'

    if (url.pathname === '/admin/drain') {
      const id = env.CHAT_ROOM.idFromName(room)
      await env.CHAT_ROOM.get(id).shutdown()
      return new Response(null, { status: 204 })
    }

    const id = env.CHAT_ROOM.idFromName(room)
    return env.CHAT_ROOM.get(id).fetch(request)
  },
} satisfies ExportedHandler<Env>
```

Under hibernation, `shutdown()` first wakes every hibernated socket through the engine so the drain reaches all of them — a fresh instance starts with an empty in-memory connection map, so skipping the wake would leave those clients hanging.

## Extending the Durable Object class

`server(...)` returns a real class, so you can `extend` it when you need to add your own RPC methods or hold a reference to the Durable Object state. Call `super(ctx, env)` first.

```ts [worker.ts]
import { server } from '@wskit/server-cloudflare'
import { chatHandler } from './handler'

const Base = server(chatHandler)

export class ChatRoom extends Base {
  #ctx: DurableObjectState

  constructor(ctx: DurableObjectState, env: Env) {
    super(ctx, env)
    this.#ctx = ctx
  }

  async memberCount(): Promise<number> {
    return this.#ctx.getWebSockets().length
  }
}
```

The added `memberCount()` is callable as a Durable Object RPC method, alongside the built-in `shutdown()`.

## The direct Cloudflare access point: `ctx.platform`

Most handler code should use the high-level WSKit APIs — `ctx.sql`, `ctx.kv`, `ctx.schedule`, `ctx.env`. When you need a raw Cloudflare capability that WSKit does not wrap, use `ctx.platform`. It exposes the Durable Object state and your env.

`ctx.platform` is typed `unknown` (the core engine is platform-agnostic), so cast it with the `Platform<Env>` type the Cloudflare adapter exports:

```ts [list-by-tag.ts]
import type { Platform } from '@wskit/server-cloudflare'

const handleCount = base.on('count-room', {
  input: v.object({}),
  run(ctx) {
    const platform = ctx.platform as Platform<Env>
    // List every socket the runtime tagged "room:lobby".
    const sockets = platform.ctx.getWebSockets('room:lobby')
    ctx.send('count', { n: sockets.length })
  },
})
```

`Platform<Env>` gives `platform.ctx` — `getWebSockets(tag?)`, `blockConcurrencyWhile(...)`, `waitUntil(...)`, and `storage` — plus `platform.env`, your typed env. Use it only when you must — most needs are covered by the typed surface in [Context and storage](/server/context-and-storage/overview).

## Running multiple handlers

A real app rarely has one server — you might have a chat room, a presence tracker, and a live document, each with its own contract. WSKit has no `router()` API; you run several handlers the plain Cloudflare way: one Worker `fetch`, several Durable Object classes, and a switch on the request path.

### One class per handler

Each handler becomes its own Durable Object class through `server(...)`:

```ts [servers.ts]
import { server } from '@wskit/server-cloudflare'
import { chatHandler } from './chat-handler'
import { docHandler } from './doc-handler'
import { presenceHandler } from './presence-handler'

export const ChatRoom = server(chatHandler)
export const Presence = server(presenceHandler)
export const Document = server(docHandler)
```

### Route in the Worker `fetch`

Match the path, pick the matching binding, and forward the request. Once you have more than a couple of routes, a lookup table reads better than a stack of `if`s:

```ts [worker.ts]
export { ChatRoom, Presence, Document } from './servers'

const ROUTES: Record<string, keyof Env> = {
  '/ws/chat': 'CHAT_ROOM',
  '/ws/presence': 'PRESENCE',
  '/ws/document': 'DOCUMENT',
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url)
    const room = url.searchParams.get('room') ?? 'default'

    const bindingName = ROUTES[url.pathname]
    if (bindingName) {
      const namespace = env[bindingName] as DurableObjectNamespace
      return namespace.get(namespace.idFromName(room)).fetch(request)
    }

    return new Response('not found', { status: 404 })
  },
} satisfies ExportedHandler<Env>
```

### Bind every class in `wrangler.jsonc`

Each class needs a binding and a `migrations` entry as `new_sqlite_classes` under a fresh `tag`:

```jsonc [wrangler.jsonc]
{
  "name": "app",
  "main": "src/worker.ts",
  "compatibility_date": "2026-04-07",
  "durable_objects": {
    "bindings": [
      { "name": "CHAT_ROOM", "class_name": "ChatRoom" },
      { "name": "PRESENCE", "class_name": "Presence" },
      { "name": "DOCUMENT", "class_name": "Document" },
    ],
  },
  "migrations": [
    { "tag": "v1", "new_sqlite_classes": ["ChatRoom", "Presence", "Document"] },
  ],
}
```

Each `idFromName(room)` keeps rooms isolated — `/ws/chat?room=lobby` and `/ws/chat?room=staff` are two Durable Object instances of the same `ChatRoom` class, with separate connections and storage. The `room` can be anything that names an instance: a user ID, a document ID, a tenant ID.
