Inbox makes one promise: every member of the channel gets every message, even the ones sent while they were offline. It keeps that promise with three moving parts, and this page walks each one: the durable per-member row written on every broadcast, the `__received__` acknowledgement that settles that row, and the reconnect drain that re-delivers any row a member never acknowledged. The [Overview](/server/inbox/overview) frames inbox against replay and lays out the storage model; here we go through the delivery mechanics.

## One row per member, held until acknowledged

When a handler broadcasts to an inbox channel, the engine writes a durable row into **every current member's queue** as the message goes out — this is [**fan-out on write**](/learn/reliability#fan-out-on-read-vs-fan-out-on-write). Connected members also get the message live, straight away. The row stays in a member's queue until that member confirms it arrived by sending a `__received__` acknowledgement; at that point the row is *settled* and, by default, dropped.

Nothing in your handler mentions any of this. You broadcast as usual, and the engine turns each broadcast into a durable per-member delivery.

```typescript [inbox-server.ts]
import { define, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { dedup } from '@wskit/server/dedup'
import { inbox } from '@wskit/server/inbox'
import { persistence } from '@wskit/server/persistence'
import { sequence } from '@wskit/server/sequence'
import * as v from 'valibot'
import { requireUsername } from './upgrade'

const RoomMsg = v.object({ text: v.string(), from: v.string() })
const SendRoomMsg = v.object({ text: v.string() })

const base = define({
  env: t<Env>(),
  upgrade: (request) => requireUsername(request),
  capabilities: [
    persistence(),
    channels(),
    sequence({ persist: true }),
    dedup(),
    inbox(),
  ],
})

// A persistent channel with inbox on: every broadcast writes one held row per member.
const chat = base.channel('chat', {
  persistent: true,
  inbox: true,
  outgoing: { emits: { 'room-msg': t<v.InferOutput<typeof RoomMsg>>() } },
})

export const handleSendRoomMsg = chat.on('send-room-msg', {
  input: SendRoomMsg,
  run(ctx, payload) {
    ctx.channel.broadcast('room-msg', { text: payload.text, from: ctx.meta.username })
  },
})
```

::note
Inbox delivers to a **member identity**, so members need a stable identity — set one on upgrade (here `requireUsername`). An anonymous connection with no identity still gets messages live while it is connected, but has no durable queue: no offline drain, no guarantee. See the [Overview requirements](/server/inbox/overview#requirements) for the full list.
::

## The client acknowledges for you

You do not write the `__received__` acknowledgement by hand. The [client `inbox()` primitive](/client/primitives/inbox) tracks the highest sequence number it has seen on each inbox channel and sends `__received__` automatically. It learns which channels are inbox channels from the `__subscribeOk__` acknowledgement — that frame carries `__wskit.inbox: true` for an inbox channel.

The acknowledgement travels as a channel-scoped frame:

```json
{ "event": "__received__", "payload": { "receivedThrough": 7 }, "__wskit": { "channel": "chat" } }
```

`receivedThrough` is a sequence number: it means "I have everything on this channel up to and including seq 7." That single cursor settles every held row at or below it in one shot.

The client also **re-acks on reconnect**. When the socket comes back and the client rejoins the channel, it resends its highest cursor, so a member who acknowledged just before the drop does not get those rows drained back to them.

## The reconnect drain

A member who was offline when a broadcast landed still has their rows waiting. On reconnect, [persistence](/server/capabilities/persistence) auto-rejoins the channel, and then the engine **drains** the held rows — re-delivering them in order, each still carrying its original sequence number.

Because a drained row can overlap with something the member already saw live before the socket dropped, [`dedup()`](/server/capabilities/dedup) on the client filters the repeats out by message ID, so your `on()` handlers run once per message. That is why `dedup()` is a build requirement for inbox.

Walking the offline path end to end:

::steps{level="3"}

### Both members subscribe

Alice and Bob both subscribe to `chat`, so both have durable memberships that outlive a dropped socket.

### Alice's socket drops

Alice goes offline. Her membership stays; only her connection is gone.

### Bob broadcasts

Bob broadcasts `room-msg`. The engine writes a held row into Alice's queue — she is still a durable member — and delivers live to any connected member.

### Alice reconnects and drains

Alice reconnects. Persistence auto-rejoins `chat`, then the drain re-delivers her held `room-msg`, still carrying its original sequence number.

### The client acks

Alice's client auto-acks with `__received__ { receivedThrough: <seq> }`. The row settles and, by default, drops.

### A later reconnect does not repeat it

Alice's socket drops and reconnects again. The row is gone, so it is **not** re-delivered.

::

That last step is the whole point: an acknowledged message never comes back, even across many reconnects.

## `afterDelivered`: delete or keep

Once a member acknowledges a row, `afterDelivered` decides what happens to it:

| Value | Behaviour |
|---|---|
| `'delete'` (default) | The row is dropped the moment it settles. The queue holds only what is still undelivered. |
| `'keep'` | The row is retained after it settles. Useful when you want the delivered history to stick around rather than evaporate on acknowledgement. |

```typescript [after-delivered.ts]
// Default: acknowledged rows are dropped.
const chat = base.channel('chat', {
  persistent: true,
  inbox: true,
  outgoing: { emits: { 'room-msg': t<v.InferOutput<typeof RoomMsg>>() } },
})

// Keep acknowledged rows — requires retention to bound them.
const audited = base.channel('audited', {
  persistent: true,
  inbox: {
    afterDelivered: 'keep',
    retention: { maxMessages: 500 },
  },
  outgoing: { emits: { 'room-msg': t<v.InferOutput<typeof RoomMsg>>() } },
})
```

::warning
`afterDelivered: 'keep'` **requires** a `retention` block, or the build throws `[wskit] inbox `afterDelivered: 'keep'` requires `retention` so kept rows can age out.` Without a bound, kept rows would grow forever. See [Overflow and the gap signal](/server/inbox/overflow-and-gap) for what `retention` does.
::

## Seeding a member's queue: `ctx.channel.inbox.backfill`

Inside a channel handler you can inject held rows for one member by hand — to seed a late joiner with history, or to migrate an existing message log into inbox. `ctx.channel.inbox.backfill(identity, messages)` writes the given frames straight into that member's queue, each keeping its own `seq` and `messageId`.

These cursor surfaces attach to `ctx.channel` at runtime and are not on the static context type yet, so the handler casts to reach them — the same pattern the fixtures use:

```typescript [backfill.ts]
interface ChannelInboxCtx {
  inbox: {
    backfill(
      identity: string,
      messages: { event: string; payload: unknown; __wskit: { seq: number; messageId: string } }[],
    ): void
  }
}

export const handleSeedHistory = chat.on('seed-history', {
  input: v.object({ identity: v.string() }),
  run(ctx, payload) {
    const inboxCtx = ctx.channel as unknown as ChannelInboxCtx
    inboxCtx.inbox.backfill(payload.identity, [
      { event: 'room-msg', payload: { text: 'welcome', from: 'system' }, __wskit: { seq: 1, messageId: 'seed-1' } },
      { event: 'room-msg', payload: { text: 'house rules', from: 'system' }, __wskit: { seq: 2, messageId: 'seed-2' } },
    ])
  },
})
```

The `seq` and `messageId` on each frame are what the client uses to order and de-duplicate the injected rows, exactly as it would for a normal drained row. Choose them so they slot correctly into that member's cursor.

## Who received up to a message: `ctx.channel.inbox.receiversOf`

Because inbox already tracks each member's acknowledgement, it can tell you which members have received up to a given sequence. `ctx.channel.inbox.receiversOf(seq)` returns the identities whose received cursor has reached `seq`. It reads the same cast surface:

```typescript [received-by.ts]
interface ChannelInboxQueryCtx {
  inbox: { receiversOf(seq: number): string[] }
}

export const handleWhoGotIt = chat.on('who-got-it', {
  input: v.object({ seq: v.number() }),
  run(ctx, payload) {
    const inboxCtx = ctx.channel as unknown as ChannelInboxQueryCtx
    const identities = inboxCtx.inbox.receiversOf(payload.seq)
    ctx.send('got-it', { seq: payload.seq, identities })
  },
})
```

This is the server-side foundation of received receipts. The [Receipts](/server/inbox/receipts) page covers how that cursor also fans out live to the channel as a `__received__` tick, and how read receipts build on the same shape.
