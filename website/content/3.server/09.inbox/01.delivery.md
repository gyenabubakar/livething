Inbox makes one promise: every member of the channel gets every message, even the ones sent while they were offline. It keeps that promise with three moving parts, and this page walks each one: the durable per-member row written on every broadcast, the `__received__` acknowledgement that settles that row, and the reconnect drain that re-delivers any row a member never acknowledged. The [Overview](/server/inbox/overview) frames inbox against replay and lays out the storage model; here we go through the delivery mechanics.

## One row per member, held until acknowledged

When a handler broadcasts to an inbox channel, the engine writes a durable row into **every current member's queue** as the message goes out — this is [**fan-out on write**](/learn/reliability#fan-out-on-read-vs-fan-out-on-write). Connected members also get the message live, straight away. The row stays in a member's queue until that member confirms it arrived by sending a `__received__` acknowledgement; at that point the row is _settled_ and, by default, dropped.

Nothing in your handler mentions any of this. You broadcast as usual, and the engine turns each broadcast into a durable per-member delivery.

```typescript [inbox-server.ts]
import { define, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { dedup } from '@wskit/server/dedup'
import { inbox } from '@wskit/server/inbox'
import { sequence } from '@wskit/server/sequence'
import * as v from 'valibot'
import { requireUsername } from './upgrade'

const RoomMsg = v.object({ text: v.string(), from: v.string() })
const SendRoomMsg = v.object({ text: v.string() })

const base = define({
  env: t<Env>(),
  upgrade: (request) => requireUsername(request),
  capabilities: [channels(), sequence({ persist: true }), dedup()],
})

// A channel with inbox listed in its own capabilities: every broadcast writes
// one held row per member.
const chat = base.channel('chat', {
  capabilities: [inbox()],
  outgoing: { emits: { 'room-msg': t<v.InferOutput<typeof RoomMsg>>() } },
})

export const handleSendRoomMsg = chat.on('send-room-msg', {
  input: SendRoomMsg,
  run(ctx, payload) {
    ctx.channel.broadcast('room-msg', {
      text: payload.text,
      from: ctx.meta.username,
    })
  },
})
```

::note
Inbox delivers to a **member's user id**, so members need a stable `userId` — set one on upgrade (here `requireUsername`). An anonymous connection with no `userId` still gets messages live while it is connected, but has no durable queue: no offline drain, no guarantee. See the [Overview requirements](/server/inbox/overview#requirements) for the full list.
::

## The client acknowledges for you

You do not write the `__received__` acknowledgement by hand. The [client `inbox()` primitive](/client/primitives/inbox) tracks the highest sequence number it has seen on each inbox channel and sends `__received__` automatically. It learns which channels are inbox channels from the `__subscribeOk__` acknowledgement — that frame carries `__wskit.inbox: true` for an inbox channel.

The acknowledgement travels as a channel-scoped frame:

```json
{
  "event": "__received__",
  "payload": { "receivedThrough": 7 },
  "__wskit": { "channel": "chat" }
}
```

`receivedThrough` is a sequence number: it means "I have everything on this channel up to and including seq 7." That single cursor settles every held row at or below it in one shot.

The client also **re-acks on reconnect**. When the socket comes back and the client rejoins the channel, it resends its highest cursor, so a member who acknowledged just before the drop does not get those rows drained back to them.

## The reconnect drain

A member who was offline when a broadcast landed still has their rows waiting. On reconnect, [durable membership](/server/channels/membership-and-presence) auto-rejoins the channel, and then the engine **drains** the held rows — re-delivering them in order, each still carrying its original sequence number.

Because a drained row can overlap with something the member already saw live before the socket dropped, [`dedup()`](/server/capabilities/dedup) on the client filters the repeats out by message ID, so your `on()` handlers run once per message. That is why `dedup()` is a build requirement for inbox.

Walking the offline path end to end:

::steps{level="3"}

### Both members subscribe

Alice and Bob both subscribe to `chat`, so both have durable memberships that outlive a dropped socket.

### Alice's socket drops

Alice goes offline. Her membership stays; only her connection is gone.

### Bob broadcasts

Bob broadcasts `room-msg`. The engine writes a held row into Alice's queue — she is still a durable member — and delivers live to any connected member.

### Alice reconnects and drains

Alice reconnects. Durable membership auto-rejoins `chat`, then the drain re-delivers her held `room-msg`, still carrying its original sequence number.

### The client acks

Alice's client auto-acks with `__received__ { receivedThrough: <seq> }`. The row settles and, by default, drops.

### A later reconnect does not repeat it

Alice's socket drops and reconnects again. The row is gone, so it is **not** re-delivered.

::

That last step is the whole point: an acknowledged message never comes back, even across many reconnects.

## `onDelivered`: delete or retain

Once a member acknowledges a row, `onDelivered` decides what happens to it:

| Value                | Behaviour                                                                                                                              |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `'delete'` (default) | The row is dropped the moment it settles. The queue holds only what is still undelivered.                                              |
| `'retain'`           | The row is kept after it settles. Useful when you want the delivered history to stick around rather than evaporate on acknowledgement. |

```typescript [on-delivered.ts]
// Default: acknowledged rows are dropped.
const chat = base.channel('chat', {
  capabilities: [inbox()],
  outgoing: { emits: { 'room-msg': t<v.InferOutput<typeof RoomMsg>>() } },
})

// Retain acknowledged rows — requires retention to bound them.
const audited = base.channel('audited', {
  capabilities: [
    inbox({
      onDelivered: 'retain',
      retention: { maxMessages: 500 },
    }),
  ],
  outgoing: { emits: { 'room-msg': t<v.InferOutput<typeof RoomMsg>>() } },
})
```

::warning
`onDelivered: 'retain'` **requires** a `retention` block, or the build throws `[wskit] inbox `onDelivered: 'retain'`requires`retention` so kept rows can age out.` Without a bound, kept rows would grow forever. See [Overflow and the gap signal](/server/inbox/overflow-and-gap) for what `retention` does.
::

## Seeding a member's queue: `ctx.channel.inbox.backfill`

Inside a channel handler you can inject held rows for one member by hand — to seed a late joiner with history, or to migrate an existing message log into inbox. Inside `chat`'s own handler, `ctx.channel.inbox` is the channel's `ChannelInbox` surface, typed because `chat` lists `inbox()` in its own `capabilities` — the engine attaches it directly, so it is never `null` here:

```typescript [backfill.ts]
export const handleSeedHistory = chat.on('seed-history', {
  input: v.object({ userId: v.string() }),
  run(ctx, payload) {
    ctx.channel.inbox.backfill(payload.userId, [
      {
        event: 'room-msg',
        payload: { text: 'welcome', from: 'system' },
        __wskit: { seq: 1, messageId: 'seed-1' },
      },
      {
        event: 'room-msg',
        payload: { text: 'house rules', from: 'system' },
        __wskit: { seq: 2, messageId: 'seed-2' },
      },
    ])
  },
})
```

The `seq` and `messageId` on each frame are what the client uses to order and de-duplicate the injected rows, exactly as it would for a normal drained row. Choose them so they slot correctly into that member's cursor.

## Who received up to a message: `ctx.channel.inbox.receiversOf`

Because inbox already tracks each member's acknowledgement, it can tell you which members have received up to a given sequence. `receiversOf(seq)` on that same surface returns the user ids whose received cursor has reached `seq`:

```typescript [received-by.ts]
export const handleWhoGotIt = chat.on('who-got-it', {
  input: v.object({ seq: v.number() }),
  run(ctx, payload) {
    const userIds = ctx.channel.inbox.receiversOf(payload.seq)
    ctx.send('got-it', { seq: payload.seq, userIds })
  },
})
```

This is the server-side foundation of received receipts. The [Receipts](/server/inbox/receipts) page covers how that cursor also fans out live to the channel as a `__received__` tick, and how read receipts build on the same shape.

## Reaching inbox from any handle: `handle.inbox()` / `handle.readReceipts()`

`ctx.channel.inbox` and `ctx.channel.readReceipts` are the surface object inside a handler scoped to that exact channel — the engine attaches them directly there, and they are typed as always present (never `null`) because the channel's own `capabilities` list carries `inbox()` / `readReceipts()`. From anywhere else — another channel's handler, a top-level handler, a hook, a scheduled task — reach the same surfaces through any other channel handle's `inbox()` and `readReceipts()` methods. Both are nullable: they return the surface when that channel has the matching feature enabled, or `null` otherwise, so you can check before using them.

```typescript [handle-inbox.ts]
export const handleBackfillOther = base.on('backfill-other-room', {
  input: v.object({ room: v.string(), userId: v.string() }),
  run(ctx, input) {
    const other = ctx.channels.get(input.room)
    const otherInbox = other.inbox()
    if (!otherInbox) return

    otherInbox.backfill(input.userId, [
      {
        event: 'room-msg',
        payload: { text: 'catch up on this', from: 'system' },
        __wskit: { seq: 1, messageId: 'seed-1' },
      },
    ])
  },
})
```

`ctx.channels.get(...)` works from any handler, so this reaches an inbox or read-receipts channel you are not currently inside. A handle for a channel with neither feature on returns `null` from both methods — there is nothing to cast, no capability check needed beyond the `null` guard.

## Who is behind: `ctx.channel.inbox.backlog()`

`backlog()` is an observability query, not a warning: it lists every member that still has unacked held rows for this channel, so you can see who is behind and how many rows each is holding. It reads the same rows and cursors the reconnect drain uses — nothing here is a separate log or estimate.

```typescript [inbox-backlog.ts]
export const handleInspectBacklog = chat.on('inspect-backlog', {
  input: v.object({}),
  run(ctx) {
    const entries = ctx.channel.inbox.backlog()
    for (const entry of entries) {
      ctx.log.info('inbox backlog', {
        userId: entry.userId,
        online: entry.online,
        heldRows: entry.heldRows,
        receivedThrough: entry.receivedThrough,
        oldestHeldAt: entry.oldestHeldAt,
      })
    }
  },
})
```

Each entry is an `InboxBacklogEntry`:

::field-group
::field{name="userId" type="string"}
The member's user id.
::
::field{name="online" type="boolean"}
Whether this user has a live connection on this instance right now. A member that is `online` and still has `heldRows` growing is behind on acking, not behind on connectivity — a different problem than an offline member with the same held rows.
::
::field{name="heldRows" type="number"}
Count of unacked rows still held for this member on this channel.
::
::field{name="receivedThrough" type="number"}
The member's `received_through` cursor for this channel — `0` if it has never acked.
::
::field{name="oldestHeldAt" type="number"}
`created_at` (ms) of the member's oldest unacked held row — how long the oldest gap has been open.
::
::field{name="lastSeenAt" type="number | null | undefined"}
The member's last-seen timestamp. Present only when the [`lastSeen()`](/server/capabilities/last-seen) capability is also installed; `undefined` (the field is absent) otherwise.
::
::

Only members with at least one held row appear — a member fully caught up is not in the list at all. A member with no `lastSeen()` installed simply has no `lastSeenAt` key on its entry; there is no `lag` field, since "how far behind" is already `heldRows` and `oldestHeldAt` rather than a single derived number.

`backlog()` is available the same way as `backfill` and `receiversOf` — on `ctx.channel.inbox` inside this channel's own handler, or on any handle's `inbox()` from anywhere via `ctx.channels.get(name).inbox()?.backlog()`.
