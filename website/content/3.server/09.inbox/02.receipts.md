Receipts answer two questions about a message: **who received it** and **who read it**. The grey double-check and the blue check. They split cleanly by owner: `inbox()` owns received, `readReceipts()` owns read. Inbox already tracks each member's delivery acknowledgement, so the received cursor comes for free; pushing it live to members is an opt-in flag, and read receipts are a small capability layered on top. This page covers both, the live `__received__` / `__read__` ticks they fan out, the member cap, and the query round-trip for asking after the fact.

## Received receipts: the cursor is free, the live tick opts in

Every inbox channel already holds a **received cursor** per member — the sequence up to which that member has acknowledged delivery (see [Delivery and acknowledgements](/server/inbox/delivery)). The cursor itself needs nothing extra: you get it the moment you have inbox.

Two things surface that cursor:

- **On the server**, `ctx.channel.inbox.receiversOf(seq)` returns the user ids whose received cursor has reached `seq`. This works on any inbox channel, with no opt-in.
- **To members**, when a member's cursor advances, the engine can fan out a `__received__` frame carrying `{ userId, receivedThrough }` — a live tick every other member can render as "Bob has now received up to here." This live push is **off by default**; turn it on with `broadcastReceipts: true` in the channel's `inbox(...)` config.

::note
**An anonymous connection never appears in `receiversOf` / `readersOf`.** Both cursors are keyed on a member's `userId` (see [Requirements](/server/inbox/overview#requirements)), and a connection with no `userId` — no `onUpgrade`, or one that returned none — has no cursor row to advance. Its acks are accepted (the socket still gets live delivery), but they never get a durable receipt, so it is invisible to both queries and both live ticks.
::

```typescript [broadcast-receipts.ts]
const chat = base.channel('chat', {
  capabilities: [inbox({ broadcastReceipts: true })], // push the grey double-check tick to members
  outgoing: { emits: { 'room-msg': t<{ text: string; from: string }>() } },
})
```

With `broadcastReceipts` on, the received tick fans out like this:

```json
{
  "event": "__received__",
  "payload": { "userId": "bob", "receivedThrough": 7 },
  "__wskit": { "channel": "chat" }
}
```

That is the same `__received__` event a client sends to acknowledge delivery — one direction carries the sender's own mark, the other names whose mark advanced. Inbox owns both halves.

## Read receipts: the opt-in `readReceipts()` capability

A member _receiving_ a message is not the same as _reading_ it. Read receipts track the blue check — who has actually looked at the message. That is a separate `readReceipts()` capability, channel-only like `inbox()`. List it alongside `inbox()` in the channel's own `capabilities`, optionally passing `{ maxReceiptAudience }`.

```typescript [receipts-server.ts]
import { define, emits, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { dedup } from '@wskit/server/dedup'
import { inbox, readReceipts } from '@wskit/server/inbox'
import { sequence } from '@wskit/server/sequence'
import * as v from 'valibot'
import { requireUsername } from './upgrade'

const RoomMsg = v.object({ text: v.string(), from: v.string() })
const SendRoomMsg = v.object({ text: v.string() })

const base = define({
  env: t<Env>(),
  upgrade: (request) => requireUsername(request),
  capabilities: [
    channels(),
    sequence({ persist: true }),
    dedup(),
    emits({
      'cursor-answer': t<{
        kind: 'received' | 'read'
        seq: number
        userIds: string[]
      }>(),
    }),
  ],
})

const chat = base.channel('chat', {
  capabilities: [inbox(), readReceipts()],
  outgoing: { emits: { 'room-msg': t<v.InferOutput<typeof RoomMsg>>() } },
})

export const handleSendRoomMsg = chat.on('send-room-msg', {
  input: SendRoomMsg,
  run(ctx, payload) {
    ctx.channel.broadcast('room-msg', {
      text: payload.text,
      from: ctx.meta.username,
    })
  },
})
```

::note
`readReceipts()` requires `inbox()` in that same channel's `capabilities` (and inbox's own host requirement, `sequence({ persist: true })`). It has nowhere to store the read cursor without them, so the build fails if it stands alone. See [Requirements](/server/capabilities/read-receipts#requirements) on the capability page.
::

The client advances the read cursor with `markAsRead()`, which sends a `__read__` frame:

```json
{
  "event": "__read__",
  "payload": { "readThrough": 7 },
  "__wskit": { "channel": "chat" }
}
```

Like a received ack, this advances a cursor and fans out — this time a `__read__` carrying `readThrough`:

```json
{
  "event": "__read__",
  "payload": { "userId": "bob", "readThrough": 7 },
  "__wskit": { "channel": "chat" }
}
```

On the server, `ctx.channel.readReceipts.readersOf(seq)` returns the user ids whose read cursor has reached `seq`.

::tip
**Read implies received.** A `__read__` also settles that member's inbox rows up to the read mark — you cannot have read a message you never received. So marking read advances both cursors, and the rows settle either way. If the received mark actually moved (rare — the client auto-acks received first) and the channel has `broadcastReceipts` on, the server also fans out a `__received__` so the received column stays honest.
::

## Querying a cursor from a handler

Both cursor surfaces are already on `ctx.channel` as its `inbox` and `readReceipts` properties — typed and guaranteed present here since `chat` lists both `inbox()` and `readReceipts()` in its own `capabilities`. Here one handler answers either cursor and sends the authoritative server view back as its own event, independent of the live fan-out:

```typescript [ask-cursor.ts]
const AskCursor = v.object({
  kind: v.picklist(['received', 'read']),
  seq: v.number(),
})

export const handleAskCursor = chat.on('ask-cursor', {
  input: AskCursor,
  run(ctx, input) {
    const userIds =
      input.kind === 'read'
        ? ctx.channel.readReceipts.readersOf(input.seq)
        : ctx.channel.inbox.receiversOf(input.seq)
    ctx.send('cursor-answer', { kind: input.kind, seq: input.seq, userIds })
  },
})
```

This "ask-cursor → cursor-answer" shape is the authoritative pattern: the live tick is best-effort UI sugar, but `receiversOf` / `readersOf` read the stored cursors directly, so this answer is always current.

::note
`ctx.channel.readReceipts` (like `ctx.channel.inbox`) exists in `chat.on(...)` handlers and in the `subscribe`, `unsubscribe`, and `sessionEnd` lifecycle hooks — each of those is written after the `base.channel(...)` object is finished. It does **not** exist in `check`, `commit`, or `revalidate` — those three are written inside that same object, alongside the `capabilities` list, so TypeScript cannot yet work out what `capabilities` adds to `ctx.channel`. The runtime also leaves `readReceipts()` off handles returned by `ctx.channels.get(...)` during those three gates. See [Auth Gate](/server/channels/auth-gate).
::

## The client side

On the client, the [`inbox()`](/client/primitives/inbox) and [`readReceipts()`](/client/primitives/read-receipts) primitives each add **their own** surface to a channel handle whose contract has the matching flag — there is no combined store. A `chat` channel with `inbox: true` gets `receivers` / `onReceived` / `receiversOf`; adding `readReceipts: true` gets `readers` / `onRead` / `markAsRead` / `readersOf`.

```typescript [receipts-client.ts]
import {
  channels,
  client,
  connect,
  dedup,
  inbox,
  readReceipts,
  reconnection,
} from '@wskit/client'
import type { ReceiptsClient } from './socket-types'

const socket = client<ReceiptsClient>()(
  connect('wss://example.com/receipts'),
  channels(),
  inbox(),
  readReceipts(),
  dedup(),
  reconnection({ maxDelay: 400 }),
)

const chat = socket.channel('chat')

// Two live stores, one per owner — each a Map<userId, cursor>.
chat.receivers.subscribe(() => {
  for (const [userId, receivedThrough] of chat.receivers.get())
    render(userId, { received: receivedThrough })
})
chat.readers.subscribe(() => {
  for (const [userId, readThrough] of chat.readers.get())
    render(userId, { read: readThrough })
})

// Advance the read cursor for everything received so far.
chat.markAsRead()

// Ask the server, authoritatively, who reached seq 1 on each cursor.
const receivedIdentities = await chat.receiversOf(1)
const readIdentities = await chat.readersOf(1)
```

`chat.receivers` and `chat.readers` are readable stores, each a `Map<userId, number>` keyed by member, dropping anyone still at `0`. `receivers` updates from `__received__` ticks (only when the server channel has `broadcastReceipts` on), `readers` from `__read__` ticks. `markAsRead()` with no argument marks everything received so far. `receiversOf(seq)` and `readersOf(seq)` round-trip a query to the server (below) and resolve to a list of user ids. The [client inbox primitive](/client/primitives/inbox#the-received-surface) and [read receipts primitive](/client/primitives/read-receipts) cover them in full.

## The live fan-out and its member cap

The received / read tick is a live convenience: every time a member's cursor moves, every other member hears about it. (The received tick only fires when the channel opts in with `broadcastReceipts`; the read tick comes with `readReceipts()`.) That is fine for small channels, but fanning out on every cursor move is **O(members²)** — with N members, one message can produce N acks, each fanned to N members. On a large channel that is a lot of frames.

So the live tick is capped by `maxReceiptAudience` (default 256). Both `inbox()` and `readReceipts()` accept it per channel:

```typescript [max-receipt-audience.ts]
const big = base.channel('big-room', {
  capabilities: [
    inbox({ broadcastReceipts: true, maxReceiptAudience: 100 }),
    readReceipts({ maxReceiptAudience: 100 }),
  ],
  outgoing: { emits: { 'room-msg': t<v.InferOutput<typeof RoomMsg>>() } },
})
```

While the channel has **at most** `maxReceiptAudience` members, cursors fan out live as `__received__` / `__read__` ticks. Above that cap, the live tick stops — but the cursor is **still tracked**. You lose only the real-time push; you can still ask who received or read a message with `receiversOf` / `readersOf` (server) or `chat.receiversOf(seq)` / `chat.readersOf(seq)` (client). For a big channel, that query-on-demand path is the one to use.

## The query round-trip: `__receivedQuery__` and `__readQuery__`

`receiversOf` travels over `__receivedQuery__`, `readersOf` over `__readQuery__` — each paired by a `correlationId`, the same request/response shape as `__error__`. The request names a `seq`; the reply echoes the `correlationId` and lists the user ids. Each query is owned by its capability, so `receiversOf` works with `inbox()` alone — it does not need `readReceipts()` present.

```json
// client -> server
{ "event": "__receivedQuery__", "payload": { "seq": 7 }, "__wskit": { "channel": "chat", "correlationId": "q-1" } }

// server -> client
{ "event": "__receivedQuery__", "payload": { "userIds": ["bob"] }, "__wskit": { "channel": "chat", "correlationId": "q-1" } }
```

::warning
**Only a member may query.** A connection that is not a live member of the channel gets its `__receivedQuery__` / `__readQuery__` **dropped silently** — no reply frame at all. The same goes for a non-member's `__read__`: it fans out nothing. Membership gates the whole receipts surface, so a stranger cannot probe who read what.
::
