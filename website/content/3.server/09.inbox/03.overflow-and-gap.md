Inbox holds a durable row per member until that member acknowledges it. A member who never comes back would otherwise pile up rows forever. `retention` bounds that queue — and when a bound is hit while a member is behind, the oldest held row is evicted. This page is about that eviction, the **overflow watermark** it raises, and the `__gap__` frame that tells a reconnecting client "you missed some, and the earliest are gone."

## Bounding held rows with `retention`

`retention` caps how many rows inbox keeps **per member**. It takes two optional bounds:

| Field         | What it does                                                                                                           |
| ------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `maxMessages` | Keep at most this many undelivered rows per member. An `(N+1)`th broadcast while a member is behind evicts the oldest. |
| `maxAgeMs`    | Age rows out by time — a row older than this is dropped regardless of acknowledgement.                                 |

```typescript [retention.ts]
const chat = base.channel('chat', {
  capabilities: [
    inbox({
      retention: { maxMessages: 500, maxAgeMs: 86_400_000 },
    }),
  ],
  outgoing: { emits: { 'room-msg': t<v.InferOutput<typeof RoomMsg>>() } },
})
```

Here each member keeps at most 500 undelivered rows, and any row older than a day is aged out. Without `retention`, a member's queue is unbounded — fine for channels where members reconnect promptly, dangerous for ones where a member might vanish for a long time.

## What overflow means

When a member is behind — offline, or just not acknowledging — and a new broadcast pushes their queue past `maxMessages`, the **oldest held row is evicted** to make room. That row is gone; the member will never receive it. To record that a hole opened, the engine raises that member's **overflow watermark** to the sequence of the evicted row.

The smallest example makes it concrete: `maxMessages: 1` keeps exactly one undelivered row per member.

```typescript [inbox-gap-server.ts]
import { define, t } from '@wskit/server'
import { channels } from '@wskit/server/channels'
import { dedup } from '@wskit/server/dedup'
import { inbox } from '@wskit/server/inbox'
import { sequence } from '@wskit/server/sequence'
import * as v from 'valibot'
import { requireUsername } from './upgrade'

const RoomMsg = v.object({ text: v.string(), from: v.string() })
const SendRoomMsg = v.object({ text: v.string() })

const base = define({
  env: t<Env>(),
  upgrade: (request) => requireUsername(request),
  capabilities: [channels(), sequence({ persist: true }), dedup()],
})

const chat = base.channel('chat', {
  capabilities: [inbox({ retention: { maxMessages: 1 } })],
  outgoing: { emits: { 'room-msg': t<v.InferOutput<typeof RoomMsg>>() } },
})

export const handleSendRoomMsg = chat.on('send-room-msg', {
  input: SendRoomMsg,
  run(ctx, payload) {
    ctx.channel.broadcast('room-msg', {
      text: payload.text,
      from: ctx.meta.username,
    })
  },
})
```

Now walk the overflow:

::steps{level="3"}

### Both members subscribe

Alice and Bob both subscribe to `chat`, so both are durable members.

### Alice's socket drops

Alice goes offline. Her one-row queue is empty and her membership stays.

### First broadcast fills the queue

Bob broadcasts `m1`. Alice's queue holds one row: `m1`.

### Second broadcast overflows

Bob broadcasts `m2`. Alice is already at her one-row cap, so `m1` is **evicted** and her overflow watermark is raised to `m1`'s sequence. Her queue now holds `m2`.

::

Alice has permanently missed `m1`. The remaining question is how she finds out.

## The `__gap__` frame on the drain

When Alice reconnects, the [reconnect drain](/server/inbox/delivery#the-reconnect-drain) runs. Because her overflow watermark is set, the engine emits a `__gap__` frame for the channel **before** the surviving rows:

```json
// server -> client, before the surviving rows
{ "event": "__gap__", "__wskit": { "channel": "chat" } }

// then the surviving row
{ "event": "room-msg", "payload": { "text": "m2", "from": "bob" }, "__wskit": { "channel": "chat", "seq": 2 } }
```

The order matters: the gap comes first so a client can react to the hole before rendering the messages that survived it. This is the honest version of guaranteed delivery — inbox still guarantees you get everything it _held_, and tells you plainly about anything it had to drop.

## Only a client running `replay()` sees the gap

Here is the important detail. The `__gap__` frame is **owned by the [`replay()` client primitive](/client/primitives/replay)** — replay is what carries `__gap__` and the `onGap` callback. An **inbox-only client** — one whose stack has `inbox()` but not `replay()` — has nothing to consume the frame, so it **silently drops it**. Delivery still works; the member just does not learn about the hole.

So to react to overflow gaps, add `replay()` to the client stack. It slots in alongside inbox:

```typescript [gap-client.ts]
import {
  channels,
  client,
  connect,
  dedup,
  inbox,
  reconnection,
  replay,
} from '@wskit/client'
import type { InboxGapClient } from './socket-types'

const socket = client<InboxGapClient>()(
  connect('wss://example.com/inbox-gap'),
  channels(),
  inbox(),
  dedup(),
  replay(),
  reconnection({ maxDelay: 400 }),
)

const chat = socket.channel('chat')

chat.onGap((info) => {
  // Everything at or below info.missedThrough on this channel is gone —
  // fall back to a full reload or a server-side history fetch.
  reloadChannelHistory(chat, info.missedThrough)
})
```

An inbox overflow is a **channel-scoped** gap, so it lands on `socket.channel(...).onGap(...)`, not the top-level `socket.onGap(...)`. The callback receives a `GapInfo`:

- `missedThrough` — the highest sequence such that everything at or below it is gone. That is the evicted row's sequence.
- `channel` / `channelFamily` — set on a channel gap, absent on a top-level one.

::warning
`channel.onGap` needs `replay()` in the client stack. Calling it without `replay()` throws `[wskit] channel.onGap needs the replay() primitive — add replay() to client().` The `onGap` surface is installed by replay; inbox alone does not provide it.
::

::note
This is the same `onGap` you use for [replay's own catch-up gaps](/server/replay/overview) — when replay could not fully catch a channel up because retention had already evicted messages the client had not seen. Inbox overflow and replay eviction are two sources of the same signal, and a single `onGap` handler covers both.
::

## Choosing your bounds

`retention` trades memory for how far a member can fall behind without losing anything:

- **No `retention`** — no member ever loses a message, but a vanished member's queue grows without limit. Good when members reconnect promptly and you trust them to return.
- **`maxMessages` / `maxAgeMs` set** — bounded memory, but a member far enough behind loses the oldest messages and gets a `__gap__` on return. Good for busy channels where an absent member catching up on days of backlog is neither useful nor affordable.

If you set bounds, pair the client with `replay()` so a member who overflows is told, rather than silently missing messages they will never see delivered.
