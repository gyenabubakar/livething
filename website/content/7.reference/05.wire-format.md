A LiveThing text frame is a JSON array with exactly three items, and a [binary frame](#binary-frames) carries the same array in front of raw bytes:

```json
[event, payload, metadata]
```

- `event` is a string.
- `payload` is an object or `null` when there is no payload.
- `metadata` is a nested object or `null`; it is never omitted.

Metadata uses these groups:

```json
{
  "exchange": { "id": "request-42", "source": "client" },
  "channel": { "name": "room:general", "family": "rooms" },
  "delivery": { "id": "message-7", "seq": 12 },
  "stream": {
    "id": "scout-1",
    "event": "ask-scout",
    "durability": "persistent",
    "seq": 3,
    "nudgeId": "nudge-1",
    "terminated": false
  },
  "upload": { "id": "upload-1", "seq": 2, "size": 600000 }
}
```

Use `exchange.id` for request matching, `channel` for channel routing, `delivery` for message IDs and delivery cursors, `stream` for stream state, and `upload` for the frames of one [upload](/server/binary/uploads): `id` (up to 128 characters), the piece number `seq`, and the file's `size` at the start. The [reserved events](/learn/wire-protocol) have their own examples.

## Binary frames

With [`binary()`](/server/binary/overview) listed, the server takes and sends binary WebSocket messages. One binary message holds one LiveThing message:

```text
[ magic:          4 bytes = 0x6C 0x74 0x62 0x66 ("ltbf") ]
[ version:        1 byte  = 0x01                         ]
[ envelopeLength: 4 bytes, unsigned, big-endian          ]
[ envelope:       envelopeLength bytes, UTF-8 JSON       ]
[ bytes:          all the remaining bytes                ]
```

- The **envelope** is a normal three-item frame: `[event, info, metadata]`. The info is in the payload's place, and it follows the same rules as a payload: an object, or `null`. The metadata groups are the same as above.
- The envelope is at most 64 KiB (65,536 bytes).
- The **bytes** are the application's own data. LiveThing never reads them. There can be zero bytes.

A binary `screen-frame` event that the server sends to a room looks like this:

```text
ltbf | 1 | length | ["screen-frame",{"from":"u_amara"},{"channel":{"name":"room:general","family":"rooms"},"delivery":{"id":"m-8","seq":3}}] | picture bytes
```

The server uses binary messages only for data: events, the reply to a binary request, the chunks of a binary stream, binary server requests with their answers, and the start and the pieces of an upload. Each one carries the metadata of its JSON version: `exchange` for a request and its reply, and `stream` (with `id`, `durability` and `seq`) for a chunk. Every framework event (`__subscribe__`, `__error__`, `__subscribeOk__`, `__streamOk__`, `__streamEnd__`, `__streamCancel__`, `__nudgeOk__`, `__uploadAck__`, `__uploadEnd__`, `__uploadCancel__`, `__uploadDone__` and the rest) and every nudge is a text frame, in both directions. An upload's start is `[event, input, { upload: { id, size? } }]` with no bytes, and each piece is `[event, null, { upload: { id, seq } }]` with its bytes. The server [checks each binary message](/learn/wire-protocol#binary-frames) before it reaches a handler.
