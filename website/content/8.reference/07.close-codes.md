`@livething/core` exports the shared close-code names:

```typescript
import { CloseCodes } from '@livething/core'
```

`CloseCodes` gives both sides the same names for close reasons. It deliberately does not export a validator: server and browser client close operations have different rules. The server accepts protocol-valid codes (`1000`–`1014` except `1004`, `1005`, and `1006`, plus `3000`–`4999`). Browser client code may send only `1000` or `3000`–`4999` through `socket.disconnect(...)`.

| Code   | Export                        | Meaning                                                                             |
| ------ | ----------------------------- | ----------------------------------------------------------------------------------- |
| `1000` | `CloseCodes.NORMAL`           | Normal closure                                                                      |
| `1001` | `CloseCodes.GOING_AWAY`       | Server restart, deploy, or shutdown                                                 |
| `1002` | `CloseCodes.PROTOCOL_ERROR`   | Protocol violation                                                                  |
| `1003` | `CloseCodes.UNSUPPORTED_DATA` | Unsupported frame data                                                              |
| `1009` | `CloseCodes.MESSAGE_TOO_BIG`  | A message over the server's message limit                                           |
| `1011` | `CloseCodes.INTERNAL_ERROR`   | Server internal failure; LiveThing's server-side fallback for an invalid close code |
| `1013` | `CloseCodes.TRY_AGAIN_LATER`  | The client read too slowly; reconnect. A very slow client may see `1006` instead    |
| `4001` | `CloseCodes.AUTH_EXPIRED`     | Refresh credentials, then reconnect                                                 |
| `4002` | `CloseCodes.AUTH_INVALID`     | Do not reconnect with the same credentials                                          |
| `4003` | `CloseCodes.DUPLICATE`        | Another connection replaced this one                                                |
| `4004` | `CloseCodes.IDLE`             | Keepalive timed out                                                                 |
| `4005` | `CloseCodes.RATE_LIMITED`     | Back off before reconnecting                                                        |
| `4009` | `CloseCodes.BANNED`           | Do not reconnect                                                                    |
| `4010` | `CloseCodes.CAPACITY`         | Retry with backoff                                                                  |

Server-sent events have no close frame, so the server sends the code and reason in a last `__close__` frame. When the stream request gets an HTTP error from LiveThing, the client turns it into a close code: `401` is `4001` (`AUTH_EXPIRED`), `429` is `4005` (`RATE_LIMITED`), and `403` and the other `4xx` statuses are `4002` (`AUTH_INVALID`). A `404`, `405`, `426`, a `5xx`, and an error from a proxy are `1006`. See [Codes for a server-sent events stream](/core/close-codes#codes-for-a-server-sent-events-stream).

Use a named code when possible. The [shared list of close codes](/core/close-codes) also gives the fallback behavior, the upgrade rejection rules and the reconnection advice. LiveThing validates the close operation in the package that performs it, so application code normally does not need a validator.
