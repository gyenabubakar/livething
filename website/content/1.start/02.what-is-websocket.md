LiveThing is a typed WebSocket framework, so it helps to know what a WebSocket actually is. This page is the quick grounding in the protocol underneath it — how it differs from HTTP, how it compares to the other realtime options, and why a raw one isn't enough on its own. Already comfortable with WebSockets? Skip straight to [Why LiveThing](/start/why-livething).

## HTTP asks, WebSocket converses

The web runs on HTTP, and HTTP is a one-shot exchange: the client sends a request, the server sends a response, and the exchange is over. The server can't speak unless spoken to. To fake "live" updates over HTTP you have to _poll_ — ask again and again, "anything new yet?" — which is wasteful and always a little behind.

A **WebSocket** is the opposite shape. It's a single connection that stays open, and once it's open **either side can send a message at any time**, as many times as it likes, with almost no per-message overhead. That two-way, always-on channel is what makes real-time features — chat, live cursors, streaming tokens, presence — natural instead of a hack.

|                  | HTTP request                 | WebSocket                           |
| ---------------- | ---------------------------- | ----------------------------------- |
| Shape            | One request, one response    | One long-lived connection           |
| Who can send     | Client asks, server answers  | Both sides, any time                |
| Lifetime         | Closes after the response    | Stays open until either side closes |
| Per-message cost | Full headers every time      | A few bytes of framing              |
| Good for         | Fetching and submitting data | Live, push, back-and-forth          |

## How a connection opens

A WebSocket doesn't start as its own thing — it starts as an ordinary HTTP request that asks to **upgrade**. The browser sends a normal `GET` with a couple of special headers; if the server agrees, it replies `101 Switching Protocols`, and from that moment the same TCP connection is reused as a two-way WebSocket.

```text [client request]
GET /ws HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
```

```text [server response]
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
```

That handshake is the one moment the connection looks like a normal HTTP request — with a URL, headers, and cookies — so it's the natural place to **authenticate**. LiveThing gives you a hook right there (covered later under the upgrade gate).

::note
WebSocket URLs use their own schemes: `ws://` for plain and **`wss://`** for TLS-encrypted — the WebSocket equivalent of `http://` and `https://`. Use `wss://` in production, the same way you'd never ship plain `http://`.
::

## Messages, not a byte stream

Once the connection is open, the two sides exchange **messages**, not a raw stream of bytes. Each send is one discrete message — usually a string of JSON, sometimes binary. The protocol also has a few **control messages** the browser handles for you: `ping`/`pong` (a heartbeat to check the other end is still alive) and a `close` message that carries a numeric **close code** explaining why the connection ended.

That's the whole model: an open pipe, discrete messages each way, and a clean close at the end.

## The raw browser API

Every browser ships a `WebSocket` object. Here's the entire surface:

```typescript [raw-websocket.ts]
const ws = new WebSocket('wss://example.com/ws')

ws.addEventListener('open', () => {
  ws.send(JSON.stringify({ type: 'hello', name: 'gyen' }))
})

ws.addEventListener('message', (event) => {
  const data = JSON.parse(event.data) // event.data is a string — you parse it
  console.log('got', data)
})

ws.addEventListener('close', (event) => {
  console.log('closed', event.code, event.reason)
})

ws.addEventListener('error', () => {
  console.log('something went wrong')
})

// later
ws.close(1000, 'done')
```

That's it: open a socket, listen for four events, `send()` strings, and `close()`. It's a great primitive — and a low-level one.

## How WebSocket compares to the alternatives

WebSocket isn't the only way to do realtime on the web. It's worth knowing the menu, because the right tool depends on which way the data needs to flow.

- **Short polling** — the client asks "anything new?" on a timer. Dead simple and works everywhere, but it's wasteful (most requests come back empty) and laggy: the delay is however long your interval is.
- **Long polling** — the client makes a request and the server _holds it open_ until it has something, then answers; the client immediately asks again. Lower latency than short polling, but it's still a fresh request per message and a constant churn of connections. This is the fallback Socket.IO drops to when a WebSocket can't be established.
- **Server-Sent Events (SSE)** — a browser standard (the `EventSource` API) for a one-way server-to-client stream over a single long-lived HTTP response. It's simple, reconnects automatically, and rides on plain HTTP — but it only flows **one way** (the client can't send back over it) and carries **text only**. Ideal for notifications, feeds, and progress where the client just listens.
- **WebSocket** — one connection, **both directions**, text or binary, with tiny per-message overhead. The general-purpose choice for two-way realtime, and supported everywhere that matters.
- **WebTransport** — a newer API built on HTTP/3 (QUIC). Like WebSocket it's bidirectional, but it adds **unreliable datagrams** alongside reliable streams — useful for games and media where a dropped packet is better than a late one. It's the most likely successor, but it's still landing across browsers, so it isn't a safe default yet.
- **WebRTC data channels** — **peer-to-peer**, not client-to-server. Built on UDP for very low latency, optionally unreliable and unordered, aimed at video, voice, and P2P games. Powerful, but it needs a signalling step and STUN/TURN servers to connect peers, so it's a different shape of problem from "talk to my server."

| Approach            | Direction                | Best for                                      |
| ------------------- | ------------------------ | --------------------------------------------- |
| Short polling       | Client asks, repeatedly  | The simplest possible "is it done yet?"       |
| Long polling        | One way per held request | A realtime-ish feel with no WebSocket support |
| Server-Sent Events  | Server → client only     | Notifications, feeds, progress — listen-only  |
| **WebSocket**       | **Both ways**            | **General-purpose two-way realtime**          |
| WebTransport        | Both ways (+ datagrams)  | Games and media, once support is broad        |
| WebRTC data channel | Peer-to-peer             | Video, voice, and P2P games                   |

::note
A couple of names you'll hear are a layer _above_ this list, not competitors to it. **MQTT** is a publish/subscribe messaging protocol common in IoT — it often runs _over_ a WebSocket in the browser. **gRPC** offers streaming too, but its browser flavour (gRPC-Web) can't do full bidirectional streaming, so it's mostly used for service-to-service calls rather than browser realtime.
::

For a typical app that needs two-way communication with its server, WebSocket is the default: broad support, a simple model, and traffic in both directions. Reach for SSE when you only ever push _to_ the client, watch WebTransport for the future, and use WebRTC when the connection is genuinely peer-to-peer.

## What a raw WebSocket doesn't give you

Notice everything the snippet above _doesn't_ do. `event.data` is just a string, so there are **no types** — you `JSON.parse` and hope. If the connection drops (a sleeping laptop, a flaky network, a deploy), it stays dropped — there's **no reconnection**. There's no way to send a message and `await` a reply, no concept of **rooms**, no catching up on messages you missed while away, and no heartbeat tuned to notice a connection that died silently.

A raw WebSocket is the transport. Everything that makes it usable in a real app, you build yourself — and you build it untyped, on both ends, where the two sides can drift apart.

That gap is exactly what LiveThing fills.
