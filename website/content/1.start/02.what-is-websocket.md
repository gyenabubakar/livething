LiveThing is a typed WebSocket framework, so it helps to know what a WebSocket is. This page is a short introduction to the protocol that LiveThing uses. It covers how a WebSocket differs from HTTP, how it compares with other realtime options, and why a raw WebSocket is not enough on its own. If you already know WebSockets well, go to [Why LiveThing](/start/why-livething).

## HTTP asks, WebSocket talks both ways

The web runs on HTTP. In HTTP, each exchange happens once: the client sends a request, the server sends a response, and the exchange ends. The server can only send data as an answer to a request. To show "live" updates over HTTP, the client has to _poll_. Polling means the client asks again and again: "Is there anything new?" This wastes requests, and the updates always arrive a little late.

A **WebSocket** works in a different way. It is a single connection that stays open. While it is open, **either side can send a message at any time**, as many times as it wants. Each message adds only a few bytes of extra data. This two-way connection that stays open makes realtime features easy to build: chat, live cursors, AI answers that arrive word by word, and presence (showing who is online).

|                  | HTTP request                 | WebSocket                           |
| ---------------- | ---------------------------- | ----------------------------------- |
| Shape            | One request, one response    | One long-lived connection           |
| Who can send     | Client asks, server answers  | Both sides, any time                |
| Lifetime         | Closes after the response    | Stays open until either side closes |
| Per-message cost | Full headers every time      | A few bytes of framing              |
| Good for         | Fetching and submitting data | Live updates, push, back-and-forth  |

_Framing_ is the small header the protocol adds to each message to mark where the message starts and ends.

## How a connection opens

A WebSocket starts as an ordinary HTTP request that asks to **upgrade**. This first exchange is called the _handshake_. The browser sends a normal `GET` request with a few special headers. If the server agrees, it replies with `101 Switching Protocols`. From then on, the same TCP connection (the network connection that carries the HTTP request) is used as a two-way WebSocket.

```text [client request]
GET /huddle HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
```

```text [server response]
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
```

The handshake is the only moment when the connection looks like a normal HTTP request, with a URL, headers, and cookies. This makes it the right place to **authenticate** the user (check who they are). LiveThing gives you a function that runs at this moment, called the [upgrade gate](/server/server/upgrade).

::note
WebSocket URLs have their own schemes. `ws://` is the plain version and **`wss://`** is the version encrypted with TLS (the same encryption that `https://` uses). They match `http://` and `https://`. Use `wss://` in production, the same way you use `https://` for a website.
::

## Messages, not a byte stream

After the connection opens, the two sides exchange **messages**, not a continuous stream of bytes. Each send is one separate message. It is usually a string of JSON (a text format for data), and sometimes binary data. LiveThing uses text messages only, and it rejects binary frames. The protocol also has a few **control messages** that the browser handles for you:

- `ping` and `pong`: a heartbeat. One side sends `ping`, and the other side answers `pong` to show it is still there.
- `close`: the last message. It carries a number called a **close code** that says why the connection ended.

So the model is simple: one open connection, separate messages in both directions, and a clean close at the end.

## The raw browser API

Every browser has a built-in `WebSocket` object. This is the whole API:

```typescript [client/raw-huddle-socket.ts]
const ws = new WebSocket('wss://example.com/huddle')

ws.addEventListener('open', () => {
  ws.send(JSON.stringify({ type: 'hello', name: 'Ada' }))
})

ws.addEventListener('message', (event) => {
  const data = JSON.parse(event.data) // event.data is a string. You parse it yourself.
  console.log('got', data)
})

ws.addEventListener('close', (event) => {
  console.log('closed', event.code, event.reason)
})

ws.addEventListener('error', () => {
  console.log('something went wrong')
})

// later
ws.close(1000, 'done')
```

You open a socket, listen for four events, `send()` strings, and call `close()`. It is a useful building block, but a low-level one.

## How WebSocket compares to the alternatives

WebSocket is not the only way to build realtime features on the web. The right choice depends on which direction the data needs to travel. _Latency_ below means the delay between an event and the moment the other side sees it.

- **Short polling.** The client asks "Is there anything new?" on a timer. It is very simple and works everywhere. But it wastes requests, because most answers are empty. It is also slow: the delay can be as long as the timer interval.
- **Long polling.** The client sends a request, and the server _holds it open_ until it has something to send. Then the server answers, and the client sends a new request right away. Latency is lower than short polling. But every message still needs a new request, so connections open and close all the time. Socket.IO (a popular realtime library) uses long polling when it cannot open a WebSocket.
- **Server-Sent Events (SSE).** A browser standard (the `EventSource` API) for a one-way stream from the server to the client, sent over one long-lived HTTP response. It is simple, it reconnects on its own, and it uses plain HTTP. But data only flows **one way**: the client cannot send data back over it. It also carries **text only**. It fits notifications, feeds, and progress updates, where the client only listens.
- **WebSocket.** One connection, **both directions**, text or binary, with very little extra data per message. It is the general choice for two-way realtime, and every modern browser and server runtime supports it.
- **WebTransport.** A newer API built on HTTP/3 and QUIC (a newer network protocol that HTTP/3 runs on). Like WebSocket, it sends data both ways. It also adds **unreliable datagrams**: small messages that can be lost and are not sent again. Games and media use them, because for them a lost packet is better than a late one. All major browsers support it only since 2026, and many servers, hosting platforms, and older browsers do not support it yet.
- **WebRTC data channels.** These connect two browsers directly (**peer-to-peer**, or P2P), not a browser and a server. They run on UDP (a network protocol that does not wait for lost data), so latency is very low. Messages can be unreliable and arrive out of order if you choose. They are made for video, voice, and P2P games. To connect two peers, you need a signalling step (a way to exchange connection details first) and STUN/TURN servers (servers that help peers find each other and relay traffic when a direct link fails). This is a different problem from "talk to my server."

| Approach            | Direction                | Best for                                         |
| ------------------- | ------------------------ | ------------------------------------------------ |
| Short polling       | Client asks, repeatedly  | The simplest "is it done yet?" check             |
| Long polling        | One way per held request | Near-realtime updates without WebSocket support  |
| Server-Sent Events  | Server → client only     | Notifications, feeds, and progress (listen-only) |
| **WebSocket**       | **Both ways**            | **General-purpose two-way realtime**             |
| WebTransport        | Both ways (+ datagrams)  | Games and media on newer browsers and servers    |
| WebRTC data channel | Peer-to-peer             | Video, voice, and P2P games                      |

::note
You may also hear two other names. They work at a layer _above_ this list and do not replace it. **MQTT** is a publish/subscribe messaging protocol (senders publish to a topic, and everyone subscribed to the topic receives it). It is common in IoT (internet-connected devices), and in the browser it often runs _over_ a WebSocket. **gRPC** also supports streaming. But its browser version (gRPC-Web) cannot stream in both directions at once, so gRPC is mostly used between servers, not for browser realtime.
::

For a typical app that needs two-way communication with its server, WebSocket is the default choice. It has broad support, a simple model, and traffic in both directions. Use SSE when you only send data _to_ the client. Consider WebTransport when you need datagrams and your platforms support it. Use WebRTC when the connection is truly peer-to-peer.

## What a raw WebSocket doesn't give you

Look at what the example above does _not_ do:

- **No types.** `event.data` is only a string. You call `JSON.parse` and hope the data has the shape you expect.
- **No reconnection.** If the connection drops (a laptop goes to sleep, the network fails, or the server restarts during a deploy), it stays closed.
- **No request and reply.** You cannot send a message and `await` an answer.
- **No rooms.** There is no built-in way to send a message to a group of users.
- **No catch-up.** Messages sent while a client was offline are lost to that client.
- **No dead-connection check.** Nothing notices a connection that stopped working without closing.

A raw WebSocket only carries messages. You must build everything else that a real app needs yourself. You also build it without types, on both the client and the server, so the two sides can stop matching without any error.

LiveThing provides these missing parts.
