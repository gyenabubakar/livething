This is the smallest real LiveThing app. It has four parts: a server that sends one event and handles one incoming event, an adapter entry, the inferred contract type, and a client that listens and sends. There are no channels, no auth, and no streams. The page only shows how the contract goes from the server to the client.

This page runs the server on Node.js with [Express](https://expressjs.com), a popular web framework for Node.js. The server code is the same on every platform. Only the adapter entry changes.

::callout{icon="i-ph-package-duotone" to="/start/installation"}
First install `@livething/client`, `@livething/server`, `@livething/server-node`, `@livething/core`, `valibot`, and `express`. See [Installation](/start/installation).
::

::steps{level="3"}

### Create the server

The contract has two events:

- The server **emits** (sends) `message`. It goes from the server to the client.
- The server **handles** `send-message`. It goes from the client to the server.

The `emits({...})` capability lists the events the server can send, and turns on `ctx.send` and `ctx.broadcast` for them. `ctx` is the context object that every handler receives. Each value is a `t<Shape>()` type marker: it gives TypeScript the payload type, but it is not a runtime schema.

```typescript [chat.ts]
import { emits, server, t } from '@livething/server'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'

const base = server({
  capabilities: [
    emits({
      message: t<{ text: string; from: string }>(),
    }),
  ],
})

export const handleSendMessage = base.on('send-message', {
  input: v.object({ text: v.string(), from: v.string() }),
  run(ctx, input) {
    // Typed against the emits() declaration.
    // includeSelf also sends the event to the connection that sent the message.
    ctx.broadcast(
      'message',
      { text: input.text, from: input.from },
      { includeSelf: true },
    )
  },
})

export const definition = base.assemble({
  handlers: [handleSendMessage],
})

// This one type is the whole client contract.
export type ChatSocket = InferClient<typeof definition>
```

`base.on('send-message', ...)` returns an incoming handler. Its `input` schema checks the client's payload before `run` gets it. `ctx.broadcast` sends an event to every open connection except the caller. The `{ includeSelf: true }` option adds the caller too, so a single test client also sees its own message. `base.assemble(...)` collects the handlers you list into a `ServerDefinition`, which is the object the adapter runs.

### Add the adapter entry

The adapter connects your server definition to the platform. On Node.js, `setup()` gives you a `bind` function, and `bind(definition)` creates an **endpoint**: the object that accepts WebSocket connections for this definition.

Express handles normal HTTP routes, but WebSocket connections do not go through Express routes. A WebSocket connection starts as an HTTP request that asks to **upgrade** to a WebSocket. Node.js reports these requests with an `upgrade` event on the HTTP server. So you create the HTTP server yourself and send the upgrade requests for `/ws/chat` to the endpoint:

```typescript [index.ts]
import { createServer } from 'node:http'
import { setup } from '@livething/server-node'
import express from 'express'
import { definition } from './chat'

const app = express()
app.get('/health', (_request, response) => {
  response.json({ ok: true })
})

const httpServer = createServer(app)
const { bind, ready } = setup()
const chat = bind(definition, { sql: './data/chat.sqlite' })

httpServer.on('upgrade', (request, socket, head) => {
  const url = new URL(request.url ?? '/', 'http://localhost')

  if (url.pathname === '/ws/chat') {
    chat.upgrade(request, socket, head)
    return
  }

  socket.destroy()
})

await ready()
httpServer.listen(3000)
```

`ready()` waits until the endpoint is ready to accept connections. `socket.destroy()` closes any upgrade request for a path that LiveThing does not handle. The `sql` option is the SQLite file where LiveThing stores its data. See [Express](/server/adapters/node/express) for the other options.

### Connect from the client

Import the inferred `ChatSocket` type. You do not declare any event types again on the client. `client<ChatSocket>()` returns a factory function. You call it with your primitives (the client features you want). The only required primitive is `connect`, which sets the server URL.

```typescript [app.ts]
import { client, connect } from '@livething/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(
  connect('ws://localhost:3000/ws/chat'),
)

socket.connect()

// `data` has the type { text: string; from: string }, inferred from the server's emits()
socket.on('message', (data) => {
  console.log(`${data.from}: ${data.text}`)
})

// Checked against the input schema of the server's send-message handler
socket.send('send-message', { text: 'hello', from: 'amara' })
```

## Watch the types flow

The contract is mirrored between the two sides, so the words change:

- The server **emits** `message`. The client **receives** it with `socket.on('message', ...)`.
- The server **handles** `send-message`. The client **sends** it with `socket.send('send-message', ...)`.

Try it: in the server's `emits({...})`, rename `message` to `chat`. The client's `socket.on('message', ...)` is now a type error, because `InferClient` builds the contract again from the new server code. You did not change the client, and the compiler found the mismatch.
