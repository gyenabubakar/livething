LiveThing is a typed WebSocket framework. It comes as two packages, `@livething/server` and `@livething/client`, and both use **one shared contract**. You write the contract once on the server, and the client gets the same types automatically.

## Two packages, one contract

On the server, you declare what your app can send and receive. On the client, you don't declare any of it again. You import a single type, and the whole client API becomes typed.

The examples in these docs all come from the same small app, **Huddle**: a team chat app with rooms and an AI assistant called Scout. The link between the two sides is the `InferClient` type. On the server you write:

```typescript
import type { InferClient } from '@livething/server'

export const huddle = base.assemble({
  handlers: [
    /* ...handlers */
  ],
})
export type HuddleSocket = InferClient<typeof huddle>
```

Here `base` is the server base you create with `server(...)`. The [Quickstart](/start/quickstart) shows the full file.

On the client you use that type:

```typescript
import { client, connect } from '@livething/client'
import type { HuddleSocket } from '../server/huddle'

const socket = client<HuddleSocket>()(connect('wss://example.com/ws'))
socket.connect()

socket.on('message', (data) => {
  // data is fully typed. Its type comes from the server code.
})
```

The contract is **mirrored** between the two sides. What one side sends, the other side receives, so the names flip:

- The server's `emits` (events from the server to the client) become the client's `incoming` events.
- The server's `base.on` handlers, listed in `base.assemble(...)`, become the client's `outgoing` events.

`incoming` and `outgoing` always describe the view of the side that holds the type. Requests, server-to-client requests, streams, channels, and errors are also part of the client type. Inside each channel, the events flip in the same way.

## Opt-in features

LiveThing includes very little by default. You add each feature yourself:

- **Server capabilities**: you list them in `server({ capabilities: [...] })`. Most capabilities are imported from their own subpath, for example `channels()` from `@livething/server/channels`. A few basic ones, such as `emits()`, come from `@livething/server`. When you list a capability, its code goes into your bundle. When you leave it out, its code is not in the bundle.
- **Client primitives**: you pass them to `client()`. For example, `reconnection()` reconnects automatically, `channels()` adds rooms, and `keepalive()` sends pings to check that the connection is still alive. If you don't pass a primitive, its methods don't exist on the socket.

This is why the minimal client is about **5.24 KB** (minified and gzipped). The build ships one file per module. Your bundler removes the modules you don't import. This step is called tree-shaking.

## Where it runs

The server runs on many platforms. Each platform has its own **adapter** package, for example `@livething/server-cloudflare` for Cloudflare Durable Objects (a Cloudflare service that runs small stateful servers). Your server code stays the same on every platform. Only the small adapter entry file changes.

The client works in any environment that has a `WebSocket`: browsers, React Native, Node.js, Bun, Deno, and Cloudflare Workers.

## What type safety gives you

The client types come from the server code. You never copy them by hand, so the two sides always match:

- Calling `socket.on()` with an event the server doesn't emit is a compile error.
- Sending a payload with the wrong shape is a compile error.
- When you rename an event on the server, TypeScript shows an error at every client call that still uses the old name.
- Autocomplete works for every event name and payload field, on both sides.

You declare your events once, and the compiler checks that both sides agree.
