A raw WebSocket is a great primitive and a poor foundation. The moment you ship one to real users, you start rebuilding the same pile of glue code — and none of it is typed.

## The problem with hand-rolling

The browser gives you `new WebSocket(url)`, `send()`, and four events. Everything else is yours to build:

- **Reconnection.** Sockets drop — deploys, network blips, sleeping laptops. You need backoff, jitter, and a way to not stampede the server when 10,000 clients reconnect at once.
- **Keepalive.** Proxies kill idle connections. You need pings, pong tracking, and a way to notice a "half-open" socket that looks alive but isn't.
- **Request/response.** WebSockets are fire-and-forget. Anything that needs an answer means inventing correlation IDs and a pending-promise map.
- **Rooms.** Group messaging means tracking who's in what, enforcing auth on entry, and scoping broadcasts.
- **Catch-up after a drop.** Did the client miss messages while offline? Now you need sequence numbers and replay.
- **Types.** None of the above is typed. Event names are strings. Payloads are `any`. The server and client drift, and you find out in production.

You end up writing a small framework badly, inside your app, with no type safety.

## What WSKit gives you

WSKit is that framework, done once and typed end to end. Everything is **opt-in** — you add only what you need:

- **A typed contract** inferred from the server, shared with the client. No drift, full autocomplete.
- **Reconnection** with exponential backoff and jitter (`reconnection()`).
- **Keepalive** with pings and missed-pong detection (`keepalive()`).
- **Request/response** over the socket, both client → server and server → client (`clientRequests()` / `serverRequests()`).
- **Channels** — server-managed rooms with auth on entry, membership tracking, and scoped broadcasts (`channels()`).
- **Streaming** for progressive data like LLM tokens, including durable streams that survive a disconnect (`stream()`).
- **Replay** to catch up on missed messages after reconnecting (`replay()`).
- **Deduplication**, **message buffering**, **connection quality**, and more — each its own primitive.

Because everything is opt-in, you pay only for what you import — on both the client and the server.

## Bundle size

WSKit ships one module per feature and marks every package side-effect free, so your bundler drops anything you don't use.

- **Client.** A minimal client — a typed `on`/`send` socket — is about **4.42 KB gzipped**. Pull in every primitive and it reaches about **18 KB**. Reconnection, channels, and streams cost only if you import them.
- **Server.** The engine sets a floor of about **28 KB gzipped** — connection handling, routing, and storage plumbing that every adapter ships. Each capability you list adds to it: a few hundred bytes for `dedup` or `keepalive`, a few kilobytes for `channels`, `clientRequests`, or `serverRequests`, up to about **10 KB** for a durable stream.

The server already bundles [valibot](https://valibot.dev) — it validates the wire protocol with it, so the validator core is part of that floor. Writing your handler schemas in valibot then adds little on top, since they share the same code. WSKit accepts any [Standard Schema](https://standardschema.dev) validator, but reaching for a second one means shipping its code alongside valibot's.

## How it compares

WSKit is not magic and it doesn't try to be everything.

### Versus a raw WebSocket

If your app sends a couple of fire-and-forget messages and never reconnects, a raw WebSocket is fine — WSKit would be overkill. WSKit earns its place once you need reconnection, typing, requests, rooms, or catch-up. The lighter your needs, the smaller WSKit stays, but a raw socket is still the simpler choice at the very bottom end.

### Versus Socket.IO

Socket.IO's headline feature is **transport fallback** — when a WebSocket can't be established, it drops down to HTTP long-polling. To support that, it ships a connection layer, its own framing, and the polling machinery on both ends.

**If you target WebSocket-capable clients and don't need that fallback, WSKit is the better fit.** Every modern browser, React Native, and server runtime speaks WebSocket, so for most apps the fallback buys nothing — and skipping it is exactly why WSKit stays small, typed, and predictable. You give up one thing and gain several:

- **The trade:** no fallback transports. Socket.IO falls back to HTTP long-polling when WebSockets aren't available; WSKit **requires** WebSocket. On any current target that's a non-issue.
- **Typed end to end.** Socket.IO event names are strings and payloads are untyped. WSKit infers one contract from the server, so every event and payload is checked at compile time.
- **Channels do more than rooms.** Over plain Socket.IO rooms you also get mandatory auth on entry, membership tracking, and scoped request-response and streaming — all type-safe.
- **Bring your own server language.** Pair `@wskit/client` with `@wskit/server` for zero-config typing, or implement the WSKit wire protocol in any language.

If you genuinely need to reach environments where WebSocket can't connect at all, Socket.IO's fallback is the reason to choose it. Short of that, WSKit gives you a smaller, fully typed stack.
