This is the smallest real LiveThing app. It has four parts: a server that sends one event and handles one incoming event, an adapter entry, the inferred contract type, and a client that listens and sends. There are no channels and no streams, and sign-in is only the small check that tells the server who is connected. The example is the smallest slice of **Huddle**, the team chat app used across these docs: a person sets their status, and everyone sees it. The page only shows how the contract goes from the server to the client.

This page runs the server on Node.js with [Express](https://expressjs.com), a popular web framework for Node.js. The server code is the same on every platform. Only the adapter entry changes.

### Create the server

The contract has two events:

- The server **emits** (sends) `status-changed`. It goes from the server to the client.
- The server **handles** `set-status`. It goes from the client to the server.

The `emits({...})` capability lists the events the server can send, and turns on `ctx.send` and `ctx.broadcast` for them. `ctx` is the context object that every handler receives. Each value is a `t<Shape>()` type marker: it gives TypeScript the payload type, but it is not a runtime schema.

```typescript [server/huddle-definition.ts]
import { emits, server, t } from '@livething/server'
import { CloseCodes, RejectAuth } from '@livething/server/errors'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'
import { verifySession } from './auth'

const Status = v.picklist(['active', 'away', 'busy'])
type Status = v.InferOutput<typeof Status>

const base = server({
  async authenticate(request) {
    const token = request.headers
      .get('Authorization')
      ?.replace('Bearer ', '')
    const user = await verifySession(token)
    if (!user) {
      throw RejectAuth(CloseCodes.AUTH_INVALID, 'invalid session')
    }

    return {
      userId: user.id,
      meta: { userId: user.id, name: user.name, role: user.role },
    }
  },
  capabilities: [
    emits({
      'status-changed': t<{ userId: string; status: Status }>(),
    }),
  ],
})

export const handleSetStatus = base.on('set-status', {
  input: v.object({ status: Status }),
  run(ctx, input) {
    // Typed against the emits() declaration.
    // includeSelf also sends the event to the connection that sent the status.
    ctx.broadcast(
      'status-changed',
      { userId: ctx.user.id, status: input.status },
      { includeSelf: true },
    )
  },
})

export const huddle = base.assemble({
  handlers: [handleSetStatus],
})

// This one type is the whole client contract.
export type HuddleSocket = InferClient<typeof huddle>
```

The `authenticate` function runs once for each new connection. It checks the session token and returns who the user is. That is how `ctx.user.id` is known inside a handler. [Sign-in and access](/learn/identity-and-access) explains it.

`base.on('set-status', ...)` returns an incoming handler. Its `input` schema checks the client's payload before `run` gets it. `ctx.broadcast` sends an event to every open connection except the caller. The `{ includeSelf: true }` option adds the caller too, so a single test client also sees its own status change. `base.assemble(...)` collects the handlers you list into a `ServerDefinition`, which is the object the adapter runs.

### Add the adapter entry

The adapter connects your server definition to the platform. On Node.js, `setup()` gives you a `bind` function, and `bind(huddle)` creates an **endpoint**: the object that accepts WebSocket connections for this definition.

Express handles normal HTTP routes, but WebSocket connections do not go through Express routes. A WebSocket connection starts as an HTTP request that asks to **upgrade** to a WebSocket. Node.js reports these requests with an `upgrade` event on the HTTP server. So you create the HTTP server yourself and send the upgrade requests for `/huddle` to the endpoint:

```typescript [huddle-server.ts]
import { createServer } from 'node:http'
import { setup } from '@livething/server-node'
import express from 'express'
import { huddle } from './server/huddle-definition'

const app = express()
app.get('/health', (_request, response) => {
  response.json({ ok: true })
})

const httpServer = createServer(app)
const { bind, ready } = setup()
const huddleEndpoint = bind(huddle, { sql: './data/huddle.sqlite' })

httpServer.on('upgrade', (request, socket, head) => {
  const url = new URL(request.url ?? '/', 'http://localhost')

  if (url.pathname === '/huddle') {
    huddleEndpoint.upgrade(request, socket, head)
    return
  }

  socket.destroy()
})

await ready()
httpServer.listen(3000)
```

`ready()` waits until the endpoint is ready to accept connections. `socket.destroy()` closes any upgrade request for a path that LiveThing does not handle. The `sql` option is the SQLite file where LiveThing stores its data. The [Node.js](/runtimes/adapters/node) page lists the other options.

### Connect from the client

Import the inferred `HuddleSocket` type. You do not declare any event types again on the client. `client<HuddleSocket>()` returns a factory function. You call it with your primitives. The only required primitive is `connect`, which sets the server URL.

```typescript [client/socket.ts]
import { client, connect } from '@livething/client'
import { getSessionToken } from './huddle-data'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('ws://localhost:3000/huddle', {
    token: () => getSessionToken(),
  }),
)

socket.connect()

// `data` has the type { userId: string; status: Status }, inferred from the server's emits()
socket.on('status-changed', (data) => {
  console.log(`${data.userId} is now ${data.status}`)
})

// Checked against the input schema of the server's set-status handler
socket.send('set-status', { status: 'away' })
```

::

`getSessionToken()` is Huddle's own function. It returns the signed-in user's session token, which the server's `authenticate` hook checks with `verifySession` in the [full sign-in flow](/learn/identity-and-access). The `token` function runs again on each connection attempt, so a reconnect sends a fresh token.

## Watch the types flow

The contract is mirrored between the two sides, so the words change:

- The server **emits** `status-changed`. The client **receives** it with `socket.on('status-changed', ...)`.
- The server **handles** `set-status`. The client **sends** it with `socket.send('set-status', ...)`.

Try it: in the server's `emits({...})`, rename `status-changed` to `presence`. The client's `socket.on('status-changed', ...)` is now a type error, because `InferClient` builds the contract again from the new server code. You did not change the client, and the compiler found the mismatch.
