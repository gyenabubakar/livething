[WebSocket](/start/what-is-websocket) is the best way to talk to a server in realtime. But some networks block it. A company proxy, an antivirus tool that reads your traffic, or a school network can stop the WebSocket handshake, and the app stops getting updates. Plain HTTP still works there, because without it nothing on the web would.

A **Split Stream** is LiveThing's answer. It is a way to get a live, two-way connection out of plain HTTP requests. You turn it on with LiveThing's [`http()` transport](/server/adapters/transports). The idea is new to most developers, so this page explains it from the start.

::split-stream-overview
::

## The idea in one sentence

**Split one two-way connection into two one-way streams: one that the server holds open to send down, and one that the browser holds open to send up.**

A WebSocket is one connection that carries messages both ways. HTTP cannot do that in one request. But HTTP can do each direction on its own, if a request or a response just stays open:

- **Down, from the server to the browser:** a `GET` request whose response never ends. The server writes each event into it as the event happens. This is a web standard called **server-sent events** (SSE), and every browser supports it.
- **Up, from the browser to the server:** a `POST` request whose **body** never ends. The browser writes each message into the body as you send it. The server reads the body as it arrives, and runs each message at once.

Put the two side by side and you have a full two-way connection, made of plain HTTP. Each half is a normal request, so proxies, firewalls and load balancers that allow HTTP allow it too.

## A request body that stays open

The down half is old and well known. The up half is the new part, so it is worth a closer look.

Usually a request body is ready before the request starts: a form, a JSON object, a file. The browser sends it, and the request is done. Newer browsers can also send a body that is not ready yet. You give `fetch` a `ReadableStream` as the body, and you write to the stream later, piece by piece. This is called a **streaming upload**. The request stays open for as long as the stream does.

You never write this code yourself. LiveThing does it for you. But here it is, so you can see that it is plain browser API:

```typescript [client/raw-huddle-upload.ts]
let writer: ReadableStreamDefaultController<Uint8Array> | undefined
const body = new ReadableStream<Uint8Array>({
  start(controller) {
    writer = controller
  },
})

// One POST. Its body is open, so the request stays open too.
void fetch('https://example.com/huddle', {
  method: 'POST',
  body,
  duplex: 'half',
} as RequestInit)

// Later, every time the user sends a message. This writes bare text:
// LiveThing puts a small header before each message, as you will see below.
writer?.enqueue(new TextEncoder().encode('{"text":"Standup in 5"}'))
```

A stream body needs `duplex: 'half'`: the browser sends the whole body before it reads the answer. Two rules come with a streaming upload:

- It works **only over HTTP/2 and newer**. Browsers refuse a streaming upload on HTTP/1.1.
- Today only **Chromium browsers** support it: Chrome, Edge, Brave, Opera, Arc and the others built on Chromium. The stable releases of Firefox and Safari do not stream a request body yet. Neither does any browser on iOS, because they all run on Safari's engine there. The client checks each browser when it connects, so a browser gets stream mode as soon as it supports it.

**Why LiveThing uses it already.** A streaming upload is part of the Fetch standard, not a Chrome-only feature. Most people use a Chromium browser, so on HTTP/2 most of them get stream mode today. For them, every message goes into one open request, so a message costs less than in batch mode, where each POST is a new request (see the [benchmarks](/start/benchmarks#over-the-fallback-transports)). When Firefox and Safari support streaming uploads, their users get stream mode too, with no change to your app. Until then, they use batch mode, which works everywhere.

These rules matter, because a Split Stream must work everywhere. The next sections show how LiveThing keeps it working when a browser or a network does not allow a streaming upload.

## How it compares

The usual answer when WebSocket is blocked is **long polling**. The client sends a request, and the server holds it until it has an event. Then the server answers, the request ends, and the client must open a new one at once. So every answer costs a new request, and one answer can carry several events that waited. A Split Stream sends one request down for the whole connection. Up, it sends in one of two ways, which the [next section](#a-fallback-inside-the-fallback) explains:

- **Batch mode:** short POSTs, each carrying every message that waited. It works everywhere.
- **Stream mode:** the one long POST from above, where the browser allows it.

Below, long polling and both modes run the same traffic at the same time. Pick one to watch how many requests it opens, and how many messages must wait. Each tab shows its total, so you can compare them. Use the buttons to send your own:

::split-stream-compare
::

Fewer requests means less work for the server. Each new request makes the server read headers, check the connection, and write an answer. It also means less delay, most of all behind a proxy, which adds its own time to every request.

## A fallback inside the fallback

Here are the two ways to send up, in more detail. LiveThing picks one by itself, for each connection:

- **Stream mode** is the one long POST from above. Each message goes into its body as you send it.
- **Batch mode** uses normal POST requests, one at a time. A POST is **in flight** from when the browser sends it until the server answers. While one POST is in flight, the messages you send wait. Then the next POST carries all of them together, up to 255 messages or the size limit of one POST (`maxPostBytes`), whichever comes first.

Every connection starts in batch mode, because batch mode works in every browser, on every network. When its first POST gets an answer, the client checks whether stream mode can work, and moves to it when it can:

::split-stream-decide
::

So the down half is always the same SSE stream, and only the up half changes. Your app does not see the difference: every message, request, channel and stream works the same in both modes.

## The probe

The browser checks are simple: does `fetch` support a streaming upload, and is the site on HTTP/2 or newer? The network check is harder. Some proxies read the **whole** body of a request before they pass it on. A long POST's body never ends, so such a proxy holds it forever. It does not fail the request, and the browser cannot see the problem.

So the client asks. It opens the long POST and writes a tiny **probe** into it. When the server reads the probe, it answers at once, on the SSE stream. If the answer comes back within 2 seconds, the path is clear, and the client moves to stream mode. If it does not, the client stays in batch mode. It also remembers the failed probe for that site for 10 minutes, so new connections in that time do not try again. Turn on the proxy below to see both cases:

::split-stream-probe
::

nginx is one proxy that holds request bodies by default. Add `proxy_request_buffering off;` to the location of your endpoint, and stream mode gets through. Without it, everything still works, in batch mode.

## Batch mode, up close

Batch mode is what most browsers use today, so it is built to be fast too. There is only ever **one POST in flight**. The messages you send while it is in flight wait in a queue, and the next POST takes the whole queue. So many messages sent close together cost one or two requests, not one each:

::split-stream-batch
::

Inside a POST, and inside the long POST of stream mode, each message is one **frame**: one byte for its type, four bytes for its length, then the message itself. The server reads the frames one by one, so a message can be JSON text or raw bytes:

::split-stream-frame
::

Your messages travel on the **data lane**: the POSTs of batch mode, or the long POST of stream mode. A second, separate lane, the **control lane**, carries only the small `ping`, `pong` and close messages, in short POSTs of their own, one at a time. So a big batch on the data lane can never delay a `pong`, and a slow upload never makes the server think the client is gone. In stream mode, the close goes in the long POST instead, after your last messages, so it can never overtake them.

## Nothing lost, nothing twice

A long POST can die halfway: a short network drop, a proxy that times out, a server limit. The messages inside it must not be lost, and none may run twice. Two small tools make this safe:

- **Numbers.** Each message gets a number, counted from 1 for the whole connection, in both modes.
- **Answers.** After the server takes messages from the long POST, it writes a short answer on the SSE stream: "I have everything up to number 5". When many messages arrive close together, it sends one answer for all of them, not one each.

When the long POST dies, the client sends every message that has no answer yet again, in batch mode. The server checks the numbers and drops the ones it already has. Step through it:

::split-stream-recovery
::

The client also ends the long POST on purpose after 8 MiB of messages, and opens a fresh one, because proxies and hosts limit the size of one request body. The fresh one starts again from the first message with no answer, in the same way.

The numbers protect messages within one connection. When the whole connection drops and the client connects again, it starts new numbers, as a WebSocket would. So, as on WebSocket, delivery from the client to the server is **at most once**: a message can be lost when the connection drops, but it never runs twice. So make actions that change data safe to repeat, and use [`replay()`](/server/capabilities/replay) for the messages the client missed.

## One connection, or three

On HTTP/2 and newer, one connection carries many requests at the same time. So the SSE stream, the long POST and any batch POST all share **one connection**, just like a WebSocket. On HTTP/1.1, each open request needs its own connection, and a browser allows only six for each site, shared by all its tabs:

::split-stream-connections
::

So serve your site over HTTP/2 or HTTP/3. Most hosts and CDNs already do. HTTP/2 is also what makes stream mode possible at all.

## Turn it on

A Split Stream is what LiveThing's `http()` transport does. You never choose stream mode or batch mode: the client picks for each connection. List `http()` next to `websocket()` on the server:

```ts [huddle-server.ts]
import { http, setup, websocket } from '@livething/server-node'
import { huddle } from './server/huddle-definition'

const { bind } = setup()
const huddleEndpoint = bind(huddle, {
  sql: './data/huddle.sqlite',
  transports: [websocket(), http()],
})
```

And on the client, in the order you prefer:

```typescript [client/socket.ts]
import {
  binary,
  client,
  connect,
  http,
  websocket,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle', {
    transports: [websocket(), http()],
  }),
  binary(),
)
```

The client tries WebSocket first. When a network blocks it, the client moves to the Split Stream, with no error and no change in your app code. `socket.transport` tells you which one is in use. You can also list only `http()`, so your whole app runs over plain HTTP. [Transports](/server/adapters/transports) has the setup for every runtime and framework.

## What it costs

A Split Stream is built to be fast, but it is still more HTTP than one WebSocket. Know these before you turn it on:

- **Binary is bigger going down.** SSE carries text only, so the server sends a binary message as base64 text, about a third bigger. Binary going up travels as raw bytes.
- **On Cloudflare, an open stream keeps the Durable Object awake.** A WebSocket with [hibernation](/server/server/hibernation) lets Cloudflare take the object out of memory between messages. A Split Stream does not, so it gets no hibernation savings.
- **Several Node instances need sticky routing.** Your load balancer must send the stream and all its POSTs to the same Node process.
- **It needs [`keepalive()`](/server/capabilities/keepalive).** A proxy can keep a stream open after the client is gone, and only pings find that out.

[Costs and limits](/server/adapters/transports#costs-and-limits) on the Transports page has the full list, and [Server Benchmarks](/start/benchmarks#over-the-fallback-transports) measures `http()` against Socket.IO's long polling.
