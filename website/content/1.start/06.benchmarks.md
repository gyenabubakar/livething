LiveThing does more work for each message than a raw WebSocket server: it checks the message, finds the handler, builds the `ctx`, and tracks channel members. This page shows what that work costs on Node.js, and where LiveThing is faster than writing the server yourself on [`ws`](https://github.com/websockets/ws), the WebSocket library that `@livething/server-node` uses.

## What was measured

The benchmark runs one small chat app twice:

- **LiveThing**: the app on `@livething/server-node`, with channels and member tracking.
- **Plain `ws`**: the same app written directly on `ws`, with no framework. It reads each message, parses the JSON, and keeps a list of members for each room. It sends every message the simple way: one `ws.send()` call for each recipient.

Both servers send the same events with the same payloads, in the same JSON format. The one exception is joins: LiveThing also tells the members who joined (see [Joining a channel](#joining-a-channel)).

The server runs alone in its own process. 2,000 real WebSocket clients run in another process on the same machine, and the same clients test both servers. For each step, the benchmark reads how much CPU time the **server** process used and divides it by the units of work in that step: one connection, one message, one join or one delivery. CPU time for each unit changes little with the speed of the clients.

The tables below turn that CPU time into **how many units one CPU core can handle per second**. Higher is better. Node.js runs your JavaScript on one thread, so one core is the limit for one server process.

| Machine  | Value                                                                 |
| -------- | --------------------------------------------------------------------- |
| Computer | Apple M1 Pro, 16 GB                                                   |
| Node.js  | 24.12.0                                                               |
| `ws`     | 8.18.0                                                                |
| Clients  | 2,000 WebSocket connections                                           |
| Runs     | 7, LiveThing and `ws` one after the other; the tables show the median |

## Results

### Where LiveThing is faster

| Work                                               | LiveThing          | Plain `ws`         | Result                                   |
| -------------------------------------------------- | ------------------ | ------------------ | ---------------------------------------- |
| Broadcast deliveries in a channel of 2,000 members | 858,000 per second | 206,000 per second | LiveThing handles **4.2 times** as many  |
| Message deliveries in channels of 10 members       | 228,000 per second | 184,000 per second | LiveThing handles **1.24 times** as many |

A broadcast sends the same message to many members. Most of its cost is not JavaScript. It is the **system call**: the request that hands bytes to the operating system to send. Plain `ws` makes one system call for each message to each member. LiveThing does two things to cut this cost:

- **It builds a broadcast message once.** The bytes of the WebSocket message are made one time and written to every member, instead of once for each member. This saves JavaScript work.
- **It sends a connection's messages together.** LiveThing holds a connection's messages until the code that is running now ends, and then sends them in one system call. When several broadcasts happen in that code, for example in the handlers of several messages that arrived together, each member gets all of them in one write. Code that continues after an `await` starts a new write. This saves system calls. The order of the messages does not change, and a message waits only until the running code ends. A connection that has 64 KiB waiting sends it at once.

In this benchmark, each sender sends several messages in a row (10 in the big channel, 5 in the channels of 10), so the server often handles several broadcasts at once, and their messages to each member go out together. An app that sends one broadcast at a time gets less from the second change. The first change works only when compression is off, which is the default: with `compression` on, each member's message is compressed on its own.

You can write both changes yourself in a `ws` server. LiveThing does them for every app.

### Where plain `ws` is faster

| Work                                       | LiveThing         | Plain `ws`        | Result                              |
| ------------------------------------------ | ----------------- | ----------------- | ----------------------------------- |
| Echo: a message in, a message back         | 60,000 per second | 82,000 per second | `ws` handles **1.35 times** as many |
| Request and response                       | 56,000 per second | 93,000 per second | `ws` handles **1.66 times** as many |
| New connections                            | 4,800 per second  | 9,000 per second  | `ws` handles **1.88 times** as many |
| Disconnects                                | 9,100 per second  | 13,200 per second | `ws` handles **1.45 times** as many |
| JavaScript memory for each open connection | 9.1 KB            | 4.3 KB            | `ws` uses **2.1 times** less        |

Here LiveThing does extra work that plain `ws` does not do. For each message, LiveThing checks that the message follows the LiveThing [wire protocol](/learn/wire-protocol), routes it to its handler, and gives the handler a typed `ctx`. For each request, it also matches the reply to the request. For each connection, it runs the sign-in hook and sets up the connection's state. The app in this benchmark has no payload schemas. A schema on a handler adds the cost of your validator.

### Joining a channel

A LiveThing channel has **presence** by default: a join tells every member who joined, so each client can show who is online. The plain `ws` app does not do this. It only adds the connection to a list. So the benchmark also runs LiveThing with [presence off](/server/channels/membership-and-presence#turning-presence-off), which is the fair comparison.

Joins per second:

| Channel size             | LiveThing, presence on | LiveThing, presence off | Plain `ws` | Presence off vs `ws` |
| ------------------------ | ---------------------- | ----------------------- | ---------- | -------------------- |
| 10 members, 200 channels | 9,200                  | 13,100                  | 26,400     | `ws` **2×**          |
| 500 members              | 3,000                  | 6,000                   | 10,600     | `ws` **1.77×**       |
| 1,000 members            | 2,800                  | 9,100                   | 18,200     | `ws` **2×**          |
| 2,000 members            | 2,100                  | 13,200                  | 24,700     | `ws` **1.87×**       |

With presence on, the message to the members is why the cost grows with the size of the channel. In this benchmark, every client joins in the same moment, which is the worst case. With presence off, a LiveThing join still does more work than adding the connection to a list.

Each step also has a fixed cost that does not depend on the number of joins. The channels of 500 and 1,000 have fewer joins to share that cost, so each of their joins looks more expensive, on both servers. The rows with 2,000 joins are the closest to the real cost of one join.

## What the numbers mean for your app

- **One server process can do a lot.** Even the slowest number above, about 2,100 joins per second into one big channel, is far more than most apps see.
- **Busy broadcast apps gain the most.** Chat rooms, live dashboards and multiplayer state send one message to many people, often several at once. That is where LiveThing uses the least CPU.
- **Your handlers cost more than LiveThing does.** A handler that reads a database or calls another service takes milliseconds. The whole server cost of one message here is about 17 to 18 microseconds, and plain `ws` already uses about 11 to 12 of them.
- **A real network adds time, not CPU.** The clients here are on the same machine. Over a real network, each message takes longer to arrive, but the server does the same work.

The results depend on the machine, the Node.js version and the size of the messages. Run the benchmark on your own machine to see your numbers.

## Run it yourself

The benchmark is in the LiveThing repository. Clone it, install the dependencies, and build the packages:

```bash
pnpm install
pnpm build
```

Then run each server with 2,000 clients from the Node.js adapter's folder:

```bash
cd server-adapters/node
node bench/load.mjs livething 2000
node bench/load.mjs ws 2000
```

To run LiveThing with presence off, set `LOAD_PRESENCE=off`:

```bash
LOAD_PRESENCE=off node bench/load.mjs livething 2000
```

Each run prints one line for each step. `cpuUsPerUnit` is the server's CPU time for one unit, in microseconds. One second divided by that number gives the units per second that the tables show.
