LiveThing does more work for each message than a raw WebSocket server: it checks the message, finds the handler, builds the `ctx`, and tracks channel members. This page shows what that work costs on Node.js. It compares LiveThing with the same app written on [`ws`](https://github.com/websockets/ws), the WebSocket library that `@livething/server-node` uses, and on [Socket.IO](https://socket.io), a popular realtime library.

## What was measured

The benchmark runs one small chat app on three servers:

- **LiveThing**: the app on `@livething/server-node`, with channels.
- **Plain `ws`**: the same app written directly on `ws`, with no framework. It reads each message, parses the JSON, and keeps a list of members for each room. It sends every message the simple way: one `ws.send()` call for each recipient.
- **Socket.IO**: the same app on Socket.IO, with its rooms. Compression is off, as it is on the other two servers.

All three servers send the same events with the same payloads. Each step uses JSON messages, except the binary steps, which send raw bytes.

The app runs over WebSocket on all three servers. It also runs over the fallback transport of each framework: [`http()`](/server/adapters/transports) on LiveThing, and HTTP long-polling on Socket.IO. See [Over the fallback transports](#over-the-fallback-transports).

LiveThing runs with [presence off](/server/channels/membership-and-presence#turning-presence-off), because the other two servers do not tell members who joined or left. [Joining a channel](#joining-a-channel) also shows LiveThing with presence on.

The server runs alone in its own process. 2,000 real clients run in another process on the same machine. They use the `ws` client for LiveThing and plain `ws` over WebSocket, the Socket.IO client for Socket.IO, and a small HTTP client that follows the LiveThing protocol for `http()`. For each step, the benchmark reads how much CPU time the **server** process used and divides it by the units of work in that step: one connection, one message, one join or one delivery. CPU time for each unit changes little with the speed of the clients.

The tables below turn that CPU time into **how many units one CPU core can handle per second**. Higher is better. Memory is the one exception: there, lower is better. In each row, the best result is in **bold** on a green background. The second best is in _italics_ on a yellow background. Node.js runs your JavaScript on one thread, so one core is the limit for one server process.

| Machine   | Value                                                                         |
| --------- | ----------------------------------------------------------------------------- |
| Computer  | Apple M1 Pro, 16 GB                                                           |
| Node.js   | 24.12.0                                                                       |
| `ws`      | 8.18.0                                                                        |
| Socket.IO | 4.8.4, which uses `ws` 8.21.0                                                 |
| Clients   | 2,000 connections                                                             |
| Runs      | 5 of each server, in a different order each round; the tables show the median |

## Over WebSocket

### Where LiveThing is faster

| Work                                               | LiveThing                          | Plain `ws`                         | Socket.IO                          |
| -------------------------------------------------- | ---------------------------------- | ---------------------------------- | ---------------------------------- |
| Broadcast deliveries in a channel of 2,000 members | **915,000 per second**{.bench-win} | 195,000 per second                 | _237,000 per second_{.bench-close} |
| Message deliveries in channels of 10 members       | **251,000 per second**{.bench-win} | _176,000 per second_{.bench-close} | 175,000 per second                 |

In a channel of 2,000 members, LiveThing handles **4.7 times** as many deliveries as plain `ws`, and **3.9 times** as many as Socket.IO.

A broadcast sends the same message to many members. Most of its cost is not JavaScript. It is the **system call**: the request that hands bytes to the operating system to send. Plain `ws` makes one system call for each message to each member. LiveThing does two things to cut this cost:

- **It builds a broadcast message once.** The bytes of the WebSocket message are made one time and written to every member, instead of once for each member. This saves JavaScript work.
- **It sends a connection's messages together.** LiveThing holds a connection's messages until the code that is running now ends, and then sends them in one system call. When several broadcasts happen in that code, for example in the handlers of several messages that arrived together, each member gets all of them in one write. Code that continues after an `await` starts a new write. This saves system calls. The order of the messages does not change, and a message waits only until the running code ends. A connection that has 64 KiB waiting sends it at once.

In this benchmark, each sender sends several messages in a row (10 in the big channel, 5 in the channels of 10), so the server often handles several broadcasts at once, and their messages to each member go out together. An app that sends one broadcast at a time gets less from the second change. The first change works only when compression is off, which is the default: with `compression` on, each member's message is compressed on its own.

You can write both changes yourself in a `ws` server. LiveThing does them for every app that runs on the Node.js adapter's own server or on Fastify. The Hono and h3 adapters do not use them yet.

### Where plain `ws` is faster

| Work                                       | LiveThing                         | Plain `ws`                         | Socket.IO                         |
| ------------------------------------------ | --------------------------------- | ---------------------------------- | --------------------------------- |
| Echo: a message in, a message back         | _69,500 per second_{.bench-close} | **91,100 per second**{.bench-win}  | 63,100 per second                 |
| Request and response                       | 62,300 per second                 | **104,000 per second**{.bench-win} | _76,400 per second_{.bench-close} |
| New connections                            | _5,300 per second_{.bench-close}  | **10,300 per second**{.bench-win}  | 5,200 per second                  |
| Disconnects                                | 13,700 per second                 | **17,600 per second**{.bench-win}  | _14,200 per second_{.bench-close} |
| JavaScript memory for each open connection | _9.7 KB_{.bench-close}            | **4.3 KB**{.bench-win}             | 12.5 KB                           |

Here LiveThing does extra work that plain `ws` does not do. For each message, LiveThing checks that the message follows the LiveThing [wire protocol](/learn/wire-protocol), routes it to its handler, and gives the handler a typed `ctx`. For each request, it also matches the reply to the request. For each connection, it runs the sign-in hook and sets up the connection's state. The app in this benchmark has no payload schemas. A schema on a handler adds the cost of your validator.

Socket.IO also does work for each message, so it is close to LiveThing in this table. It is faster than LiveThing for requests, slower for echo, about the same for connections and disconnects, and it uses more memory.

### Binary messages

The binary steps send bytes with [`binary()`](/server/binary/events). The bytes are not turned into JSON or base64, and each frame has only a small JSON header. Each client sends bytes and gets them back (binary echo), and one channel of 2,000 members gets bytes from a few senders (binary fan-out).

| Work                                     | LiveThing                          | Plain `ws`                         | Socket.IO                        |
| ---------------------------------------- | ---------------------------------- | ---------------------------------- | -------------------------------- |
| Binary echo, 1 KiB                       | _60,100 per second_{.bench-close}  | **70,800 per second**{.bench-win}  | 38,200 per second                |
| Binary echo, 64 KiB                      | 4,070 per second                   | **5,440 per second**{.bench-win}   | _4,110 per second_{.bench-close} |
| Binary deliveries, 1 KiB, 2,000 members  | **465,000 per second**{.bench-win} | _219,000 per second_{.bench-close} | 95,000 per second                |
| Binary deliveries, 64 KiB, 2,000 members | _40,500 per second_{.bench-close}  | **51,300 per second**{.bench-win}  | 28,500 per second                |

Small binary messages act like JSON messages: an echo costs a little more than on plain `ws`, and a broadcast costs much less. With 64 KiB messages, plain `ws` is faster for both echo and broadcast.

### Joining a channel

A LiveThing channel has **presence** by default: a join tells every member who joined, so each client can show who is online. Plain `ws` and Socket.IO do not do this. They only add the connection to a list.

Joins per second:

| Channel size             | LiveThing, presence on | LiveThing, presence off | Plain `ws`             | Socket.IO              |
| ------------------------ | ---------------------- | ----------------------- | ---------------------- | ---------------------- |
| 10 members, 200 channels | 11,900                 | 18,800                  | **28,900**{.bench-win} | _26,700_{.bench-close} |
| 500 members              | 4,600                  | 15,500                  | **22,900**{.bench-win} | _19,700_{.bench-close} |
| 1,000 members            | 3,400                  | 21,400                  | **36,800**{.bench-win} | _26,800_{.bench-close} |
| 2,000 members            | 2,300                  | 23,300                  | **40,800**{.bench-win} | _32,400_{.bench-close} |

With presence on, the message to the members is why the cost grows with the size of the channel. In this benchmark, every client joins in the same moment, which is the most work at once. With presence off, a LiveThing join still does more work than adding the connection to a list.

Each step also has a small cost that does not depend on the number of joins. So without presence, the rows with more joins show a lower cost for each join, and the rows with 2,000 joins are the closest to the real cost of one join.

## Over the fallback transports

When a client cannot use WebSocket, LiveThing can use [`http()`](/server/adapters/transports): the server sends with server-sent events on one long HTTP response, and the client sends with POST requests. Socket.IO has no server-sent events. Its fallback is **HTTP long-polling**: the client keeps a GET request open until the server has data for it, and sends with POST requests.

The same 2,000 clients and the same steps run over both fallbacks, on HTTP/1.1. The `http()` column uses batch mode (short POSTs), which every browser and every proxy supports. It does not use [stream mode](/server/adapters/transports#stream-mode). The WebSocket column of LiveThing is there to show what the fallback costs, so the green marks only compare the two fallbacks. All three columns come from their own set of 5 runs, so the WebSocket numbers differ a little from the tables above.

| Work                                               | LiveThing, `http()`                | Socket.IO, long-polling            | LiveThing, WebSocket |
| -------------------------------------------------- | ---------------------------------- | ---------------------------------- | -------------------- |
| Broadcast deliveries in a channel of 2,000 members | _357,000 per second_{.bench-close} | **631,000 per second**{.bench-win} | 870,000 per second   |
| Message deliveries in channels of 10 members       | _104,000 per second_{.bench-close} | **142,000 per second**{.bench-win} | 242,000 per second   |
| Binary deliveries, 1 KiB, 2,000 members            | **232,000 per second**{.bench-win} | _198,000 per second_{.bench-close} | 426,000 per second   |
| Binary deliveries, 64 KiB, 2,000 members           | **31,000 per second**{.bench-win}  | _5,000 per second_{.bench-close}   | 36,800 per second    |
| Echo: a message in, a message back                 | _30,500 per second_{.bench-close}  | **34,200 per second**{.bench-win}  | 66,900 per second    |
| Request and response                               | _34,600 per second_{.bench-close}  | **48,500 per second**{.bench-win}  | 59,300 per second    |
| Binary echo, 1 KiB                                 | _25,600 per second_{.bench-close}  | **32,100 per second**{.bench-win}  | 56,000 per second    |
| Binary echo, 64 KiB                                | _1,370 per second_{.bench-close}   | **2,170 per second**{.bench-win}   | 3,930 per second     |
| Joins, 2,000 members, presence off                 | **10,900 per second**{.bench-win}  | _9,600 per second_{.bench-close}   | 21,900 per second    |
| New connections                                    | **4,900 per second**{.bench-win}   | _3,600 per second_{.bench-close}   | 5,100 per second     |
| Disconnects                                        | **8,400 per second**{.bench-win}   | _8,200 per second_{.bench-close}   | 12,300 per second    |
| JavaScript memory for each open connection         | _16.1 KB_{.bench-close}            | **13.0 KB**{.bench-win}            | 9.7 KB               |

A message from a client costs about twice as much CPU on a fallback as on WebSocket, because it comes in an HTTP request.

- **Socket.IO is faster for JSON messages and for binary echo.** When several messages wait for a client, Socket.IO sends all of them in one HTTP response. LiveThing writes each message to the open response as its own event.
- **LiveThing is faster for binary broadcasts.** Server-sent events carry only text, so LiveThing sends bytes as base64, which is a third bigger. It builds the base64 of a broadcast once for all members. With 64 KiB messages, it handles **6.2 times** as many deliveries as Socket.IO.
- **LiveThing is faster for new connections**, about the same for joins and disconnects, and it uses more memory for each connection.

The fallback is for the clients that cannot use WebSocket. Most clients still connect over WebSocket, so most of your server's work has the costs in the WebSocket tables.

In Node.js, the Socket.IO long-polling client opens a new TCP connection for every request unless it gets an HTTP agent that keeps connections open. Browsers keep connections open, so the benchmark gives the client such an agent, and the server keeps idle connections for 65 seconds. The operating system queues only so many new connections that the server has not accepted yet (128 on macOS), so both HTTP clients open at most 100 new connections at a time, and every client opens its connections the same way.

## What the numbers mean for your app

- **One server process can do a lot.** Even the slowest number over WebSocket, about 2,300 joins per second into one big channel with presence on, is far more than most apps see.
- **Busy broadcast apps gain the most.** Chat rooms, live dashboards and multiplayer state send one message to many people, often several at once. That is where LiveThing uses the least CPU.
- **Your handlers cost more than LiveThing does.** A handler that reads a database or calls another service takes milliseconds. The whole server cost of one message here is about 14 microseconds, and plain `ws` already uses about 11 of them.
- **A real network adds time and some CPU.** The clients here are on the same machine and do not use TLS. Over a real network, each message takes longer to arrive, and the operating system and TLS (`wss://` and `https://`) add CPU that these numbers do not include. Every server pays that cost the same way.

The results depend on the machine, the Node.js version and the size of the messages. Run the benchmark on your own machine to see your numbers.

## Run it yourself

The benchmark is in the LiveThing repository. Clone it, install the dependencies, and build the packages:

```bash
pnpm install
pnpm build
```

Then run each server with 2,000 clients from the Node.js adapter's folder. `LOAD_PRESENCE=off` turns presence off on LiveThing, as the tables do, and the other servers ignore it:

```bash
cd server-adapters/node
LOAD_PRESENCE=off node bench/load.mjs livething 2000
node bench/load.mjs ws 2000
node bench/load.mjs socket.io 2000
```

Run the fallback transports with `livething-http` and `socket.io-polling`:

```bash
LOAD_PRESENCE=off node bench/load.mjs livething-http 2000
node bench/load.mjs socket.io-polling 2000
```

Leave out `LOAD_PRESENCE=off` to run LiveThing with presence on. `LOAD_BINARY_SIZES` sets the sizes of the binary steps, in bytes (default: `1024,65536`), and an empty value skips them. The top of `bench/load.mjs` lists every environment variable it reads.

Each run prints one line for each step. `cpuUsPerUnit` is the server's CPU time for one unit, in microseconds. One second divided by that number gives the units per second that the tables show.
