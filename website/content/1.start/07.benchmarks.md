LiveThing does more work for each message than a raw WebSocket server: it checks the message, finds the handler, builds the `ctx`, and tracks channel members. This page shows what that work costs on Node.js. It compares LiveThing with the same app written on [`ws`](https://github.com/websockets/ws), the WebSocket library that `@livething/server-node` uses, and on [Socket.IO](https://socket.io), a popular realtime library.

## What was measured

The benchmark runs one small chat app on three servers:

- **LiveThing**: the app on `@livething/server-node`, with channels. The channels are [ephemeral](/server/channels/defining#membership-keep-membership-after-a-reconnect), the default: a member leaves when its connection closes, and LiveThing keeps the members only in memory. This works like the rooms of the other two servers.
- **Plain `ws`**: the same app written directly on `ws`, with no framework. It reads each message, parses the JSON, and keeps a list of members for each room. It sends every message the simple way: one `ws.send()` call for each recipient.
- **Socket.IO**: the same app on Socket.IO, with its rooms. Compression is off, as it is on the other two servers.

All three servers send the same events with the same payloads. Each step uses JSON messages, except the binary steps, which send raw bytes.

The app runs over WebSocket on all three servers. It also runs over the fallback transport of each framework: [`http()`](/server/adapters/transports) on LiveThing, and HTTP long-polling on Socket.IO. See [Over the fallback transports](#over-the-fallback-transports).

LiveThing runs with [presence off](/server/channels/membership-and-presence#turning-presence-off), because the other two servers do not tell members who joined or left. [Joining a channel](#joining-a-channel) also shows LiveThing with presence on.

The server runs alone in its own process. 2,000 real clients run in another process on the same machine. They use the `ws` client for LiveThing and plain `ws` over WebSocket, the Socket.IO client for Socket.IO, and a small HTTP client that follows the LiveThing protocol for `http()`. For each step, the benchmark reads how much CPU time the **server** process used and divides it by the units of work in that step: one connection, one message, one join or one delivery. CPU time for each unit changes little with the speed of the clients.

The tables below turn that CPU time into **how many units one CPU core can handle per second**. Higher is better. Memory is the one exception: there, lower is better. In each row, the best result is in **bold** on a green background. The second best is in _italics_ on a yellow background. Under each of them, small text says how many times better it is than the next result: the best against the second, and the second against the third. Node.js runs your JavaScript on one thread, so one core is the limit for one server process.

| Machine   | Value                                                                         |
| --------- | ----------------------------------------------------------------------------- |
| Computer  | Apple M1 Pro, 16 GB                                                           |
| Node.js   | 24.12.0                                                                       |
| `ws`      | 8.18.0                                                                        |
| Socket.IO | 4.8.4, which uses `ws` 8.21.0                                                 |
| Clients   | 2,000 connections                                                             |
| Runs      | 5 of each server, in a different order each round; the tables show the median |

## Over WebSocket

### Where LiveThing is faster

| Work                                               | LiveThing                                                        | Plain `ws`                                                      | Socket.IO                                                      |
| -------------------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------- |
| Broadcast deliveries in a channel of 2,000 members | **1,530,000 per second**{.bench-win} [7.0× the 2nd]{.bench-lead} | 163,000 per second                                              | _219,000 per second_{.bench-close} [1.3× the 3rd]{.bench-lead} |
| Message deliveries in channels of 10 members       | **285,000 per second**{.bench-win} [1.8× the 2nd]{.bench-lead}   | _162,000 per second_{.bench-close} [1.07× the 3rd]{.bench-lead} | 152,000 per second                                             |

In a channel of 2,000 members, LiveThing handles **9.4 times** as many deliveries as plain `ws`, and **7.0 times** as many as Socket.IO.

A broadcast sends the same message to many members. Most of its cost is not JavaScript. It is the **system call**: the request that hands bytes to the operating system to send. Plain `ws` makes one system call for each message to each member. LiveThing does two things to cut this cost:

- **It builds a broadcast message once.** The bytes of the WebSocket message are made one time and written to every member, instead of once for each member. This saves JavaScript work.
- **It sends a connection's messages together.** Node.js reads the messages that arrive together, from all clients, and runs their handlers one after another. LiveThing holds what those handlers send until Node.js has run them all. Then it copies each connection's small messages into one buffer and sends it in one system call. So when several handlers broadcast, each member gets all of their messages in one write. This saves system calls. The order of the messages does not change, and a message never waits for new data from the network. A connection that has 64 KiB waiting sends it at once.

In this benchmark, each sender sends several messages in a row (10 in the big channel, 5 in the channels of 10), so the server often handles several broadcasts at once, and their messages to each member go out together. An app that sends one broadcast at a time gets less from the second change. Both changes work only when compression is off, which is the default: with `compression` on, each member's message is compressed and sent on its own.

You can write both changes yourself in a `ws` server. LiveThing does them for every app that runs on the Node.js adapter's own server or on Fastify. The Hono and h3 adapters do not use them yet.

### Where plain `ws` is faster

| Work                                       | LiveThing                                                     | Plain `ws`                                                    | Socket.IO                                                      |
| ------------------------------------------ | ------------------------------------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------- |
| Echo: a message in, a message back         | _76,000 per second_{.bench-close} [1.3× the 3rd]{.bench-lead} | **84,200 per second**{.bench-win} [1.1× the 2nd]{.bench-lead} | 59,200 per second                                              |
| Request and response                       | 65,300 per second                                             | **94,700 per second**{.bench-win} [1.3× the 2nd]{.bench-lead} | _71,600 per second_{.bench-close} [1.10× the 3rd]{.bench-lead} |
| New connections                            | _5,400 per second_{.bench-close} [1.1× the 3rd]{.bench-lead}  | **10,000 per second**{.bench-win} [1.9× the 2nd]{.bench-lead} | 4,900 per second                                               |
| Disconnects                                | 13,600 per second                                             | **16,900 per second**{.bench-win} [1.2× the 2nd]{.bench-lead} | _13,700 per second_{.bench-close} [1.01× the 3rd]{.bench-lead} |
| JavaScript memory for each open connection | _9.4 KB_{.bench-close} [1.3× less than the 3rd]{.bench-lead}  | **4.3 KB**{.bench-win} [2.2× less than the 2nd]{.bench-lead}  | 12.5 KB                                                        |

Here LiveThing does extra work that plain `ws` does not do. For each message, LiveThing checks that the message follows the LiveThing [wire protocol](/learn/wire-protocol), routes it to its handler, and gives the handler a typed `ctx`. For each request, it also matches the reply to the request. For each connection, it runs the sign-in hook and sets up the connection's state. The app in this benchmark has no payload schemas. A schema on a handler adds the cost of your validator.

Socket.IO also does work for each message, so it is close to LiveThing in this table. It is faster than LiveThing for requests, slower for echo, about the same for connections and disconnects, and it uses more memory.

### Binary messages

The binary steps send bytes with [`binary()`](/server/binary/events). The bytes are not turned into JSON or base64, and each frame has only a small JSON header. Each client sends bytes and gets them back (binary echo), and one channel of 2,000 members gets bytes from a few senders (binary fan-out).

| Work                                     | LiveThing                                                      | Plain `ws`                                                     | Socket.IO                                                     |
| ---------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------- |
| Binary echo, 1 KiB                       | _59,900 per second_{.bench-close} [1.7× the 3rd]{.bench-lead}  | **66,200 per second**{.bench-win} [1.1× the 2nd]{.bench-lead}  | 36,300 per second                                             |
| Binary echo, 64 KiB                      | 4,080 per second                                               | **5,310 per second**{.bench-win} [1.3× the 2nd]{.bench-lead}   | _4,140 per second_{.bench-close} [1.01× the 3rd]{.bench-lead} |
| Binary deliveries, 1 KiB, 2,000 members  | **799,000 per second**{.bench-win} [4.3× the 2nd]{.bench-lead} | _188,000 per second_{.bench-close} [2.2× the 3rd]{.bench-lead} | 87,000 per second                                             |
| Binary deliveries, 64 KiB, 2,000 members | _39,300 per second_{.bench-close} [1.3× the 3rd]{.bench-lead}  | **47,200 per second**{.bench-win} [1.2× the 2nd]{.bench-lead}  | 29,300 per second                                             |

Small binary messages act like JSON messages: an echo costs a little more than on plain `ws`, and a broadcast costs much less. With 64 KiB messages, plain `ws` is faster for both echo and broadcast, and a 64 KiB echo costs about the same on LiveThing and Socket.IO.

### Joining a channel

A LiveThing channel has **presence** by default: a join tells every member who joined, so each client can show who is online. Plain `ws` and Socket.IO do not do this. They only add the connection to a list.

Joins per second:

| Channel size             | LiveThing, presence on | LiveThing, presence off | Plain `ws`                                          | Socket.IO                                          |
| ------------------------ | ---------------------- | ----------------------- | --------------------------------------------------- | -------------------------------------------------- |
| 10 members, 200 channels | 14,900                 | 22,300                  | **28,600**{.bench-win} [1.09× the 2nd]{.bench-lead} | _26,200_{.bench-close} [1.2× the 3rd]{.bench-lead} |
| 500 members              | 4,900                  | 14,400                  | **22,100**{.bench-win} [1.1× the 2nd]{.bench-lead}  | _19,300_{.bench-close} [1.3× the 3rd]{.bench-lead} |
| 1,000 members            | 3,600                  | 21,100                  | **36,600**{.bench-win} [1.4× the 2nd]{.bench-lead}  | _26,100_{.bench-close} [1.2× the 3rd]{.bench-lead} |
| 2,000 members            | 2,000                  | 24,900                  | **40,000**{.bench-win} [1.3× the 2nd]{.bench-lead}  | _31,700_{.bench-close} [1.3× the 3rd]{.bench-lead} |

With presence on, the message to the members is why the cost grows with the size of the channel. In this benchmark, every client joins in the same moment, which is the most work at once. With presence off, a LiveThing join still does more work than adding the connection to a list.

Each step also has a small cost that does not depend on the number of joins. So without presence, the rows with more joins show a lower cost for each join, and the rows with 2,000 joins are the closest to the real cost of one join.

## Over the fallback transports

When a client cannot use WebSocket, LiveThing can use [`http()`](/server/adapters/transports): the server sends with server-sent events on one long HTTP response, and the client sends with POST requests. Socket.IO has no server-sent events. Its fallback is **HTTP long-polling**: the client keeps a GET request open until the server has data for it, and sends with POST requests.

The same 2,000 clients and the same steps run over both fallbacks. LiveThing runs in its two modes:

- **Batch mode** on HTTP/1.1: the client sends with short POSTs. Every browser and every proxy supports it.
- **[Stream mode](/server/adapters/transports#stream-mode)** on HTTP/2: the client sends all its messages in one long POST. The server serves the HTTP/2 streams with [`handleStream`](/server/adapters/transports#less-memory-on-http2). The benchmark uses HTTP/2 without TLS, as no column here uses TLS.

Socket.IO long-polling runs on HTTP/1.1. The WebSocket column of LiveThing is there to show what a fallback costs, so the marks only compare the three fallbacks.

| Work                                               | LiveThing, batch mode                                            | LiveThing, stream mode                                           | Socket.IO, long-polling                                       | LiveThing, WebSocket |
| -------------------------------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------- | -------------------- |
| Broadcast deliveries in a channel of 2,000 members | _1,750,000 per second_{.bench-close} [2.7× the 3rd]{.bench-lead} | **2,550,000 per second**{.bench-win} [1.5× the 2nd]{.bench-lead} | 652,000 per second                                            | 1,530,000 per second |
| Message deliveries in channels of 10 members       | _177,000 per second_{.bench-close} [1.2× the 3rd]{.bench-lead}   | **277,000 per second**{.bench-win} [1.6× the 2nd]{.bench-lead}   | 149,000 per second                                            | 285,000 per second   |
| Binary deliveries, 1 KiB, 2,000 members            | _555,000 per second_{.bench-close} [2.5× the 3rd]{.bench-lead}   | **709,000 per second**{.bench-win} [1.3× the 2nd]{.bench-lead}   | 219,000 per second                                            | 799,000 per second   |

| Echo: a message in, a message back                 | _36,200 per second_{.bench-close} [1.03× the 3rd]{.bench-lead}   | **60,500 per second**{.bench-win} [1.7× the 2nd]{.bench-lead}    | 35,300 per second                                             | 76,000 per second    |

| Disconnects                                        | **9,700 per second**{.bench-win} [1.02× the 2nd]{.bench-lead}    | _9,500 per second_{.bench-close} [1.1× the 3rd]{.bench-lead}     | 8,500 per second                                              | 13,600 per second    |

- **A JSON broadcast in a big channel can cost less than on WebSocket.** Both send the messages that wait for one member as one buffer, in one write. In the channel of 2,000 members, both modes handle more deliveries than WebSocket. In the channels of 10 and for binary broadcasts, WebSocket costs less. In the channel of 2,000 members, batch mode handles **2.7 times** as many deliveries as Socket.IO, and stream mode **3.9 times**.
- **A message from a client costs more than on WebSocket.** In batch mode, each message comes in an HTTP request, so an echo costs about twice as much CPU as on WebSocket. In stream mode, all messages come in one open request, so an echo costs only about a quarter more.
- **Socket.IO is faster than batch mode for requests, and uses the least memory.** Stream mode is the fastest of the three for requests, but uses the most memory: it holds two open HTTP/2 streams for each client.
- **Big binary messages cost more than on WebSocket, and the most in stream mode.** Server-sent events carry only text, so both modes send bytes as base64, which is a third bigger. It builds the base64 of a broadcast once for all members. With 64 KiB messages, batch mode handles **6.0 times** as many deliveries as Socket.IO, and stream mode **4.0 times**.
- **Batch mode is the fastest for new connections**, and about the same as stream mode for disconnects. A stream-mode client also opens its long POST and checks that it works.

The fallback is for the clients that cannot use WebSocket. Most clients still connect over WebSocket, so most of your server's work has the costs in the WebSocket tables.

In Node.js, the Socket.IO long-polling client opens a new TCP connection for every request unless it gets an HTTP agent that keeps connections open. Browsers keep connections open, so the benchmark gives the client such an agent, and the server keeps idle connections for 65 seconds. The operating system queues only so many new connections that the server has not accepted yet (128 on macOS), so both HTTP clients open at most 100 new connections at a time, and every client opens its connections the same way. In stream mode, each client opens one HTTP/2 connection.

## What the numbers mean for your app

- **One server process can do a lot.** Even the slowest number over WebSocket, about 2,000 joins per second into one big channel with presence on, is far more than most apps see.
- **Busy broadcast apps gain the most.** Chat rooms, live dashboards and multiplayer state send one message to many people, often several at once. That is where LiveThing uses the least CPU.
- **Your handlers cost more than LiveThing does.** A handler that reads a database or calls another service takes milliseconds. The whole server cost of one message here is about 13 microseconds, and plain `ws` already uses about 12 of them.
- **A real network adds time and some CPU.** The clients here are on the same machine and do not use TLS. Over a real network, each message takes longer to arrive, and the operating system and TLS (`wss://` and `https://`) add CPU that these numbers do not include. Every server pays that cost the same way.

The results depend on the machine, the Node.js version and the size of the messages. Run the benchmark on your own machine to see your numbers.

## Run it yourself

The benchmark is in the LiveThing repository. Clone it, install the dependencies, and build the packages:

```bash
pnpm install
pnpm build
```

Then run each server with 2,000 clients from the Node.js adapter's folder. `LOAD_PRESENCE=off` turns presence off on LiveThing, as the tables do, and the other servers ignore it:

```bash
cd server-adapters/node
LOAD_PRESENCE=off node bench/load.mjs livething 2000
node bench/load.mjs ws 2000
node bench/load.mjs socket.io 2000
```

Run the fallback transports with `livething-http` (batch mode), `livething-http-stream` (stream mode) and `socket.io-polling`. `LOAD_H2_ENTRY=stream` serves the HTTP/2 streams with `handleStream`, as the table does:

```bash
LOAD_PRESENCE=off node bench/load.mjs livething-http 2000
LOAD_PRESENCE=off LOAD_H2_ENTRY=stream node bench/load.mjs livething-http-stream 2000
node bench/load.mjs socket.io-polling 2000
```

Leave out `LOAD_PRESENCE=off` to run LiveThing with presence on. `LOAD_BINARY_SIZES` sets the sizes of the binary steps, in bytes (default: `1024,65536`), and an empty value skips them. The top of `bench/load.mjs` lists every environment variable it reads.

Each run prints one line for each step. `cpuUsPerUnit` is the server's CPU time for one unit, in microseconds. One second divided by that number gives the units per second that the tables show.
