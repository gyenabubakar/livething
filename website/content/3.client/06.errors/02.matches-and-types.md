A WSKit error is a `WSKitError` — a regular `Error` subclass with two extra fields:

```typescript [shape]
class WSKitError extends Error {
  code: string    // a stable kebab-case id, e.g. 'forbidden'
  detail: unknown // extra data, narrowed to its real type by .matches()
}
```

You never read `code` with a string comparison or check `instanceof WSKitError` by hand. Each error you define comes with a `.matches()` type guard that does both — and narrows `detail` to its declared type — in one call.

## Defining an error

You define errors with the `error()` factory, in a file both halves of your app import. There are two forms:

```typescript [errors.ts]
import { error } from '@wskit/client/errors'
import * as v from 'valibot'

// code-only — no detail payload
export const NotFound = error('not-found')

// with a detail schema — any Standard Schema (valibot, zod, arktype)
export const Forbidden = error('forbidden', v.object({ reason: v.string() }))
```

Both forms return a callable factory. Calling it builds the error — `NotFound()` for a code-only one, `Forbidden({ reason: 'private post' })` for one with detail. The server throws these; the client matches them. (Defining and throwing on the server is covered in the [Errors](/learn/messaging/errors) chapter in Learn.)

::note
`error()` is the same factory whether you import it from `@wskit/client/errors` or `@wskit/core` — they're the one function. Put your shared error definitions wherever both your client and server can import them.
::

## Narrowing with `.matches()`

`.matches(err)` is a type guard. It returns `true` only when `err` is a `WSKitError`, its `code` matches, and — if the error was defined with a schema — its `detail` passes that schema. Inside a `true` branch, TypeScript knows both the code and the `detail` type:

```typescript [app.ts]
import { NotFound, Forbidden } from '../server/errors'

try {
  const post = await socket.request('get-post', { id })
} catch (err) {
  if (NotFound.matches(err)) {
    showMissing() // err is WSKitError<'not-found', void>
  } else if (Forbidden.matches(err)) {
    showBlocked(err.detail.reason) // err.detail typed as { reason: string }
  } else {
    throw err // not one of ours — let it propagate
  }
}
```

The same guard works anywhere you hold an unknown error — a `catch`, an `onError` callback, a stream's `onError` handler:

```typescript [app.ts]
socket.onError((err) => {
  if (Forbidden.matches(err)) lockUi(err.detail.reason)
})
```

## Why a type guard, not a string check

Comparing `err.code === 'forbidden'` would tell TypeScript nothing about `detail` — you'd be casting blind. `.matches()` is better on two counts:

- **It narrows the type.** After `Forbidden.matches(err)`, `err.detail` is `{ reason: string }`, checked by the compiler.
- **It validates at runtime.** If the error carries the right code but a `detail` that doesn't fit the schema, `.matches()` returns `false` rather than handing you a malformed object — so a code match with the wrong shape is treated as a non-match, not a crash.

## Codes are unique

An error code is a single global identifier on the wire, so you can't reuse a code the framework already ships (`internal-error`, `rate-limited`, `validation-failed`, and the rest). `error('rate-limited')` throws at definition time — pick your own code. The full list of reserved codes is the [built-in errors](/client/errors/builtin-errors).
