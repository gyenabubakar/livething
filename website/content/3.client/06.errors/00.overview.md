Every error the client can hand you is a **`WSKitError`** — a plain `Error` subclass with a stable `code` and an optional typed `detail`. That's true whether the error came from your server, from the client itself, or from the framework. Because they all share one shape, you catch and narrow them all the same way. This chapter covers where errors land on the client and how to handle them; the shared model and the full catalog live in [Core](/core/overview).

```typescript [shape]
class WSKitError extends Error {
  code: string   // a stable id, e.g. 'forbidden', 'timeout'
  detail: unknown // a typed payload, narrowed by .matches()
}
```

## Three families of error

A client sees errors from three places, imported from three places:

| Family | Examples | Import from |
|---|---|---|
| **Your own** typed errors | `Forbidden`, `NotFound` | your shared errors file |
| **Client-side** errors | `Timeout`, `Disconnected`, `Dropped` | `@wskit/client/errors` |
| **Framework** built-ins | `ValidationFailed`, `RateLimited`, `StreamAborted` | `@wskit/core` |

All three are `WSKitError`s and all three narrow with `.matches()` — the family only decides where you import the definition from. The client-side three are detailed in [Client-side Errors](/client/errors/client-side-errors); the framework catalog is in [Core](/core/builtin-errors).

## Two ways an error reaches you

An error either **rejects the specific call** it belongs to, or **surfaces on `onError`** when nothing claimed it:

```typescript [app.ts]
// 1. Claimed — it rejects the exact call that was waiting:
try {
  await socket.request('get-post', { id })
} catch (err) {
  if (NotFound.matches(err)) showMissing()
}

// 2. Unclaimed — a typed server error no request/stream/channel was waiting for,
//    a WebSocket-level failure, or a throw from one of your handlers:
socket.onError((err) => report(err))
```

A request rejects its promise, a stream loop throws, a channel `subscribe()` rejects — those are *claimed* errors, delivered to the code that was waiting. Anything left over goes to `onError`. The routing rules are in [onError Routing](/client/errors/onerror-routing).

## Narrowing

You never compare error strings. `ErrorDef.matches(err)` is a type guard that confirms the code **and** narrows `detail` to its real type:

```typescript [app.ts]
import { Forbidden } from '../server/errors'

if (Forbidden.matches(err)) {
  console.log(err.detail.reason) // detail typed as { reason: string }
}
```

How `.matches()` works and how to define your own errors is in the [Error Model](/core/error-model) — it's the same on the client and the server, so it's documented once in Core.
