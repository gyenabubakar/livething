Testing UI that reacts to a socket usually comes down to one question: "when this event arrives, does my code do the right thing?" You don't want a real WebSocket server in a unit test for that. WSKit ships two helpers — `inject` and `injectChannel` — that push a fake message through the **real** incoming pipeline, so your `.on()` handlers, intercepts, and primitives all run exactly as they would in production. The socket never has to connect.

Both come from the `@wskit/client/testing` subpath:

```ts [chat.test.ts]
import { inject, injectChannel } from '@wskit/client/testing'
```

## Injecting an event

`inject(socket, event, payload)` delivers a message as if the server sent it. It runs through the full incoming path — every primitive's `onIncoming` (channels, dedup, and the rest), then your intercepts, then your `.on()` handlers — and works even while the socket is `'closed'`. It doesn't open the socket; it pushes the message straight into the same pipeline a real frame would hit:

```ts [chat.test.ts]
import { client, connect } from '@wskit/client'
import { inject } from '@wskit/client/testing'
import { expect, test, vi } from 'vitest'
import type { ChatSocket } from '../server/chat'

test('shows an incoming notification', () => {
  const socket = client<ChatSocket>()(connect('wss://example.com/ws'))

  const handler = vi.fn()
  socket.on('notification', handler)

  inject(socket, 'notification', { title: 'Hello' })

  expect(handler).toHaveBeenCalledWith({ title: 'Hello' })
  expect(socket.getState()).toBe('closed') // never connected
})
```

You never call `socket.connect()`. That's the point — the handler logic is tested in isolation, with no network, no timers, no flakiness.

## Injecting a channel message

A channel message is routed by a tag on the frame, so a plain `inject` won't reach a channel handler. Use `injectChannel(socket, channel, event, payload)` — it tags the frame with the channel so the `channels()` primitive delivers it to that channel's handlers:

```ts [room.test.ts]
import { client, connect, channels } from '@wskit/client'
import { injectChannel } from '@wskit/client/testing'
import { expect, test, vi } from 'vitest'
import type { ChatSocket } from '../server/chat'

test('routes a message to the right channel', () => {
  const socket = client<ChatSocket>()(connect('wss://example.com/ws'), channels())

  const handler = vi.fn()
  socket.channel('general').on('message', handler)

  injectChannel(socket, 'general', 'message', { text: 'hi', from: 'ada' })

  expect(handler).toHaveBeenCalledWith({ text: 'hi', from: 'ada' })
})
```

The channel tag matters. An `injectChannel` aimed at `general` only fires `general`'s handlers, never another channel's. A plain `inject('message', …)` is *not* a channel message — it won't reach any channel handler. And `injectChannel` needs `channels()` registered to route, just like a real app.

## Intercepts and primitives still run

Because injection uses the real pipeline, anything that sits in front of your handlers runs too. An [`intercept`](/client/primitives/intercept) that throws `Block` drops the injected message before it reaches `.on()`, exactly as it would for a real one:

```ts [filter.test.ts]
import { client, connect, intercept } from '@wskit/client'
import { Block } from '@wskit/client/errors'
import { inject } from '@wskit/client/testing'
import { expect, test, vi } from 'vitest'
import type { ChatSocket } from '../server/chat'

test('an intercept can block an injected message', () => {
  const socket = client<ChatSocket>()(
    connect('wss://example.com/ws'),
    intercept((m) => { if (m.event === 'spam') throw Block }),
  )

  const handler = vi.fn()
  socket.on('spam', handler)

  inject(socket, 'spam', { id: '1' })

  expect(handler).not.toHaveBeenCalled() // the intercept dropped it
})
```

This is what makes injection useful beyond "did my handler run" — you can assert that your filtering, deduplication, or other primitive behavior does the right thing on a known input.

## The injectors are typed from your contract

`inject` and `injectChannel` take the same contract as `client<ChatSocket>()`, so the event name, channel name, and payload shape are all checked at compile time. A typo or a wrong payload is a type error, not a test that silently passes:

```ts [typing.test.ts]
inject(socket, 'notification', { title: 'ok' })

// @ts-expect-error 'nope' isn't an incoming event
inject(socket, 'nope', { title: 'ok' })

// @ts-expect-error title must be a string
inject(socket, 'notification', { title: 42 })

// @ts-expect-error 'lobby' isn't a channel on this contract
injectChannel(socket, 'lobby', 'message', { text: 'hi', from: 'ada' })
```

The same `ChatSocket` type that powers `.on()` powers the test, so the test breaks the moment the contract changes — which is exactly when you want it to.

## Beyond unit tests

`inject` covers server-pushed events and channel messages — the bulk of client behavior. For round trips that need a real server (a `request()` that must get a correlated response, reconnection, the wire protocol itself), run against an actual server in an end-to-end test instead. WSKit's own suite does this with a real Cloudflare Worker; a minimal echo server works just as well for app-level checks.
