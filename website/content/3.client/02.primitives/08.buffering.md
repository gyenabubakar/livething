`buffering()` holds messages you `send()` while the socket is down and replays them, in order, when it reconnects. Without it (the default), a `send()` on a closed socket is dropped and returns `false`. It adds no methods — it owns the outgoing buffer. For the concept, see [Buffering](/learn/reliability/buffering).

```typescript [app.ts]
import { client, connect, reconnection, buffering } from '@wskit/client'
import type { MySocket } from './socket-types'

const socket = client<MySocket>()(
  connect('wss://example.com/ws'),
  reconnection(),
  buffering({ enabled: true, maxSize: 50 }),
)
```

## Options

```typescript [app.ts]
buffering({
  enabled: true,       // queue sends made while disconnected (default: false)
  maxSize: 50,         // most messages to hold; the oldest is dropped when full (default: 50)
  ttl: 10_000,         // time-to-live for queued messages (default: none) — see below
  flushInterval: 0,    // ms between messages on flush; 0 sends them all at once (default: 0)
})
```

Note `enabled` defaults to `false` — you turn buffering on by passing `{ enabled: true }`.

## What gets queued, and when it's cleared

While the socket is closed (or while a staggered flush is still draining), a `send()` is added to the buffer and returns `true`. When the buffer is full, the **oldest** message is dropped to make room — `send()` still returns `true`, since the new message was accepted.

The buffer is treated differently depending on how the socket closed:

- An **accidental drop** keeps the queue, and the messages go out on the next reconnect.
- A deliberate **`disconnect()`** throws the queue away — disconnecting is an intentional stop, so the queued messages are discarded.

A queued frame tied to a promise-bearing operation — a `request()`, a stream trigger, a nudge — is only sent if that operation is still pending. If it already timed out or rejected on disconnect, its frame is dropped on flush rather than running something the caller was already told failed.

The reverse matters too: when a buffered operation can't be sent, its promise **rejects** instead of hanging. A buffered `request()` rejects with `Dropped` if it's evicted (the buffer filled) or its TTL expires, and with `Disconnected` if you `disconnect()` before the flush. Both are importable from `@wskit/client/errors`:

```typescript [app.ts]
import { Dropped, Disconnected } from '@wskit/client/errors'

try {
  // sent now, or queued if the socket is down
  const res = await socket.request('save', { id })
} catch (err) {
  if (Dropped.matches(err)) toast('Lost while offline — try again')
  else if (Disconnected.matches(err)) toast('Disconnected')
}
```

## Flush order

By default (`flushInterval: 0`) the whole buffer flushes at once on reconnect, in send order. For a server with rate limits, that burst can trip a disconnect — set `flushInterval` to space the messages out, one every N milliseconds. While a staggered flush is still draining, new `send()` calls queue behind the not-yet-flushed messages so order is preserved instead of racing ahead.

## Message TTL

Some messages go stale if they aren't sent quickly — a typing indicator queued 30 seconds ago is meaningless by the time the socket is back. `ttl` drops a queued message after a set time. It takes one number for all events, or a per-event map:

```typescript [app.ts]
buffering({
  enabled: true,
  ttl: { typing: 5_000, 'cursor-move': 2_000 },
})
```

The most specific value wins: a per-call `ttl` on `send()` overrides the per-event map, which overrides a single global number. Channel events have their own TTL on [`channels()`](/client/primitives/channels). Expired messages are removed before the flush and never sent.
