You can pass `connect(...)` a **function** that returns the URL, instead of a fixed string. The client calls this function on **every** connect and reconnect, so the address can be different on each attempt. This is useful for:

- **Failover:** when one server stops answering, connect to a backup server.
- **Load balancing:** spread clients across several servers so no single server gets all the traffic.
- **Regional routing:** connect each user to the server region closest to them.
- **Stateful server instances:** connect to the one server instance that holds the state for this user or room (for example, a Durable Object on the Cloudflare adapter, which is a Cloudflare server instance that keeps state).

```typescript [client/socket.ts]
import { client, connect } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(connect(() => getRegionalUrl()))
```

The function can return a string or a `Promise<string>`:

```typescript [client/socket.ts]
import { client, connect } from '@livething/client'
import { pickHealthyRegion } from './huddle-data'
import type { HuddleSocket } from '../server/huddle-definition'

const socket = client<HuddleSocket>()(
  connect(async () => {
    const region = await pickHealthyRegion()
    return `wss://${region}.example.com/huddle`
  }),
)
```

Because the function runs again on each reconnect, failover needs very little code. Choose a different host when the current one stops answering:

```typescript [client/socket.ts]
import { client, connect, reconnection } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

const primaryUrl = 'wss://a.example.com/huddle'
const backupUrl = 'wss://b.example.com/huddle'
let useBackup = false

const socket = client<HuddleSocket>()(
  connect(() => (useBackup ? backupUrl : primaryUrl)),
  reconnection(),
)

// After a failed or dropped connection, switch to the other host.
socket.onClose((event) => {
  if (!event.wasClean) useBackup = !useBackup
})
```

When the connection drops, `reconnection()` opens a new one. The URL function runs again for that attempt and returns the other host.

## When it runs

The URL function runs once per connection attempt: on the first connect and on every reconnect. So if a region goes down and the socket reconnects, your function can return a different address. The client does not cache the result. It always uses the value your function returns for the current attempt.

This is also how an auth token reaches the server: the function puts the current token in the query string. See [Auth & Query](/client/connecting/auth-and-query).

## Async resolution and `disconnect()`

When the function is async, the client waits for it to finish before it opens the socket. If you call `disconnect()` while the URL is still resolving, that attempt is cancelled. The client ignores the resolved value and does not open a socket.

```typescript [client/socket.ts]
// With the socket from above:
socket.connect() // starts resolving the URL
socket.disconnect() // cancels the attempt; the resolved URL is ignored
```

## When resolution fails

If your URL function throws an error, its promise rejects, or it gives something other than a string, the connection attempt fails:

- The error goes to your `socket.onError` listener, unchanged. A value that is not a string gives a `LiveThingConfigError` that says so. If you have no `onError` listener, the client throws the error again on a microtask (a small task that runs right after the current code finishes). This sends it to the global error handler of the page or app, such as `window.onerror` or your error tracker. The error is never lost without a report.
- The client treats it as a failed connection. Your `socket.onClose` listeners run once with `{ code: 1006, reason: 'connection failed', wasClean: false }`, the same as for a connection that fails on the network. If you added [`reconnection()`](/client/primitives/reconnection), the client waits for a growing delay (backoff) and tries again, which calls your URL function again. Without `reconnection()`, the socket stays `closed`.

So the value of `socket.state` depends on whether `reconnection()` is installed:

```typescript [client/socket.ts]
// With the failover socket from above:
socket.onError((err) => reportError(err))

// After the URL function throws:
// - with reconnection(): socket.state.get() is 'reconnecting',
//   and your URL function will run again
// - without reconnection(): socket.state.get() is 'closed'
```

A URL function that fails sometimes is handled like an unstable network. The client retries when `reconnection()` is installed, and it reports the error to your error handler in both cases.
