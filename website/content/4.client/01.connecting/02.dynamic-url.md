Instead of a fixed string, you can pass `connect(...)` a **function** that returns the URL. The client calls it on **every** connect and reconnect, so the address can change from one attempt to the next — which is what you need for failover, load balancing, regional routing, or following a Durable Object as it migrates.

```typescript [app.ts]
const socket = client<MySocket>()(connect(() => getRegionalUrl()))
```

The function can return a string or a `Promise<string>`:

```typescript [app.ts]
const socket = client<MySocket>()(
  connect(async () => {
    const region = await pickHealthyRegion()
    return `wss://${region}.example.com/ws`
  }),
)
```

Because it runs again on each reconnect, failover falls out naturally — pick a different host once the current one stops answering:

```typescript [app.ts]
const hosts = ['wss://a.example.com/ws', 'wss://b.example.com/ws']
let i = 0

const socket = client<MySocket>()(
  connect(() => hosts[i % hosts.length]),
  reconnection(), // a drop reconnects, and the next attempt rotates to the other host
)

// On a failed connection, advance so the next attempt tries the other host.
socket.onClose((event) => {
  if (!event.wasClean) i += 1
})
```

## When it runs

The URL function runs once per connection attempt — the first connect and every reconnect. So if a region goes down and the socket reconnects, your function gets another chance to return a different address. There's nothing to cache or invalidate; the latest value is always used.

The order on each attempt is: **resolve the URL first, then append query params.** If your resolved URL already carries query parameters, the [`query()`](/client/connecting/auth-and-query) primitive adds to them (with `&`) rather than replacing them.

## Async resolution and `disconnect()`

When the function is async, the client awaits it before opening the socket. If you call `disconnect()` while a URL is still resolving, that attempt is cancelled: the resolved value is discarded and no socket opens. Each attempt is tracked internally, so a result that arrives after you've disconnected is simply ignored.

```typescript [app.ts]
socket.connect() // starts resolving the URL
socket.disconnect() // cancels it — the resolved URL is thrown away
```

## When resolution fails

If your URL function throws or its promise rejects, the attempt ends through the normal connection-failure path:

- The error is reported to `socket.onError` — or, if no `onError` listener is registered, it's rethrown out of band (on a microtask) to the host's global handler (`window.onerror` / your error tracker), never silently swallowed.
- It's treated as a failed connection (close code `1006`), so if you've installed [`reconnection()`](/client/primitives/reconnection), the client backs off and tries again — calling your function once more. Without `reconnection()`, the socket settles on `closed`.

The `socket.state` outcome follows directly from whether reconnection is installed:

```typescript [app.ts]
socket.onError((err) => report(err))

// with reconnection(): the resolver throwing leaves the socket retrying
socket.state.get() // 'reconnecting' — your URL function will be called again

// without reconnection(): it stops here
socket.state.get() // 'closed'
```

This is the same path a refused or dropped connection takes, so a flaky URL resolver behaves like a flaky network: retried when reconnection is on, surfaced to your error handler either way.
