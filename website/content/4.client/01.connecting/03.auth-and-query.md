The server decides who may connect in its [`upgrade` hook](/server/server/upgrade). This hook runs during the WebSocket handshake (the first HTTP request that opens the socket, also called the upgrade request). The client's job is to send a credential, such as a session cookie or a token, to that hook. There are two ways to do it. Which one you use depends on whether the browser can send your cookies.

## Cookie auth (same-origin)

Many apps already use cookie-based sessions, for example with Better Auth or Auth.js. In that case you don't need to configure anything on the client. The browser sends its cookies on the upgrade request automatically, in the same way it does for `fetch`. This works when the socket URL is on the **same origin** as the page. An origin is the domain and port of a URL, together with its protocol. For a socket, `wss://` counts as the match for a page on `https://` (and `ws://` for `http://`). For example, a page on `https://app.example.com` and a socket on `wss://app.example.com/ws` are on the same origin.

```typescript [client/socket.ts]
import { client, connect } from '@livething/client'
import type { HuddleSocket } from '../server/definition'

export const socket = client<HuddleSocket>()(
  connect('wss://app.example.com/ws'),
)
```

Your server reads the cookie from the upgrade request's headers. It then checks the session in the same way it does for any other HTTP request.

::warning
**Cross-origin cookies.** If the socket URL is on a different origin than the page, the browser can block the cookie. Safari and Firefox block third-party cookies, for example. For a cross-origin socket, send a token in the query string instead.
::

## Token auth with `query()`

A browser WebSocket can't set custom headers. This means you can't send an `Authorization` header the way you can with `fetch`. The common solution is to put the token in the URL's query string (the `?key=value` part at the end of a URL). The `query()` primitive does this for you:

```typescript [client/socket.ts]
import { client, connect, query } from '@livething/client'
import type { HuddleSocket } from '../server/definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/ws'),
  query(() => ({ token: getSessionToken() })),
)
// Connects to: wss://example.com/ws?token=eyJhbG...
```

`query()` takes a function that returns the params as a `Record<string, string>`. The client calls this function on **every** connect and reconnect. This is the same timing as a [dynamic URL](/client/connecting/dynamic-url). So if your app refreshes the token between two attempts, the next attempt uses the new token. You don't need to write any extra code for this.

### Refreshing an expired token

The function runs on every attempt, so you can refresh the token inside it. The function may be `async`. The client waits for it to finish before it opens the socket:

```typescript [client/socket.ts]
query(async () => {
  let token = getStoredToken()
  if (isExpired(token)) token = await refreshToken()
  return { token }
})
```

You may call `disconnect()` while an async `query()` function is still running, for example during a token refresh. In that case the client cancels that connection attempt and ignores the params the function returns. A dynamic URL function is cancelled in the same way.

The refresh can also fail: the function throws, or its promise rejects. Then the connection attempt fails in the normal way. The error goes to your `socket.onError` callbacks. If you installed [`reconnection()`](/client/primitives/reconnection), it schedules another attempt. That attempt calls your `query()` function again, so it has another chance to get a valid token.

### Multiple params

Return as many params as you need. The client URL-encodes each one (it replaces characters that are not allowed in a URL, such as spaces, with safe codes) and joins them with `&`:

```typescript [client/socket.ts]
query(() => ({
  token: getSessionToken(),
  client: 'web',
  version: '2',
}))
// wss://example.com/ws?token=eyJhbG...&client=web&version=2
```

The client adds the params **after** it resolves the URL. If the URL already has a query string, the client adds the new params to it with `&`. It does not replace the existing ones. Values must be **strings**, because the function returns a `Record<string, string>`. Convert other values yourself, for example `version: String(2)`.

## On the server

With both methods, the credential arrives at the server's `upgrade` hook. The hook reads it and returns the connection's `userId`, or it rejects the handshake. See [Upgrade](/server/server/upgrade) for the server side. That page also shows how a rejection reaches the client.
