The server decides who may connect in its [`upgrade` hook](/server/server/upgrade). This hook runs during the WebSocket handshake. The client's job is to send a credential, such as a session cookie or a token, to that hook. There are two ways to do it. Which one you use depends on whether the browser can send your cookies.

## Cookie auth (same-origin)

Many apps already use cookie-based sessions, for example with Better Auth or Auth.js. In that case you don't need to configure anything on the client. The browser sends its cookies on the upgrade request automatically, in the same way it does for `fetch`. This works when the socket URL is on the **same origin** as the page. An origin is the domain and port of a URL, together with its protocol. For a socket, `wss://` counts as the match for a page on `https://` (and `ws://` for `http://`). For example, a page on `https://app.example.com` and a socket on `wss://app.example.com/huddle` are on the same origin.

```typescript [client/socket.ts]
import { binary, client, connect } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://app.example.com/huddle'),
  binary(),
)
```

Your server reads the cookie from the upgrade request's headers. It then checks the session in the same way it does for any other HTTP request.

::warning
**Cross-origin cookies.** If the socket URL is on a different origin than the page, the browser can block the cookie. Safari and Firefox block third-party cookies, for example. For a cross-origin socket, send a token in the query string instead.
::

## Token auth in the query string

A browser WebSocket can't set custom headers. This means you can't send an `Authorization` header the way you can with `fetch`. The common solution is to put the token in the URL's query string. Pass `connect()` a [URL function](/client/connecting/dynamic-url) that builds the URL with the token:

```typescript [client/socket.ts]
import { binary, client, connect } from '@livething/client'
import { getSessionToken } from './huddle-data'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect(
    () =>
      `wss://example.com/huddle?${new URLSearchParams({ token: getSessionToken() })}`,
  ),
  binary(),
)
// Connects to: wss://example.com/huddle?token=eyJhbG...
```

The client calls this function on **every** connect and reconnect. So if your app refreshes the token between two attempts, the next attempt uses the new token. You don't need to write any extra code for this. `URLSearchParams` URL-encodes each value and joins the params with `&`.

### Refreshing an expired token

The function runs on every attempt, so you can refresh the token inside it. The function may be `async`. The client waits for it to finish before it opens the socket:

```typescript [client/socket.ts]
import { connect } from '@livething/client'

connect(async () => {
  let token = getStoredToken()
  if (isExpired(token)) token = await refreshToken()
  return `wss://example.com/huddle?${new URLSearchParams({ token })}`
})
```

You may call `disconnect()` while an async URL function is still running, for example during a token refresh. In that case the client cancels that connection attempt and ignores the URL the function returns.

The refresh can also fail: the function throws, or its promise rejects. Then the connection attempt fails in the normal way. The error goes to your `socket.onError` callbacks. If you installed [`reconnection()`](/client/primitives/reconnection), it schedules another attempt. That attempt calls your URL function again, so it has another chance to get a valid token.

### Multiple params

Put as many params as you need in the `URLSearchParams`:

```typescript [client/socket.ts]
import { connect } from '@livething/client'
import { getSessionToken } from './huddle-data'

connect(() => {
  const params = new URLSearchParams({
    token: getSessionToken(),
    client: 'web',
    version: '2',
  })
  return `wss://example.com/huddle?${params}`
})
// wss://example.com/huddle?token=eyJhbG...&client=web&version=2
```

## On the server

With both methods, the credential arrives at the server's [`upgrade` hook](/server/server/upgrade). The hook reads it and returns the connection's `userId`, or it rejects the handshake. The server docs for that hook also show how a rejection reaches the client.
