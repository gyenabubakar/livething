The server decides who may connect in its [`upgrade` hook](/server/define/env-and-upgrade), which runs during the WebSocket handshake. The client's job is to get a credential to that hook. There are two ways, depending on whether you can rely on cookies.

## Cookie auth (same-origin)

If your app already uses cookie-based sessions — Better Auth, Auth.js, Lucia, and the like — there's nothing to configure. The browser sends its cookies on the WebSocket upgrade request automatically, exactly as it does for `fetch`, as long as the socket URL is on the **same origin** as the page.

```typescript [app.ts]
const socket = client<MySocket>()(
  connect('wss://app.example.com/ws'),
)
```

Your server reads the cookie from the upgrade request's headers and validates the session just like any HTTP request.

::warning
**Cross-origin cookies.** If the socket URL is on a different origin than the page, third-party cookie restrictions in Safari and Firefox can drop the cookie. For a cross-origin socket, pass a token in the query string instead.
::

## Token auth with `query()`

Browsers can't set custom headers on a WebSocket — so unlike `fetch`, you can't send an `Authorization` header. The standard workaround is to put the token in the URL query string, and the `query()` primitive does exactly that:

```typescript [app.ts]
import { client, connect, query } from '@wskit/client'
import type { MySocket } from './socket-types'

const socket = client<MySocket>()(
  connect('wss://example.com/ws'),
  query(() => ({ token: getAuthToken() })),
)
// Connects to: wss://example.com/ws?token=eyJhbG...
```

`query()` takes a function returning a `Record<string, string>` of params. It runs on **every** connect and reconnect — the same timing as a [dynamic URL](/client/connecting/dynamic-url) — so a token that's refreshed between attempts is picked up automatically, with no extra wiring.

### Refreshing an expired token

Because the function runs each time, you can refresh inside it. It may be async, and the client awaits it before opening the socket:

```typescript [app.ts]
query(async () => {
  let token = getStoredToken()
  if (isExpired(token)) token = await refreshToken()
  return { token }
})
```

If `disconnect()` is called while an async `query()` is still resolving (a token refresh in flight, say), that attempt is cancelled and the resolved params are discarded — the same cancellation a dynamic URL gets.

If the refresh itself fails — the function throws or its promise rejects — the connection attempt ends through the normal failure path: the error reaches `socket.onError`, and [`reconnection()`](/client/primitives/reconnection) retries it if installed (calling `query()` again, with another chance to get a valid token).

### Multiple params

Return as many params as you need; they're URL-encoded and joined for you:

```typescript [app.ts]
query(() => ({ token: getAuthToken(), client: 'web', version: '2' }))
// wss://example.com/ws?token=eyJhbG...&client=web&version=2
```

Params are appended **after** the URL is resolved. If the URL already has a query string, they're added with `&` rather than overwriting it. Values must be **strings** (`query()` returns a `Record<string, string>`) — convert anything else yourself, e.g. `version: String(2)`.

## On the server

Whichever route you choose, the credential arrives at the server's `upgrade` hook, which reads it and returns the connection's identity — or rejects the handshake. See [Environment and Upgrade](/server/define/env-and-upgrade) for the server side, including how a rejection reaches the client.
