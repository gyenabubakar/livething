The server decides who may connect in its [`authenticate` hook](/server/server/authenticate). This hook runs when a connection opens. The client's job is to send a credential, such as a session cookie or a token, to that hook. There are two ways to do it. Which one you use depends on whether the browser can send your cookies.

## Cookie auth (same-origin)

Many apps already use cookie-based sessions, for example with Better Auth or Auth.js. In that case you don't need to configure anything on the client. The browser sends its cookies on the connection request automatically, in the same way it does for `fetch`. On [server-sent events](/client/connecting/connect-options#transports), the stream and its POSTs use `fetch` with its default credentials, so they send cookies to the same origin only. This works when the socket URL is on the **same origin** as the page. An origin is the domain and port of a URL, together with its protocol. For a socket, `wss://` counts as the match for a page on `https://` (and `ws://` for `http://`). For example, a page on `https://app.example.com` and a socket on `wss://app.example.com/huddle` are on the same origin.

```typescript [client/socket.ts]
import { binary, client, connect } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://app.example.com/huddle'),
  binary(),
)
```

Your server reads the cookie from the connection request's headers. It then checks the session in the same way it does for any other HTTP request.

::warning
**Cross-origin cookies.** If the socket URL is on a different origin than the page, the browser can block the cookie. Safari and Firefox block third-party cookies, for example. For a cross-origin socket, send a token with the `token` option instead.
::

::note
**Origin checks.** The server refuses a connection from a browser page on another origin with `403`, unless the origin is in the server's `allowedOrigins` option. On a WebSocket, the browser reports a failed open (close code `1006`). On [server-sent events](/client/connecting/connect-options#transports), a refused origin gets no CORS headers, so the browser reports a network error, and the client treats the transport as failed. If your page is on another origin than the server, add the page's origin to [`allowedOrigins`](/server/adapters/transports#origins-cors-and-proxies).
::

## Token auth with `token`

A browser WebSocket can't set an `Authorization` header the way `fetch` can. LiveThing works around this for you. Give `connect()` a `token` function that returns the token:

```typescript [client/socket.ts]
import { binary, client, connect } from '@livething/client'
import { getSessionToken } from './huddle-data'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle', {
    token: () => getSessionToken(),
  }),
  binary(),
)
```

The server's `authenticate` hook then reads the token from the `Authorization` header, as `Bearer <token>`, on every transport:

- On a WebSocket, the client sends the token in the handshake's `Sec-WebSocket-Protocol` header, and the server moves it to `Authorization` before `authenticate` runs. The server never sends the token back. If the request already has a real `Authorization` header, that header wins.
- On [`http()`](/client/connecting/connect-options#transports), `fetch` can set headers, so the client sends a normal `Authorization: Bearer` header when the stream opens. The POSTs that carry messages do not send the token: the server knows the connection by a secret it gave the client in the first frame.

You write no encoding and no header names. Because the token ends up in a header on every transport, it must fit in one: Latin-1 characters only, no line break, and no space or tab at the end. A JWT or any ASCII token fits. When it does not, the client throws a `LiveThingConfigError` before it connects, and does not try again.

The client calls `token` once on **every** connect attempt and reconnect attempt. When the client [moves to the next transport](/client/connecting/connect-options#failover) in the same attempt, it reuses the same token. So if your app refreshes the token between two attempts, the next attempt uses the new token. Return `null` to connect with no token.

Keep the token small. A server limits the size of all request headers together (Node allows 16 KiB by default), and a request over the limit fails with HTTP `431`.

### Refreshing an expired token

The function runs on every attempt, so you can refresh the token inside it. The function may be `async`. The client waits for it to finish before it opens the socket:

```typescript [client/socket.ts]
import { connect } from '@livething/client'
import {
  getStoredToken,
  isExpired,
  refreshToken,
} from './huddle-data'

connect('wss://example.com/huddle', {
  async token() {
    const token = getStoredToken()
    return isExpired(token) ? await refreshToken() : token
  },
})
```

You may call `disconnect()` while an async `token` function is still running. In that case the client cancels that connection attempt and ignores the token the function returns.

The refresh can also fail: the function throws, or its promise rejects. Then the connection attempt fails in the normal way. The error goes to your `socket.onError` callbacks. If you installed [`reconnection()`](/client/primitives/reconnection), it schedules another attempt. That attempt calls `token` again, so it has another chance to get a valid token.

## Params in the query string

Other values the server needs, such as the client's version, can go in the URL's query string. Pass `connect()` a [URL function](/client/connecting/dynamic-url) that builds the URL. Don't put the token there: servers and proxies often log full URLs. On `http()`, each POST goes to the exact URL of its stream, query included, so a value in the URL is sent, and can be logged, with every message.

```typescript [client/socket.ts]
import { connect } from '@livething/client'
import { getSessionToken } from './huddle-data'

connect(
  () => {
    const params = new URLSearchParams({
      client: 'web',
      version: '2',
    })
    return `wss://example.com/huddle?${params}`
  },
  { token: () => getSessionToken() },
)
// wss://example.com/huddle?client=web&version=2
```

## On the server

With both methods, the credential arrives at the server's [`authenticate` hook](/server/server/authenticate). The hook reads it and returns the connection's `userId`, or it rejects the connection. The server docs for that hook also show how a rejection reaches the client.
