An **environment** is the object that supplies the visibility and network signals `platform()` needs. It's a plain object with up to two optional methods — one for each signal — and you pass it as `platform({ environment })`.

## The shape

```typescript [environment.ts]
interface ClientEnvironment {
  // visibility: true when the app/tab is shown, false when hidden
  onVisibilityChange?(callback: (visible: boolean) => void): () => void

  // network: true when online, false when offline
  onNetworkChange?(callback: (online: boolean) => void): () => void
}
```

The model is simple: **an environment declares what it supports by implementing methods.** There's no capabilities list to maintain. Implement `onVisibilityChange` and visibility-driven behavior turns on; implement `onNetworkChange` and network-driven behavior turns on; leave one out to say "this platform can't supply that signal." Each method takes a callback and returns an unsubscribe function.

The `ClientEnvironment` type and the `environment()` helper both come from the `@wskit/client/environment` subpath — not the package root:

```typescript [imports.ts]
import { environment, WebEnvironment } from '@wskit/client/environment'
import type { ClientEnvironment } from '@wskit/client/environment'
```

## The built-in `WebEnvironment`

For a browser, you don't write any of this — import the ready-made `WebEnvironment`:

```typescript [app.ts]
import { client, connect, platform } from '@wskit/client'
import { WebEnvironment } from '@wskit/client/environment'

const socket = client<ChatSocket>()(
  connect('wss://example.com/ws'),
  platform({ environment: WebEnvironment }),
)
```

It reads `document.visibilitychange` for visibility, and `navigator.onLine` plus the `online`/`offline` window events for network. Two details worth knowing:

- **It reports the current state right away**, not only on the next change — so a client that starts offline knows it immediately, instead of assuming online until something flips.
- **It's SSR-safe.** The browser globals are read inside the subscribe calls, never at import time, so importing it on the server is harmless. Where those globals don't exist (SSR, Node, a non-DOM runtime) it simply provides no signals.

## Authoring your own

Outside the browser — React Native, Electron, a custom runtime — write an environment with the `environment(...)` helper. Implement only the signals your platform can report. Here's Electron, which has window focus but no DOM `visibilitychange`:

```typescript [electron-env.ts]
import { getCurrentWindow } from '@electron/remote'
import { environment } from '@wskit/client/environment'

export const ElectronEnvironment = environment({
  onVisibilityChange(callback) {
    const win = getCurrentWindow()
    const handler = () => callback(win.isFocused())
    win.on('focus', handler)
    win.on('blur', handler)
    return () => {
      win.off('focus', handler)
      win.off('blur', handler)
    }
  },
})
```

Then pass it like any other environment:

```typescript [app.ts]
platform({ environment: ElectronEnvironment, backgroundDisconnectMs: 30_000 })
```

A React Native environment looks the same — wire `onVisibilityChange` to `AppState` and `onNetworkChange` to NetInfo. See [React Native](/recipes/framework-hooks/react-native) for that full setup.

::note
The two contracts of an environment are independent. An environment that implements only `onNetworkChange` enables network-aware reconnection but not background disconnect — and if you ask for `backgroundDisconnectMs` on an environment with no `onVisibilityChange`, `platform()` throws a `WSKitConfigError` at setup so the mistake surfaces instead of silently doing nothing.
::
