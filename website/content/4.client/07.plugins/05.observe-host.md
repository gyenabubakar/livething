A plugin's scoped socket exposes `onIncoming(handler)` and `onOutgoing(handler)` — handlers that run before an incoming frame is dispatched, and before an outgoing frame is sent. By default they follow **least privilege**: a plugin sees only its own namespaced frames. It never sees the app's frames, and it never sees another plugin's frames.

That default is right for most plugins. A presence plugin only cares about its own messages. But some plugins — a metrics counter, a logger, an audit trail — exist _to_ watch the whole socket. For those, you opt in.

## The default: own frames only

Here is a plugin that counts every frame its handlers see. With no opt-in, it counts only its own.

```typescript [counter.ts]
import { plugin } from '@wskit/client'

export const Counter = plugin<{}, { seen: () => number }>()({
  id: 'acme:counter',
  setup(socket) {
    let seen = 0

    socket.onIncoming((message) => {
      seen += 1 // only the plugin's own incoming frames reach here
      return message
    })

    return { api: () => ({ seen: () => seen }) }
  },
})
```

The app registers it like any plugin — no extra wrapping:

```typescript [app.ts]
import { client, connect } from '@wskit/client'
import { Counter } from './counter'

const socket = client<MySocket>()(connect('wss://example.com/ws'), Counter())
```

## Opting into host traffic

To see the app's frames too, set `observesHostTraffic: true` in the plugin's definition.

```typescript [metrics.ts]
import { plugin } from '@wskit/client'

export const Metrics = plugin()({
  id: 'acme:metrics',
  observesHostTraffic: true,
  setup(socket) {
    socket.onIncoming((message) => {
      // now the app's frames reach here too
      return message
    })

    return {}
  },
})
```

`observesHostTraffic` is a privilege, and a wide one: inside a host-observing `onIncoming`/`onOutgoing` handler, the value you return replaces the app's own frame before anything downstream sees it, and throwing `Block` drops or cancels the app's own frame the same as your own. So WSKit makes the app grant it on purpose. When `observesHostTraffic` is the literal `true`, **registering the plugin bare is a compile error** — you must wrap it with `observeHost(...)`.

::code-group

```typescript [granted.ts]
import { client, connect, observeHost } from '@wskit/client'
import { Metrics } from './metrics'

const socket = client<MySocket>()(
  connect('wss://example.com/ws'),
  observeHost(Metrics()), // privilege granted on purpose
)
```

```typescript [error.ts]
import { client, connect } from '@wskit/client'
import { Metrics } from './metrics'

const socket = client<MySocket>()(
  connect('wss://example.com/ws'),
  // ✗ compile error: this plugin observes host traffic — wrap it in observeHost(...)
  Metrics(),
)
```

::

The check is a phantom **brand** — a property that exists only in the type, never at runtime — carried on the object `Metrics()` returns. When `observesHostTraffic` is `true` as a literal, that object's type carries a `__requiresHostGrant` field naming the fix, and `client()`'s parameter type rejects any argument carrying it, so a bare `Metrics()` fails to compile. `observeHost(...)` strips that field from the type and, at runtime, stamps a `__hostObservationGranted` flag on the same object — the plugin's `setup` reads that flag (alongside `observesHostTraffic`) to decide whether its handlers see host traffic.

If the compile check is bypassed — say `observesHostTraffic` came from a non-literal boolean, so the brand never fired — `client()` still checks the grant at runtime. An ungranted host-observing plugin throws a clear error naming the plugin and telling you to wrap it in `observeHost(...)`. When the grant _is_ present, `client()` logs a one-time warning that the plugin can see the app's frames, so the privilege is never silent.

::caution
`observeHost(...)` only changes what the plugin **observes**. It does not let the plugin's handlers see another plugin's frames — that boundary holds no matter what. A host-observing plugin sees its own frames plus the app's, and nothing else.
::

## What sees what

| Handler owner                    | Its own frames | The app's frames   | Another plugin's frames |
| -------------------------------- | -------------- | ------------------ | ----------------------- |
| The app                          | —              | yes (it owns them) | **no**                  |
| A plugin (default)               | yes            | **no**             | no                      |
| A plugin with `observeHost(...)` | yes            | **yes**            | no                      |

Each plugin claims and dispatches its own namespaced frames before the app-level pipeline runs, so the app's own [`intercept()`](/client/primitives/intercept) never sees a frame a plugin already consumed — see [Namespacing and matching](/client/plugins/namespacing-and-matching#the-plugin-owns-its-whole-namespace). A plugin starts locked to its own slice and only widens to the app's frames with an explicit grant. The cross-plugin wall never opens, on either side: no plugin sees another plugin's frames, and the app never sees a frame a plugin has already claimed.

## Matching frames inside the handler

A host-observing handler receives a `WireMessage` — `{ event, payload }` — for every frame, its own and the app's alike, always under its **wire** name. A frame the plugin owns carries the plugin's namespace prefix, `__<id>::<name>`; anything else is the app's. Match on that prefix to tell the two apart:

```typescript [rewrite-own-vs-app.ts]
import { plugin } from '@wskit/client'

const OWN_PREFIX = '__acme:metrics::'

export const Metrics = plugin()({
  id: 'acme:metrics',
  observesHostTraffic: true,
  setup(socket) {
    socket.onIncoming((message) => {
      if (!message.event.startsWith(OWN_PREFIX)) {
        // an app frame — only visible because this plugin observes host traffic
        return message
      }
      return message
    })

    return {}
  },
})
```

::note
Errors follow the same rule. A server-pushed error whose `code` starts with the plugin's own `__<id>::` prefix is always claimed by the plugin, opt-in or not — see [Plugin errors](/client/plugins/errors) for how a plugin's `onError` receives it with the prefix stripped. Only an error the plugin does **not** own needs `observesHostTraffic` to reach its handler at all.
::

Server plugins have the equivalent grant — see [Observing host traffic](/server/plugins/observe-host) on the server side. The gate is the same shape on both sides (an own-namespace check, widened by an explicit opt-in flag), but the server additionally tags every frame with a `frame.owner` field; the client has no such field, so a host-observing handler reads the plugin's own prefix off `message.event` directly, as shown above.
