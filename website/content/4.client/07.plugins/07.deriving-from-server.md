A plugin has two halves. The server half is `plugin('acme:polls', { definition })`, from `@livething/server/plugins`. The client half is `plugin<Wire>()({ id: 'acme:polls', setup })`, from `@livething/client`. Both halves must agree on the same `Wire` type. `Wire` is the plugin's contract: the shape of everything the plugin sends and receives.

Some projects own both halves. This is a **full-stack app**: the same codebase builds the server and the client. In a full-stack app you don't write that shape twice. You derive (compute) the client's `Wire` type from the server plugin. Then, when someone changes the server plugin's contract, the client code gives a compile error. Without this, the two halves could stop matching and nothing would tell you.

## `InferPluginClient`

`InferPluginClient` is a type exported from `@livething/server/plugins`. It reads a server plugin's contract and flips it into the shape a client plugin expects. "Flip" means the direction changes: what the server receives becomes what the client sends, and what the server sends becomes what the client receives. [`InferClient`](/core/isomorphic-code) does the same flip for a whole app. `InferPluginClient` does it for one plugin.

Use it in the **server** file, next to the plugin it reads, and export the result. You use `InferClient` the same way: you call it on the server and export the type for the client to import. The client half then imports one plain type and nothing from `@livething/server`.

```typescript [polls/server.ts]
import { emits, server, t } from '@livething/server'
import { clientRequests } from '@livething/server/client-requests'
import { plugin } from '@livething/server/plugins'
import * as v from 'valibot'
import type { InferPluginClient } from '@livething/server/plugins'

const h = server({
  scope: 'plugin',
  capabilities: [
    clientRequests(),
    emits({
      'poll-updated': t<{
        pollId: string
        tally: Record<string, number>
      }>(),
    }),
  ],
})

const createPoll = h.request('create-poll', {
  input: v.object({
    question: v.string(),
    options: v.array(v.string()),
  }),
  run(ctx, input) {
    const pollId = createPollRow(input.question, input.options)
    return { pollId }
  },
})

const vote = h.request('vote', {
  input: v.object({ pollId: v.string(), option: v.string() }),
  run(ctx, input) {
    const tally = recordVote(input.pollId, input.option)
    ctx.broadcast('poll-updated', { pollId: input.pollId, tally })
    return { ok: true as const }
  },
})

const definition = h.assemble({
  handlers: [createPoll, vote],
})

export const Polls = plugin('acme:polls', { definition })

export type PollsWire = InferPluginClient<typeof Polls>
```

```typescript [polls/client.ts]
import { clientRequests, plugin } from '@livething/client'
import type { PollsWire } from './server'

interface PollsApi {
  create(
    question: string,
    options: string[],
  ): Promise<{ pollId: string }>
  vote(pollId: string, option: string): Promise<{ ok: true }>
}

export const PollsClient = plugin<PollsWire, PollsApi>()({
  id: 'acme:polls',
  dependencies: [clientRequests],
  setup(socket) {
    return {
      api: () => ({
        create: (question, options) =>
          socket.request('create-poll', { question, options }),
        vote: (pollId, option) =>
          socket.request('vote', { pollId, option }),
      }),
    }
  },
})
```

`PollsWire` is the contract for `acme:polls`, with plain names (no `__acme:polls::` prefix). It has `clientRequests` entries for `create-poll` and `vote` (what the client sends and gets back) and an `incoming` entry for `poll-updated` (what the client receives). You could write this contract by hand, but then you must keep it in sync with the server plugin yourself. `InferPluginClient<typeof Polls>` reads it from the server plugin's type instead. If someone renames an event or changes a payload shape on the server, the client gets a type error at compile time. You don't find the bug at runtime.

`InferPluginClient` accepts two inputs, and both give the same wire type:

- the plugin factory itself: `typeof Polls` (the function that `plugin(...)` returns)
- the capability that the factory produces: `ReturnType<typeof Polls>`

## When server and client share the app contract

Some full-stack apps already share the whole app's contract through [`InferClient`](/core/isomorphic-code). `InferClient` turns a `ServerDefinition` into the client's view of every event, request, stream, and channel that the server has, including the ones from plugins. Say you already have that type, as `AppContract = InferClient<typeof host>`. Then two types exported from `@livething/client` can take one plugin's part back out of it. You don't need to derive each plugin's contract again.

`PluginSlice<AppContract, 'acme:polls'>` gives you only that plugin's names, with the `__acme:polls::` wire prefix removed:

```typescript [polls/client.ts]
import { clientRequests, plugin } from '@livething/client'
import type { PluginSlice } from '@livething/client'
import type { AppContract } from './server'

type PollsWire = PluginSlice<AppContract, 'acme:polls'>

interface PollsApi {
  vote(pollId: string, option: string): Promise<{ ok: true }>
}

export const Polls = plugin<PollsWire, PollsApi>()({
  id: 'acme:polls',
  dependencies: [clientRequests],
  setup(socket) {
    return {
      api: () => ({
        vote: (pollId, option) =>
          socket.request('vote', { pollId, option }),
      }),
    }
  },
})
```

`TopLevelContract<AppContract, 'acme:polls'>` is the opposite view. It is the whole app contract with the `acme:polls` names removed. What is left is the part the app itself can reach on the socket. You don't have to apply it yourself: you pass the full `AppContract` to `client<...>()`, and `client()` removes the names of every plugin you register. Use `TopLevelContract` only when you need to write that type in your own code.

```typescript [client/socket.ts]
import { client, connect } from '@livething/client'
import { Polls } from '../polls/client'
import type { AppContract } from './server'

export const socket = client<AppContract>()(
  connect('wss://example.com/huddle'),
  clientRequests(),
  Polls(),
)

// Type error: `acme:polls` owns this name. Use Polls.use(socket).vote() instead.
socket.request('__acme:polls::vote', {
  pollId: 'poll_1',
  option: 'Yes',
})
```

This is the same split that [Namespacing and Matching](/client/plugins/namespacing-and-matching) describes. `PluginSlice` and `TopLevelContract` do it at the type level, so you don't write the split by hand.

`client()` also checks the other direction. For each plugin you register, the socket's contract must contain every name in the plugin's contract, under its `__<id>::` prefix. If a name is missing, `client()` gives a type error. LiveThing builds this check from the plugin's own wire type, so you don't write it yourself.

## A hand-written slice, for comparison

Not every client plugin has its server half in the same codebase. Sometimes you own only the client plugin, and it talks to a server plugin defined somewhere else. In that case, the wire shape is still a plain object type. You write it by hand to match the server's contract:

```typescript [polls/wire.ts]
interface PollsWire {
  incoming: {
    'poll-updated': { pollId: string; tally: Record<string, number> }
  }
  clientRequests: {
    'create-poll': {
      payload: { question: string; options: string[] }
      response: { pollId: string }
    }
    vote: {
      payload: { pollId: string; option: string }
      response: { ok: true }
    }
  }
  streams: {
    'poll-history': {
      payload: { before: number }
      chunk: { pollId: string; question: string }
    }
  }
  channels: {
    'poll-room': {
      addressing: 'dynamic'
      incoming: { 'tally-changed': { tally: Record<string, number> } }
    }
  }
}
```

`InferPluginClient<typeof Polls>` would give the same shape if the server plugin were in this codebase. A full-stack app would derive `PollsWire` instead of writing it. Either way, you pass the wire type to `plugin<PollsWire>()({ id, setup })`. The compiler then checks every `socket.on`, `socket.send`, `socket.request`, `socket.stream`, and `socket.channel` call inside `setup` against those plain names. The verbs that come from a primitive also need that primitive. See [Declaring primitive dependencies](/client/plugins/defining#declaring-primitive-dependencies).
