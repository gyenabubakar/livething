A plugin has two halves: a server half (`plugin('acme:presence', { handler, api })`, from `@wskit/server/plugin`) and a client half (`plugin<Wire, Api>()({ id: 'acme:presence', setup })`, from `@wskit/client`). Both must agree on the same `Wire` — the shape of what the plugin sends and receives. When one project owns both halves (a **full-stack app**, meaning the same codebase builds the server and the client), you don't hand-write that shape twice. You derive the client's `Wire` type from the server plugin, so a change to the server plugin's contract is a compile error on the client side instead of a silent mismatch.

## `InferPluginClient`

`InferPluginClient` is a type exported from `@wskit/server/plugin`. It reads a server plugin's contract and flips it into the shape a client plugin expects — the same flip [`InferClient`](/core/isomorphic-code) does for a whole app, but for one plugin's slice.

```typescript [server-plugin.ts]
import { define, emits, t } from '@wskit/server'
import { plugin } from '@wskit/server/plugin'
import * as v from 'valibot'

const h = define({
  scope: 'plugin',
  capabilities: [emits({ 'user-online': t<{ id: string }>() })],
})

const heartbeat = h.on('heartbeat', {
  input: v.object({}),
  run(ctx) {
    ctx.send('user-online', { id: ctx.connection.id })
  },
})

const handler = h.assemble({
  handlers: [heartbeat],
  api: (ctx) => ({
    ping() {
      ctx.send('user-online', { id: ctx.connection.id })
    },
  }),
})

export const Presence = plugin('acme:presence', { handler })
```

```typescript [client-plugin.ts]
import { plugin } from '@wskit/client'
import type { InferPluginClient } from '@wskit/server/plugin'
import { Presence } from './server-plugin'

type PresenceWire = InferPluginClient<typeof Presence>

interface PresenceApi {
  ping(): void
}

export const PresenceClient = plugin<PresenceWire, PresenceApi>()({
  id: 'acme:presence',
  setup(socket) {
    return {
      api: () => ({
        ping: () => socket.send('heartbeat', {}),
      }),
    }
  },
})
```

`PresenceWire` is the plain-name contract for `acme:presence` — an `outgoing` entry for `heartbeat` (what the client sends), an `incoming` entry for `user-online` (what the client receives), and so on. Writing that contract by hand means keeping it synced with the server plugin by eye; `InferPluginClient<typeof Presence>` reads it straight from the server plugin's type, so a renamed event or a changed payload shape shows up as a client-side type error, not a bug you find at runtime.

`InferPluginClient` accepts either the plugin factory itself (`typeof Presence`, the function `plugin(...)` returns) or the capability it produces (`ReturnType<typeof Presence>`) — both resolve to the same wire type.

## When server and client share the app contract

Some full-stack apps go further and already share the whole app's contract through [`InferClient`](/core/isomorphic-code) — the type that turns a `ServerDefinition` into the client's view of every event, request, stream, and channel the server exposes, plugins included. If you already have that type (call it `AppContract = InferClient<typeof host>`), two helpers exported from `@wskit/client` pull a single plugin's slice back out of it, instead of you re-deriving it plugin by plugin.

`PluginSlice<AppContract, 'acme:chat'>` returns just that plugin's names, with the `__acme:chat::` wire prefix removed:

```typescript [client-plugin.ts]
import { plugin } from '@wskit/client'
import type { PluginSlice } from '@wskit/client'
import type { AppContract } from './server'

type ChatWire = PluginSlice<AppContract, 'acme:chat'>

interface ChatApi {
  send(text: string): void
}

export const Chat = plugin<ChatWire, ChatApi>()({
  id: 'acme:chat',
  setup(socket) {
    return {
      api: () => ({
        send: (text) => socket.send('message', { text }),
      }),
    }
  },
})
```

`TopLevelContract<AppContract, 'acme:chat'>` is the reverse view: the whole app contract with `acme:chat`'s namespaced names removed, so the type you pass to `client<...>()` matches what's left for the app to reach directly once the plugin claims its namespace. This is the same split covered in [Namespacing and Matching](/client/plugins/namespacing-and-matching) — `PluginSlice` and `TopLevelContract` just give you a type-level shortcut instead of writing the split by hand. `NamespacedContract` is the related internal type `client()` checks a socket's contract against when a plugin declares dependencies; you don't write it yourself, it's inferred from the plugin's own wire type.

## A hand-written slice, for comparison

Not every client plugin has a server counterpart in the same codebase — sometimes the client plugin is the one thing you own, talking to a server plugin defined elsewhere. In that case the wire shape is still just a plain object type, written by hand to match the server's contract:

```typescript [feed-plugin.ts]
interface FeedWire {
  incoming: { welcome: { name: string } }
  outgoing: { hello: { name: string } }
  clientRequests: {
    echo: { payload: { text: string }; response: { echoed: string } }
  }
  streams: {
    feed: { payload: { from: number }; chunk: { row: number } }
  }
  channels: {
    room: {
      outgoing: { chat: { text: string } }
      incoming: { joined: { who: string }; said: { text: string } }
    }
  }
}
```

This is exactly what `InferPluginClient<typeof Feed>` would produce if the server plugin were reachable from this codebase — a full-stack app would derive `FeedWire` instead of writing it out. Whichever way you arrive at the wire type, it's what you pass to `plugin<FeedWire, Api>()({ id, setup })`: the compiler holds `setup`'s `socket.on`, `socket.send`, `socket.request`, `socket.stream`, and `socket.channel` calls to those plain names.
