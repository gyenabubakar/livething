A **plugin** owns a slice of the wire under its own name, called a **namespace** — a prefix (like `__e2e:feed::`) the framework adds to every event the plugin sends or listens for, so its names never collide with the app's or another plugin's. You author one with `plugin()`.

## The two-step factory

`plugin()` is called in two steps, the same split `client()` uses and for the same reason: TypeScript can't infer the contract type while you write it by hand, so the first call names it and the second call takes the definition.

```typescript [feed-plugin.ts]
import {
  channels,
  clientRequests,
  plugin,
  stream,
} from '@wskit/client'

const Feed = plugin<FeedWire>()({
  id: 'e2e:feed',
  dependencies: [clientRequests, stream, channels],
  setup(socket) {
    // wire up handlers, return the API
  },
})
```

`FeedWire` is the plugin's own **contract** — the events, requests, streams, and channels it owns, written in plain names (no namespace prefix). It's the same shape a `client<...>()` contract takes. A plugin that owns no wire names at all needs nothing here, so it's just `plugin()`.

You don't name the plugin's API type. It is read from whatever `setup` returns, so `Feed.use(socket)` already has the right shape. Name it yourself, as a second type argument, only when you want to hold the API to an interface you wrote:

```typescript [feed-plugin.ts]
const Feed = plugin<FeedWire, FeedApi>()({
  id: 'e2e:feed',
  setup(socket) {
    // `setup` must now return an api matching FeedApi exactly
  },
})
```

The second call takes the definition object. Its `id` — `'e2e:feed'` above — is inferred as a **literal type**, not widened to `string`. That's how the app socket knows which namespace this exact plugin claims: registering `Feed()` on a socket tells TypeScript the socket now owns every `__e2e:feed::…` name in its contract.

## What `setup` returns

`setup(socket)` runs once, when the socket is built. It wires up the plugin's handlers on the scoped `socket` it's given, then returns a `PluginInstance` — an object with two optional fields:

```typescript [feed-plugin.ts]
interface FeedApi {
  onWelcome(cb: (name: string) => void): void
  hello(name: string): void
}

const Feed = plugin<FeedWire, FeedApi>()({
  id: 'e2e:feed',
  setup(socket) {
    const welcomeCbs = new Set<(name: string) => void>()
    socket.on('welcome', (m) =>
      welcomeCbs.forEach((cb) => cb(m.name)),
    )

    return {
      api: () => ({
        onWelcome: (cb) => void welcomeCbs.add(cb),
        hello: (name) => void socket.send('hello', { name }),
      }),
      dispose: () => welcomeCbs.clear(),
    }
  },
})
```

- **`api`** is a factory function — `() => TApi` — that builds the object `Plugin.use(socket)` returns. It does **not** run when `setup` runs. It runs **lazily**, the first time anything calls `Feed.use(socket)`, and the same instance is reused after that — a second `.use()` call gets back the exact object the first call built.
- **`dispose`** runs once, when the socket is finished for good: either reconnection has been given up on, or the app closed the socket on purpose. It does **not** run on a normal drop that's about to reconnect — the plugin stays alive across that gap so it doesn't lose its state mid-reconnect.

Both fields are optional. A plugin that only watches the message pipeline — logging, metrics, rewriting frames — can return `{}` and skip both:

```typescript [logger-plugin.ts]
const Logger = plugin()({
  id: 'acme:logger',
  setup(socket) {
    socket.onIncoming((message) => {
      console.info('in', message.event)
      return message
    })
    return {}
  },
})
```

### The lazy-socket caveat

If the socket is **lazy** — it connects only when something first needs it, rather than immediately — no close is ever truly final. An idle-close and an intentional `disconnect()` look the same from inside the plugin, and either one might reopen the socket later. On a lazy socket, `dispose` does not run automatically.

Because of that, don't rely on `dispose` for cleanup on a lazy socket. Tie your cleanup to the unsubscribe function your own `socket.on(...)` calls return instead:

```typescript [logger-plugin.ts]
const Logger = plugin()({
  id: 'acme:logger',
  setup(socket) {
    const unsubscribe = socket.on('ping', () => console.info('ping'))

    return {
      dispose: () => unsubscribe(), // may never run on a lazy socket
    }
  },
})
```

## Declaring primitive dependencies

A plugin's scoped `socket` can carry primitive-backed verbs — `request`, `stream`, `channel`, and so on — typed from the plugin's own contract. But those verbs only work at runtime if the app actually registered the matching primitive on `client()`. List every primitive the plugin needs in `dependencies`:

```typescript [feed-plugin.ts]
import {
  channels,
  clientRequests,
  plugin,
  stream,
} from '@wskit/client'

const Feed = plugin<FeedWire, FeedApi>()({
  id: 'e2e:feed',
  dependencies: [clientRequests, stream, channels], // not clientRequests(), stream(), channels()
  setup(socket) {
    // socket.request(...), socket.stream(...), socket.channel(...) are now safe to call
  },
})
```

Pass the primitive's **factory value** — `clientRequests`, not `clientRequests()`. WSKit reads the factory's static `tag` property to know what the plugin needs, without calling the factory (calling a configured factory with no arguments could throw or run side effects, so `dependencies` never does that).

| Scoped verb                          | Needs this primitive |
| ------------------------------------ | -------------------- |
| `request`                            | `clientRequests`     |
| `stream`, `onStream`, `resumeStream` | `stream`             |
| `channel`                            | `channels`           |
| `onRequest`                          | `serverRequests`     |

If the app forgets to register a primitive the plugin depends on, calling the matching verb throws at runtime with a message naming exactly what's missing:

```
[wskit] plugin 'e2e:feed' used socket.request(), but the clientRequests primitive isn't registered. List clientRequests in the plugin's dependencies and register clientRequests() in client().
```

Listing the primitive in `dependencies` doesn't install it by itself — the app still has to pass the primitive's call (`clientRequests()`, not just the factory) to `client()`. `dependencies` only lets WSKit check that it did, and order the primitive ahead of the plugin.

## Registering and using it

Pass the plugin's call — `Feed()` — to `client()` alongside the primitives it depends on. Registration order doesn't matter: WSKit orders any primitive a plugin depends on ahead of the plugin, and every primitive's hooks run before every plugin's hooks, regardless of the order you list them in.

```typescript [app.ts]
import {
  channels,
  client,
  clientRequests,
  connect,
  stream,
} from '@wskit/client'
import { Feed } from './feed-plugin'

const socket = client<FeedHost>()(
  connect('wss://example.com/ws'),
  clientRequests(),
  stream(),
  channels(),
  Feed(),
)
```

Read the plugin's API with `Feed.use(socket)`. This is a separate step from registering — registering wires the plugin's hooks onto the socket right away, but the API is built the first time `.use()` is called:

```typescript [app.ts]
const feed = Feed.use(socket)

feed.onWelcome((name) => console.info(`welcome, ${name}`))
feed.hello('alice')
```
