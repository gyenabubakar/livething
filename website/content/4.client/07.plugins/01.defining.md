A **plugin** owns a part of the wire under its own name. This part is called a **namespace**. It is a prefix (like `__acme:feed::`) that the framework adds to every event the plugin sends or listens for. Because of the prefix, a plugin's names never collide with the app's names or with another plugin's names. You create a plugin with `plugin()`.

A plugin has its own **contract**: a TypeScript type that lists the events, requests, streams and channels the plugin owns. You write the names in plain form, without the namespace prefix. It has the same shape as the contract you pass to `client<...>()`. The examples on this page use this contract for a polls plugin:

```typescript [polls-wire.ts]
import type { SocketContract } from '@livething/client'

export interface PollsWire extends SocketContract {
  incoming: {
    'poll-updated': { pollId: string; tally: Record<string, number> }
  }
  outgoing: { 'watch-poll': { pollId: string } }
  clientRequests: {
    'create-poll': {
      payload: { question: string; options: string[] }
      response: { pollId: string }
    }
  }
  streams: {
    'poll-history': {
      payload: { before: number }
      chunk: { pollId: string; question: string }
    }
  }
  channels: {
    'poll-room': {
      addressing: 'dynamic'
      incoming: { 'tally-changed': { tally: Record<string, number> } }
      outgoing: {}
    }
  }
}
```

## The two-step factory

You call `plugin()` in two steps. `client()` uses the same split, for the same reason: TypeScript can't infer some type arguments while you write others by hand. So the first call names the contract type, and the second call takes the definition.

```typescript [polls-plugin.ts]
import {
  channels,
  clientRequests,
  plugin,
  stream,
} from '@livething/client'
import type { PollsWire } from './polls-wire'

const Polls = plugin<PollsWire>()({
  id: 'acme:polls',
  dependencies: [clientRequests, stream, channels],
  setup(socket) {
    // register handlers, return the API
  },
})
```

A plugin that owns no wire names needs no contract, so you write just `plugin()`.

You don't need to write the plugin's API type. TypeScript reads it from what `setup` returns, so `Polls.use(socket)` already has the right type. Pass the API type yourself, as a second type argument, only when you want the API to match an interface you wrote:

```typescript [polls-plugin.ts]
const Polls = plugin<PollsWire, PollsApi>()({
  id: 'acme:polls',
  setup(socket) {
    // `setup` must now return an API that matches PollsApi
  },
})
```

The second call takes the definition object. TypeScript infers its `id` (`'acme:feed'` above) as a **literal type**: the exact string `'acme:feed'`, not the general type `string`. This is how the app socket knows which namespace this plugin claims. When you register `Feed()` on a socket, TypeScript moves every `__acme:feed::…` name in the app's contract to the plugin. The app socket can no longer use those names directly.

## What `setup` returns

`setup(socket)` runs once, when the socket is built. It receives a **scoped socket**: a socket that works only inside the plugin's namespace, so you use plain names. `setup` registers the plugin's handlers on it, then returns a `PluginInstance`. This is an object with two optional fields:

```typescript [polls-plugin.ts]
interface PollsApi {
  onUpdate(
    cb: (pollId: string, tally: Record<string, number>) => void,
  ): void
  watch(pollId: string): void
}

export const Polls = plugin<PollsWire, PollsApi>()({
  id: 'acme:polls',
  setup(socket) {
    const updateCbs = new Set<
      (pollId: string, tally: Record<string, number>) => void
    >()
    socket.on('poll-updated', (m) =>
      updateCbs.forEach((cb) => cb(m.pollId, m.tally)),
    )

    return {
      api: () => ({
        onUpdate: (cb) => void updateCbs.add(cb),
        watch: (pollId) => void socket.send('watch-poll', { pollId }),
      }),
      dispose: () => updateCbs.clear(),
    }
  },
})
```

- **`api`** is a factory function (`() => TApi`) that builds the object `Feed.use(socket)` returns. It does **not** run when `setup` runs. It runs **lazily**: only the first time something calls `Feed.use(socket)`. After that, every `.use()` call returns the same object that the first call built.
- **`dispose`** runs once, when the socket is closed for good. This happens when reconnection has stopped trying, or when the app closed the socket on purpose. It does **not** run on a normal drop that will reconnect. The plugin stays alive during that gap, so it keeps its state while the socket reconnects.

Both fields are optional. A plugin that only watches the message pipeline (for logging, metrics, or changing frames) can return `{}`:

```typescript [logger-plugin.ts]
const Logger = plugin()({
  id: 'acme:logger',
  setup(socket) {
    socket.onIncoming((message) => {
      console.info('in', message.event)
      return message
    })
    return {}
  },
})
```

### `dispose` on a lazy socket

A **lazy** socket connects only when something first needs it, not right away (see [`lazy`](/client/connecting/connect-options#lazy)). A lazy socket can always open again, so no close is final. Inside the plugin, a close because the socket was idle and a close from `disconnect()` look the same, and after either one the socket may open again later. For this reason, `dispose` does not run automatically on a lazy socket.

So on a lazy socket, don't put cleanup in `dispose`. Every `socket.on(...)` call returns an unsubscribe function. Keep it, and give the app a way to call it when the app is done with the plugin:

```typescript [polls-plugin.ts]
import { plugin } from '@livething/client'

interface PollsWire {
  incoming: {
    'poll-updated': { pollId: string; tally: Record<string, number> }
  }
}

const Polls = plugin<PollsWire>()({
  id: 'acme:polls',
  setup(socket) {
    const updates: {
      pollId: string
      tally: Record<string, number>
    }[] = []
    const unsubscribe = socket.on('poll-updated', (m) =>
      updates.push(m),
    )

    return {
      api: () => ({
        all: () => updates.slice(),
        stop: () => unsubscribe(),
      }),
    }
  },
})
```

The app calls `Polls.use(socket).stop()` when it no longer needs the poll updates.

## Declaring primitive dependencies

A **primitive** is a built-in socket feature that you register on `client()`, such as `clientRequests()` or `channels()`. The plugin's scoped socket can have verbs that come from primitives (`request`, `stream`, `channel`, and others). Their types come from the plugin's own contract. But at runtime, each of those verbs works only if the app registered the matching primitive on `client()`. List every primitive the plugin needs in `dependencies`:

```typescript [polls-plugin.ts]
import {
  channels,
  clientRequests,
  plugin,
  stream,
} from '@livething/client'
import type { PollsWire } from './polls-wire'

const Polls = plugin<PollsWire, PollsApi>()({
  id: 'acme:polls',
  dependencies: [clientRequests, stream, channels], // not clientRequests(), stream(), channels()
  setup(socket) {
    // socket.request(...), socket.stream(...) and socket.channel(...) are safe to call
  },
})
```

Pass the primitive's **factory value**: `clientRequests`, not `clientRequests()`. LiveThing reads the factory's static `tag` property to learn what the plugin needs. It never calls the factory, because calling a factory that expects options with no arguments could throw or have side effects.

| Scoped verb                          | Needs this primitive |
| ------------------------------------ | -------------------- |
| `request`                            | `clientRequests`     |
| `stream`, `onStream`, `resumeStream` | `stream`             |
| `channel`                            | `channels`           |
| `onRequest`                          | `serverRequests`     |

`dependencies` does not install anything. The app must still pass the primitive's call (`clientRequests()`, not the factory) to `client()`. `dependencies` lets LiveThing check that the app did this, and run the primitive before the plugin.

When the app does not register a listed primitive, `client()` throws when it builds the socket:

```text
[livething] acme:polls requires clientRequests. Register clientRequests() in client.
```

When the plugin uses a verb whose primitive is neither listed nor registered, the socket builds, but calling that verb throws. The message names what is missing:

```text
[livething] plugin 'acme:polls' used socket.request(), but the clientRequests primitive isn't registered. List clientRequests in the plugin's dependencies and register clientRequests() in client().
```

Listing every dependency is the better choice, because the mistake then shows up as soon as the app starts, not later when a user triggers the verb.

## Registering and using it

Pass the plugin's call, `Polls()`, to `client()` together with the primitives it depends on. The app contract (`HuddleWithPolls` below) must include the plugin's names in their namespaced form, such as `__acme:polls::poll-updated`. [Deriving a contract from the server](/client/plugins/deriving-from-server) shows how to get this type from your server code.

The order of primitives and plugins in the list doesn't matter. LiveThing runs every primitive's hooks before every plugin's hooks, and it runs the primitives a plugin depends on before that plugin. Plugins run in the order you list them.

```typescript [client/socket.ts]
import {
  channels,
  client,
  clientRequests,
  connect,
  stream,
} from '@livething/client'
import { Polls } from './polls-plugin'

export const socket = client<HuddleWithPolls>()(
  connect('wss://example.com/huddle'),
  clientRequests(),
  stream(),
  channels(),
  Polls(),
)
```

Get the plugin's API with `Polls.use(socket)`. This is a separate step from registering. Registering adds the plugin's hooks to the socket right away. The API is built the first time you call `.use()`:

```typescript [client/socket.ts]
const polls = Polls.use(socket)

polls.onUpdate((pollId, tally) =>
  console.info(`poll ${pollId} updated`, tally),
)
polls.watch('poll_1')
```
