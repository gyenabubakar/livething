`setup(socket)` receives a **`PluginSocket`**. It has the same methods as the app socket (`on`, `send`, `request`, `channel`, `stream`, `onStream`, `resumeStream`, `onRequest`). The difference: it is typed to the plugin's own contract, and it is scoped to the plugin's namespace (the part of the wire that belongs only to this plugin). You write **plain names**, like `socket.on('notification', ...)` or `socket.send('mark-read', ...)`. LiveThing adds the `__<id>::` prefix on the wire for you. See [Namespacing and matching](/client/plugins/namespacing-and-matching) for how that prefix works.

Every example below uses one contract, for a notifications plugin:

```typescript [notifications-wire.ts]
import type { SocketContract } from '@livething/client'

export interface NotificationsWire extends SocketContract {
  incoming: { notification: { title: string } }
  outgoing: {
    'mark-read': { notificationId: string }
    hello: { device: string }
    resync: {}
  }
  clientRequests: {
    'unread-count': {
      payload: { topic: string }
      response: { count: number }
    }
  }
  streams: {
    history: {
      payload: { before: number }
      chunk: { id: string; title: string }
    }
  }
  serverRequests: {
    'device-info': {
      payload: {}
      response: { platform: string }
    }
  }
}
```

The examples use the plugin ID `acme:notifications`. The convention for a plugin ID is `vendor:name`, with a single colon. An ID that contains `::` throws an error when you call `plugin()`, because `::` separates the ID from the event name on the wire.

A method only exists on `socket` when the plugin's contract declares the matching section. For example, a contract with no `serverRequests` gets no `onRequest`. Calling it is a compile error, not a runtime error. Most methods also need their primitive registered on the host `client()`. See [Declaring primitive dependencies](/client/plugins/defining#declaring-primitive-dependencies) for the full list.

## Messaging: `on` and `send`

A contract with `incoming` gets `socket.on(...)`. A contract with `outgoing` gets `socket.send(...)`. Neither needs a dependency. They work with no primitives registered at all.

```typescript [notifications-plugin.ts]
import { plugin } from '@livething/client'
import type { NotificationsWire } from './notifications-wire'

export const Notifications = plugin<
  NotificationsWire,
  { markRead(notificationId: string): boolean }
>()({
  id: 'acme:notifications',
  setup(socket) {
    // 'notification' arrives on the wire as __acme:notifications::notification
    socket.on('notification', (message) =>
      console.info('new notification', message.title),
    )

    return {
      api: () => ({
        // 'mark-read' goes out as __acme:notifications::mark-read
        // returns true if the message was sent or buffered
        markRead: (notificationId) =>
          socket.send('mark-read', { notificationId }),
      }),
    }
  },
})
```

While a `socket.on(...)` listener is registered, it **keeps the socket open**, the same way the top-level `on()` does. So on a lazy socket, a plugin that only receives messages does not lose its connection to the idle timeout (see [`idleTimeout`](/client/connecting/connect-options#idletimeout)). `socket.on(...)` returns an unsubscribe function. Calling it removes the listener and stops keeping the socket open.

`socket.send(...)` returns `true` if the message was handed to the socket or buffered. It returns `false` if the message was dropped before it was sent. This is the same meaning as the top-level `send()`.

## `request`: needs `clientRequests`

A contract with a `clientRequests` section gets `socket.request(...)`, typed from the plugin's own `clientRequests` map. It needs the `clientRequests()` primitive registered on the host.

```typescript [notifications-plugin.ts]
import { clientRequests, plugin } from '@livething/client'
import type { NotificationsWire } from './notifications-wire'

export const Notifications = plugin<
  NotificationsWire,
  { unreadCount(topic: string): Promise<number> }
>()({
  id: 'acme:notifications',
  dependencies: [clientRequests],
  setup(socket) {
    return {
      api: () => ({
        // sent as __acme:notifications::unread-count
        // resolves with the typed response
        unreadCount: async (topic) =>
          (await socket.request('unread-count', { topic })).count,
      }),
    }
  },
})
```

It settles the same way the top-level [`request()`](/client/primitives/client-requests) does. It resolves with the typed response, or rejects with a typed `LiveThingError`, `Timeout`, `Disconnected` or `Dropped`. When the server throws a declared error, the caller gets its **plain** code. The plugin's prefix is already removed. See [Plugin errors](/client/plugins/errors).

## `stream`, `onStream`, `resumeStream`: need `stream`

A contract with `streams` gets all three methods:

- `socket.stream(...)` starts a stream and gives you a handle to read it.
- `socket.onStream(...)` listens to a broadcast stream (a stream the server sends to many clients).
- `socket.resumeStream(...)` does a cold resume of a durable stream (a stream the server saves so it can be read again). A cold resume means you connect to the stream again from a new handle, for example after a page reload.

They need the `stream` primitive registered on the host. They work like the top-level methods with the same names: plain names in your code, the `__<id>::` prefix on the wire.

```typescript [notifications-plugin.ts]
import { plugin, stream } from '@livething/client'
import type { StreamHandle } from '@livething/client'
import type { NotificationsWire } from './notifications-wire'

interface NotificationsApi {
  history(
    before: number,
  ): Promise<StreamHandle<{ id: string; title: string }>>
}

export const Notifications = plugin<
  NotificationsWire,
  NotificationsApi
>()({
  id: 'acme:notifications',
  dependencies: [stream],
  setup(socket) {
    return {
      api: () => ({
        // starts __acme:notifications::history and returns a handle to read
        history: (before) => socket.stream('history', { before }),
      }),
    }
  },
})
```

`socket.stream(...)` resolves to the same `StreamHandle` the top-level socket returns. Use `for await` to read chunks. If the stream declares `nudges`, use `handle.nudge(event, payload)` to send a message to the server while the stream runs. All of these use the plugin's namespace. The [Streams chapter](/client/streams/overview) covers the handle, cold resume and nudges in full. See [Nudges](/client/streams/nudges) for the nudge details. This page only shows that the three methods exist on the scoped socket, with the same types.

## `onRequest`: needs `serverRequests`

A contract with a `serverRequests` section gets `socket.onRequest(...)`, so the server can send a request to this plugin and wait for its reply. It needs the `serverRequests()` primitive registered on the host.

```typescript [notifications-plugin.ts]
import { plugin, serverRequests } from '@livething/client'
import type { NotificationsWire } from './notifications-wire'

export const Notifications = plugin<NotificationsWire>()({
  id: 'acme:notifications',
  dependencies: [serverRequests],
  setup(socket) {
    // answers a request the server sent to
    // __acme:notifications::device-info
    socket.onRequest('device-info', () => ({ platform: 'web' }))

    return { api: () => ({}) }
  },
})
```

It works like the top-level [`onRequest()`](/client/primitives/server-requests). The return value (sync or async) becomes the reply. It returns an unsubscribe function.

## `channel`

A contract with a `channels` section gets `socket.channel(...)`. It has the same three forms as the top-level socket: fixed, dynamic-member and family. It is typed from the plugin's own channels, and you use plain names. It needs the `channels` primitive registered on the host.

A plugin channel handle also has the same channel-scoped members as a top-level channel handle:

- the [`inbox()`](/client/primitives/inbox) members for received messages: `receivers`, `onReceived`, `receiversOf`
- the [`readReceipts()`](/client/primitives/read-receipts) members for read messages: `readers`, `onRead`, `markAsRead`, `readersOf`

A plugin channel gets these members when its contract sets `inbox: true` or `readReceipts: true`. Each group works only when its primitive is registered on the host. This is the same rule the top-level socket follows.

This page only shows that `channel` exists. For the three forms, sending and receiving on a plugin channel, and owning a dynamic family from inside a plugin, see [Plugin channels & dynamic families](/client/plugins/dynamic-families).

## The raw message handlers

Every plugin socket also has the raw message handlers and tools from `PluginBase`, whatever its contract. A plugin with no wire sections at all still has them.

### `onIncoming` and `onOutgoing`

`onIncoming` sees each incoming frame (one message on the wire) before LiveThing delivers it. `onOutgoing` sees each outgoing frame before it is written to the wire. These handlers see raw frames, so event names carry their full wire name with the prefix. They also see frames that are not the plugin's own: `onOutgoing` sees every frame the socket sends, and `onIncoming` sees every incoming frame that another primitive or plugin has not handled first. Check `message.event` if a handler should only act on the plugin's own frames.

Return the message, changed or not, to pass it on. Throw `Block` to drop an incoming frame or cancel an outgoing one.

```typescript [notifications-plugin.ts]
import { plugin } from '@livething/client'
import { Block } from '@livething/client/errors'
import type { NotificationsWire } from './notifications-wire'

export const Notifications = plugin<
  NotificationsWire,
  { setMuted(value: boolean): void }
>()({
  id: 'acme:notifications',
  setup(socket) {
    let muted = false

    socket.onIncoming((message) => {
      // drop notifications while muted
      if (
        muted &&
        message.event === '__acme:notifications::notification'
      )
        throw Block
      return message // pass it on unchanged
    })

    socket.onOutgoing((message) => {
      // leave frames from the app and other plugins unchanged
      if (!message.event.startsWith('__acme:notifications::'))
        return message

      return {
        ...message,
        payload: {
          ...(message.payload as object),
          sentAt: Date.now(),
        },
      }
    })

    return {
      api: () => ({
        setMuted: (value) => {
          muted = value
        },
      }),
    }
  },
})
```

You can register each handler **once**. A second `socket.onIncoming(...)` call in the same `setup` throws:

```text
[livething] plugin 'acme:notifications' registered onIncoming() twice — use a single callback.
```

### `onOpen` and `onReconnect`

`onOpen` runs on every open: the first connect and every reconnect. `onReconnect` runs only on reconnects. Both return an array of `{ event, payload }` frames to send right away, or nothing. Both use plain names. LiveThing adds the plugin's prefix before it sends them.

```typescript [notifications-plugin.ts]
import { plugin } from '@livething/client'
import type { NotificationsWire } from './notifications-wire'

export const Notifications = plugin<NotificationsWire>()({
  id: 'acme:notifications',
  setup(socket) {
    // every open
    socket.onOpen(() => [
      { event: 'hello', payload: { device: 'web' } },
    ])

    // reconnects only
    socket.onReconnect(() => [{ event: 'resync', payload: {} }])

    return { api: () => ({}) }
  },
})
```

### `onClose`

`onClose(code, reason, suspended)` runs on every close. `suspended` is `true` when the platform paused the socket (for example, a mobile app went to the background) and the same socket will reconnect later. This is not a real end, so a handler should skip teardown in that case.

```typescript [notifications-plugin.ts]
import { plugin } from '@livething/client'
import type { NotificationsWire } from './notifications-wire'

export const Notifications = plugin<NotificationsWire>()({
  id: 'acme:notifications',
  setup(socket) {
    socket.onClose((code, reason, suspended) => {
      // a pause, not a real close: keep in-memory state as it is
      if (suspended) return
      console.info('notifications plugin closed', code, reason)
    })

    return { api: () => ({}) }
  },
})
```

## The tools

The rest of `PluginBase` is small tools. LiveThing does not call them for you. You call them yourself, from inside `setup` or from inside a handler:

| Tool                  | What it does                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------------- |
| `generateId(prefix?)` | Make a unique ID. It uses the socket's own counter, so it never has the same value as another ID. |
| `hasPrimitive(tag)`   | Whether a primitive with this tag is installed, for example `hasPrimitive('channels')`.           |
| `ensureConnected()`   | Open the connection now, if the socket is lazy and has not connected yet.                         |
| `state`               | The connection state as a [reactive store](/client/overview#reactive-stores).                     |

```typescript [notifications-plugin.ts]
import { plugin } from '@livething/client'
import type { NotificationsWire } from './notifications-wire'

export const Notifications = plugin<
  NotificationsWire,
  { sessionId: string }
>()({
  id: 'acme:notifications',
  setup(socket) {
    const sessionId = socket.generateId('notifications-session')

    socket.state.subscribe((state) =>
      console.info('connection state', state),
    )

    if (socket.hasPrimitive('keepalive'))
      console.info('keepalive is installed')

    socket.ensureConnected()

    return { api: () => ({ sessionId }) }
  },
})
```

`state` is the store itself, not a method. Read it with `socket.state.get()` and watch it with `socket.state.subscribe(...)`. This is the same pair of methods the app socket's own `state` has. The plugin socket has no `getState()`.
