A **client plugin** is a reusable client feature that owns a part of the socket. That part is called a **namespace**. A namespace is a name prefix, `__<id>::`, that LiveThing adds to every event, request, and error the plugin sends or receives. Because of this prefix, a plugin's names never clash with the app's names or with another plugin's names. You create a plugin with `plugin()` and get its API with `Plugin.use(socket)`.

## A plugin vs a primitive

A built-in primitive, such as `channels()` or `clientRequests()`, adds a method directly to the socket's type. Register `channels()`, and every socket gets `socket.channel(...)`. A plugin adds **nothing** to the socket's type. You get its API through `Plugin.use(socket)` instead:

```typescript [client/socket.ts]
import { client, clientRequests, connect } from '@livething/client'
import { Polls } from './polls-plugin.ts'
import type { HuddleWithPolls } from './socket-types'

export const socket = client<HuddleWithPolls>()(
  connect('wss://example.com/huddle'),
  clientRequests(),
  Polls(),
)

const polls = Polls.use(socket) // the plugin's API, not a socket method
polls.create('Lunch on Friday?', ['Yes', 'No'])
```

The reason is compiler speed. Every method a primitive adds makes the socket's type bigger. If each third-party plugin did this, the TypeScript compiler would get slower in every project that installs plugins. An API behind `.use()` adds nothing to the socket's type, and `Plugin.use(socket)` still returns a fully typed API.

## The steps

A plugin goes through four steps, from writing it to using its API.

::steps

### Define the contract and API types

Write a contract for the plugin's own namespace. It has the same sections as an app contract: `incoming`, `outgoing`, `clientRequests`, and so on. Also write the shape of the API the plugin will expose. Both are plain TypeScript types, not function calls.

```typescript [polls-plugin.ts]
import type { SocketContract } from '@livething/client'

interface PollsWire extends SocketContract {
  incoming: {
    'poll-updated': { pollId: string; tally: Record<string, number> }
  }
  clientRequests: {
    'create-poll': {
      payload: { question: string; options: string[] }
      response: { pollId: string }
    }
  }
}

interface PollsApi {
  latest(): { pollId: string; tally: Record<string, number> } | null
  create(
    question: string,
    options: string[],
  ): Promise<{ pollId: string }>
}
```

### Write `setup(socket)` and return the API

`plugin<PollsWire, PollsApi>()` takes the plugin definition. The `setup` function receives a **scoped socket**: a socket typed to `PollsWire` and limited to the plugin's namespace. Its `on`, `request`, and other methods use plain names. LiveThing adds the `__acme:polls::` prefix on the wire. Return `{ api }` to expose the plugin's API.

```typescript [polls-plugin.ts]
import { clientRequests, plugin } from '@livething/client'

export const Polls = plugin<PollsWire, PollsApi>()({
  id: 'acme:polls',
  dependencies: [clientRequests], // socket.request needs this primitive
  setup(socket) {
    let latest: {
      pollId: string
      tally: Record<string, number>
    } | null = null
    socket.on('poll-updated', (update) => (latest = update))

    return {
      api: () => ({
        latest: () => latest,
        create: (question, options) =>
          socket.request('create-poll', { question, options }),
      }),
    }
  },
})
```

### Register it in `client()` with the primitives it needs

List the plugin in `client()` next to every primitive it needs. Here that is `clientRequests()`, because `Polls` calls `socket.request(...)`. The order does not matter, because LiveThing always sets up primitives before plugins. If a primitive in the plugin's `dependencies` is missing, `client()` throws an error that names the primitive to add.

```typescript [client/socket.ts]
import { client, clientRequests, connect } from '@livething/client'
import { Polls } from './polls-plugin.ts'

export const socket = client<HuddleWithPolls>()(
  connect('wss://example.com/huddle'),
  clientRequests(),
  Polls(),
)
```

The app contract must also list the plugin's names with the `__acme:polls::` prefix. If it doesn't, `Polls()` is a type error:

```typescript [socket-types.ts]
interface HuddleWithPolls {
  incoming: {
    notification: { title: string; body: string }
    '__acme:polls::poll-updated': {
      pollId: string
      tally: Record<string, number>
    }
  }
  clientRequests: {
    '__acme:polls::create-poll': {
      payload: { question: string; options: string[] }
      response: { pollId: string }
    }
  }
}
```

You don't have to write these names by hand. [Deriving a contract from the server](/client/plugins/deriving-from-server) shows how to get them from the server's types.

### Get the API with `Plugin.use(socket)`

The first call to `Polls.use(socket)` builds the API. Later calls return that same object.

```typescript [client/socket.ts]
const polls = Polls.use(socket)
polls.latest() // null, until the first poll-updated arrives
await polls.create('Lunch on Friday?', ['Yes', 'No'])
```
