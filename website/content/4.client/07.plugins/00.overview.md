A **client plugin** is a reusable client feature that owns a part of the socket. That part is called a **namespace**. A namespace is a name prefix, `__<id>::`, that LiveThing adds to every event, request, and error the plugin sends or receives. Because of this prefix, a plugin's names never clash with the app's names or with another plugin's names. You create a plugin with `plugin()` and get its API with `Plugin.use(socket)`.

## A plugin vs a primitive

A built-in primitive, such as `channels()` or `clientRequests()`, adds a method directly to the socket's type. Register `channels()`, and every socket gets `socket.channel(...)`. A plugin adds **nothing** to the socket's type. You get its API through `Plugin.use(socket)` instead:

```typescript [app.ts]
import { client, clientRequests, connect } from '@livething/client'
import { Chat } from './chat-plugin.ts'

const socket = client<AppContract>()(
  connect('wss://example.com/ws'),
  clientRequests(),
  Chat(),
)

const chat = Chat.use(socket) // the plugin's API, not a socket method
chat.send('hello')
```

The reason is compiler speed. Every method a primitive adds makes the socket's type bigger. If each third-party plugin did this, the TypeScript compiler would get slower in every project that installs plugins. An API behind `.use()` adds nothing to the socket's type, and `Plugin.use(socket)` still returns a fully typed API.

## The steps

A plugin goes through four steps, from writing it to using its API.

::steps

### Define the contract and API types

Write a contract for the plugin's own namespace. It has the same sections as an app contract: `incoming`, `outgoing`, `clientRequests`, and so on. Also write the shape of the API the plugin will expose. Both are plain TypeScript types, not function calls.

```typescript [chat-plugin.ts]
import type { SocketContract } from '@livething/client'

interface ChatContract extends SocketContract {
  incoming: { message: { from: string; text: string } }
  clientRequests: {
    'send-message': {
      payload: { text: string }
      response: { ok: true }
    }
  }
}

interface ChatApi {
  history(): { from: string; text: string }[]
  send(text: string): Promise<{ ok: true }>
}
```

### Write `setup(socket)` and return the API

`plugin<ChatContract, ChatApi>()` takes the plugin definition. The `setup` function receives a **scoped socket**: a socket typed to `ChatContract` and limited to the plugin's namespace. Its `on`, `request`, and other methods use plain names. LiveThing adds the `__acme:chat::` prefix on the wire. Return `{ api }` to expose the plugin's API.

```typescript [chat-plugin.ts]
import { clientRequests, plugin } from '@livething/client'

export const Chat = plugin<ChatContract, ChatApi>()({
  id: 'acme:chat',
  dependencies: [clientRequests], // socket.request needs this primitive
  setup(socket) {
    const inbox: { from: string; text: string }[] = []
    socket.on('message', (message) => inbox.push(message))

    return {
      api: () => ({
        history: () => inbox.slice(),
        send: (text) => socket.request('send-message', { text }),
      }),
    }
  },
})
```

### Register it in `client()` with the primitives it needs

List the plugin in `client()` next to every primitive it needs. Here that is `clientRequests()`, because `Chat` calls `socket.request(...)`. The order does not matter, because LiveThing always sets up primitives before plugins. If a primitive in the plugin's `dependencies` is missing, `client()` throws an error that names the primitive to add.

```typescript [app.ts]
import { client, clientRequests, connect } from '@livething/client'
import { Chat } from './chat-plugin.ts'

const socket = client<AppContract>()(
  connect('wss://example.com/ws'),
  clientRequests(),
  Chat(),
)
```

The app contract must also list the plugin's names with the `__acme:chat::` prefix. If it doesn't, `Chat()` is a type error:

```typescript [contract.ts]
interface AppContract {
  incoming: {
    notice: { text: string }
    '__acme:chat::message': { from: string; text: string }
  }
  clientRequests: {
    '__acme:chat::send-message': {
      payload: { text: string }
      response: { ok: true }
    }
  }
}
```

You don't have to write these names by hand. [Deriving a contract from the server](/client/plugins/deriving-from-server) shows how to get them from the server's types.

### Get the API with `Plugin.use(socket)`

The first call to `Chat.use(socket)` builds the API. Later calls return that same object.

```typescript [app.ts]
const chat = Chat.use(socket)
chat.history() // []
await chat.send('hello')
```
