A **client plugin** is a reusable client feature that owns a slice of the socket. That slice is called a **namespace** — a name prefix (`__<id>::`) stamped on every event, request, and error the plugin sends or receives, so its traffic never collides with the host app's or with another plugin's. You author a plugin with `plugin()` and reach its API with `Plugin.use(socket)`.

## A plugin vs a primitive

A built-in primitive — `channels()`, `clientRequests()` — adds a method straight onto the socket's type. Register `channels()` and every socket gets `socket.channel(...)`. A plugin adds **nothing** to the socket's type. Instead, its API is reached through `Plugin.use(socket)`:

```typescript [app.ts]
import { client, clientRequests, connect } from '@wskit/client'
import { Chat } from './chat-plugin.ts'

const socket = client<AppContract>()(
  connect('wss://example.com/ws'),
  clientRequests(),
  Chat(),
)

const chat = Chat.use(socket) // the plugin's API, not a socket method
chat.send('hello')
```

The reason is compiler speed: every method a primitive adds widens the socket's type, and a third-party plugin doing that on every project that installs it would slow the compiler down. Keeping the API behind `.use()` costs nothing in the socket's type, while `Plugin.use(socket)` still returns a fully typed API.

## The flow at a glance

A plugin goes through four steps from author to reading its API.

::steps

### Define the contract and API types

Write a contract for the plugin's own namespace — its `incoming`, `outgoing`, `clientRequests`, and so on — and the shape of the API it will expose. These are plain TypeScript types, not calls.

```typescript [chat-plugin.ts]
import type { SocketContract } from '@wskit/client'

interface ChatContract extends SocketContract {
  incoming: { message: { from: string; text: string } }
  clientRequests: {
    'send-message': { payload: { text: string }; response: { ok: true } }
  }
}

interface ChatApi {
  history(): { from: string; text: string }[]
  send(text: string): Promise<{ ok: true }>
}
```

### `setup(socket)` wires handlers and taps, returns the API

`plugin<ChatContract, ChatApi>()` takes the definition. `setup` gets a scoped socket typed to `ChatContract` — `on`, `request`, and the rest use plain names, and the framework adds the `__acme:chat::` prefix on the wire for you. Return `{ api }` to expose the plugin's API.

```typescript [chat-plugin.ts]
import { clientRequests, plugin } from '@wskit/client'

export const Chat = plugin<ChatContract, ChatApi>()({
  id: 'acme:chat',
  dependencies: [clientRequests], // socket.request needs this primitive
  setup(socket) {
    const inbox: { from: string; text: string }[] = []
    socket.on('message', (message) => inbox.push(message))

    return {
      api: () => ({
        history: () => inbox.slice(),
        send: (text) => socket.request('send-message', { text }),
      }),
    }
  },
})
```

### Register it in `client()`, alongside the primitives it depends on

List the plugin in `client()` next to any primitive it needs — `clientRequests()` here, because `Chat` calls `socket.request(...)`. Registration order doesn't matter; WSKit orders a plugin's dependencies ahead of it.

```typescript [app.ts]
import { client, clientRequests, connect } from '@wskit/client'
import { Chat } from './chat-plugin.ts'

const socket = client<AppContract>()(
  connect('wss://example.com/ws'),
  clientRequests(),
  Chat(),
)
```

### Read the API with `Plugin.use(socket)`

`Chat.use(socket)` builds the API the first time it's called and returns that same instance after.

```typescript [app.ts]
const chat = Chat.use(socket)
chat.history() // []
await chat.send('hello')
```
