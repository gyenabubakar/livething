The **wire** is the message stream a socket sends and receives — every event, request, and stream chunk that crosses the connection. A plugin owns a slice of the wire, called its **namespace**, so its names never collide with the app's own names or another plugin's.

## The wire shape: `__<id>::<name>`

Inside a plugin's `setup`, you write plain names — `socket.on('welcome', ...)`, `socket.send('hello', ...)`. On the wire, the framework rewrites that name to `__<id>::<name>`: two underscores, the plugin's `id`, two colons, then the plain name. For a plugin with `id: 'e2e:feed'`, the event `welcome` travels as:

```text
__e2e:feed::welcome
```

You never type the long form yourself. The framework adds it going out and strips it coming back in, so the plugin always works in plain names:

```typescript [feed-plugin.ts]
const Feed = plugin<FeedWire, FeedApi>()({
  id: 'e2e:feed',
  setup(socket) {
    // 'welcome' arrives on the wire as __e2e:feed::welcome — this handler
    // never sees the long form
    socket.on('welcome', (m) => console.info('got', m.name))

    return {
      api: () => ({
        // 'hello' goes out as __e2e:feed::hello
        hello: (name) => void socket.send('hello', { name }),
      }),
    }
  },
})
```

This also applies to protocol-looking names inside a plugin. `ping` and `pong`
are reserved heartbeat frames at the top level, but a plugin channel sends them
as `__<id>::ping` and `__<id>::pong`, so they are ordinary plugin events. A
plain app channel must still use a different event name.

## The plugin owns its whole namespace

A plugin doesn't just claim the names it declares — it claims the **entire prefix** `__<id>::`. Nothing else on the socket can read or write a name under that prefix once the plugin is registered.

This shows up at the type level too. When a full-stack app (one codebase that builds both server and client) uses `InferClient` to derive the client's contract from the server, a server plugin's names get folded into the app contract already namespaced, as `__id::name`. The client then needs to split them back out: the plugin's own slice on one side, and everything the app can still reach directly on the other. Two types do that split — `PluginSlice` pulls a single plugin's names back to plain form, and `TopLevelContract` is the app contract with every claimed plugin's namespace **removed**. Once a plugin claims `e2e:feed`, `TopLevelContract` drops every `__e2e:feed::…` key, so the top-level socket no longer types them at all.

::note
`PluginSlice` and `TopLevelContract` are covered in full, with runnable examples, in [Deriving the contract from the server](/client/plugins/deriving-from-server#when-server-and-client-share-the-app-contract). This page only covers what the split means for matching.
::

The practical result: `socket.on('__e2e:feed::message')` on the app-level socket is a **type error** once `Feed` is registered — that name isn't in `TopLevelContract` anymore, only in the plugin's own scoped socket. And even if you bypass the type system (an unsafe cast, or plain JavaScript), a raw top-level listener for a plugin's frame never fires at runtime — the plugin claims the frame before the app-level dispatch ever sees it:

```typescript [app.ts]
const socket = client<FeedHost>()(
  connect(wsUrl),
  clientRequests(),
  stream(),
  channels(),
  Feed(),
)

// this never runs: Feed() claims every __e2e:feed:: frame before
// the app-level socket dispatches it
;(
  socket as unknown as {
    on(event: string, handler: (data: { name: string }) => void): void
  }
).on('__e2e:feed::welcome', (data) => console.info('never printed', data.name))
```

## The id can't contain `::`

A plugin's `id` becomes part of the wire prefix, so it can't itself contain the `::` separator — that would make one plugin's prefix a prefix of another's, and one plugin would end up swallowing another's frames. Registering a plugin whose `id` contains `::` throws a `WSKitConfigError`:

```typescript [bad-id.ts]
plugin()({ id: 'acme::chat', setup: (socket) => ({}) })
// ✗ throws: "plugin id 'acme::chat' must not contain '::' — use a single
//   colon, like 'vendor:name'."
```

Follow the `vendor:name` convention instead — a **single** colon, like `'acme:chat'` or `'e2e:feed'`. A single colon is fine; it's only the doubled `::` that's reserved.

## What a plugin matches

Not every frame that carries a plugin's namespaced name is the plugin's to handle. A frame can also carry a channel, a `correlationId` (a request/response pairing marker), or a `streamId` — and those are claimed by the `channels`, `clientRequests`, or `stream` primitive **before** the plugin ever sees the frame, even when the frame's name is under the plugin's own prefix.

So a plugin only owns **plain top-level frames** in its namespace — a bare event or a server-initiated push, not a channel message, a request reply, or a stream chunk. Those still reach the plugin, but through the primitive that handles them first: `socket.channel('room')` inside `setup` gets channel frames routed to it, `socket.request('echo', ...)` gets its reply matched by `correlationId`, and so on. The plugin's `dependencies` list is what makes those primitives available on its scoped socket — see [Defining a plugin](/client/plugins/defining#declaring-primitive-dependencies).

```typescript [feed-plugin.ts]
setup(socket) {
  // a plain top-level frame — the plugin matches this directly by name
  socket.on('welcome', (m) => console.info(m.name))

  // a channel frame — 'room' carries a channel marker, so clientRequests/
  // channels claims it first and routes it to this channel object, not to
  // a bare socket.on('room', ...)
  const room = socket.channel('room')
  room.on('joined', (m) => console.info(m.who))
}
```

For the server-side mirror of this wire shape — how a server plugin's events, requests, channels, and storage keys get the same `__<id>::` treatment — see [Namespacing](/server/plugins/namespacing) under server plugins.
