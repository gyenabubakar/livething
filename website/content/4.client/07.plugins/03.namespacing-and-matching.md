The **wire** is the stream of messages a socket sends and receives. Each message on the wire is a **frame**: one event, one request, one reply, or one stream chunk. A plugin owns a part of the wire called its **namespace**. Because of this, its names never clash with the app's own names or with another plugin's names.

## The wire shape: `__<id>::<name>`

Inside a plugin's `setup`, you write plain names, such as `socket.on('poll-updated', ...)` and `socket.send('watch-poll', ...)`. On the wire, LiveThing changes each name to `__<id>::<name>`. That is two underscores, the plugin's `id`, two colons, and then the plain name. For a plugin with `id: 'acme:polls'`, the event `poll-updated` travels as:

```text
__acme:polls::poll-updated
```

You never type the long form yourself. LiveThing adds the prefix to frames going out and removes it from frames coming in. The plugin code only uses plain names:

```typescript [polls/client.ts]
const Polls = plugin<PollsWire, PollsApi>()({
  id: 'acme:polls',
  setup(socket) {
    // Arrives on the wire as __acme:polls::poll-updated.
    // This handler only sees the plain name 'poll-updated'.
    socket.on('poll-updated', (m) =>
      console.info('got', m.pollId, m.tally),
    )

    return {
      api: () => ({
        // Goes out as __acme:polls::watch-poll
        watchPoll: (pollId) =>
          void socket.send('watch-poll', { pollId }),
      }),
    }
  },
})
```

## The plugin owns its whole namespace

A plugin claims more than the names it declares. It claims the **whole prefix** `__<id>::`. After the plugin is registered, every incoming frame under that prefix goes to the plugin, and the app-level socket's types no longer include any name under that prefix.

You can see this in the types. The app contract lists plugin names in their wire form, `__id::name`. You can write that contract by hand, or get it from `InferClient`, a type that reads your server definition and produces the client contract (server plugins included). Either way, the client splits the contract into two parts: the plugin's own names, and the names the app can still use directly. Two types do this split:

- `PluginSlice` takes one plugin's names and turns them back into plain names.
- `TopLevelContract` is the app contract with every claimed plugin's namespace **removed**. Once a plugin claims `acme:feed`, `TopLevelContract` drops every `__acme:feed::…` key, so the app-level socket has no types for those names.

::note
[Deriving the contract from the server](/client/plugins/deriving-from-server#when-server-and-client-share-the-app-contract) covers `PluginSlice` and `TopLevelContract` in full, with runnable examples. This page only covers what the split means for matching.
::

In practice, once `Polls` is registered, `socket.on('__acme:polls::poll-updated')` on the app-level socket is a **type error**. That name is no longer in `TopLevelContract`. It exists only on the plugin's own scoped socket.

You can skip the type check with an unsafe cast, or by writing plain JavaScript. Even then, an app-level listener for a plugin's frame never runs. The plugin takes the frame before the app-level socket passes it to any listener:

```typescript [client/socket.ts]
const socket = client<HuddleWithPolls>()(
  connect(wsUrl),
  clientRequests(),
  stream(),
  channels(),
  Polls(),
)

// This handler never runs. Polls() takes every __acme:polls:: frame
// before the app-level socket passes it to a listener.
;(
  socket as unknown as {
    on(
      event: string,
      handler: (data: { pollId: string }) => void,
    ): void
  }
).on('__acme:polls::poll-updated', (data) =>
  console.info('never printed', data.pollId),
)
```

## The ID can't contain `::`

A plugin's `id` becomes part of the wire prefix, so the `id` itself can't contain the `::` separator. If it could, one plugin's prefix could be the start of another plugin's prefix, and one plugin would take the other plugin's frames. Defining a plugin whose `id` contains `::` throws a `LiveThingConfigError` when `plugin()` runs:

```typescript [polls/client.ts]
plugin()({ id: 'acme::polls', setup: () => ({}) })
// ✗ throws: "plugin id 'acme::polls' must not contain '::' — use a single
//   colon, like 'vendor:name'."
```

Use the `vendor:name` convention instead: a **single** colon, like `'acme:polls'`. A single colon is fine. Only the double `::` is reserved.

## What a plugin matches

A frame can carry a name in the plugin's namespace and still not be the plugin's to handle. A frame can also carry metadata (extra routing data sent with the frame):

- `metadata.channel` marks a channel message. The `channels` primitive handles it.
- `metadata.exchange` marks a request or its reply, matched by `metadata.exchange.id`. The `clientRequests` or `serverRequests` primitive handles it.
- `metadata.stream` marks a stream frame, matched by `metadata.stream.id`. The `stream` primitive handles it.

These primitives run **before** the plugin. They take the frame even when its name is under the plugin's prefix.

So a plugin matches only **plain top-level frames** in its namespace: a plain event pushed by the server. It does not match a channel message, a request reply, or a stream chunk directly. Those frames still reach the plugin, but through the primitive that handles them. `socket.channel('poll-room', ...)` inside `setup` gets the channel's frames. `socket.request('create-poll', ...)` gets its reply, matched by `metadata.exchange.id`. The plugin's `dependencies` list makes those primitives available on its scoped socket. See [Defining a plugin](/client/plugins/defining#declaring-primitive-dependencies).

```typescript [polls/client.ts]
setup(socket) {
  // A plain top-level frame. The plugin matches it directly by name.
  socket.on('poll-updated', (m) => console.info(m.pollId, m.tally))

  // A channel frame. It carries metadata.channel, so the channels primitive
  // takes it first and passes it to this channel object. A plain
  // socket.on('tally-changed', ...) would not receive it.
  const room = socket.channel('poll-room', 'poll:1')
  room.on('tally-changed', (m) => console.info(m.tally))

  return {}
}
```

A server plugin's events, requests, channels, and storage keys get the same `__<id>::` prefix. See [Namespacing](/server/plugins/namespacing) under server plugins.
