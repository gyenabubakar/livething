A plugin's errors work like the [client's own error model](/core/error-model), with one difference. On the wire, every error a plugin sends or throws carries the plugin's namespace prefix, for example `__acme:room::room-full`. LiveThing removes that prefix before your code receives the error. The sections below show where this happens.

## The scoped `onServerError`

When a plugin's contract declares an `errors` section, the socket that `setup` receives has an `onServerError` method. A plugin with no `errors` section has no `onServerError` method, and calling it is a compile error.

```typescript [room-plugin.ts]
import { channels, clientRequests, plugin } from '@livething/client'

interface RoomWire {
  errors: {
    'room-full': { limit: number }
  }
  clientRequests: {
    join: { payload: { room: string }; response: { ok: true } }
  }
  channels: {
    lobby: {
      incoming: { joined: { who: string } }
    }
  }
}

interface RoomApi {
  join(room: string): Promise<{ ok: true }>
  enterLobby(): Promise<void>
}

export const Room = plugin<RoomWire, RoomApi>()({
  id: 'acme:room',
  dependencies: [clientRequests, channels],
  setup(socket) {
    socket.onServerError('room-full', (err) => {
      console.warn('The room is full. Limit:', err.detail.limit)
    })

    return {
      api: () => ({
        join: (room: string) => socket.request('join', { room }),
        enterLobby: () => socket.channel('lobby').subscribe(),
      }),
    }
  },
})
```

`err` is a real [`LiveThingError`](/core/error-model), so `err instanceof LiveThingError` is `true`. When you pass a code as the first argument, `err.detail` has the type you declared for that code. Here, `err.detail.limit` is a `number`.

The code in `err.code` is the **plain** name you declared (`'room-full'`). It is not the wire code (`__acme:room::room-full`), because LiveThing removes the plugin's prefix before it calls your handler.

`onServerError` has two forms:

- `onServerError(code, handler)` runs only for that declared code.
- `onServerError(handler)` runs for every server error code. This includes a code that a newer version of the server added and the client does not know yet. In this form, `err.code` is a `string` and `err.detail` is `unknown`. A `switch` on `err.code` does not give `detail` a type, so use an error definition's `.matches()` or check the value at runtime.

Each call returns a function that removes that listener. You can call `onServerError` more than once to add several listeners.

The plugin's error type comes from the plugin's declared `errors` map. On the server, only the plugin's declared codes get the plugin's prefix. If server plugin code throws a `LiveThingError` with a code the plugin did not declare, the server does not add the prefix. It sends the code only when the application or LiveThing itself declares that code (for example, a [built-in error](/core/builtin-errors)). In every other case, the server sends the built-in `internal-error` instead.

### What reaches it

The scoped `onServerError` runs only for an **unclaimed** server error in the plugin's namespace. An unclaimed error is a server-sent error that no pending `request`, `stream`, or channel operation in that namespace was waiting for. When a request fails or a channel subscribe is rejected, the error goes to that call (see [below](#a-thrown-error-reaches-the-caller-plain)). It never goes to `onServerError`.

### With no matching handler registered

The plugin still owns the errors in its namespace when no `onServerError` listener matches the code. The error does not reach the app as an ordinary message. Instead, LiveThing passes the unclaimed error to the app socket's own [`onServerError`](/client/errors/onerror-routing). There, the error **keeps** its namespaced code (`__acme:room::room-full`, not `room-full`). This way, the app can tell it apart from the other server errors that reach the same listener. If the app socket has no matching listener either, LiveThing throws the error again, as described in [onError routing](/client/errors/onerror-routing).

A plugin's `onServerError` is only for unclaimed server errors. When one of the plugin's own handlers throws (for example, an `on()` handler or an `onServerError` handler), that error goes to the app socket's `onError`.

## A thrown error reaches the caller plain

A server plugin can throw one of its declared errors from a request handler, a stream, or a channel's `check` function (the server function that accepts or rejects a subscribe). The client call then fails with the **plain** code. This is the same code the plugin author declared on the server, with no namespace prefix. The error goes to the promise or loop of that request, stream, or channel. It follows the normal routing for [that kind of call](/client/errors/onerror-routing), not the scoped `onServerError` above.

In the app, get the plugin's API with `Room.use(socket)`:

```typescript [app.ts]
import { LiveThingError } from '@livething/client/errors'
import { Room } from './room-plugin'

const room = Room.use(socket)

// The server's request handler throws its declared `room-full` error.
// On the wire, the code is `__acme:room::room-full`.
// Here, the promise rejects with the plain `room-full`.
try {
  await room.join('lobby')
} catch (err) {
  if (err instanceof LiveThingError && err.code === 'room-full') {
    showFullRoomNotice()
  }
}
```

A channel subscribe works the same way. When the plugin's `check` function rejects the subscribe, the subscribe promise rejects with the plain code, not the namespaced one.

```typescript [app.ts]
// The server's channel `check` throws its declared `room-full` error.
// The subscribe promise rejects with the plain code.
try {
  await room.enterLobby()
} catch (err) {
  if (err instanceof LiveThingError && err.code === 'room-full') {
    showFullRoomNotice()
  }
}
```

In both cases, the plugin author writes and matches one plain code, `'room-full'`, on the server and on the client. LiveThing adds the `__<id>::` prefix when the error goes on the wire and removes it when the error arrives. Application code never uses the prefix.
