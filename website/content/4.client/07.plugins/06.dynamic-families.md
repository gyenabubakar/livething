A plugin can own channels too. When the plugin's contract declares a `channels` section, the scoped socket that `setup` receives gets a `channel` method. It has the same three forms as `socket.channel(...)` on the app socket, but it is typed from the plugin's own channels. This page covers only the plugin side. For how channels work (handles, dynamic families, presence, subscribing and leaving), see [Channels](/client/channels/overview) and [Scoped Features](/learn/scoped-features).

## The three forms

The plugin's socket has `channel` only when the plugin's contract has a `channels` section. A plugin with no channels has no `channel` method at all, so calling it is a compile error.

| Form                     | Channel shape                  | Returns                       |
| ------------------------ | ------------------------------ | ----------------------------- |
| `channel(name)`          | a fixed channel                | a handle for that one channel |
| `channel(family, name)`  | one member of a dynamic family | a handle for that one room    |
| `channel.family(family)` | a dynamic family, as a whole   | a callable family handle      |

The plugin's contract decides which form compiles, the same way as on the app socket. A channel marked `addressing: 'dynamic'` needs a family key and a name. Any other channel takes only its name.

## A fixed channel a plugin owns

Give the plugin's contract a `channels` section. Then, inside `setup`, call `socket.channel(name)` with the plain name, without any plugin prefix. LiveThing adds the `__<id>::` prefix for you on every frame (one message on the WebSocket) that goes over the wire.

```typescript [feed-wire.ts]
export interface FeedWire {
  channels: {
    room: {
      outgoing: { chat: { text: string } }
      incoming: {
        joined: { who: string }
        said: { text: string }
      }
    }
  }
}
```

```typescript [feed-plugin.ts]
import { channels, plugin } from '@livething/client'
import type { FeedWire } from './feed-wire'

interface FeedApi {
  chat(text: string): void
  onSaid(callback: (text: string) => void): void
  joinRoom(): Promise<void>
}

export const Feed = plugin<FeedWire, FeedApi>()({
  id: 'acme:feed',
  dependencies: [channels], // channel() needs the channels() primitive
  setup(socket) {
    const saidCallbacks = new Set<(text: string) => void>()

    const room = socket.channel('room') // a fixed channel, plain name
    room.on('said', (data) => {
      for (const callback of saidCallbacks) callback(data.text)
    })

    return {
      api: () => ({
        chat: (text) => {
          // the event 'chat' goes out as '__acme:feed::chat'
          room.send('chat', { text })
        },
        onSaid: (callback) => {
          saidCallbacks.add(callback)
        },
        joinRoom: () => room.subscribe(),
      }),
    }
  },
})
```

The prefix is added in both directions:

- **What the plugin sends** on its channel goes out with the prefix. `room.send('chat', { text })` sends the event `__acme:feed::chat` on the channel `__acme:feed::room`. So it reaches only the server handler for that plugin channel. A `chat` handler on the app's own `room` channel does not receive it.
- **What the server broadcasts back** also arrives with the prefix. The plugin's `room.on(...)` removes the prefix before your callback runs. A `joined` broadcast from the server's `__acme:feed::room` channel reaches `room.on('joined', ...)` as plain `joined`. The app code never sees the prefix.

## A dynamic family a plugin owns

A dynamic family is one channel declaration that covers many rooms, such as `thread:general` and `thread:support`. A plugin can own one the same way the app can. Add `addressing: 'dynamic'` to the channel in the plugin's contract, then open one member with `channel(family, name)`:

```typescript [feed-wire.ts]
export interface FeedWire {
  channels: {
    thread: {
      addressing: 'dynamic'
      incoming: { posted: { thread: string } }
    }
  }
}
```

```typescript [feed-plugin.ts]
import { channels, plugin } from '@livething/client'
import type { FeedWire } from './feed-wire'

interface FeedApi {
  joinThread(
    id: string,
    onPosted: (thread: string) => void,
  ): Promise<void>
}

export const Feed = plugin<FeedWire, FeedApi>()({
  id: 'acme:feed',
  dependencies: [channels],
  setup(socket) {
    return {
      api: () => ({
        joinThread: (id, onPosted) => {
          // one member of the 'thread' family, under the plugin's namespace
          const thread = socket.channel('thread', `thread:${id}`)
          thread.on('posted', (data) => onPosted(data.thread))
          return thread.subscribe()
        },
      }),
    }
  },
})
```

`Feed.use(socket).joinThread('general', ...)` subscribes to the room `thread:general` in the family `__acme:feed::thread`. Only the family key gets the prefix. The room name stays as you wrote it, because the server matches it against the family's name pattern. The server finds the plugin's family from the prefixed key, and its broadcasts come back with the same prefix. The app sees only the plain `posted` event and the plain room name.

To work with the whole family from inside a plugin (list the active rooms, or listen on all of them), use `socket.channel.family(key)`, the same as on the app socket:

```typescript [feed-plugin.ts]
import { channels, plugin } from '@livething/client'
import type { FeedWire } from './feed-wire'

interface FeedApi {
  activeThreads(): string[]
}

export const Feed = plugin<FeedWire, FeedApi>()({
  id: 'acme:feed',
  dependencies: [channels],
  setup(socket) {
    const threads = socket.channel.family('thread')

    threads.on('posted', (data, channelName) => {
      console.info(`${channelName} got a post`, data.thread)
    })

    return {
      api: () => ({ activeThreads: () => threads.list() }),
    }
  },
})
```

## Why the wire prefix matters

The plugin author always writes plain names, such as `channel('room')`, `channel('thread', 'thread:general')` and `room.send('chat', ...)`, and never writes the `__<id>::` prefix. The prefix keeps a plugin's channels apart from the app's channels and from other plugins' channels. Two plugins can each own a channel named `room`. On the wire they are `__acme:feed::room` and `__acme:other::room`, which are two different channels.

::note
`channel` on the plugin's socket needs the `channels()` primitive registered on the host `client()`, the same as `socket.channel(...)` on the app socket. List `channels` in the plugin's `dependencies`. Then, if the host forgets to register it, LiveThing throws an error when the socket is built, and the message names what to add. Without the dependency, the error comes later, only when the plugin calls `channel`. See [Declaring primitive dependencies](/client/plugins/defining#declaring-primitive-dependencies).
::
