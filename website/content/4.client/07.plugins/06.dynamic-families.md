A plugin can own channels too. When the plugin's contract declares a `channels` section, its scoped socket gets a `channel` method — the same three forms `socket.channel(...)` has at the top level, just typed from the plugin's own channels and reached through the socket `setup` receives. This page covers only that plugin-scoped angle. For channel mechanics themselves — handles, dynamic families, presence, subscribe lifecycle — see [Channels](/client/channels/overview) and [Scoped Features](/learn/scoped-features).

## The three forms

`channel` is only present on the plugin's socket when the plugin's contract has a `channels` section — a plugin with no channels gets no `channel` method at all, so calling it is a compile error, not a runtime one.

| Form                     | Channel shape                  | Returns                         |
| ------------------------ | ------------------------------ | ------------------------------- |
| `channel(name)`          | a fixed channel                | a handle for that one channel   |
| `channel(family, name)`  | one member of a dynamic family | a handle for that concrete room |
| `channel.family(family)` | a dynamic family, as a whole   | a callable family handle        |

Which form compiles is typed from the plugin's contract, exactly like the top-level socket: a channel marked `addressing: 'dynamic'` needs a family key plus a name, and any other channel takes just its name.

## A fixed channel a plugin owns

Give the plugin's contract a `channels` section, then call `socket.channel(name)` inside `setup` with the plain name — no plugin prefix. The framework adds the `__<id>::` prefix for you on every frame that crosses the wire.

```typescript [feed-wire.ts]
export interface FeedWire {
  channels: {
    room: {
      outgoing: { chat: { text: string } }
      incoming: {
        joined: { who: string }
        said: { text: string }
      }
    }
  }
}
```

```typescript [feed-plugin.ts]
import { channels, plugin } from '@livething/client'
import type { FeedWire } from './feed-wire'

interface FeedApi {
  chat(text: string): void
  onSaid(callback: (text: string) => void): void
  joinRoom(): Promise<void>
}

export const Feed = plugin<FeedWire, FeedApi>()({
  id: 'acme:feed',
  dependencies: [channels], // channel() needs the channels() primitive installed
  setup(socket) {
    const saidCallbacks = new Set<(text: string) => void>()

    const room = socket.channel('room') // a fixed channel, plain name
    room.on('said', (data) =>
      saidCallbacks.forEach((callback) => callback(data.text)),
    )

    return {
      api: () => ({
        // outgoing 'chat' leaves the socket as '__acme:feed::chat'
        chat: (text) => void room.send('chat', { text }),
        onSaid: (callback) => void saidCallbacks.add(callback),
        joinRoom: () => room.subscribe(),
      }),
    }
  },
})
```

Both directions are namespaced, not just the one you'd expect:

- **What the plugin sends** on its channel goes out prefixed. `room.send('chat', { text })` puts `__acme:feed::chat` on the wire, so it only reaches the server's channel handler for that same namespaced channel — a plain `chat` handler on an unprefixed `room` channel never sees it.
- **What the server broadcasts back** arrives prefixed too, and the plugin's `room.on(...)` strips the prefix before your callback sees it. A `joined` broadcast from the server's `__acme:feed::room` channel reaches `room.on('joined', ...)` as plain `joined` — the app never has to know the prefix exists.

## A dynamic family a plugin owns

A plugin can own a dynamic family — one declaration covering many rooms, like `thread:general`, `thread:support` — the same way the app can. Add `addressing: 'dynamic'` to the channel in the plugin's contract, then address one member with `channel(family, name)`:

```typescript [feed-wire.ts]
export interface FeedWire {
  channels: {
    thread: {
      addressing: 'dynamic'
      incoming: { posted: { thread: string } }
    }
  }
}
```

```typescript [feed-plugin.ts]
import { channels, plugin } from '@livething/client'
import type { FeedWire } from './feed-wire'

interface FeedApi {
  joinThread(
    id: string,
    onPosted: (thread: string) => void,
  ): Promise<void>
}

export const Feed = plugin<FeedWire, FeedApi>()({
  id: 'acme:feed',
  dependencies: [channels],
  setup(socket) {
    return {
      api: () => ({
        joinThread: (id, onPosted) => {
          // one member of the 'thread' family, under the plugin's namespace
          const t = socket.channel('thread', `thread:${id}`)
          t.on('posted', (data) => onPosted(data.thread))
          return t.subscribe()
        },
      }),
    }
  },
})
```

Calling `Feed.use(socket).joinThread('general', ...)` subscribes to the concrete room `__acme:feed::thread:general`. The server's dynamic-family handler sees the plugin's namespace on the channel name, resolves `thread:general` as the family member, and its broadcast comes back through the same prefix — the app only ever sees the plain `posted` event and the plain thread name.

To act on the whole family at once from inside a plugin — list active rooms, or listen across every one — use `socket.channel.family(key)`, same as the top level:

```typescript [feed-plugin.ts]
import { channels, plugin } from '@livething/client'
import type { FeedWire } from './feed-wire'

interface FeedApi {
  activeThreads(): string[]
}

export const Feed = plugin<FeedWire, FeedApi>()({
  id: 'acme:feed',
  dependencies: [channels],
  setup(socket) {
    const threads = socket.channel.family('thread')

    threads.on('posted', (data, channelName) => {
      console.info(`${channelName} got a post`, data.thread)
    })

    return {
      api: () => ({ activeThreads: () => threads.list() }),
    }
  },
})
```

## Why the wire prefix matters

The plugin author writes plain names throughout — `channel('room')`, `channel('thread', 'thread:general')`, `room.send('chat', ...)` — and never touches the `__<id>::` prefix directly. That prefix is what keeps a plugin's channels from colliding with the app's own channels or another plugin's: two plugins can each own a channel named `room` without conflict, because on the wire they're `__acme:feed::room` and `__acme:other::room`, two different channels.

::note
`channel` on the plugin's socket needs the `channels()` primitive registered on the host `client()`, just like the top-level `socket.channel(...)` does — list `channels` in the plugin's `dependencies` so a host that forgets to register it gets a clear error naming what to add, instead of a missing-method failure. See [Declaring primitive dependencies](/client/plugins/defining#declaring-primitive-dependencies).
::
