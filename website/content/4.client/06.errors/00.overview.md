Almost every error the client can hand you is a **`WSKitError`** — a plain `Error` subclass with a stable `code` and an optional typed `detail`. That's true whether the error came from your server, from the client itself, or from the framework. Because they all share one shape, you catch and narrow them all the same way. This chapter covers where errors land on the client and how to handle them; the shared model and the full catalog live in [Core](/core/overview).

```typescript [shape]
class WSKitError extends Error {
  code: string // a stable id, e.g. 'forbidden', 'timeout'
  detail: unknown // a typed payload, narrowed by .matches()
}
```

::note
Values that are not `WSKitError`s arrive on `onError`: a WebSocket transport failure hands you the raw DOM `Event`, and an unsupported binary frame or a thrown handler/primitive/plugin value reaches the callback unchanged. Unclaimed server `WSKitError`s use [`onServerError`](/client/errors/onerror-routing) instead.
::

## Three families of error

A client sees errors from three places, imported from three places:

| Family                    | Examples                                                             | Import from             |
| ------------------------- | -------------------------------------------------------------------- | ----------------------- |
| **Your own** typed errors | `Forbidden`, `NotFound`                                              | your shared errors file |
| **Client-side** errors    | `Timeout`, `Disconnected`, `Dropped`                                 | `@wskit/client/errors`  |
| **Framework** built-ins   | `ValidationFailed`, `RateLimited`, `ConnectionBusy`, `StreamAborted` | `@wskit/core`           |

All three are `WSKitError`s and all three narrow with `.matches()` — the family only decides where you import the definition from. The client-side three are detailed in [Client-side Errors](/client/errors/client-side-errors); the framework catalog is in [Core](/core/builtin-errors).

When the server client type is derived with `InferClient`, its error union contains the server's declared errors together with the framework's built-in errors (and declared plugin errors). A server can only send a custom error code that appears in its declared `errors([...])` contract. If server code throws a `WSKitError` with an undeclared code, the engine logs a warning and sends the built-in `internal-error` instead, so the client does not receive an unknown contract error from a valid WSKit server.

## Three ways an error reaches you

An error either **rejects the specific call** it belongs to, **surfaces on `onServerError`** when a server error has no claimant, or **surfaces on `onError`** when local code or the transport fails:

```typescript [app.ts]
// 1. Claimed — it rejects the exact call that was waiting:
try {
  await socket.request('get-post', { id })
} catch (err) {
  if (NotFound.matches(err)) showMissing()
}

// 2. Unclaimed server error — no request/stream/channel was waiting for it:
socket.onServerError((err) => reportServerError(err))

// 3. Local or transport failure:
socket.onError((err) => reportLocalFailure(err))
```

A request rejects its promise, a stream loop throws, a channel `subscribe()` rejects — those are _claimed_ errors, delivered to the code that was waiting. An unclaimed server error goes to `onServerError`; local and transport failures go to `onError`. The routing rules are in [Error Routing](/client/errors/onerror-routing).

## Narrowing

You never compare error strings. `ErrorDef.matches(err)` is a type guard that confirms the code **and** narrows `detail` to its real type:

```typescript [app.ts]
import { Forbidden } from '../server/errors'

if (Forbidden.matches(err)) {
  console.log(err.detail.reason) // detail typed as { reason: string }
}
```

How `.matches()` works and how to define your own errors is in the [Error Model](/core/error-model) — it's the same on the client and the server, so it's documented once in Core.
