Almost every error the client gives you is a **`LiveThingError`**. It is a plain `Error` subclass with a stable `code` and an optional typed `detail`. This is true when the error comes from your server, from the client itself, or from the framework. All of these errors have the same shape, so you catch them and **narrow** them the same way. This chapter shows where errors arrive on the client and how to handle them. The shared error model and the full list of built-in errors are in [Core](/core/overview).

```typescript [shape]
declare class LiveThingError extends Error {
  code: string // a stable ID, for example 'forbidden' or 'timeout'
  detail: unknown // extra typed data, narrowed by .matches()
}
```

::note
Some values that are not `LiveThingError`s arrive on `onError`. When the WebSocket connection itself fails, you get the browser's raw `Event` object. When your listener, a primitive, or a plugin throws a value, that value reaches the callback unchanged. Server errors that no pending call is waiting for go to [`onServerError`](/client/errors/onerror-routing) instead.
::

## Three families of error

A client sees errors from three sources. You import each kind from a different place:

| Family                    | Examples                                                                  | Import from                |
| ------------------------- | ------------------------------------------------------------------------- | -------------------------- |
| **Your own** typed errors | `Forbidden`, `NotFound`                                                   | your shared errors file    |
| **Client-side** errors    | `Timeout`, `Disconnected`, `Dropped`, `StreamCorrupted`, `StreamOverflow` | `@livething/client/errors` |
| **Framework** built-ins   | `ValidationFailed`, `RateLimited`, `ConnectionBusy`, `StreamAborted`      | `@livething/core`          |

In Huddle, the typed errors `NotFound`, `Forbidden` and `RoomFull` are defined in [`../shared/errors`](/core/isomorphic-code#shared-error-definitions). The server and the client both import that file, and Huddle's definition lists all three in its [`errors(...)`](/server/capabilities/errors#declaring-typed-errors) capability. All three families are `LiveThingError`s, and all three narrow with `.matches()`. The family only decides where you import the definition from. The five client-side errors are described in [Client-side Errors](/client/errors/client-side-errors). The framework errors are listed in [Core](/core/builtin-errors).

When you build the client type with `InferClient`, its list of possible errors has three parts: the errors the server declares, the framework's built-in errors, and the errors that plugins declare. A server can only send a custom error code that it declares with the `errors([...])` capability. If server code throws a `LiveThingError` with a code it did not declare, the server logs a warning and sends the built-in `internal-error` instead. So a LiveThing server never sends the client a custom code that is missing from the contract.

## Three ways an error reaches you

An error reaches your code in one of three ways:

1. It **rejects the call** it belongs to. We say that the call **claims** the error.
2. It arrives on **`onServerError`** when it is a server error and no pending call claims it.
3. It arrives on **`onError`** when your local code or the connection fails.

```typescript [client/profile.ts]
import { NotFound } from '../shared/errors'
import { showMissingProfile } from './huddle-ui'
import { socket } from './socket'

// 1. Claimed: it rejects the exact call that was waiting.
try {
  await socket.request('get-profile', { userId: 'kofi' })
} catch (err) {
  if (NotFound.matches(err)) showMissingProfile('kofi')
}

// 2. Unclaimed server error: no request, stream, or channel was waiting for it.
socket.onServerError((err) => console.error('Server error', err.code))

// 3. Local or connection failure.
socket.onError((err) => console.error('Local failure', err))
```

Claimed errors go to the code that was waiting. A request rejects its promise. A stream loop throws. A channel `subscribe()` call rejects. An unclaimed server error goes to `onServerError`. Local and connection failures go to `onError`. The full rules are in [Error Routing](/client/errors/onerror-routing).

## Narrowing

You don't need to compare error strings. `ErrorDef.matches(err)` is a **type guard**: a function that returns `true` or `false`, and when it returns `true`, TypeScript also knows the type of `err`. It checks the code **and** narrows `detail` to its real type:

```typescript [client/profile.ts]
import { Forbidden } from '../shared/errors'
import { socket } from './socket'

try {
  await socket.request('get-profile', { userId: 'kofi' })
} catch (err) {
  if (Forbidden.matches(err)) {
    console.log(err.detail.reason) // detail typed as { reason: string }
  }
}
```

The [Error Model](/core/error-model) page explains how `.matches()` works and how to define your own errors. It works the same way on the client and the server, so Core documents it once.
