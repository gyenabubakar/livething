Most errors go to the call they belong to. A `request()` promise rejects, a stream loop throws, and a channel `subscribe()` rejects. Two socket listeners handle the rest:

- `onServerError` receives **unclaimed** server errors. An unclaimed error is an error from the server that no pending call is waiting for.
- `onError` receives local failures, transport failures, and setup failures.

This page shows exactly which error goes where.

```typescript [client/error-listeners.ts]
import { socket } from './socket'

const stopServer = socket.onServerError((error) =>
  console.error('Server error', error.code),
)
const stopLocal = socket.onError((error) =>
  console.error('Local failure', error),
)
// Call stopServer() or stopLocal() to remove that listener.
```

The `onError` callback receives `unknown`, because local code can throw any JavaScript value.

`onServerError` has two **overloads**. The broad overload takes only a callback. Its callback receives `LiveThingError<string, unknown>`, so it can also handle an error code that your client doesn't know yet, for example a code added in a newer server version. The code-specific overload takes an error code first. Its callback gets the `detail` type that your server declared for that code:

```typescript [client/error-listeners.ts]
import { socket } from './socket'

socket.onServerError('rate-limited', (error) => {
  showToast(`Slow down. Try again in ${error.detail.retryAfterMs} ms`)
})
```

## What lands on `onError`

These errors go to `onError`:

- **A WebSocket-level failure.** The browser's `WebSocket` fired its `error` event. You get the raw DOM `Event`, not a `LiveThingError`.
- **A failed connection attempt.** The socket could not be opened at all. For example, the `WebSocket` constructor threw, a [dynamic URL](/client/connecting/dynamic-url) function threw, or that function returned something other than a string, which gives a `LiveThingConfigError`. `onError` receives the thrown value as it is, so its message is kept. This happens on the first connect and on every reconnect attempt.
- **A value thrown by your own code.** When your `on()` listeners, intercepts, or plugin or primitive hooks throw, LiveThing catches the value and sends it here. The error is not lost.
- **An invalid `socket.disconnect(code, reason)` call.** The client closes the connection with code `1000` and reports a `RangeError` here. The connection still closes. Your code asked to close the connection, so keeping it open would be less safe.
- **A binary message the client cannot route.** Without [`binary()`](/client/primitives/binary), every binary message is reported here as a plain `Error` and dropped. With `binary()`, only a binary message that does not start with the LiveThing header is reported here, because it is not LiveThing data. A LiveThing binary frame that is broken is logged and dropped, the same as broken JSON text, and it does not reach `onError`.

::note
An unclaimed server error does not land here. It goes to [`onServerError`](#what-lands-on-onservererror). This includes an error in a plugin's namespace that no plugin listener handled.
::

To narrow an error you expect, use the `.matches(error)` method of its **error definition**. Keep the last branch ready for any other value:

```typescript [client/error-listeners.ts]
import { InternalError } from '@livething/core'
import { errorTracker, showOfflineNotice } from './huddle-ui'
import { socket } from './socket'

socket.onError((error) => {
  if (error instanceof Event) {
    // A transport-level WebSocket error.
    showOfflineNotice()
  } else if (InternalError.matches(error)) {
    // The socket could not be opened.
    showOfflineNotice()
  } else {
    // Any other value thrown by local code.
    errorTracker.capture(error)
  }
})
```

When you call `disconnect()`, use `CloseCodes.NORMAL` (`1000`) or an application code from `3000` to `4999`. Browsers only accept those codes from client code. The close reason must be at most 123 bytes when encoded as UTF-8.

## What lands on `onServerError`

The server reports an error with an `__error__` frame. A pending request, stream, channel, or plugin gets the error first when it is waiting for it. Only an `__error__` frame that none of them is waiting for reaches `onServerError`. One example is a top-level error that the server sends when no operation is pending. The callback always receives a `LiveThingError`, never a local thrown value:

```typescript [client/error-listeners.ts]
import { RateLimited } from '@livething/core'
import { showToast } from './huddle-ui'
import { socket } from './socket'

socket.onServerError((error) => {
  if (RateLimited.matches(error)) {
    showToast(
      `Slow down. Try again in ${error.detail.retryAfterMs} ms`,
    )
  } else {
    console.error('Server error', error.code)
  }
})
```

Use the broad overload for **version skew**: the server and the client were built from different versions, so the server can send a code this client was not built with. The code-specific overload only accepts a code that your server declares, and its callback gets the matching `detail` type. If no broad listener and no matching code listener is attached, the error is thrown again outside the socket's code, so it reaches the global error handler (see [With no listener attached](#with-no-listener-attached)).

## What does _not_ land on either listener

An error that a specific call is waiting for goes to that call. It does not go to either socket listener. The two paths never overlap:

```typescript [client/profile.ts]
import { NotFound } from '../shared/errors'
import { showMissingProfile } from './huddle-ui'
import { socket } from './socket'

// This rejects the request promise. Neither socket listener runs for it.
try {
  await socket.request('get-profile', { userId: 'kofi' })
} catch (err) {
  if (NotFound.matches(err)) showMissingProfile('kofi')
}
```

| Error tied to…                                                 | Goes to                               | Not to                 |
| -------------------------------------------------------------- | ------------------------------------- | ---------------------- |
| a pending `request()`                                          | that promise's `catch`                | either socket listener |
| a running `stream()`                                           | the `for await` loop throws           | either socket listener |
| a pending channel `subscribe()`                                | that promise's `catch`                | either socket listener |
| a channel rejoin after a reconnect                             | that channel's `onSubscriptionFailed` | either socket listener |
| any other error for a channel (for example a rejected message) | **`onServerError`**                   | `onError`              |
| an unclaimed server error                                      | **`onServerError`**                   | `onError`              |
| a local or transport failure                                   | **`onError`**                         | `onServerError`        |

## Plugin namespaces

A plugin's **namespace** is the prefix that LiveThing adds to the plugin's event names and error codes on the wire, so they don't clash with your app's names. A plugin gets its own unclaimed server errors first. Its scoped `onServerError` receives the plain code (`poll-closed`). If no plugin listener matches, the host socket's `onServerError` receives the namespaced code (`__acme:polls::poll-closed`). When a plugin's setup or handler code throws, the error goes to the host socket's `onError`. It does not become a scoped server error. See [Plugin Errors](/client/plugins/errors).

## With no listener attached

If no matching listener is attached, the error is **not lost**. This applies to a local or transport failure with no `onError` listener, and to an unclaimed server error with no matching `onServerError` listener. LiveThing throws the error again in a separate **microtask**. The error then reaches the global error handler, such as `window.onerror` or your error tracker:

```typescript [client/error-tracking.ts]
// No socket.onError listener is attached, so the global handler gets the error.
window.addEventListener('error', (event) => {
  errorTracker.capture(event.error)
})
```

So a bug in an `on()` handler, or an unclaimed server error, always shows up somewhere. In Node.js, the thrown error is an uncaught exception, which stops the process by default. When a matching listener is attached, the error goes to that listener and is not thrown again.

## Multiple listeners

You can attach more than one `onError` listener. Each call returns its own unsubscribe function. This lets a global error reporter and a feature-specific handler run side by side:

```typescript [client/error-listeners.ts]
import { socket } from './socket'

const stopReporter = socket.onError((err) =>
  errorTracker.capture(err),
)
const stopBanner = socket.onError((err) => {
  if (err instanceof Event) showOfflineNotice()
})
```
