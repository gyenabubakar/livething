Most errors reach you through the call they belong to — a `request()` promise rejects, a stream loop throws, a channel `subscribe()` rejects. The two socket listeners handle different leftovers: `onServerError` receives unclaimed server errors, while `onError` receives local, transport, and setup failures. This page is the exact routing.

```typescript [app.ts]
const stopServer = socket.onServerError((error) => reportServerError(error))
const stopLocal = socket.onError((error) => reportLocalFailure(error))
// stop() to remove the listener
```

`onError` is typed as `unknown`, because local code can throw any JavaScript value. The broad `onServerError` overload receives `WSKitError<string, unknown>` so it can handle a code added by a newer server. The code-specific overload preserves the declared detail type:

```typescript [app.ts]
socket.onServerError('rate-limited', (error) => {
  backOff(error.detail.retryAfter)
})
```

## What lands on `onError`

These route to `onError`:

- **A WebSocket-level failure** — the browser's `WebSocket` fired its `error` event. You get the raw DOM `Event`, not a `WSKitError`.
- **A failed connection attempt** — the socket couldn't be opened at all (the `WebSocket` constructor threw, or a dynamic-URL resolver threw). You get a `WSKitError` with code `internal-error` here, since the thrown value is wrapped before it surfaces. The same wrapped-error path fires whether it's the first connect or a reconnect retry — one `_openConnection` handles both.
- **A thrown value from your own code** — anything your `on()` listeners, intercepts, or a plugin/primitive hook throws is caught and surfaced here instead of being swallowed.
- **An unsupported binary frame** — the server sent a binary message. Binary frames aren't supported yet, so the client surfaces a plain `Error` here rather than crashing the socket callback.

::note
An unclaimed server error does not land here. It goes to [`onServerError`](#what-lands-on-onservererror), including an error in a plugin namespace that no plugin listener claimed.
::

Use an `ErrorDef`'s `.matches(error)` to narrow errors you expect, but keep the callback ready for arbitrary local values:

```typescript [app.ts]
socket.onError((error) => {
  if (error instanceof Event) {
    // a transport-level WebSocket error
    showConnectionTrouble()
  } else {
    // An arbitrary local thrown value.
    report(error)
  }
})
```

## What lands on `onServerError`

An unclaimed server `__error__` frame reaches `onServerError` after requests, streams, channels, and plugins have had a chance to claim it. A top-level error sent without a pending operation is one example. The callback receives a `WSKitError`, not a local thrown value:

```typescript [app.ts]
socket.onServerError((error) => {
  if (RateLimited.matches(error)) backOff(error.detail.retryAfter)
  else reportServerError(error)
})
```

The broad overload is the version-skew escape hatch: it handles a code this client was not built with. The code overload only accepts a declared code and gives its callback the matching `detail` type. If no broad listener or matching code listener is registered, the unclaimed server error is rethrown out of band to the host's global handler.

## What does _not_ land on either listener

An error that a specific call is waiting for is delivered **there**, not to either socket listener. The paths don't overlap:

```typescript [app.ts]
// This rejects the request promise — neither socket listener fires for it:
try {
  await socket.request('get-post', { id })
} catch (err) {
  if (NotFound.matches(err)) showMissing()
}
```

| Error tied to…                                      | Goes to                               | Not to                 |
| --------------------------------------------------- | ------------------------------------- | ---------------------- |
| a pending `request()`                               | that promise's `catch`                | either socket listener |
| a running `stream()`                                | the `for await` loop throws           | either socket listener |
| any channel (rejoin or a plain channel-tagged send) | that channel's `onSubscriptionFailed` | either socket listener |
| an unclaimed server error                           | **`onServerError`**                   | `onError`              |
| a local or transport failure                        | **`onError`**                         | `onServerError`        |

## Plugin namespaces

A plugin claims its own unclaimed server errors first. Its scoped `onServerError` receives the plain code (`room-full`). If no plugin listener matches, the host `onServerError` receives the namespaced code (`__acme:room::room-full`). Local plugin setup and handler throws still go to the host socket's `onError`; they do not become scoped server errors. See [Plugin Errors](/client/plugins/errors).

## With no listener attached

If no matching listener is registered, the error is **not swallowed**. A local or transport failure with no `onError` listener, or an unclaimed server error with no matching `onServerError` listener, is rethrown out of band (on a microtask) so it reaches the host's global error handler — `window.onerror`, your error tracker — instead of vanishing:

```typescript [app.ts]
// No matching listener: the error still reaches window.onerror / your reporter.
```

This means a bug in an `on()` handler or an unclaimed server error won't silently disappear. Once you attach the matching listener, it takes over and the rethrow stops.

## Multiple listeners

`onError` can have more than one listener, and each call returns its own unsubscribe function. That lets a global reporter and a feature-specific handler coexist:

```typescript [app.ts]
const stopReporter = socket.onError((err) => errorTracker.capture(err))
const stopBanner = socket.onError((err) => {
  if (err instanceof Event) showOfflineBanner()
})
```
