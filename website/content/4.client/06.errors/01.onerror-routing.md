Most errors reach you through the call they belong to — a `request()` promise rejects, a stream loop throws, a channel `subscribe()` rejects. `onError` is the **catch-all** for everything else: errors that no specific call was waiting for. This page is the exact routing.

```typescript [app.ts]
const stop = socket.onError((error) => {
  report(error)
})
// stop() to remove the listener
```

The callback is typed to your contract's error union plus a plain DOM `Event`, because more than one kind of thing can land here.

## What lands on `onError`

These route to `onError`:

- **A WebSocket-level failure** — the browser's `WebSocket` fired its `error` event. You get the raw DOM `Event`, not a `WSKitError`.
- **A failed connection attempt** — the socket couldn't be opened at all (the `WebSocket` constructor threw, or a dynamic-URL resolver threw). You get a `WSKitError` with code `internal-error` here, since the thrown value is wrapped before it surfaces. The same wrapped-error path fires whether it's the first connect or a reconnect retry — one `_openConnection` handles both.
- **An unclaimed typed error** — the server sent a `WSKitError` that no `request`, `stream`, or `channel` was waiting for. A server `ctx.send`-ing a top-level error (one not tagged to any channel), for instance. An error tagged to a channel goes to that channel's `onSubscriptionFailed` instead — see [Lifecycle Hooks](/client/channels/lifecycle-hooks).
- **A thrown value from your own code** — anything your `on()` listeners, intercepts, or a plugin/primitive hook throws is caught and surfaced here instead of being swallowed.
- **An unsupported binary frame** — the server sent a binary message. Binary frames aren't supported yet, so the client surfaces a plain `Error` here rather than crashing the socket callback.

::note
An unclaimed error in a **plugin's** namespace does not land here first. It goes to that plugin's own scoped `onError` (or, if the plugin has no `errors` section or no handler registered, falls through to this top-level `onError` with the namespaced code kept). See [Plugin Errors](/client/plugins/errors) for the full routing.
::

`onError`'s callback is typed to `ContractError<TContract> | Event | UnrecognizedError` — a union of your contract's declared errors, the plain DOM `Event` from the first case above, or an `UnrecognizedError` for anything else a listener, intercept, or hook threw that is neither of those (a plain `Error`, a string, or any other thrown value). `ContractError` already folds in the framework's built-in errors alongside your server's and any plugins' errors, so narrow with `error instanceof Event` first, then `error instanceof WSKitError` and `switch (error.code)` for a typed `error.detail`, and treat whatever is left as unexpected:

```typescript [app.ts]
import { WSKitError } from '@wskit/client/errors'

socket.onError((error) => {
  if (error instanceof Event) {
    // a transport-level WebSocket error
    showConnectionTrouble()
  } else if (error instanceof WSKitError) {
    switch (error.code) {
      case 'rate-limited':
        backOff(error.detail.retryAfter)
        break
      default:
        // a code the contract doesn't declare can still arrive at
        // runtime — a server the client's types don't match
        report(error)
    }
  } else {
    // an UnrecognizedError — a thrown value from your own code that is
    // neither a WSKitError nor a transport Event; treat it as a bug to log
    report(error)
  }
})
```

## What does _not_ land on `onError`

An error that a specific call is waiting for is delivered **there**, not to `onError`. The two paths don't overlap:

```typescript [app.ts]
// This rejects the request promise — onError does NOT fire for it:
try {
  await socket.request('get-post', { id })
} catch (err) {
  if (NotFound.matches(err)) showMissing()
}
```

| Error tied to…                                      | Goes to                               | Not to    |
| --------------------------------------------------- | ------------------------------------- | --------- |
| a pending `request()`                               | that promise's `catch`                | `onError` |
| a running `stream()`                                | the `for await` loop throws           | `onError` |
| any channel (rejoin or a plain channel-tagged send) | that channel's `onSubscriptionFailed` | `onError` |
| nothing in particular                               | **`onError`**                         | —         |

So `onError` is genuinely the leftovers — the typed errors that arrived with no waiting caller, plus transport failures and bugs in your own handlers.

## With no listener attached

If no `onError` listener is registered, those leftover errors are **not swallowed**. They're rethrown out of band (on a microtask) so they reach the host's global error handler — `window.onerror`, your error tracker — instead of vanishing:

```typescript [app.ts]
// No onError listener: an unclaimed server error or a throw in a listener
// still surfaces — it reaches window.onerror / your error reporter.
```

This means a bug in an `on()` handler won't silently disappear even before you've wired up `onError`. Once you do attach a listener, it takes over and the rethrow stops.

## Multiple listeners

`onError` can have more than one listener, and each call returns its own unsubscribe function. That lets a global reporter and a feature-specific handler coexist:

```typescript [app.ts]
const stopReporter = socket.onError((err) => errorTracker.capture(err))
const stopBanner = socket.onError((err) => {
  if (err instanceof Event) showOfflineBanner()
})
```
