Most errors a client sees come from the server. Five errors come from the **client itself**. The client creates them locally when a call can't finish, and they are never sent over the network. Import them from `@livething/client/errors`:

| Error             | Code               | Meaning                                                                                             |
| ----------------- | ------------------ | --------------------------------------------------------------------------------------------------- |
| `Timeout`         | `timeout`          | No answer arrived in time.                                                                          |
| `Disconnected`    | `disconnected`     | The socket closed (or was already closed) before the call could finish.                             |
| `Dropped`         | `dropped`          | The call's message was removed from the offline buffer before it was sent, or was too big to go in. |
| `StreamCorrupted` | `stream-corrupted` | A chunk of a stream is missing, so the stream failed instead of ending with a hole in it.           |
| `StreamOverflow`  | `stream-overflow`  | The chunks a stream's loop had not read yet went over `stream({ maxBytes })`, so the stream failed. |

## Where each error comes from

**`Timeout`** rejects these calls when no answer arrives before their timeout ends:

- `socket.request()`: the server sent no reply.
- an upload's [`start()`](/client/primitives/uploads#starting-and-retrying): the server did not answer the start within 30 seconds. Once the upload runs, it has no timeout.
- `socket.stream()`: the promise it returns rejects when the server does not start the stream in time.
- [`handle.nudge()`](/client/streams/nudges) on a stream: the server did not confirm the nudge.
- The channel queries [`receiversOf()`](/client/primitives/inbox) and [`readersOf()`](/client/primitives/read-receipts): the server sent no answer.

`Timeout` also ends a running stream. The `for await` loop over the stream throws it when no chunk arrives within the stream's timeout. After a reconnect, a durable stream also throws it when no continued chunk arrives in time.

**`Disconnected`** rejects a call when the socket closes while the call waits. This includes a call to `disconnect()` and a connection that drops. It also rejects a call made when the socket is closed and no reconnect is in progress, so the call fails right away instead of waiting for its timeout. The calls are:

- `socket.request()`
- `socket.stream()`, while it waits for the stream to start
- `handle.nudge()` on a stream (a nudge also fails right away when the socket is not open)
- `receiversOf()` and `readersOf()`
- a channel `subscribe()`
- a channel `unsubscribe()`, when the leave can't be confirmed: you called `disconnect()`, or the client stopped trying to reconnect
- an upload's [`start()`](/client/primitives/uploads#starting-and-retrying). The upload is not lost: call `start()` again when the socket is open, and it resumes

`Disconnected` also ends a running stream. The `for await` loop throws it when the socket closes, unless the stream is durable and the client will reconnect. A durable stream still throws it if the client stops trying to reconnect.

**`Dropped`** only happens with the [`buffering()`](/client/primitives/buffering) primitive. That primitive keeps outgoing messages in a buffer while the socket is offline, and sends them when it opens again. A `request()` or a `stream()` start that waits in this buffer rejects with `Dropped` when its message is removed before it is sent. This happens in three cases:

- The buffer is full. The oldest message is removed to make room for a new one.
- The message's TTL (time to live, the longest time a message may wait in the buffer) ran out while the client was offline.
- The message alone is bigger than the buffer's `maxBytes`, so it never goes in. The call rejects at once.

When you call `disconnect()`, the buffer is cleared, and a buffered `request()` or `stream()` start rejects with `Disconnected` instead.

**`StreamCorrupted`** ends a stream when a chunk is missing. Each chunk carries a sequence number (`seq`) that goes up by 1, so the client knows which chunk comes next. Its `detail` is `{ expected, got }`: the `seq` the client was waiting for, and the one that came. The `for await` loop over a stream you started throws it. For a plain stream, the client also tells the server to stop it. A recorded stream keeps its recording, so you can call [`continueStream()`](/client/streams/durable-and-continue) with the last `seq` you got and receive the missing chunks. A broadcast listener's `onError` gets it, and the rest of that run is ignored. The client checks:

- the first chunk of a stream you started, which must be `seq` 1,
- the first chunk after [`continueStream()`](/client/streams/durable-and-continue), which must be `lastKnownSeq + 1`,
- each next chunk, which must be exactly one more than the last,
- the end of the stream: the server's end message carries the last `seq` it sent. If that is not the last one the client got, the stream fails with `expected` set to the server's last `seq` and `got` set to the client's.

A broadcast listener can join a stream while it runs, so its first chunk can have any number. The check starts from the chunk after it. It also starts again after a reconnect, or after the member leaves and joins the channel again, because chunks sent while it was away were missed, not lost.

**`StreamOverflow`** ends a stream whose `for await` loop reads more slowly than the chunks arrive. The chunks that wait for the loop are limited by [`stream({ maxBytes })`](/client/primitives/stream#limiting-unread-chunks), 16 MiB by default. A text chunk counts the UTF-8 bytes of its payload, and a [binary chunk](/client/primitives/binary#streams) counts its info and its bytes. When a chunk would go over the limit, the loop gets the chunks that were already waiting, then throws `StreamOverflow`. Its `detail` is `{ maxBytes }`. As for `StreamCorrupted`, the client tells the server to stop a plain stream, and a recorded stream keeps its recording, so you can continue it. A broadcast listener's `onChunk` runs for each chunk as it arrives, so it never gets this error.

The calls that `Timeout`, `Disconnected` and `Dropped` reject on this page have binary versions, and those reject in the same way: `socket.binary.request()` like `socket.request()`, and `socket.binary.stream()` like `socket.stream()`. See [binary](/client/primitives/binary).

`@livething/client/errors` also exports `UploadAborted`. The client creates it for two of its reasons, `'cancelled'` and `'not-resumable'`, and the server sends the others. The server can send `'cancelled'` too, to a start it was still handling when the cancel came. See [uploads · Errors](/client/primitives/uploads#errors).

## Narrowing a client-side error

These errors are `LiveThingError`s like any other error, so you narrow them with `.matches()`:

```typescript [client/room.ts]
import {
  Disconnected,
  Dropped,
  Timeout,
} from '@livething/client/errors'
import {
  appendMessage,
  showToast,
  waitForReconnection,
} from './huddle-ui'
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')
await room.subscribe({})

try {
  const older = await room.request('load-history', {
    before: Date.now(),
  })
  for (const message of older.messages) appendMessage(message)
} catch (err) {
  if (Timeout.matches(err)) {
    showToast('History is slow. Try again.')
  } else if (Disconnected.matches(err)) {
    waitForReconnection()
  } else if (Dropped.matches(err)) {
    showToast('Your request was not sent')
  } else {
    throw err
  }
}
```

## Narrowing any error on the client

A `catch` block can receive a client-side error, a typed error from your server, or a framework error. All of them are `LiveThingError`s, and you narrow all of them the same way. An [`onServerError`](/client/errors/onerror-routing) callback receives only the server and framework errors, never the client-side ones. Match the errors you handle and throw the rest again:

```typescript [client/room.ts]
import { Timeout } from '@livething/client/errors'
import { NotFound } from '../shared/errors' // your own errors, shared with the server

import {
  render,
  retryLoadingProfile,
  showMissingProfile,
} from './huddle-ui'
import { socket } from './socket'

try {
  const profile = await socket.request('get-profile', {
    userId: 'kofi',
  })
  render(profile.name)
} catch (err) {
  if (NotFound.matches(err)) showMissingProfile('kofi')
  else if (Timeout.matches(err)) retryLoadingProfile('kofi')
  else throw err // not one we handle here
}
```

The [Error Model](/core/error-model) page explains the `LiveThingError` shape, the `error()` factory, and how `.matches()` works. The [Built-in Errors](/core/builtin-errors) page lists every framework error your server can send, such as `RateLimited`, `ConnectionBusy`, `StreamAborted`, and `ValidationFailed`. Both pages are in the [Core](/core/overview) section, because the client and the server share them.
