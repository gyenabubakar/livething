Reconnection is **opt-in**: without this primitive, a dropped socket stays closed. Add `reconnection()` and a connection that drops unexpectedly — a server restart, a network blip, a deploy — comes back on its own, with exponential backoff and jitter.

```typescript [app.ts]
import { client, connect, reconnection } from '@wskit/client'
import { CloseCodes } from '@wskit/core'
import type { MySocket } from './socket-types'

const socket = client<MySocket>()(
  connect('wss://example.com/ws'),
  reconnection({
    maxAttempts: Infinity,
    nonRetryableCodes: [CloseCodes.BANNED, CloseCodes.CAPACITY],
  }),
)
```

It adds no methods; it drives the `reconnecting` state and the retry loop.

## Backoff and jitter

Each retry waits longer than the last — the delay doubles (1s, 2s, 4s, …) up to `maxDelay`, with a random ±30% added so a crowd of clients reconnecting after a server restart spread out instead of stampeding. The backoff resets to its base after a successful connection. The doubling and the jitter are fixed; the only knobs are `maxDelay` (the cap) and `maxAttempts` (how many tries).

## Options

```typescript [app.ts]
reconnection({
  maxAttempts: 10,        // retries before giving up; Infinity never stops (default: 10)
  maxDelay: 30_000,       // cap on the backoff delay, in ms (default: 30_000)
  networkAware: true,     // pause retries while offline (default: true)
  shouldReconnect: (code, reason) => undefined, // per-close decision (see below)
  nonRetryableCodes: [],  // close codes that should NOT reconnect
})
```

When `maxAttempts` is reached, the state goes to `closed` and `socket.onReconnectFailed(...)` fires once — the place to surface a "connection lost, please refresh" UI:

```typescript [app.ts]
socket.onReconnectFailed(() => showPermanentDisconnectBanner())
```

It stays closed until you call `connect()` again. With `maxAttempts: Infinity` it never gives up (and `onReconnectFailed` never fires). Note `onReconnectFailed` is **only** for running out of attempts — a retry suppressed by `shouldReconnect`/`nonRetryableCodes` goes straight to `closed` without firing it (see below).

## Deciding per close code

Not every close should retry. Reconnecting after `AUTH_INVALID` with the same bad token is pointless; after `BANNED` it's harmful. Two options control this:

- **`nonRetryableCodes`** — a shorthand list of close codes that should not reconnect.
- **`shouldReconnect(code, reason)`** — a callback for full control. Return `true` to force a retry, `false` to suppress it, or `undefined` to fall through to the default.

```typescript [app.ts]
reconnection({
  shouldReconnect(code, reason) {
    if (code === CloseCodes.AUTH_EXPIRED) {
      refreshAuthToken() // query() picks up the new token on the retry
      return true
    }
    if (code === CloseCodes.BANNED) return false
    // return undefined → use the default
  },
})
```

The decision is checked in order: any primitive/plugin `shouldReconnect` hook first, then your callback, then `nonRetryableCodes`, then the default (reconnect). When a retry is suppressed, the state goes straight to `closed` — `onReconnectFailed` does **not** fire on that path (it's only for running out of attempts).

## Network-aware retries

`networkAware` (on by default) pauses the retry loop while the device is offline, then reconnects immediately — with the backoff reset — when it comes back. It reads the `online` signal from a [platform environment](/client/platform/environments), so it only does anything when you've installed `platform({ environment })` with an environment that reports network changes. Without that signal it quietly stays timer-only and never throws — going offline never calls `disconnect()`, the socket just waits.
