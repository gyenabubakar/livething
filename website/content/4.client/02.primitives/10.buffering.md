`buffering()` keeps the messages you `send()` while the socket is not connected. When the socket connects again, it sends them in the same order. We call this list of waiting messages the **buffer**, and sending all of it is a **flush**. Without buffering (the default), a `send()` on a socket that is not open is dropped and returns `false`. This primitive adds no methods to the socket. It only manages the buffer of outgoing messages. Use it together with [`reconnection()`](/client/primitives/reconnection), which connects the socket again so the buffer can flush.

```typescript [client/socket.ts]
import {
  binary,
  buffering,
  client,
  connect,
  reconnection,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  reconnection(),
  buffering({ maxMessages: 50 }),
)
```

## Options

```typescript [client/socket.ts]
import { buffering } from '@livething/client'

buffering({
  maxMessages: 50, // most messages to hold; the oldest is dropped when full (default: 50)
  maxBytes: 1024 * 1024, // most bytes to hold; the oldest is dropped when full (default: 1 MiB)
  ttl: 10_000, // time-to-live in ms for queued messages (default: none). See below
  flushInterval: 0, // ms between messages on flush; 0 sends them all at once (default: 0)
})
```

Adding `buffering()` turns it on: every send made while the socket is down is queued. All options are optional.

A message's size is its length on the wire. For a text message, that is its UTF-8 bytes. For a [binary message](/client/primitives/binary), it is the whole frame: the 9-byte header, the info and the metadata, and the bytes. A 2 MiB avatar sent while offline is over the default `maxBytes`, so it is not queued and `binary.send` returns `false`. Raise `maxBytes` to queue large binary messages. A queued binary message keeps its own copy of the bytes, and it waits in the same queue as text, so the two keep their order. The message count and the byte count both apply: the buffer drops the oldest messages until the new one fits in both.

`maxMessages` and `maxBytes` must be positive whole numbers. `buffering({ maxMessages: 0 })`, or a negative or decimal value, throws a `LiveThingConfigError` when you build the socket with `client()`. So does a `ttl` that is `NaN`, infinite or negative (a `ttl` of `0` is allowed and means the message never expires), and a `flushInterval` outside `0` to `2147483647` (`2 ** 31 - 1`, the longest a timer can hold).

## What gets queued, and when the queue is cleared

A `send()` goes into the buffer and returns `true` in two cases:

- The socket is not open. Its state is `closed`, `connecting` or `reconnecting`.
- A slow flush (see [Flush order](#flush-order)) is still sending the older messages.

When the buffer is full (it holds `maxMessages` messages, or the new message would take it over `maxBytes`), the **oldest** message is dropped to make room. `send()` still returns `true`, because the new message was accepted.

A single message bigger than `maxBytes` is never queued, because it could never fit. When the socket is open and nothing is waiting in the buffer, it is sent as normal, since it does not need the buffer. When it would have to wait (the socket is not open, or a slow flush is still running), it is refused. It is not sent ahead of the queue either. Then `send()` returns `false`, and a `request()` or `stream()` rejects with `Dropped` at once.

What happens to the buffer depends on how the socket closed:

- An **unexpected drop** (for example, the network fails) keeps the queue. The messages go out on the next reconnect.
- A call to **`disconnect()`** deletes the queue. You chose to stop, so the queued messages are not sent.

Some operations return a promise: a [`request()`](/client/primitives/client-requests), and the [`stream()`](/client/primitives/stream) call that starts a stream. Their messages can go into the buffer too. On flush, such a message is sent only if its promise is still waiting. If the promise already failed (for example, it timed out), the message is dropped. This way the server does not run an operation that your code was already told had failed.

It also works the other way. When a buffered operation can't be sent, its promise **rejects**, so it does not wait forever. A buffered `request()` rejects with:

- `Dropped` if the buffer drops it (the buffer was full, or the message alone is bigger than `maxBytes`) or its TTL passes.
- `Disconnected` if a connection closes before the flush, for example a reconnect attempt fails or you call `disconnect()`.

You import both errors from `@livething/client/errors`. `request()` needs the [`clientRequests()`](/client/primitives/client-requests) primitive, so this socket adds it:

```typescript [client/socket.ts]
import {
  binary,
  buffering,
  client,
  clientRequests,
  connect,
  reconnection,
} from '@livething/client'
import { Disconnected, Dropped } from '@livething/client/errors'
import { showToast } from './huddle-ui'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  reconnection(),
  buffering(),
  clientRequests(),
)

try {
  // sent now, or queued if the socket is not connected
  await socket.request('report-message', {
    messageId: 'm-42',
    reason: 'spam',
  })
} catch (err) {
  if (Dropped.matches(err)) {
    showToast('Not sent while offline. Try again.')
  } else if (Disconnected.matches(err)) {
    showToast('Disconnected')
  }
}
```

## Flush order

By default (`flushInterval: 0`), the whole buffer is sent at once on reconnect, in the order you sent the messages. A server with rate limits may disconnect a client that sends many messages at once. To avoid this, set `flushInterval`. The buffer then sends one message every `flushInterval` milliseconds. While this slow flush is still running, new `send()` calls go into the buffer after the messages that are still waiting. So the order stays the same, and a new message is never sent before an older one.

## Message TTL

TTL (time-to-live) is how long a message may wait in the buffer. Some messages are useless if they are sent late. For example, a status change from 30 seconds ago is wrong by the time the socket is back online. `ttl` drops a queued message after that many milliseconds. It is one number for every queued message, top-level and channel sends alike:

```typescript [client/socket.ts]
import { buffering } from '@livething/client'

buffering({
  ttl: 30_000,
})
```

To give one message its own lifetime, set `ttl` on that `send()` call. The per-call value wins over the `buffering()` value. This works the same on a channel handle. Like the `buffering()` option, it must be a finite number, 0 or more: `NaN`, `Infinity` or a negative number throws a `LiveThingConfigError`. A `start-typing` notice is wrong a few seconds later, while a chat message should wait for the full 30 seconds. This example uses a socket built with `buffering({ ttl: 30_000 })`:

```typescript [client/socket.ts]
socket.send('set-status', { status: 'away' }, { ttl: 1_000 })

const room = socket.channel('rooms', 'room:general')
room.send('start-typing', {}, { ttl: 5_000 }) // dropped if it waited more than 5 seconds
room.send('send-message', { text: 'hello' }) // no ttl here, so it uses the 30 seconds from buffering()
```

The client picks the TTL in this order:

1. The `ttl` you passed to `send()`, if any.
2. The `ttl` from `buffering()`, if any.
3. Otherwise, no TTL: the message waits until the flush, or until the buffer is full and drops its oldest message.

Expired messages are removed just before the flush and are never sent.

::note
The `send()` call that queued an expired message still returned `true`, because at that moment the buffer accepted the message. The drop happens later.

A `ttl` of `0` does **not** drop the message at once. It means the message never expires, the same as no TTL. Use it on one `send()` to keep an important message past the `buffering()` TTL.
::
