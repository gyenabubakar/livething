`buffering()` keeps the messages you `send()` while the socket is not connected. When the socket connects again, it sends them in the same order. We call this list of waiting messages the **buffer**, and sending all of it is a **flush**. Without buffering (the default), a `send()` on a socket that is not open is dropped and returns `false`. This primitive adds no methods to the socket. It only manages the buffer of outgoing messages. Use it together with [`reconnection()`](/client/primitives/reconnection), which connects the socket again so the buffer can flush.

```typescript [client/socket.ts]
import {
  buffering,
  client,
  connect,
  reconnection,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  reconnection(),
  buffering({ enabled: true, maxSize: 50 }),
)
```

## Options

```typescript [client/socket.ts]
buffering({
  enabled: true, // queue sends made while disconnected (default: false)
  maxSize: 50, // most messages to hold; the oldest is dropped when full (default: 50)
  ttl: 10_000, // time-to-live in ms for queued messages (default: none). See below
  flushInterval: 0, // ms between messages on flush; 0 sends them all at once (default: 0)
})
```

`enabled` defaults to `false`, so `buffering()` alone queues nothing. You turn buffering on with `{ enabled: true }`.

`maxSize` must be a positive whole number. `buffering({ maxSize: 0 })`, or a negative or decimal value, throws a `LiveThingConfigError` when you build the socket with `client()`.

## What gets queued, and when the queue is cleared

A `send()` goes into the buffer and returns `true` in two cases:

- The socket is not open. Its state is `closed`, `connecting` or `reconnecting`.
- A slow flush (see [Flush order](#flush-order)) is still sending the older messages.

When the buffer is full, the **oldest** message is dropped to make room. `send()` still returns `true`, because the new message was accepted.

What happens to the buffer depends on how the socket closed:

- An **unexpected drop** (for example, the network fails) keeps the queue. The messages go out on the next reconnect.
- A call to **`disconnect()`** deletes the queue. You chose to stop, so the queued messages are not sent.

Some operations return a promise: a [`request()`](/client/primitives/client-requests), and the [`stream()`](/client/primitives/stream) call that starts a stream. Their messages can go into the buffer too. On flush, such a message is sent only if its promise is still waiting. If the promise already failed (for example, it timed out), the message is dropped. This way the server does not run an operation that your code was already told had failed.

It also works the other way. When a buffered operation can't be sent, its promise **rejects**, so it does not wait forever. A buffered `request()` rejects with:

- `Dropped` if the buffer drops it (the buffer was full) or its TTL passes.
- `Disconnected` if a connection closes before the flush, for example a reconnect attempt fails or you call `disconnect()`.

You import both errors from `@livething/client/errors`. `request()` needs the [`clientRequests()`](/client/primitives/client-requests) primitive, so this socket adds it:

```typescript [client/socket.ts]
import {
  buffering,
  client,
  clientRequests,
  connect,
  reconnection,
} from '@livething/client'
import { Disconnected, Dropped } from '@livething/client/errors'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  reconnection(),
  buffering({ enabled: true }),
  clientRequests(),
)

try {
  // sent now, or queued if the socket is not connected
  await socket.request('report-message', {
    messageId,
    reason: 'spam',
  })
} catch (err) {
  if (Dropped.matches(err))
    showToast('Not sent while offline. Try again.')
  else if (Disconnected.matches(err)) showToast('Disconnected')
}
```

## Flush order

By default (`flushInterval: 0`), the whole buffer is sent at once on reconnect, in the order you sent the messages. A server with rate limits (a maximum number of messages per second) may disconnect a client that sends many messages at once. To avoid this, set `flushInterval`. The buffer then sends one message every `flushInterval` milliseconds. While this slow flush is still running, new `send()` calls go into the buffer after the messages that are still waiting. So the order stays the same, and a new message is never sent before an older one.

## Message TTL

TTL (time-to-live) is how long a message may wait in the buffer. Some messages are useless if they are sent late. For example, a status change from 30 seconds ago is wrong by the time the socket is back online. `ttl` drops a queued message after that many milliseconds. It takes one number for all events, or a map with one value per event:

```typescript [client/socket.ts]
buffering({
  enabled: true,
  ttl: { 'set-status': 5_000 },
})
```

You can also set `ttl` on one `send()` call. The per-call value wins over the `buffering()` value:

```typescript [client/socket.ts]
socket.send('set-status', { status: 'away' }, { ttl: 1_000 })
```

Expired messages are removed just before the flush and are never sent. For events sent in a channel, a TTL you set on [`channels()`](/client/primitives/channels) wins over the `buffering()` value.
