`gaps()` adds `onGap()` to the socket and its channel handles. It tells your app that the server had already deleted messages the client had not seen, so a normal reconnect cannot fully catch up.

Each `onGap()` call returns a cleanup function. It is safe to call that
function more than once, including after a newer listener has been registered.

```typescript [app.ts]
import {
  channels,
  client,
  connect,
  dedup,
  gaps,
  replay,
} from '@livething/client'
import type { MySocket } from './socket-types'

const socket = client<MySocket>()(
  connect('wss://example.com/ws'),
  channels(),
  dedup(),
  replay(),
  gaps(),
)

socket.onGap((info) => {
  refetchTopLevelData(info.missedThrough)
})

socket.channel('chat').onGap((info) => {
  refetchChannel(info.channel, info.missedThrough)
})
```

`socket.onGap` receives only top-level gaps. A channel gap goes only to that channel's `onGap`; channels with the same name in different dynamic families remain separate.

The callback receives:

```typescript
interface GapInfo {
  missedThrough: number
  channel?: string
  channelFamily?: string
}
```

`missedThrough` is the highest sequence that is gone. Treat the affected scope as incomplete and reload it from an API or another source of truth.

## Why it is separate

Both [`replay()`](/client/primitives/replay) and [`inbox()`](/client/primitives/inbox) can receive the same `__gap__` protocol frame. They still do their own internal work: replay advances its catch-up cursor, while inbox acknowledges the missing range. `gaps()` only owns the app-facing callback and consumes the reserved frame after those primitives have read it.

This means:

- Use `replay()` without `gaps()` when catch-up should stay silent.
- Use `inbox()` with `gaps()` to report inbox overflow without adding replay.
- Use all three when the app needs inbox delivery, replay catch-up, and a visible gap signal.

Without `gaps()`, `onGap` is not part of the socket or channel type. The reserved `__gap__` frame still never reaches ordinary `on()` handlers.
