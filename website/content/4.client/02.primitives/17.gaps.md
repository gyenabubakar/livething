`gaps()` adds an `onGap()` method to the socket and to each channel handle. A **gap** is a range of messages that the client never received and that the server has already deleted. The server deletes old messages because of [replay](/client/primitives/replay) retention limits or [inbox](/client/primitives/inbox) overflow limits. When there is a gap, a normal reconnect cannot give the client every missed message. `onGap()` tells your app about it, so the app can load the missing data another way.

Each `onGap()` call returns a cleanup function. Call it to stop listening. You can call it more than once. A second call does nothing, even if you added a new listener after the first call.

```typescript [app.ts]
import {
  channels,
  client,
  connect,
  dedup,
  gaps,
  replay,
} from '@livething/client'
import type { MySocket } from './socket-types'

const socket = client<MySocket>()(
  connect('wss://example.com/ws'),
  channels(),
  dedup(),
  replay(),
  gaps(),
)

socket.onGap((info) => {
  reloadNotifications(info.missedThrough)
})

socket.channel('chat').onGap((info) => {
  reloadChatHistory('chat', info.missedThrough)
})
```

`socket.onGap` receives only top-level gaps. A **top-level** gap is a gap in the messages sent to the socket itself, outside any channel. A channel gap goes only to the `onGap` of that channel. Two channels with the same name in different dynamic families are separate channels, so a gap in one never reaches the other. (A **dynamic family** is a group of channels that share one definition, such as `rooms`.)

The callback receives a `GapInfo` object:

```typescript
interface GapInfo {
  missedThrough: number
  channel?: string
  channelFamily?: string
}
```

- `missedThrough` is the highest sequence number that the server deleted. Every message you had not received, up to and including this number, is gone.
- `channel` and `channelFamily` are set on a channel gap. They are not set on a top-level gap. For a dynamic family, use both values together to know which channel it is.

When a gap arrives, treat that data as incomplete. Load it again from its **source of truth**: the place that keeps the full data, such as your HTTP API or your database.

## Why it is separate

[`replay()`](/client/primitives/replay) and [`inbox()`](/client/primitives/inbox) both read the same `__gap__` frame. (A frame is one message on the wire. `__gap__` is a protocol frame that LiveThing sends, not an event from your contract.) Each primitive does its own work with it:

- `replay()` moves its catch-up cursor forward to `missedThrough`, so the next reconnect does not ask for the deleted messages again.
- `inbox()` acknowledges the missing range, so the server does not report the same gap again.

`gaps()` adds only the `onGap` callback for your app. It reads the frame after those primitives have read it. Then it removes the frame, so no other code sees it.

So you can combine them in these ways:

- Use `replay()` without `gaps()` when catch-up should happen without telling the app about gaps.
- Use `inbox()` with `gaps()` to report inbox overflow. You do not need `replay()` for this.
- Use all three when the app needs inbox delivery, replay catch-up, and a gap callback.

Without `gaps()`, `onGap` does not exist on the socket or channel type, so TypeScript reports an error if you call it. The `__gap__` frame still never reaches your normal `on()` handlers.
