`uploads()` lets the client send **one large file in pieces** to a server's [upload handler](/server/binary/uploads). The client cuts the file into pieces, sends them only as fast as the server reads them, and resumes the upload after a drop, from the last bytes the server stored. A small file that fits in one message can go with [`binary.send`](/client/primitives/binary#sending) instead.

`uploads()` needs [`binary()`](/client/primitives/binary), because the pieces are binary messages:

```typescript [client/socket.ts]
import {
  binary,
  channels,
  client,
  connect,
  reconnection,
  uploads,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://huddle.example.com/huddle'),
  binary(),
  uploads(),
  channels(),
  reconnection(),
)
```

Without `binary()`, `client()` gives a type error and throws, as for any primitive whose dependency is missing. Without `uploads()`, `socket.binary.upload` is a stub on the type: calling it is a type error with this message:

```text
[livething] binary.upload needs the uploads() primitive — add uploads() to client()
```

## Making an upload

`socket.binary.upload` makes an upload. It takes the event name, the file, and `{ input }` with the options. The file comes second because the upload is about the file. It is on the socket, not on a channel handle: an upload belongs to no channel, so a channel handle has no `binary.upload`. A plugin's [scoped socket](/client/plugins/scoped-socket#binary-needs-binary) has it too, for the plugin's own uploads, with their short names. The plugin lists `binary` and `uploads` in its `dependencies`, and the app registers `uploads()`.

::field-group
::field{name="event" type="string" required}
The name of the server's `binary.upload(...)` handler.
::
::field{name="source" type="Blob | Uint8Array | ArrayBuffer | AsyncIterable<Uint8Array>" required}
The file. A `File` is a `Blob`. For a `Blob` or bytes, the client sends the total size at the start, so the server refuses a file over its `maxBytes` before any piece is sent. An `AsyncIterable` has [some limits](#asynciterable-sources).
::
::field{name="options.input" required}
The JSON input that the server's `input` schema checks, such as the name and type of the file. Its type comes from the server's handler. When that type allows `undefined`, you can leave out the whole options object.
::
::field{name="options.uploadId" type="string"}
The ID of an earlier upload, to [resume it](#resuming-after-a-reload). Without it, the upload gets a new ID.
::
::

It returns an `Upload` handle. **Nothing is sent until you call `start()`.** So you can make the upload, add a progress listener, and keep its ID first.

::field-group
::field{name="upload.id" type="string"}
The upload's ID. Keep it to [resume](#resuming-after-a-reload) the upload later.
::
::field{name="upload.start()" type="Promise<{ info }>"}
[Sends the upload](#starting-and-retrying), or resumes it after a drop. Resolves with the reply's info.
::
::field{name="upload.cancel()" type="void"}
[Stops the upload](#cancelling) on the client and on the server.
::
::field{name="upload.onProgress(listener)" type="() => void"}
Calls `listener` with the [progress](#progress), the bytes the server's `run` has read. Returns an unsubscribe.
::
::

## Starting and retrying

`upload.start()` sends the upload, and resolves with `{ info }`, the reply of the server's `run`. When the socket closes, it rejects with `Disconnected`. The upload is not lost: call `start()` again, and the client resumes it from the bytes the server stored. The app does this itself, usually as soon as the socket is open again. Huddle has one function for it, `uploadUntilDone`, in two steps:

::steps{level="3"}

### Start again after each drop

`uploadUntilDone` calls `start()` in a loop. Only `Disconnected` means "try again". Any other error ends the loop:

<!-- docs-check: skip -->

```typescript [client/upload-until-done.ts]
for (;;) {
  try {
    const { info } = await upload.start()

    return info
  } catch (error) {
    if (!Disconnected.matches(error)) throw error

    await whenReconnected()
  }
}
```

### Wait until the socket is open again

`whenReconnected()` resolves when the socket is `'open'`, and rejects with `Disconnected` when it is `'closed'`. While it is `'connecting'` or `'reconnecting'`, it waits:

<!-- docs-check: skip -->

```typescript [client/upload-until-done.ts]
function settled(state: ConnectionState): boolean {
  if (state === 'open') resolve()
  else if (state === 'closed') reject(Disconnected())
  else return false

  return true
}

if (settled(socket.state.get())) return

const stop = socket.state.subscribe((state) => {
  if (settled(state)) stop()
})
```

::

::code-collapse

```typescript [client/upload-until-done.ts]
import { Disconnected } from '@livething/client/errors'
import type { ConnectionState, Upload } from '@livething/client'
import { socket } from './socket'

/** Resolves when the socket is open again, and rejects when nothing reconnects it. */
export function whenReconnected(): Promise<void> {
  return new Promise((resolve, reject) => {
    function settled(state: ConnectionState): boolean {
      if (state === 'open') resolve()
      else if (state === 'closed') reject(Disconnected())
      else return false

      return true
    }

    if (settled(socket.state.get())) return

    const stop = socket.state.subscribe((state) => {
      if (settled(state)) stop()
    })
  })
}

/** Starts the upload, and starts it again after each drop, until the server replies. */
export async function uploadUntilDone<TInfo>(
  upload: Upload<TInfo>,
): Promise<TInfo> {
  for (;;) {
    try {
      const { info } = await upload.start()

      return info
    } catch (error) {
      if (!Disconnected.matches(error)) throw error

      await whenReconnected()
    }
  }
}
```

::

The loop waits while [`reconnection()`](/client/primitives/reconnection) reconnects the socket, then starts the upload again. When the socket is `'closed'` and nothing reconnects it, for example when `reconnection()` stopped trying, or on a [lazy](/client/connecting/connect-options#lazy) socket with no `reconnection()`, `whenReconnected()` rejects with `Disconnected`, so the loop never waits forever. Call `uploadUntilDone` again later: `start()` opens a lazy socket by itself, and the upload resumes from the bytes the server stored.

Huddle uploads an attachment with it. The reply's info is the ID of the stored attachment:

```typescript [client/attachments.ts]
import { socket } from './socket'
import { uploadUntilDone } from './upload-until-done'

export async function uploadAttachment(file: File): Promise<string> {
  const upload = socket.binary.upload('upload-attachment', file, {
    input: { fileName: file.name, fileType: file.type },
  })
  const { attachmentId } = await uploadUntilDone(upload)
  return attachmentId
}
```

What `start()` does:

- **It waits for the socket to be open**, then sends the upload. On a [lazy](/client/connecting/connect-options#lazy) socket, it opens the socket, and the socket stays open while the upload runs. When the socket is closed and no reconnect is in progress, it rejects with `Disconnected` at once.
- **It has no timeout once the upload runs.** A large file can take many minutes, so the `timeout` of `clientRequests()` does not apply. Only the first answer has a limit: when the server does not answer the start within 30 seconds, for example because an intercept dropped it with `Block`, `start()` rejects with `Timeout`, and the client tells the server to stop the upload.
- **While it runs**, a second call returns the same promise.
- **After it resolves**, a call returns the same result, and sends nothing.
- **It rejects** with `Disconnected` when the socket closes, with [`UploadAborted`](#errors), or with the error that the server's `run` threw, such as Huddle's `Forbidden`. Only `Disconnected` means "try again".
- **The pieces go straight to the socket.** They never wait in the [`buffering()`](/client/primitives/buffering) queue, so `buffering({ maxBytes })` does not limit an upload. Each piece must follow the server's answer to the start, so a piece that waited in the queue could arrive too late.

When the server lost the reply in a drop, `start()` again gets the stored reply, and the server's `run` does not run a second time.

The server can also lose a running upload while the socket stays open, for example when Cloudflare restarted or moved the Durable Object. It then answers the next piece with `UploadAborted` and the reason `'interrupted'`. For a `Blob` or bytes, the running `start()` starts the upload again by itself, and continues from the bytes the server stored. It gives up after 3 tries in a row that store no new bytes. A try that moves the saved offset starts the count again. You see `'interrupted'` only when that keeps failing. An `'interrupted'` that comes before the server's first answer to this start is ignored: it is about pieces of an earlier start. An [`AsyncIterable`](#asynciterable-sources) cannot be read again, so its `start()` rejects with `'not-resumable'` instead.

## Progress

`upload.onProgress(listener)` listens for progress. The listener gets the number of bytes that the server's `run` has read, each time the server says so. It returns a function that stops listening:

```typescript [client/attachments.ts]
import { showUploadProgress } from './huddle-ui'
import { socket } from './socket'
import { uploadUntilDone } from './upload-until-done'

export async function uploadWithProgress(
  file: File,
): Promise<string> {
  const upload = socket.binary.upload('upload-attachment', file, {
    input: { fileName: file.name, fileType: file.type },
  })
  const stop = upload.onProgress((receivedBytes) => {
    showUploadProgress(file.name, receivedBytes, file.size)
  })
  try {
    return (await uploadUntilDone(upload)).attachmentId
  } finally {
    stop()
  }
}
```

The number counts the bytes the server **read**, not the bytes the client sent, so the bar never runs ahead of the server. After a resume, it can go **back**: the server continues from the last bytes it stored, which can be a little before the bytes it had read.

## Cancelling

`upload.cancel()` stops the upload, and tells the server. The server stops its `run`, runs `onDiscard` to delete what was stored, and forgets the upload. A running `start()` rejects with `UploadAborted` and the reason `'cancelled'`, and so does every later `start()`:

```typescript [client/attachments.ts]
import type { Upload } from '@livething/client'

export function cancelOnClick(
  button: HTMLButtonElement,
  upload: Upload<unknown>,
) {
  button.addEventListener('click', () => upload.cancel())
}
```

`cancel()` after the upload is done does nothing. A `cancel()` while the socket is not open is sent when the socket opens again, and a `start()` that waits for the socket rejects at once.

## Resuming after a reload

A page reload ends the upload on the client, but the server keeps its record. To resume it, make the upload again with the same `uploadId`, the same input and the same file. Huddle keeps the ID in `localStorage`, under a key made from the file, so the user can pick the same file again after a reload:

```typescript [client/attachments.ts]
import { socket } from './socket'
import { uploadUntilDone } from './upload-until-done'

export async function uploadPickedFile(file: File): Promise<string> {
  // The same file, picked again after a reload, gets the same key.
  const key = `upload:${file.name}:${file.size}:${file.lastModified}`
  const upload = socket.binary.upload('upload-attachment', file, {
    input: { fileName: file.name, fileType: file.type },
    uploadId: localStorage.getItem(key) ?? undefined,
  })
  localStorage.setItem(key, upload.id)
  const { attachmentId } = await uploadUntilDone(upload)
  localStorage.removeItem(key)

  return attachmentId
}
```

- The first progress after the resume is the number of bytes the server already stored. The client sends only the rest.
- The input and the size must be the same as at the first start. Otherwise `start()` rejects with `UploadAborted` and the reason `'input-mismatch'`.
- An upload ID that the server no longer knows, because the upload expired, starts a new upload with that ID, from the first byte.
- When `start()` rejects with the reason `'gone'`, the old upload is being discarded. Remove the key, and start a new upload.
- The same ID in a second tab **takes over** the upload: the first tab's `start()` rejects with the reason `'taken-over'`, and the second tab continues from the stored bytes.

## AsyncIterable sources

An `AsyncIterable<Uint8Array>` is a file that the client makes while it sends it. Here Huddle compresses a log file before it sends it:

```typescript [client/attachments.ts]
import { socket } from './socket'

async function* readAll(
  stream: ReadableStream<Uint8Array>,
): AsyncIterable<Uint8Array> {
  const reader = stream.getReader()
  for (;;) {
    const { done, value } = await reader.read()
    if (done) return

    yield value
  }
}

export function uploadCompressed(file: File) {
  const gzip = file
    .stream()
    .pipeThrough(new CompressionStream('gzip'))
  return socket.binary.upload('upload-attachment', readAll(gzip), {
    input: {
      fileName: `${file.name}.gz`,
      fileType: 'application/gzip',
    },
  })
}
```

An `AsyncIterable` works differently from a `Blob` in four ways:

- **The client does not know its size**, so the server can refuse a file over `maxBytes` only when the bytes over the limit come.
- **It can be read only once.** On its first `start()`, the client skips the bytes the server already stored, for example for an `uploadId` from before a reload. The client starts reading it after the server's first answer. If the connection drops before that, nothing was read, so a second `start()` works. After that point, a second `start()` after a drop, or after the server lost the upload (`'interrupted'`), cannot read the bytes again, so it rejects with `UploadAborted` and the reason `'not-resumable'`. The client then tells the server to discard the upload, so the server's `onDiscard` runs at once, not after the expiry. Make a new upload to send the file again.
- The chunks can have any size. The client joins and cuts them into pieces of the server's piece size.
- When the iterable throws after the upload started, `start()` rejects with that error, and the client tells the server to stop the upload, so the server's `onDiscard` runs.

Use a `Blob` when you have the whole file, so the upload can resume.

## Several files with one caption

To send several photos as one upload, join them into one `Blob`. `new Blob(files)` copies no bytes, and the upload can still resume. List each photo's name, type and size in the input, in the same order, so the server can cut the bytes apart. Huddle's [`post-photos`](/server/binary/several-files) posts them to a room with one caption:

```typescript [client/photos.ts]
import { socket } from './socket'
import { uploadUntilDone } from './upload-until-done'

export async function postPhotos(
  roomId: string,
  caption: string,
  photos: File[],
): Promise<string[]> {
  const upload = socket.binary.upload(
    'post-photos',
    new Blob(photos),
    {
      input: {
        roomId,
        caption,
        photos: photos.map((photo) => ({
          fileName: photo.name,
          fileType: photo.type,
          size: photo.size,
        })),
      },
    },
  )
  const { attachmentIds } = await uploadUntilDone(upload)
  return attachmentIds
}
```

The photos succeed or fail together: the room gets one message with all of them, or none.

## Upload first, then post

Huddle's `upload-attachment` stores a file that no room uses yet. To post it, send its ID to a room with `post-files`, a normal JSON event. The `rooms` channel checks that the user is a member when the message comes:

```typescript [client/attachments.ts]
import { socket } from './socket'
import { uploadUntilDone } from './upload-until-done'

export async function postFile(
  file: File,
  text: string,
): Promise<void> {
  const upload = socket.binary.upload('upload-attachment', file, {
    input: { fileName: file.name, fileType: file.type },
  })
  const { attachmentId } = await uploadUntilDone(upload)
  const general = socket.channel('rooms', 'room:general')
  await general.subscribe()
  general.send('post-files', { text, attachmentIds: [attachmentId] })
}
```

Every member of the room gets a `files-posted` event. In which order the app does things is its own choice: it can show the text at once with a spinner on the file, or show nothing until the file is posted. `post-attachment` does both steps in one upload instead. The server docs call this [upload, then post](/server/binary/upload-then-post).

## Errors

`start()` rejects with `UploadAborted` when the upload cannot continue. Import it from `@livething/client/errors`, and read `detail.reason`:

| Reason             | Where                    | Meaning                                                                                                                                                                                   |
| ------------------ | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `'cancelled'`      | the client or the server | You called `upload.cancel()`. The server also sends it to a start it was still handling when your cancel came.                                                                            |
| `'not-resumable'`  | the client               | The source is an `AsyncIterable` that the client already started to read, so the upload cannot start again.                                                                               |
| `'too-large'`      | the server               | The file is over the handler's `maxBytes`.                                                                                                                                                |
| `'input-mismatch'` | the server               | A resume sent another input or size than the first start.                                                                                                                                 |
| `'bad-state'`      | the server               | On a resume, the server could not read back the state it saved for the upload, for example after a deploy changed it. The upload is discarded. Start the file again with a new upload ID. |
| `'taken-over'`     | the server               | Another tab or device of the same user started the same upload. The upload continues there.                                                                                               |
| `'gone'`           | the server               | The upload is being discarded: it was cancelled, it failed, its stored state was bad (`'bad-state'`), or its user was purged.                                                             |
| `'interrupted'`    | the server               | The server lost the running upload, for example when its Durable Object restarted, and 3 tries in a row stored no new bytes.                                                              |
| `'bad-piece'`      | the server               | A piece broke the protocol. The LiveThing client never does this.                                                                                                                         |
| `'window'`         | the server               | The client sent too many bytes before the server read them. The LiveThing client never does this.                                                                                         |

```typescript [client/attachments.ts]
import { UploadAborted } from '@livething/client/errors'
import { showToast } from './huddle-ui'
import { socket } from './socket'
import { uploadUntilDone } from './upload-until-done'

export async function attachFile(file: File): Promise<string | null> {
  const upload = socket.binary.upload('upload-attachment', file, {
    input: { fileName: file.name, fileType: file.type },
  })
  try {
    return (await uploadUntilDone(upload)).attachmentId
  } catch (error) {
    if (UploadAborted.matches(error)) {
      if (error.detail.reason === 'too-large') {
        showToast('This file is too big.')
      }

      return null
    }

    throw error
  }
}
```

An upload also needs a signed-in user. On a connection with no `userId`, `start()` rejects with `durable-stream-requires-user`. The start can also get the errors of any message: `validation-failed` for input that fails the server's schema, and `rate-limited` with [`rateLimit()`](/server/capabilities/rate-limit).

The [upload messages on the wire](/learn/wire-protocol#uploads) are part of the wire protocol.
