`inbox()` is the client half of guaranteed per-member delivery. On the server an [inbox channel](/server/capabilities/inbox) writes a durable copy of every broadcast for each member and holds it until that member confirms it arrived. `inbox()` is what sends that confirmation: as inbox messages arrive it tracks the highest sequence per channel, sends a `__received__` acknowledgement, and re-acks on reconnect — so the server can drop your held copy and never re-deliver it. Without it, guaranteed delivery never settles.

```typescript [app.ts]
import {
  channels,
  client,
  connect,
  dedup,
  inbox,
  reconnection,
} from '@livething/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(
  connect('wss://example.com/ws'),
  channels(),
  inbox(),
  dedup(),
  reconnection(),
)
```

## It needs `dedup()`, and runs after `channels()`

`inbox()` depends on [`dedup()`](/client/primitives/dedup); building the socket without it throws when you call `client()(...)`. The reason: on reconnect the server drains your held rows and re-delivers any it hadn't seen an ack for, and some of those also arrived live before the drop. `dedup()` throws the repeats away so your `on()` handlers run once per message.

Registration order does not matter: LiveThing sorts the primitives before they run. `inbox()` runs after [`channels()`](/client/primitives/channels), and when [`replay()`](/client/primitives/replay) is present, replay runs after inbox so both can process the same gap before replay consumes the reserved frame. Pairing with [`reconnection()`](/client/primitives/reconnection) makes sense too, since the re-ack runs on reconnect.

An inbox channel's scope is identified by the pair **(`channelFamily`, concrete channel name)**. For a dynamic family, the concrete name alone is not enough: `rooms` at `room-42` and `rooms` at `room-43` are separate scopes, and `rooms` at `room-42` stays separate from `projects` at `room-42`. The client keeps these pieces together for delivery acknowledgements. [`gaps()`](/client/primitives/gaps) uses the same composite identity when it routes channel gaps.

## It learns which channels are inbox-backed

You don't tell the client which channels have an inbox. When you subscribe, the server's `__subscribeOk__` carries an `inbox` flag, and `inbox()` reads it — from then on it acks that channel and only that channel. A plain channel with no inbox is never acked.

So the auto-acknowledgement is invisible in your code. You subscribe and read messages the normal way:

```typescript [app.ts]
const chat = socket.channel('chat')

await chat.subscribe()
chat.on('room-msg', (msg) => appendMessage(msg.text))
```

Every `room-msg` that arrives advances the acked cursor for `chat`; the `__received__` frame goes out on its own. If you drop and reconnect, the client re-sends the high-water mark so the server can settle anything that was still held.

## The received surface

On a channel whose contract sets `inbox: true`, the handle gains three received-receipt members. They read the `__received__` frames the server fans out — the double-grey check — into a local view of who has received what. Those frames only arrive when the **server** channel enables `broadcastReceipts`; without it, `receivers` and `onReceived` stay quiet, though `receiversOf` still answers from the stored cursor. (Who has _read_ a message is the separate [`readReceipts()`](/client/primitives/read-receipts) surface.)

### `receivers` — the reactive store

`channel.receivers` is a [reactive store](/client/overview#reactive-stores) of every member's received cursor, keyed by user id. Its snapshot is a `CursorList` (`ReadonlyMap<userId, number>`) mapping each member to its `receivedThrough` — the highest sequence that member has confirmed receiving — dropping any member still at `0`, so every entry is a member to show the grey double-check for.

```typescript [app.ts]
chat.receivers.subscribe(() => {
  for (const [userId, receivedThrough] of chat.receivers.get()) {
    markReceived(userId, receivedThrough)
  }
})
```

The store is **cleared when you really leave the channel** — a matching `__unsubscribeOk__` (when no rejoin is already underway) or any `__kicked__` empties it. A confirmation from an earlier leave — whether it arrives after a rejoin or while another leave is pending — is ignored and cannot wipe the new subscription's state.

### `onReceived(cb)` — one member's cursor advanced

`channel.onReceived(cb)` fires each time a member's received cursor moves forward, with that member's user id and new cursor. It returns an unsubscribe.

```typescript [app.ts]
const stop = chat.onReceived((userId, receivedThrough) => {
  markReceived(userId, receivedThrough)
})
```

### `receiversOf(seq)` — ask the server who got it

`receivers` and `onReceived` reflect the live fan-out, which the server caps by member count. For the authoritative answer, `channel.receiversOf(seq)` asks the server directly and resolves to the user ids that have received up to at least `seq`:

```typescript [app.ts]
const userIds = await chat.receiversOf(1)
renderReceivedBy(userIds.slice().sort().join('|'))
```

Only a member of the channel may query; a non-member's request is dropped silently on the server. Because inbox owns this query, `receiversOf` works with `inbox()` alone — you do not need `readReceipts()` for it.

## Options

`inbox({ timeout })` sets how long a `receiversOf` query waits for the server's answer before rejecting, in milliseconds. The default is `10_000` (10s). Override a single call with `receiversOf(seq, { timeout })`.

```typescript [app.ts]
inbox({ timeout: 5_000 })
```

## A realistic construction

Here is the full stack from the receipts fixture — `channels()`, `inbox()`, and `dedup()`, with read receipts added on top (see [Read receipts](/client/primitives/read-receipts)):

```typescript [app.ts]
import {
  channels,
  client,
  connect,
  dedup,
  inbox,
  readReceipts,
  reconnection,
} from '@livething/client'
import type { ReceiptsClient } from '../server/receipts'

const socket = client<ReceiptsClient>()(
  connect('wss://example.com/ws'),
  channels(),
  inbox(),
  readReceipts(),
  dedup(),
  reconnection({ maxDelay: 400 }),
)
```

::note
The received surface needs **both** things: the server channel's contract must set `inbox: true` and reach `base.assemble(...)` (pass the channel object for config-only assembly, or any routed handler value from that channel), **and** `inbox()` itself must be registered in `client()`. A routed handler value also activates that route; the channel object alone does not. Miss either one and `receivers` / `onReceived` / `receiversOf` are not on the channel handle's type at all — calling them is a compile error, the same "property does not exist" TypeScript gives for any missing member. A plain channel handle, or one built without `inbox()`, has none of these members.
::

## When the server has inbox but the client doesn't register it

If a channel's contract sets `inbox: true` but `inbox()` isn't in your `client()` stack, you don't get a compile error at the call site — there's simply nothing to call, since the surface doesn't exist. What you do get is a runtime signal: the first time that channel's `__subscribeOk__` arrives, `channels()` logs a warning through the client's [debug logger](/client/primitives/debug):

```text
[livething] channel 'chat' is inbox-backed but inbox() is not registered — received receipts will not be tracked. Add inbox() to client().
```

This only prints when [`debug()`](/client/primitives/debug) is on (debug logs are always gated that way), and at most once per channel — resubscribing doesn't repeat it. Without `inbox()` registered, nothing on the client ever sends `__received__` for that channel, so the server's held rows for this member never settle — the message still arrives live, but the guaranteed-delivery half of the contract silently goes unfulfilled. The warning is the only signal you get; a channel with no `inbox` flag never warns.

::tip
The double-grey check only tells you a message was **received**. For the blue check — who has **read** it — add [`readReceipts()`](/client/primitives/read-receipts). If the channel bounds its held rows and a member falls behind, the server signals a hole with `__gap__` on reconnect. `inbox()` acknowledges that missing range through `missedThrough`; add [`gaps()`](/client/primitives/gaps) when the app also needs the `onGap` callback. Without `gaps()`, the reserved frame still does not reach ordinary message handlers.
::

For the server half — held rows, the `__received__` fan-out and its member cap, and `receiversOf` — see [Receipts](/server/inbox/receipts) in the Server section.
