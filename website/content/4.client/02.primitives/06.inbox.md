`inbox()` is the client half of guaranteed per-member delivery. On the server, an [inbox channel](/server/capabilities/inbox) writes a stored copy of every broadcast for each member. It keeps that copy until the member confirms that the message arrived. This confirmation is called an **acknowledgement** (ack for short).

`inbox()` sends that acknowledgement for you. Every channel message has a **sequence number** (a number that grows with each new message). As inbox messages arrive, `inbox()` remembers the highest sequence number per channel and sends it to the server in a `__received__` frame. It sends the same number again after a reconnect. The server then marks the stored copies up to that number as delivered and does not deliver them again. Without `inbox()`, the server never gets an acknowledgement, so the stored copies are never settled.

```typescript [app.ts]
import {
  channels,
  client,
  connect,
  dedup,
  inbox,
  reconnection,
} from '@livething/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(
  connect('wss://example.com/ws'),
  channels(),
  inbox(),
  dedup(),
  reconnection(),
)
```

## It needs `dedup()`, and runs after `channels()`

`inbox()` depends on [`dedup()`](/client/primitives/dedup). If `dedup()` is missing, `client()(...)` throws a `LiveThingConfigError` when you build the socket. The reason: on reconnect, the server sends again every stored copy that it has no acknowledgement for. Some of those copies also arrived live before the connection dropped. `dedup()` removes the repeated messages, so your `on()` handlers run once per message.

The order in which you list primitives does not matter. LiveThing sorts the primitives before they run. `inbox()` runs after [`channels()`](/client/primitives/channels), so a channel rejoin reaches the server before the acknowledgement for that channel. When [`replay()`](/client/primitives/replay) is present, it runs after `inbox()`. Both of them read the same `__gap__` frame (see the tip at the end of this page). It also makes sense to add [`reconnection()`](/client/primitives/reconnection), because `inbox()` sends its acknowledgements again after each reconnect.

The client tracks each inbox channel by two values together: the channel family and the concrete channel name. (A **channel family** is a group of dynamic channels that share one definition, such as `rooms`.) For a dynamic family, the name alone is not enough. `rooms` at `room-42` and `rooms` at `room-43` are separate channels. `rooms` at `room-42` is also separate from `projects` at `room-42`. The client keeps family and name together in every acknowledgement it sends. [`gaps()`](/client/primitives/gaps) uses the same pair when it routes channel gaps.

## It learns which channels have an inbox

You don't tell the client which channels have an inbox. When you subscribe, the server's `__subscribeOk__` frame carries an `inbox` flag, and `inbox()` reads it. From then on, it acknowledges that channel. It never acknowledges a plain channel with no inbox.

So you never write acknowledgement code yourself. You subscribe and read messages in the normal way:

```typescript [app.ts]
const chat = socket.channel('chat')

await chat.subscribe()
chat.on('room-msg', (msg) => appendMessage(msg.text))
```

Every `room-msg` that arrives moves the acknowledged position for `chat` forward, and `inbox()` sends the `__received__` frame automatically. If the connection drops and comes back, the client sends its **high-water mark** again (the highest sequence number it has seen on that channel). The server then settles any copies it still holds up to that number.

## The received surface

On a channel whose contract sets `inbox: true`, the channel handle gets three extra members. They show which members have received which messages. In chat apps this is often drawn as a double grey check mark, so this page calls it the "double-grey check".

The server tells every member when another member's position moves forward. It does this by sending a `__received__` frame to each member of the channel (a **fan-out**). These frames only arrive when the **server** channel enables `broadcastReceipts`. Without it, `receivers` and `onReceived` never change, but `receiversOf` still works, because it reads the position that the server stores. (Who has _read_ a message is a separate feature: see [`readReceipts()`](/client/primitives/read-receipts).)

Each member's position is a **cursor**: `receivedThrough`, the highest sequence number that member has confirmed receiving.

### `receivers`: the reactive store

`channel.receivers` is a [reactive store](/client/overview#reactive-stores) with every member's received cursor, keyed by user ID. The user ID is the stable `userId` the server gives the connection when it accepts it. The store's value is a `CursorList`, which is a `ReadonlyMap<string, number>` from user ID to `receivedThrough`. Members whose cursor is still `0` are left out, so every entry is a member you can show the double-grey check for.

```typescript [app.ts]
chat.receivers.subscribe(() => {
  for (const [userId, receivedThrough] of chat.receivers.get()) {
    markReceived(userId, receivedThrough)
  }
})
```

The store is **cleared when you really leave the channel**. This happens when a matching `__unsubscribeOk__` arrives and no rejoin is already in progress, or when any `__kicked__` arrives. It is also cleared if a rejoin fails. A leave confirmation from an earlier leave is ignored. This is true whether it arrives after a rejoin or while another leave is still waiting. It cannot clear the state of the new subscription.

### `onReceived(cb)`: one member's cursor moved forward

`channel.onReceived(cb)` calls `cb` each time a member's received cursor moves forward. It passes that member's user ID and the new cursor. A repeated or out-of-order frame that does not raise the cursor does not call `cb`. `onReceived` returns a function that stops the listener.

```typescript [app.ts]
const stop = chat.onReceived((userId, receivedThrough) => {
  markReceived(userId, receivedThrough)
})
```

### `receiversOf(seq)`: ask the server who got it

`receivers` and `onReceived` show only the live fan-out. The server skips that fan-out when the channel has more members than a set limit (`maxReceiptAudience` on the server, 256 by default). To get the full answer, `channel.receiversOf(seq)` asks the server directly. It resolves to the user IDs whose received cursor is at least `seq`:

```typescript [app.ts]
const userIds = await chat.receiversOf(1)
renderReceivedBy(userIds)
```

Only a member of the channel may ask. The server ignores the request from a non-member and sends no answer, so the call rejects with `Timeout` when its wait ends. The promise rejects in these cases:

- `ChannelNotSubscribed`: the channel is not active.
- `Timeout`: no answer came before the timeout.
- `Disconnected`: the query could not be sent, or the socket closed before the answer came.

`Timeout` and `Disconnected` are described in [Client-side errors](/client/errors/client-side-errors). `receiversOf` belongs to `inbox()`, so it works with `inbox()` alone. You do not need `readReceipts()` for it.

## Options

`inbox({ timeout })` sets how long a `receiversOf` call waits for the server's answer before it rejects, in milliseconds. The default is `10_000` (10 seconds). To change the wait for a single call, use `receiversOf(seq, { timeout })`.

```typescript [app.ts]
inbox({ timeout: 5_000 })
```

## A full setup

This socket uses `channels()`, `inbox()`, and `dedup()`, and adds read receipts as well (see [Read receipts](/client/primitives/read-receipts)):

```typescript [app.ts]
import {
  channels,
  client,
  connect,
  dedup,
  inbox,
  readReceipts,
  reconnection,
} from '@livething/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(
  connect('wss://example.com/ws'),
  channels(),
  inbox(),
  readReceipts(),
  dedup(),
  reconnection(),
)
```

::note
The received surface needs **two** things. First, on the server, the channel must list `inbox()` in its `capabilities`, and the channel must be part of the assembled definition (through its handlers or the channel object itself). This is what puts `inbox: true` into the contract that `InferClient` reads. Second, on the client, `inbox()` must be registered in `client()`. If either one is missing, `receivers`, `onReceived`, and `receiversOf` are not on the channel handle's type at all. Calling them is a compile error, the same "property does not exist" error TypeScript gives for any missing member. A plain channel handle, or one built without `inbox()`, has none of these members.
::

## When the server has an inbox but the client doesn't register `inbox()`

If a channel's contract sets `inbox: true` but `inbox()` isn't in your `client()` call, you get no compile error where you use the channel. The received members simply don't exist on the handle, so there is nothing to call. Instead, you get a runtime warning. The first time that channel's `__subscribeOk__` arrives, `channels()` logs a warning through the client's [debug logger](/client/primitives/debug):

```text
[livething] channel 'chat' is inbox-backed but inbox() is not registered — received receipts will not be tracked. Add inbox() to client().
```

This warning only prints when [`debug()`](/client/primitives/debug) is on, because all debug logs depend on it. It prints at most once per channel. Subscribing again doesn't repeat it. Without `inbox()`, the client never sends `__received__` for that channel. The message still arrives live, but the server keeps this member's stored copies and never settles them, so guaranteed delivery never completes. The warning is the only sign of this. A channel with no `inbox` flag never warns.

::tip
The double-grey check only tells you that a message was **received**. For the blue check (who has **read** it), add [`readReceipts()`](/client/primitives/read-receipts). A channel can limit how many copies it stores. If a member falls too far behind, the server sends a `__gap__` frame on reconnect to report the missing range. `inbox()` acknowledges that missing range up to its `missedThrough` value. Add [`gaps()`](/client/primitives/gaps) when your app also needs the `onGap` callback. Without `gaps()`, the `__gap__` frame still never reaches your normal message handlers.
::

For the server half (stored copies, the `__received__` fan-out and its member limit, and `receiversOf`), see [Receipts](/server/inbox/receipts) in the Server section.
