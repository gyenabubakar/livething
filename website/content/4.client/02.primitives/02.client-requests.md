`clientRequests()` adds `socket.request(...)`. It sends a message and returns a promise. The promise resolves with the server's reply to that exact message. Use it when you need an answer. Use `send()` when you only need to send the message and do not wait for any answer. For the server half, see [clientRequests](/server/capabilities/client-requests).

```typescript [client/socket.ts]
import {
  binary,
  client,
  clientRequests,
  connect,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  clientRequests(),
)
socket.connect()

const profile = await socket.request('get-profile', {
  userId: 'u_123',
})
// profile: { id: string; name: string; status: Status }, typed from the contract
console.log(`${profile.name} is ${profile.status}`)
```

Internally, each request carries a unique ID in `metadata.exchange.id`. This ID is called the **correlation ID**. The server copies it onto its reply, and the primitive uses it to find the promise that the reply belongs to. The payload you send and the response you get are both typed from the `clientRequests` map in your contract.

## The contract side

`request()` is typed from the `clientRequests` map in your socket contract. Each entry pairs the `payload` you send with the `response` you get back:

```typescript [shape]
import type { Status } from '../server/base'

interface HuddleSocket {
  clientRequests: {
    'get-profile': {
      payload: { userId: string }
      response: { id: string; name: string; status: Status }
    }
    'delete-message': {
      payload: { messageId: string }
      response: { deleted: boolean }
    }
  }
}
```

With `@livething/server`, `InferClient` builds this map from your server code, so you don't write it yourself. Then `socket.request('get-profile', …)` suggests the event name in your editor, checks the payload, and gives the resolved value its type.

## How the promise settles

`Forbidden` and `NotFound` come from `../shared/errors`, a file that both the server and the client import. Huddle's definition declares them with `errors([NotFound, Forbidden, RoomFull])`.

```typescript [client/room.ts]
import { Timeout } from '@livething/client/errors'
import { Forbidden, NotFound } from '../shared/errors'
import { removeFromView, showToast } from './huddle-ui'
import { socket } from './socket'

try {
  const result = await socket.request('delete-message', {
    messageId: 'm-42',
  })
  if (result.deleted) removeFromView('m-42')
} catch (err) {
  if (Forbidden.matches(err))
    showToast(err.detail.reason) // typed server error
  else if (NotFound.matches(err))
    showToast('That message is already gone') // another typed error
  else if (Timeout.matches(err)) showToast('Server took too long')
  else throw err
}
```

The promise settles in one of these ways:

- **Resolves** with the typed response when the server replies. If the server handler returns nothing, it resolves with no value (a [void acknowledgement](#acknowledgement-requests)).
- **Rejects with a typed `LiveThingError`** if the server answers with one of your declared errors. Use `.matches()` to check which error it is, then read `err.detail`.
- **Rejects with `Timeout`** if no reply arrives before the timeout ends.
- **Rejects with `Disconnected`** if the connection closes while the request waits for its reply. This happens when you call `disconnect()`, and also when the connection drops.
- **Rejects with `Dropped`** if the request was buffered (see [below](#when-the-socket-isnt-open)) and then removed before it could be sent. This happens when the buffer is full, or when the request's TTL (time to live) ends. A request bigger than the buffer's `maxBytes` is never buffered, and rejects with `Dropped` at once. `Dropped`, `Timeout` and `Disconnected` are all imported from `@livething/client/errors`.
- **Rejects with `internal-error`** if the server handler throws something that is not one of your declared errors.
- **Rejects at once with `ValidationFailed`** if the event name is empty, reserved, or longer than 128 characters. A reserved name is any name that starts or ends with `__`. This check runs on the client, so no frame is sent.

## Acknowledgement requests

Sometimes you don't need a value back. You only want to know that the server **received and handled** your message. This is an _acknowledgement_ request. On the server, the handler returns nothing. On the client, `request()` resolves with `undefined`. You `await` it only to know that the server finished.

```typescript [shape]
interface HuddleSocket {
  clientRequests: {
    // `response: void` means an acknowledgement. There is no value to read.
    'report-message': {
      payload: { messageId: string; reason: string }
      response: void
    }
  }
}
```

```typescript [client/room.ts]
// Resolves after the server has logged the report for a moderator to review.
await socket.request('report-message', {
  messageId: 'm-42',
  reason: 'spam',
})
console.log('the server recorded the report')
```

This is how it differs from `send()`. `send()` returns `true` when the message is accepted, which means it was passed to the socket or buffered. It never tells you that the server got the message. An acknowledgement request resolves only **after** the server handler ran. So awaiting it confirms that the message arrived and was processed, even when you need no data back.

```typescript [client/room.ts]
// `start-typing` is a message handler on the server, so the client uses send()
room.send('start-typing', {}) // true = accepted, not delivered

// `report-message` is a request handler on the server, so the client uses request()
await socket.request('report-message', {
  messageId: 'm-42',
  reason: 'spam',
}) // resolves = the server handled it
```

## Concurrent requests

Each request has its own correlation ID. So you can have many requests waiting at the same time, and each one resolves on its own:

```typescript [client/room.ts]
const [author, mentioned] = await Promise.all([
  socket.request('get-profile', { userId: 'u_100' }),
  socket.request('get-profile', { userId: 'u_200' }),
])
```

## Timeout

By default, a request waits 10 seconds for a reply. Set a different default for all requests with the primitive option. Set it for one call with the third argument:

```typescript [client/socket.ts]
import {
  binary,
  client,
  clientRequests,
  connect,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  clientRequests({ timeout: 5_000 }), // default for every request
)

// a longer wait for a lookup that may hit a cold cache
const profile = await socket.request(
  'get-profile',
  { userId: 'u_999' },
  { timeout: 30_000 },
)
```

A `timeout` must be a number from `1` to `2147483647` (`2 ** 31 - 1`, the longest a timer can hold). Any other value is a `LiveThingConfigError`: `clientRequests()` throws it, and a `request()` rejects with it.

## When the socket isn't open

`request()` needs a socket that is open or connecting:

- On a **lazy** socket (one created with `connect(url, { lazy: true })`), calling `request()` opens the connection. The request is sent when the connection is open.
- While the socket is **connecting** or **reconnecting**, the client holds the frame and sends it, in order, when the connection opens. If that connection attempt fails, the request rejects with `Disconnected`. With [`buffering()`](/client/primitives/buffering) installed, the request goes into the buffer like any other send.
- On a socket that is **not lazy** and that you haven't opened with `connect()` yet (state `closed`), `request()` rejects at once with `Disconnected`. It does not wait until the timeout. Call `connect()` first, or use a lazy socket.

## Requests that carry bytes

With [`binary()`](/client/primitives/binary) installed, `clientRequests()` also adds `socket.binary.request(event, info, bytes?, options?)`, and the same on channel handles. It sends one binary message, and resolves with the info and the bytes of the binary reply, such as the picture that Huddle's `get-thumbnail` sends back. It rejects in the same ways as `request()`. A text reply to it rejects with `request-invalid-response`, and a binary reply never settles `request()`. See [binary · Requests](/client/primitives/binary#requests).

## On a channel

With [`channels()`](/client/primitives/channels) installed, channel handles also get a `request()` method. It is typed from that channel's contract, and the request is sent to that channel:

```typescript [client/room.ts]
const room = socket.channel('rooms', 'room:general')
await room.subscribe({})
const older = await room.request('load-history', {
  before: Date.now(),
})
```

Call `await room.subscribe({})` first. If you call `room.request()`, `room.send()` or `room.stream()` before the channel is active, it **throws `ChannelNotSubscribed` right away**. This is a thrown error, not a rejected promise. So a `.catch()` on the request does not catch it. Use `try`/`catch` around the call, or subscribe first.

For the other direction, where the server asks _you_ a question and waits for your answer, see [`serverRequests()`](/client/primitives/server-requests).
