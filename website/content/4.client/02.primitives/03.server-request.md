`serverRequest()` is the mirror of [`requestResponse()`](/client/primitives/request-response): it lets the **server** ask this client a question and wait for the answer. From your side the request arrives _inbound_ — you register a handler, and whatever it returns is sent back as the reply. For the server half — issuing the request — see [requests](/server/capabilities/requests) in the Server section.

```typescript [app.ts]
import { client, connect, serverRequest } from '@wskit/client'
import type { ApiSocket } from '../server/api'

const socket = client<ApiSocket>()(
  connect('wss://example.com/ws'),
  serverRequest(),
)
socket.connect()

const unsubscribe = socket.onRequest('get-device-info', (payload) => {
  // payload is typed from the contract's `serverRequests`
  return { platform: 'web', version: navigator.userAgent }
})
```

## The contract side

`onRequest()` is typed from the `serverRequests` map in your contract. Each entry pairs the `payload` the server sends with the `response` your handler must return:

```typescript [socket-types.ts]
interface ApiSocket {
  serverRequests: {
    'get-device-info': {
      payload: {}
      response: { platform: string; version: string }
    }
    'confirm-action': {
      payload: { action: string }
      response: { allowed: boolean }
    }
  }
}
```

With `@wskit/server`, `InferClient` produces this map from the server's request declarations. Both the `payload` your handler receives and the value it must return are checked against it.

## Answering a request

The handler's return value, awaited, becomes the reply. It can be sync or async — so you can `await` a dialog, a permission prompt, or a `fetch` before answering:

```typescript [app.ts]
// Sync answer
socket.onRequest('get-device-info', () => ({
  platform: 'web',
  version: navigator.userAgent,
}))

// Async answer — ask the user, then reply
socket.onRequest('confirm-action', async (payload) => {
  const allowed = await showConfirmDialog(`Allow ${payload.action}?`)
  return { allowed }
})
```

`onRequest()` returns an unsubscribe function; call it to stop answering that event.

## Acknowledgement requests

Some server requests don't need a value back — the server just wants to know the client received and handled it. For those, your handler does its work and returns nothing; the client sends an **empty reply**, and the server's pending request resolves. Returning nothing is the acknowledgement, not an error.

```typescript [socket-types.ts]
interface ApiSocket {
  serverRequests: {
    // The server asks the client to flush its analytics; it only needs confirmation.
    'flush-analytics': { payload: { reason: string }; response: void }
  }
}
```

```typescript [app.ts]
socket.onRequest('flush-analytics', async (payload) => {
  await analytics.flush(payload.reason)
  // return nothing → the client sends an empty reply → the server's request resolves.
  // The server now knows the flush ran, with no data to read back.
})
```

Only a **missing handler** or a **thrown error** produces an error reply instead — see below.

## What happens without a handler, or on a throw

- **No handler registered** for an incoming server request: the client immediately replies with an error (`request-no-response`) so the server's pending request rejects fast, instead of waiting out its timeout.
- **The handler throws**: the client replies with an error, and the server's request rejects.
- **The handler returns the wrong shape**: your return value is validated on the server against the request's declared response. A value that doesn't fit makes the server's request reject with `request-invalid-response` — so return exactly what the contract types.
- **The handler never resolves** (e.g. you `await` a dialog the user ignores): nothing is sent back, and the _server's_ request waits out its own timeout. Make sure your handler always resolves.
- **Registering a second handler for the same event** replaces the first (and logs a warning) — there's one handler per event at a time.

```typescript [app.ts]
socket.onRequest('confirm-action', () => {
  throw new Error('user dismissed') // → the server's request() rejects
})
```

## How it stays separate from your own requests

A server-initiated request and a reply to one of _your_ requests can carry the same event name, so direction is decided by a marker, not the name: server-initiated frames carry `source: 'server'`. `serverRequest()` answers only those; [`requestResponse()`](/client/primitives/request-response) ignores them and claims only replies to its own requests. The two never cross-fire, whatever order you register them in.

## On a channel

With [`channels()`](/client/primitives/channels) installed, channel handles gain `onRequest(...)`. A channel-scoped handler answers only requests tagged with that channel; a top-level handler answers only unscoped ones — they don't cross.

```typescript [app.ts]
const room = socket.channel('rooms', 'room-1')
await room.subscribe()

room.onRequest('get-cursor', () => ({ x: cursorX, y: cursorY }))
```
