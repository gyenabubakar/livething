`readReceipts()` is the client half of read receipts. A read receipt tells you that a member has **read** a message. Many chat apps show it as a blue check.

Receipts have two sides:

- **Received** (many chat apps show a double grey check). [`inbox()`](/client/primitives/inbox) gives you this side. `receiversOf()` works with `inbox()` alone. The live `receivers` store also needs the server channel to enable `broadcastReceipts`.
- **Read** (the blue check). `readReceipts()` adds this side.

Each member has a **read cursor**. A cursor is one number: the highest message sequence number (`seq`) that the member has read. The server gives every inbox message on a channel a `seq` that grows by one each time. So "read through 12" means "read every message up to and including number 12".

`readReceipts()` adds these members to a channel handle:

- `markAsRead(seq?)` moves your own read cursor forward.
- `readers` lets you watch who has read what.
- `onRead(cb)` runs a callback each time a member's read cursor moves forward.
- `readersOf(seq)` asks the server who has read a message.

The channel must also turn on read receipts on the server with the [`readReceipts`](/server/capabilities/read-receipts) capability.

```typescript [client/dms.ts]
import {
  channels,
  client,
  connect,
  dedup,
  inbox,
  readReceipts,
  reconnection,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  channels(),
  inbox(),
  readReceipts(),
  dedup(),
  reconnection(),
)
```

## Where it sits in the stack

Read receipts build on channels and the inbox. Register `readReceipts()` together with [`channels()`](/client/primitives/channels) and [`inbox()`](/client/primitives/inbox). The order you list them in does not matter: LiveThing sorts the primitives, and `readReceipts()` always runs after `channels()` and `inbox()`.

Read means received too. When you mark a message as read, the server also marks it as received. So a member's received cursor is never behind its read cursor.

## The read surface

On a channel whose contract sets `readReceipts: true`, the channel handle gets four members. They match the received members that `inbox()` adds (`receivers`, `onReceived`, `receiversOf`), but for the read side.

### `readers`: the live read store

`channel.readers` is a [reactive store](/client/overview#reactive-stores) of every member's read cursor. The server sends a `__read__` frame to the channel each time a member's read cursor moves, and the store is updated from those frames.

The store's value is a `CursorList`, which is a `ReadonlyMap<userId, number>`. It maps each member's user ID to its `readThrough` number (the member's read cursor). Members who have read nothing yet are not in the map. So every entry is a member you can show the blue check for.

```typescript [client/dms.ts]
dm.readers.subscribe(() => {
  for (const [userId, readThrough] of dm.readers.get()) {
    showBlueCheck(userId, readThrough)
  }
})
```

The store is cleared when you really leave the channel, when you are kicked, or when a rejoin fails. A leave confirmation (`__unsubscribeOk__`) from an earlier leave does not clear it if a new rejoin has already started.

### `markAsRead(seq?)`: move your read cursor forward

`channel.markAsRead(seq)` tells the server that you have read every message up to `seq`. Leave out `seq` to mark **everything this client has received on the channel so far**. Use that form when the user opens the conversation and can see it.

`markAsRead()` does not wait for an answer and returns nothing. The server moves your read cursor forward. If the channel has no more members than the server's receipt limit, the server also sends a `__read__` frame to the channel's members.

The channel must be subscribed first. If it is not active, `markAsRead()` throws `ChannelNotSubscribed` right away.

```typescript [client/dms.ts]
const dm = socket.channel('dms', 'dm:u_100+u_200')

await dm.subscribe({})
dm.on('message', (msg) => appendMessage(msg.text))

// The user opened the conversation, so mark all of it as read.
dm.markAsRead()
```

Because a read mark also marks messages as received, `markAsRead()` moves your received cursor forward too.

### `onRead(cb)`: one member's read cursor moved

`channel.onRead(cb)` calls `cb` each time a member's read cursor moves forward. It passes that member's user ID and the new cursor. A repeated or out-of-order `__read__` frame that does not raise the cursor does not call it. `onRead()` returns a function that removes the callback.

```typescript [client/dms.ts]
const stop = dm.onRead((userId, readThrough) => {
  markRead(userId, readThrough)
})
```

### `readersOf(seq)`: ask the server who read it

`readers` and `onRead` show only the live `__read__` frames. The server stops sending those frames when the channel has more members than its receipt limit (`maxReceiptAudience`, 256 members by default). The server still stores every read cursor.

For the complete answer, `channel.readersOf(seq)` asks the server which user IDs have read up to at least `seq`. It returns a promise that resolves to that list of user IDs. Only a member of the channel can ask. The server ignores a request from a non-member and sends no answer, so the promise rejects when it times out.

```typescript [client/dms.ts]
const userIds = await dm.readersOf(1)
renderReadBy(userIds)
```

The promise rejects in these cases:

- `ChannelNotSubscribed`: the channel is not active.
- `Timeout`: no answer came before the timeout.
- `Disconnected`: the query could not be sent, or the socket closed before the answer came.

`Timeout` and `Disconnected` come from `@livething/client/errors`.

## Options

`readReceipts({ timeout })` sets how long a `readersOf` query waits for the server's answer before it rejects, in milliseconds. The default is `10_000` (10 seconds). To change it for one call, pass `readersOf(seq, { timeout })`.

```typescript [client/dms.ts]
readReceipts({ timeout: 5_000 })
```

::note
`readers`, `onRead`, `markAsRead` and `readersOf` need **both** of these:

- **On the server**, the channel lists `capabilities: [inbox(), readReceipts()]`, and the channel is part of the assembled definition (through its handlers or the channel object itself). This is what puts `readReceipts: true` into the contract that `InferClient` reads.
- **On the client**, `readReceipts()` is registered in `client()`.

If one is missing, the four members are not on the channel handle's type. Calling them is a compile error, the same as any other missing property. A channel with only `inbox: true` has the received members but no read members.
::

## When the server has read receipts but the client doesn't register it

A channel's contract can set `readReceipts: true` while `readReceipts()` is not in your `client()` stack. Then the read members do not exist on the handle, so there is nothing to call. You only get a compile error if your code tries to use one of them.

At runtime you get a warning. The first time that channel's `__subscribeOk__` arrives, `channels()` logs a warning through the client's [debug logger](/client/primitives/debug). It logs at most once per channel:

```text
[livething] channel 'dms' has read receipts enabled but readReceipts() is not registered — read receipts will not be tracked. Add readReceipts() to client().
```

Like the inbox warning, this only prints when [`debug()`](/client/primitives/debug) is on. Without `readReceipts()`, this client never sends `__read__` for that channel, so its read cursor never moves. If `inbox()` is registered, it still confirms that messages were received.

For the server half (the read cursor, the `__read__` frames and `readersOf`), see [Receipts](/server/inbox/receipts) in the Server section.
