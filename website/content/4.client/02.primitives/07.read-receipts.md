`readReceipts()` is the read half of receipts — the blue check. [`inbox()`](/client/primitives/inbox) gives you the _received_ side (the double-grey check) — `receiversOf` for free, and a live `receivers` store when the server channel enables `broadcastReceipts`; this primitive adds the read side: `markAsRead(seq?)` to advance your own read cursor, `readers` to watch who has read what, and `readersOf(seq)` to ask the server authoritatively. The channel must opt in on the server with [`readReceipts`](/server/capabilities/read-receipts).

```typescript [app.ts]
import {
  channels,
  client,
  connect,
  dedup,
  inbox,
  readReceipts,
  reconnection,
} from '@wskit/client'
import type { ReceiptsClient } from '../server/receipts'

const socket = client<ReceiptsClient>()(
  connect('wss://example.com/ws'),
  channels(),
  inbox(),
  readReceipts(),
  dedup(),
  reconnection({ maxDelay: 400 }),
)
```

## Where it sits in the stack

Read receipts build on inbox, so add `readReceipts()` **after** [`channels()`](/client/primitives/channels) **and** [`inbox()`](/client/primitives/inbox). Read implies received: marking a message read also settles it as received on the server, so a member's received cursor never lags behind its read cursor.

## The read surface

On a channel whose contract sets `readReceipts: true`, the handle gains four members. They mirror inbox's received surface, one column over.

### `readers` — the live read store

`channel.readers` is a [reactive store](/client/overview#reactive-stores) of every member's read cursor, fed by the `__read__` frames the server fans out. Its snapshot is a `CursorList` (`ReadonlyMap<userId, number>`) mapping each member to its `readThrough`, dropping any member who has read nothing yet — so every entry is a member to show the blue check for. It is cleared when you really leave the channel or are kicked. A stale `__unsubscribeOk__` from an earlier leave cannot clear state after a rejoin is already in progress.

```typescript [app.ts]
chat.readers.subscribe(() => {
  for (const [userId, readThrough] of chat.readers.get()) {
    showBlueCheck(userId, readThrough)
  }
})
```

### `markAsRead(seq?)` — advance your read cursor

`channel.markAsRead(seq)` tells the server you have read everything up to `seq`. Omit `seq` to mark **everything received so far** — the common case for "the user is looking at the thread." It is fire-and-forget: the server advances your read cursor and, on a broadcasting channel, tells the other members.

```typescript [app.ts]
const chat = socket.channel('chat')

chat.on('room-msg', (msg) => appendMessage(msg.text))

// User opened the thread — mark it all read.
chat.markAsRead()
```

Because a read mark also settles delivery, calling `markAsRead()` covers the received cursor too.

### `onRead(cb)` — one member's read cursor advanced

`channel.onRead(cb)` fires each time a member's read cursor moves forward, with that member's user id and new cursor. It returns an unsubscribe.

```typescript [app.ts]
const stop = chat.onRead((userId, readThrough) => {
  markRead(userId, readThrough)
})
```

### `readersOf(seq)` — ask the server who read it

`readers` and `onRead` reflect the live fan-out, which the server caps by member count. For the authoritative answer, `channel.readersOf(seq)` asks the server which user ids have read up to at least `seq`, and resolves to that list. Like `receiversOf`, only a member may query — a non-member's request is dropped silently.

```typescript [app.ts]
const userIds = await chat.readersOf(1)
renderReadBy(userIds.slice().sort().join('|'))
```

## Options

`readReceipts({ timeout })` sets how long a `readersOf` query waits for the server's answer before rejecting, in milliseconds. The default is `10_000` (10s). Override a single call with `readersOf(seq, { timeout })`.

```typescript [app.ts]
readReceipts({ timeout: 5_000 })
```

::note
`readers`, `onRead`, `markAsRead`, and `readersOf` need **both** things: on the server, the channel must list `capabilities: [readReceipts()]` (alongside `inbox()`) and reach `base.assemble(...)` — pass the channel object for config-only assembly, or any routed handler value from that channel — **and**, on the client, `readReceipts()` must be registered in `client()`. A routed handler value also activates that route; the channel object alone does not. Miss either one and the four members simply are not on the channel handle's type — calling them is a compile error, same as any other missing property. A channel with only `inbox: true` has the received surface but no read surface.
::

## When the server has read receipts but the client doesn't register it

If a channel's contract sets `readReceipts: true` but `readReceipts()` isn't in your `client()` stack, there is no read surface to call — nothing to catch at compile time beyond the missing property. What you do get is a runtime signal: the first time that channel's `__subscribeOk__` arrives, `channels()` logs a warning through the client's [debug logger](/client/primitives/debug), at most once per channel:

```text
[wskit] channel 'chat' has read receipts enabled but readReceipts() is not registered — read receipts will not be tracked. Add readReceipts() to client().
```

Like the inbox warning, this only prints when [`debug()`](/client/primitives/debug) is on. Without `readReceipts()` registered, nothing sends `__read__` for that channel and the read cursor never advances from this client, even though `inbox()` (if present) keeps acking delivery independently.

For the server half — the read cursor, the `__read__` fan-out, and `readersOf` — see [Receipts](/server/inbox/receipts) in the Server section.
