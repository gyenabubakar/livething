`binary()` lets the client send and receive **binary messages**: pictures, files and other bytes, with no base64 step. Each binary message has two parts, the same as on the [server](/server/binary/overview):

- The **info** is JSON, such as the type of a file or who sent it. Its type comes from the server's declaration.
- The **bytes** are the data itself, as a `Uint8Array`.

The info always comes before the bytes, in listeners and in senders.

```typescript [client/socket.ts]
import {
  binary,
  channels,
  client,
  clientRequests,
  connect,
  serverRequests,
  stream,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://huddle.example.com/huddle'),
  binary(),
  channels(),
  clientRequests(),
  serverRequests(),
  stream(),
)
```

`binary()` alone gives `binary.on` and `binary.send`. Binary requests and streams also need the primitive that makes them for JSON: [`clientRequests()`](/client/primitives/client-requests) for `binary.request`, [`serverRequests()`](/client/primitives/server-requests) for `binary.onRequest`, and [`stream()`](/client/primitives/stream) for `binary.stream` and `binary.onStream`. Without that primitive, the method does not exist at runtime. On the type, it is a stub, as for a JSON `socket.request` without `clientRequests()`: calling it is a type error with a message that names the primitive to add. A method is on the type only when the server declares something it can use: `socket.binary.request` exists only when the server has a binary request at the top level.

**A server that uses binary needs `binary()` on the client.** When the contract has any binary entries, at the top level or in a channel, and `binary()` is not in the list, `client()` gives a type error on the `connect(...)` argument:

```text
[livething] this server sends binary. Register binary() in client().
```

In plain JavaScript there is no type error. The socket then reports every binary message to [`onError`](/client/errors/onerror-routing) and drops it.

TypeScript can do this check only when it knows the contract. A loose contract, such as `any` or `Record<string, any>`, never asks for `binary()`. A function of your own that wraps `client()` and takes the contract as a type parameter cannot be checked: inside it, `client<TContract>()(connect(url))` is a type error, because `TContract` may have binary entries. Cast the argument there, and make sure the apps that call your function register `binary()` when their server uses binary:

```typescript [client/create-socket.ts]
import { client, connect } from '@livething/client'
import type { SocketContract } from '@livething/client'

export function createSocket<TContract extends SocketContract>(
  url: string,
) {
  return client<TContract>()(connect(url) as never)
}
```

`binary()` sets the WebSocket's `binaryType` to `'arraybuffer'`. A `Blob`, the browser's default, can only be read with `await`, and a message that arrives later could be handled first. With an `ArrayBuffer`, the client reads each message at once, in order.

## Receiving

`socket.binary.on(event, listener)` listens for a binary event. The listener gets the info, then the bytes. It returns a function that stops listening, like `on`:

```typescript [client/avatar.ts]
import { showAvatar } from './huddle-ui'
import { socket } from './socket'

const stop = socket.binary.on('avatar-preview', (_info, bytes) => {
  showAvatar(bytes)
})
```

A channel handle has the same method, for the binary events of that channel. Here, the info says who shares the screen:

```typescript [client/screen-share.ts]
import { paintScreen } from './huddle-ui'
import { socket } from './socket'

const general = socket.channel('rooms', 'room:general')
general.binary.on('screen-frame', (info, bytes) => {
  paintScreen(info.from, bytes)
})
await general.subscribe()
```

A binary event never reaches a normal `on(...)` listener, and a JSON event never reaches a `binary.on(...)` listener.

::warning
`bytes` is a **view** of the message that arrived, not a copy, so `bytes.buffer` is the **whole message**, with LiveThing's header and the info in front of your bytes. Do not pass `bytes.buffer` to an API that wants only your bytes. To keep the bytes, or to get an `ArrayBuffer` of only your bytes, copy them first: `bytes.slice().buffer`.
::

## Sending

`socket.binary.send` sends a binary event. It takes the event name, the bytes, and `{ info }` with the options. The bytes come second because a binary method is about the bytes. The info goes in `{ info }`, next to the other options. When the event's info can be `undefined`, you can leave out the whole object. A channel handle has `general.binary.send(...)`. As with `send`, the channel must be subscribed first, or the call throws `ChannelNotSubscribed`:

```typescript
// After `socket` and `general` from the examples above
socket.binary.send('upload-avatar', avatarBytes, {
  info: { fileType: 'image/png' },
})
general.binary.send('share-screen-frame', pictureBytes, {
  info: null,
})
```

- **The bytes** are a `Uint8Array` or an `ArrayBuffer`. Pass `undefined`, and the server handler gets an empty `Uint8Array`. Any other value, such as a string or `null`, throws a `TypeError`.
- **It returns** what `send` returns: `true` when the socket sent the message or [buffered](/client/primitives/buffering) it, and `false` when it was dropped.
- **`options.ttl`** works as it does on `send`: with `buffering()`, a message that waits longer is dropped.
- **The info and the metadata** together are at most 64 KiB. A bigger info throws a `RangeError`. Put large data in the bytes.

The client copies your bytes into the message when it sends it. A message that waits in the [buffer](/client/primitives/buffering) keeps its own copy, so you can reuse your array after `binary.send` returns.

### Size limit

`binary({ maxFrameBytes })` is the largest message `binary.send` accepts, in bytes. It counts the **whole message**: LiveThing's 9-byte header, the info and the metadata, and the bytes. The default is 32 MiB, the same as the server adapters' default. A bigger message is never sent and never queued: `binary.send` returns `false`, and `binary.request` and `binary.stream` reject with a `RangeError`. The limit also applies to the answers that `binary.onRequest` sends.

```typescript [client/socket.ts]
import { binary, client, connect } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://huddle.example.com/huddle'),
  binary({ maxFrameBytes: 4 * 1024 * 1024 }), // 4 MiB
)
```

`maxFrameBytes` must be a whole number above `0`, or `binary()` throws a `LiveThingConfigError`. The client cannot know the limit of the server, so set it to the server's limit or lower. A message over the server's limit closes the socket with `1009`.

On [`http()`](/client/connecting/connect-options#transports), each message goes up in a POST, so it must also fit in the server's `maxPostBytes` (512 KiB by default), with its 5-byte frame header. A bigger message throws a `RangeError` when you send it, nothing is sent, and the connection stays open. Send large files with [uploads](/client/primitives/uploads), which work on `http()` too. Binary messages from the server arrive there as base64 text, about a third bigger than on a WebSocket. The client turns them back into bytes, so your code gets the same `Uint8Array`.

[`buffering({ maxBytes })`](/client/primitives/buffering) counts the whole message too, and it is 1 MiB by default. So a 2 MiB avatar sent while offline is not queued, and `binary.send` returns `false`. Raise `maxBytes` to queue large messages.

### Sending many large messages

A loop of sends can give the browser far more bytes than the network carries. `socket.drain()` waits until the socket's send buffer is below 256 KiB. On a WebSocket that is its `bufferedAmount`, and on `http()` it is the bytes queued for POST and not yet sent:

```typescript
// Inside an async function, after `general` from the examples above
for (const picture of screenPictures) {
  general.binary.send('share-screen-frame', picture, { info: null })
  await socket.drain()
}
```

`socket.drain()` checks every 25 ms. It resolves at once when the socket is not open, and it stops waiting after about 50 seconds. It watches only the open socket's buffer, not the [`buffering()`](/client/primitives/buffering) queue, so it does not slow the sends that `buffering()` queues while offline: those wait in the queue, and `maxBytes` limits them. It is on every socket, without `binary()` too, because a loop of large text sends needs it as well. It is the client's version of the server's `ctx.stream.drain()`.

A large message counts as activity on the server only when all of it has arrived. Send a large file in pieces, and call `socket.drain()` between them, so no single message takes longer than the [keepalive](/client/primitives/keepalive) time. Pieces also let the app show progress and start again where it stopped.

## Requests

`socket.binary.request` is [`request`](/client/primitives/client-requests) for bytes. It takes the event name, the bytes, and `{ info }` with the options, as `binary.send` does. It sends one binary message, and the server's [binary request handler](/server/binary/requests) answers with one binary message. The promise resolves with that answer's info and bytes:

```typescript
// Inside an async function, after `socket` from the top of this page
const thumbnail = await socket.binary.request(
  'get-thumbnail',
  undefined,
  { info: { attachmentId: 'att_1' } },
)
showThumbnail(thumbnail.info.fileType, thumbnail.bytes)
```

- **The bytes** work as for `binary.send`. `get-thumbnail` sends none, so it passes `undefined`, and the server handler gets an empty `Uint8Array`.
- **`options.timeout`** is the wait for the answer, in ms, as for `request`. The default comes from `clientRequests({ timeout })`.
- **It rejects** as `request` does: with `Timeout`, with `Disconnected`, or with the typed error that the server's handler throws, such as Huddle's `NotFound` for an attachment the user may not read. That error comes back as a normal text `__error__` message.
- **A text answer** is not a valid answer to a binary request, so the promise rejects with `request-invalid-response`. A binary answer never settles a JSON `request`, which keeps waiting for its text answer. A LiveThing server never sends either one.
- **A message over `maxFrameBytes`** is not sent, and the promise rejects with a `RangeError`. With [`buffering()`](/client/primitives/buffering), a request made while offline waits in the queue, as a JSON request does.

To set a timeout on `get-thumbnail`, which sends no bytes:

```typescript
// Inside an async function, after `socket` from the top of this page
const thumbnail = await socket.binary.request(
  'get-thumbnail',
  undefined,
  { info: { attachmentId: 'att_1' }, timeout: 5_000 },
)
```

A channel handle has the same method, for the binary requests of that channel: `general.binary.request(...)`. As with `request`, the channel must be subscribed first, or the call throws `ChannelNotSubscribed`.

## Answering server requests

`socket.binary.onRequest` is [`onRequest`](/client/primitives/server-requests) for bytes. It takes the event name and a handler. The handler gets the info and the bytes of the server's request, and returns `{ info, bytes }`, or a promise of it. The client sends it back as one binary message. When a member starts sharing their screen, Huddle's server asks their client for one full picture:

```typescript
// After `socket` from the top of this page
socket.binary.onRequest('capture-screen', async (info) => {
  const bytes = await capturePng(info.maxWidth)
  return { info: { fileType: 'image/png' }, bytes }
})
```

- **The bytes** of the answer are optional. Leave them out, and the server gets an empty `Uint8Array`.
- **The answer must have an `info` key.** When the server's `in` has no schema, the type of the info is `null`: return `{ info: null, bytes }`. The info alone, such as `{ fileType: 'image/png' }`, is not an answer.
- **When the handler throws**, or returns something that is not an object with an `info` key, or bytes that are not a `Uint8Array` or an `ArrayBuffer`, the client sends a text `__error__` with the code `request-no-response`. The server's `ctx.binary.request(...)` rejects with it. The same happens at once when no handler is registered, so the server does not wait for its timeout.
- **One kind each:** a JSON `onRequest` handler never answers a binary request, and a `binary.onRequest` handler never answers a JSON one. The other kind is declined with `request-no-response`.
- **It returns** a function that removes the handler. A second handler for the same event replaces the first.

A channel handle has the same method, for the binary server requests of that channel: `general.binary.onRequest(...)`. Without `serverRequests()`, a binary server request is handled the same way as a text one: a top-level one is delivered to its event's `binary.on(...)` listeners, and one in a channel reaches no listener.

## Streams

`socket.binary.stream` is [`stream`](/client/primitives/stream) for bytes. It takes the event name, the bytes, and `{ info }` with the options, as `binary.send` does. The server's [binary stream](/server/binary/streams) sends each chunk as one binary message. The handle is the same as a JSON stream's, and each item of the `for await` loop is `{ info, bytes }`. Huddle's `download-attachment` puts the file's name and type in the info of the first chunk, and `null` in the others:

```typescript [client/download.ts]
import { appendToFile, startFile } from './huddle-ui'
import { socket } from './socket'

export async function downloadAttachment(
  attachmentId: string,
): Promise<void> {
  const download = await socket.binary.stream(
    'download-attachment',
    undefined,
    { info: { attachmentId, fromByte: 0 } },
  )

  for await (const { info, bytes } of download) {
    if (info) startFile(info.fileName, info.fileType)
    await appendToFile(bytes)
  }
}
```

- **The message that starts the stream** is binary. `info` is what the server's `input` checks, and the bytes work as for `binary.send`. `options.streamId` works as it does on `stream`. A start message over `maxFrameBytes` is not sent, and the promise rejects with a `RangeError`.
- **The handle** is the [stream handle](/client/streams/stream-handle): `break` or `cancel()` stops the stream on the server, and `nudge(...)` sends a [nudge](/client/streams/nudges). The stream's other messages stay text: `__streamOk__`, `__streamEnd__`, the server's `__error__`, the client's `__streamCancel__` and every nudge.
- **The loop ends** when the server's generator finishes. It throws the server's typed error when the generator throws, `Timeout` when no chunk comes in time, and `Disconnected` when the socket closes.
- **A missing chunk** fails the loop with [`StreamCorrupted`](/client/errors/client-side-errors), as for a JSON stream. A text chunk in a binary stream is not part of it: the client drops it, so the next chunk shows the gap.
- **A loop that reads slowly** cannot fill the memory: the chunks that wait for it are limited by [`stream({ maxBytes })`](/client/primitives/stream#limiting-unread-chunks), 16 MiB by default. A binary chunk counts its info and its bytes. Over the limit, the loop throws `StreamOverflow`.

A plain binary stream that loses its connection throws `Disconnected`. To go on, start the stream again from the last byte you got, with the position in the info. This is what `fromByte` is for:

```typescript [client/download.ts]
import { Disconnected } from '@livething/client/errors'
import { appendToFile } from './huddle-ui'
import { socket } from './socket'

/** Returns the byte to start again from after a drop, or `null` when the file is complete. */
export async function downloadFrom(
  attachmentId: string,
  fromByte: number,
): Promise<number | null> {
  let received = fromByte
  try {
    const download = await socket.binary.stream(
      'download-attachment',
      undefined,
      { info: { attachmentId, fromByte } },
    )
    for await (const { bytes } of download) {
      await appendToFile(bytes)
      received += bytes.byteLength
    }

    return null
  } catch (error) {
    // Call downloadFrom again with this byte when the socket is open again.
    if (Disconnected.matches(error)) return received

    throw error
  }
}
```

### Recorded binary streams

A [recorded binary stream](/server/binary/streams#recorded-binary-streams) on the server stores each chunk with its bytes, such as Huddle's `export-room-pdf`. Start it with `socket.binary.stream(...)` as above. It does not throw `Disconnected` when the connection drops: the client continues it by itself after it reconnects, and the loop gets the chunks it missed, as for a JSON [recorded stream](/client/streams/durable-and-continue). A hibernation wake on the server is continued the same way.

To continue it from another page, for example after a reload, call `socket.binary.continueStream` with the event name, the stream ID, and options if you need them. It is [`continueStream`](/client/streams/durable-and-continue) for bytes: it returns the stream handle at once, the server sends the stored chunks after `lastKnownSeq` again as binary messages, and each item is `{ info, bytes }`. Pass a `streamId` when you start the stream, so the page can keep it:

```typescript [client/export.ts]
import { appendToFile, startFile } from './huddle-ui'
import { socket } from './socket'

export async function exportRoomPdf(roomId: string): Promise<void> {
  const streamId = `export-${roomId}`
  sessionStorage.setItem('room-pdf-export', streamId)
  const pdf = await socket.binary.stream(
    'export-room-pdf',
    undefined,
    {
      info: { roomId },
      streamId,
    },
  )
  for await (const { info, bytes } of pdf) {
    if (info) startFile(info.fileName, 'application/pdf')
    await appendToFile(bytes)
  }
}

// After a reload: get the whole PDF again, from the first stored chunk.
export async function continueRoomPdf(
  streamId: string,
): Promise<void> {
  const pdf = socket.binary.continueStream(
    'export-room-pdf',
    streamId,
  )
  for await (const { info, bytes } of pdf) {
    if (info) startFile(info.fileName, 'application/pdf')
    await appendToFile(bytes)
  }
}
```

`binary.continueStream` takes only the names of recorded binary streams: a plain binary stream, or a JSON stream, is a type error. A text chunk is not part of a binary stream, so the client drops it, and the next chunk shows the gap.

### Broadcast binary streams

`socket.binary.onStream` is [`onStream`](/client/streams/broadcast-onstream) for bytes. It takes the event name and an object of handlers: it listens to a binary stream that the server broadcasts, and `onChunk` gets `{ info, bytes }`. A channel handle has `general.binary.stream(...)`, `general.binary.onStream(...)` and `general.binary.continueStream(...)` for the binary streams of that channel. A `binary.onStream` listener gets only binary chunks, and an `onStream` listener only text ones.

## Plugins

A plugin's [scoped socket](/client/plugins/scoped-socket) has `.binary` too, with the plugin's normal `__<id>::` prefix on every event name. It has `binary.request`, `binary.onRequest`, `binary.stream`, `binary.onStream` and `binary.continueStream` when the plugin's contract has binary requests and streams. A plugin that uses them lists `binary` and the primitive that each one needs in its `dependencies`, and `client()` gives a type error when the app forgets one.

## Messages the client drops

| Binary message                    | With `binary()`                                                 | Without `binary()`             |
| --------------------------------- | --------------------------------------------------------------- | ------------------------------ |
| A LiveThing frame                 | Delivered to its `binary.on(...)` listeners                     | Reported to `onError`, dropped |
| A LiveThing frame that is broken  | Logged when debug logging is on, dropped, like broken JSON text | Reported to `onError`, dropped |
| Data without the LiveThing header | Reported to `onError`, dropped                                  | Reported to `onError`, dropped |

The messages still go through the whole incoming pipeline first: [`dedup()`](/client/primitives/dedup) drops a repeat, [`replay()`](/client/primitives/replay) counts its sequence number, and an [`intercept()`](/client/primitives/intercept) sees it, with the bytes in `message.bytes`. An intercept, or a plugin's `onIncoming` or `onOutgoing` hook, can change the event, the info and the metadata, but not the bytes, the same as on the server: a binary message stays binary with its own bytes, and a text message stays text. With [replay](/server/replay/overview#binary-events) on in the server, a client that was away gets the binary messages it missed back after it reconnects. Each one reaches its `binary.on(...)` listeners as one message with the whole bytes, the same as a live one.

## `TextDecoder`

`binary()` reads the info with `TextDecoder` and `fatal: true`, and it checks for them when `client(...)` runs. Every browser, Node, Bun and Deno has them. On a platform without `TextDecoder`, or with one that does not honour `fatal: true`, `client(...)` throws a `LiveThingConfigError`, with a different message for each case. A React Native app may need a polyfill: see [TextDecoder on React Native](/client/platform/environments#textdecoder-on-react-native).

## Bundle size

`binary()` adds about :package-size{id="client.binary"} after minifying and gzip. A client without it does not ship the frame parser, the encoder or `socket.binary`. The socket only keeps a few small hooks for it. The code of `binary.request`, `binary.onRequest` and `binary.stream` is part of `binary()` too, so an app without `binary()` does not ship it in `clientRequests()`, `serverRequests()` or `stream()`.
