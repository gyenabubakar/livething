`binary()` lets the client send and receive **binary messages**: pictures, files and other bytes, with no base64 step. Each binary message has two parts, the same as on the [server](/server/capabilities/binary):

- The **info** is JSON, such as the type of a file or who sent it. Its type comes from the server's declaration.
- The **bytes** are the data itself, as a `Uint8Array`.

The info always comes before the bytes, in listeners and in senders.

```typescript [client/socket.ts]
import { binary, channels, client, connect } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://huddle.example.com/huddle'),
  binary(),
  channels(),
)
```

**A server that uses binary needs `binary()` on the client.** When the contract has any binary entries, at the top level or in a channel, and `binary()` is not in the list, `client()` gives a type error on the `connect(...)` argument:

```text
[livething] this server sends binary. Register binary() in client().
```

In plain JavaScript there is no type error. The socket then reports every binary message to [`onError`](/client/errors/onerror-routing) and drops it.

TypeScript can do this check only when it knows the contract. A loose contract, such as `any` or `Record<string, any>`, never asks for `binary()`. A function of your own that wraps `client()` and takes the contract as a type parameter cannot be checked: inside it, `client<TContract>()(connect(url))` is a type error, because `TContract` may have binary entries. Cast the argument there, as in `client<TContract>()(connect(url) as never)`, and make sure the apps that call your function register `binary()` when their server uses binary.

`binary()` sets the WebSocket's `binaryType` to `'arraybuffer'`. A `Blob`, the browser's default, can only be read with `await`, and a message that arrives later could be handled first. With an `ArrayBuffer`, the client reads each message at once, in order.

## Receiving

`socket.binary.on(event, listener)` listens for a binary event. The listener gets the info, then the bytes. It returns a function that stops listening, like `on`:

```typescript [client/avatar.ts]
import { showAvatar } from './huddle-ui'
import { socket } from './socket'

const stop = socket.binary.on('avatar-preview', (_info, bytes) => {
  showAvatar(bytes)
})
```

A channel handle has the same method, for the binary events of that channel. Here, the info says who shares the screen:

```typescript [client/screen-share.ts]
import { paintScreen } from './huddle-ui'
import { socket } from './socket'

const general = socket.channel('rooms', 'room:general')
general.binary.on('screen-frame', (info, bytes) => {
  paintScreen(info.from, bytes)
})
await general.subscribe()
```

A binary event never reaches a normal `on(...)` listener, and a JSON event never reaches a `binary.on(...)` listener.

::warning
`bytes` is a **view** of the message that arrived, not a copy, so `bytes.buffer` is the **whole message**, with LiveThing's header and the info in front of your bytes. Do not pass `bytes.buffer` to an API that wants only your bytes. To keep the bytes, or to get an `ArrayBuffer` of only your bytes, copy them first: `bytes.slice().buffer`.
::

## Sending

`socket.binary.send(event, info, bytes?, options?)` sends a binary event. A channel handle has `general.binary.send(...)`. As with `send`, the channel must be subscribed first, or the call throws `ChannelNotSubscribed`:

```typescript
// After `socket` and `general` from the examples above
socket.binary.send(
  'upload-avatar',
  { fileType: 'image/png' },
  avatarBytes,
)
general.binary.send('share-screen-frame', null, pictureBytes)
```

- **The bytes** are a `Uint8Array` or an `ArrayBuffer`. Leave them out, and the server handler gets an empty `Uint8Array`. To pass options with no bytes, pass `undefined` for the bytes. Any other value, such as a string or `null`, throws a `TypeError`.
- **It returns** what `send` returns: `true` when the socket sent the message or [buffered](/client/primitives/buffering) it, and `false` when it was dropped.
- **`options.ttl`** works as it does on `send`: with `buffering()`, a message that waits longer is dropped.
- **The info and the metadata** together are at most 64 KiB. A bigger info throws a `RangeError`. Put large data in the bytes.

The client copies your bytes into the message when it sends it. A message that waits in the [buffer](/client/primitives/buffering) keeps its own copy, so you can reuse your array after `binary.send` returns.

### Size limit

`binary({ maxFrameBytes })` is the largest message `binary.send` accepts, in bytes. It counts the **whole message**: LiveThing's 9-byte header, the info and the metadata, and the bytes. The default is 32 MiB, the same as the server adapters' default. A bigger message is never sent and never queued: `binary.send` returns `false`.

```typescript [client/socket.ts]
import { binary, client, connect } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://huddle.example.com/huddle'),
  binary({ maxFrameBytes: 4 * 1024 * 1024 }), // 4 MiB
)
```

`maxFrameBytes` must be a whole number above `0`, or `binary()` throws a `LiveThingConfigError`. The client cannot know the limit of the server, so set it to the server's limit or lower. A message over the server's limit closes the socket with `1009`.

[`buffering({ maxBytes })`](/client/primitives/buffering) counts the whole message too, and it is 1 MiB by default. So a 2 MiB avatar sent while offline is not queued, and `binary.send` returns `false`. Raise `maxBytes` to queue large messages.

### Sending many large messages

A loop of sends can give the browser far more bytes than the network carries. `socket.drain()` waits until the socket's send buffer (the WebSocket's `bufferedAmount`) is below 256 KiB:

```typescript
// Inside an async function, after `general` from the examples above
for (const picture of screenPictures) {
  general.binary.send('share-screen-frame', null, picture)
  await socket.drain()
}
```

`socket.drain()` checks every 25 ms. It resolves at once when the socket is not open, and it stops waiting after about 50 seconds. It watches only the open socket's buffer, not the [`buffering()`](/client/primitives/buffering) queue, so it does not slow the sends that `buffering()` queues while offline: those wait in the queue, and `maxBytes` limits them. It is on every socket, without `binary()` too, because a loop of large text sends needs it as well. It is the client's version of the server's `ctx.stream.drain()`.

A large message counts as activity on the server only when all of it has arrived. Send a large file in pieces, and call `socket.drain()` between them, so no single message takes longer than the [keepalive](/client/primitives/keepalive) time. Pieces also let the app show progress and start again where it stopped.

## Requests and streams

The `@livething/client` package does not have binary requests, binary streams or binary server requests yet. A binary reply or stream chunk that arrives is dropped, and logged when [debug logging](/client/connecting/debug-logging) is on. It never reaches a JSON `request` or `stream`.

A binary server request is never answered by a JSON `onRequest` handler. With [`serverRequests()`](/client/primitives/server-requests) on the socket, the client declines it at once with a text `__error__` frame and the code `request-no-response`, so the server does not wait for its timeout. Without `serverRequests()`, it is handled the same way as a text server request: a top-level one is delivered to its event's `binary.on(...)` listeners, and one in a channel reaches no listener. See [binary](/server/capabilities/binary) for what the server sends.

## Plugins

A plugin's [scoped socket](/client/plugins/scoped-socket) has `.binary` too, with the plugin's normal `__<id>::` prefix on every event name. A plugin that uses it lists `binary` in its `dependencies`, and `client()` gives a type error when the app forgets `binary()`.

## Messages the client drops

| Binary message                    | With `binary()`                                                 | Without `binary()`             |
| --------------------------------- | --------------------------------------------------------------- | ------------------------------ |
| A LiveThing frame                 | Delivered to its `binary.on(...)` listeners                     | Reported to `onError`, dropped |
| A LiveThing frame that is broken  | Logged when debug logging is on, dropped, like broken JSON text | Reported to `onError`, dropped |
| Data without the LiveThing header | Reported to `onError`, dropped                                  | Reported to `onError`, dropped |

The messages still go through the whole incoming pipeline first: [`dedup()`](/client/primitives/dedup) drops a repeat, [`replay()`](/client/primitives/replay) counts its sequence number, and an [`intercept()`](/client/primitives/intercept) sees it, with the bytes in `message.bytes`. An intercept, or a plugin's `onIncoming` or `onOutgoing` hook, can change the event, the info and the metadata, but not the bytes, the same as on the server: a binary message stays binary with its own bytes, and a text message stays text. The server does not store binary messages for replay, so a client that was away misses them. See [Replay · Binary events](/server/replay/overview#binary-events).

## `TextDecoder`

`binary()` reads the info with `TextDecoder` and `fatal: true`, and it checks for them when `client(...)` runs. Every browser, Node, Bun and Deno has them. On a platform without `TextDecoder`, or with one that does not honour `fatal: true`, `client(...)` throws a `LiveThingConfigError`, with a different message for each case. A React Native app may need a polyfill: see [TextDecoder on React Native](/client/platform/environments#textdecoder-on-react-native).

## Bundle size

`binary()` adds about 1.5 KB after minifying and gzip. A client without it does not ship the frame parser, the encoder or `socket.binary`. The socket only keeps a few small hooks for it.
