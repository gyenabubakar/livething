Reconnection is **opt-in**. Without this primitive, a socket that drops stays closed. When you add `reconnection()`, a connection that closes unexpectedly (for example, because the server restarts, the network fails for a moment, or you deploy a new version) opens again by itself. The client waits a little longer before each new try. This growing wait is called **backoff**. The client also adds a small random amount to each wait, which is called **jitter**.

This also covers a **first** `connect()` that never opens. A first connection that fails gets [close code](/core/close-codes) `1006` and retries in the same way as a connection that drops later.

```typescript [client/socket.ts]
import {
  binary,
  client,
  connect,
  reconnection,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  reconnection({ maxAttempts: Infinity }),
)
```

The primitive runs the retry loop and moves the socket into the `reconnecting` state while it waits. It also adds one [reactive store](/client/overview#reactive-stores) that you can use to watch the loop.

## The reconnection store

`socket.reconnection` is a store of `ReconnectionInfo`, a type that `@livething/client` exports:

```ts
interface ReconnectionInfo {
  retrying: boolean
  attempt: number
  nextRetryAt: number | null
}
```

It has what you need to show a "Reconnecting, attempt 3" message, so you don't have to track the lifecycle callbacks yourself.

- `retrying` is `true` from the drop until the next successful open.
- `attempt` is the number of tries since the count last [reset](#when-the-count-resets). It reads `0` when nothing is retrying.
- `nextRetryAt` is the time of the next try, as a `Date.now()` value in milliseconds. It is `null` when no try is scheduled. With [`platform()`](/client/platform/network-aware), it also becomes `null` while the device is offline: `retrying` stays `true` and `attempt` does not change, and the client tries again as soon as the network returns.

```typescript [client/reconnecting-banner.ts]
import { hideBanner, showBanner } from './huddle-ui'
import { socket } from './socket'

socket.reconnection.subscribe(
  ({ retrying, attempt, nextRetryAt }) => {
    if (!retrying) return hideBanner()

    const seconds = nextRetryAt
      ? Math.round((nextRetryAt - Date.now()) / 1000)
      : 0
    showBanner(
      `Reconnecting… attempt ${attempt}, retrying in ${seconds}s`,
    )
  },
)
```

This store works like every other reactive store on the socket, so the same small [framework adapter](/recipes/framework-hooks/react) connects it to your UI.

## Backoff and jitter

Each try waits longer than the one before. The wait doubles each time (1s, 2s, 4s, …) until it reaches `maxDelay`. On every try, the client also adds or removes a random amount of up to 30% of that wait. So the first wait of 1 second is really between 0.7 and 1.3 seconds. With the default `maxDelay` of 30 seconds, once the wait reaches that limit, each wait is between 21 and 39 seconds. The random part is there because after a server restart, many clients drop at the same moment. Without it, they would all try again at the same moment too and overload the server. With it, their tries are spread out.

You can't change the doubling or the 30%. You can only set `maxDelay` (the longest base wait) and `maxAttempts` (how many tries).

### When the count resets

The wait goes back to 1 second when the count of tries resets. An open alone does not reset it, because a connection can open and then fail. The count resets when the connection shows that it works:

- On WebSocket, when the server's first frame, `__connected__`, arrives.
- On [`http()`](/client/connecting/connect-options#transports), when the connection has stayed open for 30 seconds and one POST has gone through. So a connection that opens and then fails every POST still backs off, and does not reconnect in a fast loop.

`retrying` goes back to `false` as soon as the socket opens. Only the count waits for the reset, and `maxAttempts` counts every try until then.

The count also resets on a `disconnect()`, including the [lazy idle close](/client/connecting/connect-options#lazyidletimeoutms), so the next connect does not start with an old wait.

## Options

```typescript [client/socket.ts]
import { reconnection } from '@livething/client'

reconnection({
  maxAttempts: 10, // tries before it stops; Infinity never stops (default: 10)
  maxDelay: 30_000, // longest base wait between tries, in ms (default: 30_000)
  networkAware: true, // wait while the device is offline (default: true)
  shouldReconnect: (code, reason) => undefined, // decide for each close (see below)
  nonRetryableCodes: [], // more close codes that should NOT reconnect (adds to AUTH_INVALID, DUPLICATE, BANNED)
})
```

`maxAttempts` must be a whole number, `0` or more, or `Infinity`. `maxDelay` must be a number from `1` to `2147483647` (`2 ** 31 - 1`, the longest a timer can hold). Any other value makes `reconnection()` throw a `LiveThingConfigError`.

If a `connect()` URL function returns something that isn't a string, retrying can't help. The client reports the `LiveThingConfigError` once through `socket.onError(...)`, moves to `closed`, and doesn't retry. A URL function that throws its own error is retried like any failed connection.

When the client reaches `maxAttempts`, the state changes to `closed` and `socket.onReconnectFailed(...)` runs once. Use it to show a message such as "Connection lost, please refresh":

```typescript [client/socket.ts]
socket.onReconnectFailed(() =>
  showBanner('Connection lost, please refresh'),
)
```

The socket stays closed until you call `socket.connect()` again. With `maxAttempts: Infinity`, the client never stops trying, so `onReconnectFailed` never runs.

## Deciding per close code

Some closes should not retry, so the client stops after these three codes by default:

- `AUTH_INVALID` (`4002`): a retry with the same bad token fails again.
- `DUPLICATE` (`4003`): a newer connection for the same user replaced this one, for example when the server's `users` option has `onExceed: 'replace'`. A retry would push that newer connection out, and the two would keep replacing each other.
- `BANNED` (`4009`): the server has blocked this user, so a retry only opens connections that the server closes again.

Two options change this:

- **`nonRetryableCodes`** lists more close codes that should not reconnect. It adds to the three codes above. It does not replace them.
- **`shouldReconnect(code, reason)`** is a callback that gives you full control. Return `true` to retry, `false` to stop, or `undefined` to let the next rule decide. Returning `true` also retries one of the three built-in codes.

Keep temporary codes, such as `CAPACITY` (the server is full right now), off the no-retry list. The client then tries again later with backoff.

```typescript [client/socket.ts]
import { reconnection } from '@livething/client'
import { CloseCodes } from '@livething/core'
import { refreshAuthToken } from './huddle-data'

reconnection({
  shouldReconnect(code) {
    if (code === CloseCodes.AUTH_EXPIRED) {
      refreshAuthToken() // the connect() token function reads the new token on the next try
      return true
    }
    // return undefined → use the next rule
  },
})
```

The client checks the rules in this order:

1. Your `shouldReconnect` callback.
2. The no-retry list: `AUTH_INVALID`, `DUPLICATE`, `BANNED`, and your `nonRetryableCodes`.
3. The default, which is to reconnect.

The first rule that returns `true` or `false` decides. When the decision is not to retry, the state changes straight to `closed`. `onReconnectFailed` does **not** run in this case. It runs only when the client uses up all its tries.

Plugins built with `plugin()` can't take part in this decision. If your `shouldReconnect` callback throws an error, the client reports the error to `onError` and moves on to the next rule. The error does not stop the retry.

## Network-aware retries

`networkAware` is on by default. While the device is offline, the client does not try to reconnect. When the device is online again, the client tries at once, and the wait goes back to 1 second. The primitive learns about network changes from a [platform environment](/client/platform/environments). So `networkAware` only has an effect when you add `platform({ environment })` with an environment that reports network changes. Without that, the client uses only its timer and does not throw an error. Going offline never calls `disconnect()`. After a drop, the socket waits in the `reconnecting` state until the device is online again.
