`intercept()` looks at every incoming message before your `on()` handlers do. Use it to filter, transform, or annotate messages in one place. It adds no methods.

```typescript [app.ts]
import { client, connect, intercept } from '@wskit/client'
import { Block } from '@wskit/client/errors'
import type { MySocket } from './socket-types'

const socket = client<MySocket>()(
  connect('wss://example.com/ws'),

  // Observe — return nothing to leave the message alone
  intercept((message) => {
    console.log(message.event, message.payload)
  }),

  // Drop — throw Block to stop the message here
  intercept((message) => {
    if (message.event === 'heartbeat') throw Block
  }),

  // Transform — return a new message to replace it
  intercept((message) => ({
    ...message,
    payload: { ...(message.payload as object), receivedAt: Date.now() },
  })),
)
```

## How an interceptor behaves

Each interceptor receives the parsed message and does one of three things:

- **Return nothing** (or the message unchanged) — it passes through to the next interceptor and then your handlers.
- **Return a new message** — the replacement continues down the chain.
- **Throw `Block`** — the message is dropped. No further interceptors run, and no `on()` handlers fire. `Block` comes from `@wskit/client/errors`.

Interceptors are synchronous — return a message or throw, not a promise.

::warning
**Only `Block` drops a message.** Any *other* throw is isolated, not a drop: it's reported to `socket.onError`, that one interceptor is skipped, and the message plus the remaining interceptors still run. A bug in an interceptor can't silently swallow your traffic — if you mean to drop a message, throw `Block`.
::

A few kinds of frame never reach interceptors: an `__error__` frame (a typed server error goes straight to `socket.onError`), and any frame another primitive already consumed — a channel or stream frame, a reply to your own `request()`, an incoming server-request, or one [`dedup()`](/client/primitives/dedup) dropped. Interceptors run **last**, after every primitive's `onIncoming` hook, so anything a primitive claims first is gone before your `intercept()` sees it.

Unlike server-side intercepts, a client interceptor gets **no context object** — the socket itself provides any state you need through `getState()`, `getQuality()`, and the like.

## Multiple interceptors

`intercept()` is the one primitive you can add more than once. They run in the order you list them, and the chain stops at the first `Block`.

```typescript [app.ts]
const socket = client<MySocket>()(
  connect('wss://example.com/ws'),
  intercept(dropAds),     // runs first
  intercept(stampTime),   // runs second, on whatever dropAds passed through
)
```
