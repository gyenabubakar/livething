`serverRequests()` works in the opposite direction to [`clientRequests()`](/client/primitives/client-requests). It lets the **server** ask this client a question and wait for the answer. On the client, the request is _inbound_ (it comes in from the server). You register a handler for it, and the value the handler returns is sent back to the server as the reply. For the server half, see [serverRequests](/server/capabilities/server-requests).

```typescript [client/socket.ts]
import {
  binary,
  client,
  connect,
  serverRequests,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  serverRequests(),
)
socket.connect()

socket.onRequest('confirm-delete', (payload) => {
  return { confirmed: window.confirm(`Delete "${payload.preview}"?`) }
})
```

## The contract side

`onRequest()` is typed from the `serverRequests` map in your contract. Each entry pairs the `payload` the server sends with the `response` your handler must return:

```typescript [shape]
interface HuddleSocket {
  serverRequests: {
    'confirm-delete': {
      payload: { preview: string }
      response: { confirmed: boolean }
    }
  }
}
```

With `@livething/server`, `InferClient` builds this map from the server's request declarations. TypeScript checks both the `payload` your handler receives and the value it returns against this map.

## Answering a request

The client waits for the handler's return value and sends it as the reply. The handler can be sync or async. The example above is sync: `window.confirm` blocks until the person answers. An async handler can `await` a dialog, a permission prompt, or a `fetch` before it answers:

```typescript [client/delete-confirmation.ts]
import { showConfirmDialog } from './huddle-ui'
import { socket } from './socket'

// Show Huddle's own dialog, then reply with what the person picked
socket.onRequest('confirm-delete', async (payload) => {
  const confirmed = await showConfirmDialog(
    `Delete "${payload.preview}"?`,
  )
  return { confirmed }
})
```

`onRequest()` returns an unsubscribe function. Call it to stop answering that event:

```typescript [client/delete-confirmation.ts]
import { socket } from './socket'

const stopAnswering = socket.onRequest('confirm-delete', () => ({
  confirmed: false,
}))

stopAnswering()
```

## Acknowledgement requests

An **acknowledgement** is a reply that only says "I received this and handled it". Some server requests need only that, and no value back. For those, the contract sets `response: void`. Your handler does its work and returns nothing. The client then sends an **empty reply**, and the server's pending request resolves. Returning nothing is the acknowledgement. It is not an error.

Huddle's own server request, `confirm-delete`, returns a value. So this example uses a small separate server, `muteServer`, that sends a `muted-notice` when an admin mutes someone.

::code-group

```typescript [client/socket.ts]
import { client, connect, serverRequests } from '@livething/client'
import { showMutedBanner } from './huddle-ui'
import type { MuteSocket } from '../server/mute-definition'

const socket = client<MuteSocket>()(
  connect('wss://example.com/huddle'),
  serverRequests(),
)

socket.onRequest('muted-notice', async (payload) => {
  await showMutedBanner(payload.reason)
  // Return nothing: the client sends an empty reply and the server's request resolves.
  // The server knows the client saw the notice. It has no data to read back.
})
```

```typescript [server/mute-definition.ts]
import { server, t } from '@livething/server'
import { serverRequests } from '@livething/server/server-requests'
import type { InferClient } from '@livething/server'

// An admin muted this person. The server only needs to know the client saw it.
// With no `in` schema, the request is an acknowledgement.
const base = server({
  capabilities: [
    serverRequests({
      'muted-notice': { out: t<{ reason: string }>() },
    }),
  ],
})

export const muteServer = base.assemble({ handlers: [] })
export type MuteSocket = InferClient<typeof muteServer>
```

::

Only a **missing handler** or a **thrown error** sends an error reply instead. The next section explains both.

## What happens without a handler, or on a throw

- **No handler is registered** for the incoming server request: the client replies at once with a `request-no-response` error. The server's pending request rejects right away. It does not wait for its timeout.
- **The handler throws**: the client logs a warning and replies with a `request-no-response` error. The server's request rejects with that error.
- **The handler returns the wrong shape**: the server checks your return value against the request's declared response. A value that does not match makes the server's request reject with `request-invalid-response`. So return exactly the type the contract gives.
- **The handler never resolves** (for example, you `await` a dialog the user ignores): the client sends nothing back, and the _server's_ request waits until its own timeout ends. Make sure your handler always resolves.
- **You register a second handler for the same event**: it replaces the first one, and the client logs a warning. Each event has one handler at a time.

```typescript [client/delete-confirmation.ts]
import { socket } from './socket'

socket.onRequest('confirm-delete', () => {
  throw new Error('user dismissed') // the server's request() rejects
})
```

## How it stays separate from your own requests

A request from the server and a reply to one of _your_ requests can have the same event name. So the client does not use the name to decide the direction. It uses a marker in the frame's metadata: a request from the server carries `source: 'server'`. `serverRequests()` answers only those frames. [`clientRequests()`](/client/primitives/client-requests) ignores them and takes only the replies to its own requests. The two primitives never handle each other's frames, in any order you install them.

## On a channel

When you install both `serverRequests()` and [`channels()`](/client/primitives/channels), channel handles also get `onRequest(...)`. It is typed from the `serverRequests` map inside that channel's contract. A channel handler answers only requests the server sends on that channel. A top-level handler (`socket.onRequest`) answers only requests that are not on a channel. One never answers the other's requests.

Huddle's `rooms` declares no server requests. So this example uses a small separate server, `presenceServer`, where `rooms` also asks a `confirm-presence` question.

::code-group

```typescript [client/room.ts]
import {
  channels,
  client,
  connect,
  serverRequests,
} from '@livething/client'
import type { PresenceSocket } from '../server/presence-definition'

const socket = client<PresenceSocket>()(
  connect('wss://example.com/huddle'),
  serverRequests(),
  channels(),
)
socket.connect()

const room = socket.channel('rooms', 'room:general')
await room.subscribe({})

// The room admin sometimes checks that a quiet member is still around.
room.onRequest('confirm-presence', () => ({
  present: !document.hidden,
}))
```

```typescript [server/presence-definition.ts]
import { server, t } from '@livething/server'
import { channels } from '@livething/server/channels'
import { serverRequests } from '@livething/server/server-requests'
import * as v from 'valibot'
import type { InferClient } from '@livething/server'

const base = server({ capabilities: [channels(), serverRequests()] })

const rooms = base.channel(['rooms', 'room:{roomId}'], {
  capabilities: [
    serverRequests({
      'confirm-presence': {
        out: t<null>(),
        in: v.object({ present: v.boolean() }),
      },
    }),
  ],
})

export const presenceServer = base.assemble({ handlers: [rooms] })
export type PresenceSocket = InferClient<typeof presenceServer>
```

::

The server defines `rooms` with a `{roomId}` part in its name, which makes it a channel family, so `socket.channel('rooms', 'room:general')` takes a family key and a channel name. If a request arrives on a channel that has no handler for it, the client replies with `request-no-response`, the same as at the top level.
