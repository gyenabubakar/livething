`quality()` sets the latency limits that decide the **connection-quality tier**. A tier is a simple label for how fast the connection is, such as `'good'` or `'poor'`. `quality()` only sets these limits. It adds no methods to the socket.

`quality()` works only together with [`keepalive()`](/client/primitives/keepalive). `keepalive()` sends the pings, measures the latency, and adds the `socket.quality` and `socket.latency` stores.

```typescript [client/socket.ts]
import {
  client,
  connect,
  keepalive,
  quality,
} from '@livething/client'
import type { HuddleSocket } from '@monorepo/server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  keepalive(),
  quality({
    thresholds: { excellent: 30, good: 100, degraded: 300 },
  }),
)
```

## The tiers

**Latency** is the time in milliseconds (ms) between a ping and its pong. The tier comes from the average latency of the last 5 pongs. The thresholds split that average into tiers. With the default thresholds:

| Tier           | Default average latency          | Meaning      |
| -------------- | -------------------------------- | ------------ |
| `excellent`    | under 50 ms                      | fast         |
| `good`         | 50 to 149 ms                     | fine         |
| `degraded`     | 150 to 499 ms                    | slow         |
| `poor`         | 500 ms or more, or a missed pong | bad          |
| `disconnected` | none                             | not measured |

`socket.quality` is `'disconnected'` when the socket isn't open. It is also `'disconnected'` after the socket opens, until the first pong arrives.

Because the tier uses an average, one slow pong does not change it much. A missed pong is different: the tier changes to `'poor'` right away, without averaging.

The three thresholds must go up in order: `excellent` < `good` < `degraded`. LiveThing does not check this. If they are out of order (for example, `good` is lower than `excellent`), you get no error, but some tiers can never be reached.

## Reading it in your UI

The values are in the two [stores](/client/overview#reactive-stores) that [`keepalive()`](/client/primitives/keepalive) adds: `socket.quality` and `socket.latency`. A common use is a colored dot that shows the connection status:

```typescript [client/socket.ts]
import type { ConnectionQuality } from '@livething/client'

const dotColor: Record<ConnectionQuality, string> = {
  excellent: 'green',
  good: 'green',
  degraded: 'amber',
  poor: 'red',
  disconnected: 'grey',
}

socket.quality.subscribe((quality) => {
  setDotColor(dotColor[quality])
})

// null before the first pong, and again after a missed pong
socket.latency.subscribe((latency) => {
  setTooltip(latency === null ? 'measuring…' : `${latency} ms`)
})
```

`socket.quality` changes only when the tier changes. `socket.latency` changes on every pong and shows the latest single measurement, not the average. That is why the example listens to each store on its own.

Both are reactive stores, so you connect them to a UI framework with the same small adapter you use for the connection state. See [Framework Hooks](/recipes/framework-hooks/react).

## Options

```typescript [client/socket.ts]
quality({
  thresholds: { excellent: 50, good: 150, degraded: 500 }, // limits in ms (these are the defaults)
})
```

You give the three limits. `poor` is everything at or above `degraded`.

::note
The client and the server each compute quality on their own, so they can report different tiers for the same connection. `@livething/server` uses its own limits. The client tiers are only for your UI. They are not sent over the wire, so don't treat them as a value that both sides share.
::

Without `keepalive()` the client sends no pings. There is nothing to measure, so the thresholds are not used. Add `keepalive()` to get live quality, and add `quality()` only when the default limits don't fit your app.
