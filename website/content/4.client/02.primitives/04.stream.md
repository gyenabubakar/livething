`stream()` adds the methods for reading server streams. A stream is data that the server sends in many small pieces (chunks), for example the words of Scout's reply, a page of chat history, or a [piece of a file](#streams-that-carry-bytes). For the server half (writing the generator that produces the chunks), see [Streams](/server/streams/overview) in the Server section. For the full client API, see the [Streams chapter](/client/streams/overview).

```typescript [client/socket.ts]
import { binary, client, connect, stream } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  stream(),
)
```

The examples on this page use this `socket`.

## The contract side

The three methods are typed from the `streams` key of your contract. Each entry has:

- `payload`: the data that starts the stream.
- `chunk`: the shape of each piece the stream sends.
- `kind`: `'ephemeral'` (a one-time stream that ends if the connection drops) or `'persistent'` (a durable stream that the server keeps, so the client can continue it).
- `nudges` (optional): a map of messages you can send into a running stream.

This is the shape for three of Huddle's streams, shortened:

```typescript [shape]
import type { Message } from '../server/base'

interface HuddleSocket {
  streams: {
    'search-messages': {
      payload: { query: string }
      chunk: { hit: Message }
      kind: 'ephemeral'
    }
    'tail-audit-log': {
      payload: {}
      chunk: { line: string }
      kind: 'ephemeral'
      nudges: {
        stop: undefined
        'set-level': { level: 'info' | 'warn' | 'error' }
      }
    }
  }
  channels: {
    rooms: {
      addressing: 'dynamic'
      streams: {
        // Scout answers inside a room, so this stream belongs to the room channel
        'ask-scout': {
          payload: { prompt: string }
          chunk: { text: string }
          kind: 'persistent'
        }
      }
    }
  }
}
```

A channel has its own `streams` key in the same shape, and the methods on a channel handle read from it.

With `@livething/server`, `InferClient` produces this map for you, so you don't write it by hand. A server `stream` becomes `kind: 'ephemeral'`. A server `recordedStream` becomes `kind: 'persistent'`.

`payload` types the second argument to `stream(...)`, and `chunk` types each value you get in the `for await` loop. `kind: 'persistent'` is what allows `continueStream(...)` for that stream. An `'ephemeral'` stream can't be passed to `continueStream(...)`.

The primitive adds three methods, all typed from your contract's `streams`.

## `stream(event, payload, options?)`: start and read a stream

`stream(...)` starts a stream and returns a promise for a **handle**. The handle is an object you read with `for await`. The promise resolves when the server accepts the stream. It rejects if the server refuses the stream, if the connection closes first, or if the server doesn't answer within `timeout` (see [Options](#options)).

```typescript [client/scout.ts]
const hits = await socket.stream('search-messages', {
  query: 'launch date',
})

for await (const chunk of hits) {
  appendSearchHit(chunk.hit) // chunk is typed from the stream's `chunk`
}
// the loop ended normally, so the stream finished
```

The loop **ends** when the stream completes. It **throws** on a terminal error or on a per-chunk timeout, so wrap it in `try/catch` to handle those. If you leave the loop with `break` or `return`, the stream is cancelled for you.

The optional third argument sets the stream ID yourself (`{ streamId: 'ask-scout-general' }`) instead of letting LiveThing generate one. A fixed ID is useful when you want to continue the same stream after a page reload.

### The handle

```typescript [client/admin.ts]
const log = await socket.stream('tail-audit-log', {})

log.nudge('set-level', { level: 'error' }) // message into the running stream
log.cancel() // ask the server to stop; the loop ends without throwing
log.streamId // the ID shared by all chunks of this stream
log.active // true while the stream is still running
```

`nudge(event, payload, options?)` sends a message _into_ the running server generator, for example to change which lines it sends. It returns a promise:

- It resolves when the server confirms the nudge.
- It rejects if the server refuses the nudge or if `nudgeTimeout` passes.
- If the stream finishes before the server confirms, it resolves when the stream ends normally or is cancelled, and rejects with the error that ended the stream.

A rejected nudge does **not** end the stream. Only the client that started the stream can nudge it. After a stream has finished, `nudge()` and `cancel()` do nothing (`nudge()` resolves without sending anything).

### Limiting unread chunks

Chunks wait in a queue, in order, until your `for await` body reads them. If your loop is much slower than the server, chunks build up in memory. `stream({ maxBytes })` limits that queue for each stream, and it is 16 MiB by default. A text chunk counts the UTF-8 bytes of its payload, and a [binary chunk](/client/primitives/binary#streams) counts its info and its bytes. A chunk that the loop is already waiting for does not wait in the queue, so it does not count.

When a chunk would go over the limit, the client does not drop it in silence. The stream fails: the loop throws [`StreamOverflow`](/client/errors/client-side-errors), with `{ maxBytes }` as its `detail`, after the chunks that were already in the queue. The client also tells the server to stop a plain stream. A durable stream fails but is not cancelled, so its recording stays on the server, and you can [continue it](/client/streams/durable-and-continue) when your loop is ready.

When the server is fast and your UI is slow, keep the loop body short: move slow work out of the loop, or skip some chunks (for example, render only the latest one).

## `onStream(event, handlers)`: listen only (broadcasts)

When the server broadcasts a stream to many clients, your client did not start it. Scout's reply to `ask-scout` in a room works this way: everyone in the room gets the same chunks, not only the person who asked. You read it with callbacks instead of a `for await` loop:

```typescript [client/room.ts]
import {
  appendScoutText,
  markScoutReplyDone,
  showScoutError,
  showScoutStalled,
} from './huddle-ui'
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')

const unsubscribe = room.onStream('ask-scout', {
  onChunk(chunk, streamId) {
    appendScoutText(chunk.text)
  },
  onEnd(streamId, finalSeq) {
    markScoutReplyDone()
  },
  onError(err, streamId) {
    showScoutError(err)
  },
  onTimeout(streamId) {
    showScoutStalled()
  },
})
```

The callbacks run for every stream with that event name. If several streams with the same name run at the same time, use `streamId` to tell them apart. On a broadcast, a terminal error reaches every subscriber, so `onError` runs for all of them. Call `unsubscribe()` to stop listening.

## `continueStream(event, streamId, options?)`: reattach by stream ID

`continueStream(...)` connects to a **durable** stream again by its ID. Use it after a page reload, or to join a broadcast stream when you already have its ID. It only accepts streams whose `kind` is `'persistent'`. Passing an ephemeral stream is a compile error.

```typescript [client/room.ts]
import { appendScoutText } from './huddle-ui'
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')
await room.subscribe({})

// Saved earlier: the stream ID, and how many chunks the page had shown
const savedStreamId = localStorage.getItem('scout-stream-id')
const shownChunks = Number(localStorage.getItem('scout-chunks') ?? 0)
if (savedStreamId) {
  const continued = room.continueStream('ask-scout', savedStreamId, {
    lastKnownSeq: shownChunks,
  })
  for await (const chunk of continued) appendScoutText(chunk.text)
}
```

Each chunk has a sequence number (`seq`). It starts at 1 and goes up by 1, so it equals the number of chunks you already showed. `lastKnownSeq` is the highest sequence number you already received. The server sends only the chunks after it.

If the server's generator stopped before it finished (it threw, or the server restarted while it ran), the loop first gets the stored chunks, then throws `StreamAborted` with the reason `'interrupted'`. See [Durable & Continue](/client/streams/durable-and-continue#a-stream-that-was-cut-off).

## Durable streams reconnect automatically

A `'persistent'` stream (a server `recordedStream`) continues by itself when the socket reconnects. The **same `for await` loop keeps receiving chunks**, starting after the last chunk it received. You don't write any reconnect code, and you don't call `continueStream()`:

```typescript [client/scout.ts]
import { appendScoutText, markScoutReplyDone } from './huddle-ui'
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')
await room.subscribe({})

// `ask-scout` is a persistent stream. If the socket drops and then
// reconnects while Scout is replying, this loop keeps receiving chunks.
const reply = await room.stream('ask-scout', {
  prompt: 'summarize the last hour of this room',
})
for await (const chunk of reply) {
  appendScoutText(chunk.text)
}

markScoutReplyDone()
```

This works only with two other primitives installed:

- [`reconnection()`](/client/primitives/reconnection), so the socket reconnects after a drop. Without it, the loop throws `Disconnected`.
- [`keepalive()`](/client/primitives/keepalive), so the client notices a half-open connection. Without it, the loop can wait forever.

Use `continueStream()` only to reattach: when the handle in memory is gone, for example after a page reload or in a second browser tab.

A running stream has one reader. When a second tab continues a stream that the first tab is still reading, the second tab takes it over. The first tab's `for await` loop throws `StreamAborted` with `detail.reason === 'taken-over'`, and it doesn't continue on its own. To take the stream back, call `continueStream()` again in the first tab.

## Options

```typescript [client/socket.ts]
import { stream } from '@livething/client'

stream({
  timeout: 30_000, // wait for the NEXT chunk; restarts on every chunk, it is not a total limit (default: 30_000)
  nudgeTimeout: 10_000, // how long nudge() waits for the server to confirm (default: 10_000)
  maxBytes: 16 * 1024 * 1024, // the most bytes of chunks the loop has not read yet (default: 16 MiB)
})
```

`maxBytes` must be a whole number above `0`, or `stream()` throws a `LiveThingConfigError`. See [Limiting unread chunks](#limiting-unread-chunks).

`timeout` also limits how long `stream(...)` waits for the server to accept the stream. Set `timeout: 0` to turn the per-chunk timeout off. You set `timeout` only here, on the primitive. You can change the nudge timeout for one call with `nudge(event, payload, { timeout })`. `nudgeTimeout: 0` (or `{ timeout: 0 }` on one call) turns off the nudge timeout in the same way, so `nudge()` waits with no time limit.

## Streams that carry bytes

With [`binary()`](/client/primitives/binary) installed, `stream()` also adds `socket.binary.stream(...)`, `socket.binary.onStream(...)` and `socket.binary.continueStream(...)`, and the same on channel handles. They read the server's binary streams, such as Huddle's `download-attachment` and its recorded `export-room-pdf`: the handle is the same, and each chunk is `{ info, bytes }`. See [binary · Streams](/client/primitives/binary#streams).

## On a channel

With [`channels()`](/client/primitives/channels) installed, channel handles also get `stream(...)`, `onStream(...)`, and `continueStream(...)`. These methods work on that channel only and are typed from the channel's contract. This is how `room.onStream('ask-scout', ...)` above reaches only the room's own broadcast, and not another room's.
