`channels()` adds `socket.channel(...)`. It returns a handle for a **channel**, which is a room that the server manages. A channel handle is a [Messaging](/client/overview#the-messaging-interface) object, so it has the same `on()` and `send()` methods as the socket. It also has the room controls: subscribing, leaving, membership, and presence. This page is the client-side reference. For the server side, see [Channels](/server/channels/overview) in the Server section.

```typescript [client/socket.ts]
import { binary, channels, client, connect } from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  binary(),
  channels(),
)
```

The examples on this page use this `socket`.

## The contract side

`channel(...)` gets its types from the `channels` key of your contract. Each entry is one channel (or one family of channels) with its own **nested** contract. It has its own `incoming` and `outgoing`, and it can also have `subscribePayload`, `clientRequests`, `serverRequests`, and `streams`. These work the same way as at the top level. `addressing` tells the client whether the entry is one fixed channel (`'static'`) or a **dynamic family**, which is a group of channels that share one contract and differ only by name (`'dynamic'`).

`InferClient` is the type that builds a client contract from your server code. This is the shape that it creates for Huddle's read-only `announcements` channel and its `rooms` family, shortened. In this shape `rooms` also takes an `inviteToken` when you subscribe, to show `subscribePayload`. Huddle's own `rooms` has no subscribe payload, so the examples on this page call `subscribe()` with none, except the one that shows a payload function.

```typescript [shape]
interface HuddleSocket {
  channels: {
    announcements: {
      addressing: 'static'
      incoming: {
        announcement: { text: string }
      }
      outgoing: {}
    }
    rooms: {
      addressing: 'dynamic'
      subscribePayload: { inviteToken?: string }
      incoming: {
        message: {
          id: string
          text: string
          from: string
          sentAt: number
        }
        typing: { from: string }
      }
      outgoing: {
        'send-message': { text: string }
        'start-typing': {}
      }
    }
  }
}
```

So on a room's handle, `on` and `send` take their types from _that channel's_ `incoming` and `outgoing`:

```typescript
// After `socket` from the top of this page
const general = socket.channel('rooms', 'room:general')
general.on('message', (message) => appendMessage(message))
await general.subscribe()
general.send('send-message', { text: 'good morning' })
```

The same event name can mean different things in different channels.

## Getting a handle

`socket.channel(name)` returns a handle at once, before the server confirms any subscription. You can add listeners to it right away. They do nothing until the channel becomes active.

```typescript [client/room.ts]
const announcements = socket.channel('announcements') // a fixed channel
const general = socket.channel('rooms', 'room:general') // one channel in a dynamic family
```

The channel name (and, for a family, the family key) is typed from your contract's `channels`. If you don't know the channel names in a family ahead of time, use [family handles](#family-handles).

## Subscribing and leaving

You must call `subscribe()` before you can `send()` on a channel.

```typescript [client/room.ts]
const room = socket.channel('rooms', 'room:general')

await room.subscribe() // resolves when the server confirms

room.on('message', (data) => appendMessage(data))
room.send('send-message', { text: 'hello' })

await room.unsubscribe()
```

- **`subscribe(data?)`** resolves when the server confirms the join. It rejects if the server refuses the join (for example, an auth failure) or if the connection drops before the server replies. When the server channel declares a `subscribe` schema for the join payload, the contract has a `subscribePayload` for that channel, and `subscribe(data)` **requires** that typed payload, even when every field in it is optional. Without a schema, the payload is optional and untyped. You can add `on()` listeners before you subscribe. They start to work when the channel becomes active. You can't `send()` until the channel is active: `send()` throws. This check happens even when [buffering](/client/primitives/buffering) is installed, so the message is not buffered.
- **`unsubscribe()`** marks the channel inactive at once, so a `send()` after it throws right away. The promise it returns resolves only when the server confirms the leave. The client sends the leave again after each reconnect until the server confirms it. So a leave that was lost when the connection dropped still completes.

::tip
You can pass `subscribe()` a **function** instead of a value. The client calls it for the first subscribe. On an **ephemeral** channel (the default), the client also subscribes again after every reconnect, and it calls your function again each time to get a new payload. Use this to send a new short-lived token for the channel each time. This example needs a channel with a subscribe payload, such as the `rooms` in the shape above, which takes an `inviteToken`.

```typescript [client/room.ts]
await room.subscribe(() => ({ inviteToken: loadInviteToken() }))
```

On a **persistent** channel, one whose server definition sets `membership: 'persistent'`, the server itself adds you back to the channel after a reconnect, so the client does not subscribe again and does not call your function. If the channel has a `revalidate` function, the server runs it to check the membership again (the [auth gate](/server/channels/auth-gate)).
::

## Membership and presence

`channel.members` is the current list of members, as a [reactive store](/client/overview#reactive-stores). Four listeners tell you about changes:

```typescript [client/room.ts]
room.members.get() // ReadonlyMap<memberId, { meta, online }>

room.onMemberJoin((memberId, member) =>
  addAvatar(memberId, member.meta),
)
room.onMemberLeave((memberId) => removeAvatar(memberId))
room.onMemberOnline((memberId) => showOnlineDot(memberId))
room.onMemberOffline((memberId) => hideOnlineDot(memberId))
```

A **member ID** is the user's ID on a persistent channel (so it stays the same across reconnects and tabs), and the connection ID on an ephemeral channel or for an anonymous connection.

`channel.status` is a second store. Its value is `'subscribing'`, `'subscribed'`, `'unsubscribed'` or `'failed'`. Use it to show a "joining…" message from the current value, instead of using the lifecycle listeners below.

The two pairs of listeners answer different questions:

- **`onMemberJoin` / `onMemberLeave`** tell you who is _in the group_. They fire only when membership really changes: a first subscribe, a leave, a kick, or a removal by the server. What a disconnect does depends on the channel type:
  - On a **persistent** channel, a disconnect does not fire them. When the member reconnects, they don't fire either, because the member never left the group. An anonymous connection is the exception: its disconnect is a leave.
  - On an **ephemeral** channel (the default), a disconnect is a real leave. It fires `onMemberLeave`, and the member's next subscribe after a reconnect fires `onMemberJoin` again, with a new member ID.
- **`onMemberOnline` / `onMemberOffline`** tell you whether a member can be _reached right now_. Online fires when a member gets their first live connection in the channel. Offline fires when their last live connection goes away. Use them for "online dot" UIs. They never add or remove members; they only change `member.online`. On a persistent channel, a member who is offline stays in the list with `online: false`.

`member.meta` is the member's metadata, which the server set during `authenticate` (in Huddle, `{ name, role }`). The member list is filled from one sync message that the server sends right after you subscribe, and again after each reconnect.

## Channel lifecycle

Four more listeners tell you about the channel's own state, separate from other members:

- **`onSubscribed((source) => …)`**: the channel became active for you. `source` is `'client'` (the client sent the join) or `'server'` (the server added you, for example when it adds you back to a persistent channel after a reconnect).
- **`onUnsubscribed(() => …)`**: the channel is no longer active on your side. This happens when you call `unsubscribe()`, when the server kicks you, or when the socket closes for good (you call `disconnect()`, or reconnecting fails).
- **`onKicked((reason) => …)`**: the server removed you from the channel. `onUnsubscribed` fires right after it. A server that removes members, for example to enforce a ban, triggers it. Huddle's definition has no kick action today.
- **`onSubscriptionFailed((error) => …)`**: the server refused a rejoin after a reconnect (for example, the room reached its member limit while you were away). The channel becomes inactive, so `send()` throws until you call `subscribe()` again. Check `error` with `.matches()` to see why. A refused `subscribe()` call rejects its promise instead of firing this listener.

Each listener returns a function that removes it.

## Family handles

Sometimes you don't know the channel names in a dynamic family ahead of time. `socket.channel.family(key)` returns a handle for the whole family. You can call the handle like a function to get one channel. Its listeners fire for every channel in the family:

```typescript [client/room.ts]
import { appendToRoom, openTab } from './huddle-ui'
import { socket } from './socket'

const rooms = socket.channel.family('rooms')

rooms.on('message', (data, channelName) =>
  appendToRoom(channelName, data),
) // channelName tells you which
rooms.onSubscribed((channelName, source) => openTab(channelName))
rooms.list() // the channel names that are active now

rooms('room:general').send('send-message', { text: 'hi' }) // one specific room
```

These two calls return the same handle:

```typescript
// After `socket` from the top of this page
const byName = socket.channel('rooms', 'room:general')
const byFamily = socket.channel.family('rooms')('room:general')
```

## Scoped requests and streams

When you also install [`clientRequests()`](/client/primitives/client-requests), [`serverRequests()`](/client/primitives/server-requests), or [`stream()`](/client/primitives/stream), the channel handle gets the matching methods: `room.request(...)`, `room.onRequest(...)`, and `room.stream(...)`. Each one is typed from that channel's own contract, and its messages are marked with the channel on the wire.

## Options

`channels()` takes no options. A channel send queued while offline follows the [`buffering()` TTL](/client/primitives/buffering#message-ttl), and a `ttl` on one `send()` call wins over it:

```typescript [client/room.ts]
room.send('start-typing', {}, { ttl: 5_000 }) // a stale typing notice is worthless, so drop it fast
```

For the full client-side channel reference (handles, families, presence timing, and reconnection), see the [Channels chapter](/client/channels/overview).
