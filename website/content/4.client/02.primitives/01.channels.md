`channels()` adds `socket.channel(...)`, the handle for a server-managed room. A channel handle is a [Messaging](/client/overview#the-messaging-interface) object — it has the same `on()` / `send()` as the socket — plus the room controls: subscribing, leaving, membership, and presence. This page is the client-side reference; for the server half, see [Channels](/server/channels/overview) in the Server section.

```typescript [app.ts]
import { client, connect, channels } from '@wskit/client'
import type { ChatSocket } from '../server/chat'

const socket = client<ChatSocket>()(
  connect('wss://example.com/ws'),
  channels(),
)
```

## The contract side

`channel(...)` is typed from the `channels` key of your contract. Each entry is a room with its own **nested** contract — its own `incoming`, `outgoing`, and (if present) `requests`, `serverRequests`, and `streams` — mirrored the same way the top level is:

```typescript [socket-types.ts]
interface ChatSocket {
  channels: {
    rooms: {
      incoming: { message: { text: string; from: string } }
      outgoing: { say: { text: string }; 'start-typing': {} }
      // subscribePayload, requests, serverRequests, streams may appear here too
    }
  }
}
```

So `socket.channel('rooms', 'room-42').on('message', …)` and `.send('say', …)` are typed from *that room's* `incoming` and `outgoing` — the same name can mean different things in different channels.

## Getting a handle

`socket.channel(name)` returns a handle immediately — before any subscription is confirmed. You can register listeners on it right away; they stay dormant until the channel becomes active.

```typescript [app.ts]
const room = socket.channel('general')          // a fixed channel
const room42 = socket.channel('rooms', 'room-42') // one channel in a dynamic family
```

The channel name (and, for a family, the family key) is typed from your contract's `channels`. For an unknown-up-front family, use [family handles](#family-handles).

## Subscribing and leaving

You must `subscribe()` before you can `send()` on a channel.

```typescript [app.ts]
const room = socket.channel('rooms', 'room-42')

await room.subscribe({ inviteToken: 'abc' }) // resolves when the server confirms

room.on('message', (data) => appendMessage(data))
room.send('say', { text: 'hello' })

await room.unsubscribe()
```

- **`subscribe(data?)`** resolves once the server confirms, and rejects on an auth failure or a disconnect while pending. When the server channel declared a subscribe validator, the inferred contract carries a `subscribePayload` for that channel, and `subscribe(data)` **requires** that typed payload; without one, it's an optional, untyped value. You can register `on()` listeners before subscribing — they activate when the channel does. You can't `send()` until it's active (that throws), and this guard wins even over [buffering](/client/primitives/buffering).
- **`unsubscribe()`** marks the channel inactive immediately — a later `send()` throws right away — but the returned promise resolves only when the server confirms the leave. The leave is resent across reconnects until it's acknowledged, so a leave lost to a drop still completes.

::tip
Pass `subscribe()` a **function** instead of a value to regenerate the payload on every reconnect. That's how you keep a rotating per-channel credential fresh — the client re-subscribes automatically after a drop, and calls your function each time.

```typescript [app.ts]
await room.subscribe(() => ({ token: getRoomToken() }))
```
::

## Membership and presence

`channel.members` is the live roster, and four listeners track changes:

```typescript [app.ts]
room.members // ReadonlyMap<connectionId, { meta }>

room.onMemberJoin((connectionId, member) => addAvatar(member.meta))
room.onMemberLeave((connectionId) => removeAvatar(connectionId))
room.onMemberOnline((connectionId, member) => showDot(connectionId))
room.onMemberOffline((connectionId) => hideDot(connectionId))
```

The two pairs answer different questions:

- **`onMemberJoin` / `onMemberLeave`** track who's *in the group* — they fire only when membership actually changes (a first subscribe, a kick, a server-side removal). On a persistent channel, a member reconnecting on a new socket does **not** fire these, because they never left the group.
- **`onMemberOnline` / `onMemberOffline`** track whether a specific connection is *reachable right now* — they fire on every fresh subscribe (including a reconnect's auto-rejoin) and every disconnect. These drive "online dot" UIs.

`member.meta` is the connection's metadata as the server set it during `upgrade`. The roster is populated from one sync frame the server sends right after you subscribe; `channel.resyncMembers()` asks the server to resend it (fire-and-forget), useful to recover a stale roster.

## Channel lifecycle

Four more listeners cover the channel's own state, separate from other members:

- **`onSubscribed((source) => …)`** — the channel became active for you. `source` is `'client'` (you asked) or `'server'` (the server pushed it, e.g. a persistent channel auto-rejoining on reconnect).
- **`onUnsubscribed(() => …)`** — the channel left the active set on your side (you called `unsubscribe()`, or you were kicked).
- **`onKicked((reason) => …)`** — the server forcibly removed you.
- **`onSubscriptionFailed((error) => …)`** — a re-subscribe after a reconnect was rejected (permissions changed while you were away). The channel is cleared, so `send()` then throws until you `subscribe()` again. Narrow `error` with `.matches()` to see why.

Each listener returns an unsubscribe function.

## Family handles

For a dynamic family whose concrete names you don't know up front, `socket.channel.family(key)` returns a handle you call like a function, with listeners that fire across every channel in the family:

```typescript [app.ts]
const rooms = socket.channel.family('rooms')

rooms.on('message', (data, channelName) => append(channelName, data)) // channelName tells you which
rooms.onSubscribed((channelName, source) => openTab(channelName))
rooms.list() // the concrete names currently active

rooms('room-42').send('say', { text: 'hi' }) // one specific channel
```

`socket.channel('rooms', 'room-42')` and `socket.channel.family('rooms')('room-42')` resolve to the same handle.

## Scoped requests and streams

When you also install [`requestResponse()`](/client/primitives/request-response), [`serverRequest()`](/client/primitives/server-request), or [`stream()`](/client/primitives/stream), the channel handle gains the matching scoped methods — `room.request(...)`, `room.onRequest(...)`, `room.stream(...)` — each typed from that channel's own contract and tagged to its scope on the wire.

## Options

`channels({ ttl })` sets the buffer time-to-live for **channel** events — one number for all channel events, or a per-event map. It's separate from the top-level `ttl` on [`buffering()`](/client/primitives/buffering), since channel events and top-level events often want different lifetimes.

```typescript [app.ts]
channels({ ttl: { 'start-typing': 5_000, 'stop-typing': 5_000 } })
```

For the full client-side channel surface — handles, families, presence timing, and reconnection — see the [Channels chapter](/client/channels/overview).
