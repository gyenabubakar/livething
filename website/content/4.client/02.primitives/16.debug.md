`debug()` turns on console logging of what the socket is doing — connection events, messages in and out, reconnection, and more. It's a development aid; leave it off in production.

```typescript [app.ts]
import { client, connect, debug } from '@livething/client'
import type { MySocket } from './socket-types'

const socket = client<MySocket>()(
  connect('wss://example.com/ws'),
  debug(true),
)
```

A common pattern is to gate it on your build's dev flag:

```typescript [app.ts]
debug(import.meta.env.DEV)
```

## Toggling at runtime

You don't have to decide at build time. Every socket has `setDebug(...)` to switch logging on or off while it's running — handy for turning logs on only when you're chasing a problem:

```typescript [app.ts]
socket.setDebug(true) // start logging
socket.setDebug(false) // stop
```

## What it logs

With debug on, the socket reports things like:

- State transitions — `closed → connecting`, the URL it's connecting to.
- Messages received (`received 'chat'`) and sent (`send('chat')`).
- A send that didn't go out — `send('chat') not sent — not connected`, `send('chat') buffered`, or `send('ping') dropped — reserved event name`.
- Reconnection attempts, lazy connect/idle-timeout, and connection failures.
- Ping and pong, and a primitive handling or an intercept dropping a message.
- Deduplicated messages, and parse errors from malformed server data.

The output is plain `console` lines with a `[livething]` prefix, for example:

```text
[livething] closed → connecting
[livething] connecting to wss://example.com/ws
[livething] received 'chat' { text: 'hi', from: 'gyen' }
[livething] send('mark-read') buffered
[livething] dropped duplicate 'price' (delivery id m-7)
```

The exact lines depend on which primitives you've installed — each logs its own activity through the same channel. There's no custom log sink or namespace to configure: debug writes to `console`, on or off.
