`replay()` catches you up after a reconnect. While the socket is open it remembers the highest sequence number it has seen; when it reconnects it asks the server for everything after that, so you don't miss what happened during the gap. It adds no methods — it works through the message pipeline. For the server half — answering the catch-up request — see [replay](/server/capabilities/replay) in the Server section.

```typescript [app.ts]
import {
  client,
  connect,
  dedup,
  reconnection,
  replay,
} from '@wskit/client'
import type { MySocket } from './socket-types'

const socket = client<MySocket>()(
  connect('wss://example.com/ws'),
  reconnection(),
  dedup(),
  replay(),
)
```

## It needs `dedup()`

`replay()` depends on [`dedup()`](/client/primitives/dedup), and building the socket without it throws — a runtime check that runs when you call `client()(...)`, not a TypeScript compile-time gate. The reason: on catch-up the server may resend a message or two you already received before the drop, and `dedup()` is what filters those repeats out. (It also makes sense to pair it with [`reconnection()`](/client/primitives/reconnection) — replay runs when the socket reconnects.)

## How it works

As messages arrive, the primitive tracks the highest `__wskit.seq` it has seen, **per scope** — the top level and each channel keep their own high-water mark. It ignores stream chunks (their `seq` is a per-stream counter, not the catch-up cursor). On reconnect it sends one `__replay__` request per scope it has seen — a top-level one, plus one for each channel that received messages — each carrying that scope's last sequence. The server replays the missing messages, and they flow through your normal `on()` handlers, intercepts, and dedup.

There's nothing to call and no options. The catch-up is invisible in your code — missed messages arrive through the **same `on()` handlers** as live ones:

```typescript [app.ts]
// You write this once. It receives both live messages and, after a reconnect,
// the ones you missed while disconnected — replayed in order, de-duplicated.
socket.on('order-update', (data) => updateOrder(data))
```

If no messages have arrived yet, there's nothing to catch up on and no request is sent.

## Best-effort

Replay needs the server to support it for that scope. If the server doesn't, it answers that the protocol is unsupported: the client keeps running (no catch-up, no error thrown) and the error surfaces on [`socket.onServerError`](/client/errors/overview) every time. For extra visibility, `replay()` also logs a console warning — but only when [debug mode](/client/primitives/debug) is on (`debug()` or `setDebug(true)`); in a default/production config you'll see it on `onServerError`, not in the console. Turn replay on for that scope on the server, or remove `replay()` from the client.

## When catch-up misses messages

Replay can restore only the messages the server still has. If retention already deleted messages the client had not seen, the server sends a `__gap__` frame before the messages that are still available.

`replay()` reads that frame and advances its saved cursor through `missedThrough`, which stops the next reconnect from asking for the same deleted range again. It does not add a callback API. Add [`gaps()`](/client/primitives/gaps) when the app needs `socket.onGap(...)` or `channel.onGap(...)`.

The server sends a replay gap only when the client already has a cursor for that scope. A fresh load from sequence `0` never produces one. Snapshot mode never produces a gap either because it resends the current state.

See [`gaps()`](/client/primitives/gaps) for listener setup and the full `GapInfo` rules. The same primitive also surfaces [inbox overflow gaps](/server/inbox/overflow-and-gap), without making inbox depend on replay.
