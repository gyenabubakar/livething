`replay()` gets you the messages you missed while the socket was disconnected. The server gives many messages a **sequence number** (`seq`), a number that grows with each message. While the socket is open, `replay()` remembers the highest sequence number it has seen. When the socket reconnects, it asks the server for every message after that number. You get the messages addressed to you that you missed during the gap: broadcasts, messages to your user, and messages the server sent to your old connection alone.

`replay()` adds no methods to the socket. It works inside the message pipeline (the steps every incoming and outgoing message passes through). The server must also answer the catch-up request. For that part, see [replay](/server/capabilities/replay) in the Server section.

```typescript [client/socket.ts]
import {
  client,
  connect,
  dedup,
  reconnection,
  replay,
} from '@livething/client'
import type { HuddleSocket } from '../server/huddle-definition'

export const socket = client<HuddleSocket>()(
  connect('wss://example.com/huddle'),
  reconnection(),
  dedup(),
  replay(),
)
```

## It needs `dedup()`

`replay()` depends on [`dedup()`](/client/primitives/dedup). If you build the socket without `dedup()`, the `client()(...)` call fails to compile, with the message `replay() requires dedup(). Register it in client().` When TypeScript cannot be sure (see [Primitives](/client/primitives/overview) for the cases), and in plain JavaScript, the call throws a `LiveThingConfigError` instead.

The reason: during catch-up, the server can resend one or two messages that you already received before the connection dropped. `dedup()` removes those repeated messages.

You should also add [`reconnection()`](/client/primitives/reconnection). `replay()` does its work when the socket reconnects, and `reconnection()` is the primitive that reconnects it.

## How it works

Each message can belong to a **scope**: the top level of the socket, or one channel. As messages arrive, `replay()` saves the highest `metadata.delivery.seq` for each scope separately. The top level has its own number, and each channel has its own number. This saved number is the **cursor**: the point where catch-up starts. A channel's cursor starts at the number in its `__subscribeOk__` frame, so a channel that stayed quiet before the drop still catches up.

`replay()` ignores stream chunks. A stream chunk's `seq` counts the chunks of that one stream, so it is not a catch-up cursor.

When replay is on in the server, each connection also gets a secret **resume token** in a `__resume__` frame. `replay()` keeps the tokens of the last 8 connections. The same frame carries a sequence number that marks where the connection started. If the client has no top-level cursor yet, `replay()` uses that number as its cursor. So a client that drops before its first message still catches up on what it missed.

On reconnect, `replay()` sends one `__replay__` request for each scope that has a cursor. That is one request for the top level, plus one for each channel that received messages. Each request carries the cursor for its scope and the saved tokens. The server then resends the missed messages: the broadcasts, the messages sent to this user, and the messages sent only to one of those earlier connections (such as `ctx.send` or a tag broadcast). They go through your normal `on()` handlers, intercepts, and `dedup()`.

You don't call anything, and `replay()` has no options. Missed messages arrive in the **same `on()` handlers** as live messages:

```typescript [client/announcements.ts]
import { socket } from './socket'

// `announcement` is one of Huddle's top-level events.
// This handler receives live announcements. After a reconnect, it also receives
// the announcements you missed, in order and without repeats.
socket.on('announcement', (data) => showToast(data.text))
```

A channel gets its cursor from its first message. So if a channel has received no message yet, `replay()` sends no request for it.

## Best-effort

Replay works only when the server has replay turned on for that scope. So it is **best-effort**: the client asks, and it gets the missed messages only if the server can send them.

If the server does not support replay for the top level, it answers with an `unsupported-protocol` error. The client keeps running. It does not catch up, and it does not throw. The error goes to [`socket.onServerError`](/client/errors/overview) after each reconnect.

`replay()` also logs a console warning for this error, but only when [debug logging](/client/connecting/debug-logging) is on (with `socket.setDebug(true)`). With debug mode off, as in production, you see the error only in `onServerError`, not in the console.

To fix it, turn replay on for that scope on the server, or remove `replay()` from the client.

## When catch-up misses messages

Replay can resend only the messages the server still stores. The server deletes old messages when they pass an age limit or a count limit. This is called **retention**. If retention already deleted messages the client had not seen, the server first sends a `__gap__` frame (a protocol message that says "some messages are gone"). Then it sends the messages it still has.

The `__gap__` frame has a `missedThrough` field: the sequence number of the last deleted message. `replay()` moves its cursor forward to `missedThrough`. Because of this, the next reconnect does not ask for the same deleted messages again. `replay()` does not add a callback for gaps. Add [`gaps()`](/client/primitives/gaps) when your app needs `socket.onGap(...)` or `channel.onGap(...)`.

The server sends a replay gap only when the client already has a cursor for that scope. A client that starts fresh (from sequence `0`) never gets one. Snapshot mode also never sends a gap. (In snapshot mode, the server keeps only the latest message for each key and resends those, not the full history.)

See [`gaps()`](/client/primitives/gaps) for how to add listeners and for all the `GapInfo` rules. `gaps()` also reports [inbox overflow gaps](/server/inbox/overflow-and-gap), and inbox does not need `replay()` for that.
