When you test UI that reacts to a socket, the main question is: "When this event arrives, does my code do the right thing?" A unit test (a small, fast test of one piece of code) should not need a real WebSocket server to answer that. LiveThing has two helpers for this: `inject` and `injectChannel`. They push a fake message through the **real** incoming pipeline. The incoming pipeline is the list of steps that every message from the server goes through before it reaches your code. So your `.on()` handlers, intercepts, and primitives all run the same way they do in production. The socket never has to connect.

Both helpers come from the `@livething/client/testing` subpath:

```ts [client/socket.test.ts]
import { inject, injectChannel } from '@livething/client/testing'
```

## Injecting an event

`inject(socket, event, payload)` delivers a message as if the server sent it. The message goes through the full incoming pipeline in this order:

1. The `onIncoming` hook of every primitive (channels, dedup, and the others).
2. Your intercepts.
3. Your `.on()` handlers.

It works even while the socket is `'closed'`. It does not open the socket. It puts the message directly into the same pipeline that a real frame (one message on the WebSocket) goes through:

```ts [client/socket.test.ts]
import { client, connect } from '@livething/client'
import { inject } from '@livething/client/testing'
import { expect, test, vi } from 'vitest'
import type { HuddleSocket } from '@monorepo/server/huddle-definition'

test('shows an incoming notification', () => {
  const socket = client<HuddleSocket>()(
    connect('wss://example.com/huddle'),
  )

  const handler = vi.fn()
  socket.on('notification', handler)

  inject(socket, 'notification', {
    title: 'Reminder',
    body: 'Standup in 5 minutes',
  })

  expect(handler).toHaveBeenCalledWith({
    title: 'Reminder',
    body: 'Standup in 5 minutes',
  })
  expect(socket.state.get()).toBe('closed') // never connected
})
```

The test never calls `socket.connect()`, so it tests the handler logic alone. There is no network and there are no timers, so the test gives the same result every time.

## Injecting a channel message

The client finds the right channel for a message by reading a channel tag on the frame. A plain `inject` adds no tag, so its message does not reach a channel handler. Use `injectChannel(socket, channel, event, payload)` instead. It adds the channel tag to the frame, so the `channels()` primitive delivers the message to that channel's handlers:

```ts [client/room.test.ts]
import { channels, client, connect } from '@livething/client'
import { injectChannel } from '@livething/client/testing'
import { expect, test, vi } from 'vitest'
import type { HuddleSocket } from '@monorepo/server/huddle-definition'

test('routes a message to the announcements channel', () => {
  const socket = client<HuddleSocket>()(
    connect('wss://example.com/huddle'),
    channels(),
  )

  const handler = vi.fn()
  socket.channel('announcements').on('announcement', handler)

  injectChannel(socket, 'announcements', 'announcement', {
    text: 'Office closed Friday for the holiday',
  })

  expect(handler).toHaveBeenCalledWith({
    text: 'Office closed Friday for the holiday',
  })
})
```

The channel tag decides which handlers run:

- An `injectChannel` call for `announcements` runs only the handlers of `announcements`. It never runs the handlers of another channel.
- A plain `inject(socket, 'announcement', …)` is _not_ a channel message. It does not reach any channel handler.
- `injectChannel` needs the `channels()` primitive on the socket to route the message, the same as in a real app.

## Intercepts and primitives still run

Injection uses the real pipeline, so every step before your handlers runs too. For example, an [`intercept`](/client/primitives/intercept) that throws `Block` drops the injected message before it reaches `.on()`. It does the same with a real message:

```ts [client/socket.test.ts]
import { client, connect, intercept } from '@livething/client'
import { Block } from '@livething/client/errors'
import { inject } from '@livething/client/testing'
import { expect, test, vi } from 'vitest'
import type { HuddleSocket } from '@monorepo/server/huddle-definition'

test('an intercept can block an injected notification', () => {
  const doNotDisturb = true

  const socket = client<HuddleSocket>()(
    connect('wss://example.com/huddle'),
    intercept((m) => {
      if (m.event === 'notification' && doNotDisturb) throw Block
    }),
  )

  const handler = vi.fn()
  socket.on('notification', handler)

  inject(socket, 'notification', {
    title: 'Reminder',
    body: 'Standup in 5 minutes',
  })

  expect(handler).not.toHaveBeenCalled() // the intercept dropped it
})
```

So you can test more than "did my handler run". You can also check that your filters, deduplication (dropping a message that arrives twice), and other primitives do the right thing with a known input.

## The injectors are typed from your contract

`inject` and `injectChannel` use the same contract type as `client<HuddleSocket>()`. TypeScript checks the event name, the channel name and the payload shape when it compiles the test. A typo or a wrong payload is a type error, so the test cannot pass by mistake. The `socket` below is a `client<HuddleSocket>()` socket like the ones above:

```ts [client/socket.test.ts]
inject(socket, 'notification', {
  title: 'Reminder',
  body: 'Standup in 5 minutes',
})

// @ts-expect-error 'nope' isn't an incoming event
inject(socket, 'nope', {
  title: 'Reminder',
  body: 'Standup in 5 minutes',
})

// @ts-expect-error title must be a string
inject(socket, 'notification', {
  title: 42,
  body: 'Standup in 5 minutes',
})

// @ts-expect-error 'lobby' isn't a channel on this contract
injectChannel(socket, 'lobby', 'announcement', {
  text: 'hi',
})
```

The test and your `.on()` handlers use the same `HuddleSocket` type. When the contract changes, the test stops compiling and shows you what to update.

## Beyond unit tests

`inject` and `injectChannel` cover events that the server pushes and channel messages. This is most of what a client does. Some flows need a real server:

- a `request()` that must get its matching response
- a request from the server that your code answers with `onRequest()`
- the chunks of a stream
- reconnection
- the wire protocol itself

For these, write an end-to-end test (a test that runs your client against a real, running server). `inject()` and `injectChannel()` send frames without the routing data that LiveThing uses to match a response to its request, or a chunk to its stream. So they cannot test request matching or stream grouping. Use a real server, or a small echo server (a server that sends back what it receives), for those flows.
