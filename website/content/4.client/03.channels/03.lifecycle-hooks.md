A channel moves through a lifecycle: you ask to join, the server confirms, you're active for a while, then you leave or get removed. Two methods drive it — `subscribe()` and `unsubscribe()` — and four hooks report it. This page covers both.

## Subscribing

`subscribe(data?)` asks the server to let you into the room. It returns a promise that **resolves once the server confirms** and **rejects** if the join is refused or the socket drops while it's pending.

```typescript [app.ts]
const room = socket.channel('rooms', 'room-42')

try {
  await room.subscribe()
  // active — now send() works and members is populated
} catch (err) {
  // the gate refused you, or the socket dropped mid-subscribe
}
```

A few behaviors worth knowing:

- **Already active** → `subscribe()` resolves immediately without sending anything.
- **Called again before the first reply** → you get the _same_ promise back, not a second join request.
- **Disconnected while pending** → the promise rejects with a `Disconnected` error.
- **Empty or too-long name or family key** → the promise rejects locally, before anything goes on the wire — relevant when you build a family room name from user input, e.g. `socket.channel('rooms', '').subscribe()`.

### The subscribe payload

When the server's channel declares a subscribe validator, the contract carries a `subscribePayload` for that channel and the argument becomes **required and typed**. Without one, it's an optional, untyped value.

```typescript [app.ts]
// channel declared a subscribe schema → payload required and typed
await room.subscribe({ token: 'tok-member' })

// channel declared none → no argument needed
await socket.channel('general').subscribe()
```

### A payload that refreshes on reconnect

Pass a **function** instead of a value and the client re-runs it on every reconnect. That's how you keep a rotating per-channel credential fresh — when the client auto-rejoins after a drop, it calls your function again for a current token instead of replaying the stale one:

```typescript [app.ts]
await room.subscribe(() => ({ token: getFreshRoomToken() }))
```

The function can be async, and it's re-run before each reconnect's rejoin.

## Unsubscribing

`unsubscribe()` leaves the room. It takes effect **locally and immediately** — the channel goes inactive at once, so a later `send()` throws right away — but the returned promise resolves only when the server **confirms** the leave:

```typescript [app.ts]
await room.unsubscribe() // resolves once the server acknowledges the leave
```

Because the confirmation matters, the leave is **resilient**: if the socket drops before the server acknowledges it, the client resends the leave on every reconnect until it's confirmed. A leave lost to a blip still completes. Repeat `unsubscribe()` calls share the same promise, and unsubscribing a channel that's already inactive just resolves.

It **can** reject, though: if the connection is abandoned before the leave is ever confirmed — you call `disconnect()` mid-leave, or `reconnection()` gives up — the promise rejects with `Disconnected`. Wrap the `await` if you act on the confirmation:

```typescript [app.ts]
import { Disconnected } from '@wskit/client/errors'

try {
  await room.unsubscribe()
} catch (err) {
  if (Disconnected.matches(err)) {
    // the socket was abandoned before the server could confirm the leave
  }
}
```

## The send guard

You can't `send()` on a channel that isn't active — it throws `ChannelNotSubscribed`. This guard wins even over [buffering](/client/primitives/buffering): an inactive channel's send is a programming error, not something to queue.

```typescript [app.ts]
const room = socket.channel('rooms', 'room-42')

room.send('say', { text: 'hi' }) // throws — not subscribed yet

await room.subscribe()
const accepted = room.send('say', { text: 'hi' }) // fine; returns true
```

Once the channel is active, `send()` returns a boolean: `true` if the message was sent or buffered, `false` if it was dropped before going anywhere. A `false` has more than one cause — a reserved or invalid event name, a socket that isn't open with no [`buffering()`](/client/primitives/buffering) installed to queue it, or a plugin's `onOutgoing` hook throwing `Block`. `true` means "accepted," not "the server received it" — pair the channel with a [request](/client/primitives/client-requests) if you need confirmation.

Listeners are the opposite — `on()`, `onMemberJoin()`, and the rest are safe to register before subscribing; they wait for the channel to activate.

## The four hooks

Each hook returns an unsubscribe function.

```typescript [app.ts]
room.onSubscribed((source) => {
  /* became active */
})
room.onUnsubscribed(() => {
  /* left the active set */
})
room.onKicked((reason) => {
  /* server removed you */
})
room.onSubscriptionFailed((error) => {
  /* a rejoin was refused */
})
```

### onSubscribed(source)

Fires when the channel becomes active. `source` tells you who started it:

- `'client'` — you called `subscribe()`.
- `'server'` — the server pushed the subscription, which is how a **persistent** channel auto-rejoins after a reconnect (see below).

```typescript [app.ts]
room.onSubscribed((source) => {
  if (source === 'server') console.log('auto-rejoined by the server')
})
```

### onUnsubscribed()

Fires when the channel leaves the active set on your side — whether you called `unsubscribe()` or the server kicked you. (A kick fires `onKicked` first, then `onUnsubscribed`.)

### onKicked(reason)

Fires when the server forcibly removes you, with the reason string the server sent.

```typescript [app.ts]
room.onKicked((reason) => showToast(`Removed: ${reason}`))
```

### onSubscriptionFailed(error)

Fires when a channel-level error arrives that no request or stream claimed. The important case is a **rejoin after reconnect being refused** — e.g. your permissions changed while you were away. The channel is cleared, so `send()` throws until you `subscribe()` again. Narrow the error with `.matches()` to see why:

```typescript [app.ts]
import { Forbidden } from '../server/errors'

room.onSubscriptionFailed((error) => {
  if (Forbidden.matches(error))
    showToast('You no longer have access to this room')
  void room.subscribe().catch(() => {}) // or try to rejoin
})
```

A failure of a _live_ `subscribe()` call rejects that call's own promise instead of firing this hook — so use `try/catch` around `subscribe()` for the initial join, and `onSubscriptionFailed` for failures that happen later, on their own.

## Persistent channels

A channel the server marks **persistent** auto-rejoins on reconnect: the server re-adds you and pushes a fresh subscription, so `onSubscribed` fires with `source: 'server'` and you don't call `subscribe()` yourself. A non-persistent channel is the opposite — the client re-sends your `subscribe()` to rejoin after a drop. Either way the rejoin is automatic; the difference is only who initiates it.

## Leave beats rejoin

If you call `unsubscribe()` and then `subscribe()` again before the leave is confirmed, the client orders them correctly on the wire — the re-join waits until the leave is acknowledged, then runs (re-running a function payload for a fresh value). And while a leave is outstanding, any subscription the _server_ tries to push is ignored: you asked to leave, and that wins until the server confirms it. You almost never have to think about this — it just means rapid leave/rejoin sequences resolve to the last thing you asked for.
