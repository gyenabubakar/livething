A channel goes through a **lifecycle**, a fixed series of states. You ask to join. The server confirms. The channel is **active** for a while (you are in it and can send). Then you leave, or the server removes you. Two methods move a channel through this lifecycle: `subscribe()` and `unsubscribe()`. Four **hooks** (callbacks that the client calls when the state changes) report it. This page covers both. The examples use the `socket` from the [channels overview](/client/channels/overview#a-channel-handle).

## Subscribing

`subscribe(data?)` asks the server to let you into the channel. It returns a promise. The promise **resolves when the server confirms** the join. It **rejects** if the server refuses the join, or if the socket closes before the server replies.

```typescript [client/room.ts]
const room = socket.channel('rooms', 'room:general')

try {
  await room.subscribe({})
  // active: send() works and room.members is filled in
} catch (err) {
  // the server refused the join, or the socket closed before it replied
}
```

Some details about `subscribe()`:

- **The channel is already active:** `subscribe()` resolves at once and sends nothing.
- **You call it again before the server replies:** you get the _same_ promise back. The client does not send a second join request.
- **The socket closes while the join is waiting:** the promise rejects with a `Disconnected` error.
- **The channel name or family key is empty or too long:** the promise rejects at once with a `ValidationFailed` error, and nothing is sent. The limits are 256 characters for a channel name and 128 for a family key. This matters when you build a channel name from user input, for example `socket.channel('rooms', '').subscribe()`.

### The subscribe payload

A **payload** is the data you send with the join. The server can check it, for example to read a room password or an access token.

When the server's channel declares a `subscribe` schema, the contract has a `subscribePayload` for that channel. Then the argument of `subscribe()` is **required and typed**. Without that schema, the argument is optional and untyped.

Huddle's `rooms` declares no subscribe schema. In the next two examples, `rooms` also checks an invite token, so it does declare one:

```typescript [client/room.ts]
// 'rooms' declares a subscribe schema here, so the payload is required (its fields can still be optional)
const room = socket.channel('rooms', 'room:design')
const inviteToken =
  new URLSearchParams(location.search).get('invite') ?? undefined
await room.subscribe({ inviteToken })

// 'announcements' declares none, so no argument is needed
await socket.channel('announcements').subscribe()
```

### A payload that is new on each reconnect

You can pass a **function** instead of a value. The client calls it for the first join. On an **ephemeral** channel (the default), the client joins again by itself after every reconnect, and it calls your function again each time. Use this for a short-lived token for the channel: each rejoin sends a new token instead of the old one.

```typescript [client/room.ts]
await room.subscribe(() => ({ inviteToken: getFreshInviteToken() }))
```

The function can be `async`. The client runs it before each rejoin. If it throws during a reconnect, the client sends the error to `socket.onError` and joins again with the last value.

A **persistent** channel (`membership: 'persistent'` on the server) does not call your function again. The server adds you back after a reconnect, so the client does not send a join. See [Persistent and ephemeral channels](#persistent-and-ephemeral-channels) below.

## Unsubscribing

`unsubscribe()` leaves the channel. The channel becomes inactive **on your side at once**, so a later `send()` throws. The promise that `unsubscribe()` returns resolves only when the server **confirms** the leave:

```typescript [client/room.ts]
await room.unsubscribe() // resolves when the server confirms the leave
```

The client makes sure the leave reaches the server. If the socket closes before the server confirms, the client sends the leave again after each reconnect, until the server confirms it. So a leave that was lost in a short network drop still completes. Calling `unsubscribe()` again while the leave is waiting gives you the same promise. Calling it on a channel that is not active resolves at once.

The promise **can** reject. This happens when the connection ends for good before the server confirms the leave: you call `disconnect()` during the leave, or [`reconnection()`](/client/primitives/reconnection) stops trying. Then the promise rejects with `Disconnected`. Use `try`/`catch` if your code depends on the confirmation:

```typescript [client/room.ts]
import { Disconnected } from '@livething/client/errors'
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')

try {
  await room.unsubscribe()
} catch (err) {
  if (Disconnected.matches(err)) {
    // the connection ended before the server could confirm the leave
  }
}
```

## The send check

You can't `send()` on a channel that is not active. `send()` throws a `ChannelNotSubscribed` error. This check happens even when [buffering](/client/primitives/buffering) is installed. A send on an inactive channel is a bug in your code, so the client throws instead of putting the message in the buffer.

```typescript [client/room.ts]
const room = socket.channel('rooms', 'room:general')

room.send('send-message', { text: 'hi' }) // throws: not subscribed yet

await room.subscribe({})
const accepted = room.send('send-message', { text: 'hi' }) // works and returns true
```

When the channel is active, `send()` returns a boolean. `true` means the client sent the message or put it in the buffer. `false` means the client dropped the message before it left. A `false` has several possible causes:

- the event name is empty or reserved,
- the socket is not open and no [`buffering()`](/client/primitives/buffering) is installed to keep the message,
- a plugin's `onOutgoing` hook threw `Block` to cancel the message.

`true` means "accepted by the client". It does not mean "the server received it". If you need a confirmation from the server, use a [request](/client/primitives/client-requests) on the channel.

Listeners work the other way. You can register `on()`, `onMemberJoin()`, and the other listeners before you subscribe. They start to receive events when the channel becomes active.

## The four hooks

Each hook returns a function that removes that hook.

```typescript [client/room.ts]
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')

room.onSubscribed((source) => {
  /* the channel became active */
})
room.onUnsubscribed(() => {
  /* the channel is no longer active */
})
room.onKicked((reason) => {
  /* the server removed you */
})
room.onSubscriptionFailed((error) => {
  /* the server refused a rejoin after a reconnect */
})
```

### onSubscribed(source)

Runs when the channel becomes active. `source` tells you who started the join:

- `'client'`: you called `subscribe()`, or the client joined again by itself after a reconnect.
- `'server'`: the server added you. This is how a **persistent** channel adds you back after a reconnect (see below).

```typescript [client/room.ts]
room.onSubscribed((source) => {
  if (source === 'server')
    console.log('the server added you back to the room')
})
```

### onUnsubscribed()

Runs when the channel stops being active on your side. This happens when you call `unsubscribe()`, when the server kicks you, and when the connection ends for good (you call `disconnect()`, or reconnecting fails). A kick runs `onKicked` first, then `onUnsubscribed`.

### onKicked(reason)

Runs when the server removes you from the channel. `reason` is the text that the server sent. Huddle's definition has no kick action today, so this hook runs only for servers that remove members.

```typescript [client/room.ts]
room.onKicked((reason) => showToast(`Removed: ${reason}`))
```

### onSubscriptionFailed(error)

Runs when the server refuses a **rejoin after a reconnect**. For example, your permissions changed while you were offline. The channel becomes inactive, so `send()` throws until you call `subscribe()` again.

An error for one message you sent during the rejoin, such as a `room.send()` whose payload the server rejected, does not run `onSubscriptionFailed`. It goes to `socket.onServerError`, and the channel keeps rejoining.

On a persistent channel, the server checks the membership again with the channel's `revalidate` function. When `revalidate` throws, the error is `RejoinRejected` from `@livething/core`. Use `.matches()` to check the error:

```typescript [client/room.ts]
import { RejoinRejected } from '@livething/core'
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')

room.onSubscriptionFailed((error) => {
  if (RejoinRejected.matches(error)) {
    showToast('You no longer have access to this room')
    return
  }

  void room.subscribe().catch(() => {}) // try to join again
})
```

Other errors for the channel, for example when the server rejects a message that you sent on it, do not run this hook. They go to the socket's [`onServerError`](/client/errors/onerror-routing), and the channel stays active.

When a `subscribe()` call that you made is refused, its own promise rejects and this hook does not run. So use `try`/`catch` around `subscribe()` for the first join, and use `onSubscriptionFailed` for failures that happen later, when you did not call anything.

## Persistent and ephemeral channels

Channels are **ephemeral** by default. After a reconnect, the client sends your `subscribe()` again by itself, and `onSubscribed` runs with `source` set to `'client'`.

A **persistent** channel (`membership: 'persistent'` on the server) works the other way. The server saves a persistent membership by user ID. After a reconnect, the server adds you back to the channel itself: `onSubscribed` runs with `source` set to `'server'`, and you don't call `subscribe()`. If the server has not added you back within 5 seconds (for example, because the connection has no user ID), the client sends the join itself, with the last payload.

In both cases the rejoin is automatic. The only difference is which side starts it.

## A leave comes before a rejoin

You can call `unsubscribe()` and then `subscribe()` again before the server confirms the leave. The client keeps them in the right order: the new join waits until the server confirms the leave, and then it runs. If you passed a function payload, the client calls it again at that point for a new value.

While a leave is waiting for its confirmation, the client ignores any join that the server starts. You asked to leave, so the leave comes first. The result is that a fast series of leaves and joins always ends in the state you asked for last.
