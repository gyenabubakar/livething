When the server broadcasts a stream to many clients at once — a shared live feed, a ticker everyone watches — you didn't trigger it, so there's no handle to iterate. You consume it **listen-only** with `socket.onStream(event, handlers)`, which fires callbacks as chunks arrive.

```typescript [app.ts]
const unsubscribe = socket.onStream('live-feed', {
  onChunk(chunk, streamId) {
    append(chunk)
  },
  onEnd(streamId, finalSeq) {
    markComplete(streamId)
  },
  onError(err, streamId) {
    showError(err)
  },
  onTimeout(streamId) {
    showStalled(streamId)
  },
})

// later:
unsubscribe()
```

`onStream(...)` returns an unsubscribe function; call it to stop listening. Only `onChunk` is required — the other three are optional.

## The handlers

| Handler     | Fires when                            | Arguments               |
| ----------- | ------------------------------------- | ----------------------- |
| `onChunk`   | a chunk arrives                       | `(chunk, streamId)`     |
| `onEnd`     | the stream finishes                   | `(streamId, finalSeq?)` |
| `onError`   | the stream errors out                 | `(error, streamId)`     |
| `onTimeout` | no chunk within the per-chunk timeout | `(streamId)`            |

`chunk` is typed from the stream's contract `chunk`. `error` is a `WSKitError` you can narrow with `.matches()`.

`onTimeout` uses the same per-chunk timeout as [`stream({ timeout })`](/client/streams/stream-handle#the-per-chunk-timeout) — the value you set when installing the primitive (default 30s). There's no per-`onStream()` override, and `timeout: 0` disables `onTimeout` here too.

## Telling concurrent runs apart

`onStream` fires for **every** stream that matches the event name, and several can run at once. Every callback gets the `streamId`, so you key your state by it rather than assuming one stream at a time:

```typescript [app.ts]
const feeds = new Map<string, Chunk[]>()

socket.onStream('live-feed', {
  onChunk(chunk, streamId) {
    const list = feeds.get(streamId) ?? []
    list.push(chunk)
    feeds.set(streamId, list)
  },
  onEnd(streamId) {
    finalize(feeds.get(streamId))
    feeds.delete(streamId)
  },
})
```

Chunks are de-duplicated by sequence per run, so a chunk replayed across a reconnect won't fire `onChunk` twice for the same `streamId`.

## Terminal events reach everyone

A broadcast has many listeners, so when the stream ends, errors, or stalls, **every** subscriber to that event is notified — `onError` fires for all of them, not just one. `onEnd` carries a `finalSeq` (the last sequence number) so you can check you didn't miss a chunk before the stream closed. `finalSeq` is optional and can be `undefined` — a stream that ends before sending any chunk has no last sequence — so guard it before comparing.

## Scope

A top-level `socket.onStream(...)` matches only **unscoped** broadcasts. A channel-scoped broadcast is delivered to a channel handle's `onStream(...)`, not the top-level one — the two don't cross:

```typescript [app.ts]
const room = socket.channel('rooms', 'room-1')
await room.subscribe()

room.onStream('room-feed', {
  onChunk(chunk, streamId) {
    appendToRoom(chunk)
  },
})
```

## Listen-only

There's no `nudge()` or `cancel()` here — you're a listener on a stream the server owns, not its creator. To steer a stream, you have to be the one who started it with [`stream(...)`](/client/streams/stream-handle).

Unlike `socket.stream()`, `onStream()` never throws or rejects for being disconnected — it's a passive subscription. You can register it before you ever call `connect()`; it simply sits idle and starts firing once matching broadcasts arrive.

::note
A handler that throws is reported and isolated — the other subscribers to the same stream still get their callbacks, so one bad listener can't break the feed for the rest.
::
