A **broadcast stream** is one stream that many clients receive at the same time, for example Scout's reply streaming into a room for every member, not only the person who asked. On the server, the stream has `broadcast: true` (see [Broadcast](/server/streams/broadcast) in the Server section). One client starts it with `stream(...)`. The server then sends the same chunks to every other connection: every connected client for a top-level stream, or every other member of the channel for a channel stream.

If you did not start the stream, you have no handle to loop over. Instead, you listen with `onStream(event, handlers)`. It is **listen-only**: you only receive chunks, and your callback functions run as the chunks arrive. `onStream` is available when the client has the [`stream()`](/client/primitives/stream) primitive.

The examples on this page use Huddle's `ask-scout` stream, which belongs to the `rooms` channel family:

```typescript [shape]
export interface HuddleSocket {
  channels: {
    rooms: {
      addressing: 'dynamic'
      streams: {
        'ask-scout': {
          payload: { prompt: string }
          chunk: { text: string }
          kind: 'persistent'
        }
      }
    }
  }
}
```

```typescript [client/room.ts]
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')
await room.subscribe({})

const unsubscribe = room.onStream('ask-scout', {
  onChunk(chunk, streamId) {
    appendScoutText(chunk.text)
  },
  onEnd(streamId, finalSeq) {
    markScoutReplyDone()
  },
  onError(err, streamId) {
    showToast('Scout ran into an error')
  },
  onTimeout(streamId) {
    showToast('Scout is taking too long')
  },
})

// later:
unsubscribe()
```

`onStream(...)` returns an unsubscribe function. Call it to stop listening. It only removes your callbacks on this client and sends nothing to the server. Only `onChunk` is required. The other three callbacks are optional.

## The handlers

| Handler     | Runs when                              | Arguments               |
| ----------- | -------------------------------------- | ----------------------- |
| `onChunk`   | a chunk arrives                        | `(chunk, streamId)`     |
| `onEnd`     | the stream finishes                    | `(streamId, finalSeq?)` |
| `onError`   | the stream ends with an error          | `(error, streamId)`     |
| `onTimeout` | the next chunk does not arrive in time | `(streamId)`            |

The type of `chunk` comes from the `chunk` entry of that stream in your contract. `error` is a `LiveThingError`. To check which error it is, use the `.matches()` method of an error definition, for example `InternalError.matches(error)` with `InternalError` from `@livething/core`.

`onTimeout` uses the same per-chunk timeout as [`stream({ timeout })`](/client/streams/stream-handle#the-per-chunk-timeout). This is the value you set when you add the `stream()` primitive (default: 30 seconds). The clock starts when the first chunk of a run arrives and restarts on every chunk. You cannot set a different timeout for one `onStream()` call. With `timeout: 0`, `onTimeout` never runs.

## Telling concurrent runs apart

Each time a client starts the stream, the server creates a new **run** of it with its own stream ID. `onStream` runs for **every** run of a stream with that event name, and several runs can be active at the same time: two different members can each ask Scout something at once. Every callback receives the `streamId`, so store your state by stream ID. Do not assume there is only one run at a time:

```typescript [client/room.ts]
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')
await room.subscribe({})

const replies = new Map<string, string[]>()

room.onStream('ask-scout', {
  onChunk(chunk, streamId) {
    const pieces = replies.get(streamId) ?? []
    pieces.push(chunk.text)
    replies.set(streamId, pieces)
  },
  onEnd(streamId) {
    appendMessage({
      id: streamId,
      text: (replies.get(streamId) ?? []).join(''),
      from: 'scout',
      sentAt: Date.now(),
    })
    replies.delete(streamId)
  },
})
```

Each chunk carries a **sequence number** (`seq`), which counts up by one for every chunk in a run. If a chunk arrives with a sequence number that the client has already seen for that run, the client drops it, so `onChunk` does not run twice for the same chunk. The client keeps these numbers across a reconnect. So when you continue a durable broadcast after a drop, and the server sends the stored chunks again, `onChunk` runs only for the chunks you did not get yet. The client forgets the numbers when you call `disconnect()`, or when reconnecting gives up.

## Terminal events reach everyone

A **terminal event** is an event that ends a run: the stream finishes, ends with an error, or times out. A broadcast has many listeners, so a terminal event reaches **every** listener of that event on the client. For example, `onError` runs for all of them, not only for one.

`onEnd` receives `finalSeq`, the sequence number of the last chunk. Compare it with the last sequence number you received to check that you did not miss a chunk. `finalSeq` is `undefined` only when the client that started a non-durable broadcast cancels it. The server then ends the run for the other listeners with no sequence number. A durable broadcast, such as `ask-scout`, still sends `finalSeq` when someone tells Scout to `stop`. Check for `undefined` before you compare.

A durable broadcast keeps running when the client that started it disconnects, so listeners still get the rest and `onEnd`. If the server's generator stops before it finishes (it throws, or the server restarts while it runs), a listener that continues the stream gets the stored chunks, then `onError` with a `StreamAborted` error whose reason is `'interrupted'`, not `onEnd`.

## Scope

A top-level `socket.onStream(...)` receives only broadcasts that do **not** belong to a channel, for example a top-level `stream` handler with `broadcast: true`. A broadcast from a channel stream, such as `ask-scout`, goes only to the `onStream(...)` of that channel's handle, not to the top-level one. The two never mix. You receive a channel broadcast only while you are a member of the channel, so subscribe first, as in the example above.

## Listen-only

`onStream` has no `nudge()` and no `cancel()`. The client that started the stream owns the run, and you are only a listener. To control a stream, you must start it yourself with [`stream(...)`](/client/streams/stream-handle). The client that started a broadcast reads the chunks through its own handle. Its `onStream` callbacks do not run for that run.

`socket.stream()` rejects when the socket is disconnected. `onStream()` never throws or rejects for that reason, because it only registers callbacks. You can call it before you call `connect()`. It does nothing until matching broadcasts arrive. On a [lazy](/client/connecting/connect-options#lazy) socket, `onStream()` counts as needing the connection, in the same way as `on()`, so it opens the socket.

::note
If one of your callbacks throws, the client catches the error and passes it to the socket's [`onError`](/client/errors/onerror-routing) listener. The other listeners of the same stream still get their callbacks, so one broken listener does not stop the stream for the others.
::
