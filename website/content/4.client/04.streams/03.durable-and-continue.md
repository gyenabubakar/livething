A **durable** stream is a stream whose contract `kind` is `'persistent'`. It continues after a disconnect, because the server keeps enough state to send the rest: a cursor stream runs its generator again from a saved checkpoint, and a recorded stream sends its stored chunks. On the client you see this in two ways:

- The stream **reconnects automatically** when the same socket reconnects.
- You can **reattach to it** with its ID. Reattaching means you connect to the stream again from a new handle, for example after a page reload or in another tab.

## Automatic reconnect

You don't write any code for this. When the socket drops and reconnects, a persistent stream attaches itself again. The **same `for await` loop keeps receiving chunks**, starting after the last chunk you received. Your code does not see the break:

```typescript [client/room.ts]
// `export-room` is a persistent stream. If the socket drops while the export
// is running and then reconnects, the loop keeps receiving chunks.
// You don't need any reconnect code here.
const pages = await socket.stream('export-room', {
  roomId: 'room:general',
})

for await (const chunk of pages) {
  appendExportedMessages(chunk.messages)
}
markExportDone()
```

### What it needs

Automatic reconnect works only if the socket can come back, and only if the client can tell when the connection is dead:

- [`reconnection()`](/client/primitives/reconnection) makes the socket reconnect after a drop.
- [`keepalive()`](/client/primitives/keepalive) detects a _half-open_ socket (a connection that stopped working with no close frame). A stream waits for its next chunk. Without keepalive's pings, a half-open connection leaves the loop waiting until the per-chunk timeout fails it, or forever if you turned that timeout off. In debug mode, a persistent stream started with `stream()` logs a warning when `keepalive()` is missing.

Sometimes the socket cannot reconnect: you closed it yourself, reconnection gave up, or the close code is one that does not allow a retry. Then the stream cannot continue, so the loop **throws `Disconnected`** instead of waiting forever.

## The sequence number

Reconnecting uses a **sequence number** (`seq`) on each chunk. The first chunk has `seq` 1, and each next chunk adds 1. The client remembers the highest `seq` it has delivered to your loop. On reconnect, it sends this number to the server, and the server sends the chunks after it. The client drops any chunk whose `seq` it has already delivered. So if a chunk arrives twice around the reconnect, your loop still gets it only once.

A reconnect can take longer than the gap between two chunks, because the server may need to send many saved chunks at once, or run a cursor stream's generator again. So while a reconnect is running, the client uses a longer deadline than the per-chunk timeout. This deadline is 30 seconds, or your per-chunk `timeout` if you set it higher. If no continued chunk arrives before the deadline, the loop throws `Timeout` instead of waiting forever. The normal per-chunk timer starts again only when the first continued chunk arrives. If you set `timeout: 0`, the reconnect deadline is turned off together with the per-chunk timeout. A reconnect that never gets an answer then waits forever.

::note
On the Cloudflare adapter, the server runs in a Durable Object (a Cloudflare server instance that keeps state). A Durable Object can sleep while it has no work, which Cloudflare calls **hibernation**. When it wakes up, the server can bring a durable stream back. The client then sends the `__continueStream__` request again, and the chunks arrive again. Your loop does not change.
::

## Reattaching with `continueStream`

Automatic reconnect needs the handle that is still in memory. After a **page reload**, or in a **second tab**, that handle does not exist. The server can still hold the stream. `continueStream(event, streamId, options?)` connects to it again by its ID:

```typescript [client/room.ts]
// After a reload. savedStreamId was saved earlier, for example in localStorage.
// You had already shown 12 pages, so ask only for the chunks after seq 12.
const continued = socket.continueStream(
  'export-room',
  savedStreamId,
  {
    lastKnownSeq: 12,
  },
)

for await (const chunk of continued) {
  appendExportedMessages(chunk.messages)
}
```

Things to know about `continueStream`:

- It returns a **handle directly**, not a promise. You can iterate it at once.
- It **never rejects when you call it**, even for an old or unknown `streamId`. The error comes _inside_ the loop instead: the `for await` throws `StreamAborted` with the reason `not-found`, `expired`, or `cursor-invalid`. `socket.stream()` works the other way: its promise rejects before you iterate. So always put a reattached stream's loop in a `try/catch`.
- It only accepts streams whose `kind` is `'persistent'`. Passing an ephemeral stream is a compile error, because there is nothing to continue.
- `lastKnownSeq` is the highest chunk `seq` you already have, so the server sends only the chunks after it. The handle does not show `seq`, but since `seq` starts at 1 and goes up by 1, it equals the number of chunks you already received. Leave `lastKnownSeq` out to get every chunk the server still holds.

```typescript [client/room.ts]
import { StreamAborted } from '@livething/core'

const continued = socket.continueStream('export-room', savedStreamId)
try {
  for await (const chunk of continued) {
    appendExportedMessages(chunk.messages)
  }
} catch (err) {
  // An old or unknown ID ends up here, not at the continueStream() call.
  // err.detail.reason is 'not-found', 'expired' or 'cursor-invalid'.
  if (StreamAborted.matches(err)) {
    startFresh()
  } else {
    throw err
  }
}
```

To reattach, save the stream ID while the stream runs: read it from `handle.streamId`, or [pin the stream ID](/client/streams/stream-handle#pinning-the-stream-id) yourself. After a reload, pass that ID to `continueStream`. See the [server abort reasons](/server/streams/config-and-lifecycle) for what each reason means.

## Auto-reconnect vs `continueStream`

Each one is for a different situation:

|           | Automatic reconnect                  | `continueStream()`                                          |
| --------- | ------------------------------------ | ----------------------------------------------------------- |
| When      | The same socket drops and reconnects | The handle is gone, after a reload or in another tab        |
| Your code | None. The loop keeps going           | Call `continueStream(event, id)` and iterate the new handle |
| Needs     | `reconnection()` + `keepalive()`     | A `streamId` you saved earlier                              |

## On a channel

With [`channels()`](/client/primitives/channels), a channel handle also has its own `continueStream(...)`. Use it to continue a durable stream that ran inside that room:

```typescript [client/room.ts]
const room = socket.channel('rooms', 'room:general')
await room.subscribe({})

const continued = room.continueStream('ask-scout', savedStreamId)
for await (const chunk of continued) {
  appendScoutText(chunk.text)
}
```
