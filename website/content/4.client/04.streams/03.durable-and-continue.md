A **durable** stream is a stream whose contract `kind` is `'persistent'`. On the server it is a recorded stream. Its generator keeps running when the client drops, and it stores every chunk, so a client that comes back gets the rest. On the client you see this in two ways:

- The stream **reconnects automatically** when the same socket reconnects.
- You can **reattach to it** with its ID. Reattaching means you connect to the stream again from a new handle, for example after a page reload or in another tab.

## Automatic reconnect

You don't write any code for this. When the socket drops and reconnects, a persistent stream attaches itself again. The **same `for await` loop keeps receiving chunks**, starting after the last chunk you received. Your code does not see the break:

```typescript [client/room.ts]
import { appendScoutText, markScoutReplyDone } from './huddle-ui'
// `ask-scout` is a persistent stream. If the socket drops while Scout is
// replying and then reconnects, the loop keeps receiving chunks.
// You don't need any reconnect code here.
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')
await room.subscribe({})

const reply = await room.stream('ask-scout', {
  prompt: 'summarize the last hour of this room',
})

for await (const chunk of reply) {
  appendScoutText(chunk.text)
}
markScoutReplyDone()
```

### What it needs

Automatic reconnect works only if the socket can come back, and only if the client can tell when the connection is dead:

- [`reconnection()`](/client/primitives/reconnection) makes the socket reconnect after a drop.
- [`keepalive()`](/client/primitives/keepalive) detects a _half-open_ socket (a connection that stopped working with no close frame). A stream waits for its next chunk. Without keepalive's pings, a half-open connection leaves the loop waiting until the per-chunk timeout fails it, or forever if you turned that timeout off. In debug mode, a persistent stream started with `stream()` logs a warning when `keepalive()` is missing.

Sometimes the socket cannot reconnect: you closed it yourself, reconnection gave up, or the close code is one that does not allow a retry. Then the stream cannot continue, so the loop **throws `Disconnected`** instead of waiting forever.

## A stream that was cut off

The server's generator can stop before it finishes: it throws, or the server restarts, crashes, or is evicted while the stream runs. When the client continues such a stream, it first gets the stored chunks it missed. Then the loop throws `StreamAborted` with the reason `'interrupted'`, instead of ending normally. So your app can tell a cut-off stream from a finished one:

```typescript [client/room.ts]
import { StreamAborted } from '@livething/core'
import {
  appendScoutText,
  markScoutReplyDone,
  showRetryButton,
} from './huddle-ui'
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')
await room.subscribe({})

const reply = await room.stream('ask-scout', {
  prompt: 'summarize the last hour of this room',
})

try {
  for await (const chunk of reply) appendScoutText(chunk.text)
  markScoutReplyDone()
} catch (err) {
  if (
    StreamAborted.matches(err) &&
    err.detail.reason === 'interrupted'
  ) {
    showRetryButton() // the reply was cut off; ask Scout again
  } else throw err
}
```

A listener that watches the stream with `onStream(...)` gets the same error in its `onError` callback, not `onEnd`.

## The sequence number

Reconnecting uses a **sequence number** (`seq`) on each chunk. The first chunk has `seq` 1, and each next chunk adds 1. The client remembers the highest `seq` it has delivered to your loop. On reconnect, it sends this number to the server, and the server sends the chunks after it. The client drops any chunk whose `seq` it has already delivered. So if a chunk arrives twice around the reconnect, your loop still gets it only once. A chunk must also be exactly the next `seq`. If one is missing, the loop throws [`StreamCorrupted`](/client/errors/client-side-errors) instead of ending with a hole in the data. The recording is kept, so you can continue the stream again from the last `seq` you got. The same check applies to `continueStream()`: its first chunk must be `lastKnownSeq + 1`.

A reconnect can take longer than the gap between two chunks, because the server may need to send many saved chunks at once. So while a reconnect is running, the client uses a longer deadline than the per-chunk timeout. This deadline is 30 seconds, or your per-chunk `timeout` if you set it higher. If no continued chunk arrives before the deadline, the loop throws `Timeout` instead of waiting forever. The normal per-chunk timer starts again only when the first continued chunk arrives. If you set `timeout: 0`, the reconnect deadline is turned off together with the per-chunk timeout. A reconnect that never gets an answer then waits forever.

::note
On the Cloudflare adapter, the server runs in a Durable Object (a Cloudflare server instance that keeps state). A Durable Object can sleep while it has no work, which Cloudflare calls **hibernation**. When it wakes up, the client sends the `__continueStream__` request again and gets the stored chunks it missed. If the stream's generator stopped while the Durable Object slept, the loop then throws `StreamAborted` with the reason `'interrupted'` (see [A stream that was cut off](#a-stream-that-was-cut-off)).
::

## Reattaching with `continueStream`

Automatic reconnect needs the handle that is still in memory. After a **page reload**, or in a **second tab**, that handle does not exist. The server can still hold the stream. `continueStream(event, streamId, options?)` connects to it again by its ID:

```typescript [client/room.ts]
import { appendScoutText } from './huddle-ui'
// After a reload. The stream ID and the number of chunks already shown
// were saved earlier in localStorage. Ask only for the chunks after those.
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')
await room.subscribe({})

const savedStreamId = localStorage.getItem('scout-stream-id')
const shownChunks = Number(localStorage.getItem('scout-chunks') ?? 0)
if (savedStreamId) {
  const continued = room.continueStream('ask-scout', savedStreamId, {
    lastKnownSeq: shownChunks,
  })

  for await (const chunk of continued) {
    appendScoutText(chunk.text)
  }
}
```

Things to know about `continueStream`:

- It returns a **handle directly**, not a promise. You can iterate it at once.
- It **never rejects when you call it**, even for an old or unknown `streamId`. The error comes _inside_ the loop instead: the `for await` throws `StreamAborted` with the reason `not-found` or `expired` (or `interrupted` after the stored chunks, for a stream that was cut off). `socket.stream()` works the other way: its promise rejects before you iterate. So always put a reattached stream's loop in a `try/catch`.
- It only accepts streams whose `kind` is `'persistent'`. Passing an ephemeral stream is a compile error, because there is nothing to continue.
- `lastKnownSeq` is the highest chunk `seq` you already have, so the server sends only the chunks after it. The handle does not show `seq`, but since `seq` starts at 1 and goes up by 1, it equals the number of chunks you already received. Leave `lastKnownSeq` out to get every chunk the server still holds.

```typescript [client/room.ts]
import { StreamAborted } from '@livething/core'
import { appendScoutText, askScoutAgain } from './huddle-ui'
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')
await room.subscribe({})

const savedStreamId = localStorage.getItem('scout-stream-id')
if (savedStreamId) {
  const continued = room.continueStream('ask-scout', savedStreamId)
  try {
    for await (const chunk of continued) {
      appendScoutText(chunk.text)
    }
  } catch (err) {
    // An old or unknown ID ends up here, not at the continueStream() call.
    // err.detail.reason is 'not-found', 'expired' or 'interrupted'.
    if (StreamAborted.matches(err)) {
      askScoutAgain()
    } else {
      throw err
    }
  }
}
```

To reattach, save the stream ID while the stream runs: read it from `handle.streamId`, or [pin the stream ID](/client/streams/stream-handle#pinning-the-stream-id) yourself. After a reload, pass that ID to `continueStream`. See the [server abort reasons](/server/streams/config-and-lifecycle) for what each reason means.

## Auto-reconnect vs `continueStream`

Each one is for a different situation:

|           | Automatic reconnect                  | `continueStream()`                                          |
| --------- | ------------------------------------ | ----------------------------------------------------------- |
| When      | The same socket drops and reconnects | The handle is gone, after a reload or in another tab        |
| Your code | None. The loop keeps going           | Call `continueStream(event, id)` and iterate the new handle |
| Needs     | `reconnection()` + `keepalive()`     | A `streamId` you saved earlier                              |

## On a channel

With [`channels()`](/client/primitives/channels), a channel handle also has its own `continueStream(...)`. Use it to continue a durable stream that ran inside that room:

```typescript [client/room.ts]
import { appendScoutText } from './huddle-ui'
import { socket } from './socket'

const room = socket.channel('rooms', 'room:general')
await room.subscribe({})

const savedStreamId = localStorage.getItem('scout-stream-id')
if (savedStreamId) {
  const continued = room.continueStream('ask-scout', savedStreamId)
  for await (const chunk of continued) {
    appendScoutText(chunk.text)
  }
}
```
