A **durable** stream — one whose contract `kind` is `'persistent'` — survives a disconnect. The server keeps enough state that the stream can pick up where it left off. On the client this shows up two ways: it resumes **automatically** when the same socket reconnects, and you can **cold-resume** it by ID after a reload or in another tab.

## Automatic resume on reconnect

This is the part you don't write. A persistent stream re-attaches itself when the socket drops and reconnects — the **same `for await` loop keeps producing chunks**, picking up after the last one you saw. The gap is invisible in your code:

```typescript [app.ts]
// `ask-ai` is a persistent stream. If the socket drops mid-generation and
// reconnects, the loop simply keeps receiving — no reconnect handling here.
const answer = await socket.stream('ask-ai', { prompt })

for await (const chunk of answer) {
  appendToken(chunk.text)
}
markComplete()
```

### What it needs

Automatic resume only works if the socket can actually come back, and notice when it's dead:

- [`reconnection()`](/client/primitives/reconnection) — so a drop reconnects at all.
- [`keepalive()`](/client/primitives/keepalive) — so a *half-open* socket (one that died with no close frame) is noticed. A stream waits for its next chunk; without keepalive's pings, a half-open connection would leave the loop waiting forever. (In debug mode, a persistent stream running without keepalive warns.)

If reconnection is genuinely abandoned — the socket closed for good, or the close code is non-retryable — the stream can't resume, so the loop **throws `Disconnected`** instead of hanging.

## The sequence cursor

Resume is driven by a per-chunk **sequence number**. The client remembers the highest `seq` it has delivered; on resume it asks the server for everything after that, and the server replays only the missing chunks. Chunks you already saw are dropped by `seq`, so a chunk that arrives twice across the reconnect is never delivered to your loop twice.

While a resume is in flight, the client waits on a more generous deadline than the per-chunk timeout (a replayed buffer can take a moment) — at least 30 seconds, or your per-chunk `timeout` if you set it higher. If no resumed chunk ever arrives, that deadline ends the stream rather than letting it hang. The normal per-chunk timer only restarts once the first resumed chunk lands. Setting `timeout: 0` turns this deadline off along with the per-chunk timeout, so a resume that never lands then waits indefinitely.

::note
If the server hibernated and woke, it may tell a durable stream to resume itself. The client handles that for you — it re-sends the resume request and the chunks continue. Nothing changes in your loop.
::

## Cold resume with `resumeStream`

Automatic resume relies on the in-memory handle still being there. After a **page reload**, or in a **second tab**, that handle is gone — but the stream can still be running server-side. `resumeStream(event, streamId, options?)` re-attaches to it by ID:

```typescript [app.ts]
// after a reload — savedStreamId was persisted (e.g. in localStorage)
const resumed = socket.resumeStream('ask-ai', savedStreamId, { lastKnownSeq: 12 })

for await (const chunk of resumed) {
  appendToken(chunk.text)
}
```

A few things to note:

- It returns a **handle directly**, not a promise — you iterate it straight away.
- It **never rejects up front**, even for a stale or unknown `streamId`. That failure surfaces *inside* the loop instead: the `for await` throws `StreamAborted` (with reason `not-found`, `expired`, or `cursor-invalid`). This is the opposite shape from `socket.stream()`, whose promise rejects before you iterate — so always wrap a cold resume's loop in `try/catch`.
- It's **type-gated to persistent streams**: `resumeStream` only accepts a stream whose `kind` is `'persistent'`. Passing an ephemeral stream is a compile error — there's nothing to resume.
- `lastKnownSeq` is the highest chunk sequence you already have, so the server sends only what's after it. Leave it off to get whatever the server still holds.

```typescript [app.ts]
import { StreamAborted } from '@wskit/core'

const resumed = socket.resumeStream('ask-ai', savedStreamId)
try {
  for await (const chunk of resumed) appendToken(chunk.text)
} catch (err) {
  // a stale/unknown id lands here, not at the resumeStream() call
  if (StreamAborted.matches(err)) startFresh() // reason: 'not-found' | 'expired' | 'cursor-invalid'
  else throw err
}
```

This is why [pinning the stream ID](/client/streams/stream-handle#pinning-the-stream-id) matters: you save the ID while the stream runs, and after a reload you hand it to `resumeStream`. See the [server abort reasons](/server/streams/config-and-lifecycle) for what each reason means.

## Auto-resume vs `resumeStream`

They cover different situations — use the right one:

| | Automatic resume | `resumeStream()` |
|---|---|---|
| When | The same socket drops and reconnects | The handle is gone — a reload or another tab |
| Your code | Nothing — the loop keeps going | Call `resumeStream(event, id)` and iterate the new handle |
| Needs | `reconnection()` + `keepalive()` | A `streamId` you saved earlier |

## On a channel

A channel handle gains a scoped `resumeStream(...)` too, for resuming a durable stream that ran inside that room:

```typescript [app.ts]
const room = socket.channel('rooms', 'room-1')
await room.subscribe()

const resumed = room.resumeStream('history', savedStreamId)
for await (const item of resumed) render(item)
```
