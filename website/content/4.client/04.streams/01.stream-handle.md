`socket.stream(event, payload, options?)` starts a stream and returns a **promise for a handle**. The promise resolves once the server accepts the stream, and the handle is an async iterable you read chunk by chunk.

```typescript [app.ts]
const tokens = await socket.stream('ask-ai', { prompt: 'Explain WebSockets' })

for await (const chunk of tokens) {
  appendToken(chunk.text) // chunk is typed from the stream's `chunk`
}
// loop exits normally → the stream finished
```

## When the promise settles

The promise `stream(...)` returns is about _starting_ the stream, not finishing it:

- **Resolves** once the server confirms it accepted the stream — before any chunk.
- **Rejects** if the server refuses it up front. The usual reasons are a `streamId` already in use (`stream-id-collision`) or another stream already running for that event (`stream-already-active`) — **by default** a connection runs one stream per event name at a time. The server can lift that with `allowConcurrent: true` on the stream handler (see [server streams](/server/handlers/stream)), which drops the `stream-already-active` guard.
- **Rejects** with `Disconnected` if the socket isn't open and can't get there — on a non-lazy socket you haven't `connect()`ed, the call rejects at once; a lazy socket connects on first use.
- **Rejects** with `Timeout` if the server never confirms within the per-chunk timeout.
- **Rejects with a plain `TypeError`** — not a `WSKitError` — if the trigger payload can't be serialized (for example a circular reference). It fails locally before anything is sent, so `.matches()` won't catch this one; a `try/catch` will.

Started while the socket is still connecting, the trigger is held and sent the moment it opens — you don't have to wait for `open` yourself.

## Iterating

You read chunks with `for await`. The loop:

- **exits** when the server ends the stream — the `for await` simply finishes,
- **throws** on a terminal error or a per-chunk timeout — wrap it in `try/catch`,
- **cancels** the stream if you `break` or `return` out of it.

```typescript [app.ts]
try {
  for await (const chunk of tokens) {
    if (chunk.text === 'STOP') break // breaking cancels the stream for you
    appendToken(chunk.text)
  }
} catch (err) {
  // a terminal server error, or a per-chunk timeout
  showError(err)
}
```

A thrown error is a `WSKitError`. Narrow it with `.matches()` to tell the cases apart — a per-chunk timeout is `Timeout`, a terminal disconnect is `Disconnected`, and a server error is whatever your contract declared:

```typescript [app.ts]
import { Disconnected, Timeout } from '@wskit/client/errors'
import { QuotaExceeded } from '../server/errors'

try {
  for await (const chunk of tokens) appendToken(chunk.text)
} catch (err) {
  if (Timeout.matches(err)) showStalled()
  else if (Disconnected.matches(err)) showOffline()
  else if (QuotaExceeded.matches(err))
    showUpgrade(err.detail) // a typed server error
  else showError(err)
}
```

Chunks are queued in order and delivered to your loop one at a time; if a chunk arrives while your loop is busy, it waits its turn. There's **no client-side cap** on that queue — if the server produces far faster than your loop consumes, chunks pile up in memory. For a fast producer and a slow UI, do the heavy work outside the loop (or sample) so you keep up.

## The handle

```typescript [app.ts]
const tokens = await socket.stream('ask-ai', { prompt })

tokens.streamId // the id grouping this stream's chunks
tokens.active // whether it's still running
tokens.nudge('add-context', { context: 'be brief' }) // mid-stream message — see Nudges
tokens.cancel() // ask the server to stop; the loop exits without throwing
```

- **`streamId`** is the ID grouping this run's chunks. Pin it yourself with the third argument (below) or read the generated one here.
- **`active`** is `true` while the stream runs, `false` once it ends, errors, or is cancelled.
- **`nudge(...)`** sends a message into the running server generator — covered in [Nudges](/client/streams/nudges).
- **`cancel()`** asks the server to stop. The loop exits **without throwing** (unlike an error). After the stream has already finished, `cancel()` is a harmless no-op.

`cancel()` and `break` do the same thing — breaking out of the loop calls `cancel()` for you.

## The per-chunk timeout

`stream()` waits for the **next chunk**, not the whole stream. The clock resets on every chunk, so a long stream that keeps producing never times out; only a _gap_ longer than the limit does. On a timeout the loop throws `Timeout`.

```typescript [app.ts]
const socket = client<AiSocket>()(
  connect('wss://example.com/ws'),
  stream({
    timeout: 30_000, // wait for the next chunk; resets on each one (default: 30_000)
  }),
)
```

Set `timeout: 0` to turn the per-chunk timeout off entirely.

## Pinning the stream ID

By default each stream gets a generated ID. Pass `streamId` in the third argument to pin it — useful as a stable handle you can resume later, keyed to something meaningful like a conversation:

```typescript [app.ts]
const answer = await socket.stream(
  'ask-ai',
  { prompt },
  { streamId: 'conversation-42' },
)
```

A pinned `streamId` must be non-empty, at most **128 characters**, and not a reserved identifier. It's checked locally first, so an invalid one rejects the `stream()` promise with `ValidationFailed` before any frame reaches the server.

A pinned ID is what lets you [cold-resume](/client/streams/durable-and-resume) the same stream after a reload.

## On a channel

With [`channels()`](/client/primitives/channels), a channel handle gains the same `stream(...)`, scoped to that room and typed from its contract:

```typescript [app.ts]
const room = socket.channel('rooms', 'room-1')
await room.subscribe()

const feed = await room.stream('history', { limit: 50 })
for await (const item of feed) render(item)
```
